# How an Academy lesson is written

One file per module: `data/academy/lessons/<MODULE-ID>.md`. The app shows the title, level,
minutes and prerequisites from `curriculum.yaml`, so **the file has no H1** — it starts at `##`.

## The smooth-learning-curve rules (non-negotiable)

1. **Assume only what the prerequisites taught.** A module with no prerequisites assumes a
   beginner who can write a basic Java class and nothing more. Never use a term a prerequisite
   didn't introduce without defining it right there.
2. **Define every new term at first use**, in one plain sentence, before using it.
3. **Concrete before abstract.** Show a tiny example (a few lines, a real situation), *then* state
   the general rule.
4. **One new idea per section.** Short sections. If a section needs two new ideas, split it.
5. **Build on the last lesson.** Open with a 2–3 line recap of what the reader now knows and why
   this lesson is the natural next step.
6. **At most one analogy per concept**, and say where the analogy breaks.
7. **Say why before how.** Every mechanism starts with the problem it solves.
8. **Refer to other lessons by display code** (JAVA-JVM-2, SPRING-BOOT-6): the track's `code` in
   curriculum.yaml plus the lesson's position in that track. Never by internal id (A2, D6).
9. **Accurate over impressive.** No invented numbers, dates or company claims. If unsure, leave
   it out or say "roughly". Java code targets Java 21 and must compile.
10. **Interactive, not a wall of text.** One learner reads these alone, so every lesson makes him do
    something every few minutes (see "Interactive elements" below): predict before reading, click a
    quiz, watch the flow move, run the code, break it.

## Interactive elements

The app renders these inside lessons. A lesson (about 25 minutes) should have **at least**: a story
hook, 2 predict-then-reveal moments, 3–4 ```quiz blocks (one Check, one or two Apply, one Interview trap), 1 diagram (```mermaid) or animation
(```anim) wherever something moves or has structure, and a runnable or breakable lab.

- **Story hook** (in `## The problem`): a concrete incident or task in the second person ("It is
  9 pm and checkout is timing out..."), never a definition first.
- **Predict, then reveal:** a bold **Predict:** line before an explanation or a code result, then
  the answer in the next paragraph. Short; one question.
- **Quiz** (click-to-answer; exactly one correct option; every option has a `why`):

  ````markdown
  ```quiz
  {"question": "What does this print?", "level": "medium",
   "code": ["Integer a = 127, b = 127;", "System.out.println(a == b);"],
   "options": [
     {"text": "true", "correct": true, "why": "Integers from -128 to 127 are cached, so both refer to one object."},
     {"text": "false", "why": "That happens outside the cache range, e.g. with 128."}]}
  ```
  ````

  Wrong options are real misconceptions, not filler. `code` is optional (an array of lines).
  Every quiz has a `level` (shown as a badge), and a lesson's quizzes follow this mix:

  | `level` | Badge | Share | What it tests |
  |---|---|---|---|
  | `easy` | Check | about 30% (1 per lesson) | Did the idea land? Recall and understanding of what was just explained |
  | `medium` | Apply | about 45% (1–2 per lesson) | Use it: predict output, pick the right tool for a situation, spot the step that changes |
  | `hard` | Interview trap | about 25% (1 per lesson) | The follow-up interviewers use to separate depth from definitions: an edge case, a wrong-but-popular belief, "what breaks if..." |

  So a typical lesson has 3–4 quizzes: one Check, one or two Apply, one Interview trap. Hard quizzes
  must still be answerable from this lesson and its prerequisites, never trivia.
- **Diagram:** ```mermaid (flowchart, sequenceDiagram, classDiagram, stateDiagram-v2), following
  the Mermaid rules in docs/ANSWERS.md. Small: about 12 nodes at most.
- **Animation:** ```anim JSON (format in docs/ANSWERS.md, "Watch it"). A *flow* animation (`stages`
  plus frames with only `note` and `stage`) can be written by hand for a request path or lifecycle.
  An *algorithm* animation (arrays, grids, maps) must be generated by `tools/anim/build.py`.
- **Runnable code:** a complete Java 21 class with `public static void main` gets a Run button
  that opens it in the Playground. Prefer one runnable example per lesson.
- **Copy** buttons appear on every code block automatically.

Check every lesson with `cd frontend && node scripts/check-diagrams.mjs <file>`: it parses the
diagrams and validates quiz and animation JSON.

## Sections, in this order

```markdown
## Where we are
2–3 lines: what you already know (from the prerequisites) and what this lesson adds.

## The problem
The situation that makes this topic necessary. Concrete.

## <Concept sections — one idea each>
Predict → explanation → tiny example → the general rule, with a quiz or a diagram where it helps
(see "Interactive elements"). ```text blocks are still fine for small ASCII sketches.

## Lab (~10 min)
A small, runnable Java 21 exercise (or a design exercise for design topics): what to build,
starter code, what you should observe. For "break it" labs, say how to break it and what failure
to watch for.

## Gotchas
3–6 bullets. Each one: the trap, and how to avoid it. These become review cards.

## In interviews
The ways this is asked. Link bank questions that exist as [Title](#/q/slug) — only slugs listed
in the bank index. Then 1–2 typical follow-ups and what a strong answer contains.

## Explain it in 2 minutes
One prompt to answer out loud, plus the 4–6 points a good answer hits.

## Check yourself
3–5 questions. Then a `### Answers` subsection with short answers.

## Next
One line pointing at the module(s) this unlocks and why.
```

Length: roughly 1,200–2,200 words — about 25 minutes including the lab.
