## Where we are

In S2 you ran ShopKart on servlets: one long-lived process with a thread per request. It was fast, and sessions worked. You also saw the cost: shared fields race, and HTML mixed into Java (or Java mixed into JSP) leaves no clear place for anything. This lesson adds **structure**. Every request passes through a single entry point, and the code is split into model, view and controller.

## The problem

Imagine ShopKart with 30 servlets and 40 JSPs. Each servlet does everything itself: parses parameters, checks login, validates input, talks to the database, chooses a page, and handles errors in its own way. Asking "where is the login check?" gets "in about 25 places, slightly different in each." Adding audit logging to every request means editing 30 files. Some JSPs run SQL.

The application needs **one consistent pipeline** for every request and **a clear home for each kind of code**.

## The idea: Model–View–Controller

**MVC** splits an application into three roles. The idea comes from Smalltalk desktop GUIs in the late 1970s and was adapted to the web.

- **Model**: the data and business rules (an `Order`, "quantity must be positive"). It knows nothing about HTTP or HTML.
- **View**: renders the model as output, such as an HTML page. It contains no business logic.
- **Controller**: receives the input, calls the model, and *chooses* which view to show.

Example: for "create order", the controller reads `item` and `qty`, the model validates and stores the order, and the controller then picks the `orders` view (on success) or the `error` view, which renders the list or the message.

Rule: **controllers decide, models compute, views display.** Each piece of code should belong to exactly one of the three.

## The pattern: a front controller

The early Java form of this was called **"Model 2"**: a servlet acts as controller, plain Java classes form the model, and JSPs are the views. The key move was the **front controller**: **one** servlet receives *every* request and dispatches it to a small handler class.

```text
          every /orders/* request
browser ─────────────────────────► FrontController (one servlet)
                                      1. look up path in a mapping table
                                      2. call the Action (controller logic)
                                      3. Action returns a view name: "orders"
                                      4. view resolver renders "orders"
                                      5. one place for errors, logging, security
```

Because every request now passes through one place, cross-cutting work such as login checks, logging and error pages is written **once**.

Rule: **centralise the "how" of handling requests, and let each action contain only the "what".**

## The framework: Apache Struts

**Apache Struts** packaged this pattern for Java. Struts 1 appeared at Apache around 2000–2001 and became a standard choice in enterprise Java web apps of the 2000s. You configured it in XML: `struts-config.xml` mapped URLs to `Action` classes and named "forwards" to JSPs. An action looked roughly like this:

```java
// Struts 1 shape (historical; don't install it)
public class CreateOrderAction extends Action {
    public ActionForward execute(ActionMapping mapping, ActionForm form,
                                 HttpServletRequest request, HttpServletResponse response) {
        // ... read form, call model ...
        return mapping.findForward("success");    // a name mapped to a JSP in XML
    }
}
```

Two details from that signature come back later:

- Struts 1 actions, like servlets, were **single shared instances**, so instance fields had the same race problem as in S2.
- Every action **depended on the servlet API** (`HttpServletRequest`).

Struts 2, released in 2007, came from merging with another framework, WebWork. It created a new action object per request. Struts 1 was declared end-of-life in 2013.

## The new pain: XML sprawl and untestable actions

Structure arrived, and so did new problems:

1. **XML sprawl.** Every action, form and forward needed an XML entry. A large app ended up with thousands of lines of configuration that the compiler never checked. A typo in a class name only surfaced at runtime.
2. **Coupling to the servlet API.** An action that takes an `HttpServletRequest` can't be unit-tested without a container or a mock of a large interface.
3. **Inheritance lock-in.** Your classes had to `extend Action`, so your code was tied to the framework's class hierarchy.

The way out, in S4 and S5, is plain classes (**POJOs**) that don't extend framework classes, with the framework calling them. That is exactly what Spring MVC's `@Controller` methods are.

## Industry case: Equifax, 2017

Frameworks become part of your **attack surface**, meaning code an attacker can reach. In March 2017 a critical vulnerability in Apache Struts 2 was disclosed and patched: **CVE-2017-5638**. In Struts 2's Jakarta Multipart parser, a crafted `Content-Type` header could be evaluated as an **OGNL** expression (OGNL is the expression language Struts 2 uses internally), which let an attacker run commands on the server, known as *remote code execution*.

Equifax, the US credit bureau, had not patched a public-facing application that used Struts. Attackers got in through it in May 2017, and personal data on roughly 147 million people was exposed. The bug was in the framework, but the failure was in **patch discipline**: knowing which applications use which library versions, and updating them quickly.

Rule: **every dependency is code you are responsible for.** Track versions, scan for known CVEs, and have a fast way to ship a patch. This is also why the labs here never install end-of-life frameworks.

## Lab (~10 min)

**Build** your own front controller on embedded Tomcat, using the same Maven dependency as S2. Create `actions.properties` in the folder you run from (the project root in IntelliJ):

```properties
/orders/list=ShopKartMvc$ListOrdersAction
/orders/create=ShopKartMvc$CreateOrderAction
```

These names assume `ShopKartMvc` is in the default package. If you put it in a package, prefix the names with it, for example `shopkart.ShopKartMvc$ListOrdersAction`.

```java
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.File;
import java.io.FileReader;
import java.io.IOException;
import java.util.List;
import java.util.Map;
import java.util.Properties;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.CopyOnWriteArrayList;
import org.apache.catalina.Context;
import org.apache.catalina.startup.Tomcat;

public class ShopKartMvc {

    // ---- Model: plain data + a store (no HTTP here) ----
    record Order(String item, int qty) {}
    static final List<Order> ORDERS = new CopyOnWriteArrayList<>();

    // ---- Controller contract, Struts-1 style: tied to the servlet API ----
    interface Action {
        String execute(HttpServletRequest req, HttpServletResponse resp) throws Exception; // returns a view name
    }

    public static class ListOrdersAction implements Action {
        public String execute(HttpServletRequest req, HttpServletResponse resp) {
            req.setAttribute("orders", ORDERS);
            return "orders";
        }
    }

    public static class CreateOrderAction implements Action {
        public String execute(HttpServletRequest req, HttpServletResponse resp) {
            String item = req.getParameter("item");
            int qty = Integer.parseInt(req.getParameter("qty"));
            if (qty <= 0) { req.setAttribute("error", "qty must be positive"); return "error"; }
            ORDERS.add(new Order(item, qty));
            req.setAttribute("orders", ORDERS);
            return "orders";
        }
    }

    // ---- View resolver: view name -> renderer. (Real apps used JSP files.) ----
    static String render(String view, HttpServletRequest req) {
        return switch (view) {
            case "orders" -> {
                StringBuilder sb = new StringBuilder("<h1>Orders</h1><ul>");
                for (Object o : (List<?>) req.getAttribute("orders")) sb.append("<li>").append(o).append("</li>");
                yield sb.append("</ul>").toString();
            }
            case "error" -> "<h1>Error</h1><p>" + req.getAttribute("error") + "</p>";
            default -> throw new IllegalArgumentException("No view named " + view);
        };
    }

    // ---- The front controller: ONE servlet receives every request ----
    public static class FrontController extends HttpServlet {
        private final Map<String, Action> actions = new ConcurrentHashMap<>();

        @Override
        public void init() {
            try (FileReader reader = new FileReader("actions.properties")) {
                Properties mapping = new Properties();
                mapping.load(reader);
                for (String path : mapping.stringPropertyNames()) {
                    Class<?> type = Class.forName(mapping.getProperty(path));
                    actions.put(path, (Action) type.getDeclaredConstructor().newInstance());
                }
                System.out.println("Mapped actions: " + actions.keySet());
            } catch (Exception e) {
                throw new IllegalStateException("Bad actions.properties", e);
            }
        }

        @Override
        protected void service(HttpServletRequest req, HttpServletResponse resp) throws IOException {
            Action action = actions.get(req.getPathInfo() == null ? req.getServletPath() : req.getServletPath() + req.getPathInfo());
            if (action == null) { resp.sendError(404, "No action for " + req.getRequestURI()); return; }
            try {
                String view = action.execute(req, resp);          // 1. controller picks a view
                resp.setContentType("text/html");
                resp.getWriter().print(render(view, req));        // 2. view renders the model
            } catch (Exception e) {                               // 3. one place for error handling
                resp.sendError(500, e.getMessage());
            }
        }
    }

    public static void main(String[] args) throws Exception {
        Tomcat tomcat = new Tomcat();
        tomcat.setPort(8083);
        tomcat.getConnector();
        Context ctx = tomcat.addContext("", new File(".").getAbsolutePath());
        Tomcat.addServlet(ctx, "front", new FrontController());
        ctx.addServletMappingDecoded("/orders/*", "front");      // every /orders/... URL goes to one servlet
        tomcat.start();
        System.out.println("Try http://localhost:8083/orders/create?item=book&qty=2");
        tomcat.getServer().await();
    }
}
```

Try `/orders/create?item=book&qty=2`, `/orders/create?item=pen&qty=0` (error view) and `/orders/nope` (404 from the single front controller). Add a line that logs every request inside `service()`, and notice that it covers *all* actions at once.

**Break.**

1. Imagine 15 more actions: that means 15 more classes and 15 more mapping lines. Mistype one class name in `actions.properties` and restart. The app compiles fine and fails only at start-up. That is the XML sprawl problem in miniature.
2. Try to write a unit test for `CreateOrderAction` in a plain `main`. You need an `HttpServletRequest`, an interface with dozens of methods. You either implement them all or bring in a mocking library.

**Overcome.** Change the contract so actions take plain data and return plain data:

```java
record ModelAndView(String view, Map<String, Object> model) {}

interface PojoAction {                                   // no servlet types anywhere
    ModelAndView execute(Map<String, String> params);
}
```

Now `new CreateOrderAction().execute(Map.of("item", "book", "qty", "2"))` can be tested in a plain `main` with no container. The front controller converts the request into a `Map` and the `ModelAndView` into HTML. That is the shape Spring MVC adopted, and its class really is called `ModelAndView`.

**Debate (5 min, optional).** "It's 2017 and your 2012 app is on Struts 2. Patch, upgrade or rewrite?" Write three lines for each option covering cost, risk and time to safety, then pick one. A strong answer says *patch today* to close the hole, then plans the migration separately.

## Gotchas

- **Fat controllers.** Putting business rules in actions recreates the S2 mess one level down. Keep actions thin and move rules into the model or service classes.
- **Shared state in actions.** Singleton actions (as in Struts 1, and Spring controllers later) have the same race problem as servlets. Avoid mutable instance fields.
- **Configuration the compiler can't check.** Class names in XML or properties fail at runtime. Prefer type-checked configuration (annotations, Java config) and fail-fast start-up checks.
- **Framework types in your logic.** If your logic takes `HttpServletRequest`, it can only be tested with a container. Convert to plain types at the edge.
- **Unpatched frameworks.** A framework CVE is your CVE. Keep a dependency inventory, scan it, and make it possible to patch within days.

## In interviews

- [SOLID principles and dependency inversion](#/q/solid-principles): MVC is the single-responsibility principle applied to web requests.
- [Inheritance vs composition](#/q/inheritance-vs-composition): `extends Action` is the inheritance lock-in that POJO frameworks removed.
- [Preventing SQL Injection](#/q/sql-injection-prevention): input that crosses the controller boundary is untrusted, the same lesson as CVE-2017-5638.

Typical follow-ups:

- *"What is the front controller pattern? Where is it in Spring?"* A single entry point that handles cross-cutting concerns and dispatches to handlers. In Spring it is `DispatcherServlet`, with handler mappings, controllers and view resolvers playing the roles you just built.
- *"How would you stop an Equifax-style incident?"* A dependency inventory (SBOM), automated CVE scanning in CI, a fast patch-and-deploy path, a WAF as a stop-gap, and network segmentation so one compromised app can't reach everything.

## Explain it in 2 minutes

*"Explain MVC and the front controller, and what problem they solved for Java web apps."*

A good answer hits:

1. Before: each servlet or JSP mixed parsing, logic, data access and HTML, with cross-cutting code copied everywhere.
2. MVC separates **model** (data and rules), **view** (rendering) and **controller** (input and choosing the view).
3. The **front controller** is one servlet that receives every request, maps the path to an action, calls it and renders the chosen view. Cross-cutting concerns live there once.
4. Struts packaged this, at the cost of **XML sprawl**, **servlet-API coupling** and **inheritance from framework classes**, which made code hard to test.
5. The way forward was POJO actions that take plain inputs and return a model and view name, which is what Spring MVC does with `DispatcherServlet`.
6. Equifax 2017 (CVE-2017-5638): frameworks are attack surface, so patch discipline is part of architecture.

## Check yourself

1. In MVC, which part chooses the page to show?
2. What does the front controller give you that 30 separate servlets don't?
3. Why was a Struts 1 action hard to unit-test?
4. What was the root cause of the Equifax breach: a framework bug or an operations failure?

### Answers

1. The controller. It handles the input, calls the model and returns a view name.
2. A single place for routing and cross-cutting concerns (auth, logging, error handling) and a consistent pipeline for every request.
3. Its `execute` took servlet API objects (`HttpServletRequest`, `HttpServletResponse`), which need a container or mocks, and it had to extend a framework class.
4. Both, but the decisive failure was operational. A fix for CVE-2017-5638 was available in March 2017, and the vulnerable application was still unpatched when attackers got in that May.
