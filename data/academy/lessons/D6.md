## Where we are

From D3 you know that `@Transactional` is advice applied by a proxy: a call through the proxy
begins a transaction, and normal return commits it. This lesson goes below that annotation, into
what Hibernate does inside the transaction. That covers the persistence context, dirty checking,
flushing, lazy loading and the N+1 problem. Then we return to `@Transactional` itself, with
propagation, isolation and the rollback rules that surprise people.

## The problem

Three real symptoms, all from not knowing what Hibernate is doing:

- "I changed an entity's field and it was saved, even though I never called `save()`."
- "This endpoint runs 300 SQL queries to show one page."
- "`LazyInitializationException: could not initialize proxy - no Session`."

None of these is a bug in Hibernate. Each one follows directly from a single mechanism: the
persistence context.

## JPA, Hibernate, Spring Data: who is who

- **JPA** (`jakarta.persistence`) is the *specification*: annotations such as `@Entity` and
  `@OneToMany`, plus the `EntityManager` API.
- **Hibernate** is the *implementation* that generates and runs the SQL.
- **Spring Data JPA** generates repository classes (`JpaRepository`) that call the
  `EntityManager` for you.

An **entity** is a class mapped to a table. In this repo, `Question` has a `@OneToMany` list of
`Sighting`s, and each `Sighting` has a `@ManyToOne(fetch = LAZY)` back to its `Question`.

## The persistence context: a per-transaction identity map

The **persistence context** is a map from *entity id* to *managed object* that the
`EntityManager` keeps for the life of a transaction. An entity in it is **managed**. Once the
context closes, the entity becomes **detached**: a plain object that Hibernate no longer
watches.

Concretely, inside one transaction:

```java
Question q     = questions.findAllWithSightings().get(0);
Question again = questions.findById(q.getSlug()).orElseThrow();   // no SELECT is run
System.out.println(q == again);                                   // true: same object
```

The rule: **within one persistence context, one database row is one Java object**, and asking
for it again is served from the map. This is also called the *first-level cache*.

## Dirty checking: why you didn't need `save()`

When Hibernate loads a managed entity, it keeps a **snapshot** of its field values. At flush
time, it compares each managed entity with its snapshot and writes an `UPDATE` for every one
that changed. This is **dirty checking**.

```java
@Transactional
public void rename(String slug, String title) {
    questions.findById(slug).orElseThrow().setTitle(title);   // no save(): an UPDATE still runs
}
```

The flip side is that **any change to a managed entity is persisted**, even one you only meant
for display. Map to a DTO before you modify anything for the view, or use
`@Transactional(readOnly = true)`, which tells Hibernate to skip dirty checking for that
transaction.

## Flush is not commit

**Flush** means "send the pending SQL (INSERT/UPDATE/DELETE) to the database *now*". **Commit**
means "make it permanent". A flush happens:

1. just before commit;
2. before a query whose results the pending changes could affect (the default `AUTO` flush
   mode);
3. when you call `em.flush()`.

After a flush and before the commit, other transactions still cannot see your rows (with the
usual isolation levels), and a rollback still undoes them.

This repo has a real use for an explicit flush. In `DataImporter.importAll()`, the bulk deletes
run, then `em.flush(); em.clear();`, and only then the new rows are saved. The comment explains
that the flush stops Hibernate from ordering the replacement inserts ahead of the deletes, which
would collide on the same ids. `clear()` empties the persistence context so that no stale
managed objects linger.

## Lazy loading

A **lazy** association is loaded only when you first touch it. Until then, Hibernate leaves a
placeholder: a proxy for a `@ManyToOne`, or an uninitialised collection wrapper for a
`@OneToMany`.

| Mapping | JPA default fetch |
|---|---|
| `@OneToMany`, `@ManyToMany` | `LAZY` |
| `@ManyToOne`, `@OneToOne` | **`EAGER`** (set it to `LAZY` explicitly, as `Sighting` does) |

The placeholder can only load data while its persistence context is open. Touch it after the
transaction has ended and you get **`LazyInitializationException`**. This repo sets
`spring.jpa.open-in-view: false` in `application.yml`, which turns off Boot's "keep the session
open until the view renders" behaviour. So every service method must load what it needs inside
its own `@Transactional` boundary. That is a deliberate and healthy choice.

## N+1: see it, then fix it

Load a list of N parents, then touch a lazy collection on each one. The result is 1 query for
the list plus 1 query per parent. This is the **N+1 problem**.

Here is the SQL log from this repo, with `spring.jpa.show-sql=true`, after `findAll()` and then
`q.getSightings().size()` on three questions:

```text
select q1_0.slug,q1_0.academy,...,q1_0.type from question q1_0
select s1_0.question_slug,s1_0.id,... from sighting s1_0 where s1_0.question_slug=? order by s1_0.seen_on desc
select s1_0.question_slug,s1_0.id,... from sighting s1_0 where s1_0.question_slug=? order by s1_0.seen_on desc
select s1_0.question_slug,s1_0.id,... from sighting s1_0 where s1_0.question_slug=? order by s1_0.seen_on desc
```

`BankService.questions()` touches every question's sightings. With the whole bank, which is
roughly 300 questions, that would be roughly 300 extra round trips. This is why the repo's
`QuestionRepository` has:

```java
@Query("select distinct q from Question q left join fetch q.sightings")
List<Question> findAllWithSightings();
```

and the log then shows **one** query:

```text
select distinct q1_0.slug,...,s1_0.question_slug,s1_0.id,s1_0.company,... from question q1_0 left join sighting s1_0 on q1_0.slug=s1_0.question_slug
```

The fixes, with when to use each:

- **`join fetch` in JPQL**, or **`@EntityGraph(attributePaths = "sightings")`** on a repository
  method: load the association in the same query. This is the usual fix.
- **Batch fetching** (`spring.jpa.properties.hibernate.default_batch_fetch_size=50`, or
  `@BatchSize`): lazy loads are grouped into `where ... in (?, ?, ...)`, giving 1 + N/50
  queries. Use it when a join would multiply rows too much.
- **A DTO projection query**: select only the columns the screen needs. This is often the
  fastest for read-only lists.

How to spot N+1 in the first place: turn on SQL logging in development and look for the same
statement repeated with different parameters.

## `@Transactional`: propagation

**Propagation** decides what happens when a transactional method is called while a transaction
already exists:

| Propagation | Existing transaction? | None? |
|---|---|---|
| `REQUIRED` (default) | join it | start one |
| `REQUIRES_NEW` | **suspend it**, start a separate one | start one |
| `NESTED` | savepoint inside it (JDBC transaction managers only) | start one |
| `SUPPORTS` | join | run without |
| `MANDATORY` | join | throw |
| `NOT_SUPPORTED` | suspend, run without | run without |
| `NEVER` | throw | run without |

The common use of `REQUIRES_NEW` is an audit or outbox row that must commit even if the caller
rolls back. Remember D3: propagation is applied by the proxy, so a self-invoked `REQUIRES_NEW`
method silently joins the outer transaction instead.

## Isolation

**Isolation** decides what concurrent transactions can see of each other:

| Level | Prevents | Still allows |
|---|---|---|
| `READ_UNCOMMITTED` | — | dirty reads |
| `READ_COMMITTED` | dirty reads | non-repeatable reads, phantoms |
| `REPEATABLE_READ` | + non-repeatable reads | phantoms (by the SQL standard; databases differ) |
| `SERIALIZABLE` | all three | — (pays with locking or aborts) |

`Isolation.DEFAULT` means "use the database's default": `READ_COMMITTED` on PostgreSQL, and
`REPEATABLE_READ` on MySQL InnoDB. For lost updates (two users editing the same row), the usual
answer is not a higher isolation level. Use **optimistic locking**: add a `@Version` column, and
the second writer fails with an optimistic-lock exception.

## Rollback rules: checked exceptions commit

By default, Spring rolls back on **`RuntimeException` and `Error`** only. A **checked exception
thrown from a `@Transactional` method commits the transaction.**

```java
@Transactional
public void renameThenFail(String slug) throws Exception {
    questions.findById(slug).orElseThrow().setTitle("RENAMED");
    throw new Exception("checked failure");      // the UPDATE is still committed
}
```

There are three ways to fix this:

- per method, with `@Transactional(rollbackFor = Exception.class)`;
- application-wide, from Spring Framework 6.2 onwards, with
  `@EnableTransactionManagement(rollbackOn = RollbackOn.ALL_EXCEPTIONS)`;
- or, simplest, throw unchecked exceptions from your services.

A related trap: an inner `REQUIRED` method throws a `RuntimeException`, which marks the *shared*
transaction rollback-only. If the outer method catches the exception and carries on, the commit
then fails with `UnexpectedRollbackException`.

## Lab (~10 min)

Add this lab-only test as `src/test/java/com/companywiseprep/bank/JpaLabTest.java` and run
`./mvnw test -Dtest=JpaLabTest`. It uses an in-memory H2 database, so your real progress data is
untouched.

```java
package com.companywiseprep.bank;

import static org.junit.jupiter.api.Assertions.assertThrows;

import org.hibernate.LazyInitializationException;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.context.TestConfiguration;
import org.springframework.context.annotation.Bean;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.support.TransactionTemplate;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.NONE, properties = {
        "spring.datasource.url=jdbc:h2:mem:jpalab",
        "spring.jpa.show-sql=true",
        "logging.level.root=WARN" })
class JpaLabTest {

    @Autowired QuestionRepository questions;
    @Autowired TransactionTemplate tx;
    @Autowired LabService lab;

    @Test
    void nPlusOne() {
        tx.executeWithoutResult(s -> {
            System.out.println("---- findAll(), then touch the sightings of 3 questions");
            questions.findAll().stream().limit(3).forEach(q -> q.getSightings().size());
            System.out.println("---- findAllWithSightings() (join fetch)");
            questions.findAllWithSightings().stream().limit(3).forEach(q -> q.getSightings().size());
        });
    }

    @Test
    void persistenceContextAndDirtyChecking() {
        tx.executeWithoutResult(s -> {
            Question q = questions.findAllWithSightings().get(0);
            System.out.println("---- findById for an id already in the persistence context");
            Question again = questions.findById(q.getSlug()).orElseThrow();
            System.out.println("same instance? " + (q == again));
            q.setTitle(q.getTitle() + " (edited)");            // note: no save() call
            System.out.println("---- end of transaction: flush, then commit");
        });
    }

    @Test
    void lazyLoadingOutsideTransaction() {
        Question q = tx.execute(s -> questions.findAll().get(0));   // transaction over, context closed
        assertThrows(LazyInitializationException.class, () -> q.getSightings().size());
    }

    @Test
    void rollbackRules() {
        String slug = tx.execute(s -> questions.findAll().get(0).getSlug());
        assertThrows(IllegalStateException.class, () -> lab.renameThenFailUnchecked(slug));
        System.out.println("after RuntimeException, title = " + titleOf(slug));
        assertThrows(Exception.class, () -> lab.renameThenFailChecked(slug));
        System.out.println("after checked Exception, title = " + titleOf(slug));
    }

    private String titleOf(String slug) {
        return tx.execute(s -> questions.findById(slug).orElseThrow().getTitle());
    }

    @TestConfiguration
    static class Config {
        @Bean
        LabService labService(QuestionRepository questions) { return new LabService(questions); }
    }

    static class LabService {
        private final QuestionRepository questions;

        LabService(QuestionRepository questions) { this.questions = questions; }

        @Transactional
        public void renameThenFailUnchecked(String slug) {
            questions.findById(slug).orElseThrow().setTitle("RENAMED (unchecked)");
            throw new IllegalStateException("unchecked failure");
        }

        @Transactional
        public void renameThenFailChecked(String slug) throws Exception {
            questions.findById(slug).orElseThrow().setTitle("RENAMED (checked)");
            throw new Exception("checked failure");
        }
    }
}
```

What you should see in the output (checked on this repo with Boot 4):

- **nPlusOne:** one `select ... from question`, then three `select ... from sighting ... where
  question_slug=?`. After the second marker there is a **single** `left join` query.
- **persistenceContextAndDirtyChecking:** `same instance? true`, with **no** SELECT for
  `findById`, then an `update question set ...` after the last marker, without any `save()`.
- **lazyLoadingOutsideTransaction:** passes, because the exception was thrown.
- **rollbackRules:** after the `RuntimeException` the title is unchanged, and no UPDATE was
  sent. After the checked `Exception` an `update question ...` is logged and the title is
  **`RENAMED (checked)`**: the transaction committed. Add `rollbackFor = Exception.class` and
  run it again to see the title stay unchanged.

Delete the test file when you are done.

## Gotchas

- **Modifying a managed entity persists the change, with or without `save()`.** Map to DTOs
  before changing anything for display, and use `readOnly = true` for read paths.
- **Checked exceptions commit by default.** Use `rollbackFor`, the Spring 6.2+ `rollbackOn`
  setting, or unchecked exceptions.
- **N+1 hides behind innocent getters.** Keep `show-sql` (or a SQL logger) on in development, and
  fix it with `join fetch`, `@EntityGraph` or batch fetching.
- **`join fetch` combined with paging over a collection** makes Hibernate paginate in memory,
  and it logs a warning. Page over the ids first, or use batch fetching.
- **`save()` on an entity with an assigned id runs a SELECT first.** Spring Data cannot tell
  whether the entity is new, so it calls `merge`. In this repo, `companies.saveAll(...)` during
  the import logs one `select ... from company where slug=?` per company before the inserts.
  Implementing `Persistable` or adding a `@Version` field avoids it.
- **`LazyInitializationException` means the transaction boundary is in the wrong place.** Don't
  turn on open-in-view as a fix. Load what you need inside the service transaction.

## In interviews

This is asked as "What is the N+1 problem and how do you fix it?", "Explain the persistence
context and dirty checking", "Does a checked exception roll back?" and "`REQUIRED` vs
`REQUIRES_NEW`?"

- [Connection Pooling and the DB Connection Process](#/q/jdbc-connection-pooling): a
  transaction holds one pooled connection from begin to commit. That is why long transactions
  and N+1 inside them exhaust the pool.
- [Code review: Java/SQL connection snippet](#/q/review-jdbc-connection-code): resource
  handling, injection risks and transactions are what JPA and Spring manage for you.
- [Preventing SQL Injection](#/q/sql-injection-prevention): JPQL with bound parameters
  (`:slug`) is parameterised. String-built queries are not.
- [Indexes, Partitioning and Sharding](#/q/db-indexing-partitioning-sharding): N+1 queries on
  an unindexed foreign key are doubly slow.

Typical follow-ups:

- *"How do you detect N+1 in production?"* Look at SQL counts per request in tracing or metrics,
  and at a slow-query log full of identical statements. Hibernate statistics help too.
- *"How do you prevent lost updates?"* Optimistic locking with `@Version`, retrying on
  conflict, or pessimistic locks (`SELECT ... FOR UPDATE`) for short, contended rows.

## Explain it in 2 minutes

*"What happens between `@Transactional` begin and commit in a JPA app?"*

- The transaction opens a persistence context: an identity map of managed entities with
  snapshots.
- Reads go through it (the same id gives the same object), and lazy associations load on first
  access while it is open.
- Before commit, or before an affected query, Hibernate flushes: it dirty-checks against the
  snapshots and sends the INSERT/UPDATE/DELETE statements.
- Commit makes the changes permanent. Rollback happens on `RuntimeException`/`Error`, but **not**
  on checked exceptions unless configured.
- Lazy loops cause N+1. Fix them with `join fetch`, entity graphs or batch fetching.
- Propagation decides join versus new transaction, and isolation decides what concurrent
  readers see.

## Check yourself

1. Why does changing a field on a loaded entity produce an UPDATE without `save()`?
2. What is the difference between flush and commit?
3. A method throws `IOException` from inside `@Transactional`. Is the transaction rolled back?
4. `findAll()` followed by `getSightings()` in a loop issues 301 queries. Name two fixes.
5. When would you use `REQUIRES_NEW`?

### Answers

1. The entity is managed. At flush, dirty checking compares it with its snapshot and writes the
   difference.
2. Flush sends the SQL within the open transaction, so it can still be rolled back. Commit makes
   it permanent and visible to others.
3. No, it commits by default. Use `rollbackFor = Exception.class`, or the 6.2+ `rollbackOn`.
4. A `join fetch` query (or `@EntityGraph`), or batch fetching
   (`default_batch_fetch_size`). A DTO projection is a third option.
5. When work must commit independently of the caller's outcome, such as audit or outbox
   records. Call it through another bean so that the proxy applies.
