## Where we are

From C1 you can count operations and state Big-O for loops. But some operations don't have one
fixed cost: `ArrayList.add` is usually instant and occasionally copies the whole list. This lesson
gives you the tool for describing such operations honestly. It's called **amortised analysis**, and
you'll use it to defend three structures that interviewers love: dynamic arrays, monotonic stacks
and union-find.

## The problem

You write this and the interviewer asks, "What's the complexity?"

```java
List<Integer> list = new ArrayList<>();
for (int i = 0; i < n; i++) list.add(i);
```

If you say "add is O(1), so O(n)", they ask: "But add sometimes copies the whole array. Isn't that
O(n) per add, so O(n²)?" Both statements sound reasonable. You need a precise way to say why the
answer is O(n).

## A dynamic array, from scratch

An `ArrayList` keeps its elements in a plain Java array with some spare room. The array's length is
the **capacity**. The number of elements actually stored is the **size**.

```text
capacity 4:  [ 7 | 3 | 9 | _ ]   size 3 → add(5) is one write: O(1)
capacity 4:  [ 7 | 3 | 9 | 5 ]   size 4 → add(8): array is full
             allocate a bigger array, copy all 4 elements, then write 8
capacity 6:  [ 7 | 3 | 9 | 5 | 8 | _ ]                     ← that add cost 5 writes
```

In OpenJDK the new capacity is about 1.5× the old one. The exact factor doesn't matter for this
lesson, only that it **multiplies** rather than adds a fixed amount.

## Amortised cost: total ÷ count

**Amortised cost** is the total cost of a whole sequence of operations, divided by the number of
operations, in the worst case for that sequence. It's a guarantee about the sequence, not about any
single call.

Let's count element copies for n adds with a growth factor of 2 (the arithmetic is cleaner, and 1.5
works the same way):

```text
resize at size:   1    2    4    8   ...   n/2
copies:           1 +  2 +  4 +  8 + ... + n/2   <  n
```

Doubling sums form a **geometric series**: each term is half the next, so the whole sum is less than
the last term doubled. Total work for n adds is n writes plus fewer than n copies, which is under 2n.
Divide by n and you get under 2 per add: **amortised O(1)**. (With a factor of 1.5 the bound is
about 3 per add. Still a constant.)

So the honest answer is: **"Each `add` is amortised O(1), worst case O(n) for a single call, so n
adds are O(n) total."**

## Amortised is not "average"

These two words get confused, so be precise:

- **Average-case** assumes something about the input being random, for example "HashMap get is O(1)
  on average, assuming a good hash spread".
- **Amortised** assumes nothing random. Even the worst possible sequence of n adds costs O(n) total.

One analogy: amortised cost is like a monthly budget for an annual insurance bill. Each month you
"pay" a little, so the big bill is always covered. Where it breaks: the real bill still arrives on
one day. In a latency-sensitive system, the single slow call (a big resize, a long pause) still
happens. That's why, when you know the final size, you pre-size with `new ArrayList<>(n)` or
`new HashMap<>(capacity)`.

## Why growth must be multiplicative

What if the array grew by a fixed 10 slots each time instead?

```text
resize at size: 10, 20, 30, ..., n   → copies 10 + 20 + ... + n ≈ n² / 20
```

That's O(n²) total, or O(n) amortised per add. The general rule: **amortised O(1) append needs
geometric growth.** The same reasoning is why `HashMap` doubles its table when it resizes, which
keeps `put` amortised O(1).

## Monotonic stack: the inner loop that isn't quadratic

**Problem:** for each element, find the next element to its right that is greater ("next greater
element"). The brute force scans right from every index, which is O(n²).

A **monotonic stack** is a stack whose contents are kept in sorted order (here, decreasing values
from bottom to top) by popping anything that would break the order before pushing.

```java
static int[] nextGreater(int[] a) {
    int[] ans = new int[a.length];
    java.util.Arrays.fill(ans, -1);
    Deque<Integer> stack = new ArrayDeque<>();        // holds indices, values decreasing
    for (int i = 0; i < a.length; i++) {
        while (!stack.isEmpty() && a[stack.peek()] < a[i]) {
            ans[stack.pop()] = a[i];                   // a[i] is the next greater for that index
        }
        stack.push(i);
    }
    return ans;
}
```

A `while` inside a `for` looks like O(n²). But count differently: **each index is pushed exactly
once and popped at most once.** Over the whole run there are at most n pushes and n pops, so the
total work is at most 2n: O(n) total, amortised O(1) per element, even though a single iteration
might pop many items.

This argument, "charge the work to the element, not to the loop", is the **aggregate method** of
amortised analysis. It's the most useful one to say out loud in interviews.

The same reasoning covers the **monotonic deque** in Sliding Window Maximum, where each index enters
and leaves the deque at most once, and the stack solution to Trapping Rain Water.

## Union-find: almost constant, amortised

**Union-find** (also called **disjoint set union**, DSU) tracks which items are in the same group.
It supports `union(a, b)` to merge two groups and `find(a)` to name a's group. Each item points to a
parent, and the item at the top of the chain (the root) names the group.

```java
static int[] parent, size;

static int find(int x) {
    while (parent[x] != x) {
        parent[x] = parent[parent[x]];   // path halving: point to grandparent as we climb
        x = parent[x];
    }
    return x;
}

static boolean union(int a, int b) {
    int ra = find(a), rb = find(b);
    if (ra == rb) return false;          // already in the same group
    if (size[ra] < size[rb]) { int t = ra; ra = rb; rb = t; }
    parent[rb] = ra;                     // union by size: small tree under big tree
    size[ra] += size[rb];
    return true;
}
```

Two tricks keep the trees flat:

- **Union by size:** hang the smaller tree under the larger, so a tree of n items has height at
  most about log₂ n.
- **Path compression** (here, the halving variant): while climbing, re-point nodes closer to the
  root, so later finds are shorter.

A single `find` can still walk a long chain once. But with both tricks, any sequence of m operations
on n items costs O(m · α(n)), where **α is the inverse Ackermann function**, which grows so slowly
that it is at most 4 for any input size you could store. In an interview, say: **"amortised nearly
constant, O(α(n)) per operation"**. Don't claim "O(1) worst case".

## Lab (~10 min)

Count the copies that different growth policies cause, so you see the geometric series yourself.

```java
public class GrowthPolicyLab {

    interface Policy { int grow(int capacity); }

    static long copiesFor(int n, Policy policy) {
        int[] data = new int[1];
        int size = 0;
        long copies = 0;
        for (int i = 0; i < n; i++) {
            if (size == data.length) {
                int[] bigger = new int[policy.grow(data.length)];
                System.arraycopy(data, 0, bigger, 0, size);
                copies += size;
                data = bigger;
            }
            data[size++] = i;
        }
        return copies;
    }

    public static void main(String[] args) {
        Policy doubling = c -> c * 2;
        Policy oneAndHalf = c -> c + Math.max(1, c >> 1);   // roughly what ArrayList does
        Policy plusTen = c -> c + 10;                        // fixed-step growth

        System.out.printf("%10s %14s %14s %16s%n", "n", "x2 copies/n", "x1.5 copies/n", "+10 copies/n");
        for (int n = 1_000; n <= 1_000_000; n *= 10) {
            System.out.printf("%10d %14.2f %14.2f %16.1f%n", n,
                    copiesFor(n, doubling) / (double) n,
                    copiesFor(n, oneAndHalf) / (double) n,
                    copiesFor(n, plusTen) / (double) n);
        }
    }
}
```

Run it with `java GrowthPolicyLab.java`.

**What to observe:** the ×2 and ×1.5 columns stay flat (a small constant: amortised O(1)), while
the +10 column grows about 10× every time n does (O(n) per add, O(n²) total).

**Extension:** use the union-find above, but delete the path-halving line *and* the union-by-size
swap. Then call `union(i + 1, i)` for i = 0..n−2, which hangs the existing chain under each new
node and builds one long chain, and call `find(0)` n times. Time it at n = 10⁴ and 4 × 10⁴, and watch quadratic growth return.

## Gotchas

- **Trap: calling `ArrayList.add` "O(1)" without qualification.** Say "amortised O(1)". If pushed,
  the worst single call is O(n).
- **Trap: "while inside for = O(n²)" without checking.** Ask how many times each element can be
  pushed and popped *in total*. If it's once each, the total is O(n).
- **Trap: confusing amortised with average.** Amortised needs no randomness. HashMap's O(1) is
  average (it depends on hashing) *and* amortised (it depends on resizing).
- **Trap: union-find without union by size and path compression.** Without them, trees can
  degenerate into chains and `find` becomes O(n).
- **Trap: ignoring the spike when latency matters.** Pre-size collections when you know n. In
  systems answers, mention that resizes and rehashes cause latency spikes.

## In interviews

Amortised arguments are how you justify the complexity of these problems:

- [Sliding Window Maximum](#/q/sliding-window-maximum): a monotonic deque, O(n) total because each
  index enters and leaves once.
- [Trapping Rain Water](#/q/trapping-rain-water): has a monotonic stack solution, with the same

- [The earliest moment when everyone becomes friends](#/q/the-earliest-moment-when-everyone-become-friends):

- [Reachable Nodes per Query](#/q/connected-component-size-queries): union-find with component sizes.
- [Last Day Where You Can Still Cross](#/q/last-day-where-you-can-still-cross): union-find,
  adding cells in reverse.
- [Min Stack](#/q/min-stack) and [Insert Delete GetRandom O(1)](#/q/insert-delete-getrandom-o1):
  "O(1)" claims that rest on amortised dynamic arrays.

**Typical follow-up:** "You have a while loop inside a for loop. Why isn't this O(n²)?" A strong
answer counts pushes and pops over the whole run, concludes the total is at most 2n, and calls that
amortised O(1) per element.

## Explain it in 2 minutes

*"What does amortised O(1) mean for ArrayList.add?"*

A good answer covers:

1. Amortised means total cost ÷ number of operations, guaranteed for any sequence.
2. Most adds write one slot. When the array is full, it allocates a bigger one and copies everything.
3. Capacity grows geometrically (about 1.5× in OpenJDK), so total copies form a geometric series
   bounded by a constant × n.
4. Fixed-step growth would make it O(n²) total.
5. A single add can still be O(n), so pre-size when you know n and latency matters.

## Check yourself

1. What is amortised cost, in one sentence?
2. Why does growing by a factor give amortised O(1) but growing by a fixed step doesn't?
3. In the next-greater-element code, what is the maximum total number of pops across the whole run?
4. What are the two union-find optimisations, and what complexity do they give together?
5. How is amortised different from average-case?

### Answers

1. The worst-case total cost of a sequence of operations divided by the number of operations.
2. Factor growth makes total copies a geometric series (under a constant × n). Fixed steps make the
   copies an arithmetic series, about n²/step.
3. n, because each index is pushed once, so it can be popped at most once.
4. Union by size (or rank) and path compression: O(α(n)) amortised per operation, which is
   effectively constant.
5. Average-case assumes a random input or random hashing. Amortised holds for every sequence of
   operations, with no randomness.
