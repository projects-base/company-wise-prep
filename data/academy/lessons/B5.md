## Where we are

From B4 you can submit tasks to a pool and get a `Future` back. But `future.get()` blocks the calling thread until the result arrives, and a `Future` has no way to say "when this finishes, do that." This lesson covers `CompletableFuture`, which lets you describe a whole pipeline of async steps (fan out, combine, chain, recover, time out) without blocking a thread at every step.

## The problem

A product page needs a price, the stock level and reviews from three services, each taking about 300 ms. Here is how that looks with plain `Future`s:

```java
Future<String> p = pool.submit(() -> price(id));
Future<String> s = pool.submit(() -> stock(id));
String page = p.get() + s.get();    // main sits blocked; no fallback if one fails; no deadline
```

The calls do run in parallel, but the code that combines them is clumsy. Real flows also need more than this: "get the user, *then* get their orders", "if reviews fail, show a placeholder", "give up on recommendations after 500 ms". Writing all of that with `Future.get()` means a blocked thread at every step and a pile of `try`/`catch` blocks.

## A future you can attach steps to

A **`CompletableFuture<T>`** (CF) is a `Future` that can also run callbacks when it completes. Each callback produces a new CF, so you chain them into a pipeline. Each link in the chain is called a **stage**.

```java
CompletableFuture<String> price =
    CompletableFuture.supplyAsync(() -> price(42), ioPool);   // start async work on ioPool

CompletableFuture<Integer> rupees =
    price.thenApply(s -> Integer.parseInt(s.substring(6)));   // runs when price completes
```

- `supplyAsync(supplier, executor)` runs a task that returns a value. `runAsync(runnable, executor)` runs one that returns nothing.
- **If you leave out the executor, the task runs on `ForkJoinPool.commonPool()`.** As B4 explained, that pool is small and shared, so never put blocking I/O there. Always pass your own executor for I/O.

## Transforming: `thenApply`, `thenAccept`, `thenRun`

- `thenApply(fn)` takes the value and returns a new one: `T → U`. It is like `map` on a stream.
- `thenAccept(consumer)` takes the value and returns nothing. Use it for side effects such as writing a response.
- `thenRun(runnable)` ignores the value and just runs something next.

Which thread runs these callbacks? If the previous stage has **already completed** when you attach the callback, the thread that attaches it runs the callback immediately. Otherwise, the thread that **completes** the previous stage runs it. The `...Async` variants (`thenApplyAsync(fn, executor)`) always hand the callback to an executor. Use them when the callback is slow or blocking, so it does not hold up whichever thread happened to complete the previous stage.

## Chaining a dependent call: `thenCompose`

Suppose you need the user id before you can fetch that user's orders, and the fetch is itself async. If you use `thenApply` here, you get a future inside a future, `CompletableFuture<CompletableFuture<List<Order>>>`. `thenCompose` flattens it:

```java
CompletableFuture<List<String>> orders =
    findUserAsync("akhil")                         // CF<String>
        .thenCompose(id -> ordersOfAsync(id));     // fn returns CF<List<String>>, which is flattened
```

The rule: **use `thenApply` when the function returns a plain value, and `thenCompose` when it returns a CF.** (This is the same as `map` versus `flatMap`.)

## Combining independent calls: `thenCombine`, `allOf`, `anyOf`

- `a.thenCombine(b, (x, y) -> ...)` waits for both futures and merges their results.
- `CompletableFuture.allOf(f1, f2, f3)` completes when all of them do. It returns `CF<Void>`, so you read each result afterwards with `fN.join()`. That `join()` does not block, because every future has finished by then.
- `anyOf(...)` completes with the first result *or the first failure*.

```java
CompletableFuture.allOf(p, s, r)
    .thenApply(v -> p.join() + " | " + s.join() + " | " + r.join());
```

## Failures flow down the chain

If a stage throws, every later transforming stage is **skipped**, and the failure travels down the chain until something handles it:

- `exceptionally(ex -> fallback)` runs only on failure and replaces the failure with a value.
- `handle((value, ex) -> ...)` always runs and can turn either outcome into a new value.
- `whenComplete((value, ex) -> ...)` always runs, for side effects such as logging, and passes the original outcome through unchanged.

There are two wrapping details that interviewers like to check:

- The `ex` you receive is usually a **`CompletionException` wrapping the real exception**, so call `ex.getCause()` to get the original.
- `join()` throws an unchecked `CompletionException`. `get()` throws a checked `ExecutionException`. Both wrap the cause.

## Deadlines: `orTimeout` and `completeOnTimeout` (Java 9+)

- `orTimeout(500, MILLISECONDS)` fails the CF with a `TimeoutException` if it has not finished in time.
- `completeOnTimeout(defaultValue, 500, MILLISECONDS)` completes it with a default value instead.

Neither one **stops the underlying work**. The task keeps running and keeps using its thread. Calling `cancel(true)` on a `CompletableFuture` does not interrupt the running task either: the `true` argument is ignored. To really stop the work, the task has to watch for cancellation itself, or the call underneath it needs its own timeout (for example, an HTTP client timeout).

## Lab (~10 min)

Save this as `ProductPage.java` and run it with `java ProductPage.java`.

```java
import java.util.List;
import java.util.concurrent.*;

public class ProductPage {
    static final boolean REVIEWS_FAIL = true;   // flip to see the happy path
    static final ExecutorService IO = Executors.newFixedThreadPool(8, Thread.ofPlatform().name("io-", 0).factory());

    public static void main(String[] args) {
        try (IO) {
            // 1. Sequential: about 300 + 300 + 300 ms
            long t0 = System.nanoTime();
            String seq = price(42) + " | " + stock(42) + " | " + safeReviews(42);
            System.out.println("sequential " + ms(t0) + " ms: " + seq);

            // 2. Parallel fan-out, then combine: about 300 ms
            t0 = System.nanoTime();
            CompletableFuture<String> p = CompletableFuture.supplyAsync(() -> price(42), IO);
            CompletableFuture<String> s = CompletableFuture.supplyAsync(() -> stock(42), IO);
            CompletableFuture<String> r = CompletableFuture.supplyAsync(() -> reviews(42), IO)
                .exceptionally(ex -> {                                 // ex is a CompletionException
                    System.out.println("   reviews failed: " + ex.getCause().getMessage());
                    return "reviews unavailable";                      // fallback value
                });
            String page = CompletableFuture.allOf(p, s, r)
                .thenApply(v -> p.join() + " | " + s.join() + " | " + r.join())   // all done: join is instant
                .join();
            System.out.println("parallel   " + ms(t0) + " ms: " + page);

            // 3. Dependent calls: orders need the user first -> thenCompose
            t0 = System.nanoTime();
            List<String> orders = CompletableFuture.supplyAsync(() -> findUser("akhil"), IO)
                .thenCompose(userId -> CompletableFuture.supplyAsync(() -> ordersOf(userId), IO))
                .join();
            System.out.println("composed   " + ms(t0) + " ms: " + orders);

            // 4. A slow dependency with a deadline
            t0 = System.nanoTime();
            String rec = CompletableFuture.supplyAsync(() -> slowRecommendations(42), IO)
                .completeOnTimeout("no recommendations", 500, TimeUnit.MILLISECONDS)
                .join();
            System.out.println("deadline   " + ms(t0) + " ms: " + rec);
        }
    }

    // Fake remote calls
    static String price(int id)   { sleep(300); return "price=499"; }
    static String stock(int id)   { sleep(300); return "stock=7"; }
    static String reviews(int id) {
        sleep(300);
        if (REVIEWS_FAIL) throw new IllegalStateException("reviews service 500");
        return "rating=4.4";
    }
    static String safeReviews(int id) {
        try { return reviews(id); } catch (RuntimeException e) { return "reviews unavailable"; }
    }
    static String findUser(String name)         { sleep(200); return "u-17"; }
    static List<String> ordersOf(String userId) { sleep(200); return List.of("o-1", "o-2"); }
    static String slowRecommendations(int id)   { sleep(3_000); return "you may also like..."; }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
    static long ms(long t0) { return (System.nanoTime() - t0) / 1_000_000; }
}
```

What you should observe (timings will vary slightly):

```text
sequential ~900 ms: price=499 | stock=7 | reviews unavailable
   reviews failed: reviews service 500
parallel   ~300 ms: price=499 | stock=7 | reviews unavailable
composed   ~400 ms: [o-1, o-2]
deadline   ~500 ms: no recommendations
```

1. Running the three calls in parallel costs roughly as long as the slowest call, not the sum of all three.
2. The reviews failure became a fallback value. The page still rendered, and `ex.getCause()` gave you the original message.
3. `thenCompose` ran the two dependent calls back to back (200 + 200 ms).
4. **Watch the end:** the program lingers for about 2.5 seconds after the last line. `completeOnTimeout` answered the caller after 500 ms, but the 3-second task kept running, and `close()` waits for it. That is the "timeouts do not cancel work" gotcha, live.

**Break it:** remove the `, IO` argument from every `supplyAsync` call. The code still works, but now it is sleeping on the common pool. On a machine with few cores, the parallel step gets slower, because the common pool has only about cores − 1 threads. Then remove the `.exceptionally(...)` and watch `join()` throw `CompletionException`.

## Gotchas

- **No executor means the common pool.** Pass a dedicated executor for any blocking work.
- **`thenApply` with an async function** gives you `CF<CF<T>>`. Use `thenCompose`.
- **Unwrap the exception.** In `exceptionally` and `handle`, `ex` is often a `CompletionException`. Check `ex.getCause()`.
- **Timeouts and `cancel(true)` do not stop running work.** Add real timeouts to the underlying calls.
- **Calling `join()` in the middle of a pipeline** blocks a thread and throws away the benefit. Join once, at the edge (for example in a controller, or in a test).
- **Failures with nobody listening.** A CF that fails with no `exceptionally`, `handle` or `join` loses the error silently. End every chain with handling or logging.

## In interviews

[Implement a CompletableFuture-like primitive](#/q/design-completable-future) asks you to build one yourself. The core is a state (pending, value or failure), a list of callbacks, and a CAS or a lock on completion, so that callbacks run exactly once, whether they were attached before or after completion. It is the natural capstone for this lesson together with B3.

Typical follow-ups:

- **"`thenApply` vs `thenApplyAsync`?"** The non-async version runs on whichever thread completed the previous stage, or on the caller if it was already complete. The async version always runs on an executor. Use async when the callback is slow, or when you must not run on the completing thread (for example, a Netty event-loop thread).
- **"How do you call three services in parallel with a 1-second budget and a partial response?"** Start each with `supplyAsync` on an I/O executor, give each `completeOnTimeout(fallback)` or `exceptionally(fallback)`, combine them with `allOf`, and join once. Mention that the underlying clients need their own timeouts as well.

## Explain it in 2 minutes

*"How does `CompletableFuture` improve on `Future`?"*

- A `Future` can only be waited on. A CF can be completed, and has callbacks attached that run when it completes.
- `thenApply` maps a value, `thenCompose` chains a dependent async call, and `thenCombine` and `allOf` join independent calls.
- Failures skip transforming stages until `exceptionally` or `handle` deals with them. They arrive wrapped in a `CompletionException`.
- Callbacks run on the completing thread unless you use the `...Async` variants. The default executor is the common pool, so pass your own for I/O.
- `orTimeout` and `completeOnTimeout` set deadlines, but they do not cancel the underlying work.

## Check yourself

1. You have `CF<String> userId` and `String → CF<Order> fetchOrder`. Which method do you use to chain them?
2. `allOf(a, b, c)` completes. How do you get `a`'s value, and does it block?
3. In `exceptionally(ex -> ...)` after `supplyAsync` threw an `IllegalStateException`, what type is `ex`?
4. Does `cf.orTimeout(1, SECONDS)` stop the task after one second?
5. Which thread runs `cf.thenApply(fn)` if `cf` is already complete?

### Answers

1. `thenCompose(fetchOrder)`. Using `thenApply` would produce a `CF<CF<Order>>`.
2. `a.join()`. It returns at once, because `a` is already complete.
3. A `CompletionException` whose `getCause()` is the `IllegalStateException`.
4. No. It completes the CF exceptionally with a `TimeoutException`, and the task keeps running.
5. The thread that called `thenApply`. It runs immediately and synchronously.
