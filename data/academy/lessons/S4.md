## Where we are

You now have ShopKart structured as MVC behind a front controller (S3). But a real business app needs more than pages. It needs **transactions** (all-or-nothing database changes), **security** (who may call what), and often calls to code running **on other machines**. This lesson covers the enterprise answer of 1999–2006, **J2EE and EJB 2**: a heavyweight container that provided all of this, and the weight that eventually sank it.

## The problem

ShopKart's "place order" must do three things together: save the order, reduce stock, and charge the card. If the charge fails after stock was reduced, the stock has to be put back. That is a **transaction**: a group of operations that either all happen (*commit*) or none do (*rollback*).

Writing this by hand with JDBC in every service method looks like this:

```java
Connection c = dataSource.getConnection();
try {
    c.setAutoCommit(false);
    saveOrder(c, order);
    reduceStock(c, order);
    c.commit();
} catch (Exception e) {
    c.rollback();
    throw e;
} finally {
    c.close();
}
```

Repeat that in 200 methods and add security checks and logging to each, and the business logic disappears under plumbing. Banks and telecoms also wanted transactions that span **two databases**, plus calls to services on other servers, all with that same safety.

## The invention: a container that provides services

**J2EE** (Java 2 Platform, Enterprise Edition; version 1.2 shipped in late 1999) was a set of specifications. Vendors implemented them in **application servers**, large runtimes such as BEA WebLogic, IBM WebSphere and JBoss. Inside them ran **Enterprise JavaBeans (EJBs)**: components whose lifecycle and calls were managed by an **EJB container**.

The core idea was good, and it is still with us:

> You write the business method. The container wraps every call with **transactions, security, pooling and remoting**, configured **declaratively** (in a descriptor file), not coded by hand.

```text
client ──call──► [ container-generated stub/proxy ]
                    1. check security role
                    2. begin transaction (if the descriptor says "Required")
                    3. call YOUR bean method
                    4. commit, or roll back on a system exception
                ◄── result
```

Declarative means you state *what* you want ("this method requires a transaction") and the platform makes it happen.

## The kinds of beans

EJB 2.0 (2001) had three kinds:

- **Session beans** hold business logic. *Stateless* ones keep no per-client state and are pooled. *Stateful* ones keep conversation state for one client.
- **Entity beans** are persistent objects mapped to database rows. With *container-managed persistence (CMP)*, the container generated the SQL.
- **Message-driven beans** consume messages from a queue (JMS), which made them asynchronous workers.

## The shape of one EJB 2 service

Here is what one stateless "OrderService" needed. This is historical code: it won't compile without the old `javax.ejb` API, so read it rather than run it.

```java
// 1. Remote interface: what clients can call. Every method throws RemoteException.
public interface OrderService extends javax.ejb.EJBObject {
    void placeOrder(String item, int qty) throws java.rmi.RemoteException;
}

// 2. Home interface: a factory the client looks up to get an OrderService.
public interface OrderServiceHome extends javax.ejb.EJBHome {
    OrderService create() throws javax.ejb.CreateException, java.rmi.RemoteException;
}

// 3. Bean class: your logic, plus lifecycle callbacks the container requires.
public class OrderServiceBean implements javax.ejb.SessionBean {
    public void placeOrder(String item, int qty) { /* the actual business logic */ }
    public void ejbCreate() {}
    public void ejbActivate() {}
    public void ejbPassivate() {}
    public void ejbRemove() {}
    public void setSessionContext(javax.ejb.SessionContext ctx) {}
}
```

```xml
<!-- 4. ejb-jar.xml: the deployment descriptor wiring it together -->
<session>
  <ejb-name>OrderService</ejb-name>
  <home>shopkart.OrderServiceHome</home>
  <remote>shopkart.OrderService</remote>
  <ejb-class>shopkart.OrderServiceBean</ejb-class>
  <session-type>Stateless</session-type>
  <transaction-type>Container</transaction-type>
</session>
<!-- ...plus an assembly-descriptor with <trans-attribute>Required</trans-attribute> per method,
     plus a vendor-specific descriptor for WebLogic/WebSphere -->
```

```java
// 5. Client: look it up by name in JNDI, a directory service mapping names to objects.
InitialContext ctx = new InitialContext();
Object ref = ctx.lookup("java:comp/env/ejb/OrderService");
OrderServiceHome home = (OrderServiceHome) javax.rmi.PortableRemoteObject.narrow(ref, OrderServiceHome.class);
OrderService service = home.create();
service.placeOrder("book", 2);
```

That is five artefacts for **one method of business logic**, and the bean class implements the interface's methods without ever declaring `implements OrderService`. The container connected the two at deploy time.

## The new pain: weight

- **Untestable.** The bean only works inside a running application server. Testing meant packaging an archive, deploying it, and calling it remotely. Feedback took minutes instead of milliseconds.
- **Slow cycle.** Change a line, rebuild the EAR (enterprise archive), redeploy, and wait for the server.
- **Remote by default, slow by default.** Calls through remote interfaces crossed the network and copied every argument. Calling `getName()`, `getPrice()` and `getQty()` on a remote entity bean meant three network round-trips. Whole patterns existed only to work around this, collected in *Core J2EE Patterns* (2001): the **Value Object**, later renamed **Transfer Object** and today called a DTO (send one bulk object instead of many calls), the **Session Facade** (one coarse-grained call instead of many small ones), and the **Service Locator** (cache those JNDI lookups).
- **Framework lock-in.** Your classes implemented `SessionBean` and threw `RemoteException`, so the business logic could not exist outside the container.
- **Entity beans disappointed.** Many teams found CMP entity beans slow and restrictive and wrote JDBC by hand instead.

## Industry case: the standard copies the rebels

Through the early 2000s, banks, insurers and telecoms ran core systems on WebLogic and WebSphere. EJB 2's transactions and security were valuable to them. Its cost in productivity was obvious too, and alternatives grew outside the standard: the Spring Framework (S5) and the Hibernate ORM.

The standard then changed course. **EJB 3.0 (2006, part of Java EE 5)** made beans plain classes with annotations (`@Stateless`). It dropped the home interfaces, and it replaced entity beans with the **Java Persistence API (JPA)**, which was heavily influenced by Hibernate. Java EE later moved to the Eclipse Foundation and was renamed **Jakarta EE**, which is why S2's servlets import `jakarta.*`.

The lesson for architects: **when a standard is much heavier than its alternatives, the alternatives win, and the standard ends up adopting their ideas.**

## Lab (~10 min)

**Part 1: Build (write, don't run).** Using the shape above, write the EJB 2 version of `OrderService` with a second method, `cancelOrder(long id)`. Count the files and lines. Then count what one plain class needs.

**Part 2: Break, then keep the good idea.** EJB's real insight was **intercepting calls to add services**. You can reproduce it with only the JDK. A `java.lang.reflect.Proxy` is an object the JDK generates at runtime that implements an interface and sends every call to a handler you write. Save this as `MiniContainer.java` and run `java MiniContainer.java`:

```java
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Proxy;
import java.util.Map;

public class MiniContainer {

    // The business interface and a plain class: no container types at all.
    interface OrderService {
        void placeOrder(String item, int qty);
        int countOrders();
    }

    static class OrderServiceImpl implements OrderService {
        private int orders = 0;
        public void placeOrder(String item, int qty) {
            if (qty <= 0) throw new IllegalArgumentException("qty must be positive");
            orders++;
            System.out.println("  business logic: stored " + qty + " x " + item);
        }
        public int countOrders() { return orders; }
    }

    // Our "deployment descriptor": transaction attribute per method, outside the code.
    static final Map<String, String> TX_ATTRIBUTES = Map.of(
            "placeOrder", "Required",
            "countOrders", "Supports");

    // The "container": hands out a proxy that wraps every call with a service.
    @SuppressWarnings("unchecked")
    static <T> T deploy(Class<T> businessInterface, T bean) {
        return (T) Proxy.newProxyInstance(
                businessInterface.getClassLoader(),
                new Class<?>[] {businessInterface},
                (proxy, method, args) -> {
                    boolean tx = "Required".equals(TX_ATTRIBUTES.get(method.getName()));
                    if (tx) System.out.println("[container] BEGIN transaction for " + method.getName());
                    try {
                        Object result = method.invoke(bean, args);
                        if (tx) System.out.println("[container] COMMIT");
                        return result;
                    } catch (InvocationTargetException e) {
                        if (tx) System.out.println("[container] ROLLBACK because " + e.getCause().getMessage());
                        throw e.getCause();
                    }
                });
    }

    public static void main(String[] args) {
        // 1. Testable without any container: just a class.
        OrderService plain = new OrderServiceImpl();
        plain.placeOrder("book", 1);
        System.out.println("plain object works in main(): " + plain.countOrders() + " order(s)\n");

        // 2. Same class, "deployed": the caller gets a proxy that adds transactions.
        OrderService managed = deploy(OrderService.class, new OrderServiceImpl());
        managed.placeOrder("pen", 2);
        try {
            managed.placeOrder("ink", 0);
        } catch (IllegalArgumentException e) {
            System.out.println("caller saw: " + e.getMessage());
        }
        System.out.println("orders: " + managed.countOrders());
        System.out.println("what the caller holds: " + managed.getClass().getName());
    }
}
```

**What you should observe:**

- The plain object runs in `main` with no container, which the EJB 2 bean could never do.
- The "deployed" object prints BEGIN and COMMIT around the good call, and BEGIN and ROLLBACK around the failing one. `countOrders` gets no transaction because the descriptor says `Supports`.
- The caller holds a **generated proxy class** (a name like `$Proxy0`), not `OrderServiceImpl`.

That is the whole lesson in about 60 lines: **keep the container's services, drop the container's weight.** Spring (S5) does the same thing with proxies and `@Transactional`.

## Gotchas

- **"EJB was all bad."** It wasn't. Declarative transactions, security roles and pooling were the right ideas. The failure was the programming model (mandatory interfaces, remote by default, untestable).
- **Remote calls in loops.** Fine-grained calls across a network multiply latency. Design coarse-grained remote APIs, a lesson that returns with microservices in S8.
- **Rollback rules surprise people.** In EJB, a system (unchecked) exception rolled back the container transaction, while an application (checked) exception did not by default. Spring's `@Transactional` has a similar rule: rollback on unchecked exceptions only, unless configured otherwise.
- **Proxies only see calls that go *through* them.** If the bean called its own method directly, the container never saw it. Remember this for S5.
- **Old tutorials mean old packages.** `javax.ejb` code and Jakarta EE's `jakarta.ejb` are not interchangeable.

Typical follow-ups:

- *"What did EJB get right that Spring kept?"* Declarative transactions, declarative security, container-managed lifecycle and pooling, and interception (proxies) as the mechanism. Spring dropped the mandatory interfaces, remote-by-default calls and the requirement for an application server.
- *"Why were remote entity beans slow?"* Each getter was a network call with serialisation, so the fix was coarse-grained facades and transfer objects (DTOs).

## Explain it in 2 minutes

*"What did EJB get right, what went wrong, and what replaced it?"*

A good answer hits:

1. Goal: enterprise services (transactions, security, remoting, pooling) provided by a **container**, declared rather than coded.
2. Mechanism: the client calls a **container-generated proxy** that wraps the bean method. It is the same idea as Spring AOP.
3. Pain: five artefacts per service, beans only runnable inside an app server, slow deploy cycles, remote-by-default calls needing DTO and facade workarounds.
4. Entity beans were widely replaced by hand-written JDBC and then by Hibernate.
5. Spring and Hibernate offered the same services on **plain classes**, and EJB 3.0 and JPA (2006) adopted POJOs and annotations.
6. Takeaway: keep the services and lose the weight.

### Answers

1. You declare that a method needs a transaction (in a descriptor or annotation) and the platform begins and commits or rolls back around it, so you write no transaction code.
2. Session beans (stateless and stateful), entity beans, and message-driven beans.
3. It implemented container interfaces and was reached through home and remote interfaces via JNDI. Its services and lifecycle only existed inside a deployed application server.
4. Too many fine-grained remote calls. One serialisable object carries all the data in a single round-trip.
5. Its "descriptor" attribute was `Supports`, not `Required`, so the proxy did not start a transaction.
