## Where we are

From A1 you know `javac` produces `.class` files and the JVM loads classes lazily, the first time
they are needed, before interpreting and JIT-compiling them. This lesson zooms into that "load"
step: who finds the bytes, in what order, and what goes wrong. It explains several confusing
production errors and how app servers and Spring Boot run many jars in one JVM.

## The problem

A modest Spring Boot service touches thousands of classes: `java.lang.String` from the JDK,
`ObjectMapper` from a library jar, your own `OrderService`. The JVM needs a way to:

1. find the bytes for a class *name* when it is first used,
2. never let your code replace a core class such as `java.lang.String`,
3. avoid loading the same class twice by accident,
4. and still, when it is wanted, run two versions of a library side by side (two web apps in one
   Tomcat, plugins, hot reload).

The mechanism that does all four is the **class loader**.

## What a class loader is

A **class loader** is an ordinary Java object (a subclass of `java.lang.ClassLoader`) whose job is:
given a class name, find its bytes and turn them into a `Class` object the JVM can use.

```java
System.out.println(String.class.getClassLoader());        // null
System.out.println(java.sql.Date.class.getClassLoader()); // ...PlatformClassLoader@...
System.out.println(MyApp.class.getClassLoader());          // ...AppClassLoader@...
```

Three different answers, so there are at least three loaders. `null` is not a bug: it means the
**bootstrap loader**, which is part of the JVM's native code and has no Java object to return.

## The three built-in loaders

```text
 ┌──────────────────────────┐
 │ Bootstrap loader (native)│  java.base: java.lang.*, java.util.*, ...
 └────────────▲─────────────┘
              │ parent
 ┌────────────┴─────────────┐
 │ Platform loader          │  other JDK modules: java.sql, java.net.http, ...
 └────────────▲─────────────┘  (called "extension" loader before Java 9)
              │ parent
 ┌────────────┴─────────────┐
 │ Application loader       │  your class path / module path: your code and libraries
 └────────────▲─────────────┘
              │ parent
 ┌────────────┴─────────────┐
 │ custom loaders (optional)│  Tomcat web apps, Spring Boot jars, plugins
 └──────────────────────────┘
```

Each loader has a **parent**. The arrows are "asks first", not "inherits from".

## Parent delegation

**Parent delegation** is the rule: before a loader looks for a class itself, it asks its parent;
only if the parent cannot find it does the loader try.

Concrete walk-through, the app needs `java.lang.String` and then `com.shop.Order`:

```text
 "java.lang.String"                      "com.shop.Order"
 App ──ask──► Platform ──ask──► Boot     App ──ask──► Platform ──ask──► Boot
                                 found ✔                                 not mine ✘
                                                      not mine ✘ ◄───────┘
              App searches class path: found ✔ ◄──────┘
```

Why this order?

- **Safety:** even if you put a fake `java/lang/String.class` on your class path, the bootstrap
  loader answers first, so the real one always wins. (The module system adds a second wall: you
  cannot define classes in `java.*` packages at all.)
- **Consistency:** every part of the program sees the *same* `String` class, because they all
  delegate up to the same loader.

**Rule:** look up first, then down. The loader that actually reads the bytes is the class's
**defining loader**.

## Class identity: name plus loader

At run time a class is identified by **its full name *and* its defining loader**. Load the same
bytes through two unrelated loaders and you get two different classes.

```text
loader L1 ── defines ──► Greeter (#1)
loader L2 ── defines ──► Greeter (#2)      Greeter#1 != Greeter#2
```

This is what makes isolation possible: Tomcat gives each web app its own loader, so two apps can
use different versions of the same library. It is also the source of the most baffling error in
Java:

```text
java.lang.ClassCastException: class com.shop.Order cannot be cast to class com.shop.Order
  (com.shop.Order is in unnamed module of loader 'app';
   com.shop.Order is in unnamed module of loader org.example.PluginLoader @6d06d69c)
```

Same name, different loaders, therefore different types. Modern JDKs print the loaders in the
message, which is your clue.

## The three phases: load, link, initialise

Getting a class ready is three steps, and they happen at different times.

```text
 LOADING      find bytes, parse them, create the Class object
     │
 LINKING      verify   – bytecode is well-formed and type-safe
     │        prepare  – allocate static fields, set to defaults (0, false, null)
     │        resolve  – turn symbolic names into direct references (often lazily)
     │
 INITIALISING run <clinit>: static field initialisers and static { } blocks, in source order
```

`<clinit>` is the name the compiler gives to a class's combined static initialisation code.

Note the gap between *prepare* and *initialise*: a static field briefly holds its default value.
That is why a static initialiser that reads another class's not-yet-initialised static can see
`0` or `null`.

## When initialisation happens

Loading can happen early, but **initialisation** happens exactly once, on the class's *first
active use*:

- `new Config()`, calling a static method, or reading/writing a static field that is not a
  compile-time constant;
- `Class.forName("Config")` (which initialises by default);
- initialising a subclass (the superclass goes first);
- the main class at start-up.

These do **not** initialise it: declaring a variable of that type, creating an array `new
Config[3]`, using `Config.class`, or reading a `static final` primitive/`String` constant (javac
copies the value into the caller's bytecode).

```java
public class InitOrder {
    static class Config {
        static { System.out.println("Config <clinit> runs"); }
        static final int MAX = 10;                       // constant: inlined by javac
        static final long STARTED = System.nanoTime();   // not a constant: needs init
    }

    public static void main(String[] args) {
        System.out.println("1. array:    " + new Config[3].length);         // no init
        System.out.println("2. literal:  " + Config.class.getSimpleName()); // no init
        System.out.println("3. constant: " + Config.MAX);                   // no init
        System.out.println("4. field:    " + (Config.STARTED > 0));         // init happens here
    }
}
```

The JVM guarantees initialisation runs **once, under a lock**, even if many threads race to use
the class. That guarantee is what the *lazy holder* singleton relies on:

```java
public final class Registry {
    private Registry() { }
    private static final class Holder {               // not initialised until getInstance()
        static final Registry INSTANCE = new Registry();
    }
    public static Registry getInstance() { return Holder.INSTANCE; }
}
```

## Two errors that look alike

| Error | Means | Typical cause |
|---|---|---|
| `ClassNotFoundException` (checked) | Code asked for a class *by name* (`Class.forName`, `loadClass`) and no loader found it | Missing dependency, wrong loader |
| `NoClassDefFoundError` | A class that *was* present at compile time cannot be loaded or initialised now | Jar missing at run time, or an earlier failed `<clinit>` |

The second case catches people: if a static initialiser throws, the first use gets
`ExceptionInInitializerError`, and **every later use** gets `NoClassDefFoundError: Could not
initialize class X`. Always scroll up to the first error.

## When delegation is bent on purpose

- **Servlet containers** (Tomcat) use *child-first* loading for each web app's own jars, so an
  app's library version wins over a shared one (core `java.*` classes still go to the parent).
- **The thread context class loader** lets framework code loaded high up (for example, JDK code
  using `ServiceLoader`) find classes that only a lower loader can see. Get it with
  `Thread.currentThread().getContextClassLoader()`.
- **Spring Boot executable jars** put your dependencies as jars *inside* the jar under
  `BOOT-INF/lib`. The standard application loader cannot read nested jars, so Boot's launcher
  starts first and creates its own class loader that can. (Spring Boot DevTools similarly uses a
  separate "restart" loader for your code so it can throw it away on reload.)

## Unloading

A class is unloaded only when its **class loader** becomes unreachable (so in practice never for
the three built-in loaders). If anything keeps one object, one `Class` or one thread pointing into
a custom loader, every class it loaded stays in memory. Redeploying a web app ten times with such
a reference leaks ten copies of its classes: the classic metaspace leak, revisited in A5.

## Lab (~10 min)

Prove "same bytes, two loaders, two classes". Create two folders, `plugin` and `app`.

`plugin/Greeter.java`:

```java
public class Greeter {
    static { System.out.println("  Greeter initialised by " + Greeter.class.getClassLoader()); }
    public static final String VERSION = "1.0";
    public static String hello() { return "hello"; }
}
```

`app/Loaders.java`:

```java
import java.net.URL;
import java.net.URLClassLoader;
import java.nio.file.Path;

public class Loaders {
    public static void main(String[] args) throws Exception {
        System.out.println("String     -> " + String.class.getClassLoader());          // null = bootstrap
        System.out.println("java.sql   -> " + java.sql.Date.class.getClassLoader());   // platform
        System.out.println("Loaders    -> " + Loaders.class.getClassLoader());         // app

        URL[] path = { Path.of(args[0]).toUri().toURL() };
        ClassLoader parent = ClassLoader.getPlatformClassLoader();   // skips the app class path
        try (URLClassLoader l1 = new URLClassLoader(path, parent);
             URLClassLoader l2 = new URLClassLoader(path, parent)) {
            Class<?> c1 = Class.forName("Greeter", false, l1);   // load, do not initialise
            Class<?> c2 = Class.forName("Greeter", false, l2);
            System.out.println("same name?  " + c1.getName().equals(c2.getName()));
            System.out.println("same class? " + (c1 == c2));
            System.out.println("calling hello() via l1 ...");
            System.out.println("  " + c1.getMethod("hello").invoke(null));   // initialises c1 only
        }
    }
}
```

Run:

```text
javac -d plugin-out plugin/Greeter.java
javac -d app-out app/Loaders.java
java -cp app-out Loaders plugin-out
```

Observe: `same name? true`, `same class? false`; the static block prints only when `hello()` is
called (the `false` in `forName` delayed initialisation), and only for loader `l1`.

Then:

- Save the `InitOrder` example above and run `java InitOrder.java`. The static block prints just
  before line 4, not at line 3.
- Run any program with `-Xlog:class+load` and skim the output. Hundreds of JDK classes load before
  `main`; many say `source: shared objects file`, which is Class Data Sharing (a pre-parsed archive
  of JDK classes that speeds start-up).

## Gotchas

- **"X cannot be cast to X"** means two loaders. Look at the loader names in the message; find
  who loaded the second copy (often a duplicate jar or a plugin/hot-reload loader).
- **`NoClassDefFoundError: Could not initialize class`** hides the real cause. Find the first
  `ExceptionInInitializerError` earlier in the log.
- **Static initialisers run once, forever.** If one fails (bad config, network down), the class is
  unusable for the life of that loader. Keep heavy work out of `static {}`.
- **Constants are copied into callers.** Change `static final int MAX` in a library and recompile
  only the library: callers still use the old value until they are recompiled.
- **Class-loader leaks** keep every class of a redeployed app alive. Common holders: threads the
  app started, `ThreadLocal`s on pooled threads, JDBC drivers registered in `DriverManager`.

## In interviews

Asked as "Explain the class loader hierarchy and parent delegation", "Why can't I replace
`java.lang.String`?", "`ClassNotFoundException` vs `NoClassDefFoundError`?", "When is a static
block executed?", "How does a thread-safe lazy singleton work without `synchronized`?". The bank
has no question that targets class loading directly yet; it often appears as a follow-up to
singleton or Spring start-up questions.

Follow-ups and strong answers:

- *Why delegate to the parent first?* Security (core classes cannot be spoofed) and consistency
  (one `String` for everybody). Mention that containers deliberately invert it for web-app jars.
- *How does Spring Boot run a fat jar?* Its launcher creates a class loader that reads jars nested
  under `BOOT-INF/lib`, then calls your `main` through it.

## Explain it in 2 minutes

Prompt: "How does the JVM find and prepare a class?"

- Class loaders map names to bytes; bootstrap → platform → application, plus custom ones.
- Parent delegation: ask the parent first; protects core classes and keeps one copy of shared
  types.
- Runtime identity is name + defining loader; two loaders give two types (isolation, and
  "X cannot be cast to X").
- Phases: load, link (verify, prepare defaults, resolve), initialise (`<clinit>`) on first active
  use, once, thread-safely.
- Errors: `ClassNotFoundException` (lookup by name failed) vs `NoClassDefFoundError` (missing at
  run time or failed init).
- Unloading only when the loader is unreachable; leaks come from references into it.

## Check yourself

1. What does `String.class.getClassLoader()` return, and why?
2. In what order does the application loader look for `com.shop.Order`?
3. Does reading `Config.MAX` (a `static final int` constant) run `Config`'s static block?
4. Your log says `NoClassDefFoundError: Could not initialize class PriceTable`. What do you look
   for?
5. Why does the lazy holder singleton need no `volatile` or `synchronized`?

### Answers

1. `null`, meaning the bootstrap loader, which is native and has no Java object.
2. It asks the platform loader, which asks bootstrap; both fail; then it searches the class path
   itself.
3. No. javac copied the constant into the caller's bytecode, so `Config` is never actively used.
4. The first failure: an `ExceptionInInitializerError` from `PriceTable`'s static initialiser,
   earlier in the log.
5. Class initialisation runs once under a JVM-held lock, and its results are visible to every
   thread that later uses the class.
