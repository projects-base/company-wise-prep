## Where we are

From JAVA-FUND-4 you know try-with-resources and how to design exceptions; from JAVA-FUND-7 you can write stream
pipelines and lambdas. This lesson is about getting data **in and out** of a Java process: reading and writing files,
character encodings, and turning objects into bytes and back. Almost every backend bug report that says "the name
shows as `JosÃ©`" or "the consumer broke after we added a field" lives here.

## The problem

A nightly job reads `orders.csv` from a partner and posts each order as JSON to another service. The first version:

```java
FileReader reader = new FileReader("orders.csv");          // which charset?
int c;
while ((c = reader.read()) != -1) { /* build lines by hand */ }
// reader never closed if anything above throws
String json = "{\"id\":\"" + id + "\",\"customer\":\"" + name + "\"}";  // hand-built JSON
```

It has four bugs waiting to happen: an unclosed file handle, one-character-at-a-time reads, a charset chosen by
whatever machine it runs on, and JSON that breaks the first time a name contains a quote. Each section below fixes
one.

## Bytes versus characters

A file or socket holds **bytes**. Text is **characters**. Java keeps the two worlds apart:

| | Bytes | Characters |
|---|---|---|
| Read | `InputStream` | `Reader` |
| Write | `OutputStream` | `Writer` |
| Examples | `FileInputStream`, socket streams, `ByteArrayInputStream` | `BufferedReader`, `StringReader` |

The bridge between them is a **charset**: the rule that maps characters to bytes. `InputStreamReader` decodes bytes
into characters; `OutputStreamWriter` encodes the other way. Both take a charset argument, and you should always pass
one.

```java
Reader r = new InputStreamReader(socket.getInputStream(), StandardCharsets.UTF_8);
```

These classes are built with the **Decorator** pattern: each wrapper adds one behaviour (decoding, buffering) around
another stream with the same interface. Closing the outermost wrapper closes everything inside it.

## Buffering: stop paying per byte

`FileInputStream.read()` with no arguments returns one byte, and each call can go down to the operating system.
Reading a million bytes that way means up to a million trips across the boundary between your program and the OS.
A **buffer** reads a large block (8 KB by default for `BufferedInputStream` and `BufferedReader`) in one call, then
hands out bytes from memory.

```java
try (BufferedReader in = new BufferedReader(new InputStreamReader(new FileInputStream(path), UTF_8))) {
    String line;
    while ((line = in.readLine()) != null) {
        process(line);
    }
}
```

**The rule:** never do small reads or writes on an unbuffered stream. Either wrap it in a buffered stream or read into
your own `byte[]` in chunks. For writers, remember that a buffer holds data until `flush()` or `close()`; a program
that exits without closing can lose its last few kilobytes.

## try-with-resources, for every handle

A file handle, socket or database connection is an OS resource, and the OS gives a process a limited number. Leak
them in a loop and you eventually get `IOException: Too many open files`. You met try-with-resources in JAVA-FUND-4:

```java
try (InputStream in = Files.newInputStream(src);
     OutputStream out = Files.newOutputStream(dst)) {
    in.transferTo(out);                    // Java 9+: copies with an internal buffer
}                                          // closed in reverse order, even on exception
```

If both the body and `close()` throw, the body's exception wins and the close failure is attached as a **suppressed**
exception (`e.getSuppressed()`), so you keep the root cause.

## java.nio.file: the modern file API

Java 7 added `java.nio.file` (often called NIO.2). Prefer it over `java.io.File` for new code: errors are real
exceptions with reasons (`NoSuchFileException`, `AccessDeniedException`) instead of `false` return values.

- **`Path`** is a file-system path: `Path p = Path.of("data", "orders.csv");`
- **`Files`** holds static operations on paths:

```java
String all = Files.readString(p);                         // small files only: whole file in memory, UTF-8
List<String> lines = Files.readAllLines(p, UTF_8);        // also all in memory
Files.writeString(out, json, UTF_8);                      // create or truncate, then write

try (Stream<String> lines = Files.lines(p, UTF_8)) {      // lazy: reads as the stream is consumed
    long paid = lines.skip(1).filter(l -> l.endsWith(",PAID")).count();
}
```

`Files.lines`, `Files.list` and `Files.walk` return streams that hold an open file or directory handle. Unlike a
stream over a `List`, they **must** be closed, so they go in try-with-resources.

For a file another process reads, write to a temporary file in the same directory and then rename it with
`Files.move(tmp, target, StandardCopyOption.ATOMIC_MOVE)`. Readers then see either the old file or the new one, never
half a file. (Whether the move is truly atomic depends on the file system; it throws `AtomicMoveNotSupportedException`
when it cannot be.)

The older `java.nio` package (Java 1.4) is a different thing with a similar name: channels, buffers and selectors for
non-blocking I/O, where one thread watches many sockets. You rarely use it directly; Tomcat's NIO connector and Netty
are built on it.

## Charsets: where UTF-8 goes wrong

**UTF-8** encodes each character in 1 to 4 bytes: ASCII letters take 1, `é` takes 2, most emoji take 4. That breaks
three assumptions people make without noticing:

1. **`String.length()` is not a byte count.** `"José".length()` is 4; its UTF-8 encoding is 5 bytes. Size limits on
   a column or a `Content-Length` header are in bytes.
2. **Decoding with the wrong charset corrupts text silently.** The UTF-8 bytes of `é` (`C3 A9`), decoded as
   ISO-8859-1 (Latin-1), become two characters, `Ã©`. That is **mojibake**, and it throws no exception.
3. **The default charset depends on the Java version and the machine.** Before Java 18, `new FileReader(f)`,
   `new String(bytes)` and `s.getBytes()` used the platform default, which on many Windows machines was `windows-1252`.
   Java 18 (JEP 400) made UTF-8 the default for these APIs. Console output is separate: `System.out` uses the
   terminal's encoding (`stdout.encoding`), which is why a correct string can still print as `?` on a Windows console.

**The rule:** at every byte/character boundary, name the charset explicitly (`StandardCharsets.UTF_8`). It documents
intent and behaves the same on every JVM version and machine.

## Java serialization, and why you avoid it

Java has a built-in way to turn an object graph into bytes: implement the marker interface `Serializable` and write
it with `ObjectOutputStream`.

```java
record Session(String user, Instant expires) implements Serializable {}

try (var out = new ObjectOutputStream(Files.newOutputStream(p))) {
    out.writeObject(new Session("akhil", Instant.now()));
}
```

Fields marked `transient` are skipped. Each class has a **`serialVersionUID`**, a version number stored in the bytes.
If you do not declare one, the compiler computes it from the class's structure, so adding a field changes it and old
bytes then fail with `InvalidClassException`. Declaring `private static final long serialVersionUID = 1L;` keeps it
stable across compatible changes.

Modern code avoids Java serialization, for two reasons:

- **Security.** `ObjectInputStream.readObject` creates objects of whatever classes the byte stream names, and runs
  their deserialization logic, before your code gets a chance to check anything. Attackers chain together
  existing library classes (**gadget chains**) so that merely deserializing a crafted payload runs commands. The
  Apache Commons Collections chain published in 2015 led to remote-code-execution fixes across many Java servers.
  Never deserialize untrusted bytes. If you must read serialized data, use an allow-list `ObjectInputFilter`
  (Java 9+).
- **Coupling and fragility.** The format is tied to Java class names and internals; renaming a package breaks
  stored data, and non-Java services cannot read it.

For data that leaves the process, use JSON (or a schema-based format such as Protobuf or Avro).

## JSON with Jackson: ObjectMapper

**Jackson** is the JSON library Spring Boot uses by default. Its central class is **`ObjectMapper`**: it converts Java
objects to JSON (**serialization**) and JSON to Java objects (**deserialization**), using getters, fields, record
components and annotations.

```java
static final ObjectMapper MAPPER = new ObjectMapper();

String json = MAPPER.writeValueAsString(order);                 // object -> JSON
Order back = MAPPER.readValue(json, Order.class);               // JSON -> object
List<Order> list = MAPPER.readValue(arrayJson, new TypeReference<List<Order>>() {});
```

The `TypeReference` is there because of type erasure (JAVA-FUND-5): `List<Order>.class` does not exist, so an
anonymous subclass carries the full generic type to Jackson.

**Create it once and reuse it.** An `ObjectMapper` is expensive to build (it discovers and caches serializers per
type), and it is **thread-safe once configured**, so one shared instance serves every thread. Creating
`new ObjectMapper()` per request throws that cache away each time. In Spring Boot, inject the `ObjectMapper` bean
that Boot builds instead of creating your own; it already has Boot's settings and modules applied. Do not change its
configuration after it is in use; build a copy (`mapper.copy()`) for a variant.

Spring Boot 4 moves to **Jackson 3**, where the main package is `tools.jackson.databind`, mappers are built immutably
(`JsonMapper.builder()...build()`) and `java.time` support is built in. The annotations keep their
`com.fasterxml.jackson.annotation` package, and the concepts in this lesson carry over; some defaults changed, so
check the migration notes when you upgrade.

## Annotations that shape the JSON

```java
record Order(@JsonProperty("order_id") String id,      // JSON name differs from Java name
             long amountCents,
             @JsonIgnore String internalNote,           // never written, ignored on read
             @JsonInclude(JsonInclude.Include.NON_NULL) String coupon) {}  // omit when null
```

Records have worked with Jackson since 2.12: it uses the canonical constructor to deserialize, so records give you
immutable DTOs with no extra annotations. Use `@JsonIgnore` (or a separate DTO) for anything that must not leave the
service, such as password hashes or internal flags.

## Unknown properties: be a tolerant reader

A plain `ObjectMapper` (Jackson 2) has `FAIL_ON_UNKNOWN_PROPERTIES` **on**: if the JSON contains a field your class
does not have, `readValue` throws `UnrecognizedPropertyException`. That means a producer adding a harmless new field
breaks every consumer. Between services you usually want the **tolerant reader** behaviour: ignore what you do not
understand.

```java
mapper.disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES);   // whole mapper
@JsonIgnoreProperties(ignoreUnknown = true)                          // one class
```

Spring Boot's auto-configured mapper already disables it. A plain `new ObjectMapper()` in a test or a library does
not, which is a classic "works in the app, fails in the test" difference.

## Dates and times

`java.time` types (`Instant`, `LocalDate`, `OffsetDateTime`) need Jackson 2's **`JavaTimeModule`** (artifact
`jackson-datatype-jsr310`). Without it, Jackson 2.12+ throws `InvalidDefinitionException: Java 8 date/time type
... not supported by default`. With it but default settings, dates are written as numbers (timestamps); disable
`WRITE_DATES_AS_TIMESTAMPS` to get ISO-8601 strings such as `"2026-10-31T10:15:30Z"`, which humans and other
languages read safely (the lab shows both settings). Spring Boot registers the module and turns timestamps off.

Prefer `Instant` or `OffsetDateTime` for moments in time; a `LocalDateTime` has no zone, so two services can read
the same value as different moments.

## Polymorphic deserialization: the dangerous switch

Sometimes a field can hold several subtypes (`Payment` is `Card` or `Upi`). Jackson can write a type marker so it
knows which class to build. The safe way names a **logical** type from a closed list:

```java
@JsonTypeInfo(use = JsonTypeInfo.Id.NAME, property = "type")
@JsonSubTypes({@JsonSubTypes.Type(value = Card.class, name = "card"),
               @JsonSubTypes.Type(value = Upi.class, name = "upi")})
sealed interface Payment permits Card, Upi {}
```

The unsafe way lets the JSON name a **Java class**: `JsonTypeInfo.Id.CLASS` on a broad type like `Object`, or global
"default typing" (`enableDefaultTyping`, now deprecated). Then the attacker chooses which class gets instantiated,
which is the same gadget-chain problem as Java serialization; Jackson has had many CVEs in this area. Use `Id.NAME`
with explicit subtypes, or, if you truly need class names, `activateDefaultTyping` with a strict
`PolymorphicTypeValidator` allow-list.

## Lab (~10 min)

**Part A (JDK only).** Save as `IoLab.java`, run with `java IoLab.java`.

```java
import java.io.*;
import java.nio.charset.StandardCharsets;
import java.nio.file.*;
import java.util.List;

public class IoLab {
    public static void main(String[] args) throws IOException {
        String name = "José";                               // "José", written with an escape
        System.out.println("chars: " + name.length() + ", UTF-8 bytes: "
                + name.getBytes(StandardCharsets.UTF_8).length);

        Path file = Files.createTempFile("orders", ".csv");
        Files.writeString(file, "id,customer\n1," + name + "\n", StandardCharsets.UTF_8);

        List<String> wrong = Files.readAllLines(file, StandardCharsets.ISO_8859_1);
        List<String> right = Files.readAllLines(file, StandardCharsets.UTF_8);
        System.out.println("ISO-8859-1 read matches: " + wrong.get(1).equals("1," + name)
                + " (length " + wrong.get(1).length() + ")");
        System.out.println("UTF-8 read matches:      " + right.get(1).equals("1," + name)
                + " (length " + right.get(1).length() + ")");

        Path bin = Files.createTempFile("big", ".bin");
        Files.write(bin, new byte[1_000_000]);
        System.out.println("unbuffered ms: " + timeRead(new FileInputStream(bin.toFile())));
        System.out.println("buffered ms:   " + timeRead(new BufferedInputStream(new FileInputStream(bin.toFile()))));

        Files.delete(file);
        Files.delete(bin);
    }

    static long timeRead(InputStream in) throws IOException {
        long start = System.nanoTime();
        try (in) {
            while (in.read() != -1) {
                // one byte per call
            }
        }
        return (System.nanoTime() - start) / 1_000_000;
    }
}
```

Observe: 4 chars but 5 bytes; the Latin-1 read gives a line one character longer (mojibake, no exception); the
unbuffered read is many times slower than the buffered one. Your exact times will differ.

**Part B (Jackson 2).** Save as `JsonLab.java`. Put `jackson-databind`, `jackson-core`, `jackson-annotations` and
`jackson-datatype-jsr310` (2.12 or later, same version) on the classpath, for example from your `~/.m2` folder, and
run `java -cp "<jars separated by ; on Windows, : elsewhere>" JsonLab.java`. Or paste it into a test in a Spring Boot 3
project, which ships Jackson 2.

```java
import com.fasterxml.jackson.annotation.JsonIgnore;
import com.fasterxml.jackson.annotation.JsonProperty;
import com.fasterxml.jackson.core.type.TypeReference;
import com.fasterxml.jackson.databind.DeserializationFeature;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.databind.SerializationFeature;
import com.fasterxml.jackson.databind.exc.InvalidDefinitionException;
import com.fasterxml.jackson.databind.exc.UnrecognizedPropertyException;
import com.fasterxml.jackson.datatype.jsr310.JavaTimeModule;
import java.time.Instant;
import java.util.List;

public class JsonLab {
    record Order(@JsonProperty("order_id") String id, long amountCents, Instant placedAt,
                 @JsonIgnore String internalNote) {}

    // One mapper, configured once, shared: ObjectMapper is thread-safe after configuration
    static final ObjectMapper MAPPER = new ObjectMapper()
            .registerModule(new JavaTimeModule())
            .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS);

    public static void main(String[] args) throws Exception {
        Order order = new Order("o-1", 1250, Instant.parse("2026-10-31T10:15:30Z"), "do not leak");

        String json = MAPPER.writeValueAsString(order);
        System.out.println("serialised:   " + json);
        System.out.println("round trip:   " + MAPPER.readValue(json, Order.class));

        // 1. Generic types need a TypeReference (type erasure)
        List<Order> list = MAPPER.readValue("[" + json + "]", new TypeReference<List<Order>>() {});
        System.out.println("list element: " + list.get(0).getClass().getSimpleName());

        // 2. A new field from the producer breaks a strict consumer
        String newer = json.replace("}", ",\"currency\":\"INR\"}");
        try {
            MAPPER.readValue(newer, Order.class);
        } catch (UnrecognizedPropertyException e) {
            System.out.println("strict:       unknown field '" + e.getPropertyName() + "'");
        }
        ObjectMapper tolerant = MAPPER.copy().disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES);
        System.out.println("tolerant:     " + tolerant.readValue(newer, Order.class).id());

        // 3. Forget the JavaTimeModule
        try {
            new ObjectMapper().writeValueAsString(order);
        } catch (InvalidDefinitionException e) {
            System.out.println("no module:    " + e.getOriginalMessage().lines().findFirst().orElse(""));
        }
    }
}
```

Observe: `order_id` instead of `id`, an ISO-8601 date, no `internalNote` (and `null` after the round trip), the strict
mapper rejecting `currency` while the tolerant copy accepts it, and the plain mapper refusing `Instant`.

**Break it:** remove `.disable(WRITE_DATES_AS_TIMESTAMPS)` and see `placedAt` become a number.

## Gotchas

- **No charset argument.** `getBytes()`, `new String(bytes)` and `FileReader` without a charset behave differently
  before and after Java 18 and across machines. Always pass `StandardCharsets.UTF_8`.
- **`Files.lines` / `Files.walk` not closed.** They hold OS handles; a long-running job leaks until "Too many open
  files". Use try-with-resources.
- **`new ObjectMapper()` per call.** Slow, and it skips the configuration Spring Boot applied. Inject the shared,
  thread-safe bean.
- **Strict unknown-property handling between services.** A producer's new field breaks consumers. Be a tolerant
  reader, and test with a payload containing an extra field.
- **Deserializing untrusted input into "any class".** Java serialization, `Id.CLASS` and default typing all let the
  payload choose the class. Use logical type names with an explicit subtype list.
- **`Files.readString` on a large file** loads it all into the heap. Stream it with `Files.lines` or a
  `BufferedReader` instead.

## In interviews

Asked as "Difference between `InputStream` and `Reader`?", "Why buffer?", "What is `serialVersionUID`?", "Why is Java
serialization considered dangerous?", "Is `ObjectMapper` thread-safe?", "Your API consumer broke after you added a
field; why?", and "How do you serialize `LocalDateTime` with Jackson?". Bank:
[Java serialization](#/q/java-serialization), and [Web services (REST/SOAP) fundamentals](#/q/web-services-fundamentals)
when the discussion moves to payload formats.

A strong answer shape, in four layers (example: "Explain Java serialization"):

1. **What:** `Serializable` marker interface; `ObjectOutputStream` writes an object graph to bytes, `transient`
   skips fields, `serialVersionUID` versions the class.
2. **How inside:** the stream records class names and field values; on read, the JVM instantiates the named classes
   without running their own constructors (records excepted) and runs their `readObject` hooks.
3. **Where used:** legacy RMI, some session replication and caches. New systems use JSON, Protobuf or Avro.
4. **What goes wrong:** gadget-chain remote code execution from untrusted bytes, `InvalidClassException` after a
   class change without a fixed UID, Java-only coupling. Mitigation: do not use it across trust boundaries;
   `ObjectInputFilter` if you must.

**Follow-up: "Is `ObjectMapper` thread-safe?"** Yes, once configured; reads and writes from many threads are safe,
and sharing one instance is the recommended practice because of its serializer cache. Reconfiguring it while in use
is not safe; use `copy()`, or `ObjectReader`/`ObjectWriter` (immutable, created with `mapper.readerFor(...)`,
`mapper.writerFor(...)`).

## Explain it in 2 minutes

Prompt: *"How do you read a file and send its contents as JSON to another service, correctly?"*

- Bytes versus characters: `InputStream`/`Reader`, bridged by an explicit charset (UTF-8).
- Buffer the I/O, and put every handle in try-with-resources (`Files.newBufferedReader`, `Files.lines`).
- Use `java.nio.file` (`Path`, `Files`); write to a temp file and atomic-move for files others read.
- Build JSON with Jackson, never by string concatenation: one shared `ObjectMapper`, records as DTOs, `@JsonProperty`
  and `@JsonIgnore` to shape output.
- Configure for evolution: tolerate unknown properties, `JavaTimeModule` with ISO-8601 dates.
- Never deserialize untrusted data with Java serialization or class-name-based polymorphic typing.

## Check yourself

1. Why is `"naïve".getBytes(UTF_8).length` not equal to `"naïve".length()`?
2. What two problems does `BufferedReader` around an `InputStreamReader` solve?
3. A class implementing `Serializable` without a `serialVersionUID` gets a new field. What happens when old bytes are
   read?
4. Why should a Spring service inject `ObjectMapper` instead of creating one?
5. Why is `@JsonTypeInfo(use = JsonTypeInfo.Id.CLASS)` on an `Object` field risky?

### Answers

1. `ï` takes 2 bytes in UTF-8, so the string is 5 characters and 6 bytes.
2. `InputStreamReader` decodes bytes to characters with a charset; `BufferedReader` reads in large blocks (fewer OS
   calls) and adds `readLine()`.
3. The computed UID changes, so deserializing the old bytes throws `InvalidClassException`.
4. Building a mapper is expensive and it is thread-safe, so one shared instance is right; the injected bean also
   carries Spring Boot's configuration (time module, tolerant reading, your customisations).
5. The JSON chooses which Java class to instantiate, so an attacker can name a gadget class and trigger code
   execution during deserialization. Use `Id.NAME` with an explicit `@JsonSubTypes` list.
