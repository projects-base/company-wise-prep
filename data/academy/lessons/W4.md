## Where we are

From BE-STORY-1 you know a client opens a TCP connection to a server's IP and port. JAVA-FUND-8 covered byte
streams versus character readers, and JAVA-CONC-1 covered threads. WEB-API-1 showed that HTTP is text sent over that
connection. This lesson opens the connection yourself: what a **socket** is, how TCP behaves, and how to write
servers and clients in Java, from one blocking thread up to the NIO event loop inside Tomcat, Netty and Redis.

## The problem

Every remote call your service makes goes through a socket: the JDBC driver to PostgreSQL, the Redis client, the
Kafka producer, `RestClient` to another service. So do the requests Tomcat accepts for you. When a socket goes
wrong, the symptoms look like this:

- Every request thread is stuck in `SocketInputStream.read` (or `NioSocketImpl.read` on newer JDKs). A downstream
  service hung, and nobody set a read timeout.
- `java.net.ConnectException: Connection refused` right after a deploy.
- `java.net.SocketException: Connection reset` now and then, under load.
- `java.io.IOException: Too many open files`, and then the service stops accepting connections.
- Thousands of connections sit in `TIME_WAIT` after a load test.

Each of these is a socket concept: timeouts, a listening port, an RST packet, file descriptors, connection
teardown. You debug them quickly once you have written a socket server yourself.

## What a socket is

A **socket** is one endpoint of a two-way network conversation. The operating system owns it. Your program only
holds a handle to it: a **file descriptor** on Linux, a small integer the kernel gives the process.

- An endpoint is an **IP address plus a port** (for example `10.0.0.5:8080`). A port is a number from 0 to 65535 that
  tells the OS which program on that machine gets the bytes.
- A TCP connection is identified by a **4-tuple**: client IP, client port, server IP, server port. That is how one
  server port (8080) serves thousands of clients at once: each connection differs in the client half.
- The client's port is usually an **ephemeral port**: the OS picks a free one from a high range for each outgoing
  connection.

```text
 client 192.168.1.7:53122  ◄═══════ one TCP connection ═══════►  server 10.0.0.5:8080
 (ephemeral port, picked by the OS)                       (well-known port, chosen by you)
```

In Java, `java.net.Socket` is one connected endpoint, and `java.net.ServerSocket` is a listening endpoint that
produces a new `Socket` for each client that connects.

## TCP versus UDP

Sockets come in two main kinds, and the choice decides which guarantees you get.

| | TCP (`Socket`, `ServerSocket`) | UDP (`DatagramSocket`) |
|---|---|---|
| Connection | Yes: a handshake first | No: just send packets |
| Delivery | Reliable: lost segments are resent | Best effort: packets may be lost |
| Order | In order | Any order |
| Shape | A **byte stream**, no message boundaries | Separate **datagrams**, each a message |
| Flow and congestion control | Yes | No |
| Used by | HTTP/1.1, HTTP/2, JDBC, Redis, Kafka, SMTP | DNS, video calls, games, QUIC (HTTP/3 runs on UDP) |

Backend services use TCP for almost everything. The rest of this lesson is TCP.

## The life of a TCP connection

```text
 SERVER                                         CLIENT
 socket() → bind(:9000) → listen(backlog)
 accept()  ...blocks...
                                                socket() → connect(server:9000)
            ◄──────────── SYN ───────────────
            ───────────── SYN-ACK ──────────►        three-way handshake
            ◄──────────── ACK ───────────────        (one round trip before any data)
 accept() returns a NEW socket for this client
            ◄──────── data (request) ─────────
            ───────── data (response) ───────►
            ◄──────────── FIN ───────────────        client closes
            ───────────── ACK, FIN ──────────►
            ◄──────────── ACK ───────────────        the side that closed first waits in TIME_WAIT
```

- **bind** claims the port. **listen** tells the OS to queue incoming connections. The queue length is the
  **backlog**. When it is full, new clients wait or are refused.
- The kernel completes the handshake by itself and places the finished connection in the queue. `accept()` just
  takes the next one.
- **Connection refused** means nothing is listening on that port: the client got an RST in reply to its SYN. You see
  it while a service is still starting, or when the port is wrong.
- **Connection reset** means the other side sent an RST on an open connection. It crashed, it closed while unread
  data remained, or a proxy or firewall dropped the idle connection.
- **TIME_WAIT** keeps the closing side's 4-tuple reserved for a short time (a few tens of seconds to a couple of
  minutes, depending on the OS), so late packets from the old connection can't corrupt a new one. Thousands of
  `TIME_WAIT` entries mean you open and close connections too often. Reuse them through a pool.

## Your first server and client

An echo server: read a line, send it back. It uses one thread and handles one client at a time.

```java
import java.io.*;
import java.net.*;
import java.nio.charset.StandardCharsets;

public class EchoServer {
    public static void main(String[] args) throws IOException {
        try (ServerSocket server = new ServerSocket(9000)) {          // bind + listen on port 9000
            System.out.println("Listening on " + server.getLocalPort());
            while (true) {
                try (Socket client = server.accept();                  // blocks until a client connects
                     var in = new BufferedReader(new InputStreamReader(client.getInputStream(), StandardCharsets.UTF_8));
                     var out = new PrintWriter(new OutputStreamWriter(client.getOutputStream(), StandardCharsets.UTF_8), true)) {
                    System.out.println("Connected: " + client.getRemoteSocketAddress());
                    String line;
                    while ((line = in.readLine()) != null) {           // null = the client closed its side
                        out.println("echo: " + line);
                    }
                }
            }
        }
    }
}
```

```java
import java.io.*;
import java.net.*;
import java.nio.charset.StandardCharsets;

public class EchoClient {
    public static void main(String[] args) throws IOException {
        try (Socket socket = new Socket()) {
            socket.connect(new InetSocketAddress("localhost", 9000), 2_000); // connect timeout: 2 s
            socket.setSoTimeout(5_000);                                     // read timeout: 5 s
            var out = new PrintWriter(new OutputStreamWriter(socket.getOutputStream(), StandardCharsets.UTF_8), true);
            var in = new BufferedReader(new InputStreamReader(socket.getInputStream(), StandardCharsets.UTF_8));
            for (String msg : new String[] {"hello", "world"}) {
                out.println(msg);                       // println adds the newline the server reads up to
                System.out.println(in.readLine());      // waits at most 5 s, then SocketTimeoutException
            }
        }
    }
}
```

Run the server, then the client. The client prints `echo: hello` and `echo: world`. Things to notice:

- A socket gives you an `InputStream` and an `OutputStream` of **bytes**. You wrap them in readers and writers with an
  explicit charset, exactly as in JAVA-FUND-8.
- `readLine()` returning `null` (or `read()` returning `-1`) means the peer closed its side. That is the normal end
  of a conversation, not an error.
- try-with-resources closes the socket, which releases the file descriptor. A leaked socket is a leaked descriptor.
- While this server talks to one client, a second client's connection sits in the backlog. Its `connect` succeeds,
  because the kernel did the handshake, but nobody reads it. The next section fixes that.

## TCP is a stream: you need framing

TCP delivers bytes in order, but it does not keep your message boundaries. If you write `"hello"` and then
`"world"`, the reader may get `"helloworld"` in one `read`, or `"hel"` and then `"loworld"`. **Framing** is how a
protocol marks where one message ends. There are three common ways:

| Framing | How | Who uses it |
|---|---|---|
| Delimiter | End each message with a marker, such as a newline | Our echo server, Redis (`\r\n`), SMTP |
| Length prefix | Send the length first, then that many bytes | Kafka, the PostgreSQL wire protocol, gRPC frames |
| Headers then length | Text headers, a blank line, then `Content-Length` bytes | HTTP/1.1 (WEB-API-1) |

If you write a custom protocol and assume one `write` arrives as one `read`, it works on localhost and breaks in
production.

## Serving many clients: thread per connection

The classic fix: the accept loop only accepts, and each connection gets its own thread. That is BE-STORY-3's
"thread per request" model, and it is what Tomcat does for blocking servlets. Java 21 virtual threads (JAVA-CONC-6)
make one thread per connection cheap, because a virtual thread blocked on a socket read gives its carrier thread
back.

```java
import java.io.*;
import java.net.*;
import java.nio.charset.StandardCharsets;
import java.util.concurrent.*;

public class VirtualEchoServer {
    public static void main(String[] args) throws IOException {
        try (ServerSocket server = new ServerSocket(9000);
             ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            while (true) {
                Socket client = server.accept();        // the accept loop only accepts...
                pool.submit(() -> handle(client));      // ...each connection gets its own (virtual) thread
            }
        }
    }

    static void handle(Socket client) {
        try (client;
             var in = new BufferedReader(new InputStreamReader(client.getInputStream(), StandardCharsets.UTF_8));
             var out = new PrintWriter(new OutputStreamWriter(client.getOutputStream(), StandardCharsets.UTF_8), true)) {
            client.setSoTimeout(30_000);                // an idle client is dropped after 30 s
            String line;
            while ((line = in.readLine()) != null) out.println("echo: " + line);
        } catch (IOException e) {                       // one bad client must not kill the server
            System.err.println(client.getRemoteSocketAddress() + ": " + e);
        }
    }
}
```

With platform threads you would use a **bounded** pool (`Executors.newFixedThreadPool(200)`). An unbounded "new
thread per connection" lets a traffic spike create thousands of OS threads, each with its own stack, until the
process runs out of memory. With virtual threads the limit moves elsewhere: to file descriptors, and to whatever the
handler calls (a database pool of 10 connections still allows only 10 queries at once).

## Timeouts: the default is forever

A blocking socket call waits **indefinitely** unless you set a timeout. There are two:

- **Connect timeout**: how long to wait for the handshake. Use `socket.connect(address, millis)`.
- **Read timeout** (`SO_TIMEOUT`): how long one `read` may wait for bytes. Use `socket.setSoTimeout(millis)`. When it
  expires you get `SocketTimeoutException`, and the socket is still usable.

Every client library exposes the same two settings under its own names. Examples are HikariCP's `connectionTimeout`,
the PostgreSQL JDBC driver's `connectTimeout` and `socketTimeout`, and the connect and read timeouts of
`java.net.http.HttpClient` and Spring's `RestClient` request factories. "All threads stuck in socket read" in a
thread dump (LIFECYCLE-2) almost always means a missing read timeout on a call to a dependency that slowed down.
DIST-SYS-3 builds retries and circuit breakers on top of these timeouts.

## One thread, many sockets: NIO and the Selector

Thread per connection spends a thread on every idle connection. A chat or push server holding 100,000 mostly quiet
WebSocket connections needs something else: **non-blocking I/O**. Put each socket in non-blocking mode, register it
with a **Selector**, and let one thread ask the OS which sockets are ready. On Linux the Selector is built on
`epoll`, on macOS on `kqueue`.

```java
import java.io.IOException;
import java.net.InetSocketAddress;
import java.nio.ByteBuffer;
import java.nio.channels.*;
import java.util.Iterator;

public class NioEchoServer {
    public static void main(String[] args) throws IOException {
        Selector selector = Selector.open();
        ServerSocketChannel server = ServerSocketChannel.open();
        server.bind(new InetSocketAddress(9000));
        server.configureBlocking(false);
        server.register(selector, SelectionKey.OP_ACCEPT);

        while (true) {
            selector.select();                              // ONE thread waits for ANY ready socket
            Iterator<SelectionKey> keys = selector.selectedKeys().iterator();
            while (keys.hasNext()) {
                SelectionKey key = keys.next();
                keys.remove();
                if (key.isAcceptable()) {                   // a new connection is waiting
                    SocketChannel client = server.accept();
                    client.configureBlocking(false);
                    client.register(selector, SelectionKey.OP_READ, ByteBuffer.allocate(1024));
                } else if (key.isReadable()) {              // bytes arrived on some connection
                    SocketChannel client = (SocketChannel) key.channel();
                    ByteBuffer buf = (ByteBuffer) key.attachment();
                    int n = client.read(buf);               // never blocks: reads what is there now
                    if (n == -1) {                          // the client closed
                        key.cancel();
                        client.close();
                        continue;
                    }
                    buf.flip();                             // switch the buffer from filling to draining
                    client.write(buf);                      // echo back (a real server also handles partial writes)
                    buf.clear();
                }
            }
        }
    }
}
```

This is an **event loop**, the same shape as Redis's single command thread (DIST-SYS-1). It is powerful, and also
hard to get right: partial reads and writes, framing across buffers, and the rule that one slow handler stalls every
connection on that loop. So you rarely write it by hand. You use what is built on it:

- **Tomcat's NIO connector**, the default in Spring Boot: a few poller threads watch all connections, and a request
  goes to a worker thread only when its bytes are ready.
- **Netty**: event loops plus a pipeline of handlers for framing and codecs. It runs under Spring WebFlux, gRPC Java,
  and many database and messaging clients.

Rule of thumb today: thread per connection on virtual threads for request/response services, and an event loop
(through Netty or WebFlux) when you hold huge numbers of long-lived, mostly idle connections.

## Connections are expensive: pool and reuse them

A new connection costs a handshake round trip, plus TLS round trips when it is encrypted (WEB-API-1), a file
descriptor on both ends, and a `TIME_WAIT` entry when it closes. That is why clients keep connections open:

- **Database pools** such as HikariCP (DB-SQL-5) keep a few connections open and lend them out.
- **HTTP keep-alive**: HTTP clients keep a pool of open connections per host, and HTTP/2 multiplexes many requests
  over one connection.
- **Socket options** you will meet in configs: `SO_KEEPALIVE` (the OS probes an idle connection to detect a dead
  peer), `TCP_NODELAY` (turns off Nagle's algorithm, which delays small writes to batch them; low-latency protocols
  turn it off), and `SO_REUSEADDR` (lets a restarted server bind its port while old connections are still in
  `TIME_WAIT`).

## WebSockets: a socket the browser can use

A browser can't open a raw TCP socket. A **WebSocket** starts as an ordinary HTTP request with `Upgrade: websocket`.
The server answers `101 Switching Protocols`, and from then on the same TCP connection carries small **frames** in
both directions. That gives push without polling, which is what the chat and live-odds designs in SYS-DES-7 and
SYS-DES-8 rely on. In Spring Boot (`spring-boot-starter-websocket`):

```java
@Configuration
@EnableWebSocket
class WsConfig implements WebSocketConfigurer {
    @Override
    public void registerWebSocketHandlers(WebSocketHandlerRegistry registry) {
        registry.addHandler(new EchoHandler(), "/ws").setAllowedOrigins("https://app.example.com");
    }
}

class EchoHandler extends TextWebSocketHandler {
    @Override
    protected void handleTextMessage(WebSocketSession session, TextMessage message) throws Exception {
        session.sendMessage(new TextMessage("echo: " + message.getPayload()));
    }
}
```

The server-side costs come straight from this lesson: each open WebSocket is a long-lived TCP connection and a file
descriptor. Load balancers must allow the upgrade and long idle times. Scaling out means a client stays on the node
that holds its connection, with pub/sub between nodes to fan messages out.

## Lab (~10 min)

Build a tiny HTTP server on a raw socket, then break it.

```java
import java.io.*;
import java.net.*;
import java.nio.charset.StandardCharsets;
import java.time.Instant;
import java.util.concurrent.*;

public class TinyHttpServer {
    public static void main(String[] args) throws IOException {
        try (ServerSocket server = new ServerSocket(8088);
             ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            System.out.println("Try: curl -v http://localhost:8088/hello");
            while (true) {
                Socket client = server.accept();
                pool.submit(() -> serve(client));
            }
        }
    }

    static void serve(Socket client) {
        try (client) {
            client.setSoTimeout(10_000);
            var in = new BufferedReader(new InputStreamReader(client.getInputStream(), StandardCharsets.US_ASCII));
            String requestLine = in.readLine();                       // e.g. "GET /hello HTTP/1.1"
            if (requestLine == null) return;
            String header;
            while ((header = in.readLine()) != null && !header.isEmpty()) {
                System.out.println("  " + header);                    // a blank line ends the headers
            }
            String[] parts = requestLine.split(" ");
            boolean found = parts.length == 3 && parts[0].equals("GET") && parts[1].equals("/hello");
            String body = found ? "{\"message\":\"hello\",\"at\":\"" + Instant.now() + "\"}\n" : "{\"error\":\"not found\"}\n";
            byte[] bytes = body.getBytes(StandardCharsets.UTF_8);
            String head = "HTTP/1.1 " + (found ? "200 OK" : "404 Not Found") + "\r\n"
                    + "Content-Type: application/json\r\n"
                    + "Content-Length: " + bytes.length + "\r\n"
                    + "Connection: close\r\n"
                    + "\r\n";
            OutputStream out = client.getOutputStream();
            out.write(head.getBytes(StandardCharsets.US_ASCII));
            out.write(bytes);
            out.flush();
        } catch (IOException e) {
            System.err.println("client failed: " + e);
        }
    }
}
```

1. Run it: `java TinyHttpServer.java`. Then run `curl -v http://localhost:8088/hello`. You get a `200` with JSON,
   and the server prints the request headers curl sent. Try `/nope` and get a `404`. This is all Tomcat does at
   the bottom, before Spring MVC (SPRING-BOOT-6) takes over.
2. **Break the framing.** Delete the `Content-Length` header and the `Connection: close` line, and remove `client`
   from the try-with-resources so the socket stays open. curl now has no way to tell where the body ends, so it
   prints the body and keeps waiting for more (press Ctrl+C). You have also leaked a socket per request. Put them
   back.
3. **See the timeout.** Run `telnet localhost 8088` (or `nc localhost 8088`) and type nothing. After 10 seconds the
   server logs a `SocketTimeoutException` and closes the connection. Remove `setSoTimeout`, and an idle client now
   holds a thread and a descriptor forever.
4. **See refused versus timeout.** Stop the server and run curl again: `Connection refused`, immediately. Then run
   `curl --connect-timeout 3 http://10.255.255.1:8088` (an address that drops packets). It waits 3 seconds and
   times out. Refused is fast; an unreachable host hangs until the connect timeout.
5. Optional: run the echo server and look at the connections with `netstat -an | findstr 9000` (Windows) or
   `ss -tan | grep 9000` (Linux). Find `LISTEN`, `ESTABLISHED` and, after the client quits, `TIME_WAIT`.

## Gotchas

- **No timeouts.** Blocking reads wait forever by default. Set connect and read timeouts on every client, socket,
  JDBC, HTTP and Redis alike.
- **Assuming one write equals one read.** TCP is a byte stream. Frame your messages with a delimiter or a length
  prefix, and loop until you have the whole message.
- **Leaking sockets.** Every socket is a file descriptor. Always close it in try-with-resources, or a busy service
  hits "Too many open files".
- **A new connection per call.** You pay the handshake and TLS every time and pile up `TIME_WAIT`. Use connection
  pools and keep-alive.
- **Unbounded platform threads per connection.** A spike creates thousands of OS threads. Bound the pool, or use
  virtual threads and limit the real bottleneck instead.
- **Blocking inside an event loop.** One slow call in a Netty or WebFlux handler stalls every connection on that
  loop. Move blocking work off the loop.

Typical follow-ups:

- *"How does one server port handle 10,000 clients?"* A strong answer: connections are told apart by the 4-tuple;
  `accept()` returns a new socket per client; then thread per connection (cheap with virtual threads) or an event
  loop with a Selector (epoll); the limits are file descriptors, memory, and downstream capacity.
- *"Your threads are all stuck in socket read. What happened?"* A dependency slowed down and there is no read
  timeout. Fix it with timeouts, then a circuit breaker and a bulkhead (DIST-SYS-3), and check pool sizes.

## Explain it in 2 minutes

Prompt: *"What happens when a Java client calls a server over TCP, and how would you write the server?"*

- A socket is an OS endpoint (IP plus port) behind a file descriptor; a connection is identified by the 4-tuple.
- The server binds and listens, the kernel completes the three-way handshake, and `accept()` returns a new socket
  per client.
- Data is a reliable, ordered byte stream, so the protocol needs framing (newline, length prefix, or HTTP headers
  plus `Content-Length`).
- Concurrency: thread per connection (virtual threads in Java 21) or an NIO Selector event loop (Tomcat NIO, Netty).
- Always set connect and read timeouts, close sockets, and reuse connections through pools and keep-alive.
- Failures: refused (nothing listening), reset (peer sent RST), timeout (slow or unreachable), `TIME_WAIT` (many
  short connections).

## Check yourself

1. A client's `connect()` succeeds, but the server never reads its request. How can that happen?
2. Your protocol writes `"PING"` and then `"PONG"`, and the receiver once got `"PINGPONG"` in one read. Bug or
   expected? How do you fix it?
3. What is the difference between `Connection refused` and a connect timeout?
4. Why do clients pool connections instead of opening one per request?
5. When would you pick an NIO event loop over thread per connection, even with virtual threads available?

### Answers

1. The kernel completes the handshake and queues the connection in the backlog before the application calls
   `accept()`. A single-threaded or overloaded server hasn't accepted it yet.
2. Expected: TCP is a byte stream with no message boundaries. Add framing, either a delimiter (end each message with
   a newline) or a length prefix, and read until you have a full message.
3. Refused: the host answered with an RST because nothing listens on that port, so it fails fast. Connect timeout:
   no answer at all (the host is down, or a firewall drops packets), so the client waits until its timeout.
4. Each new connection costs a TCP handshake (plus TLS), file descriptors, and a `TIME_WAIT` slot on close. Pools and
   keep-alive pay that once and reuse it.
5. When you hold a very large number of long-lived, mostly idle connections (WebSockets, push gateways, proxies),
   or need fine control over framing and backpressure. That is where Netty or WebFlux event loops are designed to
   shine.
