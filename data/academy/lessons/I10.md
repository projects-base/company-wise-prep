## Where we are

DIST-SYS-7 showed how to see what a service is doing in production, and JAVA-JVM-8 showed how to profile
it. Both tell you about traffic you already have. This lesson is about finding the limits *before*
users do: designing a load test that tells the truth, reading its results, and turning them into
capacity numbers.

## The problem

ShopKart's team runs a load test before a sale: 100 users in a loop, on a laptop, against a staging box
with an empty database. Average response is 40 ms, so they call it done. On sale day, real traffic takes
checkout down in nine minutes.

Every step was wrong. The data was too small to stress any query, the laptop may have been the
bottleneck, the average hid the tail, and the test's model of "users" did not match how real traffic
behaves. A load test that gives false comfort is worse than no test at all.

## Kinds of performance test

Each kind answers a different question:

| Test | Shape | Question it answers |
|---|---|---|
| **Smoke** | Tiny load, a minute or two | Does the script and the system work at all? |
| **Load** | Expected peak, held steady | Do we meet the target at normal peak? |
| **Stress** | Keep increasing until it breaks | Where is the limit, and how does it fail? |
| **Spike** | A sudden jump | Does it survive, and does autoscaling keep up? |
| **Soak** | Normal load for hours | Are there leaks or slow degradation? |

Soak tests are the most often skipped, and they are what catch memory leaks, growing tables and
connections that are never returned.

## Start from a target

"Make it fast" cannot pass or fail. A useful target has a load and a limit:

```text
At 500 orders per second, p99 stays under 800 ms and errors stay under 0.1%.
```

Get the load from production data where you can: the peak hour, multiplied by the growth you expect.
Tie the limits to your SLO (DIST-SYS-7). Report percentiles, never only the average.

## Little's Law: the one formula

**Little's Law** links three numbers in any stable system:

```text
concurrency (N)  =  throughput (λ)  ×  time in the system (W)
```

If you serve 500 requests per second and each takes 0.2 seconds, there are on average 100 requests in
flight at any moment. That is useful in three ways:

- **Sizing.** 100 in flight needs at least 100 threads or connections available at each stage that
  holds them for the full time.
- **Finding the ceiling.** With a fixed limit, say a pool of 20 connections held for 50 ms each, the
  maximum throughput is 20 ÷ 0.05 = 400 per second. No amount of extra traffic gets past that.
- **Spotting trouble.** If latency doubles at the same throughput, the requests in flight double too.
  That is how a slow dependency uses up every thread in a service.

## Why latency explodes near capacity

Latency does not rise steadily with load. It stays flat for a long time, then shoots upward:

```text
 latency
    │                                      ╱
    │                                     ╱
    │                                   ╱
    │                               ╱
    │ ────────────────────────
    └───────────────────────────────────── load
                      ~70%     ~90%   100%
```

As a resource gets busy, arrivals increasingly find it occupied and join a queue. Close to full
utilisation, a small increase in traffic makes a large increase in waiting. That is why a system at
85% can feel fine and one at 95% can fall over, and why you need **headroom**. Exactly where the curve
bends depends on your system, so find it with a stress test rather than trusting a rule of thumb.

The test result you most want is that **knee**: the highest load before latency takes off.

## Closed and open models

This is the idea that most separates a useful test from a misleading one.

- **Closed model:** a fixed number of virtual users, each sending a request, waiting for the reply and
  then sending the next. When the server slows down, the load *falls*, because users are stuck waiting.
- **Open model:** new requests arrive at a set rate, regardless of how the server is doing. When the
  server slows down, the requests *keep coming*.

The real internet is mostly open: a million phones do not pause because your server is slow. They keep
sending, and often retry. A closed test politely backs off just when a real system would be getting
hammered, so it makes a struggling service look fine.

## Coordinated omission

That politeness also corrupts the numbers. Suppose the server freezes for one second. A closed client
records **one** slow request, since it was waiting and sent nothing else. Real users arriving during that
second would all have been delayed, but the test never sent those requests, so they are never measured.

This is **coordinated omission**, a term from Gil Tene: the load tool coordinates with the system under
test, and leaves out the worst samples. It can make p99 look fine during a serious stall. The lab
produces exactly that result.

The fix: use an open model, and measure latency from when a request *should* have been sent.

## Gatling

**Gatling** lets you write load tests as code, in Java, and keep them in the repository. It runs an open
model with `injectOpen`, and pass or fail rules can fail a CI build:

```java
public class CheckoutSimulation extends Simulation {
    HttpProtocolBuilder protocol = http.baseUrl("https://staging.shopkart.example");

    ScenarioBuilder checkout = scenario("Checkout")
            .exec(http("Browse").get("/products").check(status().is(200)))
            .pause(1, 3)
            .exec(http("Place order").post("/orders").body(StringBody("{\"sku\":\"BOOK\",\"quantity\":1}"))
                    .asJson().check(status().is(201)));

    {
        setUp(checkout.injectOpen(rampUsersPerSec(1).to(50).during(300), constantUsersPerSec(50).during(600)))
                .protocols(protocol)
                .assertions(global().responseTime().percentile(99.0).lt(800), global().failedRequests().percent().lt(0.1));
    }
}
```

That ramps up over 5 minutes, holds for 10, and fails if p99 goes over 800 ms or more than 0.1% of
requests fail. The `.pause(1, 3)` is **think time**: real users read pages, so without it each virtual
user generates far more load than a person would.

The other tools you will meet are **k6**, with scripts in JavaScript and an easy CI story, and
**JMeter**, an older tool driven largely through a GUI, still common in big companies. The concepts
are the same in all of them, so learn one properly. Whichever you use, check what model it applies,
because JMeter's standard thread groups are closed.

## Making the test realistic

A test only says something about the setup it ran on:

- **Environment:** match production's instance sizes, limits, and topology. Results from a smaller
  environment do not simply scale up.
- **Data volume:** an empty table fits in memory and every query flies. Load production-sized data
  without real personal data, because the plan the database chooses depends on it.
- **Traffic mix:** weight scenarios as production does, such as 90% browsing and 2% checkout.
- **Varied inputs:** one product id repeated forever just tests the cache. Use many, with a realistic
  skew towards popular items.
- **Dependencies:** replace third parties such as payment gateways with a stub that has realistic
  latency, and never load test someone else's system without their agreement.
- **The load generator:** watch its CPU and network. If it is the bottleneck, you are measuring it.
- **Warm-up:** the JVM starts slow, because JIT compilation has not happened yet (JAVA-JVM-1). Ignore the
  first few minutes of results.

## Finding the bottleneck

During the test, watch DIST-SYS-7's dashboard, and look for the **first** thing to saturate:

| Symptom | Usual suspect |
|---|---|
| CPU near 100% | Hot code or GC: profile it (JAVA-JVM-8) |
| CPU low, latency high | Something is waiting: pool, lock, or dependency |
| `hikaricp.connections.pending` above 0 | Database pool, or slow queries holding connections |
| GC pauses growing | Heap pressure from allocation (JAVA-JVM-7) |
| Tomcat threads all busy | Blocking calls; check what they are blocked on |
| Consumer lag rising | Kafka consumers cannot keep up |

Low CPU with high latency is the classic sign: the service is not working hard, it is waiting.

Then change **one thing at a time**, and rerun. A thread dump taken during the slowdown (`jcmd <pid>
Thread.print`) often shows where everyone is stuck. Fix the first bottleneck and the next one appears.
That is normal, so stop once you meet the target.

## From results to capacity

Say one instance holds 120 requests per second at target latency, and peak is expected to be 1,000:

```text
needed for peak        1,000 ÷ 120          = 8.3  → 9 instances
survive losing one AZ  5 per AZ across 3 AZs: lose one, 10 remain → 15 instances
```

The 2 zones left after a failure must still hold 9 instances, so each zone needs 5. Scaling out is
rarely perfectly linear, because the shared database and caches do not grow with your app. So test at the planned size, and check that the **database connection
count** survives it: 15 instances × a pool of 20 is 300 connections, which may exceed the database's limit.

Also check how the system **fails**. Past capacity, a good service sheds load and returns fast `429` or
`503` responses (DIST-SYS-3). A bad one accepts everything, runs out of memory and takes minutes to
recover. Keep pushing past the limit, stop, and confirm that it recovers without help.

## Testing failure on purpose

Load tests assume everything works. **Chaos engineering** deliberately injects faults to check that your
resilience design holds: kill a pod, add 500 ms to a dependency, drop a network link, fail over the
database.

Do it in a controlled way. State a hypothesis first ("if one pod dies, the error rate stays under
0.1%"), start in staging with a small blast radius, have a way to stop, and only move towards production
once you are confident. A retry storm or a timeout that was never tested is much better found on a
Tuesday afternoon. Do this during a load test, because many failures only appear under pressure.

## Lab (~10 min)

A simulated server freezes for one second during a ten-second test. Measure it with a closed client and
an open client, using the same server. Press Run, or save it as `LoadModelLab.java` and run
`java LoadModelLab.java`.

```java
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class LoadModelLab {
    static final long SERVICE_MS = 10;
    static final long TEST_MS = 10_000;
    static final long STALL_START = 5_000;
    static final long STALL_END = 6_000;

    /** When a request that may start at this moment actually begins, given the server's freeze. */
    static long startTime(long ready) {
        return ready >= STALL_START && ready < STALL_END ? STALL_END : ready;
    }

    /** One user who sends, waits for the reply, then sends again. */
    static List<Long> closedClient() {
        List<Long> latencies = new ArrayList<>();
        long now = 0;
        while (now < TEST_MS) {
            long finished = startTime(now) + SERVICE_MS;
            latencies.add(finished - now);
            now = finished;
        }
        return latencies;
    }

    /** Requests arrive on schedule, whatever the server is doing. Latency counts from the arrival. */
    static List<Long> openClient(long intervalMs) {
        List<Long> latencies = new ArrayList<>();
        long serverFree = 0;
        for (long arrival = 0; arrival < TEST_MS; arrival += intervalMs) {
            long finished = startTime(Math.max(arrival, serverFree)) + SERVICE_MS;
            latencies.add(finished - arrival);
            serverFree = finished;
        }
        return latencies;
    }

    static void report(String name, List<Long> latencies) {
        List<Long> sorted = new ArrayList<>(latencies);
        Collections.sort(sorted);
        long p50 = sorted.get((int) Math.ceil(0.50 * sorted.size()) - 1);
        long p99 = sorted.get((int) Math.ceil(0.99 * sorted.size()) - 1);
        long slow = sorted.stream().filter(ms -> ms > 100).count();
        System.out.printf("%-8s requests=%-5d p50=%-5d p99=%-5d max=%-5d over 100 ms=%d%n",
                name, sorted.size(), p50, p99, sorted.get(sorted.size() - 1), slow);
    }

    public static void main(String[] args) {
        report("closed", closedClient());
        report("open", openClient(20));
    }
}
```

**What to observe:**

1. The closed client reports a p99 of 10 ms: a perfect result, with a single slow request hidden in the
   max. That is coordinated omission.
2. The open client, on the same server, shows a p99 close to a full second, and a large number of slow
   requests. Those people really waited.
3. The server's queue takes about as long to drain as the freeze lasted, because there is little spare
   capacity to catch up with. The damage outlasts the fault.
4. **Change the load:** try `openClient(12)`, then `openClient(11)`. The server goes from 50% busy to
   about 83% and 91%, and slow requests jump from 91 to 417 and 455. That is the curve from earlier:
   the same one-second fault hurts far more people when there is little headroom to recover with.

## Gotchas

- **Empty or tiny test data.** Everything is cached, so queries look fast. Use production-sized data.
- **Closed-model tests for internet traffic.** Load falls as the system struggles, which hides the
  failure. Use an open model.
- **Reporting the average.** Use p95 and p99, plus the error rate.
- **Counting failures as fast responses.** A quick `500` improves latency numbers. Check errors first.
- **Results during warm-up.** JIT and cold caches distort them. Discard the start.
- **The load generator is the bottleneck.** Watch its CPU, and spread it across machines if needed.

## In interviews

Asked as "How would you load test this service?", "How do you find a bottleneck?", "How many instances
do you need?" and "What is the difference between load and stress testing?". Bank:
[How would you optimise a slow API?](#/q/optimize-slow-api).

**Follow-up: "CPU is at 20% but latency is high. What's going on?"** The service is waiting, not
working. Look at the connection pool, thread pool, locks and downstream calls. Take a thread dump to see
where the threads are parked, and use Little's Law to check whether a pool size caps throughput.

**Follow-up: "Staging is smaller than production. Is the test still useful?"** Yes, for finding
regressions, bottlenecks and per-instance limits, but do not extrapolate blindly. Before a major event,
test at the real size, or test in production in a controlled way, with synthetic traffic that is
clearly marked.

## Explain it in 2 minutes

"How would you prove a service is ready for a big sale?"

- Set a target from real data: requests per second, p99 and error rate.
- Use realistic data volume, traffic mix and varied inputs, with third parties stubbed.
- Run load, stress, spike and soak tests, using an open model.
- Watch for the first resource to saturate, fix one thing at a time, and rerun.
- Find the knee, calculate capacity with headroom for losing a zone, and check database connections.
- Confirm it fails gracefully and recovers, and test faults under load.

## Check yourself

1. What is the difference between a stress test and a soak test?
2. A pool has 10 connections, each held for 20 ms. What is the maximum throughput?
3. Why does latency rise sharply as a system nears full utilisation?
4. What is coordinated omission?
5. CPU is low but latency is high. What does that suggest?

### Answers

1. Stress increases load until the system breaks, to find its limit. Soak holds normal load for hours,
   to reveal leaks and slow degradation.
2. 10 ÷ 0.02 = 500 per second.
3. Arrivals are more and more likely to find the resource busy, so queues build, and waiting time grows
   much faster than load.
4. A closed test stops sending while the server is stalled, so the requests that real users would have
   sent during that stall never get measured, and the percentiles look better than reality.
5. The service is waiting on something: a pool, a lock or a dependency, not doing CPU work.
