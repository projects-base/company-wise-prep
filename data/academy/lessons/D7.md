## Where we are

From D5 you know the trip a request takes: Tomcat hands it to a chain of servlet **filters**, then to the `DispatcherServlet`, which finds your controller. This lesson puts a guard on that trip. Spring Security is just more filters, placed in front of the `DispatcherServlet`. By the end you will have a JWT-protected API, and you will be able to say which filter rejected a request and why.

## The problem

Here is this repo's `ApiController` today:

```java
@PutMapping("/questions/{slug}/progress")
public ProgressService.View updateProgress(@PathVariable String slug, @Valid @RequestBody ProgressRequest req) { ... }
```

Anyone who can reach port 8090 can change Akhil's progress. The app gets away with this only because `application.yml` binds it to `127.0.0.1`. Once you deploy it, every endpoint needs to answer two questions:

1. **Who is calling?** This is called **authentication**: proving identity.
2. **Are they allowed to do this?** This is called **authorization**: checking permission.

The naive fix is an `if` statement at the top of every controller method. That repeats the same check in many places, it is easy to forget once, and it runs too late. By the time the controller runs, the request body has already been parsed and validated. Security checks belong *before* any of that, in one place, applied to every request.

## Filters are the right place

A **servlet filter** is an object that wraps a request. It can inspect the request, reject it, or pass it on to the next link in the chain. You met filters in D5. Here is a tiny one:

```java
public class ApiKeyFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        if (!"secret".equals(req.getHeader("X-Api-Key"))) {
            res.sendError(401);
            return;                       // never reaches the DispatcherServlet
        }
        chain.doFilter(req, res);         // let it through
    }
}
```

**The rule:** security is a *cross-cutting* concern, meaning it applies to every endpoint and not to one feature. It has to happen before your code runs. A chain of filters is exactly that kind of hook. Spring Security is a well-tested, configurable version of the filter above, split into many small filters that each do one job.

## How Spring Security plugs in: three layers

Tomcat knows nothing about Spring beans, yet the security filters need to be beans so they can get dependencies injected. Spring Security bridges that gap with three layers:

```text
Tomcat filter chain
  ├─ CharacterEncodingFilter
  ├─ DelegatingFilterProxy ("springSecurityFilterChain")   <- a plain servlet filter Tomcat knows
  │     └─ FilterChainProxy (a Spring bean)                 <- picks ONE SecurityFilterChain
  │           └─ SecurityFilterChain #1 (matches /api/**)   <- your configured list of filters
  │                 SecurityContextHolderFilter
  │                 CsrfFilter
  │                 BearerTokenAuthenticationFilter
  │                 ExceptionTranslationFilter
  │                 AuthorizationFilter
  └─ DispatcherServlet
```

- **`DelegatingFilterProxy`** is registered with Tomcat and forwards each request to a Spring bean.
- **`FilterChainProxy`** holds one or more `SecurityFilterChain`s. For each request it uses the **first** chain whose matcher fits.
- A **`SecurityFilterChain`** is the ordered list of security filters you configure.

Spring Boot registers all of this for you as soon as the security starter is on the classpath. With no configuration at all, Boot locks every endpoint behind a generated password, which it logs at startup.

## Authentication: who are you?

Spring Security represents "who is calling" as an **`Authentication`** object. It holds a principal (the user), credentials, and a list of **`GrantedAuthority`** values (permission strings such as `SCOPE_progress:write`).

That object lives in the **`SecurityContextHolder`**. By default the holder is a `ThreadLocal`, a per-thread storage slot. That works because the request runs on a single Tomcat thread from start to finish.

Here is how an authentication filter fills that slot:

```text
request ──► BearerTokenAuthenticationFilter
              reads "Authorization: Bearer <token>"
              builds an unauthenticated token object
              │
              ▼
           AuthenticationManager (ProviderManager)
              asks each AuthenticationProvider "can you handle this?"
              │
              ▼
           JwtAuthenticationProvider ──► JwtDecoder (verify signature, expiry)
              │ success
              ▼
           SecurityContextHolder.getContext().setAuthentication(auth)
```

**The rule:** one filter pulls the credentials out of the request. An `AuthenticationManager` checks them. The result is stored in the `SecurityContextHolder` for the rest of the request. If there is no token at all, the filter simply passes the request on, unauthenticated. Rejecting it is authorization's job.

## Authorization: may you do this?

Near the end of the chain, **`AuthorizationFilter`** checks the request against the rules you declared:

```java
http.authorizeHttpRequests(auth -> auth
        .requestMatchers("/actuator/health/**").permitAll()
        .requestMatchers(HttpMethod.PUT, "/api/**").hasAuthority("SCOPE_progress:write")
        .anyRequest().authenticated());
```

The rules are checked top to bottom and the **first match wins**, so put the specific rules first.

For checks that depend on method arguments, add `@EnableMethodSecurity` to a configuration class and annotate the service method:

```java
@PreAuthorize("hasAuthority('SCOPE_admin')")
public Summary importAll() { ... }
```

Method security is implemented with AOP proxies (D3), so the self-invocation trap applies to it too.

## 401 versus 403: the ExceptionTranslationFilter

When `AuthorizationFilter` refuses a request, it throws an exception. **`ExceptionTranslationFilter`** sits just before it and turns that exception into an HTTP response:

- No authentication, or an anonymous user: the request goes to the **`AuthenticationEntryPoint`**, which returns **401 Unauthorized**. A resource server also adds a `WWW-Authenticate: Bearer` header.
- Authenticated but lacking permission: the **`AccessDeniedHandler`** returns **403 Forbidden**.

A 401 means "I don't know who you are." A 403 means "I know who you are, and the answer is no."

## JWT in one picture

A **JWT** (JSON Web Token) is three Base64URL-encoded parts joined by dots: `header.payload.signature`.

- The **payload** holds **claims**: facts about the caller, such as `sub` (subject), `exp` (expiry), `iss` (issuer) and `scope`.
- The **signature** proves the token came from whoever holds the signing key and has not been edited.

The flow involves three parties. An **authorization server** (Keycloak, Auth0, Entra ID and so on) logs the user in and *issues* the token. Your API is a **resource server**: it never sees a password. It only *verifies* tokens.

```text
client ──login──► authorization server ──JWT──► client
client ──"Authorization: Bearer <JWT>"──► your API (resource server)
your API: fetch issuer's public keys (JWKS, cached) → verify signature → check exp/iss → trust claims
```

The analogy is a passport. The border guard checks the stamp and the expiry date and never phones the issuing country. The analogy breaks on revocation. A passport can be flagged in a database, but a JWT stays valid until its `exp` time unless you add extra machinery. That is why access tokens are kept short-lived.

## Turning your app into a resource server

You need two things: the `spring-boot-starter-oauth2-resource-server` dependency (Boot 4 also publishes it as `spring-boot-starter-security-oauth2-resource-server`) and one property:

```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://login.example.com/realms/prep
```

Boot's resource-server auto-configuration builds a `JwtDecoder` from that issuer. The decoder discovers the issuer's keys and validates `iss` and `exp`. Then write your own chain:

```java
@Configuration
@EnableMethodSecurity
class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/actuator/health/**").permitAll()
                .anyRequest().authenticated())
            .oauth2ResourceServer(rs -> rs.jwt(Customizer.withDefaults()))
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .csrf(csrf -> csrf.disable());   // safe ONLY because no cookies carry credentials
        return http.build();
    }
}
```

By default, each entry in the `scope` (or `scp`) claim becomes an authority with the prefix `SCOPE_`. If your identity provider puts roles in a different claim, configure a `JwtAuthenticationConverter` whose `JwtGrantedAuthoritiesConverter` has `setAuthoritiesClaimName("roles")` and `setAuthorityPrefix("ROLE_")`. Boot can also do this through the `spring.security.oauth2.resourceserver.jwt.authorities-claim-name` and `authority-prefix` properties.

## Lab (~10 min)

This lab runs offline. Instead of a real identity provider, you sign tokens yourself with an HMAC key.

1. Add `spring-boot-starter-oauth2-resource-server` and, for tests, `org.springframework.security:spring-security-test`.
2. Add the `SecurityConfig` above, plus a dev-only decoder bean. When you define your own `JwtDecoder`, Boot backs off and you don't need the `issuer-uri` property:

```java
@Bean
JwtDecoder jwtDecoder(@Value("${demo.jwt.secret}") String secret) {
    SecretKey key = new SecretKeySpec(secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256");
    return NimbusJwtDecoder.withSecretKey(key).macAlgorithm(MacAlgorithm.HS256).build();
}
```

   Set `demo.jwt.secret` to any string of at least 32 characters.

3. Write this test:

```java
@SpringBootTest(properties = "demo.jwt.secret=0123456789abcdef0123456789abcdef")
@AutoConfigureMockMvc
class SecurityLabTest {

    @Autowired MockMvc mvc;

    String token(String scope) {
        SecretKey key = new SecretKeySpec("0123456789abcdef0123456789abcdef".getBytes(StandardCharsets.UTF_8), "HmacSHA256");
        JwtEncoder enc = NimbusJwtEncoder.withSecretKey(key).algorithm(MacAlgorithm.HS256).build();
        JwtClaimsSet claims = JwtClaimsSet.builder()
                .subject("akhil").claim("scope", scope)
                .issuedAt(Instant.now()).expiresAt(Instant.now().plusSeconds(300)).build();
        return enc.encode(JwtEncoderParameters.from(JwsHeader.with(MacAlgorithm.HS256).build(), claims)).getTokenValue();
    }

    @Test void noToken_is401() throws Exception {
        mvc.perform(get("/api/companies")).andExpect(status().isUnauthorized());
    }

    @Test void validToken_is200() throws Exception {
        mvc.perform(get("/api/companies").header("Authorization", "Bearer " + token("read")))
           .andExpect(status().isOk());
    }

    @Test void shortcut_withoutSigning() throws Exception {   // SecurityMockMvcRequestPostProcessors.jwt()
        mvc.perform(get("/api/companies").with(jwt())).andExpect(status().isOk());
    }
}
```

**Observe:**

- Set `logging.level.org.springframework.security=TRACE` and run `noToken_is401`. The log lists every filter in the chain in order, and shows `AuthorizationFilter` denying the request.
- **Break it:** change one character in the token and expect 401 with `invalid_token` in the `WWW-Authenticate` header. Then set `expiresAt` in the past and expect 401 again.
- **Bonus:** add `.requestMatchers(HttpMethod.PUT, "/api/**").hasAuthority("SCOPE_progress:write")` and call a `PUT` with scope `read`. You should get 403, not 401.

## Gotchas

- **Rule order.** `anyRequest()` must come last, and an early broad matcher shadows any later specific ones. Write the specific rules first.
- **Disabling CSRF blindly.** CSRF (cross-site request forgery) attacks exploit browsers that send cookies automatically. Disable CSRF protection only for stateless APIs that authenticate with a header token. Keep it on for cookie or session login.
- **`hasRole("ADMIN")` versus `hasAuthority("ADMIN")`.** `hasRole` adds the `ROLE_` prefix for you. JWT scopes arrive as `SCOPE_x`. A mismatched prefix gives a 403 that looks mysterious.
- **The `SecurityContext` is thread-local.** Code running in `@Async` methods or your own executors does not see the user unless you propagate the context, for example with `DelegatingSecurityContextExecutor`.
- **Filter-chain 401s never reach `@ControllerAdvice`.** They happen before the `DispatcherServlet` runs. Customise them with an `AuthenticationEntryPoint` or `AccessDeniedHandler` instead.
- **Long-lived JWTs.** A JWT cannot be revoked by default. Keep access tokens short-lived (minutes) and use refresh tokens for longer sessions.

## In interviews

Typical prompts are "Walk me through how Spring Security authenticates a request", "Authentication vs authorization?", "How does a resource server validate a JWT without calling the auth server?" and "401 vs 403?". Bank: [OAuth and JWT tokens](#/q/oauth-and-jwt), [Preventing SQL Injection](#/q/sql-injection-prevention) (often comes up in the same security round).

**Follow-up: "How would you revoke a JWT?"** A strong answer says that a JWT is valid until `exp`, so you keep tokens short-lived and use refresh tokens. Where you truly need revocation, you keep a deny-list of token ids (`jti`), or you switch to opaque tokens with introspection, which costs a network call per request.

**Follow-up: "Why not just check the token in an interceptor?"** Interceptors run after the `DispatcherServlet` has chosen a handler. That is later than a filter, and it misses static resources and error dispatches.

## Explain it in 2 minutes

*"What happens when a request with a bearer token hits a Spring Boot API?"*

- Tomcat's filter chain reaches `DelegatingFilterProxy`, which hands the request to `FilterChainProxy`, which picks the first matching `SecurityFilterChain`.
- `BearerTokenAuthenticationFilter` extracts the token and passes it to the `AuthenticationManager`, then `JwtAuthenticationProvider`, then `JwtDecoder`. The decoder checks the signature against the issuer's cached JWKS, then `exp` and `iss`.
- On success, an `Authentication` with its authorities (`SCOPE_*`) goes into the thread-local `SecurityContextHolder`.
- `AuthorizationFilter` applies the URL rules (first match wins). `@PreAuthorize` applies method-level rules through a proxy.
- On failure, `ExceptionTranslationFilter` turns the exception into a 401 (unknown caller) or a 403 (known caller, not allowed).
- The setup is stateless: no session, CSRF off, short-lived tokens.

## Check yourself

1. Why does Spring Security need `DelegatingFilterProxy` at all?
2. A request has no `Authorization` header. Which filter produces the 401, and how?
3. Your JWT has `"scope": "admin"`, but `hasRole("ADMIN")` returns 403. Why?
4. When is it safe to disable CSRF?
5. Why does a `@ControllerAdvice` not see a 401 from an invalid token?

### Answers

1. Tomcat creates filters itself and knows nothing about Spring. The proxy is a plain filter that looks up the `FilterChainProxy` bean, so the security filters can be Spring beans with injected dependencies.
2. `BearerTokenAuthenticationFilter` passes the request through unauthenticated. `AuthorizationFilter` then denies the anonymous user, and `ExceptionTranslationFilter` calls the `AuthenticationEntryPoint`, which writes the 401.
3. The scope becomes the authority `SCOPE_admin`, but `hasRole("ADMIN")` looks for `ROLE_ADMIN`. Use `hasAuthority("SCOPE_admin")`, or remap the claim and prefix with a `JwtAuthenticationConverter`.
4. When no credential travels automatically with the browser. In practice that means a stateless API that authenticates with an `Authorization` header and uses no session cookie.
5. The rejection happens in the filter chain, before the `DispatcherServlet`, and `@ControllerAdvice` only handles exceptions thrown inside the `DispatcherServlet`.
