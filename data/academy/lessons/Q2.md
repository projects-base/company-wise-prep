## Where we are

From Q1 you can read rows, join tables along their foreign keys, find rows with no match, and avoid
the NULL traps. Every query so far returned one output row per input row, or per joined pair. This
lesson adds summarising: totals, counts and averages per group. It also adds queries inside queries,
which you need for questions like "above average".

## The problem

The trading team asks three things:

1. "What is the **turnover** (total amount staked) per punter?"
2. "Which punters are net losers on settled bets?"
3. "Who staked more than the average punter?"

None of these is a list of rows. Each needs rows **collapsed** into a single number per group, and
the third compares each group with a number computed from all the groups. That takes aggregation,
`GROUP BY`, `HAVING`, and subqueries or CTEs.

## Aggregate functions

An **aggregate function** takes many rows and returns one value.

```sql
SELECT COUNT(*)                AS bets,
       COUNT(payout)           AS settled_with_payout,
       COUNT(DISTINCT user_id) AS punters,
       SUM(stake)              AS turnover,
       ROUND(AVG(stake), 2)    AS avg_stake,
       MIN(stake)              AS min_stake,
       MAX(stake)              AS max_stake
FROM bets;
```

| bets | settled_with_payout | punters | turnover | avg_stake | min_stake | max_stake |
|---|---|---|---|---|---|---|
| 20 | 16 | 5 | 655.00 | 32.75 | 5.00 | 100.00 |

Read the first two columns carefully. `COUNT(*)` counts **rows**: 20. `COUNT(payout)` counts rows
where `payout` is **not NULL**: 16, because the 4 open bets have no payout. All aggregates except
`COUNT(*)` **skip NULLs**. `AVG(payout)` would average only the 16 settled bets, not divide by 20.

`ROUND(x, 2)` keeps two decimals. Without it, the two engines print `AVG` with different numbers of
digits.

## GROUP BY: one row per group

`GROUP BY status` sorts the rows into buckets, one per distinct status. The aggregates are then
computed once per bucket.

```sql
SELECT status, COUNT(*) AS bets, SUM(stake) AS turnover
FROM bets
GROUP BY status
ORDER BY status;
```

| status | bets | turnover |
|---|---|---|
| LOST | 7 | 180.00 |
| OPEN | 4 | 70.00 |
| VOID | 1 | 5.00 |
| WON | 8 | 400.00 |

```text
 bets (20 rows)            GROUP BY status            one row per group
 ┌──────┬───────┐          ┌── LOST: 7 rows ──┐       LOST  7  180.00
 │ WON  │ 20.00 │   ──►    ├── OPEN: 4 rows ──┤  ──►  OPEN  4   70.00
 │ LOST │ 15.00 │          ├── VOID: 1 row  ──┤       VOID  1    5.00
 │ ...  │  ...  │          └── WON:  8 rows ──┘       WON   8  400.00
```

Now question 1, with a join so you can show names:

```sql
SELECT u.id, u.name, COUNT(*) AS bets, SUM(b.stake) AS turnover, SUM(b.payout) AS paid_out
FROM bets b
JOIN users u ON u.id = b.user_id
GROUP BY u.id, u.name
ORDER BY turnover DESC, u.id;
```

| id | name | bets | turnover | paid_out |
|---|---|---|---|---|
| 3 | Chloe | 4 | 220.00 | 395.00 |
| 2 | Ben | 5 | 185.00 | 88.00 |
| 5 | Ella | 2 | 115.00 | 180.00 |
| 1 | Asha | 6 | 110.00 | 115.00 |
| 4 | Dev | 3 | 25.00 | 5.00 |

**The rule:** every column in `SELECT` must either be in `GROUP BY` or be inside an aggregate.
Otherwise the database can't know which of the group's many values to show. PostgreSQL relaxes this
in one case. If you group by a table's primary key, it lets you select that table's other columns,
because they are determined by the key. H2 accepted the same query in our run. In an interview, list
`u.id, u.name` anyway: it is unambiguous on every database.

## HAVING: filter the groups

`WHERE` filters **rows before** grouping. `HAVING` filters **groups after** grouping, so it can test
an aggregate.

```sql
SELECT user_id, COUNT(*) AS bets
FROM bets
GROUP BY user_id
HAVING COUNT(*) >= 4
ORDER BY user_id;
```

| user_id | bets |
|---|---|
| 1 | 6 |
| 2 | 5 |
| 3 | 4 |

Question 2 uses both. "Settled" is a row condition, so it goes in `WHERE`. "Net loser" is a group
condition, so it goes in `HAVING`.

```sql
SELECT user_id, SUM(payout - stake) AS profit
FROM bets
WHERE status IN ('WON', 'LOST', 'VOID')
GROUP BY user_id
HAVING SUM(payout - stake) < 0
ORDER BY profit;
```

| user_id | profit |
|---|---|
| 2 | -72.00 |
| 4 | -20.00 |

## The logical order of evaluation

You write `SELECT` first, but the database evaluates it near the end. The **logical order** (the
order the result is defined by, not necessarily how the engine runs it) is:

```text
 1. FROM / JOIN   build the joined rows
 2. WHERE         drop rows
 3. GROUP BY      form groups
 4. HAVING        drop groups
 5. SELECT        compute output columns and aliases (window functions run here, Q3)
 6. ORDER BY      sort
 7. LIMIT         cut
```

Most "why doesn't this work?" errors in SQL come from this order. An alias made in step 5 doesn't
exist yet in step 2:

```sql
SELECT id, payout - stake AS profit FROM bets WHERE profit > 0;
```

```text
ERROR: column "profit" does not exist
```

Repeat the expression in `WHERE`, or compute it in a subquery or CTE first (below). `ORDER BY` runs
after `SELECT`, so `ORDER BY profit` is fine. PostgreSQL and H2 also accept an alias in `GROUP BY`,
but standard SQL doesn't, so repeat the expression there when you want portability.

## CASE: if-then inside a query

A **CASE expression** returns a value chosen by conditions, like a Java `switch` expression. The
first true `WHEN` wins, `ELSE` is the fallback, and with no `ELSE` the result is `NULL`.

```sql
SELECT id, stake, status,
       CASE WHEN stake >= 50 THEN 'high'
            WHEN stake >= 20 THEN 'medium'
            ELSE 'low' END AS stake_band
FROM bets
WHERE user_id = 2
ORDER BY id;
```

| id | stake | status | stake_band |
|---|---|---|---|
| 7 | 50.00 | LOST | high |
| 8 | 50.00 | LOST | high |
| 9 | 20.00 | LOST | medium |
| 10 | 40.00 | WON | medium |
| 11 | 25.00 | OPEN | medium |

Put a CASE inside `SUM` and you get **conditional aggregation**: several counts from one pass over
the table.

```sql
SELECT user_id,
       COUNT(*)                                        AS bets,
       SUM(CASE WHEN status = 'WON'  THEN 1 ELSE 0 END) AS won,
       SUM(CASE WHEN status = 'LOST' THEN 1 ELSE 0 END) AS lost
FROM bets
GROUP BY user_id
ORDER BY user_id;
```

| user_id | bets | won | lost |
|---|---|---|---|
| 1 | 6 | 3 | 2 |
| 2 | 5 | 1 | 3 |
| 3 | 4 | 3 | 0 |
| 4 | 3 | 0 | 2 |
| 5 | 2 | 1 | 0 |

Q4 builds pivot tables out of exactly this.

## Aggregating across joins

**GGR** (gross gaming revenue) is what the bookmaker keeps: stakes minus payouts on settled bets.
GGR per sport needs the Q1 join chain plus a `GROUP BY`:

```sql
SELECT sp.name AS sport,
       SUM(b.stake)            AS settled_stake,
       SUM(b.payout)           AS paid_out,
       SUM(b.stake - b.payout) AS ggr
FROM bets b
JOIN selections s ON s.id = b.selection_id
JOIN markets m    ON m.id = s.market_id
JOIN events e     ON e.id = m.event_id
JOIN sports sp    ON sp.id = e.sport_id
WHERE b.status <> 'OPEN'
GROUP BY sp.name
ORDER BY ggr DESC;
```

| sport | settled_stake | paid_out | ggr |
|---|---|---|---|
| Tennis | 120.00 | 203.00 | -83.00 |
| Football | 465.00 | 580.00 | -115.00 |

The punters won in this small seed, so GGR is negative. Horse Racing doesn't appear because all its
bets are still open.

Two join-plus-aggregate traps are worth knowing by heart.

**Trap 1: `COUNT(*)` after a LEFT JOIN counts the NULL row.**

```sql
SELECT u.name, COUNT(*) AS count_star, COUNT(b.id) AS count_bets
FROM users u
LEFT JOIN bets b ON b.user_id = u.id
GROUP BY u.id, u.name
ORDER BY u.id;
```

| name | count_star | count_bets |
|---|---|---|
| Asha | 6 | 6 |
| Ben | 5 | 5 |
| Chloe | 4 | 4 |
| Dev | 3 | 3 |
| Ella | 2 | 2 |
| Finn | 1 | 0 |
| Gita | 1 | 0 |

Finn has no bets, but the LEFT JOIN still gives him one row (with NULL bet columns), and `COUNT(*)`
counts it. Count a column from the optional side, `COUNT(b.id)`.

**Trap 2: fan-out.** Join a user to their bets *and* their deposits, and each bet row pairs with
every deposit row. Ben has 5 bets and 2 deposits, so the join makes 10 rows, and both sums are
inflated:

```sql
SELECT u.name, SUM(b.stake) AS turnover, SUM(w.amount) AS deposits
FROM users u
JOIN bets b ON b.user_id = u.id
JOIN wallet_transactions w ON w.user_id = u.id AND w.type = 'DEPOSIT'
WHERE u.name = 'Ben'
GROUP BY u.id, u.name;
```

| name | turnover | deposits |
|---|---|---|
| Ben | 370.00 | 1500.00 |

His real turnover is 185.00 and his real deposits are 300.00. The fix is to **aggregate each child
table on its own first, then join the totals**. That needs a query inside a query.

## Subqueries

A **subquery** is a query in parentheses inside another query. There are four common shapes.

**Scalar subquery: returns one value.** "Bets above the average stake":

```sql
SELECT id, user_id, stake
FROM bets
WHERE stake > (SELECT AVG(stake) FROM bets)
ORDER BY stake DESC, id;
```

| id | user_id | stake |
|---|---|---|
| 14 | 3 | 100.00 |
| 19 | 5 | 100.00 |
| 7 | 2 | 50.00 |
| 8 | 2 | 50.00 |
| 12 | 3 | 50.00 |
| 13 | 3 | 50.00 |
| 10 | 2 | 40.00 |

The average is 32.75. You can't write `WHERE stake > AVG(stake)`, because aggregates aren't allowed
in `WHERE` (step 2 runs before grouping).

**Correlated subquery: refers to the outer row**, so conceptually it runs once per outer row. "Each
user's biggest bet":

```sql
SELECT b.user_id, b.id, b.stake
FROM bets b
WHERE b.stake = (SELECT MAX(b2.stake) FROM bets b2 WHERE b2.user_id = b.user_id)
ORDER BY b.user_id, b.id;
```

| user_id | id | stake |
|---|---|---|
| 1 | 5 | 30.00 |
| 2 | 7 | 50.00 |
| 2 | 8 | 50.00 |
| 3 | 14 | 100.00 |
| 4 | 16 | 10.00 |
| 4 | 17 | 10.00 |
| 5 | 19 | 100.00 |

Ties come back as two rows (Ben, Dev). Whether that's right is a question to ask the interviewer.

**`IN` and `EXISTS`: membership.** "Users who have bet on Tennis" (sport 2):

```sql
SELECT u.name
FROM users u
WHERE u.id IN (
  SELECT b.user_id
  FROM bets b
  JOIN selections s ON s.id = b.selection_id
  JOIN markets m    ON m.id = s.market_id
  JOIN events e     ON e.id = m.event_id
  WHERE e.sport_id = 2)
ORDER BY u.id;
```

| name |
|---|
| Asha |
| Ben |
| Chloe |
| Dev |

The `EXISTS` form puts `AND b.user_id = u.id` inside the subquery and returns the same four names.
For the positive case, `IN` and `EXISTS` are equivalent, and PostgreSQL usually plans them the same
way. For the negative case, use `NOT EXISTS` (Q1, Trap 3).

**Derived table: a subquery in `FROM`**, used like a temporary table. It must have an alias.
"Average turnover per punter" means average the per-user totals, not the bets:

```sql
SELECT ROUND(AVG(turnover), 2) AS avg_turnover_per_punter
FROM (SELECT user_id, SUM(stake) AS turnover FROM bets GROUP BY user_id) t;
```

| avg_turnover_per_punter |
|---|
| 131.00 |

## CTEs: name your steps

A **CTE** (common table expression) is a named subquery written up front with `WITH name AS (…)`.
Later steps, and the main query, can refer to it by name. It does the same job as a derived table,
but it reads top to bottom, like small functions in Java.

Question 3, "punters who staked more than the average punter":

```sql
WITH per_user AS (
  SELECT user_id, SUM(stake) AS turnover
  FROM bets
  GROUP BY user_id
),
avg_turnover AS (
  SELECT AVG(turnover) AS avg_t FROM per_user
)
SELECT u.name, p.turnover
FROM per_user p
JOIN users u ON u.id = p.user_id
CROSS JOIN avg_turnover a
WHERE p.turnover > a.avg_t
ORDER BY p.turnover DESC;
```

| name | turnover |
|---|---|
| Chloe | 220.00 |
| Ben | 185.00 |

`CROSS JOIN` pairs every row with every row. Here the right side has one row (the average), so it
just attaches the average to each user. Note the second CTE reads from the first.

And here is the fan-out fix: aggregate each table in its own CTE, then LEFT JOIN the totals to
`users`.

```sql
WITH stakes AS (
  SELECT user_id, SUM(stake) AS turnover FROM bets GROUP BY user_id
),
deposits AS (
  SELECT user_id, SUM(amount) AS deposited
  FROM wallet_transactions WHERE type = 'DEPOSIT' GROUP BY user_id
)
SELECT u.name, s.turnover, d.deposited
FROM users u
LEFT JOIN stakes s   ON s.user_id = u.id
LEFT JOIN deposits d ON d.user_id = u.id
ORDER BY u.id;
```

| name | turnover | deposited |
|---|---|---|
| Asha | 110.00 | 100.00 |
| Ben | 185.00 | 300.00 |
| Chloe | 220.00 | 300.00 |
| Dev | 25.00 | 50.00 |
| Ella | 115.00 | 250.00 |
| Finn | NULL | 50.00 |
| Gita | NULL | NULL |

Each CTE has at most one row per user, so the joins can't multiply anything.

**Performance note.** Since PostgreSQL 12, a CTE that is referenced once (and has no side effects)
is folded into the main query and optimised with it. A CTE referenced more than once is computed
once and stored by default. `WITH x AS MATERIALIZED (…)` or `NOT MATERIALIZED` overrides this.
Before version 12, every CTE was stored, which acted as an "optimisation fence". You may hear that
phrase in interviews.

## Gotchas

- **`COUNT(col)` skips NULLs; `COUNT(*)` doesn't.** After a LEFT JOIN, count a column from the
  optional table, or every unmatched row counts as 1.
- **Aggregates ignore NULLs.** `AVG(payout)` averages only settled bets. If NULL should mean 0, write
  `AVG(COALESCE(payout, 0))`, and say which one you meant.
- **An alias can't be used in `WHERE`.** `WHERE` runs before `SELECT`. Repeat the expression or wrap
  the query in a CTE.
- **Aggregate conditions go in `HAVING`, row conditions in `WHERE`.** Filtering rows in `HAVING` is
  legal for grouped columns but wastes work, because the rows are grouped first and dropped after.
- **Fan-out:** joining two one-to-many children of the same parent multiplies rows and inflates
  `SUM`/`COUNT`. Aggregate each child in its own CTE first. `COUNT(DISTINCT …)` hides the symptom
  only for counts, not for sums.
- **Integer division:** in both engines, `3 / 4` is `0`. Use `100.0 * a / b` or cast to `NUMERIC`.

## In interviews

Aggregation is in almost every SQL round. Classic shapes:

- "Departments with at least N employees" or "managers with at least 5 reports": `GROUP BY` plus
  `HAVING` (LeetCode 570).
- "Highest salary in each department" (LeetCode 184): a correlated subquery or a join to a per-group
  `MAX`. Q3 gives you the window-function version.
- "Cancellation rate per day" (LeetCode 262, Trips and Users): conditional aggregation with a
  `CASE`, after filtering with joins.

[DB indexing, partitioning and sharding](#/q/db-indexing-partitioning-sharding) and
[RDBMS scaling vs NoSQL](#/q/rdbms-scaling-vs-nosql) are where these aggregate queries meet scale.
A `GROUP BY` over a billion-row `bets` table is why reporting goes to replicas or pre-aggregated
tables (Q8).

**Typical follow-up:** "Your total looks too big. Why?" A strong answer suspects fan-out right away,
checks the row count before grouping, and moves each child aggregation into its own CTE.

**Another follow-up:** "WHERE or HAVING?" Explain the logical order and put each condition at the
earliest step that can evaluate it.

## Explain it in 2 minutes

*"Walk me through how a query with GROUP BY and HAVING is evaluated."*

1. The logical order is FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.
2. WHERE removes rows before grouping. HAVING removes groups after, so only HAVING can test
   aggregates.
3. After GROUP BY, each SELECT column must be grouped or aggregated.
4. Aggregates skip NULLs, except `COUNT(*)`.
5. SELECT aliases exist only from step 5 on: usable in ORDER BY, not in WHERE.
6. For multi-step logic, use CTEs, and aggregate each child table separately to avoid fan-out.

3. What's the difference between a correlated and an uncorrelated subquery?

### Answers

1. 20 and 16. `COUNT(*)` counts rows. `COUNT(settled_at)` skips the 4 open bets, whose `settled_at`
   is NULL.
2. `WHERE` runs before grouping, so no aggregate exists yet. Use `GROUP BY user_id HAVING SUM(stake)
   > 100`.
3. A correlated subquery refers to columns of the outer query, so it is (conceptually) evaluated per
   outer row. An uncorrelated subquery stands alone and is evaluated once.
4. 15 (5 × 3). That is fan-out, and it inflates both sums.
5. It reads top to bottom with named steps, a later CTE can reuse an earlier one, and the same CTE
   can be referenced several times without repeating its text.

-- 3
