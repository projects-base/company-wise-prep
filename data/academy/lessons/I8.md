## Where we are

DIST-SYS-5 packaged a service as an image, DIST-SYS-6 shipped it, and DIST-SYS-7 watched it run.
SYS-DES-1 named the building blocks: load balancers, caches, queues, databases. This lesson maps those
blocks onto real cloud services, mainly AWS with Azure's names alongside, at the level a backend
engineer needs: where your code runs, where the data lives, who can reach what, and what it costs.

## The problem

ShopKart runs on two servers in one data centre. A disk failure takes the database down for a day.
Sale traffic needs ten servers for a week, but buying them takes a month. Invoices fill the app
server's disk. A database password lives in a config file on both boxes.

Cloud providers rent all of this by the minute through an API: machines, disks, managed databases,
networks. You give up some control and take on a bill that grows if nobody watches it. In return,
capacity arrives in minutes and much of the failure handling is built in.

## Regions, zones and who is responsible

A **region** is a geographic area, such as Mumbai or Hyderabad. An **Availability Zone (AZ)** is one
or more separate data centres inside a region, with independent power and networking, connected to
the other AZs by fast links.

```text
Region ap-south-1
 ├── AZ a:  app instances, primary database
 ├── AZ b:  app instances, standby database
 └── AZ c:  app instances
```

The rule that follows: **run across at least two AZs.** One data centre can fail, and a design in one
AZ fails with it. Multi-*region* is much harder and much more expensive, because of data replication
and latency, so it needs a real business reason.

The **shared responsibility model** says who looks after what. The provider secures the cloud itself:
buildings, hardware, the virtualisation layer. You secure what you put in it: your code, your data,
your access rules, and your operating system patches if you rent a plain VM. A public bucket is your
mistake, not the provider's.

## Compute: where the code runs

The choice is how much you manage against how much control you keep:

| Service | What it is | You manage | Good for |
|---|---|---|---|
| **EC2** | A virtual machine | OS, patches, scaling setup | Full control, unusual needs |
| **ECS on Fargate** | Containers, no servers to look after | Image, task config | Most services, without Kubernetes |
| **EKS** | Managed Kubernetes | Workloads and much of the cluster | Teams already on Kubernetes |
| **Lambda** | A function run per event | Code only | Spiky, short, event-driven work |

For EC2, an **AMI** is the machine image it boots from, and an **Auto Scaling Group** keeps a number
of instances running, replaces unhealthy ones, and adds or removes instances according to rules.

Lambda's limits matter for Java. A run can last at most 15 minutes, and a new instance has to start
first, which is a **cold start**. A JVM with Spring is slow at that, so Java teams reach for SnapStart,
which restores a snapshot of an initialised function, or keep Spring out of the function. Lambda also
scales out quickly, which can flood a database with connections.

For a typical Spring Boot service the sensible default is containers on Fargate or EKS. The app stays
long-running, and DIST-SYS-5's probes and graceful shutdown all still apply.

## Storage: object, block, file

Three shapes, and picking the wrong one causes real pain:

- **S3** is an **object store**: you put and get whole objects by key in a bucket, over HTTP. There are
  no real folders (`invoices/2026/42.pdf` is one key), and you cannot edit part of an object.
  It is highly durable and effectively unlimited. Use it for uploads, invoices, backups and exports.
- **EBS** is a **block disk** attached to an EC2 instance, like a local drive. It lives in one AZ and
  normally belongs to one instance.
- **EFS** is a **shared network file system** that many instances can mount at once.

Storing user files on an app server's disk breaks statelessness (SYS-DES-1): the next request may
land on another instance, and the file disappears with the instance. Put them in S3 and keep the key
in your database.

## S3 in a Spring Boot service

Do not stream large files through your service. Hand the client a **presigned URL**: a link signed
with your service's credentials, valid for a short time, that lets the client talk to S3 directly.

```java
import java.net.URL;
import java.time.Duration;
import software.amazon.awssdk.services.s3.model.GetObjectRequest;
import software.amazon.awssdk.services.s3.presigner.S3Presigner;
import software.amazon.awssdk.services.s3.presigner.model.GetObjectPresignRequest;

class InvoiceLinks {
    URL downloadLink(String key) {
        try (S3Presigner presigner = S3Presigner.create()) {
            GetObjectRequest object = GetObjectRequest.builder().bucket("shopkart-invoices").key(key).build();
            GetObjectPresignRequest request = GetObjectPresignRequest.builder()
                    .signatureDuration(Duration.ofMinutes(10))
                    .getObjectRequest(object)
                    .build();
            return presigner.presignGetObject(request).url();
        }
    }
}
```

There is no access key in that code. The SDK's default credentials chain finds the role attached to
the running service, which brings us to IAM. In a real service, create the presigner once as a bean.

Your service still does the authorisation check ("is this order yours?") before it issues the link.
Keep buckets private, leave Block Public Access on, and use lifecycle rules to move old objects to
cheaper storage classes or delete them.

## Managed databases and caches

**RDS** runs Postgres or MySQL for you: backups, patching, failover. **Aurora** is AWS's own engine,
compatible with Postgres and MySQL, with storage replicated across AZs. Two RDS features are often
confused, and interviewers like this one:

| | **Multi-AZ standby** | **Read replica** |
|---|---|---|
| Purpose | Availability | Read scale |
| Replication | Synchronous | Asynchronous |
| Serves reads? | No, in the classic setup | Yes |
| Risk | A failover pause | Stale reads (DB-SQL-10) |

Failover changes the IP behind the database's DNS name, so your connection pool must drop dead
connections and reconnect (DB-SQL-5's pooling, DIST-SYS-3's retries).

**DynamoDB** is a managed key-value and document store (DB-SQL-11). **ElastiCache** is managed Redis
or Valkey (DIST-SYS-1). "Managed" removes the patching work. It does not remove bad indexes, hot
keys or wrong data models.

## Load balancers, DNS and the CDN

SYS-DES-1 explained L4 and L7 load balancing. On AWS:

- **ALB (Application Load Balancer):** L7. Reads HTTP, routes by path or host, terminates TLS. The
  default for REST services.
- **NLB (Network Load Balancer):** L4. Forwards TCP or UDP with very low latency and supports static
  IPs. Use it for non-HTTP protocols or extreme connection counts.

Both send traffic to a **target group** and check each target's health. Two settings connect to what
you already know. Point the health check at the readiness endpoint (SPRING-BOOT-11), not at a page
that calls every dependency. And keep the **deregistration delay** in step with graceful shutdown, so
that in-flight requests finish during a deploy.

**Route 53** is DNS, and **CloudFront** is a CDN that caches content close to users.

## Networking: VPC, subnets, security groups

A **VPC** is your private network inside the cloud. You divide it into **subnets**, each in one AZ.

```text
                        Internet
                           │
                  Internet Gateway
 VPC 10.0.0.0/16           │
 ┌─────────────────────────┼───────────────────────────┐
 │  Public subnets         ▼                           │
 │    ALB          NAT Gateway                         │
 │     │               ▲                               │
 │  Private subnets    │ outbound only                 │
 │    ECS tasks ───────┘                               │
 │     │                                               │
 │  Isolated subnets                                   │
 │    RDS, ElastiCache                                 │
 └─────────────────────────────────────────────────────┘
```

A subnet is **public** if its route table points at an Internet Gateway. Only the load balancer needs
that. Services sit in **private** subnets and reach out through a **NAT Gateway**, which lets them
start connections out but not receive them. Databases get no route to the internet at all.

A **security group** is a firewall around a resource. It only allows, and it is *stateful*: if a
request is allowed in, the reply is allowed out. The strong pattern is to refer to other groups rather
than IP addresses: "the database accepts 5432 only from the app's security group". A **network ACL**
is the subnet-level, stateless layer below, and most teams leave it at its defaults.

When a service cannot reach the database, the usual cause is a security group, a route table, or DNS.

## IAM: who can do what

**IAM** decides who can call which AWS API. A **policy** is a JSON document of allowed or denied
actions on resources. Everything is denied by default, and an explicit deny always wins.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::shopkart-invoices/*"
  }]
}
```

A **user** is a long-lived identity with long-lived keys. A **role** is an identity that is *assumed*
and gives temporary credentials that rotate on their own. **Services should always use roles:** an
ECS task role, an EC2 instance profile, or on EKS a role mapped to the pod's service account.

Two rules. Grant **least privilege**: this exact action on this exact bucket, never `"Action": "*"`.
And **never put access keys in code, images or Git**, because leaked keys are found by automated
scanners very quickly. Application secrets such as a payment gateway key go in **Secrets Manager**
or **Parameter Store**, and **KMS** manages the encryption keys.

## Queues, events and the rest of the map

**SQS** is a managed queue: one consumer takes each message. Standard queues give at-least-once
delivery with best-effort ordering, so consumers must be idempotent (DIST-SYS-3). FIFO queues preserve
order within a group. **SNS** is pub/sub: one message fans out to many subscribers, and SNS into several
SQS queues is a very common pattern. **MSK** is managed Kafka. Choose it when you need replay, long
retention and partitioned ordering (DIST-SYS-2); choose SQS when you just need work handed off.

**CloudWatch** holds logs, metrics and alarms, which are DIST-SYS-7's signals in AWS's own form.

**Infrastructure as code** means describing all this in versioned files instead of clicking in a
console, using **Terraform** or **CloudFormation**. Changes get reviewed, and environments can be
rebuilt. Clicked-together infrastructure drifts and cannot be reproduced.

## The same map on Azure

The concepts carry across clouds; the names change. Learn one cloud properly, and keep this table:

| Job | AWS | Azure |
|---|---|---|
| Virtual machines | EC2 | Virtual Machines |
| Serverless containers | ECS on Fargate | Container Apps |
| Kubernetes | EKS | AKS |
| Functions | Lambda | Azure Functions |
| Object storage | S3 | Blob Storage |
| Managed Postgres | RDS / Aurora | Azure Database for PostgreSQL |
| Managed Redis | ElastiCache | Azure Managed Redis |
| L7 load balancer | ALB | Application Gateway |
| L4 load balancer | NLB | Azure Load Balancer |
| Private network | VPC | Virtual Network (VNet) |
| Service identity | IAM role | Managed Identity |
| Secrets | Secrets Manager | Key Vault |
| Queue / pub-sub | SQS / SNS | Service Bus |
| Monitoring | CloudWatch | Azure Monitor |

## Cost is a design constraint

Cloud bills surprise people in predictable places: data leaving the cloud, traffic between AZs, NAT
Gateway data processing, idle resources, and logs kept forever. Good habits: right-size from real
metrics, scale down outside peak hours, tag every resource by team, set budget alerts, and use
lifecycle rules on storage. Spot capacity is much cheaper but can be taken back at short notice, so
use it for work that can restart.

A senior answer mentions cost without being asked, because it is one more trade-off in the design.

## Lab (~10 min)

A design exercise, with no account needed. Draw ShopKart on AWS on one page. It has a React front end,
an Orders service, a Payments service, Postgres, Redis, and users uploading product images.

For each decision, write one line of *why*:

1. Where does the front end live? (Hint: static files, S3 plus CloudFront.)
2. Which compute runs the two services, and in how many AZs?
3. Which subnets hold the load balancer, the services and the database?
4. How does an image get from the user to storage, without passing through Orders?
5. What exact IAM permission does Orders need for this, and on which resource?
6. Which security group rule lets Orders reach Postgres?
7. Where does the payment gateway's API key live, and how does the app read it?
8. Orders needs to tell Payments and Notifications about a new order. SQS, SNS into SQS, or MSK?

**Then break it:**

- AZ `a` goes down. Walk through what happens to the load balancer, the tasks and the database.
- A deploy starts and requests fail for 30 seconds. Name two settings to check. (Health check path,
  deregistration delay against graceful shutdown.)
- A service gets `AccessDenied` from S3. In what order do you check? (Which role it really has, the
  policy's action and resource, the bucket policy, encryption key access.)

## Gotchas

- **Single-AZ production.** One data centre failure takes you down. Spread services and the database
  across at least two AZs.
- **Access keys in code or images.** Use roles. Temporary credentials cannot leak for long.
- **Multi-AZ standby taken for read scale.** It exists for failover. Reads need a replica, which can
  be stale.
- **Local disk for user files.** It breaks statelessness, and the file dies with the instance. Use
  S3 and keep the key in your database.
- **Lambda in front of a relational database, with no thought for connections.** Scale-out can exhaust
  the database. Use a connection proxy such as RDS Proxy, or limit concurrency.
- **Security group open to `0.0.0.0/0` "just to test".** It stays open. Refer to the caller's security
  group instead.

## In interviews

Asked as "Have you worked with AWS? Which services?", "How would you deploy this?", "S3 vs EBS?",
"ALB vs NLB?" and "How does your service get its AWS credentials?". Bank:
[Design your current project without cloud](#/q/design-current-project-without-cloud),
[Design an image hosting service](#/q/design-image-hosting-service).

**Follow-up: "How would you make this highly available?"** Stateless services in at least two AZs
behind a load balancer with health checks, auto scaling, a Multi-AZ database, retries with backoff on
the client side, and tested backups. Then say what you would *not* do: multi-region, unless the
business needs that level of availability and accepts the cost and complexity.

**Follow-up: "Your EC2 instance can't reach RDS."** Work through it in order: DNS resolves, security
group allows it from the caller, route table and subnets are right, the database is up and accepting
connections, then credentials. A timeout usually means network; a refusal or authentication error
means you got there.

## Explain it in 2 minutes

"Walk me through how you'd deploy a Spring Boot service on AWS."

- Build an image in CI, push it to a registry, and run it on ECS Fargate or EKS in two or more AZs.
- ALB in public subnets; tasks in private subnets; database in isolated subnets.
- RDS Multi-AZ for availability, read replicas if reads need scaling, ElastiCache for caching.
- Task role with least privilege, secrets from Secrets Manager, no keys in the image.
- Files in S3 through presigned URLs; health checks on readiness; graceful shutdown with deregistration.
- CloudWatch or Prometheus for signals, Terraform for everything, budget alerts for cost.

## Check yourself

1. Why does production run across two AZs, and why is two regions a much bigger decision?
2. When would you pick S3, EBS and EFS?
3. What is the difference between an RDS Multi-AZ standby and a read replica?
4. Why does a service use an IAM role rather than an access key?
5. What is the difference between a public and a private subnet, and where does each tier go?

### Answers

1. An AZ can fail on its own, and spreading across two costs little. Two regions need cross-region
   data replication, with higher latency, conflicts or lag, and much more cost and complexity.
2. S3 for whole objects by key, such as files and backups. EBS for a disk attached to one instance.
   EFS for a file system that several instances share.
3. A Multi-AZ standby is synchronous and for failover, and does not serve reads in the classic setup.
   A read replica is asynchronous and serves reads, so it can be stale.
4. Role credentials are temporary and rotate automatically, and nothing needs storing. A long-lived
   key can leak from code or an image and keeps working until someone revokes it.
5. A public subnet has a route to an Internet Gateway; a private one does not. The load balancer goes
   in public, services in private with outbound through NAT, and databases in isolated subnets.
