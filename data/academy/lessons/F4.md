## Where we are

F3 gave you an eight-step method (requirements, estimates, API, data model, high-level design,
deep dives, bottlenecks, trade-offs) on top of F1's building blocks. This lesson runs the method
end to end on three of the questions Microsoft asks most often in recent reports: a URL shortener,
a rate limiter and a notification system. This is a case-study lesson, so it is longer. Split it
over two sittings if you need to: the URL shortener in one, the other two in the next.

## The problem

All three look easy, and that is the trap. A Microsoft interviewer reportedly rejected a textbook
URL-shortener answer and pushed into "components and scenarios". The rate limiter appears in both
LLD and HLD rounds. The notification system has caught out at least one candidate who reached for a pattern
before asking about requirements. The value is in the deep dives and the follow-ups, so that is
where this lesson spends its time.

## Case 1: URL shortener

### Requirements

```text
Functional:   POST a long URL → get a short link (e.g. sho.rt/aZ3kQ9x)
              GET the short link → redirect to the long URL
              optional: custom alias, expiry, click counts
NFR:          100M new links/month, reads 100× writes,
              redirect p99 < 50 ms (excluding the client's network), 99.99% available,
              links never silently change target
Out of scope: user accounts UI, link editing
```

### Estimates

```text
Writes:   100M/month ÷ (30 × 86,400) ≈ 40/s          peak ≈ 120/s
Reads:    100 × 40                    ≈ 4,000/s       peak ≈ 12,000/s
Storage:  100M × 12 × 5 years = 6B links × ~500 B   ≈ 3 TB   (×3 replicas ≈ 9 TB)
Key space: base62 (a–z, A–Z, 0–9), 7 characters = 62^7 ≈ 3.5 trillion  ≫ 6B
Cache:    reads/day ≈ 4,000 × 86,400 ≈ 350M; hottest 20% × 500 B ≈ 35 GB → a small cache cluster
```

**So…** writes are trivial. Reads are heavy but very cacheable (a few links get most clicks). 3 TB
is a modest amount for a sharded key-value store. Seven characters is plenty. **The hard part is
generating unique short codes without a bottleneck.**

### API

```text
POST /links   {longUrl, customAlias?, expiresAt?}   → 201 {code, shortUrl}
GET  /{code}                                         → 302 Location: <longUrl>   | 404
```

### Data model

```text
links
  code        VARCHAR(10)  PK        ← every read is "get by code"
  long_url    TEXT
  owner_id    BIGINT       NULL
  created_at  TIMESTAMP
  expires_at  TIMESTAMP    NULL
```

There is one access pattern, a lookup by primary key. That fits a key-value store (DynamoDB,
Cassandra, Cosmos DB) sharded by `code`, or a sharded relational database.

### High-level design

```text
                 ┌──────────────┐
 client ──► CDN/edge (rate limit, WAF) ──► LB ──► link service ──► cache (code → url)
                                                    │   │                │ miss
                                                    │   └────────────────▼
                                                    │              links store (sharded by code)
                                                    ▼
                                          ID range allocator (etcd/ZooKeeper or a DB row)
                                                    │
                     click events ──► stream (Kafka/Event Hubs) ──► analytics workers ──► OLAP store
```

### Deep dive 1: generating the code

| Option | How | Problem |
|---|---|---|
| Hash and truncate | First 7 chars of base62(MD5(longUrl)) | Collisions: check, then retry with a salt. The same URL always gets the same code, which may or may not be wanted |
| One global counter | DB sequence → base62 | One database is a bottleneck and a single point of failure. Codes are guessable in order |
| **Range allocation** | Each server leases a block (e.g. 1,000 ids) from a coordinator and hands them out from memory | A crashed server wastes its unused block, which is fine with 3.5 trillion codes |
| Snowflake-style | 64-bit id = 41 bits of timestamp + 10 bits of machine id + 12 bits of sequence | No coordination per id, but 64 bits is up to 11 base62 chars, too long for a "short" link |

**Choice:** range allocation. The coordinator is touched once per 1,000 links (at 120 writes/s,
that's well under one call per second), so it is never a bottleneck. If guessable codes are a
concern (people enumerating links), pass the counter through a reversible scramble, such as a
keyed permutation of the id, before base62-encoding it. Custom aliases go through a conditional
insert ("insert if not exists") and return `409 Conflict` on a clash.

### Deep dive 2: the redirect itself

- **301 (permanent)** lets browsers cache the redirect. That means fewer hits on you, but you lose
  click analytics and can never change or expire the link for that browser.
- **302 (temporary)** sends every click through you. You keep analytics and expiry.

Most shorteners that sell analytics use 302. Say which you pick and why.

Read path latency: edge → cache hit → redirect, all in a few milliseconds. Click logging must not
slow the redirect, so the service writes a click event to a stream **asynchronously** and replies
immediately.

### Deep dive 3: abuse and DDoS

- Rate-limit creation per user/IP (Case 2). Requests for non-existent codes are a cheap attack
  because every miss reaches the store. Cache negative results briefly, or put a **Bloom filter**
  (F1) of existing codes in front of the store.
- An edge/CDN with a web application firewall absorbs volumetric attacks before they reach your
  region.
- Scan long URLs against malware/phishing lists at creation time, and allow takedowns. That is why
  302 helps: you can still change what a link does.

### Follow-ups

- **"Make it multi-region."** Give each region its own id ranges, so creation needs no cross-region
  coordination. Replicate the links table asynchronously to all regions. A link created in one
  region and clicked a second later in another may miss, so fall back to the home region on a miss
  (the region can be encoded in the code or found via the range).
- **"The same long URL is submitted a million times."** Either return the existing code (needs an
  index on `long_url`, or a hash of it) or create a new one per request. Ask which the product
  wants, since per-user analytics usually wants separate codes.

## Case 2: rate limiter

### Requirements

```text
Functional:   limit requests per client (API key, user or IP) per rule,
              e.g. 100 requests/minute per key; return 429 when over
              rules configurable per tenant and per endpoint
NFR:          adds < a few ms per request; works across many gateway nodes;
              ~1M requests/s in total across the fleet; limits are approximate (±a few %) but fair
```

### Estimates

```text
Active keys: 10M. State per key (counter or tokens + timestamp + key) ≈ 100 B with overhead
→ 10M × 100 B ≈ 1 GB     → fits in memory on one Redis node; shard for throughput
Checks: 1M/s → beyond one Redis node's comfortable range → shard the counters by key
```

**So…** memory is easy. Throughput and the extra network hop on every request are the real
constraints.

### Where it lives

```text
client ──► [ API gateway / middleware: rate limiter ] ──► services
                         │
                         ▼
               Redis cluster (counters, sharded by client key)
               + rules config (cached locally, refreshed every few seconds)
```

Put it in the gateway or a shared middleware so every service gets it for free. Client-side
limits help but can't be trusted.

### Deep dive 1: algorithms

| Algorithm | Idea | Pro | Con |
|---|---|---|---|
| Fixed window | Count per calendar minute; reset at :00 | Tiny, simple | 2× burst at the boundary (100 at 0:59 + 100 at 1:00) |
| Sliding log | Store every request timestamp; count the last 60 s | Exact | Memory grows with traffic |
| Sliding window counter | Current window + previous window × overlap fraction | Close to exact, 2 numbers | An approximation |
| **Token bucket** | Bucket holds up to B tokens, refills at R/s; a request takes one | Allows controlled bursts, 2 numbers | Two knobs to explain |
| Leaky bucket | Requests queue and drain at a fixed rate | Smooth output | Adds latency, and bursts wait |

**Choice:** token bucket for APIs. It matches how people describe limits ("10 per second, bursts up
to 20"). The lab builds one.

### Deep dive 2: making it distributed

With 50 gateway nodes, each one can't count alone. A user spread across nodes would get 50× the
limit. The options:

1. **A central store (Redis).** Each check is a read-modify-write. Two nodes doing it at once can
   both see "99" and both allow, a **race condition**. Fix it by making the check atomic in Redis:
   `INCR` with an expiry for fixed windows, or a **Lua script** (Redis runs it atomically) for token
   buckets.
2. **Local counters with periodic sync.** Each node allows `limit / N` locally, or syncs counts
   every 100 ms. This is faster with no hop, but less exact. It is fine when "roughly 100/min" is
   acceptable.

**Failure mode:** if Redis is unreachable, do you **fail open** (allow everything, which protects
availability) or **fail closed** (reject everything, which protects the backend)? Most public APIs
fail open with a local fallback limit. A login or OTP endpoint should fail closed. Say this out
loud; interviewers look for it.

### Deep dive 3: the response and multi-tenancy

```text
HTTP/1.1 429 Too Many Requests
Retry-After: 2
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
```

For a **multi-tenant, pluggable** version (a reported Microsoft variant), define a
`RateLimitStrategy` interface (`allow(key, now)`) with token-bucket and sliding-window
implementations. A rules service maps `(tenant, endpoint)` to `(strategy, parameters)`, and the
gateway caches those rules. Adding an algorithm then means a new class, not an edit to existing
ones.

### Follow-ups

- **"A single huge customer is hot."** Their key lands on one Redis shard. Use local pre-aggregation
  for that key, or split their bucket into sub-keys across shards, each with a share of the limit.
- **"Limit by several dimensions at once"** (per user and per IP and globally). Check each rule. A
  request must pass all of them. Order the checks cheapest first.

## Case 3: notification system

### Requirements

```text
Functional:   internal services send notifications to users via push (iOS/Android),
              SMS and email; templates; user preferences and opt-outs;
              scheduled sends; delivery status
NFR:          OTP/security messages delivered within seconds; marketing can lag minutes;
              no lost notifications (at-least-once) and no visible duplicates;
              ~20M notifications/day, campaigns of 10M in an hour
```

Ask first: which channels, which priorities, and must the caller know the outcome? This is where
reaching for a design pattern before scoping costs points.

### Estimates

```text
Average:   20M/day ÷ 86,400 ≈ 230/s
Campaign:  10M in 1 hour ≈ 2,800/s on top
Storage:   20M × ~1 KB log row = 20 GB/day → ~7 TB/year (keep 90 days hot: ~1.8 TB)
```

**So…** the average is easy. The problem is **bursts** and **slow, flaky third-party providers**
(APNs for Apple, FCM for Android, an SMS gateway, an email service), each with its own rate limit.
That points to queues.

### High-level design

```text
 services ──► Notification API ──► validate → load prefs → dedup → render template
                    │                                          │
                    │ 202 Accepted + notificationId            ▼
                    │                              ┌─ queue: push   (high / low priority)
                    │                              ├─ queue: sms    (high / low priority)
                    │                              └─ queue: email  (high / low priority)
                    ▼                                          │
            notification log DB  ◄── status updates ── channel workers ──► APNs / FCM / SMS / email
                                                               │ failed after N retries
                                                               ▼
                                                        dead-letter queue
 scheduler ──(due sends)──► Notification API
```

### Data model

```text
notifications       (id PK, user_id, category, channel, template_id, payload JSON,
                     priority, status, idempotency_key UNIQUE, created_at, sent_at)
user_preferences    (user_id, category, channel, enabled, quiet_hours)
device_tokens       (user_id, device_id, platform, token, updated_at)
templates           (id, channel, locale, version, body)
```

### Deep dive 1: reliability without duplicates

- The API writes the notification row **before** returning 202, so nothing is lost after the
  caller hears "accepted". Use the transactional outbox pattern (write the row and an outbox entry
  in one DB transaction, and a relay publishes the outbox to the queue) so the DB and the queue
  can't disagree.
- Workers retry failures with **exponential backoff and jitter** (F2). After N attempts the message
  goes to a **dead-letter queue (DLQ)**, a parking queue that people can inspect and replay.
- Duplicates: callers send an **idempotency key** (for example `order-123-shipped`). The unique
  constraint rejects a second insert. Workers check the row's status before sending, so a
  redelivered queue message for an already-sent notification is dropped. The provider call itself
  can still double-send on a timeout, which is why "no *visible* duplicates" is the honest goal.

### Deep dive 2: priority, fairness and limits

- **Separate queues per priority**, so a 10M-user campaign can't delay an OTP. Give high-priority
  queues their own workers.
- **Per-user limits** (for example at most 3 marketing pushes a day) and **quiet hours**, checked
  before enqueueing. This reuses Case 2.
- **Per-provider limits:** workers apply back-pressure (F2). If the SMS provider returns 429, slow
  down rather than hammering it. Keep a second provider for failover on critical channels.

### Deep dive 3: tracking

Providers report delivery through callbacks (webhooks), and opens and clicks arrive through
tracking links. All of them update `status` asynchronously. For Microsoft-style follow-ups, name
the **metrics**: queue depth and age per channel, send latency p99, provider error rate, and DLQ
size, with an alert on "OTP queue age > 10 s".

### Follow-ups

- **"A user has three devices."** Send to every active token. Remove tokens that the provider
  reports as invalid.
- **"Send to all 50M users."** Don't create 50M API calls up front. A campaign job pages through the
  audience in batches and enqueues gradually at a controlled rate.

## Lab (~10 min)

Build the token bucket from Case 2 and watch bursts and steady rates. Save this as
`TokenBucketLab.java` and run `java TokenBucketLab.java`.

```java
import java.util.concurrent.ConcurrentHashMap;

public class TokenBucketLab {

    /** One bucket per client. Refills continuously; each request takes one token. */
    static final class TokenBucket {
        private final long capacity;          // the largest burst allowed
        private final double refillPerNano;   // the steady rate
        private double tokens;
        private long lastRefill;

        TokenBucket(long capacity, double tokensPerSecond, long nowNanos) {
            this.capacity = capacity;
            this.refillPerNano = tokensPerSecond / 1_000_000_000.0;
            this.tokens = capacity;
            this.lastRefill = nowNanos;
        }

        synchronized boolean tryAcquire(long nowNanos) {
            tokens = Math.min(capacity, tokens + (nowNanos - lastRefill) * refillPerNano);
            lastRefill = nowNanos;
            if (tokens >= 1) {
                tokens -= 1;
                return true;
            }
            return false;
        }
    }

    static final class RateLimiter {
        private final ConcurrentHashMap<String, TokenBucket> buckets = new ConcurrentHashMap<>();
        private final long capacity;
        private final double perSecond;

        RateLimiter(long capacity, double perSecond) {
            this.capacity = capacity;
            this.perSecond = perSecond;
        }

        boolean allow(String clientId, long nowNanos) {
            return buckets.computeIfAbsent(clientId, id -> new TokenBucket(capacity, perSecond, nowNanos))
                          .tryAcquire(nowNanos);
        }
    }

    public static void main(String[] args) {
        RateLimiter limiter = new RateLimiter(5, 2.0);   // burst of 5, then 2 requests/second
        long t = 0;                                      // a fake clock makes the run repeatable
        long ms = 1_000_000L;

        StringBuilder burst = new StringBuilder();
        for (int i = 0; i < 8; i++) burst.append(limiter.allow("alice", t) ? "Y" : "n");
        System.out.println("t=0ms, 8 requests at once: " + burst);

        t += 500 * ms;
        System.out.println("t=500ms: " + (limiter.allow("alice", t) ? "Y" : "n"));
        System.out.println("t=500ms again: " + (limiter.allow("alice", t) ? "Y" : "n"));
        System.out.println("bob at t=500ms: " + (limiter.allow("bob", t) ? "Y" : "n"));

        int allowed = 0;
        for (int step = 0; step < 100; step++) {         // 10 s of steady traffic, one request every 100 ms
            t += 100 * ms;
            if (limiter.allow("alice", t)) allowed++;
        }
        System.out.println("next 10s at 10 req/s, allowed: " + allowed);
    }
}
```

**What you should see:** `YYYYYnnn` (a burst of 5, then refusals), one `Y` after 500 ms (half a
second refills one token at 2 per second), `bob` unaffected, and **20** allowed out of 100 over the
next 10 seconds, which is exactly the 2-per-second rate.

**Then try:** write a fixed-window limiter (100 per minute) and send 100 requests at 0:59.9 and 100
at 1:00.1. It allows all 200 in a fifth of a second. That boundary burst is why the token bucket
exists.

## Gotchas

- **Base62 of a 64-bit id isn't "short".** It can be up to 11 characters. Short codes come from a
  smaller counter space or truncated hashes, with collision handling.
- **301 versus 302 isn't trivia.** 301 gives up analytics and the ability to change or expire a link,
  because browsers cache it.
- **A read-modify-write rate limiter on Redis races.** Use atomic `INCR` or a Lua script, never GET
  then SET.
- **Fail open versus fail closed must be decided per endpoint**, not left to whatever the client
  library does by default.
- **"Exactly-once notifications" isn't a real promise.** Say at-least-once with dedup by
  idempotency key and status checks, and admit the residual provider-level risk.
- **One shared queue for all notification types** lets a marketing campaign delay OTPs. Separate
  them by priority.

Typical follow-ups and what a strong answer contains:
- **"How do you prevent DDoS on the shortener?"** Layers: edge/WAF and per-IP limits, a cache and a
  Bloom filter for non-existent codes, creation limits per account, and autoscaling the read path
  behind the cache.
- **"Your rate limiter's Redis is down. What happens?"** Fail open with a conservative local
  per-node limit for normal APIs, fail closed for auth and OTP, plus an alert, because a silent
  fail-open is an outage waiting to happen.
- **"How does the caller know the notification was delivered?"** Return an id at once (202). The
  status is queryable and pushed by webhook. "Delivered" depends on provider callbacks and isn't
  guaranteed for every channel.

## Explain it in 2 minutes

*"Design a URL shortener. Focus on what's actually hard."*

- Scope and numbers: about 40 writes/s and 4,000 reads/s, 3 TB over 5 years, 7 base62 chars.
- Read path: edge, cache, a key-value store sharded by code, and a 302 redirect for analytics.
- Code generation: range allocation from a coordinator, plus scrambling to stop enumeration.
- Clicks go to a stream asynchronously, so the redirect stays fast.
- Abuse: rate limits, a WAF, a Bloom filter or negative cache for misses, URL scanning.
- Multi-region: per-region ranges, async replication, fallback to the home region on a miss.

## Check yourself

1. Why does range allocation remove the counter bottleneck?
2. Show the fixed-window boundary problem with numbers for a limit of 10 per minute.
3. Why must a token-bucket check in Redis be a single atomic script?
4. Why does the notification API write to the database before returning 202?
5. What two things stop an OTP from waiting behind a marketing campaign?

### Answers

1. Each server talks to the coordinator once per block (e.g. 1,000 ids) and hands out the rest from
   memory, so the coordinator sees about 1/1,000 of the write traffic.
2. 10 requests at 0:59 and 10 more at 1:00 are all allowed, so 20 requests pass in about one second.
3. Otherwise two gateway nodes can read the same token count at the same time and both allow, which
   lets the client exceed the limit.
4. So an accepted notification survives a crash, and the queue can be fed reliably from it (the
   outbox pattern) without losing or inventing messages.
5. Separate high-priority queues with their own workers, and checking per-user limits and
   preferences before enqueueing, so campaign volume never sits in front of OTPs.
