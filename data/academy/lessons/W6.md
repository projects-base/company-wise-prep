## Where we are

WEB-API-3 designed REST APIs properly, and WEB-API-5 compared REST, gRPC and events for service-to-service
calls. This lesson goes deeper on the three request-response styles: how gRPC works in code, what
GraphQL actually solves and what it costs, and how to choose between them without following fashion.

## The problem

ShopKart's mobile home screen needs a customer's name, their last three orders, and the first image
of each product. With REST, that takes five calls over a slow phone network, and each response carries
fields the screen never shows. The web team wants different fields, so the API gains
`/orders?view=mobile` and `/orders?view=web-compact`. Meanwhile an internal pricing service makes
thousands of calls a second, and much of that time goes on converting JSON.

These are two different problems: the first is about **client flexibility**, and the second is about
**efficiency between services**. No single style solves both, which is why large systems use more than
one.

## Three styles, three shapes

| | REST | gRPC | GraphQL |
|---|---|---|---|
| You model | Resources | Procedures | A graph of types |
| Contract | OpenAPI (optional) | `.proto` (required) | Schema (required) |
| Format | Usually JSON | Protobuf, binary | JSON |
| Transport | HTTP | HTTP/2 | Usually HTTP POST |
| Who shapes the response | Server | Server | **Client** |
| HTTP caching | Built in | None | Hard |
| Streaming | Limited | Built in | Subscriptions |
| Browser use | Direct | Needs a proxy | Direct |

Keep these in mind as you read on: REST's strength is the web's own infrastructure, gRPC's is a strict
fast contract, and GraphQL's is letting the client ask for exactly what it needs.

## gRPC: contract first

With gRPC, you write the contract first in a `.proto` file:

```protobuf
syntax = "proto3";

package shopkart.orders.v1;

service OrderService {
  rpc GetOrder (GetOrderRequest) returns (Order);
  rpc WatchOrder (GetOrderRequest) returns (stream OrderStatus);
}

message GetOrderRequest {
  string order_id = 1;
}

message Order {
  string id = 1;
  int64 total_paise = 2;
  repeated string skus = 3;
}

message OrderStatus {
  string state = 1;
}
```

The `protoc` compiler generates a client and a server base class in Java, Go, Python and more. A typo
in a field name then becomes a compile error, not a production bug. The server fills in the methods:

```java
class Orders extends OrderServiceGrpc.OrderServiceImplBase {
    @Override
    public void getOrder(GetOrderRequest request, StreamObserver<Order> response) {
        if (request.getOrderId().isBlank()) {
            response.onError(Status.INVALID_ARGUMENT.withDescription("order_id is required").asRuntimeException());
            return;
        }
        response.onNext(Order.newBuilder().setId(request.getOrderId()).setTotalPaise(99_800).addSkus("BOOK").build());
        response.onCompleted();
    }
}
```

And the caller reads like a local method call:

```java
Order order = stub.withDeadlineAfter(1, TimeUnit.SECONDS)
        .getOrder(GetOrderRequest.newBuilder().setOrderId("o-1").build());
```

## What protobuf numbers are for

Those `= 1`, `= 2` are **field numbers**, and they are the real contract. JSON repeats every field name
in every message. Protobuf sends only the number, the type and the value, so that message is 15 bytes
on the wire, where the JSON version is 47.

That gives you the evolution rules:

- **Never change or reuse a field number.** Old clients would misread the data.
- **Adding a field is safe.** Old readers skip numbers they don't know.
- **Removing is safe if you `reserved` the number,** so nobody reuses it later.
- **Renaming is safe on the wire,** because names are not sent, though generated code changes.

## Four call types and deadlines

gRPC has four call shapes, thanks to HTTP/2's streams:

| Type | Example |
|---|---|
| **Unary:** one request, one response | `GetOrder` |
| **Server streaming:** one request, many responses | `WatchOrder` sends status updates |
| **Client streaming:** many requests, one response | Upload readings, get a summary |
| **Bidirectional:** both sides stream | Live chat, game state |

Failures use a fixed set of **status codes** rather than HTTP's: `INVALID_ARGUMENT`, `NOT_FOUND`,
`UNAVAILABLE`, `DEADLINE_EXCEEDED`. `UNAVAILABLE` is usually safe to retry, and `INVALID_ARGUMENT` never
is (DIST-SYS-3).

A **deadline** is a point in time by which the whole call must finish. It is carried along with the
call, so a chain A → B → C shares one time budget, and work stops when nobody is waiting for the answer
any more. By default there is no deadline at all, so a stuck server can hold a client forever. Always
set one. In testing, a 50 ms deadline on a 500 ms call failed with `DEADLINE_EXCEEDED` as it should.

One operational trap from WEB-API-5 is worth repeating: HTTP/2 holds one long-lived connection, so a
plain L4 load balancer pins a client to a single pod. You need client-side balancing, or an L7 proxy.

## GraphQL: one endpoint, client-shaped responses

GraphQL gives you a typed **schema**, and clients write **queries** that state exactly what they want:

```graphql
type Query {
  recentOrders(limit: Int!): [Order!]!
}

type Order {
  id: ID!
  total: Int!
  customer: Customer!
}

type Customer {
  id: ID!
  name: String!
}
```

```graphql
query HomeScreen {
  recentOrders(limit: 3) {
    id
    customer { name }
  }
}
```

One request returns exactly those fields, in that shape. That fixes two REST problems at once:
**over-fetching** (getting fields you don't need) and **under-fetching** (needing several calls to fill
one screen). Mobile and web can ask for different fields with no server changes, which removes the
`?view=` variants. Writes go through **mutations**, and **subscriptions** push live updates.

GraphQL is a query language for your API. It is not a database technology, and it does not talk to
your database by itself.

## Resolvers and the N+1 problem

Each field in the schema is filled in by a **resolver**, a function that fetches that field. Simple
fields read straight from the parent object. Here is the trap: for `recentOrders` with `customer`, a
naive setup calls the customer resolver once per order. Fifty orders means one query for the orders,
then fifty for the customers. That is the same N+1 you met with JPA in DB-SQL-8, now in the API layer.

The fix is **batching**: collect all the customer ids at this level of the query, then load them in one
call. Spring for GraphQL has `@BatchMapping` for this, built on the **DataLoader** pattern:

```java
@Controller
class OrderGraphql {
    private final Orders orders;
    private final Customers customers;

    OrderGraphql(Orders orders, Customers customers) {
        this.orders = orders;
        this.customers = customers;
    }

    @QueryMapping
    List<Order> recentOrders(@Argument int limit) {
        return orders.recent(limit);
    }

    @BatchMapping
    Map<Order, Customer> customer(List<Order> orders) {
        Map<String, Customer> byId = customers.findAllById(orders.stream().map(Order::customerId).distinct().toList())
                .stream().collect(Collectors.toMap(Customer::id, c -> c));
        return orders.stream().collect(Collectors.toMap(o -> o, o -> byId.get(o.customerId())));
    }
}
```

The lab counts the calls both ways.

## What GraphQL costs you

The client's freedom is also the server's problem:

- **Abusive queries.** A client can ask for orders → customer → orders → customer, nested as deep as it
  likes. Limit query **depth** and **complexity**, and set timeouts.
- **Rate limiting is harder.** One request may be trivial or huge, so counting requests means little.
  Limit by calculated query cost.
- **Caching is harder.** Everything is a POST to `/graphql`, so CDNs and HTTP caches do not help by
  default. **Persisted queries** help: the client sends a known query's id, which also lets you allow only
  queries you have approved.
- **Errors look different.** A response can be `200 OK` with a partial result and an `errors` array, so
  monitoring on HTTP status alone misses failures.
- **Authorisation goes per field.** The same `Customer.email` can be reached through many paths, so
  checks belong in the business layer, not at the endpoint.
- **Observability needs effort.** Every request has the same URL, so metrics must use the operation name.

## Versioning in each style

| | How it changes over time |
|---|---|
| REST | Additive changes; a new version for breaking changes (WEB-API-3) |
| gRPC | Additive field numbers; a new package such as `orders.v2` for breaking changes |
| GraphQL | No versions: add fields, mark old ones `@deprecated`, remove them once usage reaches zero |

Each one has the same core rule: adding is safe and removing is a project. For GraphQL, field-level
usage metrics tell you when removal is safe.

## How to choose

Ask who the client is, and pick the simplest thing that fits:

| Situation | Choice | Why |
|---|---|---|
| Public API, partners, unknown clients | **REST** | Everyone can use it; caching; simple tools |
| Internal, high-volume service calls | **gRPC** | Compact, typed, deadlines, streaming |
| Many client apps with varied screens | **GraphQL** | Clients shape data, fewer round trips |
| Live two-way traffic to a browser | **WebSocket** | WEB-API-2 |
| Fire and forget, many consumers | **Events** | WEB-API-5, DIST-SYS-2 |

A common real shape uses several at once:

```text
 browser / mobile ── GraphQL or REST ──► gateway or BFF ── gRPC ──► internal services
                                                               └─ events ─► other services
```

Be wary of two arguments. "gRPC is faster" is true for encoding, but it rarely matters if the time is
going on a database query, so measure first. And "GraphQL replaces REST" is wrong: if you have a few
known clients and stable screens, REST is simpler to run and secure.

## Lab (~10 min)

Two experiments in plain Java: encode the same order as JSON and as protobuf's wire format, then count
the calls a GraphQL resolver makes with and without batching. Press Run, or save it as `ApiStylesLab.java`
and run `java ApiStylesLab.java`.

```java
import java.io.ByteArrayOutputStream;
import java.nio.charset.StandardCharsets;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;
import java.util.function.Function;
import java.util.stream.Collectors;
import java.util.stream.IntStream;

public class ApiStylesLab {
    // A protobuf tag packs the field number with a wire type: 0 = varint, 2 = length-prefixed bytes.
    static void varint(ByteArrayOutputStream out, long value) {
        while (value >= 0x80) {
            out.write((int) (value & 0x7F) | 0x80);
            value >>>= 7;
        }
        out.write((int) value);
    }

    static void string(ByteArrayOutputStream out, int field, String text) {
        byte[] bytes = text.getBytes(StandardCharsets.UTF_8);
        varint(out, (long) field << 3 | 2);
        varint(out, bytes.length);
        out.writeBytes(bytes);
    }

    static void number(ByteArrayOutputStream out, int field, long value) {
        varint(out, (long) field << 3);
        varint(out, value);
    }

    record Order(String id, String customerId) {}
    record Customer(String id, String name) {}

    static int customerQueries = 0;

    static Customer loadOne(String id) {
        customerQueries++;
        return new Customer(id, "name-" + id);
    }

    static Map<String, Customer> loadMany(Set<String> ids) {
        customerQueries++;
        return ids.stream().collect(Collectors.toMap(Function.identity(), id -> new Customer(id, "name-" + id)));
    }

    public static void main(String[] args) {
        String json = "{\"id\":\"o-1\",\"totalPaise\":99800,\"skus\":[\"BOOK\"]}";
        ByteArrayOutputStream proto = new ByteArrayOutputStream();
        string(proto, 1, "o-1");
        number(proto, 2, 99_800);
        string(proto, 3, "BOOK");
        System.out.println("JSON bytes:     " + json.getBytes(StandardCharsets.UTF_8).length);
        System.out.println("Protobuf bytes: " + proto.size());

        List<Order> orders = IntStream.rangeClosed(1, 50)
                .mapToObj(i -> new Order("o-" + i, "c-" + i % 10)).toList();

        orders.forEach(order -> loadOne(order.customerId()));
        System.out.println("Resolver per order: " + customerQueries + " queries");

        customerQueries = 0;
        Set<String> ids = new LinkedHashSet<>();
        orders.forEach(order -> ids.add(order.customerId()));
        Map<String, Customer> byId = loadMany(ids);
        System.out.println("Batched: " + customerQueries + " query for " + byId.size() + " customers");
    }
}
```

**What to observe:**

1. Protobuf comes to 15 bytes, the same size real generated code reported for this message. Most of
   JSON's extra bytes are field names and punctuation, repeated in every message.
2. The saving depends on the data. Change `"BOOK"` to a 2,000-character description in both encodings:
   the text dominates, and the ratio nearly disappears. Compression narrows it further.
3. The naive resolver makes 50 queries and batching makes 1, for the same answer.
4. **Break it:** change `string(proto, 3, "BOOK")` to `string(proto, 1, "BOOK")`. The encoder still runs,
   but a real reader would treat `BOOK` as the order id. That is why field numbers can never be reused.

## Gotchas

- **Reusing a protobuf field number.** Old clients silently misread data. Mark removed ones `reserved`.
- **gRPC calls with no deadline.** The default is to wait forever. Always set one.
- **gRPC behind an L4 load balancer.** One connection sticks to one pod. Use an L7 proxy or client-side balancing.
- **GraphQL resolvers with no batching.** It is N+1 at the API layer. Use `@BatchMapping`.
- **Public GraphQL with no depth or cost limit.** One query can flatten the service.
- **Alerting on HTTP status for GraphQL.** Failures can come back as `200` with an `errors` array.

## In interviews

Asked as "REST vs GraphQL vs gRPC?", "When would you not use GraphQL?", "How does gRPC stay compatible
across versions?" and "What is the N+1 problem in GraphQL?". Bank:
[Microservices communication: gRPC vs REST vs events](#/q/microservices-communication-grpc-vs-rest-eda).

**Follow-up: "Would you move your REST API to GraphQL?"** Ask what hurts first. If clients suffer from
many round trips and varied screens, a GraphQL layer or a BFF at the edge may help, in front of the
existing services. If the API has a few stable clients, the migration buys nothing and adds query cost
limits, caching work and new monitoring.

**Follow-up: "Would you expose gRPC publicly?"** Usually not to browsers, which need gRPC-Web or a
gateway that translates to JSON. For partners who control their own clients it can work, but REST with
OpenAPI is easier for them to adopt.

## Explain it in 2 minutes

"How do you choose between REST, gRPC and GraphQL?"

- Start from the client: who calls this, how many kinds, and what they need.
- REST for public and simple APIs, because caching and tooling come for free.
- gRPC inside the system: typed contract, compact binary, streaming, deadlines.
- GraphQL when many clients need different shapes and round trips hurt.
- Name each cost: GraphQL's cost limits, N+1 and caching; gRPC's browser and load-balancing limits.
- They mix: GraphQL or REST at the edge, gRPC and events inside.

## Check yourself

1. What are over-fetching and under-fetching, and how does GraphQL address them?
2. Why must a protobuf field number never be reused?
3. What does a gRPC deadline do that a simple client timeout does not?
4. How does N+1 appear in GraphQL, and what fixes it?
5. Why is HTTP caching harder with GraphQL?

### Answers

1. Over-fetching is receiving fields you don't use, and under-fetching is needing several calls for one
   view. GraphQL lets the client request exactly the fields it wants in one query.
2. The number identifies the field on the wire, so an old client would read new data as the old field.
3. It travels with the call, so all services down the chain share one time budget and can stop work
   when the caller has given up.
4. A field resolver runs once per parent, such as a customer query for each order. Batch with a
   DataLoader or `@BatchMapping`.
5. Queries are usually POSTs to one URL, with the query in the body, so URL-based caches cannot tell them
   apart. Persisted queries help.
