## Where we are

E1 gave you interfaces as seams, and E2 and E3 showed how objects are created and wrapped.
Behavioural patterns are about **how objects decide and communicate**: who picks the algorithm,
who hears about an event, who handles a request, and how behaviour changes as an object moves
through its life. These five carry most LLD interview answers.

## The problem

A checkout flow has four kinds of change pressure at once:

- The shipping-cost rule differs by country and changes every quarter.
- When an order is placed, email, analytics and inventory all need to react, and next month a
  fraud check will want to as well.
- Every incoming request must pass authentication, rate limiting and validation, in order, and
  any of them can stop it.
- An order can be paid, shipped, delivered or cancelled, but you can't ship an unpaid order or
  cancel a delivered one.

Written naively, each of these becomes a growing `if/else` block inside the one class that
knows everything. Each pattern below takes one of these pressures out of that class.

## Strategy: swap the algorithm

**Problem.** One task, several ways to do it, chosen at runtime. (This is E1's OCP fix.)

**Minimal example.**

```java
interface ShippingCost { long cents(Order o); }

final class FlatRate      implements ShippingCost { public long cents(Order o) { return 500; } }
final class WeightBased   implements ShippingCost { public long cents(Order o) { return 100 + 50L * o.weightKg(); } }
final class FreeOverLimit implements ShippingCost { public long cents(Order o) { return o.totalCents() > 50_00 ? 0 : 500; } }

final class Checkout {
    private final Map<String, ShippingCost> byCountry;     // chosen by data, not by if/else
    Checkout(Map<String, ShippingCost> byCountry) { this.byCountry = byCountry; }
    long shipping(Order o) { return byCountry.getOrDefault(o.country(), new FlatRate()).cents(o); }
}
```

Because `ShippingCost` has one method, a lambda also works: `o -> 0` is a valid strategy.

**The rule:** define a family of algorithms behind one interface, and let the caller (or a
factory) choose. The class that uses the strategy never changes when a new one is added.

**Where the JDK and Spring use it:** `Comparator` passed to `List.sort` is the everyday example.
`ThreadPoolExecutor` takes a `RejectedExecutionHandler` (abort, caller-runs, discard). In Spring,
`PasswordEncoder` implementations are interchangeable strategies, and a very common idiom is
injecting `List<YourStrategy>` and indexing it by a `key()` method.

## Observer: tell interested parties that something happened

**Problem.** When an order is placed, several unrelated parts of the system react. If
`OrderService` calls each one directly, it must change every time a new reaction is added, and
it becomes coupled to email, analytics and inventory.

**Minimal example.**

```java
record OrderPlaced(String orderId, long totalCents) { }
interface OrderListener { void on(OrderPlaced e); }

final class OrderEvents {
    private final List<OrderListener> listeners = new CopyOnWriteArrayList<>(); // safe to iterate while others subscribe
    void subscribe(OrderListener l) { listeners.add(l); }
    void publish(OrderPlaced e)     { listeners.forEach(l -> l.on(e)); }
}

// events.subscribe(e -> emailService.confirm(e.orderId()));
// events.subscribe(e -> analytics.track("order", e.totalCents()));
```

The **subject** (the thing that publishes) knows only the listener interface. Adding the fraud
check is one more `subscribe` call, and `OrderService` doesn't change.

**The rule:** the subject keeps a list of observers and notifies them of events. Publishers and
listeners don't know about each other's details.

**Where the JDK and Spring use it:**

- Spring's **`ApplicationEventPublisher.publishEvent(...)`** with **`@EventListener`** methods.
  `@TransactionalEventListener` runs the listener only after the surrounding transaction commits,
  which stops you sending "order confirmed" for an order that was then rolled back.
- Spring Boot's own startup events, such as `ApplicationReadyEvent`.
- JDK: `java.beans.PropertyChangeListener` and Swing's `ActionListener`. (`java.util.Observer`
  exists but has been deprecated since Java 9.)
- At system scale, a message broker such as Kafka is the same idea across processes.

**Watch out:** Spring events are **synchronous by default**. The listener runs on the
publisher's thread, a slow listener slows the publisher, and an exception in a listener
propagates back to the publisher. Use `@Async` or a queue when that matters.

## Template Method: fixed skeleton, variable steps

**Problem.** Several classes do the same sequence of steps and differ in only one or two of
them. Copy-pasting the sequence means a bug fix has to be made in every copy.

**Minimal example.**

```java
abstract class ReportGenerator {
    public final String generate(List<String> rows) {     // final: the order of steps is fixed
        StringBuilder out = new StringBuilder(header());
        for (String r : rows) out.append(formatRow(r));
        return out.append(footer()).toString();
    }
    protected abstract String header();                    // steps subclasses must fill in
    protected abstract String formatRow(String row);
    protected String footer() { return ""; }               // a "hook": optional override
}

final class CsvReport extends ReportGenerator {
    protected String header()            { return "name\n"; }
    protected String formatRow(String r) { return r + "\n"; }
}
```

**The rule:** the base class owns the algorithm's skeleton in a `final` method; subclasses fill
in the steps. It uses inheritance, so it is less flexible than Strategy. Modern Java often
replaces the abstract steps with lambdas passed in, which turns it into a Strategy.

**Where the JDK and Spring use it:**

- **`JdbcTemplate`**: it owns the fixed steps (get a connection, prepare the statement, execute,
  iterate the result set, handle exceptions, close everything) and you supply only the varying
  step as a callback such as a `RowMapper`. It is the callback form of the pattern, which is why
  it is named a *template*. `RestTemplate`, `TransactionTemplate` and `JmsTemplate` follow the
  same idea.
- Spring's `OncePerRequestFilter`: you implement `doFilterInternal`, and the base class decides
  when to call it.
- JDK: `AbstractList` (implement `get` and `size`, inherit the rest) and `InputStream`, whose
  `read(byte[])` is built on the abstract single-byte `read()`.

## Chain of Responsibility: pass the request along

**Problem.** A request must go through several checks in order, and any of them can stop it.
Hard-coding `if (!auth) ...; if (!rateOk) ...; if (!valid) ...` in every endpoint repeats the
code, and reordering or adding a check means editing all of them.

**Minimal example** (shaped like a servlet filter chain):

```java
record Request(String user, String path) { }
interface Filter { String apply(Request req, Chain next); }

record Chain(List<Filter> filters, int index, Function<Request, String> endpoint) {
    String proceed(Request req) {
        if (index == filters.size()) return endpoint.apply(req);        // end of chain: the real handler
        return filters.get(index).apply(req, new Chain(filters, index + 1, endpoint));
    }
}

final class AuthFilter implements Filter {
    public String apply(Request req, Chain next) {
        if (req.user() == null) return "401 Unauthorized";             // stop the chain
        return next.proceed(req);                                      // or pass it on
    }
}
// new Chain(List.of(new AuthFilter(), new LoggingFilter()), 0, r -> "200 OK").proceed(request)
```

Each handler decides two things: whether to do something, and whether to pass the request on.
Because handlers run code *after* `next.proceed(...)` returns, one handler can also time or log
the whole rest of the chain.

**The rule:** link handlers so each one can handle, modify or reject a request and then pass it
to the next. The sender doesn't know which handler will deal with it.

**Where the JDK and Spring use it:** the **Servlet `FilterChain`**
(`chain.doFilter(request, response)` is the `next.proceed` above), **Spring Security's filter
chain** (a long ordered list of filters), Spring MVC's `HandlerInterceptor` (returning `false`
from `preHandle` stops the request), and `java.util.logging`, where a `Logger` passes records up
to its parent's handlers.

## State: behaviour depends on the current state

**Problem.** An order behaves differently depending on its status. Without a pattern, every
method starts with `switch (status)`, and the allowed transitions are scattered across them.

**Minimal example** (an enum where each constant is one state):

```java
enum OrderState {
    CREATED { @Override OrderState pay()    { return PAID; }
              @Override OrderState cancel() { return CANCELLED; } },
    PAID    { @Override OrderState ship()   { return SHIPPED; }
              @Override OrderState cancel() { return CANCELLED; } },
    SHIPPED { @Override OrderState deliver(){ return DELIVERED; } },
    DELIVERED,
    CANCELLED;

    // Default: not allowed. Each state overrides only what it permits.
    OrderState pay()     { throw notAllowed("pay"); }
    OrderState ship()    { throw notAllowed("ship"); }
    OrderState deliver() { throw notAllowed("deliver"); }
    OrderState cancel()  { throw notAllowed("cancel"); }

    private IllegalStateException notAllowed(String action) {
        return new IllegalStateException("cannot " + action + " an order that is " + name());
    }
}

final class Order {
    private OrderState state = OrderState.CREATED;
    void pay()  { state = state.pay(); }                  // the order delegates to its state
    void ship() { state = state.ship(); }
    OrderState state() { return state; }
}
```

The whole transition table is in one place, and an illegal move fails loudly.

**The rule:** the object (the *context*) holds a state object and delegates behaviour to it;
each state decides what is allowed and which state comes next. Use an enum when states have no
data of their own. Use one class per state (implementing a `State` interface) when states hold
data or need dependencies, as in a vending machine where the "has money" state tracks the
balance.

**Where you see it:** the JDK has no famous class built this way (`Thread.State` is only an
enum of values). You meet the pattern in workflow and order systems, and in libraries such as
Spring Statemachine. It is very common in LLD questions: vending machines, elevators, ATMs and
traffic lights.

## The rest of the behavioural family

| Pattern | Problem it solves | Where you see it |
|---|---|---|
| Command | Turn a request into an object so it can be queued, logged or undone | `Runnable`/`Callable` submitted to an executor; undo/redo stacks |
| Iterator | Walk a collection without knowing its structure | `java.util.Iterator`, the enhanced `for` loop |
| Mediator | Objects talk through one coordinator instead of to each other | `DispatcherServlet` coordinating handler mappings, adapters and view resolvers |
| Memento | Save and restore an object's state without exposing its internals | Editor undo snapshots; saving game state |
| Visitor | Add operations to a fixed set of types without editing them | `Files.walkFileTree` with a `FileVisitor`; compiler syntax-tree visitors |
| Interpreter | Evaluate sentences in a small language | `java.util.regex.Pattern`; Spring Expression Language (SpEL) |

## Lab (~10 min)

Take the `OrderState` enum and `Order` class above and put them in `StateLab.java` with a `main`.

1. Add a `StateListener` interface (`void onChange(OrderState from, OrderState to)`) and let
   `Order` keep a `CopyOnWriteArrayList` of listeners. Route every transition through one private
   `move(OrderState next)` method that notifies them. That is State plus Observer.
2. Subscribe a listener that prints `CREATED -> PAID` and so on. Run `pay()`, `ship()` and
   `deliver()`.
3. **Break it:** call `cancel()` on the delivered order. You should see
   `cannot cancel an order that is DELIVERED`, and the listener should *not* fire.
4. Add a `RETURNED` state reachable only from `DELIVERED`. Count how many places you edited. It
   should be one: the enum.

What to observe: the transition rules live in one place, and adding a reaction (the listener)
or a state didn't touch the other.

## Gotchas

- **Strategy vs State look identical in code.** The difference: a client *chooses* a strategy,
  while states *replace themselves* as the object's life moves on.
- **Observer leaks.** Listeners that are never unsubscribed keep objects alive and keep receiving
  events. Give long-lived subjects an `unsubscribe`.
- **Spring events are synchronous by default.** A slow or failing `@EventListener` slows or fails
  the publisher. Use `@TransactionalEventListener` for after-commit work and `@Async` or a queue
  for slow work.
- **A Chain where a handler forgets `next.proceed(...)` silently swallows requests.** Every
  branch of a handler must either respond or pass on.
- **Template Method locks you into inheritance.** If subclasses multiply in two directions,
  switch to Strategy (pass the steps in).

## In interviews

These patterns are the vocabulary of the LLD round:

- **Strategy:** the pluggable algorithm in [Design a Rate Limiter](#/q/design-rate-limiter) and
  the eviction policy in [Cache Service with Pluggable Eviction](#/q/design-cache-pluggable-eviction).
- **Observer:** [Design a Notification System](#/q/design-notification-system),
  [Design an Alert Monitoring System](#/q/design-alert-monitoring-system) and the callbacks in
  [LLD for a High-Frequency Trading System](#/q/design-hft-system-observer-callbacks).
- **State:** [Design a Vending Machine](#/q/design-vending-machine) and
  [Design an Elevator System](#/q/design-elevator-system) (with a Strategy for choosing which
  elevator answers a call).
- **Chain of Responsibility:** log levels and appenders in
  [Design a Multi-module Logging Framework](#/q/design-logging-framework).
- **Command and Memento:** [Undo/Redo for a Text Editor](#/q/design-undo-redo-text-editor).

Typical follow-ups:

- *"Why not just an if/else?"* A strong answer: with two fixed cases an `if` is fine; with an
  open-ended set that changes, the pattern keeps the core class closed (OCP) and each variant
  testable alone.
- *"Your observers are slow. What now?"* Make delivery asynchronous (an executor or a queue),
  isolate failures per listener, and decide whether ordering and at-least-once delivery matter.

Don't open with the pattern name. The Microsoft dossier records a candidate marked down for
jumping straight to Observer without exploring requirements. Name the pattern *after* the
requirement that justifies it.

## Explain it in 2 minutes

Prompt: *"Pick three behavioural patterns and show where Spring uses them."*

- Strategy: interchangeable algorithms behind one interface (`Comparator`, `PasswordEncoder`,
  injected `List<Strategy>`).
- Observer: publish an event and let listeners react (`ApplicationEventPublisher`,
  `@EventListener`, `@TransactionalEventListener` after commit; synchronous by default).
- Template Method: a fixed skeleton with variable steps (`JdbcTemplate` with a `RowMapper`,
  `OncePerRequestFilter`).
- Chain of Responsibility: an ordered list of handlers, each can stop the request (servlet
  filters, Spring Security).
- State: the object delegates to its current state, which decides the allowed transitions.

## Check yourself

1. What is the structural difference between Strategy and State, if any, and what is the real
   difference?
2. Why can `@EventListener` make your `placeOrder` endpoint slow?
3. In the `Chain` example, how would a filter measure the time taken by the rest of the chain?
4. `JdbcTemplate` doesn't make you subclass anything. Why is it still called a template?
5. Which pattern fits "an elevator that behaves differently when moving up, moving down, idle or
   under maintenance"?

### Answers

1. Structurally they are almost the same (a context delegating to an interface). With Strategy
   the client chooses the algorithm; with State the state objects decide the next state as the
   object's life moves on.
2. Listeners run synchronously on the publisher's thread by default, so the endpoint waits for
   every listener (and fails if one throws).
3. Record the time, call `next.proceed(req)`, then record the time again after it returns.
4. It owns the fixed algorithm (connection, statement, iteration, exception translation,
   cleanup) and you supply only the variable step as a callback. That is the template idea,
   delivered through a callback instead of a subclass.
5. State, usually combined with a Strategy for choosing which elevator serves a request.
