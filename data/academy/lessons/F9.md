## Where we are

DB-SQL-6 and DB-SQL-7 covered indexes and transactions, DB-SQL-10 covered scaling a database, and
SYS-DES-2 gave you a design method. This lesson uses them on a design that nearly every B2B product
needs: many customer companies on one system, each one sure that nobody else can see its data.

## The problem

ShopKart now sells its platform to other retailers. Each retailer is a **tenant**: a customer
organisation with its own users and data, sharing your software. On Monday a developer writes a report
query and forgets `WHERE tenant_id = ?`. One retailer's dashboard shows another retailer's revenue. On
Tuesday the largest tenant imports two million products, and every other tenant's pages time out.

These are the two problems of **multi-tenancy**: **isolation** (no tenant ever sees another's data)
and **fairness** (no tenant ruins performance for the rest). Each decision here trades those against
cost and operational effort.

## Three isolation models

| Model | How | Isolation | Cost per tenant | Operations |
|---|---|---|---|---|
| **Silo:** database per tenant | Own database or cluster | Strongest | Highest | Hard at scale: N migrations, N backups |
| **Bridge:** schema per tenant | One database, a schema each | Medium | Medium | Migrations run N times; catalogs grow |
| **Pool:** shared tables | A `tenant_id` column on each row | Weakest by default | Lowest | Simple, but one mistake leaks data |

There is no single right answer, and the honest choice depends on your tenants:

- **Thousands of small tenants:** pool. A database each would be unaffordable.
- **A few large regulated customers:** silo. Contracts may demand it, and backup, restore and data
  residency become per-customer actions.
- **A mix:** pool for the standard plan and silo for enterprise. This hybrid is common, and works if
  the app can route each tenant to its database.

## Finding the tenant

Every request has to answer "which tenant is this?" before it touches data. Typical sources are a
claim in a verified JWT (SPRING-BOOT-9), or a subdomain such as `acme.shopkart.com`
checked against the logged-in user's memberships.

**The rule: the tenant comes from authenticated identity, never from something the client can freely
set.** Taking `X-Tenant-Id` from a header or `tenantId` from a request body, without checking
membership, is the classic hole. It is an IDOR across companies: change one value and read someone
else's data.

Resolve it once, at the edge, and keep it for the request:

```java
public final class TenantContext {
    private static final ThreadLocal<String> CURRENT = new ThreadLocal<>();

    public static void set(String tenantId) { CURRENT.set(tenantId); }
    public static void clear() { CURRENT.remove(); }

    public static String require() {
        String tenant = CURRENT.get();
        if (tenant == null) throw new IllegalStateException("No tenant in context");
        return tenant;
    }
}
```

A servlet filter sets it after authentication and clears it in `finally`. Three things follow:

- `require()` **fails closed.** No tenant means an error, never "all tenants".
- A pooled thread that keeps a value serves the next request as the wrong tenant, so `clear()` matters.
- Like DIST-SYS-7's MDC, it does not cross threads by itself. Async work needs a `TaskDecorator`.

## Layer one: filtering in the application

In the pool model, every query needs a tenant filter. Writing it by hand means it will be forgotten
one day, so let the framework add it. Hibernate has a discriminator approach built in:

```java
@Entity
class Invoice {
    @Id
    Long id;

    @TenantId                     // Hibernate fills this on insert and filters on it in queries
    String tenantId;
}

@Component
class TenantResolver implements CurrentTenantIdentifierResolver<String> {
    @Override
    public String resolveCurrentTenantIdentifier() {
        return TenantContext.require();
    }

    @Override
    public boolean validateExistingCurrentSessions() {
        return true;
    }
}
```

That closes the gap for code that goes through Hibernate. It does nothing for a native SQL query, a
`JdbcTemplate` report, a data fix, or a BI tool that connects directly. For those you want a second
layer that sits in the database itself.

## Layer two: row-level security in Postgres

**Row-level security (RLS)** makes the database filter rows according to a **policy**, so that a query
which forgets its `WHERE` clause still sees only one tenant's rows.

```sql
ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON invoices
    USING      (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)
    WITH CHECK (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid);
```

- `USING` filters which existing rows are visible to reads, updates and deletes.
- `WITH CHECK` validates new or changed rows, so you cannot write into another tenant.
- `current_setting('app.tenant_id', true)` reads a custom setting; `true` means "return NULL rather
  than fail if it was never set".

Each line here prevents something real. All of these were observed on a real Postgres:

| Situation | Result |
|---|---|
| `ENABLE` only, connected as the table owner | **All rows visible**: owners bypass RLS |
| `FORCE` added, owner, no tenant set | 0 rows |
| App role, no tenant set | 0 rows: it fails closed |
| App role, tenant set in the transaction | That tenant's rows only |
| Insert a row for another tenant | Blocked: `new row violates row-level security policy` |
| Without `nullif`, after a transaction ends | **Error:** `invalid input syntax for type uuid: ""` |

That last row is a subtle trap. Once a custom setting has been used on a connection, it does not go
back to NULL after `SET LOCAL` ends. It goes back to an empty string, and casting that to `uuid`
fails. `nullif(..., '')` turns it back into NULL, and the policy simply matches no rows.

Superusers and roles with `BYPASSRLS` always skip these policies. So the app must connect as an
ordinary role. Migrations need a separate role that can bypass RLS, because `FORCE` applies to the
owner too.

## Setting the tenant safely with a pool

This is the part that causes real leaks. Connections are reused (DB-SQL-5), and settings live on the
connection. So a tenant set at session level stays there for the next request that borrows it.

```java
@Transactional
public List<Invoice> invoices() {
    jdbc.queryForObject("select set_config('app.tenant_id', ?, true)", String.class, TenantContext.require());
    return jdbc.query("select id, amount from invoices", invoiceMapper);
}
```

The third argument of `set_config`, `true`, means **transaction-local**, the same as `SET LOCAL`. The
value disappears at commit or rollback, so it cannot reach the next borrower. With `false`, the value
survived the commit in testing, and the same connection still showed tenant 2's rows. That is the leak.
Transaction-local also works with PgBouncer in transaction pooling mode, where a session setting would
not be reliable.

In a real service, put that one call in a single place, such as an aspect that runs right after the
transaction begins, so that nobody needs to remember it.

## Indexes and keys for shared tables

In the pool model, nearly every query filters on `tenant_id`, so design for that:

- **Put `tenant_id` first in composite indexes:** `(tenant_id, created_at)`, as DB-SQL-6 explained
  for left-most prefixes.
- **Make unique constraints per tenant:** `UNIQUE (tenant_id, email)`. Two tenants can have a user with
  the same email address.
- **Include the tenant in foreign keys** where you can, so that a row cannot point at another
  tenant's row.
- **Consider partitioning by tenant** (DB-SQL-10). A huge tenant can then be moved to its own shard.

Sizes will be very uneven: a few large tenants usually hold most of the data. So hash-sharding by
`tenant_id` can leave one shard overloaded, and the query planner's statistics can suit small tenants
and hurt large ones. Keep a lookup table that maps each tenant to its shard, so you can move them.

## Noisy neighbours

A **noisy neighbour** is a tenant whose load hurts others. Isolation of data does nothing for this, so
you need limits at each shared resource:

| Resource | Protection |
|---|---|
| API | Per-tenant rate limits by plan (SYS-DES-4) |
| Database | Statement timeouts; heavy reports on a replica; limited connections per tenant |
| Background jobs | A fair queue per tenant, not one global FIFO |
| Kafka | Avoid `tenant_id` alone as the key when one tenant dominates: it makes a hot partition |
| Storage | Quotas per plan |

The largest step up is **cell-based architecture**: several complete copies of the stack, each serving
a set of tenants. A bad deploy or a runaway tenant then affects one cell, not everybody. The cost is
running and routing across many copies, so it is for later, not for day one.

## Everything else that must know the tenant

The database is only one place data lives. The leaks that get past review tend to be here:

- **Caches:** the key must include the tenant, as in `tenant:acme:product:42`. Without that, one
  tenant is served another's cached page.
- **Files:** a prefix per tenant in S3, and a tenant check before issuing a presigned URL (DIST-SYS-8).
- **Messages:** carry the tenant in the event, and restore `TenantContext` in the consumer. Consumers
  have no HTTP request to get it from.
- **Scheduled jobs:** there is no request, so loop over tenants explicitly and set the context for each.
- **Search indexes and exports:** each needs the same filter.
- **BI dashboards:** tools such as QuickSight and Metabase connect outside your app, so they need
  their own row-level rules, tied to the viewer's tenant.
- **Logs and metrics:** put the tenant in logs and traces. Be careful with it as a metric label when
  there are thousands of tenants, for DIST-SYS-7's cardinality reasons.

Also plan the tenant lifecycle: onboarding, plan changes, data export, and deletion. A customer who
leaves may have a contractual right to have all of their data removed, including from backups according
to your retention policy. If deleting a tenant is hard, that is a design flaw.

## Proving isolation

Do not rely on reviewers noticing a missing filter. Write a test that creates two tenants, adds data
for each, and asserts that tenant A can never read or change tenant B's records, through each API.
Run this against real Postgres with Testcontainers (SPRING-BOOT-8), because H2 has no row-level
security. Also test that a request with no tenant fails, and connect as the real app role, because a
test running as a superuser passes while proving nothing.

## Lab (~10 min)

**Part 1: noisy neighbours.** Tenant `big` drops 1,000 jobs into the queue just before tenant `small`
submits 5. Compare one global queue with round-robin across tenants. Press Run, or save it as
`FairQueueLab.java` and run `java FairQueueLab.java`.

```java
import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Queue;

public class FairQueueLab {
    record Job(String tenant, int number) {}

    static List<Job> submitted() {
        List<Job> jobs = new ArrayList<>();
        for (int i = 1; i <= 1000; i++) jobs.add(new Job("big", i));
        for (int i = 1; i <= 5; i++) jobs.add(new Job("small", i));
        return jobs;
    }

    static List<Job> globalFifo(List<Job> jobs) {
        return new ArrayList<>(jobs);
    }

    static List<Job> fairRoundRobin(List<Job> jobs) {
        Map<String, Queue<Job>> perTenant = new LinkedHashMap<>();
        for (Job job : jobs) perTenant.computeIfAbsent(job.tenant(), t -> new ArrayDeque<>()).add(job);

        List<Job> order = new ArrayList<>();
        while (!perTenant.isEmpty()) {
            perTenant.values().removeIf(queue -> {
                order.add(queue.remove());       // one job from each tenant per turn
                return queue.isEmpty();
            });
        }
        return order;
    }

    static void report(String name, List<Job> order) {
        int lastSmall = 0;
        for (int i = 0; i < order.size(); i++) {
            if (order.get(i).tenant().equals("small")) lastSmall = i + 1;
        }
        System.out.printf("%-12s small tenant finished at position %d of %d%n", name, lastSmall, order.size());
    }

    public static void main(String[] args) {
        report("global FIFO", globalFifo(submitted()));
        report("fair", fairRoundRobin(submitted()));
    }
}
```

**What to observe:** with one global queue, `small` waits behind all of `big`'s work: position 1005.
With fair scheduling, it finishes at position 10, while `big` finishes only 5 positions later than
before. Fairness costs the big tenant almost nothing and changes everything for the small one.

**Part 2: try RLS, if you have Postgres locally.** Create `invoices` with a `tenant_id uuid` column,
add rows for two tenants, apply the policy above, and create a non-superuser role with table grants.

1. Connect as that role and run `SELECT * FROM invoices`: 0 rows.
2. `BEGIN; SET LOCAL app.tenant_id = '<a tenant uuid>'; SELECT * FROM invoices; COMMIT;`: one tenant.
3. **Break it:** take `nullif` out of the policy, and repeat step 1 on the same connection after step 2.
   You get the `uuid` error from the table above.
4. **Break it again:** `ALTER TABLE invoices NO FORCE ROW LEVEL SECURITY` and read as the owner: all rows.

## Gotchas

- **Tenant id taken from a header or request body.** Any user can change it. Take it from verified
  identity and check membership.
- **`ENABLE` without `FORCE`, or an app connecting as owner or superuser.** RLS silently does nothing.
  Test as the real app role.
- **Session-level `SET` on pooled connections.** The next request inherits the tenant. Use `SET LOCAL`
  or `set_config(..., true)` inside a transaction.
- **Cache keys without the tenant.** One tenant is served another's data. Prefix every key.
- **Background jobs and consumers with no tenant context.** Set it explicitly, and fail if it's missing.
- **Global unique constraints.** `UNIQUE (email)` stops two tenants having the same user. Scope it by tenant.

## In interviews

Asked as "Design a multi-tenant SaaS platform", "Shared database or a database per tenant?", "How do
you stop one customer seeing another's data?" and "How do you handle a noisy neighbour?". If your
resume mentions multi-tenant work, expect "How exactly did you enforce isolation?", and be ready with
what was enforced in the app, in the database, and in the BI layer.

**Follow-up: "A large customer now wants their own database."** Design for this early. Keep a tenant
registry that maps each tenant to a data source, route on it, and support moving a tenant: copy the
data, catch up with changes (CDC, DB-SQL-10), switch over, verify, then delete the old rows.

**Follow-up: "Schema-per-tenant with 5,000 tenants?"** Migrations must run 5,000 times and can fail
halfway, and Postgres catalogs and connection pools come under strain. Past a certain point, the pool
model with RLS is usually easier to run.

## Explain it in 2 minutes

"How would you design tenant isolation for a SaaS product?"

- Pick a model by customer mix: pool for many small tenants, silo for large or regulated ones, often both.
- Resolve the tenant from authenticated identity at the edge, and fail closed if it's missing.
- Defence in depth: automatic filtering in the app, plus row-level security in Postgres.
- Set the tenant per transaction so pooled connections cannot leak it.
- Carry it everywhere: caches, files, messages, jobs, search and dashboards.
- Protect fairness with per-tenant limits and fair queues, and prove isolation with two-tenant tests.

## Check yourself

1. What are the three isolation models, and when would you pick each one?
2. Why must the tenant not come from a request header?
3. What does `FORCE ROW LEVEL SECURITY` add to `ENABLE`?
4. Why is `set_config(..., true)` safe on a pooled connection when `false` is not?
5. Name three places outside the database that also need the tenant.

### Answers

1. Silo (a database each) for large or regulated tenants, bridge (a schema each) for a moderate number
   needing more separation, pool (shared tables) for many small tenants.
2. The client controls it, so a user could read another tenant's data. It has to come from verified
   identity, with membership checked.
3. It applies the policies to the table owner too. Superusers and `BYPASSRLS` roles still skip them.
4. `true` limits the value to the current transaction, so it is gone before the connection returns to
   the pool. `false` sets it for the session, and the next borrower inherits it.
5. Any three of: cache keys, S3 prefixes, messages and consumers, scheduled jobs, search indexes,
   exports, BI dashboards.
