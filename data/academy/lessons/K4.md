## Where we are

After CAPSTONE-3, TicketHub is a Spring Boot service. The in-memory `BookingEngine` and `EventCatalog` are beans, configuration is typed and validated, and three read-only endpoints serve events and seat maps. Nothing can be booked over HTTP yet, and the errors are handled ad hoc. Today you add the write side the way WEB-API-2 describes it, using the MVC pipeline from SPRING-BOOT-7.

## Goal

Expose holds, confirm and release over REST with production-grade edges. Requests are validated declaratively. Every error, whether yours or Spring's, comes back as an RFC 9457 **problem detail** with a stable `code`. Creating a hold returns `201 Created` with a `Location` header and is safe to retry thanks to an `Idempotency-Key` header. `/events` is paginated, and every log line carries a request id. Idempotency is in memory for now, behind an interface that CAPSTONE-5 backs with the `idempotency_key` table. Every status code gets a MockMvc test.

## Steps

### 1. Requests, responses, and a validated controller (12 min)

```java
package com.tickethub.booking;

public record HoldRequest(@NotEmpty @Size(max = 10) List<@NotNull @Positive Long> seatIds) {
    @AssertTrue(message = "seatIds must not contain duplicates")
    public boolean isSeatIdsUnique() {           // validated as property "seatIdsUnique"
        return seatIds == null || new HashSet<>(seatIds).size() == seatIds.size();
    }
}
```

The duplicate check matters. Without it, `SeatHold`'s constructor throws `IllegalArgumentException`, which surfaces as a `500`. Validation at the edge turns a client mistake into a `400`; the domain invariant stays as the last line of defence.

```java
package com.tickethub.booking;

@RestController
@RequestMapping("/api/v1")
class HoldController {
    private final HoldService holdService;
    private final BookingEngine engine;

    HoldController(HoldService holdService, BookingEngine engine) {
        this.holdService = holdService;
        this.engine = engine;
    }

    @PostMapping("/events/{eventId}/holds")
    ResponseEntity<HoldResponse> create(@PathVariable long eventId,
                                        @RequestHeader("Idempotency-Key") @NotBlank @Size(max = 100) String idempotencyKey,
                                        @RequestHeader("X-User-Id") @NotBlank String userId,
                                        @Valid @RequestBody HoldRequest request) {
        SeatHold hold = holdService.hold(eventId, userId, idempotencyKey, request.seatIds());
        URI location = ServletUriComponentsBuilder.fromCurrentContextPath()
                .path("/api/v1/holds/{id}").buildAndExpand(hold.id()).toUri();
        return ResponseEntity.created(location).body(HoldResponse.from(hold));
    }

    @GetMapping("/holds/{id}")
    HoldResponse get(@PathVariable UUID id) { return HoldResponse.from(engine.findHold(id)); }

    @PostMapping("/holds/{id}/confirm")
    BookingResponse confirm(@PathVariable UUID id) { return BookingResponse.from(engine.confirm(id)); }

    @DeleteMapping("/holds/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    void release(@PathVariable UUID id) { engine.release(id); }
}
```

Because parameters carry constraint annotations, Spring 6.1+ applies **built-in method validation** to the whole method. A failure is reported as `HandlerMethodValidationException`, while a body-only failure is `MethodArgumentNotValidException`. Your handler treats both the same. Do **not** put `@Validated` on the controller: that switches to the older AOP-based validation, which throws `ConstraintViolationException` and becomes a `500` unless you handle it separately.

### 2. Idempotency key (15 min)

**The problem:** the client sends `POST /holds`, the network drops the response, and the client retries. Without protection the retry fails with `409` against the client's *own* hold, or, with different seats, creates a second hold. An **idempotency key** is a client-generated unique id for one logical operation. The server remembers the key and its outcome, and answers a retry with the original result.

The three cases to handle: same key with the same request → replay the original response; same key with a *different* request → `422` (a client bug); same key while the first request is still running → `409`, try again shortly.

```java
package com.tickethub.common;

public interface IdempotencyStore<T> {
    /** Reserves the key. Empty if this caller now owns it; otherwise the record already stored. */
    Optional<IdempotencyRecord<T>> reserve(String key, String fingerprint);
    void complete(String key, T response);
    void abandon(String key);
}

public record IdempotencyRecord<T>(String fingerprint, T response) {
    public boolean completed() { return response != null; }
}
```

`InMemoryIdempotencyStore<T>` wraps a `ConcurrentHashMap<String, IdempotencyRecord<T>>`. In `reserve`, `putIfAbsent(key, new IdempotencyRecord<>(fingerprint, null))` is the atomic "first one wins". `complete` uses `computeIfPresent` to fill in the response, and `abandon` calls `remove`. Register it as `@Bean IdempotencyStore<SeatHold> holdIdempotencyStore()` in `BookingConfig`. Spring matches the generic type when it injects.

```java
package com.tickethub.booking;

@Service
public class HoldService {
    private final BookingEngine engine;
    private final IdempotencyStore<SeatHold> store;

    public HoldService(BookingEngine engine, IdempotencyStore<SeatHold> store) {
        this.engine = engine;
        this.store = store;
    }

    public SeatHold hold(long eventId, String userId, String idempotencyKey, List<Long> seatIds) {
        String key = userId + ":" + idempotencyKey;                     // keys are scoped per client
        String fingerprint = eventId + ":" + seatIds.stream().sorted().toList();
        Optional<IdempotencyRecord<SeatHold>> existing = store.reserve(key, fingerprint);
        if (existing.isPresent()) {
            IdempotencyRecord<SeatHold> rec = existing.get();
            if (!rec.fingerprint().equals(fingerprint)) throw new IdempotencyKeyReusedException(idempotencyKey);
            if (!rec.completed()) throw new IdempotencyRequestInProgressException(idempotencyKey);
            return rec.response();                                       // replay: same hold, same Location
        }
        try {
            SeatHold hold = engine.hold(eventId, userId, seatIds);
            store.complete(key, hold);
            return hold;
        } catch (RuntimeException e) {
            store.abandon(key);    // failures are not cached: the same key may retry after a 409
            throw e;
        }
    }
}
```

The in-memory store forgets everything on restart and never expires keys. CAPSTONE-5 moves it to the `idempotency_key` table with a creation timestamp, written in the **same transaction** as the hold. That is what makes "hold created, key not recorded" impossible.

### 3. Problem details for every error (12 min)

**RFC 9457** (which replaced RFC 7807) defines `application/problem+json`: a standard error body with `type` (a URI naming the problem kind), `title`, `status`, `detail` and any extension members. Your extension is `code`. Extending `ResponseEntityExceptionHandler` makes Spring's own exceptions (malformed JSON, missing header, wrong method, validation) come out as problem details too.

```java
package com.tickethub.common;

@RestControllerAdvice
class ApiExceptionHandler extends ResponseEntityExceptionHandler {
    private static final Map<String, HttpStatus> STATUS_BY_CODE = Map.of(
            "EVENT_NOT_FOUND", HttpStatus.NOT_FOUND,
            "HOLD_NOT_FOUND", HttpStatus.NOT_FOUND,
            "BOOKING_NOT_FOUND", HttpStatus.NOT_FOUND,
            "SEAT_UNAVAILABLE", HttpStatus.CONFLICT,
            "HOLD_EXPIRED", HttpStatus.GONE,
            "IDEMPOTENCY_KEY_REUSED", HttpStatus.UNPROCESSABLE_ENTITY,
            "IDEMPOTENCY_IN_PROGRESS", HttpStatus.CONFLICT);

    @ExceptionHandler(TicketHubException.class)
    ProblemDetail handleDomain(TicketHubException ex) {
        HttpStatus status = STATUS_BY_CODE.getOrDefault(ex.code(), HttpStatus.INTERNAL_SERVER_ERROR);
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(status, ex.getMessage());
        pd.setType(URI.create("https://tickethub.example/problems/" + ex.code().toLowerCase(Locale.ROOT).replace('_', '-')));
        pd.setProperty("code", ex.code());
        return pd;
    }

    @Override
    protected ResponseEntity<Object> handleExceptionInternal(Exception ex, Object body, HttpHeaders headers,
                                                             HttpStatusCode status, WebRequest request) {
        ResponseEntity<Object> response = super.handleExceptionInternal(ex, body, headers, status, request);
        if (response != null && response.getBody() instanceof ProblemDetail pd) {
            switch (ex) {
                case MethodArgumentNotValidException e -> {
                    pd.setProperty("code", "VALIDATION_FAILED");
                    pd.setProperty("errors", e.getBindingResult().getFieldErrors().stream()
                            .map(f -> f.getField() + ": " + f.getDefaultMessage()).toList());
                }
                case HandlerMethodValidationException e -> {
                    pd.setProperty("code", "VALIDATION_FAILED");
                    pd.setProperty("errors", e.getAllErrors().stream()
                            .map(MessageSourceResolvable::getDefaultMessage).toList());
                }
                default -> pd.setProperty("code", "HTTP_" + status.value());
            }
        }
        return response;
    }
}
```

Two details matter here. The status mapping is keyed on the **stable code**, so the advice never imports feature classes, and adding an error is one map entry. And `super.handleExceptionInternal` is what builds the `ProblemDetail` (the `body` argument is usually `null`), so you decorate the result *after* calling it. Map status codes deliberately: `409` means the request conflicts with current state, `410` means the hold existed but is gone for good, and `422` means a well-formed request the server refuses to process.

> Boot 4 / Spring 7 note: `HttpStatus.UNPROCESSABLE_ENTITY` is renamed `UNPROCESSABLE_CONTENT`.

### 4. Pagination (6 min)

```java
package com.tickethub.common;

public record PageResponse<T>(List<T> content, int page, int size, long totalElements, int totalPages) {
    public static <T> PageResponse<T> of(List<T> all, int page, int size) {
        List<T> content = all.stream().skip((long) page * size).limit(size).toList();
        return new PageResponse<>(content, page, size, all.size(), (all.size() + size - 1) / size);
    }
}
```

```java
@GetMapping
PageResponse<EventResponse> list(@RequestParam(defaultValue = "0") @Min(0) int page,
                                 @RequestParam(defaultValue = "20") @Min(1) @Max(100) int size) {
    List<EventResponse> all = catalog.upcoming(clock.instant()).stream()
            .map(e -> EventResponse.from(e, catalog.venueOf(e.id()))).toList();
    return PageResponse.of(all, page, size);
}
```

This is **offset pagination**. It is stable only because CAPSTONE-2 sorts with an `id` tie-breaker. CAPSTONE-5 pushes `LIMIT/OFFSET` into SQL through Spring Data's `Pageable`, and the response shape stays the same. Capping `size` at 100 stops `size=1000000` from becoming a denial-of-service. The list is now wrapped in an object, so update CAPSTONE-3's `listsUpcomingEvents` to read `$.content.length()` and `$.content[0].name`.

### 5. Request id filter (6 min)

A **filter** runs for every request, before the `DispatcherServlet`, including 404s and errors. An aspect only wraps controller methods, which is why this is a filter. The **MDC** (Mapped Diagnostic Context) is a per-thread map that the logging pattern can print.

```java
package com.tickethub.common;

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
class RequestIdFilter extends OncePerRequestFilter {
    static final String HEADER = "X-Request-Id";
    private static final Logger log = LoggerFactory.getLogger(RequestIdFilter.class);

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
            throws ServletException, IOException {
        String requestId = Optional.ofNullable(request.getHeader(HEADER))
                .filter(id -> id.matches("[A-Za-z0-9-]{1,64}"))           // never trust raw input into logs
                .orElseGet(() -> UUID.randomUUID().toString());
        long start = System.nanoTime();
        MDC.put("requestId", requestId);
        response.setHeader(HEADER, requestId);
        try {
            chain.doFilter(request, response);
        } finally {
            log.info("{} {} -> {} in {} ms", request.getMethod(), request.getRequestURI(),
                    response.getStatus(), (System.nanoTime() - start) / 1_000_000);
            MDC.remove("requestId");                                     // pooled threads: always clean up
        }
    }
}
```

In `application.yml`, set `logging.pattern.level: "%5p [%X{requestId:-}]"`.

## Hints

- **Validation errors return `400` but with `code: HTTP_400`**: your `switch` did not match. Check which exception arrived. With constrained headers on the method, body errors come as `HandlerMethodValidationException`.
- **`Location` is `http://localhost/...` in tests**: MockMvc's default host. Assert with `startsWith("http://localhost/api/v1/holds/")`.
- **The replay test returns `409 SEAT_UNAVAILABLE`**: the key is not scoped consistently, or `abandon` ran after a success. Log the reserve result once.
- **`ProblemDetail` serialises as plain JSON**: you returned `ResponseEntity<Map>` somewhere. Return `ProblemDetail` itself (or `ErrorResponse`) to get `application/problem+json`.
- **The MDC value leaks into the next request's logs**: the `finally` is missing, or it calls `MDC.put` again after `remove`.

## Talk about it in interviews

**"How do you make a POST idempotent?"**
- *What:* the client sends an `Idempotency-Key`, and the server stores key → (request fingerprint, outcome) and replays the outcome on retries.
- *How it works inside:* an atomic reserve (`putIfAbsent` now, a unique constraint on `idempotency_key` in CAPSTONE-5) decides one owner. A different fingerprint with the same key is `422`, and a still-running first request is `409`. Failures are not cached, so the client can retry.
- *Where used:* TicketHub's `POST /events/{id}/holds` returns the same hold and `Location` on a replay. Payment APIs use the same pattern.
- *What goes wrong:* storing the key outside the business transaction ("hold created, key lost" leads to a double hold after a crash), keys not scoped per client, no expiry (the table grows forever), and caching a transient `5xx` as if it were the final answer.

**"How do you design API errors?"** Use RFC 9457 problem details with a stable machine `code` that clients and alerts can key on. Choose statuses on purpose (`409` conflict, `410` gone, `422` semantically invalid, `400` malformed), use one `@RestControllerAdvice`, and never put stack traces or internal ids in `detail`. In TicketHub, Spring's own errors go through the same path, so clients only ever parse one shape.

**"Offset or cursor pagination?"** Offset (`page`, `size`) is simple and lets users jump to a page, but deep pages get slow in SQL (the database still walks the skipped rows), and inserts shift items between pages. A cursor (`after=<last sort key>`) is stable and fast but forward-only. Either way, the order must be deterministic: TicketHub sorts by `startsAt`, then `id`.

**"How do you trace one request through the logs?"** A filter assigns or accepts a validated request id, puts it in the MDC, returns it in a header, and removes it in `finally`. Because the MDC is per-thread, async work has to copy it across. CAPSTONE-10 carries the same idea through Kafka headers.
