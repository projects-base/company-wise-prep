## Where we are

From B1 you can start, join and interrupt threads, and you have watched two threads lose updates to a shared counter. From A6 you know two things: **happens-before** is the rule that decides when one thread is guaranteed to see another's writes, and `volatile` gives visibility but not atomicity. This lesson fixes the lost update with locks, and then shows you the new bug that locks bring with them: deadlock.

## The problem

`count++` is three steps: read, add, write. The B1 lab showed that two threads can interleave those steps and lose increments. Making `count` `volatile` did not help, because `volatile` makes each read and write visible but does nothing to stop a second thread from slipping in between them.

What we need is a way to say "while I am doing these three steps, nobody else may touch `count`."

## Critical sections and mutual exclusion

A **critical section** is a piece of code that touches shared state and must not run in two threads at once. **Mutual exclusion** means at most one thread is inside the critical section at a time. A **lock** (also called a **mutex**, short for "mutual exclusion") is the object that enforces it. A thread *acquires* the lock to enter and *releases* it to leave. Any other thread that tries to acquire the lock while it is held must wait.

## `synchronized`: Java's built-in lock

Every Java object has a hidden lock called its **monitor**. (It is also called the **intrinsic lock**.) The `synchronized` keyword acquires and releases that monitor for you.

```java
class Counter {
    private final Object lock = new Object();
    private int count;

    void increment() {
        synchronized (lock) {   // acquire lock's monitor (wait here if another thread holds it)
            count++;            // read-add-write, now with no interleaving
        }                       // release, even if an exception is thrown
    }

    int get() {
        synchronized (lock) { return count; }
    }
}
```

There are two shorthand forms:

- A `synchronized` instance method locks `this`.
- A `static synchronized` method locks the `Class` object (`Counter.class`).

Locking a `private final` object, as above, is often better than locking `this`. Outside code cannot grab your lock and interfere with it.

## A lock gives two guarantees, not one

1. **Atomicity.** The block runs as one indivisible step from the point of view of every other thread that uses the *same* lock.
2. **Visibility.** Releasing a monitor *happens-before* every later acquisition of that same monitor (this is the A6 rule). So the next thread to take the lock sees every write made inside the block.

That second point is why `get()` above is also `synchronized`. If the reader takes no lock, nothing guarantees that it sees the latest value. The rule is that **every access to the shared state, reads included, goes through the same lock.** Two different locks protecting the same field give you no protection at all.

## Reentrancy

Suppose a `synchronized` method calls another `synchronized` method on the same object. Does the thread deadlock with itself? It does not, because Java locks are **reentrant**. A thread that already holds a lock can acquire it again. The lock keeps a *hold count* and is released only when the count returns to zero.

```java
synchronized void a() { b(); }   // holds this's monitor
synchronized void b() { }        // acquires it again: count goes 1 → 2 → 1 → 0
```

## `ReentrantLock`: the lock as an object

`synchronized` is simple, but it is also rigid. A thread waiting for a monitor cannot be interrupted, cannot give up after a timeout, and cannot ask "is the lock free?" `java.util.concurrent.locks.ReentrantLock` adds all three.

```java
private final ReentrantLock lock = new ReentrantLock();

void increment() {
    lock.lock();
    try {
        count++;
    } finally {
        lock.unlock();          // ALWAYS in finally, or one exception leaves it locked forever
    }
}
```

Here is what it adds:

| Feature | `synchronized` | `ReentrantLock` |
|---|---|---|
| Released automatically | yes, when the block exits | no, you must `unlock()` in `finally` |
| Give up after a timeout | no | `tryLock(1, SECONDS)` |
| Interruptible while waiting | no | `lockInterruptibly()` |
| Fair ordering option | no | `new ReentrantLock(true)` |
| Several wait-conditions | one per object | `newCondition()`, many per lock |

A **fair** lock hands itself to the thread that has waited longest. That prevents starvation but lowers throughput, so the default is unfair.

The rule: use `synchronized` by default, because it is shorter and impossible to leave locked by accident. Reach for `ReentrantLock` when you need a timeout, interruptibility, fairness, or several conditions. (B6 adds one more reason: on Java 21, a virtual thread that blocks inside `synchronized` pins its carrier thread.)

There is one more variant worth knowing. `ReentrantReadWriteLock` lets many readers in at once but only one writer. It helps when reads are frequent and slow. When the critical section is tiny, its extra bookkeeping usually costs more than it saves.

## Deadlock

Locks bring a new failure. Consider two bank accounts, where each transfer locks both of them:

```java
void transfer(Account from, Account to, int amount) {
    synchronized (from) {
        synchronized (to) {
            from.balance -= amount;
            to.balance   += amount;
        }
    }
}
```

Now suppose thread 1 runs `transfer(a, b)` while thread 2 runs `transfer(b, a)`:

```text
Thread 1: lock a ✔ ──── wants b ──┐
                                  │   each holds what the other needs:
Thread 2: lock b ✔ ──── wants a ──┘   neither can ever proceed
```

That is a **deadlock**: a set of threads, each waiting for a lock that another thread in the set holds. Nothing crashes, CPU usage drops to zero, and those requests simply never finish.

A deadlock needs all four of these conditions, known as the **Coffman conditions**:

1. **Mutual exclusion.** A resource can be held by only one thread.
2. **Hold and wait.** A thread holds one lock while waiting for another.
3. **No preemption.** Nobody can take a lock away from the thread that holds it.
4. **Circular wait.** There is a cycle: T1 waits for T2, which waits for T1.

To prevent deadlock, you break one of the four. In practice there are two common ways:

- **Lock ordering** breaks circular wait. Always acquire locks in one global order, for example by account id. If every thread locks the lower id first, no cycle can form.
- **`tryLock` with a timeout** breaks hold-and-wait. If you cannot get the second lock, release the first, back off for a random moment, and retry.

## Finding a deadlock in production

A **thread dump** is a snapshot of every thread's stack and state. Take one with `jstack <pid>` or `jcmd <pid> Thread.print`. For deadlocks on monitors and on `ReentrantLock`, the JVM finds the cycle for you and prints `Found one Java-level deadlock:` along with the threads and locks involved. You can also check from inside your code with `ManagementFactory.getThreadMXBean().findDeadlockedThreads()`.

## Livelock and starvation

Two related failures are worth naming:

- **Livelock.** Threads keep reacting to each other without making progress, for example two `tryLock` loops that back off and retry in perfect lockstep. Adding *random* backoff fixes it.
- **Starvation.** A thread never gets the lock because others keep winning it. A fair lock fixes it, at the cost of throughput.

## Lab (~10 min)

Save this as `Deadlock.java` and run it with `java Deadlock.java`.

```java
import java.lang.management.ManagementFactory;
import java.util.concurrent.TimeUnit;

public class Deadlock {
    static final boolean ORDERED = false;   // flip to true for the fix

    static final class Account {
        final int id; int balance;
        Account(int id, int balance) { this.id = id; this.balance = balance; }
    }

    static void transfer(Account from, Account to, int amount) {
        Account first = from, second = to;
        if (ORDERED && from.id > to.id) { first = to; second = from; }  // lock lower id first
        synchronized (first) {
            sleep(50);                       // widen the window so the bug shows every time
            synchronized (second) {
                from.balance -= amount;
                to.balance   += amount;
            }
        }
    }

    public static void main(String[] args) throws Exception {
        Account a = new Account(1, 100), b = new Account(2, 100);

        Thread t1 = Thread.ofPlatform().name("t1").start(() -> transfer(a, b, 10));
        Thread t2 = Thread.ofPlatform().name("t2").start(() -> transfer(b, a, 20));

        t1.join(TimeUnit.SECONDS.toMillis(2));
        t2.join(TimeUnit.SECONDS.toMillis(2));

        long[] stuck = ManagementFactory.getThreadMXBean().findDeadlockedThreads();
        if (stuck != null) {
            System.out.println("DEADLOCK: " + stuck.length + " threads; t1=" + t1.getState() + ", t2=" + t2.getState());
            System.exit(1);   // the stuck threads are not daemons, so we must force the exit
        }
        System.out.println("done: a=" + a.balance + ", b=" + b.balance + " (total stays 200)");
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}
```

What you should observe:

1. With `ORDERED = false`, it prints `DEADLOCK: 2 threads; t1=BLOCKED, t2=BLOCKED`. **Before the program exits**, run `jstack <pid>` in another terminal (`jps` lists the pid) and find the `Found one Java-level deadlock` section. To give yourself time, change `join(...)` to plain `join()` so the program hangs.
2. Set `ORDERED = true`. It prints `done: a=110, b=90`. Both threads lock account 1 first, so no cycle can form.
3. Fix the B1 race: wrap `count++` in `synchronized (ThreadBasics.class) { ... }` and confirm the count is now always exact.

## Gotchas

- **`unlock()` outside `finally`.** A single exception leaves the lock held forever. Always use `lock(); try { ... } finally { unlock(); }`.
- **Unsynchronized reads.** A reader without the lock may see a stale value. Reads and writes must use the *same* lock.
- **Locking on the wrong object.** Examples include `synchronized` on a field that gets reassigned, on a boxed `Integer`, or on a string literal, which is shared JVM-wide. Lock on a `private final Object`.
- **Calling unknown code while holding a lock.** Callbacks, listeners and remote calls can take other locks or block, which invites deadlock and long hold times. Copy what you need, release the lock, then call out.
- **Inconsistent lock order.** Any two code paths that take the same two locks in different orders can deadlock. Pick one global order.
- **A thread blocked on `synchronized` ignores `interrupt()`.** Use `lockInterruptibly()` or `tryLock(timeout)` when a waiter must be cancellable.

Typical follow-ups:

- **"`synchronized` vs `ReentrantLock`?"** A strong answer covers the feature table (timeout, interruptible, fairness, conditions, manual unlock), says that both are reentrant and give the same visibility guarantee, and states the default: `synchronized` unless you need one of those features.
- **"Your service hangs with zero CPU. What do you do?"** Take two or three thread dumps a few seconds apart, look for `Found one Java-level deadlock` or for threads BLOCKED on the same lock, find the cycle, fix it with lock ordering, and add a `tryLock` timeout as a safety net.

## Explain it in 2 minutes

*"How do locks make `count++` safe, and how can they hang a system?"*

- `count++` is read-add-write. A lock makes the sequence atomic with respect to other users of the same lock.
- Unlocking happens-before the next lock of the same monitor, which gives visibility. That means readers need the lock too.
- Locks are reentrant: the owner can re-acquire, and a hold count tracks it.
- `ReentrantLock` adds `tryLock` with timeout, interruptible waiting, fairness and conditions. It must be unlocked in `finally`.
- Deadlock needs mutual exclusion, hold-and-wait, no preemption and circular wait. Break circular wait with a global lock order.
- To diagnose, take a thread dump; the JVM reports Java-level deadlock cycles itself.
