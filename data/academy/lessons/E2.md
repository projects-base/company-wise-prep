## Where we are

In E1 you refactored a god class into small classes behind interfaces, so that `OrderService`
depends on `DiscountPolicy` and `OrderStore` rather than on concrete classes. That raises a new
question: if business code no longer calls `new GoldDiscount()`, *who does*? Creational patterns
answer it. They are the standard ways to create objects without spreading `new` everywhere.

A **design pattern** is a named, reusable solution to a problem that keeps coming up. The 23
classic ones come from the 1994 "Gang of Four" (GoF) book. The names matter mostly because they
let you say "a Strategy chosen by a Factory" in an interview and be understood in five words.

## The problem

After E1, the choice of discount still has to happen somewhere:

```java
DiscountPolicy policy;
if (customer.tier() == Tier.GOLD) policy = new GoldDiscount();
else if (customer.tier() == Tier.SILVER) policy = new SilverDiscount();
else policy = new NoDiscount();
```

If this block is copied into checkout, invoicing and refunds, every new tier means three edits.
Some objects are also hard to build correctly: an HTTP request has a URL, a method, ten optional
headers and a timeout, and a constructor with 14 parameters is unreadable. And some objects (a
connection pool, a configuration) should exist only once. Those are the three problems this
lesson covers.

## Factory: put the choice in one place

**Problem.** Deciding which implementation to create is logic. If it is copied around, it breaks
OCP in every copy.

**Minimal example.** A *simple factory* is one class (or static method) that owns the decision.

```java
final class DiscountFactory {
    private static final Map<Tier, DiscountPolicy> BY_TIER = Map.of(
            Tier.GOLD, new GoldDiscount(),
            Tier.SILVER, new SilverDiscount());

    static DiscountPolicy forTier(Tier tier) {
        return BY_TIER.getOrDefault(tier, new NoDiscount());
    }
}
```

The callers now say `DiscountFactory.forTier(c.tier())`. A new tier means one new class and one
new map entry, both in one place. Using a map instead of an `if` chain keeps the factory itself
short. Because these policies hold no state, the same instance can be shared.

**Factory Method** (the GoF version) goes one step further: a base class declares an abstract
"create" method and lets subclasses decide what to create.

```java
abstract class ReportExporter {
    abstract Formatter createFormatter();          // the factory method
    String export(List<String> rows) {
        Formatter f = createFormatter();
        return f.format(rows);
    }
}
class CsvExporter  extends ReportExporter { Formatter createFormatter() { return new CsvFormatter(); } }
class JsonExporter extends ReportExporter { Formatter createFormatter() { return new JsonFormatter(); } }
```

**The rule:** callers ask for "a thing that does X" and the factory decides which class. Callers
depend only on the interface.

**Where the JDK and Spring use it:**

- `List.of(...)`, `Map.of(...)`, `Optional.of(...)`, `Path.of(...)`: *static factory methods*.
  You get back an implementation class you never name.
- `EnumSet.noneOf(type)` returns one of two hidden implementations, a compact one for small enums
  and a larger one for big enums. Callers never know which.
- `Collection.iterator()` is a textbook Factory Method: each collection creates its own iterator.
- Spring's `BeanFactory` (and `ApplicationContext` on top of it) is a factory for every bean. A
  class that implements `FactoryBean<T>` tells Spring "call me to build the T".

## Builder: build complex objects readably

**Problem.** An object with many fields, most optional, leads to *telescoping constructors*
(`new Request(url)`, `new Request(url, method)`, `new Request(url, method, timeout)`, ...) or to
a 10-argument constructor where `null, null, 30, true` means nothing to the reader. Setters
make the object mutable and possibly half-built.

**Minimal example.**

```java
import java.time.Duration;
import java.util.*;

public final class HttpCall {
    private final String url;
    private final String method;
    private final Map<String, String> headers;
    private final Duration timeout;

    private HttpCall(Builder b) {
        this.url = b.url;
        this.method = b.method;
        this.headers = Map.copyOf(b.headers);
        this.timeout = b.timeout;
    }

    public static Builder newBuilder(String url) { return new Builder(url); }

    public static final class Builder {
        private final String url;                     // required: in the constructor
        private String method = "GET";                // optional: with defaults
        private final Map<String, String> headers = new HashMap<>();
        private Duration timeout = Duration.ofSeconds(10);

        private Builder(String url) { this.url = Objects.requireNonNull(url); }

        public Builder method(String m)              { this.method = m; return this; }
        public Builder header(String k, String v)    { headers.put(k, v); return this; }
        public Builder timeout(Duration t)           { this.timeout = t; return this; }

        public HttpCall build() {                     // validate once, at the end
            if (timeout.isNegative() || timeout.isZero()) throw new IllegalArgumentException("timeout must be positive");
            return new HttpCall(this);
        }
    }
}

// HttpCall call = HttpCall.newBuilder("https://api.example.com/orders")
//         .method("POST").header("Idempotency-Key", "abc").timeout(Duration.ofSeconds(3)).build();
```

Required fields go in the builder's constructor, optional fields get named methods with
defaults, and `build()` validates everything and returns an **immutable** object (one whose
fields can't change after construction).

**The rule:** use a Builder when there are about four or more parameters, several of them
optional, or when the object must be valid and immutable once built. For two or three
parameters, a constructor or a `record` is simpler.

**Where the JDK and Spring use it:**

- `java.net.http.HttpClient.newBuilder()` and `HttpRequest.newBuilder()`: almost exactly the
  example above.
- `StringBuilder`: builds a `String` (which is immutable) step by step. It is usually given as
  the everyday example, though it is a looser fit than the GoF form.
- `Stream.builder()`, `Locale.Builder`.
- Spring: `UriComponentsBuilder`, `ResponseEntity.ok().header(...).body(...)`,
  `WebClient.builder()`, `RestClient.builder()`, and Spring Security's `HttpSecurity` DSL.
- Lombok's `@Builder` generates this boilerplate for you.

## Singleton: exactly one instance

**Problem.** Some things should exist once per application, such as a connection pool or a
metrics registry. Two pools would double the connections to the database.

**Minimal example: the safe ways in Java.**

```java
// 1. Eager: created when the class is first used. Thread-safe because the JVM
//    guarantees class initialisation happens once.
final class Metrics {
    private static final Metrics INSTANCE = new Metrics();
    private Metrics() { }
    static Metrics get() { return INSTANCE; }
}

// 2. Lazy holder: created on the first call to get(). Same JVM guarantee, no locks.
final class Registry {
    private Registry() { }
    private static final class Holder { static final Registry INSTANCE = new Registry(); }
    static Registry get() { return Holder.INSTANCE; }
}

// 3. Enum: also safe against serialization and reflection tricks.
enum IdGenerator {
    INSTANCE;
    private final java.util.concurrent.atomic.AtomicLong next = new java.util.concurrent.atomic.AtomicLong();
    long nextId() { return next.incrementAndGet(); }
}
```

**The pitfalls (this is what interviewers actually probe):**

1. **The naive lazy version is not thread-safe.** `if (instance == null) instance = new X();`
   lets two threads both see `null` and both create one. You will break it in the lab.
2. **Double-checked locking needs `volatile`.** Without it, another thread can see a non-null
   reference to an object whose constructor hasn't finished, because the JVM may reorder the
   writes. With `volatile` it is correct, but the holder idiom is simpler.
3. **Global state hurts testing.** `Metrics.get()` called deep inside a method is a hidden
   dependency (the DIP problem from E1). You can't swap in a fake, and tests leak state into
   each other.
4. **"One" is per class loader, not per machine or cluster.** Two class loaders (for example two
   web apps in one server) give two instances, and three pods give three.
5. **A singleton with mutable state is shared by every thread.** Its fields need to be thread-safe.

**Where the JDK and Spring use it:**

- `Runtime.getRuntime()` is a classic JDK singleton. `Collections.emptyList()` returns one shared
  immutable instance.
- **Spring beans are singletons by default**, but in a different sense: one instance *per
  application context*, created and injected by the container. The class itself is an ordinary
  class with a public constructor. This gives you "only one" without the testing pain, because
  tests can construct their own instance. This is the modern answer: **let the container
  manage the single instance and inject it**, and avoid static `getInstance()`.
- The consequence of pitfall 5 is the most common Spring bug in this area: a singleton
  `@Service` with a mutable field (for example a `SimpleDateFormat` or a `HashMap` cache) is
  shared by all request threads.

## The rest of the creational family

| Pattern | Problem it solves | Where you see it |
|---|---|---|
| Abstract Factory | Create *families* of related objects that must match (for example a Windows button with a Windows checkbox) | `DocumentBuilderFactory`, `XPathFactory`; JDBC's `Connection` creating matching `Statement`s |
| Prototype | Create new objects by copying a configured one, when building from scratch is costly | `Object.clone()` (widely considered awkward; prefer copy constructors), Spring's `prototype` bean scope (a new instance per request, a related but different idea) |

## Lab (~10 min)

Save as `SingletonLab.java` and run `java SingletonLab.java`.

```java
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class SingletonLab {
    public static void main(String[] args) throws Exception {
        try (var pool = Executors.newFixedThreadPool(10)) {
            var start = new CountDownLatch(1);
            for (int i = 0; i < 10; i++) {
                pool.submit(() -> { start.await(); NaiveConfig.get(); return null; });
            }
            start.countDown();
        }
        System.out.println("NaiveConfig instances created: " + NaiveConfig.CREATED.get());
    }
}

class NaiveConfig {
    static final AtomicInteger CREATED = new AtomicInteger();
    private static NaiveConfig instance;

    private NaiveConfig() {
        CREATED.incrementAndGet();
        try { Thread.sleep(50); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }

    static NaiveConfig get() {
        if (instance == null) instance = new NaiveConfig();   // the race
        return instance;
    }
}
```

1. Run it. You should usually see more than 1 instance created. The `sleep` only widens a window
   that always exists.
2. Fix it with the lazy holder idiom. Run again: exactly 1.
3. Builder exercise: write a `RetryConfig` with `maxAttempts` (required), `baseDelay` (default
   100 ms) and `maxDelay` (default 5 s). `build()` must reject `maxAttempts < 1` and
   `baseDelay > maxDelay`. Write a `main` that shows one valid build and one rejected one.

## Gotchas

- **Don't reach for `getInstance()` in Spring code.** Make it a bean and inject it. You keep the
  single instance and get testability back.
- **Lazy singleton without `volatile` or the holder idiom is a race.** Default to eager or the
  holder idiom, and use `enum` if serialization matters.
- **Builders without validation in `build()` just move the bug.** Validate once at the end, and
  return an immutable object.
- **A factory full of `if/else` still breaks OCP inside the factory.** Use a
  `Map<Key, Supplier<T>>`, or, in Spring, inject `List<Strategy>` and index it by a `key()` method.
- **Spring singleton beans must be stateless or thread-safe.** Mutable fields in a `@Service` are
  shared across all requests.

## In interviews

In LLD rounds, creational patterns show up as supporting players rather than as the question:

- A factory that picks the vehicle type, spot type or pricing strategy in
  [Design a (Multi-level) Parking Lot](#/q/design-parking-lot).
- A builder for a configurable object, for example the limits in
  [Design a Rate Limiter](#/q/design-rate-limiter) or the cache in
  [Cache Service with Pluggable Eviction](#/q/design-cache-pluggable-eviction).
- "Make the logger a singleton" in
  [Design a Multi-module Logging Framework](#/q/design-logging-framework). A strong answer gives
  the thread-safe idiom *and* says that in a Spring app you would make it a bean instead.

Typical follow-ups:

- *"Is your singleton thread-safe?"* Name the race in the naive version, then give the holder or
  enum idiom and explain why it is safe (the JVM initialises a class exactly once).
- *"Why not a constructor?"* Count the parameters, point out which are optional, and say that the
  built object is immutable and validated.

## Explain it in 2 minutes

Prompt: *"When do you use a Factory, a Builder and a Singleton, and what goes wrong with
Singleton?"*

- Factory: puts "which class?" in one place, so callers depend on the interface (OCP and DIP).
  JDK: `List.of`, `EnumSet`; Spring: `BeanFactory`.
- Builder: many optional parameters, readable call sites, validation in `build()`, immutable
  result. JDK: `HttpClient.newBuilder()`; Spring: `UriComponentsBuilder`.
- Singleton: one instance. Safe idioms: eager, holder, enum.
- Pitfalls: naive lazy init races; double-checked locking needs `volatile`; global state hurts
  testing; "one" is per class loader.
- In Spring, prefer singleton-scoped beans that are injected, and keep them stateless.

## Check yourself

1. Why is `if (instance == null) instance = new X();` unsafe with two threads?
2. Why does the holder idiom need no lock?
3. You have a class with 2 required and 6 optional fields. Constructor, setters or Builder? Why?
4. How is a Spring singleton bean different from a GoF Singleton?
5. Name one JDK static factory method and say what it hides from you.

### Answers

1. Both threads can read `null` before either assigns, so both construct an instance.
2. The JVM initialises the `Holder` class once, on first use, and that initialisation is
   guaranteed to be thread-safe and visible to all threads.
3. A Builder: required fields in the builder's constructor, optional ones as named methods with
   defaults, and a validated, immutable object at the end. Setters would leave it mutable and
   possibly half-built.
4. A Spring bean is one instance per application context, created and injected by the container,
   and the class has an ordinary constructor, so tests can make their own. A GoF Singleton
   enforces one instance itself through a private constructor and a static accessor.
5. For example `List.of(...)`: it hides which immutable list class you get (the JDK picks
   different internal classes for different sizes).
