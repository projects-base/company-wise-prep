## Where we are

From G1 you know that a model hallucinates when it has to recall facts it doesn't have, and that the context window is how you give it facts. From G2 you know how to call a model, constrain its output and log what it costs. This lesson combines the two: find the right facts automatically, put them in the context, and have the model answer from them. That is **RAG**.

## The problem

This app's question bank has a few hundred questions, each a Markdown file with notes and sightings. You want a feature: *"Ask the bank: what have Microsoft interviewers asked about caching?"*

- Asking the model directly fails: it has never seen your bank, so it will make up plausible questions (G1).
- Pasting the whole bank into every prompt is too slow and too expensive per call, and it gets worse as the bank grows. Burying the relevant three questions among hundreds can also make answers worse.

What you need is to pick out the handful of passages that matter for *this* question and send only those.

## RAG in one picture

**Retrieval-augmented generation (RAG)** means: retrieve relevant text from your own data, put it into the prompt, and have the model generate an answer grounded in that text.

```text
  OFFLINE (indexing)                          ONLINE (per question)
  ───────────────────                         ─────────────────────
  documents                                   user question
     │ split                                      │ embed
     ▼                                            ▼
  chunks ──embed──► vectors ──► [vector DB] ◄── search (top-k)
                                                  │ (optional) rerank
                                                  ▼
                                   prompt = instructions + top chunks + question
                                                  │
                                                  ▼
                                            LLM answer (with citations)
```

Each box below is one idea. We start with the strangest one: embeddings.

## Embeddings: meaning as a point in space

An **embedding** is a list of numbers (a **vector**, typically several hundred to a few thousand numbers long) that an **embedding model** produces for a piece of text. Texts with similar *meaning* get vectors that point in similar directions.

```text
"LRU cache eviction"            → [0.12, -0.40, 0.88, ...]
"least-recently-used caching"   → [0.10, -0.38, 0.91, ...]   ← close
"TCP congestion control"        → [-0.70, 0.22, 0.05, ...]   ← far
```

Analogy: a map where each sentence is a pin, and sentences about the same thing land in the same neighbourhood even when they share no words. Where it breaks: a real map has 2 dimensions, while embeddings have hundreds, and "neighbourhood" is measured by angle (**cosine similarity**, 1.0 means the same direction) rather than by kilometres.

Notes:

- The embedding model is a separate, smaller model from the chat model. You can use any provider's embedding model or an open-source one run locally. Anthropic doesn't offer one of its own.
- The question and the documents **must be embedded with the same model**. Vectors from different models aren't comparable.

## Chunking: what unit do you retrieve?

You don't embed a whole 20-page document as one vector. A single vector can't represent twenty topics, and you want to send only the relevant part. **Chunking** splits documents into retrievable pieces.

```text
question file "lru-cache.md"
 ├─ chunk 1: title + problem statement
 ├─ chunk 2: approach (HashMap + doubly linked list)
 └─ chunk 3: company sightings and follow-ups
```

Rules of thumb:

- **Split on structure first** (headings, sections, functions), size second. A chunk should make sense when read on its own.
- **Prepend context** to each chunk: the document title, section name and company. "It uses a linked list" is useless without knowing what "it" is.
- **Use a little overlap** between size-based chunks so a sentence isn't cut in half at the boundary.
- **Store metadata** with each chunk (slug, type, companies) so you can filter and cite.

There is no universally right chunk size. Try a couple of sizes and measure (see Evaluation below).

## Vector search with pgvector

A **vector store** holds the vectors and finds the ones nearest to a query vector. This app already runs Postgres, and **pgvector** is a Postgres extension that adds a vector column type and nearest-neighbour search. One less system to run.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunk (
  id         bigserial PRIMARY KEY,
  slug       text NOT NULL,
  companies  text[] NOT NULL,
  content    text NOT NULL,
  embedding  vector(1024) NOT NULL        -- dimension must match your embedding model
);

-- Approximate nearest-neighbour index for cosine distance
CREATE INDEX ON chunk USING hnsw (embedding vector_cosine_ops);

-- Top 5 chunks closest to the query vector, filtered to Microsoft
SELECT slug, content
FROM chunk
WHERE 'microsoft' = ANY(companies)
ORDER BY embedding <=> :queryVector       -- <=> is cosine distance (smaller = closer)
LIMIT 5;
```

**HNSW** is an *approximate* nearest-neighbour index: it trades a little accuracy for a lot of speed, the same kind of trade a B-tree doesn't have to make. At a few thousand chunks you could scan every row exactly. The index matters at larger scale.

## Hybrid search: vectors miss exact words

Try the query *"LFU"*. Vector search may return LRU chunks, because the meanings are close, and miss the one chunk that literally says "LFU". Embeddings are good at meaning and bad at exact tokens: ids, error codes, acronyms, names.

**Keyword search** finds documents containing the query's words. **BM25** is the standard keyword-scoring formula: it rewards documents that contain rare query words and adjusts for document length. Postgres full-text search (`tsvector`, `ts_rank`) is a close relative of BM25, not an exact implementation, and it is good enough to start with.

**Hybrid search** runs both and merges the results. A simple, robust way to merge is **Reciprocal Rank Fusion (RRF)**: score each document by `sum(1 / (k + rank))` across the result lists, with `k` around 60. It uses only ranks, so you don't have to make the two kinds of score comparable.

```text
vector:  [lru-cache, lfu-cache, design-distributed-cache]
keyword: [lfu-cache, design-cache-pluggable-eviction]
RRF:     lfu-cache (in both lists) rises to the top
```

## Reranking: a second, smarter pass

Embedding search is fast because the query and each document are embedded *separately*. That speed costs precision. A **reranker** (a **cross-encoder**) reads the query and a candidate *together* and scores how relevant the candidate is. It is much more accurate and far too slow to run over everything.

The pattern: retrieve broadly (say the top 50 from hybrid search), rerank, keep the best 5 for the prompt. A cheap LLM call with a strict scoring schema (G2) can act as a reranker too.

## Generation: answer only from the context

The final prompt must make grounding explicit:

```text
Answer using ONLY the passages below. Cite the slug for each claim.
If the passages don't contain the answer, say "Not in the bank."
<passage slug="lru-cache">...</passage>
<passage slug="llm-cost-caching-and-observability">...</passage>
Question: What have Microsoft interviewers asked about caching?
```

Citations let users check the answer, and "say you don't know" gives the model a valid alternative to inventing one.

## Evaluation: measure retrieval and answers separately

When a RAG answer is wrong, either **retrieval** didn't find the right chunk, or **generation** had it and still got the answer wrong. Measure each separately:

- **Retrieval:** build 20–50 questions, each with the chunk ids that *should* come back. Measure **recall@k**: the fraction of questions where a right chunk appears in the top k.
- **Generation:** given the right chunks, is the answer correct, and is every claim supported by a cited chunk (**faithfulness**)? G6 covers grading this at scale.

Change one thing at a time (chunk size, hybrid on or off, reranker on or off) and re-run the set.

## When RAG is the wrong answer

- **The data fits in the context and changes rarely.** Just include all of it and use prompt caching (G2). Simpler, and often better.
- **The question is structured.** "How many Microsoft LLD questions are there?" is a SQL `COUNT`, not a similarity search. Give the model a query tool instead (G2, G4).
- **The task needs the whole corpus at once.** "Summarise every trend across all questions" needs aggregation or map-reduce, not top-5 retrieval.
- **You need the model to behave differently**, not to know more. That is prompting, or eventually fine-tuning, not retrieval.

## Lab (~10 min)

Build hybrid retrieval in plain Java with toy 3-dimensional "embeddings", so you can see RRF rescue an exact-keyword match. No API is needed.

```java
import java.util.*;
import java.util.stream.*;

public class HybridLab {
    record Chunk(String slug, String text, double[] vec) {}

    static double cosine(double[] a, double[] b) {
        double dot = 0, na = 0, nb = 0;
        for (int i = 0; i < a.length; i++) { dot += a[i] * b[i]; na += a[i] * a[i]; nb += b[i] * b[i]; }
        return dot / (Math.sqrt(na) * Math.sqrt(nb));
    }

    static List<String> vectorSearch(List<Chunk> chunks, double[] q) {
        return chunks.stream()
            .sorted(Comparator.comparingDouble((Chunk c) -> cosine(c.vec(), q)).reversed())
            .map(Chunk::slug).toList();
    }

    static List<String> keywordSearch(List<Chunk> chunks, String term) {
        return chunks.stream()
            .filter(c -> c.text().toLowerCase().contains(term.toLowerCase()))
            .map(Chunk::slug).toList();
    }

    static List<String> rrf(List<List<String>> rankings, int k) {
        Map<String, Double> score = new HashMap<>();
        for (List<String> ranking : rankings)
            for (int i = 0; i < ranking.size(); i++)
                score.merge(ranking.get(i), 1.0 / (k + i + 1), Double::sum);
        return score.entrySet().stream()
            .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
            .map(Map.Entry::getKey).collect(Collectors.toList());
    }

    public static void main(String[] args) {
        // dims ~ [caching, eviction-by-recency, networking]
        List<Chunk> chunks = List.of(
            new Chunk("lru-cache", "LRU cache: evict least recently used", new double[] {0.9, 0.9, 0.0}),
            new Chunk("lfu-cache", "LFU cache: evict least frequently used", new double[] {0.9, 0.3, 0.0}),
            new Chunk("design-distributed-cache", "Distributed cache design", new double[] {0.8, 0.2, 0.3}),
            new Chunk("tcp-vs-udp", "TCP vs UDP", new double[] {0.0, 0.0, 1.0}));

        double[] queryVec = {0.9, 0.8, 0.0};   // pretend embedding of "LFU eviction" (embedder confused it with LRU)
        List<String> vec = vectorSearch(chunks, queryVec);
        List<String> kw = keywordSearch(chunks, "LFU");
        System.out.println("vector : " + vec);
        System.out.println("keyword: " + kw);
        System.out.println("hybrid : " + rrf(List.of(vec, kw), 60));
    }
}
```

What to observe: vector search ranks `lru-cache` first, keyword search finds only `lfu-cache`, and the hybrid list puts `lfu-cache` first because it scores in both lists.

**Break it:** search for the keyword "cache" instead. Every caching chunk matches, keyword search adds no signal, and hybrid falls back to roughly the vector order. Keyword search only helps when the term is *distinctive*. That is BM25's rare-word intuition.

## Gotchas

- **Mixing embedding models** (or re-embedding only some documents after switching models) silently breaks search. Store the model name with each vector and re-embed everything when it changes.
- **Chunks without context** ("It then retries…") retrieve badly and confuse the model. Prepend the title and section.
- **Vector-only search for ids, acronyms and error codes.** Add keyword search (hybrid) for exact matches.
- **Judging RAG only by final answers.** Measure retrieval recall separately, or you can't tell which half failed.
- **Retrieved text is untrusted input.** A chunk can contain "ignore your instructions…". Treat it as data (G6).
- **Using RAG for counting and filtering questions.** Those belong in SQL behind a tool.

## In interviews

RAG rarely appears as a standalone question in the bank. It shows up inside AI system design and as a follow-up on cost.

- [Design an Agentic Workflow](#/q/design-agentic-workflow): retrieval is usually one of the agent's tools. Explain how documents are indexed and kept fresh.
- [Caching to reduce LLM cost; LLM observability](#/q/llm-cost-caching-and-observability): cache embeddings (never re-embed unchanged text), cache the stable prompt prefix, and log retrieval hits alongside model usage.
- [Local Search with Ranking](#/q/design-local-search-with-ranking) is a good place to bring up hybrid ranking ideas.

Typical follow-ups:

- *"Answers are wrong. How do you debug it?"* Check retrieval first (was the right chunk in the top k?), then faithfulness. Have an eval set for both.
- *"How do you keep the index fresh?"* Re-index on document change events, run idempotent upserts by chunk id, store a content hash to skip unchanged chunks, and plan a full re-embed when the model changes.

## Explain it in 2 minutes

*"Explain RAG and how you'd build it on Postgres."*

1. The model doesn't know your data, and the whole corpus doesn't fit cheaply in the context, so retrieve only what's relevant.
2. Chunk the documents by structure, with context prepended, then embed the chunks with one embedding model.
3. Store the vectors in pgvector with an HNSW index and filter by metadata.
4. Use hybrid search (vector plus keyword, merged with RRF), then rerank the top candidates.
5. Prompt the model to answer only from the passages, with citations and "not found" as an allowed answer.
6. Evaluate retrieval recall and answer faithfulness separately. Skip RAG when the data is small, the question is structured, or the task needs the whole corpus.

## Check yourself

1. Why must the query and the documents use the same embedding model?
2. What is a typical weakness of pure vector search, and what fixes it?
3. What does a reranker do that the first retrieval stage doesn't?
4. Answers are wrong. How do you tell whether retrieval or generation is at fault?
5. Give two situations where RAG is the wrong tool.

### Answers

1. Each model has its own vector space. Similarity is only meaningful between vectors from the same model.
2. Exact tokens (ids, acronyms, names) get blurred into similar meanings. Hybrid search with BM25 or keyword search fixes it.
3. It reads the query and the document together, so it judges relevance much more accurately. It is too slow for the whole corpus, so it runs only on the top candidates.
4. Measure retrieval recall@k on a labelled set. If the right chunk was retrieved and the answer is still wrong or unsupported, the problem is generation.
5. Small, stable data (put it all in the context and cache it). Structured or aggregate questions (use SQL behind a tool). Also whole-corpus summarisation.
