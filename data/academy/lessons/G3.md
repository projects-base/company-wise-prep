## Where we are

What you already know:

- **AI-ENG-1:** a model hallucinates when it has to recall facts it doesn't have, and the context window is how you give it facts.
- **AI-ENG-2:** how to call a model, constrain its output and log what it costs.

This lesson combines the two: find the right facts automatically, put them in the context, and have the model answer from them. That is **RAG**.

## The problem

This app's question bank has a few hundred questions, each a Markdown file with notes and sightings. You want a feature: *"Ask the bank: what have Microsoft interviewers asked about caching?"*

- Asking the model directly fails: it has never seen your bank, so it will make up plausible questions (AI-ENG-1).
- Pasting the whole bank into every prompt is too slow and too expensive per call, and it gets worse as the bank grows. Burying the relevant three questions among hundreds can also make answers worse.

What you need is to pick out the handful of passages that matter for *this* question and send only those.

## RAG in one picture

**Retrieval-augmented generation (RAG)** means: retrieve relevant text from your own data, put it into the prompt, and have the model generate an answer grounded in that text.

```text
  OFFLINE (indexing)                          ONLINE (per question)
  ───────────────────                         ─────────────────────
  documents                                   user question
     │ split                                      │ embed
     ▼                                            ▼
  chunks ──embed──► vectors ──► [vector DB] ◄── search (top-k)
                                                  │ (optional) rerank
                                                  ▼
                                   prompt = instructions + top chunks + question
                                                  │
                                                  ▼
                                            LLM answer (with citations)
```

Each box below is one idea. We start with the strangest one: embeddings.

## Embeddings: meaning as a point in space

An **embedding** is a list of numbers (a **vector**, typically several hundred to a few thousand numbers long) that an **embedding model** produces for a piece of text. Texts with similar *meaning* get vectors that point in similar directions.

```text
"LRU cache eviction"            → [0.12, -0.40, 0.88, ...]
"least-recently-used caching"   → [0.10, -0.38, 0.91, ...]   ← close
"TCP congestion control"        → [-0.70, 0.22, 0.05, ...]   ← far
```

Analogy: a map where each sentence is a pin, and sentences about the same thing land in the same neighbourhood even when they share no words.

Where it breaks:

- a real map has 2 dimensions, while embeddings have hundreds;
- "neighbourhood" is measured by angle (**cosine similarity**, 1.0 means the same direction) rather than by kilometres.

Notes:

- The embedding model is a separate, smaller model from the chat model. You can use any provider's embedding model or an open-source one run locally. Anthropic doesn't offer one of its own.
- The question and the documents **must be embedded with the same model**. Vectors from different models aren't comparable.

## Chunking: what unit do you retrieve?

You don't embed a whole 20-page document as one vector. A single vector can't represent twenty topics, and you want to send only the relevant part.

**Chunking** splits documents into retrievable pieces.

```text
question file "lru-cache.md"
 ├─ chunk 1: title + problem statement
 ├─ chunk 2: approach (HashMap + doubly linked list)
 └─ chunk 3: company sightings and follow-ups
```

Rules of thumb:

- **Split on structure first** (headings, sections, functions), size second. A chunk should make sense when read on its own.
- **Prepend context** to each chunk: the document title, section name and company. "It uses a linked list" is useless without knowing what "it" is.
- **Use a little overlap** between size-based chunks so a sentence isn't cut in half at the boundary.
- **Store metadata** with each chunk (slug, type, companies) so you can filter and cite.

There is no universally right chunk size. Try a couple of sizes and measure (see Evaluation below).

## Vector search with pgvector

A **vector store** holds the vectors and finds the ones nearest to a query vector.

This app already runs Postgres, and **pgvector** is a Postgres extension that adds a vector column type and nearest-neighbour search. One less system to run.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunk (
  id         bigserial PRIMARY KEY,
  slug       text NOT NULL,
  companies  text[] NOT NULL,
  content    text NOT NULL,
  embedding  vector(1024) NOT NULL        -- dimension must match your embedding model
);

-- Approximate nearest-neighbour index for cosine distance
CREATE INDEX ON chunk USING hnsw (embedding vector_cosine_ops);

-- Top 5 chunks closest to the query vector, filtered to Microsoft
SELECT slug, content
FROM chunk
WHERE 'microsoft' = ANY(companies)
ORDER BY embedding <=> :queryVector       -- <=> is cosine distance (smaller = closer)
LIMIT 5;
```

**HNSW** is an *approximate* nearest-neighbour index: it trades a little accuracy for a lot of speed, the same kind of trade a B-tree doesn't have to make. At a few thousand chunks you could scan every row exactly. The index matters at larger scale.

## The vector store landscape

pgvector is one choice among three families. Interviewers ask "why not Pinecone?", so have the comparison ready.

| Way | How | When to choose | Pitfall |
|---|---|---|---|
| pgvector | A Postgres extension: a `vector` column next to your rows | You already run Postgres; you need SQL filters, joins and transactions; up to millions of vectors | Filters run *after* the approximate index scan, so a filtered query can return fewer than `LIMIT` rows (0.8.0+ adds iterative index scans to fix this) |
| Dedicated vector DB (Qdrant, Weaviate, Milvus; Pinecone as a managed service) | A separate database built around vector search | Vectors are the main workload, at a scale or with a tenancy model Postgres struggles with | A second system to keep in sync with the source of truth, including updates and deletes |
| Elasticsearch / OpenSearch | Vector (kNN) search next to BM25 full-text search in one engine | You already run it for search, and hybrid search is central | A heavy cluster to run if you don't already have one |

**HNSW vs IVFFlat**, the two pgvector index types (from the pgvector README):

| | HNSW | IVFFlat |
|---|---|---|
| Speed vs recall | Better | Worse |
| Build time, memory | Slower, more | Faster, less |
| Build on an empty table? | Yes, no training step | Possible but useless: it learns its `lists` from the rows present, so build it after loading data |
| Tuning | `m` (16), `ef_construction` (64), query-time `hnsw.ef_search` (40) | `lists` (about rows/1000 up to 1M rows), query-time `ivfflat.probes` (default 1) |

Both index a `vector` of at most **2,000 dimensions**; `halfvec` (half precision) indexes up to 4,000.

**Picking an embedding model.** Measure recall@k on your own eval set (see Evaluation below); public leaderboards are only a shortlist. Then weigh: more **dimensions** mean more storage and memory and slower search, maximum input length (it limits chunk size), price per token, and where it runs (sensitive data may require a self-hosted model).

**Re-embedding when the model changes.** Vectors from two models aren't comparable, so a model change means re-embedding *everything*. Treat it like a schema migration:

```text
1. add column embedding_v2 vector(N) + embedding_model text      (new dims → new column)
2. backfill in batches, idempotent (skip rows already done); new writes fill both columns
3. build the index on embedding_v2; run the retrieval eval on old vs new
4. switch reads to v2 if recall@k holds; later drop the old column
```

The rule: start on pgvector if you are on Postgres, move only when measurement says so, and record which model made every vector.

## Hybrid search: vectors miss exact words

Try the query *"LFU"*. Vector search may return LRU chunks, because the meanings are close, and miss the one chunk that literally says "LFU".

Embeddings are good at meaning and bad at exact tokens:

- ids;
- error codes;
- acronyms;
- names.

**Keyword search** finds documents containing the query's words. **BM25** is the standard keyword-scoring formula: it rewards documents that contain rare query words and adjusts for document length. Postgres full-text search (`tsvector`, `ts_rank`) is a close relative of BM25, not an exact implementation, and it is good enough to start with.

**Hybrid search** runs both and merges the results. A simple, robust way to merge is **Reciprocal Rank Fusion (RRF)**: score each document by `sum(1 / (k + rank))` across the result lists, with `k` around 60. It uses only ranks, so you don't have to make the two kinds of score comparable.

```text
vector:  [lru-cache, lfu-cache, design-distributed-cache]
keyword: [lfu-cache, design-cache-pluggable-eviction]
RRF:     lfu-cache (in both lists) rises to the top
```

## Reranking: a second, smarter pass

Embedding search is fast because the query and each document are embedded *separately*. That speed costs precision.

A **reranker** (a **cross-encoder**) reads the query and a candidate *together* and scores how relevant the candidate is.

- **Good:** much more accurate.
- **Cost:** far too slow to run over everything.

The pattern: retrieve broadly (say the top 50 from hybrid search), rerank, keep the best 5 for the prompt. A cheap LLM call with a strict scoring schema (AI-ENG-2) can act as a reranker too.

## Query transformation: fix the question before searching

Users ask "and for Amazon?" or "LRU thing?". The words in the question are often a poor search key.

**Query transformation** spends one cheap LLM call to make a better one.

| Way | How | When to choose | Pitfall |
|---|---|---|---|
| Rewriting | An LLM turns the latest message plus the chat history into one standalone query, expanding acronyms | Chat interfaces with follow-up questions | It can drop a detail the user cared about; log the rewritten query |
| Multi-query | Generate 3–5 phrasings, search with each, merge with RRF | Vague questions, varied vocabulary in the documents | 3–5 times the searches; more noise if you don't rerank |
| HyDE | Ask the LLM to write a *hypothetical answer*, embed that and search with it | Short questions and long documents: an answer-shaped text lands closer to answer chunks | The made-up answer can steer retrieval towards the model's own mistakes; never show it to the user |

```text
user:   "and for Amazon?"            (history: "caching questions at Microsoft")
rewrite → "caching interview questions asked at Amazon"
```

The rule: add a transformation only when recall@k shows the gain, because each one costs an extra call of latency before retrieval starts.

## Generation: answer only from the context

The final prompt must make grounding explicit:

```text
Answer using ONLY the passages below. Cite the slug for each claim.
If the passages don't contain the answer, say "Not in the bank."
<passage slug="lru-cache">...</passage>
<passage slug="llm-cost-caching-and-observability">...</passage>
Question: What have Microsoft interviewers asked about caching?
```

Citations let users check the answer, and "say you don't know" gives the model a valid alternative to inventing one.

## Evaluation: measure retrieval and answers separately

When a RAG answer is wrong, either **retrieval** didn't find the right chunk, or **generation** had it and still got the answer wrong. Measure each separately:

- **Retrieval:** build 20–50 questions, each with the chunk ids that *should* come back. Measure **recall@k**: the fraction of questions where a right chunk appears in the top k.
- **Generation:** given the right chunks, is the answer correct, and is every claim supported by a cited chunk (**faithfulness**)? AI-ENG-6 covers grading this at scale.

Change one thing at a time (chunk size, hybrid on or off, reranker on or off) and re-run the set.

## When RAG is the wrong answer

- **The data fits in the context and changes rarely.** Just include all of it and use prompt caching (AI-ENG-2). Simpler, and often better.
- **The question is structured.** "How many Microsoft LLD questions are there?" is a SQL `COUNT`, not a similarity search. Give the model a query tool instead (AI-ENG-2, AI-ENG-4).
- **The task needs the whole corpus at once.** "Summarise every trend across all questions" needs aggregation or map-reduce, not top-5 retrieval.
- **You need the model to behave differently**, not to know more. That is prompting, or eventually fine-tuning, not retrieval.

## RAG vs fine-tuning vs long context

Three ways to get knowledge or behaviour into a model's answer. The first question is always: **does the model need to *know* more, or *behave* differently?**

| Way | How | Freshness | Cost and latency | Changes | Pitfall |
|---|---|---|---|---|---|
| RAG | Retrieve the top chunks per question and put them in the prompt | Fresh as soon as the index is updated | An index to run, plus a small prompt per call; retrieval adds a little latency | Knowledge | Wrong answers when retrieval misses the right chunk |
| Long context | Put the whole corpus in every prompt; prompt caching makes the repeats cheap | Fresh on every call | Simple to build; cost and latency grow with corpus size (current Claude models accept up to 1M tokens) | Knowledge | The relevant fact can be buried among hundreds of others, and every call pays for the whole corpus |
| Fine-tuning | Train the model further on example inputs and outputs | Stale from the day training ends; every change means retraining | A training run, data preparation and evals up front; not offered for every provider or model | Behaviour: format, tone, a narrow task | Facts learned this way are hard to update and still get hallucinated; no citations |

**Predict:** the policy documents change weekly, and the model must also answer in a strict house style. Which one, or which mix?

Both kinds of need, so a mix: RAG (or long context, if the documents are small) for the weekly facts, and prompting with examples for the style. Fine-tune for style only if prompting can't hold it, and never for the facts.

```text
need fresh facts, large corpus           → RAG
need fresh facts, small corpus           → long context + prompt caching
need a behaviour that prompting can't fix → fine-tuning (after prompt + examples failed on the eval)
need both                                → combine: fine-tuned or prompted behaviour + RAG facts
```

The rule: knowledge goes in the context (RAG or long context), behaviour goes in the prompt first and the weights last.

## Lab (~10 min)

Build hybrid retrieval in plain Java with toy 3-dimensional "embeddings", so you can see RRF rescue an exact-keyword match. No API is needed.

```java
import java.util.*;
import java.util.stream.*;

public class HybridLab {
    record Chunk(String slug, String text, double[] vec) {}

    static double cosine(double[] a, double[] b) {
        double dot = 0, na = 0, nb = 0;
        for (int i = 0; i < a.length; i++) { dot += a[i] * b[i]; na += a[i] * a[i]; nb += b[i] * b[i]; }
        return dot / (Math.sqrt(na) * Math.sqrt(nb));
    }

    static List<String> vectorSearch(List<Chunk> chunks, double[] q) {
        return chunks.stream()
            .sorted(Comparator.comparingDouble((Chunk c) -> cosine(c.vec(), q)).reversed())
            .map(Chunk::slug).toList();
    }

    static List<String> keywordSearch(List<Chunk> chunks, String term) {
        return chunks.stream()
            .filter(c -> c.text().toLowerCase().contains(term.toLowerCase()))
            .map(Chunk::slug).toList();
    }

    static List<String> rrf(List<List<String>> rankings, int k) {
        Map<String, Double> score = new HashMap<>();
        for (List<String> ranking : rankings)
            for (int i = 0; i < ranking.size(); i++)
                score.merge(ranking.get(i), 1.0 / (k + i + 1), Double::sum);
        return score.entrySet().stream()
            .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
            .map(Map.Entry::getKey).collect(Collectors.toList());
    }

    public static void main(String[] args) {
        // dims ~ [caching, eviction-by-recency, networking]
        List<Chunk> chunks = List.of(
            new Chunk("lru-cache", "LRU cache: evict least recently used", new double[] {0.9, 0.9, 0.0}),
            new Chunk("lfu-cache", "LFU cache: evict least frequently used", new double[] {0.9, 0.3, 0.0}),
            new Chunk("design-distributed-cache", "Distributed cache design", new double[] {0.8, 0.2, 0.3}),
            new Chunk("tcp-vs-udp", "TCP vs UDP", new double[] {0.0, 0.0, 1.0}));

        double[] queryVec = {0.9, 0.8, 0.0};   // pretend embedding of "LFU eviction" (embedder confused it with LRU)
        List<String> vec = vectorSearch(chunks, queryVec);
        List<String> kw = keywordSearch(chunks, "LFU");
        System.out.println("vector : " + vec);
        System.out.println("keyword: " + kw);
        System.out.println("hybrid : " + rrf(List.of(vec, kw), 60));
    }
}
```

What to observe: vector search ranks `lru-cache` first, keyword search finds only `lfu-cache`, and the hybrid list puts `lfu-cache` first because it scores in both lists.

**Break it:** search for the keyword "cache" instead. Every caching chunk matches, keyword search adds no signal, and hybrid falls back to roughly the vector order. Keyword search only helps when the term is *distinctive*. That is BM25's rare-word intuition.

## Gotchas

- **Mixing embedding models:** silently breaks search. Store the model name per vector; re-embed everything on a change.
- **Chunks without context** ("It then retries…"): prepend title and section.
- **Vector-only search for ids, acronyms, error codes:** add keyword search (hybrid).
- **Judging only final answers:** measure retrieval recall separately.
- **Trusting retrieved text:** a chunk can say "ignore your instructions". Treat it as data (AI-ENG-6).
- **RAG for counting or filtering:** use SQL behind a tool.

## Explain it in 2 minutes

*"Explain RAG and how you'd build it on Postgres."*

1. The model lacks your data and the corpus won't fit cheaply, so retrieve only what's relevant.
2. Chunk by structure with context prepended; embed with one model; store in pgvector with HNSW and metadata filters.
3. Hybrid search (vector + keyword, merged with RRF), then rerank the top candidates.
4. Answer only from the passages, with citations and "not found" allowed.
5. Evaluate retrieval and faithfulness separately; skip RAG for small data, structured or whole-corpus questions.
