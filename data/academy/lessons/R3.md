## Where we are

LLD-DESIGN-7 showed how bounded contexts and ports and adapters shape one service, and BE-STORY-10 showed what
microservices cost. This page zooms out: every architecture style a senior engineer is expected to name, what each
buys, what each costs, and how to choose between them.

## How to use this page

- **A design pattern shapes a few classes; an architecture style shapes the whole system**: how it is split, how the
  parts talk, how it is deployed and who owns what. REFERENCE-2 is the pattern catalog; this is the style catalog.
- **Each entry has the same shape:** what it is, a diagram where it helps, *Benefits*, *Costs*, *Fits when*,
  *Avoid when*, *Real-world flavour*, and *Depth* (the lesson that teaches it properly, if one exists).
- **Styles combine.** A real system is often "a modular monolith with hexagonal modules, event-driven integration with
  two extracted services, deployed multi-tenant in a pool model". Name each layer of that sentence.
- **Two terms used throughout.** *Coupling* is how much one part must know about, or change with, another.
  *Operational cost* is what it takes to deploy, monitor and debug the thing in production, in people as well as money.

## Monolith (layered / n-tier)

One deployable application, organised in horizontal layers where each layer only calls the one below. "N-tier" often
also means the layers run on separate machines (browser, app server, database).

```text
  [ Presentation  ]   controllers, JSON
         |
  [ Business      ]   services, rules
         |
  [ Persistence   ]   repositories
         |
  [ Database      ]
```

- *Benefits:* simplest to build, test, deploy and debug; one process, so calls are cheap and one database transaction
  covers everything; every developer already knows it.
- *Costs:* layers are horizontal, so one feature touches every layer; without discipline, everything calls everything
  (the "big ball of mud"); the whole app scales and deploys as one unit; dependencies point down toward the database,
  so the domain tends to depend on persistence details.
- *Fits when:* a new product, a small team, a simple domain, or anything whose scale fits on a few instances.
- *Avoid when:* many teams must release independently, or parts of the system have very different scaling needs.
- *Real-world flavour:* the default Spring Boot service: `controller`, `service`, `repository` packages over one
  database.
- *Depth:* BE-STORY-4, SPRING-BOOT-6.

## Modular monolith

One deployable, but split internally into **vertical modules by business capability**, each with a public API and
private internals. Modules talk through their APIs or in-process events, never by reaching into each other's tables
or classes.

```text
  +------------------- one deployable --------------------+
  |  [ Orders ]  --API/event-->  [ Payments ]  [ Catalog ] |
  |   own pkgs                    own pkgs      own pkgs   |
  |   own tables                  own tables    own tables |
  +--------------------------------------------------------+
```

- *Benefits:* most of the simplicity of a monolith (one deploy, in-process calls, local transactions where you allow
  them) with clear ownership; boundaries can be checked by tests; a well-bounded module can later be extracted into a
  service with little rework.
- *Costs:* boundaries erode without enforcement; still one deploy and one scaling unit; one bad module can crash the
  process; a shared database makes it tempting to cross boundaries with joins.
- *Fits when:* most teams most of the time. It is the usual recommended starting point for a growing product.
- *Avoid when:* parts genuinely need independent scaling, independent release by separate teams, or different
  technology stacks today, not hypothetically.
- *Real-world flavour:* Spring Modulith, which verifies module dependencies in a test and publishes events between
  modules. CompanyWisePrep itself is built this way.
- *Depth:* BE-STORY-12.

## Hexagonal (ports and adapters)

Named by Alistair Cockburn.

- The domain sits in the middle and defines **ports** (interfaces) for what it needs and offers.
- **adapters** on the outside implement them for HTTP, databases, queues and third-party APIs.
- Dependencies point inward, so the domain knows nothing about Spring, JPA or Kafka.

```text
   HTTP adapter --> [ in-port ]                    [ out-port ] <-- JPA adapter
                         \                          /
                          +----- domain core ------+
                         /                          \
  Kafka listener --> [ in-port ]                   [ out-port ] <-- payment client adapter
```

- *Benefits:* domain logic testable without a database or web server; swapping a vendor or database touches one
  adapter; forces you to state what the domain actually needs.
- *Costs:* more interfaces and mapping code (domain object to entity to DTO); overkill for thin CRUD services; easy to
  build "ports" that just mirror one implementation.
- *Fits when:* a service with real business rules, several integrations, or a likely change of infrastructure.
- *Avoid when:* the service is mostly CRUD or a thin proxy; the indirection costs more than it protects.
- *Real-world flavour:* a Spring Boot service with `domain`, `application` and `adapter` packages, with the
  ArchUnit-style rule "domain imports nothing from adapters".
- *Depth:* LLD-DESIGN-7.

## Clean and Onion architecture

Two close relatives of hexagonal:

- **Onion** (Jeffrey Palermo) draws concentric rings: domain model, domain services, application services, then
  infrastructure and UI on the outside.
- **Clean Architecture** (Robert C. Martin) draws entities, use cases, interface adapters and frameworks, with one
  rule: **source dependencies point only inward**.

```text
  +--------------------------------------------+
  | frameworks, DB, web, UI                    |
  |  +--------------------------------------+  |
  |  | interface adapters (controllers,     |  |
  |  | gateways, presenters)                |  |
  |  |  +--------------------------------+  |  |
  |  |  | use cases (application rules)  |  |  |
  |  |  |  +--------------------------+  |  |  |
  |  |  |  | entities (domain rules)  |  |  |  |
  |  |  |  +--------------------------+  |  |  |
  |  |  +--------------------------------+  |  |
  |  +--------------------------------------+  |
  +--------------------------------------------+
```

- *Benefits:* same as hexagonal, plus an explicit place for use cases (one class per application action), which
  keeps services from becoming god objects.
- *Costs:* even more layers and mappings; teams apply it ritually to services with no domain logic.
- *Fits when / Avoid when:* as for hexagonal. In interviews, the useful point is that all three share the
  dependency rule and differ mostly in how they draw and name the rings.
- *Depth:* LLD-DESIGN-7.

## Microkernel (plugin)

A small core provides the minimal runtime and an extension contract; features live in **plugins** that the core
discovers and loads.

```text
        [ plugin A ]   [ plugin B ]   [ plugin C ]
              \             |             /
               +---- extension points ---+
                            |
                    [  core system  ]
```

- *Benefits:* features added, removed or sold separately without touching the core; third parties can extend the
  product; the core stays small and stable.
- *Costs:* the plugin contract is a public API that is hard to change; plugin isolation, versioning and
  compatibility are real work; a bad plugin can still destabilise the host.
- *Fits when:* products with many optional features or third-party extensions: IDEs, build tools, CI servers,
  browsers, rules engines, insurance or tax products with per-region rules.
- *Avoid when:* the feature set is fixed and owned by one team; a plugin system is then speculative abstraction.
- *Real-world flavour:* IDE and CI-server plugin ecosystems; in Java, `ServiceLoader` and OSGi. Spring Boot
  auto-configuration has a similar shape: starters plug features into a core when they are on the classpath.
- *Depth:* SPRING-BOOT-12 (custom starters).

## SOA and the enterprise service bus

**Service-oriented architecture** splits an enterprise into services with formal contracts (historically SOAP and
WSDL). It was usually built around an **enterprise service bus (ESB)**: central middleware that routes, transforms
and orchestrates messages between services.

```text
  [ CRM ]   [ Billing ]   [ Inventory ]
     \           |             /
  ======== Enterprise Service Bus ========   routing, transformation, orchestration
     /           |             \
  [ ERP ]   [ Portal ]    [ Legacy mainframe ]
```

- *Benefits:* reuse of business services across an enterprise; integration of very different systems (including
  legacy) through one hub; formal, machine-readable contracts.
- *Costs:* the "smart pipe" bus accumulates business logic and becomes a bottleneck owned by one central team; heavy
  standards and tooling; changes need cross-team coordination.
- *Fits when:* integrating many existing, heterogeneous enterprise systems that you cannot rewrite.
- *Avoid when:* building new product services; microservices replaced the smart bus with "smart endpoints, dumb
  pipes".
- *Real-world flavour:* large enterprises integrating ERP, CRM and mainframe systems; integration frameworks such as
  Apache Camel and MuleSoft are the modern descendants.
- *Depth:* BE-STORY-9.

## Microservices

Many small services, each owning one business capability and **its own data**, deployed independently and talking
over the network (HTTP, gRPC, events).

```text
  client --> [ API gateway ] --> [ Orders ] --event--> [ Shipping ]
                         |          |  DB                 DB
                         +-----> [ Payments ]
                                    DB
```

- *Benefits:* independent deployment and scaling per service; teams own services end to end; fault isolation if
  resilience patterns are in place; freedom to choose technology per service.
- *Costs:* every call can fail or be slow; no cross-service transactions (sagas, outbox, eventual consistency);
  distributed tracing, service discovery, contract versioning and platform work; much harder local development and
  debugging. Done badly, it becomes a distributed monolith.
- *Fits when:* several teams that need to release independently, a domain with clear bounded contexts, real
  differences in scaling, and a platform (CI/CD, Kubernetes, observability) already in place.
- *Avoid when:* one small team, an unclear domain (boundaries will be wrong), or low ops maturity.
- *Real-world flavour:* large consumer platforms with hundreds of engineers; Spring Boot services on Kubernetes behind
  a gateway with Kafka between them.
- *Depth:* BE-STORY-10, WEB-API-5, DIST-SYS-3.

## Event-driven architecture

Components communicate by **publishing events** (facts: "OrderPlaced") to a broker; others subscribe and react. The
producer does not know who listens. Martin Fowler distinguishes several meanings; the two that matter most here:

- **Event notification:** the event is small ("order 42 placed"); consumers call back the producer for details.
  Very loose coupling of the message, but the callback re-couples them at runtime and adds load.
- **Event-carried state transfer:** the event carries the data consumers need (order lines, totals, address).
  Consumers keep their own local copy and never call back, so they work even if the producer is down. The cost is
  bigger events, duplicated data and eventual consistency.

```text
  [ Orders ] --OrderPlaced--> ( topic ) --> [ Shipping ]
                                       \--> [ Email ]
                                        \-> [ Analytics ]
```

- *Benefits:* add consumers without touching producers; temporal decoupling (a consumer can be down and catch up);
  natural fit for async workflows and fan-out; buffers traffic spikes.
- *Costs:* nobody sees the whole flow; debugging needs correlation ids and tracing; at-least-once delivery means
  idempotent consumers; ordering is limited (per partition in Kafka); event schemas become public contracts.
- *Fits when:* many reactions to the same business fact, integration between bounded contexts, spiky workloads.
- *Avoid when:* the caller needs an immediate answer (use a synchronous call), or the flow is a simple request and
  response between two components.
- *Real-world flavour:* order, payment and notification flows over Kafka; in-process, Spring application events
  between modules of a modular monolith.
- *Depth:* BE-STORY-11, DIST-SYS-2.

## CQRS + event sourcing

**CQRS** separates the write model (commands that enforce rules) from read models (queries shaped for screens).
**Event sourcing** stores the stream of events as the source of truth and derives state by replaying them. They are
separate ideas but often combined: the event stream feeds projections that build the read models.

```text
  command --> [ write model ] --append--> [ event store ] --project--> [ read model(s) ] <-- query
```

- *Benefits:* reads and writes optimised and scaled separately; full audit history; new read models built by
  replaying history; temporal questions ("what was the balance on 1 March?") become natural.
- *Costs:* read models are eventually consistent; event schemas live forever and must be versioned; replays need
  snapshots; much more machinery than CRUD; hard to retrofit and hard to remove.
- *Fits when:* audit-critical domains (ledgers, bookings, betting), complex domains where read and write shapes
  differ a lot, or very read-heavy systems. CQRS alone (without event sourcing) fits many more cases.
- *Avoid when:* simple CRUD, or a team new to the domain. Applying it system-wide is a common over-reach; use it in
  the one bounded context that needs it.
- *Real-world flavour:* account ledgers where the transaction log is the truth and balances are projections.
- *Depth:* DB-SQL-10.

## Space-based architecture

Designed for extreme and unpredictable load. Instead of every request hitting one database, processing units hold
data in a **replicated in-memory data grid**; the database is updated asynchronously in the background.

```text
  requests --> [ processing unit + in-memory grid ] <--replication--> [ processing unit + grid ]
                              \                                           /
                               +--> async writers --> [ database ] <-----+
```

- *Benefits:* removes the database as the bottleneck for hot paths; processing units scale out elastically.
- *Costs:* complex and expensive (a lot of memory); data consistency and collisions between replicas; risk of data
  loss before async persistence; hard to test.
- *Fits when:* very spiky, very high concurrency on a bounded data set: flash sales, ticket on-sales, bidding.
- *Avoid when:* large data sets that do not fit in memory, or strong consistency needs on every write.
- *Real-world flavour:* in-memory data grids such as Hazelcast or Apache Ignite.

## Serverless / FaaS

You deploy functions (**Function as a Service**) or containers; the provider runs, scales (including to zero) and
bills per invocation or per use. Usually event-triggered: HTTP, a queue message, a file upload, a schedule.

```text
  S3 upload --> [ function ] --> DB
  HTTP      --> [ function ] --> queue --> [ function ]
```

- *Benefits:* no servers to patch or capacity to plan; scales automatically; pay nothing when idle; fast to wire
  simple event flows.
- *Costs:* cold starts (noticeable for JVM functions; SnapStart, tuned runtimes or native images reduce them);
  execution time and resource limits (AWS Lambda caps a run at 15 minutes); hard local testing; vendor lock-in;
  per-call pricing can exceed always-on servers at steady high load; connection storms against relational databases
  (use a connection proxy).
- *Fits when:* spiky or low-volume workloads, glue between managed services, scheduled jobs, file processing.
- *Avoid when:* steady high throughput, latency-critical paths that cannot tolerate cold starts, long-running work.
- *Real-world flavour:* AWS Lambda behind API Gateway or triggered by SQS and S3; scale-to-zero container platforms
  such as Cloud Run.
- *Depth:* BE-STORY-11, DIST-SYS-8.

## Pipeline (pipes and filters), batch and stream

A **pipeline** passes data through independent stages (**filters**) connected by **pipes**; each stage does one
transformation. **Batch** runs the pipeline over a bounded data set on a schedule; **stream** runs it continuously over
unbounded events.

```text
  source --> [ parse ] --> [ validate ] --> [ enrich ] --> [ aggregate ] --> sink
```

Two classic data architectures:

- **Lambda architecture:** a batch layer recomputes accurate results; a speed layer gives fresh approximate results;
  a serving layer merges them. Correct and fresh, but the same logic lives in two code paths.
- **Kappa architecture:** a single streaming path; to reprocess, replay the retained log (for example Kafka) through
  a new version of the job. One code path, but it needs a replayable log and a stream engine you trust.

- *Benefits:* each stage simple, testable and reusable; stages scale separately; stream processing gives
  near-real-time results.
- *Costs:* error handling across stages (poison records, partial failure); stage contracts; streaming adds state,
  windows, late data and exactly-once concerns.
- *Fits when:* ETL, reporting, fraud detection, metrics, any data transformation flow.
- *Avoid when:* interactive request-response logic.
- *Real-world flavour:* Spring Batch nightly jobs; Kafka Streams or Flink for streams; Unix shell pipes are the
  original pipes and filters.
- *Depth:* DIST-SYS-9, SYS-DES-5.

## Service mesh

An infrastructure layer for service-to-service traffic. A proxy runs beside each service (classically a sidecar
container) and a **control plane** configures all of them: mTLS, retries, timeouts, traffic splitting, telemetry.

```text
  [ svc A | proxy ] <==== mTLS, retries, metrics ====> [ proxy | svc B ]
              ^                                           ^
              +------------ control plane (config) -------+
```

- *Benefits:* security, observability and traffic control consistently across all services and languages, without
  code changes; canary releases by traffic percentage.
- *Costs:* significant operational complexity; extra latency and resources per hop; another system to upgrade and
  debug; retries in both the mesh and the app can multiply.
- *Fits when:* many services, several languages, and zero-trust or mTLS requirements, with a platform team to run it.
- *Avoid when:* a handful of services; libraries (Resilience4j) and an ingress controller are enough.
- *Real-world flavour:* Istio and Linkerd on Kubernetes, with Envoy as a common proxy; sidecar-less modes (such as
  Istio's ambient mode) exist to cut the per-pod cost.
- *Depth:* BE-STORY-11.

## Cell-based architecture

The whole stack (services, databases, queues) is deployed as several **independent, identical cells**, each serving a
subset of customers. A thin **routing layer** sends each customer to their cell.

```text
                 [ cell router ]   (customer -> cell)
               /        |        \
       [ cell 1 ]   [ cell 2 ]   [ cell 3 ]
       full stack   full stack   full stack
       own data     own data     own data
```

- *Benefits:* limits the **blast radius**: a bad deploy, a noisy tenant or a data corruption affects one cell; deploys
  roll out cell by cell; capacity grows by adding cells, each with a known, tested maximum size.
- *Costs:* duplicated infrastructure; the router is critical and must stay very simple; moving customers between cells
  is hard; cross-cell features (global search, reporting) need separate aggregation.
- *Fits when:* large multi-tenant SaaS where availability matters more than infrastructure cost.
- *Avoid when:* small scale; one well-run deployment is cheaper and simpler.
- *Real-world flavour:* cloud providers publish guidance on cell-based design for reducing the scope of impact; large
  SaaS products use it for regional and tenant isolation.
- *Depth:* SYS-DES-9.

## Micro-frontends

Microservices applied to the UI: the web front end is split into parts owned by different teams, built and deployed
independently, and composed in the browser or at the edge.

```text
  [ shell app ]
    |-- header      (team A)
    |-- catalog     (team B)
    +-- checkout    (team C)
```

- *Benefits:* frontend teams release independently, aligned with their backend services; large UIs become manageable.
- *Costs:* duplicated dependencies and bigger bundles; inconsistent look and feel without a shared design system;
  cross-part state and routing are hard; more build and deploy infrastructure.
- *Fits when:* a large web app worked on by several independent teams.
- *Avoid when:* one frontend team; a well-structured single app is simpler and faster.
- *Real-world flavour:* composition through webpack Module Federation, single-spa, Web Components, or server-side
  includes.

## Multi-tenant SaaS models

How customers (**tenants**) share one product's infrastructure.

| Model | Shape | Isolation | Cost per tenant |
|---|---|---|---|
| **Silo** | A database (or whole stack) per tenant | Strongest | Highest |
| **Bridge** | One database, a schema per tenant | Medium | Medium |
| **Pool** | Shared tables with a `tenant_id` column | Weakest by default | Lowest |

- *Benefits:* pool is cheapest and simplest to operate at many tenants; silo gives strong isolation, per-tenant
  backups and compliance; bridge sits between.
- *Costs:* pool risks data leaks from one missing filter (defend with row-level security) and noisy neighbours; silo
  multiplies migrations, connections and cost; bridge runs migrations once per schema.
- *Fits when:* pool for many small tenants; silo for large or regulated ones; commonly a hybrid of both.
- *Avoid when:* choosing silo for thousands of small tenants (unaffordable) or pool for tenants whose contracts demand
  physical separation.
- *Depth:* SYS-DES-9.

## Data mesh and lakehouse (brief)

**Data mesh** (described by Zhamak Dehghani) is an organisational architecture for analytics: instead of one central
data team, each domain team owns and publishes its data **as a product**, on a self-serve platform, under federated
governance. It suits large organisations where the central data team is the bottleneck, and it costs real platform
investment and data-ownership maturity in every team.

A **lakehouse** stores data cheaply in open file formats in object storage (a data lake) and adds warehouse features
on top (transactions, schemas, time travel) through open table formats such as Delta Lake, Apache Iceberg or Apache
Hudi.

- It replaces separate lake and warehouse copies with one.
- Both matter mainly in data-platform interviews; for a backend role, know the names and the problem each solves.
- *Depth:* DIST-SYS-9 (OLTP vs OLAP).

## Peer-to-peer (brief)

Every node is both client and server; there is no central coordinator. Nodes find each other and share data directly.

- *Benefits:* no single point of failure, capacity grows with the number of peers.
- *Costs:* discovery, trust, security and consistency are hard, and behaviour is hard to control.
- *Real-world flavour:* BitTorrent-style file sharing, blockchains, and, inside a single system, leaderless databases
  whose nodes gossip membership and state to each other.

For most backend products it appears as an internal technique, not the product's architecture.

## Comparison table

Ratings are relative and typical, not absolute; a well-run style beats a badly run "better" one.

| Style | Coupling | Scalability | Team size fit | Operational cost | Consistency |
|---|---|---|---|---|---|
| Layered monolith | High inside, tends to mud | Whole app only | 1 small team | Low | Strong (one DB transaction) |
| Modular monolith | Low between modules if enforced | Whole app only | 1 to a few teams | Low | Strong, or eventual between modules by choice |
| Hexagonal / Clean / Onion | Low (domain isolated) | Same as host style | Any | Low (code structure only) | Same as host style |
| Microkernel | Low between plugins; contract is fixed | Moderate | 1 core team + plugin authors | Low to medium | Strong within the host |
| SOA with ESB | Coupled through the bus | Moderate; bus bottleneck | Many teams + a central bus team | High | Mixed |
| Microservices | Low if well bounded | Per service | Many teams | High | Eventual across services |
| Event-driven | Very low at build time | High | Medium to many | Medium to high | Eventual |
| CQRS + event sourcing | Low between read and write sides | High (reads scale apart) | Experienced team | High | Eventual read models; strong write side |
| Space-based | Medium | Very high, elastic | Experienced team | High | Eventual to the database |
| Serverless / FaaS | Low per function; tied to vendor | Automatic, to zero | Small to medium | Low to run, harder to debug | Depends on the stores used |
| Pipeline / stream | Low between stages | High | Small to medium | Medium | Eventual; exactly-once is extra work |
| Service mesh | (Infrastructure layer) | Supports many services | Needs a platform team | High | Not applicable |
| Cell-based | Low between cells | Add cells | Large organisation | High | Strong inside a cell |
| Micro-frontends | Low between UI parts | Team scaling, not load | Several frontend teams | Medium to high | Not applicable |
| Multi-tenant pool / bridge / silo | Pool shares most, silo least | Pool densest; silo per tenant | Any | Pool low, silo high | Strong inside a tenant |

## How to choose

Ask these questions, in this order, and say them out loud in an interview:

1. **How many teams will work on it, and do they need to release independently?** One team rarely benefits from
   microservices. Conway's law (systems mirror the communication structure of the organisation that builds them)
   cuts both ways: design boundaries that match the teams you have.
2. **How complex is the domain?** Thin CRUD: a layered monolith is honest. Rich rules: hexagonal or clean modules, a
   domain model, bounded contexts.
3. **What scale, and is it uniform?** If one part has very different load (an image pipeline, a pricing engine),
   that part is a candidate for extraction, serverless or streaming. If load is uniform, scale the whole app
   horizontally.
4. **What consistency does the business need?** Money moving and seat booking need strong consistency at the point of
   decision; feeds, search and analytics can be eventual. Every network boundary you add is a place where you lose a
   local transaction.
5. **How mature is operations?** Microservices, meshes and cells need CI/CD, observability, on-call and a platform.
   Without them, the style costs more than it returns.
6. **What is the blast radius you can tolerate?** High availability needs across many tenants push toward bulkheads,
   cells and silo tenants.

The default recommendation: **start with a modular monolith, with hexagonal-style modules where the domain is rich,
and extract a service only with evidence**, such as:

- a module that needs independent scaling;
- a team blocked by shared releases;
- or a different availability requirement.

Extracting a well-bounded module is a contained job; merging badly split services back together is far harder.

## In interviews

How this comes up:

- *"Monolith or microservices?"* A strong answer refuses the binary: ask about teams, domain, scale and ops maturity,
  then recommend a modular monolith with named extraction triggers. See
  [Microservices patterns: API gateway, service discovery, circuit breaker, saga](#/q/microservices-design-patterns).
- *"Explain hexagonal architecture."* Ports are interfaces the domain owns; adapters implement them; dependencies
  point inward; the payoff is testability and replaceable infrastructure. See
  [Hexagonal architecture (ports and adapters)](#/q/hexagonal-architecture) and
  [SOLID principles and dependency inversion](#/q/solid-principles).
- *"When would you use CQRS?"* Read and write shapes differ greatly, or reads dominate; mention the eventual
  consistency cost and that event sourcing is optional. See [CQRS: command query responsibility segregation](#/q/cqrs).
- *"Sync or async between services?"* See
  [Microservices communication: gRPC vs REST vs events](#/q/microservices-communication-grpc-vs-rest-eda) and
  [Messaging systems (queues, pub/sub) in backend services](#/q/messaging-systems-fundamentals).
- *"Explain the architecture of your current system."* Name the style at each level and one trade-off you would
  change. Practise with [Describe a design pattern you have used](#/q/describe-a-design-pattern) as a warm-up.

Typical follow-ups and what a strong answer contains:

- *"Your monolith is slow to deploy and teams block each other. What now?"* Modularise first (boundaries, owned
  tables, events between modules), then extract the module with the clearest independent need, using the strangler
  fig pattern and an anti-corruption layer. Measure before and after.
- *"What does microservices cost you?"* Network failures, no cross-service transactions (saga, outbox, idempotency),
  distributed tracing, contract versioning, platform and on-call load.

## Check yourself

1. What is the one rule hexagonal, onion and clean architecture share?
2. Event notification vs event-carried state transfer: what does each trade?
3. Why is a modular monolith usually the recommended starting point?
4. What does cell-based architecture protect against, and what does it cost?
5. Lambda vs Kappa architecture: what is the key difference?

### Answers

1. Source dependencies point inward: the domain depends on nothing in the infrastructure; adapters depend on the
   domain's ports.
2. Notification keeps events small but consumers call the producer back for details, re-coupling them at runtime.
   Event-carried state transfer puts the data in the event so consumers are independent of the producer's
   availability, at the cost of larger events, duplicated data and eventual consistency.
3. It keeps one deployment, in-process calls and local transactions, while giving clear module boundaries and
   ownership; a well-bounded module can be extracted later when evidence demands it, which is far cheaper than
   merging badly split services.
4. It limits the blast radius: a bad deploy, noisy tenant or failure affects one cell's customers. It costs duplicated
   infrastructure, a critical routing layer, and hard cross-cell features and customer moves.
5. Lambda runs a batch path and a speed path and merges them, so logic exists twice. Kappa uses one streaming path
   and reprocesses by replaying the retained log.
