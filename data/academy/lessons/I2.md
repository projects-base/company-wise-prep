## Where we are

SYS-DES-1 put a cache in front of the database: cache-aside, TTLs, delete-on-write, and the stampede when a hot key expires. Its example cache was Redis, treated as a black box with `get` and `put`. This lesson opens the box. Redis is a data-structure server, and knowing its threading model, types, expiry, eviction, persistence and clustering lets you use it for much more than caching: leaderboards, rate limiters and locks, plus the limits of each.

## The problem

Your prep app goes multi-instance behind a load balancer. Suddenly you need:

- a **cache** for company dossiers that does not blow up memory,
- a **leaderboard** of who solved the most questions this week,
- a **rate limiter** of 100 API calls per minute per user, shared by all instances,
- a **lock** so only one instance runs the nightly import.

An in-process `HashMap` cannot do any of these, because each instance has its own. You need one shared, fast store that every instance can reach. Redis does all four, but each use has a trap.

## Why Redis is fast: one thread, all in memory

Redis keeps every key in RAM, and **one main thread executes all commands**, one after another. It handles thousands of client connections with an **event loop**: the OS (via `epoll` on Linux) tells Redis which sockets have data, and Redis reads, runs and replies to each command in turn, without blocking on any one client.

```text
clients ──► sockets ──► [ event loop: read cmd → execute → write reply ] ──► next ready socket
                              one thread, no locks, data in RAM
```

Why this is fast: no disk reads on the hot path, no lock contention, no context switches between worker threads, and simple data structures with known costs. Network I/O can be spread over extra I/O threads since Redis 6, but command execution is still single-threaded.

Two consequences:

1. **Every single command is atomic.** `INCR counter` from 50 instances never loses an update. No other command runs in the middle of it.
2. **One slow command blocks everyone.** `KEYS *` on ten million keys, `DEL` of a huge set, or `HGETALL` on a giant hash stalls every client. Use `SCAN` to iterate and `UNLINK` to delete big keys in the background.

## Data types, and the job for each

Redis values are typed. Choosing the right type is half of every Redis design.

| Type | What it is | Key commands | Typical use |
|---|---|---|---|
| **String** | Bytes, up to 512 MB | `SET`, `GET`, `INCR`, `SET ... EX` | Cached JSON, counters, feature flags |
| **Hash** | Field → value map under one key | `HSET`, `HGET`, `HINCRBY` | An object's fields: a user session, a cart |
| **List** | Ordered list, fast at both ends | `LPUSH`, `RPOP`, `BRPOP`, `LTRIM` | Simple work queue, "last 50 activities" |
| **Set** | Unordered unique members | `SADD`, `SISMEMBER`, `SINTER` | Tags, "has this user voted?", unique visitors |
| **Sorted set** | Unique members, each with a score, kept sorted | `ZADD`, `ZINCRBY`, `ZREVRANGE`, `ZRANK` | **Leaderboards**, delay queues, sliding-window rate limits |
| **Stream** | Append-only log with consumer groups | `XADD`, `XREADGROUP`, `XACK` | Lightweight event log, job queue with acknowledgements |

Also worth naming: **bitmaps** (one bit per user id for daily-active flags), **HyperLogLog** (approximate unique counts in about 12 KB) and **geo** sets (nearby search).

**The leaderboard** is the classic sorted-set question:

```text
ZINCRBY lb:week:44 1 "akhil"      # akhil solved one more
ZINCRBY lb:week:44 3 "riya"
ZREVRANGE lb:week:44 0 9 WITHSCORES   # top 10, highest first
ZREVRANK lb:week:44 "akhil"           # akhil's position (0-based)
```

A sorted set is a skip list plus a hash table, so updates and rank lookups are O(log N), and member-to-score lookup is O(1). Doing the same in SQL means an `ORDER BY` over every row for each request.

**Streams versus Kafka:** a Redis stream has consumer groups, acknowledgements and pending-entry lists, which suits modest workloads. It lives in memory and has no partitions, so it is not a replacement for Kafka at high volume or long retention (DIST-SYS-2 goes deep on Kafka next).

## TTL and how keys expire

**The problem:** cached data must go away on its own, or memory fills with stale entries.

```text
SET dossier:google "{...}" EX 600   # set with a 10-minute TTL
TTL dossier:google                  # seconds left; -1 = no TTL, -2 = key gone
EXPIRE session:abc 1800             # add or reset a TTL on an existing key
```

Redis expires keys two ways: **lazily** (a key is checked when someone touches it, and deleted if past its time) and **actively** (a background task samples keys with TTLs several times a second and deletes expired ones). So an expired key stops being visible immediately, but its memory may be freed a little later.

**Trap:** a plain `SET` on an existing key **removes its TTL**. Use `SET key value EX n` again, or `SET ... KEEPTTL`.

## Eviction: what happens when memory is full

TTL removes keys by time. **Eviction** removes keys when Redis reaches `maxmemory`. The `maxmemory-policy` decides which:

| Policy | Evicts from | Choose |
|---|---|---|
| `noeviction` (default) | Nothing; writes fail with an OOM error | Redis used as a store you must not lose from |
| `allkeys-lru` | Any key, least recently used | Pure cache: the usual choice |
| `allkeys-lfu` | Any key, least frequently used | Cache with stable "popular" keys |
| `volatile-lru` / `volatile-lfu` | Only keys with a TTL | Mixed: cache keys have TTLs, important keys don't |
| `volatile-ttl` | Keys with a TTL, nearest expiry first | Rarely |
| `allkeys-random` / `volatile-random` | Random | Rarely |

Redis LRU is **approximate**: it samples a few keys (`maxmemory-samples`, default 5) and evicts the best candidate, rather than keeping an exact LRU list. That costs almost no memory and is close enough in practice.

**The rule:** a cache-only Redis uses `allkeys-lru` or `allkeys-lfu`. Leaving `noeviction` on a cache is a common reason for sudden write errors.

## Persistence: RDB versus AOF

Redis is in memory, but it can write to disk so a restart does not start empty.

- **RDB (snapshots):** every so often Redis `fork()`s; the child writes the whole dataset to a compact `.rdb` file while the parent keeps serving (copy-on-write). Fast restarts and good backups, but **you lose writes since the last snapshot**. Fork needs extra memory when there are many writes during the snapshot.
- **AOF (append-only file):** every write command is appended to a log, replayed on restart. `appendfsync everysec` (the default) loses at most about one second of writes; `always` fsyncs every write and is much slower. A background **rewrite** compacts the log.
- **Both:** the common production setting. Modern AOF files can start with an RDB snapshot and then append commands, which gives fast loads and small loss windows.

For a pure cache, persistence may be off entirely: on restart you warm up from the database. For anything that is the *source of truth* (rate-limit counters you can tolerate losing are fine; money is not), Redis is the wrong primary store even with AOF.

## Replication, Sentinel and Cluster

**Replication:** a primary streams its writes to replicas **asynchronously**. Replicas serve reads and stand by for failover. Because replication is async, a write acknowledged by the primary can be lost if it dies before replicas copy it. (`WAIT` can make a client wait for replicas, but it does not make Redis strongly consistent.)

**Sentinel:** separate processes that watch the primary, agree (by quorum) that it is down, promote a replica, and tell clients the new address. High availability for one dataset that fits on one machine.

**Cluster:** for data larger than one machine or more write throughput. The key space is split into **16,384 hash slots**: `slot = CRC16(key) mod 16384`. Each primary owns a range of slots and has its own replicas.

```text
primary A: slots 0–5460      primary B: 5461–10922      primary C: 10923–16383
client asks A for "user:42" → A replies MOVED 12182 <C's address> → client caches the slot map
```

Multi-key commands (`MGET`, transactions, Lua scripts) only work if all keys are in **one slot**. **Hash tags** force that: only the part inside `{}` is hashed, so `{user:42}:cart` and `{user:42}:profile` share a slot. Overusing one tag recreates a hot shard.

## Cache failure modes: stampede, penetration, avalanche

SYS-DES-1 introduced the stampede. The three names interviewers use:

- **Stampede (breakdown):** one hot key expires, and many requests miss and rebuild it at once. Fixes: let one caller rebuild (a short `SET NX` lock, next section) while others serve the stale value or wait briefly; refresh hot keys before they expire.
- **Penetration:** requests for keys that **do not exist** (`/companies/zzz-unknown`, or an attacker's random ids) always miss and always hit the database. Fixes: cache the "not found" result with a short TTL; put a Bloom filter (SYS-DES-1) of valid ids in front.
- **Avalanche:** **many** keys expire at the same moment (all set with the same TTL by a warm-up job), or the cache cluster goes down, and the whole load lands on the database. Fixes: add random jitter to TTLs; keep a small in-process cache in front of Redis; replicate Redis; rate-limit or circuit-break calls to the database so it survives.

## A distributed lock with SET NX PX

**The problem:** three instances run the nightly import at 02:00. Only one should.

```text
SET lock:import 7f3c-uuid NX PX 30000
```

- `NX`: set only if the key does not exist, so exactly one caller succeeds.
- `PX 30000`: the lock **expires** in 30 s, so a crashed holder cannot block everyone forever.
- The value is a **random token** unique to this holder.

Release must check the token, and must do it atomically, so you never delete a lock someone else now holds (yours expired, they acquired it). A Lua script runs atomically on the single thread:

```text
if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end
```

**Its limits, which a senior answer names:**

1. **The lease can expire while you still think you hold it.** A long GC pause or slow network call outlasts the 30 s; another instance acquires the lock; now two "holders" write.
2. **Failover can lose the lock.** The primary acknowledges your `SET`, dies before replicating it, a replica is promoted without the key, and a second client acquires the lock.

**Redlock** is Redis's answer to (2): acquire the lock on a majority of N (typically 5) independent Redis primaries within a time limit. Martin Kleppmann's well-known critique argues that it still depends on timing assumptions (clocks, pauses) and, like any lease, does not solve (1). Redis's author published a rebuttal. The practical takeaway both sides support: the fix for (1) is a **fencing token**.

A **fencing token** is a number that increases every time the lock is granted. The holder sends it with each write, and the **storage rejects any write with a token lower than one it has already seen**.

```text
client A gets lock, token 33 → pauses (GC)
lock expires; client B gets lock, token 34 → writes with 34 → storage records 34
client A wakes, writes with 33 → storage rejects (33 < 34)
```

**The rule:** use a Redis lock for **efficiency** (avoid doing the same work twice, where a rare double run is harmless). For **correctness** (money, inventory), rely on the database: a unique constraint, a conditional update with a version column, or a lock service such as etcd or ZooKeeper that provides fencing.

## A rate limiter with Redis

**Fixed window:** one counter per user per minute.

```text
INCR rl:user42:202610311405     → returns the count
PEXPIRE rl:user42:202610311405 60000   (only when the count is 1)
```

Run both in one Lua script so a crash between them cannot leave a counter with no TTL. Its weakness: a user can send 100 requests at 14:05:59 and 100 more at 14:06:00, 200 in two seconds.

**Sliding window log** with a sorted set fixes that: score = timestamp; on each request `ZREMRANGEBYSCORE` drops entries older than 60 s, `ZCARD` counts what remains, `ZADD` records this request. Accurate, but it stores one entry per request. A **token bucket** in Lua (store tokens and last-refill time in a hash) allows controlled bursts with constant memory. LLD-DESIGN-6 compared these algorithms in memory; Redis makes the state shared across instances.

## Lab (~10 min)

Start Redis and explore with the CLI:

```text
docker run -d --name redis -p 6379:6379 redis:7.4
docker exec -it redis redis-cli
> SET k v EX 5
> TTL k                       # watch it count down, then -2
> SET k v EX 100
> SET k v2                    # plain SET
> TTL k                       # -1: the TTL is gone
> CONFIG GET maxmemory-policy # noeviction by default
```

Then a Java 21 program with Jedis (`redis.clients:jedis`) that builds a leaderboard, a lock and a fixed-window rate limiter:

```java
import redis.clients.jedis.JedisPooled;
import redis.clients.jedis.params.SetParams;
import redis.clients.jedis.resps.Tuple;
import java.util.List;
import java.util.UUID;

public class RedisLab {
    static final String RELEASE =
        "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end";
    static final String RATE =
        "local n = redis.call('INCR', KEYS[1]) "
      + "if n == 1 then redis.call('PEXPIRE', KEYS[1], ARGV[1]) end "
      + "return n";

    public static void main(String[] args) {
        try (var jedis = new JedisPooled("localhost", 6379)) {
            jedis.zincrby("lb:week", 3, "riya");
            jedis.zincrby("lb:week", 5, "akhil");
            jedis.zincrby("lb:week", 1, "sam");
            for (Tuple t : jedis.zrevrangeWithScores("lb:week", 0, 2)) {
                System.out.println(t.getElement() + " " + t.getScore());
            }

            String token = UUID.randomUUID().toString();
            String first = jedis.set("lock:import", token, SetParams.setParams().nx().px(30_000));
            String second = jedis.set("lock:import", "other", SetParams.setParams().nx().px(30_000));
            System.out.println("first=" + first + " second=" + second);     // first=OK second=null
            System.out.println("wrong-token release=" + jedis.eval(RELEASE, List.of("lock:import"), List.of("other")));
            System.out.println("own release=" + jedis.eval(RELEASE, List.of("lock:import"), List.of(token)));

            for (int i = 1; i <= 5; i++) {
                long n = (Long) jedis.eval(RATE, List.of("rl:user42"), List.of("60000"));
                System.out.println("request " + i + (n <= 3 ? " allowed" : " rejected") + " (count " + n + ")");
            }
        }
    }
}
```

**Observe:** the leaderboard prints akhil, riya, sam; the second lock attempt returns `null`; releasing with the wrong token returns `0` and leaves the lock; requests 4 and 5 are rejected. Run it again within a minute and all five are rejected until the key expires.

**Break it:** set the lock's `px` to 1000, add `Thread.sleep(2000)` before releasing, and acquire the lock from a second `redis-cli` during the sleep. Your "own release" now returns `0`: the lease expired and someone else holds it. That is limit (1) in miniature.

## Gotchas

- **`KEYS *` or huge `DEL` in production.** They block the single thread for every client. Use `SCAN` and `UNLINK`.
- **`SET` silently dropping the TTL.** Re-set the expiry or use `KEEPTTL`; otherwise "cache" keys live forever.
- **A cache running with `noeviction`.** When full, writes fail. Use `allkeys-lru` or `allkeys-lfu` for caches.
- **Releasing a lock with a plain `DEL`.** You may delete another holder's lock. Compare the token and delete in one Lua script.
- **Treating a Redis lock as a correctness guarantee.** Leases expire and async failover loses keys. Protect the data with fencing tokens or database constraints.
- **Cross-slot commands in Cluster.** `MGET` across slots fails with `CROSSSLOT`. Group related keys with hash tags, sparingly.

## In interviews

Typical prompts: "Why is Redis so fast if it is single-threaded?", "Design a leaderboard", "Implement a distributed rate limiter", "How would you implement a distributed lock, and is it safe?", "RDB vs AOF?", "What are cache penetration and avalanche?". Bank: [Redis: how it works and the algorithms behind it](#/q/redis-internals), [Design a Leaderboard](#/q/design-leaderboard), [Design a Rate Limiter](#/q/design-rate-limiter), [Design a distributed cache optimised for a given task](#/q/design-distributed-cache), [Diagnosing a low cache hit ratio](#/q/diagnose-low-cache-hit-ratio).

A strong answer has four layers:

1. **What:** an in-memory data-structure server, used as cache, counter store, leaderboard, rate limiter, lightweight queue and lock service.
2. **How it works inside:** single-threaded event loop (atomic commands, no locks); typed values (sorted set = skip list + hash); lazy plus active expiry; approximate LRU/LFU eviction; RDB fork snapshots and AOF logs; async replication; Sentinel failover; 16,384 hash slots in Cluster.
3. **Where used:** cache-aside in front of a database, session store, leaderboards, per-user rate limits shared across instances, job de-duplication locks.
4. **What goes wrong:** slow commands blocking everyone, stampede / penetration / avalanche, memory full under `noeviction`, data loss on failover, locks that expire under a paused holder.

**Follow-up: "Is your Redis lock safe?"** Say it is safe for efficiency, not for correctness: name GC-pause lease expiry and async-replication failover, mention Redlock and the debate around it, and finish with fencing tokens or a database constraint for anything that must not happen twice.

**Follow-up: "Your leaderboard has 100 million users."** One sorted set still works (O(log N)), but memory and one hot key become the limits. Shard by region or time window, and keep the global top-K in a small separate set.

## Explain it in 2 minutes

*"Why is Redis fast, and how would you use it safely as a cache and a lock?"*

- All data is in memory and one thread runs commands from an event loop, so each command is atomic and there is no lock contention; the cost is that one slow command blocks everyone.
- Pick the type for the job: strings for cached values and counters, hashes for objects, sorted sets for leaderboards and sliding windows, streams for small event logs.
- As a cache: TTL with jitter, `allkeys-lru`/`lfu` eviction, cache-aside, with defences against stampede, penetration and avalanche.
- Durability is RDB snapshots and/or AOF; replication is async, so acknowledged writes can be lost on failover.
- Locks: `SET key token NX PX`, release by compare-and-delete in Lua; good for efficiency, but use fencing tokens or database constraints for correctness.

## Check yourself

1. Two app instances call `INCR views` at the same instant. Can an update be lost? Why?
2. Which data type and commands would you use for "top 10 users this week", and what is the cost of an update?
3. What is the difference between cache penetration and cache avalanche, and one fix for each?
4. Why must the lock's value be a random token, and why is release done in Lua?
5. In Redis Cluster, `MGET user:1:name user:1:email` fails. Why, and how do you fix it?

### Answers

1. No. Commands run one at a time on the single main thread, so each `INCR` is atomic and both increments apply.
2. A sorted set: `ZINCRBY` on each solve, `ZREVRANGE key 0 9 WITHSCORES` to read. Updates are O(log N).
3. Penetration is repeated requests for keys that don't exist, so they always reach the database: cache "not found" briefly or use a Bloom filter. Avalanche is many keys expiring together (or the cache failing): jitter TTLs and protect the database with rate limits.
4. The token identifies the holder, so you only delete the lock if it is still yours, not one another client acquired after yours expired. `GET` and `DEL` must happen atomically, and a Lua script runs without any other command in between.
5. The two keys hash to different slots, and multi-key commands need one slot. Use a hash tag such as `{user:1}:name` and `{user:1}:email`, so only `user:1` is hashed.
