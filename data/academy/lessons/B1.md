## Where we are

From S0 you know that a **process** is a running program with its own memory, and a **thread** is one path of execution inside a process. All threads in a process share that memory. This lesson turns that idea into Java: you will create threads, wait for them, stop them politely, and watch two threads silently corrupt a shared number.

## The problem

Suppose your program must fetch three web pages and each fetch takes about one second. If you do them one after another, the user waits about three seconds. Almost all of that time the CPU is idle, waiting for the network. If three threads each fetch one page at the same time, the user waits about one second.

Servers have the same problem at a larger scale. A Servlet container runs each request on its own thread (you will see this in S2), so a slow request does not hold up the others.

So we want several things happening at once. Java gives us `Thread` for that, along with a set of rules we must learn to use it safely.

## You already have one thread

Every Java program starts on a thread the JVM creates for you, called `main`.

```java
public class Hello {
    public static void main(String[] args) {
        System.out.println(Thread.currentThread().getName()); // prints: main
    }
}
```

`Thread.currentThread()` returns the `Thread` object for whichever thread is running that line. You will use it constantly while debugging.

## Starting a second thread

A **task** is the code you want run. In Java it is usually a `Runnable`, an interface with one method, `void run()`. A **thread** is the worker that runs a task.

```java
Runnable task = () -> System.out.println("hi from " + Thread.currentThread().getName());

Thread t = new Thread(task, "worker-1");
t.start();                       // a new thread runs task.run()
System.out.println("main continues");
```

Run this a few times. Sometimes `main continues` prints first, and sometimes `hi from worker-1` does. The order is not defined.

The rule is that **`start()` creates a new thread of execution and that new thread calls `run()`**. If you call `t.run()` yourself, nothing new is created. The code simply runs on the current thread, like any other method call. A thread can be started only once. A second `start()` throws `IllegalThreadStateException`.

Java 21 also has a builder, which reads well and makes naming easy:

```java
Thread t = Thread.ofPlatform().name("worker-1").start(task);
```

A **platform thread** is the classic kind of Java thread. Each one is backed by exactly one operating-system thread. (B6 introduces the other kind, virtual threads.)

Prefer passing a `Runnable` over writing `class MyThread extends Thread`. Keeping the task separate from the worker is what lets thread pools (B4) run your task on a thread they already have.

## Waiting for a thread: `join`

`t.join()` makes the calling thread wait until `t` has finished.

```java
Thread t = Thread.ofPlatform().start(() -> System.out.println("working"));
t.join();                        // main waits here
System.out.println("worker is done");
```

`join` gives you two guarantees:

- **Ordering.** The code after `join()` runs only after the thread has finished.
- **Visibility.** Everything the finished thread wrote to memory can be seen by the thread that called `join`.

The second guarantee matters more than it sounds. As A6 explains, without such a guarantee one thread may not see another thread's writes at all. `join` is one of the few places where Java promises that you will see them.

`join` can throw `InterruptedException`. We cover that below.

## The life of a thread (short version)

A thread moves through a small set of states. `t.getState()` tells you which one it is in.

```text
 new Thread(..)        start()                     run() returns or throws
 ──────────────► NEW ─────────► RUNNABLE ───────────────────────► TERMINATED
                                  │   ▲
           sleep / join / wait /  │   │  time is up / woken up /
           waiting for a lock     ▼   │  lock acquired
                          BLOCKED, WAITING, TIMED_WAITING
```

- **NEW**: the thread object exists but has not been started.
- **RUNNABLE**: the thread is running on a CPU *or* is ready to run and waiting for a CPU. Java does not tell these two apart.
- **BLOCKED / WAITING / TIMED_WAITING**: the thread is parked and is not using the CPU. Each means something different, and L3 goes through exactly which method leads to which.
- **TERMINATED**: `run()` finished, either normally or with an exception. A terminated thread cannot be restarted.

## `sleep` and the scheduler

The **scheduler** is the part of the operating system that decides which runnable thread gets a CPU core, and for how long. You do not control it.

`Thread.sleep(200)` puts the current thread into TIMED_WAITING for at least 200 ms. After that it becomes RUNNABLE again and waits its turn for a core.

The rule is to **never use `sleep` to make threads happen in a particular order**. "Sleep 100 ms and the other thread will have finished by then" works on your laptop and fails on a busy server. Use `join`, or the coordination tools in B3.

## Stopping a thread: interruption

Why not just kill a thread? Because it might be halfway through changing shared data. Killing it there would leave that data half-updated for every other thread to see. `Thread.stop()` did exactly that and has been deprecated for decades. Since roughly Java 20 it throws `UnsupportedOperationException`.

Java uses **interruption** instead. It is a polite request that the thread is free to act on.

- `t.interrupt()` sets a boolean **interrupt flag** on `t`. That is all it does.
- Code running in `t` checks the flag with `Thread.currentThread().isInterrupted()`.
- If `t` is blocked in `sleep`, `join`, `wait`, or a blocking queue's `take`, that method wakes up early, **clears the flag**, and throws `InterruptedException`.

The standard pattern for a loop that can be cancelled looks like this:

```java
Runnable worker = () -> {
    while (!Thread.currentThread().isInterrupted()) {
        try {
            System.out.println("tick");
            Thread.sleep(300);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt(); // restore the flag that sleep cleared
            break;                              // then actually stop
        }
    }
    System.out.println("worker exits cleanly");
};
```

Rule: **never swallow `InterruptedException`.** Either let it propagate by declaring `throws InterruptedException`, or catch it, restore the flag with `interrupt()`, and wind down. If you swallow it, the request to stop disappears and code higher up the stack never learns about it.

There are two similar-looking methods, and the difference between them is a classic trap:

- `t.isInterrupted()` reads the flag and leaves it unchanged.
- `Thread.interrupted()` is a *static* method that reads the current thread's flag **and clears it**.

Not everything responds to an interrupt. A thread waiting to enter a `synchronized` block (B2) ignores it, and so does a platform thread blocked in a classic `java.io` socket read.

## Daemon threads

The JVM exits when every **non-daemon** thread has finished. A **daemon thread** is a background helper that does not keep the JVM alive. You call `t.setDaemon(true)` before `start()`. When the JVM exits, daemon threads are simply abandoned mid-step and their `finally` blocks do not run. So never give a daemon thread work that must complete, such as flushing a file.

## Two threads, one counter

This is where things go wrong. `count++` looks like one step, but it is really three:

```text
1. read  count from memory into a register
2. add   1 to the register
3. write the register back to count
```

If two threads interleave those steps, one of the increments disappears:

```text
count = 5
Thread A: read 5
Thread B: read 5
Thread A: add 1 → 6, write 6
Thread B: add 1 → 6, write 6        ← A's increment is lost; count should be 7
```

This is a **race condition**: the result depends on the timing of the threads. It is also a **lost update**: one thread's write overwrites another's. Nothing crashes and nothing is logged. The number is simply wrong. You will see it happen in the lab below and fix it in B2.

## Lab (~10 min)

Save this as `ThreadBasics.java` and run it with `java ThreadBasics.java` (Java 21 runs a single source file directly).

```java
public class ThreadBasics {
    // volatile only stops the JIT (the JVM's run-time compiler) from turning the loop into one
    // big "count += n". It does NOT make count++ safe; A6 and B2 explain why.
    static volatile int count = 0;   // shared, unprotected

    public static void main(String[] args) throws Exception {
        // Part 1: watch the states
        Thread sleeper = new Thread(() -> {
            try { Thread.sleep(500); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }, "sleeper");
        System.out.println("1. " + sleeper.getState());   // NEW
        sleeper.start();
        Thread.sleep(100);
        System.out.println("2. " + sleeper.getState());   // TIMED_WAITING
        sleeper.join();
        System.out.println("3. " + sleeper.getState());   // TERMINATED

        // Part 2: interrupt a worker politely
        Thread worker = Thread.ofPlatform().name("ticker").start(() -> {
            while (!Thread.currentThread().isInterrupted()) {
                try {
                    System.out.println("   tick");
                    Thread.sleep(200);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    break;
                }
            }
            System.out.println("   ticker exits cleanly");
        });
        Thread.sleep(700);
        worker.interrupt();
        worker.join();

        // Part 3: the race
        for (int run = 1; run <= 5; run++) {
            count = 0;
            Runnable inc = () -> { for (int i = 0; i < 5_000_000; i++) count++; };
            Thread a = new Thread(inc), b = new Thread(inc);
            a.start(); b.start();
            a.join();  b.join();
            System.out.println("run " + run + ": count = " + count + " (expected 10000000)");
        }
    }
}
```

What you should observe:

1. The states print `NEW`, `TIMED_WAITING`, `TERMINATED`.
2. A few `tick` lines appear, and then `ticker exits cleanly`.
3. Most runs print a number **below 10,000,000**, and the number changes from run to run. That is the lost update. (Occasionally a run comes out exact. A race can be invisible, which is why it is dangerous.)

**Break it:** in Part 2, delete the `Thread.currentThread().interrupt(); break;` lines and leave the `catch` block empty. Now the ticker never stops and the program hangs. `sleep` cleared the flag and your code threw the request away. Press Ctrl+C to stop it.

**Try it:** in Part 3, call `a.run(); b.run();` instead of `start()`. The count is now always exactly 10,000,000, because both loops ran one after the other on `main`. There were no extra threads, so there was no race.

## Gotchas

- **Calling `run()` instead of `start()`.** No new thread is created, and the code runs on the caller. Always call `start()`, or use `Thread.ofPlatform().start(task)`.
- **Swallowing `InterruptedException`.** The cancellation request is lost. Restore the flag with `Thread.currentThread().interrupt()` or rethrow it.
- **Using `Thread.interrupted()` just to check.** It clears the flag. Use `isInterrupted()` to read without clearing.
- **Relying on output order or `sleep` timing.** The scheduler decides who runs. Use `join` or proper coordination.
- **An exception kills only its own thread.** The stack trace goes to stderr and the other threads keep going, often with half-finished work. Set an `UncaughtExceptionHandler` or let an executor capture the failure (B4).
- **Daemon threads skip `finally` at JVM exit.** Never use one for work that must complete.

## In interviews

Early in a concurrency round, or in an OS round, you will usually hear "What is the difference between a process and a thread?" and "What happens when two threads update a shared variable?" See [Process vs thread, shared variables and race conditions](#/q/process-vs-thread).

Typical follow-ups:

- **"How do you stop a thread?"** A strong answer says interruption is cooperative. It explains the flag, which methods throw `InterruptedException` and clear the flag, the restore-the-flag pattern, and why `stop()` is unsafe: it would abandon shared data in a half-updated state.
- **"`start()` vs `run()`?"** Only `start()` creates a new thread of execution. Calling `run()` is an ordinary method call.

## Explain it in 2 minutes

*"Walk me through creating a thread in Java, waiting for it, and cancelling it."*

- A `Runnable` is the task and a `Thread` is the worker. `start()` creates the new thread, and `run()` is just the method body.
- The states run NEW → RUNNABLE ⇄ BLOCKED/WAITING/TIMED_WAITING → TERMINATED. RUNNABLE covers both "running" and "ready to run".
- `join` waits for a thread to finish, and also makes that thread's writes visible to the caller.
- Interruption sets a flag. Blocking methods throw `InterruptedException` and clear it, so you restore the flag or rethrow.
- Shared mutable state plus non-atomic operations such as `count++` give race conditions and lost updates.

## Check yourself

1. What does `t.run()` do differently from `t.start()`?
2. A platform thread is stuck inside a classic `java.io` socket read, waiting for bytes. What does `getState()` report?
3. After `Thread.sleep` throws `InterruptedException`, is the interrupt flag set or cleared?
4. Why can `count++` on a shared `int` lose updates?
5. Your program's `main` has finished, but the JVM does not exit. What is a likely cause?

### Answers

1. `run()` executes the task on the current thread like a normal method call. `start()` creates a new thread that calls `run()`.
2. RUNNABLE. The thread is blocked in the operating system, but Java does not distinguish "running", "ready to run" and "inside a native I/O call". So a thread dump full of RUNNABLE threads does not mean the CPU is busy.
3. Cleared. That is why you must restore it or rethrow.
4. It is three steps (read, add, write). Two threads can both read the same old value, and one write overwrites the other.
5. Some non-daemon thread is still running. Find it in a thread dump (`jstack <pid>`) and stop it, or make it a daemon if it really is disposable background work.
