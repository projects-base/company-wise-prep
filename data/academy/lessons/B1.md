## Where we are

From BE-STORY-1 you know that a **process** is a running program with its own memory, and a **thread** is one path of execution inside a process. All threads in a process share that memory. This lesson turns that idea into Java: you will create threads, wait for them, stop them politely, and watch two threads silently corrupt a shared number.

## The problem

You are building a dashboard page that calls three slow services, each taking about one second. Called one after another, the page takes about three seconds, and the product owner wants it under one and a half. Almost all of those three seconds the CPU is idle, waiting for the network. If three threads each make one call at the same time, the page takes about one second.

Servers have the same problem at a larger scale. A Servlet container (the server that runs Java web code) runs each request on its own thread (you will see this in BE-STORY-3), so a slow request does not hold up the others.

So we want several things happening at once. Java gives us `Thread` for that, along with a set of rules we must learn to use it safely. Break those rules and the page is fast but sometimes shows wrong numbers, with nothing in the logs.

## You already have one thread

Every Java program starts on a thread the JVM creates for you, called `main`.

```java
public class Hello {
    public static void main(String[] args) {
        System.out.println(Thread.currentThread().getName()); // prints: main
    }
}
```

`Thread.currentThread()` returns the `Thread` object for whichever thread is running that line. You will use it constantly while debugging.

## Starting a second thread

A **task** is the code you want run. In Java it is usually a `Runnable`, an interface with one method, `void run()`. A **thread** is the worker that runs a task.

```java
Runnable task = () -> System.out.println("hi from " + Thread.currentThread().getName());

Thread t = new Thread(task, "worker-1");
t.start();                       // a new thread runs task.run()
System.out.println("main continues");
```

Run this a few times. Sometimes `main continues` prints first, and sometimes `hi from worker-1` does. The order is not defined.

**Predict:** replace `t.start()` with `t.run()`. What prints now, and is the order still random?

Always `hi from main`, then `main continues`. The rule is that **`start()` creates a new thread of execution and that new thread calls `run()`**. If you call `t.run()` yourself, nothing new is created. The code simply runs on the current thread, like any other method call.

Java 21 also has a builder, which reads well and makes naming easy:

```java
Thread t = Thread.ofPlatform().name("worker-1").start(task);
```

A **platform thread** is the classic kind of Java thread. Each one is backed by exactly one operating-system thread. (JAVA-CONC-6 introduces the other kind, virtual threads.)

Prefer passing a `Runnable` over writing `class MyThread extends Thread`. Keeping the task separate from the worker is what lets thread pools (JAVA-CONC-4) run your task on a thread they already have.

## Waiting for a thread: `join`

`t.join()` makes the calling thread wait until `t` has finished.

```java
Thread t = Thread.ofPlatform().start(() -> System.out.println("working"));
t.join();                        // main waits here
System.out.println("worker is done");
```

`join` gives you two guarantees:

- **Ordering.** The code after `join()` runs only after the thread has finished.
- **Visibility.** Everything the finished thread wrote to memory can be seen by the thread that called `join`.

The second guarantee matters more than it sounds. As JAVA-JVM-6 explains, without such a guarantee one thread may not see another thread's writes at all. `join` is one of the few places where Java promises that you will see them.

`join` can throw `InterruptedException`. We cover that below.

## The life of a thread (short version)

A thread moves through a small set of states. `t.getState()` tells you which one it is in.

```text
 new Thread(..)        start()                     run() returns or throws
 ──────────────► NEW ─────────► RUNNABLE ───────────────────────► TERMINATED
                                  │   ▲
           sleep / join / wait /  │   │  time is up / woken up /
           waiting for a lock     ▼   │  lock acquired
                          BLOCKED, WAITING, TIMED_WAITING
```

- **NEW**: the thread object exists but has not been started.
- **RUNNABLE**: the thread is running on a CPU *or* is ready to run and waiting for a CPU. Java does not tell these two apart (nor, as LIFECYCLE-2 shows, a thread stuck in socket I/O).
- **BLOCKED / WAITING / TIMED_WAITING**: the thread is parked and is not using the CPU. Each means something different, and LIFECYCLE-2 goes through exactly which method leads to which.
- **TERMINATED**: `run()` finished, either normally or with an exception. A terminated thread cannot be restarted.

## `sleep` and the scheduler

The **scheduler** is the part of the operating system that decides which runnable thread gets a CPU core, and for how long. You do not control it.

`Thread.sleep(200)` puts the current thread into TIMED_WAITING for at least 200 ms. After that it becomes RUNNABLE again and waits its turn for a core.

The rule is to **never use `sleep` to make threads happen in a particular order**. "Sleep 100 ms and the other thread will have finished by then" works on your laptop and fails on a busy server. Use `join`, or the coordination tools in JAVA-CONC-3.

## Stopping a thread: interruption

Why not just kill a thread? Because it might be halfway through changing shared data. Killing it there would leave that data half-updated for every other thread to see. `Thread.stop()` did exactly that and has been deprecated for decades. Since Java 20 it throws `UnsupportedOperationException`.

Java uses **interruption** instead. It is a polite request that the thread is free to act on.

- `t.interrupt()` sets a boolean **interrupt flag** on `t`. That is all it does.
- Code running in `t` checks the flag with `Thread.currentThread().isInterrupted()`.
- If `t` is blocked in `sleep`, `join`, `wait`, or a blocking queue's `take`, that method wakes up early, **clears the flag**, and throws `InterruptedException`.

The standard pattern for a loop that can be cancelled looks like this:

```java
Runnable worker = () -> {
    while (!Thread.currentThread().isInterrupted()) {
        try {
            System.out.println("tick");
            Thread.sleep(300);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt(); // restore the flag that sleep cleared
            break;                              // then actually stop
        }
    }
    System.out.println("worker exits cleanly");
};
```

Rule: **never swallow `InterruptedException`.** Either let it propagate by declaring `throws InterruptedException`, or catch it, restore the flag with `interrupt()`, and wind down. If you swallow it, the request to stop disappears and code higher up the stack never learns about it.

There are two similar-looking methods, and the difference between them is a classic trap:

- `t.isInterrupted()` reads the flag and leaves it unchanged.
- `Thread.interrupted()` is a *static* method that reads the current thread's flag **and clears it**.

Not everything responds to an interrupt. A thread waiting to enter a `synchronized` block (JAVA-CONC-2) ignores it, and so does a platform thread blocked in a classic `java.io` socket read.

## Daemon threads

The JVM exits when every **non-daemon** thread has finished. A **daemon thread** is a background helper that does not keep the JVM alive. You call `t.setDaemon(true)` before `start()`. When the JVM exits, daemon threads are simply abandoned mid-step and their `finally` blocks do not run. So never give a daemon thread work that must complete, such as flushing a file.

## Two threads, one counter

**Predict:** two threads share `static volatile int count = 0` (as in the lab; `volatile` is explained below), and
each runs `count++` five million times. After both are joined, what is `count`?

Usually well below 10,000,000 (around 5.5 to 6.5 million on one laptop run), and different every run. `count++` looks like one step, but it is really three:

```text
1. read  count from memory into a register
2. add   1 to the register
3. write the register back to count
```

If two threads interleave those steps, one of the increments disappears. Step through it:


This is a **race condition**: the result depends on the timing of the threads. It is also a **lost update**: one thread's write overwrites another's. Nothing crashes and nothing is logged. The number is simply wrong. You will see it happen in the lab below and fix it in JAVA-CONC-2.

Marking a field **`volatile`** guarantees that every read sees the most recent write to it by any thread (JAVA-JVM-6
explains how). It says nothing about doing read-add-write as one step, which is why the lab's `volatile` counter still
loses updates.

## Lab (~10 min)

Save this as `ThreadBasics.java` and run it with `java ThreadBasics.java` (Java 21 runs a single source file directly). **Predict** the three state names in Part 1 and how many `tick` lines Part 2 prints before you run it.

```java
public class ThreadBasics {
    // volatile only stops the JIT (the JVM's run-time compiler) from turning the loop into one
    // big "count += n". It does NOT make count++ safe; JAVA-JVM-6 and JAVA-CONC-2 explain why.
    static volatile int count = 0;   // shared, unprotected

    public static void main(String[] args) throws Exception {
        // Part 1: watch the states
        Thread sleeper = new Thread(() -> {
            try { Thread.sleep(500); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }, "sleeper");
        System.out.println("1. " + sleeper.getState());   // NEW
        sleeper.start();
        Thread.sleep(100);
        System.out.println("2. " + sleeper.getState());   // TIMED_WAITING
        sleeper.join();
        System.out.println("3. " + sleeper.getState());   // TERMINATED

        // Part 2: interrupt a worker politely
        Thread worker = Thread.ofPlatform().name("ticker").start(() -> {
            while (!Thread.currentThread().isInterrupted()) {
                try {
                    System.out.println("   tick");
                    Thread.sleep(200);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    break;
                }
            }
            System.out.println("   ticker exits cleanly");
        });
        Thread.sleep(700);
        worker.interrupt();
        worker.join();

        // Part 3: the race
        for (int run = 1; run <= 5; run++) {
            count = 0;
            Runnable inc = () -> { for (int i = 0; i < 5_000_000; i++) count++; };
            Thread a = new Thread(inc), b = new Thread(inc);
            a.start(); b.start();
            a.join();  b.join();
            System.out.println("run " + run + ": count = " + count + " (expected 10000000)");
        }
    }
}
```

What you should observe:

1. The states print `NEW`, `TIMED_WAITING`, `TERMINATED`.
2. A few `tick` lines appear, and then `ticker exits cleanly`.
3. Most runs print a number **below 10,000,000**, and the number changes from run to run. That is the lost update. (Occasionally a run comes out exact. A race can be invisible, which is why it is dangerous.)

**Break it:** in Part 2, delete the `Thread.currentThread().interrupt(); break;` lines and leave the `catch` block empty. Now the ticker never stops and the program hangs. `sleep` cleared the flag and your code threw the request away. Press Ctrl+C to stop it.

**Try it:** in Part 3, call `a.run(); b.run();` instead of `start()`. The count is now always exactly 10,000,000, because both loops ran one after the other on `main`. There were no extra threads, so there was no race.

## Gotchas

- **`run()` instead of `start()`:** no new thread; the task runs on the caller. Call `start()`.
- **Swallowed `InterruptedException`:** the stop request vanishes. Restore the flag or rethrow.
- **`Thread.interrupted()` to check:** it clears the flag. Use `isInterrupted()`.
- **`sleep` for ordering:** the scheduler decides. Use `join` or real coordination.
- **An uncaught exception kills only its own thread:** the rest carry on with half-done work. Set an `UncaughtExceptionHandler` or use an executor (JAVA-CONC-4).
- **Daemon threads skip `finally` at JVM exit:** never give them must-finish work.

Follow-ups:

- **"How do you stop a thread?"** Interruption is cooperative: set the flag, blocking calls throw and clear it, restore it and wind down. `stop()` would leave shared data half-updated.
- **"`start()` vs `run()`?"** Only `start()` creates a thread; `run()` is a plain method call.

## Explain it in 2 minutes

*"Walk me through creating a thread in Java, waiting for it, and cancelling it."*

- `Runnable` is the task, `Thread` the worker; `start()` makes the new thread.
- NEW → RUNNABLE ⇄ BLOCKED/WAITING/TIMED_WAITING → TERMINATED.
- `join` waits and makes the thread's writes visible.
- Interrupt sets a flag; blocking methods throw and clear it.
- Shared state plus non-atomic `count++` means lost updates.
