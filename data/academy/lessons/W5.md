## Where we are

From SPRING-BOOT-9 you can put a `SecurityFilterChain` in front of an API and validate JWTs; from SPRING-BOOT-10 you
know where those tokens come from. From WEB-API-3 you can design the endpoints themselves. But a perfectly
authenticated API can still leak every customer's data. This lesson is about the bugs that live *behind* the login:
the OWASP Top 10 as a Java backend developer meets them, plus password storage, secrets and TLS between services.

## The problem

Three incidents, none caused by weak login:

- `GET /api/orders/1043` returns your order. Change it to 1044 and you see a stranger's address. The token was valid.
- A search endpoint builds SQL with `+`. Someone types `' OR '1'='1` and downloads the users table.
- A "preview this link" feature fetches any pasted URL. Someone pastes the cloud metadata address and gets the
  server's cloud credentials.

Each is a failure *after* "who are you" was answered correctly.

## The OWASP Top 10 (2021) as a map

**OWASP** (Open Worldwide Application Security Project) publishes a ranked list of the most common web application
risk categories. The 2021 edition is the one most interviewers quote (OWASP has since published a newer edition, so
expect the numbering to drift):

| # | Category | What it looks like in a Spring service |
|---|---|---|
| A01 | Broken Access Control | IDOR, missing ownership checks, admin endpoints open to users |
| A02 | Cryptographic Failures | plain HTTP, SHA-256 passwords, home-made crypto |
| A03 | Injection | SQL/JPQL by concatenation, log injection, XSS |
| A04 | Insecure Design | no rate limit on OTP verification, business-logic holes |
| A05 | Security Misconfiguration | exposed Actuator, stack traces, `CORS *` |
| A06 | Vulnerable and Outdated Components | an old library with a known CVE |
| A07 | Identification and Authentication Failures | brute-forceable login, weak session handling |
| A08 | Software and Data Integrity Failures | insecure deserialization, unsigned updates |
| A09 | Security Logging and Monitoring Failures | no audit trail, attacks unnoticed |
| A10 | Server-Side Request Forgery | fetching user-given URLs |

The sections below take the categories you touch in code.

## Broken access control: IDOR and ownership

An **IDOR** (insecure direct object reference) is an endpoint that trusts an id from the request without checking
that the caller may see that object:

```java
@GetMapping("/orders/{id}")
Order get(@PathVariable long id) {
    return orderRepository.findById(id).orElseThrow();      // any logged-in user, any order
}
```

Sequential ids make it trivial; UUIDs make guessing harder but do not fix it. The fix is an ownership check on every
object access. The most robust form puts the owner in the query, so a forgotten check is impossible:

```java
Optional<Order> findByIdAndOwnerId(long id, String ownerId);   // Spring Data derived query

@GetMapping("/orders/{id}")
Order get(@PathVariable long id, @AuthenticationPrincipal Jwt jwt) {
    return orderRepository.findByIdAndOwnerId(id, jwt.getSubject())
            .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND));
}
```

Return **404, not 403**, for "not yours", so the API does not confirm which ids exist. When the rule is more complex
(owner *or* support agent), use method security, enabled with `@EnableMethodSecurity` as in SPRING-BOOT-9:

```java
@PreAuthorize("hasRole('SUPPORT') or @orderAccess.isOwner(#id, authentication)")
public Order getOrder(long id) { ... }
```

`@orderAccess` is a bean you write; `#id` binds to the method parameter, which needs the `-parameters` compiler flag
(the Spring Boot build plugins set it).

## Injection: data that becomes code

**Injection** happens when untrusted input is pasted into something an interpreter parses: SQL, JPQL, a shell, a log
line, HTML. The classic:

```java
String sql = "SELECT * FROM users WHERE email = '" + email + "'";   // email = x' OR '1'='1
```

The input changes the *structure* of the query. A `PreparedStatement` (DB-SQL-5) sends the SQL with `?` placeholders
to the database, which parses it once; values are bound afterwards and can never become SQL. JPA is safe only if you
use it the same way:

```java
// vulnerable: JPQL is parsed too
em.createQuery("select u from User u where u.email = '" + email + "'", User.class);
// safe
em.createQuery("select u from User u where u.email = :email", User.class).setParameter("email", email);
```

Spring Data derived queries and `@Query` with `:param` are parameterised. Two holes remain. **Identifiers cannot be
parameters**: a `?sort=` column name must be checked against an allowlist before it goes into `ORDER BY`. And
**log injection**: logging `"login failed user=" + username` with a username containing a newline lets an attacker
forge a fake log line. Strip CR/LF from untrusted values or use structured (JSON) logging. Log4Shell (CVE-2021-44228)
was this class of bug at its worst: Log4j 2 interpreted `${jndi:...}` inside logged strings.

## Insecure deserialization

**Deserialization** turns bytes back into objects (JAVA-FUND-8). Java native serialization (`ObjectInputStream`)
lets the *byte stream* choose which classes to instantiate, and some library classes run code while being
deserialized; chains of these ("gadgets") have turned `readObject()` on untrusted bytes into remote code execution.
Never deserialize untrusted data that way; if a legacy protocol forces it, allowlist classes with `ObjectInputFilter`.

Jackson is safe by default because *your* code names the target class. It stops being safe when the JSON may name
the class: `ObjectMapper.activateDefaultTyping(...)` or
`@JsonTypeInfo(use = JsonTypeInfo.Id.CLASS)` on a broad type like `Object`. For polymorphism use
`JsonTypeInfo.Id.NAME` with an explicit `@JsonSubTypes` list.

## SSRF: your server as the attacker's proxy

**SSRF** (server-side request forgery) is making your server send a request the attacker chose. Webhooks, "import
from URL" and link previews all fetch user-given URLs, from *inside* your network, where `localhost` admin ports,
internal services and the cloud metadata endpoint (`169.254.169.254`) are reachable.

```java
static void checkTarget(URI uri) throws UnknownHostException {
    if (!"https".equals(uri.getScheme()) || uri.getHost() == null) throw new IllegalArgumentException("bad URL");
    for (InetAddress a : InetAddress.getAllByName(uri.getHost())) {
        if (a.isLoopbackAddress() || a.isSiteLocalAddress() || a.isLinkLocalAddress() || a.isAnyLocalAddress()) {
            throw new IllegalArgumentException("internal address");
        }
    }
}
```

Necessary, not sufficient: disable redirects (`HttpClient.Redirect.NEVER`), connect to the IP you validated (DNS can
answer differently the second time: **DNS rebinding**), and remember `isSiteLocalAddress` misses IPv6 unique-local
addresses. A domain allowlist beats any blocklist. On AWS, requiring IMDSv2 removes the easiest payoff.

## Security misconfiguration

Most of these are one line in `application.yml`:

- **Actuator.** Spring Boot exposes only `health` over HTTP by default. Teams add `include: "*"` while debugging;
  then `/actuator/heapdump` hands out a memory dump with secrets and user data, and `/actuator/env` lists
  configuration. Expose only what you need, on a separate management port, behind authentication.
- **Stack traces.** `server.error.include-stacktrace` defaults to `never`. Setting it to `always`, or returning
  `e.getMessage()` from a `@ControllerAdvice`, tells attackers your libraries and SQL.
- **CORS `*`.** As WEB-API-1 showed, CORS is not access control; but `allowedOriginPatterns("*")` with
  `allowCredentials(true)` lets any website make credentialed calls with your users' cookies. List exact origins.

## Vulnerable dependencies

A Spring Boot jar carries many transitive libraries, and a CVE in any of them is your CVE. Scan in CI: **OWASP
Dependency-Check** (`dependency-check-maven`, with `failBuildOnCVSS` to fail above a severity score) checks your
dependency tree against the NVD vulnerability database; **Dependabot** (or Renovate) opens upgrade PRs. Boot's
dependency management moves most transitive versions together, so staying on a supported Boot line is itself a
security control.

## XSS and CSRF: browser attacks, backend decisions

**XSS** (cross-site scripting) is injection into HTML: a stored comment containing `<script>` runs in every reader's
browser, with their session. For a JSON API your part is: return `Content-Type: application/json`, keep
`X-Content-Type-Options: nosniff`, never build HTML by concatenation (Thymeleaf's `th:text` escapes, `th:utext`
does not), and send a Content-Security-Policy where you serve pages.

**CSRF** (cross-site request forgery) tricks a logged-in browser into sending a request to your site; the browser
attaches cookies automatically. So CSRF matters exactly when **credentials ride in cookies** (session login, a BFF
with a session cookie). Keep Spring's CSRF protection on there; for a SPA use
`csrf.csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())` so the JavaScript can echo the token in a
header. An API that only accepts `Authorization: Bearer` from JavaScript is not exposed, because a forged
cross-site request cannot attach that header; that is why SPRING-BOOT-9 disabled CSRF. `SameSite` cookies help but are
defence in depth, not a replacement.

## Password storage: slow on purpose

If you store passwords (rather than delegating to an identity provider), store a **hash**, never the password or a
reversible encryption. But not SHA-256: it is designed to be *fast*, and fast is what an attacker with a GPU and a
leaked table wants. Unsalted, identical passwords also produce identical hashes, so one precomputed table cracks
every copy.

A password hash needs three properties:

1. **Salt**: random bytes per user, stored next to the hash, so equal passwords hash differently.
2. **Work factor**: a tunable cost (bcrypt's strength, Argon2's memory and iterations) you raise as hardware improves.
3. **Constant-time comparison** when verifying.

Spring gives you all three:

```java
@Bean
PasswordEncoder passwordEncoder() {
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();   // bcrypt by default
}
// stored: {bcrypt}$2a$10$<22-char salt><hash>
boolean ok = passwordEncoder.matches(rawPassword, storedHash);
```

`BCryptPasswordEncoder` generates the salt and embeds it, with the cost (`$10$`, the default strength) in the
string. The `{bcrypt}` prefix is the **DelegatingPasswordEncoder**'s trick: each stored hash names its algorithm, so you
can switch new hashes to `{argon2}` (`Argon2PasswordEncoder`, needs Bouncy Castle) while old ones still verify, and
re-hash on the next successful login (`UserDetailsPasswordService`). Argon2id is the current OWASP first choice;
bcrypt remains acceptable. Note bcrypt only uses the first 72 bytes of input.

## Secrets: out of git, out of logs, rotatable

A **secret** is any credential: DB password, API key, JWT signing key, TLS private key. The levels:

- **In `application.yml` in git**: wrong. History keeps it after deletion; a leaked secret must be **rotated**.
- **Environment variables** (`password: ${DB_PASSWORD}`): out of the repo and fine for small setups, but visible to
  anyone who can inspect the process or container definition, and leaked by an open `/actuator/env` or crash dumps.
- **A secret manager** (AWS Secrets Manager, GCP Secret Manager, HashiCorp Vault): IAM-controlled, audited,
  versioned, rotatable. Spring loads them via `spring.config.import` (`aws-secretsmanager:` with Spring Cloud AWS,
  `vault://` with Spring Cloud Vault).

Add a secret scanner (gitleaks, GitHub secret scanning) to CI, and design for rotation: support two valid keys at once
(the JWKS `kid` from SPRING-BOOT-10 is exactly this for signing keys).

## TLS and mTLS between services

WEB-API-1 covered the TLS handshake. Two backend decisions remain. First, **where TLS ends**: often at the load
balancer, which means traffic inside the network is plain HTTP unless you re-encrypt. "Internal network is trusted"
is the assumption SSRF and a single compromised pod break. Second, **mutual TLS**: the client also presents a
certificate, so service B knows the caller *is* service A at the transport layer. In Spring Boot 3.1+ you define an
SSL bundle with a keystore (your certificate) and a truststore (the CA that signs client certificates), then set
`server.ssl.bundle` and `server.ssl.client-auth: need`. Often a service mesh (Istio, Linkerd) handles mTLS and
certificate rotation instead. mTLS authenticates the *service*; you still need tokens (client credentials,
SPRING-BOOT-10) for *authorization*.

## Rate limiting and security headers

Login, OTP verification and password reset must be rate-limited, or a 6-digit OTP falls to brute force. Limit per
account *and* per IP, return **429** with `Retry-After`, and prefer increasing delays over hard lockout (lockout lets
an attacker lock out any user). Bucket4j or the gateway can enforce it; the algorithms are in DIST-SYS-3.

Spring Security already sends useful headers: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
`Cache-Control: no-cache, no-store`, and HSTS on HTTPS requests. Add a CSP where you serve HTML:

```java
http.headers(h -> h
        .contentSecurityPolicy(csp -> csp.policyDirectives("default-src 'self'"))
        .httpStrictTransportSecurity(hsts -> hsts.includeSubDomains(true).maxAgeInSeconds(31536000)));
```

## Lab (~10 min)

Plain JDK, no Spring. Save as `SecurityLab.java`, run `java SecurityLab.java`. It shows injection, IDOR, log
injection and password hashing side by side. PBKDF2 stands in for bcrypt here only because it ships with the JDK;
the salt and work-factor ideas are the same.

```java
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.SecureRandom;
import java.util.HexFormat;
import java.util.List;
import java.util.Map;
import javax.crypto.SecretKeyFactory;
import javax.crypto.spec.PBEKeySpec;

public class SecurityLab {
    record BoundQuery(String sql, List<Object> params) { }      // what a PreparedStatement keeps apart
    record Order(long id, String ownerId, int total) { }

    static final Map<Long, Order> ORDERS = Map.of(1L, new Order(1, "alice", 499), 2L, new Order(2, "bob", 1299));

    static String unsafeQuery(String email) {
        return "SELECT id, email FROM users WHERE email = '" + email + "'";
    }

    static BoundQuery safeQuery(String email) {
        return new BoundQuery("SELECT id, email FROM users WHERE email = ?", List.of(email));
    }

    static Order getOrderUnsafe(String callerId, long orderId) {
        return ORDERS.get(orderId);                               // trusts the id from the URL
    }

    static Order getOrderSafe(String callerId, long orderId) {
        Order order = ORDERS.get(orderId);
        if (order == null || !order.ownerId().equals(callerId)) {
            throw new IllegalStateException("404 not found");     // same answer for missing and not-yours
        }
        return order;
    }

    static String forLog(String untrusted) {
        return untrusted.replaceAll("[\\r\\n]", "_");
    }

    static String sha256(String password) throws Exception {
        return HexFormat.of().formatHex(
                MessageDigest.getInstance("SHA-256").digest(password.getBytes(StandardCharsets.UTF_8)));
    }

    static byte[] pbkdf2(String password, byte[] salt, int iterations) throws Exception {
        PBEKeySpec spec = new PBEKeySpec(password.toCharArray(), salt, iterations, 256);
        try {
            return SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256").generateSecret(spec).getEncoded();
        } finally {
            spec.clearPassword();
        }
    }

    public static void main(String[] args) throws Exception {
        System.out.println(unsafeQuery("alice@example.com"));
        System.out.println(unsafeQuery("x' OR '1'='1"));         // WHERE is now always true
        System.out.println(safeQuery("x' OR '1'='1"));           // just a strange email value

        System.out.println("unsafe, alice reads order 2: " + getOrderUnsafe("alice", 2));
        try {
            getOrderSafe("alice", 2);
        } catch (IllegalStateException e) {
            System.out.println("safe, alice reads order 2: " + e.getMessage());
        }

        String user = "bob\nINFO login succeeded user=admin";
        System.out.println("raw:   login failed user=" + user);
        System.out.println("clean: login failed user=" + forLog(user));

        System.out.println("sha256: " + sha256("Summer2024!"));
        System.out.println("sha256: " + sha256("Summer2024!") + "  <- identical");
        SecureRandom random = new SecureRandom();
        byte[] salt = new byte[16];
        for (int i = 0; i < 2; i++) {
            random.nextBytes(salt);
            long start = System.nanoTime();
            byte[] hash = pbkdf2("Summer2024!", salt, 600_000);
            System.out.printf("pbkdf2: %s  %d ms%n", HexFormat.of().formatHex(hash).substring(0, 24),
                    (System.nanoTime() - start) / 1_000_000);
        }
        byte[] stored = pbkdf2("Summer2024!", salt, 600_000);
        System.out.println("right password: " + MessageDigest.isEqual(stored, pbkdf2("Summer2024!", salt, 600_000)));
        System.out.println("wrong password: " + MessageDigest.isEqual(stored, pbkdf2("summer2024!", salt, 600_000)));
    }
}
```

**Observe:** the second unsafe `WHERE` is always true, while the bound version keeps the attack as a value; Alice
gets Bob's order from the unsafe lookup; the raw log shows a forged line; the SHA-256 hashes are identical and
instant, while the PBKDF2 hashes differ (different salts) and each takes a noticeable fraction of a second. 600,000
iterations is the OWASP Password Storage Cheat Sheet's figure for PBKDF2-HMAC-SHA256 at the time of writing.

**Break it:** reuse one fixed salt for both PBKDF2 runs and watch the hashes become identical. Change `MessageDigest.isEqual` to
`Arrays.equals` and ask why the original matters (an early-exit comparison leaks timing).

## Gotchas

- **Checking ownership in the controller only.** Another endpoint or a batch job reuses the service and skips the
  check. Scope the repository query by owner, or put `@PreAuthorize` on the service.
- **Parameterising values but concatenating `ORDER BY`.** Column names cannot be bound; map user input to an
  allowlist of known columns.
- **`management.endpoints.web.exposure.include: "*"` in production.** Heap dumps contain secrets. Expose `health`
  and the few you need, on a separate port, authenticated.
- **Disabling CSRF because "we use JWT" while the JWT sits in a cookie.** The browser still sends it automatically;
  CSRF protection must stay on.
- **Removing a committed secret with a new commit.** History still has it. Rotate the secret first, then clean up.

## In interviews

Asked as "What is the OWASP Top 10? Which have you dealt with?", "How do you prevent SQL injection in JPA?", "How do
you store passwords?", "When do you need CSRF protection?", "How do you manage secrets in a Spring Boot service?",
"How do two services trust each other?". Bank: [Preventing SQL Injection](#/q/sql-injection-prevention),
[OAuth and JWT tokens](#/q/oauth-and-jwt), [Design a Rate Limiter](#/q/design-rate-limiter) (login brute force is
the motivating case).

A strong answer has four layers (example: "How do you store passwords?"):

1. **What:** a slow, salted, adaptive one-way hash; never plain text, encryption or SHA-256.
2. **How inside:** per-user random salt embedded in the hash string, a tunable work factor, constant-time compare;
   `DelegatingPasswordEncoder` prefixes the algorithm id so you can migrate.
3. **Where used:** the user store behind form login; often avoided entirely by delegating to an identity provider.
4. **What goes wrong:** fast hashes cracked offline after a breach, a work factor never raised, bcrypt's 72-byte
   limit, and no rate limit on the login endpoint.

**Follow-up: "Your API uses UUIDs, so IDOR is solved?"** No. UUIDs only make ids hard to guess; ids leak through
URLs, logs and shared links. Authorization must check ownership on every access.

## Explain it in 2 minutes

*"How do you secure a Spring Boot REST API beyond authentication?"*

- Authorization on every object: owner-scoped queries or `@PreAuthorize`, 404 for not-yours (IDOR, A01).
- No string-built SQL/JPQL; parameters everywhere, allowlists for identifiers; CR/LF stripped from logs (A03).
- Passwords via `PasswordEncoder` (bcrypt/Argon2); secrets in a secret manager, rotatable, never in git (A02).
- Safe config: Actuator locked down, no stack traces, exact CORS origins, CSRF on whenever cookies carry auth (A05).
- No native deserialization of untrusted data, no Jackson default typing; SSRF guards on any URL fetch (A08, A10).
- Dependency scanning in CI, TLS everywhere (mTLS inside), rate limits on login and OTP, security headers.

## Check yourself

1. Why is `findByIdAndOwnerId` better than loading by id and then checking the owner in the controller?
2. Your JPA code uses `:email` parameters, yet a pentest finds injection in the list endpoint. Where do you look?
3. Why is salted SHA-256 still a poor password hash?
4. Your SPA calls the API with `Authorization: Bearer` from memory. Do you need CSRF protection? What if the token
   moves to an `HttpOnly` cookie?
5. A webhook feature checks that the URL is not `localhost`. Name two ways an attacker still reaches internal
   services.

### Answers

1. The check cannot be forgotten by another caller of the repository, and data the caller may not see is never
   loaded. Not-found and not-yours become the same 404.
2. Anything concatenated: a sort or filter column in `ORDER BY`, a native query built with `+`, or a
   `createQuery` string with user input. Identifiers need an allowlist.
3. Salt defeats precomputed tables, but SHA-256 is fast, so an attacker can still try enormous numbers of guesses per
   second against each leaked hash. A password hash must be deliberately slow and tunable.
4. No for the header: a cross-site request cannot attach it. Yes for the cookie: the browser sends it automatically,
   so turn CSRF protection back on.
5. Another internal address (`169.254.169.254`, `10.x`, `127.0.0.2`, IPv6 forms), a public hostname whose DNS points
   to an internal IP (or changes between check and fetch), or an allowed URL that redirects inside.
