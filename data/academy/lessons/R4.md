## Where we are

You have now met most backend tools one lesson at a time, ending with Terraform in DIST-SYS-11. This
page puts them side by side: what each is for, why teams pick it, what it costs you, and what it competes
with. It is a map to come back to, not a lesson to read top to bottom.

## How to use this page

- **Before an interview:** skim the groups for the job description's stack. For each tool listed, make
  sure you can say its job in one phrase and name one alternative and one trade-off.
- **When a tool comes up you do not know:** find its group. Knowing which tool it replaces gets you most
  of the way ("Micronaut, so a Spring Boot alternative").
- **The Lesson column** gives the display code where the Academy covers the tool. A dash means it is not
  covered in depth; the row is enough for an interview mention.


## How to talk about tools in interviews

Interviewers rarely care that you know a tool's name. They care whether you choose tools for reasons.
Three habits:

1. **Choose by problem, not by fashion.** Start with the need: "we needed replay and per-key ordering
   across consumers", then the tool: "so Kafka, not RabbitMQ". If the need was simple work hand-off, say
   so and pick the simpler tool.
2. **Name the trade-off.** Every tool on this page has a Cost column for a reason. "Testcontainers made
   our tests trustworthy, at the price of slower CI and Docker on the build agents." A trade-off said out
   loud is what separates a senior answer from a list.
3. **Say what you used and why, honestly.** "At work I use Selenium for older flows and Playwright for new
   ones, because auto-waiting cut our flaky failures" is stronger than claiming every tool. If you have
   only read about one, say that and describe how you would evaluate it.

A useful sentence shape: *"For <problem> we used <tool> because <benefit>; the cost was <watch-out>,
which we handled by <mitigation>. If <condition changed>, I would look at <alternative>."*

## Check yourself

1. A team needs per-customer event ordering and the ability to replay a week of events. Kafka or
   RabbitMQ, and why?
2. Name one benefit and one cost of Testcontainers compared with H2 for repository tests.
3. When would you pick CloudFormation over Terraform?
4. Micrometer, Prometheus and Grafana: what does each one do in the chain?
5. Selenium or Playwright for a new browser automation flow, and what is the main reason?

### Answers

1. Kafka: a partition keyed by customer keeps that customer's order, and retention allows replay.
   RabbitMQ classic queues delete messages on ack; RabbitMQ Streams (3.9+) add an append-only log with
   replay, but Kafka's partitioned log is the usual choice for keyed ordering plus replay at scale.
2. Benefit: tests run against the real database engine, so SQL dialect and behaviour match production.
   Cost: slower tests and Docker required in CI.
3. When the team is AWS-only and wants AWS to manage state, or already uses CDK and CloudFormation.
4. Micrometer records metrics in the app; Prometheus scrapes and stores them and evaluates alerts;
   Grafana draws dashboards over them.
5. Usually Playwright: built-in auto-waiting and tracing reduce flaky failures. Selenium still makes
   sense where its ecosystem or an existing suite already exists.
