## Where we are

You've followed backend from CGI scripts to AI-native systems. Each era fixed the last era's pain
and created a new one: threads fixed process cost, Spring fixed EJB weight, services fixed team
coupling, modular monoliths fixed accidental complexity, virtual threads fixed reactive's
readability, and LLMs brought non-determinism into the request path (S12). This last lesson does
two things: it looks ahead (as **opinion**, clearly marked), and it gives you a sustainable way to
keep up after the course ends.

## The problem

Two problems, really:

1. **The future is uncertain.** Nobody knows which of today's ideas will matter in five years. In
   2014 many people expected every company to run hundreds of microservices; by 2023 some were
   merging them back (S10).
2. **The firehose.** Every week brings new frameworks, JDK features, AI models and "X is dead"
   posts. With 25 minutes a day, you can't follow it all, and trying leads to burnout.

The answer to both is the same skill this track has been training: **ask what pain a thing solves,
and what new pain it creates.**

## Facts first: what is already shipping

Before the opinions, things that exist today, so you can tell the two apart.

- **Java 25** (September 2025) is the current long-term-support release after Java 21.
- **Faster JVM start-up.** *Project Leyden* is moving work from run time to an earlier training
  run: Java 24 added an ahead-of-time class loading and linking cache (JEP 483), and Java 25
  extended it. *CRaC* (Coordinated Restore at Checkpoint) is a separate OpenJDK project that
  snapshots a warmed-up JVM and restores it; Spring Boot has supported it since 3.2. *GraalVM
  Native Image* compiles a Spring Boot app ahead of time into a native executable.
- **Project Valhalla** is working on value classes: objects without identity that the JVM can
  store flat, like primitives. Early-access builds exist; check the OpenJDK site for status.
- **Virtual threads** are final (Java 21), with `synchronized` pinning fixed in Java 24.
  *Structured concurrency* (treating a group of related tasks as one unit) is still a preview API
  as of Java 25.
- **MCP** (2024) is an open standard for connecting AI applications to tools and data.
- **WebAssembly (Wasm)**: a portable binary format first built for browsers, now also run on
  servers through WASI, its system interface.

## Opinion: where backend is heading

*Everything in this section is the author's opinion, not established fact. Hold it loosely and
argue with it.*

**1. Agentic systems become ordinary backend work.** Agents (S12) will look less like magic and
more like workflow engines with a non-deterministic step: queues, retries, timeouts, idempotent
tool calls, audit logs, human approval for risky actions. The engineers who do well will be the
ones who already know sagas and outboxes (S8), because an agent's multi-step task *is* a long-running
saga.

**2. Start-up time stops being Java's weak spot.** Serverless and fast autoscaling punished slow
JVM starts (S9). Leyden, CRaC and native images attack this from three directions. My guess: for
most Spring services, a Leyden-style AOT cache becomes the boring default, and native images stay
for cases where start-up and memory dominate.

**3. The architecture pendulum slows down.** After microservices and the modular-monolith
correction, I expect less fashion and more fit: modular monolith by default, services where there
is a measured reason. The interesting work moves to platform engineering: internal platforms that
make the right thing (tracing, safe deploys, secrets) the default for every team.

**4. Valhalla changes performance advice, slowly.** When value classes land, some of today's
memory tips (avoid boxing, avoid small wrapper objects) will change. Expect years, not months,
before libraries catch up.

**5. Wasm on the server stays niche for Java teams** for a while: useful for plugins and sandboxed
user code, less so for ordinary services.

**6. Judgement beats frameworks.** Code generation by AI makes *writing* code cheaper. Deciding
*what* to build, where the boundaries go, and what can fail becomes a larger share of the job. That
is what this whole track has been practising.

Notice the pattern in all six: each prediction is just "pain → invention → new pain" projected
forward. That is the reusable skill; the specific guesses may be wrong.

## How to evaluate anything new

When a new tool or idea appears, ask five questions before spending an evening on it:

1. **What pain does it solve?** Do I have that pain now?
2. **What does it cost?** New failure modes, operations, learning, lock-in.
3. **What did it replace, and why did that fall short?** (The story lens.)
4. **Who runs it in production, and what do their post-mortems say?**
5. **Is it stable?** Preview APIs, 0.x versions and launch-week blog posts can wait.

If the answers are "no", "a lot", or "not yet", write one line in a *later* list and move on.

## How to keep up without burning out

This is the practical part. It's built for a tight schedule like yours.

**A fixed budget, not a feed.** Give "keeping up" one 30-minute slot a week. When the slot ends,
stop. News that matters will still matter next week; most news won't matter at all.

**Pull, don't push.** Unsubscribe from anything that sends you a daily stream. Instead, check a few
primary sources on your weekly slot:

- JDK release notes and JEP pages (twice a year, at each Java release),
- the Spring blog's release announcements,
- engineering blogs of companies you respect, and their post-mortems,
- one curated newsletter at most.

**Learn just in time, mostly.** Keep a short "later" list. Deep-dive a topic when a project,
an interview or a real problem needs it; that's when it sticks. Allow yourself one *just-in-case*
topic per quarter, chosen deliberately.

**Read originals, not summaries.** This track's cases were all named so you can find the original
post or paper. A summary loses the conditions that made the decision right.

**Turn reading into a review card.** After anything worth remembering, write one question and a
two-line answer. Spaced review (which this app does) beats rereading.

**Build tiny.** A 50-line lab teaches more than five articles. Every era in this track had one.

**Read one post-mortem a month.** Incidents (Knight Capital, the 2017 S3 outage, CrowdStrike) teach
trade-offs faster than success stories, because the trade-off was paid for.

**Permission to skip.** You don't need an opinion on every launch. "I haven't looked at that yet;
here's how I'd evaluate it" is a strong interview answer and a healthy habit.

**Watch for burnout signals:** reading feels like obligation, you skim without retaining, or you
feel behind no matter what. When that happens, cut the budget in half for a month. The basics in
this track change slowly; you won't fall behind on them.

## Lab (~10 min)

**Design exercise: your personal radar and one decision record.**

1. **Radar (5 min).** Draw four rings: *Adopt* (use by default), *Trial* (use on a real but
   low-risk project), *Assess* (read and build a tiny lab), *Hold* (not now). This is the shape
   Thoughtworks uses for its public Technology Radar. Place at least eight items, for example:
   virtual threads, Spring Modulith, Kafka, Kubernetes, GraalVM native image, CRaC, MCP, RAG with
   pgvector, reactive WebFlux, service mesh. For each, write one line: *the pain it would solve for
   me*.
2. **Decision record (5 min).** Pick one item from *Trial* and write a half-page record for
   ShopKart:

```text
Title:     Adopt <X> for <where>
Context:   the pain today, with a number if you have one
Decision:  what we will do, and the smallest first step
Costs:     new failure modes, ops work, learning, lock-in
Exit:      how we'd notice it's not working, and how we'd back out
Revisit:   date
```

The *Exit* line is the one most people skip, and the one that makes a decision safe.

## Gotchas

- **Presenting opinions as facts.** In interviews and design docs, label predictions as opinions
  and give your reasoning. It reads as maturity, not weakness.
- **Adopting on launch week.** Early versions change. Wait for production reports unless the pain
  is acute.
- **Learning "just in case" without limit.** It feels productive and rarely sticks. Cap it.
- **Reading summaries of case studies.** Details matter; a headline like "X went back to a monolith"
  often hides a narrow, specific workload.
- **No exit plan.** Every adoption decision should say how you'd back out.

## In interviews

Forward-looking questions are usually behavioural or open-ended:

- [How are AI tools helping you?](#/q/how-you-use-ai-tools): give a specific, honest example
  including a limitation.
- [An innovative idea you implemented](#/q/innovation-you-drove): show the evaluation process (pain,
  cost, small trial, result), not just the shiny tool.
- [Delivering with little guidance](#/q/delivering-with-little-guidance): learning a new area fast
  and safely is the same skill as this lesson.
- [Why are you looking for a change?](#/q/why-are-you-looking-for-a-change): a good place to show
  curiosity grounded in real problems.

Typical follow-ups:

- *"What technology are you excited about, and would you use it in production?"* Strong answer:
  name it, state the pain it solves, the risk, and a small first step with an exit plan.
- *"How do you stay current?"* Strong answer: a concrete routine (primary sources, small labs,
  post-mortems) rather than "I read a lot of blogs".

## Explain it in 2 minutes

**Prompt:** "Where do you think backend engineering is heading, and how do you stay current?"

1. Frame with the pattern: each era solves a pain and creates a new one.
2. Separate facts (Java 25, Leyden/CRaC, virtual threads, MCP) from opinions, and say which is which.
3. One or two reasoned predictions (agents as workflows needing saga discipline; JVM start-up).
4. How you evaluate new things: pain, cost, maturity, exit plan.
5. Your routine: fixed weekly budget, primary sources, tiny labs, post-mortems, review cards.

2. Why might an AI agent's multi-step task need the same tools as a saga?
3. What are the five questions to ask about a new technology?
4. What does the *Exit* line of a decision record contain, and why does it matter?

### Answers

1. Any two of: Project Leyden's AOT cache (Java 24+), CRaC checkpoint/restore, GraalVM Native Image.
2. It performs several steps against external systems that can fail midway, so it needs
   compensations, idempotent steps, retries with limits and an audit trail.
3. What pain does it solve; what does it cost; what did it replace and why; who runs it and what do
   their post-mortems say; is it stable.
4. How you'll notice the decision isn't working and how you'll back out; it keeps a reversible
   decision reversible and makes trials safe.
5. Reading feels like an obligation; you skim without retaining; you feel behind no matter how
   much you read.
