## Where we are

You can write plain Java classes, give them constructors and call methods on them. That is all
this lesson assumes. Today you build, in about 150 lines, the core idea behind Spring: a
**container** that creates your objects and connects them for you. Once you have written one,
Spring stops being magic. It becomes a much bigger version of something you already understand.

## The problem

Here is a tiny greeting app with three classes, each one needing the one below it:

```java
var repo       = new InMemoryGreetingRepository();
var service    = new GreetingService(repo);
var controller = new GreetingController(service);
controller.handle("Akhil");
```

A **dependency** is an object another object needs to do its job. `GreetingService` depends on
a repository, and `GreetingController` depends on the service.

With three classes, wiring them by hand is fine. A real app has hundreds, and hand wiring
starts to hurt in four ways:

- **Order.** You must create the dependencies before the objects that need them, and you have
  to work that order out yourself.
- **Sharing.** If ten services need the same repository, you have to pass the same instance to
  all ten, and nothing stops someone from calling `new` on a second one.
- **Swapping.** Moving from the in-memory repository to a database means editing the wiring
  code by hand.
- **Repetition.** Each new class means another hand edit to `main`.

We will fix these one at a time.

## Step 1: let objects receive their dependencies

The first fix is a habit, not a tool. A class should **receive** what it needs through its
constructor instead of calling `new` itself:

```java
class GreetingService {
    private final GreetingRepository repo;
    GreetingService(GreetingRepository repo) { this.repo = repo; }   // given, not built
}
```

This is **dependency injection (DI)**: someone outside the class hands it its dependencies.
The class only knows the *interface* `GreetingRepository`, so you can pass in any
implementation, including a fake one in a test.

The rule: **classes declare what they need, and something else decides what they get.** That
"something else" is still `main`, though. Next we move it out of `main`.

## Step 2: a registry

A **registry** is a map from a type to the object that serves it:

```java
Map<Class<?>, Object> registry = new HashMap<>();
registry.put(GreetingRepository.class, new InMemoryGreetingRepository());
registry.put(GreetingService.class,
        new GreetingService((GreetingRepository) registry.get(GreetingRepository.class)));
```

`GreetingRepository.class` is a **`Class` object**, Java's runtime description of a type. Every
class has exactly one, and you can use it as a map key.

This fixes sharing: everyone who asks for `GreetingService` gets the same instance. You still
have to write each line and get the order right, though. To automate that, the code needs to
look at classes while the program runs. That is what reflection is for.

## Step 3: a little reflection

**Reflection** is Java's API for inspecting and using classes at runtime: listing their
constructors, reading their annotations and creating instances without writing `new`.

```java
Class<?> type = GreetingService.class;
Constructor<?> ctor = type.getDeclaredConstructors()[0];
Class<?>[] needs = ctor.getParameterTypes();   // [GreetingRepository.class]
Object service = ctor.newInstance(repo);       // same as: new GreetingService(repo)
```

With this, a program can find out what a constructor needs, go and get it, and call the
constructor. That is all a DI container does.

## Step 4: mark the classes with an annotation

An **annotation** is a label such as `@Component` that you attach to a class. On its own it does
nothing, but code can read it through reflection. It survives to runtime only if it is declared
with `@Retention(RUNTIME)`.

```java
@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.TYPE)
@interface Component {}

@Component class GreetingService { ... }
```

The container's rule is "manage every class labelled `@Component`, and ignore the rest". Your
code now says *what* the parts are. The container works out *how* to connect them.

## Step 5: constructor injection, recursively

To build a class, the container finds its constructor and asks itself for each parameter type.
Building those parameters may mean building *their* dependencies first, so it calls itself
recursively. The right creation order falls out of this on its own, so you never have to write
it down.

If a parameter is an interface, the container looks for the single `@Component` class that
implements it. If there are none, or more than one, it fails with a clear message.

## Step 6: singletons and cycle detection

A **singleton** here means "one instance per container". The container caches each object the
first time it creates it and returns that same instance afterwards. If a class wants a new
instance on every request, it can opt out with a second annotation.

There is one trap to handle. If A needs B and B needs A, the recursion never ends. The container
keeps a set of the classes it is "currently creating", and if it is asked for one of those
again, it reports the cycle instead of overflowing the stack.

## The whole container

Save this as `MiniDi.java` and run it with `java MiniDi.java`. Java 21 runs a single source file
directly.

```java
import java.lang.annotation.*;
import java.lang.reflect.Constructor;
import java.util.*;

// In single-file mode, the class with main() must be the first type in the file.
public class MiniDi {
    public static void main(String[] args) {
        var container = new Container(InMemoryGreetingRepository.class, GreetingService.class,
                GreetingController.class, RequestId.class, NotAComponent.class);
        container.start();

        GreetingController c1 = container.getBean(GreetingController.class);
        GreetingController c2 = container.getBean(GreetingController.class);
        System.out.println(c1.handle("Akhil"));
        System.out.println("same controller? " + (c1 == c2));
        System.out.println("same RequestId?  "
                + (container.getBean(RequestId.class) == container.getBean(RequestId.class)));
    }
}

@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.TYPE) @interface Component {}
@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.TYPE) @interface Prototype {}

class Container {
    private final List<Class<?>> components = new ArrayList<>();
    private final Map<Class<?>, Object> singletons = new HashMap<>();
    private final Set<Class<?>> inCreation = new HashSet<>();

    Container(Class<?>... candidates) {
        for (Class<?> c : candidates) {
            if (c.isAnnotationPresent(Component.class)) components.add(c);
        }
        System.out.println("components: " + components.stream().map(Class::getSimpleName).toList());
    }

    /** Create every singleton now, so wiring errors appear at start-up, not on first use. */
    void start() {
        for (Class<?> c : components) {
            if (!c.isAnnotationPresent(Prototype.class)) getBean(c);
        }
    }

    <T> T getBean(Class<T> type) {
        Class<?> impl = implementationOf(type);
        boolean singleton = !impl.isAnnotationPresent(Prototype.class);
        if (singleton && singletons.containsKey(impl)) {
            return type.cast(singletons.get(impl));
        }
        Object bean = create(impl);
        if (singleton) singletons.put(impl, bean);
        return type.cast(bean);
    }

    private Class<?> implementationOf(Class<?> type) {
        List<Class<?>> matches = components.stream().filter(type::isAssignableFrom).toList();
        if (matches.isEmpty()) {
            throw new IllegalStateException("No component of type " + type.getSimpleName());
        }
        if (matches.size() > 1) {
            throw new IllegalStateException("More than one " + type.getSimpleName() + ": " + matches);
        }
        return matches.get(0);
    }

    private Object create(Class<?> impl) {
        if (!inCreation.add(impl)) {
            throw new IllegalStateException("Circular dependency involving " + impl.getSimpleName());
        }
        try {
            Constructor<?>[] ctors = impl.getDeclaredConstructors();
            if (ctors.length != 1) {
                throw new IllegalStateException(impl.getSimpleName() + " must have exactly one constructor");
            }
            Constructor<?> ctor = ctors[0];
            Class<?>[] needs = ctor.getParameterTypes();
            Object[] args = new Object[needs.length];
            for (int i = 0; i < needs.length; i++) {
                args[i] = getBean(needs[i]);          // recursion builds dependencies first
            }
            ctor.setAccessible(true);
            Object bean = ctor.newInstance(args);
            System.out.println("created " + impl.getSimpleName());
            return bean;
        } catch (ReflectiveOperationException e) {
            throw new IllegalStateException("Cannot create " + impl.getSimpleName(), e);
        } finally {
            inCreation.remove(impl);
        }
    }
}

// ---- the application: it never calls `new` on its collaborators ----

interface GreetingRepository { String template(); }

@Component
class InMemoryGreetingRepository implements GreetingRepository {
    public String template() { return "Hello, %s!"; }
}

@Component
class GreetingService {
    private final GreetingRepository repo;
    GreetingService(GreetingRepository repo) { this.repo = repo; }
    String greet(String name) { return repo.template().formatted(name); }
}

@Component
class GreetingController {
    private final GreetingService service;
    private final RequestId requestId;
    GreetingController(GreetingService service, RequestId requestId) {
        this.service = service;
        this.requestId = requestId;
    }
    String handle(String name) { return "[" + requestId.value + "] " + service.greet(name); }
}

@Component @Prototype
class RequestId {
    final String value = UUID.randomUUID().toString().substring(0, 8);
}

class NotAComponent {}   // no @Component, so the container ignores it
```

Expected output (the ids will differ):

```text
components: [InMemoryGreetingRepository, GreetingService, GreetingController, RequestId]
created InMemoryGreetingRepository
created GreetingService
created RequestId
created GreetingController
[3da61fd6] Hello, Akhil!
same controller? true
created RequestId
created RequestId
same RequestId?  false
```

Notice that you never wrote a creation order. The container worked out "repository, then service, then controller" from the
constructors alone.

## What Spring calls each piece

| Your container | Spring's name |
|---|---|
| `@Component` | `@Component` (and `@Service`, `@Repository` and `@Controller`, which are all marked with it) |
| The `candidates` list | **Component scanning**: Spring finds the classes by scanning packages on the classpath |
| The `components` list | **Bean definitions**: Spring's recipe for each object, kept in a `BeanDefinitionRegistry` |
| A managed object | A **bean** |
| `Container` | The **IoC container**: `BeanFactory` and `ApplicationContext` (D2) |
| `getBean(type)` | `BeanFactory.getBean(Class)` |
| `singletons` map | The singleton cache in `DefaultSingletonBeanRegistry` |
| `@Prototype` | `@Scope("prototype")` |
| One constructor, used automatically | Spring autowires a class's single constructor without needing `@Autowired` |
| "No component of type…" | `NoSuchBeanDefinitionException` |
| "More than one…" | `NoUniqueBeanDefinitionException`, fixed with `@Primary` or `@Qualifier` |
| `inCreation` set | Spring's "currently in creation" tracking, which raises `BeanCurrentlyInCreationException` |
| `start()` | Eager creation of singletons during `ApplicationContext.refresh()` |

**Inversion of Control (IoC)** is the name for what you built: your classes no longer control
how their collaborators are created, because the container does. Real Spring adds a great deal
on top, including configuration, profiles, lifecycle callbacks and proxies. The core loop is the
same, though: read the definitions, resolve the constructor arguments by type, create each
object, and cache it.

## Gotchas

- **Annotations without `@Retention(RUNTIME)` are invisible to reflection.** The default
  retention is `CLASS`, so `isAnnotationPresent` returns false. Spring's own annotations are
  all declared with `RUNTIME`.
- **A singleton is one per container, not one per JVM.** Two containers give you two
  instances. This is different from the GoF Singleton pattern with a static `getInstance()`.
- **A singleton that holds a prototype keeps the same one.** `GreetingController` received one
  `RequestId` when it was built and keeps it for good. Spring has exactly the same trap (D2).
- **Injecting interfaces only works when there is exactly one implementation.** If there are
  two, you must say which one you want.
- **Constructor injection makes a cycle fail fast.** That is a feature: a cycle usually means a
  design problem.

## In interviews

This usually comes up as "What is dependency injection, and why use it?" or "How does Spring
create beans?", and sometimes as "Design a simple DI container".

- [SOLID principles and dependency inversion](#/q/solid-principles): DI is how the "D" in SOLID
  is put into practice.
- [Inheritance vs composition](#/q/inheritance-vs-composition): DI is composition, with the
  wiring done for you.

Typical follow-ups:

- *"Constructor or field injection?"* A strong answer prefers constructor injection: fields can
  be `final`, dependencies are explicit, tests can call `new` with fakes, and a cycle fails at
  start-up.
- *"How does the container know the order?"* It resolves the dependency graph recursively from
  constructor parameters, as you just built. A cycle cannot be ordered, so it fails.

## Explain it in 2 minutes

*"Explain dependency injection and how a container like Spring implements it."*

- Without DI, a class builds its own dependencies with `new`, which hard-codes them and makes
  them hard to test and share.
- With DI, a class declares its dependencies in its constructor and someone else provides them.
- A container automates this. It finds marked classes, reads their constructors with
  reflection, and builds dependencies recursively.
- It caches singletons, so the same instance is shared everywhere.
- It fails clearly when there is no candidate, more than one candidate, or a cycle.
- Spring is this idea plus bean definitions, scopes, lifecycle callbacks and proxies.

### Answers

1. It lets the container discover a class's constructors and parameter types at runtime, read
   annotations, and create instances, without that code knowing the class in advance.
2. To detect circular dependencies. Without it, A → B → A would recurse until a
   `StackOverflowError`.
3. Exactly one: the instance injected when the controller was built.
4. Yours throws an error. Spring uses the constructor marked `@Autowired`. If none is marked, it
   falls back to the no-argument constructor if there is one, and fails if there isn't.
