## Where we are

After CAPSTONE-7 TicketHub expires holds with a batched, multi-instance-safe job and prices seats through strategies. Right now, though, anyone can call any endpoint, and "who is the user" is the `X-User-Id` header, which the caller chooses. This session adds real identity and permissions using SPRING-BOOT-9 (the filter chain and JWT), then switches on virtual threads using JAVA-CONC-6.

## Goal

Turn TicketHub into an OAuth2 **resource server**: an API that does not log anyone in itself, but accepts a signed JWT access token on every request and trusts its claims after checking the signature and expiry. For local development the token is signed with HS256, a shared secret read from an environment variable. In production you would switch to an identity provider's public keys (see Hints).

The rules:

- Anyone may browse events.
- A `USER` can hold, confirm and release seats, and read bookings, **but only their own**. Someone else's hold or booking answers `404`, as if it did not exist.
- An `ADMIN` can also create events.

Then enable virtual threads and learn the one limit they do not remove: the database connection pool.

## What you build

- [ ] Dependencies: `spring-boot-starter-oauth2-resource-server`, plus `spring-security-test` (test scope)
- [ ] `SecurityConfig`: a stateless filter chain, a `JwtDecoder` for HS256 from `TICKETHUB_JWT_SECRET`, a `roles` claim mapped to `ROLE_` authorities, `@EnableMethodSecurity`
- [ ] Controllers take the user id from the token subject (`jwt.getSubject()`), not from a header
- [ ] Ownership enforced in the queries: `findByIdAndUserId…`, so another user's resource is not found and gets `404`
- [ ] `POST /api/v1/events` (admin only): creates the event and its `event_seat` rows
- [ ] `TestJwts`, a token-minting helper in test sources, plus a `DevToken` main for local curl
- [ ] `SecurityIntegrationTest` covering 200 / 401 / 403 / 404
- [ ] `spring.threads.virtual.enabled: true`, a bounded Hikari pool, and notes on pinning

## Steps

**1. The filter chain and decoder (12 min).**

```java
@Configuration
@EnableMethodSecurity
class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        http.csrf(csrf -> csrf.disable())    // no cookies or sessions: the bearer token is the credential, so CSRF does not apply
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers(HttpMethod.POST, "/api/v1/events").hasRole("ADMIN")
                    .requestMatchers(HttpMethod.GET, "/api/v1/events", "/api/v1/events/**").permitAll()
                    .requestMatchers("/actuator/health/**").permitAll()
                    .anyRequest().authenticated())
            .oauth2ResourceServer(rs -> rs.jwt(jwt -> jwt.jwtAuthenticationConverter(rolesConverter())));
        return http.build();
    }

    @Bean
    JwtDecoder jwtDecoder(@Value("${tickethub.security.jwt-secret}") String secret,
                          @Value("${tickethub.security.issuer:tickethub-local}") String issuer) {
        byte[] key = secret.getBytes(StandardCharsets.UTF_8);
        if (key.length < 32) {
            throw new IllegalStateException("tickethub.security.jwt-secret must be at least 32 bytes for HS256");
        }
        NimbusJwtDecoder decoder = NimbusJwtDecoder.withSecretKey(new SecretKeySpec(key, "HmacSHA256"))
                .macAlgorithm(MacAlgorithm.HS256)
                .build();
        decoder.setJwtValidator(JwtValidators.createDefaultWithIssuer(issuer));   // exp/nbf (60 s skew) + iss
        return decoder;
    }

    private static JwtAuthenticationConverter rolesConverter() {
        var roles = new JwtGrantedAuthoritiesConverter();
        roles.setAuthoritiesClaimName("roles");     // {"roles": ["USER"]}  ->  ROLE_USER
        roles.setAuthorityPrefix("ROLE_");
        var converter = new JwtAuthenticationConverter();
        converter.setJwtGrantedAuthoritiesConverter(roles);
        return converter;
    }
}
```

```yaml
tickethub.security:
  jwt-secret: ${TICKETHUB_JWT_SECRET}      # no default: the app refuses to start without it
  issuer: tickethub-local
```

Boot has properties for the public-key forms (`jwk-set-uri`, `public-key-location`) but none for an HMAC secret. That is why you define the `JwtDecoder` bean yourself. Generate a local secret with `openssl rand -base64 48`, put it in your shell profile or IDE run configuration, and never commit it. In `src/test/resources/application.yml`, set a clearly fake test secret of at least 32 characters.

Three details in that chain matter:

- `hasRole("ADMIN")` checks for the authority `ROLE_ADMIN`. That is why the converter adds the prefix.
- The `POST /api/v1/events` matcher is exact, so `POST /api/v1/events/{id}/holds` does not match it. That request falls through to `authenticated()`.
- Admin-only creation is enforced twice, by the URL rule and by `@PreAuthorize` on the service (step 3). If one is removed by mistake, the other still holds. This is defense in depth.

**2. Identity comes from the token (5 min).** In `HoldController` and `BookingController`, replace every `@RequestHeader("X-User-Id") String userId` with the token's subject:

```java
@PostMapping("/events/{eventId}/holds")
ResponseEntity<HoldResponse> create(@PathVariable long eventId,
                                    @RequestHeader("Idempotency-Key") @NotBlank @Size(max = 100) String idempotencyKey,
                                    @AuthenticationPrincipal Jwt jwt,
                                    @Valid @RequestBody HoldRequest request) {
    SeatHold hold = bookingService.hold(eventId, jwt.getSubject(), idempotencyKey, request.seatIds());
    URI location = ServletUriComponentsBuilder.fromCurrentContextPath()
            .path("/api/v1/holds/{id}").buildAndExpand(hold.id()).toUri();
    return ResponseEntity.created(location).body(HoldResponse.from(hold));
}

@PostMapping("/holds/{id}/confirm")
BookingResponse confirm(@PathVariable UUID id, @AuthenticationPrincipal Jwt jwt) {
    return BookingResponse.from(bookingService.confirm(id, jwt.getSubject()));
}
```

`GET /holds/{id}`, `DELETE /holds/{id}`, `GET /bookings/{id}` and `GET /me/bookings` get the same `@AuthenticationPrincipal Jwt jwt` parameter. Their service methods gain a `String userId` argument.

Because `idempotency_key` has been keyed `(user_id, idem_key)` since CAPSTONE-5, bob reusing alice's key cannot replay alice's hold.

**3. Ownership: not found, not forbidden (12 min).** Put the owner into the query itself, so that "load someone else's booking" cannot happen by accident:

```java
// BookingRepository
@EntityGraph(attributePaths = "seatIds")
Optional<BookingEntity> findWithSeatsByIdAndUserId(UUID id, String userId);

// SeatHoldRepository
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select h from SeatHoldEntity h where h.id = :id and h.userId = :userId")
Optional<SeatHoldEntity> findByIdAndUserIdForUpdate(UUID id, String userId);
```

```java
@Transactional(readOnly = true)
public Booking get(UUID bookingId, String userId) {
    return bookings.findWithSeatsByIdAndUserId(bookingId, userId)
            .map(BookingEntity::toDomain)
            .orElseThrow(() -> new BookingNotFoundException(bookingId));     // same 404 as an id that never existed
}
```

`confirm(holdId, userId)` and `release(holdId, userId)` switch from CAPSTONE-7's `findByIdForUpdate` to `findByIdAndUserIdForUpdate`. `findHold(holdId, userId)`, behind `GET /holds/{id}`, uses a plain `findByIdAndUserId`. When nothing is found, throw `HoldNotFoundException`, which gives `404 HOLD_NOT_FOUND`: exactly what an id that never existed returns.

Why `404` and not `403`? A `403` says "this booking exists, but it isn't yours". That confirms the id is real, which is enough to enumerate ids or probe whether someone holds a booking. A `404` gives an attacker nothing. From each user's point of view, other people's bookings really do not exist. GitHub does the same for private repositories you cannot see. The trade-off is that support cannot tell the two cases apart from the response alone. Log the distinction server-side, with ids only. This bug class is called **IDOR** (insecure direct object reference). OWASP's API Top 10 lists it first, as Broken Object Level Authorization.

The admin endpoint lives in `event`, but the `event_seat` rows belong to `booking`, and `event` must not depend on `booking`. CAPSTONE-3 set that direction. So `event` publishes an in-process event, and `booking` reacts to it. A plain `@EventListener` runs synchronously, on the same thread and inside the same transaction. The event and its seat rows therefore commit or roll back together.

```java
package com.tickethub.event;

public record EventCreated(long eventId, long venueId) {}

@Service
public class EventAdminService {
    // constructor-injected EventRepository events, ApplicationEventPublisher publisher

    @PreAuthorize("hasRole('ADMIN')")
    @Transactional
    public Event create(NewEvent cmd) {
        EventEntity saved = events.save(EventEntity.from(cmd));
        publisher.publishEvent(new EventCreated(saved.getId(), cmd.venueId()));
        return saved.toDomain();
    }
}
```

```java
package com.tickethub.booking;

@Component
class SeatInventory {
    private final EventSeatRepository eventSeats;
    SeatInventory(EventSeatRepository eventSeats) { this.eventSeats = eventSeats; }

    @EventListener

// EventSeatRepository
@Modifying
@Query(value = """
        insert into event_seat (event_id, seat_id, status)
```

**4. Minting tokens for tests and curl (8 min).** Put this in `src/test/java/com/tickethub/common/TestJwts.java`:

```java
public final class TestJwts {
    public static final String TEST_SECRET = "test-only-secret-not-used-anywhere-else-32b";

    private TestJwts() {}

    public static String mint(String secret, String subject, Duration ttl, String... roles) {
        var key = new SecretKeySpec(secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256");
        var encoder = new NimbusJwtEncoder(new ImmutableSecret<>(key));
        Instant now = Instant.now();
        JwtClaimsSet claims = JwtClaimsSet.builder()
                .issuer("tickethub-local")
                .subject(subject)
                .issuedAt(now)
                .expiresAt(now.plus(ttl))
                .claim("roles", List.of(roles))
                .build();
        return encoder.encode(JwtEncoderParameters.from(JwsHeader.with(MacAlgorithm.HS256).build(), claims))
                .getTokenValue();
    }

    public static String user(String subject) { return mint(TEST_SECRET, subject, Duration.ofMinutes(5), "USER"); }

    public static String admin(String subject) { return mint(TEST_SECRET, subject, Duration.ofMinutes(5), "USER", "ADMIN"); }
}
```

`TEST_SECRET` must equal the secret in the test `application.yml`. `ImmutableSecret` comes from Nimbus (`com.nimbusds.jose.jwk.source`), which ships with the resource-server starter. For local curl, add a `DevToken` class with a `main` method in test sources. It reads `TICKETHUB_JWT_SECRET` from the environment and prints `TestJwts.mint(secret, args[0], Duration.ofHours(1), roles…)`. It lives in test sources so that no endpoint in the running app ever hands out tokens.

`HoldApiTest` and the other CAPSTONE-4 tests now get `401`. Replace `.header("X-User-Id", "alice")` with `.header("Authorization", "Bearer " + TestJwts.user("alice"))` in their `postHold` helper and its siblings. Nothing else changes. Your CAPSTONE-6 `@WebMvcTest` classes also get `401`. Add `@Import(SecurityConfig.class)` and use `spring-security-test`'s post-processor, `.with(jwt().authorities(new SimpleGrantedAuthority("ROLE_USER")))`. **6. Virtual threads (8 min).**

```yaml
spring:
  threads.virtual.enabled: true     # Java 21+: Tomcat requests, @Async and @Scheduled run on virtual threads
  datasource.hikari:
    maximum-pool-size: 10           # the real concurrency limit; keep it explicit
    connection-timeout: 2000        # fail in 2 s with a clear error instead of queueing for the default 30 s
```

A **virtual thread** is a JVM-managed thread that is not tied to an OS thread. When it blocks on I/O, the JVM unmounts it from its **carrier**, the OS thread underneath, which can then run another virtual thread. Ten thousand blocked requests cost memory, not ten thousand OS threads. What to watch:

- **The connection pool is now the bottleneck.** Tomcat's default 200 platform threads used to throttle traffic for free. With virtual threads, 2,000 concurrent holds means 2,000 threads all asking Hikari for one of 10 connections. Do not "fix" this by raising the pool to 2,000. Each Postgres connection is a server process, and Postgres defaults to 100 connections in total. Keep transactions short, and keep slow calls out of them. The payment call in CAPSTONE-10 goes outside the transaction for exactly this reason.
- **Pinning.** On Java 21, a virtual thread that blocks while inside a `synchronized` block cannot unmount, so it **pins** its carrier, and a few pinned threads can stall the small carrier pool. Prefer `ReentrantLock` in your own code. Detect pinning with the JFR event `jdk.VirtualThreadPinned` (or `-Djdk.tracePinnedThreads=full` on Java 21). Java 24 (JEP 491) removes most `synchronized` pinning. Check library behaviour with JFR rather than assuming it.
- **Not faster for CPU work.** Virtual threads add concurrency for waiting, not speed for computing. Pricing math gains nothing.
- **ThreadLocal.** It still works, and the `SecurityContextHolder` is per request. Never pool virtual threads to reuse ThreadLocal caches, though: they are cheap to create, so create one per task.

## Hints

- **Every request returns 401, even with a token.** The usual causes are an issuer mismatch (`iss` must equal `tickethub.security.issuer`), a secret mismatch between the minter and the app, or the token sent without the `Bearer ` prefix. Set `logging.level.org.springframework.security=DEBUG` and the log names the failing check.
- **`@PreAuthorize` returns 500 instead of 403.** A catch-all `@ExceptionHandler(Exception.class)` in your advice is swallowing `AccessDeniedException`. Map that exception explicitly to `403` before the catch-all.
- **`hasRole('ROLE_ADMIN')` never matches.** `hasRole` adds the prefix itself. Write `hasRole('ADMIN')` or `hasAuthority('ROLE_ADMIN')`.
- **401/403 bodies are empty, not problem details.** They are produced by filters before MVC runs, so your `@RestControllerAdvice` never sees them. That is acceptable for now. The stretch below fixes it.
- **HS256 means anyone with the secret can mint tokens.** That is fine for local development. In production, use an identity provider with RS256/ES256 and `jwk-set-uri`, so the API holds only public keys.

## Stretch

## Talk about it in interviews

**"How does JWT authentication work in your service?"**
1. *What:* a stateless resource server. Every request carries a bearer token, and nothing is stored server-side.
2. *How it works inside:* `BearerTokenAuthenticationFilter` extracts the token. `JwtAuthenticationProvider` asks the `NimbusJwtDecoder` to verify the HS256 signature, `exp`/`nbf` with skew, and `iss`. My converter maps `roles` to `ROLE_*`, the result lands in the `SecurityContextHolder`, and `AuthorizationFilter` plus `@PreAuthorize` decide.
3. *Where it's used:* any API behind an identity provider. Locally I use a shared secret, and in production I would use asymmetric keys from a JWKS endpoint.
4. *What goes wrong:* a weak or committed secret, no issuer or audience check, long-lived tokens with no revocation story, and a catch-all exception handler turning 403 into 500.

**"401 vs 403, and when do you return 404 instead?"** 401 means "I don't know who you are". 403 means "I know who you are, and the answer is no" (a `USER` creating an event). Someone else's booking gets 404 to avoid confirming that it exists (IDOR / BOLA). The check lives in the query, `findByIdAndUserId`, so it cannot be forgotten.

**"Did virtual threads make your service faster?"** The honest answer: they removed the thread-per-request ceiling, not the database ceiling. Explain that throughput is bounded by the Hikari pool and short transactions, that I watch for pinning with JFR, and that CPU-bound work gains nothing.
