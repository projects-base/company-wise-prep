## Where we are

You now know the container (D2), its proxies (D3), auto-configuration (D4), the web layer (D5), transactions (D6) and production tooling (D8). This lesson turns that knowledge into a *habit*: a repeatable five-step way to add any feature to a Spring app without guessing. You will work through one real feature in this repo, then learn to read Spring's own code in a debugger.

## The problem

Without a method, a new feature goes like this. You search the web for "spring cache example", paste in an annotation, see it "work" locally, and ship. In production it serves stale data, or does nothing at all because the method calls itself and bypasses the proxy. Each part was simple. What went wrong was skipping the steps that would have caught these problems.

## The playbook

```text
1. Find the extension point   – where does Spring WANT this kind of code to go?
2. Read the auto-config source – what will Boot build for me, and when does it back off?
3. Write the failing test      – a test that fails for the RIGHT reason
4. Implement                   – the smallest change that makes it pass
5. Observe                     – prove it in a running app: logs, metrics, traces
```

The feature: **`GET /api/questions` re-reads every question and sighting on every page load. The content only changes on `POST /api/admin/reload`. Cache it.**

## Step 1: find the extension point

An **extension point** is a place Spring deliberately leaves open for your code: an interface to implement, an annotation to use, a bean to override. Here are the candidates for this feature:

| Option | Verdict |
|---|---|
| A `volatile List` field in `BankService` | You own thread-safety, eviction and metrics. That means reinventing a cache. |
| HTTP caching (`ETag`) | The server still builds the whole list to compute the tag. |
| Spring's cache abstraction (`@Cacheable`) | Built for this. A proxy around a method stores results in a `CacheManager`. |

How do you find the options in general? Check the reference docs' table of contents (for this feature, "Integration → Cache Abstraction"). Search the "Common Application Properties" appendix for a prefix (here, `spring.cache.*`). Look for an `@EnableXxx` annotation (here, `@EnableCaching`).

Now read the code you are about to change, `BankService.questions()`:

```java
Map<String, ProgressService.View> prog = progress.all();      // changes on every click
return questions.findAllWithSightings().stream()               // changes only on reload
        .map(q -> new QuestionSummary(..., p.done(), p.starred()))
```

**The trap:** this method mixes *content*, which rarely changes, with *progress*, which changes on every click. Put `@Cacheable` on it and the "done" ticks go stale. So the extension point is right, but the **seam** is wrong. A seam is the place where you split code so that one part can change on its own. Here you need a new bean that returns content only, with `BankService` merging fresh progress into it on every call. It must be a *separate bean*, because a `@Cacheable` method called from inside the same class bypasses the proxy (D3).

## Step 2: read the auto-config source

Before adding a starter, read what it will do. In your IDE, press Go to Class, type `CacheAutoConfiguration`, and download the sources. Here is what you find:

- It is conditional on a `CacheAspectSupport` bean being present. That means **nothing happens until you add `@EnableCaching`**.
- It backs off if you define your own `CacheManager`.
- It imports one configuration per cache type and uses the **first one whose library is on the classpath**: JCache, Redis, Caffeine and others, falling back to a simple `ConcurrentHashMap` cache. You can force a choice with `spring.cache.type`.
- The Caffeine variant reads `spring.cache.cache-names` and `spring.cache.caffeine.spec`.

The Actuator documentation adds one more fact: cache metrics are bound only for caches **known at startup**, and Caffeine reports hit and miss counts only if its spec includes `recordStats`.

You can see the same decisions at runtime with `--debug`, or at `/actuator/conditions`. Ten minutes of reading here gave you the three properties you need and two traps to avoid.

## Step 3: write the failing test

```java
@SpringBootTest(properties = "spring.datasource.url=jdbc:h2:mem:cachetest;DB_CLOSE_DELAY=-1")
class QuestionCatalogCacheTest {

    @Autowired BankService bank;
    @Autowired CacheManager caches;
    @Autowired DataImporter importer;
    @Autowired ProgressService progress;

    @Test
    void catalogIsCachedButProgressStaysFresh() {
        bank.questions();
        assertThat(caches.getCache("questionCatalog").get(SimpleKey.EMPTY)).isNotNull();

        progress.apply("lru-cache", ProgressService.Action.DONE, null);
        assertThat(bank.questions())
                .filteredOn(q -> q.slug().equals("lru-cache"))
                .singleElement()
                .extracting(BankService.QuestionSummary::done).isEqualTo(true);
    }

    @Test
    void reloadEvictsTheCatalog() {
        bank.questions();
        importer.importAll();
        assertThat(caches.getCache("questionCatalog").get(SimpleKey.EMPTY)).isNull();
    }
}
```

`SimpleKey.EMPTY` is the key Spring's default key generator uses for a method with no parameters.

Run the test now. It fails with `NoSuchBeanDefinitionException: CacheManager`, which is the *right* reason: caching does not exist yet. If it had failed with a 404 or a typo instead, you would fix the test before going on. The second assertion in the first test guards the progress trap from step 1.

## Step 4: implement

Add the dependencies: `spring-boot-starter-cache` and `com.github.ben-manes.caffeine:caffeine`. Then set:

```yaml
spring:
  cache:
    cache-names: questionCatalog
    caffeine:
      spec: maximumSize=10,expireAfterWrite=6h,recordStats
```

The content-only bean is immutable records in, immutable list out:

```java
@Component
public class QuestionCatalog {
    public record Entry(String slug, String title, String type, String difficulty, List<String> tags,
                        String leetcode, List<String> companies, int sightings, String lastSeen) {}

    private final QuestionRepository questions;
    public QuestionCatalog(QuestionRepository questions) { this.questions = questions; }

    @Cacheable("questionCatalog")
    @Transactional(readOnly = true)
    public List<Entry> entries() {
        return questions.findAllWithSightings().stream()
                .map(q -> new Entry(/* the content fields BankService builds today */))
                .toList();
    }
}
```

`BankService.questions()` now calls `catalog.entries()` and adds `done` and `starred` from `progress.all()`. Put `@EnableCaching` on `CompanyWisePrepApplication`.

**Eviction must happen after the reload commits.** If you evict inside the transaction, a concurrent request can re-cache the *old* rows before the commit lands. So publish an event from `importAll()` and clear the cache only once the transaction has committed:

```java
public record BankReloaded() {}

// in DataImporter.importAll(), last line before return:
events.publishEvent(new BankReloaded());          // ApplicationEventPublisher injected

@Component
class CatalogEvictor {
    private final CacheManager caches;
    CatalogEvictor(CacheManager caches) { this.caches = caches; }

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    void on(BankReloaded e) { caches.getCache("questionCatalog").clear(); }
}
```

Both tests go green. Then run the whole suite, `AppTest` included, to show you broke nothing.

## Step 5: observe

A passing test proves the logic. Observing the running app proves the deployment.

- Set `logging.level.org.hibernate.SQL=debug`. The first `GET /api/questions` logs the select. The second logs nothing for the catalog; only the progress query remains.
- `GET /actuator/caches` lists `questionCatalog`.
- `GET /actuator/metrics/cache.gets?tag=name:questionCatalog&tag=result:hit` shows the hit count climbing.
- `http.server.requests` for `uri=/api/questions` shows the mean time dropping. Write the before and after numbers in the PR.

## Reading Spring's own code in a debugger

When behaviour surprises you, read the framework instead of guessing. You rarely need to *build* Spring to do that. Maven already downloads `-sources.jar` files that match your exact version, and your IDE attaches them. Set breakpoints in these classes, then send one request:

```text
DispatcherServlet.doDispatch                      – every MVC request enters here
AbstractHandlerMethodMapping.lookupHandlerMethod  – which controller method matched, and why
InvocableHandlerMethod.getMethodArgumentValues    – each argument resolver at work
CacheInterceptor.invoke                           – the @Cacheable proxy: hit or miss
TransactionInterceptor.invoke                     – @Transactional begin/commit
RequestResponseBodyMethodProcessor.handleReturnValue – JSON writing
```

Make the breakpoint in `doDispatch` *conditional* on `request.getRequestURI().startsWith("/api")`. That way static asset requests don't stop you. In the frames view, the stack between your controller and `doDispatch` *is* the proxy chain from D3.

**Building Spring Framework from source** is worth doing when you want to add logging inside the framework, try a fix, or contribute:

```text
git clone https://github.com/spring-projects/spring-framework.git
cd spring-framework
git checkout v<your version>          # find it: ./mvnw dependency:tree | grep spring-webmvc
# set version=<your version>-local in gradle.properties, so it can't shadow the real release in ~/.m2
./gradlew :spring-webmvc:compileJava  # quick sanity build of one module
./gradlew publishToMavenLocal         # full install into ~/.m2 (slow)
```

Then, in your app's `pom.xml`, set `<spring-framework.version><your version>-local</spring-framework.version>`. Spring Boot's parent manages every Spring Framework artifact through that one property. Check the repository README for the JDK the build needs, because it is not always the one your app uses.

## Lab (~10 min)

1. Make the step 3 test fail for the right reason. Write down the exception message.
2. Implement step 4. Shortcut: if time is short, keep the `QuestionCatalog` mapping minimal (slug and title) and adapt the test.
3. **Break it twice:**
   - Move `@Cacheable` onto a private helper inside `BankService`, called from `questions()`. The cache stays empty: that is self-invocation, so no proxy is involved.
   - Remove `recordStats` from the spec. `cache.gets` now reports nothing useful.
4. Set the conditional breakpoint in `doDispatch`, send `GET /api/questions` twice, and step until you reach `CacheInterceptor.invoke`. On the second call, watch it return without ever reaching `QuestionCatalog.entries()`.

## Gotchas

- **Caching a method that mixes slow-changing and per-user or per-click data.** Find the seam first, and cache only the stable part.
- **Self-invocation.** `@Cacheable`, `@Transactional` and `@Async` only work through the proxy. Put the annotated method on a separate bean.
- **Caching JPA entities.** They are mutable and become detached, with lazy fields that throw later. Cache immutable DTOs or records.
- **Evicting before commit** lets a concurrent reader re-cache the old data. Evict `AFTER_COMMIT`.
- **Skipping step 2.** Without `@EnableCaching`, Boot creates no `CacheManager`, and `@Cacheable` silently does nothing. Reading the conditions takes minutes and saves hours.
- **Publishing a locally built framework under the release version** overwrites the real jar in `~/.m2`. Use a `-local` suffix.

## In interviews

Typical prompts are "Walk me through how you'd add feature X to a Spring service", "How do you debug a framework behaviour you don't understand?" and "Add caching to this endpoint: what can go wrong?". Bank: [Diagnosing a low cache hit ratio](#/q/diagnose-low-cache-hit-ratio), [Design a distributed cache optimised for a given task](#/q/design-distributed-cache), [Design an Idempotent API](#/q/design-idempotent-api) (the same playbook, where the extension point is a filter or interceptor).

**Follow-up: "Your app now runs on three instances. Does this cache still work?"** Each instance has its own Caffeine cache, and a reload only evicts on the instance that handled it. A strong answer offers options: broadcast the eviction (a message topic or a Postgres `LISTEN/NOTIFY`), use a shared cache (Redis), or accept staleness bounded by `expireAfterWrite`.

## Explain it in 2 minutes

*"How do you ship a new feature in a Spring Boot codebase you don't fully know?"*

- Find the extension point Spring intends for it, using the docs, the properties appendix and `@EnableXxx` annotations. Then find the right seam in *your* code.
- Read the auto-configuration source or the conditions report: what gets built, which properties matter, when it backs off.
- Write a failing test and check that it fails for the right reason.
- Make the smallest implementation that passes, keeping proxies and transaction boundaries in mind.
- Observe it in the running app through logs, Actuator and metrics, and record the before and after numbers.
- When surprised, step through the framework source in a debugger instead of guessing.

### Answers

2. `CacheAutoConfiguration`. It is conditional on a `CacheAspectSupport` bean, and that bean is registered by `@EnableCaching`.
