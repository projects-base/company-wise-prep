## Where we are

After CAPSTONE-5, TicketHub runs on PostgreSQL 16 with Flyway, a JPA `BookingService`, optimistic locking on `event_seat`, and idempotency keys stored in the hold transaction. You checked it by hand with curl, and the CAPSTONE-3/4 `@SpringBootTest` classes are `@Disabled` because they have no database. This session replaces "I tried it" with tests that a reviewer can run, using SPRING-BOOT-8 (slices and Testcontainers) and DB-SQL-7 (N+1 and query counting).

## Goal

Build a test suite in three layers:

- **Fast slice tests** for the web and repository layers.
- **Integration tests against a real Postgres** started by Testcontainers. These never touch H2: an in-memory database that only pretends to be Postgres would hide exactly the locking behaviour you care about.
- **A concurrency test** that fires two threads at one seat and asserts that exactly one booking wins.

Then find, measure and fix an N+1 query in `GET /me/bookings`. An N+1 is one query for a list plus one more query per row. Lock the fix in with a test that counts SQL statements.

## Steps

**1. One shared Postgres for all tests (5 min).** Boot 3.5 manages the Testcontainers versions, so add the three test-scoped dependencies without versions. Then:

```java
@TestConfiguration(proxyBeanMethods = false)
public class TestcontainersConfiguration {
    @Bean
    @ServiceConnection
    PostgreSQLContainer<?> postgres() {
        return new PostgreSQLContainer<>("postgres:16-alpine");
    }
}
```

`@ServiceConnection` tells Boot to read the container's JDBC URL, username and password and build the `DataSource` from them. You no longer need `@DynamicPropertySource` boilerplate. Flyway runs `V1__init.sql` on startup, so tests get the real schema. Tests run with the `test` profile, not `dev`, so the dev seed does not load. Each test class loads the rows it needs with `@Sql`.

The Spring test context is cached and shared between test classes with the same configuration. That means one container start for the whole suite, not one per class.

*Boot 4 note:* Testcontainers 2 renames the module artifacts (for example `testcontainers-postgresql`) and moves the container classes into module packages. The slice annotations also move into per-technology test modules. The concepts here do not change.

Translate CAPSTONE-3's `test-seed.json` into `src/test/resources/sql/test-seed.sql`, keeping its ids. That gives venue 1 with seats 1001–1010 and events 1–3, all `STANDARD`:

```sql
insert into venue (id, name, row_count, seats_per_row) values (1, 'Test Hall', 2, 5);
insert into seat (id, venue_id, row_no, seat_no)
select 1000 + (r - 1) * 5 + n, 1, r, n from generate_series(1, 2) r, generate_series(1, 5) n;
```

`src/test/resources/sql/clean.sql` is one line: `truncate venue, seat, event, event_seat, seat_hold, booking, booking_seat, idempotency_key cascade;`.

Now re-enable the CAPSTONE-3/4 classes. Remove `@Disabled`, add `@Import(TestcontainersConfiguration.class)` and `@Sql({"/sql/clean.sql", "/sql/test-seed.sql"})`, and delete `seed-location` from `application-test.yml`. Their assertions do not change. That is the payoff of keeping the API contract fixed while the storage underneath changed. If a test depended on state left behind by another test, `clean.sql` now exposes it, so give that test its own seat, as CAPSTONE-4 advised.

**2. Repository slice (8 min).** `@DataJpaTest` starts only JPA, Flyway and the repositories, and wraps each test in a transaction that rolls back at the end.

```java
@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)  // keep the container, not an embedded DB
@Import(TestcontainersConfiguration.class)
@Sql({"/sql/clean.sql", "/sql/test-seed.sql"})
class EventSeatRepositoryTest {
    @Autowired EventSeatRepository eventSeats;
    @Autowired EntityManager em;

    @Test
    void staleVersionIsRejected() {
        EventSeatEntity seat = eventSeats.findById(new EventSeatId(1, 1001)).orElseThrow();   // version 0, managed
        em.createNativeQuery("update event_seat set version = version + 1 where event_id = 1 and seat_id = 1001")
          .executeUpdate();                       // simulates another transaction winning first

        seat.hold(UUID.randomUUID());
        assertThatThrownBy(() -> eventSeats.saveAndFlush(seat))
                .isInstanceOf(ObjectOptimisticLockingFailureException.class);
    }
}
```

The native update bumps the version in the database, but the entity in memory still holds version 0. That is exactly the stale read a racing transaction would have. The random hold id never reaches a foreign-key check: the `UPDATE ... WHERE version = 0` matches no row, so Hibernate throws before any constraint is evaluated.

**3. Web slice (8 min).** `@WebMvcTest` starts only MVC: your controller, the `@RestControllerAdvice`, Jackson and validation. The service is a mock.


Add one test per exception type, plus a missing `Idempotency-Key` and an empty `seatIds` list, which should both return `400`. These tests run in about a second because no database is involved.

**4. The race test (15 min).** This is the test you will describe in interviews.

```java
@SpringBootTest
@ActiveProfiles("test")
@Import(TestcontainersConfiguration.class)
@Sql({"/sql/clean.sql", "/sql/test-seed.sql"})
class DoubleBookingRaceTest {
    @Autowired BookingService bookingService;
    @Autowired JdbcTemplate jdbc;

    @Test
    void twoUsersOneSeatExactlyOneWins() throws Exception {
        int threads = 2;
        var ready = new CountDownLatch(threads);
        var go = new CountDownLatch(1);
        var wins = new AtomicInteger();
        var losses = new AtomicInteger();

        try (ExecutorService pool = Executors.newFixedThreadPool(threads)) {
            List<Future<Object>> results = new ArrayList<>();
            for (int i = 0; i < threads; i++) {
                String user = "user-" + i;
                results.add(pool.submit(() -> {
                    ready.countDown();
                    go.await();                          // every thread is parked here
                    try {
                        bookingService.hold(1L, user, UUID.randomUUID().toString(), List.of(1001L));
                        wins.incrementAndGet();
                    } catch (SeatUnavailableException expected) {
                        losses.incrementAndGet();
                    }
                    return null;
                }));
            }
            ready.await(5, TimeUnit.SECONDS);
            go.countDown();                              // release them together
            for (Future<Object> f : results) {
                f.get(10, TimeUnit.SECONDS);             // rethrows anything unexpected
            }
        }

        assertThat(wins).hasValue(1);
        assertThat(losses).hasValue(1);
        assertThat(jdbc.queryForObject("select count(*) from seat_hold", Integer.class)).isEqualTo(1);
        assertThat(jdbc.queryForObject(
                "select count(*) from event_seat where event_id = 1 and seat_id = 1001 and status = 'HELD'", Integer.class))
                .isEqualTo(1);
    }
}
```

The details that make this a real test:

- **Do not put `@Transactional` on the test.** A transaction belongs to one thread, so the test transaction would hold the
  `@Sql` rows uncommitted where the worker threads cannot see them. Each `hold` call must start and commit its own
  transaction, exactly as two HTTP requests would.
- **Two latches.** `ready` makes sure both threads exist. `go` releases them at the same moment, which makes it much more likely that both read version 0 before either one writes.
- **`f.get(...)` matters.** A `NullPointerException` or a `DataIntegrityViolationException` inside a thread would otherwise vanish, and the counters could still look right.
- **The winner is not fixed.** Either thread may win. Assert on counts, never on which user got the seat.

The loser may lose in one of two ways. Sometimes it reads the seat after the winner commits, and the `hold()` fast-path check throws. Sometimes both read version 0, and the versioned update fails. Both paths must end in `SeatUnavailableException`, and the test accepts either. To exercise the version path harder, raise `threads` to 10 and assert `wins == 1, losses == 9`. Keep Hikari's pool size at the default of 10 or more, or threads will wait for connections instead of racing.

**5. Find the N+1 (6 min).** Turn on statistics in `src/test/resources/application.yml`:

```yaml
spring.jpa.properties.hibernate.generate_statistics: true
logging.level.org.hibernate.SQL: debug   # watch the statements while you investigate; remove later
```

Write the test first:

```java
@SpringBootTest
@ActiveProfiles("test")
@Import(TestcontainersConfiguration.class)
@Sql({"/sql/clean.sql", "/sql/test-seed.sql"})
class MyBookingsQueryCountTest {
    @Autowired BookingService bookingService;
    @Autowired EntityManagerFactory emf;
    @Autowired BookingTestData data;          // a tiny @TestComponent that inserts bookings with JdbcTemplate

    @Test
    void constantQueryCount() {
        data.insertBookings("alice", 5);      // 5 bookings, 2 seats each
        Statistics stats = emf.unwrap(SessionFactory.class).getStatistics();
        stats.clear();

        Page<Booking> page = bookingService.myBookings("alice", PageRequest.of(0, 20));

        assertThat(page.getContent()).hasSize(5).allSatisfy(b -> assertThat(b.seatIds()).hasSize(2));
        assertThat(stats.getPrepareStatementCount()).isLessThanOrEqualTo(3);
    }
}
```

`BookingTestData` needs `@Import(BookingTestData.class)` on the test, or make it a plain helper that takes the `JdbcTemplate`. Each booking needs its own `seat_hold` row first, because `booking.hold_id` is a non-null foreign key. Give each booking two distinct seats out of 1001–1010. The test fails with 7 statements: the page query, the count query, then one `select ... from booking_seat where booking_id = ?` for each of the five bookings. The cause is that `toDomain()` reads the lazy `seatIds` collection on each booking, inside the service's transaction. Because you turned off open-in-view in CAPSTONE-5, at least it happens there and not during JSON rendering.

**6. Fix it, and avoid the trap (10 min).** The obvious fix is a fetch join on the paged query:

```java
@Query("select b from BookingEntity b left join fetch b.seatIds where b.userId = :userId")
Page<BookingEntity> findByUserId(String userId, Pageable pageable);    // DON'T
```

Hibernate cannot apply `LIMIT` to a query that fetches a collection, because rows are multiplied per seat. So it loads **every** booking for the user and pages in memory, and logs warning `HHH90003004`. An `@EntityGraph(attributePaths = "seatIds")` on the same method has the same problem. That is fine for a single booking (`GET /bookings/{id}`), but wrong for a page.

The correct fix is two queries: page the ids, then fetch the entities for exactly those ids.

```java
public interface BookingRepository extends JpaRepository<BookingEntity, UUID> {

    @Query(value = "select b.id from BookingEntity b where b.userId = :userId order by b.createdAt desc, b.id",
           countQuery = "select count(b) from BookingEntity b where b.userId = :userId")
    Page<UUID> findIdsByUserId(String userId, Pageable pageable);

    @Query("select b from BookingEntity b left join fetch b.seatIds where b.id in :ids order by b.createdAt desc, b.id")
    List<BookingEntity> findWithSeatsByIdIn(Collection<UUID> ids);

    @EntityGraph(attributePaths = "seatIds")
    Optional<BookingEntity> findWithSeatsById(UUID id);
}
```

```java
@Transactional(readOnly = true)
public Page<Booking> myBookings(String userId, Pageable pageable) {
    Page<UUID> ids = bookings.findIdsByUserId(userId, pageable);
    if (ids.isEmpty()) {
        return Page.empty(pageable);
    }
    List<Booking> content = bookings.findWithSeatsByIdIn(ids.getContent()).stream()
            .map(BookingEntity::toDomain)
            .toList();
    return new PageImpl<>(content, pageable, ids.getTotalElements());
}
```

That is three statements whatever the page size. Hibernate 6 removes the duplicate parent rows from a fetch join on its own, so you no longer need `distinct`. Pass an unsorted `Pageable`, because the order is fixed in the query, and that order matches `ix_booking_user_created` from CAPSTONE-5.

A one-line alternative is `spring.jpa.properties.hibernate.default_batch_fetch_size: 50`. Lazy collections then load in batches with `where booking_id in (...)`, giving 1 + ⌈N/50⌉ queries. It is a good global safety net, but the explicit query states what the endpoint needs.

## Hints

- **"Could not find a valid Docker environment".** Start Docker Desktop and check that `docker ps` works from the same
  terminal. Do not expose the daemon on an unauthenticated TCP port to make it work.
- **`wins == 2`.** Something bypasses the version check. Look for a missing `@Version`, a bulk JPQL `update` that skips it,
  or a test that calls `new BookingService(...)` instead of the injected (transactional) bean.
- **The race test hangs.** A thread threw before `ready.countDown()`. Always count down first, and always use timeouts on `await` and `get`.
- **Tests leak into each other.** `@SpringBootTest` does not roll back, which is why every class starts with `clean.sql`.
- **The statement count is off by one.** `stats.clear()` must come after the setup inserts, and `getPrepareStatementCount()` counts the count query too.

## Talk about it in interviews

**"How do you test concurrency bugs?"**
1. *What:* a deterministic harness. N threads, a start gate, real transactions against the real database, and assertions on invariants, not on who won.
2. *How it works inside:* `CountDownLatch` parks the threads and releases them together. Each call commits in its own transaction through the Spring proxy. Postgres row locks plus the `@Version` check decide the winner, and I collect exceptions through `Future.get`.
3. *Where it's used:* anything with a uniqueness or "never twice" invariant: payments, inventory, idempotency keys.
4. *What goes wrong:* a `@Transactional` test that hides the race, H2 behaving differently from Postgres, swallowed thread exceptions, and a flaky pass hiding a real bug. That is why I run it repeatedly and prove it fails when I remove `@Version`.

**"What is an N+1 query and how did you fix one?"** Cover the cause (a lazy collection read in a loop) and how I measured it (Hibernate statistics, 7 statements for 5 rows). Then explain why a fetch join with pagination is a trap (in-memory paging, `HHH90003004`), and give the two-query fix and the `batch_fetch_size` alternative.

**"Slice tests vs `@SpringBootTest` vs Testcontainers?"** Slices are fast and focused, and they test one layer's wiring. Full context plus a real database is for behaviour that only exists in the integration: transactions, locking, Flyway. Mocks cannot tell you whether your SQL is right.
