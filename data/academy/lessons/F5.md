## Where we are

F4 ran the method on mostly **request/response** systems: a client asks and the server answers. F2
gave you consistency models, ordering, idempotency and conflict handling. This lesson combines
them for **real-time, stateful** systems, where the server must push data to clients and several
people change shared state at once: chat, news feed and a collaborative editor. Like F4, this is a
long case-study lesson, so take one case per sitting if you need to.

## The problem

In F4, the client always started the conversation. Now:

```text
Chat:    Bob's phone must learn about Alice's message without asking.
Feed:    one post by an account with 50M followers must reach 50M feeds.
Editor:  Alice and Bob type into the same sentence at the same millisecond.
```

These need three new ideas: **server push**, **fan-out**, and **merging concurrent edits**. Each
case below is built around one of them.

## Case 1: chat (Microsoft Teams messaging)

### Requirements

```text
Functional:   1:1 and group chats (groups up to 10k members); send/receive in real time;
              history; multiple devices per user; offline users catch up; read receipts; presence
NFR:          delivery to online recipients < ~500 ms p99; messages never lost;
              per-conversation order identical for every member; 99.99% available
Out of scope: calls, file storage internals, search
```

### Estimates

```text
DAU 50M × 40 messages sent/day = 2B messages/day ≈ 23,000/s    peak ≈ 70,000/s
Size: ~300 B with metadata → 2B × 300 B = 600 GB/day → ~220 TB/year (before replication)
Concurrent connections at peak: assume 20M
  if one gateway server holds ~50k long-lived connections (an assumption, depends on tuning)
  → ~400 gateway servers
```

**So…** storage grows fast and must be partitioned. The connection layer is a large stateful fleet
of its own. Group messages multiply the deliveries: one message to a 10k group is 10k deliveries.

### Push: how the server reaches the client

| Option | How | Verdict |
|---|---|---|
| Short polling | Client asks "anything new?" every few seconds | Wasteful and slow |
| Long polling | Client asks; the server holds the request open until something arrives | Works through any proxy; reconnects per message |
| **WebSocket** | One long-lived, two-way connection over TCP, opened with an HTTP upgrade | Low latency, both directions. **Choice** |
| Server-Sent Events | One-way server → client stream over HTTP | Fine for feeds, but chat also sends upward |

Keep long polling as a fallback for networks that block WebSockets.

### High-level design

```text
 devices ══WebSocket══► gateway fleet (stateful: holds connections)
                           │  ▲                         session registry (Redis):
                           │  │ deliver                 userId → [gateway, deviceId]...
                           ▼  │
                       chat service ── assign seq ──► message store (partitioned by conversation_id)
                           │
                           ├──► pub/sub to the gateways of online members
                           └──► push notification service (F4) for offline members
```

Send path: the device sends `{clientMsgId, conversationId, text}` → the gateway → the chat service
assigns the next **sequence number** for that conversation → persists → acks the sender → fans
out to members' gateways via the session registry.

### Data model

```text
messages        partition key: conversation_id     clustering: seq (ascending)
                (conversation_id, seq, message_id, sender_id, body, created_at, client_msg_id)
conversations   (conversation_id, type, last_seq, ...)
members         (conversation_id, user_id, role, last_read_seq)      ← read receipts
user_convs      (user_id, conversation_id, last_activity)            ← "my chat list"
```

Partitioning by `conversation_id` keeps "load the last 50 messages of this chat" on one partition,
already sorted. A wide-column store (Cassandra-style) or a sharded relational table both fit. For a
very old, very busy chat, add a time bucket to the partition key so one partition doesn't grow
forever.

### Deep dive 1: ordering

**Timestamps can't order messages.** Clocks on different servers drift by milliseconds or more, so
two messages a few milliseconds apart can come out reversed.

Use a **per-conversation sequence number**: a counter that increases by one with each message in
that conversation. Exactly one writer assigns it: the shard that owns the conversation, using an
atomic increment of `conversations.last_seq`. Every member then sorts by `seq`, so everyone sees
the same order. A per-conversation counter is enough. You don't need a global order across all
chats, and asking for one would create a bottleneck.

Retries: if the ack is lost, the device resends with the same `clientMsgId`, and the server
dedups on it (F2's idempotency).

### Deep dive 2: offline sync and multiple devices

Each device remembers the last `seq` it has for each conversation. On reconnect it asks: "for
each of my conversations with `last_seq` higher than mine, send the messages after my seq". Gaps
are easy to detect: receiving seq 41 right after 39 means 40 is missing, so the client fetches it.
Read receipts are a single number per member (`last_read_seq`), not a row per message per reader.

### Deep dive 3: the 10k-member group

Pushing the full message to 10k members means 10k sends per message, and a busy channel can make
that a storm. Mitigations:
- Send the full payload only to members who are **online**, and use a batched, throttled push
  notification for the rest, or skip it for muted channels.
- For very large channels, push a lightweight "conversation X has new messages up to seq N" signal,
  and let clients fetch the content (**fan-out on read**).
- Presence and typing indicators are **ephemeral**: they are never stored, throttled hard, and
  sent only to people currently viewing that chat.

### Follow-ups

- **"A gateway server dies."** Its clients reconnect (with jittered backoff) to other gateways,
  update the session registry and resync from their last seq. Nothing is lost, because messages
  were persisted before being acked.
- **"Edit and delete messages."** Model them as new events (`edit` of message_id) with their own
  seq, so they replay in order during sync.

## Case 2: news feed

### Requirements

```text
Functional:   post (text/media); home feed of posts from accounts you follow; ranked or recent
NFR:          feed load p99 < 300 ms; a new post visible to followers within seconds to a minute
              (eventual is fine); 200M DAU
```

### Estimates

```text
Feed reads:  200M × 5 loads/day = 1B/day ≈ 12,000/s     peak ≈ 35,000/s
Posts:       40M/day ≈ 460/s
Average followers: 200 → push fan-out writes = 40M × 200 = 8B/day ≈ 93,000/s
Feed cache:  keep 500 post ids × 8 B per user → 4 KB/user × 200M ≈ 800 GB (+ overhead)
```

**So…** reads must be cheap, which argues for precomputing feeds. But some accounts have tens of
millions of followers, and precomputing for them is very expensive.

### Fan-out: the central trade-off

```text
Fan-out on WRITE (push)                       Fan-out on READ (pull)
post ──► for each follower:                   feed request ──► for each followee:
         prepend post id to their feed cache                    fetch recent posts, merge, rank
+ reads are one cache lookup                  + posting is one write
− a 50M-follower post = 50M writes            − every read touches ~200 followees
− wasted on inactive followers                − slow for heavy readers
```

**Hybrid (the usual answer):** push for ordinary accounts. Don't push for celebrity accounts (above
a follower threshold). At read time, merge the precomputed feed with recent posts pulled from the
few celebrities the user follows. Skip pushing to users who haven't been active for weeks, and
rebuild their feed when they return.

### High-level design

```text
post ──► post service ──► posts DB (by post_id) + media to object store/CDN
              │
              └──► stream ──► fan-out workers ──► feed cache (user_id → [post ids])
                                     ▲ followers from social graph service

feed request ──► feed service ──► feed cache ids ∪ celebrity posts (pull)
                                  ──► ranking service ──► hydrate (post cache) ──► client
```

Ranking is usually two stages: **candidate generation** (the few hundred posts above) and then
**scoring** with a model or rules (recency, affinity, engagement). Paginate with a cursor (F3),
never with offsets, because the feed changes while the user scrolls.

### Follow-ups

- **"A celebrity posts. Walk me through it."** One write to posts. No fan-out. Followers see it on
  their next feed load through the pull merge, and a hot-key cache in front of that celebrity's
  recent posts absorbs the reads.
- **"User deletes a post."** Mark it deleted in the posts DB. Hydration filters it out. You don't
  need to scrub every feed cache straight away.

## Case 3: collaborative editor (Google Docs)

### Requirements

```text
Functional:   many users edit one document at once; see each other's edits and cursors live;
              version history; permissions (view/comment/edit); works on flaky networks
NFR:          local typing feels instant; everyone CONVERGES to the same text;
              no edit silently lost; most documents have a handful of simultaneous editors
```

**So…** scale per document is small. **The hard part is concurrency correctness.** That's why
Microsoft interviewers reportedly push on OT versus CRDT and on convergence.

### Why the obvious approaches fail

- **Lock the document while someone types:** there's no real collaboration.
- **Send the whole document, last writer wins:** one user's edits silently vanish.
- **Send "insert X at position 2" as-is:** positions shift under concurrent edits, so users
  **diverge**:

```text
start "abc".   Alice: insert X at 0.    Bob (at the same time): insert Y at 2.
Alice applies hers → "Xabc", then Bob's "Y at 2"  → "XaYbc"
Bob applies his  → "abYc", then Alice's "X at 0" → "XabYc"     ✗ different documents
```

Bob meant "after the b". Once Alice's X has gone in front, "after the b" is position 3. Both fixes
below come from that observation.

### Fix 1: Operational Transformation (OT)

**Operational Transformation (OT)** rewrites an incoming operation against the concurrent
operations already applied, so it keeps its intended meaning. For two inserts: if the other insert
landed at or before my position, shift mine right by one, with a fixed tie-break such as user id
when the positions are equal.

```text
transform(Bob's "Y at 2", against Alice's "X at 0") = "Y at 3"
Alice: "Xabc" + "Y at 3" → "XabYc"      Bob: "abYc" + "X at 0" → "XabYc"   ✓ converged
```

The correctness condition is called **convergence**: applying A then transformed-B must give the
same document as B then transformed-A.

How it is deployed: a **central server** gives every operation a single order (a revision
number). A client sends `op + the revision it was based on`. The server transforms the op against
everything committed since that revision, applies it, assigns the next revision and broadcasts it.
Clients transform their own unacknowledged ops against incoming ones. Google Docs is widely
described as using OT with a central server. The central server keeps the transformation cases
manageable. Fully peer-to-peer OT is notoriously hard to get right.

### Fix 2: CRDTs

A **CRDT (Conflict-free Replicated Data Type)** is a data structure designed so that concurrent
updates **commute**: replicas can apply them in any order and still end up identical. There's
nothing to transform.

For text, the intuition is: **give every character a unique, permanent id and position it
relative to its neighbours, not by index.**

```text
"abc" →  a(id 1.1)  b(id 1.2)  c(id 1.3)
Bob:   insert Y "after id 1.2"          (not "at index 2")
Alice: insert X "at the start"
Any replica, in any order: X a b Y c    ✓  (ties broken by comparing ids)
Deletes leave a "tombstone": the character is hidden but its id stays, so others can still refer to it.
```

### OT versus CRDT

| | OT | CRDT |
|---|---|---|
| Needs a central server? | In practice, yes, to order ops | No: works peer-to-peer and offline |
| Metadata | Small: ops are plain positions | Per-character ids and tombstones, so documents grow |
| Long offline edits | Painful: long transform chains | Natural: merge when you reconnect |
| Implementation | Transform functions for every op pair; subtle bugs | The data structure is subtle, but good libraries exist (Yjs, Automerge) |
| Typical fit | Server-centric products | Offline-first, local-first, peer-to-peer apps |

**A strong interview answer:** "Edits go through a server anyway (permissions, history, presence),
so I'd use server-ordered OT. If offline editing for hours is a requirement, I'd use a CRDT and pay
the metadata cost, with periodic compaction of tombstones."

### High-level design

```text
 clients ══WebSocket══► collaboration service  (all editors of doc D routed to the same node,
                              │                  via consistent hashing on doc_id)
                              │  in memory: current doc state + revision
                              ├──► op log (append-only, by doc_id, revision)   ← persist before ack
                              ├──► snapshotter: every N ops → snapshot to object storage
                              ├──► presence/cursors via pub/sub (ephemeral)
                              └──► ACL service (can this user edit D?)
 open doc = latest snapshot + replay ops since it
 version history = snapshots + op log
```

### Follow-ups

- **"The collaboration node for a document crashes."** Clients reconnect. The new owner node loads
  the latest snapshot and replays the op log. Clients resend unacked ops, and dedup by
  `(clientId, opSeq)` makes the resend safe.
- **"A document has 500 simultaneous viewers."** Separate editors from viewers. Viewers get a
  broadcast stream and are throttled. Cursor updates are batched and sampled.
- **"How do you store documents?"** As snapshots plus the operation log, not as a row rewritten on
  every keystroke. The in-memory structure can be a rope or piece table (structures for fast
  insertion into long text). Mention it if asked.

## Lab (~10 min)

See divergence happen, then fix it with OT. Save this as `OtLab.java` and run `java OtLab.java`.

```java
public class OtLab {

    /** "Insert character ch at position pos", made by the user with id site. */
    record Insert(int pos, char ch, int site) {}

    static String apply(String doc, Insert op) {
        return doc.substring(0, op.pos()) + op.ch() + doc.substring(op.pos());
    }

    /**
     * Rewrite op so it still means the same thing after 'applied' has already been applied.
     * If the other insert landed before us (or at the same spot, and wins the tie), shift right by one.
     */
    static Insert transform(Insert op, Insert applied) {
        boolean shift = applied.pos() < op.pos()
                || (applied.pos() == op.pos() && applied.site() < op.site());
        return shift ? new Insert(op.pos() + 1, op.ch(), op.site()) : op;
    }

    static void run(String start, Insert alice, Insert bob) {
        // Naive: each side applies its own op, then the other's op exactly as received.
        String aliceNaive = apply(apply(start, alice), bob);
        String bobNaive = apply(apply(start, bob), alice);

        // OT: each side transforms the incoming op against the op it already applied.
        String aliceOt = apply(apply(start, alice), transform(bob, alice));
        String bobOt = apply(apply(start, bob), transform(alice, bob));

        System.out.printf("start=%s  alice=%s  bob=%s%n", start, alice, bob);
        System.out.printf("  naive: alice sees %-6s bob sees %-6s %s%n",
                aliceNaive, bobNaive, aliceNaive.equals(bobNaive) ? "converged" : "DIVERGED");
        System.out.printf("  OT:    alice sees %-6s bob sees %-6s %s%n",
                aliceOt, bobOt, aliceOt.equals(bobOt) ? "converged" : "DIVERGED");
    }

    public static void main(String[] args) {
        run("abc", new Insert(0, 'X', 1), new Insert(2, 'Y', 2));   // different positions
        run("abc", new Insert(1, 'X', 1), new Insert(1, 'Y', 2));   // same position: needs a tie-break
    }
}
```

**What you should see:** in both runs, the naive version prints `DIVERGED` (for example `XaYbc`
versus `XabYc`), and the OT version converges (`XabYc`, and `aXYbc` for the tie).

**Break it:** delete the tie-break (`|| (applied.pos() == op.pos() && ...)`). The first run still
converges, but the second diverges, because both users think they should go first. Every OT and
CRDT design needs a deterministic tie-break.

**Stretch:** add a `Delete(int pos)` record and write the three missing transform cases
(insert/delete, delete/insert, delete/delete). You'll see quickly why OT implementations are
famous for subtle bugs.

## Gotchas

- **Ordering chat by timestamp.** Clock skew reorders messages. Use a per-conversation sequence
  number with a single writer.
- **Global ordering "just in case".** A global sequence across all chats is a bottleneck nobody
  needs. Order within a conversation only.
- **Pure fan-out on write** breaks on celebrity accounts. Pure fan-out on read breaks on heavy
  readers. Name the hybrid and the threshold.
- **Persisting presence and typing indicators.** They are ephemeral. Storing them wastes write
  capacity on data nobody reads later.
- **Saying "CRDTs have no conflicts, so they're free".** They trade conflicts for metadata growth
  (ids, tombstones) and need compaction.
- **Forgetting the tie-break.** Two concurrent inserts at the same position diverge without a
  deterministic rule.

Typical follow-ups:
- **"Sequence numbers or timestamps for ordering?"** Sequence numbers per conversation, from one
  writer. Timestamps are for display only. Explain clock skew and gap detection.
- **"Prove your OT converges."** State the property (A then B′ equals B then A′), show the
  insert/insert case with the tie-break, and explain that a central server reduces the cases you
  must prove.
- **"WebSockets versus long polling?"** WebSockets for latency and two-way traffic, long polling as a
  fallback through restrictive proxies, and why the gateway fleet is stateful and needs a session
  registry.

## Explain it in 2 minutes

*"How do two people edit the same Google Doc without breaking it?"*

- Sending raw positions diverges, because concurrent inserts shift each other's positions.
- OT transforms each incoming op against concurrent ones so it keeps its intent. A central server
  orders the ops.
- CRDTs give each character a permanent id and position it relative to neighbours, so ops commute
  in any order.
- Trade-off: OT is compact and server-centric. CRDT is offline and peer-to-peer friendly, but
  carries metadata and tombstones.
- The system: WebSockets, a per-document owner node, an op log persisted before the ack, snapshots
  for loading and history.

## Check yourself

1. Why can't two chat messages be ordered reliably by server timestamp?
2. A device receives seq 101 and 103 for a chat. What should it do?
3. Explain the hybrid feed strategy in two sentences.
4. In OT, what does "convergence" require of the transform function?
5. Give one reason to choose a CRDT over OT.

### Answers

1. Server clocks drift, so a message sent later can carry an earlier timestamp, and members could
   see different orders.
2. It detects the gap and fetches seq 102 (sync from its last contiguous seq) before displaying in
   order.
3. Push post ids into followers' feed caches for normal accounts, but not for celebrities. At read
   time, merge in recent celebrity posts pulled on demand.
4. Applying A then transform(B, A) must produce the same document as applying B then
   transform(A, B), for every pair of concurrent ops.
5. Long offline editing or peer-to-peer sync without a central server, because CRDT ops merge in any
   order.
