## Where we are

BE-STORY-10 split ShopKart into services; WEB-API-3 connected them and DIST-SYS-3 made them survive
failures. Every one of those lessons quietly assumed something runs the services, restarts them and
routes traffic only to healthy ones. This lesson is that something: Docker to package a Spring Boot
service, and Kubernetes to run it, at the depth a backend engineer is expected to own.

## The problem

Orders is a Spring Boot fat jar (BE-STORY-8). To run it in production you need the right JDK on
every machine, a way to start 3 copies, to restart a crashed one, to ship version 1.5 without
downtime, to give it config and a database password, and to stop it without dropping requests.
Doing that with scripts and SSH works for one service; it collapses at thirty. Containers solve the
packaging half; Kubernetes solves the running half.

## Image vs container

An **image** is a read-only, versioned package: a filesystem (OS libraries, JRE, your jar) plus
metadata such as the start command. A **container** is a running process started from an image,
isolated by the Linux kernel: its own view of files, network and process ids (**namespaces**), and
capped CPU and memory (**cgroups**, control groups).

```text
image  orders:1.4.2  (built once, stored in a registry)
   ├── container A  (running on node 1)
   └── container B  (running on node 2)      same bytes, separate processes
```

The analogy is class vs object: one image, many containers. It breaks on state: anything a
container writes to its own filesystem is lost when it is replaced, so state lives in databases and
volumes, never in the container.

A container is **not** a virtual machine: there is no guest kernel. It is an ordinary process that
starts in about the time the process itself takes, which for the JVM is your Spring Boot start-up.

## Layers: why Dockerfile order matters

An image is a stack of **layers**; each Dockerfile instruction that changes files adds one. Layers
are cached and shared: if a layer's inputs have not changed, Docker reuses it, and a registry push
or pull only moves layers the other side lacks.

So put what changes rarely at the bottom and what changes often at the top. A Spring Boot fat jar
copied as one file is one layer of perhaps tens of MB that changes on every commit, although
almost all of it is dependencies that changed months ago. Spring Boot can split the jar into
**layers**: `dependencies`, `spring-boot-loader`, `snapshot-dependencies`, `application`. A
code-only change then rebuilds and ships just the small `application` layer.

## A good Spring Boot Dockerfile

```dockerfile
# ---- build stage: has the JDK and Maven, never shipped ----
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY mvnw pom.xml ./
COPY .mvn .mvn
RUN ./mvnw -q dependency:go-offline              # cached until pom.xml changes
COPY src src
RUN ./mvnw -q -DskipTests package \
 && cp target/*.jar app.jar \
 && java -Djarmode=tools -jar app.jar extract --layers --destination /extracted

# ---- runtime stage: JRE only, non-root, layered ----
FROM eclipse-temurin:21-jre
RUN groupadd --system app && useradd --system --gid app --no-create-home app
WORKDIR /app
COPY --from=build /extracted/dependencies/ ./
COPY --from=build /extracted/spring-boot-loader/ ./
COPY --from=build /extracted/snapshot-dependencies/ ./
COPY --from=build /extracted/application/ ./
USER app
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

What each choice buys:

- **Multi-stage build**: the JDK, Maven and source code stay in the `build` stage; the final image
  holds only a JRE and the app. Smaller image, smaller attack surface.
- **Dependencies before source**: `dependency:go-offline` sits in its own cached layer, so editing
  a class does not re-download the internet.
- **Layered extraction**: `-Djarmode=tools ... extract --layers` is Spring Boot 3.3+. Older
  versions used `-Djarmode=layertools -jar app.jar extract` and started
  `org.springframework.boot.loader.launch.JarLauncher` instead.
- **Non-root user**: if the app is compromised, the attacker is not root inside the container.
- **Exec-form `ENTRYPOINT`** (the JSON array): `java` runs as PID 1 and receives `SIGTERM`
  directly. The shell form (`ENTRYPOINT java -jar app.jar`) wraps it in `/bin/sh`, which may not
  forward the signal, so graceful shutdown never happens.

No Dockerfile at all is also an option: `./mvnw spring-boot:build-image` builds a layered,
non-root image with Cloud Native Buildpacks.

## The JVM inside a container

Since JDK 10 (and 8u191) the JVM is **container-aware**: it reads the cgroup limits instead of the
host's totals. Two consequences you must know:

- **Default max heap is 25% of the container memory limit.** A 1 GiB container gets roughly a
  256 MB heap and wastes the rest. Set `-XX:MaxRAMPercentage=75.0` (commonly 60–75%) rather than a
  fixed `-Xmx`, so the heap follows the limit when someone changes it.
- **The heap is not all the memory.** Metaspace, thread stacks (about 1 MB each by default for
  platform threads), the JIT's code cache, GC structures and direct buffers live outside the heap
  (JAVA-JVM-2). Leave room for them.

The two ways to die look different, and interviewers like the distinction:

```text
heap full                       → java.lang.OutOfMemoryError in your logs; the JVM may limp on
container exceeds memory limit  → kernel OOM killer sends SIGKILL; no Java stack trace;
                                  exit code 137 (128 + 9); Kubernetes shows OOMKilled
```

CPU: the JVM sizes its GC threads, JIT threads and `availableProcessors()` (and so the common
`ForkJoinPool`) from the CPU **limit**. With under 2 CPUs or under about 1792 MB it also stops
treating the machine as "server class" and picks the Serial GC instead of G1 (JAVA-JVM-5).
With no CPU limit at all, recent JDKs see every core on the node and size pools to match; then
`-XX:ActiveProcessorCount=N` is how you tell the JVM what it should actually use.

## docker compose for local dependencies

For development you rarely containerise the app itself; you containerise what it needs.

```yaml
# compose.yaml
services:
  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: orders
      POSTGRES_USER: orders
      POSTGRES_PASSWORD: local-only        # a dev throwaway, never a real secret
    ports: ["5432:5432"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U orders"]
      interval: 5s
  redis:
    image: redis:7
    ports: ["6379:6379"]
```

`docker compose up -d` starts both. Spring Boot 3.1+ goes further: with the
`spring-boot-docker-compose` dependency, `./mvnw spring-boot:run` starts this file itself and
wires the datasource URL and credentials from the running containers, with no properties to write.
For tests, Testcontainers (SPRING-BOOT-8) is the same idea per test run.

## Kubernetes: the objects you actually touch

Kubernetes keeps the cluster in your **desired state** (the full story is coming in BE-STORY-11): you declare
objects in YAML, and controllers work continuously to make reality match. The six you will meet
every week:

| Object | What it is |
|---|---|
| **Pod** | One or more containers scheduled together on one node, sharing an IP. The unit that runs. Disposable. |
| **Deployment** | Declares "N pods from this template" and manages rolling updates between versions. You create this, not pods. |
| **Service** | Stable name, virtual IP and DNS entry for a set of pods chosen by label; sends traffic only to ready pods (WEB-API-3). |
| **Ingress** | HTTP routing from outside the cluster (host and path) to Services, implemented by an ingress controller. |
| **ConfigMap** | Non-secret configuration, injected as environment variables or files. |
| **Secret** | Sensitive values, injected the same way. Only base64-encoded by default: restrict access and enable encryption at rest, or use an external secret manager. |

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders
spec:
  replicas: 3
  selector:
    matchLabels: { app: orders }
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }   # add one new pod before removing an old one
  template:
    metadata:
      labels: { app: orders }
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: orders
          image: registry.example.com/orders:1.4.2       # an immutable tag, never :latest
          ports: [{ containerPort: 8080 }]
          env:
            - name: JAVA_TOOL_OPTIONS
              value: "-XX:MaxRAMPercentage=75.0"
            - name: SPRING_DATASOURCE_PASSWORD
              valueFrom: { secretKeyRef: { name: orders-db, key: password } }
          envFrom:
            - configMapRef: { name: orders-config }
          resources:
            requests: { cpu: "500m", memory: "768Mi" }
            limits: { memory: "768Mi" }
          startupProbe:
            httpGet: { path: /actuator/health/liveness, port: 8080 }
            periodSeconds: 5
            failureThreshold: 24                          # allows up to 120 s to start
          livenessProbe:
            httpGet: { path: /actuator/health/liveness, port: 8080 }
            periodSeconds: 10
          readinessProbe:
            httpGet: { path: /actuator/health/readiness, port: 8080 }
            periodSeconds: 5
          lifecycle:
            preStop:
              exec: { command: ["sh", "-c", "sleep 10"] }
---
apiVersion: v1
kind: Service
metadata:
  name: orders
spec:
  selector: { app: orders }
  ports: [{ port: 8080, targetPort: 8080 }]
```

Spring Boot's relaxed binding maps `SPRING_DATASOURCE_PASSWORD` to `spring.datasource.password`, so
twelve-factor config (BE-STORY-10) needs no code.

## Probes: liveness vs readiness vs startup

Kubernetes asks each container three different questions:

- **Liveness**: "Is this process broken beyond repair?" Failing it makes the kubelet **restart**
  the container. Use it for deadlocks and wedged states, nothing else.
- **Readiness**: "Should this pod receive traffic right now?" Failing it **removes the pod from the
  Service's endpoints**; nothing restarts. Used during start-up warm-up, shutdown and temporary
  overload.
- **Startup**: "Has it finished starting?" Until it succeeds, liveness and readiness checks are
  held off, so a slow JVM start is not mistaken for a dead process.

Spring Boot Actuator (SPRING-BOOT-11) provides `/actuator/health/liveness` and
`/actuator/health/readiness`, backed by the application's `LivenessState` and `ReadinessState`.
They are enabled automatically when Boot detects Kubernetes; elsewhere set
`management.endpoint.health.probes.enabled=true`.

**The rule that prevents outages:** liveness must check only the process itself. If liveness
includes the database, a database blip makes Kubernetes restart every pod at once, and the
restarts then hammer the recovering database: a cascade (DIST-SYS-3) you configured yourself. Be
cautious adding external checks even to readiness, since a shared dependency failing would pull
every pod out of the Service together.

## Rolling updates

Changing the Deployment's image starts a **rolling update**: new pods are created, and old ones are
removed only as new ones become **ready**. `maxSurge` is how many extra pods may exist during the
update; `maxUnavailable` how many may be missing. A new version that never becomes ready stalls the
rollout instead of taking the service down; `kubectl rollout undo deployment/orders` goes back.

Two consequences: readiness must be honest (ready only when it can serve), and for a while old and
new versions run **side by side**. Every API change and database migration must work with both,
hence additive "expand, then contract" schema changes.

## Requests, limits and CPU throttling

- A **request** is what the scheduler reserves: a pod is placed only on a node with that much free.
  HPA utilisation (below) is measured against it.
- A **limit** is the ceiling the kernel enforces.

They behave differently per resource. Memory is not compressible: exceed the limit and the
container is OOMKilled. So set memory request equal to the limit and size the heap inside it.

CPU is compressible: a CPU limit is enforced as a quota per scheduling period (by default 100 ms).
With a limit of 1 CPU, a container may use 100 ms of CPU time per 100 ms. A JVM running many GC
and JIT threads can burn that quota in the first 30 ms and then be **throttled**, frozen, for the
remaining 70 ms. That shows up as latency spikes with CPU usage that looks low on average, and as
very slow start-ups. Many teams therefore set a CPU request but no CPU limit, or a generous one;
follow your platform team's policy, and watch the container's throttling metric
(`container_cpu_cfs_throttled_periods_total`) when p99 latency is mysteriously bad.

## Autoscaling with HPA

A **HorizontalPodAutoscaler** changes a Deployment's replica count to hold a metric near a target.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: orders }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: orders }
  minReplicas: 3
  maxReplicas: 12
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }
```

It needs a metrics source (metrics-server) and CPU requests, since 70% means 70% *of the request*.
Scale-down waits through a stabilisation window (5 minutes by default) to avoid flapping. CPU is a
poor signal for I/O-bound services; custom metrics such as requests per second or Kafka consumer
lag often fit better. New JVM pods are slow at first (JIT warm-up), so scale before you are at the
limit.

## Graceful shutdown

Pods are deleted constantly: every rollout, scale-down and node drain. The sequence:

```text
pod marked Terminating
  ├─ (in parallel) endpoints controller removes the pod from Services; proxies and ingress update
  └─ kubelet runs preStop (sleep 10) ─► then sends SIGTERM to PID 1 (java)
        Spring Boot: readiness → refusing traffic; web server stops accepting new requests,
        finishes in-flight ones (up to spring.lifecycle.timeout-per-shutdown-phase, default 30 s);
        context closes (pools, Kafka consumers commit, executors stop)
  └─ after terminationGracePeriodSeconds in total: SIGKILL
```

The `preStop` sleep exists because removing the pod from load balancers is not instantaneous;
without it, some requests still arrive after the server has stopped accepting and fail with
connection errors. Spring Boot 3.4+ shuts down gracefully by default (`server.shutdown=graceful`;
set it explicitly on older versions). Make sure preStop plus the shutdown timeout fits inside
`terminationGracePeriodSeconds` (default 30 s), which is why the example raises it to 45. Newer
Kubernetes versions also offer a native `sleep` action for `preStop`, for images without a shell.

## Lab (~10 min)

**Break it: the JVM vs the container limit.** Needs Docker. Save this as `Hog.java` in an empty
folder and run the commands from that folder (in PowerShell use `${PWD}` instead of `"$PWD"`).

```java
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;

public class Hog {
    public static void main(String[] args) throws InterruptedException {
        System.out.println("max heap = " + Runtime.getRuntime().maxMemory() / (1024 * 1024) + " MB, cpus = "
                + Runtime.getRuntime().availableProcessors());
        List<byte[]> keep = new ArrayList<>();
        for (int i = 1; ; i++) {
            byte[] block = new byte[10 * 1024 * 1024];
            Arrays.fill(block, (byte) 1);              // touch the pages so the OS really commits them
            keep.add(block);
            System.out.println("holding " + i * 10 + " MB");
            Thread.sleep(20);
        }
    }
}
```

1. **Defaults.** `docker run --rm -m 512m --cpus=1 eclipse-temurin:21-jre java -XX:+PrintCommandLineFlags -version`.
   Find `MaxHeapSize` (about a quarter of 512 MB) and `-XX:+UseSerialGC` (one CPU, small memory:
   not "server class").
2. **Heap OOM.** `docker run --rm -m 512m -v "$PWD":/w -w /w eclipse-temurin:21-jdk java Hog.java`.
   It dies with `java.lang.OutOfMemoryError` near the reported max heap: a Java error, with a stack
   trace.
3. **Tune.** Add `-e JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75` and rerun: max heap roughly triples.
4. **Container OOM.** Replace the option with `-Xmx1g`, add `--memory-swap 512m` (so the container
   cannot spill into swap), rerun, then `echo $?`. No stack trace;
   the process just vanishes with exit code **137**: the kernel killed it for exceeding 512 MB.
   This is what `OOMKilled` looks like in `kubectl describe pod`.

**Optional (kind or minikube):** deploy the YAML above with any Boot app, run
`kubectl rollout restart deployment/orders` while a loop curls the Service, and check that no
request fails. Then delete the `preStop` hook and repeat under load.

## Gotchas

- **Fixed `-Xmx` equal to the container limit.** The heap fills the limit and off-heap memory pushes
  the container over: OOMKilled with no stack trace. Use `MaxRAMPercentage` and leave headroom.
- **Liveness probes that check dependencies.** A database blip restarts every pod at once. Liveness
  checks the process only; be careful with readiness too.
- **No startup probe on a slow-starting JVM.** Liveness kills the pod before it finishes starting,
  forever (`CrashLoopBackOff`). Add a startup probe with enough budget.
- **Shell-form `ENTRYPOINT`.** `SIGTERM` goes to `sh`, not to `java`; after the grace period the
  pod is killed mid-request. Use the exec form.
- **CPU limits throttling the JVM.** Low average CPU, high p99 and slow starts. Check throttling
  metrics; prefer requests without tight CPU limits if your platform allows.
- **`:latest` tags and secrets in images.** A mutable tag makes rollbacks and audits guesswork;
  secrets baked into a layer stay in the image history. Use immutable tags and inject secrets at
  run time.

## In interviews

Bank questions on this are rare as standalone prompts; it comes up inside
[Design a Payment Service](#/q/design-payment-system),
[Debugging requests across microservices](#/q/debugging-across-microservices),
[A system failure you handled](#/q/system-failure-and-fault-tolerance-story) and
[Re-architect Your Current Project Without Public Cloud](#/q/design-current-project-without-cloud).

Answer in four layers:

- **"Liveness vs readiness vs startup probe?"** *What:* restart vs remove from traffic vs hold off
  the other two during start-up. *Inside:* kubelet polls; readiness edits the Service's endpoints;
  Actuator exposes both states. *Where:* every Deployment. *What goes wrong:* dependency checks in
  liveness causing mass restarts, no startup probe on a slow JVM.
- **"Your pod keeps restarting with OOMKilled. What do you check?"** *What:* the kernel killed it
  for exceeding its memory limit. *Inside:* heap vs non-heap, 25% default heap, cgroup limit, exit
  137. *Where:* `kubectl describe pod`, container memory metrics, Native Memory Tracking
  (`-XX:NativeMemoryTracking=summary`). *What goes wrong:* `-Xmx` near the limit, too many threads,
  direct-buffer growth; fix with `MaxRAMPercentage`, a right-sized limit, or a leak hunt.
- **"How do you deploy without downtime?"** *What:* rolling update. *Inside:* `maxSurge` and
  `maxUnavailable`, readiness gating, graceful shutdown with preStop, `SIGTERM`, grace period.
  *Where:* every release. *What goes wrong:* dishonest readiness, non-backward-compatible schema
  changes while versions overlap, shell-form entrypoints dropping requests.

**Follow-up: "Requests vs limits?"** Requests drive scheduling and HPA maths; limits are enforced
ceilings. Memory over the limit kills, CPU over the limit throttles; set memory request = limit.

## Explain it in 2 minutes

*"How do you package and run a Spring Boot service on Kubernetes?"*

- Multi-stage Dockerfile: build with the JDK, run on a JRE, layered jar, non-root, exec-form entry.
- JVM sized to the container with `MaxRAMPercentage`, leaving room for non-heap memory.
- A Deployment with replicas, an immutable image tag, config from ConfigMap, secrets from Secret.
- Startup, liveness (process only) and readiness probes on Actuator's health groups.
- Requests and limits: memory request = limit; careful with CPU limits; HPA on a sensible metric.
- Rolling updates gated by readiness, and graceful shutdown: preStop, `SIGTERM`, drain, grace period.

## Check yourself

1. What is the difference between an image and a container?
2. Why does the Dockerfile copy dependencies before the application code?
3. A 1 GiB container runs a JVM with no flags. Roughly what is the max heap, and what would you set?
4. What happens when liveness fails, and when readiness fails?
5. Why add a `preStop` sleep when Spring Boot already shuts down gracefully?

### Answers

1. An image is an immutable, layered package; a container is a running, isolated process started
   from it. One image, many containers.
2. Layers are cached; dependencies change rarely, code changes on every commit, so a code change
   rebuilds and ships only the small top layer.
3. About 256 MB (25% of the limit). Set `-XX:MaxRAMPercentage=75.0` or similar, leaving room for
   metaspace, threads and other non-heap memory.
4. Liveness failure: the container is restarted. Readiness failure: the pod is removed from the
   Service's endpoints and gets no traffic, but keeps running.
5. Removal from Services and load balancers happens in parallel with termination and takes a
   moment; the sleep keeps the pod serving until traffic has stopped arriving, then `SIGTERM`
   starts the drain.
