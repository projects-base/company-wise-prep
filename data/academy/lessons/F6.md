## Where we are

F4 ran the method on a shortener, a rate limiter and a notification system, and F1 introduced
caches and consistent hashing as building blocks. This lesson designs two pieces of
**infrastructure** that other systems depend on: a **distributed cache** and a **metrics and
monitoring system**. The second has a Microsoft flavour: observability and live-site (on-call)
engineering appear in most of their job postings and in HLD follow-ups. This is a case-study
lesson, so take one case per sitting if you need to.

## The problem

```text
Cache:      "Design a distributed cache optimised for <this workload>."
            The interviewer pastes a workload. The design must change with it.

            and how do you find which of 400 services is at fault?"
```

Both reward the same habit: let the numbers and the failure modes drive the design.

## Case 1: distributed cache

### Requirements

```text
Functional:   get / put / delete by key, TTL per key, eviction when memory is full
NFR (sample workload): 1 TB of hot data, values ~1 KB, 1M reads/s, 100k writes/s,
              p99 < 2 ms inside the datacentre; may lose data (the DB is the source of truth),
              but must not serve very stale data for long
```

Ask at once which way the workload leans: read-heavy or write-heavy, small or large values, hot
keys or not, and **whether losing the cache is acceptable**. Each answer changes the design (see
the table at the end of this case).

### Estimates

```text
Memory:      assume ~50 GB usable per node → 1 TB / 50 GB ≈ 20 shards
Replicas:    1 replica per shard → 40 nodes
Throughput:  1.1M ops/s ÷ 20 shards ≈ 55k ops/s per primary → comfortable for an in-memory node
Network:     1M reads × 1 KB ≈ 1 GB/s across the cluster → ~50 MB/s per node
```

**So…** memory, not CPU, sets the node count. Throughput per node is modest **if keys are evenly
spread**, so hot keys are the real risk.

### High-level design

```text
 app ──► cache client library ──(consistent hashing on key)──► shard owner
           │  holds the cluster map                              │
           ▼                                                     ▼
   config / membership service (etcd-style, Raft)     [ shard 7 primary ] ──async──► [ shard 7 replica ]
   "which nodes own which ranges; who is primary"
```

**Routing options:**
- **Client-side** (the library hashes the key and connects directly): no extra hop, but every
  client needs the current cluster map.
- **Proxy** (clients talk to a routing proxy): simple clients, but one more hop and one more fleet
  to run.
- **Server-side redirect:** any node accepts a request and redirects to the owner. Redis Cluster,
  for example, splits the key space into 16,384 hash slots assigned to nodes, and tells clients
  where a slot lives.

### Inside one node

A hash map plus a doubly linked list gives **O(1) LRU** (least recently used) eviction: on each
access, move the entry to the head, and evict from the tail when memory is full. This is the
`lru-cache` coding problem, and interviewers like it when you connect the two.
- **TTL expiry:** expire **lazily** (check on read) plus an **active** sweep that samples keys with
  TTLs and deletes expired ones, so memory is reclaimed without scanning everything.
- **Eviction policy:** LRU is the default. LFU (least frequently used) is better when a few keys
  stay popular for a long time and a one-off scan would otherwise flush them.

### Deep dive 1: hot keys

One key (a celebrity profile, a config blob) gets 200k reads/s, so its shard melts while the others
sit idle.
- **Near cache:** each app server keeps a tiny in-process copy with a 1–5 s TTL. Most reads never
  leave the box.
- **Replicate hot keys** to several nodes (`key#1..key#N`) and pick one at random on read.
- **Request coalescing:** on a miss, only one caller loads from the DB. The rest wait for its result
  (F1's stampede fix).

### Deep dive 2: staying close to the database

Cache-aside with delete-on-write (F1) still has one race:

```text
reader: miss → reads OLD value from DB ...................... → SET key = OLD   ✗ stale until TTL
writer:              updates DB → DELETE key
```

The reader's slow `SET` lands after the writer's `DELETE`. Fixes: a short TTL as a backstop;
**versioned writes** (store the row's version, and refuse a `SET` older than what's there); or a
**lease** (on a miss, the cache hands out a token, and a `DELETE` invalidates it, so the late `SET`
is rejected). Name the race. Interviewers rarely expect a perfect fix, but they do expect you to see
it.

### Deep dive 3: failure and growth

- **A node dies:** the membership service notices missed heartbeats and promotes the replica.
  Because replication is async, a few recent writes may be lost, which is acceptable for a cache.
  If there's no replica, that shard's keys fall through to the DB, so protect the DB with coalescing
  and rate limits.
- **Adding nodes:** consistent hashing (F1) moves about 1/N of the keys. Warm the new node
  gradually, or accept a short dip in hit ratio.
- **Watch:** hit ratio, evictions/s, memory, p99 latency per node, hot-key detection (top keys by
  request rate).

### How the workload changes the design

| If the workload is… | Then… |
|---|---|
| Very read-heavy, tolerant of staleness | Near caches, more replicas, long TTLs |
| Write-heavy | Write-behind or no caching for those keys; watch replication lag |
| Large values (100 KB+) | Fewer keys per node; compress; maybe the CDN or an object store instead |
| Losing the cache would overload the DB | Replicate every shard; warm standby; coalescing everywhere |
| Strict freshness | Short TTL plus versioned writes or leases, or don't cache that data |

## Case 2: metrics and monitoring (telemetry)

### Three kinds of telemetry

**Telemetry** is the data a running system emits about itself. **Observability** is how well you
can answer new questions about the system's behaviour from that data. Three kinds, each with a job:

| Signal | What it is | Answers |
|---|---|---|
| **Metrics** | Numbers over time: `http_requests{service=checkout,status=500}` | "Is something wrong, and since when?" |
| **Logs** | Timestamped event records, ideally structured (JSON) | "What exactly happened in this request?" |
| **Traces** | One request's path across services, as timed spans sharing a **trace id** | "Which service made it slow?" |

A **correlation id** (or trace id) is generated at the edge and passed through every call and every
log line, so you can join all three signals for a single request. This case designs the metrics
pipeline, the part interviewers ask to see.

### Requirements

```text
Functional:   ingest metrics from all services and hosts; dashboards and ad-hoc queries;
              alert rules → page the on-call engineer; retention: raw 15 days, rollups 1 year
NFR:          100k hosts; alert within ~1 minute of a problem; the pipeline must never
              slow down or crash the services it monitors; it must stay up during their outages
```

A **time series** is one metric name plus one set of **tags** (labels), with a stream of
`(timestamp, value)` points. Every distinct tag combination is a separate series.

### Estimates

```text
Series:    100k hosts × 500 series each           = 50M active series
Points:    one point per series every 10 s        = 5M points/s
Raw size:  16 B per point (8 B time + 8 B value)  → 80 MB/s ≈ 7 TB/day
Compressed: Facebook's Gorilla paper reported roughly 1.4 B per point using
            delta-of-delta timestamps and XOR-encoded values → ~7 MB/s ≈ 600 GB/day
```

**So…** ingestion is a high-throughput, write-heavy stream. Compression is what makes retention
affordable. Queries mostly read recent data, so keep recent blocks in memory.

### High-level design

```text
 hosts/services
   [ agent ]  pre-aggregates, buffers on disk, drops low-priority data if backed up
      │
      ▼
 ingestion gateway  (auth, validation, per-tenant rate limits, cardinality limits)
      │
      ▼
 stream (Kafka / Event Hubs, partitioned by series id)  ← decouples bursts from storage
      │                         │
      ▼                         ▼
 TSDB writers              stream aggregator ──► rollups (1 min, 1 h)
      │                         └──► alert evaluator ──► notification system (F4) ──► on-call
      ▼
 time-series DB: shards by hash(series id); time-partitioned blocks
   recent ~2 h in memory → compressed blocks on disk → old blocks in object storage
      │
      ▼
 query service (fan out to shards, merge) ──► dashboards, ad-hoc queries
```

**Push or pull?** Agents can **push** to the gateway, or the system can **pull** (scrape) an
endpoint on each service, which is the Prometheus model. Pull makes it easy to see when a target is
down (the scrape fails) and keeps load under the collector's control. Push suits short-lived jobs
and crossing network boundaries. Pick one and say why.

### Data model

```text
series index:   series_id = hash(name + sorted tags) → {name, tags}
inverted index: tag "service=checkout" → [series ids]        ← "all series for checkout"
data blocks:    (series_id, block_start_time) → compressed points for e.g. 2 hours
rollups:        same shape, at 1-minute and 1-hour resolution, kept longer
```

### Deep dive 1: cardinality

**Cardinality** is the number of distinct series. One careless tag such as `user_id` or
`request_id` multiplies series by millions, and the index and memory explode. Enforce limits per
metric at the ingestion gateway, reject or drop new series over the limit, and alert the owning
team. High-cardinality detail belongs in **logs and traces**, not metrics.

### Deep dive 2: percentiles can't be averaged

The p99 latency of the fleet isn't the average of each host's p99 (the lab proves it). Hosts should
send **histograms**: counts per latency bucket, with the same bucket bounds everywhere. Counts can
simply be added across hosts and time, and the percentile is computed afterwards from the merged
counts. The precision is limited by the bucket width, so choose bounds around your SLO threshold.

### Deep dive 3: alerting that people trust

An **SLI (service level indicator)** is a measured number, such as "the fraction of checkout
requests that succeed in under 300 ms". An **SLO (objective)** is the target, say 99.9% over 30
days. The **error budget** is what's left over: 0.1% of requests may be bad.

- Static thresholds ("CPU > 80%") page people for things users don't notice. Alert on **symptoms
  users feel** (errors, latency) first.
- **Burn-rate alerts** page when the error budget is being spent far faster than sustainable (for
  example, at a rate that would exhaust 30 days of budget in a couple of days), checked over both a
  short and a long window so a brief blip doesn't page anyone. The Google SRE Workbook describes
  this approach.
- Require the condition to hold for a duration ("for 5 minutes") to avoid **flapping** (an alert
  firing and clearing repeatedly).
- **Monitor the monitor:** a heartbeat alert that fires when data *stops arriving*. Silence must
  never look like health.

### Deep dive 4: live-site, the Microsoft angle

Microsoft calls the on-call owner of a service the **DRI** (directly responsible individual), and
10 of the 17 postings in the dossier require on-call ownership. Interviewers ask how your design
behaves during an incident:

```text
detect  → alert fires on an SLO burn rate (not a customer email)
triage  → DRI acknowledges; severity by user impact; dashboard: which region/version/instance?
mitigate FIRST → roll back the last deploy, fail over a region, turn off a feature flag
diagnose → traces show the slow span; logs with that correlation id show the error
learn   → blameless postmortem; repair items (a missing alert, a missing timeout)
```

Two habits score well: **mitigate before you root-cause** (restore users, then understand), and
**safe deployment**: staged rollouts to small slices first, with automatic rollback when health
metrics regress. Seven of the 17 postings mention CI/CD and safe deployment. Telemetry is what
makes the rollback automatic.

### Follow-ups

- **"The monitoring pipeline is overloaded during a big incident."** Exactly when you need it most.
  Agents buffer locally and shed low-priority metrics first. The gateway applies back-pressure (F2)
  per tenant, and alerting reads from the stream aggregator so it isn't blocked behind slow storage
  writes.
- **"Checkout p99 doubled in one region."** Slice the latency histogram by region, version and
  instance. Find the dimension that explains it, follow a trace exemplar to the slow span, then
  check that service's recent deploys.

## Lab (~10 min)

Prove that averaging p99s lies, and that histograms fix it. Save this as `PercentileLab.java` and
run `java PercentileLab.java`.

```java
import java.util.Arrays;
import java.util.Random;

public class PercentileLab {

    static double p99(double[] values) {
        double[] sorted = values.clone();
        Arrays.sort(sorted);
        return sorted[(int) Math.ceil(0.99 * sorted.length) - 1];
    }

    /** Buckets with fixed upper bounds (ms). Servers ship counts; counts can simply be added. */
    static final double[] BOUNDS = {10, 20, 30, 40, 50, 60, 80, 100, 200, 500, 1000, 5000};

    static long[] histogram(double[] values) {
        long[] counts = new long[BOUNDS.length + 1];          // last bucket = above the top bound
        for (double v : values) {
            int i = 0;
            while (i < BOUNDS.length && v > BOUNDS[i]) i++;
            counts[i]++;
        }
        return counts;
    }

    static double p99FromHistogram(long[] counts) {
        long total = Arrays.stream(counts).sum();
        long target = (long) Math.ceil(0.99 * total), seen = 0;
        for (int i = 0; i < counts.length; i++) {
            seen += counts[i];
            if (seen >= target) return i < BOUNDS.length ? BOUNDS[i] : Double.POSITIVE_INFINITY;
        }
        return Double.NaN;
    }

    public static void main(String[] args) {
        Random rnd = new Random(42);
        // Three servers. Server C is unhealthy and gets little traffic, but it is slow.
        double[] a = new double[100_000], b = new double[100_000], c = new double[1_000];
        for (int i = 0; i < a.length; i++) a[i] = 10 + rnd.nextExponential() * 8;
        for (int i = 0; i < b.length; i++) b[i] = 10 + rnd.nextExponential() * 8;
        for (int i = 0; i < c.length; i++) c[i] = 300 + rnd.nextExponential() * 400;

        System.out.printf("p99 per server: A=%.0f  B=%.0f  C=%.0f ms%n", p99(a), p99(b), p99(c));
        System.out.printf("average of the three p99s: %.0f ms   <- meaningless%n",
                (p99(a) + p99(b) + p99(c)) / 3);

        double[] all = new double[a.length + b.length + c.length];
        System.arraycopy(a, 0, all, 0, a.length);
        System.arraycopy(b, 0, all, a.length, b.length);
        System.arraycopy(c, 0, all, a.length + b.length, c.length);
        System.out.printf("true fleet p99 (all raw values): %.0f ms%n", p99(all));

        long[] merged = new long[BOUNDS.length + 1];
        for (double[] server : new double[][] {a, b, c}) {
            long[] h = histogram(server);
            for (int i = 0; i < merged.length; i++) merged[i] += h[i];
        }
        System.out.printf("fleet p99 from merged histograms: <= %.0f ms (bucket upper bound)%n",
                p99FromHistogram(merged));
    }
}
```

**What you should see** (with seed 42): per-server p99s of about 47, 47 and over 2,000 ms; an
"average of p99s" of about 750 ms; a true fleet p99 of about 52 ms; and the merged histogram saying
"≤ 60 ms", which is correct to within one bucket.

**Notice the second lesson:** the fleet p99 looks healthy, yet every request on server C is
terrible. That's why dashboards slice by instance, region and version. An aggregate can hide a
sick minority.

**Break it:** remove the 50 and 60 ms bounds and rerun. The histogram answer gets coarser ("≤ 80
ms"). Bucket bounds are a precision trade-off you choose up front.

## Gotchas

- **Treating the cache as the source of truth.** If losing it loses data or takes down the DB, it's
  a database. Design the fallback path and its load.
- **Ignoring hot keys.** Even hashing doesn't help when one key gets most of the traffic. Use near
  caches, hot-key replication and coalescing.
- **Averaging percentiles** across hosts or time windows. Ship histograms and merge counts.
- **Unbounded tag values** (`user_id` as a metric tag) explode cardinality and can take the
  monitoring system down.
- **Paging on causes, not symptoms.** CPU alerts wake people for nothing. Page on SLO burn, and use
  cause metrics for diagnosis.
- **A monitoring agent that can hurt the host.** Agents must cap memory and CPU and drop data rather
  than block the application.

## Explain it in 2 minutes

*"Design a metrics monitoring system for a large fleet."*

- Scope: 100k hosts and 50M series at 10 s resolution gives about 5M points/s, which is a
  write-heavy stream.
- Pipeline: agents (buffer, shed), gateway (limits), a stream, TSDB writers plus a stream
  aggregator.
- Storage: shard by series id, use time blocks, compression (delta-of-delta, XOR), rollups for
  long retention.
- Correctness: histograms for percentiles, and cardinality limits.
- Alerting: SLO burn-rate alerts on user-facing symptoms, plus a heartbeat for missing data.
- Live-site: mitigate first, with traces and correlation ids for diagnosis and staged rollouts with
  automatic rollback.

## Check yourself

1. In the sample cache workload, what sets the number of nodes: memory or CPU? Why?
2. Describe the race that leaves a stale value in a cache-aside cache even with delete-on-write.
3. Why can't you average p99s across hosts? What do you ship instead?
4. What's wrong with tagging a request-latency metric with `request_id`?
5. During an incident, what comes first: root cause or mitigation? Give one mitigation.

### Answers

1. Memory. 1 TB at about 50 GB per node needs about 20 shards, and that gives each node only about
   55k ops/s, which is easy for an in-memory store.
2. A reader misses and reads the old value. A writer then updates the DB and deletes the key. The
   reader finally sets the old value, which stays until its TTL expires.
3. Percentiles don't combine linearly, and a low-traffic outlier distorts the average. Ship
   histograms (bucket counts), add them up, then compute the percentile.
4. Every request creates a new series, so cardinality grows without limit and the TSDB's index and
   memory blow up. Put request ids in logs and traces.
5. Mitigation, for example rolling back the last deployment or failing over to a healthy region.
   Root cause comes after users are restored.
