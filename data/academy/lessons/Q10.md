## Where we are

From DB-SQL-1 you can join tables along foreign keys, and from DB-SQL-2 you can group, aggregate and
write CTEs. Every query so far ran against a schema someone else designed. This lesson is about
designing it yourself: which tables, which keys, which constraints. It also covers when to break the
textbook rules on purpose.

## The problem

A food-ordering startup kept its first version in one table, because "it was quick":

| order_id | customer_email | customer_name | restaurant | restaurant_city | items | total |
|---|---|---|---|---|---|---|
| 101 | asha@example.com | Asha | Spice Hut | Pune | Paneer Tikka x2, Naan x3 | 640.00 |
| 102 | asha@example.com | Asha R | Spice Hut | Pune | Naan x1 | 60.00 |
| 103 | ben@example.com | Ben | Dosa Corner | Bengaluru | Masala Dosa x2 | 240.00 |

Three bugs are already in it:

- **Update anomaly.** Asha changed her name, and only order 102 got the update. Which name is right?
- **Insert anomaly.** A new restaurant has signed up but has no orders yet. There is nowhere to store it.
- **Delete anomaly.** Delete order 103 (a refund) and you lose the only record that Dosa Corner exists.

And "how many naans did Spice Hut sell?" means parsing strings. Data modeling is how you avoid this.

## From requirements to an ER model

An **ER (entity-relationship) model** is a sketch of the domain before you write any SQL. It has three
parts:

- An **entity** is a thing you store many of, each with an identity: customer, restaurant, menu item,
  order.
- An **attribute** is a fact about one entity: a customer's email, a menu item's price.
- A **relationship** connects entities: a customer *places* orders, an order *contains* menu items.

Read the requirements and underline the nouns (candidate entities) and verbs (candidate relationships).
Then, for every relationship, ask "how many on each side?". That question is **cardinality**.

```text
customer 1 ──< order >── 1 restaurant 1 ──< menu_item
                  │                             │
                  1                             1
                  └────────< order_line >───────┘
  1 ──<  means "one on the left, many on the right"
```

An order has many menu items, and a menu item appears in many orders: that is many-to-many. In tables
it always becomes a third table, here `order_line`.

## Primary keys: natural or surrogate

A **natural key** is a real-world value that is already unique, such as an email or a PAN number. A
**surrogate key** is a meaningless value the database generates, such as `id = 42`.

Prefer surrogate keys for entities. Natural keys look unique until they aren't. People change emails,
and a PAN gets entered wrongly and must be corrected. Then every foreign key that copied the value must
change too. Keep the natural key, but as a `UNIQUE` constraint next to the surrogate.

Which surrogate type?

| Choice | Size | Good | Watch out |
|---|---|---|---|
| `BIGINT` identity / sequence | 8 bytes | small, ordered, fast B-tree inserts | guessable; one DB hands them out |
| UUID v4 (random) | 16 bytes | made anywhere (app, offline, many shards) | random inserts scatter across the index |
| UUID v7 (time-ordered) | 16 bytes | made anywhere *and* roughly ordered | needs a library, or PostgreSQL 18's `uuidv7()` |

A **sequence** is a database object that hands out increasing numbers. `GENERATED ... AS IDENTITY`
is the standard way to attach one to a column. Why do random UUIDs hurt? The B-tree index (DB-SQL-6)
must insert each new key at a random leaf page. That splits pages and keeps the whole index hot in
memory. Ordered keys always append at the right edge.

For JPA, prefer `GenerationType.SEQUENCE` over `IDENTITY`. With `IDENTITY`, Hibernate must run each
`INSERT` at once to learn the id, so it can't batch the inserts. With a sequence and an
`allocationSize`, it reserves a block of ids up front and batches the inserts.

Never expose a sequential id where guessing it is a risk (`/orders/1002` → try `/orders/1003`).
Authorise every read anyway. A UUID only hides the id, it doesn't protect anything.

## Foreign keys and ON DELETE

A foreign key (DB-SQL-1) also decides what happens when the parent row is deleted:

| Option | Delete a restaurant that has menu items... |
|---|---|
| `NO ACTION` / `RESTRICT` (default is `NO ACTION`) | fails. You must delete children first |
| `CASCADE` | deletes its menu items too |
| `SET NULL` | keeps the items, sets `restaurant_id` to NULL |

Use `CASCADE` only for true parts of the parent: an order's lines live and die with the order. Never
cascade from a customer to their orders. Orders are financial records, and one careless delete would
wipe history.

One PostgreSQL detail matters in production. **Postgres does not index foreign-key columns
automatically.** Deleting a parent, or joining parent to child, then scans the child table. Add the
index yourself (DB-SQL-6).

## The three relationship shapes

```sql
-- one-to-many: the FK lives on the "many" side
CREATE TABLE menu_item (id BIGINT PRIMARY KEY, restaurant_id BIGINT NOT NULL REFERENCES restaurant(id));

-- one-to-one: an FK that is also UNIQUE (or is the primary key itself)
CREATE TABLE customer_profile (customer_id BIGINT PRIMARY KEY REFERENCES customer(id), bio TEXT);

-- many-to-many: a join table with two FKs; the pair is the key
CREATE TABLE restaurant_cuisine (
  restaurant_id BIGINT REFERENCES restaurant(id),
  cuisine_id    BIGINT REFERENCES cuisine(id),
  PRIMARY KEY (restaurant_id, cuisine_id)
);
```

A **join table** (also called a junction or link table) turns one many-to-many into two one-to-manys.
It often grows its own columns. `order_line` is a join table with `quantity` and `unit_price`, and
that's a sign it is a real entity.

Ask why a one-to-one table exists at all. Good reasons: optional data most rows don't have, large
columns you rarely read, or columns with stricter access rules (e.g. KYC documents).

## Constraints are the last line of defence

Your Java validation runs in one service. The database is shared by every service, migration script,
admin console and 2 a.m. hotfix. Put the rules that must *never* break in the schema:

```sql
quantity    INTEGER NOT NULL CHECK (quantity > 0),
email       VARCHAR(254) NOT NULL UNIQUE,
status      VARCHAR(20) NOT NULL CHECK (status IN ('PLACED', 'PREPARING', 'DELIVERED', 'CANCELLED'))
```

- `NOT NULL` is the default you want. Allow NULL only when "unknown" or "not yet" is a real state.
- `UNIQUE` is the only safe way to prevent duplicates. A "check then insert" in Java races under
  concurrency (DB-SQL-7). The constraint doesn't.
- `CHECK` encodes row-level rules: positive amounts, `end_at > start_at`, allowed statuses.

## Normalization, one step at a time

**Normalization** is reorganising tables so each fact is stored once. It removes the three anomalies.
It relies on one idea. A **functional dependency** `A → B` means "knowing A tells you exactly one B".
Email determines customer name. Order id determines restaurant.

**1NF: atomic values, no repeating groups.** The `items` column holds a list, which breaks first normal
form. Split it so each row holds one value per column:

| order_id | item | qty | unit_price | customer_email | customer_name | restaurant | restaurant_city |
|---|---|---|---|---|---|---|---|
| 101 | Paneer Tikka | 2 | 200.00 | asha@example.com | Asha | Spice Hut | Pune |
| 101 | Naan | 3 | 80.00 | asha@example.com | Asha | Spice Hut | Pune |

The key is now `(order_id, item)`.

**2NF: no partial dependencies.** With a composite key, every non-key column must depend on the
*whole* key. Here `customer_email`, `restaurant`, and the rest depend only on `order_id`. Move them
out:

```text
order      (order_id PK, customer_email, customer_name, restaurant, restaurant_city)
order_line (order_id, item, qty, unit_price)   PK (order_id, item)
```

**3NF: no transitive dependencies.** Inside `order`, `customer_email → customer_name` and
`restaurant → restaurant_city`. Those are facts about the customer and the restaurant, not the order.
Move them to their own tables, each with a surrogate key:

```text
customer   (id PK, email UNIQUE, name)
restaurant (id PK, name, city)
order      (id PK, customer_id FK, restaurant_id FK, placed_at)
menu_item  (id PK, restaurant_id FK, name, price)
order_line (order_id FK, menu_item_id FK, qty, unit_price)
```

The rule to remember: every non-key column depends on "the key, the whole key, and nothing but the
key".

**BCNF** (Boyce-Codd normal form) is a stricter 3NF. *Every* determinant must be a candidate key, even
when the dependent column is itself part of a key. It rarely differs from 3NF in practical schemas.
Saying that much in an interview is enough.

Notice `order_line.unit_price`. Isn't that a copy of `menu_item.price`? No. It is a different fact:
the price *when the order was placed*. The menu price will change, but the order's price must not.
Snapshotting it is correct modeling, not denormalization.

## When and how to denormalize

**Denormalization** means storing a derived or duplicated fact on purpose, to make reads cheaper.
Normalize first, then denormalize only where a measured read path needs it.

Common, defensible cases:

- **Counters and aggregates.** `restaurant.rating_avg` and `rating_count`, so the listing page doesn't
  aggregate every review on every view.
- **Copied display fields.** `order.restaurant_name`, so the "my orders" list skips a join. A copy
  can also be a deliberate snapshot.
- **Reporting tables.** Daily sales per restaurant, rebuilt by a job or kept as a materialized view
  (a stored query result, refreshed on demand). DB-SQL-10's CQRS read models are this idea at scale.

The cost is always the same: **one fact now lives in two places, and they can drift.** Pick how you
keep them in sync, and say it out loud in an interview:

1. In the same transaction as the write: simplest and consistent, but writes get slower, and a hot
   counter row gets contended.
2. With a database trigger: hidden logic, easy to forget in reviews.
3. Asynchronously from an event (DIST-SYS-2): fast writes, eventually consistent, needs a
   reconciliation job for drift.

## Practical column decisions

**Soft vs hard delete.** A **soft delete** sets `deleted_at` instead of removing the row. You keep
history and can undo. The costs: every query must filter `deleted_at IS NULL`, and `UNIQUE (email)`
now blocks re-registering a deleted email. Postgres fixes that with a partial unique index,
`CREATE UNIQUE INDEX ... ON customer (email) WHERE deleted_at IS NULL`. Privacy laws (such as India's
DPDP Act) can require real erasure of personal data, so soft delete isn't a universal answer.
Hibernate 6.4+ has `@SoftDelete`.

**Audit columns.** `created_at`, `updated_at`, and often `created_by`, plus a `version` column for
optimistic locking (DB-SQL-7). If you need *what* changed, use a separate history table, not more
columns.

**Money.** Never `FLOAT`/`DOUBLE`. Binary floating point can't represent 0.10 exactly. Use
`NUMERIC(12,2)` with Java `BigDecimal`, or `BIGINT` in the smallest unit (paise) with Java `long`.
Store the currency too if there can ever be more than one.

**Timestamps.** Use `TIMESTAMP WITH TIME ZONE` (`timestamptz`) for moments in time. Postgres
converts the value to UTC and stores the instant, not the zone. Plain `TIMESTAMP` is a wall-clock
reading with no zone, so the same value means different moments in Mumbai and London. Map it to
`Instant` or `OffsetDateTime` in Java.

**Enums.** Three options:

- `VARCHAR` + `CHECK`: simple and readable. Adding a value needs a migration.
- A lookup table (`order_status(code PK, label)`) + FK: values become data, can carry extra columns,
  and change without DDL.
- A Postgres `ENUM` type: compact, but removing or renaming a value is awkward.

Use text + CHECK for small, stable sets, and a lookup table when the business edits the list. In JPA,
always use `@Enumerated(EnumType.STRING)`. `ORDINAL` stores 0, 1, 2, so inserting a constant in the
middle silently changes the meaning of every row.

## How this maps to JPA

SPRING-BOOT-7 covers JPA in depth. The modeling rules carry over directly:

```java
@Entity
class MenuItem {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)   // owning side: holds the FK column
    @JoinColumn(name = "restaurant_id")
    Restaurant restaurant;
}

@Entity
class Restaurant {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE) Long id;

    @OneToMany(mappedBy = "restaurant")                     // inverse side: no column, just a view
    List<MenuItem> menu = new ArrayList<>();
}
```

- The **owning side** is the entity whose table holds the FK. In a one-to-many that's always the
  `@ManyToOne`. Hibernate writes the FK only from the owning side. Setting just
  `restaurant.getMenu().add(item)` saves nothing.
- `@ManyToOne` is **EAGER by default**. Make it `LAZY`, or you get N+1 queries (DB-SQL-8).
- **Be careful with `@ManyToMany`.** It hides the join table, so you can't add `quantity` or
  `created_at` later without remapping. Mapped as a `List`, Hibernate may delete every link row and
  re-insert them on a change. Model the join table as its own entity (`OrderLine`) with two
  `@ManyToOne`s.

## Lab (~10 min)

Design the schema for the food-ordering app. Requirements:

1. Customers have a unique email, a name and an optional phone.
2. Restaurants have a name and city. A restaurant is tagged with several cuisines, and a cuisine
   covers many restaurants.
3. Each restaurant has a menu. Item names are unique *within* a restaurant. Prices are positive.
4. An order belongs to one customer and one restaurant. It has a status (PLACED, PREPARING,
   DELIVERED, CANCELLED), a placed time, and lines with a quantity and the price at order time.
5. Restaurant listing pages show the average rating and the number of ratings, without aggregating.

Write DDL that runs on PostgreSQL and H2, then compare it with the model answer in **Answers**. Then
try to break it: insert a line with `quantity = 0`, a second item called "Naan" for the same
restaurant, and a status of `'LOST'`. Each should fail with a constraint violation.

## Gotchas

- **Unindexed foreign keys.** Postgres doesn't create them. Parent deletes and joins scan the child.
  Index every FK you join or delete through.
- **`ON DELETE CASCADE` on business records.** Cascade only from a parent to its true parts (an order
  to its lines), never from a customer to their orders.
- **Natural keys as primary keys.** Emails and phone numbers change. Use a surrogate PK plus a
  `UNIQUE` constraint on the natural key.
- **Money in `double`.** Rounding errors appear in totals. Use `NUMERIC` with `BigDecimal`, or integer
  paise with `long`.
- **`EnumType.ORDINAL`.** Reordering the Java enum silently rewrites the meaning of stored data. Use
  `STRING`.
- **Denormalizing without a sync plan.** Every copy needs an owner: same transaction, trigger or
  event, plus a way to detect drift.

## In interviews

The common shapes:

- "Design the tables for X" (an e-commerce store, a library, a parking lot, a betting platform).
  Start from entities and cardinalities, then keys, then constraints, then the two or three main
  queries and their indexes.
- "Normalize this table." Name each anomaly, then walk 1NF → 2NF → 3NF and state the dependency each
  step removes.
- "Why would you denormalize?" Read-heavy paths, counters, reporting. Name the cost (drift, write
  amplification) and the sync mechanism.

**Typical follow-up:** "UUID or bigint for the primary key?" A strong answer: bigint identity when one
database assigns ids. Use UUIDs when ids must be created outside the database or across shards, and
prefer v7 so inserts stay ordered. Either way, authorise every access.

**Another follow-up:** "The menu price changes. What happens to old orders?" Nothing, because
`order_line.unit_price` snapshots the price at order time.

## Explain it in 2 minutes

*"Take me from a requirements paragraph to a schema."*

1. Nouns become entities, verbs become relationships. Decide each relationship's cardinality.
2. Surrogate primary keys, with natural keys as `UNIQUE`. Bigint identity unless ids are created
   outside the DB.
3. One-to-many puts the FK on the many side. Many-to-many gets a join table, often a real entity.
4. Constraints (`NOT NULL`, `UNIQUE`, `CHECK`, FKs with a chosen `ON DELETE`) enforce the rules every
   client must obey.
5. Normalize to 3NF so each fact lives once and the anomalies disappear.
6. Denormalize only for measured read paths, with an explicit way to keep copies in sync.

## Check yourself

1. Name the three anomalies, with one example each from the flat orders table.
2. A table has key `(order_id, item_id)` and a column `customer_name`. Which normal form does it break,
   and why?
3. Why does `IDENTITY` generation stop Hibernate from batching inserts?
4. Is `order_line.unit_price` a denormalization? Why or why not?
5. Your app soft-deletes customers. A deleted customer re-registers with the same email and gets a
   unique-violation error. Fix it in Postgres.

### Answers

1. Update: Asha's name changed in only one row. Insert: you can't add a restaurant with no orders.
   Delete: deleting Dosa Corner's only order loses the restaurant.
2. 2NF. `customer_name` depends on `order_id` alone, which is only part of the composite key: a
   partial dependency.
3. The id comes from the `INSERT` itself, so Hibernate must execute each insert immediately to learn
   the id. A sequence lets it fetch ids first, in blocks, and batch the inserts.
4. No. It records a different fact, the price at order time, which must not change when the menu
   does.
5. Replace `UNIQUE (email)` with a partial unique index:
   `CREATE UNIQUE INDEX uq_customer_email_live ON customer (email) WHERE deleted_at IS NULL;`

Lab model answer (runs on PostgreSQL and H2 2.x):

```sql
CREATE TABLE customer (
  id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  email      VARCHAR(254) NOT NULL UNIQUE,
  name       VARCHAR(100) NOT NULL,
  phone      VARCHAR(20),
  created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE restaurant (
  id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name         VARCHAR(100) NOT NULL,
  city         VARCHAR(60)  NOT NULL,
  rating_sum   INTEGER NOT NULL DEFAULT 0 CHECK (rating_sum >= 0),   -- denormalized, kept in the
  rating_count INTEGER NOT NULL DEFAULT 0 CHECK (rating_count >= 0)  -- same transaction as each rating
);

CREATE TABLE cuisine (
  id   BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE restaurant_cuisine (
  restaurant_id BIGINT NOT NULL REFERENCES restaurant(id) ON DELETE CASCADE,
  cuisine_id    BIGINT NOT NULL REFERENCES cuisine(id),
  PRIMARY KEY (restaurant_id, cuisine_id)
);

CREATE TABLE menu_item (
  id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  restaurant_id BIGINT NOT NULL REFERENCES restaurant(id),
  name          VARCHAR(100) NOT NULL,
  price_paise   BIGINT NOT NULL CHECK (price_paise > 0),
  available     BOOLEAN NOT NULL DEFAULT TRUE,
  CONSTRAINT uq_menu_item_name UNIQUE (restaurant_id, name)
);

CREATE TABLE customer_order (                       -- "order" is a reserved word
  id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  customer_id   BIGINT NOT NULL REFERENCES customer(id),
  restaurant_id BIGINT NOT NULL REFERENCES restaurant(id),
  status        VARCHAR(20) NOT NULL
                CHECK (status IN ('PLACED', 'PREPARING', 'DELIVERED', 'CANCELLED')),
  placed_at     TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
  version       INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE order_line (
  order_id         BIGINT NOT NULL REFERENCES customer_order(id) ON DELETE CASCADE,
  menu_item_id     BIGINT NOT NULL REFERENCES menu_item(id),
  quantity         INTEGER NOT NULL CHECK (quantity > 0),
  unit_price_paise BIGINT NOT NULL CHECK (unit_price_paise > 0),   -- snapshot, not a copy
  PRIMARY KEY (order_id, menu_item_id)
);

CREATE INDEX ix_menu_item_restaurant ON menu_item (restaurant_id);
CREATE INDEX ix_order_customer       ON customer_order (customer_id, placed_at);
CREATE INDEX ix_order_restaurant     ON customer_order (restaurant_id, placed_at);
CREATE INDEX ix_order_line_item      ON order_line (menu_item_id);
CREATE INDEX ix_restaurant_cuisine_c ON restaurant_cuisine (cuisine_id);
```

Design notes: the average rating is `rating_sum / rating_count`, computed on read, so the stored
pair never needs a division to stay correct. The order total isn't stored. It is
`SUM(quantity * unit_price_paise)` over the lines, and you'd add a `total_paise` column only if a
measured read path needed it. `restaurant_cuisine` and `order_line` lead with their first FK in the
primary key, so only the second FK needs its own index.
