## Where we are

From B3 you have atomics, `ConcurrentHashMap` and blocking queues. From B4 you have executors, bounded queues and backpressure. This lesson uses them to solve the three concurrency problems interviewers ask most: **producer-consumer with a bounded buffer**, a **thread-safe LRU cache**, and a **token-bucket rate limiter**. You get complete code for each, its complexity, and the trade-offs you will be asked to defend.

## The problem

In a senior round, "make it thread-safe" is where an ordinary solution gets separated from a strong one. The interviewer wants three things:

- **Working code**: no lost wake-ups, no races, no deadlock.
- **Reasoning**: why `while` and not `if`, and why a read needs a lock.
- **Trade-offs**: one lock or many, exact or approximate, one machine or distributed.

We go from writing the primitive by hand to using the JDK's version, because interviewers often ask for both.

## 1a. Producer-consumer by hand: `wait` and `notifyAll`

**Producers** create work items and **consumers** process them. A **bounded buffer** between them holds at most N items. Producers must wait while it is full, and consumers must wait while it is empty. That waiting is the backpressure from B4.

To wait for a condition inside `synchronized`, Java gives every monitor three methods:

- `wait()` **atomically releases the monitor** and suspends the thread until it is notified. Before `wait()` returns, the thread re-acquires the monitor.
- `notify()` wakes one waiting thread. `notifyAll()` wakes all of them.
- All three must be called while holding that object's monitor. Otherwise they throw `IllegalMonitorStateException`.

```java
class BoundedBuffer<T> {
    private final Object[] items;
    private int head, tail, count;           // ring buffer: take at head, put at tail

    BoundedBuffer(int capacity) { items = new Object[capacity]; }

    public synchronized void put(T item) throws InterruptedException {
        while (count == items.length) wait(); // WHILE, not if: re-check after every wake-up
        items[tail] = item;
        tail = (tail + 1) % items.length;
        count++;
        notifyAll();                          // wake consumers (and producers; they re-check)
    }

    @SuppressWarnings("unchecked")
    public synchronized T take() throws InterruptedException {
        while (count == 0) wait();
        T item = (T) items[head];
        items[head] = null;                   // let GC reclaim it
        head = (head + 1) % items.length;
        count--;
        notifyAll();
        return item;
    }
}
```

**Why `while` and not `if`?** There are two reasons:

1. **Spurious wake-ups.** The JVM is allowed to return from `wait()` even though nobody called `notify`.
2. **Stolen conditions.** Between being notified and re-acquiring the monitor, another consumer can take the item first. When this thread finally runs, the buffer is empty again.

So the rule is: **always wait inside a loop that re-checks the condition.**

**Why `notifyAll` and not `notify`?** Producers and consumers wait in the *same* wait set, the monitor's single queue of waiting threads. `notify()` might wake a producer when the buffer just became non-empty, or a consumer when it just became non-full. The thread that wakes re-checks, goes back to sleep, and the thread that should have woken never does. If that keeps happening, every thread ends up waiting: a hang. `notifyAll` wakes everyone, and the loops sort out who proceeds.

Complexity: `put` and `take` are O(1), and the buffer uses O(capacity) space. The cost of `notifyAll` is a "thundering herd": many threads wake up, but only one makes progress.

## 1b. Two conditions: what `ArrayBlockingQueue` does

A `ReentrantLock` can have several `Condition`s, which are separate wait sets. Producers wait on `notFull` and consumers on `notEmpty`, so `signal()` (the equivalent of `notify`) always wakes the right kind of thread:

```java
private final ReentrantLock lock = new ReentrantLock();
private final Condition notFull = lock.newCondition();
private final Condition notEmpty = lock.newCondition();

public void put(T item) throws InterruptedException {
    lock.lock();
    try {
        while (count == items.length) notFull.await();   // only producers wait here
        items[tail] = item; tail = (tail + 1) % items.length; count++;
        notEmpty.signal();                                // wake exactly one consumer
    } finally { lock.unlock(); }
}
// take() mirrors it: await notEmpty, signal notFull
```

`ArrayBlockingQueue` is essentially this design. `LinkedBlockingQueue` goes one step further and uses two locks, one for `put` and one for `take`, so a producer and a consumer can work at the same time.

## 1c. Producer-consumer the production way: `BlockingQueue`

In real code you would never write the buffer yourself:

```java
static final String POISON = "__STOP__";       // a sentinel value that means "no more work"

static void run() throws InterruptedException {
    BlockingQueue<String> queue = new ArrayBlockingQueue<>(100);   // bounded: backpressure
    int consumers = 4;
    try (ExecutorService pool = Executors.newFixedThreadPool(consumers + 1)) {
        pool.submit(() -> {                                        // producer
            for (int i = 0; i < 1_000; i++) queue.put("job-" + i); // blocks while full
            for (int c = 0; c < consumers; c++) queue.put(POISON); // one pill per consumer
            return null;
        });
        for (int c = 0; c < consumers; c++) {
            pool.submit(() -> {                                    // consumer
                for (String job = queue.take(); !job.equals(POISON); job = queue.take()) {
                    process(job);                                  // take() blocks while empty
                }
                return null;
            });
        }
    }   // close() waits for all of them
}
```

There are two ways to shut the pipeline down:

- A **poison pill**, as above: a special item that tells each consumer to stop. Send one per consumer.
- **Interrupting** the consumers with `shutdownNow()`. `take()` throws `InterruptedException`, but any items still in the queue are dropped.

The key trade-offs to mention are bounded versus unbounded queues (backpressure versus OOM), what capacity to choose, and the delivery guarantees. This is in-memory only: if the process crashes, the queued items are lost. Durability needs a real message broker.

## 2. A thread-safe LRU cache

An **LRU (least recently used) cache** holds at most N entries and evicts the entry that was used longest ago. The classic O(1) design combines a `HashMap` from key to node with a **doubly linked list** kept in order of recency. On every access, the node moves to the front. To evict, you remove from the back.

The concurrency insight is that **`get` is a write**, because it moves a node in the list. So a `ReadWriteLock` with `get` under the read lock is a bug: two readers would rearrange the list at the same time and corrupt it. Every operation needs exclusive access.

**Option A, two lines:** `LinkedHashMap` in access order, wrapped in a single lock.

```java
static <K, V> Map<K, V> lruMap(int capacity) {
    return Collections.synchronizedMap(new LinkedHashMap<K, V>(16, 0.75f, true) {   // true = access order
        @Override protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
            return size() > capacity;
        }
    });
}
```

**Option B, what interviewers usually want:** write it yourself.

```java
class LruCache<K, V> {
    private static final class Node<K, V> {
        final K key; V value; Node<K, V> prev, next;
        Node(K key, V value) { this.key = key; this.value = value; }
    }

    private final int capacity;
    private final Map<K, Node<K, V>> map = new HashMap<>();
    private final Node<K, V> head = new Node<>(null, null);  // sentinel: most recent side
    private final Node<K, V> tail = new Node<>(null, null);  // sentinel: least recent side
    private final ReentrantLock lock = new ReentrantLock();

    LruCache(int capacity) {
        this.capacity = capacity;
        head.next = tail; tail.prev = head;
    }

    public V get(K key) {
        lock.lock();
        try {
            Node<K, V> n = map.get(key);
            if (n == null) return null;
            unlink(n); linkFirst(n);          // a read MUTATES the order, so it needs the lock too
            return n.value;
        } finally { lock.unlock(); }
    }

    public void put(K key, V value) {
        lock.lock();
        try {
            Node<K, V> n = map.get(key);
            if (n != null) { n.value = value; unlink(n); linkFirst(n); return; }
            if (map.size() == capacity) {     // evict the least recently used
                Node<K, V> lru = tail.prev;
                unlink(lru);
                map.remove(lru.key);
            }
            n = new Node<>(key, value);
            map.put(key, n);
            linkFirst(n);
        } finally { lock.unlock(); }
    }

    public int size() {
        lock.lock();
        try { return map.size(); } finally { lock.unlock(); }
    }

    boolean checkConsistent() {               // lab helper: list length == map size
        lock.lock();
        try {
            int len = 0;
            for (Node<K, V> n = head.next; n != tail; n = n.next) len++;
            return len == map.size();
        } finally { lock.unlock(); }
    }

    private void unlink(Node<K, V> n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private void linkFirst(Node<K, V> n) {
        n.next = head.next; n.prev = head;
        head.next.prev = n; head.next = n;
    }
}
```

Complexity: O(1) for `get` and `put`, and O(capacity) space. The **sentinel** nodes are dummy head and tail nodes. They remove every null check from `unlink` and `linkFirst`.

**Scaling it**, which is the usual follow-up:

- **One lock serializes everything.** That is fine up to moderate load, but under high contention it becomes the bottleneck.
- **Sharding.** Use N independent LRU caches, picking one by `hash(key) % N`. This divides contention by N. Eviction becomes "least recently used *within a shard*", which is an approximation of global LRU.
- **`ConcurrentHashMap` + `ConcurrentLinkedDeque`** sounds lock-free, but removing a node from the middle of the deque is O(n), and the map and the deque can disagree between the two calls. Name it as a trap.
- **Production caches such as Caffeine** keep the data in a `ConcurrentHashMap`, record reads into small buffers, and replay them onto the recency order in batches under a lock. Reads almost never contend. Recency is slightly delayed, which is the trade-off.

## 3. A token-bucket rate limiter

The requirement is: allow each client at most *r* requests per second on average, but tolerate short bursts.

A **token bucket** holds up to *C* tokens and gains *r* tokens per second, never exceeding *C*. Each request removes one token, and a request that finds no token is rejected. Bursts of up to *C* requests pass immediately, and the long-run rate is *r*.

You do not need a background thread to add tokens. Use a **lazy refill**: on each call, add `elapsed time × r` tokens.

```java
class TokenBucket {
    private final long capacity;
    private final double refillPerNano;
    private double tokens;
    private long lastRefill;

    TokenBucket(long capacity, double tokensPerSecond) {
        this.capacity = capacity;
        this.refillPerNano = tokensPerSecond / 1_000_000_000.0;
        this.tokens = capacity;                // start full: allows an initial burst
        this.lastRefill = System.nanoTime();
    }

    public synchronized boolean tryAcquire() {
        long now = System.nanoTime();
        tokens = Math.min(capacity, tokens + (now - lastRefill) * refillPerNano);  // lazy refill
        lastRefill = now;
        if (tokens >= 1) { tokens -= 1; return true; }
        return false;
    }
}
```

Notice `System.nanoTime()`. It never jumps backwards. `currentTimeMillis()` can, for example when the clock is adjusted by NTP. The refill, the check and the decrement must happen as **one atomic step**, which is why the method is `synchronized`. Two threads must never both spend the last token.

For one bucket per client, use `computeIfAbsent`, which is atomic per key (B3), so two threads cannot both create a bucket for the same client:

```java
class RateLimiter {
    private final ConcurrentHashMap<String, TokenBucket> buckets = new ConcurrentHashMap<>();
    private final long capacity; private final double perSecond;

    RateLimiter(long capacity, double perSecond) { this.capacity = capacity; this.perSecond = perSecond; }

    boolean allow(String clientId) {
        return buckets.computeIfAbsent(clientId, id -> new TokenBucket(capacity, perSecond))
                      .tryAcquire();
    }
}
```

Complexity: O(1) time per request and O(1) memory per client. Clients that go idle leave their buckets behind forever, so in production you evict idle buckets with a scheduled sweep, or store them in an expiring cache.

**Compare the algorithms:**

| Algorithm | Memory per client | Bursts | Weakness |
|---|---|---|---|
| Fixed window counter | O(1) | up to 2× the limit across a window boundary | spike at the boundary |
| Sliding window log | O(requests in window) | exact | memory grows with traffic |
| Sliding window counter | O(1) | roughly smoothed | approximate |
| Token bucket | O(1) | up to C, then rate r | two parameters to tune |
| Leaky bucket | O(queue) | none: the output is smoothed | adds queueing delay |

**Distributed**, with many app instances: in-memory buckets limit each instance, not the whole system. One option is to give each of N instances `limit / N`, which is simple but inaccurate when load is uneven. The common alternative keeps the bucket state in Redis and performs the refill, check and decrement in a single Lua script, so the step stays atomic across instances. The cost is a network round trip per request.

## Lab (~10 min)

Create `ClassicLab.java`. Put this `main` class first, then paste `BoundedBuffer` (1a), `LruCache` (2, Option B) and `TokenBucket` (3) below it in the same file. Run it with `java ClassicLab.java`.

```java
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;
import java.util.concurrent.locks.*;

public class ClassicLab {
    public static void main(String[] args) throws Exception {
        // 1. Producer-consumer: 3 producers, 3 consumers, a buffer of 4
        BoundedBuffer<Integer> buf = new BoundedBuffer<>(4);
        int producers = 3, perProducer = 100_000;
        AtomicLong consumedSum = new AtomicLong();
        List<Thread> threads = new ArrayList<>();
        for (int p = 0; p < producers; p++)
            threads.add(Thread.ofPlatform().start(() -> {
                try { for (int i = 1; i <= perProducer; i++) buf.put(i); }
                catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            }));
        for (int c = 0; c < 3; c++)
            threads.add(Thread.ofPlatform().start(() -> {
                try { for (int i = 0; i < perProducer; i++) consumedSum.addAndGet(buf.take()); }
                catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            }));
        for (Thread t : threads) t.join();
        long expected = (long) producers * perProducer * (perProducer + 1) / 2;
        System.out.println("buffer:  consumed sum " + consumedSum.get() + ", expected " + expected);

        // 2. LRU cache: 8 threads hammering a capacity-100 cache
        LruCache<Integer, Integer> lru = new LruCache<>(100);
        try (ExecutorService pool = Executors.newFixedThreadPool(8)) {
            for (int t = 0; t < 8; t++)
                pool.submit(() -> {
                    ThreadLocalRandom r = ThreadLocalRandom.current();
                    for (int i = 0; i < 200_000; i++) {
                        int k = r.nextInt(1_000);
                        if (lru.get(k) == null) lru.put(k, k * k);
                    }
                });
        }
        System.out.println("lru:     size " + lru.size() + " (must be <= 100), consistent = " + lru.checkConsistent());

        // 3. Token bucket: capacity 5, refill 10/s, 20 threads trying for 1 second
        TokenBucket bucket = new TokenBucket(5, 10);
        AtomicInteger allowed = new AtomicInteger(), rejected = new AtomicInteger();
        long end = System.nanoTime() + TimeUnit.SECONDS.toNanos(1);
        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int t = 0; t < 20; t++)
                pool.submit(() -> {
                    while (System.nanoTime() < end) {
                        if (bucket.tryAcquire()) allowed.incrementAndGet(); else rejected.incrementAndGet();
                        Thread.sleep(1);
                    }
                    return null;
                });
        }
        System.out.println("limiter: allowed " + allowed + " (about 5 burst + 10 refilled = ~15), rejected " + rejected);
    }
}
```

What you should observe:

```text
buffer:  consumed sum 15000150000, expected 15000150000
lru:     size 100 (must be <= 100), consistent = true
limiter: allowed 14 (about 5 burst + 10 refilled = ~15), rejected ~1,300
```

The limiter result is about 14 to 15 allowed, never more than 15, however many threads try.

**Break it:**

1. In `BoundedBuffer`, change both `while` loops to `if`. Consumers crash with `NullPointerException`: they woke up, did not re-check, and took from an empty buffer. Meanwhile producers overwrite slots in a full buffer, and the sum comes out wildly wrong.
2. Restore the loops. In `LruCache.get`, delete `lock.lock();` and the `lock.unlock();` inside its `finally`. Run it a few times. You will see `consistent = false`, an exception, or even a hang, because a corrupted list can form a cycle that the consistency check loops around forever. That is the "a read mutates the list" race.
3. Make `tryAcquire` non-`synchronized` and run it several times. Some runs let 16 or more requests through, because two threads spent the same token. The race is rare at this low contention, which is exactly how it slips into production.

## Gotchas

- **`if` around `wait()`.** It breaks on spurious wake-ups and stolen conditions. Always use `while`.
- **`notify()` with mixed waiters** can wake the wrong kind of thread and hang everything. The hang is rare and hard to reproduce, which is what makes it dangerous. Use `notifyAll()` or separate `Condition`s.
- **`ReadWriteLock` for an LRU `get`.** Reads reorder the list, so they need the exclusive lock.
- **Per-key check-then-create** (`if (!map.containsKey(id)) map.put(id, new Bucket())`) races. Use `computeIfAbsent`.
- **`currentTimeMillis()` in limiters.** The wall clock can jump. Use `nanoTime()` for elapsed time.
- **Forgetting the pill count.** One poison pill stops only one consumer. Send one per consumer.

## Explain it in 2 minutes

*"Implement a bounded blocking queue and explain every line that matters."*

- It is a ring buffer with `head`, `tail` and `count`, and every method holds one monitor.
- `wait()` sits in a `while` loop because of spurious wake-ups and stolen conditions. `wait()` releases the monitor and re-acquires it before returning.
- `notifyAll()` because producers and consumers share one wait set. Alternatively, a `ReentrantLock` with `notFull` and `notEmpty` conditions lets you `signal()` precisely.
- `put` and `take` are O(1). Bounded capacity gives backpressure.
- In production, use `ArrayBlockingQueue` or `LinkedBlockingQueue` (two locks), and shut down with a poison pill per consumer or with interrupts.

## Check yourself

1. Why must `wait()` be called while holding the monitor, and what does it do with that monitor?
2. Give the two reasons for `while (cond) wait();` instead of `if`.
3. Why can't an LRU `get` use a read lock?
4. A token bucket has capacity 10 and refills 5 per second. After a long idle period, how many requests pass instantly, and what is the rate after that?
5. What does sharding an LRU cache give up?

### Answers

1. Waiting must be coordinated with the state check, which happens under the lock. `wait()` atomically releases the monitor so that others can change the state, then re-acquires it before returning. Calling it without the monitor throws `IllegalMonitorStateException`.
2. Spurious wake-ups, and the condition being "stolen" by another thread between the notification and re-acquiring the monitor.
3. `get` moves the node to the front of the list. That is a structural write, and concurrent writers would corrupt the links.
4. Ten pass at once (the full bucket). After that, about 5 per second.
5. Exact global LRU order. Eviction picks the least recently used entry within one shard, so an entry used more recently may be evicted before an older entry in another shard.
