## Where we are

From D2 you know that Spring builds beans from definitions, injects them by type and caches
singletons. This lesson adds the last big idea of Spring core: Spring often injects a
**stand-in object** in place of your bean, and that stand-in is what makes `@Transactional`,
`@Async` and `@Cacheable` work. Once you see the stand-in, the most common Spring bug ("my
annotation is ignored") becomes obvious.

## The problem

Some concerns cut across every service: starting and committing transactions, timing calls,
checking a cache, running work on another thread. Written by hand, they look like this:

```java
public void transfer(...) {
    var tx = txManager.getTransaction(def);
    try {
        // the 3 lines you actually care about
        txManager.commit(tx);
    } catch (RuntimeException e) {
        txManager.rollback(tx);
        throw e;
    }
}
```

Copy that into 200 methods and the real logic gets buried. You want to *declare*
"this is transactional" and have the begin, commit and rollback happen around the method
automatically. That is **AOP**.

## AOP in four words

**Aspect-Oriented Programming (AOP)** lets you write a cross-cutting concern once and apply it
to many methods. You only need four terms:

- **Advice:** the extra code, such as "begin a transaction, call the method, commit".
- **Join point:** a point where advice can run. In Spring AOP, that is always a *method call
  on a bean*.
- **Pointcut:** the rule that picks join points, such as "methods annotated `@Transactional`".
- **Aspect:** advice plus pointcut, packaged together.

You can write your own aspect:

```java
@Aspect @Component
class TimingAspect {
    @Around("@annotation(com.example.Timed)")
    Object time(ProceedingJoinPoint pjp) throws Throwable {
        long t0 = System.nanoTime();
        try { return pjp.proceed(); }                       // call the real method
        finally { System.out.println(pjp.getSignature() + " took " + (System.nanoTime() - t0) / 1_000 + " µs"); }
    }
}
```

Custom `@Aspect` classes need AspectJ's annotations on the classpath. In Boot 3 that means the
`spring-boot-starter-aop` starter, which Boot 4 renamed to `spring-boot-starter-aspectj`.
`@Transactional`, `@Async` and `@Cacheable` are aspects that Spring has already written for you.
The interesting part is *how* the advice gets in front of your method.

## The mechanism: a proxy

A **proxy** is an object with the same type as your bean that sits in front of it. Each call
reaches the proxy first. The proxy runs the advice and then forwards the call to your real
object, called the **target**.

```text
  CheckoutController                 proxy (what got injected)            target (your object)
        │  service.importAll() ──►  ┌───────────────────────────┐
        │                           │ BEGIN tx                  │
        │                           │ target.importAll() ───────┼──►  importAll() { ... }
        │                           │ COMMIT (or ROLLBACK)      │
        │                           └───────────────────────────┘
```

Spring creates the proxy while the bean is being built, just after its init methods run, in a
BeanPostProcessor (see L4 for the full lifecycle). It then stores the **proxy**, not your
object, in the singleton cache, so every injection point receives the proxy.

## Two ways to build a proxy: JDK vs CGLIB

| | JDK dynamic proxy | CGLIB proxy |
|---|---|---|
| How | a new class that **implements your interfaces** | a generated **subclass of your class** |
| Needs | the bean implements an interface | the class and its methods are not `final` |
| Inject as | the interface only | the interface or the class |
| Class name looks like | `jdk.proxy2.$Proxy42` | `ImportService$$SpringCGLIB$$0` |

In plain Spring, if a bean implements an interface, Spring uses a JDK proxy, and otherwise it
uses CGLIB. **Spring Boot defaults to CGLIB for everything**
(`spring.aop.proxy-target-class=true`), so in a Boot app you can still inject by class.

The rule: **advice runs only when a call passes through the proxy.** Everything else in this
lesson follows from that one sentence.

## The bug, made visible

Here is the shape of a real bug in this repo. At start-up, `DataImporter.run()` calls
`importAll()`, which is annotated `@Transactional`:

```java
@Component
public class DataImporter implements ApplicationRunner {
    @Override
    public void run(ApplicationArguments args) {   // (originally no @Transactional here)
        importAll();                                // ← this.importAll()
    }

    @Transactional
    public Summary importAll() { /* delete all rows, flush, insert new rows */ }
}
```

Spring Boot calls `run()` through the proxy, but `run()` has no annotation, so no transaction
starts. Inside `run()`, `importAll()` means **`this.importAll()`**, and `this` is the *target*,
not the proxy. That call never passes through the proxy, so `@Transactional` on `importAll()` is
simply never consulted.

```text
  Boot ──► proxy.run() ──► target.run() ──► target.importAll()      ✗ never touches the proxy
  POST /api/admin/reload ──► proxy.importAll() ──► BEGIN … COMMIT   ✓ works
```

The same method works when `ApiController` calls it (`/api/admin/reload` goes through the
injected proxy), but runs **without a transaction** at start-up. With no surrounding
transaction, each repository call commits on its own, so a failure halfway through could leave
the tables deleted but not refilled. JPA also refuses `em.flush()` outside a transaction and
throws `TransactionRequiredException`. That is exactly what happened when this app was first built:
the very first test run failed with `No EntityManager with actual transaction available for current
thread - cannot reliably process 'flush' call`, and the whole application refused to start. This is
**the self-invocation trap**.

## How it was fixed, and the other fixes

The repo moved `@Transactional` onto the method that is entered **through the proxy**:

```java
/** Transactional itself: calling importAll() from here is a self-invocation, which skips the
 *  proxy, so importAll()'s own @Transactional would never apply (CURRICULUM D3). */
@Override
@Transactional
public void run(ApplicationArguments args) { Summary s = importAll(); ... }
```

The transaction now begins at `proxy.run()`, and `importAll()` simply runs inside it.

All the fixes, from most to least preferred:

1. **Move the method to another bean.** For example, an `ImportService` that `DataImporter`
   injects. The call then crosses a bean boundary, which means it goes through a proxy. This is
   usually the cleanest design.
2. **Annotate the entry method**, as the repo did. This works when the outer method should own
   the transaction anyway.
3. **Use programmatic transactions:** `transactionTemplate.execute(status -> importAll())`.
   This is explicit and needs no proxy.
4. **Inject yourself**, with `@Lazy` on a self-reference or `ObjectProvider<DataImporter>`, and
   call `self.importAll()`. It works, but it reads as a hack.
5. **Use AspectJ weaving** (`mode = AdviceMode.ASPECTJ`), which changes the bytecode so that
   even `this` calls are advised. This is powerful, but it brings build and setup cost.

## The same trap, three annotations

Self-invocation breaks every proxy-based annotation in the same way:

| Annotation | Called via `this`, you get… |
|---|---|
| `@Transactional` | no transaction, so no rollback and no atomicity |
| `@Async` | the method runs **synchronously on the caller's thread** |
| `@Cacheable` | the cache is **never read or written**, so the work is recomputed every time |

None of these throws an error. The call quietly runs without the advice, which is why the bug
is so expensive to find.

## Methods a proxy cannot intercept

A CGLIB proxy works by **overriding** your methods in a subclass. A JDK proxy can only see
**interface** methods. So:

- **`private` methods:** they cannot be overridden, so the annotation is ignored.
- **`final` methods:** they cannot be overridden either, so the annotation is ignored. A `final`
  *class* cannot be subclassed at all, so CGLIB fails at start-up.
- **`static` methods:** these are not called on an instance, so the annotation is ignored.
- **Non-public methods:** since Spring Framework 6.0, `protected` and package-private methods
  *are* transactional with CGLIB proxies. With JDK proxies, only interface methods are.

Kotlin classes are `final` by default, which is why Kotlin Spring projects use the `all-open`
(`kotlin-spring`) compiler plugin.

## Lab (~10 min)

Use `spring-context` and `spring-tx`. No database is needed: a fake transaction manager prints
`BEGIN` and `COMMIT` so that you can see the transaction.

```java
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.stereotype.Service;
import org.springframework.transaction.PlatformTransactionManager;
import org.springframework.transaction.TransactionDefinition;
import org.springframework.transaction.TransactionStatus;
import org.springframework.transaction.annotation.EnableTransactionManagement;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.support.SimpleTransactionStatus;

public class ProxyTrapLab {
    public static void main(String[] args) {
        try (var ctx = new AnnotationConfigApplicationContext(TxConfig.class, ImportService.class)) {
            ImportService svc = ctx.getBean(ImportService.class);
            System.out.println("bean class: " + svc.getClass().getSimpleName());

            System.out.println("== 1. another bean calls importAll()");
            svc.importAll();

            System.out.println("== 2. run() calls this.importAll()");
            svc.run();
        }
    }
}

@Configuration
@EnableTransactionManagement
class TxConfig {
    @Bean
    PlatformTransactionManager transactionManager() { return new LoggingTxManager(); }
}

/** A fake transaction manager that only prints, so you can SEE when a transaction starts. */
class LoggingTxManager implements PlatformTransactionManager {
    @Override public TransactionStatus getTransaction(TransactionDefinition def) {
        System.out.println("   [tx] BEGIN " + def.getName());
        return new SimpleTransactionStatus();
    }
    @Override public void commit(TransactionStatus status)   { System.out.println("   [tx] COMMIT"); }
    @Override public void rollback(TransactionStatus status) { System.out.println("   [tx] ROLLBACK"); }
}

@Service
class ImportService {
    public void run() {
        System.out.println("   run(): calling importAll()");
        importAll();                       // really this.importAll(): the proxy is not involved
    }

    @Transactional
    public void importAll() {
        System.out.println("   importAll(): deleting and inserting rows");
    }
}
```

Output (checked on Spring Framework 7.0):

```text
bean class: ImportService$$SpringCGLIB$$0
== 1. another bean calls importAll()
   [tx] BEGIN ImportService.importAll
   importAll(): deleting and inserting rows
   [tx] COMMIT
== 2. run() calls this.importAll()
   run(): calling importAll()
   importAll(): deleting and inserting rows
```

Case 2 runs with no `BEGIN` and no `COMMIT`. That is the bug, now visible.

1. **Fix it:** add `@Transactional` to `run()`. Case 2 now prints
   `[tx] BEGIN ImportService.run` … `COMMIT`.
2. **Fix it properly:** move `importAll()` into a new `@Service Importer` and inject that into
   `ImportService`. Remove the annotation from `run()` and confirm that case 2 shows
   `BEGIN Importer.importAll`.
3. **Break it (JDK proxy):** make `ImportService` implement an interface
   `interface Importer { void run(); void importAll(); }`. Plain Spring now creates a JDK proxy,
   and `ctx.getBean(ImportService.class)` fails with
   `NoSuchBeanDefinitionException: No qualifying bean of type 'ImportService'`. Then try
   `@EnableTransactionManagement(proxyTargetClass = true)`, which is Boot's default.
4. Make `importAll()` `final` and call it as in case 1. The transaction disappears. The only
   sign is a start-up `WARNING: Public final method [...] cannot get proxied via CGLIB`, which is
   easy to miss among the logs. Worse, the final method runs on the *proxy instance*, whose
   injected fields are `null`, so any real method would hit a `NullPointerException`.

## Gotchas

- **Self-invocation skips the proxy.** `this.method()` never gets `@Transactional`, `@Async` or
  `@Cacheable`. Move the method to another bean, or annotate the entry point.
- **`private`, `final` and `static` methods are never advised.** Nothing fails. At most, Spring
  logs a start-up warning for public `final` methods, and the annotation is otherwise ignored.
- **JDK proxies only implement interfaces.** Injecting a JDK-proxied bean by its class fails.
  Boot avoids this by defaulting to CGLIB.
- **Advice exists only after the proxy exists.** Calls made inside `@PostConstruct` or the
  constructor are never advised (see L4).
- **"Check the `@Transactional` boundaries before debugging 'not saved'."** Print
  `TransactionSynchronizationManager.isActualTransactionActive()` to see whether a real
  transaction is active.

## In interviews

This is asked as "Why doesn't `@Transactional` work when I call the method from the same
class?", "JDK vs CGLIB proxies?" and "Can `@Transactional` be on a private method?"

- [Inheritance vs composition](#/q/inheritance-vs-composition): a CGLIB proxy uses
  inheritance, while a JDK proxy uses composition through an interface.
- [final Methods and synchronized Method Access](#/q/java-final-and-synchronized-methods): a
  `final` method cannot be overridden, so a CGLIB proxy cannot intercept it.
- [Design a Multi-module Logging Framework](#/q/design-logging-framework): logging is the
  standard example of a cross-cutting concern, and an aspect is one way to add it.

Typical follow-ups:

- *"How would you fix it?"* A strong answer lists moving the method to a separate bean,
  annotating the entry point, `TransactionTemplate`, and AspectJ mode, then picks the first and
  says why.
- *"Where is the proxy created?"* In a BeanPostProcessor's after-initialisation step
  (auto-proxy creation), so the cache holds the proxy, not the raw bean.

## Explain it in 2 minutes

*"Explain why `@Transactional` sometimes does nothing."*

- `@Transactional`, `@Async` and `@Cacheable` are aspects applied by a proxy that wraps the
  bean.
- The proxy is either a JDK interface proxy or a CGLIB subclass. Boot uses CGLIB by default.
- Advice runs only when a call goes *through* the proxy. `this.method()` calls the target
  directly, so the advice is skipped.
- Private, final and static methods cannot be intercepted either.
- Real example: `DataImporter.run()` called `importAll()` internally, and the fix was to put
  `@Transactional` on `run()`. A separate bean is the cleanest general fix.
- To diagnose it, check the bean class name and whether a transaction is active.

## Check yourself

1. Why does `this.importAll()` skip the transaction, while `importer.importAll()` from the
   controller doesn't?
2. A `@Service` implements `PaymentApi`. In plain Spring, which proxy type do you get, and what
   breaks if you inject `PaymentServiceImpl`?
3. What happens when a `@Async` method is self-invoked?
4. Is a package-private `@Transactional` method transactional under Spring 6+ with CGLIB?

### Answers

1. `this` is the raw target. The controller holds a reference to the proxy, which runs the
   transaction advice.
2. A JDK proxy that implements `PaymentApi`. Injecting the class fails because the proxy is not
   a `PaymentServiceImpl`.
3. It runs synchronously on the calling thread.
4. Yes. Since Spring Framework 6.0, protected and package-private methods are supported with
   class-based proxies. Private methods are not.
