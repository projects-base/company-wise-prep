## Where we are

From WEB-API-1 you know HTTP itself: methods, status codes, headers, and which methods are safe and
idempotent. From SPRING-BOOT-6 you know how Spring MVC maps a request to a controller, binds the body,
runs `@Valid` and turns exceptions into `ProblemDetail` responses. This lesson is about the *design*
on top of those mechanics: what URLs, methods, codes and payloads a good API exposes, so that clients
can retry safely, page through data and survive your next release.

## The problem

A betting app's first API grew one endpoint at a time:

```text
POST /placeBet              body: {...}         -> 200 {"success": false, "msg": "stake too low"}
GET  /getBetsForUser?u=42&page=7
POST /updateBet             body: {"id": 9, "stake": 20}
```

Three things then go wrong in production:

- A phone on a flaky network sends `POST /placeBet`, the response is lost, the app retries, and the
  user has **two** bets.
- A developer renames `msg` to `message`, and every installed app version that reads `msg` breaks.
- Page 7 shows a bet the user already saw on page 6, because new bets arrived in between.

None of these is a Spring bug. They are design bugs, and each has a standard fix.

## Resources, not actions

A **resource** is a thing the API exposes, named by a noun and identified by a URL. Clients act on it
with HTTP methods instead of verbs in the path:

```text
GET    /bets              list bets (filtered, paged)
POST   /bets              create a bet
GET    /bets/{id}         read one
PUT    /bets/{id}         replace one
PATCH  /bets/{id}         change part of one
DELETE /bets/{id}         remove one
GET    /users/{id}/bets   bets belonging to one user (a sub-collection)
```

Conventions: plural nouns, lowercase with hyphens (`/betting-markets`), opaque ids, and nesting at
most one level deep. Deeper nesting such as `/users/1/bets/9/legs/3` couples the URL to one access
path; give the leg its own `/legs/{id}` instead.

Some operations really are actions, such as cashing out a bet. Model them as a resource that gets
created (`POST /bets/{id}/cash-outs`) or as a state change (`PATCH /bets/{id}` with
`{"status": "CANCELLED"}`). A verb in the path (`POST /bets/{id}/cancel`) is acceptable when nothing
else fits; just keep it rare and consistent.

**The rule:** URLs name things; methods say what you do to them.

## Status codes, per operation

WEB-API-1 taught the codes. Here is which one each operation should return:

| Operation | Success | Common failures |
|---|---|---|
| `GET /bets/{id}` | 200 | 404 not found |
| `GET /bets` | 200 (empty list, never 404) | 400 bad filter |
| `POST /bets` | **201 Created** + `Location: /bets/{id}` | 400/422 invalid, 409 conflict |
| `PUT /bets/{id}` | 200 with body, or 204 | 400, 404, 409, 412 |
| `PATCH /bets/{id}` | 200 with body, or 204 | 400, 404, 409, 412 |
| `DELETE /bets/{id}` | 204 | 404 (or 204 again; see below) |
| Long-running work | **202 Accepted** + a URL to poll | |

Plus the cross-cutting ones: 401 (who are you?), 403 (not allowed), 415 (unsupported
`Content-Type`), 429 (rate-limited, with `Retry-After`) and 503 (temporarily unavailable).

The anti-pattern is `200 {"success": false}`. Proxies, retry libraries, monitoring and client SDKs all
read the status code. A failure dressed as a 200 is invisible to every one of them.

## Idempotency, and why retries need it

Recall from WEB-API-1: a method is **idempotent** if sending the same request twice leaves the server
in the same state as sending it once. `GET`, `PUT` and `DELETE` are idempotent by definition; `POST` is
not, and `PATCH` is not guaranteed to be.

That matters because networks fail *after* the server has acted. The client sees a timeout and cannot
tell "never arrived" from "done, but the reply was lost". The only safe move is to retry, and retrying
is only safe for an idempotent operation.

`DELETE` shows that idempotency is about **state, not the response**. The first `DELETE /bets/9`
returns 204; the second may return 404. The bet is gone either way, so the operation is idempotent.

## Idempotency keys for POST

To make `POST /bets` retry-safe, the client generates a unique **idempotency key** (usually a UUID)
per logical operation and sends it in a header. Retries reuse the same key:

```text
POST /bets
Idempotency-Key: 7f9c2e1a-...        <- same value on every retry of THIS bet
{"eventId": "ev-1", "stake": 10}
```

The server:

1. Looks up the key. Not seen: process the request, then store `key → (request fingerprint, response)`.
2. Seen with the same request: return the **stored response**; do not process again.
3. Seen with a *different* request body: reject (422), because the client reused a key by mistake.
4. Seen but still in progress (a concurrent retry): reject with 409 and let the client retry later.

Store keys in the database with a **unique constraint** on the key, ideally in the same transaction as
the bet itself, so two concurrent retries cannot both win. Expire keys after a window such as 24 hours.
This header is what payment APIs such as Stripe use, and the IETF has a draft standardising the
`Idempotency-Key` header.

The analogy is a numbered cheque: the bank cashes cheque #1042 once, however many times you hand it
over. It breaks in that the bank keeps cheque numbers forever, while servers expire keys, so a retry
after the window is treated as new.

## PUT versus PATCH

**`PUT`** replaces the whole resource with the body you send. Fields you leave out are cleared (or the
request is rejected). Sending the same `PUT` twice gives the same result, so it is idempotent.

**`PATCH`** sends only the changes. The two common formats:

- **JSON Merge Patch** (RFC 7396, `application/merge-patch+json`): send a partial object;
  `{"stake": 20}` changes the stake, `{"note": null}` removes the note.
- **JSON Patch** (RFC 6902, `application/json-patch+json`): a list of operations such as
  `[{"op": "replace", "path": "/stake", "value": 20}]`.

`PATCH {"stake": 20}` happens to be idempotent; `PATCH` "add 5 to the stake" is not. That is why the
spec doesn't promise it.

**Lost updates.** Two clients read version 3 of a bet and both `PUT` changes; the second silently
overwrites the first. The fix is optimistic concurrency with the HTTP caching headers from WEB-API-1:
the `GET` returns `ETag: "3"`, the client sends `If-Match: "3"` on the update, and the server answers
**412 Precondition Failed** if the resource has moved on.

## Filtering, sorting and field selection

Use query parameters on the collection:

```text
GET /bets?status=OPEN&eventId=ev-1&placedAfter=2026-10-01T00:00:00Z
GET /bets?sort=-placedAt,stake          (minus means descending)
```

Rules: document which fields are filterable and sortable, validate them against an allow-list (a
user-supplied sort field must never be pasted into a query; DB-SQL-5, coming soon, shows why), use ISO-8601 for
times, and reject unknown parameters with 400 rather than silently ignoring them.

## Pagination: offset versus cursor

A collection can be huge, so the server returns it in pages. Two designs:

**Offset pagination:** `GET /bets?offset=40&limit=20` ("skip 40, give me 20").

- Easy, and lets the user jump to page 7.
- Rows shift when data changes: a new bet arriving pushes everything down by one, so the next page
  repeats an item. A deleted bet makes one get skipped.
- The database still has to walk past every skipped row, so page 5,000 is slow. DB-SQL-8, coming later,
  shows this at the SQL level.

**Cursor (keyset) pagination:** the response includes an opaque token pointing just past the last item.

```json
{
  "items": [ { "id": 101, "...": "..." }, { "id": 120, "...": "..." } ],
  "nextCursor": "eyJpZCI6MTIwfQ"
}
```

The client sends `GET /bets?limit=20&cursor=eyJpZCI6MTIwfQ`. The server decodes "after id 120" and
asks the database for the next 20 rows *after* that key, which an index finds directly.

- Stable under inserts and deletes; fast on any page.
- No "jump to page 7"; the sort key must be unique (add the id as a tie-breaker:
  `(placedAt, id)`).
- Make the cursor opaque (Base64 of the key) so you can change its contents later.

**The rule:** offset for small, admin-style tables where page numbers matter; cursor for feeds, large
tables and anything clients scroll or sync. Always cap `limit`.

## Errors: one format, RFC 9457

Every error should have the same machine-readable shape. **RFC 9457** ("Problem Details for HTTP
APIs", which replaced RFC 7807) defines one, with media type `application/problem+json`:

```json
{
  "type": "https://api.example.com/problems/insufficient-funds",
  "title": "Insufficient funds",
  "status": 422,
  "detail": "Stake 50.00 exceeds available balance 20.00.",
  "instance": "/bets",
  "balance": "20.00"
}
```

- `type` is a stable URI identifying the error *kind*; clients branch on it, never on `detail` text.
- `title` is a short human summary of the kind; `detail` explains this occurrence.
- Extra members (`balance` above, or a list of field errors) are allowed.

You met Spring's `ProblemDetail` in SPRING-BOOT-6. Set `spring.mvc.problemdetails.enabled=true` and
Spring's own exceptions (validation failures, missing headers, wrong media types) come out in this
format too. Never put stack traces, SQL or internal hostnames in an error body.

## Validation

Validate at the edge, with `@Valid` and Bean Validation annotations on the request record, and return
every field error at once, not just the first. Teams split on the code: some use **400** for every
invalid request, others use 400 for malformed JSON and **422** for well-formed JSON that breaks a rule
("stake must be positive"). Either is fine; pick one and apply it everywhere. Business rules that need
data, such as "insufficient balance", belong in the service and usually map to 409 or 422.

## Versioning

Sooner or later you must make a change old clients can't handle. The options:

| Style | Example | For | Against |
|---|---|---|---|
| URI path | `/v1/bets` | Obvious, easy to route, cache and test in a browser | Version is part of the resource's identity |
| Header | `X-API-Version: 2` | Clean URLs | Invisible in logs and links; easy to forget |
| Media type | `Accept: application/vnd.bets.v2+json` | The "most RESTful"; versions the representation | Awkward for clients and tools |
| Query param | `/bets?version=2` | Simple | Easy to drop; muddles caching |

Most public APIs choose the URI path because it is the easiest to operate. Spring Framework 7 (Spring
Boot 4) adds built-in API versioning, where you configure where the version comes from and map
handlers with a `version` attribute; earlier versions simply use path prefixes or header conditions.

Versioning is the expensive path, because every version is code you run and test. The cheaper path is
to avoid breaking changes in the first place.

## Backward compatibility rules

**Safe (additive) changes:** a new endpoint, a new *optional* request field, a new response field, a
new optional query parameter.

**Breaking changes:** removing or renaming a field, changing a field's type or format, making an
optional request field required, changing a status code or error `type`, changing default sorting or
page size, or changing what a field *means*.

Two habits make additive change safe:

- **Tolerant reader:** clients ignore fields they don't know. In Jackson that means not failing on
  unknown properties, which is Spring Boot's default.
- **Enums are a trap:** adding a value such as `VOIDED` to `status` breaks clients that `switch` over
  the known values. Document that new values may appear.

To retire something, announce it, mark responses with a `Deprecation` header and a `Sunset` header
carrying the removal date (RFC 8594), watch traffic until it drops, then remove it.

## HATEOAS, briefly

**HATEOAS** (Hypermedia As The Engine Of Application State) means responses include links to the
actions available next, such as a `cash-out` link present only while the bet is open. Clients follow
links instead of building URLs. Spring HATEOAS supports it with formats such as HAL. In practice most
JSON APIs skip it; know the term, its intent (servers can change URLs and expose state-dependent
actions), and why teams rarely pay for it (clients hard-code URLs anyway).

## OpenAPI: the contract

**OpenAPI** is a YAML/JSON format describing every endpoint, parameter, schema and response. It drives
documentation (Swagger UI), client generation, mock servers and contract tests. Two ways to get one:

- **Code-first:** add `springdoc-openapi-starter-webmvc-ui`; the spec is generated from your
  controllers at `/v3/api-docs` and browsable at `/swagger-ui.html`.
- **Contract-first:** write the spec, review it with the consumers, then generate server interfaces.
  Slower to start, but the design gets reviewed before anyone codes against it.

Either way, diff the spec in CI so a breaking change shows up in review, not in production.

## Lab (~10 min)

Build a retry-safe, paged bets endpoint. Spring Boot 3.2+ with `spring-boot-starter-web` and
`spring-boot-starter-validation`; set `spring.mvc.problemdetails.enabled=true`.

```java
import jakarta.validation.Valid;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Positive;
import java.net.URI;
import java.nio.charset.StandardCharsets;
import java.time.Instant;
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicLong;
import org.springframework.http.*;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.server.ResponseStatusException;

record CreateBetRequest(@NotBlank String eventId, @Positive long stake) {}
record Bet(long id, String eventId, long stake, Instant placedAt) {}
record PageResponse<T>(List<T> items, String nextCursor) {}

class IdempotencyKeyReusedException extends RuntimeException {
    IdempotencyKeyReusedException(String key) { super("Idempotency key " + key + " was used for a different request"); }
}

@RestController
@RequestMapping("/v1/bets")
class BetController {
    private record Stored(CreateBetRequest request, Bet bet) {}

    private final AtomicLong ids = new AtomicLong();
    private final ConcurrentSkipListMap<Long, Bet> bets = new ConcurrentSkipListMap<>();
    private final ConcurrentMap<String, Stored> byKey = new ConcurrentHashMap<>();

    @PostMapping
    ResponseEntity<Bet> place(@RequestHeader("Idempotency-Key") String key, @Valid @RequestBody CreateBetRequest req) {
        Stored stored = byKey.computeIfAbsent(key, k -> {        // atomic per key: concurrent retries wait
            Bet bet = new Bet(ids.incrementAndGet(), req.eventId(), req.stake(), Instant.now());
            bets.put(bet.id(), bet);
            return new Stored(req, bet);
        });
        if (!stored.request().equals(req)) {
            throw new IdempotencyKeyReusedException(key);
        }
        return ResponseEntity.created(URI.create("/v1/bets/" + stored.bet().id())).body(stored.bet());
    }

    @GetMapping("/{id}")
    Bet get(@PathVariable long id) {
        Bet bet = bets.get(id);
        if (bet == null) {
            throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Bet " + id + " not found");
        }
        return bet;
    }

    @GetMapping
    PageResponse<Bet> list(@RequestParam(required = false) String cursor,
                           @RequestParam(defaultValue = "2") int limit) {
        long after = cursor == null ? 0
                : Long.parseLong(new String(Base64.getUrlDecoder().decode(cursor), StandardCharsets.UTF_8));
        int size = Math.clamp(limit, 1, 100);                     // always cap the page size
        List<Bet> page = bets.tailMap(after, false).values().stream().limit(size).toList();
        String next = page.size() < size ? null
                : Base64.getUrlEncoder().withoutPadding().encodeToString(
                        String.valueOf(page.getLast().id()).getBytes(StandardCharsets.UTF_8));
        return new PageResponse<>(page, next);
    }
}

@RestControllerAdvice
class ApiErrors {
    @ExceptionHandler(IdempotencyKeyReusedException.class)
    ProblemDetail keyReused(IdempotencyKeyReusedException e) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatusCode.valueOf(422), e.getMessage());
        pd.setType(URI.create("https://api.example.com/problems/idempotency-key-reused"));
        pd.setTitle("Idempotency key reused");
        return pd;
    }
}
```

**Observe** (with `curl -i`):

- `POST /v1/bets` with `Idempotency-Key: k1` and `{"eventId":"ev-1","stake":10}` returns **201** with a
  `Location` header. Send the identical request again: same id, and no second bet in `GET /v1/bets`.
- Same key, `"stake":99`: **422** with `Content-Type: application/problem+json` and your `type` URI.
- No `Idempotency-Key` header, or `"stake":0`: **400** as a problem-details body, produced by Spring.
- Create five bets with different keys, then follow `nextCursor` from `GET /v1/bets`. Create a new bet
  between page requests: no item repeats, unlike offset paging.
- **Break it:** replace `computeIfAbsent` with a `get` then `put`, add `Thread.sleep(200)` between them,
  and fire two identical requests in parallel. You get two bets: the check-then-act race that a database
  unique constraint on the key prevents in a real system.

## Gotchas

- **`200 {"success": false}`.** Use real status codes; every tool between client and server reads them.
- **Retrying a plain `POST`.** Without an idempotency key, a lost response plus a retry creates a
  duplicate. Require the key on money-moving `POST`s and enforce it with a unique constraint.
- **Offset paging on a live feed.** Items repeat or vanish as rows shift, and deep pages get slow. Use a
  cursor on a unique, indexed sort key.
- **Clients branching on error `detail` text.** Give each error kind a stable `type` URI and branch on
  that.
- **"Small" renames.** Renaming or removing a response field, or adding an enum value, is a breaking
  change. Add the new field, deprecate the old, and remove it only after traffic stops.
- **Returning JPA entities directly.** The API then changes whenever the table does. Return
  dedicated response records; your schema and your contract evolve separately.

## In interviews

Typical prompts: "Design the REST API for X", "PUT vs POST vs PATCH?", "How do you make a payment API
idempotent?", "How do you version an API?", "Offset or cursor pagination?". Bank:
[POST vs PUT in REST APIs](#/q/http-post-vs-put), [Design an Idempotent API](#/q/design-idempotent-api),
[Idempotency in Payment Systems](#/q/idempotency-in-payment-systems),
[How would you optimise a slow API?](#/q/optimize-slow-api),
[Entain take-home: Spring Boot sport events API](#/q/entain-sport-events-api-take-home).

A strong answer comes in four layers. For "How do you make `POST /payments` idempotent?":

1. **What:** the client sends an `Idempotency-Key` per logical operation; repeats return the first
   result instead of acting again.
2. **How it works inside:** a keys table with a unique constraint, written in the same transaction as
   the payment; it stores a request fingerprint and the response; in-flight duplicates get 409,
   mismatched bodies get 422; keys expire after a window.
3. **Where used:** payment and order creation, any `POST` a mobile client or message consumer may
   retry, and webhook handlers receiving at-least-once deliveries.
4. **What goes wrong:** check-then-insert races without the unique constraint, storing the key in a
   different transaction from the effect (crash between them), keys scoped globally instead of per
   client, and expiry shorter than the client's retry horizon.

**Follow-up: "Is PATCH idempotent?"** Not by definition. A merge patch that sets values is; an
operation such as "increment" is not. Say so, then mention `If-Match` to stop lost updates.

**Follow-up: "How do you remove a field without breaking clients?"** Additive first, deprecate with
headers and docs, measure usage, remove in a new version or after the sunset date.

## Explain it in 2 minutes

*"Walk me through how you would design a public REST API for placing and listing bets."*

- Nouns and methods: `POST /v1/bets`, `GET /v1/bets/{id}`, `GET /v1/bets?status=OPEN`, with 201 +
  `Location`, 200, 204, and real 4xx/5xx codes.
- Retry safety: `GET`/`PUT`/`DELETE` are idempotent; `POST` gets an `Idempotency-Key` backed by a
  unique constraint.
- Updates: `PATCH` with merge patch, and `ETag`/`If-Match` to prevent lost updates (412).
- Lists: allow-listed filters and sorts, capped `limit`, cursor pagination for large or live data.
- Errors: RFC 9457 problem details with stable `type` URIs; validation returns all field errors.
- Evolution: additive changes only, tolerant readers, path versioning for true breaks, an OpenAPI spec
  diffed in CI.

## Check yourself

1. Why is `DELETE` idempotent even though the second call may return 404?
2. A client retries `POST /bets` with the same `Idempotency-Key` but a different stake. What should
   happen, and why?
3. Give two problems with offset pagination on a busy feed.
4. Which of these are breaking changes: adding a response field, renaming a response field, adding a
   new value to a `status` enum, adding an optional query parameter?
5. Why should clients branch on a problem's `type` rather than its `detail`?

### Answers

1. Idempotency is about server state. After the first call the bet is gone; further calls leave it
   gone, whatever status they return.
2. Reject it, typically with 422: the key identifies one logical request, so a different body means a
   client bug, and silently returning the old result would hide it.
3. Items repeat or are skipped as rows are inserted or deleted between requests, and deep offsets are
   slow because the database still walks past every skipped row.
4. Renaming a field is breaking. Adding an enum value is breaking for clients that handle only known
   values. Adding a response field and adding an optional parameter are safe.
5. `type` is a stable identifier for the error kind; `detail` is human text that can change or be
   localised at any time.
