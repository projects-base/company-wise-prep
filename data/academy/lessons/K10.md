## Where we are

After CAPSTONE-9, TicketHub caches event pages and the seat map in Redis, expires holds through a Redis TTL fast path, and exposes liveness, readiness and booking metrics. Confirming a hold calls a stubbed `PaymentClient` inline, and nothing outside the service learns that a booking happened.

## Goal

Publish `BookingConfirmed` to Kafka in a way that can never lose an event or announce a booking that rolled back. You do this with the **transactional outbox**: the confirm transaction also inserts a row into `outbox_event`, and a separate relay publishes those rows to `tickethub.bookings`. Kafka plus a relay gives **at-least-once** delivery, so the `notification` consumer must be **idempotent**, meaning that processing the same event twice has the same effect as processing it once. Poison messages go to a dead-letter topic. Finally, you wrap the payment call in Resilience4j (timeout, retry with backoff and jitter for transient faults only, circuit breaker) and decide what the user sees when payments are down. This uses DIST-SYS-2 (Kafka) and DIST-SYS-3 (resilience patterns, outbox).

## What you build

- [ ] Kafka (KRaft, single broker) in `compose.yaml`; topics `tickethub.bookings` and `tickethub.bookings.DLT`
- [ ] Flyway migration: `outbox_event` (if CAPSTONE-5 did not already create it) and `processed_event`
- [ ] `confirm` writes the `outbox_event` row **in the same transaction** as the booking
- [ ] `OutboxRelay`: a scheduled poller that publishes unpublished rows with key `bookingId`, then marks them published
- [ ] `notification` consumer, deduplicated on `bookingId` through `processed_event`
- [ ] `DefaultErrorHandler` with a `DeadLetterPublishingRecoverer`; bad JSON skips the retries
- [ ] `ResilientPaymentClient` (a Decorator around the stub): time limiter, retry, circuit breaker
- [ ] `503` problem detail with code `PAYMENT_UNAVAILABLE` and a `Retry-After` header

## Acceptance criteria

1. `docker compose up -d kafka`, then `docker compose exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list` lists `tickethub.bookings` and `tickethub.bookings.DLT` once the app has started.
2. Confirm a hold. Then `psql -c "select event_type, published_at is not null from outbox_event"` shows `BookingConfirmed | t`, and `kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic tickethub.bookings --from-beginning --property print.key=true` prints `<bookingId>` followed by the JSON payload.
3. `OutboxIT`: when the confirm transaction is forced to fail after the booking insert, **no** `outbox_event` row exists and nothing reaches Kafka.
4. `NotificationIT`: the same `BookingConfirmed` record produced twice leads to exactly **one** notification sent and one `processed_event` row.
5. Producing `not-json` to `tickethub.bookings` puts that record on `tickethub.bookings.DLT` without retries, and the consumer keeps processing the next record.
6. `ResilientPaymentClientTest`: a transient failure is retried (3 attempts in total), a decline is **not** retried, a slow provider times out after 2 s, and after 5 failing calls the circuit opens. The next call fails immediately with `PaymentUnavailableException` and the stub is not invoked.
7. With the stub in `FAIL` mode, `POST /api/v1/holds/{id}/confirm` returns `503`, `code: PAYMENT_UNAVAILABLE`, and `Retry-After`. The hold stays held until it expires, so the user can retry. `GET /actuator/health` (as admin) shows the `circuitBreakers` component.

### 3. Write the event in the confirm transaction (10 min)

**Why not just call `kafkaTemplate.send` in `confirm`?** That is the dual-write problem. If you send before the commit and the commit fails, you have announced a booking that does not exist. If you send after the commit and the process dies, the event is lost forever. The outbox makes the event part of the same database transaction, so the booking and the event commit together or not at all.

```java
package com.tickethub.booking;

import java.time.Instant;
import java.util.List;
import java.util.UUID;

public record BookingConfirmed(UUID bookingId, long eventId, String userId, List<Long> seatIds,
                               long totalCents, Instant occurredAt) {}
```

```java
package com.tickethub.common.outbox;

import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.ObjectMapper;
import java.time.Clock;
import java.util.UUID;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Transactional;

@Component
public class OutboxWriter {

    private final JdbcClient jdbc;
    private final ObjectMapper mapper;
    private final Clock clock;

    public OutboxWriter(JdbcClient jdbc, ObjectMapper mapper, Clock clock) {
        this.jdbc = jdbc;
        this.mapper = mapper;
        this.clock = clock;
    }

    @Transactional(propagation = Propagation.MANDATORY)
    public void append(String aggregateType, String aggregateId, Object event) {
        try {
            jdbc.sql("""
                    insert into outbox_event (id, aggregate_type, aggregate_id, event_type, payload, created_at)
                    values (?, ?, ?, ?, cast(? as jsonb), ?)""")
                .params(UUID.randomUUID(), aggregateType, aggregateId, event.getClass().getSimpleName(),
                        mapper.writeValueAsString(event), java.sql.Timestamp.from(clock.instant()))
                .update();
        } catch (JsonProcessingException e) {
            throw new IllegalStateException("cannot serialise " + event.getClass().getSimpleName(), e);
        }
    }
}
```

`Propagation.MANDATORY` fails fast if someone calls it without a surrounding transaction, which would silently bring back the dual-write problem. In `BookingService.confirm`, after the booking is saved:

```java
outbox.append("Booking", booking.id().toString(), new BookingConfirmed(booking.id(), booking.eventId(),
        booking.userId(), booking.seatIds(), booking.totalCents(), clock.instant()));
```

JPA and `JdbcClient` share the same `DataSource` transaction under `JpaTransactionManager`, so both writes commit together. Adapt the accessor names to your `Booking` class.

### 4. The relay (10 min)

```java
package com.tickethub.common.outbox;

import java.time.Clock;
import java.util.List;
import java.util.UUID;
import java.util.concurrent.TimeUnit;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
class OutboxRelay {

    private static final String TOPIC = "tickethub.bookings";
    private final JdbcClient jdbc;
    private final KafkaTemplate<String, String> kafka;
    private final Clock clock;

    OutboxRelay(JdbcClient jdbc, KafkaTemplate<String, String> kafka, Clock clock) {
        this.jdbc = jdbc;
        this.kafka = kafka;
        this.clock = clock;
    }

    record Row(UUID id, String aggregateId, String payload) {}

    @Scheduled(fixedDelayString = "${tickethub.outbox.poll:500ms}")
    @Transactional
    public void publishBatch() throws Exception {
        List<Row> rows = jdbc.sql("""
                select id, aggregate_id, payload::text as payload from outbox_event
                where published_at is null order by created_at limit 100
                for update skip locked""")
            .query(Row.class).list();
        for (Row row : rows) {
            kafka.send(TOPIC, row.aggregateId(), row.payload()).get(5, TimeUnit.SECONDS);
            jdbc.sql("update outbox_event set published_at = ? where id = ?")
                .params(java.sql.Timestamp.from(clock.instant()), row.id()).update();
        }
    }
}
```

- **Key = `bookingId`.** Kafka orders records only within a partition, and the key picks the partition. So all events for one booking stay in order.
- **`for update skip locked`** lets two app instances poll at the same time without picking the same rows.
- **`.get(5, SECONDS)`** waits for the broker's ack, with a timeout. If it throws, the transaction rolls back, the rows stay unpublished, and the next tick retries.
- **At-least-once:** if the process dies after Kafka acked but before the commit, the row is sent again. The relay cannot avoid this. That is why step 5 exists.

Spring Boot configures the `KafkaTemplate<String, String>` with `StringSerializer` by default, and `@EnableScheduling` already exists from CAPSTONE-7.

### 5. The idempotent notification consumer (8 min)

```java
package com.tickethub.notification;

import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.tickethub.booking.BookingConfirmed;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
class BookingConfirmedListener {

    private static final String CONSUMER = "notification";
    private final ObjectMapper mapper;
    private final JdbcClient jdbc;
    private final NotificationSender sender;

    BookingConfirmedListener(ObjectMapper mapper, JdbcClient jdbc, NotificationSender sender) {
        this.mapper = mapper;
        this.jdbc = jdbc;
        this.sender = sender;
    }

    @KafkaListener(topics = "tickethub.bookings")
    @Transactional
    public void on(String payload) throws JsonProcessingException {
        BookingConfirmed event = mapper.readValue(payload, BookingConfirmed.class);
        int inserted = jdbc.sql("""
                insert into processed_event (consumer, dedupe_key, processed_at) values (?, ?, now())
                on conflict do nothing""")
            .params(CONSUMER, event.bookingId().toString()).update();
        if (inserted == 0) {
            return;                                   // duplicate: already handled
        }
        sender.bookingConfirmed(event);               // stub: logs bookingId only, never personal data
    }
}
```

The primary key on `(consumer, dedupe_key)` makes the database the referee. If two deliveries race, one insert wins. If `sender` throws, the transaction rolls back, the dedupe row disappears, and the redelivery tries again. The remaining gap: if the email goes out and then the commit fails, the user gets a second email. For notifications that is the right direction to fail. Never lose; occasionally repeat.

### 6. Dead-letter topic for poison messages (5 min)

A **poison message** is one that fails every time it is processed, for example malformed JSON. Without a DLT it blocks its partition forever.

```java
@Bean
DefaultErrorHandler kafkaErrorHandler(KafkaTemplate<String, String> template) {
    var handler = new DefaultErrorHandler(new DeadLetterPublishingRecoverer(template), new FixedBackOff(1_000L, 2));
    handler.addNotRetryableExceptions(JsonProcessingException.class);
    return handler;
}
```

Boot wires a single `CommonErrorHandler` bean into the listener container factory. The recoverer publishes to `<topic>.DLT` on the same partition number, which is why the DLT also has 3 partitions.

### 7. Resilience4j on payments (12 min)

Three new errors, all extending `TicketHubException`: `PaymentTransientException` (a timeout or a 5xx, so retry), `PaymentDeclinedException` (the card was refused, so never retry), and `PaymentUnavailableException` (we gave up, so return 503, code `PAYMENT_UNAVAILABLE`).

```yaml
resilience4j:
  circuitbreaker.instances.payments:
    sliding-window-size: 10
    minimum-number-of-calls: 5
    failure-rate-threshold: 50
    wait-duration-in-open-state: 10s
    permitted-number-of-calls-in-half-open-state: 2
    automatic-transition-from-open-to-half-open-enabled: true
    ignore-exceptions: com.tickethub.payment.PaymentDeclinedException
    register-health-indicator: true
  timelimiter.instances.payments.timeout-duration: 2s
management.health.circuitbreakers.enabled: true
```

A decline is the provider working correctly, so it must not count as a failure and trip the breaker.

```java
package com.tickethub.payment;

import io.github.resilience4j.circuitbreaker.CallNotPermittedException;
import io.github.resilience4j.circuitbreaker.CircuitBreaker;
import io.github.resilience4j.circuitbreaker.CircuitBreakerRegistry;
import io.github.resilience4j.core.IntervalFunction;
import io.github.resilience4j.retry.Retry;
import io.github.resilience4j.retry.RetryConfig;
import io.github.resilience4j.timelimiter.TimeLimiter;
import io.github.resilience4j.timelimiter.TimeLimiterRegistry;
import java.time.Duration;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeoutException;
import java.util.function.Supplier;

public class ResilientPaymentClient implements PaymentClient {

    private final PaymentClient delegate;
    private final CircuitBreaker breaker;
    private final TimeLimiter timeLimiter;
    private final Retry retry;
    private final ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();

    public ResilientPaymentClient(PaymentClient delegate, CircuitBreakerRegistry breakers, TimeLimiterRegistry limiters) {
        this.delegate = delegate;
        this.breaker = breakers.circuitBreaker("payments");
        this.timeLimiter = limiters.timeLimiter("payments");
        this.retry = Retry.of("payments", RetryConfig.custom()
                .maxAttempts(3)
                .intervalFunction(IntervalFunction.ofExponentialRandomBackoff(Duration.ofMillis(200), 2.0, 0.5))
                .retryExceptions(PaymentTransientException.class)
                .build());
    }

    @Override
    public PaymentResult charge(PaymentRequest request) {
        Supplier<PaymentResult> attempt = CircuitBreaker.decorateSupplier(breaker, () -> withTimeout(request));
        try {
            return Retry.decorateSupplier(retry, attempt).get();
        } catch (CallNotPermittedException | PaymentTransientException e) {
            throw new PaymentUnavailableException(e);
        }
    }

    private PaymentResult withTimeout(PaymentRequest request) {
        try {
            return timeLimiter.executeFutureSupplier(
                    () -> CompletableFuture.supplyAsync(() -> delegate.charge(request), executor));
        } catch (TimeoutException e) {
            throw new PaymentTransientException("payment provider timed out", e);
        } catch (RuntimeException e) {
            throw e;
        } catch (Exception e) {
            throw new IllegalStateException(e);
        }
    }
}
```

Register it as the `@Primary PaymentClient` bean that wraps the stub. Read the layers from the inside out: each attempt has a 2 s **timeout**. The **circuit breaker** records every attempt. **Retry** is outermost, so the user waits at most about 3 × 2 s plus backoff. An open breaker throws `CallNotPermittedException`, which is not in `retryExceptions`, so it fails fast and is not retried. The retry config lives in code because `IntervalFunction.ofExponentialRandomBackoff` (exponential backoff with jitter) is the exact policy we want. Jitter (random spread in the wait) stops many clients from retrying at the same instant.

Make retries safe on the provider side too: put `holdId` in the `PaymentRequest` as the provider's idempotency key, so a retried charge after a lost response does not charge twice.

### 8. What the user sees (3 min)

In the CAPSTONE-4 `@RestControllerAdvice`, map `PaymentUnavailableException` to `503 Service Unavailable`, `code: PAYMENT_UNAVAILABLE`, `detail: "Payments are temporarily unavailable. Your seats stay held until <expiresAt>; please try again."`, and the header `Retry-After: 10`. The booking stays `HELD`, so no seat is lost and no money is taken. Add a `mode` property to the stub (`OK`, `SLOW`, `FAIL`, `DECLINE`) so you can demo each path.

## Hints

- **The consumer never receives anything:** check `auto-offset-reset: earliest` and the group id. Inspect the group with `kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group notification`.
- **`OutboxWriter` throws `IllegalTransactionStateException`:** the caller is not transactional. That is `MANDATORY` doing its job.
- **The payment call happens inside the confirm transaction,** so a DB connection is held for up to about 7 s while payments struggle. That is acceptable at this scale. Say so in interviews, and see Stretch for the fix.
- **Testcontainers Kafka:** `@Container @ServiceConnection static KafkaContainer kafka = new KafkaContainer("apache/kafka:3.9.0");` uses `org.testcontainers.kafka.KafkaContainer`, not the older `confluentinc` one.
- **Asserting asynchronous work:** use Awaitility (`await().atMost(10, SECONDS).untilAsserted(...)`), never `Thread.sleep`.

## Stretch

- Split confirm into *reserve* (tx 1), *charge* (no transaction), and *finalize* (tx 2), with a `PAYMENT_PENDING` state, so no DB connection waits on the network.
- Replace polling with change data capture (Debezium reading the Postgres WAL), and write down what you gain and what you now have to operate.
- Add `@RetryableTopic` non-blocking retries and compare it with the blocking `DefaultErrorHandler`.

## Talk about it in interviews

**"How do you publish an event reliably when the DB write succeeds?"**
1. *What:* the transactional outbox. The event row commits atomically with the booking.
2. *How it works inside:* `outbox_event` is inserted in the confirm transaction. A relay polls with `for update skip locked`, sends with key `bookingId`, waits for the ack, and marks the row published.
3. *Where used:* any "change state, then tell others" flow: bookings, orders, payments.
4. *What goes wrong:* duplicates (at-least-once), relay lag, an outbox table that grows (purge old published rows), and lost ordering if you pick the wrong key.

**"Exactly-once?"** Delivery is at-least-once. The *effect* is made once by the idempotent consumer: a unique `(consumer, bookingId)` row inserted in the same transaction as the side effect. Kafka transactions give exactly-once only for Kafka-to-Kafka processing, not for a Postgres write.

**"How do you handle a poison message?"** Bounded retries, then a DLT. Do not retry errors that can never succeed (bad JSON). Alert on DLT depth.

**"What happens when the payment provider is down?"** Each attempt has a 2 s timeout. Only transient errors are retried, 3 times with exponential backoff and jitter. After 50% failures the breaker opens and calls fail fast. The user gets a 503 with `Retry-After`, the seats stay held, and nobody is charged twice, because the provider receives an idempotency key.
