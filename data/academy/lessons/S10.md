## Where we are

S8 split ShopKart into services; S9 gave us the platforms to run them (containers, Kubernetes,
Kafka, tracing) and showed their cost. This lesson is about the correction that followed: many
teams found they had split too early or too finely, and moved back toward one deployable unit,
with firm boundaries *inside* it. That shape is the **modular monolith**.

## The problem

Two years after the split, ShopKart has 40 services and 12 engineers. A typical week:

- Adding a "gift message" field touches Orders, Checkout, Email and the BFF: four repos, four
  pipelines, four deploys in the right order.
- Half the incidents are timeouts or version mismatches between services, not bugs in features.
- The cloud bill for the platform (cluster, broker, tracing, mesh) is larger than for the
  application code.
- Nobody can run "the whole shop" on a laptop.

The splits were not wrong in principle. They were wrong **for this team size and this stage**.
This is **accidental complexity**: difficulty that comes from our choices, not from the problem.

## The pendulum

Architecture has swung back and forth for decades:

```text
 one big app ──► SOA + ESB ──► microservices ──► "too many services" ──► modular monolith
 (tangled)       (central       (independent      (network pain,          (one deploy,
                  bottleneck)    teams)            platform cost)          firm boundaries)
```

Each swing fixes the last era's pain and overshoots. The lesson is not "monoliths good" or
"microservices good". It is: **choose for your team size, your scale and how well you know the
domain, and expect to change as those change.**

## What a modular monolith is

A **modular monolith** is one application, deployed as one unit, built from **modules**: parts
with a clear public API and hidden internals, each owning its own data, that may only use each
other through those APIs.

```text
┌───────────────────── ShopKart (one jar, one deploy) ─────────────────────┐
│  orders               inventory              payments                    │
│  ├─ OrderService ◄──  ├─ InventoryService    ├─ PaymentService  ◄─ API   │
│  └─ internal/  ✗      └─ internal/  ✗        └─ internal/  ✗   ◄─ hidden │
│        │ events: OrderPlaced ──────────►                                 │
└────────┼─────────────────────────────────────────────────────────────────┘
       [one database, but each module owns its own tables or schema]
```

It keeps from microservices: boundaries by business capability, data ownership, events between
parts. It drops: the network between them, separate deploys, distributed transactions. A call
between modules is a method call, and a cross-module change can be one commit and one test run.

The rule that makes it work: **boundaries must be enforced by a tool, not just by good intentions.**
Without enforcement, a monolith drifts back into a tangle within months.

## Enforcing boundaries: Spring Modulith

**Spring Modulith** (a Spring project; 1.0 was released in 2023) treats each direct sub-package of
your main application package as a module. Classes in a module's top-level package are its API;
sub-packages (like `orders.internal`) are hidden. A test checks the rules:

```java
ApplicationModules.of(ShopKartApplication.class).verify();
```

`verify()` fails the build if one module uses another's internal classes, or if modules depend on
each other in a cycle. Plain Java alternatives exist too: Java's own module system (JPMS), separate
Maven modules, or ArchUnit tests.

## Talking between modules: events

If Orders calls Inventory and Inventory calls Orders, you have a cycle and the boundary means
little. The usual fix is the same as in S9, but in-process: Orders publishes an **application
event**, and Inventory listens.

```java
events.publishEvent(new OrderPlaced(orderId, sku, quantity));   // in orders
```

```java
@TransactionalEventListener          // in inventory: runs after the order transaction commits
void on(OrderPlaced e) { reserve(e.sku(), e.quantity()); }
```

A plain after-commit listener has the S8 outbox problem: if it fails, the event is lost. Spring
Modulith adds an **event publication registry** that stores each event in the database with the
transaction and marks it done when the listener succeeds, the outbox idea again, and an
`@ApplicationModuleListener` annotation for this async, transactional style of listener.

## Extracting later

Because a module already has an API, owns its data and talks through events, extracting it into a
service later is mostly mechanical: the API becomes HTTP or gRPC, the in-process events go onto a
broker. That is the point: **a good modular monolith keeps the microservices option open** without
paying for it now.

## When to split, when to merge

| Signal | Points toward |
|---|---|
| One or a few teams; domain still being learned | Modular monolith |
| Parts need very different scaling or runtimes (GPU, huge memory) | Separate service for that part |
| Teams block each other's releases despite clean modules | Extract the busiest boundary |
| Most changes touch several services together | Merge those services |
| Weak deploy automation and observability | Fewer deployables |
| Hard isolation needed (security, compliance, blast radius) | Separate service |

## Industry cases

Read each original; these are pointers, not full summaries.

- **Segment, *Goodbye Microservices* (2018)**, by Alexandra Noonan. Segment ran a separate service
  for each destination it sends data to, well over a hundred. Shared-library versions drifted
  apart and operational load grew with every destination, so they merged the destinations into one
  service. Notice the reason: many near-identical services, all changing for the same reasons.
- **Shopify, *Deconstructing the Monolith* (2019)**, by Kirsten Westeinde. Instead of splitting
  their large Rails monolith into services, they reorganised it into components with enforced
  boundaries. They later open-sourced a tool, Packwerk, to check those boundaries.
- **Amazon Prime Video (2023)**: *Scaling up the Prime Video audio/video monitoring service and
  reducing costs by 90%*. One monitoring tool, first built from serverless pieces (AWS Step
  Functions and Lambda), was moved into a single process running on containers; the title states
  the cost saving. Read carefully: it is about one tool, not all of Prime Video, and the new design
  still runs on AWS. The lesson is about matching the design to the workload.
- **Stack Overflow**: Nick Craver's post *Stack Overflow: The Architecture – 2016 Edition*
  describes serving a very large site from a monolithic application on a small number of servers.
- **DHH, *The Majestic Monolith* (2016)**: Basecamp's argument for a well-built monolith for a small
  team. Opinionated, and a useful counterweight.

## Lab (~10 min)

**Build: merge two over-split services into modules and verify the boundaries.** You need a Spring
Boot project with the Spring Modulith starter (`spring-modulith-starter-core`) and test starter
(`spring-modulith-starter-test`), using the Spring Modulith BOM version that matches your Boot version.

```java
// com/shopkart/ShopKartApplication.java
package com.shopkart;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class ShopKartApplication {
    public static void main(String[] args) { SpringApplication.run(ShopKartApplication.class, args); }
}
```

```java
// com/shopkart/orders/OrderPlaced.java      (part of the orders API)
package com.shopkart.orders;

public record OrderPlaced(String orderId, String sku, int quantity) {}
```

```java
// com/shopkart/orders/OrderService.java     (part of the orders API)
package com.shopkart.orders;

import org.springframework.context.ApplicationEventPublisher;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderService {
    private final ApplicationEventPublisher events;

    OrderService(ApplicationEventPublisher events) { this.events = events; }

    @Transactional
    public void place(String orderId, String sku, int quantity) {
        // save the order in the orders tables (omitted)
        events.publishEvent(new OrderPlaced(orderId, sku, quantity));
    }
}
```

```java
// com/shopkart/inventory/internal/StockLedger.java   (hidden inside inventory)
package com.shopkart.inventory.internal;

import org.springframework.stereotype.Component;

@Component
public class StockLedger {
    public void reserve(String sku, int quantity) {
        System.out.println("reserved " + quantity + " x " + sku);
    }
}
```

```java
// com/shopkart/inventory/InventoryListener.java
package com.shopkart.inventory;

import com.shopkart.inventory.internal.StockLedger;
import com.shopkart.orders.OrderPlaced;
import org.springframework.stereotype.Component;
import org.springframework.transaction.event.TransactionalEventListener;

@Component
class InventoryListener {
    private final StockLedger ledger;

    InventoryListener(StockLedger ledger) { this.ledger = ledger; }

    @TransactionalEventListener
    void on(OrderPlaced event) { ledger.reserve(event.sku(), event.quantity()); }
}
```

```java
// src/test/java/com/shopkart/ModularityTests.java
package com.shopkart;

import org.junit.jupiter.api.Test;
import org.springframework.modulith.core.ApplicationModules;

class ModularityTests {
    @Test
    void verifiesModuleBoundaries() {
        ApplicationModules.of(ShopKartApplication.class).verify();
    }
}
```

1. Run the test: it passes. Inventory depends on the orders API (`OrderPlaced`); nothing reaches
   into internals.
2. **Break it:** inject `StockLedger` into `OrderService` and call it directly. Run the test again
   and read the violation: orders is using an internal type of inventory.
3. **Break it differently:** move `StockLedger` up into `com.shopkart.inventory` (so it is API),
   call it from orders again, and run the test. Now orders depends on inventory and inventory on
   orders: a cycle, which `verify()` also reports. This is why the event exists.

**Debate:** "When is splitting a service the wrong answer?" Write three situations and, for each,
what you would do instead (a module, a library, a separate scaling group for one endpoint, a queue).

## Gotchas

- **"Monolith" without modules.** One deploy is fine; one tangle is not. Enforce boundaries with a
  test from day one.
- **Shared tables across modules.** If two modules write the same table, they are one module. Give
  each its own tables or schema and go through the owning module's API.
- **Cycles hidden by events.** Events remove compile-time cycles, but a ping-pong of events is still
  coupling. Draw the flow.
- **Losing events after commit.** A plain after-commit listener that throws loses work. Use a
  persisted event registry (an outbox) for anything that matters.
- **Reading a case study as a verdict.** Segment and Prime Video were specific workloads. Take the
  reasoning, not the headline.

## In interviews

Usually asked as judgement or behavioural questions:

- [Technical debt under a deadline](#/q/tech-debt-vs-deadline): consolidating services, or not,
  is a classic example.
- [Most challenging project, end to end](#/q/most-challenging-project): a migration story in either
  direction works well if you show the reasoning.
- [SOLID principles and dependency inversion](#/q/solid-principles): module APIs and hidden internals
  are dependency inversion at the architecture level.
- [Design an E-commerce Admin Portal](#/q/design-ecommerce-admin-portal): a good place to propose a
  modular monolith and say when you would split.

Typical follow-ups:

- *"Isn't a modular monolith just a monolith?"* Strong answer: the difference is enforced
  boundaries and data ownership, checked in the build, which keep extraction cheap.
- *"How would you decide to extract a module?"* Strong answer: a measured signal (release
  contention, scaling difference, isolation need), the module already has a clean API and owns its
  data, and you extract with the strangler approach from S8.

## Explain it in 2 minutes

**Prompt:** "Microservices or modular monolith for a new product with 10 engineers?"

1. Accidental complexity: network, deploys and platform cost don't pay off for one or two teams.
2. Modular monolith: one deploy, modules by business capability, hidden internals, own data.
3. Enforce boundaries with a tool (Spring Modulith, ArchUnit, JPMS); events between modules.
4. Keep extraction cheap; extract when a real signal appears.
5. Cite a case accurately (Segment, Shopify) and its specific reason.

## Check yourself

1. What is accidental complexity? Give an example from microservices.
2. In Spring Modulith, what makes a class part of a module's API vs internal?
3. Why do modules often communicate through events rather than direct calls?
4. What problem does an event publication registry solve?
5. Name one good reason to extract a module into its own service.

### Answers

1. Difficulty caused by our solution, not the problem; for example, four coordinated deploys to
   add one field.
2. By default, types in the module's top-level package are API; types in sub-packages are internal.
3. To avoid dependency cycles and keep the publisher unaware of who reacts.
4. Losing an event when the after-commit listener fails or the app stops; events are stored and
   retried until handled.
5. Very different scaling or runtime needs, release contention between teams, or hard isolation
   for security or blast radius.
