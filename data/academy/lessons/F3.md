## Where we are

F1 gave you the building blocks: load balancers, caches, CDNs, replicas, shards, queues,
consistent hashing and Bloom filters. Knowing the parts isn't the same as passing the round. This
lesson gives you a **repeatable method** for running a 45–60 minute design interview, including the
arithmetic that tells you which parts you actually need.

## The problem

Two candidates get "Design Pastebin".

```text
Candidate 1: "So we'll have Kafka, Redis, Cassandra, a CDN, microservices..." (minute 2)
Candidate 2: "Before I draw anything: who uses it, how many, how big is a paste,
              how long do we keep them? ... OK, that's ~12 writes/s and ~18 TB over
              five years, so storage is the real problem, not traffic."
```

Candidate 1 recites a textbook architecture. Microsoft interview reports describe interviewers
rejecting exactly that, and the hiring bar there is "defend trade-offs and go deep where pushed".
Candidate 2 lets the numbers choose the design. The method below makes you candidate 2 every time.

## The method in one picture

```text
 1. Requirements      what must it do, and how well?           ~5 min
 2. Estimates         QPS, storage, bandwidth, memory           ~5 min
 3. API               the few calls clients make                ~3 min
 4. Data model        entities + the queries they must serve    ~4 min
 5. High-level design boxes and arrows for the main flows       ~10 min
 6. Deep dives        2 hard parts, done properly               ~15 min
 7. Bottlenecks       what breaks first, failures, hot spots    ~5 min
 8. Trade-offs        what you chose, what you gave up          ~3 min
```

Times are for a 60-minute round with about 50 minutes of design. The sections below take each step
in turn.

## Step 1: requirements

**Functional requirements** are what the system does ("create a paste, read a paste by link").
**Non-functional requirements (NFRs)** are how well it does them: scale, latency, availability,
consistency and durability.

Ask, then write the answers down where the interviewer can see them:

```text
Functional:   create paste (text ≤ 1 MB), read by short link, optional expiry
Out of scope: accounts, editing, search      ← say this explicitly
NFR:          1M new pastes/day, reads 10× writes, p99 read < 200 ms,
              99.9% available, a paste must never be lost
```

**p99 latency** means 99% of requests finish faster than this. **99.9% available** means at most
about 8.8 hours of downtime a year (about 43 minutes a month). 99.99% allows about 53 minutes a
year.

**The rule:** pick 2–3 core features and say out loud what you're leaving out. A narrow design
done deeply beats a wide one done shallowly.

## Step 2: back-of-envelope estimates

**Back-of-envelope estimation** means rough arithmetic, accurate to within a factor of a few, that
tells you which resources matter. The numbers worth memorising:

```text
1 day  = 86,400 s  ≈ 10^5 s (round to this; your answers come out ~15% low, which is fine)
1M per day   ≈ 12 per second         100M per day ≈ 1,200 per second
peak         ≈ 2–3 × average          (state it as an assumption)

1 KB × 1M = 1 GB      1 KB × 1B = 1 TB      1 MB × 1M = 1 TB

latency, roughly:  RAM read ~100 ns · SSD random read ~100 µs
                   same-datacentre round trip ~0.5 ms · cross-continent ~100+ ms
```

**Worked example: Pastebin.** Assume an average paste of 10 KB.

```text
Writes:   1M/day ÷ 86,400        ≈ 12/s     peak ×3  ≈ 35/s
Reads:    10M/day ÷ 86,400       ≈ 116/s    peak ×3  ≈ 350/s
Storage:  1M × 10 KB = 10 GB/day → 3.65 TB/year → ~18 TB in 5 years
          × 3 replicas           ≈ 55 TB
Read bandwidth: 116/s × 10 KB    ≈ 1.2 MB/s     (tiny)
Cache:    keep the hottest 20% of a day's reads: 0.2 × 10M × 10 KB = 20 GB
          → fits in one or two cache nodes
```

**What the numbers tell you:** traffic is tiny, so one database could handle the QPS. **Storage is
the real problem**: 55 TB is too much for one database box. So paste bodies go into an **object
store** (blob storage such as S3 or Azure Blob, cheap and built for huge files), and a small
database keeps only the metadata. You now have a reason for every box you draw.

**The rule:** every estimate must end in a sentence that starts with "so…". If a number doesn't
change the design, don't spend time on it.

## Step 3: the API

Define the few calls clients make. Keep it at this level:

```text
POST /pastes                 {content, expiresIn?}     → 201 {id, url}
GET  /pastes/{id}                                      → 200 {content, createdAt}
                                                       → 404 if missing or expired
```

Things to mention briefly: authentication (if it's in scope), **pagination** for lists (a
**cursor**, an opaque "continue from here" token, beats page numbers on large or changing data),
idempotency keys on unsafe POSTs (F2), and rate limiting.

## Step 4: the data model

List the entities, then the **access patterns** (the exact queries the system runs). The access
patterns decide the storage, not the other way round.

```text
paste_metadata
  id          CHAR(8)     PK      ← the short link
  blob_key    TEXT                ← where the body lives in object storage
  created_at  TIMESTAMP
  expires_at  TIMESTAMP   NULL

Access patterns:  get by id (99%)  ·  delete where expires_at < now (background job)
```

SQL or NoSQL? Say why. Here, a single key-value lookup by id at modest QPS means either works. A
relational database is the simple default, and a key-value store is the natural choice once you
need to shard it.

## Step 5: the high-level design

Draw the main flows end to end: one write path and one read path.

```text
            ┌──────────── write ───────────┐
 client ──► LB ──► paste service ──► object store (body)
            │            │      └──► metadata DB
            │            ▼
            └─ read ─► cache (id → metadata/body) ──miss──► metadata DB + object store
```

Walk the interviewer through one request: "A POST arrives, we generate an id, write the body to
blob storage, then the metadata row, then return the URL." Keep the components justified by
Steps 1 and 2.

## Step 6: deep dives

Pick **two** hard parts, or let the interviewer choose: "I could go deeper into ID generation or
into expiry. Which is more interesting to you?" For Pastebin:
- **ID generation:** random 8-character base62 versus a counter, and handling collisions (F4 goes
  deep on this).
- **Expiry:** lazy (check `expires_at` on read) plus a background sweep that deletes in batches.

A deep dive means alternatives, the trade-off, your choice, and what would change it.

## Step 7: bottlenecks and failures

Go through the diagram box by box and ask "what if this dies, or gets 10× the load?":

```text
LB dies            → redundant pair / managed LB
cache node dies    → misses fall to DB; protect DB with coalescing
DB primary dies    → promote replica (F2: consensus, possible lost async writes)
viral paste        → hot key: CDN or a local in-process cache in front of the shared cache
abuse / spam       → rate limit per IP and per user, size limits
```

For Microsoft in particular, add **how you would know**: the metrics and alerts that detect each
failure (F6 covers this).

## Step 8: trade-offs

End with a short summary in this shape: **two options, the trade-off, my choice, what would change
it**.

> "I put bodies in object storage rather than the database. It costs an extra hop on reads, but it
> keeps the database small and cheap. If pastes were tiny, under 1 KB, I'd keep them inline."

## Time management and what to say

| Minute (60-min round) | Minute (45-min round) | You are… | Say something like |
|---|---|---|---|
| 0–5 | 0–4 | Requirements | "Let me pin down scope before designing." |
| 5–10 | 4–7 | Estimates | "Quick numbers so the design is driven by load, not habit." |
| 10–17 | 7–12 | API + data model | "These are the access patterns the storage must serve." |
| 17–27 | 12–20 | High-level design | "Let me walk one write and one read end to end." |
| 27–47 | 20–35 | Deep dives | "The hardest part is X. Here are two options…" |
| 47–55 | 35–42 | Bottlenecks, failures | "What breaks first at 10× load is…" |
| 55–60 | 42–45 | Trade-offs, questions | "To summarise the key choices…" |

Habits that help:
- **Think aloud.** Silence gives the interviewer nothing to grade.
- **Check in** at each step: "Does this scope match what you had in mind?"
- **When pushed, don't defend by reflex.** "Good point. That breaks when X. I'd change it to Y."
- **Watch the clock.** If you're at minute 30 without a full diagram, stop polishing and draw it.
- **Google L5 rounds** expect you to drive the whole thing yourself, and often add a change of
  requirements at the end. Leave 5 minutes for it.

## Lab (~10 min)

A design exercise with pen and paper. Estimate a photo-sharing service:

- 10M daily active users.
- Each uploads 0.2 photos a day on average, at 2 MB per photo.
- Each views 50 photos a day.
- Keep photos forever. Assume a peak of 3× the average.

Work out the upload QPS, the view QPS, storage per day and per year, and read bandwidth. Then write
two "so…" sentences. Only then check here:

```text
Uploads:   2M/day ÷ 86,400 ≈ 23/s,   peak ≈ 70/s
Views:     500M/day ÷ 86,400 ≈ 5,800/s,  peak ≈ 17,000/s
Storage:   2M × 2 MB = 4 TB/day → ~1.5 PB/year (before replication)
Bandwidth: 5,800/s × 2 MB ≈ 11.6 GB/s if you serve originals (!)
```

**So…** (1) Never serve originals. Generate thumbnails (say 200 KB), which cuts bandwidth about 10×,
and put a CDN in front, because most views are of popular photos. (2) Petabytes per year means
object storage with tiering (cold photos move to cheaper storage). The metadata stays in a
sharded database.

## Gotchas

- **Drawing before asking.** Jumping to a solution without exploring requirements is a classic way
  to lose points. One Microsoft report describes a candidate marked down for exactly this, in an
  LLD round. Spend the first 5 minutes on scope.
- **Estimates with no conclusion.** Numbers that don't lead to "so we need X" waste minutes. Always
  close the loop.
- **Forgetting peak and replication.** Average QPS and single-copy storage understate the need by
  3× or more. Multiply and say so.
- **Deep-diving everything.** Two strong deep dives beat five shallow ones. Ask the interviewer to
  choose.
- **Running out the clock on the diagram.** Have the end-to-end design on the board by about the
  halfway mark.
- **Textbook answers.** "Use Kafka" with no reason reads as recall. Every component needs a
  "because".

## In interviews

Every HLD question is graded on this method as much as on the final design. Practise running the
full eight steps, with timings, on [Design a URL Shortener](#/q/design-url-shortener),
[Design a Ticket Booking System](#/q/design-ticket-booking) and
[Design a Proximity Service](#/q/design-proximity-service). For a design that leans heavily on
estimates, try [Design an image/GIF/video hosting service (no sign-up)](#/q/design-image-hosting-service).

Typical follow-ups:
- **"Why did you pick that database?"** A strong answer cites the access patterns from Step 4 and
  the numbers from Step 2, names the alternative, and says what would make you switch.
- **"Now the traffic is 100× higher."** A strong answer redoes the estimate, names which component
  breaks first, and changes only that, instead of redesigning everything.

## Explain it in 2 minutes

*"Walk me through how you approach a system design question."*

- Clarify functional requirements and NFRs, and state what's out of scope.
- Estimate QPS (with peak), storage (with replication) and bandwidth, each ending in a "so…".
- Define the API and the data model from the access patterns.
- Draw the high-level design and walk one read and one write through it.
- Deep-dive two hard parts with alternatives and trade-offs.
- Close with bottlenecks, failure modes, monitoring and a summary of trade-offs.

## Check yourself

1. 50M requests a day: roughly what average QPS, and what peak?
2. 200M records a day at 500 bytes each, kept for 3 years. Roughly how much storage, before
   replication?
3. What is the difference between a functional requirement and an NFR? Give one of each for a chat
   app.
4. Why does the data model step start from access patterns?
5. You are at minute 32 of 60 with no diagram. What do you do?

### Answers

1. 50M ÷ 86,400 ≈ 580/s on average, and about 1,500–1,750/s at peak (2–3×).
2. 200M × 500 B = 100 GB/day → about 36.5 TB/year → about 110 TB over 3 years.
3. Functional is what it does ("send a message to a group"). An NFR is how well it does it
   ("delivered within 500 ms at p99", "99.99% available").
4. Storage choice, keys and indexes all exist to serve specific queries. A schema designed without
   them often needs scatter-gather queries or a rewrite.
5. Stop refining. Draw the end-to-end read and write paths now, then pick one deep dive.
