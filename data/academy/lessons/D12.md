## Where we are

From SPRING-BOOT-7 you know how JPA, Hibernate and `@Transactional` behave, including the persistence
context and the fact that a flush is not a commit. You have also built controllers (SPRING-BOOT-6) and
written JDBC by hand (DB-SQL-5). This lesson is about proving all of that works, with tests that are
fast enough to run on every change and honest enough to catch real bugs.

## The problem

A typical inherited Spring Boot test suite looks like this:

- Every test class is `@SpringBootTest`, so the suite takes eight minutes and people stop running it.
- Repository tests run on H2, so a Postgres-only bug ships to production.
- Service tests mock six collaborators and verify every call, so any refactor breaks twenty tests
  while real bugs slip through.
- Two tests fail "sometimes" on CI, so everyone has learned to press re-run.

Each symptom has a specific cause and a standard fix. The tools are JUnit 5, AssertJ, Mockito, Spring's
test slices and Testcontainers. The skill is choosing the *smallest* test that can catch a given bug.

## The test pyramid

```text
            /\         few    end-to-end: @SpringBootTest, real HTTP, real DB   (seconds each)
           /  \
          /----\       some   slices: @WebMvcTest, @DataJpaTest + Testcontainers (sub-second to seconds)
         /      \
        /--------\     many   unit: plain JUnit + Mockito, no Spring             (milliseconds)
```

- **Unit tests** check one class's logic with its collaborators replaced. No Spring, no database.
- **Slice (integration) tests** start one layer of Spring with real infrastructure for that layer:
  the MVC machinery, or JPA against a real database.
- **End-to-end tests** start the whole application and drive it through its real API.

**The rule:** push each check down to the lowest level that can catch the bug. Business rules belong in
unit tests; "does this JSON map to that request" belongs in a web slice; "does this query work on
Postgres" needs a real Postgres. A handful of end-to-end tests then prove the wiring.

## JUnit 5: anatomy and lifecycle

```java
class StakeRulesTest {

    StakeRules rules;

    @BeforeAll static void once() { }            // runs once per class; static by default
    @BeforeEach void setUp() { rules = new StakeRules(new BigDecimal("1000")); }   // before EVERY test

    @Test
    @DisplayName("stake above the limit is rejected")
    void rejectsAboveLimit() {
        assertThat(rules.isAllowed(new BigDecimal("1000.01"))).isFalse();
    }

    @Nested class AtTheBoundary {                // groups related cases; inner class sees the fields
        @Test void exactlyTheLimitIsAllowed() {
            assertThat(rules.isAllowed(new BigDecimal("1000"))).isTrue();
        }
    }
}
```

JUnit creates a **new instance of the test class for every test method**. That is deliberate: fields
cannot leak state from one test into the next. It is also why `@BeforeAll` must be `static` (no
instance exists yet), unless you opt into `@TestInstance(Lifecycle.PER_CLASS)`.

JUnit 5 is built on an **extension model**: `@ExtendWith(...)` plugs in behaviour such as Mockito's
annotation processing or Spring's context loading. `@SpringBootTest` and the slice annotations already
include `@ExtendWith(SpringExtension.class)`.

Test methods run in a deterministic but *deliberately unspecified* order. Never let one test depend on
another having run first.

## Parameterized tests

When the same rule must hold for many inputs, don't copy the test:

```java
@ParameterizedTest(name = "stake {0} -> allowed={1}")
@CsvSource({
        "0.01,    true",
        "1000,    true",
        "1000.01, false",
        "0,       false",
        "-5,      false"
})
void stakeLimits(BigDecimal stake, boolean allowed) {
    assertThat(rules.isAllowed(stake)).isEqualTo(allowed);
}
```

Other sources: `@ValueSource` for one argument, `@EnumSource` for every value of an enum, and
`@MethodSource("cases")` pointing at a static method that returns a `Stream<Arguments>` for complex
objects. Each row is reported as its own test, so a failure names the exact input.

## AssertJ: assertions that read like sentences

Spring Boot's test starter includes **AssertJ**, a fluent assertion library. Prefer it to JUnit's
`assertEquals`, because the failure messages are far better and the chains read naturally:

```java
assertThat(bets).hasSize(2)
                .extracting(Bet::getEventId)
                .containsExactlyInAnyOrder("ev-1", "ev-2");

assertThatThrownBy(() -> service.place(cmdWithStake("0")))
        .isInstanceOf(IllegalArgumentException.class)
        .hasMessageContaining("positive");

assertThat(total).isEqualByComparingTo("10.0");   // BigDecimal: compare value, ignore scale
```

That last line matters: `new BigDecimal("10.00").equals(new BigDecimal("10.0"))` is `false`, because
`BigDecimal.equals` compares scale too (JAVA-FUND-3's `equals` contract, applied).

## Mockito: mock, stub, verify

A **test double** is any object that stands in for a real collaborator. A **mock** is a double
generated at runtime that records how it was called and returns what you tell it to. Mockito does
three things with one:

```java
@ExtendWith(MockitoExtension.class)
class BetServiceTest {

    @Mock BetRepository bets;                     // 1. mock: a fake implementation of the interface
    @Mock WalletClient wallet;
    Clock clock = Clock.fixed(Instant.parse("2026-10-31T10:00:00Z"), ZoneOffset.UTC);
    BetService service;

    @BeforeEach void setUp() { service = new BetService(bets, wallet, clock); }

    @Test void debitsWalletAndSavesBet() {
        when(bets.save(any(Bet.class))).thenAnswer(inv -> inv.getArgument(0));    // 2. stub

        BetView bet = service.place(new PlaceBet(42L, "ev-1", new BigDecimal("10.00")));

        assertThat(bet.placedAt()).isEqualTo(Instant.parse("2026-10-31T10:00:00Z"));
        verify(wallet).debit(42L, new BigDecimal("10.00"));                       // 3. verify
    }
}
```

- **Stub** (`when(...).thenReturn(...)` / `thenThrow` / `thenAnswer`): decide what a call returns.
  For `void` methods use `doThrow(...).when(wallet).debit(anyLong(), any())`.
- **Verify** (`verify(mock).method(args)`, `never()`, `times(2)`, `verifyNoInteractions(...)`): check a
  call happened. Use it for *side effects* that are the point of the method, such as the debit.
- **Argument matchers** (`any()`, `eq()`, `argThat(...)`): if one argument uses a matcher, all must.

`MockitoExtension` uses **strict stubs**: a stub your test never uses fails the test with
`UnnecessaryStubbingException`. That is a feature; it removes dead setup that misleads readers.

Note the injected `Clock`. Code that calls `Instant.now()` directly cannot be tested deterministically;
code that asks a `Clock` bean can be given a fixed one.

## ArgumentCaptor: inspect what was passed

Sometimes the object passed to a mock is built inside the method, so you can't construct an equal one
in the test. Capture it instead:

```java
ArgumentCaptor<Bet> saved = ArgumentCaptor.forClass(Bet.class);
verify(bets).save(saved.capture());

assertThat(saved.getValue())
        .extracting(Bet::getAccountId, Bet::getEventId)
        .containsExactly(42L, "ev-1");
```

Use a captor when you verify; don't capture in a stub (`when(bets.save(captor.capture()))`), because a
failed match then hides as a `null` return instead of a clear verification failure.

## Over-mocking: when mocks make tests worse

A mock encodes *how* the code does its job. Mock too much and your tests assert the implementation, not
the behaviour: any refactor breaks them, and they still pass when the real collaborators disagree.

- **Mock roles at boundaries, not values.** Mock `WalletClient` (a remote call) and `BetRepository` (the
  database). Never mock records, entities, DTOs or `List`; build real ones.
- **Don't mock types you don't own.** Mocking `RestClient` or `JdbcTemplate` call chains tests your guess
  about the library. Wrap it in your own interface, or test it for real in a slice.
- **Prefer checking outcomes to verifying calls.** Assert on the returned value or saved state; verify
  only the calls that *are* the behaviour (sending the debit, publishing the event).
- **Many mocks means the class does too much.** Five or more collaborators is a design smell
  (LLD-DESIGN-1's single responsibility), not a testing problem.

The analogy is a flight simulator: excellent for practising procedures, useless for discovering that
the real engine has a fault. Mocks prove your class follows its protocol, never that the protocol is
right. That is what the slice tests are for.

## @SpringBootTest: the whole application

```java
@SpringBootTest                       // full context, mock servlet environment by default
@AutoConfigureMockMvc
class PlaceBetFlowTest {
    @Autowired MockMvc mvc;
    // calls go through filters, controller, service, repository, real DB (via Testcontainers)
}
```

`webEnvironment = RANDOM_PORT` starts a real embedded server on a free port, for tests that need real
HTTP. One trap: with a real server the request runs on a *server* thread, so `@Transactional` on the
test method does not roll back what the request wrote. Clean up explicitly.

## Context caching: why some suites are fast

Starting a Spring context takes seconds. The Spring TestContext framework therefore **caches**
contexts and reuses one for every test class with the *same* configuration. The cache key includes
the configuration classes, active profiles, test properties, and the set of bean overrides such as
`@MockitoBean`. By default up to 32 contexts are kept.

```text
OrderTest    @SpringBootTest                         -> context A (started)
BetTest      @SpringBootTest                         -> context A (reused, ~0 s)
WalletTest   @SpringBootTest + @MockitoBean Clock    -> context B (started: different key)
LegacyTest   @DirtiesContext                         -> A thrown away; the next class starts again
```

**The rule:** keep the number of distinct configurations small. Put shared mocks and properties in one
base class or one test configuration, and treat `@DirtiesContext` as a last resort.

## Slices: @WebMvcTest and MockMvc

A **slice** loads one layer. **`@WebMvcTest(BetController.class)`** loads the MVC infrastructure from
SPRING-BOOT-6 (message converters, validation, `@ControllerAdvice`, filters) and that controller. No
services, no repositories, no database. **MockMvc** sends requests through the real `DispatcherServlet`
without a network:

```java
@WebMvcTest(BetController.class)
class BetControllerTest {

    @Autowired MockMvc mvc;
    @MockitoBean BetService service;              // replaces the bean the controller needs

    @Test void zeroStakeIs400AndNeverReachesTheService() throws Exception {
        mvc.perform(post("/v1/bets").contentType(MediaType.APPLICATION_JSON).content("""
                        {"accountId": 42, "eventId": "ev-1", "stake": 0}
                        """))
           .andExpect(status().isBadRequest());
        verifyNoInteractions(service);
    }

    @Test void validBetIs201WithLocation() throws Exception {
        when(service.place(any()))
                .thenReturn(new BetView(7L, "ev-1", new BigDecimal("10.00"), Instant.parse("2026-10-31T10:00:00Z")));
        mvc.perform(post("/v1/bets").contentType(MediaType.APPLICATION_JSON).content("""
                        {"accountId": 42, "eventId": "ev-1", "stake": 10.00}
                        """))
           .andExpect(status().isCreated())
           .andExpect(header().string("Location", "/v1/bets/7"))
           .andExpect(jsonPath("$.eventId").value("ev-1"));
    }
}
```

This catches what unit tests can't: URL mappings, JSON field names, validation annotations, status
codes and error bodies, all of the WEB-API-3 contract. Spring Framework 6.2 also adds
**`MockMvcTester`**, an AssertJ-style alternative to `perform(...).andExpect(...)`.

Other slices follow the same idea: `@JsonTest` (Jackson mapping only), `@RestClientTest` (an HTTP client
against a mock server) and `@JdbcTest` (JDBC without JPA).

## @MockitoBean versus @MockBean

`@MockitoBean` (package `org.springframework.test.context.bean.override.mockito`, Spring Framework
6.2+) replaces a bean in the test's application context with a Mockito mock; `@MockitoSpyBean` wraps the
real bean instead. They replace Spring Boot's older `@MockBean` and `@SpyBean`, which were deprecated in
Boot 3.4 and removed in Boot 4. The behaviour is the same; the newer ones belong to the core framework.

Don't confuse the two kinds of mock: `@Mock` (plain Mockito, no Spring) in unit tests, `@MockitoBean`
only when a Spring context needs a bean replaced. Every distinct `@MockitoBean` set is a new context
cache key.

## @DataJpaTest: repositories against a real database

**`@DataJpaTest`** loads JPA, your entities and repositories, and a `TestEntityManager`. Each test runs
in a transaction that is **rolled back** at the end, so tests don't see each other's data.

That rollback hides a trap you know from SPRING-BOOT-7: if nothing forces a flush, Hibernate may never
send the SQL, so constraint violations and broken mappings never reach the database and the test
passes. Flush, and clear the persistence context, before asserting:

```java
bets.save(new Bet(42L, "ev-1", new BigDecimal("10.00"), Instant.parse("2026-10-31T10:00:00Z")));
em.flush();          // send the INSERT now: constraints and column types are checked here
em.clear();          // forget cached entities, so the next read really hits the database
assertThat(bets.findByAccountId(42L)).hasSize(1);
```

## Testcontainers and @ServiceConnection

By default `@DataJpaTest` swaps your database for an embedded one such as H2. But H2 is not Postgres:
types, locking, JSON operators and SQL dialect all differ. **Testcontainers** starts a real database in
Docker for the test run, and Boot's **`@ServiceConnection`** (Boot 3.1+) points the `DataSource` at it,
with no URL properties:

```java
@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)   // keep the real DB
@Testcontainers
class BetRepositoryTest {

    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired BetRepository bets;
    @Autowired TestEntityManager em;

    @Test void findsBetsForAccount() { /* the save / flush / clear / assert block above */ }
}
```

`static` matters: one container per class, not one per test. To share one container across *all*
classes, declare it as a bean in a `@TestConfiguration` (`@Bean @ServiceConnection PostgreSQLContainer<?>
postgres()`) and `@Import` that configuration. The container then lives as long as the cached context.

Package names moved between versions: on Testcontainers 1.x the class is
`org.testcontainers.containers.PostgreSQLContainer`; on 2.x (used by Boot 4) it is
`org.testcontainers.postgresql.PostgreSQLContainer`, and Boot 4 moved the slice annotations into
per-technology test modules. The concepts are unchanged.

## Flaky tests: causes and cures

A **flaky test** passes and fails on the same code. The usual causes:

| Cause | Cure |
|---|---|
| Time: `Instant.now()`, midnight, time zones | Inject a `Clock`; use `Clock.fixed` in tests |
| Order: relying on `HashMap`/`HashSet` iteration or test execution order | Assert in any order; make each test set up its own data |
| Shared state: static fields, a shared DB without rollback | Reset per test; unique ids per test; avoid statics |
| Async: `Thread.sleep(500)` then assert | Wait for a condition with a timeout (Awaitility) |
| External systems: real third-party APIs, the network | Stub at the boundary, or run it in a container |
| Randomness | Seed it, or inject the random source |

Treat a flaky test as a bug with a cause, not as noise. A suite that is re-run until green has stopped
telling you anything.

## Lab (~10 min)

You need a Boot 3.4+ app with `spring-boot-starter-web`, `-validation`, `-data-jpa`, `-test`, the
Postgres driver, and `spring-boot-testcontainers` plus Testcontainers' `postgresql` module. Docker must be
running for step 3.

```java
@Entity
public class Bet {
    @Id @GeneratedValue private Long id;          // sequence-based: the INSERT waits for a flush
    private long accountId;
    private String eventId;
    private BigDecimal stake;
    private Instant placedAt;

    protected Bet() { }
    public Bet(long accountId, String eventId, BigDecimal stake, Instant placedAt) {
        this.accountId = accountId; this.eventId = eventId; this.stake = stake; this.placedAt = placedAt;
    }
    public Long getId() { return id; }
    public long getAccountId() { return accountId; }
    public String getEventId() { return eventId; }
    public BigDecimal getStake() { return stake; }
    public Instant getPlacedAt() { return placedAt; }
}

public interface BetRepository extends JpaRepository<Bet, Long> { List<Bet> findByAccountId(long accountId); }
public interface WalletClient { void debit(long accountId, BigDecimal amount); }
public record PlaceBet(long accountId, @NotBlank String eventId, @NotNull @Positive BigDecimal stake) { }
public record BetView(Long id, String eventId, BigDecimal stake, Instant placedAt) {
    static BetView from(Bet b) { return new BetView(b.getId(), b.getEventId(), b.getStake(), b.getPlacedAt()); }
}

@Service
public class BetService {
    private final BetRepository bets;
    private final WalletClient wallet;
    private final Clock clock;

    public BetService(BetRepository bets, WalletClient wallet, Clock clock) {
        this.bets = bets; this.wallet = wallet; this.clock = clock;
    }

    @Transactional
    public BetView place(PlaceBet cmd) {
        if (cmd.stake().signum() <= 0) {
            throw new IllegalArgumentException("stake must be positive");
        }
        wallet.debit(cmd.accountId(), cmd.stake());
        Bet saved = bets.save(new Bet(cmd.accountId(), cmd.eventId(), cmd.stake(), Instant.now(clock)));
        return BetView.from(saved);
    }
}

@RestController
@RequestMapping("/v1/bets")
class BetController {
    private final BetService service;

    BetController(BetService service) { this.service = service; }

    @PostMapping
    ResponseEntity<BetView> place(@Valid @RequestBody PlaceBet cmd) {
        BetView bet = service.place(cmd);
        return ResponseEntity.created(URI.create("/v1/bets/" + bet.id())).body(bet);
    }
}
```

Also give the app a `@Bean Clock clock() { return Clock.systemUTC(); }` and some `WalletClient` bean.

1. Write `BetServiceTest` from the Mockito section, plus a `@ParameterizedTest` with
   `@ValueSource(strings = {"0", "-1", "0.00"})` asserting `IllegalArgumentException` and
   `verifyNoInteractions(wallet, bets)`. It should run in milliseconds with no Spring log at all.
2. **Break it:** change the verify to `new BigDecimal("10.0")`. It fails with "Argument(s) are
   different", even though the amounts are equal in value. Fix it with
   `argThat(a -> a.compareTo(new BigDecimal("10")) == 0)`.
3. Write `BetRepositoryTest` with Testcontainers, adding
   `properties = "spring.jpa.hibernate.ddl-auto=create-drop"` to `@DataJpaTest` so Hibernate creates the
   table on the container. Add `@Column(length = 5)` to `eventId`, then write a test that saves a bet with
   `"ev-123456"` and only asserts `getId()` is not null. It **passes**: the id came from a sequence, the
   INSERT was queued, and the rollback discarded it unsent. Add `em.flush()` after the save and it fails
   on the real column limit.
4. Write `BetControllerTest`, then copy it to a second class `BetControllerAgainTest`. Run both and count
   the "Started ... in N seconds" lines in the log: one, because the context is cached. Add
   `@MockitoBean Clock clock;` to the copy only and count again: two.

## Gotchas

- **Everything is `@SpringBootTest`.** Slow, and failures point nowhere. Unit-test logic, slice-test
  layers, and keep only a few full-context tests.
- **Mocking what you don't own, or mocking values.** Mock your own boundary interfaces; build real
  records and entities; test library integrations in a slice.
- **`@DataJpaTest` passing without a flush.** The rollback hides SQL that never ran. `flush()` and
  `clear()` before asserting.
- **Trusting H2 for Postgres behaviour.** Use Testcontainers with `@ServiceConnection` for repository and
  migration tests.
- **Context-cache busting.** Every new `@MockitoBean` set, profile or property combination, and every
  `@DirtiesContext`, starts another context. Centralise test configuration.
- **`Instant.now()` and `Thread.sleep` in tests.** Inject a `Clock`; wait on conditions with a timeout.

## In interviews

Typical prompts: "How do you test a Spring Boot service?", "Unit vs integration tests?", "`@SpringBootTest`
vs `@WebMvcTest`?", "When would you not mock?", "How do you test against a real database?", "A test fails
intermittently on CI; what do you do?". Bank:
[How do you ensure code quality?](#/q/ensuring-code-quality).

A strong answer comes in four layers. For "How do you test a Spring Boot service?":

1. **What:** a pyramid: many fast unit tests, some slice tests, a few end-to-end tests, all run in CI.
2. **How it works inside:** JUnit 5 with a new instance per test; Mockito mocks at boundaries;
   `@WebMvcTest` loads only MVC and goes through the real `DispatcherServlet` via MockMvc; `@DataJpaTest`
   rolls back each test; contexts are cached by configuration key; `@ServiceConnection` wires a
   Testcontainers database into the `DataSource`.
3. **Where used:** service rules in unit tests; JSON contracts, validation and error bodies in web
   slices; queries and migrations against real Postgres; one or two full flows end to end.
4. **What goes wrong:** over-mocking that tests the implementation, H2 hiding dialect bugs, missing
   flushes, slow suites from context-cache misses, and flaky tests from time, order and async waits.

**Follow-up: "Why not just use H2? It's faster."** Because the bug you most need a repository test for is
the one where the real database behaves differently. A cached Testcontainers instance costs a few
seconds per suite run, not per test.

**Follow-up: "What's wrong with verifying every interaction?"** It freezes the implementation. Verify the
side effects that are the behaviour; assert outcomes for the rest.

## Explain it in 2 minutes

*"Walk me through your testing strategy for a Spring Boot REST service."*

- Pyramid: unit tests for logic (JUnit 5, AssertJ, Mockito, a fixed `Clock`), slices for layers, a few
  end-to-end tests.
- Mockito: stub queries, verify side effects, `ArgumentCaptor` for built objects; mock only boundaries.
- `@WebMvcTest` + MockMvc for URLs, JSON, validation and status codes, with `@MockitoBean` services.
- `@DataJpaTest` with Testcontainers and `@ServiceConnection` on real Postgres; flush before asserting.
- Speed: context caching by configuration key; few distinct configurations; no `@DirtiesContext`.
- Reliability: no real time, no ordering assumptions, no sleeps, no shared state; flaky means a bug.

## Check yourself

1. Why does JUnit 5 create a new test-class instance for each test method?
2. What is the difference between `@Mock` and `@MockitoBean`, and when do you use each?
3. A `@DataJpaTest` saves an entity that violates a `NOT NULL` column, yet the test passes. Why?
4. Your suite starts seven Spring contexts. Name two likely causes.
5. Give three causes of flaky tests and the fix for each.

### Answers

1. So instance fields cannot carry state between tests; each test starts clean and order-independent.
2. `@Mock` is plain Mockito for unit tests without Spring. `@MockitoBean` replaces a bean inside a Spring
   test context, for slices or `@SpringBootTest`; each distinct set changes the context cache key.
3. The INSERT was never flushed before the test's transaction rolled back, so the database never saw it.
   Call `flush()` (and `clear()`) before asserting.
4. Different `@MockitoBean` sets, profiles or properties across test classes, and `@DirtiesContext`
   evicting cached contexts.
5. Time-dependence (inject a fixed `Clock`), reliance on ordering of tests or hash collections (isolate
   data, assert in any order), and sleeps around async work (wait on a condition with a timeout).
