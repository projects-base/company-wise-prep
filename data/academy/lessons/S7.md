## Where we are

In BE-STORY-7 you replaced XML with annotations and `@Bean` methods, and Maven made dependencies reproducible.

One problem was left: **every project repeated the same setup** and then deployed a WAR into a separately installed server. The setup:

- DispatcherServlet, JSON;
- DataSource and pool, transactions;
- logging, compatible versions.

This lesson covers **Spring Boot**, which automates that list, and the new question it raises: *what exactly got configured, and why?*

## The problem

Starting a new ShopKart service in 2013 meant an hour or more of setup copied from the last project before the first line of business code.

- Versions drifted between teams.
- "Works on my Tomcat" bugs appeared because each server was configured by hand.

In the same years, **Docker (2013)** made "ship one self-contained runnable thing" the norm.

A WAR that needs a pre-installed server fits that model badly.

## The idea: convention over configuration

**Convention over configuration** means the framework assumes sensible defaults, and you configure only where you differ.

Ruby on Rails (first released in 2004) made the phrase famous: name things the conventional way and the wiring follows.

**Spring Boot 1.0 (April 2014)** applied it to Spring:

> If a library is on your classpath and you haven't defined the relevant bean yourself, Boot configures a sensible one for you.

Rule: **defaults for everything, and any default can be overridden.**

You'll see the mechanism in a moment. It is only `@Configuration` classes with conditions.

## Starters: one dependency per capability

A **starter** is a Maven dependency that contains no code, only a curated set of compatible dependencies for one job.

In Boot 4:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-webmvc</artifactId>   <!-- Spring MVC + embedded Tomcat + JSON -->
</dependency>
```

There is no version on it.

- The **Spring Boot parent POM / BOM** (a "bill of materials", a list of versions known to work together) supplies one tested version for hundreds of libraries.
- That ends the "choose 20 compatible versions" chore from BE-STORY-7.

In Boot 3 and earlier this starter was called `spring-boot-starter-web`. Boot 4 renamed it `spring-boot-starter-webmvc` and deprecated the old name.

## Auto-configuration: conditional `@Configuration`

**Auto-configuration** classes are ordinary `@Configuration` classes that ship inside Boot and are switched on or off by **conditions**:

```java
@AutoConfiguration
@ConditionalOnProperty(name = "greeting.enabled", havingValue = "true", matchIfMissing = true)
public class GreetingAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                 // back off if the application defined its own
    public GreetingService greetingService() {
        return new GreetingService("Hello from auto-config");
    }
}
```

The most important conditions:

- `@ConditionalOnClass`: only if a class is on the classpath (for example, configure Tomcat only if Tomcat's classes are present).
- `@ConditionalOnMissingBean`: only if **you** haven't defined one. This is how your choices win over Boot's defaults.
- `@ConditionalOnProperty`: only if a setting has a given value.

Boot finds auto-configuration classes through a file in each JAR:

- `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` lists one class name per line.
- At start-up Boot evaluates every listed class's conditions and keeps the ones that match.

Rule: **auto-configuration is just conditional `@Configuration` that backs off when you define the bean yourself.**

## The embedded server and the fat jar

BE-STORY-3's lab started Tomcat from `main`. Boot made that the default:

- The web starter brings **embedded Tomcat**, which starts inside your application's process.
- `mvn package` builds an **executable "fat" jar** containing your code plus all dependencies. You run it with `java -jar shopkart.jar`.

```text
Before (BE-STORY-7):  build WAR ──► install + configure Tomcat ──► deploy WAR into it
After  (BE-STORY-8):  build JAR ──► java -jar app.jar   (the server is inside)
```

One artefact, started the same way on a laptop, in CI and in a container.

This fit the container era closely.

## Externalised configuration

Defaults are changed with **properties**, not code:

- `application.properties` or `application.yml`;
- environment variables;
- or command-line arguments.

They follow a documented precedence order (command-line arguments override the file, for example).

```properties
server.port=8085
spring.datasource.url=jdbc:postgresql://localhost:5432/shopkart
greeting.enabled=false
```

The same jar runs in dev, test and prod with different settings.

That is one of the **twelve-factor app** practices, and it comes up again in BE-STORY-10.

## What happens on `SpringApplication.run`

This is a classic interview question. Here is the outline.

Track LIFECYCLE-4 goes deeper.

```text
SpringApplication.run(App.class, args)
  1. decide the app type from the classpath (servlet web / reactive web / none)
  2. prepare the Environment: properties, env vars, args, profiles
  3. create the ApplicationContext
  4. register bean definitions: component scan from App's package
     + auto-configuration classes, filtered by their conditions
  5. refresh: create singleton beans, apply proxies (AOP), start the embedded web server
  6. call CommandLineRunner / ApplicationRunner beans
  7. publish ApplicationReadyEvent: ready for traffic
```

`@SpringBootApplication` is a combination of three annotations:

- `@SpringBootConfiguration` (a `@Configuration`);
- `@EnableAutoConfiguration`;
- `@ComponentScan`.

## The new pain: "where did this bean come from?"

Boot wires dozens of beans you never wrote. Something behaves unexpectedly, such as:

- the wrong DataSource;
- a missing JSON setting;
- your bean being ignored.

Then the question becomes *which auto-configuration made this decision, and why?* The answer is always in the **condition evaluation report**:

- start with `--debug`, or set `debug=true` in `application.properties`, and Boot prints which auto-configurations **matched** and which **did not**, with the reason;
- with Actuator enabled, the same report is available at `/actuator/conditions`.

The second new pain grows slowly.

Boot makes it so easy to add features to one deployable that the **monolith keeps growing**, which leads toward the service eras after BE-STORY-8.

## Alternatives to Boot

Boot wasn't the first to ship a server inside the jar.

- **Dropwizard**, from Yammer and released before Boot, bundled Jetty, Jersey (JAX-RS), Jackson and the Metrics library into one runnable fat jar with an opinionated layout.
- It proved the "just `java -jar` it" style for REST services.
- Boot won the mainstream mostly because it carried the whole Spring ecosystem with it.

The next challenge came from start-up time and memory, which matter for containers and serverless (BE-STORY-11).

- **Micronaut** (2018) and **Quarkus** (Red Hat, 2019) do dependency injection and much of the framework set-up **at build time** instead of with runtime reflection.
- Apps start faster, use less memory, and compile well to **GraalVM native images**, which start in milliseconds.
- Spring responded: Spring Boot 3 and 4 support ahead-of-time processing and GraalVM native images too.

How to choose:

- **Boot:** for its ecosystem and the hiring pool.
- **Quarkus or Micronaut:** when fast cold starts or a small memory footprint per instance are the main constraints.

## Lab (~10 min)

**Build.** Generate a project at start.spring.io:

- Maven, Java 21, Spring Boot 4.0.x;
- group `com.example`, artifact `shopkart`;
- dependency **Spring Web**.

Add a controller in `com.example.shopkart`:

```java
package com.example.shopkart;

import java.util.List;
import java.util.concurrent.CopyOnWriteArrayList;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class OrderController {
    private final List<String> orders = new CopyOnWriteArrayList<>();

    @PostMapping("/orders")
    public List<String> create(@RequestParam String item) {
        orders.add(item);
        return orders;
    }

    @GetMapping("/orders")
    public List<String> list() {
        return orders;
    }
}
```

Run it, then `curl -X POST "localhost:8080/orders?item=book"` and `curl localhost:8080/orders`. You get JSON, with:

- no server install;
- no `web.xml`;
- no DispatcherServlet registration;
- no Jackson setup.

**Count** your configuration lines and compare them with the "new pain" list in BE-STORY-7.

**Build your own auto-configuration.** In a package **outside** the app's scan root (`com.example.greeting`), create:

```java
package com.example.greeting;

public class GreetingService {
    private final String prefix;
    public GreetingService(String prefix) { this.prefix = prefix; }
    public String greet(String name) { return prefix + ", " + name + "!"; }
}
```

…the `GreetingAutoConfiguration` shown earlier, and the file `src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` containing one line:

```text
com.example.greeting.GreetingAutoConfiguration
```

Then add to the application class:

```java
@Bean
CommandLineRunner showGreeting(ObjectProvider<GreetingService> greeting) {
    return args -> System.out.println(greeting.getIfAvailable() == null
            ? ">>> no GreetingService bean"
            : ">>> " + greeting.getObject().greet("Akhil"));
}
```

`ObjectProvider` is an optional lookup: it returns `null` instead of failing when no bean exists.

The imports are `org.springframework.beans.factory.ObjectProvider` and `org.springframework.boot.CommandLineRunner`.

**Observe:**

1. Run it and you get `>>> Hello from auto-config, Akhil!`. You never declared that bean.
2. Set `greeting.enabled=false` in `application.properties` and run it: `>>> no GreetingService bean`. You switched the auto-config off with a property.
3. Remove that line, set `debug=true` and run it. In the report, find:

```text
GreetingAutoConfiguration matched:
   - @ConditionalOnProperty (greeting.enabled=true) matched (OnPropertyCondition)
GreetingAutoConfiguration#greetingService matched:
   - @ConditionalOnMissingBean (types: com.example.greeting.GreetingService; ...) did not find any beans
```

**Break.**

1. Define your own bean in the application class, `@Bean GreetingService myGreeting() { return new GreetingService("Namaste from my app"); }`, and run with `debug=true`.
   - Your greeting wins, and the report now lists `GreetingAutoConfiguration#greetingService` under **Did not match**, with the reason `found beans of type ... myGreeting`.
   - That is backing off, which is how every Boot default yields to you.
2. Now delete `@ConditionalOnMissingBean` from the auto-config and run again.
   - Start-up fails with `A component required a single bean, but 2 were found`, naming both beans and where each was defined.
   - This is the same ambiguity as BE-STORY-7, now caused by a starter.
   - When two starters both define a bean such as a `DataSource`, this report is where you find out who defined what.

**Ship it:** run `./mvnw package`, then `java -jar target/shopkart-0.0.1-SNAPSHOT.jar` (the exact name depends on your version).

One artefact, with the server inside.

## Gotchas

- **One stray `@Bean ObjectMapper` or `DataSource`** turns off all Boot's defaults for that type; check the conditions report.
- **Main class in the wrong package:** scanning starts at the `@SpringBootApplication` package, so sibling-package controllers silently 404.
- **Overriding most of an auto-config?** Exclude it (`@SpringBootApplication(exclude = ...)`) and configure that area explicitly.
- **A value "won't change":** an env variable or command-line argument overrides `application.properties`.
- **Overriding a BOM-managed version** can break compatibility Boot tested; do it only with a reason.
- **Old tutorials use old names** (`-starter-web`, `javax.*`); check the Boot version they target.

## Explain it in 2 minutes

*"What does Spring Boot actually do for you, and how would you find out why a bean exists?"*

1. **Starters** per capability, versions from Boot's BOM.
2. **Auto-configuration:** conditional `@Configuration` listed in `AutoConfiguration.imports`; **your beans win** (back-off).
3. **Embedded server + executable jar:** `java -jar` everywhere, container-friendly.
4. **Externalised configuration** with precedence: one artefact, every environment.
5. Debug with the **condition evaluation report** (`--debug`, `/actuator/conditions`); risks are hidden config and a growing monolith.
