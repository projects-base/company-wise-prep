## Where we are

From D2 you know the plain Spring container: bean definitions from scanning and `@Bean` methods,
`ApplicationContext.refresh()`, profiles, and an `Environment` of ordered property sources. In
plain Spring, *you* declare every infrastructure bean: the `DataSource`, the transaction manager,
the `DispatcherServlet`, the JSON mapper. Spring Boot declares them for you, and this lesson
shows exactly how. It is ordinary Spring config, guarded by conditions.

## The problem

A minimal plain-Spring web and JPA app needs a long list of configuration before you write any
business code: a connection pool, an `EntityManagerFactory`, a `JpaTransactionManager`,
`@EnableTransactionManagement`, a `DispatcherServlet`, Jackson converters, an embedded Tomcat,
error pages… Every project copied the same few hundred lines and got small details wrong.

Boot's answer is to **ship that configuration as a library, and make each piece step aside the
moment you configure it yourself.**

## `@SpringBootApplication` is three annotations

```java
@SpringBootApplication          // this repo's CompanyWisePrepApplication
public class CompanyWisePrepApplication { ... }
```

expands to:

```java
@SpringBootConfiguration        // = @Configuration: this class can declare @Bean methods
@EnableAutoConfiguration        // = "import Boot's ready-made configuration classes"
@ComponentScan                  // scan this package and below (plus two Boot exclude filters)
```

Two consequences follow:

- **Package placement matters.** Scanning starts at the main class's package. A `@Service` in a
  sibling package such as `com.other` is never found.
- **The main class is itself a config class.** That is why `CompanyWisePrepApplication` can
  declare `@Bean Clock clock()`.

## Auto-configuration: ordinary config, loaded from a list

An **auto-configuration** is a normal `@Configuration` class (marked `@AutoConfiguration`) that
lives in a Boot jar. `@EnableAutoConfiguration` finds them by reading a plain text file from
every jar on the classpath:

```text
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

In Boot 4 the auto-configurations are split by technology into modules, each with its own file.
For example, `spring-boot-webmvc-4.0.5.jar` lists:

```text
org.springframework.boot.webmvc.autoconfigure.DispatcherServletAutoConfiguration
org.springframework.boot.webmvc.autoconfigure.WebMvcAutoConfiguration
org.springframework.boot.webmvc.autoconfigure.error.ErrorMvcAutoConfiguration
...
```

Two details make this safe:

1. **They are processed after your configuration.** So when an auto-config asks "has the user
   defined a `DataSource`?", your beans are already registered.
2. **Every one of them is guarded by conditions.** Being on the list only makes a class a
   *candidate*. Its conditions decide whether it applies.

## Conditions: `@Conditional*`

A **condition** is a check that runs while bean definitions are being read and decides whether
a config class or `@Bean` method is registered at all. Here are the ones you will see most:

| Annotation | Registers only if… |
|---|---|
| `@ConditionalOnClass(X.class)` | class X is on the classpath (the library is present) |
| `@ConditionalOnMissingClass` | a class is absent |
| `@ConditionalOnMissingBean(T.class)` | **no bean of type T exists yet** (your bean wins) |
| `@ConditionalOnBean` / `@ConditionalOnSingleCandidate` | a bean exists (or exactly one does) |
| `@ConditionalOnProperty` / `@ConditionalOnBooleanProperty` | a property has a given value |
| `@ConditionalOnWebApplication(type = SERVLET)` | the app is a servlet web app |

A simplified view of the pattern Boot uses everywhere:

```java
@AutoConfiguration
@ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class })   // JDBC on the classpath?
class DataSourceAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean(DataSource.class)                          // did the user define one?
    HikariDataSource dataSource(DataSourceProperties props) { ... }
}
```

The rule: **adding a jar turns a feature on (`OnClass`), and defining your own bean turns Boot's
version off (`OnMissingBean`).** That is "convention over configuration" in two annotations.

## Starters: dependency bundles, no code

A **starter** is a Maven artifact that contains almost no code. It exists to pull in a
consistent set of libraries. This repo's `pom.xml` uses `spring-boot-starter-web` (Spring MVC,
embedded Tomcat, Jackson), `spring-boot-starter-data-jpa` (Hibernate, Spring Data JPA, HikariCP)
and `spring-boot-starter-validation`. Boot 4 also offers `spring-boot-starter-webmvc` as the more
explicit name.

The starter puts classes on the classpath, `@ConditionalOnClass` notices them, and the matching
auto-configuration switches on. The parent POM (`spring-boot-starter-parent`) pins compatible
versions, which is why the starters carry no version numbers.

## Externalised configuration: who wins

Boot adds many property sources to the `Environment` (D2). A source higher in this list
overrides one below it:

```text
 highest  ┌─ test overrides (@TestPropertySource, @DynamicPropertySource, @SpringBootTest(properties))
          ├─ command-line args            --prep.data-dir=./x
          ├─ SPRING_APPLICATION_JSON
          ├─ Java system properties       -Dprep.data-dir=./x
          ├─ OS environment variables     PREP_DATADIR=./x
          ├─ config files:  application-{profile}.yml  outside jar > inside jar
          │                 application.yml            outside jar > inside jar
          ├─ @PropertySource on your @Configuration classes
 lowest   └─ SpringApplication.setDefaultProperties(...)
```

Three practical rules follow from this:

- **Profile-specific files beat the base file.** `application-prod.yml` overrides
  `application.yml`.
- **Environment variables use relaxed binding.** `prep.data-dir` becomes `PREP_DATADIR`:
  uppercase, with `.` replaced by `_` and dashes removed. This is how containers and Kubernetes
  inject configuration.
- **Prefer `@ConfigurationProperties`** (a typed, validated record bound from a prefix) over
  many scattered `@Value` lookups once you have more than two or three related settings.

## Reading the conditions report (`--debug`)

When you ask "why is this bean here?" or "why isn't it?", start Boot with `--debug`. It prints a
**CONDITIONS EVALUATION REPORT** with four parts: *Positive matches*, *Negative matches*,
*Exclusions* and *Unconditional classes*. Here are real lines from this repo, run with
`--debug --spring.main.web-application-type=none`:

```text
   AopAutoConfiguration.AspectJAutoProxyingConfiguration.CglibAutoProxyConfiguration matched:
      - @ConditionalOnBooleanProperty (spring.aop.proxy-target-class=true) matched (OnPropertyCondition)

   DataSourceConfiguration.Hikari matched:
      - @ConditionalOnClass found required class 'com.zaxxer.hikari.HikariDataSource' (OnClassCondition)
      - @ConditionalOnMissingBean (types: javax.sql.DataSource; SearchStrategy: all) did not find any beans (OnBeanCondition)

   DataSourceTransactionManagerAutoConfiguration.JdbcTransactionManagerConfiguration#transactionManager:
      Did not match:
         - @ConditionalOnMissingBean (types: org.springframework.transaction.TransactionManager; SearchStrategy: all) found beans of type 'org.springframework.transaction.TransactionManager' transactionManager (OnBeanCondition)

   WebMvcAutoConfiguration:
      Did not match:
         - not a servlet web application (OnWebApplicationCondition)
```

Read each block as "class, then verdict, then which condition decided it":

- The first block is why D3 said that Boot uses CGLIB proxies.
- HikariCP is the pool because its class is present and you defined no `DataSource`.
- The JDBC transaction manager backed off because JPA's auto-config had already registered a
  `transactionManager`. That is `OnMissingBean` working as designed.
- Web MVC was skipped because the run turned the web stack off.

In a running app, Actuator's `/actuator/conditions` endpoint shows the same data (D8).

## Lab (~10 min)

Run these in this repo, from its root. In PowerShell, set environment variables with
`$env:PREP_DATADIR="./from-env"` and clear them afterwards with `Remove-Item Env:PREP_DATADIR`.

1. **The report.** Run `./mvnw spring-boot:run "-Dspring-boot.run.arguments=--debug"`. Find
   `DataSourceConfiguration.Hikari`, `HibernateJpaAutoConfiguration` and
   `DispatcherServletAutoConfiguration` under *Positive matches*. Then pick any negative match
   and explain it out loud.
2. **Precedence.** `DataImporter` reads `@Value("${prep.data-dir}")`, and `application.yml` sets
   it to `./data`. Point it at directories that don't exist, so the import fails and tells you
   which value won (`Data directory not found: ...from-X`):
   - set the environment variable `PREP_DATADIR=./from-env` and run. The env var wins over the
     yml.
   - add the system property `-Dprep.data-dir=./from-sysprop` (for example with
     `"-Dspring-boot.run.jvmArguments=-Dprep.data-dir=./from-sysprop"`). The system property
     wins over the env var.
   - add the argument `--prep.data-dir=./from-cli`. The command line wins over everything.
3. **Make Boot back off.** In `CompanyWisePrepApplication`, add a `@Bean DataSource` (for
   example `new DriverManagerDataSource("jdbc:h2:mem:lab", "sa", "")`). Run with `--debug`.
   `DataSourceAutoConfiguration.PooledDataSourceConfiguration` now appears under *Negative
   matches* with `@ConditionalOnMissingBean (types: javax.sql.DataSource,javax.sql.XADataSource
   ...) found beans of type 'javax.sql.DataSource' dataSource`. Boot's pool backed off and yours
   is used. Remove the bean when you are done.

## Gotchas

- **Classes outside the main class's package tree are not scanned.** Keep the
  `@SpringBootApplication` class in the root package.
- **`@ConditionalOnMissingBean` is reliable only in auto-configuration.** In your own
  `@Configuration` classes, the order of evaluation isn't guaranteed. Use it in auto-configs
  and starters (D9).
- **"It works locally but not in prod" is often a property-source surprise.** An environment
  variable or argument is overriding the yml. Check the effective value with `--debug`, or with
  Actuator's `/actuator/env` (D8).
- **A starter can switch on features you didn't ask for.** Adding a jar turns on its
  auto-configuration. Exclude a specific one with
  `@SpringBootApplication(exclude = X.class)` or `spring.autoconfigure.exclude`.
- **Boot 4 moved auto-configuration packages** (for example
  `org.springframework.boot.webmvc.autoconfigure`). Old imports and excludes that use Boot 3
  class names need updating.

## Explain it in 2 minutes

*"How does Spring Boot configure a database without you writing any config?"*

- `@SpringBootApplication` is `@Configuration`, `@EnableAutoConfiguration` and `@ComponentScan`.
- Auto-config classes are listed in each jar's `AutoConfiguration.imports` and processed after
  your own config.
- The data JPA starter puts Hikari, Hibernate and the JDBC classes on the classpath, so the
  `@ConditionalOnClass` checks pass.
- `@ConditionalOnMissingBean` means your own `DataSource`, if you define one, wins.
- Connection settings come from the `Environment`. The command line beats system properties,
  which beat env vars, which beat `application.yml`.
- `--debug` prints the conditions report that explains every decision.

## Check yourself

1. Why must the main class be in the root package?
2. You add `spring-boot-starter-data-jpa` but define your own `DataSource`. Which conditions
   explain the result?
3. `application.yml` says `prep.data-dir: ./data`, and the container sets `PREP_DATADIR=/srv/data`.
   Which value is used?
4. Where would you look to learn why `WebMvcAutoConfiguration` did not apply?

### Answers

1. `@ComponentScan` starts at the main class's package and only scans below it.
2. `@ConditionalOnClass` passes, because the JPA and Hikari classes are present.
   `@ConditionalOnMissingBean(DataSource)` fails, so Boot's pool backs off and yours is used.
3. `/srv/data`, because OS environment variables beat config files.
4. The *Negative matches* section of the `--debug` conditions report (or
   `/actuator/conditions`). For example: `not a servlet web application`.
