## Where we are

In F1 you added replicas, shards and queues. Each of them quietly created a new question: when
there are several copies of the data, which one is right? When a message can arrive twice, what
happens? This lesson gives you the theory to answer those questions precisely, which is what
"go deeper" means in an HLD round.

## The problem

Here are three real situations from F1's design:

```text
1. A user changes their name. The primary has it; a replica doesn't yet.
   The next page load reads from the replica → old name.
2. The network between two data centres breaks for 30 seconds.
   Both sides keep receiving writes. Do you accept them or refuse them?
3. A payment request times out. The client retries. Did the first one go through?
```

None of these is a bug you can fix with more code. They are trade-offs, and you need words for
them.

## A partition, and the CAP theorem

A **network partition** is when some machines can't reach others, even though all of them are
still running. In a system spread over several machines, partitions will happen, through a bad
switch, a misconfigured firewall or a long GC pause that looks like a dead node.

Picture two replicas, A and B, and a partition between them. A client writes `x = 2` to A. Another
client reads `x` from B. B has two choices:

```text
   client ──write x=2──► [ A ]   ✂ partition ✂   [ B ] ◄──read x── client
                                                 x = 1 (old)
   Option C: B refuses to answer (error/timeout)  → consistent, not available
   Option A: B answers x = 1                      → available, not consistent
```

The **CAP theorem** says that during a partition, a replicated system must choose between
**Consistency** (every read sees the latest write) and **Availability** (every request to a working
node gets an answer). The P isn't really a choice, because partitions happen anyway. So the real
question is: **when the network splits, do you refuse requests or serve possibly stale data?**

- A bank balance or seat booking usually picks **C** (refuse rather than double-book).
- A social feed's like count or a shopping cart usually picks **A** (stale is fine for a moment).

## PACELC: the everyday trade-off

CAP only talks about the rare partition. **PACELC** adds the common case: **if Partition, choose A
or C; Else, choose Latency or Consistency.**

Even with a healthy network, a strongly consistent write must wait for other replicas to confirm,
which adds a network round trip. If you don't wait, you're faster but a replica can be behind.

```text
   write ──► leader ──wait for replica ack──► reply      (consistent, slower)
   write ──► leader ──reply now, copy later              (fast, may be stale)
```

**The rule:** in an interview, say which choice you make **for each piece of data**, not for the
whole system. "Payments: CP and we pay the latency. View counts: AP and eventual."

## Consistency models: a ladder

A **consistency model** is a promise about what reads can return. From strongest to weakest:

| Model | The promise | Example of when you need it |
|---|---|---|
| **Linearizable** (strong) | It behaves like a single copy. Once a write finishes, every later read sees it | Locks, leader election, account balances |
| **Causal** | If B happened because of A, everyone sees A before B | A reply never shows up before the message it answers |
| **Read-your-writes** | You always see your own writes | Editing your profile |
| **Monotonic reads** | You never see time go backwards | Refreshing a page doesn't show an older state |
| **Eventual** | If writes stop, all copies converge, at some point | Like counts, view counts, DNS |

The weaker the promise, the cheaper and more available it is. Most real systems use eventual
consistency plus one or two session guarantees (read-your-writes, monotonic reads), with strong
consistency only where money or uniqueness is at stake.

## Replication: three shapes

**Replication** means keeping copies of the same data on several machines.

1. **Single-leader** (what F1 used): one leader takes writes, followers copy. Simple and the most
   common. If writes are copied **synchronously** (the leader waits for followers), you don't lose
   data on failover but writes are slower. **Asynchronous** copying is faster, but the last few
   writes can be lost if the leader dies.
2. **Multi-leader:** each region has its own leader that accepts writes. Writes are fast
   everywhere, but two regions can change the same row, which is a **conflict**. You need a rule:
   last-writer-wins (simple, loses data) or a merge (F5's CRDTs).
3. **Leaderless** (Dynamo-style, Cassandra): the client writes to several replicas and reads from
   several. With **N** replicas, a write waits for **W** acks and a read asks **R** replicas.

```text
   N = 3 replicas.  W = 2, R = 2  →  R + W > N
   write hits {A, B}; read asks {B, C}  → they overlap at B, so the read sees the write
```

**The quorum rule:** if `R + W > N`, every read set overlaps every write set, so a read sees the
latest write (in the simple case). Lower W or R buys speed and availability at the cost of
staleness.

## Raft: how machines agree on a leader (intuition)

**Problem:** with a single leader, who decides the leader is dead and who replaces it? If two nodes
both think they are leader (a **split brain**), both accept writes and the data diverges.

**Consensus** is getting several machines to agree on one value, or one ordered log, even when some
fail. **Raft** is a consensus algorithm designed to be easy to understand. It is used inside etcd
(which Kubernetes runs on), Consul and many databases. The intuition fits in four steps:

```text
   5 nodes. Majority = 3.

   1. Every node starts as a follower, waiting for heartbeats from a leader.
   2. No heartbeat for a random timeout (e.g. 150–300 ms)? Become a candidate:
      increase the TERM number (an election counter), vote for yourself, ask the others.
   3. Get votes from a majority (3 of 5) → you are leader for this term.
      Each node votes once per term, so two leaders in one term are impossible.
   4. The leader appends each write to its log and sends it to followers.
      Once a MAJORITY has stored it, the entry is COMMITTED and applied.
```

Why a **majority**? Any two majorities of the same group share at least one node. So a new leader's
voters always include someone who saw every committed entry, and Raft only lets a candidate win if
its log is at least as up to date as the voter's. Committed data survives leader changes.

The consequences you should say out loud:
- A cluster of 5 survives **2** failures. A cluster of 3 survives 1. Use odd sizes.
- The minority side of a partition can't elect a leader or commit writes. That is Raft choosing
  **C over A**.
- Every write costs a round trip to a majority, so consensus is used for **small, critical
  data** (config, leader election, locks, metadata), not for every user request.

## Idempotency

**Problem:** situation 3. The client sent "charge $100", then the connection dropped. It can't tell
whether the server charged and the reply was lost, or the request never arrived. The only safe
move for the client is to retry. The retry must not charge twice.

An operation is **idempotent** if doing it twice has the same effect as doing it once. `SET x = 5`
is idempotent. `x = x + 5` is not. `PUT` and `DELETE` are meant to be idempotent in HTTP. `POST`
usually isn't.

The standard fix is an **idempotency key**: the client generates a unique id (a UUID) for each
*logical* operation and sends it with every retry. The server stores `key → result`:

```text
   POST /payments   Idempotency-Key: 7f3a...   {amount: 100}
   server: have I seen 7f3a?  no  → charge, store (7f3a → receipt), return receipt
   retry with 7f3a            yes → return the stored receipt, charge nothing
```

In a real system, the key is stored in the same database transaction as the side effect, using a
unique constraint, so that two concurrent retries can't both get through.

## Exactly-once: mostly a myth

Messages between machines can be delivered **at-most-once** (send once and never retry, so messages
can be lost) or **at-least-once** (retry until acknowledged, so messages can be duplicated).
**Exactly-once delivery** over an unreliable network isn't achievable in general: a sender can't
tell "the message was lost" from "the ack was lost".

What systems actually offer is **exactly-once *effect***, also called exactly-once processing:

```text
   at-least-once delivery  +  idempotent / deduplicating consumer  =  effect happens once
```

Kafka's "exactly-once semantics" is real, but it is scoped: it covers read-from-Kafka →
process → write-to-Kafka inside Kafka's transactions. The moment your consumer calls an outside
system (sends an email, charges a card), you are back to at-least-once plus idempotency.

**The rule:** in an interview, never claim exactly-once delivery. Say "at-least-once, with
idempotent consumers keyed by event id".

## Back-pressure

**Problem:** producers are faster than consumers. A queue between them grows without limit until
memory runs out, or every item waits minutes, which is just as bad.

**Back-pressure** is a way for a slow consumer to push back on a fast producer: "slow down".

```text
   producer ──► [ bounded queue: 1,000 ] ──► consumer
                 full? → producer blocks, or gets an error, or the item is dropped
```

Your options, from gentle to brutal:
1. **Block** the producer (`BlockingQueue.put` on a bounded queue). Good inside one process.
2. **Reject** with an error, for example HTTP `429 Too Many Requests` or `503` with `Retry-After`.
   The client backs off.
3. **Shed load**: drop low-priority work (analytics before payments).
4. **Pull instead of push**: consumers ask for N items when they are ready (Reactive Streams
   `request(n)`, Kafka consumers polling).

Combine back-pressure with **exponential backoff with jitter** on the client (wait 100 ms, 200 ms,
400 ms, each plus a random amount). Otherwise all clients retry in lock-step and cause a **retry
storm**.

**The rule:** every queue needs a bound and a policy for what happens when it's full.

## Lab (~10 min)

Prove that an idempotency key turns five retries into one charge. Save this as
`IdempotencyLab.java` and run `java IdempotencyLab.java`.

```java
import java.util.ArrayList;
import java.util.List;
import java.util.UUID;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.AtomicLong;

public class IdempotencyLab {

    record Receipt(String paymentId, long amount) {}

    static final class PaymentService {
        final AtomicLong totalCharged = new AtomicLong();
        // idempotency key -> the result of the first request with that key
        private final ConcurrentHashMap<String, CompletableFuture<Receipt>> seen = new ConcurrentHashMap<>();

        Receipt charge(String idempotencyKey, long amount) {
            CompletableFuture<Receipt> mine = new CompletableFuture<>();
            CompletableFuture<Receipt> existing = seen.putIfAbsent(idempotencyKey, mine);
            if (existing != null) {
                return existing.join();             // duplicate: return the first result
            }
            totalCharged.addAndGet(amount);         // the side effect happens once
            Receipt r = new Receipt(UUID.randomUUID().toString(), amount);
            mine.complete(r);
            return r;
        }

        Receipt chargeNaive(long amount) {          // no key: every retry charges again
            totalCharged.addAndGet(amount);
            return new Receipt(UUID.randomUUID().toString(), amount);
        }
    }

    public static void main(String[] args) throws Exception {
        PaymentService svc = new PaymentService();
        String key = UUID.randomUUID().toString();   // the client creates ONE key per logical payment

        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            List<CompletableFuture<Receipt>> attempts = new ArrayList<>();
            for (int i = 0; i < 5; i++) {               // the client "times out" and retries 5 times
                attempts.add(CompletableFuture.supplyAsync(() -> svc.charge(key, 100), pool));
            }
            for (var a : attempts) System.out.println("receipt " + a.get().paymentId());
        }
        System.out.println("with key, total charged = " + svc.totalCharged.get());

        PaymentService naive = new PaymentService();
        for (int i = 0; i < 5; i++) naive.chargeNaive(100);
        System.out.println("without key, total charged = " + naive.totalCharged.get());
    }
}
```

**What you should see:** five identical receipt ids, `with key, total charged = 100` and
`without key, total charged = 500`.

**Break it:**
1. Replace `putIfAbsent` with a `containsKey` check followed by `put`. Run it several times. Now and
   then two threads both pass the check and you get 200. That race is why real systems use a
   database **unique constraint** on the key.
2. Make the charge throw an exception before `mine.complete(r)`. The duplicate callers hang on
   `join()` forever. A real design stores a status (`IN_PROGRESS`, `SUCCEEDED`, `FAILED`) and lets a
   retry after a failure try again.

## Gotchas

- **"CA systems" don't exist across a network.** Partitions happen, so the choice is only C or A
  during one. Saying "we choose CA" is a red flag.
- **Quorums don't give linearizability by themselves.** Sloppy quorums, clock-based
  last-writer-wins and concurrent writes can still produce anomalies. Say "R + W > N gives overlap",
  not "it is strongly consistent".
- **Even-sized consensus clusters waste a node.** Four nodes tolerate one failure, the same as
  three. Use 3 or 5.
- **An idempotency key must be created by the client, once per logical operation.** If the server
  generates it or the client makes a new key per retry, it protects nothing.
- **Unbounded queues hide overload** until memory runs out. Bound them and decide what "full" means.
- **Retries without jitter** turn a brief outage into a synchronised retry storm.

[Design a Payment Service](#/q/design-payment-system),
[Design a Distributed Key-Value Store](#/q/design-distributed-key-value-store) (quorums, replication,

(consensus-backed, watch for changes). For the theory side, see
[Replica vs snapshot vs checkpoint; deadlock detection](#/q/dbms-replica-snapshot-checkpoint).

Typical follow-ups:
- **"The leader dies mid-write. What does the client see?"** A strong answer: the write either
  reached a majority (committed, so the new leader has it) or didn't (lost, and the client times
  out). Because the client can't tell which, it retries with the same idempotency key.
- **"Can you guarantee exactly-once?"** A strong answer: not delivery. Effect, yes: at-least-once
  delivery, a dedup table keyed by message id written in the same transaction as the state change,
  and a retention window for that table.

## Explain it in 2 minutes

*"Explain CAP and how you would apply it to a booking system."*

- A partition is unavoidable, so during one you choose to refuse requests (C) or serve possibly
  stale data (A).
- PACELC: even without partitions, consistency costs latency.
- Choose per data type: seat inventory is CP (no double-booking). Search results and reviews are AP.
- Consistency for seats comes from a single leader, or consensus, plus conditional writes.
- Clients retry with idempotency keys, so a timeout never books twice.

1. N = 5, W = 3. What is the smallest R that guarantees overlap with the latest write?
2. Why can't a Raft cluster's minority side accept writes during a partition?
3. Is `UPDATE account SET balance = balance - 100 WHERE id = 7` idempotent? How would you make
   the operation safe to retry?
4. A consumer reads from Kafka and sends an email. Can Kafka's exactly-once feature stop duplicate
   emails?
5. Name two back-pressure strategies for an HTTP API.

### Answers

1. R = 3, since 3 + 3 > 5.
2. It can't gather votes from a majority, so it can't elect a leader or commit entries. This is
   deliberate: it prevents a split brain.
3. No, because each run subtracts again. Record the operation id in a table with a unique
   constraint in the same transaction, and skip it if the id already exists.
4. No. The email is an external side effect. Use a dedup record per event id, or rely on the email
   provider's own idempotency key.
5. Return `429`/`503` with `Retry-After`, and shed low-priority traffic. A bounded internal queue
   that rejects when full also counts.
