## Where we are

From D2 you know that Spring reads bean definitions (recipes) first, then creates every singleton
in `refresh()` and caches it. In D2, "create" was a single box. This lesson opens that box and
walks through each step a bean goes through, from recipe to garbage. Knowing these steps tells you
where your own code can hook in, and where Spring quietly swaps your object for a different one.

## The problem

Three questions come up often in real code:

- "I read an injected field in my constructor and it was `null`. Why?"
- "Where should I put start-up work, such as warming a cache or validating config?"
- "`getBean(MyService.class).getClass()` prints `MyService$$SpringCGLIB$$0`. Where did that
  class come from?"

All three have the same answer: the order of the bean lifecycle.

## The whole lifecycle in one picture

```text
  BeanDefinition (recipe)                         ← from scanning / @Bean (D2)
        │
  1  Instantiate        constructor runs; constructor args are injected
        │
  2  Populate           field and setter injection (@Autowired fields, setters)
        │
  3  Aware callbacks    setBeanName, setBeanFactory, (setApplicationContext)
        │
  4  BPP before-init    every BeanPostProcessor.postProcessBeforeInitialization
        │
  5  @PostConstruct
  6  InitializingBean.afterPropertiesSet()
  7  custom init-method  (@Bean(initMethod = "..."))
        │
  8  BPP after-init     every BeanPostProcessor.postProcessAfterInitialization
        │               ← AOP proxies (@Transactional, @Async, @Cacheable) are made HERE
        ▼
  9  In use             the object in the singleton cache, maybe a proxy, is what others get
        │
     context.close()
        │
  10 @PreDestroy
  11 DisposableBean.destroy()
  12 custom destroy-method
```

The sections below take each step in turn and explain why it exists.

## Steps 1–2: instantiate, then populate

Spring first calls the constructor, giving it any constructor dependencies. Then it fills in
**field and setter** dependencies.

That explains the first puzzle. **Inside the constructor, `@Autowired` fields are still
`null`**, because they are not populated until step 2. Constructor parameters do not have this
problem, which is one more reason to prefer constructor injection.

## Step 3: Aware interfaces

An **Aware interface** is a callback that hands a bean a piece of the container itself. For
example, `BeanNameAware.setBeanName(String)` tells the bean its own name, and `BeanFactoryAware`
hands it the factory. Ordinary application code rarely needs these, because injecting what you
need is cleaner. Framework code uses them a lot.

`ApplicationContextAware` is technically delivered by a BeanPostProcessor that runs at step 4,
but it still arrives before any init method.

## Step 4 and step 8: BeanPostProcessors

A **BeanPostProcessor (BPP)** is a special bean that Spring calls for *every other bean*, once
just before its init methods and once just after. It can modify the bean, or **return a
different object to use in its place**.

```java
public interface BeanPostProcessor {
    default Object postProcessBeforeInitialization(Object bean, String beanName) { return bean; }
    default Object postProcessAfterInitialization(Object bean, String beanName)  { return bean; }
}
```

This is how most of Spring's "magic" is built. Spring's own BPPs:

- process `@Autowired` and `@Value` (step 2 is really done by a BPP-like processor);
- call `@PostConstruct` and `@PreDestroy`;
- and, in **after-init**, wrap beans in **proxies**.

A **proxy** is an object that looks like your bean, because it has the same type, but runs extra
code (start a transaction, run on another thread, check a cache) before handing the call to your
real object. D3 covers proxies in depth. For now the key fact is this: **the object other beans
receive is whatever the last BPP returned, not necessarily the one your constructor built.**
That answers the third puzzle.

## Steps 5–7: three init hooks

All three run after injection is complete, so they are the right place for start-up work that
needs dependencies.

| Hook | Comes from | Use when |
|---|---|---|
| `@PostConstruct` | `jakarta.annotation` | default choice in application code |
| `afterPropertiesSet()` | implementing `InitializingBean` | framework code; couples you to Spring |
| `initMethod` | `@Bean(initMethod = "start")` | third-party classes you can't annotate |

They run in the order shown. If a bean uses more than one, all of them run.

One timing detail matters: **init hooks run before the proxy exists** (the proxy is created at
step 8). So inside `@PostConstruct`, calling your own `@Transactional` method gets **no
transaction**. For work that needs the fully proxied application, use an `ApplicationRunner` or
listen for `ApplicationReadyEvent` (L5).

## Steps 10–12: destruction

When the context closes, singletons are destroyed in roughly the reverse order of their
dependencies: `@PreDestroy`, then `DisposableBean.destroy()`, then the custom destroy-method.
Use these to close pools, flush buffers and stop threads.

Two cautions:

- **Prototype beans are never destroyed by Spring.** The container hands them out and forgets
  them, so cleanup is your job.
- **On `@Bean` methods, Spring infers a destroy method** by default: a public `close()` or
  `shutdown()` method is called automatically. That is usually what you want for pools and
  clients.

## Lab (~10 min)

You need `spring-context` on the classpath, as in D2. `jakarta.annotation-api` is also needed for
`@PostConstruct`. Spring Boot includes it, and in a plain project you add
`jakarta.annotation:jakarta.annotation-api` yourself.

```java
import java.lang.reflect.Proxy;

import org.springframework.beans.factory.BeanNameAware;
import org.springframework.beans.factory.DisposableBean;
import org.springframework.beans.factory.InitializingBean;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.config.BeanPostProcessor;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;

public class LifecycleLab {
    public static void main(String[] args) {
        var ctx = new AnnotationConfigApplicationContext(LifecycleConfig.class);
        System.out.println("--- context ready ---");
        Greeter greeter = ctx.getBean(Greeter.class);
        System.out.println(greeter.greet("Akhil"));
        System.out.println("class you were given: " + greeter.getClass().getName());
        System.out.println("--- closing ---");
        ctx.close();
    }

    static void log(String step) { System.out.println("  " + step); }
}

interface Greeter { String greet(String name); }

class Clockwork {}   // a dependency, so there is something to inject

class LoggingGreeter implements Greeter, BeanNameAware, InitializingBean, DisposableBean {
    private Clockwork clockwork;

    LoggingGreeter()                           { LifecycleLab.log("1  constructor (instantiate)"); }
    @Autowired void setClockwork(Clockwork c)  { this.clockwork = c; LifecycleLab.log("2  setter injection (populate)"); }
    @Override public void setBeanName(String n) { LifecycleLab.log("3  BeanNameAware -> " + n); }
    @PostConstruct void postConstruct()        { LifecycleLab.log("5  @PostConstruct"); }
    @Override public void afterPropertiesSet() { LifecycleLab.log("6  InitializingBean.afterPropertiesSet"); }
    void customInit()                          { LifecycleLab.log("7  @Bean(initMethod)"); }

    @Override public String greet(String name) {
        return "9  in use: Hello, " + name + " (clockwork set: " + (clockwork != null) + ")";
    }

    @PreDestroy void preDestroy()              { LifecycleLab.log("10 @PreDestroy"); }
    @Override public void destroy()            { LifecycleLab.log("11 DisposableBean.destroy"); }
    void customDestroy()                       { LifecycleLab.log("12 @Bean(destroyMethod)"); }
}

class TracingPostProcessor implements BeanPostProcessor {
    @Override
    public Object postProcessBeforeInitialization(Object bean, String name) {
        if (bean instanceof Greeter) LifecycleLab.log("4  BeanPostProcessor before-init");
        return bean;
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String name) {
        if (!(bean instanceof Greeter target)) return bean;
        LifecycleLab.log("8  BeanPostProcessor after-init: returning a proxy instead");
        return Proxy.newProxyInstance(Greeter.class.getClassLoader(), new Class<?>[] {Greeter.class},
                (proxy, method, methodArgs) -> {
                    LifecycleLab.log("   proxy intercepts " + method.getName() + "()");
                    return method.invoke(target, methodArgs);
                });
    }
}

@Configuration
class LifecycleConfig {
    @Bean
    static TracingPostProcessor tracingPostProcessor() { return new TracingPostProcessor(); }

    @Bean
    Clockwork clockwork() { return new Clockwork(); }

    @Bean(initMethod = "customInit", destroyMethod = "customDestroy")
    LoggingGreeter greeter() { return new LoggingGreeter(); }
}
```

What you should see (checked against Spring Framework 7.0):

```text
  1  constructor (instantiate)
  2  setter injection (populate)
  3  BeanNameAware -> greeter
  4  BeanPostProcessor before-init
  5  @PostConstruct
  6  InitializingBean.afterPropertiesSet
  7  @Bean(initMethod)
  8  BeanPostProcessor after-init: returning a proxy instead
--- context ready ---
     proxy intercepts greet()
9  in use: Hello, Akhil (clockwork set: true)
class you were given: $Proxy13
--- closing ---
  10 @PreDestroy
  11 DisposableBean.destroy
  12 @Bean(destroyMethod)
```

The proxy's class name varies. What matters is that it is *not* `LoggingGreeter`.

Then try these:

1. **Break it:** call `ctx.getBean(LoggingGreeter.class)`. It fails with
   `NoSuchBeanDefinitionException: No qualifying bean of type 'LoggingGreeter'`. The bean is now
   a proxy that implements only `Greeter`, so it no longer *is* a `LoggingGreeter`. You meet the
   same failure when you inject a JDK-proxied bean by its class (D3).
2. Print `clockwork` inside the constructor. It is `null`, because population happens after
   construction.
3. Remove `static` from the `tracingPostProcessor()` method. Spring 7 logs a warning that
   `lifecycleConfig` "is not eligible for getting processed by all BeanPostProcessors (for
   example: not eligible for auto-proxying)". The config class has to be created early in order
   to call the method.

## Gotchas

- **Injected fields are `null` in the constructor.** Use constructor injection, or do the work
  in `@PostConstruct`.
- **No proxy yet in `@PostConstruct`.** A `@Transactional` call there has no transaction. Use
  `ApplicationRunner` or `ApplicationReadyEvent` for start-up work that needs it.
- **Declare `BeanPostProcessor` `@Bean` methods `static`.** Otherwise the enclosing
  configuration, and everything it pulls in, is created too early to be post-processed.
- **A BPP that depends on ordinary beans makes those beans skip some post-processing.** Watch
  for "not eligible for getting processed by all BeanPostProcessors" in the logs.
- **Prototype beans get init callbacks but not destroy callbacks.** You must clean them up
  yourself.

## In interviews

This is asked as "Explain the Spring bean lifecycle", "Where are AOP proxies created?",
"`@PostConstruct` vs constructor?" and "What is a BeanPostProcessor?". The bank has no Spring
lifecycle question yet. A close relative is
[Design a Multi-module Logging Framework](#/q/design-logging-framework), where a
post-processor or proxy that adds logging to every bean is a strong answer.

Typical follow-ups:

- *"Why isn't my `@Transactional` working in `@PostConstruct`?"* The proxy is created in BPP
  after-init, which comes after `@PostConstruct`, and you are calling `this`, not the proxy.
- *"BeanPostProcessor vs BeanFactoryPostProcessor?"* A BPP works on bean *instances*. A
  BeanFactoryPostProcessor (BFPP) works on *definitions* before any bean exists.
  `PropertySourcesPlaceholderConfigurer` is one (D9).

## Explain it in 2 minutes

*"Walk me through a Spring singleton's life."*

- It starts as a definition, then is instantiated through the constructor, then fields and
  setters are injected.
- Aware callbacks give it container references.
- BPP before-init runs, then `@PostConstruct`, `afterPropertiesSet` and the init-method, in that
  order.
- BPP after-init can replace the bean, and this is where AOP proxies are created.
- The cached object, possibly a proxy, is what everyone gets injected.
- On close come `@PreDestroy`, `destroy()` and the destroy-method. Prototypes are never
  destroyed.

## Check yourself

1. Which runs first: `@PostConstruct` or `afterPropertiesSet()`?
2. At which step is a `@Transactional` proxy created, and why does that matter for
   `@PostConstruct`?
3. Why can a BeanPostProcessor change which object other beans receive?
4. What does Spring do with a prototype bean when the context closes?

### Answers

1. `@PostConstruct`, then `afterPropertiesSet()`, then the custom init-method.
2. In BPP after-init, after every init hook. Inside `@PostConstruct` there is no proxy yet, so
   no transaction.
3. Because the object it returns from `postProcessAfterInitialization` is what goes into the
   singleton cache.
4. Nothing. Destroy callbacks are not called for prototypes.
