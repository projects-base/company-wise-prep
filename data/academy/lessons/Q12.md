## Where we are

DB-SQL-9 gave you:

- **the interview method:** clarify, build in CTE steps, test the edge cases, name the index;
- **the first four patterns:** Nth highest, top-N per group, duplicates, and gaps and islands.

This lesson finishes the set with the five shapes that reporting questions take, on the same betting schema and seed.

## The problem

It is Monday, 9:40, and the head of trading wants a one-page report before the 10 o'clock meeting:

- turnover per day with a running total;
- the change from last month;
- each punter's turnover by sport;
- the typical stake rather than the average one;
- the punters who bet on Football but never on Tennis.

You have twenty minutes and a SQL prompt. In an interview the same requests arrive one at a time, each followed by
a twist such as "what if a month has no bets?".

Every one of them is a window or a conditional aggregate on top of a `GROUP BY`, and every
one has an edge case that quietly gives the wrong number.

## Pattern 5: Running totals

**Ask:** "Cumulative turnover by day, and the first day it passed 300." Clarify: calendar days in
which time zone? (Here, the stored timestamp.) Should days with no bets appear? (See Pattern 6 for
filling gaps.)

**Step 1: aggregate to one row per day. Step 2: run a window sum over the days.** Summing per day
*first* also removes the `RANGE`-ties problem from DB-SQL-4, because each day is now unique.

```sql
WITH daily AS (
  SELECT CAST(placed_at AS DATE) AS bet_day, SUM(stake) AS day_turnover
  FROM bets
  GROUP BY CAST(placed_at AS DATE)
)
SELECT bet_day, day_turnover,
       SUM(day_turnover) OVER (ORDER BY bet_day) AS cumulative_turnover
FROM daily
WHERE bet_day <= DATE '2026-09-07'
ORDER BY bet_day;
```

| bet_day | day_turnover | cumulative_turnover |
|---|---|---|
| 2026-08-18 | 20.00 | 20.00 |
| 2026-08-19 | 60.00 | 80.00 |
| 2026-08-20 | 120.00 | 200.00 |
| 2026-09-04 | 20.00 | 220.00 |
| 2026-09-05 | 25.00 | 245.00 |
| 2026-09-06 | 40.00 | 285.00 |
| 2026-09-07 | 55.00 | 340.00 |

**Careful:** the `WHERE` in the outer query runs *before* the window.

- Filtering the days in the outer query is fine here, because we cut off only the end.
- If you filtered out *early* days, the running total would restart from the first remaining day.
- **Fix:** to show a later range with the true cumulative total, compute the running sum in a CTE and filter outside it.

**Step 3: the first crossing.** Running sum in a CTE, filter, take the earliest:

```sql
WITH daily AS (
  SELECT CAST(placed_at AS DATE) AS bet_day, SUM(stake) AS day_turnover
  FROM bets
  GROUP BY CAST(placed_at AS DATE)
),
running AS (
  SELECT bet_day, SUM(day_turnover) OVER (ORDER BY bet_day) AS cumulative_turnover
  FROM daily
)
SELECT bet_day, cumulative_turnover
FROM running
WHERE cumulative_turnover >= 300
ORDER BY bet_day
LIMIT 1;
```

| bet_day | cumulative_turnover |
|---|---|
| 2026-09-07 | 340.00 |

**A shortcut, PostgreSQL only.** A window over an aggregate, `SUM(SUM(stake)) OVER (…)`, does steps 1
and 2 in one SELECT:

```sql
SELECT CAST(placed_at AS DATE) AS bet_day,
       SUM(stake) AS day_turnover,
       SUM(SUM(stake)) OVER (ORDER BY CAST(placed_at AS DATE)) AS cumulative_turnover
FROM bets
GROUP BY CAST(placed_at AS DATE)
ORDER BY bet_day
LIMIT 3;
```

| bet_day | day_turnover | cumulative_turnover |
|---|---|---|
| 2026-08-18 | 20.00 | 20.00 |
| 2026-08-19 | 60.00 | 80.00 |
| 2026-08-20 | 120.00 | 200.00 |

H2 rejected this exact query ("Column PLACED_AT must be in the GROUP BY list"). The CTE form runs on
both.

The per-user running balance (DB-SQL-4) is the same pattern with `PARTITION BY user_id`.

**Index:**

- `wallet_transactions (user_id, created_at)` for per-user balances.
- For the daily rollup, an index on `bets (placed_at)` helps only when you restrict a date range.
- At scale, keep a `daily_turnover` summary table that a job updates, rather than re-summing raw bets.

## Pattern 6: Month-over-month change

**Ask:** "Monthly turnover and the change from the previous month, in money and %." Clarify:

- calendar months?
- What if a month has no bets (show 0, or skip)?
- What if last month was 0 (division by zero)?

**Step 1: bucket by month.** `DATE_TRUNC('month', ts)` rounds a timestamp down to the first instant of
its month. It works in PostgreSQL and H2.

```sql
SELECT DATE_TRUNC('month', placed_at) AS month_start, SUM(stake) AS turnover
FROM bets
GROUP BY DATE_TRUNC('month', placed_at)
ORDER BY month_start;
```

| month_start | turnover |
|---|---|
| 2026-08-01 00:00:00 | 200.00 |
| 2026-09-01 00:00:00 | 385.00 |
| 2026-10-01 00:00:00 | 70.00 |

**Step 2: `LAG` over the months.** `NULLIF(x, 0)` returns NULL when `x` is 0, so dividing by it gives
NULL instead of a division-by-zero error.

```sql
WITH monthly AS (
  SELECT DATE_TRUNC('month', placed_at) AS month_start, SUM(stake) AS turnover
  FROM bets
  GROUP BY DATE_TRUNC('month', placed_at)
)
SELECT month_start, turnover,
       LAG(turnover) OVER (ORDER BY month_start) AS prev_turnover,
       turnover - LAG(turnover) OVER (ORDER BY month_start) AS change,
       ROUND(100 * (turnover - LAG(turnover) OVER (ORDER BY month_start))
             / NULLIF(LAG(turnover) OVER (ORDER BY month_start), 0), 1) AS pct_change
FROM monthly
ORDER BY month_start;
```

| month_start | turnover | prev_turnover | change | pct_change |
|---|---|---|---|---|
| 2026-08-01 00:00:00 | 200.00 | NULL | NULL | NULL |
| 2026-09-01 00:00:00 | 385.00 | 200.00 | 185.00 | 92.5 |
| 2026-10-01 00:00:00 | 70.00 | 385.00 | -315.00 | -81.8 |

October is a partial month (the seed stops on 4 October). A good answer points out that comparing a
partial month with a full one is misleading.

**Edge case: missing months.** `LAG` compares with the previous *row*, not the previous *month*. If
July had no bets, there is no July row, and August would be compared with June.

Fix it by building the list of months and LEFT JOINing the totals. A `VALUES` list works on both engines:

```sql
WITH months (month_start) AS (
  VALUES (TIMESTAMP '2026-07-01 00:00:00'), (TIMESTAMP '2026-08-01 00:00:00'),
         (TIMESTAMP '2026-09-01 00:00:00'), (TIMESTAMP '2026-10-01 00:00:00')
),
monthly AS (
  SELECT DATE_TRUNC('month', placed_at) AS month_start, SUM(stake) AS turnover
  FROM bets
  GROUP BY DATE_TRUNC('month', placed_at)
)
SELECT m.month_start, COALESCE(t.turnover, 0) AS turnover,
       COALESCE(t.turnover, 0) - LAG(COALESCE(t.turnover, 0)) OVER (ORDER BY m.month_start) AS change
FROM months m
LEFT JOIN monthly t ON t.month_start = m.month_start
ORDER BY m.month_start;
```

| month_start | turnover | change |
|---|---|---|
| 2026-07-01 00:00:00 | 0 | NULL |
| 2026-08-01 00:00:00 | 200.00 | 200.00 |
| 2026-09-01 00:00:00 | 385.00 | 185.00 |
| 2026-10-01 00:00:00 | 70.00 | -315.00 |

In PostgreSQL you'd generate the months instead of listing them:

```sql
SELECT month_start
FROM generate_series(TIMESTAMP '2026-07-01 00:00:00', TIMESTAMP '2026-10-01 00:00:00',
                     INTERVAL '1 month') AS g(month_start);
```

| month_start |
|---|
| 2026-07-01 00:00:00 |
| 2026-08-01 00:00:00 |
| 2026-09-01 00:00:00 |
| 2026-10-01 00:00:00 |

`generate_series` is PostgreSQL-only. H2 rejected this call.

**Per punter:** add `user_id` to the `GROUP BY` and `PARTITION BY user_id` to each window. The
missing-month problem gets worse per punter, because most punters skip some months.

**Index:** filter months with a range such as `placed_at >= '2026-08-01' AND placed_at <
'2026-10-01'`, never with `EXTRACT(MONTH FROM placed_at) = 9`.

- A function wrapped around the column stops a plain index on `bets (placed_at)` from being used.
- At scale this is a classic case for a monthly rollup table.

## Pattern 7: Pivot with CASE

**Ask:** "One row per punter, one column per sport, with turnover in each cell." A **pivot** turns
values in rows into columns.

Clarify: is the list of columns fixed? SQL needs to know its output columns when the query is written, so a pivot
over "whatever sports exist" needs dynamic SQL or a pivot in the application.

**Step 1: the long form.** One row per (punter, sport):

```sql
SELECT b.user_id, sp.name AS sport, SUM(b.stake) AS turnover
FROM bets b
JOIN selections s ON s.id = b.selection_id
JOIN markets m    ON m.id = s.market_id
JOIN events e     ON e.id = m.event_id
JOIN sports sp    ON sp.id = e.sport_id
GROUP BY b.user_id, sp.name
ORDER BY b.user_id, sp.name;
```

| user_id | sport | turnover |
|---|---|---|
| 1 | Football | 75.00 |
| 1 | Horse Racing | 10.00 |
| 1 | Tennis | 25.00 |
| 2 | Football | 120.00 |
| 2 | Horse Racing | 25.00 |
| 2 | Tennis | 40.00 |
| 3 | Football | 150.00 |
| 3 | Horse Racing | 20.00 |
| 3 | Tennis | 50.00 |
| 4 | Football | 20.00 |
| 4 | Tennis | 5.00 |
| 5 | Football | 100.00 |
| 5 | Horse Racing | 15.00 |

**Step 2: one conditional SUM per column** (DB-SQL-2's conditional aggregation):

```sql
WITH bet_sport AS (
  SELECT b.user_id, e.sport_id, b.stake
  FROM bets b
  JOIN selections s ON s.id = b.selection_id
  JOIN markets m    ON m.id = s.market_id
  JOIN events e     ON e.id = m.event_id
)
SELECT u.name,
       SUM(CASE WHEN bs.sport_id = 1 THEN bs.stake ELSE 0 END) AS football,
       SUM(CASE WHEN bs.sport_id = 2 THEN bs.stake ELSE 0 END) AS tennis,
       SUM(CASE WHEN bs.sport_id = 3 THEN bs.stake ELSE 0 END) AS racing,
       SUM(bs.stake)                                           AS total
FROM bet_sport bs
JOIN users u ON u.id = bs.user_id
GROUP BY u.id, u.name
ORDER BY u.id;
```

| name | football | tennis | racing | total |
|---|---|---|---|---|
| Asha | 75.00 | 25.00 | 10.00 | 110.00 |
| Ben | 120.00 | 40.00 | 25.00 | 185.00 |
| Chloe | 150.00 | 50.00 | 20.00 | 220.00 |
| Dev | 20.00 | 5.00 | 0 | 25.00 |
| Ella | 100.00 | 0 | 15.00 | 115.00 |

**Edge cases.**

- `ELSE 0` gives 0 for "no bets". Leave out the `ELSE` and you get NULL, which some reports prefer, since
  "no activity" isn't the same as "staked 0".
- Sanity-check that the columns add up to `total`: here they do. If a fourth sport gets bets, it appears in
  `total` but in no column. Say so.
- PostgreSQL (and H2) also accept the standard `FILTER` clause, `SUM(stake) FILTER (WHERE sport_id =
  1)`, which reads more cleanly and returns NULL for no rows. The `CASE` form runs everywhere, including MySQL.

LeetCode 1179 (Reformat Department Table) is this pattern.

**Index:** a pivot reads every matching bet, so the indexes that matter are the ones for the join:
`bets (selection_id)`, `selections (market_id)` and `markets (event_id)`. PostgreSQL doesn't create
these foreign-key indexes for you.

## Pattern 8: Median

**Ask:** "Median stake."

- The **median** is the middle value once the values are sorted. With an even count, it is the average of the two
  middle values.
- It resists outliers: one 10,000 bet barely moves it, but it drags the mean up a lot.

Clarify:

- an even count → average the middle two (the usual reading)?
- Include open bets?
- What about NULLs?

**The built-in (PostgreSQL, also H2):**

```sql
SELECT PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY stake) AS median_stake
FROM bets;
```

| median_stake |
|---|
| 22.5 |

- `PERCENTILE_CONT` interpolates between the two middle values.
- `PERCENTILE_DISC` returns an actual value from the data instead.
- PostgreSQL returns a `double precision` here (shown as 22.5). H2 returned `22.500`.
- MySQL has neither function, which is why interviewers often ask for the manual version.

**The manual version: number the rows, keep the middle one or two.** For n rows, the middle positions
are `(n + 1) / 2` and `(n + 2) / 2` in integer division.

- When n is odd these are the same position.
- When n is even they are the two middle ones.

```sql
WITH ordered AS (
  SELECT stake,
         ROW_NUMBER() OVER (ORDER BY stake) AS rn,
         COUNT(*)     OVER ()               AS n
  FROM bets
)
SELECT ROUND(AVG(stake), 2) AS median_stake
FROM ordered
WHERE rn IN ((n + 1) / 2, (n + 2) / 2);
```

| median_stake |
|---|
| 22.50 |

**Predict:** the median stake is 22.50. Is the mean stake higher or lower, and why?

There are 20 bets, so positions 10 and 11 hold 20.00 and 25.00, and their average is 22.50. The mean
is 32.75, pulled up by the two 100.00 bets. **Per group:** add `PARTITION BY user_id` to both windows
and `GROUP BY user_id` outside:

```sql
WITH ordered AS (
  SELECT user_id, stake,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY stake, id) AS rn,
         COUNT(*)     OVER (PARTITION BY user_id)                    AS n
  FROM bets
)
SELECT user_id, ROUND(AVG(stake), 2) AS median_stake
FROM ordered
WHERE rn IN ((n + 1) / 2, (n + 2) / 2)
GROUP BY user_id
ORDER BY user_id;
```

| user_id | median_stake |
|---|---|
| 1 | 17.50 |
| 2 | 40.00 |
| 3 | 50.00 |
| 4 | 10.00 |
| 5 | 57.50 |

**Edge cases.**

- Ties don't matter, because equal values are interchangeable.
- NULLs do. Filter them out (`WHERE stake IS NOT NULL`) *before* numbering, or `n` counts rows that have no value.

**Index:** an index on `bets (stake)` gives sorted order for free. An exact median over a huge table
still has to read half of it.

At scale, use approximate percentiles (sketches such as t-digest in the metrics pipeline) or precomputed values.

## Pattern 9: Users who did X but not Y

**Ask:** "Punters who bet on Football but never on Tennis." Clarify: does a `VOID` tennis bet count as
"bet on Tennis"? Should punters with no bets at all appear? (No, they didn't do X.)

**The `EXISTS` / `NOT EXISTS` form**, the clearest and NULL-safe:

```sql
WITH bet_sport AS (
  SELECT b.user_id, e.sport_id, b.status
  FROM bets b
  JOIN selections s ON s.id = b.selection_id
  JOIN markets m    ON m.id = s.market_id
  JOIN events e     ON e.id = m.event_id
)
SELECT u.id, u.name
FROM users u
WHERE EXISTS     (SELECT 1 FROM bet_sport x WHERE x.user_id = u.id AND x.sport_id = 1)
  AND NOT EXISTS (SELECT 1 FROM bet_sport y WHERE y.user_id = u.id AND y.sport_id = 2)
ORDER BY u.id;
```

| id | name |
|---|---|
| 5 | Ella |

**The one-pass `GROUP BY … HAVING` form:** count X and Y per user with conditional aggregation, and
keep "X > 0 and Y = 0". This one shines when there are several conditions (did A and B, but not C):

```sql
WITH bet_sport AS (
  SELECT b.user_id, e.sport_id
  FROM bets b
  JOIN selections s ON s.id = b.selection_id
  JOIN markets m    ON m.id = s.market_id
  JOIN events e     ON e.id = m.event_id
)
SELECT user_id
FROM bet_sport
GROUP BY user_id
HAVING SUM(CASE WHEN sport_id = 1 THEN 1 ELSE 0 END) > 0
   AND SUM(CASE WHEN sport_id = 2 THEN 1 ELSE 0 END) = 0
ORDER BY user_id;
```

| user_id |
|---|
| 5 |

**The set form:** `EXCEPT` returns rows of the first query that are not in the second (and removes
duplicates):

```sql
WITH bet_sport AS (
  SELECT b.user_id, e.sport_id
  FROM bets b
  JOIN selections s ON s.id = b.selection_id
  JOIN markets m    ON m.id = s.market_id
  JOIN events e     ON e.id = m.event_id
)
SELECT user_id FROM bet_sport WHERE sport_id = 1
EXCEPT
SELECT user_id FROM bet_sport WHERE sport_id = 2
ORDER BY user_id;
```

| user_id |
|---|
| 5 |

**Predict:** Dev bet on Football, and his only Tennis bet was voided. If a voided bet doesn't count as "bet on
Tennis", does the answer change?

**Edge case: the clarification changes the answer.** Dev's only tennis bet was voided. If voided bets
don't count, Dev qualifies too:

```sql
WITH bet_sport AS (
  SELECT b.user_id, e.sport_id, b.status
  FROM bets b
  JOIN selections s ON s.id = b.selection_id
  JOIN markets m    ON m.id = s.market_id
  JOIN events e     ON e.id = m.event_id
)
SELECT u.id, u.name
FROM users u
WHERE EXISTS     (SELECT 1 FROM bet_sport x WHERE x.user_id = u.id AND x.sport_id = 1)
  AND NOT EXISTS (SELECT 1 FROM bet_sport y WHERE y.user_id = u.id AND y.sport_id = 2
                                              AND y.status <> 'VOID')
ORDER BY u.id;
```

| id | name |
|---|---|
| 4 | Dev |
| 5 | Ella |

Avoid `user_id NOT IN (SELECT user_id …)` here (DB-SQL-1, Trap 3). It's correct only while the subquery can
never return NULL.

**Index:** each `EXISTS` probe is "does this user have a bet on sport S?".

- `bets (user_id,
  selection_id)` lets the database check one user's bets without touching the rest.
- The foreign-key indexes make the climb to `events.sport_id` cheap.
- In a real schema you'd often denormalise `sport_id` onto `bets` for reporting. That is a DB-SQL-3
  denormalisation trade-off.

## Gotchas

- **`LAG` means the previous row, not the previous month.** Generate the full list of periods and LEFT JOIN,
  or the gaps silently compare the wrong months.
- **Filtering before a window changes the window.** `WHERE` runs first, so a running total or rank covers only
  the surviving rows. Compute it in a CTE, filter outside.
- **Functions on indexed columns block the index.** `EXTRACT(MONTH FROM placed_at) = 9` can't use an index on
  `placed_at`; a half-open range (`>= start AND < next_start`) can.
- **`NOT IN` with a nullable subquery.** One NULL in the list and it returns nothing. Use `NOT EXISTS`.

## Explain it in 2 minutes

*"Build monthly turnover with the change from last month. What can go wrong?"*

1. Aggregate to one row per month (`DATE_TRUNC`), then window over the months.
2. `LAG` is the previous row, not the previous month: generate the months and LEFT JOIN.
3. Handle the edges: `NULLIF` for division, `COALESCE` for missing periods, `NOT EXISTS` over `NOT IN`.
4. Flag a partial month: four days of October against all of September misleads.
5. Performance: a half-open timestamp range, not `EXTRACT`; a monthly rollup table at scale.

3. `WHERE` runs before the window, so dropping early days in the same SELECT restarts the total at the first
   remaining day.

```sql
                  WHERE b.user_id = u.id
                    AND b.placed_at >= TIMESTAMP '2026-10-01 00:00:00'
                    AND b.placed_at <  TIMESTAMP '2026-11-01 00:00:00')
ORDER BY u.id;
```
