## Where we are

Q5 made a single query fast with the right index, and taught you to read `EXPLAIN`. Q6 made
concurrent transactions correct with atomic updates, locks and MVCC. This lesson is about everything
*between* your Java code and those queries: how many round trips a request makes, how you page
through results, how you write in bulk, and how many connections you open. In production, these
usually decide latency more than any single query plan.

## The problem

The "My bets" endpoint is fast in development. On Saturday at 3 pm, p99 latency is 2.5 seconds and
the logs fill with:

```text
HikariPool-1 - Connection is not available, request timed out after 30000ms.
```

Yet the database CPU is only at 40%, and every query in the endpoint takes about 1 ms when you run
it by hand. Nothing is slow on its own. The request just makes too many trips, holds connections
too long, and the pool runs dry.

## Round trips are the hidden cost

A **round trip** is one request from the app to the database and its reply. Inside one data
centre, that's roughly 0.5 ms of network time (F3's number), before the database does any work.

```text
1 query  × 0.5 ms  =   0.5 ms of waiting
200 queries × 0.5 ms = 100 ms of waiting, even if each query takes 0 ms to run
```

**The rule:** count statements per request, not just the time per statement. Most of the fixes in
this lesson reduce that count.

## N+1, at the SQL level

D6 showed N+1 inside Hibernate: load N bets, then touch a lazy association on each, and you get 1 +
N queries. In SQL terms:

```sql
SELECT id, selection_id, stake FROM bets WHERE user_id = 42;      -- 1 query, 50 rows
SELECT name FROM selections WHERE id = 101;                        -- + 50 queries,
SELECT name FROM selections WHERE id = 205;                        --   one per bet
-- ...
```

There are two fixes. The first is a **join**, so everything comes back in one round trip:

```sql
SELECT b.id, b.stake, s.name
FROM bets b JOIN selections s ON s.id = b.selection_id
WHERE b.user_id = 42;
```

The second is **batching**: collect the ids and fetch them all in one query. In Postgres, pass a
single array parameter rather than building an `IN (?, ?, ...)` list of varying length, so the
statement text stays the same whatever the count:

```java
try (PreparedStatement ps = conn.prepareStatement(
        "SELECT id, name FROM selections WHERE id = ANY(?)")) {
    ps.setArray(1, conn.createArrayOf("bigint", selectionIds.toArray()));
    ...
}
```

Use batching when a join would duplicate a lot of data, or when the second fetch goes to a
different service or cache. Hibernate's `default_batch_fetch_size` (D6) does exactly this for you.

## Pagination: OFFSET reads what it throws away

The history screen pages through a user's bets 20 at a time. The obvious way:

```sql
SELECT id, stake, placed_at FROM bets
WHERE user_id = 42
ORDER BY placed_at DESC, id DESC
LIMIT 20 OFFSET 4000;
```

To return page 201, the database must produce 4,020 rows in order and discard the first 4,000.
Page *n* costs work proportional to *n*. Worse, if a new bet is placed while the user is paging,
everything shifts by one, and they see a duplicate or miss a row.

**Keyset pagination** (also called the seek method) remembers where the last page ended and asks for
rows *after* that point:

```sql
SELECT id, stake, placed_at FROM bets
WHERE user_id = 42
  AND (placed_at, id) < (TIMESTAMP '2026-09-14 19:02:11', 880417)   -- last row of previous page
ORDER BY placed_at DESC, id DESC
LIMIT 20;
```

With an index on `(user_id, placed_at DESC, id DESC)`, this jumps straight to the cursor position
and reads 20 index entries, whatever the page number. `id` is included as a tie-breaker, because two
bets can share a `placed_at`. The row comparison `(a, b) < (x, y)` means "a < x, or a = x and
b < y", which is exactly the sort order.

The API returns the last row's `(placed_at, id)` as an opaque **cursor** token (F3), and the
client sends it back for the next page.

| | OFFSET | Keyset |
|---|---|---|
| Cost of page *n* | grows with *n* | constant |
| New rows while paging | duplicates or gaps | stable |
| Jump to page 57 | yes | no, only next/previous |
| Needs | nothing | an index matching the `ORDER BY`, and a unique tie-breaker |

**The rule:** use keyset for feeds, histories and exports. OFFSET is fine for small admin tables
where people really do jump to page 7.

## Batching writes

Inserting 1,000 rows with 1,000 `executeUpdate()` calls costs 1,000 round trips. JDBC batching
sends them together:

```java
try (PreparedStatement ps = conn.prepareStatement(
        "INSERT INTO wallet_transactions (user_id, amount, type, created_at) VALUES (?, ?, ?, ?)")) {
    for (Credit cr : credits) {
        ps.setLong(1, cr.userId());
        ps.setBigDecimal(2, cr.amount());
        ps.setString(3, "BET_PAYOUT");
        ps.setTimestamp(4, Timestamp.from(cr.at()));
        ps.addBatch();
    }
    ps.executeBatch();
}
```

Three Postgres and Hibernate details that matter:

- **`reWriteBatchedInserts=true`** on the PgJDBC URL rewrites a batch of single-row `INSERT`s into
  multi-row `INSERT ... VALUES (...), (...), ...` statements, which is usually faster still.
- **Hibernate batches only when told to** (`hibernate.jdbc.batch_size`), and it **can't batch
  inserts for entities with `GenerationType.IDENTITY`**, because it needs each generated id back
  immediately. Use a sequence (`GenerationType.SEQUENCE` with an `allocationSize`) for tables you
  insert into in bulk.
- **`COPY`** (PgJDBC's `CopyManager`) is the fastest way to load very large volumes, such as a
  nightly import.

The same idea applies to updates. Settling a market by looping over bets in Java is N round trips.
One set-based statement is one:

```sql
UPDATE bets
SET status     = CASE WHEN selection_id = 101 THEN 'WON' ELSE 'LOST' END,
    payout     = CASE WHEN selection_id = 101 THEN stake * odds_at_placement ELSE 0 END,
    settled_at = CURRENT_TIMESTAMP
WHERE selection_id IN (101, 102, 103) AND status = 'OPEN';
```

(For millions of rows you'd run it in chunks, to keep each transaction short. F8 covers that.)

## Prepared statements

A **prepared statement** separates the SQL text from its parameter values. Two benefits:

1. **Safety.** Values are sent separately and never parsed as SQL, which prevents SQL injection.
2. **Less work per call.** The database can parse and plan the statement once and reuse that work.

With PgJDBC, a `PreparedStatement` that runs repeatedly switches to a **server-side** prepared
statement after `prepareThreshold` executions (5 by default). Postgres, in turn, plans the first
few executions for the specific values supplied, then may switch to one **generic plan** reused for
all values. That is usually good. It can hurt when values are very skewed: a generic plan that suits
an average user may be poor for a user with 2 million bets. If one statement is fast by hand but
slow from the app, this is a suspect.

**The rule:** always use bind parameters. Never build SQL strings from input.

## Chatty transactions

A **chatty transaction** makes many small round trips while it holds a connection, and often locks:

```text
BEGIN
  SELECT user            ─┐
  SELECT limits           │  8 round trips + an HTTP call to a
  SELECT wallet FOR UPDATE│  risk service, all while holding the
  call risk-service (80ms)│  wallet row lock and a pooled connection
  UPDATE wallet           │
  INSERT bet             ─┘
COMMIT
```

Every millisecond inside the transaction is a millisecond the connection and the row lock are
unavailable to anyone else. The fixes:

- Do slow, non-transactional work (remote calls, validation, reading reference data from a cache)
  **before** `BEGIN`.
- Combine statements: a conditional `UPDATE` instead of `SELECT ... FOR UPDATE` plus `UPDATE` (Q6).
- In Spring, keep `@Transactional` on a small method that only does the database work, and never
  call another service from inside it.

## Connection pools, and why bigger is often slower

Opening a Postgres connection is expensive. It means a TCP connection, often TLS, authentication,
and a new **backend process** on the server for every connection. So apps keep a **connection
pool**: a fixed set of open connections that requests borrow and return. **HikariCP** is Spring
Boot's default.

How many do you need? **Little's law:** connections in use = requests per second × time each
request holds a connection.

```text
2,000 transactions/s × 5 ms per transaction = 10 connections busy on average
```

Now the counter-intuitive part. The database can only *execute* about as many queries at once as it
has CPU cores (plus a little for waiting on disk). Give it 400 active connections on 16 cores, and
they don't run 25× faster. They take turns: more context switching, more contention on locks and
shared memory, and more memory per backend process. Each query gets slower, total throughput stays
flat or falls, and timeouts start. HikariCP's own pool-sizing guide gives a starting point for the
number of connections the database is actually working on at once:

```text
connections ≈ (database CPU cores × 2) + effective disk spindles
```

That's a starting point to measure from, not a law. Two consequences people miss:

- **It's per database, not per app instance.** 40 pods × a pool of 20 is 800 connections. Check the
  total against Postgres's `max_connections`, and put a proxy such as PgBouncer or RDS Proxy in
  between if the fleet is large.
- **A small pool with a queue beats a big pool.** Requests waiting a few milliseconds for a
  connection in Hikari's queue are cheaper than requests fighting inside the database.

Useful HikariCP settings: `maximumPoolSize` (default 10); `minimumIdle` left unset, so the pool
stays a fixed size, which HikariCP recommends; and `connectionTimeout`, default 30 s. Lower it to a
second or two, so an exhausted pool fails fast with a 503 instead of stacking up threads. Also set
`maxLifetime` (default 30 minutes) a little below any network or database idle-connection cut-off.

## Finding slow queries

You can't fix what you can't see. Three tools, from cheapest to richest:

1. **The slow query log.** `log_min_duration_statement = 250` (milliseconds) makes Postgres log every
   statement slower than that.
2. **`pg_stat_statements`.** An extension that groups statements by their normalised text (literal
   values replaced by `$1`, `$2`) and keeps totals. It must be listed in
   `shared_preload_libraries`, then created with `CREATE EXTENSION pg_stat_statements;`.

   ```sql
   SELECT query, calls,
          round(total_exec_time) AS total_ms,
          round(mean_exec_time::numeric, 2) AS mean_ms,
          rows
   FROM pg_stat_statements
   ORDER BY total_exec_time DESC
   LIMIT 10;
   ```

   **Sort by total time, not mean.** A 2 ms query called 5 million times a day costs more than a
   3-second report run once.
3. **`auto_explain`.** A module that logs the plan of any statement over a threshold, so you
   capture the plan from production rather than guessing. On Aurora and RDS, **Performance
   Insights** shows database load by wait type and the top SQL statements in a dashboard.

## A diagnose-and-fix walkthrough

**Step 1: find it.** `pg_stat_statements` shows the history page's query at the top by total time:
fairly fast on average, but called constantly, and much slower for heavy bettors.

```sql
SELECT b.id, b.stake, b.placed_at, s.name AS selection, e.name AS event
FROM bets b
JOIN selections s ON s.id = b.selection_id
JOIN markets m    ON m.id = s.market_id
JOIN events e     ON e.id = m.event_id
WHERE b.user_id = 42
  AND date(b.placed_at) >= DATE '2026-09-01'
ORDER BY b.placed_at DESC
LIMIT 20 OFFSET 40;
```

**Step 2: get the real plan** with `EXPLAIN (ANALYZE, BUFFERS)` on a heavy user. **Illustration
only**, with numbers made up to show the shape:

```text
Limit  (actual time=812.4..812.5 rows=20 loops=1)
  ->  Sort  (actual time=812.3..812.4 rows=60 loops=1)
        Sort Key: b.placed_at DESC
        Sort Method: top-N heapsort  Memory: 31kB
        ->  Nested Loop  (actual time=0.9..790.2 rows=48210 loops=1)
              ->  Nested Loop  (actual time=0.8..520.7 rows=48210 loops=1)
                    ->  Nested Loop  (actual time=0.7..260.1 rows=48210 loops=1)
                          ->  Bitmap Heap Scan on bets b  (actual time=0.6..95.3 rows=48210 loops=1)
                                Recheck Cond: (user_id = 42)
                                Filter: (date(placed_at) >= '2026-09-01'::date)
                                Rows Removed by Filter: 151790
                                Buffers: shared hit=1650 read=38200
                                ->  Bitmap Index Scan on bets_user_id  (actual rows=200000 loops=1)
                          ->  Index Scan using selections_pkey on selections s  (actual rows=1 loops=48210)
                    ->  Index Scan using markets_pkey on markets m  (actual rows=1 loops=48210)
              ->  Index Scan using events_pkey on events e  (actual rows=1 loops=48210)
```

**Step 3: read it.** Only an index on `user_id` exists, so Postgres fetches all 200,000 of this
user's bets, removes 151,790 with the date filter (the function hides `placed_at`), joins the
remaining 48,210 three times each (`loops=48210`), sorts them, and finally keeps 20. Almost all of
that work is thrown away by the `LIMIT`. `read=38200` says much of it came from disk.

**Step 4: fix it.**

```sql
CREATE INDEX CONCURRENTLY bets_user_placed ON bets (user_id, placed_at DESC, id DESC);
```

```sql
SELECT b.id, b.stake, b.placed_at, s.name AS selection, e.name AS event
FROM bets b
JOIN selections s ON s.id = b.selection_id
JOIN markets m    ON m.id = s.market_id
JOIN events e     ON e.id = m.event_id
WHERE b.user_id = 42
  AND b.placed_at >= TIMESTAMP '2026-09-01 00:00:00'
  AND (b.placed_at, b.id) < (TIMESTAMP '2026-09-14 19:02:11', 880417)
ORDER BY b.placed_at DESC, b.id DESC
LIMIT 20;
```

Three changes: the date condition is a range on the bare column, `OFFSET` became a keyset cursor,
and the new index matches both the `WHERE` and the `ORDER BY`.

**Step 5: confirm.** Illustration only:

```text
Limit  (actual time=0.06..0.31 rows=20 loops=1)
  ->  Nested Loop  (actual time=0.06..0.30 rows=20 loops=1)
        ->  Nested Loop  (actual rows=20 loops=1)
              ->  Nested Loop  (actual rows=20 loops=1)
                    ->  Index Scan using bets_user_placed on bets b  (actual rows=20 loops=1)
                          Index Cond: ((user_id = 42) AND (placed_at >= ...) AND (ROW(placed_at, id) < ROW(...)))
                    ->  Index Scan using selections_pkey on selections s  (actual rows=1 loops=20)
              ->  Index Scan using markets_pkey on markets m  (actual rows=1 loops=20)
        ->  Index Scan using events_pkey on events e  (actual rows=1 loops=20)
```

No sort, and `loops=20` instead of 48,210: the `LIMIT` now stops the index scan after 20 rows.
Finally, check `pg_stat_statements` again the next day, after calling `pg_stat_statements_reset()`,
to confirm the total time actually fell.

## Lab (~10 min)

Measure round trips, pagination and batching, using H2 in Postgres mode. H2 runs inside your JVM,
so there is no network. The program adds a simulated 1 ms per round trip to make that cost visible.
The H2 work itself is real. Save as `QueryLab.java` and run
`java -cp <path-to>/h2-2.3.232.jar QueryLab.java`.

```java
import java.sql.*;
import java.util.ArrayList;
import java.util.List;

public class QueryLab {
    static final long ROUND_TRIP_MS = 1;   // pretend the database is ~1 ms away over the network
    static int roundTrips;

    public static void main(String[] args) throws Exception {
        try (Connection c = DriverManager.getConnection("jdbc:h2:mem:q7;MODE=PostgreSQL")) {
            setUp(c);
            for (int run = 1; run <= 2; run++) {                 // run 1 warms up the JVM; read run 2
                System.out.println("---- run " + run);
                nPlusOne(c);
                oneJoin(c);
                offsetPage(c, run);
                keysetPage(c, run);
                inserts(c);
            }
        }
    }

    static void nPlusOne(Connection c) throws SQLException {
        long t = start();
        List<Long> selectionIds = new ArrayList<>();
        try (PreparedStatement ps = c.prepareStatement("SELECT selection_id FROM bets WHERE user_id = ?")) {
            ps.setLong(1, 42);
            try (ResultSet rs = query(ps)) { while (rs.next()) selectionIds.add(rs.getLong(1)); }
        }
        try (PreparedStatement ps = c.prepareStatement("SELECT name FROM selections WHERE id = ?")) {
            for (long id : selectionIds) {                       // one more query per bet: the "+N"
                ps.setLong(1, id);
                try (ResultSet rs = query(ps)) { rs.next(); }
            }
        }
        stop("N+1 (bets, then each selection)", t);
    }

    static void oneJoin(Connection c) throws SQLException {
        long t = start();
        try (PreparedStatement ps = c.prepareStatement("""
                SELECT b.id, s.name FROM bets b JOIN selections s ON s.id = b.selection_id
                WHERE b.user_id = ?""")) {
            ps.setLong(1, 42);
            try (ResultSet rs = query(ps)) { while (rs.next()) { } }
        }
        stop("one JOIN", t);
    }

    static void offsetPage(Connection c, int run) throws SQLException {
        long t = start();
        try (PreparedStatement ps = c.prepareStatement(
                "SELECT id, stake FROM bets ORDER BY id DESC LIMIT 20 OFFSET ?")) {
            ps.setInt(1, 900_000 + run);                         // a new value each run defeats H2's result cache
            try (ResultSet rs = query(ps)) { while (rs.next()) { } }
        }
        stop("page 45,001 with OFFSET", t);
    }

    static void keysetPage(Connection c, int run) throws SQLException {
        long t = start();
        try (PreparedStatement ps = c.prepareStatement(
                "SELECT id, stake FROM bets WHERE id < ? ORDER BY id DESC LIMIT 20")) {
            ps.setLong(1, 100_001 - run);                        // last id seen on the previous page
            try (ResultSet rs = query(ps)) { while (rs.next()) { } }
        }
        stop("page 45,001 with keyset", t);
    }

    static void inserts(Connection c) throws SQLException {
        String sql = "INSERT INTO wallet_transactions (user_id, amount, type) VALUES (?, 5, 'BONUS')";
        c.setAutoCommit(false);
        long t = start();
        try (PreparedStatement ps = c.prepareStatement(sql)) {
            for (int i = 0; i < 1000; i++) { ps.setLong(1, i); ps.executeUpdate(); roundTrip(); }
        }
        c.commit();
        stop("1,000 single INSERTs", t);

        t = start();
        try (PreparedStatement ps = c.prepareStatement(sql)) {
            for (int i = 0; i < 1000; i++) { ps.setLong(1, i); ps.addBatch(); }
            ps.executeBatch(); roundTrip();
        }
        c.commit();
        stop("one batch of 1,000", t);
        c.setAutoCommit(true);
    }

    static void setUp(Connection c) throws SQLException {
        try (Statement s = c.createStatement()) {
            s.execute("CREATE TABLE selections (id BIGINT PRIMARY KEY, name VARCHAR(50))");
            s.execute("INSERT INTO selections SELECT x, 'Selection ' || x FROM SYSTEM_RANGE(1, 5000)");
            s.execute("""
                CREATE TABLE bets (id BIGINT PRIMARY KEY, user_id BIGINT, selection_id BIGINT,
                                   stake NUMERIC(12,2))""");
            // 1,000,000 bets, 50 per user (H2's SYSTEM_RANGE plays the role of generate_series)
            s.execute("""
                INSERT INTO bets SELECT x, MOD(x, 20000), 1 + MOD(x, 5000), 10
                FROM SYSTEM_RANGE(1, 1000000)""");
            s.execute("CREATE INDEX bets_user ON bets (user_id)");
            s.execute("""
                CREATE TABLE wallet_transactions (id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
                  user_id BIGINT, amount NUMERIC(12,2), type VARCHAR(20))""");
        }
    }

    static ResultSet query(PreparedStatement ps) throws SQLException { roundTrip(); return ps.executeQuery(); }

    static void roundTrip() {                    // busy-wait, because Thread.sleep(1) is coarse on Windows
        roundTrips++;
        long end = System.nanoTime() + ROUND_TRIP_MS * 1_000_000;
        while (System.nanoTime() < end) Thread.onSpinWait();
    }

    static long start() { roundTrips = 0; return System.nanoTime(); }

    static void stop(String label, long t) {
        System.out.printf("%-34s %5d round trips %8.1f ms%n", label, roundTrips, (System.nanoTime() - t) / 1e6);
    }
}
```

What you should observe in run 2 (one laptop's numbers; yours will differ, but the ratios hold):

```text
N+1 (bets, then each selection)       51 round trips     63.9 ms
one JOIN                               1 round trips      1.4 ms
page 45,001 with OFFSET                1 round trips     65.4 ms
page 45,001 with keyset                1 round trips      1.6 ms
1,000 single INSERTs                1000 round trips   1086.9 ms
one batch of 1,000                     1 round trips      9.9 ms
```

N+1 and single inserts are dominated by round trips. OFFSET is slow with only one round trip,
because the database walks 900,000 index entries to throw them away. Now set `ROUND_TRIP_MS = 0`
and run again: N+1 and the single inserts drop to a few milliseconds, while OFFSET stays slow.
That's the difference between a *latency* problem and a *work* problem.

## Gotchas

- **N+1 hides in loops and lazy getters.** Count statements per request in tests or tracing, not
  just total time. Fix with a join or a batched `= ANY(?)` query.
- **Deep OFFSET pages.** The cost grows with the page number, and results shift under concurrent
  inserts. Use keyset pagination with a unique tie-breaker column.
- **`GenerationType.IDENTITY` silently disables Hibernate insert batching.** Use a sequence with an
  allocation size for bulk-inserted entities.
- **"The pool is exhausted, so make it bigger."** Usually wrong. Find what holds connections
  (long transactions, remote calls inside them), and size the total across all instances against
  the database's cores and `max_connections`.
- **Remote calls inside `@Transactional`.** The connection and any row locks are held for the whole
  call. Do them before the transaction starts.
- **Sorting `pg_stat_statements` by mean time.** You find rare slow reports and miss the cheap query
  that runs 5 million times. Sort by `total_exec_time`.

Typical follow-ups:

- *"Keyset pagination can't jump to page 50. What do you tell product?"* For feeds and histories,
  nobody jumps to page 50; offer date filters ("bets in September") which are also index range
  scans. Where jumping is a real requirement and the table is small, OFFSET is fine.
- *"We have 60 pods and the database hits max_connections."* Total = pods × pool size. Shrink each
  pool to what Little's law says it needs, then add PgBouncer or RDS Proxy to multiplex many client
  connections onto fewer server connections.

## Explain it in 2 minutes

*"Our API is slow under load, but every query is fast in isolation. Where do you look?"*

- Count round trips per request: N+1 and statement loops multiply ~0.5 ms network waits.
- Check pagination: deep `OFFSET` does work proportional to the page number; use keyset.
- Check writes: batch inserts, set-based updates, sequences instead of identity for Hibernate.
- Check transactions: remote calls or slow logic inside them hold connections and locks.
- Check the pool: size it by Little's law and the database's cores; total across instances.
- Confirm with `pg_stat_statements` sorted by total time, then `EXPLAIN (ANALYZE, BUFFERS)`.

## Check yourself

1. A request makes 1 query for 80 bets, then 1 per bet for the event name. Roughly how much network
   wait is that at 0.5 ms per round trip, and what are two fixes?
2. Why does `LIMIT 20 OFFSET 100000` get slower as the offset grows, even with a perfect index?
3. Your service handles 3,000 transactions/s and each holds a connection for 4 ms. How many
   connections are busy on average?
4. Why can raising `maximumPoolSize` from 20 to 200 make latency worse?
5. In `pg_stat_statements`, query A has mean 900 ms and 50 calls; query B has mean 3 ms and 4
   million calls. Which do you look at first?

### Answers

1. 81 round trips ≈ 40 ms of waiting. Use a join, or one batched `WHERE id = ANY(?)` query.
2. The database must produce and discard every skipped row in order; work grows with the offset.
   Keyset pagination seeks directly to the cursor instead.
3. Little's law: 3,000 × 0.004 s = 12 connections.
4. The database can only run about as many queries at once as it has cores. Extra active
   connections contend for CPU, locks and memory, so each query slows and throughput doesn't rise.
5. B: 4M × 3 ms = 12,000 s of total time against A's 45 s.
