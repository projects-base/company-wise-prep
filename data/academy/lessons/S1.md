## Where we are

From S0 you know that a server is a **process** listening on a **port**, that HTTP requests and responses are plain text over TCP, and that a **thread** is far cheaper than a process. This lesson covers the first way the web produced *dynamic* pages, **CGI**. It works by starting a new process for every request. You'll build it and then measure what that costs.

## The problem

The first web servers only served **static files**: a request for `/about.html` returned that file from disk, and every visitor got the same bytes.

ShopKart can't work that way. `/orders?user=akhil` has to show *Akhil's* orders, which means running code that reads data and builds HTML for this particular request. In the early 1990s web servers were written in C and had no way to run your code inside them, so they needed a way to hand a request over to *another program* and send back whatever that program printed.

## The invention: the Common Gateway Interface

**CGI (Common Gateway Interface)** emerged at NCSA, home of the NCSA HTTPd web server, around 1993. It was later written down as CGI/1.1 in RFC 3875 (2004). It is a contract between a web server and a separate program, the **CGI script**:

1. The server receives a request for, say, `/cgi-bin/orders`.
2. It **starts a new process** running the script.
3. It passes the request in **environment variables**, which are named strings the OS gives a new process (`REQUEST_METHOD=GET`, `QUERY_STRING=user=akhil`, `CONTENT_LENGTH`...). A POST body arrives on the script's **standard input** (stdin).
4. The script writes headers, then a blank line, then the body to **standard output** (stdout), and then exits.
5. The server copies that output back to the browser as the HTTP response.

```text
browser ──HTTP──► web server ──start process──► orders.pl / orders.cgi
                    │   env: QUERY_STRING=user=akhil
                    │◄── stdout: "Content-Type: text/html\r\n\r\n<h1>..." ──┤
browser ◄─HTTP──────┘                                            process exits
```

A tiny CGI script in Java looks like this:

```java
public class Page {
    public static void main(String[] args) {
        String query = System.getenv("QUERY_STRING");                  // set by the server
        System.out.print("Content-Type: text/html\r\n");
        System.out.print("\r\n");                                       // blank line: headers done
        System.out.print("<h1>Hello " + (query == null || query.isEmpty() ? "stranger" : query) + "</h1>");
        System.out.print("<p>Rendered by process " + ProcessHandle.current().pid() + "</p>");
    }
}
```

In practice most CGI scripts were written in Perl or C, because both start quickly. The rule is simple: **any language that can read environment variables and print to stdout can serve web pages.** That language independence is why CGI spread so fast.

## Why it was good: isolation and simplicity

A new process per request brought real benefits:

- **Isolation.** If one request crashes its script or leaks memory, only that process dies, and the OS reclaims everything when it exits. Other requests are unaffected.
- **Nothing shared means nothing to corrupt.** Two requests never touch the same memory, so there are no race conditions.
- **Easy to deploy.** Copy a script into `cgi-bin/` and it is live.

Keep these in mind. Later eras give up isolation in exchange for speed, and they pay for it in bugs.

## The pain, part 1: start-up cost

Every request pays the full cost of starting a process: the OS creates a memory space, loads the program and runs its start-up code. For Perl that meant starting the interpreter and compiling the script **on every request**. For Java it would mean starting a whole JVM each time, which is even worse. You'll measure it in the lab.

Under load the cost multiplies. A hundred simultaneous users means a hundred processes being created, each with its own memory, all competing for CPU.

## The pain, part 2: no memory between requests

When the process exits, everything it held is gone: a database connection it opened, a cache it built, the parsed configuration. The next request has to start from zero.

```text
request 1: start process → connect to DB → query → print → exit  (connection lost)
request 2: start process → connect to DB → query → print → exit  (and again...)
```

Opening a database connection involves a network handshake and authentication, so redoing it on every request is pure waste. CGI also offers no place to keep **session state** such as "Akhil is logged in". It has to go into files or a database on every request.

## Patches inside the era: FastCGI and mod_perl

Two fixes appeared in the mid-1990s, and both point the same direction:

- **FastCGI** keeps the script running as a **long-lived worker process**. The web server sends it request after request over a socket instead of starting a new process each time. You keep the separate process but drop the start-up cost.
- **mod_perl** embeds the Perl interpreter **inside the Apache web server process**, so scripts stay compiled in memory between requests.

Rule: **stop paying start-up cost per request; keep a warm worker alive and reuse it.** Java's answer, in S2, goes one step further. A single long-lived process handles every request, each on its own **thread**.

## Lab (~10 min)

**Build** a CGI-style server with only the JDK, then **break** it under load and compare it with an in-process handler.

Put these three files in one folder: `Page.java` (shown above), plus `CgiServer.java` and `LoadTest.java` below. Compile them once with `javac -d out *.java`.

```java
import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpServer;
import java.io.IOException;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;
import java.util.concurrent.Executors;

public class CgiServer {
    public static void main(String[] args) throws IOException {
        HttpServer server = HttpServer.create(new InetSocketAddress(8081), 0);
        server.setExecutor(Executors.newCachedThreadPool());   // let requests be handled concurrently

        // Era S1: every request starts a brand-new OS process (a whole JVM!) and waits for it to exit.
        server.createContext("/cgi", exchange -> {
            ProcessBuilder pb = new ProcessBuilder("java", "-cp", "out", "Page");
            String q = exchange.getRequestURI().getQuery();
            pb.environment().put("REQUEST_METHOD", exchange.getRequestMethod());
            pb.environment().put("QUERY_STRING", q == null ? "" : q);
            Process process = pb.start();
            String output = new String(process.getInputStream().readAllBytes(), StandardCharsets.UTF_8);
            try { process.waitFor(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            int split = output.indexOf("\r\n\r\n");              // CGI output = headers, blank line, body
            send(exchange, output.substring(split + 4));
        });

        // Preview of era S2: same page, rendered inside the already-running server process.
        server.createContext("/inproc", exchange -> {
            String q = exchange.getRequestURI().getQuery();
            send(exchange, "<h1>Hello " + (q == null ? "stranger" : q) + "</h1><p>Rendered by process "
                    + ProcessHandle.current().pid() + "</p>");
        });

        server.start();
        System.out.println("Try http://localhost:8081/cgi?akhil and http://localhost:8081/inproc?akhil");
    }

    static void send(HttpExchange exchange, String html) throws IOException {
        byte[] bytes = html.getBytes(StandardCharsets.UTF_8);
        exchange.getResponseHeaders().add("Content-Type", "text/html; charset=utf-8");
        exchange.sendResponseHeaders(200, bytes.length);
        exchange.getResponseBody().write(bytes);
        exchange.close();
    }
}
```

`Executors.newCachedThreadPool()` gives the server a pool of threads, so several requests can be served at once. Track B covers pools properly. The load tester starts one plain `Thread` per simulated user:

```java
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

// Usage: java -cp out LoadTest <url> <users> <requestsPerUser>
public class LoadTest {
    public static void main(String[] args) throws Exception {
        String url = args[0];
        int users = Integer.parseInt(args[1]);
        int perUser = Integer.parseInt(args[2]);
        HttpClient client = HttpClient.newBuilder().version(HttpClient.Version.HTTP_1_1).build();
        List<Long> latenciesMs = Collections.synchronizedList(new ArrayList<>());

        long start = System.nanoTime();
        List<Thread> threads = new ArrayList<>();
        for (int u = 0; u < users; u++) {
            Thread t = new Thread(() -> {
                for (int i = 0; i < perUser; i++) {
                    long t0 = System.nanoTime();
                    try {
                        client.send(HttpRequest.newBuilder(URI.create(url)).build(),
                                HttpResponse.BodyHandlers.discarding());
                    } catch (Exception e) {
                        System.out.println("failed: " + e);
                    }
                    latenciesMs.add((System.nanoTime() - t0) / 1_000_000);
                }
            });
            threads.add(t);
            t.start();
        }
        for (Thread t : threads) t.join();
        long totalMs = (System.nanoTime() - start) / 1_000_000;

        List<Long> sorted = new ArrayList<>(latenciesMs);
        Collections.sort(sorted);
        System.out.printf("requests=%d total=%d ms  throughput=%.1f req/s%n",
                sorted.size(), totalMs, sorted.size() * 1000.0 / totalMs);
        System.out.printf("median=%d ms  p95=%d ms  max=%d ms%n",
                sorted.get(sorted.size() / 2), sorted.get((int) (sorted.size() * 0.95)), sorted.get(sorted.size() - 1));
    }
}
```

**Steps:**

1. Run `java -cp out CgiServer`, then open `/cgi?akhil` a few times. **The PID changes on every refresh**, because each request ran in a new process. Open `/inproc?akhil` and the PID stays the same.
2. Run `java -cp out LoadTest "http://localhost:8081/cgi?x" 10 3`, then the same command with `/inproc`.
3. Increase the load step by step to 20 users and then 50, watching Task Manager while you do. **Stop if your machine struggles.** Each CGI request is a whole JVM with its own memory, and that is precisely the point of the exercise.

**What you should observe:** `/cgi` has a median latency of hundreds of milliseconds and low throughput. `/inproc` responds in a few milliseconds. As you add users, CGI's latency and memory climb steeply. Write the numbers down, because S2 compares against them. (*p95* is the latency that 95% of requests beat. It shows what your slow users experience.)

## Gotchas

- **Blaming the code for process cost.** In CGI most of the time per request goes into *starting the process*, not your logic. Measure before you optimise.
- **Expecting state to survive.** A CGI process forgets everything when it exits. Connections, caches and logins must be rebuilt or stored elsewhere on every request.
- **Forgetting the blank line.** CGI output, like HTTP, needs an empty line between headers and body. Without it the server can't tell where the headers end and returns an error.
- **Trusting `QUERY_STRING`.** It is raw user input. Classic CGI scripts that pasted it into shell commands or SQL were a common source of break-ins, so validate and escape it.
- **"Isolation is free."** It isn't. You pay for it with start-up cost and memory per request. Every later era picks a different point on that tradeoff.

## In interviews

Nobody asks about CGI by name. They ask the question underneath it:

- [Process vs thread, shared variables and race conditions](#/q/process-vs-thread)
- [Inter-Process Communication Methods](#/q/ipc-mechanisms): CGI itself is IPC through environment variables and pipes (stdin/stdout).
- [Copy-on-Write Page Counts](#/q/copy-on-write-page-counts): on Unix, servers create processes with `fork`, and copy-on-write is what makes `fork` cheaper than copying all memory.

Typical follow-ups:

- *"Why is process-per-request slow, and what does a thread save you?"* A strong answer says a process needs a new address space and full program start-up (for an interpreter or JVM, that means loading and warming up the runtime every time), plus its own memory. A thread reuses the running process's memory, loaded code and open resources such as connection pools. What you lose is isolation.
- *"When would you still choose processes over threads?"* When isolation matters more than speed: running untrusted code, plugins that might crash, or memory leaks you can't fix. The fix is a crash or restart of one worker, not the whole server.

## Explain it in 2 minutes

*"Why is process-per-request slow, and what does a thread save you?"*

A good answer hits:

1. CGI: the web server starts a **new process per request**, passes the request in environment variables and stdin, reads the response from stdout, and the process exits.
2. Benefit: **isolation**. A crash or leak affects one request, and nothing is shared, so nothing can race.
3. Cost: **process start-up** on every request (address space, loading, interpreter start-up), plus memory per concurrent request.
4. Cost: **no state across requests**. DB connections and caches are rebuilt every time.
5. Fixes: **long-lived workers** (FastCGI, mod_perl) and then **threads inside one process** (servlets), which keep the runtime warm and share resources.
6. The price of threads is shared memory, and with it race conditions.

## Check yourself

1. How does a CGI script receive the query string and the POST body?
2. Why does a database connection opened by a CGI script not help the next request?
3. What did FastCGI change, and what did it keep?
4. In the lab, why did the PID change on every `/cgi` refresh but not on `/inproc`?

### Answers

1. The query string arrives in the `QUERY_STRING` environment variable (with `REQUEST_METHOD` and others alongside it). The POST body comes in on standard input, with `CONTENT_LENGTH` giving its length.
2. The process exits at the end of the request and the connection dies with it.
3. It kept the script in a separate process but made that process **long-lived**, handling many requests in turn, which removed the per-request start-up cost.
4. `/cgi` started a new OS process for each request. `/inproc` ran inside the server's single long-lived process.
