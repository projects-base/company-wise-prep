## Where we are

After CAPSTONE-6, TicketHub has slice tests, a Testcontainers Postgres, a passing double-booking race test and an N+1-free `GET /me/bookings`. Two gaps remain. A hold says it expires after `hold-duration`, and confirm does refuse it with `410`, but nothing ever gives its seats back, so they stay locked forever. And the price is simply `priceCategory.centsPerSeat() × seats`. This session fixes both, using JAVA-CONC-4 (executors and pool sizing) and LLD-DESIGN-2…4 (patterns, Strategy in particular).

## Goal

Add a scheduled job that releases expired holds. It must be safe to run twice, safe when two app instances run it at once, and testable without waiting, because it reads time from the injected `Clock`. Then make pricing pluggable with the **Strategy pattern**: one interface, one class per pricing rule, picked at runtime from the event, with no growing `switch`.

`PriceCategory` (`STANDARD`, `PREMIUM`, `VIP`) stays what CAPSTONE-1 made it: the tier that sets the base `centsPerSeat`. A new per-event `PricingRule` (`STANDARD`, `EARLY_BIRD`, `SURGE`) chooses how that base is adjusted. It arrives in your first migration on an existing schema, `V2`.

## What you build

- [ ] `HoldExpiryProperties`, a `@ConfigurationProperties("tickethub.hold-expiry")` record: `enabled`, `interval`, `batch-size`
- [ ] `HoldExpiryService.expireBatch(int)`: one transaction per batch, `FOR UPDATE SKIP LOCKED`, idempotent updates
- [ ] `HoldExpiryJob`: `@Scheduled(fixedDelay…)`, loops over batches, switched off by a property
- [ ] `BookingService.confirm` and `release` lock the hold row, so they cannot interleave with the job
- [ ] `V2__event_pricing_rule.sql`, plus `pricingRule` on `EventEntity`
- [ ] `PricingStrategy` with `StandardPricing`, `EarlyBirdPricing` and `SurgePricing`
- [ ] `PriceCalculator`: an `EnumMap` registry that fails at startup if a rule has no strategy, used by `hold()`
- [ ] Tests: `HoldExpiryServiceTest` (with CAPSTONE-1's `MutableClock`), `PricingStrategyTest` (parameterized), `PriceCalculatorTest`

## Acceptance criteria

- `HoldExpiryServiceTest.expiresOnlyOverdueHoldsAndIsIdempotent` (test profile, `hold-duration: 2m`): at +1 minute `expireBatch` returns 0. At +3 minutes it returns 1, seats 1001 and 1002 are `AVAILABLE` with `hold_id` null, and the hold is `EXPIRED`. A second call returns 0.
- `HoldExpiryServiceTest.expiredSeatsCanBeHeldAgain`: after expiry, bob's hold on seat 1001 succeeds.
- `HoldExpiryServiceTest.confirmAfterSweepIs410`: confirming an expired, swept hold still throws `HoldExpiredException`, not "not found".
- `PricingStrategyTest` covers each strategy at its boundaries: one second before and after the early-bird cut-off, and surge at 79%, 80% and 95% occupancy.
- `PriceCalculatorTest.failsFastWhenARuleHasNoStrategy` passes.
- Manual check: `./mvnw spring-boot:run -Dspring-boot.run.arguments=--tickethub.hold-duration=1m`, hold a seat, wait about 90 seconds, and `GET /api/v1/events/1/seats` shows it available. The log shows one `hold-expiry expired=1` line.
- `HoldApiTest` (including `confirmAfterExpiryIs410`) and CAPSTONE-6's race test are still green. For a `STANDARD` rule the price is unchanged: `totalCents: 5000` for one seat.

## Steps

**1. Properties (3 min).** The hold length stays `TicketHubProperties.holdDuration()` from CAPSTONE-3. The job gets its own small record:

```java
@ConfigurationProperties("tickethub.hold-expiry")
public record HoldExpiryProperties(@DefaultValue("true") boolean enabled,
                                   @DefaultValue("30s") Duration interval,
                                   @DefaultValue("200") int batchSize) {}
```

`@ConfigurationPropertiesScan` from CAPSTONE-3 picks it up. Add `@EnableScheduling` to a `common.SchedulingConfig` class.

**2. The expiry service: lock, release, mark (12 min).** Each batch is one short transaction:

```java
public interface SeatHoldRepository extends JpaRepository<SeatHoldEntity, UUID> {

    @Query(value = """
            select id from seat_hold
            where status = 'HELD' and expires_at <= :now
            order by expires_at
            limit :limit
            for update skip locked
            """, nativeQuery = true)
    List<UUID> lockExpiredHeld(Instant now, int limit);

    @Modifying
    @Query(value = "update seat_hold set status = 'EXPIRED' where id in (:ids) and status = 'HELD'", nativeQuery = true)
    int markExpired(Collection<UUID> ids);

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select h from SeatHoldEntity h where h.id = :id")
    Optional<SeatHoldEntity> findByIdForUpdate(UUID id);
}
```

```java
// in EventSeatRepository
@Modifying
@Query(value = """
        update event_seat set status = 'AVAILABLE', hold_id = null, version = version + 1
        where hold_id in (:ids) and status = 'HELD'
        """, nativeQuery = true)
int releaseHeldSeats(Collection<UUID> ids);
```

```java
@Service
public class HoldExpiryService {
    private final SeatHoldRepository holds;
    private final EventSeatRepository eventSeats;
    private final Clock clock;

    public HoldExpiryService(SeatHoldRepository holds, EventSeatRepository eventSeats, Clock clock) {
        this.holds = holds;
        this.eventSeats = eventSeats;
        this.clock = clock;
    }

    @Transactional
    public int expireBatch(int batchSize) {
        List<UUID> ids = holds.lockExpiredHeld(clock.instant(), batchSize);
        if (ids.isEmpty()) {
            return 0;
        }
        eventSeats.releaseHeldSeats(ids);
        return holds.markExpired(ids);
    }
}
```

Each line carries one property:

- **Idempotent.** Both updates repeat `status = 'HELD'`, so a re-run, or a second instance arriving late, changes nothing. The partial index `ix_seat_hold_expiry` from CAPSTONE-5 serves exactly this `where`. `<=` matches CAPSTONE-2's rule that a hold is expired *at* `expiresAt`.
- **`version = version + 1` by hand.** Bulk updates, native or JPQL, bypass `@Version`. Without the bump, a request that had read the seat at version 5 would still pass its optimistic check after the job freed the seat.
- **`FOR UPDATE SKIP LOCKED`.** `FOR UPDATE` row-locks the selected holds until commit. `SKIP LOCKED` tells another transaction to pass over rows that are already locked instead of waiting. Two instances therefore take different batches, and neither blocks the other.
- **`clock.instant()`, never `Instant.now()`.** Tests can move time.

Now close the race with confirm. In `BookingService.confirm` and `release`, load the hold with `findByIdForUpdate` instead of `findById`:

- **If the job locked the hold first,** confirm waits, then sees `EXPIRED` and throws `HoldExpiredException`. Map an `EXPIRED` status to `410`, the same answer as the clock check, so a swept hold does not turn into a `404`.
- **If confirm locked first,** the job skips that row. On its next run the status is `CONFIRMED`, so the row no longer matches.

**3. The job (5 min).** The job and the transactional service are separate beans. If both lived in one class, the self-call would bypass the transactional proxy (SPRING-BOOT-3).

```java
@Component
@ConditionalOnProperty(name = "tickethub.hold-expiry.enabled", havingValue = "true", matchIfMissing = true)
class HoldExpiryJob {
    private static final Logger log = LoggerFactory.getLogger(HoldExpiryJob.class);
    private static final int MAX_BATCHES_PER_RUN = 50;    // bound the work per tick; the next tick continues

    private final HoldExpiryService expiry;
    private final HoldExpiryProperties props;

    HoldExpiryJob(HoldExpiryService expiry, HoldExpiryProperties props) {
        this.expiry = expiry;
        this.props = props;
    }

    @Scheduled(fixedDelayString = "${tickethub.hold-expiry.interval:30s}", initialDelayString = "10s")
    void run() {
        int total = 0;
        for (int i = 0; i < MAX_BATCHES_PER_RUN; i++) {
            int expired = expiry.expireBatch(props.batchSize());
            total += expired;
            if (expired < props.batchSize()) {
                break;
            }
        }
        if (total > 0) {
            log.info("hold-expiry expired={}", total);    // counts only, never user data
        }
    }
}
```

Two choices to be able to defend:

- **`fixedDelay`, not `fixedRate`.** The next run starts a fixed time after the previous one *finishes*, so runs never overlap on one instance. The `"30s"` style of duration string is accepted by Spring Framework 6.1+, which Boot 3.5 uses. `"PT30S"` works too.
- **One transaction per batch.** If one batch fails, its rollback leaves the batches already committed intact. The scheduler logs the exception and the next tick retries.

**4. Test it with the clock you already have (10 min).** CAPSTONE-1 wrote `MutableClock`, and CAPSTONE-4's `TestClockConfig` makes it the `@Primary` clock, starting at `2026-11-01T10:00:00Z`.

**6. Strategies and the registry (14 min).**

```java
public record PricingContext(long baseCentsPerSeat, int seatCount, Instant startsAt,
                             long seatsTaken, long seatsTotal, Instant now) {}

public interface PricingStrategy {
    PricingRule rule();
    long totalCents(PricingContext ctx);
}

@ConfigurationProperties("tickethub.pricing")
public record PricingProperties(@DefaultValue("2000") int earlyBirdDiscountBps,      // 2000 basis points = 20%
                                @DefaultValue("30d") Duration earlyBirdWindow) {}
```

Money stays in `long` cents, and percentages are **basis points** (1 bp = 0.01%), so the whole calculation is integer arithmetic with no `double` rounding drift.

```java
@Component
class EarlyBirdPricing implements PricingStrategy {
    private final PricingProperties props;
    EarlyBirdPricing(PricingProperties props) { this.props = props; }

    @Override public PricingRule rule() { return PricingRule.EARLY_BIRD; }

    @Override
    public long totalCents(PricingContext ctx) {
        long full = Math.multiplyExact(ctx.baseCentsPerSeat(), ctx.seatCount());
        Instant cutOff = ctx.startsAt().minus(props.earlyBirdWindow());
        return ctx.now().isBefore(cutOff) ? full * (10_000 - props.earlyBirdDiscountBps()) / 10_000 : full;
    }
}

@Component
class SurgePricing implements PricingStrategy {
    @Override public PricingRule rule() { return PricingRule.SURGE; }

    @Override
    public long totalCents(PricingContext ctx) {
        long occupancyBps = ctx.seatsTaken() * 10_000 / ctx.seatsTotal();
        long multiplierBps = occupancyBps >= 9_500 ? 15_000 : occupancyBps >= 8_000 ? 12_500 : 10_000;
        return Math.multiplyExact(ctx.baseCentsPerSeat(), ctx.seatCount()) * multiplierBps / 10_000;
    }
}
```

`StandardPricing` returns `base × seatCount`. Write it yourself. Spring injects every `PricingStrategy` bean as a list, and the registry indexes them:

```java
@Component
public class PriceCalculator {
    private final Map<PricingRule, PricingStrategy> strategies;
    private final EventRepository events;
    private final EventSeatRepository eventSeats;
    private final Clock clock;

    public PriceCalculator(List<PricingStrategy> all, EventRepository events, EventSeatRepository eventSeats, Clock clock) {
        var byRule = new EnumMap<PricingRule, PricingStrategy>(PricingRule.class);
        for (PricingStrategy s : all) {
            if (byRule.put(s.rule(), s) != null) {
                throw new IllegalStateException("Two pricing strategies for " + s.rule());
            }
        }
        for (PricingRule r : PricingRule.values()) {
            if (!byRule.containsKey(r)) {
                throw new IllegalStateException("No pricing strategy for " + r);
            }
        }
        this.strategies = byRule;
        this.events = events;
        this.eventSeats = eventSeats;
        this.clock = clock;
    }

    public long totalCents(long eventId, int seatCount) {
        EventEntity event = events.findById(eventId).orElseThrow(() -> new EventNotFoundException(eventId));
        EventSeatRepository.Occupancy occ = eventSeats.occupancy(eventId);
        var ctx = new PricingContext(event.getPriceCategory().centsPerSeat(), seatCount, event.getStartsAt(),
                occ.getTaken(), occ.getTotal(), clock.instant());
        return strategies.get(event.getPricingRule()).totalCents(ctx);
    }
}
```

        """, nativeQuery = true)

In `BookingService.hold`, the CAPSTONE-5 line `Math.multiplyExact(event.priceCategory().centsPerSeat(), seatIds.size())` becomes `prices.totalCents(eventId, seatIds.size())`. Adding a fourth rule later means adding one class and one enum constant, with no edits to existing strategies. That is the Open/Closed principle in practice. `PriceCalculatorTest` builds the calculator with only two strategies (mocks for the repositories) and asserts the `IllegalStateException`.

**7. Executor sizing (2 min, know the answer).** Every `@Scheduled` method shares one scheduler pool, and Boot's default has **one thread** (`spring.task.scheduling.pool.size`). One job is fine on one thread. If a slow second job is added, it delays this one, so size the pool to the number of jobs that may run at the same time. The JAVA-CONC-4 formula, threads ≈ cores × (1 + wait/compute), describes CPU use. Here the scarce resource is database connections: every running batch holds one Hikari connection, and scheduler threads plus request threads must fit in the pool, or jobs and requests queue for connections. CAPSTONE-8 turns on virtual threads, and then that is the *only* limit.

## Hints

- **`@Scheduled` never fires.** Check for a missing `@EnableScheduling`, or for `hold-expiry.enabled=false` in the active profile.
- **`TransactionRequiredException` on a `@Modifying` query.** The caller is not transactional. That happens when you call `expireBatch` from inside the same class, or when the method is not `public`.
- **Expired-but-unswept holds still block their seats** for up to one interval (30 s). That is an accepted trade-off, and confirm still rejects them because it checks the clock. CAPSTONE-9 adds a Redis TTL fast path, and this job stays as the safety net.
- **Two instances without `SKIP LOCKED`:** the results stay correct thanks to the `status = 'HELD'` guards, but both instances lock the same rows and one waits for the other. With `SKIP LOCKED` they share the work.
- **ShedLock instead?** ShedLock is a library that stores a named lock in a `shedlock` table (one more Flyway migration). With `@SchedulerLock(name = "holdExpiry", lockAtMostFor = "PT5M")`, only one instance runs the job per tick. Use it for jobs that are not row-shaped, such as a nightly report. When the work is a set of rows, `SKIP LOCKED` scales better because every instance helps.

## Talk about it in interviews

**"How do you run a scheduled job safely on several instances?"**
1. *What:* a sweeper that releases expired holds every 30 seconds, in bounded batches.
2. *How it works inside:* each batch is one transaction. `SELECT ... FOR UPDATE SKIP LOCKED` hands disjoint rows to concurrent instances. The updates are guarded by `status = 'HELD'`, so re-runs do nothing. Confirm takes the same row lock, so the two cannot interleave. Time comes from an injected `Clock`.
3. *Where it's used:* reservation timeouts, outbox relays, retry queues. This is Postgres used as a job queue.
4. *What goes wrong:* `fixedRate` runs that overlap, bulk updates that skip `@Version`, one huge transaction holding locks for minutes, `Instant.now()` forcing tests to sleep. Pick ShedLock for a single runner and `SKIP LOCKED` for shared work.

**"Where did you use a design pattern, and why?"** Pricing uses Strategy plus a registry keyed by an enum. Explain why it beats a `switch`: each rule is tested alone, the code is open for extension, and a missing rule fails at startup. Then name the honest cost, which is more classes. Strategy earns its place because pricing rules change often and are owned by the business.

**"How do you handle money?"** Integer cents and basis points. Integer division rounds down, deliberately. `Math.multiplyExact` turns overflow into an exception. The price quoted at hold time is stored on the hold, so confirm charges exactly that.
