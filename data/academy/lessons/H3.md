## Where we are

You can write and run Java programs. Real backend work, and the "tell me about a production issue"
questions in interviews, need one more skill: finding out **why** a running system misbehaves,
quickly and without guessing. This lesson covers five habits that do most of that work: reproduce
first, read the stack trace, log usefully, capture heap dumps, and check transaction boundaries.

## The problem

A ticket arrives: "Orders sometimes aren't saved, and last night the service died with
`OutOfMemoryError`." The tempting move is to open the code, spot something that looks suspicious,
change it, deploy and hope. Sometimes that works. Often it fixes nothing, adds a new bug, and you
can't tell which, because you never saw the failure happen on your terms.

Debugging is an experiment: observe, form a hypothesis, test it. Each habit below makes one part of
that experiment cheaper.

## Habit 1: reproduce before you fix

**Why:** if you can't make the bug happen, you can't prove you fixed it.

A **reproduction** is the smallest set of steps or inputs that reliably triggers the failure. The best
form is an automated test that fails today:

```java
@Test
void orderWithZeroQuantityIsRejected() {
    var ex = assertThrows(IllegalArgumentException.class,
            () -> service.placeOrder(new OrderRequest("sku-1", 0)));
    assertEquals("quantity must be positive", ex.getMessage());
}
```

The loop is: **write the failing test → see it fail for the reason you expect → fix → see it pass
→ keep the test** so the bug can't quietly return.

If you can't reproduce it, collect more evidence (logs, inputs, timing, which instance, which
version) rather than guessing. Bugs that appear only "sometimes" usually depend on something you
haven't controlled yet: concurrency, data shape, configuration, or time.

## Habit 2: read the stack trace from the right end

A **stack trace** is the list of method calls that were active when an exception was thrown, newest
first.

```text
java.lang.IllegalStateException: Failed to process order 8812
    at com.shop.order.OrderService.place(OrderService.java:57)
    at com.shop.order.OrderController.create(OrderController.java:31)
    at org.springframework.web.method.support.InvocableHandlerMethod.doInvoke(...)
    (... dozens more framework frames ...)
Caused by: java.lang.NullPointerException: Cannot invoke "Address.city()" because
           the return value of "Customer.address()" is null
    at com.shop.pricing.ShippingCalculator.cost(ShippingCalculator.java:22)
    at com.shop.order.OrderService.place(OrderService.java:51)
    ... 49 more
```

How to read it:

1. **Find the last `Caused by:`.** That's the **root cause**, the original failure. The exceptions
   above it are wrappers added on the way up.
2. **Read its message.** Since Java 14, `NullPointerException` messages name exactly what was null.
   Here it's `Customer.address()`.
3. **Find the first frame in *your* code** (`com.shop...`), not in frameworks. Here that's
   `ShippingCalculator.java:22`.
4. `... 49 more` under a `Caused by:` means "the remaining frames are the same as in the trace
   above". Nothing is hidden.

**Rule:** bottom `Caused by` for *what* went wrong, your top frame for *where*.

## Habit 3: log so the next person can debug

**Why:** in production you can't attach a debugger. Logs are the evidence you'll have after the
fact.

```java
private static final Logger log = LoggerFactory.getLogger(OrderService.class);

log.info("Placing order orderId={} customerId={} items={}", orderId, customerId, items.size());
try {
    ...
} catch (PaymentException e) {
    log.error("Payment failed orderId={} provider={}", orderId, provider, e);  // e last → full stack trace
    throw e;
}
```

The habits that matter:

- **Use placeholders (`{}`), not string concatenation.** The message is only built if the level is
  enabled.
- **Include identifiers** (order ID, user ID, request ID) so you can find every line about one
  request.
- **Pass the exception as the last argument.** `log.error("failed: " + e.getMessage())` throws away
  the stack trace.
- **Log once, where you handle it.** Logging and rethrowing at every layer prints the same trace five
  times.
- **Use levels deliberately:** ERROR means someone must act; WARN means unexpected but handled; INFO
  means business events; DEBUG means detail you switch on while investigating.
- **Never log secrets:** passwords, tokens, full card numbers, personal data.
- **Add a correlation ID across services.** Put a request ID into SLF4J's **MDC** (a per-thread map
  of values added to every log line) at the edge, and pass it on to downstream calls, so one request
  can be followed through several services. Distributed tracing tools such as OpenTelemetry automate
  this.

## Habit 4: capture a heap dump when memory runs out

A **heap dump** is a snapshot file (`.hprof`) of every object in the JVM heap and what references
it. When a service dies with `OutOfMemoryError`, the dump shows *what* filled the heap.

Turn it on **before** the failure. You can't get the dump afterwards:

```text
java -Xmx512m \
     -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/var/dumps/ \
     -jar app.jar
```

You can also take one from a running process with `jcmd <pid> GC.heap_dump /tmp/app.hprof`. For a
hang rather than a memory problem, take a **thread dump** with `jcmd <pid> Thread.print` (or `jstack
<pid>`), which shows what every thread is doing and what lock it's waiting for.

Open the dump in a heap analyser such as Eclipse MAT or VisualVM, and look at the objects with the
largest **retained size** (the memory that would be freed if that object were gone). A typical
finding: a `static` map used as a cache that only ever grows.

Heap dumps contain everything in memory, including customer data and secrets. Store and share them
like production data.

## Habit 5: check `@Transactional` boundaries

**Context:** in Spring, a **transaction** is a unit of database work that either fully commits or
fully rolls back. Annotating a method with `@Transactional` asks Spring to start a transaction before
the method and commit it (or roll it back) after. Spring does this with a **proxy**: a wrapper object
around your bean that intercepts calls coming **from outside** the bean.

That one fact explains most "it wasn't saved" and "it didn't roll back" bugs:

```java
@Service
public class OrderService {

    public void placeAll(List<Order> orders) {
        for (Order o : orders) {
            place(o);              // self-call: goes straight to 'this', NOT through the proxy
        }
    }

    @Transactional
    public void place(Order o) { ... }   // so this runs WITHOUT a transaction here
}
```

Checklist when data isn't saved or isn't rolled back:

- **Self-invocation:** is the `@Transactional` method called from the same class? Then there's no
  transaction. Move it to another bean, or put the annotation on the outer method.
- **Visibility:** a `private` method is never proxied. Keep transactional methods public (the safe
  default).
- **Checked exceptions:** by default Spring rolls back only on unchecked exceptions
  (`RuntimeException`, `Error`). A checked exception commits unless you set `rollbackFor`.
- **Swallowed exceptions:** a `catch` inside the method that doesn't rethrow means Spring sees
  success and commits.
- **Other threads:** work handed to another thread (`@Async`, an executor) doesn't run in the
  caller's transaction.

To *see* the boundaries instead of guessing, set `logging.level.org.springframework.transaction=DEBUG`
(and `org.springframework.orm.jpa=DEBUG` for JPA). The log then shows each transaction being created,
committed or rolled back. In code, `TransactionSynchronizationManager.isActualTransactionActive()`
tells you whether you're inside one.

## Lab (~10 min)

Two experiments in one file: read a chained stack trace, then cause and capture an
`OutOfMemoryError`.

```java
import java.util.ArrayList;
import java.util.List;

public class DebugLab {

    record Customer(String name, String city) {}

    static final List<byte[]> CACHE = new ArrayList<>();   // a "cache" that never evicts

    static int shippingCost(Customer c) {
        return c.city().length() * 10;                     // NPE if city is null
    }

    static int placeOrder(Customer c) {
        try {
            return shippingCost(c);
        } catch (NullPointerException e) {
            throw new IllegalStateException("Failed to place order for " + c.name(), e);
        }
    }

    public static void main(String[] args) {
        if (args.length > 0 && args[0].equals("leak")) {
            for (int i = 0; ; i++) {
                CACHE.add(new byte[1024 * 1024]);          // 1 MB per entry, never removed
                if (i % 10 == 0) System.out.println("cached " + i + " MB");
            }
        }
        placeOrder(new Customer("Asha", null));
    }
}
```

**Part 1:** run `java DebugLab.java`. Find the last `Caused by:`, read the helpful NPE message, and
find the first frame in `DebugLab`. Confirm the wrapper exception points at `placeOrder` and the
root cause at `shippingCost`.

**Part 2:** run
`java -Xmx64m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=leak.hprof DebugLab.java leak`.
Watch it fail after a few tens of MB (the source launcher's compiler shares the 64 MB heap) with
`java.lang.OutOfMemoryError: Java heap space` and "Dumping heap to leak.hprof", then check that
`leak.hprof` was written. If you have VisualVM or Eclipse MAT installed, open it and find that
`DebugLab.CACHE` retains almost the entire heap.

**Part 3 (paper):** in the `OrderService` example above, list two different ways to make each
`place(o)` run in its own transaction, and one way to make the whole batch a single transaction.

## Gotchas

- **Trap: fixing before reproducing.** Write the failing test first. Without it you can't tell a fix
  from a coincidence.
- **Trap: reading only the top of a stack trace.** The root cause is the last `Caused by:`.
- **Trap: `log.error(e.getMessage())`.** It loses the stack trace. Pass `e` as the last argument.
- **Trap: enabling heap dumps after the crash.** Add `-XX:+HeapDumpOnOutOfMemoryError` and a
  `HeapDumpPath` with enough disk space to every production JVM up front.
- **Trap: `@Transactional` on a method called from the same class.** The proxy is bypassed and
  there's no transaction. Check with transaction DEBUG logging.
- **Trap: expecting rollback on a checked exception.** The default is to commit. Use
  `rollbackFor = Exception.class` if that's what you mean.

## Explain it in 2 minutes

*"A service intermittently loses writes and occasionally runs out of memory. How do you
investigate?"*

A good answer covers:

1. Reproduce first: find inputs or conditions that trigger it, ideally as a failing test.
2. For the lost writes, check transaction boundaries: self-invocation, checked exceptions,
   swallowed exceptions, async threads. Confirm with transaction DEBUG logs.
3. For the memory, make sure `-XX:+HeapDumpOnOutOfMemoryError` is on, then analyse the dump for the
   largest retained objects (often an unbounded cache or collection).
4. Use logs with correlation IDs to follow one failing request, and read the root `Caused by:`.
5. Fix, prove it with the reproduction, and add prevention (a test, an alert, bounded caches).

## Check yourself

1. In a chained stack trace, where is the root cause?
2. What's wrong with `log.error("Failed: " + e.getMessage());`?
3. Which JVM flag writes a heap dump on `OutOfMemoryError`, and why must it be set in advance?
4. Why does a `@Transactional` method called from another method of the same bean run without a
   transaction?
5. By default, does a checked exception thrown from a `@Transactional` method roll back?

### Answers

1. At the last `Caused by:` section, and in its first frame from your own code.
2. It concatenates eagerly and, more importantly, drops the stack trace. Use placeholders and pass
   `e` as the last argument.
3. `-XX:+HeapDumpOnOutOfMemoryError` (plus `-XX:HeapDumpPath`). The dump is written at the moment of
   failure, and a restart erases the evidence.
4. Transactions are applied by a proxy around the bean. A call on `this` doesn't go through the
   proxy.
5. No. It commits unless `rollbackFor` includes that exception.
