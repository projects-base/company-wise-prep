## Where we are

From B2 you can protect shared state with locks and avoid deadlock. So far, though, you have created every thread by hand with `new Thread(...)`. This lesson replaces that with **executors**, which are pools of reusable threads fed by a queue. It also covers the decision that matters most in production: how big the pool is and how big its queue is.

## The problem

Imagine a server that starts a new platform thread for every request. That has three costs:

1. **Creating a thread is not free.** Each platform thread is an operating-system thread with its own stack. Commonly about 1 MB of address space is reserved for that stack on 64-bit Linux by default, and the JVM and OS both have to set it up and tear it down.
2. **No upper limit.** A traffic spike means thousands of threads, and the machine spends its time switching between them instead of working. Eventually it fails with `OutOfMemoryError: unable to create native thread`.
3. **No control.** There is no single place to queue work, reject it, measure it or shut it down.

What we want is a fixed set of workers that take tasks from a queue.

## Executors: submit tasks, not threads

An **executor** accepts tasks and decides which thread runs them. `ExecutorService` is the interface you use day to day.

```java
try (ExecutorService pool = Executors.newFixedThreadPool(4)) {   // Java 19+: close() waits for tasks
    for (int i = 0; i < 10; i++) {
        int id = i;
        pool.execute(() -> System.out.println(id + " on " + Thread.currentThread().getName()));
    }
}
```

You will see names like `pool-1-thread-3` repeating. Four threads have handled ten tasks, because each thread loops: take a task from the queue, run it, take the next.

## Getting results back: `Future`

`execute(Runnable)` is fire-and-forget. `submit(Callable<T>)` returns a **`Future<T>`**, which is a handle to a result that will arrive later.

```java
Future<Integer> f = pool.submit(() -> slowSquare(7));
Integer result = f.get(2, TimeUnit.SECONDS);   // waits; throws TimeoutException if too slow
```

If the task throws, `get()` throws an `ExecutionException` that wraps the original exception. The two methods treat failures very differently:

- **With `execute`**, an exception kills that worker thread (the pool replaces it) and is printed by the uncaught-exception handler.
- **With `submit`**, the exception is stored inside the `Future`. **If nobody calls `get()`, the failure disappears silently.** This is a common production mystery.

`f.cancel(true)` interrupts the task if it is already running, which brings in everything B1 taught about interruption.

## Inside `ThreadPoolExecutor`

Every factory method in `Executors` builds a `ThreadPoolExecutor` with these settings:

```java
new ThreadPoolExecutor(
    corePoolSize,      // threads kept alive even when idle
    maximumPoolSize,   // upper limit on threads
    keepAliveTime, unit,   // how long threads above core may sit idle before dying
    workQueue,         // where tasks wait
    threadFactory,     // how threads are created (names, daemon flag)
    rejectionHandler); // what to do when everything is full
```

When you submit a task, the executor tries these steps in order:

```text
submit(task)
   │
   ├─ fewer than core threads? ──────────── yes ──► start a new thread for it
   │
   ├─ queue accepts it? ─────────────────── yes ──► wait in the queue
   │
   ├─ fewer than max threads? ───────────── yes ──► start a new (non-core) thread
   │
   └─ otherwise ──────────────────────────────────► rejection handler
```

The surprising consequence is that **threads beyond core are created only when the queue is full.** If the queue is unbounded, it is never full, so `maximumPoolSize` has no effect.

There are four built-in rejection handlers:

- `AbortPolicy` (the default) throws `RejectedExecutionException`.
- `CallerRunsPolicy` runs the task on the thread that submitted it. That slows the submitter down, which is natural **backpressure**: the consumer pushing back on the producer so that it slows down.
- `DiscardPolicy` silently drops the new task.
- `DiscardOldestPolicy` drops the oldest queued task.

## What the `Executors` shortcuts really build

| Factory | core / max | Queue | Risk |
|---|---|---|---|
| `newFixedThreadPool(n)` | n / n | `LinkedBlockingQueue`, **unbounded** | queue grows until the heap runs out |
| `newSingleThreadExecutor()` | 1 / 1 | unbounded | same |
| `newCachedThreadPool()` | 0 / `Integer.MAX_VALUE` | `SynchronousQueue` (no capacity) | thread count grows without limit |
| `newScheduledThreadPool(n)` | n / unbounded | delay queue, unbounded | queue growth |

Rule: **for any server work whose load comes from outside, build the `ThreadPoolExecutor` yourself**, with a bounded queue, a rejection policy you chose deliberately, and named threads. The shortcuts are fine for scripts and tests.

## Sizing the pool

How many threads should a pool have? It depends on what the tasks spend their time doing.

**CPU-bound tasks**, such as parsing, hashing or compressing, are busy the whole time. More threads than cores only adds switching overhead. Use about the number of cores: `Runtime.getRuntime().availableProcessors()`, sometimes plus one.

**I/O-bound tasks**, such as database or HTTP calls, spend most of their time waiting. While one waits, another can use the core. *Java Concurrency in Practice* gives this formula:

```text
threads ≈ cores × target CPU utilisation × (1 + wait time / compute time)

e.g. 8 cores, aim for 100%, each task waits 90 ms and computes 10 ms
     8 × 1.0 × (1 + 90/10) = 80 threads
```

**Little's law** is a second way to check the number. The average number of requests in flight equals the arrival rate multiplied by the average time each one takes. For example, 400 requests per second × 0.05 s = 20 in flight, so you need at least 20 threads, plus headroom.

Treat both formulas as a starting point, then measure under load. Also remember the resources further downstream. A pool of 200 threads sharing a database connection pool of 20 connections simply means 180 threads waiting for a connection.

## Shutting down

- `shutdown()` stops accepting new tasks and lets the queued ones finish.
- `awaitTermination(timeout)` waits for those tasks to finish.
- `shutdownNow()` interrupts the running tasks and returns the tasks that never started.
- `close()` (Java 19+) does `shutdown()` and then waits, which is what lets `try (pool) { ... }` work.

A pool that is never shut down keeps its non-daemon threads alive, and the JVM will not exit.

## ForkJoinPool and work stealing

`ForkJoinPool` is built for *divide-and-conquer*: split a big task into halves, solve the halves in parallel, then combine the results. Each worker has its own **deque**, a double-ended queue. A worker pushes and pops its own subtasks at one end. An idle worker **steals** from the other end of a busy worker's deque. Stealing from the opposite end keeps contention low.

```java
class SumTask extends RecursiveTask<Long> {
    final int[] a; final int lo, hi;
    SumTask(int[] a, int lo, int hi) { this.a = a; this.lo = lo; this.hi = hi; }
    protected Long compute() {
        if (hi - lo <= 10_000) { long s = 0; for (int i = lo; i < hi; i++) s += a[i]; return s; }
        int mid = (lo + hi) >>> 1;
        SumTask left = new SumTask(a, lo, mid);
        left.fork();                                        // push left half onto my deque
        return new SumTask(a, mid, hi).compute() + left.join();
    }
}
// long total = ForkJoinPool.commonPool().invoke(new SumTask(arr, 0, arr.length));
```

The **common pool** (`ForkJoinPool.commonPool()`) is shared by the whole JVM. Parallel streams use it, and so do `CompletableFuture`'s `...Async` methods when you pass no executor (B5). By default it has about one thread fewer than there are cores. **Never put blocking I/O on it**, because a few blocked calls can stall every parallel stream in the application.

## Lab (~10 min)

You will make a pool run out of memory, then fix it. Save this as `PoolOverload.java` and run it with a small heap: `java -Xmx64m PoolOverload.java`.

```java
import java.util.concurrent.*;

public class PoolOverload {
    static final boolean BOUNDED = false;   // flip to true for the fix

    public static void main(String[] args) throws Exception {
        ThreadPoolExecutor pool = BOUNDED
            ? new ThreadPoolExecutor(2, 2, 0, TimeUnit.SECONDS,
                  new ArrayBlockingQueue<>(20),                 // bounded queue
                  new ThreadPoolExecutor.CallerRunsPolicy())    // full? the submitter runs it
            : (ThreadPoolExecutor) Executors.newFixedThreadPool(2); // hidden unbounded queue

        long start = System.nanoTime();
        try (pool) {                                            // close() waits for queued tasks
            for (int i = 1; i <= 300; i++) {
                byte[] body = new byte[1_000_000];              // a 1 MB "request body"
                pool.execute(() -> handle(body));
                if (i % 25 == 0) {
                    long usedMb = (Runtime.getRuntime().totalMemory() - Runtime.getRuntime().freeMemory()) >> 20;
                    System.out.printf("submitted %4d  queued %4d  heap used %3d MB%n",
                                      i, pool.getQueue().size(), usedMb);
                }
            }
        }
        System.out.printf("all done in %d ms%n", (System.nanoTime() - start) / 1_000_000);
    }

    static void handle(byte[] body) {
        try { Thread.sleep(100); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        if (body.length == 0) System.out.println("never");     // keep the body "in use"
    }
}
```

What you should observe:

1. With `BOUNDED = false`, the producer adds about 1 MB per task far faster than two workers can drain them (about 20 per second). `queued` climbs, heap usage climbs, and within seconds you get `OutOfMemoryError: Java heap space`. Every queued task holds on to its body. **An unbounded queue turns a traffic spike into a crash instead of slower responses.**
2. With `BOUNDED = true`, `queued` never exceeds 20 and heap usage stays flat. When the queue is full, `CallerRunsPolicy` makes `main` run tasks itself, which slows down submission. That is backpressure. All 300 tasks finish.
3. **Try it:** switch to `new ThreadPoolExecutor.AbortPolicy()`. Now you get `RejectedExecutionException` instead. In a web service, that would become a fast `503 Service Unavailable` response, which is often the right behaviour.

## Gotchas

- **`newFixedThreadPool` has an unbounded queue.** Under sustained overload the result is an OOM. Use a bounded queue and an explicit rejection policy.
- **`maximumPoolSize` is ignored with an unbounded queue**, because extra threads start only when the queue is full.
- **Exceptions from `submit()` are swallowed** until someone calls `get()`. Either call `get()`, or wrap tasks so that they log their own failures.
- **Blocking I/O on the common pool** starves parallel streams and default async `CompletableFuture`s. Give I/O its own executor.
- **`ThreadLocal` in pools.** Threads are reused, so values leak from one task into the next (for example a user context). Clear them in `finally`.
- **Forgetting to shut down.** Non-daemon pool threads keep the JVM alive. Use `try (pool)`, or call `shutdown()` and then `awaitTermination()`.

## In interviews

Executors show up inside design questions. [Design a Message Queue (producer-consumer)](#/q/design-message-queue) and [Multi-Threaded Buffered Queue](#/q/design-bounded-blocking-queue) both probe bounded queues and backpressure. [Single-Threaded CPU](#/q/single-threaded-cpu) is a scheduling simulation built on a priority queue, which is useful practice for reasoning about task queues.

Typical follow-ups:

- **"How would you size the thread pool for this service?"** Separate CPU-bound work (about the number of cores) from I/O-bound work (cores × (1 + wait/compute)), check the answer with Little's law, mention downstream limits such as connection pools, and say that you would load-test.
- **"What happens when the pool is saturated?"** Walk through core → queue → max → reject, explain why the queue must be bounded, and choose a rejection policy: `CallerRunsPolicy` for backpressure inside one process, or `AbortPolicy` mapped to HTTP 503 at the edge.

## Explain it in 2 minutes

*"Why use a thread pool, and how do you configure one for a web service?"*

- Threads are expensive and must have an upper limit. A pool reuses N threads that take tasks from a queue.
- The submit flow is core threads → queue → extra threads up to max → rejection. Extra threads start only when the queue is full.
- The `Executors` shortcuts hide unbounded queues or unbounded threads, so build the `ThreadPoolExecutor` yourself.
- Size it to about the number of cores for CPU-bound work and cores × (1 + W/C) for I/O-bound work, checked with Little's law and a load test.
- Choose a rejection policy deliberately and shut the pool down cleanly.

## Check yourself

1. Core 4, max 16, unbounded queue, 1,000 simultaneous slow tasks. How many threads run?
2. What does `CallerRunsPolicy` do, and why is it called backpressure?
3. A task submitted with `submit()` throws, and nobody calls `get()`. What happens?
4. Why should blocking I/O not run on `ForkJoinPool.commonPool()`?
5. Roughly how many threads would you start with for an 8-core machine whose tasks wait 40 ms and compute 10 ms?

### Answers

1. Four. The queue never fills, so the pool never grows past the core size.
2. When the queue is full, the submitting thread runs the task itself. It cannot submit more while it is busy, so the producer slows to the rate the consumers can handle.
3. The exception is stored in the `Future` and never reported. It is lost silently.
4. The common pool is small (about cores − 1) and shared JVM-wide. Blocked threads starve parallel streams and default async tasks.
5. 8 × (1 + 40/10) = 40, as a starting point to load-test.
