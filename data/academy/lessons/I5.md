## Where we are

JAVA-CONC-1 gave you threads inside one JVM; WEB-API-2 showed that every socket is a file
descriptor the operating system hands out. Both quietly rested on the OS. This lesson opens that
layer: what Linux does with your process, its threads, memory and files, and the commands you run
when someone says "the box is slow". DIST-SYS-3 made services survive failures; this lesson is how
you find out *why* one is failing.

## The problem

02:10, an alert: Orders p99 latency is up from 80 ms to 4 s and one pod restarted twice. The
dashboards say "CPU high" and "memory high", nothing more. You have SSH (or `kubectl exec`) into one
machine. Which process? Which thread? Is it CPU, disk, network or memory? Was the restart a Java
`OutOfMemoryError` or the kernel killing the process? Without the OS model and a dozen commands, you
guess. With them, you have an answer in ten minutes.

## Process vs thread

A **process** is a running program with its own **virtual address space** (its private view of
memory), its own open files and its own process id (PID). A **thread** is a path of execution inside
a process; all threads of a process share its memory and file descriptors, and each has only its
own stack and registers.

```text
process orders (PID 4100)  ── one address space: heap, metaspace, code, open sockets
   ├─ thread main            (TID 4100)  own stack
   ├─ thread http-nio-8080-exec-1 (TID 4123)  own stack
   └─ thread G1 Conc#0       (TID 4107)  own stack
```

On Linux both are "tasks" to the kernel; a thread is a task that shares memory with its siblings, so
each thread has its own **TID** (thread id) and is scheduled independently. Every Java **platform
thread** is one OS thread, one to one: `new Thread()` asks the kernel for a real thread. That is why
`top` can show you per-thread CPU for a JVM. Virtual threads (JAVA-CONC-1) are different: many of
them run on a few carrier platform threads, so the OS sees only the carriers.

Why it matters:

- **Isolation.** One process crashing does not corrupt another; one thread corrupting shared state
  corrupts all of them (the race conditions of JAVA-CONC-1).
- **Context switch cost.** A **context switch** is the kernel saving one task's registers and
  loading another's. Switching between threads of the same process is cheaper than between
  processes, because the memory mappings stay the same, but neither is free: thousands of runnable
  threads spend real CPU just being switched, and caches go cold.
- **Communication.** Threads share memory directly; processes need pipes, sockets or shared memory.

## Scheduling, cores and load average

The **scheduler** decides which runnable task gets each CPU **core** next. A 4-core machine runs at
most 4 tasks at the same instant; the rest wait in the run queue.

**Load average** (the three numbers in `uptime` and `top`) is the average number of tasks that are
running or waiting to run over the last 1, 5 and 15 minutes. On Linux it also counts tasks in
**uninterruptible sleep** (state `D`, usually waiting on disk or NFS). Read it against the core
count: a load of 4 on 4 cores is full; 12 on 4 cores means tasks are queueing. A rising 1-minute
value with a flat 15-minute one means it just started.

CPU time is split into kinds, and the split tells you where to look:

| Column | Meaning | High usually means |
|---|---|---|
| `us` user | running your code (and the JVM's) | hot loop, GC, heavy JSON/regex |
| `sy` system | the kernel working for you | many syscalls, context switches, small I/O |
| `wa` iowait | idle, but waiting for disk I/O | slow or saturated disk, heavy logging, swap |
| `st` steal | the hypervisor gave your CPU to another VM | noisy neighbour on a cloud VM |
| `id` idle | nothing to do | |

High load with low `us` and high `wa` is a disk problem, not a code problem.

## Virtual memory, RSS and why RSS > -Xmx

Every process sees a large, private **virtual** address space; the kernel maps pages of it to
physical RAM only when they are touched. Two numbers follow:

- **VSZ / VIRT**: virtual memory reserved. Large and mostly meaningless for a JVM (it reserves the
  whole max heap up front, plus more).
- **RSS / RES** (resident set size): physical RAM the process actually occupies now. This is what a
  container memory limit is measured against (strictly, the cgroup counts the process's memory plus
  some page cache it caused).

A JVM's RSS is always more than its heap, because the heap is only one area (JAVA-JVM-2):

```text
RSS ≈ heap in use (≤ -Xmx)
    + metaspace (class metadata)
    + thread stacks (each platform thread reserves -Xss, 1 MB by default on 64-bit Linux;
                     only touched pages count)
    + code cache (JIT-compiled code)
    + GC data structures
    + direct ByteBuffers and other native memory (Netty, compression, JNI)
```

So a container with `-Xmx` equal to its limit will be killed even with a healthy heap. Measure
instead of guessing: start with `-XX:NativeMemoryTracking=summary` and run
`jcmd <pid> VM.native_memory summary`.

## Page cache and swap

Linux uses otherwise free RAM as **page cache**: copies of recently read or written file blocks, so
the next read is from memory. That is why `free -m` on a healthy server shows little "free"; look at
**available**, which counts cache the kernel can drop instantly. Low "free" is normal; low
"available" is not.

**Swap** is disk space used to hold memory pages that do not fit in RAM. For a JVM it is poison: a
GC must walk the whole heap, and if parts of it are on disk a pause measured in milliseconds becomes
seconds. Servers running JVMs usually run with swap off or with low swappiness, and Kubernetes nodes
traditionally require swap off. Non-zero `si`/`so` in `vmstat` means the box is swapping now.

## OOM killer vs OutOfMemoryError

Two different things run out, and they fail differently:

```text
Java heap full           → JVM throws java.lang.OutOfMemoryError: Java heap space
                           a stack trace in your log; the process may keep running, badly
RAM / cgroup limit full  → kernel OOM killer picks a process and sends SIGKILL
                           no Java stack trace, no shutdown hooks; exit code 137 (128 + 9)
```

The **OOM killer** is the kernel's last resort when memory cannot be satisfied; in a container it
fires when the cgroup exceeds its memory limit (Kubernetes reports `OOMKilled`). Evidence lives
outside the JVM: `dmesg -T | grep -i -E "killed process|out of memory"` or
`journalctl -k | grep -i oom` on a host, `kubectl describe pod` in Kubernetes. Heap OOMs are
JAVA-JVM-7's territory (heap dumps, leaks); a 137 means look at RSS and the limit.

## File descriptors and ulimit

A **file descriptor** (fd) is a small integer the kernel gives a process for each open file, socket,
pipe or epoll handle (WEB-API-2). Each process has a cap, set by **ulimit** (`ulimit -n` shows the
soft limit). Hit it and every `open()` and `accept()` fails with `java.io.IOException: Too many open
files`, which looks like a network outage but is a leak: streams or HTTP responses not closed, or
connection pools sized past the limit.

```bash
ls /proc/<pid>/fd | wc -l                 # how many are open now
grep "open files" /proc/<pid>/limits      # this process's actual limit
lsof -p <pid> | awk '{print $5}' | sort | uniq -c | sort -rn   # by type: REG, IPv4, sock...
```

A count that only climbs is a leak; raising the limit just moves the crash. In systemd services the
limit is `LimitNOFILE=`; in containers it is inherited from the runtime.

## Signals: how processes are told things

A **signal** is an asynchronous notification the kernel delivers to a process. Three matter:

| Signal | Number | Can the process handle it? | Used for |
|---|---|---|---|
| `SIGTERM` | 15 | yes | "please stop": JVM runs shutdown hooks; Spring Boot drains requests |
| `SIGKILL` | 9 | no, the kernel just removes the process | `kill -9`, OOM killer, grace period expired |
| `SIGQUIT` | 3 | yes | the JVM prints a thread dump to stdout and keeps running |

`kill <pid>` sends `SIGTERM` by default, and it is what Kubernetes and systemd send first. Reach for
`kill -9` only after `SIGTERM` failed, because it skips connection draining, transaction rollback and
Kafka offset commits. `kill -3 <pid>` is the oldest way to get a thread dump (LIFECYCLE-2 shows how to
read one); note it goes to the JVM's stdout, i.e. the container log, not your terminal.

## Namespaces and cgroups

Two kernel features make a process feel like it has a machine to itself:

- A **namespace** gives a process its own view of a global resource: PID (it sees itself as PID 1),
  network (own interfaces and ports), mount (own filesystem tree), UTS (own hostname), IPC, user.
- A **cgroup** (control group) limits and accounts for what a group of processes may use: CPU
  quota, memory limit, I/O, number of PIDs. The memory OOM kill and CPU throttling above are cgroup
  enforcement.

Put both around a process, add a packaged filesystem, and you have a container. Inside it, `top`
may still show the host's totals in places; the JVM reads the cgroup files, which is why it is
container-aware.

## The "box is slow" toolkit

Work outside in: is it the machine, which process, which thread, which resource.

```bash
uptime                      # load average vs cores (nproc)
top                         # press 1: per-core; P: sort by CPU; M: by memory; H: show threads
top -H -p <pid>             # threads of one process; the PID column now shows TIDs
ps -eo pid,ppid,stat,%cpu,%mem,rss,etime,cmd --sort=-%cpu | head
ps -L -p <pid> -o tid,pcpu,comm   # threads with CPU; comm shows the Java thread name (truncated to 15 chars)
free -m                     # total, used, free, buff/cache, available (trust available)
vmstat 1 5                  # r: run queue, b: blocked (D), si/so: swap, us sy id wa st
iostat -x 1 3               # per disk: r/s w/s, await (ms per I/O), %util near 100 = saturated
df -h                       # disk full? (logs, heap dumps) ; df -i for inodes
du -sh /var/log/* | sort -h # what is filling it
ss -tanp                    # TCP sockets: state, Recv-Q/Send-Q, peer, owning process
ss -s                       # counts per state: many TIME-WAIT or CLOSE-WAIT is a clue
lsof -p <pid>               # every open file and socket of the process
curl -v https://payments.internal/actuator/health   # DNS, TCP connect, TLS, status, headers
dig payments.internal       # does the name resolve, to what, with which TTL
tail -f app.log | grep --line-buffered ERROR
less +F app.log             # follow; Ctrl+C to search with /pattern, F to follow again
journalctl -u orders --since "10 min ago"     # logs of a systemd service
jcmd <pid> Thread.print     # thread dump (same as jstack <pid>)
jcmd <pid> GC.heap_info     # heap now; JAVA-JVM-7 for leaks, JAVA-JVM-8 for profilers
```

Reading the clues: `Recv-Q` growing on a listening socket means the app is not accepting fast enough;
many `CLOSE-WAIT` sockets mean *your* code is not closing connections the peer already closed (a
leak); `TIME-WAIT` is normal after closes (WEB-API-2). In `iostat`, high `await` with `%util` near
100 means the disk is the bottleneck. In `vmstat`, an `r` column consistently above the core count
is CPU saturation.

## From hot thread to line of code

The single most useful trick for "CPU at 100%":

```text
1. top                     → PID 4100 (java) at 99%
2. top -H -p 4100          → TID 4123 at 98%
3. printf '%x\n' 4123      → 101b
4. jstack 4100 | grep -A 15 'nid=0x101b'   (older JDKs print nid in hex)
   jstack 4100 | grep -A 15 '\[4123\]'     (recent JDKs, including 21, print the decimal id
                                             in brackets and as nid; check which you have)
5. read that thread's stack → the method spinning
```

Take two or three dumps a few seconds apart: a thread in the same frames each time is the culprit;
one that moves around is just busy. If the hot TIDs are named `GC Thread#…` or `G1 Conc#…`, the
problem is memory pressure, not your loop: go to JAVA-JVM-7.

## Lab (~10 min)

**Find the thread that is burning CPU.** Save as `HotThread.java`:

```java
public class HotThread {
    public static void main(String[] args) throws InterruptedException {
        Thread hot = new Thread(HotThread::spin, "price-recalc");   // the culprit, named on purpose
        hot.start();
        for (int i = 1; i <= 3; i++) {
            Thread idle = new Thread(HotThread::nap, "idle-worker-" + i);
            idle.start();
        }
        System.out.println("PID " + ProcessHandle.current().pid() + " running; Ctrl+C to stop");
        hot.join();
    }

    private static void spin() {
        long x = 0;
        while (!Thread.currentThread().isInterrupted()) {
            x += System.nanoTime() % 7;                     // pure CPU work, never blocks
            if (x == Long.MIN_VALUE) System.out.println(x); // keeps the JIT from removing the loop
        }
    }

    private static void nap() {
        try {
            Thread.sleep(Long.MAX_VALUE);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

On Linux (or WSL, or a container: `docker run --rm -it -v "$PWD":/w -w /w eclipse-temurin:21-jdk bash`,
then `apt-get update && apt-get install -y procps` if `top` is missing):

1. `java HotThread.java &` and note the PID it prints.
2. `top -H -p <pid>`: one TID near 100%, the rest near 0. Press `q`.
3. `ps -L -p <pid> -o tid,pcpu,comm | sort -k2 -rn | head -3`: the hot TID with the name
   `price-recalc`, because Java sets the OS thread name.
4. `printf '%x\n' <tid>`, then `jstack <pid> | grep -A 4 price-recalc`. Confirm the bracketed
   number (and `nid`, in decimal or hex depending on JDK) matches the TID, the state is `RUNNABLE`
   and the top frame is `HotThread.spin`.
5. `kill -3 <pid>` and watch the dump appear on the program's own output. Then `kill <pid>`.

**Windows / macOS without WSL or Docker:** `jcmd` lists JVMs; `jstack <pid>` works as is, and each
thread line shows `cpu=` time, so two dumps a few seconds apart reveal the thread whose CPU time grows.
On Windows, Process Explorer shows per-thread CPU by TID; on macOS, use Activity Monitor or `top`
for the process and the `cpu=` trick for the thread.

**Break it:** start the program with 4 copies of the hot thread on a 2-core container
(`docker run --cpus=2 ...`) and watch load average climb past 2 in `uptime` while `us` saturates.

## Gotchas

- **Reading "free" memory as available.** Page cache makes "free" tiny on every healthy box; use
  the `available` column.
- **Sizing `-Xmx` to the container limit.** RSS includes metaspace, stacks, code cache and direct
  buffers; the kernel kills at the limit with exit 137 and no stack trace. Leave headroom.
- **`kill -9` as the first move.** It skips shutdown hooks and graceful drain; send `SIGTERM`, wait,
  then escalate. And take a thread dump *before* killing, or the evidence is gone.
- **Raising `ulimit -n` to fix "Too many open files".** If the fd count only grows, it is a leak;
  find it with `lsof -p` (look for thousands of the same peer or `CLOSE_WAIT`).
- **Load average without core count.** A load of 8 is idle on 64 cores and on fire on 2. Divide
  by `nproc`, and check `wa`: disk waits inflate load too.
- **Matching TIDs to `nid` in the wrong base.** Older JDKs print hex, recent ones decimal; check the
  dump format before concluding the thread is missing.

## Explain it in 2 minutes

*"A Linux box running your Spring Boot service is slow. What do you do?"*

- Load average against core count; `top` for the CPU split: `us`, `sy`, `wa`, `st`.
- Hot process, then hot thread with `top -H -p`, TID to hex, `jstack` to find the code.
- Memory: `free -m` (available), RSS vs heap, swap in `vmstat`, OOM killer in `dmesg`.
- Disk: `iostat -x` await and util, `df -h` for a full disk.
- Network and files: `ss -tanp` states and queues, `lsof -p` for fd leaks, `curl -v` and `dig`.
- Evidence first (dumps, logs), then `SIGTERM`, never `kill -9` first.

## Check yourself

1. Why can `top -H` show per-thread CPU for a JVM, and would it work the same for virtual threads?
2. A 4-core box has load average 9 with `us` 10% and `wa` 70%. What is the likely bottleneck?
3. A container limited to 1 GiB runs with `-Xmx1g` and gets killed with exit 137. Explain.
4. What is the difference between `kill`, `kill -9` and `kill -3` on a JVM?
5. Your service logs "Too many open files". What two commands do you run first, and what are you
   looking for?

### Answers

1. Each platform thread is a real OS thread with its own TID, scheduled by the kernel. Virtual
   threads are multiplexed onto a few carrier threads, so the OS sees only the carriers.
2. Disk I/O: tasks are waiting on I/O (and `D`-state tasks count in load). Check `iostat -x`.
3. RSS is heap plus metaspace, thread stacks, code cache and native memory; it crossed the cgroup
   limit, so the kernel's OOM killer sent `SIGKILL` (128 + 9).
4. `kill` sends `SIGTERM`: shutdown hooks and graceful drain. `kill -9` is `SIGKILL`: immediate,
   no cleanup. `kill -3` is `SIGQUIT`: the JVM prints a thread dump and keeps running.
5. `ls /proc/<pid>/fd | wc -l` against `grep "open files" /proc/<pid>/limits`, and `lsof -p <pid>`
   to see which kind of fd is piling up (sockets to one peer, `CLOSE_WAIT`, unclosed files).
