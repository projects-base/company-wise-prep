## Where we are

From JAVA-FUND-5 you can read a signature like `<T, R> List<R> map(List<T> in, Function<? super T, ? extends R> f)`,
and from JAVA-FUND-6 you know what `ArrayList` and `HashMap` do inside. This lesson adds the other half of modern Java:
passing *behaviour* as a value (lambdas), processing collections as pipelines (Streams), and saying "maybe absent"
without `null` (Optional). Interviewers use this to check whether you write Java 8+ or Java 5 with newer syntax.

## The problem

You have a list of orders and need the total value of paid orders per customer. The pre-Java-8 version:

```java
Map<String, Long> totals = new HashMap<>();
for (Order o : orders) {
    if (o.status() == Status.PAID) {
        Long current = totals.get(o.customer());
        totals.put(o.customer(), current == null ? o.amount() : current + o.amount());
    }
}
```

Every line is *how* (loop, check, get, null-check, put). The *what* ("sum amount by customer, for paid orders") is
buried. And when you want to reuse "is paid" as a rule, you have nowhere to put it except another method, because
before Java 8 you could not pass a piece of code to a method without writing an anonymous class:

```java
Collections.sort(names, new Comparator<String>() {
    @Override
    public int compare(String a, String b) {
        return Integer.compare(a.length(), b.length());
    }
});
```

Five lines of ceremony for one expression. Lambdas remove the ceremony; Streams remove the loop bookkeeping.

## Lambdas: a function written inline

A **lambda** is an anonymous function: parameters, an arrow, a body.

```java
Collections.sort(names, (a, b) -> Integer.compare(a.length(), b.length()));
```

Shapes you will see: `() -> 42`, `s -> s.isBlank()`, `(a, b) -> a + b`, and a block body
`x -> { log(x); return x * 2; }`. Parameter types are usually inferred.

**The rule:** a lambda is just a compact way to implement a single abstract method. Which method? That is the next idea.

## Functional interfaces: the type of a lambda

A lambda has no type of its own. It takes the type of whatever the context expects, and that type must be a
**functional interface**: an interface with exactly one abstract method (default and static methods do not count).
`Comparator<T>` has one abstract method, `compare`, so a lambda fits it.

```java
@FunctionalInterface                  // optional; makes the compiler reject a second abstract method
interface PriceRule {
    long apply(long cents);
}

PriceRule tenPercentOff = cents -> cents * 90 / 100;
```

You rarely need your own, because `java.util.function` ships the common shapes:

| Interface | Method | Shape | Typical use |
|---|---|---|---|
| `Function<T, R>` | `R apply(T)` | T in, R out | `map` |
| `Predicate<T>` | `boolean test(T)` | T in, yes/no out | `filter` |
| `Consumer<T>` | `void accept(T)` | T in, nothing out | `forEach` |
| `Supplier<T>` | `T get()` | nothing in, T out | lazy defaults, factories |
| `UnaryOperator<T>` | `T apply(T)` | T in, T out | `replaceAll` |
| `BinaryOperator<T>` | `T apply(T, T)` | two T in, T out | `reduce`, merge functions |
| `BiFunction<T, U, R>` | `R apply(T, U)` | two in, one out | `Map.merge`, `compute` |

There are primitive versions (`IntPredicate`, `ToLongFunction<T>`, `IntBinaryOperator`) that avoid boxing an `int`
into an `Integer` on every call. Functional interfaces also compose: `isPaid.and(isLarge)`, `isPaid.negate()`,
`trim.andThen(toUpper)`, `Comparator.comparing(Order::customer).thenComparing(Order::amount)`.

## Capture: "effectively final"

A lambda can use local variables from the surrounding method. This is called **capturing** them.

```java
int threshold = 100;
Predicate<Order> isLarge = o -> o.amount() > threshold;   // fine
// threshold = 200;   // uncomment and the line above stops compiling
```

A captured local must be **effectively final**: never reassigned after initialisation, even if you did not write
`final`. The reason: the lambda gets a *copy* of the value, and it may run later or on another thread, after the
method has returned and its stack frame is gone (remember from JAVA-JVM-2 that locals live on the stack). If you
could reassign the variable, the copy and the original would silently disagree.

Fields are different: a lambda reads `this.count` through the `this` reference, so it sees changes, which means it
can also race on them. The classic workaround `int[] counter = {0}; list.forEach(x -> counter[0]++);` compiles
(the array reference is final, its contents are not), but it is a smell and is unsafe in parallel streams. Use
`count()` or a collector instead.

## Method references: a lambda that only calls a method

When a lambda just forwards to an existing method, a **method reference** says the same thing more directly:

| Kind | Method reference | Equivalent lambda |
|---|---|---|
| Static method | `Integer::parseInt` | `s -> Integer.parseInt(s)` |
| Method of a particular object | `System.out::println` | `x -> System.out.println(x)` |
| Instance method of an arbitrary object of a type | `String::toUpperCase` | `s -> s.toUpperCase()` |
| Constructor | `ArrayList::new` | `() -> new ArrayList<>()` |

The third row confuses people: the first lambda parameter becomes the receiver. `String::compareTo` fits a
`Comparator<String>` because `(a, b) -> a.compareTo(b)`.

## Streams: a pipeline over a source

A **stream** is a sequence of elements you process with a chain of operations. It is *not* a collection: it stores
nothing, and it can be consumed only once. Here is the problem from the top, as a stream:

```java
Map<String, Long> totals = orders.stream()                       // source
        .filter(o -> o.status() == Status.PAID)                    // intermediate
        .collect(Collectors.groupingBy(Order::customer,            // terminal
                 Collectors.summingLong(Order::amount)));
```

Every pipeline has three parts:

```text
source ──► intermediate op ──► intermediate op ──► terminal op
(list,      filter, map,        sorted, distinct,   collect, forEach, count,
 array,     flatMap, peek,      limit, skip         reduce, findFirst, anyMatch,
 Stream.of) mapToInt                                toList, min/max
            returns a Stream    returns a Stream    returns a result (or void)
```

**Intermediate** operations return a new stream and do no work yet. A **terminal** operation produces a result and
triggers the work. After the terminal operation the stream is spent; reusing it throws `IllegalStateException`.

## Laziness: nothing runs until the terminal operation

```java
Stream<String> s = Stream.of("a", "bb", "ccc")
        .filter(x -> { System.out.println("filter " + x); return x.length() > 1; });
System.out.println("built");      // printed first: filter has not run
s.findFirst();                    // now prints: filter a, filter bb  (and stops)
```

Two things happen here:

- **Lazy:** building the pipeline does nothing. The terminal operation pulls elements through.
- **Element by element, short-circuiting:** each element goes through the whole chain before the next one starts
  (not "filter everything, then map everything"). `findFirst`, `anyMatch` and `limit` stop as soon as they can,
  so `"ccc"` is never examined.

The exception is a **stateful** operation like `sorted()` or `distinct()`: `sorted` must see every element
before it can emit the first, so it buffers the whole stream.

**The rule:** read a pipeline as "for each element, do this chain", and expect no side effects until the terminal op.

## Collectors: the interview favourites

`collect` takes a **collector**, a recipe for folding elements into a container. Assume
`record Order(String customer, String city, long amount, Status status, List<String> items) {}`.

```java
// group: Map<city, List<Order>>
Map<String, List<Order>> byCity = orders.stream().collect(groupingBy(Order::city));

// group with a downstream collector: Map<city, count>
Map<String, Long> countByCity = orders.stream().collect(groupingBy(Order::city, counting()));

// partition: always exactly two keys, true and false
Map<Boolean, List<Order>> bigOrNot = orders.stream().collect(partitioningBy(o -> o.amount() > 1_000));

// toMap needs a merge function if keys can repeat
Map<String, Long> maxByCustomer = orders.stream()
        .collect(toMap(Order::customer, Order::amount, Math::max));

// sorted keys: pass a map factory
Map<String, Long> sorted = orders.stream()
        .collect(groupingBy(Order::city, TreeMap::new, counting()));

// join strings
String csv = orders.stream().map(Order::customer).distinct().collect(joining(","));
```

The trap interviewers wait for: `toMap(keyFn, valueFn)` **without** a merge function throws
`IllegalStateException: Duplicate key` the first time two elements map to the same key. Add a third argument
(`(a, b) -> a`, `Long::sum`, `Math::max`) whenever duplicates are possible. Also, `toMap` rejects `null` values
with a `NullPointerException`.

## flatMap and reduce

`map` turns one element into one element. **`flatMap`** turns one element into a *stream* of elements and
flattens them all into one stream:

```java
List<String> allItems = orders.stream()
        .flatMap(o -> o.items().stream())     // Stream<Order> -> Stream<String>
        .distinct()
        .toList();
```

**`reduce`** folds elements into a single value with an associative function and an identity value:

```java
long total = orders.stream().map(Order::amount).reduce(0L, Long::sum);
long total2 = orders.stream().mapToLong(Order::amount).sum();   // same result, no boxing
```

Prefer the specialised forms (`sum`, `max`, `count`, collectors) where they exist. Reach for `reduce` when you are
combining immutable values; do not use it to build up a mutable `List`, that is what `collect` is for.

Since Java 16, `stream.toList()` returns an **unmodifiable** list. `collect(Collectors.toList())` returns a list
whose mutability is not guaranteed (in practice an `ArrayList`). Code that later calls `add` on the result behaves
differently depending on which you used.

## Parallel streams, and when not to

`list.parallelStream()` (or `.parallel()`) splits the source and runs the pipeline on the **common ForkJoinPool**,
a JVM-wide thread pool sized by default to roughly the number of CPU cores minus one.

It can help when **all** of these hold: lots of elements, CPU-heavy work per element, a source that splits cheaply
(`ArrayList`, arrays, `IntStream.range`; not `LinkedList` or `Stream.iterate`), and no shared mutable state.

It hurts, or breaks, when:

- **The work is blocking I/O** (HTTP calls, DB queries). Those threads sit waiting, and because the pool is shared,
  every other parallel stream in the JVM stalls too. In a Spring service this is the usual reason to say no.
- **Lambdas that mutate shared state** (`list.add` from `forEach` into a plain `ArrayList`) give lost elements or even an
  `ArrayIndexOutOfBoundsException`. Let a collector do the combining.
- **Order matters**: `forEach` on a parallel stream runs in any order; use `forEachOrdered` (and lose some benefit).
- **The data is small**: splitting and merging cost more than the work.

**The rule:** sequential by default; go parallel only after measuring a CPU-bound workload.

## Optional: a return type for "maybe nothing"

**`Optional<T>`** is a container that holds either one value or nothing. It was designed as a **return type**, so a
method can say in its signature that the result might be absent:

```java
Optional<User> findByEmail(String email);

String name = repo.findByEmail(email)
        .map(User::name)                 // transform if present
        .filter(n -> !n.isBlank())
        .orElse("guest");                // default if absent

User user = repo.findByEmail(email)
        .orElseThrow(() -> new UserNotFoundException(email));
```

Do:

- Return `Optional` from finders. Chain with `map`, `flatMap`, `filter`, `ifPresent`, `ifPresentOrElse`.
- Use `orElseGet(supplier)` when the default is expensive. `orElse(x)` **always** evaluates `x`, even when a value
  is present; `orElse(createDefaultUser())` runs the method every time.
- Use `orElseThrow()` (Java 10+) instead of `get()`; it says the same thing honestly.

Don't:

- Call `opt.get()` without checking, which is just a `NullPointerException` with a different name
  (`NoSuchElementException`).
- Use `Optional` for fields, method parameters or collection elements. It is not `Serializable`, adds an object
  per value, and a parameter that is an `Optional` can itself be `null`.
- Return `Optional<List<T>>`. Return an empty list.
- Write `if (opt.isPresent()) { return opt.get(); } else { return null; }`. That is the old code with extra steps.

## Lab (~10 min)

Save as `StreamLab.java`, run with `java StreamLab.java`.

```java
import java.util.*;
import java.util.stream.*;
import static java.util.stream.Collectors.*;

public class StreamLab {
    enum Status { PAID, PENDING }
    record Order(String customer, String city, long amount, Status status, List<String> items) {}

    public static void main(String[] args) {
        List<Order> orders = List.of(
                new Order("asha", "Pune", 1200, Status.PAID, List.of("book", "pen")),
                new Order("ravi", "Delhi", 300, Status.PENDING, List.of("pen")),
                new Order("asha", "Pune", 800, Status.PAID, List.of("lamp")),
                new Order("meera", "Delhi", 2500, Status.PAID, List.of("chair", "lamp")));

        // 1. Total paid amount per customer
        Map<String, Long> paidTotals = orders.stream()
                .filter(o -> o.status() == Status.PAID)
                .collect(groupingBy(Order::customer, TreeMap::new, summingLong(Order::amount)));
        System.out.println("paid totals: " + paidTotals);

        // 2. Distinct items across all orders, sorted
        System.out.println("items: " + orders.stream().flatMap(o -> o.items().stream()).distinct().sorted().toList());

        // 3. Highest-value order per city
        Map<String, Optional<Order>> topByCity = orders.stream()
                .collect(groupingBy(Order::city, maxBy(Comparator.comparingLong(Order::amount))));
        topByCity.forEach((city, o) -> System.out.println(city + " -> " + o.map(Order::customer).orElse("-")));

        // 4. Laziness: watch the order of the prints
        Stream.of("x", "yy", "zzz")
                .peek(s -> System.out.println("saw " + s))
                .filter(s -> s.length() > 1)
                .findFirst()
                .ifPresent(s -> System.out.println("first long = " + s));

        // 5. Break it: toMap without a merge function
        try {
            orders.stream().collect(toMap(Order::customer, Order::amount));
        } catch (IllegalStateException e) {
            System.out.println("toMap failed: " + e.getMessage());
        }
    }
}
```

**Observe:**

- Step 4 prints `saw x`, `saw yy`, then `first long = yy`, and never `saw zzz`: lazy, element-by-element,
  short-circuiting.
- Step 5 prints a `Duplicate key asha` message. Fix it with `toMap(Order::customer, Order::amount, Long::sum)` and
  compare the result with step 1 (it also includes non-paid orders, so check `ravi`).
- **Bonus:** add `int seen = 0;` above step 4 and try `seen++` inside `peek`. Read the compiler error about
  effectively final variables.

## Gotchas

- **`toMap` with duplicate keys** throws `IllegalStateException`. Always ask "can keys repeat?" and pass a merge
  function if yes.
- **Side effects inside `map`/`filter`/`peek`.** They may run fewer times than you expect (short-circuiting) or in any
  order (parallel). Keep lambdas in a pipeline pure; put effects in the terminal `forEach` or after the stream.
- **`orElse` evaluates eagerly.** `orElse(expensiveCall())` always calls it. Use `orElseGet(() -> expensiveCall())`.
- **Parallel streams on the common pool** with blocking I/O starve every other parallel stream in the JVM. Use an
  executor sized for I/O (coming in JAVA-CONC-4) or virtual threads (JAVA-CONC-6) instead.
- **A stream can be consumed once.** Storing a `Stream` in a field or variable and using it twice throws
  `IllegalStateException: stream has already been operated upon or closed`. Store the collection; create streams
  on demand.
- **Checked exceptions do not fit** `Function` and friends (their methods declare no `throws`). Wrap and rethrow as an
  unchecked exception inside the lambda, or extract a method; do not swallow it (JAVA-FUND-4).

## In interviews

Asked as "What came in Java 8?", "What is a functional interface?", "Why must captured variables be effectively
final?", "Intermediate vs terminal operations?", "When would you not use a parallel stream?", and very often as a
live drill: "Group employees by department and find the highest-paid in each", "Find the second-highest salary",
"Count word frequency", "Find duplicate elements", "Find the first non-repeated character". Bank:
[Java 8 features: lambdas, functional interfaces, streams, Optional](#/q/java-8-features) and
[Java 8 stream coding drills](#/q/java-streams-coding-drills).

A strong answer shape, in four layers (example: "How do streams work?"):

1. **What:** a lazy pipeline over a source: source, zero or more intermediate operations, one terminal operation.
2. **How inside:** intermediate ops just build a chain of stages; the terminal op pulls each element through the
   whole chain in turn, short-circuiting where possible; stateful ops like `sorted` buffer everything.
3. **Where used:** service-layer transformations, DTO mapping, grouping for reports; `Optional` from repository
   finders.
4. **What goes wrong:** `toMap` duplicate keys, side effects in lambdas, parallel streams doing I/O on the common
   pool, reusing a consumed stream, `Optional.get()` without a check.

**Follow-up: "Second-highest salary with streams?"** `employees.stream().map(Employee::salary).distinct()
.sorted(Comparator.reverseOrder()).skip(1).findFirst()`; say that it returns an `Optional` because there may be no
second value, and that `distinct` is what handles ties.

**Follow-up: "Are streams faster than loops?"** Not inherently. For simple loops a plain `for` is often as fast or
faster; streams win on readability and composability. Measure before claiming either (JMH is coming in JAVA-JVM-8).

## Explain it in 2 minutes

Prompt: *"Explain lambdas, streams and Optional to a Java 7 developer."*

- A lambda is a compact implementation of a functional interface (one abstract method); `java.util.function` gives
  `Function`, `Predicate`, `Consumer`, `Supplier` and friends.
- Captured locals must be effectively final because the lambda holds a copy that can outlive the stack frame.
- Method references (`Order::amount`, `ArrayList::new`) are shorthand for lambdas that only call a method.
- A stream is a one-shot, lazy pipeline: intermediate ops build it, a terminal op runs it element by element with
  short-circuiting.
- Collectors do the heavy lifting: `groupingBy` with downstream collectors, `partitioningBy`, `toMap` with a merge
  function.
- Parallel streams use the shared common pool; only for big, CPU-bound, side-effect-free work. `Optional` is a return
  type for "maybe absent"; use `map`/`orElseGet`/`orElseThrow`, never bare `get()` or fields.

## Check yourself

1. Is `Runnable` a functional interface? Is `Comparator`, which declares `equals` as well as `compare`?
2. Why does `int n = 0; list.forEach(x -> n++);` fail to compile?
3. `Stream.of(1, 2, 3, 4).map(x -> { System.out.println(x); return x * 2; }).filter(x -> x > 4).findFirst();`
   What does it print?
4. What happens with `toMap(Person::city, Person::name)` if two people share a city, and how do you fix it?
5. Why is `orElse(loadDefaultFromDb())` a performance bug?

### Answers

1. Yes to both. `Runnable` has one abstract method, `run`. `Comparator`'s `equals` is a public method of `Object`,
   which every class already implements, so it does not count toward the single abstract method.
2. `n` is a captured local and must be effectively final; `n++` reassigns it. Use `list.size()` or `count()`.
3. `1`, `2`, `3`. Elements flow one at a time; `3` maps to `6`, passes the filter, and `findFirst` stops before `4`.
4. `IllegalStateException` (duplicate key). Pass a merge function, for example
   `toMap(Person::city, Person::name, (a, b) -> a + "," + b)`, or use `groupingBy(Person::city, mapping(Person::name,
   toList()))`.
5. The argument is evaluated before `orElse` is called, so the DB is hit even when the value is present. Use
   `orElseGet(() -> loadDefaultFromDb())`.
