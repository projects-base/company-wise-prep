## Where we are

After CAPSTONE-10, TicketHub publishes `BookingConfirmed` through the transactional outbox to `tickethub.bookings`, has an idempotent notification consumer with a DLT, and protects payments with Resilience4j. It still runs as `./mvnw spring-boot:run` on your laptop, with only the dependencies in Compose.

## Goal

Make TicketHub something you can hand to any machine or cluster and have it run the same way. You build a small, secure container image (multi-stage, layered jar, non-root, JVM sized to the container), run the **whole stack** with one `docker compose up` in which the app waits for healthy dependencies, and describe it to Kubernetes. That means a Deployment whose startup, liveness and readiness probes use the Actuator groups from CAPSTONE-9, resource requests and limits, configuration in a ConfigMap and Secret, and graceful shutdown so a rolling update drops no requests. This uses DIST-SYS-4.

## What you build

- [ ] `Dockerfile`: build stage → extract layers → JRE runtime stage, `USER` non-root, exec-form `ENTRYPOINT`
- [ ] `.dockerignore`
- [ ] `compose.yaml` with `app`, `postgres`, `redis`, `kafka`, healthchecks on each dependency, and `depends_on: condition: service_healthy`
- [ ] Graceful shutdown settings in `application.yml`
- [ ] `k8s/`: `configmap.yaml`, `secret.example.yaml`, `deployment.yaml`, `service.yaml`, plus `dev-deps.yaml` (local-only Postgres/Redis/Kafka)
- [ ] (Optional) the image running on Google Cloud Run

## Acceptance criteria

1. `docker build -t tickethub:0.11.0 .` succeeds. `docker image ls tickethub` shows a size in the low hundreds of MB, not near 1 GB.
2. `docker run --rm --entrypoint id tickethub:0.11.0` prints a non-zero `uid` (for example `uid=10001(tickethub)`).
3. Change one line in a controller and rebuild. The build log shows the dependency layer as `CACHED`, and only the application layer is rebuilt.
4. `docker compose up -d --build`, then `docker compose ps` shows `postgres`, `redis` and `kafka` as `healthy` and `app` as running. `curl -s localhost:8080/actuator/health/readiness` prints `{"status":"UP"}`.
5. The end-to-end flow works against the Compose stack: hold → confirm → the record appears on `tickethub.bookings` (CAPSTONE-10 acceptance step 2).
6. `docker compose stop app` shows `Commencing graceful shutdown` in the app log, and the container exits within the shutdown timeout, not by being killed after 10 s.
7. On a local cluster (Docker Desktop Kubernetes or kind): `kubectl apply -f k8s/` → `kubectl rollout status deploy/tickethub` reports `successfully rolled out`. `kubectl get pods` shows `2/2` pods `Running` and `READY 1/1`.
8. `kubectl port-forward svc/tickethub 8080:80`, then `curl localhost:8080/api/v1/events` returns events. `kubectl rollout restart deploy/tickethub` while a curl loop runs shows no failed requests.

## Steps

### 1. The Dockerfile (15 min)

```dockerfile
# syntax=docker/dockerfile:1

# ---- build: compile and package ----
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY mvnw pom.xml ./
COPY .mvn .mvn
RUN ./mvnw -q -B dependency:go-offline
COPY src src
RUN ./mvnw -q -B package -DskipTests

# ---- extract: split the fat jar into layers ----
FROM eclipse-temurin:21-jdk AS extract
WORKDIR /x
COPY --from=build /src/target/*.jar application.jar
RUN java -Djarmode=tools -jar application.jar extract --layers --destination extracted

# ---- runtime: JRE only, non-root ----
FROM eclipse-temurin:21-jre
RUN useradd --system --uid 10001 --no-create-home tickethub
WORKDIR /app
COPY --from=extract /x/extracted/dependencies/ ./
COPY --from=extract /x/extracted/spring-boot-loader/ ./
COPY --from=extract /x/extracted/snapshot-dependencies/ ./
COPY --from=extract /x/extracted/application/ ./
USER 10001
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError"
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "application.jar"]
```

Why each piece is there:

- **Multi-stage:** the JDK, Maven and your source stay in the build stages. The final image holds only a JRE and the app.
- **Layers:** Docker caches each `COPY` as a layer. Dependencies change rarely and your code changes on every commit. Copying them in that order means a code change pushes only a few hundred KB. `-Djarmode=tools ... extract --layers` is the Boot 3.3+ form; older guides use `layertools`, which is deprecated.
- **`dependency:go-offline` before `COPY src`:** the Maven download layer is cached until `pom.xml` changes.
- **Non-root:** if the app is compromised, the attacker does not have root inside the container. Kubernetes can enforce this with `runAsNonRoot`.
- **JVM flags:** since Java 10 the JVM reads the container's memory limit. `MaxRAMPercentage=75` sizes the heap from that limit and leaves room for metaspace, thread stacks and direct buffers. `ExitOnOutOfMemoryError` makes a broken JVM die so the orchestrator replaces it, instead of limping along.
- **Exec-form `ENTRYPOINT`** (the JSON array) runs `java` as PID 1, so it receives `SIGTERM` directly. The shell form wraps it in `sh`, which does not forward the signal.

### 2. Graceful shutdown (3 min)

```yaml
server:
  shutdown: graceful            # the default since Boot 3.4; keep it explicit
spring:
  lifecycle.timeout-per-shutdown-phase: 20s
```

On `SIGTERM`, Spring marks readiness as refusing traffic, stops accepting new requests, and lets in-flight requests finish (up to 20 s). Then it stops the Kafka listeners, the scheduler and the connection pool. The outbox makes this safe: a relay interrupted mid-batch just rolls back, and the next instance publishes the rows.

### 3. Compose for the whole stack (12 min)

```yaml
services:
  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: tickethub
      POSTGRES_USER: tickethub
      POSTGRES_PASSWORD: ${DB_PASSWORD:-tickethub}
    ports: ["5432:5432"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U tickethub -d tickethub"]
      interval: 5s
      timeout: 3s
      retries: 10

  redis:
    image: redis:7
    command: ["redis-server", "--notify-keyspace-events", "Ex"]
    ports: ["6379:6379"]
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10

  kafka:
    image: apache/kafka:3.9.0
    ports: ["9092:9092"]
    environment:
      KAFKA_NODE_ID: 1   # ...paste the full KAFKA_* block from CAPSTONE-10 here
    healthcheck:
      test: ["CMD-SHELL", "/opt/kafka/bin/kafka-broker-api-versions.sh --bootstrap-server kafka:19092 > /dev/null 2>&1"]
      interval: 10s
      timeout: 10s
      retries: 12
      start_period: 15s

  app:
    build: .
    image: tickethub:0.11.0
    ports: ["8080:8080"]
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/tickethub
      SPRING_DATASOURCE_USERNAME: tickethub
      SPRING_DATASOURCE_PASSWORD: ${DB_PASSWORD:-tickethub}
      REDIS_HOST: redis
      KAFKA_BOOTSTRAP: kafka:19092
      TICKETHUB_JWT_SECRET: ${TICKETHUB_JWT_SECRET:?set it in .env}
    depends_on:
      postgres: { condition: service_healthy }
      redis: { condition: service_healthy }
      kafka: { condition: service_healthy }
    stop_grace_period: 30s
```

- **`depends_on` without a condition** waits only until the container has *started*, not until Postgres accepts connections. `service_healthy` waits for the healthcheck to pass.
- **Inside the Compose network,** services reach each other by service name (`postgres`, `kafka:19092`). `localhost` inside the app container is the app container itself.
- **`stop_grace_period: 30s`** is longer than Spring's 20 s phase timeout. Docker's default is 10 s, after which it sends `SIGKILL`.
- **Secrets:** `${TICKETHUB_JWT_SECRET:?...}` refuses to start if the variable is unset. Put the value in `.env` and add `.env` to `.gitignore`.

Also make sure `application.yml` reads `${REDIS_HOST:localhost}` and `${KAFKA_BOOTSTRAP:localhost:9092}`, as set up in CAPSTONE-9 and CAPSTONE-10.

### 4. Kubernetes manifests (20 min)

Config that varies by environment goes in a **ConfigMap** (plain values). Sensitive values go in a **Secret** (base64-encoded, not encrypted by default; access is controlled through RBAC).

```yaml
# k8s/configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata: { name: tickethub-config }
data:
  SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/tickethub
  SPRING_DATASOURCE_USERNAME: tickethub
  REDIS_HOST: redis
  KAFKA_BOOTSTRAP: kafka:9092
```

```yaml
# k8s/secret.example.yaml   (commit the example; create the real one with kubectl, never commit it)
apiVersion: v1
kind: Secret
metadata: { name: tickethub-secrets }
type: Opaque
stringData:
  SPRING_DATASOURCE_PASSWORD: change-me
  TICKETHUB_JWT_SECRET: change-me-at-least-32-bytes-long-secret
```

Create the real Secret with `kubectl create secret generic tickethub-secrets --from-literal=SPRING_DATASOURCE_PASSWORD=... --from-literal=TICKETHUB_JWT_SECRET=...`.

```yaml
# k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: tickethub }
spec:
  replicas: 2
  selector: { matchLabels: { app: tickethub } }
  strategy:
    rollingUpdate: { maxUnavailable: 0, maxSurge: 1 }
  template:
    metadata: { labels: { app: tickethub } }
    spec:
      terminationGracePeriodSeconds: 40
      securityContext: { runAsNonRoot: true }
      containers:
        - name: app
          image: tickethub:0.11.0
          imagePullPolicy: IfNotPresent
          ports: [{ name: http, containerPort: 8080 }]
          envFrom:
            - configMapRef: { name: tickethub-config }
            - secretRef: { name: tickethub-secrets }
          resources:
            requests: { cpu: 500m, memory: 768Mi }
            limits: { memory: 768Mi }
          startupProbe:
            httpGet: { path: /actuator/health/liveness, port: http }
            periodSeconds: 3
            failureThreshold: 40
          livenessProbe:
            httpGet: { path: /actuator/health/liveness, port: http }
            periodSeconds: 10
            failureThreshold: 3
          readinessProbe:
            httpGet: { path: /actuator/health/readiness, port: http }
            periodSeconds: 5
            failureThreshold: 2
          lifecycle:
            preStop:
              exec: { command: ["sh", "-c", "sleep 5"] }
```

```yaml
# k8s/service.yaml
apiVersion: v1
kind: Service
metadata: { name: tickethub }
spec:
  selector: { app: tickethub }
  ports: [{ port: 80, targetPort: http }]
```

How the probes divide the work:

- **startupProbe** gives a slow JVM start up to 3 s × 40 = 120 s. Liveness and readiness do not run until it passes, so a slow Flyway migration does not get the pod killed.
- **livenessProbe** hits the dependency-free `liveness` group. Failing means "restart this container".
- **readinessProbe** hits `readiness`, which includes `db` and `redis`. Failing means "remove this pod from the Service's endpoints", with no restart.

Resources and shutdown:

- The memory **request** is what the scheduler reserves. The **limit** is where the kernel kills the container (OOMKilled). Setting them equal for memory makes the pod's memory predictable. With `MaxRAMPercentage=75`, the heap is about 576 Mi of the 768 Mi. CPU has a request but no limit here: a CPU limit throttles the JVM's JIT and GC threads during startup. Pick one position and be ready to defend it.
- **preStop sleep** gives the Service's endpoint removal time to reach every node before Spring stops accepting requests. Without it, a few requests still arrive at a pod that is shutting down. `terminationGracePeriodSeconds: 40` must cover the 5 s sleep plus the 20 s Spring phase, with margin.
- **`maxUnavailable: 0`** means a new pod must be ready before an old one is removed.

**Local dependencies.** Write `k8s/dev-deps.yaml` with one Deployment and one Service each for `postgres:16`, `redis:7` and `apache/kafka:3.9.0` (Kafka advertising `PLAINTEXT://kafka:9092`), with no persistent volumes. Put a comment at the top: *dev only; production uses managed Postgres, Redis and Kafka*. Running stateful systems in Kubernetes needs StatefulSets, volumes and operators, which is out of scope here.

**Load the image.** Docker Desktop's Kubernetes sees your local images. For kind, run `kind load docker-image tickethub:0.11.0`. Never use `:latest`, because `IfNotPresent` would keep running a stale image.

### 5. (Optional) Google Cloud Run (5 min, if you want a public URL)

You already use Cloud Run, so the container ships as-is:

```bash
gcloud run deploy tickethub --source . --region <your-region> --port 8080 \
  --set-env-vars SPRING_PROFILES_ACTIVE=cloud --set-secrets TICKETHUB_JWT_SECRET=tickethub-jwt:latest
```

Before you do, know these differences:

- Cloud Run has no Kafka or Redis. Use a managed Postgres (your Neon database works), a managed Redis (Memorystore, reached through VPC egress), and managed Kafka (Google Cloud Managed Service for Apache Kafka, or Confluent Cloud). Alternatively, run a `cloud` profile that disables caching and the outbox relay, and say so in the README.
- By default Cloud Run allocates CPU only while a request is being handled. The outbox relay, the hold-expiry job and the Kafka consumer run in the background, so they would stall. Use instance-based billing (`--no-cpu-throttling`) and `--min-instances 1`, or move those jobs elsewhere.
- Cloud Run has no liveness and readiness probe groups in the Kubernetes sense; it has its own startup and liveness health checks. Point them at the same Actuator paths.

## Hints

- **`./mvnw: not found` or `bad interpreter` in the build:** Windows checked out `mvnw` with CRLF line endings. Add `mvnw text eol=lf` to `.gitattributes`, re-checkout, or run `RUN sed -i 's/\r$//' mvnw` before using it.
- **Every code change re-downloads dependencies:** you copied `src` before running `dependency:go-offline`, or `pom.xml` changed.
- **`app` exits on start with a connection refused error:** the dependency was started but not healthy. Check the `condition: service_healthy` lines and each healthcheck.
- **Pods restart in a loop with no app error:** run `kubectl describe pod`. `OOMKilled` means the limit is too low for heap plus native memory. `Liveness probe failed` during startup means the startupProbe is missing or too short.
- **Readiness stays false in Kubernetes:** run `kubectl exec` into the pod and `curl -s localhost:8080/actuator/health` with an admin token to see which component is `DOWN`. It is usually Redis or the database host name in the ConfigMap.

## Talk about it in interviews

**"How do you containerise a Spring Boot app?"**
1. *What:* a multi-stage build producing a JRE-only, non-root image with the jar split into layers.
2. *How it works inside:* each `COPY` is a cached layer, so dependencies are cached and app code is the thin top layer. The JVM reads cgroup limits, and `MaxRAMPercentage` sizes the heap. Exec-form `ENTRYPOINT` makes `java` PID 1 so it receives `SIGTERM`.
3. *Where used:* the same image runs in Compose, Kubernetes and Cloud Run. Only the configuration changes.
4. *What goes wrong:* fat images, running as root, shell-form entrypoints that swallow `SIGTERM`, a heap sized to the host instead of the container, and `:latest` tags.

**"Explain liveness vs readiness vs startup probes."** Startup protects a slow boot. Liveness restarts a stuck process and must not include dependencies. Readiness removes the pod from traffic while a dependency is down. Mine map to `/actuator/health/{liveness,readiness}` from CAPSTONE-9.

**"How do you achieve zero-downtime deploys?"** Rolling update with `maxUnavailable: 0`, a readiness gate, a preStop sleep so endpoints drain, Spring graceful shutdown, a grace period longer than the drain, and backward-compatible Flyway migrations, so old and new pods can share the schema during the rollout.

**"Requests vs limits?"** A request is a scheduling reservation; a limit is enforcement. Exceeding the memory limit gets the container OOMKilled; exceeding a CPU limit gets it throttled. Heap must fit under the memory limit with room for native memory.
