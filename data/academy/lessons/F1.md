## Where we are

You have built a simple web app: one server process (say, a Spring Boot jar) talking to one
database (say, Postgres). Users send HTTP requests, the server reads or writes rows, and it answers.
This lesson grows that app into a large system one building block at a time. Each block is introduced
by the problem that forces it on you.

## The problem

Your app goes from 100 users to 10 million. Three things break, in roughly this order:

```text
   users ──► [ one server ] ──► [ one database ]
                 ▲                     ▲
   1. CPU is maxed out          2. every request does a disk read
   3. if either box dies, the whole product is down
```

System design is mostly a list of moves that fix these three problems: **too much load on one
box, too slow, and a single point of failure** (one component whose death takes everything down).
We will make eight moves, and each one creates the problem that the next one solves.

## Move 1: the load balancer

**Problem:** one server can't handle the traffic, so you start a second and a third. But users
only know one address. Who decides which server gets each request?

A **load balancer (LB)** is a component that receives every request and forwards it to one of
several identical servers behind it.

```text
                    ┌──► app-1
   users ──► [ LB ] ─┼──► app-2      ──► database
                    └──► app-3
```

How it picks a server:
- **Round robin:** 1, 2, 3, 1, 2, 3… Simple, and fine when requests cost about the same.
- **Least connections:** send to the server with the fewest open requests. Better when some
  requests are slow.
- **Hash of a key** (for example the user id): the same user always lands on the same server.

The LB also runs **health checks**: it calls each server's `/health` endpoint every few seconds
and stops sending traffic to one that fails.

Two levels you'll hear about: an **L4 load balancer** looks only at the network connection (IP and
port), which makes it fast but blind to the content. An **L7 load balancer** reads the HTTP request,
so it can route `/api/*` and `/images/*` to different pools.

**The rule:** for an LB to work, the servers must be **stateless**, which means no user data is kept
in a server's memory between requests. If you keep sessions in an `HttpSession` on app-1 and the
next request lands on app-2, the user is logged out. Move the session to a shared store (a cache or
the database) or into a signed token. Also, the LB itself must not be a single point of failure,
so in practice it runs as a redundant pair or as a managed cloud service.

## Move 2: the cache

**Problem:** the servers scale, but every request still hits the database. The same product page
is read 50,000 times an hour, and each read costs a disk lookup.

A **cache** is a fast store (usually in memory, for example Redis) that keeps copies of data you
read often, so you can skip the slow source. A **cache hit** means the data was there. A **cache
miss** means you had to go to the database.

The most common pattern is **cache-aside**: the application checks the cache first.

```java
Product get(long id) {
    Product p = cache.get(id);          // 1. try the cache
    if (p == null) {                    // 2. miss
        p = db.findProduct(id);         // 3. read the source of truth
        cache.put(id, p, Duration.ofMinutes(10)); // 4. remember it, with a TTL
    }
    return p;
}
```

**TTL (time to live)** is how long an entry stays before it expires. The hard part is
**invalidation**: when the data changes, how does the stale copy go away? Your options:

| Strategy | How it works | Trade-off |
|---|---|---|
| TTL only | Entries expire after N minutes | Simple. Readers may see stale data for up to N minutes |
| Delete on write | Update the DB, then **delete** the cache key | The next read reloads fresh data. The usual default |
| Write-through | Write to the cache and the DB together, every time | Cache always warm. Every write is slower |
| Write-behind | Write to the cache, and flush to the DB later | Fast writes. You can lose data if the cache dies |

Delete the key rather than update it on writes. If two writers update the cache in the wrong
order, the older value can win. A delete can't go stale that way.

One trap to name early is the **cache stampede**. A hot key expires and a thousand requests miss at
the same moment, so all of them hit the database. The fixes: let only one request reload the key
(a lock or "single flight"), or add random jitter to TTLs so keys don't expire together.

**The rule:** cache data that is read far more than it is written, and that can be slightly stale.
Always ask: "what happens if this is stale, and for how long?"

## Move 3: the CDN

**Problem:** your users are worldwide, but your servers are in one region. A user in Sydney waits
for every image and JavaScript file to cross the planet.

A **CDN (content delivery network)** is a cache run by a provider on hundreds of servers around
the world, called **edge locations**. Users fetch static files (images, video, CSS, JS) from the
edge near them, and only a miss goes back to your **origin** (your own servers).

```text
   Sydney user ──► [ edge, Sydney ] ──miss──► [ origin, your region ]
                        │ hit
                        ▼
                    file in ~ms
```

You control it with HTTP headers such as `Cache-Control: max-age=86400`. Because purging every
edge is slow, the usual trick is **versioned file names**: `app.3f9a1c.js`. A new deploy produces a
new name, so nothing has to be invalidated.

**The rule:** a CDN is a cache for content that is the same for many users. Per-user data, such as
"my inbox", doesn't belong there.

## Move 4: read replicas

**Problem:** the cache absorbs a lot, but the database still serves too many reads (searches,
reports, cache misses).

A **replica** is a copy of the database that is kept up to date automatically. In the common setup,
one **primary** accepts all writes and streams its changes to several **read replicas**, which only
serve reads.

```text
   writes ──► [ primary ] ──changes──► [ replica 1 ] ◄── reads
                         └─changes──► [ replica 2 ] ◄── reads
```

The catch is **replication lag**: a replica is usually a few milliseconds behind, and sometimes
seconds. A user updates their profile, refreshes the page, the read goes to a replica, and they see
the old name. The fix is **read-your-writes**: send a user's reads to the primary for a short time
after they write, or read from a replica that has caught up.

Replicas also help with failure. If the primary dies, a replica can be promoted to become the new
primary. F2 covers how that decision is made safely.

**The rule:** replicas scale **reads**. They don't help with writes at all, because every write
still goes to the one primary.

## Move 5: sharding

**Problem:** writes outgrow one primary, or the data no longer fits on one machine.

**Sharding** (also called **partitioning**) splits the data across several independent databases
called **shards**. Each one holds a slice of the rows. A **shard key** decides which slice a row
belongs to.

```text
   shard = hash(user_id) % 4

   user 17 ──► shard 1      user 42 ──► shard 2
   [shard 0] [shard 1] [shard 2] [shard 3]   each has its own primary + replicas
```

What you give up:
- **Cross-shard queries** ("top 10 users by spend") must ask every shard and merge the answers.
- **Cross-shard transactions** are hard, so pick a key that keeps related data together. Sharding
  orders by `user_id` keeps all of one user's orders on one shard.
- **Hot shards:** if one key is huge (a celebrity, a big tenant), its shard is overloaded.
- **Resharding:** with `% 4`, adding a fifth shard changes the answer for most keys. Move 7 fixes
  that.

**The rule:** choose the shard key from your most common query, and check for skew.

## Move 6: queues and streams

**Problem:** sign-up now sends a welcome email, resizes the avatar and updates analytics. The user
waits for all of it, and if the email provider is down, sign-up fails.

A **message queue** lets one part of the system leave a message ("user 42 signed up") that another
part processes later. The sender is the **producer** and the receiver is the **consumer**. The user
gets a response as soon as the message is stored.

```text
   app ──► [ queue: signups ] ──► email worker
                               ──► avatar worker
```

This gives you three things: **decoupling** (a slow email provider no longer breaks sign-up),
**smoothing of bursts** (the queue absorbs a spike and workers catch up), and **retries**.

There are two flavours, and interviewers like to hear that you know the difference:

| | Queue (RabbitMQ, SQS, Azure Service Bus) | Stream / log (Kafka, Azure Event Hubs) |
|---|---|---|
| After processing | The message is deleted | The message stays for the retention period |
| Many consumers | They compete, and each message goes to one of them | Each consumer group reads everything, at its own position |
| Replay | No | Yes: rewind the position (the **offset**) |
| Good for | Jobs and tasks | Event history, analytics, feeding many systems |

A stream is split into **partitions**, and ordering is guaranteed only within one partition. That
is why you choose a partition key such as `user_id` when per-user order matters.

**The rule:** use a queue when work can happen later. Assume a message can be delivered more than
once, and design the consumer so a duplicate does no harm (F2 covers this as idempotency).

## Move 7: consistent hashing

**Problem:** back to Move 5. With `hash(key) % N`, going from 4 to 5 nodes moves about 80% of keys.
For a cache that means most of the cache misses at once. For a database it means moving most of your
data.

**Consistent hashing** places both nodes and keys on a circle of hash values (a **ring**). A key
belongs to the first node you meet walking clockwise from the key's position.

```text
             node-A
          ·         ·
   key k1 ●           node-B        k1 → walk clockwise → node-B
        ·               ·
   node-D ·           ·  ● key k2   k2 → walk clockwise → node-C
             node-C
```

Add node-E between A and B, and only the keys in the arc just before E move to E. Everything else
stays put, so about 1/N of the keys move instead of most of them.

With one point per node, the arcs are uneven and one node can get twice its share. The fix is
**virtual nodes**: each physical node is placed at many points (say 100) on the ring, which evens
out the load. You'll measure exactly this in the lab.

**The rule:** use consistent hashing whenever nodes join and leave a sharded cache or store.
Cassandra, DynamoDB-style stores and many cache clients use it or a close variant.

## Move 8: Bloom filters

**Problem:** your sharded store gets a lot of lookups for keys that don't exist, such as "is this
username taken?" or a crawler asking "have I seen this URL?". Each miss still costs a disk read.

A **Bloom filter** is a small bit array that answers "is X in the set?" with either **"definitely
not"** or **"probably yes"**. To add X, hash it with k hash functions and set those k bits to 1. To
check X, look at the same k bits: if any is 0, X was never added.

```text
   bits:  0 0 1 0 1 0 0 1 0 0
   add "alice": h1=2, h2=4, h3=7   → set bits 2, 4, 7
   check "bob":  h1=1 ...          → bit 1 is 0 → definitely not present
   check "carol": 2, 4, 7 all 1    → "probably" (could be a false positive)
```

It never gives a false "no", but it can give a false "yes", and the false-positive rate grows as you
add items. You choose the size from how many items you expect and the error rate you can live with
(roughly 10 bits per item for about a 1% error rate). You can't delete from a basic Bloom filter.

**The rule:** put a Bloom filter in front of an expensive lookup when most answers are "no".
LSM-tree databases such as Cassandra and RocksDB keep one per data file to skip files that can't
contain a key.

## The full picture

```text
            ┌──────── CDN (static) ◄─── users
            │                              │
            ▼                              ▼
         origin ◄──────────────── [ load balancer ]
                                  /       |       \
                              app-1     app-2     app-3      (stateless)
                                │  \      |      /   │
                                │   [ cache cluster ]       (consistent hashing)
                                │          │
                     [ queue / stream ]    ▼
                         │         [ shard 0 ] [ shard 1 ] ... each: primary + replicas
                      workers
```

## Lab (~10 min)

Measure why consistent hashing exists. Save this as `RingLab.java` and run `java RingLab.java`.

```java
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.HashMap;
import java.util.Map;
import java.util.TreeMap;

public class RingLab {

    // Turn any string into a well-spread 64-bit number.
    static long hash(String s) {
        try {
            byte[] d = MessageDigest.getInstance("MD5").digest(s.getBytes(StandardCharsets.UTF_8));
            long h = 0;
            for (int i = 0; i < 8; i++) h = (h << 8) | (d[i] & 0xFF);
            return h;
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException(e);
        }
    }

    static final class Ring {
        private final TreeMap<Long, String> ring = new TreeMap<>();
        private final int vnodes;

        Ring(int vnodes) { this.vnodes = vnodes; }

        void add(String node) {
            for (int i = 0; i < vnodes; i++) ring.put(hash(node + "#" + i), node);
        }

        String nodeFor(String key) {
            Map.Entry<Long, String> e = ring.ceilingEntry(hash(key)); // first point clockwise
            return (e != null ? e : ring.firstEntry()).getValue();    // wrap around
        }
    }

    public static void main(String[] args) {
        int keys = 100_000;

        // 1. Modulo placement: 4 servers -> 5 servers
        int movedMod = 0;
        for (int i = 0; i < keys; i++) {
            long h = hash("user:" + i);
            if (Math.floorMod(h, 4) != Math.floorMod(h, 5)) movedMod++;
        }
        System.out.printf("modulo: %.1f%% of keys moved%n", 100.0 * movedMod / keys);

        // 2. Consistent hashing: 4 nodes -> 5 nodes
        for (int vnodes : new int[] {1, 100}) {
            Ring ring = new Ring(vnodes);
            for (int n = 0; n < 4; n++) ring.add("node-" + n);
            String[] before = new String[keys];
            for (int i = 0; i < keys; i++) before[i] = ring.nodeFor("user:" + i);

            ring.add("node-4");
            int moved = 0;
            Map<String, Integer> load = new HashMap<>();
            for (int i = 0; i < keys; i++) {
                String now = ring.nodeFor("user:" + i);
                if (!now.equals(before[i])) moved++;
                load.merge(now, 1, Integer::sum);
            }
            System.out.printf("ring (vnodes=%d): %.1f%% moved, load per node %s%n",
                    vnodes, 100.0 * moved / keys, new TreeMap<>(load));
        }
    }
}
```

**What you should see:**
- Modulo moves about **80%** of keys.
- The ring with 1 point per node moves few keys, but the load is wildly uneven: one node may hold
  40% and another 6%.
- The ring with 100 virtual nodes moves about **20%** (that is 1/5, the new node's fair share), and
  every node holds close to 20,000 keys.

**Break it:** change `vnodes` to 10 and to 1,000, and watch the balance improve as the number of
points grows.

## Gotchas

- **Sticky sessions hide state.** Pinning users to one server via the LB "fixes" in-memory sessions
  until that server dies. Keep servers stateless and put sessions in a shared store.
- **Updating the cache on write instead of deleting it** lets two racing writers leave the older
  value in the cache. Update the DB, then delete the key.
- **Replicas don't scale writes**, and they serve stale reads. Route a user's own reads to the
  primary right after they write, if they must see their change.
- **A shard key chosen without looking at queries** turns every request into a scatter-gather
  across all shards. Choose it from the hottest access pattern.
- **Queues deliver at least once.** A consumer that isn't safe to run twice will send two emails or
  charge twice. Make consumers idempotent.
- **A Bloom filter "yes" is only a maybe.** Use it to skip work, never to answer "it exists".

## In interviews

Every HLD question uses these blocks. You are expected to bring one in only after naming the
problem it solves, and with numbers behind it. Practise with
[Design a URL Shortener](#/q/design-url-shortener) (cache plus ID generation),
[Design a distributed cache optimised for a given task](#/q/design-distributed-cache) (consistent
hashing, replication, eviction) and [Design a Web Crawler](#/q/design-web-crawler) (queues, plus a
Bloom filter for "seen URLs"). Related domain questions are
[Indexes, Partitioning and Sharding](#/q/db-indexing-partitioning-sharding) and
[Diagnosing a low cache hit ratio](#/q/diagnose-low-cache-hit-ratio).

Typical follow-ups:
- **"Your cache node died. What happens?"** A strong answer: with consistent hashing, only that
  node's keys miss and fall through to the DB. Protect the DB from the sudden load with
  request coalescing and rate limits. If the miss storm is unacceptable, replicate hot keys.
- **"How do you pick the shard key?"** A strong answer names the dominant query, checks for skew
  (celebrity or big-tenant keys), and admits the cost of the queries it makes cross-shard.

## Explain it in 2 minutes

*"Take a single-server app to 10 million users. What do you add, and why?"*

- An LB and stateless app servers, with health checks and a redundant LB.
- A cache (cache-aside, TTL plus delete on write, stampede protection) and a CDN for static files.
- Read replicas for read load, with replication lag and read-your-writes as the catch.
- Sharding for write load and data size, chosen by shard key, with consistent hashing to grow.
- Queues to move slow work off the request path, with idempotent consumers.
- Each block exists to fix a specific bottleneck or single point of failure.

## Check yourself

1. Why must app servers be stateless behind a load balancer?
2. You update a product's price. Why delete the cache key instead of writing the new price into it?
3. Will adding five read replicas help if the database is overloaded by writes?
4. With `% N` placement, roughly what fraction of keys move from 4 to 5 nodes? With consistent hashing?
5. A Bloom filter says "probably present". What can you conclude?

### Answers

1. Any server may receive any request, so state in one server's memory is missing on the others,
   and lost when that server dies.
2. Two concurrent writers can put their values in the wrong order and leave the older price in the
   cache. A delete forces the next reader to load the current value.
3. No. Every write still goes to the single primary. You need sharding, batching or a cheaper write
   path.
4. About 80% with modulo. About 1/5 (20%) with consistent hashing and enough virtual nodes.
5. Nothing certain. You still have to check the real store. Only "definitely not present" is
   reliable.
