## Where we are

After CAPSTONE-4, TicketHub has a complete write API. `HoldController` calls `HoldService`, which runs the in-memory `IdempotencyStore` and the `BookingEngine`. `EventCatalog` serves events and seat maps from a JSON seed. Errors are problem details, `/events` is paginated, and the user comes from an `X-User-Id` header. All of it lives in memory: a restart loses every hold, and a second instance would sell the same seat again. This session puts PostgreSQL underneath, using SPRING-BOOT-7 (JPA and `@Transactional`), DB-SQL-5 (indexes) and DB-SQL-6 (isolation and locking).

## Goal

Replace the in-memory engine and catalog with JPA-backed services on PostgreSQL 16. Flyway owns the schema, not Hibernate. Every endpoint keeps its contract: the same paths, statuses and `code` values. A seat is claimed by updating its `event_seat` row under **optimistic locking**. Optimistic locking means every row carries a version number, and an update only succeeds if the version is still the one you read. Of two holds racing for one seat, exactly one commits, and the other gets `409 SEAT_UNAVAILABLE`. The idempotency key is written in the **same transaction** as the hold, which was CAPSTONE-4's promise. You also add the two booking reads the spec lists, `GET /bookings/{id}` and `GET /me/bookings`.

Add `spring-boot-starter-data-jpa`, `org.flywaydb:flyway-core`, `org.flywaydb:flyway-database-postgresql` and `org.postgresql:postgresql` (scope `runtime`). Boot manages all the versions. *Boot 4 note:* Flyway auto-configuration has its own module, so use `spring-boot-starter-flyway`.

**2. Configure (3 min).** Add this to `application.yml`, and drop `seed-location` from every profile file:

```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/tickethub
    username: tickethub
    password: ${DB_PASSWORD:tickethub}
  jpa:
    open-in-view: false          # transactions end in the service; no lazy loading while writing JSON
    hibernate.ddl-auto: validate # Flyway owns the schema; Hibernate only checks it
    properties.hibernate.jdbc.time_zone: UTC
  flyway.locations: classpath:db/migration
---
spring.config.activate.on-profile: dev
spring.flyway.locations: classpath:db/migration,classpath:db/seed
```

**Open-in-view** is a Boot default that keeps the JPA session open until the HTTP response is written. Lazy collections then load silently during JSON serialization. Turning it off makes those hidden queries fail loudly instead. CAPSTONE-6 depends on that.

**3. Write `V1__init.sql` (15 min)** in `src/main/resources/db/migration/`. `venue`, `seat` and `event` keep the `long` ids from CAPSTONE-1, as generated identities. Holds and bookings use `uuid`, because `SeatHold.create` and `Booking` already generate UUIDs. The columns are `row_no` and `seat_no`, because `ROW` is an SQL keyword.

```sql
create table venue (
    id            bigint generated by default as identity primary key,
    name          text not null,
    row_count     int  not null check (row_count > 0),
    seats_per_row int  not null check (seats_per_row > 0)
);
create table seat (
    id       bigint generated by default as identity primary key,
    venue_id bigint not null references venue (id),
    row_no   int    not null,
    seat_no  int    not null,
    constraint uq_seat_position unique (venue_id, row_no, seat_no)
);
create table event (
    id             bigint generated by default as identity primary key,
    venue_id       bigint      not null references venue (id),
    name           text        not null,
    starts_at      timestamptz not null,
    price_category text        not null check (price_category in ('STANDARD', 'PREMIUM', 'VIP'))
);
create table seat_hold (
    id          uuid primary key,
    event_id    bigint      not null references event (id),
    user_id     text        not null,
    status      text        not null check (status in ('HELD', 'CONFIRMED', 'EXPIRED', 'CANCELLED')),
    total_cents bigint      not null,
    expires_at  timestamptz not null,
    created_at  timestamptz not null
);
create table event_seat (
    event_id bigint not null references event (id),
    seat_id  bigint not null references seat (id),
    status   text   not null check (status in ('AVAILABLE', 'HELD', 'BOOKED')),
    hold_id  uuid   references seat_hold (id),
    version  bigint not null default 0,
    primary key (event_id, seat_id)
);
create table booking (
    id          uuid primary key,
    event_id    bigint      not null references event (id),
    user_id     text        not null,
    hold_id     uuid        not null unique references seat_hold (id),
    status      text        not null check (status in ('HELD', 'CONFIRMED', 'EXPIRED', 'CANCELLED')),
    total_cents bigint      not null,
    created_at  timestamptz not null
);
create table booking_seat (
    booking_id uuid   not null references booking (id),
    seat_id    bigint not null references seat (id),
    primary key (booking_id, seat_id)
);
create table idempotency_key (
    user_id     text        not null,
    idem_key    text        not null,
    fingerprint text        not null,
    hold_id     uuid        not null references seat_hold (id),
    created_at  timestamptz not null,
    primary key (user_id, idem_key)
);
create table outbox_event (
    id             uuid primary key,
    aggregate_type text        not null,
    aggregate_id   text        not null,
    event_type     text        not null,
    payload        jsonb       not null,
    created_at     timestamptz not null,
    published_at   timestamptz
);

create index ix_event_starts_at      on event (starts_at, id);
create index ix_event_seat_hold      on event_seat (hold_id) where hold_id is not null;
create index ix_seat_hold_expiry     on seat_hold (expires_at) where status = 'HELD';
create index ix_booking_user_created on booking (user_id, created_at desc);
create index ix_outbox_unpublished   on outbox_event (created_at) where published_at is null;
```

Every index answers a query you will actually run. Be ready to name it:

| Index | Query it serves |
|---|---|
| `event_seat` PK `(event_id, seat_id)` | The seat map (`where event_id = ?`, which uses the leftmost column) and claiming specific seats |
| `uq_seat_position` | Stops two seats sharing a position, and covers `seat where venue_id = ?` |
| `ix_event_starts_at` | `GET /events` ordered by `startsAt, id`: the same stable order CAPSTONE-4's pagination relies on |
| `ix_event_seat_hold` (partial) | Confirm, release and expire find a hold's seats with `hold_id = ?`. Rows with no hold stay out of the index |
| `ix_seat_hold_expiry` (partial) | The CAPSTONE-7 expiry job: `status = 'HELD' and expires_at < ?`. Finished holds never enter it |
| `ix_booking_user_created` | `GET /me/bookings`, newest first, with no sort step |
| `booking.hold_id unique` | A hold becomes at most one booking, so a double confirm cannot create two |
| `ix_outbox_unpublished` | The CAPSTONE-10 relay reads only the rows it has not sent yet |

`booking_seat` and `idempotency_key` are served by their primary keys. Postgres does not index foreign keys automatically, and you only add an index when a query filters on that column, because every index slows every write.

**4. Dev seed (5 min).** Put it in `src/main/resources/db/seed/R__dev_seed.sql`. The `R__` prefix makes it a **repeatable** migration, which Flyway re-runs whenever the file changes, so it must be safe to run twice. Keep the ids from your `dev-seed.json`, so that the CAPSTONE-4 curls with seats `1001…` still work:

```sql
insert into venue (id, name, row_count, seats_per_row) values (1, 'Arena One', 10, 20)
on conflict (id) do nothing;

insert into seat (id, venue_id, row_no, seat_no)
select 1000 + (r - 1) * 20 + n, 1, r, n from generate_series(1, 10) r, generate_series(1, 20) n
on conflict (id) do nothing;

insert into event (id, venue_id, name, starts_at, price_category)
values (1, 1, 'Synth Night', '2027-02-14T19:30:00Z', 'PREMIUM')    -- copy your JSON events here
on conflict (id) do nothing;

insert into event_seat (event_id, seat_id, status)
select e.id, s.id, 'AVAILABLE' from event e join seat s on s.venue_id = e.venue_id
on conflict do nothing;

-- explicit ids do not advance the identity sequences; without this, the next generated id collides
select setval(pg_get_serial_sequence('venue', 'id'), (select max(id) from venue));
select setval(pg_get_serial_sequence('seat', 'id'),  (select max(id) from seat));
select setval(pg_get_serial_sequence('event', 'id'), (select max(id) from event));
```

The tables use `generated by default as identity` rather than `always` precisely so that seeds can insert explicit ids.

**5. The versioned entity (8 min).** Your CAPSTONE-1 types (`Seat`, `Event`, `SeatHold`, `Booking`) stay as the domain model. JPA entities cannot be records, so they are separate classes with a `toDomain()` method. As CAPSTONE-3 decided, availability is booking knowledge, so this one lives in `com.tickethub.booking`:

```java
@Embeddable
public record EventSeatId(@Column(name = "event_id") long eventId,
                          @Column(name = "seat_id") long seatId) implements Serializable {}

@Entity
@Table(name = "event_seat")
public class EventSeatEntity {
    @EmbeddedId
    private EventSeatId id;
    @Enumerated(EnumType.STRING)
    private SeatStatus status;          // enum SeatStatus { AVAILABLE, HELD, BOOKED }
    private UUID holdId;
    @Version
    private long version;

    protected EventSeatEntity() {}      // for JPA

    public void hold(UUID holdId) {
        if (status != SeatStatus.AVAILABLE) {
            throw new SeatUnavailableException(id.eventId(), List.of(id.seatId()));
        }
        this.status = SeatStatus.HELD;
        this.holdId = holdId;
    }

    public void book() { status = SeatStatus.BOOKED; }

    public void release() { status = SeatStatus.AVAILABLE; holdId = null; }

    public EventSeatId getId() { return id; }
    public SeatStatus getStatus() { return status; }
}

public interface EventSeatRepository extends JpaRepository<EventSeatEntity, EventSeatId> {
    @Query("select s from EventSeatEntity s where s.id.eventId = :eventId and s.id.seatId in :seatIds")
    List<EventSeatEntity> findForEvent(long eventId, Collection<Long> seatIds);

    List<EventSeatEntity> findByHoldId(UUID holdId);
}
```

Because of `@Version`, Hibernate writes every change as `update event_seat set ..., version = version + 1 where event_id = ? and seat_id = ? and version = ?`. If that statement updates zero rows, someone changed the row after you read it, and Hibernate throws an optimistic-lock exception.

`BookingEntity` maps the `booking_seat` join table as a value collection:

```java
@ElementCollection
@CollectionTable(name = "booking_seat", joinColumns = @JoinColumn(name = "booking_id"))
@Column(name = "seat_id")
private Set<Long> seatIds = new HashSet<>();
```

`SeatHoldEntity` and `BookingEntity` take their `UUID` id from the domain object (`SeatHold.create`, `Booking`). Write `VenueEntity`, `SeatEntity`, `EventEntity` and `IdempotencyKeyEntity` yourself. They have the same shape and need no version.

**6. `BookingService` (15 min).** It takes over the `HoldService.hold` signature, so `HoldController` only changes the type it injects:

```java
@Service
public class BookingService {
    // constructor-injected: EventSeatRepository eventSeats, SeatHoldRepository holds, BookingRepository bookings,
    // IdempotencyKeyRepository idempotencyKeys, EventQueryService events, Clock clock, TicketHubProperties props

    @Transactional
    public SeatHold hold(long eventId, String userId, String idempotencyKey, List<Long> seatIds) {
        String fingerprint = eventId + ":" + seatIds.stream().sorted().toList();      // same as CAPSTONE-4
        var existing = idempotencyKeys.findById(new IdempotencyKeyId(userId, idempotencyKey));
        if (existing.isPresent()) {
            return replay(existing.get(), fingerprint);       // other fingerprint -> IdempotencyKeyReusedException (422)
        }
        Event event = events.get(eventId);                    // EventNotFoundException -> 404, as before
        List<EventSeatEntity> seats = eventSeats.findForEvent(eventId, seatIds);
        if (seats.size() != seatIds.size()) {
            throw new SeatUnavailableException(eventId, seatIds);   // an unknown seat counts as unavailable
        }
        SeatHold hold = SeatHold.create(eventId, userId, seatIds, clock, props.holdDuration());
        long totalCents = Math.multiplyExact(event.priceCategory().centsPerSeat(), seatIds.size());
        holds.save(SeatHoldEntity.from(hold, totalCents, clock.instant()));
        try {
            idempotencyKeys.saveAndFlush(new IdempotencyKeyEntity(userId, idempotencyKey, fingerprint, hold.id(),
                    clock.instant()));
        } catch (DataIntegrityViolationException sameKeyInFlight) {
            throw new IdempotencyRequestInProgressException(idempotencyKey);         // 409, as in CAPSTONE-4
        }
        seats.forEach(seat -> seat.hold(hold.id()));          // fast path: already HELD/BOOKED -> 409
        try {
            eventSeats.flush();                               // run the versioned UPDATEs now, inside the try
        } catch (OptimisticLockingFailureException lostRace) {
            throw new SeatUnavailableException(eventId, seatIds);   // tx rolls back: no hold, no key
        }
        return hold;
    }
}
```

Read it top to bottom as a story:

- **The idempotency key is inserted before any seat is touched.** A concurrent request with the same key blocks on the primary key until the first one commits, then fails with a unique violation, which becomes `IDEMPOTENCY_IN_PROGRESS`. Its retry is then a clean replay. Inside one transaction, the uncommitted row *is* the "in progress" marker CAPSTONE-4 kept in a map. That is why the `IdempotencyStore` interface can go: the database now does its job atomically.
- **The price is quoted at hold time** and stored on the hold, so confirm charges exactly what the user saw. CAPSTONE-7 replaces this one line with pricing strategies.
- **Why flush explicitly?** Without it, the `UPDATE`s run at commit, after your method has returned, inside the transactional proxy. The exception would then escape as `ObjectOptimisticLockingFailureException`, out of reach of your `try`. Repository calls translate Hibernate's exception into Spring's `OptimisticLockingFailureException`. As a safety net, also add `@ExceptionHandler(OptimisticLockingFailureException.class)` to `ApiExceptionHandler`, returning a `409` with `code: SEAT_UNAVAILABLE`.

Write the rest yourself:

- **`confirm(UUID holdId)`**: load the hold, or throw `HoldNotFoundException`. If `clock.instant()` is not before `expiresAt`, throw `HoldExpiredException` (`410`). If the status is not `HELD`, throw the not-found exception. Otherwise call `book()` on each seat from `findByHoldId`, set the hold to `CONFIRMED`, and save a `BookingEntity` with status `CONFIRMED` and the hold's `total_cents`.
- **`release(UUID holdId)`**: call `release()` on each seat and set the hold to `CANCELLED`. A second `DELETE` then gets `404 HOLD_NOT_FOUND`, as in CAPSTONE-4.
- **`findHold`, `get(UUID bookingId)`, `myBookings(String userId, Pageable)`**: annotate them `@Transactional(readOnly = true)`. Make the `BookingController` endpoints thin wrappers that read `X-User-Id` like `HoldController` does.

`EventQueryService` replaces `EventCatalog` in the same way: `list(page, size)` through a `Pageable` ordered by `startsAt, id`, `get(id)`, and the seat map from `event_seat`. `PageResponse` keeps its shape, filled from Spring Data's `Page`.

**7. Isolation level: leave it alone (2 min, but know why).** Postgres defaults to **READ COMMITTED**, where each statement sees the data committed before that statement began. Here is what happens when two holds race for seat 1007, both having read version 3:

```text
T1: UPDATE ... SET version=4 WHERE seat=1007 AND version=3   -> 1 row, takes the row lock
T2: UPDATE ... SET version=4 WHERE seat=1007 AND version=3   -> waits for T1's row lock
T1: COMMIT
T2: re-checks its WHERE against the new row (version=4)      -> 0 rows -> optimistic-lock failure -> 409
```

The version check plus Postgres's row lock is enough. `REPEATABLE READ` would turn T2's failure into a serialization error that you would also have to map. `SERIALIZABLE` costs more and protects nothing extra here. The alternative is **pessimistic locking**: `@Lock(PESSIMISTIC_WRITE)` issues `SELECT ... FOR UPDATE` and makes T2 wait before it even reads. It suits rows that are almost always contended. Seat claims rarely collide, so optimistic locking fits: no waiting, and the rare loser gets a fast `409`.

**8. Delete the old path (2 min).** Remove everything in the "Deleted" line of the checklist. Keeping the old engine behind a flag would be dead code. Then run the acceptance curls.

## Hints

- **Startup fails with `Schema-validation: missing column`.** An entity field does not match a column. Boot maps `holdId` to `hold_id` automatically, but `rows` does not become `row_count` on its own, so add `@Column(name = "row_count")`.
- **`save()` runs a `SELECT` before the `INSERT`.** Spring Data treats an entity with a non-null id and no `@Version` as existing, so it calls `merge`. Your holds and bookings carry domain UUIDs, so implement `Persistable<UUID>` with an `isNew()` that is `true` until the entity is persisted (a `@Transient` flag set in `@PostLoad`/`@PostPersist`), or accept the extra select.
- **A unique violation on `event` after an admin insert.** You forgot the `setval` lines in the seed.
- **Enum columns:** always use `@Enumerated(EnumType.STRING)`. The default, `ORDINAL`, stores numbers, and inserting a new constant in the middle silently changes what the old rows mean.

## Talk about it in interviews

**"How do you stop two users from buying the same seat?"**
1. *What:* each seat per event is one `event_seat` row with a `version`, and claiming the seat is a versioned update.
2. *How it works inside:* Hibernate issues `UPDATE ... WHERE version = ?`. Postgres row-locks the row, so the second writer waits, re-evaluates the `WHERE` after the first commits, matches zero rows and fails. I flush inside the service so I can turn that failure into a domain `409`, and the hold, its seats and its idempotency key roll back together.
3. *Where it's used:* any "claim a scarce thing" flow: inventory, wallet balances, workflow state transitions.
4. *What goes wrong:* an exception surfacing at commit, where the method cannot catch it. Bulk JPQL updates that skip the version bump. Retry storms on a single hot row, where pessimistic `FOR UPDATE` or a queue is better.

**"How is your idempotency key safe across restarts and concurrent retries?"** The key row is in the same transaction as the hold, under a `(user_id, idem_key)` primary key. A crash cannot leave "hold created, key lost". A concurrent duplicate waits on the key's row lock and gets `409`, then replays. A different body with the same key gets `422`.

**"Optimistic or pessimistic, and which isolation level?"** Walk through the T1/T2 timeline above, and say what each stronger level would cost.

**"Why Flyway instead of `ddl-auto=update`?"** Migrations are versioned, reviewed and repeatable across environments. `update` never drops or renames and cannot migrate data. `validate` catches drift between code and schema at startup.

**"Walk me through your indexes."** Use the table in step 3: one query per index, and partial indexes to keep the hot sets small.
