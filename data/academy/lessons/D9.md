## Where we are

D4 showed you that Spring Boot's "magic" is ordinary `@Configuration` classes. They are listed in a file, guarded by `@Conditional*`, and they back off when you define your own bean. This lesson goes one level lower, to the hooks Spring itself uses to *build* the container. Then you will use those hooks to write your own starter, the way the Boot team does.

## The problem

Say your team has twelve services, and every one of them needs the same thing: log any HTTP request slower than a threshold, with a way to switch it off. Today each service copies the same filter class and the same `@Bean` method. One team changes its copy, the others don't, and they drift apart.

You want to add one dependency and get the behaviour, configured through properties, removable with `enabled=false`, and overridable by declaring your own bean. That is exactly what `spring-boot-starter-web` does for Tomcat. To build one, you need to know where Spring lets outside code take part.

## The container has two phases

To place the hooks, first recall how the container starts. It works in two phases:

```text
Phase 1: DEFINITIONS (recipes, no objects yet)
  read @Configuration, @ComponentScan, @Import, auto-config list
  → BeanDefinition objects: class, scope, constructor args, lazy?, ...
  ── hook: BeanDefinitionRegistryPostProcessor / BeanFactoryPostProcessor
Phase 2: INSTANCES (objects)
  for each singleton definition: instantiate → inject → init
  ── hook: BeanPostProcessor (before/after init, can swap the object)
```

A **`BeanDefinition`** is the *recipe* for a bean: which class to use, its scope, whether it is lazy, and its constructor arguments. Creating the actual object is a separate, later step. Each hook below belongs to one of the two phases.

## BeanFactoryPostProcessor: edit the recipes

A **`BeanFactoryPostProcessor`** (BFPP) runs after all definitions are loaded and *before any normal bean is created*. It can read and change definitions:

```java
@Bean
static BeanFactoryPostProcessor reportOurBeans() {     // static: see Gotchas
    return beanFactory -> {
        for (String name : beanFactory.getBeanDefinitionNames()) {
            String cls = beanFactory.getBeanDefinition(name).getBeanClassName();
            if (cls != null && cls.startsWith("com.companywiseprep")) {
                System.out.println("definition: " + name + " -> " + cls);
            }
        }
    };
}
```

Spring uses this hook constantly. `PropertySourcesPlaceholderConfigurer` is a BFPP that resolves `${...}` placeholders in definitions. Most importantly, **`ConfigurationClassPostProcessor`** is a `BeanDefinitionRegistryPostProcessor`, the variant that may also *add* definitions. It is the processor that reads your `@Configuration`, `@ComponentScan`, `@Bean` and `@Import` annotations. Auto-configuration enters the container through this one class.

**The rule:** a BFPP changes *recipes*. It must not ask for beans, because calling `getBean()` here creates them too early, before the other post-processors have run.

## BeanPostProcessor: wrap the objects

A **`BeanPostProcessor`** (BPP) is called for *every bean instance*, around its init callbacks: `postProcessBeforeInitialization` first, then `postProcessAfterInitialization`. Whatever it returns *becomes the bean*. That return value is how proxies are born. `@Transactional`, `@Async` and `@Cacheable` all come from BPPs that return a proxy instead of your object (D3).

Here is a BPP that adds a "warn if slow" proxy to any bean whose class carries a marker annotation:

```java
@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.TYPE)
@interface WarnIfSlow {}

@Component
class WarnIfSlowPostProcessor implements BeanPostProcessor {
    private static final Logger log = LoggerFactory.getLogger(WarnIfSlowPostProcessor.class);

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        if (!AopUtils.getTargetClass(bean).isAnnotationPresent(WarnIfSlow.class)) return bean;
        ProxyFactory pf = new ProxyFactory(bean);
        pf.setProxyTargetClass(true);                       // CGLIB subclass proxy
        pf.addAdvice((MethodInterceptor) inv -> {
            long start = System.nanoTime();
            try { return inv.proceed(); }
            finally {
                long ms = (System.nanoTime() - start) / 1_000_000;
                if (ms > 100) log.warn("{}.{} took {} ms", beanName, inv.getMethod().getName(), ms);
            }
        });
        return pf.getProxy();
    }
}
```

Put `@WarnIfSlow` on `BankService` and every public call is now timed. The `BankService` class itself does not change.

**The rule:** use a BPP when you want to change *objects*. Typical jobs are wrapping a bean in a proxy, validating it, or registering it somewhere. Use a BFPP when you want to change *definitions*.

## ImportSelector: choose configuration in code

`@Import(SomeConfig.class)` pulls in one configuration class. An **`ImportSelector`** decides *at startup* which classes to import, and returns their names:

```java
@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.TYPE)
@Import(AuditSelector.class)
public @interface EnableAudit { boolean toDatabase() default false; }

class AuditSelector implements ImportSelector {
    @Override
    public String[] selectImports(AnnotationMetadata meta) {
        Map<String, Object> attrs = meta.getAnnotationAttributes(EnableAudit.class.getName());
        boolean db = attrs != null && (Boolean) attrs.get("toDatabase");
        return new String[] { db ? DbAuditConfig.class.getName() : LogAuditConfig.class.getName() };
    }
}
```

This is how every `@EnableXxx` annotation works. `@EnableCaching`, for example, imports a selector that picks proxy-based or AspectJ-based caching.

Two variants matter here:

- **`ImportBeanDefinitionRegistrar`** registers definitions directly. `@EnableJpaRepositories` uses one to create a bean for every repository interface.
- **`DeferredImportSelector`** runs *after* all your own configuration has been processed.

Boot's `@EnableAutoConfiguration` imports `AutoConfigurationImportSelector`, which is a `DeferredImportSelector`. Because it runs last, `@ConditionalOnMissingBean` in an auto-configuration can already see the beans *you* defined, and so it can back off.

## The AutoConfiguration.imports file

How does `AutoConfigurationImportSelector` find candidate classes? It reads every file on the classpath named:

```text
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

The file holds one fully-qualified class name per line. Open the actuator-autoconfigure jar and you will see its list, starting with `...audit.AuditAutoConfiguration`. Each listed class is annotated `@AutoConfiguration`, which is a `@Configuration` that can declare `before`/`after` ordering. Boot evaluates each class's conditions and keeps the ones that match.

This file replaced the old `spring.factories` mechanism for auto-configuration in Boot 2.7. Boot 3 and later read only the `.imports` file for this purpose.

## Lab (~10 min): a tiny starter

You will build a "slow request logger" starter. To keep it to ten minutes, it lives inside this app, in a package **outside** the component-scan root, so only the imports file can bring it in.

1. Add `src/main/java/prep/timing/TimingProperties.java`:

```java
package prep.timing;

@ConfigurationProperties("timing")
public record TimingProperties(@DefaultValue("true") boolean enabled,
                               @DefaultValue("500ms") Duration slowThreshold) {}
```

2. Add `SlowRequestFilter.java`:

```java
package prep.timing;

public class SlowRequestFilter extends OncePerRequestFilter {
    private static final Logger log = LoggerFactory.getLogger(SlowRequestFilter.class);
    private final Duration threshold;
    public SlowRequestFilter(Duration threshold) { this.threshold = threshold; }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        long start = System.nanoTime();
        try { chain.doFilter(req, res); }
        finally {
            Duration took = Duration.ofNanos(System.nanoTime() - start);
            if (took.compareTo(threshold) > 0) log.warn("SLOW {} {} took {} ms", req.getMethod(), req.getRequestURI(), took.toMillis());
        }
    }
}
```

3. Add the auto-configuration:

```java
package prep.timing;

@AutoConfiguration
@ConditionalOnWebApplication(type = ConditionalOnWebApplication.Type.SERVLET)
@ConditionalOnProperty(prefix = "timing", name = "enabled", havingValue = "true", matchIfMissing = true)
@EnableConfigurationProperties(TimingProperties.class)
public class TimingAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean
    SlowRequestFilter slowRequestFilter(TimingProperties props) {
        return new SlowRequestFilter(props.slowThreshold());
    }
}
```

4. Create `src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` containing a single line: `prep.timing.TimingAutoConfiguration`.

5. Test it without starting a server, using `ApplicationContextRunner` (from `spring-boot-test`):

```java
class TimingAutoConfigurationTest {
    private final WebApplicationContextRunner runner = new WebApplicationContextRunner()
            .withConfiguration(AutoConfigurations.of(TimingAutoConfiguration.class));

    @Test void onByDefault() {
        runner.run(ctx -> assertThat(ctx).hasSingleBean(SlowRequestFilter.class));
    }
    @Test void switchedOff() {
        runner.withPropertyValues("timing.enabled=false")
              .run(ctx -> assertThat(ctx).doesNotHaveBean(SlowRequestFilter.class));
    }
    @Test void backsOffForUserBean() {
        runner.withUserConfiguration(MyFilter.class)
              .run(ctx -> assertThat(ctx).getBean(SlowRequestFilter.class).isSameAs(ctx.getBean("mine")));
    }
    @Configuration static class MyFilter {
        @Bean SlowRequestFilter mine() { return new SlowRequestFilter(Duration.ofSeconds(5)); }
    }
}
```

**Observe:**

- Run the app with `timing.slow-threshold=1ms` and call any endpoint. You should see `SLOW GET /api/companies ...`.
- Start the app with `--debug` and find `TimingAutoConfiguration` in the **CONDITIONS EVALUATION REPORT**, under positive matches.
- Set `timing.enabled=false` and watch it move to negative matches, with the reason given.
- **To make it a real starter:** move the `prep.timing` package into its own Maven module, `timing-spring-boot-autoconfigure`. Add an empty `timing-spring-boot-starter` module that depends on it. Add `spring-boot-configuration-processor` as an optional dependency, so IDEs autocomplete `timing.*` properties.

## Gotchas

- **A non-`static` `@Bean` method for a BFPP** forces its enclosing `@Configuration` to be created early, so that class's `@Value` fields and some other processing may not apply. Spring logs a warning about it. Declare BFPP beans `static`.
- **Injecting ordinary beans into a BPP** forces those beans to be created before all BPPs are registered. You get the info message "Bean 'x' is not eligible for getting processed by all BeanPostProcessors", and those beans may miss their proxies, for example `@Transactional`. Keep BPP dependencies minimal, or make them lazy (`ObjectProvider`).
- **A component-scanned auto-configuration.** If your auto-config class sits under the app's scan root, it gets picked up as a regular configuration. It then loses its ordering and is processed *before* user beans, which breaks `@ConditionalOnMissingBean`. Keep auto-configs in a package outside the scan root, and list them only in the imports file.
- **Starter naming.** `spring-boot-starter-*` is reserved for the Boot team. Third-party starters are named `xyz-spring-boot-starter`.
- **`@ConditionalOnMissingBean` on a regular (non-auto) configuration** is evaluated in whatever order the classes happen to be processed, so the result is unreliable. It is only dependable inside auto-configurations, because those are deferred.
- **No switch-off property.** Always give your starter a `prefix.enabled` property with `matchIfMissing = true`, and back off on a user bean.

## In interviews

Typical prompts are "How does Spring Boot auto-configuration work?", "BeanPostProcessor vs BeanFactoryPostProcessor?", "How are `@Transactional` proxies created?" and "How would you write your own starter?". No bank question targets this directly yet. [SOLID principles and dependency inversion](#/q/solid-principles) is the nearest relative, since starters are dependency inversion applied at the level of whole modules.

**Follow-up: "How does `@ConditionalOnMissingBean` know about my bean?"** Auto-configurations are imported through a `DeferredImportSelector`, so they are processed after all user configuration. Conditions are checked during the definition phase, by which point the user's bean definitions are already registered.

**Follow-up: "Where would you hook in to rename every bean of type X?"** In a `BeanDefinitionRegistryPostProcessor`, because that is a definition-phase job.

## Explain it in 2 minutes

*"Walk me through how a starter adds beans to my app."*

- The starter's jar contains `META-INF/spring/...AutoConfiguration.imports`, which lists `@AutoConfiguration` classes.
- `@SpringBootApplication` includes `@EnableAutoConfiguration`, which imports `AutoConfigurationImportSelector`, a *deferred* import selector.
- `ConfigurationClassPostProcessor`, a registry post-processor, processes user configuration first, then the deferred auto-configs, evaluating `@Conditional*` on each.
- Matching configs register bean definitions. `@ConditionalOnMissingBean` backs off when the user already defined one.
- Later, during instantiation, BPPs wrap beans in proxies where needed.
- The `--debug` conditions report shows every decision.

### Answers

1. A `BeanFactoryPostProcessor`, using `beanDefinition.setLazyInit(true)`. Laziness is part of the recipe, and a BPP runs only after the instance already exists.
2. So Spring can call it without first creating its enclosing configuration bean. Creating that bean early would skip later processing on it.
3. It is a `DeferredImportSelector`, so it runs after all user configuration is processed. That lets conditions like `@ConditionalOnMissingBean` see user beans.
