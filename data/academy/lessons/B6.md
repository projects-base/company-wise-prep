## Where we are

From B4 you know that platform threads are expensive, so we pool them and size the pool carefully. From B5 you know one way around that cost: async pipelines that never block a thread. This lesson covers the other way, which arrived in Java 21. **Virtual threads** make blocking cheap, so plain, sequential, blocking code can handle very high concurrency.

## The problem

A typical request handler looks like this:

```java
User u = userRepo.find(id);         // waits ~20 ms on the database
List<Order> o = orderClient.get(u); // waits ~100 ms on HTTP
return render(u, o);                // ~1 ms of actual CPU
```

The thread spends more than 99% of its time waiting. With a pool of 200 platform threads, the service can have at most 200 requests in flight, even while the CPU sits almost idle. You can raise the pool size, but each platform thread is an OS thread with a large stack, so thousands of them get expensive. Or you can rewrite everything as `CompletableFuture` chains or reactive streams. That scales, but the code becomes harder to write, read and debug: stack traces stop telling you which request you were serving.

Virtual threads keep the simple blocking code and remove the cap.

## What a virtual thread is

A **virtual thread** is a `java.lang.Thread` that the **JVM** schedules, instead of the operating system. A virtual thread runs by being **mounted** on an ordinary platform thread, called its **carrier**. The carriers come from a small `ForkJoinPool`, by default one per CPU core.

When a virtual thread blocks (in `sleep`, a socket read, `BlockingQueue.take`, `ReentrantLock.lock`, and so on), the JVM **unmounts** it. Its stack frames are copied to the heap and the carrier is freed to run another virtual thread. When the blocking operation completes, the virtual thread is mounted again, possibly on a different carrier.

```text
 carriers (≈ CPU cores)      virtual threads (thousands to millions)

 carrier-1 ──runs──► VT-7  ── blocks on socket ──► unmounted (stack on heap)
 carrier-1 ──runs──► VT-42 ...                         │ data arrives
 carrier-2 ──runs──► VT-3  ...                         ▼
                                                  VT-7 queued, remounted on any free carrier
```

Why it is cheap: a virtual thread's stack lives on the heap and grows only as deep as it needs to. Creating one is roughly as cheap as creating a small object. Blocking costs a few memory copies instead of an OS context switch, so you can create one **per task** and simply throw it away afterwards.

## Creating them

```java
Thread t = Thread.ofVirtual().name("req-", 0).start(() -> handle(request));
Thread.startVirtualThread(() -> handle(request));

try (ExecutorService ex = Executors.newVirtualThreadPerTaskExecutor()) {
    ex.submit(() -> handle(request));         // a brand-new virtual thread for every task
}
```

In Spring Boot 3.2 and later, setting `spring.threads.virtual.enabled=true` makes the web server and `@Async` run on virtual threads.

There are some facts to remember:

- Virtual threads are always **daemon** threads.
- Their priority is ignored.
- `getState()` reports the same states as for platform threads (L3).
- Interrupts work as described in B1.

## What they do not do

Virtual threads make **waiting** cheap. They do not make **computing** faster. A CPU-bound task still needs a core, and there are only as many carriers as cores. So the rule is simple:

- **Many blocking tasks:** use virtual threads.
- **CPU-heavy work:** use a pool sized to the number of cores (B4).

## Don't pool them; limit with a semaphore

A pool exists to reuse expensive threads, and virtual threads are not expensive. Pooling them only adds a cap you did not want. If what you actually need is to *limit concurrency* (for example, "the downstream service accepts at most 20 calls at once"), limit the *resource*, not the threads:

```java
private final Semaphore dbPermits = new Semaphore(20);

String query() throws InterruptedException {
    dbPermits.acquire();                  // a virtual thread waiting here costs almost nothing
    try { return runQuery(); } finally { dbPermits.release(); }
}
```

## Pinning: when a virtual thread cannot unmount

Sometimes the JVM cannot unmount a virtual thread that is blocking. It is then **pinned**: it stays on its carrier, and the carrier is blocked too. In Java 21, two situations cause pinning:

1. Blocking **inside a `synchronized` block or method**. The monitor is tied to the carrier thread.
2. Blocking while there is a **native method or foreign function** frame on the stack.

A little pinning is harmless. Pinning on a hot path, such as a `synchronized` method that does network I/O on every request, can block every carrier at once. Throughput then collapses to the number of cores, even though nothing is using CPU.

You can see it in two ways:

- `-Djdk.tracePinnedThreads=short` (or `=full`) prints a stack trace whenever a virtual thread blocks while pinned. This flag exists in Java 21 to 23.
- The JFR event `jdk.VirtualThreadPinned` records pinned blocking that lasts longer than a threshold (20 ms by default).

To fix it on Java 21, replace a `synchronized` block that guards blocking operations with a `ReentrantLock`, which unmounts properly. Keep `synchronized` for short critical sections that never block. **Java 24 (JEP 491) removed the `synchronized` cause**, so virtual threads now unmount inside monitors. Native frames still pin. Interviewers may ask about either version, so say which one you mean.

## `ThreadLocal` with millions of threads

`ThreadLocal` still works, but every virtual thread gets its own copy. A `ThreadLocal` used as a cache (for example, one expensive formatter per thread) gives you a million formatters. Pass context explicitly, or use `ScopedValue`, which is a preview feature in Java 21 designed for this case.

## Structured concurrency (preview in Java 21)

**Structured concurrency** means that subtasks started inside a block of code finish (or are cancelled) before the block exits, just as local variables do not outlive their scope. With a plain executor, a failed sibling task keeps running and leaks. `StructuredTaskScope` fixes that:

```java
// Java 21 preview API: compile and run with --enable-preview --source 21
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask<String> user   = scope.fork(() -> findUser());      // each fork is a new virtual thread
    Subtask<String> orders = scope.fork(() -> fetchOrders());
    scope.join()            // wait for both, or for the first failure
         .throwIfFailed();  // rethrow it; the other subtask has already been cancelled (interrupted)
    return new Page(user.get(), orders.get());
}
```

If `fetchOrders` fails, `findUser` is interrupted, and the method throws an `ExecutionException`. No task outlives the `try` block. Thread dumps also show the parent-child relationship between the tasks. The API was reshaped in later previews (Java 25 uses `StructuredTaskScope.open(...)` with "joiners"), so learn the idea rather than memorizing the method names.

## Lab (~10 min)

Save this as `VirtualLab.java`.

```java
import java.time.Duration;
import java.util.concurrent.*;
import java.util.concurrent.locks.ReentrantLock;
import java.util.stream.IntStream;

public class VirtualLab {
    public static void main(String[] args) {
        if (args.length == 0) {
            // Part 1: 2,000 tasks that each block for 1 second
            time("platform pool of 200 ", Executors.newFixedThreadPool(200), 2_000, VirtualLab::blockingCall);
            time("virtual thread per task", Executors.newVirtualThreadPerTaskExecutor(), 2_000, VirtualLab::blockingCall);
        } else {
            // Part 2 (run with "pin" and the flags shown below): 10 tasks, each blocking 200 ms
            time("sleep inside synchronized", Executors.newVirtualThreadPerTaskExecutor(), 10, VirtualLab::pinned);
            time("sleep inside ReentrantLock", Executors.newVirtualThreadPerTaskExecutor(), 10, VirtualLab::notPinned);
        }
    }

    static void blockingCall() { sleep(Duration.ofSeconds(1)); }

    static void pinned() {
        Object lock = new Object();                          // a private lock: no contention at all
        synchronized (lock) { sleep(Duration.ofMillis(200)); }   // blocks while holding a monitor
    }

    static void notPinned() {
        ReentrantLock lock = new ReentrantLock();
        lock.lock();
        try { sleep(Duration.ofMillis(200)); } finally { lock.unlock(); }
    }

    static void time(String name, ExecutorService pool, int tasks, Runnable task) {
        long t0 = System.nanoTime();
        try (pool) { IntStream.range(0, tasks).forEach(i -> pool.submit(task)); }   // close() waits
        System.out.printf("%s: %,d tasks in %,d ms%n", name, tasks, (System.nanoTime() - t0) / 1_000_000);
    }

    static void sleep(Duration d) {
        try { Thread.sleep(d); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}
```

**Part 1:** run `java VirtualLab.java`. You should see something like this:

```text
platform pool of 200 : 2,000 tasks in ~10,000 ms   (2,000 / 200 threads × 1 s)
virtual thread per task: 2,000 tasks in ~1,000 ms   (all wait at the same time)
```

The tasks are identical blocking code. The only difference is that waiting no longer ties up an OS thread.

**Part 2 (pinning):** run with a single carrier so that the effect is easy to see.

```text
java -Djdk.virtualThreadScheduler.parallelism=1 -Djdk.virtualThreadScheduler.maxPoolSize=1 -Djdk.tracePinnedThreads=short VirtualLab.java pin
```

On Java 21 you should see:

- A trace like `VirtualThread[#26]/runnable@ForkJoinPool-1-worker-1 reason:MONITOR ... <== monitors:1` pointing at the `synchronized` line.
- `sleep inside synchronized: 10 tasks in ~2,000 ms`. Each pinned task held the only carrier for its whole 200 ms, so the tasks ran one after another, even though **there is no lock contention at all**.
- `sleep inside ReentrantLock: 10 tasks in ~200 ms`. Each task unmounted while it slept, so all ten waited together.

(`maxPoolSize=1` stops the scheduler from adding a temporary extra carrier to compensate, which it sometimes does.) On Java 24 or later, both lines take about 200 ms. That is JEP 491 at work.

## Gotchas

- **`synchronized` around blocking I/O on Java 21–23 pins the carrier.** Use `ReentrantLock` for those sections, or upgrade to Java 24 or later.
- **Pooling virtual threads.** It brings back the cap you were trying to remove. Create one per task, and use a `Semaphore` to protect scarce resources.
- **Expecting a CPU speed-up.** Virtual threads help only when tasks wait. CPU-bound work still needs a pool sized to the cores.
- **Unbounded fan-out hitting downstream limits.** It is now easy to fire 100,000 concurrent DB calls. The connection pool or the remote service becomes the bottleneck. Limit concurrency deliberately.
- **`ThreadLocal` caches** multiply with millions of threads. Pass context explicitly or use `ScopedValue`.
- **Structured concurrency is a preview feature in Java 21.** It needs `--enable-preview`, and its API changed in later versions.

## In interviews

Senior rounds often ask "How would you handle 10,000 concurrent slow requests?" The modern answer covers virtual threads, pinning, and protecting downstream services with semaphores. Bank questions where this comes up: [Process vs thread, shared variables and race conditions](#/q/process-vs-thread) (the follow-up is often "and what is a virtual thread?") and [Design a Message Queue (producer-consumer)](#/q/design-message-queue) (where consumer threads spend most of their time blocked).

Typical follow-ups:

- **"Virtual threads vs reactive or `CompletableFuture`?"** Both get high concurrency without one OS thread per request. Virtual threads keep blocking-style code, readable stack traces and ordinary debugging. Reactive still offers streaming and backpressure operators. Neither helps CPU-bound work.
- **"What is pinning and how do you detect it?"** A blocked virtual thread that cannot unmount (because of `synchronized` on Java 21–23, or a native frame) holds its carrier. Detect it with `jdk.tracePinnedThreads` or the JFR `jdk.VirtualThreadPinned` event. Fix it with `ReentrantLock`, or by upgrading.

## Explain it in 2 minutes

*"What are virtual threads and when would you use them?"*

- They are JVM-scheduled threads mounted on a few carrier platform threads. When they block, they unmount and their stack moves to the heap.
- They are cheap enough to create one per task and never pool, so blocking code scales to very high concurrency.
- They help I/O-bound work only. CPU-bound work still needs cores.
- Pinning happens with `synchronized` (Java 21–23) or native frames; detect it with a trace flag or JFR, and fix it with `ReentrantLock`.
- Limit downstream concurrency with semaphores, not pools.
- Structured concurrency scopes subtasks so that failures cancel their siblings (preview).

## Check yourself

1. What happens to a virtual thread's stack when it blocks on a socket read?
2. Your service uses virtual threads, but throughput is capped at about 8 concurrent requests on an 8-core box. What do you suspect first?
3. Why is `Executors.newFixedThreadPool(100, virtualThreadFactory)` usually a mistake?
4. Will virtual threads speed up a service that resizes images all day?
5. In `ShutdownOnFailure`, what happens to the other subtasks when one fails?

### Answers

1. The virtual thread unmounts, its frames are copied to the heap, and the carrier runs other virtual threads. It is remounted when data arrives.
2. Pinning. Every carrier is stuck in blocking code inside `synchronized` or a native frame. Check `jdk.tracePinnedThreads` or the JFR `VirtualThreadPinned` events.
3. It re-imposes a cap of 100 tasks at a time and pools threads that are cheap to create. Use one virtual thread per task, plus a `Semaphore` if a resource needs limiting.
4. No. Image resizing is CPU-bound and needs cores. Use a pool sized to the cores.
5. The scope shuts down and interrupts them. `join().throwIfFailed()` then rethrows the first failure.
