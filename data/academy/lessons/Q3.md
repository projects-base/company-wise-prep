## Where we are

From Q2 you can collapse rows into groups with `GROUP BY`, filter groups with `HAVING`, and break a
problem into steps with CTEs. The cost of `GROUP BY` is that the individual rows disappear. This
lesson adds **window functions**, which compute aggregates, rankings and "previous row" values while
**keeping every row**. They are the most-tested SQL feature in interviews after joins.

## The problem

Three requests that `GROUP BY` handles badly:

1. "Show each bet with **its punter's total turnover** next to it, and its share of that total."
2. "Number each punter's bets 1, 2, 3… in the order they were placed."
3. "Show each wallet transaction with the **running balance** after it."

With Q2 tools you'd aggregate in a CTE and join it back, or write a correlated subquery per row. Both
work, but they are clumsy, and for running totals they get slow. Window functions do all three in
one pass.

## OVER(): an aggregate that keeps the rows

Compare the two queries. `GROUP BY` collapses the rows:

```sql
SELECT user_id, SUM(stake) AS user_turnover
FROM bets WHERE user_id IN (1, 2) GROUP BY user_id ORDER BY user_id;
```

| user_id | user_turnover |
|---|---|
| 1 | 110.00 |
| 2 | 185.00 |

Add `OVER (…)` after the aggregate, and it becomes a **window function**. It computes over a set of
related rows (the **window**) but writes the result onto every row:

```sql
SELECT id, user_id, stake,
       SUM(stake) OVER (PARTITION BY user_id) AS user_turnover
FROM bets WHERE user_id IN (1, 2) ORDER BY user_id, id;
```

| id | user_id | stake | user_turnover |
|---|---|---|---|
| 1 | 1 | 20.00 | 110.00 |
| 2 | 1 | 10.00 | 110.00 |
| 3 | 1 | 15.00 | 110.00 |
| 4 | 1 | 25.00 | 110.00 |
| 5 | 1 | 30.00 | 110.00 |
| 6 | 1 | 10.00 | 110.00 |
| 7 | 2 | 50.00 | 185.00 |
| 8 | 2 | 50.00 | 185.00 |
| 9 | 2 | 20.00 | 185.00 |
| 10 | 2 | 40.00 | 185.00 |
| 11 | 2 | 25.00 | 185.00 |

**`PARTITION BY user_id`** splits the rows into groups, like `GROUP BY`, but the rows aren't merged.
Each row sees the total of its own partition. With empty parentheses, `OVER ()`, the window is the
whole result.

```sql
SELECT id, stake, SUM(stake) OVER () AS all_turnover, COUNT(*) OVER () AS all_bets
FROM bets WHERE user_id = 4 ORDER BY id;
```

| id | stake | all_turnover | all_bets |
|---|---|---|---|
| 16 | 10.00 | 25.00 | 3 |
| 17 | 10.00 | 25.00 | 3 |
| 18 | 5.00 | 25.00 | 3 |

Note that "whole result" means after `WHERE`. The window sees only Dev's three bets.

Because the row and the total sit side by side, request 1 is now a one-liner:

```sql
SELECT id, user_id, stake,
       ROUND(100 * stake / SUM(stake) OVER (PARTITION BY user_id), 1) AS pct_of_user
FROM bets WHERE user_id = 2 ORDER BY id;
```

| id | user_id | stake | pct_of_user |
|---|---|---|---|
| 7 | 2 | 50.00 | 27.0 |
| 8 | 2 | 50.00 | 27.0 |
| 9 | 2 | 20.00 | 10.8 |
| 10 | 2 | 40.00 | 21.6 |
| 11 | 2 | 25.00 | 13.5 |

An analogy: `GROUP BY` is a summary report with one line per team. A window function is the full
player list with a "team total" column added. It breaks down for ordered windows (next sections),
where each row can see a *different* slice of its partition.

## ORDER BY inside OVER: numbering rows

Put `ORDER BY` inside the `OVER` clause, and the rows of each partition have an order. **Ranking
functions** use that order. `ROW_NUMBER()` numbers the rows 1, 2, 3… within each partition. That is
request 2:

```sql
SELECT user_id, id, placed_at,
       ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY placed_at) AS bet_no
FROM bets WHERE user_id IN (1, 4) ORDER BY user_id, bet_no;
```

| user_id | id | placed_at | bet_no |
|---|---|---|---|
| 1 | 1 | 2026-08-18 10:00:00 | 1 |
| 1 | 2 | 2026-08-19 12:00:00 | 2 |
| 1 | 4 | 2026-09-05 18:00:00 | 3 |
| 1 | 3 | 2026-09-10 09:00:00 | 4 |
| 1 | 5 | 2026-09-12 20:00:00 | 5 |
| 1 | 6 | 2026-10-01 08:00:00 | 6 |
| 4 | 16 | 2026-08-20 19:30:00 | 1 |
| 4 | 17 | 2026-08-20 19:30:00 | 2 |
| 4 | 18 | 2026-09-07 19:00:00 | 3 |

Asha's bet 4 comes before bet 3 because it was placed earlier. The order inside `OVER` is
independent of the final `ORDER BY` of the query.

## ROW_NUMBER vs RANK vs DENSE_RANK

The three ranking functions differ only in how they treat **ties** (rows that are equal in the
`ORDER BY`):

```sql
SELECT id, stake,
       ROW_NUMBER() OVER (ORDER BY stake DESC) AS row_num,
       RANK()       OVER (ORDER BY stake DESC) AS rnk,
       DENSE_RANK() OVER (ORDER BY stake DESC) AS dense_rnk
FROM bets
WHERE stake >= 30
ORDER BY stake DESC, id;
```

| id | stake | row_num | rnk | dense_rnk |
|---|---|---|---|---|
| 14 | 100.00 | 1 | 1 | 1 |
| 19 | 100.00 | 2 | 1 | 1 |
| 7 | 50.00 | 6 | 3 | 2 |
| 8 | 50.00 | 3 | 3 | 2 |
| 12 | 50.00 | 5 | 3 | 2 |
| 13 | 50.00 | 4 | 3 | 2 |
| 10 | 40.00 | 7 | 7 | 3 |
| 5 | 30.00 | 8 | 8 | 4 |

```text
ROW_NUMBER  1 2 3 4 5 6 7 8   always distinct; ties broken arbitrarily
RANK        1 1 3 3 3 3 7 8   ties share; next rank skips (Olympic medals: 1, 1, 3)
DENSE_RANK  1 1 2 2 2 2 3 4   ties share; no gaps
```

Look at `row_num` for the four 50.00 bets: 6, 3, 5, 4. That was PostgreSQL. **H2 numbered the same
rows 3, 4, 5, 6.** Both are correct, because `ROW_NUMBER` over tied rows is **non-deterministic**: any
order of the tied rows is allowed. If the numbering matters, add a tie-breaker:
`ROW_NUMBER() OVER (ORDER BY stake DESC, id)`. With it, both engines give 3, 4, 5, 6 for bets 7, 8,
12, 13.

How to choose: "exactly N rows" → `ROW_NUMBER`. "The Nth distinct value" → `DENSE_RANK`.
"Competition ranking with gaps" → `RANK`.

## Running totals and the frame

With `ORDER BY` inside `OVER`, an aggregate becomes **cumulative**: each row sees its partition from
the start up to itself. That is request 3, Asha's wallet balance:

```sql
SELECT id, created_at, type, amount,
       SUM(amount) OVER (PARTITION BY user_id ORDER BY created_at, id) AS balance
FROM wallet_transactions
WHERE user_id = 1
ORDER BY created_at, id;
```

| id | created_at | type | amount | balance |
|---|---|---|---|---|
| 1 | 2026-08-01 09:00:00 | DEPOSIT | 100.00 | 100.00 |
| 2 | 2026-08-18 10:00:00 | STAKE | -20.00 | 80.00 |
| 3 | 2026-08-19 12:00:00 | STAKE | -10.00 | 70.00 |
| 4 | 2026-08-20 21:40:00 | PAYOUT | 61.00 | 131.00 |
| 5 | 2026-08-25 08:00:00 | WITHDRAWAL | -50.00 | 81.00 |

The set of rows an aggregate sees from the current row is called the **frame**. Once there is an
`ORDER BY`, the default frame is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. `RANGE` means
"up to the current row **and every row tied with it** in the ORDER BY". That surprises people when
there are ties. Dev's bets 16 and 17 share a timestamp:

```sql
SELECT id, placed_at, stake,
       SUM(stake) OVER (ORDER BY placed_at)                                          AS default_frame,
       SUM(stake) OVER (ORDER BY placed_at ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS rows_frame
FROM bets
WHERE placed_at < TIMESTAMP '2026-08-21 00:00:00'
ORDER BY placed_at, id;
```

| id | placed_at | stake | default_frame | rows_frame |
|---|---|---|---|---|
| 1 | 2026-08-18 10:00:00 | 20.00 | 20.00 | 20.00 |
| 2 | 2026-08-19 12:00:00 | 10.00 | 30.00 | 30.00 |
| 7 | 2026-08-19 14:00:00 | 50.00 | 80.00 | 80.00 |
| 8 | 2026-08-20 18:00:00 | 50.00 | 130.00 | 130.00 |
| 12 | 2026-08-20 19:00:00 | 50.00 | 180.00 | 180.00 |
| 16 | 2026-08-20 19:30:00 | 10.00 | 200.00 | 190.00 |
| 17 | 2026-08-20 19:30:00 | 10.00 | 200.00 | 200.00 |

With the default `RANGE`, both tied rows show 200.00. `ROWS` counts physical rows one at a time, so
it shows 190.00 and then 200.00. Which tied row comes first under `ROWS` is arbitrary, though. The
real fix is a unique `ORDER BY` (`placed_at, id`), and then both frames agree.

A frame can also be a sliding window. `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` means "this row and
the two before it". That gives a moving average of Asha's last three stakes:

```sql
SELECT id, placed_at, stake,
       ROUND(AVG(stake) OVER (PARTITION BY user_id ORDER BY placed_at
                              ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2) AS avg_last_3
FROM bets WHERE user_id = 1 ORDER BY placed_at;
```

| id | placed_at | stake | avg_last_3 |
|---|---|---|---|
| 1 | 2026-08-18 10:00:00 | 20.00 | 20.00 |
| 2 | 2026-08-19 12:00:00 | 10.00 | 15.00 |
| 4 | 2026-09-05 18:00:00 | 25.00 | 18.33 |
| 3 | 2026-09-10 09:00:00 | 15.00 | 16.67 |
| 5 | 2026-09-12 20:00:00 | 30.00 | 23.33 |
| 6 | 2026-10-01 08:00:00 | 10.00 | 18.33 |

The frame keywords: `UNBOUNDED PRECEDING` (the partition start), `n PRECEDING`, `CURRENT ROW`,
`n FOLLOWING` and `UNBOUNDED FOLLOWING` (the partition end). Ranking functions and `LAG`/`LEAD`
ignore the frame. Only aggregates and `FIRST_VALUE`/`LAST_VALUE` use it.

## LAG and LEAD: the previous and next row

`LAG(col)` returns `col` from the **previous** row of the partition, and `LEAD(col)` from the
**next** row. They replace the self-join "find the row just before this one".

```sql
SELECT id, placed_at, stake,
       LAG(stake)  OVER (PARTITION BY user_id ORDER BY placed_at) AS prev_stake,
       LEAD(stake) OVER (PARTITION BY user_id ORDER BY placed_at) AS next_stake,
       stake - LAG(stake) OVER (PARTITION BY user_id ORDER BY placed_at) AS change
FROM bets WHERE user_id = 1 ORDER BY placed_at;
```

| id | placed_at | stake | prev_stake | next_stake | change |
|---|---|---|---|---|---|
| 1 | 2026-08-18 10:00:00 | 20.00 | NULL | 10.00 | NULL |
| 2 | 2026-08-19 12:00:00 | 10.00 | 20.00 | 25.00 | -10.00 |
| 4 | 2026-09-05 18:00:00 | 25.00 | 10.00 | 15.00 | 15.00 |
| 3 | 2026-09-10 09:00:00 | 15.00 | 25.00 | 30.00 | -10.00 |
| 5 | 2026-09-12 20:00:00 | 30.00 | 15.00 | 10.00 | 15.00 |
| 6 | 2026-10-01 08:00:00 | 10.00 | 30.00 | NULL | -20.00 |

The first row has no previous row, so `LAG` gives NULL, and the arithmetic gives NULL too (Q1,
Trap 4). The full form is `LAG(col, offset, default)`. `LAG(stake, 1, 0)` returns 0 instead of NULL
on the first row. Be careful: a 0 default can turn "no previous value" into a fake 100% change.

## FIRST_VALUE and the LAST_VALUE trap

`FIRST_VALUE(col)` and `LAST_VALUE(col)` return a value from the first or last row **of the frame**.
Because the default frame stops at the current row, `LAST_VALUE` returns the current row, which is
almost never what you want:

```sql
SELECT id, placed_at, stake,
       FIRST_VALUE(stake) OVER (PARTITION BY user_id ORDER BY placed_at) AS first_stake,
       LAST_VALUE(stake)  OVER (PARTITION BY user_id ORDER BY placed_at) AS last_wrong,
       LAST_VALUE(stake)  OVER (PARTITION BY user_id ORDER BY placed_at
                                ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS last_right
FROM bets WHERE user_id = 1 ORDER BY placed_at;
```

| id | placed_at | stake | first_stake | last_wrong | last_right |
|---|---|---|---|---|---|
| 1 | 2026-08-18 10:00:00 | 20.00 | 20.00 | 20.00 | 10.00 |
| 2 | 2026-08-19 12:00:00 | 10.00 | 20.00 | 10.00 | 10.00 |
| 4 | 2026-09-05 18:00:00 | 25.00 | 20.00 | 25.00 | 10.00 |
| 3 | 2026-09-10 09:00:00 | 15.00 | 20.00 | 15.00 | 10.00 |
| 5 | 2026-09-12 20:00:00 | 30.00 | 20.00 | 30.00 | 10.00 |
| 6 | 2026-10-01 08:00:00 | 10.00 | 20.00 | 10.00 | 10.00 |

Either widen the frame to `UNBOUNDED FOLLOWING`, or use `FIRST_VALUE` with the order reversed
(`ORDER BY placed_at DESC`).

## Where window functions run: filter them in a CTE

In Q2's logical order, window functions are computed in **step 5 (SELECT)**, after `WHERE`,
`GROUP BY` and `HAVING`. That has two consequences.

**You can't filter on a window function in the same query's WHERE:**

```sql
SELECT id, ROW_NUMBER() OVER (ORDER BY stake DESC) AS rn FROM bets WHERE rn <= 3;
```

```text
ERROR: column "rn" does not exist
```

Compute it in a CTE, then filter outside. This **"rank in a CTE, filter outside"** pattern is the
backbone of Q4.

```sql
WITH ranked AS (
  SELECT id, user_id, stake, ROW_NUMBER() OVER (ORDER BY stake DESC, id) AS rn
  FROM bets
)
SELECT id, user_id, stake FROM ranked WHERE rn <= 3 ORDER BY rn;
```

| id | user_id | stake |
|---|---|---|
| 14 | 3 | 100.00 |
| 19 | 5 | 100.00 |
| 7 | 2 | 50.00 |

**A window can run over grouped results.** Because `GROUP BY` has already happened, the window can
use aggregates. This ranks punters by turnover:

```sql
SELECT user_id, SUM(stake) AS turnover,
       RANK() OVER (ORDER BY SUM(stake) DESC) AS turnover_rank
FROM bets GROUP BY user_id ORDER BY turnover_rank;
```

| user_id | turnover | turnover_rank |
|---|---|---|
| 3 | 220.00 | 1 |
| 2 | 185.00 | 2 |
| 5 | 115.00 | 3 |
| 1 | 110.00 | 4 |
| 4 | 25.00 | 5 |

## Window functions vs GROUP BY

```text
                    GROUP BY                       window function (OVER)
rows out            one per group                  one per input row
can show row cols?  only grouped/aggregated ones   yes, any column
runs at step        3 (then HAVING filters)        5 (filter it from an outer query)
use for             totals, counts per group       rank, running total, prev/next, share-of-total
```

They combine well. Aggregate first with `GROUP BY` (fewer rows), then rank or compare the groups with
a window.

## Gotchas

- **`ROW_NUMBER` over ties is non-deterministic.** PostgreSQL and H2 numbered our tied 50.00 bets
  differently. Always add a unique tie-breaker such as `id`.
- **The default frame is `RANGE … CURRENT ROW` once you add `ORDER BY`.** Tied rows share a running
  total. Use a unique ORDER BY, or say `ROWS`.
- **`LAST_VALUE` with the default frame returns the current row.** Widen the frame to `UNBOUNDED
  FOLLOWING`, or flip the sort and use `FIRST_VALUE`.
- **You can't use a window function in `WHERE`, `GROUP BY` or `HAVING`.** Compute it in a CTE, then
  filter outside.
- **`OVER ()` sees only the rows that survive `WHERE`.** "Share of all bets" computed after filtering
  to one user is a share of that user's bets.
- **`LAG` returns NULL on the first row.** That's usually right. A default of 0 can create fake
  "+100%" changes.

## In interviews

Window functions turn up in most mid-level SQL rounds, often as the follow-up: "can you do it without
a self-join?"

- "Rank the scores without gaps" (LeetCode 178, Rank Scores): `DENSE_RANK`.
- "Days warmer than the previous day" (LeetCode 197, Rising Temperature): `LAG`, or a self-join on
  the date.
- "7-day moving average of revenue" (LeetCode 1321, Restaurant Growth): a `ROWS BETWEEN 6 PRECEDING
  AND CURRENT ROW` frame, on daily totals computed first.

**Typical follow-up:** "What's the difference between RANK and DENSE_RANK?" Answer with a tiny tie
example (1,1,3 vs 1,1,2), then say which the question needs: the "Nth distinct value" needs
`DENSE_RANK`.

**Another follow-up:** "Is a window function faster than a self-join?" Usually yes. A running total
by self-join compares each row with all earlier rows, which is O(n²). A window sorts once (O(n log n),
or less if an index already provides the order) and then streams through the rows. Q5 shows how an
index on `(user_id, created_at)` can provide that order.

## Explain it in 2 minutes

*"What is a window function, and when would you use one instead of GROUP BY?"*

1. An aggregate or ranking function with `OVER (…)`. It computes over related rows but returns a
   value on every row.
2. `PARTITION BY` sets the groups. `ORDER BY` inside `OVER` sets the order for ranking, running
   totals and `LAG`/`LEAD`.
3. `ROW_NUMBER` / `RANK` / `DENSE_RANK` differ only on ties. Add a tie-breaker for deterministic
   results.
4. The frame (`ROWS`/`RANGE BETWEEN …`) decides which rows an aggregate sees. The default with
   ORDER BY is "start to current row, including ties".
5. Window functions are evaluated in the SELECT step, so you filter on them from an outer query or
   CTE.
6. Use them for rankings, top-N, running totals, previous/next comparisons and share-of-total, where
   you need the row *and* the aggregate.

### Answers

1. ROW_NUMBER 1, 2, 3; RANK 1, 1, 3; DENSE_RANK 1, 1, 2.
2. The default frame is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, which includes every row
   tied with the current one in the ORDER BY.
3. `ROWS BETWEEN CURRENT ROW AND 2 FOLLOWING`.
4. Window functions are evaluated in the SELECT step, after `WHERE`. Compute the row number in a CTE
   and filter outside.
5. Aggregate per user in a CTE and join it back to `bets`, or use a correlated scalar subquery. The
   window version is one pass, needs no join, and can't fan out.

Lab solutions:

```sql
-- 1
SELECT id, user_id,
       ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY placed_at, id) AS bet_no,
       COUNT(*)     OVER (PARTITION BY user_id)                        AS user_bets
FROM bets WHERE user_id IN (2, 5) ORDER BY user_id, bet_no;
```

```sql
-- 2
WITH sport_turnover AS (
  SELECT e.sport_id, SUM(b.stake) AS turnover
  FROM bets b
  JOIN selections s ON s.id = b.selection_id
  JOIN markets m    ON m.id = s.market_id
  JOIN events e     ON e.id = m.event_id
  GROUP BY e.sport_id
)
SELECT sp.name AS sport, st.turnover,
       DENSE_RANK() OVER (ORDER BY st.turnover DESC) AS turnover_rank
FROM sport_turnover st JOIN sports sp ON sp.id = st.sport_id
ORDER BY turnover_rank;
```

```sql
-- 3
SELECT id, user_id, amount,
       SUM(amount) OVER (PARTITION BY user_id ORDER BY created_at, id) AS balance,
       LAG(amount) OVER (PARTITION BY user_id ORDER BY created_at, id) AS prev_amount
FROM wallet_transactions WHERE user_id = 2 ORDER BY created_at, id;
```

```sql
-- 4
SELECT id, placed_at,
       LAG(placed_at) OVER (PARTITION BY user_id ORDER BY placed_at, id) AS prev_placed_at
FROM bets WHERE user_id = 3 ORDER BY placed_at;
```

```sql
-- 5
WITH bet_event AS (
  SELECT b.id, m.event_id, b.stake
  FROM bets b
  JOIN selections s ON s.id = b.selection_id
  JOIN markets m    ON m.id = s.market_id
)
SELECT id, event_id, stake,
       SUM(stake) OVER (PARTITION BY event_id) AS event_turnover,
       ROUND(100 * stake / SUM(stake) OVER (PARTITION BY event_id), 1) AS pct_of_event
FROM bet_event WHERE event_id = 2 ORDER BY id;
```
