## Where we are

You know the container (D2): it reads bean definitions, creates beans and injects them. You also know Boot's auto-configuration (D4): `@Conditional` configuration classes chosen at startup. Nearly every annotation you'll meet is an *instruction to one of those two machines*. This lesson is a reference you can keep open. Each annotation is grouped by the job it does, with what it does underneath and the mistake people most often make with it.

## The problem

A Spring Boot codebase can carry fifty different annotations. If you learn them as a flat list, they blur together, and you end up guessing why `@Transactional` "didn't work" or why a bean "wasn't found". Every annotation is handled by some specific piece of machinery: the component scanner, a `BeanPostProcessor`, a proxy, or a condition. Once you know *which*, you can predict how it behaves, including when it fails.

## The three mechanisms underneath

Almost every annotation is handled by one of three mechanisms:

```text
1. Definition time  – the scanner / ConfigurationClassPostProcessor reads it while building
                      bean definitions (@Component, @Bean, @Import, @Conditional*, @Profile)
2. Creation time    – a BeanPostProcessor reads it while creating a bean
                      (@Autowired, @Value, @PostConstruct)
3. Call time        – a PROXY wraps the bean and acts on each method call
                      (@Transactional, @Async, @Cacheable, @Validated, @PreAuthorize)
```

A **proxy** is a generated object that stands in front of your bean and runs extra code around each call. You met proxies in D3. Remember the third group, because it shares one weakness: **a call from inside the same object skips the proxy**. This is called *self-invocation*.

## 1. Stereotypes: "make this class a bean"

A **stereotype** is an annotation that marks a class for component scanning, and also says what *role* the class plays.

| Annotation | Underneath | Most common mistake |
|---|---|---|
| `@Component` | The scanner registers a bean definition for the class. | The class sits outside the package of the `@SpringBootApplication` class, so it is never scanned. |
| `@Service` | Same as `@Component`. It only documents the role. | Expecting it to add transactions. It adds nothing. |
| `@Repository` | Same, plus a post-processor translates database exceptions into Spring's `DataAccessException` hierarchy. | Adding it to Spring Data interfaces, which are already repositories. Harmless, but noise. |
| `@Controller` | A bean that the web layer scans for request-handling methods. | Returning an object and getting a "template not found" error, because you forgot `@ResponseBody`. |
| `@RestController` | `@Controller` + `@ResponseBody`: return values are written as JSON. | Using it where you wanted to render a server-side view. |
| `@Configuration` | A class of `@Bean` methods. Spring subclasses it with CGLIB so that calling one `@Bean` method from another returns the *same* singleton. | With `proxyBeanMethods = false`, those inner calls create *new* objects. |

## 2. Dependency injection: "give this bean what it needs"

| Annotation | Underneath | Most common mistake |
|---|---|---|
| `@Autowired` | `AutowiredAnnotationBeanPostProcessor` resolves by type. A single constructor needs no annotation at all. | Field injection: the bean is hard to test, and dependencies stay hidden. Prefer constructors, as this repo's `ProgressService` does. |
| `@Qualifier("name")` | Narrows several candidates of the same type to one, by name or by a custom qualifier. | Misspelling the bean name. Bean names come from the class name with a lowercase first letter (`bankService`). |
| `@Primary` | Marks the default when several beans match. | Two `@Primary` beans of the same type cause startup failure. |
| `@Value("${x}")` | Resolves a placeholder from the `Environment` (properties, YAML, environment variables). `#{...}` is a SpEL expression instead. | Writing `#{x}` when you meant `${x}`. Or using `@Value` for many related settings, where `@ConfigurationProperties` fits better. |
| `@Lazy` | Creates the bean on first use, or injects a lazy proxy. | Hiding a circular dependency instead of fixing the design. |
| `@Scope("prototype")` | A new instance on every lookup. | Injecting a prototype into a singleton gives you *one* instance forever. Use `ObjectProvider<T>`. |

## 3. Configuration: "where beans and settings come from"

| Annotation | Underneath | Most common mistake |
|---|---|---|
| `@SpringBootApplication` | `@Configuration` + `@EnableAutoConfiguration` + `@ComponentScan` of its own package. | Placing it in a sub-package, so sibling packages are never scanned. |
| `@Bean` | The method's return value becomes a bean. Its parameters are injected. | Defining a `BeanFactoryPostProcessor` with a non-`static` `@Bean` method (D9). |
| `@Import` | Pulls in other configuration classes or selectors. It is the engine behind every `@EnableXxx`. | Expecting it to component-scan the imported class's package. It does not. |
| `@ConfigurationProperties("prefix")` | Binds a whole tree of properties onto a class or record, with relaxed names (`slow-threshold` maps to `slowThreshold`). | Forgetting to register it with `@EnableConfigurationProperties` or `@ConfigurationPropertiesScan`, so it is never bound. |
| `@PropertySource` | Adds a `.properties` file to the `Environment`. | Pointing it at a YAML file. It does not load YAML. |
| `@Profile("dev")` | The bean is registered only when that profile is active. | A typo in the profile name fails silently. The bean just goes missing. |

## 4. Conditional: "only if…" (mostly for auto-configs)

| Annotation | Underneath | Most common mistake |
|---|---|---|
| `@ConditionalOnClass` | Checks whether a class is on the classpath, by reading bytecode metadata without loading the class. | Using a class literal on a `@Bean` *method* in a class that loads anyway. Use `name = "..."`, or put it on a nested configuration class. |
| `@ConditionalOnMissingBean` | Registers this bean only if no bean of the type exists *yet*. | Using it in your own (non-auto) configuration. The result depends on processing order (D9). |
| `@ConditionalOnBean` | The opposite check, with the same ordering caveat. | Same mistake. |
| `@ConditionalOnProperty` | Checks a property's value. `matchIfMissing` sets the default when the property is absent. | Forgetting `matchIfMissing = true` on an `enabled` flag, so the feature is off unless configured. |
| `@ConditionalOnWebApplication` | Checks for a servlet or reactive web context. | Testing it with a plain `ApplicationContextRunner`. Use `WebApplicationContextRunner`. |

Run with `--debug` to print the conditions report and see every one of these decisions.

## 5. Web: "map HTTP to methods"

A **handler method** is a controller method that serves a request. D5 shows the full request pipeline. Here is just the vocabulary.

| Annotation | Underneath | Most common mistake |
|---|---|---|
| `@RequestMapping` / `@GetMapping`, `@PostMapping`, … | Registered in a lookup table at startup, keyed by path, method, headers and content type. | Two methods mapped to the same path and method: an "ambiguous mapping" error at startup. |
| `@PathVariable` | Takes a value from a URI template segment (`/questions/{slug}`). | Relying on parameter names without the `-parameters` compiler flag. Boot's Maven and Gradle setups add the flag; a custom build may not. |
| `@RequestParam` | Takes a query or form parameter. It is **required by default**. | An optional parameter returns 400. Use `required = false` or `Optional<T>`. |
| `@RequestBody` | An `HttpMessageConverter` (Jackson for JSON) reads the request body into an object. | Using it on a `GET` request, or expecting it to read form data. |
| `@ResponseStatus` | Sets the status for a method, or for an exception class, like this repo's `NotFoundException` → 404. | Putting it on an exception you also handle in `@ExceptionHandler`. The handler wins. |
| `@ExceptionHandler` / `@RestControllerAdvice` | Exception-to-response mapping, in one controller or across all of them. | Expecting it to catch errors thrown in servlet filters, such as security 401s. Filters run before the `DispatcherServlet`. |

## 6. Data: "map objects to tables, and transactions"

An **entity** is a class whose instances map to table rows. A **transaction** is a group of database changes that commit or roll back together. D6 covers both properly.

| Annotation | Underneath | Most common mistake |
|---|---|---|
| `@Entity`, `@Id`, `@GeneratedValue` | Hibernate builds metadata at startup and tracks each loaded instance. | Missing no-arg constructor, or `equals`/`hashCode` based on a generated id that is `null` before save. |
| `@Transactional` | **Proxy.** It opens a transaction before the method and commits after. By default it rolls back only on unchecked exceptions. | Self-invocation (this repo's `DataImporter.run` comments on exactly that). Also, `private` methods are never proxied, and a checked exception commits unless you set `rollbackFor`. |
| `@Query` | A custom JPQL or SQL query on a repository method. | Using SQL syntax without `nativeQuery = true`. |
| `@Modifying` | Required for update and delete `@Query`s. | Stale entities in memory afterwards. Add `clearAutomatically = true`. |
| `@Version` | Optimistic locking: a version column is checked on update. | Ignoring the `OptimisticLockException` instead of retrying or returning 409. |

## 7. Async, scheduling and events: "run it later, or elsewhere"

| Annotation | Underneath | Most common mistake |
|---|---|---|
| `@EnableAsync` + `@Async` | **Proxy.** It submits the call to a `TaskExecutor` and returns immediately (`void` or `CompletableFuture`). | Self-invocation, so the call runs synchronously. Also, exceptions from `void` methods are only logged. |
| `@EnableScheduling` + `@Scheduled` | A scheduler calls the method on a fixed rate, a fixed delay or a cron expression. | Boot's default scheduler has **one thread**, so a slow job delays every other job. Set `spring.task.scheduling.pool.size`. |
| `@EventListener` | The method receives matching published events, synchronously and on the publisher's thread, by default. | Assuming listeners run in the background. Add `@Async` if you need that. |
| `@TransactionalEventListener` | Runs at a transaction phase, `AFTER_COMMIT` by default. | Publishing with no active transaction: the listener is silently skipped unless `fallbackExecution = true`. |

## 8. Validation: "reject bad input early"

| Annotation | Underneath | Most common mistake |
|---|---|---|
| `@Valid` (`jakarta.validation`) | Triggers Bean Validation on an argument and cascades into nested fields. | Forgetting it on a nested object field, so the inner constraints are never checked. |
| `@Validated` (Spring) | On a class, it enables **proxy-based** method validation, and it supports validation groups. | Expecting method validation on a bean that lacks the class-level annotation. MVC controllers are the exception (Spring 6.1+ validates their parameters itself). |
| `@NotNull`, `@NotBlank`, `@Size`, `@Email`, … | Constraints that a `Validator` checks. | Using `@NotNull` on a `String` that must have content. `""` passes. Use `@NotBlank`. |

## 9. Testing: "load just enough"

| Annotation | Underneath | Most common mistake |
|---|---|---|
| `@SpringBootTest` | Starts the full context, cached and reused across test classes with the same configuration. | Using it for every test, which makes the suite slow. |
| `@WebMvcTest`, `@DataJpaTest` | **Slices**: only one layer's auto-configs and beans. | Expecting your `@Service` to be there. Mock it. |
| `@MockitoBean` / `@MockitoSpyBean` | Replaces or wraps a bean in the context. Spring 6.2+ replaces Boot's removed `@MockBean`. | Each new combination of mocks creates a new context, which defeats the cache. |
| `@TestConfiguration` | Extra beans for a test, as in this repo's `AppTest` clock. | Putting it as a top-level class under the scan root, where it gets scanned into *every* test. |
| `@Transactional` (on a test) | Rolls back after each test. | With `webEnvironment = RANDOM_PORT` the server runs the request on another thread, so nothing rolls back. |

## Lab (~10 min)

You will *see* the three mechanisms at work. Add this test to the repo:

```java
@SpringBootTest(properties = "spring.datasource.url=jdbc:h2:mem:annlab;DB_CLOSE_DELAY=-1")
class AnnotationLabTest {
    @Autowired ApplicationContext ctx;

    @Test
    void whoIsProxied() {
        for (String name : List.of("progressService", "bankService", "apiController", "clock")) {
            Object bean = ctx.getBean(name);
            System.out.printf("%-16s %-70s proxy=%s%n", name, bean.getClass().getName(), AopUtils.isAopProxy(bean));
        }
    }
}
```

**Observe:** `progressService` and `bankService` have `@Transactional` methods, so their classes end in `$$SpringCGLIB$$0` and `proxy=true`. `apiController` and `clock` are plain objects. That is mechanism 3 made visible.

**Break it:**

1. Add a `@Component` with two `@Scheduled(fixedRate = 1000)` methods. Make one call `Thread.sleep(5000)`, put `@EnableScheduling` on the app class, and log `Thread.currentThread().getName()` in both. Both run on the same single scheduling thread, and the fast job stalls. Set `spring.task.scheduling.pool.size=2` and run again.
2. In `ApiController.ProgressRequest`, add `@NotNull` to the `String notes` component. Send `{"action":"NOTES","notes":""}` and see it accepted. Swap in `@NotBlank` and send it again to get a 400.

## Gotchas

- **Proxy annotations and self-invocation.** `@Transactional`, `@Async`, `@Cacheable` and `@Validated` only apply when the call enters through the proxy, meaning from another bean.
- **`@Transactional` rolls back on unchecked exceptions only.** A checked exception commits unless you set `rollbackFor`.
- **`@RequestParam` is required by default.** Make optional parameters explicitly optional.
- **`@ConditionalOnMissingBean` in your own configs** depends on order. Keep it for auto-configurations.
- **The single-threaded default scheduler.** Size the pool when you have more than one job.
- **`@NotNull` on Strings.** Use `@NotBlank` for "must have content".

## In interviews

Typical prompts are "Difference between `@Component`, `@Service`, `@Repository`?", "`@Controller` vs `@RestController`?", "Why didn't my `@Transactional` work?", "`@Valid` vs `@Validated`?" and "What does `@SpringBootApplication` do?". There is no exact bank question yet. The nearest are [Connection Pooling and the DB Connection Process](#/q/jdbc-connection-pooling) (the `@Transactional` → connection story) and [Code review: Java/SQL connection snippet](#/q/review-jdbc-connection-code).

**Follow-up: "So is `@Service` useless?"** A strong answer says it is identical to `@Component` in behaviour, but it documents intent, and pointcuts or tooling can target it. Only `@Repository` adds behaviour, which is exception translation.

## Explain it in 2 minutes

*"How do Spring annotations actually do anything?"*

- Annotations are only metadata. Spring code reads them at one of three times.
- Definition time: the scanner and `ConfigurationClassPostProcessor` handle `@Component`, `@Bean`, `@Import`, `@Conditional*` and `@Profile`.
- Creation time: `BeanPostProcessor`s handle `@Autowired`, `@Value` and `@PostConstruct`.
- Call time: proxies handle `@Transactional`, `@Async`, `@Cacheable`, `@Validated` and `@PreAuthorize`, so self-invocation and `private` methods bypass them.
- Boot adds `@SpringBootApplication` (scan, configuration and auto-configuration) and conditionals you can inspect with `--debug`.
- Test slices load only the auto-configs for one layer.

## Check yourself

1. Which of `@Component`, `@Service`, `@Repository` and `@Controller` adds behaviour beyond registering a bean, and what?
2. A `@Transactional` method throws `IOException`. Does the transaction roll back?
3. A `@Scheduled` job that runs every 5 seconds sometimes runs 30 seconds late. What's the likely cause?
4. Why does `@NotNull String name` accept `""`?
5. Which mechanism (definition, creation or call time) handles `@Async`, and what follows from that?

### Answers

1. `@Repository` adds translation of persistence exceptions into `DataAccessException`. `@Controller` is also *detected* by the web layer as a handler. `@Component` and `@Service` only register a bean.
2. No. By default only unchecked exceptions and `Error` roll back. Use `rollbackFor = IOException.class`.
3. Another job is hogging the single default scheduler thread. Increase `spring.task.scheduling.pool.size`.
4. `""` is not null. `@NotBlank` requires at least one non-whitespace character.
5. Call time, through a proxy. A call from within the same class bypasses the proxy and runs synchronously. Only calls that arrive from another bean, through the proxy, become async.
