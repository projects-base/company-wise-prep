## Where we are

F3 gave you a method for designing systems: requirements, estimates, API, data model, high-level
design, deep dives. Many real systems are, at heart, "run these jobs in the right order": nightly
data pipelines, CI builds, deployment workflows, AI agent workflows. This lesson builds the data
structure behind all of them, the **DAG**, from zero. Then you'll code topological sort and use it
to design a workflow scheduler.

## The problem

A nightly pipeline has six jobs:

```text
extract_orders, extract_users, clean_orders, join, report, train_model

clean_orders needs extract_orders.     join needs clean_orders and extract_users.
report needs join.                     train_model needs join.
```

Three questions follow. **In what order do you run them?** **Which can run at the same time?** And
if someone accidentally makes `extract_orders` depend on `report`, **how do you notice before
running anything, rather than waiting forever?** The answers come from viewing the jobs as a graph.

## What a graph is

A **graph** is a set of **nodes** (also called vertices, the things) connected by **edges** (the
relationships). Cities and roads, people and friendships, jobs and dependencies are all graphs.

```text
   A ─── B        nodes: A, B, C
   │              edges: A–B, A–C
   C
```

In code, the usual representation is an **adjacency list**: a map from each node to the list of
nodes it connects to, such as `Map<String, List<String>>`.

## Directed: edges with a direction

In a **directed graph**, each edge points one way. `A → B` doesn't imply `B → A`. Dependencies
are naturally directed. We'll draw an edge **from a job to the jobs that wait for it**: "run
`extract_orders` before `clean_orders`".

```text
extract_orders ──► clean_orders ──► join ──► report
                                     ▲  └──► train_model
extract_users ───────────────────────┘
```

The **in-degree** of a node is the number of edges pointing into it, which here is the number of
jobs it waits for. `join` has in-degree 2. `extract_users` has in-degree 0, so it can start
immediately.

## Acyclic: no way back

A **cycle** is a path that returns to where it started: `A → B → C → A`. In a dependency graph, a
cycle means A waits for C, which waits for B, which waits for A, so none of them can ever start.

A **DAG (directed acyclic graph)** is a directed graph with no cycles. Every valid set of
dependencies must be a DAG. That's why build tools reject circular module dependencies, and why
schedulers validate a workflow before running it.

**The rule:** a dependency graph can be executed if, and only if, it is a DAG.

## Topological order

A **topological order** lists the nodes so that every edge points forward: each job comes after
everything it depends on. For our pipeline, both of these are valid:

```text
extract_orders, extract_users, clean_orders, join, report, train_model
extract_users, extract_orders, clean_orders, join, train_model, report
```

There is usually more than one valid order. A topological order exists **exactly when the graph
has no cycle**, so the algorithm that finds the order also detects cycles.

## Kahn's algorithm

**Kahn's algorithm** is the most common way to compute a topological order: repeatedly run whatever
has no unfinished dependencies.

```text
1. Compute every node's in-degree.
2. Put all nodes with in-degree 0 in a "ready" queue.
3. Take a node from the queue, output it, and for each node that waits on it, decrease that
   node's in-degree by 1. When it hits 0, it becomes ready.
4. Repeat until the queue is empty.
5. If fewer nodes were output than exist, the leftovers are stuck in (or behind) a cycle.
```

Here it is in Java 21. It also groups the output into **waves**: each wave contains every task that
became ready at the same time, so everything within a wave can run in parallel.

```java
import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.Deque;
import java.util.HashMap;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class TopoSort {

    /**
     * Kahn's algorithm. deps maps each task to the tasks it depends on.
     * Returns the tasks grouped into "waves": everything in a wave can run in parallel.
     */
    static List<List<String>> waves(Map<String, List<String>> deps) {
        Map<String, Integer> inDegree = new HashMap<>();          // how many deps are still unfinished
        Map<String, List<String>> dependents = new HashMap<>();   // edge direction: dep -> task
        for (var e : deps.entrySet()) {
            inDegree.putIfAbsent(e.getKey(), 0);
            for (String d : e.getValue()) {
                inDegree.putIfAbsent(d, 0);
                inDegree.merge(e.getKey(), 1, Integer::sum);
                dependents.computeIfAbsent(d, k -> new ArrayList<>()).add(e.getKey());
            }
        }

        Deque<String> ready = new ArrayDeque<>();
        inDegree.forEach((task, n) -> { if (n == 0) ready.add(task); });

        List<List<String>> waves = new ArrayList<>();
        int done = 0;
        while (!ready.isEmpty()) {
            List<String> wave = new ArrayList<>(ready);           // all currently ready tasks
            ready.clear();
            waves.add(wave);
            for (String task : wave) {
                done++;
                for (String next : dependents.getOrDefault(task, List.of())) {
                    if (inDegree.merge(next, -1, Integer::sum) == 0) ready.add(next);
                }
            }
        }
        if (done != inDegree.size()) {
            throw new IllegalStateException("cycle detected: " + (inDegree.size() - done) + " tasks can never run");
        }
        return waves;
    }

    public static void main(String[] args) {
        Map<String, List<String>> pipeline = new LinkedHashMap<>();
        pipeline.put("extract_orders", List.of());
        pipeline.put("extract_users", List.of());
        pipeline.put("clean_orders", List.of("extract_orders"));
        pipeline.put("join", List.of("clean_orders", "extract_users"));
        pipeline.put("report", List.of("join"));
        pipeline.put("train_model", List.of("join"));

        System.out.println(waves(pipeline));

        pipeline.put("extract_orders", List.of("report"));          // add a cycle
        try {
            waves(pipeline);
        } catch (IllegalStateException e) {
            System.out.println(e.getMessage());
        }
    }
}
```

The output is something like
`[[extract_orders, extract_users], [clean_orders], [join], [report, train_model]]` (the order
within a wave can vary), followed by `cycle detected: 5 tasks can never run`.

**Cost:** each node enters the queue once and each edge is looked at once, so the cost is
**O(V + E)**, where V is the number of nodes and E the number of edges.

## The other way: depth-first search

You'll also see topological sort done with **depth-first search (DFS)**: follow edges as deep as
possible, and add a node to a list only **after** all of its descendants are finished. Reversing
that list gives a topological order. To detect cycles, colour each node: white (not visited),
grey (on the current path) or black (finished). Reaching a **grey** node means you've looped back
onto your own path, which is a cycle.

Kahn's algorithm is usually easier to explain in an interview, and it gives you the waves for free.
DFS is handy when you already have a recursive traversal.

## Parallelism and the critical path

Waves are a simple way to parallelise. A better scheduler starts each task **the moment its own
dependencies finish**, without waiting for the rest of its wave. With that scheduler, the total time
is set by the **critical path**: the longest chain of dependent work through the graph.

```text
extract_orders 300 ms → clean_orders 200 → join 100 → train_model 400  = 1,000 ms  ← critical path
sum of all tasks = 1,200 ms
```

Adding workers can't beat 1,000 ms here. To go faster, shorten something on the critical path.

## DAGs in build systems

A multi-module Maven project is a DAG of modules. The **reactor** (Maven's multi-module build
planner) sorts modules topologically, so `common` builds before `orders-service`, and it fails on a
cycle. Gradle builds a **task graph** (compile → test → jar) and runs independent tasks in parallel.
Bazel and similar tools add **incremental builds**: when a file changes, only the nodes downstream
of it are rebuilt, and unchanged outputs come from a cache keyed by a hash of each task's inputs.

## DAGs in workflow orchestration

A **workflow orchestrator** runs multi-step jobs reliably: it tracks state, retries failures and
resumes after crashes.

- **Airflow-style:** you declare a DAG of tasks (in Airflow, in Python) with a schedule such as
  "daily at 02:00". A **scheduler** finds tasks whose upstream tasks have succeeded and sends them to
  **workers**. Each run's task states are stored in a database, so a failed task can be retried, or
  a past date re-run (**backfill**), without redoing everything.
- **Temporal-style:** you write the workflow as ordinary code (a Java method calling activities).
  The engine records an **event history** of every step. After a crash, it replays the code against
  that history to rebuild the state, and continues where it stopped. This is called **durable
  execution**. The dependency structure is still a DAG, but it lives implicitly in your code rather
  than as a declared graph.

## Designing a job scheduler (HLD)

Use F3's method on "design a distributed job scheduler":

```text
 DAG definitions (versioned) ──► scheduler (one leader, elected via Raft/etcd: F2)
                                    │ every few seconds: find runs that are due and
                                    │ tasks whose upstream tasks have all SUCCEEDED
                                    ▼
                               task queue ──► worker pool ──► runs the task, sends heartbeats
                                    ▲                │
                                    │ retry w/ backoff│ status: RUNNING / SUCCEEDED / FAILED
                                    └───── state DB ◄─┘
                                           (dag_run, task_instance: state, attempt, heartbeat_at)
```

Deep dives worth naming:
- **State machine per task instance:** `SCHEDULED → QUEUED → RUNNING → SUCCEEDED | FAILED |
  UP_FOR_RETRY`. A worker that stops heartbeating has its task marked failed and retried.
- **At-least-once execution:** a worker can die after doing the work but before reporting it, so
  tasks run again. Tasks must be **idempotent** (F2), for example writing to a partition named
  after the run date with overwrite semantics.
- **Scheduler high availability:** run two schedulers with one elected leader, or partition DAGs
  across schedulers. Without that, two schedulers may both enqueue the same task.
- **Validation at submit time:** reject cycles with Kahn's algorithm before a DAG is accepted.
- **Back-pressure:** cap concurrency per DAG and per pool, so one huge backfill can't starve
  everything else.

## Connecting to the coding bank

- **Course Schedule II:** courses are nodes and each prerequisite is an edge from the prerequisite
  to the course. Return Kahn's output order, or an empty array if `done < numCourses` (a cycle).
  It's the algorithm above with integer ids instead of strings.
- **Alien Dictionary:** the hard part is **building** the graph. Compare each pair of adjacent words
  in the sorted list. The first position where they differ gives one edge (`'t' → 'f'` means t comes
  before f). Watch for the invalid case where a longer word comes before its own prefix (`"abc"`
  before `"ab"`), which means there's no valid order. Then topologically sort the letters. A cycle
  means the input is inconsistent, so return `""`.

The pattern in both: **"order things that have before/after constraints" means a graph plus a
topological sort.**

## Lab (~10 min)

Build a runner that starts each task as soon as its dependencies finish, and watch the critical
path decide the total time. Save this as `DagRunner.java` and run `java DagRunner.java`.

```java
import java.util.HashMap;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class DagRunner {

    record Task(String name, long millis, List<String> deps) {}

    /** Starts each task as soon as all of its dependencies have finished. Assumes no cycle. */
    static void run(Map<String, Task> tasks, ExecutorService pool) {
        Map<String, CompletableFuture<Void>> futures = new HashMap<>();
        long start = System.currentTimeMillis();
        for (String name : tasks.keySet()) schedule(name, tasks, futures, pool, start);
        CompletableFuture.allOf(futures.values().toArray(CompletableFuture[]::new)).join();
        System.out.println("all done in " + (System.currentTimeMillis() - start) + " ms");
    }

    private static CompletableFuture<Void> schedule(String name, Map<String, Task> tasks,
            Map<String, CompletableFuture<Void>> futures, ExecutorService pool, long start) {
        CompletableFuture<Void> existing = futures.get(name);
        if (existing != null) return existing;
        Task t = tasks.get(name);
        CompletableFuture<?>[] upstream = t.deps().stream()
                .map(d -> schedule(d, tasks, futures, pool, start))
                .toArray(CompletableFuture[]::new);
        CompletableFuture<Void> f = CompletableFuture.allOf(upstream).thenRunAsync(() -> {
            System.out.printf("%5d ms  start %s%n", System.currentTimeMillis() - start, name);
            try {
                Thread.sleep(t.millis());
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }, pool);
        futures.put(name, f);
        return f;
    }

    public static void main(String[] args) {
        Map<String, Task> tasks = new LinkedHashMap<>();
        for (Task t : List.of(
                new Task("extract_orders", 300, List.of()),
                new Task("extract_users", 100, List.of()),
                new Task("clean_orders", 200, List.of("extract_orders")),
                new Task("join", 100, List.of("clean_orders", "extract_users")),
                new Task("report", 100, List.of("join")),
                new Task("train_model", 400, List.of("join")))) {
            tasks.put(t.name(), t);
        }
        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            run(tasks, pool);
        }
    }
}
```

**What you should see:** both extracts start at once. `clean_orders` starts about 300 ms in, `join`
about 500 ms in, and `report` and `train_model` start together. The total is about **1,000 ms**
plus a little overhead (the critical path), not 1,200 ms (the sum).

**Break it:**
1. Make `extract_orders` depend on `report`. The runner crashes with a `StackOverflowError`, because
   it recurses around the cycle forever. Fix it the way real schedulers do: run `TopoSort.waves`
   first and refuse to start a DAG that has a cycle.
2. Change `train_model` to 50 ms. The total drops to about 700 ms, because the critical path now
   ends at `report` (300 + 200 + 100 + 100 = 700 ms) instead of `train_model`. Then set
   `extract_users` to 10 ms. Nothing changes, because it was never on the critical path.

## Gotchas

- **Edge direction mix-ups.** Decide whether an edge means "A before B" or "A depends on B", write
  it down, and build in-degrees to match. Most bugs in Course Schedule come from this.
- **Forgetting the cycle check.** Kahn's algorithm silently returns a partial order if you don't
  compare the output count with the node count.
- **Nodes with no edges** (an isolated task, or a letter that appears in only one word in Alien
  Dictionary) must still be added to the in-degree map, or they vanish from the output.
- **Non-idempotent tasks in an orchestrator.** Retries and at-least-once execution mean every task
  can run twice. Make tasks overwrite, not append.
- **Optimising off the critical path.** Speeding up a task that isn't on the longest chain doesn't
  change the total time.
- **Alien Dictionary's prefix case.** `"abc"` before `"ab"` is invalid input, not "no
  information". Return `""`.

Typical follow-ups:
- **"Detect the cycle and report which tasks are in it."** Kahn's algorithm tells you which nodes
  were never output. To print the actual cycle, run DFS with colours from one of them, and when you
  reach a grey node, walk back along the current path.
- **"A worker dies halfway through a task."** Heartbeats time out, the task instance is marked
  failed and retried (with a cap and backoff), and the task is idempotent so the retry is safe.
  Downstream tasks stay blocked until it succeeds.

## Explain it in 2 minutes

*"How would a workflow scheduler decide what to run next?"*

- The workflow is a DAG: tasks are nodes, and dependencies are directed edges.
- Validate at submit time with a topological sort, rejecting cycles.
- At run time, a task is ready when all of its upstream tasks have succeeded (in-degree 0 in Kahn's
  terms).
- Ready tasks go to a queue, workers run them, and the state lives in a DB with heartbeats.
- Retries with backoff, idempotent tasks, and a single elected scheduler leader.
- The total time is bounded by the critical path, so that's where to optimise.

1. What does it mean for a directed graph to have a topological order?
2. In Kahn's algorithm, how do you know there was a cycle?
3. Six tasks: what decides the minimum total time with unlimited workers?
4. In Alien Dictionary, which edge does the pair `"wrt"`, `"wrf"` give you?
5. Why must tasks in an orchestrator be idempotent?

### Answers

1. The nodes can be listed so that every edge points from an earlier node to a later one. That's
   possible exactly when the graph has no cycle.
2. Fewer nodes were output than exist. The remaining ones never reached in-degree 0.
3. The critical path, the longest chain of dependent task durations.
4. `t → f`: the first differing position is index 2, so `t` comes before `f`.
5. Execution is at-least-once: crashes and lost status reports cause retries, so running a task
   twice must leave the same result as running it once.
