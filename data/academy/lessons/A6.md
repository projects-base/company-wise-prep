## Where we are

From A2 you know each thread has its own stack, while all objects live on one shared heap. So two
threads can read and write the same object. This lesson answers a question that sounds trivial
and is not: when one thread writes a field, **when, and whether, does another thread see it?**
The rules are the Java Memory Model (JMM), and they are the foundation for all of track B.

## Threads in one paragraph

A **thread** is an independent path of execution inside the same JVM process. `new
Thread(task).start()` runs `task` alongside the code that started it; `t.join()` waits until `t`
finishes. Threads share the heap, so they share objects and static fields. That is all the
threading you need for this lesson (B1 covers the rest).

## The problem

This program sets a flag to tell a worker thread to stop. On a typical HotSpot JVM it **never
stops**:

```java
public class Visibility {
    static boolean running = true;

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            long spins = 0;
            while (running) {          // reads the shared field... or does it?
                spins++;
            }
            System.out.println("stopped after " + spins + " spins");
        });
        worker.start();
        Thread.sleep(1_000);
        running = false;               // main thread writes the shared field
        System.out.println("main set running=false");
    }
}
```

The write happened. The worker simply never sees it. Nothing is broken in the JVM: the program
has no rule that *requires* the worker to see it.

## Why writes go missing

Two layers are allowed to keep a thread's view of memory out of date:

**1. The compiler and JIT.** They may reorder and cache reads as long as the *single thread*
cannot tell the difference. Inside the worker, nothing changes `running`, so C2 can legally
rewrite the loop as:

```java
if (running) {
    while (true) { spins++; }   // the field is read once, then never again
}
```

This is exactly what happens in the program above.

**2. The hardware.** Each CPU core has its own caches and a *store buffer* (a queue of writes not
yet pushed to the shared cache). Writes from one core can become visible to other cores later,
or in a different order from how they were issued. x86 hides most of this; ARM (Graviton, Apple
silicon) hides less.

You cannot reason about either layer directly; they differ per CPU and JIT version. The JMM
replaces them with one contract.

## Three properties to keep apart

- **Atomicity**: an operation happens all at once or not at all; no thread sees it half-done.
- **Visibility**: a write by one thread is eventually seen by another.
- **Ordering**: writes are seen in the order they were made.

Most concurrency bugs are one of these three. The flag bug is *visibility*.

## The contract: happens-before

The JMM defines a relation called **happens-before**: if action A happens-before action B, then
B is guaranteed to see everything A (and everything before A in A's thread) wrote.

If two threads access the same field, at least one writes, and there is no happens-before between
them, that is a **data race**, and the JMM gives almost no guarantees about what you read.

The main ways to create happens-before edges:

```text
 program order    each action in a thread  ──hb──► the next action in that thread
 monitor lock     unlock of lock M         ──hb──► every later lock of the same M
 volatile         write of volatile v      ──hb──► every later read of v that sees it
 thread start     t.start()                ──hb──► first action in t
 thread end       last action in t         ──hb──► t.join() returning
 transitivity     A ─hb─► B and B ─hb─► C  ⇒ A ─hb─► C
```

`java.util.concurrent` builds on these: putting into a `BlockingQueue` happens-before taking that
element out, `submit()` to an executor happens-before the task runs, `CountDownLatch.countDown()`
happens-before `await()` returns.

**Rule:** to share data between threads you need a happens-before path from the write to the
read. No path, no guarantee.

## volatile: visibility and ordering

Declaring a field **`volatile`** creates the edge: a write to it happens-before every later read
that sees the value. The JIT may not cache it in a register or hoist it out of a loop.

```java
static volatile boolean running = true;   // the one-word fix for the flag bug
```

Crucially, the edge covers **everything written before** the volatile write, not just the field
itself. That is how you safely hand data to another thread:

```java
int data;                       // plain field
volatile boolean ready;         // the "publication" flag

// writer thread                // reader thread
data = 42;                      if (ready) {
ready = true;                       System.out.println(data);   // guaranteed 42
                                }
```

```text
 writer:  data = 42 ──program order──► ready = true (volatile write)
                                              │ happens-before
 reader:                                      ▼
                                  sees ready == true (volatile read) ──program order──► reads data: 42
```

Without `volatile` on `ready`, the reader could see `ready == true` and still read `data == 0`.

## What volatile does NOT give: atomicity

```java
static volatile int count = 0;
// two threads each run: for (...) count++;
```

`count++` is three steps: read, add one, write. Two threads can both read 5 and both write 6. Each
step is visible; the *combination* is not atomic. Fixes:

- `AtomicInteger.incrementAndGet()` (a hardware compare-and-swap; B3),
- `synchronized` around the increment,
- `LongAdder` for high-contention counters.

**Rule:** `volatile` fits one writer, or writes that don't depend on the current value (flags,
"latest config" references). Read-modify-write needs atomics or locks.

## synchronized: exclusion plus visibility

A `synchronized` block takes a **monitor lock** (every object has one): only one thread at a time
can hold it. It gives two things:

- **Mutual exclusion**, so `count++` inside it is effectively atomic.
- **Happens-before**: everything a thread did before releasing the lock is visible to the next
  thread that acquires the *same* lock.

Both reader and writer must lock the **same** object. Locking on two different objects creates no
edge at all. (B2 covers locks in depth.)

## Safe publication and final fields

*Publishing* an object means making a reference to it reachable by another thread. Publishing
through a plain field is unsafe: the JIT or CPU may make the reference visible *before* the
constructor's writes, so another thread sees a half-built object.

This is why the classic lazy singleton needs `volatile`:

```java
public final class Config {
    private static volatile Config instance;      // without volatile: half-built objects possible
    private final String url;

    private Config() { this.url = System.getenv().getOrDefault("DB_URL", "localhost"); }

    public static Config get() {
        Config c = instance;                      // one volatile read on the fast path
        if (c == null) {
            synchronized (Config.class) {
                c = instance;
                if (c == null) {
                    instance = c = new Config();
                }
            }
        }
        return c;
    }
}
```

Two other safe paths exist:

- **`final` fields**: once a constructor finishes, other threads that get a reference to the
  object are guaranteed to see the final fields' values, *provided `this` did not escape during
  construction*. That is why immutable objects (records, `String`) are safe to share without
  locks.
- **Static initialisation**: the class-init lock (A3's lazy holder) publishes safely too.

```java
        worker.join(3_000);                 // wait at most 3 s
        System.out.println(worker.isAlive()
                ? "BUG: worker never saw the write - still spinning"
                : "worker stopped");
        System.exit(0);                     // kill the spinning thread if it is stuck
```

   Run `java Visibility.java`. Expect `BUG: ...`. (It is *allowed*, not *guaranteed*: on a
   different JIT you might get lucky.)
2. Run with `-Xint` (interpreter only). It usually stops: the interpreter re-reads the field
   each time. The bug is the JIT hoisting the read, which is legal.
3. Make the field `volatile` and run normally: it stops within a moment.
4. Now atomicity. Save and run:

```java
public class LostUpdate {
    static volatile int count = 0;    // volatile: visible, but count++ is still read-modify-write

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> { for (int i = 0; i < 1_000_000; i++) count++; };
        Thread a = new Thread(task), b = new Thread(task);
        a.start(); b.start(); a.join(); b.join();
        System.out.println("expected 2000000, got " + count);
    }
}
```

   Expect a number well below 2,000,000. Replace the field with `static final AtomicInteger count =
   new AtomicInteger();` and `count.incrementAndGet()`; now it is exact.

## Gotchas

- **`volatile` is not atomic.** `count++`, `if (x == null) x = ...` and check-then-act sequences
  still race.
- **"Works on my laptop"** proves little. x86 is more forgiving than ARM, and the interpreter more
  forgiving than C2. Reason from happens-before, not from test runs.
- **Adding `System.out.println` "fixes" the bug** because `println` synchronizes internally,
  accidentally adding edges and preventing hoisting. Remove the print and it breaks again.
- **Different locks give no visibility.** Writer and reader must use the same monitor.
- **Non-volatile `long` and `double` writes may tear** (the JMM allows a 64-bit write to be seen
  as two 32-bit halves). Most 64-bit JVMs don't, but the spec permits it; `volatile` forbids it.
- **Letting `this` escape in a constructor** (registering a listener, starting a thread) breaks
  the `final` field guarantee.

Follow-ups and strong answers:

- *How is `volatile` implemented?* The JIT emits memory barriers (fences) around volatile accesses
  and does not cache the field; on x86 the main cost is a fence after volatile writes, while ARM
  uses load-acquire/store-release instructions. Then return to the contract: what matters is the
  happens-before guarantee, not the instructions.
- *When would you use `volatile` over a lock?* A single writer or independent writes with many
  readers: stop flags, a reference to an immutable config swapped atomically.

## Explain it in 2 minutes

Prompt: "Explain the Java Memory Model and `volatile` to a junior engineer."

- Compilers, the JIT and CPUs reorder and cache memory operations; one thread can't tell, others
  can.
- Atomicity, visibility, ordering are separate problems.
- The JMM's happens-before relation is the contract: program order, lock release → acquire,
  volatile write → read, `start`, `join`, transitivity.
- `volatile` gives visibility and ordering (and publishes earlier writes) but not atomicity of
  `count++`.
- `synchronized` gives exclusion plus happens-before on the same lock; `final` fields and class
  init give safe publication; DCL needs `volatile`.

## Check yourself

1. Why can the JIT turn `while (running) {}` into an infinite loop?
2. What does a volatile write guarantee about *non-volatile* writes made before it?
3. Is `volatile int count; count++` safe with two threads? Why?
4. Two threads synchronize on different objects. Is there a happens-before edge between them?
5. Why does double-checked locking need `volatile`?

### Answers

1. Without a happens-before edge the thread need not see other threads' writes, so the JIT may
   read the field once and hoist it out of the loop.
2. A thread that reads the volatile and sees that write also sees every write made before it in
   the writer's thread.
3. No. Each read and write is visible, but read-add-write is not atomic, so updates are lost.
4. No. The edge exists only between unlock and lock of the same monitor.
5. Without it, another thread may see a non-null reference before the constructor's writes are
   visible, i.e. a half-built object.
