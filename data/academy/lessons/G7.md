## Where we are

From AI-ENG-2 you know the model-level ideas: messages, system prompts, structured output, tool use, streaming, caching, batching and `usage`. From SPRING-BOOT-4 you know how Spring Boot **starters** pull in dependencies and how **auto-configuration** creates beans from properties. This lesson connects the two: how to put LLM calls into a Spring Boot service cleanly, using either **Spring AI** or the **official Anthropic Java SDK**, and the single-gateway pattern this app uses.

## The problem

The first LLM feature usually looks like this:

```java
@PostMapping("/hint")
String hint(@RequestBody String problem) {
    var client = AnthropicOkHttpClient.fromEnv();             // new client per request
    var params = MessageCreateParams.builder()
        .model("claude-opus-5-5")                              // model id hard-coded here...
        .maxTokens(16000L).addUserMessage(problem).build();
    return client.messages().create(params).content().toString();   // ...no stop_reason check, no usage log
}
```

Six features later, the model id is copied into six places, nobody logs token usage, one controller handles refusals and five don't, the unit tests call the real API, and switching a feature to a cheaper model is a code hunt. These are the problems Spring already solves elsewhere with beans, configuration and a layer boundary. You apply the same tools here.

## Option 1: Spring AI, a portable abstraction

**Spring AI** is a Spring project that gives LLM features Spring-style abstractions, with starters and auto-configuration for many model providers (Anthropic, OpenAI, Azure OpenAI, Ollama and others). Its main ideas:

- **`ChatClient`:** a fluent API for building a prompt, calling a model and reading the result as text, a stream, or a mapped Java object. With a provider starter on the classpath and its properties set, auto-configuration gives you a `ChatClient.Builder` bean (exactly the SPRING-BOOT-4 pattern).
- **Advisors:** interceptors around a `ChatClient` call that can change the request and the response. They are the Spring AI equivalent of servlet filters or AOP advice. Built-in advisors cover things like conversation memory (re-sending prior turns, since the model is stateless, as in AI-ENG-1) and RAG (retrieve from a vector store and add the passages to the prompt, as in AI-ENG-3). You can write your own for logging or guardrails (AI-ENG-6).
- **`VectorStore`:** one interface over many vector databases, including a pgvector implementation, for the AI-ENG-3 indexing and search steps.
- **Tool calling and structured output:** your Java methods become tools the model can request (AI-ENG-2), and responses map onto your records.
- **MCP support:** client and server support for the protocol from AI-ENG-4.

A minimal shape (checked against the Spring AI 2.1 reference docs; the starter auto-configures `ChatClient.Builder`):

```java
@RestController
class AskController {
    private final ChatClient chatClient;

    AskController(ChatClient.Builder builder) {               // auto-configured by the starter
        this.chatClient = builder.defaultSystem("You are a concise interview coach.").build();
    }

    @GetMapping("/ask")
    String ask(@RequestParam String q) {
        return chatClient.prompt().user(q).call().content();
    }
}
```

**Strengths:** a provider switch is mostly configuration; advisors give you reusable cross-cutting behaviour; the vector store, memory and RAG pieces come ready-made; it feels like the rest of Spring.

**Cost:** an abstraction over many providers moves at the pace of the slowest common denominator. Provider-specific features (on Claude: effort levels, prompt-cache placement, refusal fallbacks, citations, server-side web search, batches) may arrive late, behind provider-specific options, or not at all. Check before you rely on one.

## Option 2: the official Anthropic Java SDK

The **Anthropic Java SDK** (`com.anthropic:anthropic-java`) is Anthropic's own client library. It maps one-to-one onto the API, so every feature from AI-ENG-2 is available as soon as the API ships it.

```java
AnthropicClient client = AnthropicOkHttpClient.fromEnv();      // reads ANTHROPIC_API_KEY

MessageCreateParams params = MessageCreateParams.builder()
    .model("claude-opus-5-5")
    .maxTokens(16000L)
    .system("You are a concise interview coach.")
    .addUserMessage("Give me one hint for LRU cache, not the solution.")
    .outputConfig(OutputConfig.builder().effort(OutputConfig.Effort.LOW).build())
    .build();

Message response = client.messages().create(params);
```

Things worth knowing:

- **The client is thread-safe and heavyweight** (it owns an HTTP connection pool). Create it **once** as a Spring bean and inject it everywhere.
- **Builders mirror the JSON API.** `outputConfig(...)` carries effort and structured output, `systemOfTextBlockParams(...)` carries cache-control markers, and `createStreaming(...)` gives you a stream of events (all shown in AI-ENG-2).
- **Effort:** on `claude-opus-5-5` the default effort is `medium`. Set `HIGH` for hard work, such as the research step in this app, and `LOW` for quick hints.
- **Retries and timeouts are built in:** the SDK retries rate-limit, overload and connection errors a couple of times by default, and you configure the timeout on the client builder.
- **Errors are typed:** catch specific exceptions (rate limit, not found) before the general `AnthropicServiceException`, so retryable and non-retryable failures are handled differently.
- **Other clouds:** the same SDK can target Claude on Microsoft Foundry, Amazon Bedrock or Google Vertex AI through a different backend on the client builder, while the `messages()` code stays the same.

**Strengths:** complete and current, so you get the exact feature set the docs describe. **Cost:** Claude-only. Portability is up to you, and the next section handles it.

## The gateway pattern: one class owns the model

Whichever library you pick, **put every model call behind one interface you own.** This app's rule is: *Claude API via the official Java SDK, only through `ClaudeGateway`.*

```text
 controllers / jobs (hint, research, mock interview)
              │   depend on
              ▼
     LlmGateway (interface you own)  ◄── FakeLlmGateway (tests)
              │   implemented by
              ▼
     ClaudeGateway ── AnthropicClient bean ── Anthropic API
       • model ids from config, per feature
       • stop_reason check (end_turn / max_tokens / refusal)
       • usage logging per call (feature, model, tokens, cache hits)
       • retries, timeouts, error mapping
```

This is plain dependency inversion: the features depend on your interface, not on a vendor class. You get one place for cost logging and policy, a fake for tests (no API calls, no flakiness), and a single seam if you ever switch to Spring AI or another provider.

## Choosing

```text
                        Spring AI                        Anthropic Java SDK
portability             high (config switch)             Claude only (gateway gives you a seam)
newest Claude features  may lag or need provider options available when the API ships them
RAG / memory / stores   built in (advisors, VectorStore) build them yourself (AI-ENG-3 code)
fit with Spring         native (starters, beans)         wrap in your own @Configuration
best when               multi-provider, standard RAG     deep use of one provider's features
```

Both are reasonable. This app chose the SDK because its pipeline relies on Claude-specific features (effort, web search and fetch tools, structured output, batches, refusal handling) and needs exact control over prompt caching. A team standardising on several providers might choose Spring AI. Either way, keep the gateway.

## Other ways to call a model from Java

Spring AI and the SDK are the two this app weighed, but there are four common ways in total.

| Way | How | When to choose | Pitfall |
|---|---|---|---|
| Raw `java.net.http` | POST JSON to the Messages REST endpoint yourself | Learning, a strict no-dependency rule, or a one-off script | You rebuild everything the SDK gives you, and keep it current |
| Official Java SDK | Typed builders that map one-to-one onto the API | One provider, used deeply, with new features on day one | Claude-only; portability is your gateway's job |
| Spring AI | `ChatClient`, advisors, `VectorStore`, provider starters | Several providers, standard RAG and memory, Spring style | Provider-specific features can lag or need provider options |
| LangChain4j AI Services | Declare an interface; the library generates a proxy that builds the prompt and parses the reply | A declarative style with many prompts, and ready-made RAG and memory building blocks | The proxy hides the actual request, so log it; provider features can lag as well |

**What the SDK saves you.** Here is the raw version:

```java
HttpRequest req = HttpRequest.newBuilder(URI.create("https://api.anthropic.com/v1/messages"))
    .timeout(Duration.ofSeconds(60))
    .header("x-api-key", System.getenv("ANTHROPIC_API_KEY"))
    .header("anthropic-version", "2026-10-21")          // required; check the docs for the current value
    .header("content-type", "application/json")
    .POST(HttpRequest.BodyPublishers.ofString("""
        {"model":"claude-opus-5-5","max_tokens":1024,
         "messages":[{"role":"user","content":"One hint for LRU cache, not the solution."}]}"""))
    .build();
HttpResponse<String> res = HttpClient.newHttpClient().send(req, HttpResponse.BodyHandlers.ofString());
```

That works, and then you still need: retries with backoff on 429, 5xx and connection errors, typed errors instead of status-code checks, SSE parsing for streaming, response types instead of raw JSON trees, schemas derived from records for structured output, and the other cloud backends. The SDK has all of these built in.

**LangChain4j AI Services** in a few lines:

```java
interface Coach {
    @SystemMessage("You are a concise interview coach.")
    @UserMessage("Give one hint, not the solution, for: {{it}}")
    String hint(String problem);
}

Coach coach = AiServices.create(Coach.class, model);   // the Spring Boot starter can create this bean for you
```

A method can return a record (structured output) or a `TokenStream` (streaming). `chatMemoryProvider(...)` with a `@MemoryId` parameter keeps one conversation per user, `tools(...)` registers `@Tool` methods, and `contentRetriever(...)` adds RAG.

The rule: choose by *how many providers* and *how many provider-specific features* you need, then hide the choice behind the gateway.

## Streaming to the browser and cheaper calls

Two production concerns remain: users want to see tokens as they arrive, and the bill should not grow with traffic one-for-one.

| Way | How | When to choose | Pitfall |
|---|---|---|---|
| `SseEmitter` (Spring MVC) | Return an `SseEmitter`; on another thread, read the SDK stream and `send()` each text delta, then `complete()` | A servlet (MVC) app, blocking code, virtual threads | If the browser goes away, stop the upstream call (below), or you keep paying for tokens nobody reads |
| WebFlux `Flux` | Return `Flux<String>` as `text/event-stream`; Spring AI's `chatClient.prompt().user(q).stream().content()` already is a `Flux<String>` | Reactive apps, or MVC apps with webflux on the classpath (Spring AI streaming needs it) | Blocking calls inside the pipeline; a source that ignores cancellation |
| Response cache | Key = hash(model, prompt version, normalised input); store the answer with a TTL | Repeated identical, non-personal questions (FAQ-style hints) | Serving one user's answer to another: include the tenant or user in the key when answers are personal |
| Semantic cache | Embed the question; if a cached question is closer than a threshold, return its answer | Many paraphrases of the same question | False hits: "LFU eviction" can match a cached "LRU eviction" answer (the AI-ENG-3 problem again) |
| Cheap-model-first cascade | Send the request to a small model; escalate to a larger one when a rule fires | High volume where most requests are easy | You pay twice on every escalation, and caches are per model |

**Cancellation.** With `SseEmitter`, register `onCompletion`, `onTimeout` and `onError` callbacks that close the SDK's `StreamResponse` (it is `AutoCloseable`), and treat an `IOException` from `send()` as "client gone": stop reading. With WebFlux, a client disconnect cancels the subscription, and the cancel travels upstream, as long as your source releases the HTTP stream when it is cancelled.

**Escalation rules must be checkable in code**, not just a hunch:

```text
escalate to the larger model when:
  - structured output fails validation (business rules, not just shape)
  - stop_reason is max_tokens or refusal
  - a router classified the input as hard before the first call
  - a deterministic check fails (unknown slug, citation not in the passages)
never on: "the cheap model says it is unsure" alone (self-reported confidence is unreliable)
```

Before building a cascade, measure the simpler option: the strong model at lower **effort** on the same eval set. One model keeps one cache and one set of prompts.

Prompt caching (AI-ENG-2) is a different thing from a response cache. It makes the model *read* a repeated prefix more cheaply, but still generates a fresh answer. A response cache skips the call entirely.

The rule: stream what people watch and cancel what they abandon, cache exact repeats, and escalate on rules your code can check.

## Lab (~10 min)

Build the gateway skeleton in a Spring Boot 3 or 4 app on Java 21. Add `com.anthropic:anthropic-java` to the build and set `ANTHROPIC_API_KEY`.

```java
// LlmGateway.java
public interface LlmGateway {
    String complete(String feature, String system, String user);
}
```

```java
// ClaudeConfig.java
import com.anthropic.client.AnthropicClient;
import com.anthropic.client.okhttp.AnthropicOkHttpClient;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
class ClaudeConfig {
    @Bean
    AnthropicClient anthropicClient() {          // one client for the whole app
        return AnthropicOkHttpClient.fromEnv();
    }
}
```

```java
// ClaudeGateway.java
import com.anthropic.client.AnthropicClient;
import com.anthropic.models.messages.Message;
import com.anthropic.models.messages.MessageCreateParams;
import java.util.stream.Collectors;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Service;

@Service
class ClaudeGateway implements LlmGateway {
    private static final Logger log = LoggerFactory.getLogger(ClaudeGateway.class);

    private final AnthropicClient client;
    private final String model;

    ClaudeGateway(AnthropicClient client,
                  @Value("${prepos.claude.model:claude-opus-5-5}") String model) {
        this.client = client;
        this.model = model;
    }

    @Override
    public String complete(String feature, String system, String user) {
        MessageCreateParams params = MessageCreateParams.builder()
            .model(model)
            .maxTokens(16000L)
            .system(system)
            .addUserMessage(user)
            .build();

        Message response = client.messages().create(params);

        String stop = response.stopReason().map(Object::toString).orElse("none");
        log.info("llm feature={} model={} stop={} inputTokens={} outputTokens={} cacheRead={}",
            feature, model, stop,
            response.usage().inputTokens(), response.usage().outputTokens(),
            response.usage().cacheReadInputTokens());

        if (!"end_turn".equals(stop)) {
            throw new IllegalStateException("LLM call for " + feature + " stopped with " + stop);
        }
        return response.content().stream()
            .flatMap(block -> block.text().stream())
            .map(text -> text.text())
            .collect(Collectors.joining());
    }
}
```

```java
// FakeLlmGateway.java (src/test): deterministic, no network
class FakeLlmGateway implements LlmGateway {
    @Override
    public String complete(String feature, String system, String user) {
        return "[fake " + feature + "] " + user.substring(0, Math.min(20, user.length()));
    }
}
```

Then:

1. Inject `LlmGateway` into a small `HintController` and call it with `feature = "hint"`.
2. Hit the endpoint twice and read the log line: input and output tokens per call, and the stop reason.
3. Set `maxTokens` to `20` and call it again. The stop reason becomes `max_tokens` and the gateway throws instead of returning a half-sentence. That is the check you'd otherwise forget in six controllers.
4. Write a controller test that uses `FakeLlmGateway`. It runs in milliseconds and never calls the network.

(The usage and stop-reason accessors follow the SDK's generated pattern. If your SDK version differs slightly, let the compiler error point you to the right name.)

Production next steps, in the order this app plans them: per-feature model and effort settings in config, prompt caching on the system prompt (AI-ENG-2), refusal fallbacks (a beta API option that Anthropic recommends enabling on current models; check the SDK docs for the Java builder), running calls on virtual threads, and persisting `usage` to a table so cost can be queried.

## Gotchas

- **A client per request:** wastes pools and threads. One singleton bean.
- **Model ids scattered in code:** put them in per-feature config; switch via config plus an eval run (AI-ENG-6).
- **Blocking request threads on long calls:** virtual threads (`spring.threads.virtual.enabled=true`, Boot 3.2+), SSE for users, async jobs for pipelines.
- **Assuming Spring AI exposes every feature:** check caching control, effort, citations, batches in your version first.
- **Logging full prompts and responses:** they may hold personal data or secrets. Log `usage`, ids and hashes by default.
- **Tests hitting the real API:** slow, flaky, costly. Use the fake gateway; real-model checks live in evals.

## Explain it in 2 minutes

*"How would you integrate an LLM into a Spring Boot service?"*

1. Spring AI for portability and ready-made RAG/memory; the vendor SDK for full provider features.
2. Client as one bean; model ids and effort in per-feature config.
3. One gateway: check `stop_reason`, log `usage`, map errors, retry; structured output, streaming, virtual threads.
4. Fake gateway for unit tests; eval suite for real-model quality.
5. Per-feature token logs, cache hits, spend alerts.
