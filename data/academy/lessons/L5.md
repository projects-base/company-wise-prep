## Where we are

From D4 you know *what* auto-configuration is: `@Conditional` configuration classes, listed in an imports file and chosen at startup. From L4 you know the life of a single bean. This lesson connects the two. It follows the whole sequence from `SpringApplication.run(...)` to "Started CompanyWisePrepApplication in 3.2 seconds", one stage at a time, with the trap waiting at each stage.

## The problem

This repo's main method is one line:

```java
SpringApplication.run(CompanyWisePrepApplication.class, args);
```

A few seconds later, Tomcat is listening, JPA is connected and `DataImporter` has loaded the bank. When startup fails, or is slow, or something happens "too early", you need to know which stage you are in. Otherwise you can't tell where to look: a listener registered in the wrong place, a property not yet loaded, or a runner that delays readiness.

## The whole lifecycle at a glance

```text
main()
 └─ new SpringApplication(primarySource)                      (0) set-up
 └─ run(args)
     ├─ starting                → ApplicationStartingEvent      (1)
     ├─ prepare Environment     → ApplicationEnvironmentPreparedEvent   (2)
     ├─ print banner
     ├─ create ApplicationContext (servlet flavour)            (3)
     ├─ prepare context: initializers, register main class
     │                          → ApplicationContextInitializedEvent
     │                          → ApplicationPreparedEvent      (4)
     ├─ refresh()  ── definitions, auto-config, BPPs, web server, singletons   (5)
     │                          → ServletWebServerInitializedEvent
     │                          → ContextRefreshedEvent
     ├─ ApplicationStartedEvent → AvailabilityChangeEvent(LivenessState.CORRECT)   (6)
     ├─ call runners (ApplicationRunner, CommandLineRunner)    (7)
     └─ ApplicationReadyEvent   → AvailabilityChangeEvent(ReadinessState.ACCEPTING_TRAFFIC)   (8)
   on any exception: ApplicationFailedEvent + FailureAnalyzer message
```

An **`ApplicationContext`** is the Spring container itself: it holds the bean definitions and the beans. An **event** is an object that Spring *publishes* at a moment in the lifecycle. A **listener** is code that receives it. Each stage below says what happens, then names its trap.

## Stage 0: constructing `SpringApplication`

**What happens:** Spring decides what kind of application this is. It inspects the classpath: if the Servlet API and Spring MVC's `DispatcherServlet` are present, this is a *servlet* web app. It then loads early helpers, namely `ApplicationContextInitializer`s and `ApplicationListener`s, from `META-INF/spring.factories` files in your jars.

**Gotcha:** adding `spring-boot-starter-webflux` next to `spring-boot-starter-web` does not make the app reactive. When both are present, the servlet type wins. Force a choice with `spring.main.web-application-type`.

## Stage 1: starting

**What happens:** Spring creates the run listeners and publishes `ApplicationStartingEvent`. It has almost nothing yet: no environment and no beans.

**Gotcha:** a `@Component` that listens for this event **never fires**, because no beans exist yet. Listeners for early events must be registered with `app.addListeners(...)` or in `spring.factories`.

## Stage 2: the Environment

**What happens:** Spring builds the **`Environment`**, the single place to read properties, by layering property sources in priority order: command-line arguments, then environment variables, then `application-{profile}.yml`, then `application.yml`, and so on. **`EnvironmentPostProcessor`**s run at this point, and loading `application.yml` is itself done this way. Active profiles are decided here.

**Gotcha:** setting a profile in code with `@Profile`, or inside a bean, is too late to change which config files load. Profiles must be known *now*, from `spring.profiles.active` in the arguments, an environment variable or the base config file.

## Stage 3: create the context

**What happens:** Spring instantiates an empty context of the right type. For a servlet app it is a `ServletWebServerApplicationContext` variant, which knows how to start an embedded server. The banner prints just before this.

**Gotcha:** there is nothing to break here. But this is why a test with `webEnvironment = NONE` cannot serve HTTP: it gets a different context type.

## Stage 4: prepare the context

**What happens:** `ApplicationContextInitializer`s run, giving a last chance to adjust the context programmatically, and Spring publishes `ApplicationContextInitializedEvent`. Then your **primary source**, the `@SpringBootApplication` class, is registered as the first bean definition. No other definitions exist yet. Spring publishes `ApplicationPreparedEvent`.

**Gotcha:** if you pass the wrong class to `run(...)`, scanning starts from the wrong package and your beans "disappear".

## Stage 5: `refresh()`, where most of the time goes

This is the standard Spring container refresh from D2 and L4, with Boot's additions. Broken into steps:

```text
refresh()
 a. invokeBeanFactoryPostProcessors
      ConfigurationClassPostProcessor reads @SpringBootApplication:
        component scan   → your @Component/@Service/@RestController definitions
        @Import(AutoConfigurationImportSelector) — DEFERRED, so runs after your config
          → read every AutoConfiguration.imports file
          → evaluate @Conditional* on each candidate → keep the matches
 b. registerBeanPostProcessors   (autowiring, @Transactional proxies, validation…)
 c. onRefresh  → Boot CREATES the embedded web server (Tomcat), not yet accepting requests
 d. finishBeanFactoryInitialization → create every non-lazy singleton (L4's lifecycle, per bean)
      EntityManagerFactory, DataSource, your services, controllers…
 e. finishRefresh → start SmartLifecycle beans → web server STARTS listening
      → ServletWebServerInitializedEvent (port is now known)
      → ContextRefreshedEvent
```

**Gotchas at this stage:**

- **(a)** "Bean not found" or "auto-config didn't apply" problems are decided here. Run with `--debug` to print the **conditions evaluation report**, which lists every auto-configuration as a positive or negative match, with the reason.
- **(d)** This is where most startup errors happen: an `UnsatisfiedDependencyException`, a circular reference (which Boot forbids by default), or a failed database connection. Boot's **FailureAnalyzers** turn these into the readable "APPLICATION FAILED TO START … Action:" block.
- **(d)** A slow `@PostConstruct`, such as one that calls a remote service, stalls the *entire* startup.
- **(e)** Tomcat accepts connections from this point on, **before your runners have run**.

## Stage 6: started

**What happens:** Spring publishes `ApplicationStartedEvent`, then sets liveness to `CORRECT`. The context is fully usable.

**Gotcha:** "started" does not mean "ready". Readiness is still `REFUSING_TRAFFIC`.

## Stage 7: runners

**What happens:** every `ApplicationRunner` and `CommandLineRunner` bean runs once, ordered by `@Order`, on the main thread. This repo's `DataImporter` is one. It imports `data/` into the database here.

**Gotchas:**

- Runners run *after* Tomcat started listening, so a request can arrive before the import finishes. Readiness (D8) exists to cover exactly this window: orchestrators wait for `ACCEPTING_TRAFFIC`.
- An exception thrown by a runner **fails the whole startup**, and the context is closed. That is right for "data dir missing" (`DataImporter` throws). It is wrong for "optional cache warm-up failed", so catch those errors.
- A long runner delays readiness. Move work that doesn't need to finish before traffic arrives to a background executor.

## Stage 8: ready

**What happens:** Spring publishes `ApplicationReadyEvent`, then sets readiness to `ACCEPTING_TRAFFIC`. Note that the familiar "Started … in N seconds" log line was printed back at stage 6, *before* the runners. A slow runner therefore doesn't show up in that number.

**Gotcha:** `@EventListener(ApplicationReadyEvent.class)` is the right hook for "after everything is up". `ContextRefreshedEvent` is not: it can fire more than once in some context hierarchies, and it fires before the runners.

## Lab (~10 min)

Watch every stage, and note which thread runs it. Change `main` in `CompanyWisePrepApplication`:

```java
public static void main(String[] args) {
    SpringApplication app = new SpringApplication(CompanyWisePrepApplication.class);
    app.addListeners((ApplicationListener<ApplicationEvent>) e -> {
        if (e.getClass().getName().contains("Servlet") && e.getClass().getSimpleName().contains("Request")) return; // skip per-request events
        String extra = e instanceof AvailabilityChangeEvent<?> a ? " -> " + a.getState() : "";
        System.out.printf(">>> %-40s [%s]%s%n", e.getClass().getSimpleName(), Thread.currentThread().getName(), extra);
    });
    app.run(args);
}
```

Add a runner that prints a marker:

```java
@Bean
ApplicationRunner marker() {
    return args -> System.out.println(">>> runner: now running ApplicationRunner beans");
}
```

**Observe:**

1. Start the app and filter the console for `>>>`. You should see `ApplicationStartingEvent`, `ApplicationEnvironmentPreparedEvent`, `ApplicationContextInitializedEvent`, `ApplicationPreparedEvent`, `ServletWebServerInitializedEvent`, `ContextRefreshedEvent`, `ApplicationStartedEvent`, `AvailabilityChangeEvent -> CORRECT`, the runner lines (yours and `DataImporter`'s "Imported …"), `ApplicationReadyEvent` and `AvailabilityChangeEvent -> ACCEPTING_TRAFFIC`. Everything runs on `[main]`.
2. Note that "Tomcat started on port 8090" appears **before** the runner lines.
3. Start with `--debug` and find `DataSourceAutoConfiguration` under *Positive matches*. Then look up any auto-config under *Negative matches* and read its reason.
4. **Break it:** in the runner, `throw new IllegalStateException("boom")`. You get `ApplicationFailedEvent`, the context closes, and the process exits. Then point `prep.data-dir` at a missing folder and see `DataImporter`'s message fail startup the same way.
5. **Bonus:** call `app.setApplicationStartup(new BufferingApplicationStartup(4096))` with Actuator's `startup` endpoint exposed, then `POST /actuator/startup` to see which steps took the time.

## Gotchas

- **Early-event listeners as `@Component`s never fire.** Register them with `SpringApplication.addListeners` or in `spring.factories`.
- **Profiles decided after stage 2 don't change which config files load.** Set them through arguments, environment variables or the base config.
- **Runners run after the server is listening.** Use readiness probes, and keep runners short or move work to the background.
- **A runner exception kills startup.** Decide on purpose whether a failure should do that.
- **Use `ApplicationReadyEvent`, not `ContextRefreshedEvent`,** for "the app is fully up".
- **Debug auto-config with `--debug` or `/actuator/conditions`,** not by guessing.

## In interviews

Typical prompts are "What happens when a Spring Boot application starts?", "How does Boot decide which auto-configurations to apply?", "How would you run code once the application is ready?" and "Our app takes 90 seconds to start: how do you investigate?". [Design a Configuration Service](#/q/design-configuration-service) builds on stage 2's layered `Environment`.

**Follow-up: "How would you speed startup up?"** A strong answer starts by measuring, with `BufferingApplicationStartup` and the `/actuator/startup` endpoint. Then: remove unused starters (fewer auto-config candidates), avoid slow `@PostConstruct` work, consider `spring.main.lazy-initialization=true` (trading a slower first request for a faster start), and mention class data sharing (CDS), AOT compilation and native images as heavier options.

## Explain it in 2 minutes

*"Walk me through `SpringApplication.run`."*

- It deduces the app type from the classpath, and loads initializers and listeners from `spring.factories`.
- It builds the `Environment` (layered property sources, active profiles), then creates the right context type.
- `refresh()`: the configuration class processor scans components, then deferred auto-configs with their conditions are evaluated. Post-processors register, the embedded server is created, all singletons are instantiated, and the server starts listening.
- Then `ApplicationStartedEvent` and liveness `CORRECT`. Runners run.
- Then `ApplicationReadyEvent` and readiness `ACCEPTING_TRAFFIC`.
- On failure: `ApplicationFailedEvent` and a FailureAnalyzer report. Use `--debug` for the conditions report.

## Check yourself

1. Your `@Component` listener for `ApplicationEnvironmentPreparedEvent` never runs. Why?
2. At which step does Tomcat start accepting connections, relative to `DataImporter`?
3. Where in startup is `@ConditionalOnMissingBean` evaluated, and why can it see your beans?
4. Why is `ApplicationReadyEvent` better than `ContextRefreshedEvent` for warm-up work?
5. A runner throws. What happens to the application?

### Answers

1. That event fires in stage 2, before any beans exist, so a bean cannot listen for it. Register the listener on the `SpringApplication`.
2. In `finishRefresh` (stage 5e), which is before runners (stage 7) such as `DataImporter`. Readiness covers the gap.
3. In stage 5a, while `ConfigurationClassPostProcessor` processes definitions. Auto-configs are imported by a *deferred* selector, after user configuration has been processed.
4. It fires once, after refresh *and* after the runners. `ContextRefreshedEvent` fires earlier, and it can fire multiple times in context hierarchies.
5. Startup fails: `ApplicationFailedEvent` is published, the context is closed, and the process exits with an error.
