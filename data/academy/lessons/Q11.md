## Where we are

DB-SQL-10 climbed the scaling ladder for one relational database: replicas, caching, partitioning,
CQRS, and finally sharding by hand. DIST-SYS-1 covered Redis as a cache. This lesson looks at
databases that are *built* to be spread across many machines. It covers what each family gives up
to do that, and how to choose, including when the honest answer is "stay on Postgres".

## The problem

A chat product stores messages. The numbers are large and lopsided:

- Writes never stop: every message sent is an insert.
- Almost every read is the same shape: "the latest 50 messages in conversation X, then the 50 before
  that".
- Nobody joins messages to anything at read time. Nobody asks "all messages containing 'refund'
  across all users" on the hot path. That's a search feature, served separately.

Postgres can do this for a long time (DB-SQL-10). But once one primary can't absorb the writes, you
are sharding by hand: routing, rebalancing, cross-shard queries. Some databases do that partitioning
for you. In return, they ask you to design around your queries instead of around your entities.

## Why NoSQL exists

**NoSQL** is a loose label for non-relational databases. Three motivations recur:

1. **Scale-out.** The data is split across many nodes by a key, and replication is built in. Adding
   nodes adds capacity. That's **horizontal scaling**, versus a bigger single machine.
2. **Flexible schema.** Records in one collection can have different fields, so the shape can
   change without a migration. The schema still exists, just in your code instead of the DB.
3. **Access-pattern-first design.** You list the queries first, then lay the data out so each query
   reads one partition, often one contiguous chunk of disk.

What you usually give up: joins, ad-hoc queries on any column, multi-row transactions (or you get
them only in limited forms), and sometimes strong consistency (SYS-DES-3). None of the families is
"faster" in general. Each is fast *for the access pattern it was designed around*.

## Key-value: Redis and DynamoDB

A **key-value store** maps a key to an opaque value. You can get, put and delete by key, and little
else. Redis is the in-memory version (DIST-SYS-1).

**DynamoDB** (AWS, managed) is a durable, partitioned one, with a little more structure. Each item
has a **partition key**, hashed to choose a storage partition, and an optional **sort key** that
orders items within that partition. That gives you "get one item" and "query a range within one
partition key", for example all orders of customer 42 between two dates. Anything else needs a
**global secondary index**, which is effectively a second copy of the table keyed differently and
updated asynchronously. Or it needs a full scan, which you avoid.

What goes wrong: a **hot partition**, one key taking a large share of the traffic (a celebrity's
feed, a flash sale). It hits per-partition throughput limits however big the table is. DynamoDB
offers conditional writes (compare-and-set) and limited multi-item transactions. Reads are
eventually consistent by default, and you can ask for strongly consistent reads on the base table.

## Document stores: MongoDB

A **document store** keeps JSON-like documents. MongoDB stores **BSON** (binary JSON) documents in
**collections**. Every document has an `_id`. A document can nest objects and arrays, so one
document can hold what would be several joined rows in SQL.

```json
{ "_id": "o-1001", "customerId": "c-42", "status": "PLACED",
  "lines": [ { "item": "Naan", "qty": 3, "unitPricePaise": 6000 } ] }
```

The core modeling choice is **embedding vs referencing**:

- **Embed** when the child is owned by the parent, read together with it, and *bounded* in size.
  Order lines inside an order fit that.
- **Reference** (store the other document's `_id`) when the child is unbounded, shared, or updated
  on its own. Messages in a conversation are unbounded, so reference them. A document has a hard size
  limit (16 MB), and rewriting a large, growing document gets expensive long before that.

Indexes are B-trees, as in Postgres (DB-SQL-6): single-field, compound (where order matters), and
**multikey** indexes over array elements. A write to one document is atomic. **Multi-document ACID
transactions** have existed since MongoDB 4.0 (replica sets) and 4.2 (sharded clusters). They
work, but they cost more, so a schema that needs them everywhere is a hint you wanted Postgres.

Durability and consistency are settings. A **replica set** has one primary and secondaries.
`writeConcern: majority` waits until most members have the write. Reading from secondaries can
return stale data, the same replica-lag issue as DB-SQL-10.

## Wide-column: Cassandra

**Cassandra** is a **wide-column store**: tables with rows and columns, but laid out by a
two-part primary key.

- The **partition key** is hashed onto a ring of nodes (consistent hashing, SYS-DES-1). All rows with
  the same partition key live together, on the same replicas.
- **Clustering columns** sort the rows *inside* a partition on disk.

A query must name the full partition key. It may then select a range of clustering columns, in order.
That's the whole query model: no joins, and no filtering on arbitrary columns without an index or an
`ALLOW FILTERING` scan you shouldn't use in production.

So you design **query-first**: one table per query, and the same data written to several tables if
several queries need it. Denormalization (DB-SQL-3) is the normal state here, not the exception.

### Tunable consistency

Each partition is stored on **N** replicas (the replication factor, commonly 3). Each request picks
a **consistency level**: how many replicas must answer. Writes wait for **W** of them, reads for
**R**.

```text
 N = 3 replicas      write at QUORUM (W=2)      read at QUORUM (R=2)
   [A] [B] [C]       A ✓  B ✓  C (later)        reads B, C → B has it
                     R + W = 4 > N = 3  ⇒  every read set overlaps every write set
```

If **R + W > N**, every read touches at least one replica that has the latest acknowledged write.
`QUORUM` for both is the usual choice. `ONE`/`ONE` is faster and more available, but a read can
miss a recent write. Conflicts are resolved by **last write wins** using per-cell timestamps, so
clock skew between clients matters. For compare-and-set ("insert only if absent"), Cassandra has
**lightweight transactions** (`IF NOT EXISTS`). They use a Paxos round and are much slower than
normal writes.

### Why writes are fast: the LSM tree

Cassandra stores data in an **LSM tree** (log-structured merge tree). A write never updates data in
place:

```text
 write ─► commit log (sequential append, for crash recovery)
       └► memtable (sorted, in memory) ── when full, flush ──► SSTable (immutable, sorted file)
                                                    background compaction merges SSTables
```

A write is one sequential append plus an in-memory insert. There is no read-before-write and no
random disk I/O. An "update" is just a newer version, and a delete writes a **tombstone** (a
deletion marker). The cost moves to reads. A read may check the memtable and several SSTables, with
per-SSTable Bloom filters (SYS-DES-1) to skip files that can't contain the key. Compaction keeps that
number down.

What goes wrong in practice:

- **Large or hot partitions.** "All messages of a conversation" in one partition grows forever. Bucket
  it by time.
- **Tombstone build-up.** Delete-heavy, queue-like tables make reads scan many tombstones. Don't use
  Cassandra as a queue.
- **Modeling with SQL instincts.** Starting from entities instead of queries ends with no table that
  can answer the query.

## Search: Elasticsearch

**Elasticsearch** is built on an **inverted index**: a map from each term to the list of documents
containing it, like the index at the back of a book. Text is run through an **analyzer**
(tokenise, lowercase, stem) at index time and at query time, so "Refunds" matches "refund". Results
are scored for relevance. Postgres B-trees can't do that.

Two properties decide how you use it:

- **Near-real-time.** A new document becomes searchable after the next **refresh**, by default
  roughly every second. It isn't visible the instant the write returns.
- **Not a primary store.** It has no multi-document transactions, and changing a field's mapping
  usually means reindexing. Keep the source of truth in Postgres or similar, and feed Elasticsearch
  from it, via change data capture or an outbox and Kafka (DIST-SYS-2). Then you can always rebuild
  the index from the source.

## Graph and time-series, briefly

**Graph databases** (Neo4j) store nodes and relationships as first-class records. Following a
relationship is a pointer hop, not a join. They shine for many-hop questions: "friends of friends who
like X", fraud rings, permission graphs. Neo4j queries use **Cypher**, a pattern language like
`(a)-[:FOLLOWS]->(b)`. If your queries are one or two hops, SQL joins usually do fine.

**Time-series databases** (InfluxDB, TimescaleDB on Postgres, Prometheus for metrics) are optimised
for append-only, timestamped data queried by time range. They partition by time, compress columns,
downsample old data, and drop expired chunks cheaply. Use one for metrics, IoT readings or price
ticks, not for business entities.

## One access pattern, three databases

*"Messages by conversation, newest first, 50 at a time."*

**PostgreSQL**: one table, one composite index, keyset pagination (DB-SQL-8):

```sql
CREATE TABLE message (
  id              BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  conversation_id BIGINT NOT NULL,
  sender_id       BIGINT NOT NULL,
  sent_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
  body            TEXT NOT NULL
);
CREATE INDEX ix_message_conv ON message (conversation_id, sent_at DESC, id DESC);

SELECT id, sender_id, sent_at, body
FROM message
WHERE conversation_id = 42
  AND (sent_at, id) < (TIMESTAMPTZ '2026-11-01 10:00:00+05:30', 98765)   -- last row of the previous page
ORDER BY sent_at DESC, id DESC
LIMIT 50;
```

**MongoDB**: one document per message, referencing the conversation, with a compound index:

```javascript
db.messages.createIndex({ conversationId: 1, sentAt: -1, _id: -1 })
db.messages.find({ conversationId: 42, sentAt: { $lt: lastSentAt } })
           .sort({ sentAt: -1, _id: -1 }).limit(50)
```

**Cassandra**: the table *is* the query. Partition by conversation plus a month bucket, so no
partition grows forever. Cluster by a time-based id, newest first:

```sql
CREATE TABLE messages_by_conversation (
  conversation_id bigint,
  bucket          text,          -- e.g. '2026-11'
  message_id      timeuuid,      -- unique and time-ordered
  sender_id       bigint,
  body            text,
  PRIMARY KEY ((conversation_id, bucket), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);

SELECT message_id, sender_id, body FROM messages_by_conversation
WHERE conversation_id = 42 AND bucket = '2026-11' AND message_id < ?
LIMIT 50;
```

(That last block is CQL, Cassandra's SQL-like language, not PostgreSQL.) If the bucket holds fewer
than 50 older messages, the app moves on to the previous month's bucket. In Cassandra, "unread counts
per user" would need its own table. In Postgres, it's another query.

## Choosing: a checklist

| If you need... | Reach for |
|---|---|
| Transactions across entities, joins, ad-hoc reporting, strong constraints | PostgreSQL |
| Flexible, nested, aggregate-shaped records read as a whole | MongoDB, or Postgres `JSONB` |
| Very high write volume, known queries by key, multi-region, always writable | Cassandra (or DynamoDB managed) |
| Sub-millisecond reads of hot data, counters, rate limits, locks | Redis |
| Full-text search, relevance, facets | Elasticsearch, fed from the source of truth |
| Many-hop relationship queries | Neo4j |
| Metrics or sensor data by time range | A time-series DB (TimescaleDB, InfluxDB) |

Before leaving Postgres, check what it already does:

- **`JSONB`** columns store documents, with GIN indexes for containment queries (`data @> '{"veg": true}'`).
- **Partial indexes** (`WHERE status = 'OPEN'`) keep hot-subset indexes small (DB-SQL-6).
- **Full-text search** (`tsvector` + GIN) is good enough for many in-app search boxes.
- **Partitioning** and read replicas (DB-SQL-10) carry most products further than they expect.

A strong default is "Postgres, plus Redis for hot reads". Add a specialised store only when a named
access pattern or a measured limit justifies running a second database. Each new store adds backups,
monitoring, on-call knowledge, and data to keep in sync.

## The Spring Data angle

Spring Data gives every store the same repository idea. The mapping annotations change, and so do
the queries a repository can derive.

```java
@Document("messages")
class MongoMessage {
    @Id String id;
    long conversationId;
    Instant sentAt;
    String body;
}

interface MongoMessageRepository extends MongoRepository<MongoMessage, String> {
    List<MongoMessage> findByConversationIdAndSentAtBeforeOrderBySentAtDesc(long conversationId, Instant before,
                                                                             Pageable page);
}

@Table("messages_by_conversation")
class CassandraMessage {
    @PrimaryKeyColumn(name = "conversation_id", ordinal = 0, type = PrimaryKeyType.PARTITIONED) long conversationId;
    @PrimaryKeyColumn(name = "bucket", ordinal = 1, type = PrimaryKeyType.PARTITIONED) String bucket;
    @PrimaryKeyColumn(name = "message_id", ordinal = 2, type = PrimaryKeyType.CLUSTERED,
                      ordering = Ordering.DESCENDING) UUID messageId;
    String body;
}

interface CassandraMessageRepository extends CassandraRepository<CassandraMessage, MapId> {
    Slice<CassandraMessage> findByConversationIdAndBucket(long conversationId, String bucket, Pageable page);
}
```

The Mongo repository will derive almost any query you name, and that includes ones with no index.
The Cassandra repository only works when the method matches the primary key. Asking for
`findByBody` fails or needs `ALLOW FILTERING`, which is the data model telling you to add a table.
There's no `@ManyToOne` and no lazy loading in either: relationships are your modeling decision, not
the framework's.

## Lab (~10 min)

**Design exercise.** A food-delivery app needs:

1. Placing an order and charging the customer's wallet, without double-charging.
2. The rider's live location on the customer's map, updated every few seconds.
3. Each rider's full location history for 90 days, for disputes.
4. Restaurant search by name, dish and cuisine, typo-tolerant, filtered by "open now".
5. An ops dashboard: orders per city per hour.

For each requirement, pick a store and name the key or index, the consistency you need, and how the
data gets there. Then say which store you'd *drop* first if the team were only three people. A
model answer is in **Answers**.

## Gotchas

- **Choosing NoSQL for "scale" without naming the access pattern.** You lose joins and transactions
  and gain nothing. Name the queries first.
- **Unbounded partitions or documents.** A conversation's messages in one Cassandra partition or one
  Mongo document keep growing. Bucket by time, or reference instead of embedding.
- **Treating Elasticsearch as the source of truth.** Data is visible only after a refresh and can't
  be updated transactionally. Feed it from a primary store you can rebuild it from.
- **`R + W ≤ N` and expecting read-your-writes.** `ONE`/`ONE` with N=3 can return stale data. Use
  `QUORUM`/`QUORUM`, or accept eventual consistency explicitly.
- **Cassandra as a queue.** Deleting consumed rows creates tombstones, and reads slow down. Use Kafka
  (DIST-SYS-2) or a real queue.
- **Ignoring Postgres features.** `JSONB`, partial indexes, full-text search and partitioning often
  remove the need for a second database.

## In interviews

The common shapes:

- "SQL or NoSQL for X?" Don't answer with a brand. Answer with the access patterns, consistency needs,
  write volume and team cost, then pick.
- "How would you model this in Cassandra?" List the queries, make one table per query, choose the
  partition key for even spread and bounded size, and choose clustering columns for the sort order.
- "Why is Cassandra fast at writes?" Commit-log append plus memtable, immutable SSTables, compaction
  in the background, no read-before-write. Then name what that costs reads.

**Typical follow-up:** "What consistency level would you use, and what happens when a node is down?"
With N=3 and QUORUM, one replica can be down and both reads and writes still succeed. With two down,
QUORUM fails, and you choose between rejecting requests and dropping to `ONE` (availability over
consistency, SYS-DES-3).

**Another follow-up:** "Why not just use MongoDB for everything?" It can work. But if the domain is
relational, you'd rebuild joins in code and lean on multi-document transactions, and Postgres is the
better fit.

## Explain it in 2 minutes

*"How do you choose a database for a new service?"*

1. Write down the access patterns: the top queries, their shape, and read/write volume.
2. Write down the consistency and transaction needs: what must never be wrong (money, inventory).
3. Default to Postgres. Check whether `JSONB`, indexes, partitioning or replicas already cover it.
4. Add a specialised store for a named need: Redis for hot reads, Cassandra/DynamoDB for huge
   key-based writes, Elasticsearch for search, a time-series DB for metrics.
5. Model NoSQL stores query-first, with bounded partitions, and accept denormalization.
6. Keep one source of truth, and feed the derived stores asynchronously so they can be rebuilt.

## Check yourself

1. In Cassandra, what is the difference between the partition key and a clustering column?
2. N=3. You write at `ONE` and read at `QUORUM`. Is every read guaranteed to see the latest write?
3. Why does an LSM tree make writes cheap, and where does the cost go?
4. When should a MongoDB child be embedded rather than referenced?
5. Give two reasons Elasticsearch shouldn't be your primary store.

### Answers

1. The partition key is hashed to pick the replicas and groups rows together. Clustering columns sort
   rows inside that partition and allow range queries on that order.
2. No. R + W = 2 + 1 = 3, which isn't greater than N = 3. The one replica that took the write may not
   be among the two you read.
3. A write is a sequential commit-log append plus an in-memory memtable insert, with no in-place
   update and no read-before-write. Reads pay: they may merge the memtable and several SSTables
   (Bloom filters help), and compaction uses background I/O.
4. When the child is owned by the parent, read with it, and bounded in size, like order lines.
   Unbounded or shared children are referenced.
5. It's near-real-time (visible only after a refresh), it has no multi-document transactions, and
   mapping changes usually need a reindex. Keep the truth elsewhere and rebuild the index from it.

Lab model answer:

| Need | Store | Key / index | Consistency | How data arrives |
|---|---|---|---|---|
| Orders + wallet | PostgreSQL | normalized schema (DB-SQL-3), idempotency key UNIQUE | strong, one transaction (DB-SQL-7) | the API writes it |
| Live rider location | Redis | `GEOADD riders:<city>` + a per-rider key with a short TTL | latest value wins; stale for seconds is fine | rider app → API → Redis |
| 90-day location history | Cassandra | `PRIMARY KEY ((rider_id, day), recorded_at)`, 90-day TTL | `ONE` writes are acceptable | the same API call, or a Kafka consumer |
| Restaurant search | Elasticsearch | index on name, dishes, cuisines; fuzzy match; `open_now` filter | near-real-time | CDC/outbox from Postgres via Kafka |
| Orders per city per hour | Postgres read replica or rollup table | `(city, hour)` rollup, refreshed by a job | minutes stale is fine | job over replica data (DB-SQL-10) |

With a three-person team, drop Cassandra first. Postgres with a table partitioned by day and
dropping old partitions handles 90 days of location history for a long time. Drop Elasticsearch
next, using Postgres full-text search plus `pg_trgm` for typos, until search quality becomes a
product problem.
