## Where we are

After CAPSTONE-8, TicketHub is a secured REST service: Postgres with Flyway and JPA, optimistic locking on `event_seat`, Testcontainers tests including the double-booking race, a scheduled hold-expiry job, pricing strategies, JWT with `USER`/`ADMIN`, and virtual threads. Every read goes to Postgres, and nothing tells you whether the service is healthy or how many holds succeed.

## Goal

Put Redis in front of the read-heavy endpoints and use it for hold timers, without ever letting it decide who owns a seat. You cache event pages and the seat map with **cache-aside** (the app checks the cache first, loads from Postgres on a miss, and stores the result with a TTL), evict the seat map after every hold, confirm, release or expiry, and use a Redis key with a TTL as a *fast path* for expiring holds while the CAPSTONE-7 job stays as the safety net. Then you make the service observable: Actuator liveness and readiness groups (readiness checks the database and Redis) and Micrometer metrics for holds and confirms. This uses DIST-SYS-1 (Redis: TTL, keyspace events) and SPRING-BOOT-11 (Actuator, metrics).

## What you build

- [ ] `redis:7` in `compose.yaml`, with keyspace notifications for expired keys switched on
- [ ] Spring Cache backed by Redis, with an explicit TTL per cache: `event` (10 min), `eventPage` (2 min), `seatMap` (5 s)
- [ ] `@Cacheable` on the event, event-page and seat-map reads; eviction **after commit** on hold, confirm, release and expiry
- [ ] `HoldTtlStore`: writes `hold:<holdId>` with a TTL when a hold commits; a listener expires the hold when the key expires
- [ ] Actuator `health` with `liveness` and `readiness` groups; readiness includes `db` and `redis`
- [ ] Micrometer counter `tickethub.holds{outcome}` and timer `tickethub.confirms{outcome}`
- [ ] `EventCacheIT` (Testcontainers Postgres + Redis) proving caching, eviction and Redis-driven expiry

## Acceptance criteria

1. `docker compose up -d postgres redis`, then `docker compose exec redis redis-cli ping` prints `PONG`.
2. `./mvnw verify` is green, including the new `EventCacheIT` and every earlier test (the double-booking race must still pass).
3. After `curl -s localhost:8080/api/v1/events/1/seats`, `docker compose exec redis redis-cli TTL seatMap::1` prints a number between `1` and `5`.
4. After a successful `POST /api/v1/events/1/holds`, `redis-cli EXISTS seatMap::1` prints `0` (evicted) and `redis-cli TTL hold:<holdId>` prints roughly `601`.
5. With the hold duration set to `5s` (test profile), the seats are back to `AVAILABLE` within about 2 seconds of expiry, before the scheduled job's next run.
6. `redis-cli FLUSHALL` while a hold is active changes nothing about ownership: the hold is still in Postgres, and the CAPSTONE-7 job still expires it on time.
7. `curl -s localhost:8080/actuator/health/liveness` and `.../readiness` both print `{"status":"UP"}`. After `docker compose stop redis`, readiness returns HTTP `503` with `{"status":"DOWN"}` and liveness is still `UP`.
8. `curl -s -H "Authorization: Bearer $ADMIN" "localhost:8080/actuator/metrics/tickethub.holds?tag=outcome:created"` shows a `COUNT` measurement equal to the number of holds you made.

### 2. Caches with explicit TTLs (10 min)

Every cache gets its own TTL and a serializer typed to one record. A typed serializer avoids storing class names in Redis and avoids polymorphic deserialization (reading a class name from data and instantiating it, which is a known security risk).

```java
package com.tickethub.common.cache;

public final class CacheNames {
    public static final String EVENT = "event";
    public static final String EVENT_PAGE = "eventPage";
    public static final String SEAT_MAP = "seatMap";
    private CacheNames() {}
}
```

```java
package com.tickethub.common.cache;

import com.fasterxml.jackson.databind.ObjectMapper;
import com.tickethub.event.EventPage;
import com.tickethub.event.EventView;
import com.tickethub.event.SeatMapView;
import java.time.Duration;
import org.springframework.boot.autoconfigure.cache.RedisCacheManagerBuilderCustomizer;
import org.springframework.cache.annotation.EnableCaching;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.cache.RedisCacheConfiguration;
import org.springframework.data.redis.serializer.Jackson2JsonRedisSerializer;
import org.springframework.data.redis.serializer.RedisSerializationContext.SerializationPair;

@Configuration
@EnableCaching
class CacheConfig {

    @Bean
    RedisCacheManagerBuilderCustomizer tickethubCaches(ObjectMapper mapper) {
        return builder -> builder
                .withCacheConfiguration(CacheNames.EVENT, config(mapper, EventView.class, Duration.ofMinutes(10)))
                .withCacheConfiguration(CacheNames.EVENT_PAGE, config(mapper, EventPage.class, Duration.ofMinutes(2)))
                .withCacheConfiguration(CacheNames.SEAT_MAP, config(mapper, SeatMapView.class, Duration.ofSeconds(5)));
    }

    private static <T> RedisCacheConfiguration config(ObjectMapper mapper, Class<T> type, Duration ttl) {
        return RedisCacheConfiguration.defaultCacheConfig()
                .entryTtl(ttl)
                .disableCachingNullValues()
                .serializeValuesWith(SerializationPair.fromSerializer(new Jackson2JsonRedisSerializer<>(mapper, type)));
    }
}
```

Do not cache Spring's `Page<T>`: it does not deserialize cleanly. Cache your own record instead:

```java
package com.tickethub.event;

import java.util.List;

public record EventPage(List<EventView> content, int page, int size, long totalElements) {}
```

Boot 4 note: Boot 4 moves to Jackson 3, and Spring Data Redis offers Jackson 3 serializer classes with different names. The shape of this config stays the same.

### 3. Cache the reads (5 min)

```java
@Service
@Transactional(readOnly = true)
public class EventQueryService {

    @Cacheable(cacheNames = CacheNames.EVENT, key = "#id")
    public EventView get(long id) { /* unchanged: load or throw */ }

    @Cacheable(cacheNames = CacheNames.EVENT_PAGE, key = "#page + ':' + #size")
    public EventPage list(int page, int size) { /* map the JPA page into EventPage */ }

    @Cacheable(cacheNames = CacheNames.SEAT_MAP, key = "#eventId")
    public SeatMapView seatMap(long eventId) { /* the seat-map query you already have from CAPSTONE-5 */ }
}
```

Redis keys look like `seatMap::1`, which is `<cache name>::<key>`. A thrown exception is never cached, so a 404 stays a 404.

**The stale-read trade-off.** A cached seat map can be up to 5 seconds old. That is acceptable for one reason: the seat map is *advice*, and the hold is the *decision*. A hold always runs against `event_seat` in Postgres with `@Version`. So the worst a stale map can do is let a user click a seat that was just taken, and get a `409 SEAT_UNAVAILABLE`. Event details change rarely, so they get 10 minutes. Seat availability changes constantly, so it gets 5 seconds plus explicit eviction.

### 4. Evict after commit, not before (10 min)

If you evict inside the transaction, another request can re-read the *old* rows (the commit has not happened yet) and put them back into the cache. Evict only once the change is visible.

```java
package com.tickethub.event;

public record SeatsChanged(long eventId) {}
```

```java
package com.tickethub.event;

import com.tickethub.common.cache.CacheNames;
import java.util.Objects;
import org.springframework.cache.Cache;
import org.springframework.cache.CacheManager;
import org.springframework.stereotype.Component;
import org.springframework.transaction.event.TransactionPhase;
import org.springframework.transaction.event.TransactionalEventListener;

@Component
class SeatMapCacheEvictor {

    private final Cache seatMap;

    SeatMapCacheEvictor(CacheManager cacheManager) {
        this.seatMap = Objects.requireNonNull(cacheManager.getCache(CacheNames.SEAT_MAP));
    }

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT, fallbackExecution = true)
    void on(SeatsChanged event) {
        seatMap.evict(event.eventId());
    }
}
```

In `BookingService.hold`, `confirm`, `release` and in the expiry path, add `events.publishEvent(new SeatsChanged(eventId));`. Here `events` is an injected `ApplicationEventPublisher`. A small window remains: a reader that loaded rows just before the commit can write them just after the evict. The 5-second TTL bounds that window. This is why a TTL is still needed even when you evict.

For admin writes to events, use `@CacheEvict(cacheNames = CacheNames.EVENT, key = "#id")` on update, and `@CacheEvict(cacheNames = CacheNames.EVENT_PAGE, allEntries = true)` on create and update.

### 5. Hold TTL in Redis as a fast path (12 min)

Postgres stays the source of truth: `expires_at` on the hold decides. Redis adds a timer that fires close to the moment of expiry, so seats return to sale in about a second rather than at the next job run.

```java
package com.tickethub.booking;

import java.time.Clock;
import java.time.Duration;
import java.time.Instant;
import java.util.Optional;
import java.util.UUID;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.dao.DataAccessException;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Component;

@Component
public class HoldTtlStore {

    private static final Logger log = LoggerFactory.getLogger(HoldTtlStore.class);
    private static final String PREFIX = "hold:";
    private static final Duration GRACE = Duration.ofSeconds(1);

    private final StringRedisTemplate redis;
    private final Clock clock;

    public HoldTtlStore(StringRedisTemplate redis, Clock clock) {
        this.redis = redis;
        this.clock = clock;
    }

    public void track(UUID holdId, Instant expiresAt) {
        Duration ttl = Duration.between(clock.instant(), expiresAt).plus(GRACE);
        if (ttl.isNegative() || ttl.isZero()) {
            return;
        }
        try {
            redis.opsForValue().set(PREFIX + holdId, "1", ttl);
        } catch (DataAccessException e) {
            log.warn("hold TTL not tracked holdId={}; scheduled job will expire it", holdId, e);
        }
    }

    public void forget(UUID holdId) {
        try {
            redis.delete(PREFIX + holdId);
        } catch (DataAccessException e) {
            log.warn("hold TTL not removed holdId={}", holdId, e);
        }
    }

    static Optional<UUID> holdIdFrom(String key) {
        return key.startsWith(PREFIX) ? Optional.of(UUID.fromString(key.substring(PREFIX.length()))) : Optional.empty();
    }
}
```

A Redis failure must never fail a hold. Redis is an optimisation here, so it logs and moves on. Call `track` from an `AFTER_COMMIT` listener (the same pattern as step 4, with a `HoldCreated(holdId, expiresAt)` event), and call `forget` after confirm or release commits.

The listener subscribes to Redis's "key expired" channel:

```java
package com.tickethub.booking;

import java.nio.charset.StandardCharsets;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.connection.RedisConnectionFactory;
import org.springframework.data.redis.listener.PatternTopic;
import org.springframework.data.redis.listener.RedisMessageListenerContainer;

@Configuration
class HoldExpiryListenerConfig {

    @Bean
    RedisMessageListenerContainer holdExpiryListener(RedisConnectionFactory factory, HoldExpiryService expiry) {
        var container = new RedisMessageListenerContainer();
        container.setConnectionFactory(factory);
        container.addMessageListener((message, pattern) -> {
            String key = new String(message.getBody(), StandardCharsets.UTF_8);
            HoldTtlStore.holdIdFrom(key).ifPresent(expiry::expireIfDue);
        }, new PatternTopic("__keyevent@*__:expired"));
        return container;
    }
}
```

`expireIfDue(UUID holdId)` reuses the CAPSTONE-7 release path for a single hold. It must be a **no-op** unless the hold is still held *and* `expires_at <= clock.instant()` in Postgres. Three facts make this rule necessary:

- Redis pub/sub is fire-and-forget. If the app is down when the key expires, the event is lost. The scheduled job catches that hold.
- Every app instance receives the event, so two instances may try to expire the same hold. The conditional update makes the second attempt do nothing.
- The event can arrive slightly early compared with the DB clock. The 1-second `GRACE` and the `expires_at` check cover this.

### 6. Actuator health groups (8 min)

```yaml
management:
  endpoints.web.exposure.include: health,info,metrics
  endpoint.health:
    probes.enabled: true
    show-details: when-authorized
    roles: ADMIN
    group:
      liveness.include: livenessState
      readiness.include: readinessState,db,redis
```

- **Liveness** asks "is this process broken beyond repair?" A failure means *restart me*. Keep it free of dependencies. If Postgres goes down and liveness checks it, every pod restarts, and that fixes nothing.
- **Readiness** asks "should I receive traffic right now?" A failure means *stop routing to me*. Postgres and Redis belong here.

Open the endpoints in your CAPSTONE-8 `SecurityFilterChain`, before `anyRequest()`:

```java
.requestMatchers("/actuator/health/**", "/actuator/info").permitAll()
.requestMatchers("/actuator/**").hasRole("ADMIN")
```

### 7. Metrics for holds and confirms (8 min)

```java
package com.tickethub.booking;

import io.micrometer.core.instrument.MeterRegistry;
import io.micrometer.core.instrument.Timer;
import java.util.function.Supplier;
import org.springframework.stereotype.Component;

@Component
public class BookingMetrics {

    private final MeterRegistry registry;

    public BookingMetrics(MeterRegistry registry) {
        this.registry = registry;
    }

    public void hold(String outcome) {
        registry.counter("tickethub.holds", "outcome", outcome).increment();
    }

    public <T> T timeConfirm(Supplier<T> confirm) {
        Timer.Sample sample = Timer.start(registry);
        String outcome = "error";
        try {
            T result = confirm.get();
            outcome = "confirmed";
            return result;
        } catch (HoldExpiredException e) {
            outcome = "expired";
            throw e;
        } finally {
            sample.stop(registry.timer("tickethub.confirms", "outcome", outcome));
        }
    }
}
```

Call these from the **controller**, not inside the `@Transactional` service. An optimistic-lock conflict can surface at commit, which happens *after* the service method returns. The controller sees that failure; the service body does not. Use `hold("created")` on success and `hold("conflict")` on `SeatUnavailableException`. Tag values must come from a small fixed set. Never use a `userId` or `eventId` as a tag: each distinct value creates a new time series.

## Hints

- **`key = "#id"` resolves to null:** SpEL needs parameter names, and those come from the `-parameters` compiler flag. `spring-boot-starter-parent` sets it. A custom compiler plugin config can drop it.
- **`@Cacheable` does nothing:** calling a cached method from the same class skips the proxy (SPRING-BOOT-3). Call it through another bean.
- **The eviction listener never fires:** a `@TransactionalEventListener` is dropped when no transaction is active, unless `fallbackExecution = true`.
- **`allEntries = true`** uses `KEYS` by default, which blocks Redis on large keyspaces. For production, use `RedisCacheWriter.nonLockingRedisCacheWriter(factory, BatchStrategies.scan(1000))`.
- **No expiry events arrive:** check `redis-cli CONFIG GET notify-keyspace-events`. Expired keys are removed lazily or by Redis's background sampling, so the event can lag the TTL slightly.
- **Readiness is `DOWN` when you start locally without Redis:** that is the correct behaviour. Start Redis.

## Talk about it in interviews

**"How did you use caching, and how do you keep it consistent?"**
1. *What:* cache-aside in Redis for event pages (10 min TTL) and the seat map (5 s TTL plus eviction).
2. *How it works inside:* `@Cacheable` checks `seatMap::<id>` first. On a miss it loads from Postgres and writes back with a TTL. Writes publish `SeatsChanged`, and the cache is evicted only *after commit*, so nobody re-caches uncommitted state.
3. *Where used:* read-heavy, change-tolerant data. The seat map is advice; the hold against `event_seat` with `@Version` is the decision.
4. *What goes wrong:* the stale window (bounded by the TTL), evicting before commit, a stampede on a hot key when it expires, and a Redis outage. Reads then fall back to Postgres and readiness reports it.

**"What happens if Redis loses the hold keys?"** Nothing breaks. Redis is the fast path for expiry. Postgres `expires_at` plus the scheduled job is the guarantee, and expiry is a conditional, idempotent update.

**"Liveness vs readiness?"** Liveness failing means restart; readiness failing means stop routing traffic. Dependencies go only in readiness, otherwise a database blip restarts every pod.

**"Which metrics did you add, and why those?"** Hold outcomes (`created` vs `conflict`, which measures contention) and confirm latency by outcome. Tags come from a fixed set, to avoid cardinality explosions.
