## Where we are

D5 gave you a working web layer: requests come in, controllers answer. This lesson covers what an *operator* needs from that app once it is deployed. Is it alive? Is it slow? Where did this request spend its time? Can it stop without dropping work? It also covers what *you* need as the author: tests that are fast and still trustworthy.

## The problem

It is 2 a.m. and the progress API "feels slow". Without instrumentation you have three bad options: grep the logs, add `System.out` and redeploy, or guess. Kubernetes keeps sending traffic to a pod that is still loading its data, and a deploy kills requests halfway through. Meanwhile your test suite takes six minutes, because every test boots the whole app against an in-memory database that doesn't behave like Postgres.

Spring Boot has an answer for each of these. You will take them one at a time.

## Actuator: endpoints about the app itself

**Actuator** is a Boot module that adds HTTP endpoints *describing the running application*. Add `spring-boot-starter-actuator` and expose the endpoints you want:

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
  endpoint:
    health:
      probes:
        enabled: true   # adds /actuator/health/liveness and /readiness
```

Now `GET /actuator/health` returns `{"status":"UP"}`. That status combines **health indicators**, which Boot adds for what it finds on the classpath: the database, disk space, Redis and so on. Writing your own takes one small class:

```java
@Component
class DataDirHealth implements HealthIndicator {
    private final Path dir;
    DataDirHealth(@Value("${prep.data-dir}") Path dir) { this.dir = dir; }

    @Override
    public Health health() {
        return Files.isDirectory(dir) ? Health.up().build()
                : Health.down().withDetail("missing", dir.toAbsolutePath().toString()).build();
    }
}
```

**The rule:** only expose what you need. Endpoints such as `env`, `heapdump` and `beans` leak secrets or internals. By default, only `health` is exposed over the web.

## Liveness versus readiness

These are two different questions an orchestrator asks:

- **Liveness**: "Is this process broken beyond repair?" If not, restart it.
- **Readiness**: "Should I send it traffic right now?" If not, route around it.

Boot sets readiness to `ACCEPTING_TRAFFIC` only after the application runners have finished (you will see this in detail in L5). This repo's `DataImporter` is an `ApplicationRunner`, so `/actuator/health/readiness` stays down until the bank has been imported. That is exactly the behaviour you want.

**The rule:** don't put a database check in the liveness probe. A database outage would then restart every pod, which fixes nothing.

## Metrics with Micrometer

**Micrometer** is a metrics *facade*: you record numbers through one API, and a registry exports them to Prometheus, Datadog, OTLP and others. It plays the same role for metrics that SLF4J plays for logging. Boot auto-configures a `MeterRegistry` and already records many metrics for you: `http.server.requests` timings per URI, JVM memory and GC, the HikariCP connection pool, and more.

Here is how to add a business metric:

```java
@Service
class ProgressMetrics {
    private final Counter done;
    private final Timer importTime;

    ProgressMetrics(MeterRegistry registry) {
        this.done = Counter.builder("prep.progress.done").description("Questions marked done").register(registry);
        this.importTime = Timer.builder("prep.import").register(registry);
    }

    void markedDone() { done.increment(); }
    <T> T timeImport(Supplier<T> work) { return importTime.record(work); }
}
```

The main meter types are:

- **Counter**: only goes up (requests, errors).
- **Timer**: counts and durations, with optional percentiles.
- **Gauge**: a current value you sample (queue size).

Each meter can carry **tags**, which are key-value labels that let you slice the data, such as `outcome=SUCCESS`.

**The rule:** every distinct tag value creates a new time series. Tags must have **low cardinality**. A tag like `status` is fine. A tag like `userId` will eventually take down your metrics backend.

## Tracing: following one request

A metric tells you that p99 latency is 2 seconds. A **trace** tells you which part of *this* request took those 2 seconds. A trace is a tree of **spans**: timed operations such as "HTTP PUT", "SQL select" and "call pricing-service". Spans share a **trace id**, which travels to other services in a header (`traceparent`, the W3C standard).

In Boot 3 and later, tracing goes through Micrometer's **Observation** API. Add a tracer bridge (`micrometer-tracing-bridge-otel`) and an exporter (`opentelemetry-exporter-otlp`), or on Boot 4 the `spring-boot-starter-opentelemetry` starter. Then set:

```yaml
management:
  tracing:
    sampling:
      probability: 1.0   # sample everything in dev; much lower in prod
```

With that in place, incoming HTTP requests, `RestClient` calls and JDBC calls (with the right instrumentation) produce spans automatically. Boot also puts the trace id into the log pattern, so you can jump from a slow trace straight to its log lines.

## Graceful shutdown

When Kubernetes stops a pod it sends SIGTERM. Without graceful shutdown, in-flight requests are cut off. With it, the web server stops accepting *new* requests and waits for current ones to finish, up to a timeout. Since Boot 3.4 this is the default. Older versions need it switched on:

```yaml
server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 20s
```

**The rule:** the timeout must be shorter than the orchestrator's kill deadline (`terminationGracePeriodSeconds`, 30 seconds by default in Kubernetes). Otherwise SIGKILL arrives before shutdown finishes.

## Testing: slices instead of the whole app

`@SpringBootTest` starts *everything*. That is the right tool for a few end-to-end tests, like this repo's `AppTest`, and too slow for the rest. A **slice test** starts only one layer of the app.

**`@WebMvcTest(ApiController.class)`** loads MVC infrastructure, your controller, `@ControllerAdvice` and filters. It does not load services or repositories, so you mock them:

```java
@WebMvcTest(ApiController.class)
class ApiControllerTest {
    @Autowired MockMvc mvc;
    @MockitoBean BankService bank;            // org.springframework.test.context.bean.override.mockito
    @MockitoBean CampaignService campaigns;
    @MockitoBean ProgressService progress;
    @MockitoBean DataImporter importer;

    @Test void missingActionIs400() throws Exception {
        mvc.perform(put("/api/questions/x/progress").contentType(MediaType.APPLICATION_JSON).content("{}"))
           .andExpect(status().isBadRequest());
    }
}
```

**`@DataJpaTest`** loads JPA, your repositories and an `EntityManager`. Each test runs in a transaction that is rolled back at the end.

The imports differ by version. In Boot 4 these annotations live in separate test modules: `org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest` (from `spring-boot-webmvc-test`) and `org.springframework.boot.data.jpa.test.autoconfigure.DataJpaTest` (from `spring-boot-data-jpa-test`). Boot 3 kept them under `org.springframework.boot.test.autoconfigure...`. Use `@MockitoBean` from Spring Framework 6.2 or later; the older `@MockBean` is gone in Boot 4.

## Testcontainers: the real database in tests

H2 is not Postgres. JSON columns, locking behaviour and SQL dialect quirks all differ. **Testcontainers** starts a real database in Docker for the test run. Boot's **`@ServiceConnection`** reads the container's URL and credentials, so you set no properties at all:

```java
@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE) // don't swap in H2
@Testcontainers
class ProgressRepositoryPgTest {
    @Container @ServiceConnection
    static PostgreSQLContainer postgres = new PostgreSQLContainer("postgres:16-alpine");

    @Autowired ProgressRepository repo;

    @Test void savesAndFinds() {
        repo.save(new Progress("lru-cache"));
        assertThat(repo.findById("lru-cache")).isPresent();
    }
}
```

On Testcontainers 1.x, the class is `org.testcontainers.containers.PostgreSQLContainer<?>`. On 2.x (Boot 4), it is `org.testcontainers.postgresql.PostgreSQLContainer`.

This repo really had that bug. `Progress.notes` (and six other text columns) were declared `@Column(columnDefinition = "CLOB")`. H2 accepts that, but Postgres has no `CLOB` type; its equivalent is `text`. The H2-only suite never noticed; it was caught by reading the code while writing this lesson. The fix was `@Column(length = 1_000_000)`, which lets Hibernate pick each database's own large-text type. **Break it:** put `columnDefinition = "CLOB"` back on one column and run this test. It fails at schema creation, which is exactly the kind of bug Testcontainers exists to catch.

**The rule:** the test context is cached and reused between test classes that share the *same* configuration. Every distinct combination of `@MockitoBean`s, properties and profiles builds a new context. Keep that set of combinations small and the suite stays fast.

## Lab (~10 min)

1. Add `spring-boot-starter-actuator`. Expose `health,metrics` and enable probes as shown above.
2. Run the app. Call `GET /actuator/health/readiness` and `GET /actuator/metrics/http.server.requests`. Hit `/api/companies` a few times, then fetch `/actuator/metrics/http.server.requests?tag=uri:/api/companies`. Note the `COUNT` and `TOTAL_TIME`.
3. Add the `ProgressMetrics` counter. Call `markedDone()` from `ProgressService.apply` when the action is `DONE`. Mark one question done, then read `/actuator/metrics/prep.progress.done`.
4. Write the `@WebMvcTest` above and run it. Compare its startup time in the log with `AppTest`'s.
5. **Break it:** delete one `@MockitoBean` line and run again. Expect `NoSuchBeanDefinitionException` naming `ApiController`'s missing dependency. This is the slice telling you exactly what it did *not* load.

## Gotchas

- **Exposing every endpoint** (`include: "*"`) in production. `env` and `heapdump` can leak secrets. Expose a short list, and secure the management port or path.
- **Unbounded tag values** such as user ids, raw URLs or exception messages explode metric cardinality. Use templated URIs, which Boot already does for `http.server.requests`.
- **A database check in the liveness probe** makes a database outage restart every pod. Liveness should cover only the process itself.
- **Too many unique test contexts.** Each new mock or property combination costs a full context start. Share a base test class or configuration.
- **Trusting H2 for SQL behaviour.** Use Testcontainers for repository tests that depend on dialect, locking or JSON.
- **Sampling 100% of traces in production** is expensive. Sample a fraction, and keep error-biased sampling in mind.

## In interviews

Typical prompts are "How do you make a Spring Boot service production-ready?", "Liveness vs readiness?", "How do you find which service made a request slow?" and "How do you test the web layer without the database?". Bank: [Debugging requests across microservices](#/q/debugging-across-microservices), [Design a Metrics Aggregator / Monitoring System](#/q/design-metrics-monitoring-system).

**Follow-up: "Your p99 doubled after a deploy. What do you do?"** A strong answer works through the evidence in order. Check `http.server.requests` by URI and outcome to find *which* endpoint got slower. Look at a slow trace to find *where* the time went (SQL, a downstream call, the connection pool). Check pool metrics such as `hikaricp.connections.pending`. Then compare against the previous version.

## Explain it in 2 minutes

*"What does 'production-ready' mean for a Spring Boot service?"*

- Health, through Actuator. Separate liveness from readiness, and readiness only goes up after startup work is done.
- Metrics through Micrometer: automatic HTTP, JVM and pool metrics, plus business counters and timers with low-cardinality tags.
- Tracing through the Observation API: a trace id is propagated with `traceparent` and printed in logs.
- Graceful shutdown with a timeout shorter than the orchestrator's kill deadline.
- Tests as a pyramid: slice tests (`@WebMvcTest`, `@DataJpaTest`) for speed, Testcontainers for real-database truth, and a few `@SpringBootTest`s end to end.

## Check yourself

1. Why should readiness not be `UP` the moment Tomcat starts listening?
2. What goes wrong if you tag a counter with `userId`?
3. What does `@WebMvcTest` load, and what must you supply yourself?
4. What does `@ServiceConnection` save you from?
5. Graceful shutdown is set to 60s and the pod's grace period is 30s. What happens?

### Answers

1. Startup work may still be running, such as runners importing data or warming caches. Traffic sent then would fail. Boot only flips readiness after the runners finish.
2. Each user creates a new time series. Memory and storage in the metrics backend grow without bound, which is a cardinality explosion.
3. MVC infrastructure, the listed controllers, `@ControllerAdvice`, filters and converters. You mock services and repositories with `@MockitoBean`.
4. Wiring the container's random port, URL and credentials into `spring.datasource.*` by hand.
5. Kubernetes sends SIGKILL at 30s, so requests still in flight are cut off anyway. The shutdown timeout should be shorter than the grace period.
