## Where we are

F1 gave you the building blocks (load balancers, caches, queues, databases), and F3 gave you the
method and the estimation maths. This lesson packs both into a **kit you carry into every design
round**: a fixed list of questions, the numbers to know by heart, a catalogue of "if you see this,
use that" patterns, a practice ladder of bank problems, and the rubric a mock is scored against.
Use it as a reference: re-read it before each mock, not just once.

## The problem

A new design question often makes your mind go blank. "Design a ticket booking system" sounds
nothing like the betting platform you practised, so you wait for hints that never come, jump to
boxes, and lose the requirements and the numbers, the two steps that steer everything after.

But most design questions are made of the **same few patterns with different nouns**. A seat is a
wallet balance; a live score is a live price; a flash sale is a goal being scored. What you need
is not a new answer for every question but a **routine** that finds the familiar patterns inside
the unfamiliar question. The sections below give you that routine.

## The method: six steps, always in this order

| Step | Time (45-min round) | What you say and draw |
|---|---|---|
| 1. Requirements | 5 min | The checklist below. Write the answers down. |
| 2. Estimates | 3–5 min | Users, requests per second at peak, read:write ratio, storage per day. |
| 3. API and data model | 5 min | 3–5 endpoints; the main tables or entities with their keys. |
| 4. High-level design | 10 min | Boxes and arrows. **Walk one request end to end**, then the second main flow. |
| 5. Deep dive | 15 min | The 1–2 hardest parts: correctness, the hot path, the spike. |
| 6. Trade-offs and failures | 5 min | What breaks at 10×, what happens when each component dies, what you'd monitor. |

The rule that holds it together: **numbers before boxes, data model before services.** Every
component you add later should trace back to a requirement or a number from steps 1–2.

## Step 1: the requirements checklist

Ask in this order, out loud: **Who → How much → How correct → How fast → How available → Where.**

| # | Bucket | Ask | Example (live sports betting) |
|---|---|---|---|
| 1 | Who and what | Who are the users? What are the 3–4 core actions? What's out of scope? | Watch odds, place a bet, see history; cash-out out of scope |
| 2 | How much | Users total and at peak? Actions per second? Read:write? Data per day? | 2M watching the final; bets spike on a goal |
| 3 | **How correct** | What must never be wrong? What can be a bit stale? | Money never wrong; odds on screen may lag ~1 s |
| 4 | How fast | Latency target for the main action, at p99? | Odds visible < 1 s; bet placed < 500 ms |
| 5 | How available | Can it ever be down? Which part matters most? | Bet placement must work during the final |
| 6 | Where | One region or worldwide? Any data rules? | UK and EU, regulated |

Bucket 3 is the one that wins interviews. Splitting the system into **strongly consistent** parts
(money, inventory, anything you can't undo) and **eventually consistent** parts (feeds, counts,
displayed prices, history) decides your database, your caches and your async boundaries.

If you blank, say: *"Let me start with the requirements so I design the right thing,"* and go down
the list. It buys thinking time and reads as maturity.

## Step 2: numbers to know (roughly)

**Time conversions.** A day has 86,400 seconds; round it to **10^5**.

| Per day | Per second (average) |
|---|---|
| 1 million | ~12 |
| 100 million | ~1,200 |
| 1 billion | ~12,000 |

Peak is usually **2–3×** the average for steady products and **10× or more** for event-driven
ones (a goal, a sale, a breaking story). Design for the peak, and say which multiplier you chose.

**Storage.** 1 million rows a day × 1 KB = 1 GB a day ≈ 365 GB a year. Multiply by replicas
(usually 3) and keep the retention period in mind.

**Latency, order of magnitude** (exact values vary with hardware):

| Operation | Roughly |
|---|---|
| Read from memory | ~100 ns |
| Read from SSD | ~100 µs |
| Network round trip inside one data centre | ~0.5 ms |
| Redis GET over the network | ~1 ms |
| Indexed Postgres lookup | a few ms |
| Round trip between continents | 100–150 ms |

**Capacity rules of thumb** for a sanity check, not for promises:
- One app server handles **hundreds to a few thousand** simple requests per second.
- One Postgres primary handles **thousands** of simple writes per second, more with batching.
- One Redis node handles on the order of **100,000** simple operations per second.
- One push gateway holds about **50,000** open connections comfortably with non-blocking I/O.

**The fan-out check.** When one event must reach many people, multiply: 25 price changes per
second × 2 million watchers is millions of pushes per second. That product, not the write rate,
usually sizes the read side.

## Step 3: API and data model habits

- Name the **resources** and their **keys** first: `bet(id, user_id, status, placed_at, ...)`.
- Every write that a client may retry takes an **idempotency key**: `POST /bets` with
  `Idempotency-Key`, enforced by `UNIQUE (user_id, idempotency_key)`.
- Use **cursor (keyset) pagination** for lists: `GET /bets?before=<placed_at>&limit=20`.
- For each main query, say the **index** that serves it, with equality columns first:
  `(user_id, status, placed_at DESC)`.
- Keep the same names at every level (API, tables, classes), so the design reads as one system.

## Step 4: building blocks in one line each

| Block | Use it for | The cost to say out loud |
|---|---|---|
| Load balancer | Spread requests over stateless servers | Health checks; sticky sessions only if you must |
| API gateway | Auth, rate limiting, routing | One more hop; must itself scale |
| Stateless service | Business logic that scales out | State moves to DB, cache or tokens |
| Relational DB (Postgres) | Transactions, relations, constraints | Write scaling needs partitioning or sharding |
| Read replica | Offload reads | Replication lag; read-your-own-writes goes to the primary |
| Cache (Redis) | Hot reads, snapshots, counters | Staleness, invalidation, stampede on expiry |
| Queue or log (Kafka) | Async work, fan-out, decoupling | Eventual consistency; consumers must be idempotent |
| Object storage + CDN | Files, images, static content | Cache invalidation; signed URLs |
| Push (SSE / WebSocket) | Live updates to clients | Connection state per gateway; reconnects |
| Search index | Text search, filters | A second copy of data kept in sync |

## The pattern catalogue

Once requirements and numbers are down, scan the problem for these shapes (about 30 seconds,
before drawing). Each "yes" brings a ready-made answer.

| If the system… | Use… | Seen in |
|---|---|---|
| Moves money or a scarce thing (balance, seat, stock) | Atomic conditional `UPDATE ... WHERE qty >= ?` + idempotency key + outbox | Betting, payments, tickets, inventory |
| Shows changing data to many people | Push (SSE or WebSocket) + pub/sub fan-out to gateways + snapshot on reconnect + conflation | Live odds, chat, scores, dashboards |
| Has spikes or hot items | Queue in front, partition by key, back-pressure, auto-scaling, pre-warming | Goals, flash sales, ticket drops |
| Keeps growing history | Partition by time + replicas + keyset pagination + archiving | Bets, orders, logs, metrics |
| Reads far more than it writes | Cache-aside, CDN, read replicas, precomputed read models | URL shortener, feeds, catalogues |
| Writes must survive and trigger other work | Outbox in the same transaction → relay → Kafka → idempotent consumers | Any "then notify / settle / index" step |
| Spans several services in one business action | Saga with compensations, not a distributed transaction | Booking + payment, order + shipping |
| Needs unique ids across machines | Database sequence, UUIDv7, or a Snowflake-style generator | IDs, short codes |
| Limits use per user | Token bucket in Redis, keyed by user | Rate limiter, OTP, API quotas |
| Schedules or retries work | Durable job table or delay queue, leases, at-least-once + idempotency | Job scheduler, notifications |

**Patterns that are often misused:**
- A rate limiter stops abuse. It does not stop a race condition; the atomic update does.
- Kafka gives ordering per partition and durability. It does not make a write consistent.
- Caches serve reads. Never make a money decision from a cached or replicated balance.
- Sharding is a last resort. Partition and replicate first, and name the point where you'd shard.

## Steps 5–6: deep dive and trade-offs

For the deep dive, pick the part where **a wrong design loses money, data or users**, and go
three levels down: the SQL statement, the lock or constraint, and what happens on retry.

For trade-offs, answer the same four questions for every design:
1. **What breaks first at 10×?** Usually the database's reads, then one hot key.
2. **What happens when each box dies?** Retries with backoff, failover, idempotency, what the user sees.
3. **Where is the single point of failure?** Remove it or say why it's acceptable.
4. **What would you monitor?** p95/p99 latency, error rate, queue or consumer lag, saturation.

Useful phrases: *"At this scale one Postgres primary with replicas is enough; I'd shard by user
id when writes pass what one primary can take."* · *"This part is eventually consistent, and here
is why that's acceptable."* · *"I'd keep these servers small for blast radius: a crash should
affect 1–2% of users, not all of them."*

## Lab (~10 min)

Take [Design a URL Shortener](#/q/design-url-shortener) and run only steps 1–2 against a timer:
ask the six checklist questions (invent sensible answers), then compute writes per second, reads
per second, the read:write ratio and five years of storage. Then run the pattern catalogue and
write which rows apply (reads far more than writes, unique ids). Compare with the model answer.
You should finish in under 8 minutes, before drawing a single box.

## Gotchas

- **Jumping to boxes.** Without requirements and numbers you can't justify any component. Fix:
  steps 1–2 out loud, every time, even when the interviewer seems impatient.
- **Arithmetic slips under pressure.** Say each step slowly: "2M × 5% = 100k; ÷ 10 s = 10k/s."
- **Mixing two different rates.** Price changes, pushes and bets are separate numbers on separate paths.
- **"Strong consistency everywhere".** It makes the design slow and expensive. Split it, as in bucket 3.
- **No failure story.** Every box you draw will be asked "and if it dies?". Prepare the answer as you draw.
- **Over-engineering.** Microservices, sharding and multi-region need numbers that justify them.

**How to practise one problem** (about 60 minutes, spread over two days):
1. **Attempt** (45 min): timer on, out loud, on a whiteboard tool. All six steps.
2. **Compare** (10 min): read the model answer. Write down your **three biggest misses**.
3. **Redraw** (5 min, three days later): the diagram and the deep dive from memory. Mark the
   question done in the app, so it comes back for review after 3, 10 and 30 days.

**The mock rubric** (how mocks with Claude are scored, out of 10):

| Area | Points | A strong answer |
|---|---|---|
| Requirements | 1.5 | All six buckets, with a clear strong vs eventual consistency split |
| Estimates | 1 | Peak rates, read:write, storage; the arithmetic said step by step |
| API and data model | 1.5 | Endpoints with idempotency, tables with keys and indexes |

## Explain it in 2 minutes

*"How do you approach a system design question you've never seen?"* A good answer hits:
- Requirements first, with the consistency split as the key question.
- Numbers at peak: rates, read:write ratio, storage, fan-out.
- Data model and API before services, with the idempotency key and indexes.
- A pattern scan: money or scarce things, live data, spikes, growing history.
- One request walked end to end, then a deep dive on the part that can lose money or data.
- Trade-offs: what breaks at 10×, failure of each component, what you'd monitor.

## Check yourself

1. 50 million requests a day: roughly how many per second on average, and at a 3× peak?
2. Name the checklist bucket that decides what can be cached, and why.
3. A system sells limited concert seats with a flash-sale spike. Which two catalogue rows apply?
4. Why is "add a rate limiter" not a fix for two users booking the last seat?
5. What four questions do you answer about trade-offs for any design?

### Answers

1. About 600 per second on average (50M ÷ 86,400), so about 1,800 at a 3× peak.
2. "How correct": whatever must never be wrong can't be served from a cache or replica; whatever may be a bit stale can.
3. "Moves a scarce thing" (atomic conditional update, holds, idempotency) and "has spikes" (a queue in front, back-pressure, auto-scaling).
4. A rate limiter caps how often one user can call; the race is between different users at the same instant, and only an atomic update on the seat row settles it.
5. What breaks first at 10×, what happens when each component dies, where the single point of failure is, and what you'd monitor.
