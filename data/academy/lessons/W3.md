## Where we are

WEB-API-3 taught you to design one good REST API: resources, idempotency, versioning, errors.
BE-STORY-10 split ShopKart into services and listed the "Talk" patterns in one paragraph each.
This lesson opens that paragraph up: how a client finds the right service, how services find each
other, and how to choose between a REST call, a gRPC call and an event for each conversation.

## The problem

Placing an order in ShopKart now involves four services:

```text
mobile app ──► ??? ──► Orders ──► Payments
                          └─────► Inventory
                          └─────► (Email should hear about it too)
```

Four questions appear at once. Which service does the app (which knows one hostname) talk to, and
who checks its token? Payments runs as 3 instances whose IPs change on every deploy: where does
Orders send the request? Orders needs Payments' answer, Email needs to answer nothing: same kind of
call? And when Payments takes 4 seconds, how long does Orders wait, and how do you find this request
in three services' logs?

## Synchronous vs asynchronous: the first decision

A **synchronous** call means the caller sends a request and waits for the reply before it
continues. A REST or gRPC call is synchronous from the caller's point of view.

An **asynchronous** message means the sender hands a message to a **broker** (a server that stores
and forwards messages, such as Kafka from DIST-SYS-2) and carries on. Whoever receives it handles
it later.

```text
sync:   Orders ──authorize?──► Payments        Orders waits; if Payments is down, Orders fails
async:  Orders ──OrderPlaced──► [broker] ──► Email   Orders is done; Email catches up later
```

**The rule:** synchronous when the caller *needs the answer to continue* (can this card pay 40
euros?); a message when the sender only *announces a fact* or hands off work that can finish later.
A sync hop couples your availability and latency to the callee's; an async hop buys independence
and pays with eventual consistency and harder debugging.

## The API gateway: one front door

An **API gateway** is a reverse proxy that sits between external clients and your services and
gives them one entry point. Clients call `api.shopkart.com`; the gateway routes each path to the
right service.

```text
            ┌──────────── API gateway ─────────────┐
 clients ──►│ TLS · auth (JWT) · rate limit · route │──► Orders / Catalog / Payments
            │ CORS · request id · access logs       │
            └───────────────────────────────────────┘
```

What belongs there is whatever is the same for every service: **routing** by path, **TLS
termination**, **authentication** (validate the JWT once, SPRING-BOOT-9; services still do their own
*authorization*), **rate limiting** per client, and plumbing such as CORS, request ids, access logs
and canary routing. What does **not** belong: business logic, joins across services, orchestrating
a checkout. That is how the ESB of BE-STORY-9 became the bottleneck every team waited on.

In Spring, **Spring Cloud Gateway** does this. A route in its Java DSL:

```java
@Bean
RouteLocator routes(RouteLocatorBuilder builder) {
    return builder.routes()
            .route("orders", r -> r.path("/api/orders/**")
                    .filters(f -> f.stripPrefix(1))        // /api/orders/7 -> /orders/7
                    .uri("http://orders:8080"))
            .build();
}
```

Managed gateways (AWS API Gateway, Kong, NGINX, Envoy-based gateways) do the same job as
infrastructure instead of code.

## BFF: a backend per frontend

A web page shows an order with full item details; the phone app shows a compact card and must
save bandwidth. One general API ends up either too chatty for mobile or too fat for the web.

A **BFF (backend for frontend)** is a small API service owned by one client team that calls the
internal services and shapes the response for that client.

```text
web app ──► web-BFF ──┐
                      ├──► Orders, Catalog, Payments
mobile  ──► mobile-BFF┘
```

The BFF may aggregate (one call from the phone, three inside the low-latency network) but holds no
core business rules. It costs one service per client type, so use it when client needs diverge.

## Service discovery: where does Payments live right now?

Instances are created and destroyed by deploys and autoscaling, so a hard-coded IP is wrong within
a day. **Service discovery** is the mechanism that maps a logical name (`payments`) to the
current, healthy network addresses. There are two shapes.

**Client-side discovery.** Each instance registers itself in a **service registry** (Netflix
Eureka, Consul). The caller asks the registry for the list and picks an instance itself.

```text
Payments #1,#2,#3 ──register + heartbeat──► registry
Orders ──"where is payments?"──► registry ──[10.0.1.4, 10.0.1.9, 10.0.2.3]──► Orders picks one
```

In Spring Cloud, a `@LoadBalanced RestClient.Builder` resolves `http://payments/authorize` to a
real instance per call. Smart clients, but every language needs a registry client.

**Server-side discovery.** The caller sends to one stable address; a load balancer or proxy in
front knows the instances and forwards. The caller stays simple.

**How Kubernetes does it** (Kubernetes itself is coming in DIST-SYS-5). A Kubernetes **Service**
is a stable name plus a stable virtual IP for a set of pods (running instances). The cluster DNS
answers `payments` (fully: `payments.shop.svc.cluster.local`) with that virtual IP. The node's
networking layer (kube-proxy, or an eBPF replacement) forwards each connection to one of the pods
that are currently **ready**. So Orders simply calls `http://payments:8080`: no registry library,
no Eureka. That is server-side discovery built into the platform, and it is why Eureka is rare in
new Kubernetes deployments.

**The rule:** the caller should depend on a *name*, never an address. On Kubernetes the name is a
Service and DNS does the lookup; off Kubernetes a registry does.

## REST vs gRPC vs events

You know REST from WEB-API-3: resources, JSON, HTTP verbs. Two alternatives matter.

**gRPC** is a remote-procedure-call framework (open-sourced by Google in 2015). You write the
contract in a `.proto` file using **Protocol Buffers** (protobuf), a compact binary format, and a
code generator produces typed Java client and server classes.

```proto
syntax = "proto3";
package payments.v1;

service PaymentService {
  rpc Authorize (AuthorizeRequest) returns (AuthorizeReply);
  rpc WatchStatus (StatusRequest) returns (stream StatusUpdate);   // server streaming
}

message AuthorizeRequest {
  string order_id = 1;
  int64 amount_minor = 2;          // cents, never a floating-point amount
  string currency = 3;
  string idempotency_key = 4;
}
message AuthorizeReply { bool approved = 1; string payment_id = 2; }
message StatusRequest { string payment_id = 1; }
message StatusUpdate { string state = 1; }
```

What you get: **HTTP/2** (many concurrent calls multiplexed over one long-lived connection);
**smaller payloads** (binary fields identified by number, not JSON text); **streaming** (server,
client and bidirectional); a **compiler-enforced contract** (both sides generate code from the
`.proto`); and built-in **deadlines** (`stub.withDeadlineAfter(2, TimeUnit.SECONDS).authorize(req)`),
propagated so the server can stop work nobody is waiting for. What it costs: browsers cannot call
it directly (gRPC-Web or a REST edge), payloads are unreadable without tools, no HTTP caching.

**Events** (BE-STORY-10, DIST-SYS-2): a fact such as `OrderPlaced` published to a topic; the
publisher does not know who listens.

| | REST (JSON/HTTP) | gRPC (protobuf/HTTP/2) | Events (broker) |
|---|---|---|---|
| Style | sync request/response | sync, plus streaming | async, one-to-many |
| Contract | OpenAPI (optional) | `.proto` (mandatory, typed) | event schema (Avro, JSON Schema, protobuf) |
| Best for | public and browser APIs, CRUD | internal high-volume calls, streaming | notifications, fan-out, decoupling |
| Failure coupling | caller waits on callee | caller waits on callee | none at send time; consumer lag later |
| Debugging | easy (`curl`, readable) | needs tools (`grpcurl`) | hardest: no single call stack |

**Choosing, in practice:** REST at the edge and for anything a browser or partner calls; gRPC
between internal services when call volume, payload size or streaming makes it worth the tooling;
events whenever the sender does not need an answer. Most real systems use all three.

## Contracts and versioning across teams

Inside a monolith, renaming a field is a refactor; between teams it is an outage. WEB-API-3's rules
hold, with one twist per style:

- **REST**: add optional fields; clients *ignore unknown fields* (Spring Boot's Jackson default);
  breaking changes get `/v2/` running beside `/v1/` until consumers move.
- **protobuf**: the field **number** is the identity on the wire, not the name. Never change or
  reuse one; mark deleted numbers `reserved 4;`.
- **Events**: they sit on a topic for days and get replayed, so old and new consumers meet old and
  new events. Add optional fields only; a breaking change is a new event type. A **schema
  registry** can reject incompatible schemas at publish time.
- **Consumer-driven contract tests** (BE-STORY-10) catch breaks in the provider's build.

## Across hops: timeouts and correlation ids

**Timeouts.** If the gateway gives up after 3 s but Orders waits 10 s for Payments, Orders works on
a request whose user already saw an error. Use a **timeout budget** that shrinks along the chain
(gateway 3 s → Orders gives Payments 1 s), with both a **connect timeout** (to open a connection)
and a **read timeout** (to get the reply). Spring's `RestClient` on the JDK client:

```java
@Bean
RestClient paymentsClient(RestClient.Builder builder) {
    HttpClient jdk = HttpClient.newBuilder().connectTimeout(Duration.ofMillis(500)).build();
    JdkClientHttpRequestFactory factory = new JdkClientHttpRequestFactory(jdk);
    factory.setReadTimeout(Duration.ofSeconds(1));
    return builder.baseUrl("http://payments:8080").requestFactory(factory).build();
}
```

DIST-SYS-3, next, turns timeouts into a full toolkit (retries, circuit breakers, bulkheads).

**Correlation ids.** A **correlation id** is a unique id created at the edge for each incoming
request, sent on every downstream call (a header such as `X-Correlation-Id`) and written in every
log line, so one search finds one request across all services. In Spring you put it in the logging
**MDC** (mapped diagnostic context, a per-thread map that the log pattern can print).

**Distributed tracing** is the structured version of the same idea. A **trace** is the whole
journey of one request; each hop records a **span** (name, start, duration, parent span). The ids
travel in the W3C `traceparent` header. With Micrometer Tracing on the classpath (SPRING-BOOT-11),
Spring Boot's auto-configured `RestClient.Builder` and Kafka templates propagate it for you, and
the trace id appears in logs. OpenTelemetry end to end is coming in BE-STORY-11.

## Lab (~10 min)

**Break it: a timeout budget across three hops.** Java 21, JDK only. The `main` method plays the
gateway; two tiny HTTP servers play Orders and Payments.

```java
import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpServer;
import java.io.IOException;
import java.net.InetSocketAddress;
import java.net.URI;
import java.net.http.*;
import java.time.Duration;
import java.util.UUID;
import java.util.concurrent.Executors;

public class Hops {
    static final HttpClient CLIENT = HttpClient.newBuilder().connectTimeout(Duration.ofMillis(500)).build();

    static void log(String svc, String cid, String msg) {
        System.out.printf("%-8s cid=%s %s%n", svc, cid, msg);
    }

    static void reply(HttpExchange ex, int status, String body) throws IOException {
        byte[] bytes = body.getBytes();
        ex.sendResponseHeaders(status, bytes.length);
        ex.getResponseBody().write(bytes);
        ex.close();
    }

    static HttpResponse<String> call(String url, String cid, Duration timeout) throws Exception {
        HttpRequest req = HttpRequest.newBuilder(URI.create(url))
                .header("X-Correlation-Id", cid).timeout(timeout).build();
        return CLIENT.send(req, HttpResponse.BodyHandlers.ofString());
    }

    public static void main(String[] args) throws Exception {
        long paymentsDelayMs = args.length > 0 ? Long.parseLong(args[0]) : 50;

        HttpServer payments = HttpServer.create(new InetSocketAddress(8082), 0);
        payments.setExecutor(Executors.newVirtualThreadPerTaskExecutor());
        payments.createContext("/authorize", ex -> {
            String cid = ex.getRequestHeaders().getFirst("X-Correlation-Id");
            log("payments", cid, "authorizing, will take " + paymentsDelayMs + " ms");
            try { Thread.sleep(paymentsDelayMs); } catch (InterruptedException e) { return; }
            reply(ex, 200, "APPROVED");
        });

        HttpServer orders = HttpServer.create(new InetSocketAddress(8081), 0);
        orders.setExecutor(Executors.newVirtualThreadPerTaskExecutor());
        orders.createContext("/orders", ex -> {
            String cid = ex.getRequestHeaders().getFirst("X-Correlation-Id");
            log("orders", cid, "placing order, calling payments with a 1 s budget");
            try {
                String result = call("http://localhost:8082/authorize", cid, Duration.ofSeconds(1)).body();
                reply(ex, 201, "order placed: " + result);
            } catch (HttpTimeoutException e) {
                log("orders", cid, "payments timed out -> 504");
                reply(ex, 504, "payment service timed out");
            } catch (Exception e) {
                reply(ex, 502, "payment call failed");
            }
        });

        payments.start();
        orders.start();
        String cid = UUID.randomUUID().toString();
        long start = System.nanoTime();
        HttpResponse<String> resp = call("http://localhost:8081/orders", cid, Duration.ofSeconds(3));
        log("gateway", cid, resp.statusCode() + " " + resp.body()
                + " after " + (System.nanoTime() - start) / 1_000_000 + " ms");
        System.exit(0);
    }
}
```

1. `java Hops.java` — all three log lines share one `cid`, and the order is placed quickly.
2. `java Hops.java 2500` — Payments is slow. Orders gives up after about 1 s and returns a clear
   504; the gateway gets an answer well inside its own 3 s budget.
3. **Break it:** remove `.timeout(timeout)` from `call` and rerun with `5000`. Now Orders waits for
   Payments, the gateway's own call has no limit either, and the whole chain takes 5 s. In
   production that is a Tomcat thread held hostage per request.
4. **Think:** in step 2 the user got an error, but Payments may still approve the charge a second
   later. What does the client need to send so a retry does not charge twice? (Answer: an
   idempotency key, from WEB-API-3; DIST-SYS-3 builds on it.)

## Gotchas

- **Business logic in the gateway.** It becomes the new ESB every team queues for. Keep it to
  routing, auth, rate limits and plumbing; aggregation goes in a BFF or the owning service.
- **Inverted timeouts.** A callee timeout longer than its caller's wastes work nobody awaits.
  Budgets must shrink along the chain, and every client needs both connect and read timeouts.
- **gRPC on a plain Kubernetes Service does not spread load.** HTTP/2 keeps one long-lived
  connection, and the Service balances *connections*, not requests, so one pod gets everything.
  Use a headless Service with client-side balancing, or a mesh or proxy that balances per request.
- **Reusing a protobuf field number.** Old binaries decode the new field as the old one, silently.
  Mark removed numbers `reserved`.
- **Chatty synchronous chains.** A → B → C → D multiplies latency and failure odds. If the caller
  does not need the answer now, publish an event.
- **No correlation id.** Then "find this request" means guessing by timestamp. Create it at the
  edge and propagate it on every hop, events included.

## In interviews

Bank: [Microservices communication: gRPC vs REST vs events](#/q/microservices-communication-grpc-vs-rest-eda),
[Microservices patterns: API gateway, service discovery, circuit breaker, saga](#/q/microservices-design-patterns),
[Debugging requests across microservices](#/q/debugging-across-microservices),
[Design a Rate Limiter](#/q/design-rate-limiter) (usually placed at the gateway), and
[Entain BE take-home: extend a gRPC racing service](#/q/entain-racing-grpc-service-take-home).

Answer in four layers:

- **"REST vs gRPC vs events?"** *What:* three ways to talk: sync JSON over HTTP, sync typed binary
  RPC, async facts on a broker. *Inside:* gRPC is protobuf over HTTP/2 with multiplexing, streaming,
  generated stubs and deadlines; events are durable on a partitioned log. *Where:* REST at the
  edge, gRPC for hot internal paths, events for fan-out and decoupling. *What goes wrong:* gRPC load
  balancing on long-lived connections, browsers can't call it; events bring eventual consistency,
  duplicates and lag; REST chains couple latency.
- **"What does an API gateway do? Gateway vs BFF?"** *What:* one front door. *Inside:* routing, TLS,
  JWT validation, rate limits, request ids. *Where:* cluster edge; a BFF per client type behind it.
  *What goes wrong:* business logic creeping in, single point of failure, an extra hop of latency.
- **"How does service discovery work? And on Kubernetes?"** *What:* name to live addresses.
  *Inside:* client-side registry (Eureka) vs server-side load balancer; on Kubernetes a Service gets
  a DNS name and virtual IP, and traffic goes only to ready pods. *Where:* every call between
  services. *What goes wrong:* stale registry entries, routing to pods that are not ready, the
  gRPC connection-pinning issue.

**Follow-up: "How do you version a contract without breaking consumers?"** Additive changes only,
tolerant readers, run versions side by side, protobuf `reserved` numbers, compatibility rules in a
schema registry, and consumer-driven contract tests in the provider's pipeline.

## Explain it in 2 minutes

*"A mobile app places an order that touches Orders, Payments and Email. Walk me through how the
services talk."*

- The app calls one API gateway: TLS, JWT check, rate limit, route to Orders (or to a mobile BFF).
- Orders needs the payment answer, so it calls Payments synchronously, by name; Kubernetes DNS or
  a registry resolves the name to a ready instance.
- REST or gRPC for that call: gRPC if it is a hot internal path, with a deadline and an
  idempotency key.
- Email does not need to answer, so Orders publishes `OrderPlaced`; Email consumes it at its pace.
- Timeouts shrink along the chain; a correlation id and trace context travel on every hop and log.
- Contracts evolve additively, checked by contract tests.

## Check yourself

1. Give one question that decides between a synchronous call and an event.
2. Name three jobs of an API gateway and one thing that must stay out of it.
3. How does Orders reach Payments on Kubernetes without a service registry library?
4. Why might gRPC traffic all land on one pod behind a Kubernetes Service?
5. The gateway times out at 3 s. Should Orders' timeout for Payments be 5 s? Why?

### Answers

1. Does the caller need the answer to continue? If yes, synchronous; if it is only announcing a
   fact or handing off work, an event.
2. Routing, TLS termination, token validation, rate limiting, CORS, request ids. Business logic
   and cross-service orchestration stay out.
3. It calls `http://payments:8080`. Cluster DNS resolves the Service name to a virtual IP, and the
   node's proxy forwards each connection to a ready pod.
4. HTTP/2 multiplexes all calls over one long-lived connection, and the Service balances per
   connection, so all requests follow that one connection to one pod.
5. No. Orders would keep waiting after the user already got an error. Downstream budgets must be
   shorter than upstream ones, for example 1 s.
