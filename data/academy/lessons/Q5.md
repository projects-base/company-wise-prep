## Where we are

From Q1 and Q2 you can write the queries: joins, `GROUP BY`, subqueries and CTEs over the betting
schema (`users`, `events`, `markets`, `selections`, `bets`, `wallet_transactions`). Writing a
correct query is half the job. This lesson covers the other half: why the same query takes 0.1 ms
on one table and 3 seconds on another, and how to read the database's own explanation of what it
did.

## The problem

The "My open bets" screen runs this query:

```sql
SELECT id, stake, placed_at
FROM bets
WHERE user_id = 4240 AND status = 'OPEN'
ORDER BY placed_at DESC;
```

With 10,000 bets in the table it is instant. With 200 million it takes seconds, and on a Saturday
afternoon, with thousands of users opening the screen at once, the database CPU sits at 100%. The
query returns 10 rows. The trouble is that the database has to look at every row to find them.

## How a table is stored

Postgres stores a table as a **heap**: a file of fixed-size **pages** (8 KB each by default), with
rows placed wherever there is room, in no useful order. Each row has a physical address called a
**TID** (tuple id): page number plus slot number.

Without any other help, the only way to answer `WHERE user_id = 4240` is a **sequential scan**:
read every page and test every row.

```text
bets heap:  [page 0][page 1][page 2] ... [page 2,000,000]
             rows for user 4240 are scattered anywhere in here
```

Roughly: 200M rows at ~100 bytes each is ~20 GB, which is ~2.5 million pages. Reading all of that
to return 10 rows is the problem.

## A B-tree index, from zero

An **index** is a separate structure that stores the values of some columns in sorted order, each
next to the TID of its row. Postgres's default index type is the **B-tree**, a balanced tree of
pages:

```text
                         root page
                [ 1000 | 5000 | 9000 ]
               /        |        |     \
      internal pages ... ...    ...    ...
             /
   leaf pages (sorted, linked left ↔ right):
   [4238→(17,3)] [4240→(902,1)] [4240→(55,7)] [4241→(3,2)] ...
                  value → TID (page, slot) of the row in the heap
```

To find `user_id = 4240`, start at the root, follow the pointer whose range contains 4240, and
repeat until you reach a leaf. Each page holds hundreds of keys, so even 200M rows need a tree
only about 4–5 levels deep. Finding the first match costs a handful of page reads instead of
millions. Because the leaves are linked in order, a **range** (`placed_at > X`) or an `ORDER BY`
is a walk along the leaves.

**Analogy:** the index at the back of a book. You look up "Kafka", get page numbers, and jump
there. Where it breaks: a book's index is printed once, but a B-tree must be updated on every
insert, update and delete, and it rebalances itself as it grows.

**The rule:** an index turns "read everything" into "walk a short tree, then fetch only the rows
you need". Its cost is extra work on every write.

## Composite indexes: column order matters

A **composite index** covers several columns. It is sorted by the first column, then by the second
within equal firsts, and so on, like a phone book sorted by (surname, first name).

```sql
CREATE INDEX bets_user_status_time ON bets (user_id, status, placed_at);
```

```text
(4240, OPEN,    2026-10-01 18:00)
(4240, OPEN,    2026-10-03 20:15)   ← all of user 4240's OPEN bets sit together,
(4240, SETTLED, 2026-09-28 14:00)     already in placed_at order
(4241, OPEN,    ...)
```

This one index serves:

- `WHERE user_id = ?` (the leftmost column),
- `WHERE user_id = ? AND status = ?`,
- `WHERE user_id = ? AND status = ? ORDER BY placed_at DESC`, with no sort step: Postgres just
  walks the matching leaves backwards.

It does not serve `WHERE status = 'OPEN'` on its own well, for the same reason a phone book
doesn't help you find everyone called "Akhil". This is the **leftmost-prefix rule**. (Postgres 18
added a "skip scan" that can sometimes use a non-leading column when the leading column has few
distinct values. Don't design around it.)

**The rule:** put columns compared with `=` first, then the column you range over or sort by. A
range column in the middle stops the columns after it from narrowing the search.

## Selectivity: when an index is not worth it

**Selectivity** is the fraction of rows a condition matches. `user_id = 4240` matches maybe 0.0001%
of bets: very selective. `status = 'SETTLED'` might match 90%: not selective at all.

Each index match costs a random jump into the heap. Fetching 90% of the table that way is slower
than reading it front to back, so the **planner** (the part of Postgres that chooses how to run a
query) picks a sequential scan, correctly. It decides from **statistics** that `ANALYZE` (run
automatically by autovacuum) collects: row counts, the most common values and their frequencies.

**The rule:** an index helps when the condition is selective. Indexing a column like `status` on
its own rarely helps.

## Covering indexes and index-only scans

Even with a good index, each match still needs a heap fetch to get the columns the query asks for.
If the index contains every column the query needs, Postgres can answer from the index alone. That
is an **index-only scan**, and such an index is a **covering index**. `INCLUDE` adds columns to
the leaves without making them part of the sort key:

```sql
CREATE INDEX bets_user_status_time_cov ON bets (user_id, status, placed_at) INCLUDE (stake, id);
```

Now `SELECT id, stake, placed_at ... WHERE user_id = ? AND status = 'OPEN'` never touches the
heap. One catch: Postgres can only skip the heap for pages its **visibility map** marks as
"all rows visible to everyone", which vacuum maintains. Q6 explains why rows can be invisible.

## When the planner ignores your index

You add an index and the plan still says `Seq Scan`. These are the usual causes.

**1. A function or expression on the column.** The index stores `placed_at`, not
`date(placed_at)`:

```sql
-- can't use an index on placed_at
SELECT count(*) FROM bets WHERE date(placed_at) = DATE '2026-10-13';
-- can: the same question as a range on the bare column
SELECT count(*) FROM bets
WHERE placed_at >= TIMESTAMP '2026-10-13 00:00:00' AND placed_at < TIMESTAMP '2026-10-14 00:00:00';
```

**2. A leading wildcard.** `name LIKE 'Arsen%'` is a range on a sorted list. `name LIKE '%arsenal%'`
could be anywhere, so a B-tree can't help. Use the `pg_trgm` extension with a GIN index for
"contains" searches. Even the prefix form needs an index built with `text_pattern_ops` unless the
database uses the `C` collation.

**3. An implicit cast on the column.** `user_id` is `bigint`. Compare it with a `numeric` value,
such as `4240.0` or a Java `BigDecimal` bound with `setBigDecimal`, and Postgres casts the
*column* to `numeric` on every row. The index on the `bigint` values no longer matches. Bind
parameters with the column's own type.

**4. `OR` across different columns.** `WHERE user_id = 4240 OR selection_id = 77` can't be
answered by one walk of one index. Postgres can combine two separate indexes (a `BitmapOr`, below),
but if either column has no index it falls back to a full scan. Rewriting as `UNION` of two
indexed queries is the classic fix.

**5. Low selectivity or stale statistics.** Either the index really isn't worth it, or the
planner *thinks* it isn't because the statistics are out of date after a big load. Run `ANALYZE
bets;` and check again.

## Partial and expression indexes

Two Postgres features fix two common cases directly.

A **partial index** indexes only the rows that match a `WHERE` clause. Most bets are settled, and
the hot queries only care about open ones:

```sql
CREATE INDEX bets_open_by_selection ON bets (selection_id) WHERE status = 'OPEN';
```

It is a small fraction of the full index's size and stays in memory. The settlement job's query
must repeat the condition (`... WHERE selection_id = ? AND status = 'OPEN'`) for the planner to
use it.

An **expression index** indexes the result of an expression, so a query that uses that exact
expression can use it:

```sql
CREATE INDEX users_lower_name ON users (lower(name));
SELECT id FROM users WHERE lower(name) = 'akhil';
```

## Reading EXPLAIN (ANALYZE, BUFFERS)

`EXPLAIN` shows the plan the planner chose. `EXPLAIN ANALYZE` actually **runs** the query and adds
real timings. `BUFFERS` adds how many pages each step touched. Because `ANALYZE` executes the
statement, wrap an `UPDATE` or `DELETE` in `BEGIN; ... ROLLBACK;` when you explain it.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, stake, placed_at FROM bets
WHERE user_id = 4240 AND status = 'OPEN'
ORDER BY placed_at DESC;
```

**Illustration only:** the plans below show the shape Postgres prints, for a 1-million-row copy of
`bets`. The numbers are made up for teaching, not measured. (On a table this size, real Postgres
would often run the scan in parallel and show `Gather` and `Parallel Seq Scan` nodes; read them the
same way.)

Before the index:

```text
Sort  (cost=23334.15..23334.17 rows=10 width=30) (actual time=95.210..95.212 rows=10 loops=1)
  Sort Key: placed_at DESC
  Sort Method: quicksort  Memory: 25kB
  Buffers: shared hit=2012 read=6322
  ->  Seq Scan on bets  (cost=0.00..23334.00 rows=10 width=30) (actual time=0.910..95.180 rows=10 loops=1)
        Filter: ((user_id = 4240) AND (status = 'OPEN'::text))
        Rows Removed by Filter: 999990
        Buffers: shared hit=2012 read=6322
Planning Time: 0.120 ms
Execution Time: 95.240 ms
```

After `bets_user_status_time`:

```text
Index Scan Backward using bets_user_status_time on bets  (cost=0.43..44.61 rows=10 width=30) (actual time=0.028..0.041 rows=10 loops=1)
  Index Cond: ((user_id = 4240) AND (status = 'OPEN'::text))
  Buffers: shared hit=14
Planning Time: 0.140 ms
Execution Time: 0.060 ms
```

How to read them:

- **It's a tree.** Indented `->` lines are children. Read from the innermost line outwards: the
  scan produces rows, the `Sort` above it consumes them.
- **`cost=start..total`** is the planner's *estimate* in arbitrary units (reading one page in order
  is 1.0 by default), not milliseconds. Use it to compare plans for the same query, nothing else.
- **`rows=` estimated vs `actual ... rows=`.** A large gap (estimated 10, actual 500,000) means bad
  statistics, and is the most common root cause of a bad plan.
- **`loops=`.** Actual time and rows are *per loop*. A step with `loops=5000` ran 5,000 times.
- **`Rows Removed by Filter`** is wasted work: rows read and thrown away.
- **`Buffers: shared hit`** pages came from Postgres's memory cache. **`read`** pages came from
  disk (or the OS cache). 8,334 pages to return 10 rows says "missing index"; 14 pages says
  "fine".
- **No `Sort` node after the index** shows the index supplied the order. `Backward` means it walked
  the leaves in reverse for `DESC`.

## The three scan types

```text
Seq Scan          read every page in order        many rows, or no usable index
Index Scan        walk index, fetch each row      few rows
Bitmap Heap Scan  walk index, collect all TIDs,   a middling number of rows,
  ← Bitmap Index Scan  sort them by page, then    or combining indexes (BitmapAnd/BitmapOr)
                       read each page once
```

A bitmap scan sits between the other two. If 3,000 matching rows live on 2,000 different pages, an
index scan might visit the same page many times in random order. The bitmap approach first builds
a set of pages to visit, then reads each page once, in physical order. If that set gets too big
for memory it goes **lossy** (it remembers pages, not rows), which is why you will see a
`Recheck Cond:` line: the condition is re-tested on each row of the page.

**Illustration only:**

```text
Bitmap Heap Scan on bets  (cost=52.10..7810.45 rows=2900 width=30) (actual time=1.20..9.85 rows=3012 loops=1)
  Recheck Cond: (selection_id = 77)
  Heap Blocks: exact=1987
  ->  Bitmap Index Scan on bets_selection  (cost=0.00..51.38 rows=2900 width=0) (actual time=0.70..0.70 rows=3012 loops=1)
        Index Cond: (selection_id = 77)
```

## The three join types

Q1 taught what a join returns. Here is how Postgres can compute one:

```text
Nested Loop   for each row on the outer side, look up matches on the inner side
              best when the outer side is small and the inner side has an index
Hash Join     build a hash table from the smaller input, then probe it with each row of the other
              best for large, unsorted inputs joined on "="; needs memory (work_mem)
Merge Join    both inputs sorted on the join key, walk them together like a zip
              best when both sides are already sorted (e.g. by an index)
```

"My open bets with event names" is a nested loop: 10 bets on the outside, and each one is a primary
key lookup into `selections`, `markets` and `events`. "Total stake per sport this month" joins
millions of bets to a few thousand selections, so expect a hash join with `selections` as the
hashed side. A nested loop with a large `loops=` count and no index on the inner side is the plan
to worry about.

## The cost of indexes on writes

Every index is updated on every `INSERT`, and on every `DELETE`, and on an `UPDATE` too, unless
Postgres can do a **HOT update** (heap-only tuple): when no indexed column changed and the new row
version fits on the same page, the indexes are left alone. Every index also takes disk space and
memory, and adds to the write-ahead log that replicas consume.

So for `bets`, which takes a burst of inserts at every kick-off, five indexes mean roughly six
writes per bet instead of one. Index the queries you actually run. Find the ones that are never
used with `SELECT indexrelname, idx_scan FROM pg_stat_user_indexes WHERE idx_scan = 0;` and drop
them.

## Lab (~10 min)

Run an index experiment on H2 (an in-memory Java database), which you already have in `~/.m2`. H2
is not Postgres: its planner is simpler and its `EXPLAIN` output looks different. The lesson that
carries over is what changes when an index exists and when a function hides the column.

Save as `IndexLab.java` and run
`java -cp ~/.m2/repository/com/h2database/h2/2.3.232/h2-2.3.232.jar IndexLab.java` (on Windows,
use the full `C:\Users\<you>\.m2\...` path).

```java
import java.sql.*;

public class IndexLab {
    public static void main(String[] args) throws Exception {
        try (Connection c = DriverManager.getConnection("jdbc:h2:mem:lab;MODE=PostgreSQL")) {
            Statement s = c.createStatement();
            s.execute("""
                CREATE TABLE bets (
                  id BIGINT PRIMARY KEY, user_id BIGINT, selection_id BIGINT,
                  stake NUMERIC(12,2), status VARCHAR(10), placed_at TIMESTAMP)""");
            // 1,000,000 bets for 100,000 users; 1 in 10 is OPEN. SYSTEM_RANGE is H2's generate_series.
            s.execute("""
                INSERT INTO bets
                SELECT x, MOD(x, 100000), MOD(x, 5000), 10,
                       CASE WHEN MOD(x, 10) = 0 THEN 'OPEN' ELSE 'SETTLED' END,
                       DATEADD('MINUTE', x, TIMESTAMP '2026-01-01 00:00:00')
                FROM SYSTEM_RANGE(1, 1000000)""");

            String byUser = "SELECT id, stake, placed_at FROM bets "
                          + "WHERE user_id = ? AND status = 'OPEN' ORDER BY placed_at DESC";
            run(c, "1. no index", byUser);

            s.execute("CREATE INDEX bets_user_status_time ON bets (user_id, status, placed_at)");
            run(c, "2. index (user_id, status, placed_at)", byUser);

            run(c, "3. function wrapped around user_id",
                "SELECT id, stake, placed_at FROM bets WHERE abs(user_id) = ? AND status = 'OPEN'");
        }
    }

    // Runs the query for 50 different users, so H2 can't reuse a cached result.
    static void run(Connection c, String label, String sql) throws SQLException {
        try (PreparedStatement ps = c.prepareStatement(sql)) {
            long start = System.nanoTime();
            int rows = 0;
            for (int user = 1000; user < 1050; user++) {
                ps.setLong(1, user * 10L);
                try (ResultSet rs = ps.executeQuery()) { while (rs.next()) rows++; }
            }
            System.out.printf("%n== %s: %d rows, %.2f ms per query%n",
                    label, rows, (System.nanoTime() - start) / 1e6 / 50);
        }
        try (Statement s = c.createStatement();
             ResultSet rs = s.executeQuery("EXPLAIN " + sql.replace("?", "4240"))) {
            while (rs.next()) System.out.println(rs.getString(1));
        }
    }
}
```

What you should observe (the timings are from one laptop; yours will differ):

- **Run 1:** the plan comment says `/* PUBLIC.BETS.tableScan */`, and each query takes a couple of
  hundred milliseconds.
- **Run 2:** the comment names `BETS_USER_STATUS_TIME` with both conditions, and each query is
  around two orders of magnitude faster.
- **Run 3:** back to `tableScan` and slow, even though the index still exists. `abs(user_id)` hid
  the column.

Then break it on purpose: drop the index and create it as `(status, user_id, placed_at)`, and
compare. Then add a fourth query that filters only on `placed_at`, and predict the plan before you
run it.

## Gotchas

- **Wrong column order in a composite index.** `(status, user_id)` is far weaker than
  `(user_id, status)` for "this user's bets". Put equality columns first, the range or sort column
  last.
- **Functions and casts on indexed columns.** `date(placed_at) = ?`, `lower(name) = ?`, or a
  `BigDecimal` bound to a `bigint` column. Rewrite as a range, add an expression index, or bind the
  right type.
- **Trusting `EXPLAIN` without `ANALYZE`.** Plain `EXPLAIN` shows estimates only. Compare estimated
  and actual rows, and remember that `ANALYZE` really runs `UPDATE`s and `DELETE`s.
- **Reading time per node without `loops`.** `actual time=0.05 ... loops=20000` is a second, not 50
  microseconds.
- **Indexing everything.** Each index slows every insert and most updates. Drop indexes that
  `pg_stat_user_indexes` shows are never scanned.
- **`CREATE INDEX` on a live table blocks writes** for the whole build. In production use
  `CREATE INDEX CONCURRENTLY`, which is slower but lets inserts continue.

## In interviews

Asked as "How does an index work?", "Why isn't my index being used?", "What's a covering index?"
or "Here's a slow query, what do you do?". The bank question
[Indexes, Partitioning and Sharding](#/q/db-indexing-partitioning-sharding) starts here, and
[Scaling an RDBMS and When to Use NoSQL](#/q/rdbms-scaling-vs-nosql) expects "fix the queries and
indexes first" as the opening move.

Typical follow-ups:

- *"You have an index on (a, b). Does `WHERE b = ?` use it?"* Not efficiently: leftmost-prefix
  rule. Explain the sort order, mention that the planner may still scan the whole index if it is
  much smaller than the table, and propose an index on `b` if the query matters.
- *"The plan shows a seq scan even though there's an index. Why?"* List the causes in order:
  low selectivity (correct choice), stale statistics (estimate vs actual rows), a function or cast
  on the column, a leading wildcard. Then say how you'd check each one with
  `EXPLAIN (ANALYZE, BUFFERS)`.

## Explain it in 2 minutes

*"How does a database index speed up a query, and what does it cost?"*

- A table is an unordered heap of pages, so without an index a lookup reads everything.
- A B-tree keeps the column values sorted, with pointers to the rows, in a shallow balanced tree;
  a lookup is a few page reads, and ranges and `ORDER BY` walk the linked leaves.
- Composite indexes follow the leftmost-prefix rule: equality columns first, then range or sort.
- Indexes only pay off for selective conditions; functions, casts and leading wildcards hide the
  column from them.
- Check with `EXPLAIN (ANALYZE, BUFFERS)`: scan type, estimated vs actual rows, buffers.
- Every index is extra work on every write, so index the queries you run.

## Check yourself

1. You have an index on `(user_id, placed_at)`. Which of these can it serve well:
   (a) `WHERE user_id = ?`, (b) `WHERE placed_at > ?`, (c) `WHERE user_id = ? ORDER BY placed_at DESC LIMIT 20`?
2. Why would Postgres choose a sequential scan for `WHERE status = 'SETTLED'` even with an index on
   `status`?
3. A plan node says `rows=12` estimated and `actual ... rows=480000`. What do you suspect and do?
4. What is the difference between `Buffers: shared hit` and `read`?
5. Rewrite `WHERE date(placed_at) = DATE '2026-10-13'` so it can use an index on `placed_at`.

### Answers

1. (a) yes (leftmost column). (b) not efficiently: `placed_at` is second, so its values are only
   sorted within each user. (c) yes, ideally: find the user, walk the leaves backwards, stop after
   20, with no sort.
2. Most rows are settled, so the condition isn't selective. Fetching most of the table through
   random index jumps costs more than one sequential read.
3. Stale or missing statistics, so the planner picked a plan for 12 rows. Run `ANALYZE` on the
   table, then check the plan again; if the column is skewed, raise its statistics target.
4. `hit` pages were already in Postgres's shared memory cache. `read` pages had to be fetched from
   the operating system or disk, which is much slower.
5. `WHERE placed_at >= TIMESTAMP '2026-10-13 00:00:00' AND placed_at < TIMESTAMP '2026-10-14 00:00:00'`.
