## Where we are

From A4 you know reachability from GC roots, the young (eden + survivors) and old generations,
promotion by age, and the main collectors. A2 showed the heap and the object header. This lesson
follows **one object** through its whole life, from `new` to the moment its memory is reused, and
names the trap at each stage. It is the object-level companion to L1's program lifecycle.

## The problem

Bugs and performance problems attach to specific moments in an object's life:

- a half-constructed object seen by another thread (construction),
- a cache that slowly fills the old generation (promotion),
- a "cleanup" in `finalize()` that never runs, or runs too late (end of life),
- memory that never goes back to the OS (reclamation).

Seeing the stages in order turns each of these from a mystery into "that's stage 6".

## Stage 1: the class must be ready

`new Order()` first requires `Order` to be loaded, linked and initialised (L1, A3). The JVM needs
the class to know the object's size and field layout.

```text
   gotcha: the first `new` of a class can be slow (loading + static init); a failed static
           initialiser makes every `new Order()` fail with NoClassDefFoundError.
```

## Stage 2: allocation

Allocating must be fast, because programs allocate constantly. Each thread gets a private chunk
of eden called a **TLAB** (thread-local allocation buffer). Allocating inside it is a **bump
pointer**: "the object starts here; move the pointer forward by its size", with no locking.

```text
 eden:  [ ...thread A's TLAB: obj obj obj ▲free... ][ thread B's TLAB ... ]
                                           └ bump pointer
```

Objects too big for the TLAB are allocated directly in eden (with synchronisation). In G1, an
object of at least half a region is **humongous** and goes straight into dedicated old regions,
skipping the young generation entirely.

There is one more possibility: if the JIT proves the object never **escapes** the method (never
stored in a field, never returned, never passed somewhere it could be kept), **escape analysis**
may replace it with plain local variables. The object is then never allocated at all.

```text
   gotcha: allocation is cheap, but the allocation RATE decides how often young GCs run.
           Profile allocation (A8) before blaming the GC.
   gotcha: large buffers in G1 are humongous; frequent ones fill the old gen and can trigger
           full GCs. Watch for "Humongous" in GC logs.
```

## Stage 3: zeroing and the header

The JVM zeroes the object's memory and writes the **header** (mark word + class pointer; A2). So
every field already holds `0`, `false` or `null` before any of your code runs.

```text
   gotcha: a field read before the constructor assigns it sees 0/null, not garbage. This is
           what a subclass sees if a superclass constructor calls an overridden method.
```

## Stage 4: construction

Now the constructor runs. In order: the superclass constructor (up to `Object`), then this class's
field initialisers and instance initialiser blocks, then the rest of the constructor body.

```java
class Base {
    Base() { describe(); }                 // calls an overridable method: dangerous
    void describe() { }
}
class Order extends Base {
    private final String id = "ORD-" + System.nanoTime();   // assigned AFTER Base() returns
    @Override void describe() { System.out.println("id = " + id); }   // prints "id = null"
}
```

`new Order()` prints `id = null`: `Base()` ran `describe()` before `Order`'s field initialiser.
(With a pure constant like `= "ORD-1"`, javac would inline the value and hide the bug, which makes
it even more confusing when someone later changes the initialiser.)

At the end of the constructor, `final` fields are "frozen": any thread that later obtains the
reference is guaranteed to see their values (A6).

```text
   gotcha: never call overridable methods from a constructor; subclasses see default values.
   gotcha: don't let `this` ESCAPE during construction (registering a listener, starting a
           thread, storing it in a static). Others may use a half-built object, and the final
           field guarantee is lost.
   gotcha: if the constructor throws, the caller never gets a reference; the object is
           garbage immediately, unless `this` already escaped.
```

## Stage 5: in use, reachable

The object is alive as long as a chain of **strong references** (ordinary references) leads to it
from a GC root: a local variable in a stack frame, a static field, an active thread.

```text
   gotcha: "I don't use it any more" ≠ unreachable. Statics, caches, listeners, ThreadLocals and
           collections keep objects alive: that is a Java memory leak (A5).
```

## Stage 6: surviving young collections

Most objects die before the next minor GC and never get past stage 5. If ours is still reachable
when eden fills, the minor GC **copies** it into a survivor space and increments its **age** (kept
in the header's mark word). Each later minor GC copies it to the other survivor space and ages it
again.

```text
 GC#1: eden ──copy──► S0 (age 1)   GC#2: S0 ──copy──► S1 (age 2)   GC#3: S1 ──► S0 (age 3) ...
   gotcha: copying costs time proportional to SURVIVORS. Medium-lived objects (a request that
           takes 2 seconds, a short-lived session cache) are copied repeatedly and then promoted:
           the worst case for a generational GC.
```

## Stage 7: promotion to the old generation

When its age reaches the **tenuring threshold** (at most 15; the JVM may lower it adaptively), or
the survivor space is too full, the object is **promoted**: copied into the old generation. From
now on young GCs ignore it; only old-generation work (G1 concurrent marking + mixed collections,
ZGC's major cycles, or a full GC) can reclaim it.

```text
   gotcha: "premature promotion" – objects promoted just before they die fill the old gen with
           garbage that is expensive to clean. Symptom: old gen grows fast, then drops sharply at
           each old/mixed collection (unlike a leak, whose floor keeps rising).
   gotcha: an old object pointing to a young one is tracked via the card table/remembered set;
           very write-heavy old structures make young GCs slower.
```

## Stage 8: becoming unreachable

The last strong reference disappears: a method returns, a field is set to `null`, a map entry is
removed. Nothing happens immediately; there is no destructor. The object just sits there until a
collection notices.

Java also has weaker kinds of reference, which let you observe or keep an object *without*
keeping it alive:

| Reference | Cleared when | Typical use |
|---|---|---|
| strong (normal) | never while reachable | everything |
| `SoftReference` | at the GC's discretion, guaranteed before an `OutOfMemoryError` | memory-sensitive caches (rarely the best choice) |
| `WeakReference` | at the next GC that finds no strong or soft path | `WeakHashMap`, canonicalising maps, listener registries |
| `PhantomReference` | after the object is unreachable; `get()` always returns `null` | post-mortem cleanup, used by `Cleaner` |

```text
   gotcha: soft-reference caches behave unpredictably (cleared all at once under pressure,
           kept too long otherwise). Use a bounded cache with explicit eviction instead.
   gotcha: WeakHashMap keys that are string literals never disappear: literals are interned
           and stay strongly reachable.
```

## Stage 9: cleanup actions

If the object owns something outside the heap (a file handle, native memory), it must be released.
Three mechanisms, from best to worst:

1. **Explicit close**: implement `AutoCloseable` and use try-with-resources. Deterministic.
2. **`java.lang.ref.Cleaner`**: registers an action that runs on a cleaner thread after the
   object becomes phantom-reachable. A safety net for when someone forgets to close.
3. **`finalize()`**: deprecated, and deprecated *for removal* since Java 18. It runs at an
   unpredictable time (or never), delays reclamation by at least one extra GC cycle, can
   "resurrect" the object by storing `this`, and runs on a single finalizer thread that can
   back up.

```text
   gotcha: a Cleaner action that captures `this` (e.g. a lambda using a field, or an inner class)
           keeps the object reachable forever: it is never cleaned. Use a static nested class or a
           lambda that only captures what it needs.
   gotcha: never rely on GC timing for releasing scarce resources (DB connections, file
           handles). The GC only reacts to HEAP pressure.
```

## Stage 10: reclamation

The memory is finally reused:

- in the young generation, eden and the source survivor space are simply treated as empty after
  a copy;
- in the old generation, regions are evacuated (G1, ZGC) or swept/compacted (Serial, Parallel).

```text
   gotcha: freed heap memory is usually kept by the JVM for future allocation; process memory
           (RSS) does not shrink right away. G1 and ZGC can return unused memory to the OS over
           time, but don't expect `top` to drop after a GC.
```

## Lab (~10 min)

Save as `ObjectLife.java` and run `java ObjectLife.java`:

```java
import java.lang.ref.Cleaner;
import java.lang.ref.SoftReference;
import java.lang.ref.WeakReference;

public class ObjectLife {
    static final Cleaner CLEANER = Cleaner.create();

    static final class Resource implements AutoCloseable {
        private final Cleaner.Cleanable cleanable;

        Resource(String name) {
            // The cleanup action must NOT capture `this`, or the object could never become unreachable.
            Runnable action = () -> System.out.println("   cleaner ran for " + name);
            this.cleanable = CLEANER.register(this, action);
        }

        @Override public void close() { cleanable.clean(); }   // deterministic path; runs at most once
    }

    public static void main(String[] args) throws InterruptedException {
        System.out.println("1. try-with-resources closes deterministically:");
        try (Resource r = new Resource("closed-properly")) {
            System.out.println("   using it");
        }

        Resource forgotten = new Resource("forgotten");
        WeakReference<Resource> weak = new WeakReference<>(forgotten);
        SoftReference<byte[]> soft = new SoftReference<>(new byte[1_000_000]);
        System.out.println("2. strongly reachable, weak.get() != null: " + (weak.get() != null));

        forgotten = null;                                    // drop the only strong reference
        System.out.println("3. unreachable but not yet collected:    " + (weak.get() != null));

        System.gc();                                         // a request, usually honoured
        Thread.sleep(200);                                   // the Cleaner runs on its own thread
        System.out.println("4. after GC, weak ref cleared:           " + (weak.get() == null));
        System.out.println("5. soft ref survives (no memory pressure): " + (soft.get() != null));
    }
}
```

Observe:

- Step 1: the cleaner runs immediately, because `close()` called it.
- Step 3: unreachable is not the same as collected; the weak reference still answers.
- Step 4: after a GC the weak reference is cleared and the cleaner for "forgotten" runs on its own
  thread, but only because the GC happened. Without `System.gc()` it might take much longer.
- Step 5: the soft reference survived, since there was no memory pressure.

Then watch objects age: run A4's `Churn` program with `java -Xmx256m -Xlog:gc+age=trace Churn`.
The age table shows bytes at age 1, 2, 3... growing as the long-lived 1% are copied between
survivors, until they are promoted.

Break it: change the cleanup lambda to
`() -> System.out.println("   cleaner ran for " + name + " " + this)`, which captures `this`.
Step 4 now prints `false` and the cleaner for "forgotten" never runs: the Cleaner itself keeps the
object reachable through the action.

## Gotchas

- **Objects are born zeroed**: overridable methods called from a constructor see `0`/`null`.
- **`this` escaping a constructor** exposes half-built objects and voids the `final` guarantee.
- **Medium-lived objects** are the expensive ones for generational GCs: copied, then promoted.
- **Unreachable ≠ collected ≠ cleaned.** Never tie scarce resources to GC; use
  try-with-resources.
- **`finalize()` is deprecated for removal.** Use `AutoCloseable`, with `Cleaner` as a safety net
  whose action never captures `this`.
- **Soft-reference caches are unpredictable**; prefer a bounded cache with eviction.

  the deterministic-destruction world Java gave up, and why try-with-resources exists.

Follow-ups and strong answers:

- *Why is allocation in Java so cheap?* TLAB bump-pointer allocation with no locking; the cost
  moves to GC, which is cheap when most objects die young.
- *When would you use a `WeakReference`?* When something should be observed or indexed without
  keeping it alive: `WeakHashMap` metadata keyed by an object owned elsewhere, listener registries.

## Explain it in 2 minutes

Prompt: "Follow a Java object from `new` to reclamation."

- Class must be initialised; memory comes from the thread's TLAB in eden by bump pointer (or old
  regions if humongous; or nowhere, via escape analysis).
- Memory is zeroed and the header written; constructors run super-first; `final` fields freeze at
  the end; don't leak `this`.
- Alive while strongly reachable from roots; minor GCs copy survivors and age them; at the
  threshold they are promoted to old.
- When unreachable, weak/soft/phantom references are cleared according to their rules; `Cleaner`
  actions run; `finalize` is deprecated.
- Memory is reused by the collector; process RSS may not shrink.

## Check yourself

1. What is a TLAB, and why does it make allocation fast?
2. A superclass constructor calls an overridden method that prints a subclass field. What is
   printed, and why?
3. What decides when an object is promoted?
4. Order these by how easily they are cleared: weak, soft, strong.
5. Why does a `Cleaner` action that references `this` break cleanup?

### Answers

1. A thread-private chunk of eden; allocation just moves a pointer, with no locking.
2. The field's default value (`null`/`0`), because subclass field initialisers run after the
   superclass constructor returns.
3. Its age (number of minor GCs survived) reaching the tenuring threshold (at most 15), or survivor
   space overflow.
4. Weak (cleared at the next GC that finds it weakly reachable), then soft (cleared under memory
   pressure, before OOM), then strong (never while reachable).
5. The Cleaner holds the action strongly; if the action references the object, the object stays
   reachable and never becomes phantom-reachable.
