## Where we are

After CAPSTONE-2, TicketHub is a plain Maven project with a tested domain, an `EventCatalog` seeded from JSON, and a thread-safe in-memory `BookingEngine`. So far it can only be driven from tests. Today it becomes a Spring Boot service with its first HTTP endpoints, using the IoC container, scopes and profiles from SPRING-BOOT-2 and the conventions from BE-STORY-8.

## Goal

Turn the project into a Spring Boot 3.5 application without rewriting the domain. The catalog, the engine and the `Clock` become **beans** wired by constructor injection. The hold duration and the seed file location move into type-safe, validated `@ConfigurationProperties`. `dev` and `test` profiles choose different seeds. Three read-only endpoints serve events and seat availability from the in-memory engine. A MockMvc smoke test proves the wiring, and Actuator reports health. The domain classes gain **zero** Spring imports: Spring lives at the edges.

## Steps

### 1. Become a Spring Boot project (10 min)

On start.spring.io choose Maven, Java 21, the latest Spring Boot **3.5.x**, group `com.tickethub`, artifact `tickethub`, and the dependencies **Spring Web**, **Validation** and **Spring Boot Actuator**. Do not copy the generated project over yours. Copy the `<parent>`, the starters and the `spring-boot-maven-plugin` into your existing `pom.xml`, then:

- remove the explicit JUnit BOM, AssertJ and Jackson entries. `spring-boot-starter-test` brings JUnit 5, AssertJ and Mockito, and `spring-boot-starter-web` brings Jackson with the `jsr310` module, all at versions Boot has tested together;
- keep `<java.version>21</java.version>`. The Boot parent also compiles with `-parameters`, which is what lets `@PathVariable long id` work without repeating the name.

> Boot 4 note: Boot 4 moves to Jackson 3 (package `tools.jackson`). Your `SeedLoader` imports would change, which is one more reason to keep JSON handling in one class.

```java
package com.tickethub;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.context.properties.ConfigurationPropertiesScan;

@SpringBootApplication
@ConfigurationPropertiesScan
public class TicketHubApplication {
    public static void main(String[] args) {
        SpringApplication.run(TicketHubApplication.class, args);
    }
}
```

The class sits in `com.tickethub`, so component scanning covers every feature package below it.

### 2. Type-safe configuration (10 min)

`@Value("${tickethub.hold-duration}")` scattered through the code works, but it is stringly typed, it cannot be validated as a group, and nothing shows the full set of settings in one place. A `@ConfigurationProperties` record solves all three. Spring binds `tickethub.*` into the record's constructor, converts `"10m"` into a `Duration` and `"classpath:..."` into a `Resource`, and runs Bean Validation **at startup**.

```java
package com.tickethub.common;

import jakarta.validation.constraints.NotNull;
import java.time.Duration;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.core.io.Resource;
import org.springframework.validation.annotation.Validated;

@Validated
@ConfigurationProperties(prefix = "tickethub")
public record TicketHubProperties(@NotNull Duration holdDuration, @NotNull Resource seedLocation) {}
```

`src/main/resources/application.yml`:

```yaml
spring:
  application.name: tickethub
  profiles.default: dev
tickethub:
  hold-duration: 10m
management:
  endpoints.web.exposure.include: health,info
```

`application-dev.yml`:

```yaml
tickethub:
  seed-location: classpath:seed/dev-seed.json
logging.level.com.tickethub: DEBUG
```

`src/test/resources/application-test.yml`, with its own small seed:

```yaml
tickethub:
  hold-duration: 2m
  seed-location: classpath:seed/test-seed.json
```

`src/test/resources/seed/test-seed.json`: one venue (`id 1`, `"Test Hall"`, 2 rows × 5 seats, so seat ids `1001`–`1010`) and three events at that venue, `"Opening Night"`, `"Second Night"` and `"Closing Night"`, starting `2030-01-01`, `2030-01-02` and `2030-01-03` (any time of day, UTC), all `STANDARD`. Those events and seats are what the CAPSTONE-4 tests use too.

A **profile** is a named set of configuration that is active or not. `spring.profiles.default: dev` applies only when no profile is chosen, so `--spring.profiles.active=prod` later replaces it rather than adding to it.

### 3. Wire the domain as beans (10 min)

Two ways to make a bean exist: annotate the class with `@Component`/`@Service`, or write a `@Bean` method in a `@Configuration` class. Use **`@Bean` methods** here. `BookingEngine` and `EventCatalog` stay plain Java that you can still construct in a unit test with `new`, and all the Spring knowledge sits in three small classes.

```java
package com.tickethub.common;

@Configuration
class ClockConfig {
    @Bean
    Clock clock() { return Clock.systemUTC(); }
}
```

```java
package com.tickethub.event;

@Configuration
class EventConfig {
    @Bean
    EventCatalog eventCatalog(TicketHubProperties props) throws IOException {
        try (InputStream in = props.seedLocation().getInputStream()) {
            return new SeedLoader().load(in);
        }
    }
}
```

```java
package com.tickethub.booking;

@Configuration
class BookingConfig {
    @Bean
    BookingEngine bookingEngine(EventCatalog catalog, Clock clock, TicketHubProperties props) {
        return new BookingEngine(catalog, clock, props.holdDuration());
    }
}
```

The `@Bean` method parameters *are* the constructor injection. Spring resolves each one by type, builds dependencies first, and fails at startup if one is missing or ambiguous. All three beans are **singletons** (one instance per application context). That is only safe for `BookingEngine` because you made it thread-safe in CAPSTONE-2: every request thread shares that one instance.

### 4. Read-only endpoints (15 min)

First, response records that decide the JSON shape. Returning `Event` directly would tie the public API to the domain, and the domain changes in CAPSTONE-5 when JPA arrives.

```java
package com.tickethub.event;

public record EventResponse(long id, String name, Instant startsAt, String venueName, PriceCategory priceCategory) {
    static EventResponse from(Event e, Venue v) {
        return new EventResponse(e.id(), e.name(), e.startsAt(), v.name(), e.priceCategory());
    }
}
```

```java
package com.tickethub.event;

@RestController
@RequestMapping("/api/v1/events")
class EventController {
    private final EventCatalog catalog;
    private final Clock clock;

    EventController(EventCatalog catalog, Clock clock) {   // single constructor: no @Autowired needed
        this.catalog = catalog;
        this.clock = clock;
    }

    @GetMapping
    List<EventResponse> list() {
        return catalog.upcoming(clock.instant()).stream()
                .map(e -> EventResponse.from(e, catalog.venueOf(e.id())))
                .toList();
    }

    @GetMapping("/{id}")
    EventResponse get(@PathVariable long id) {
        return EventResponse.from(catalog.event(id), catalog.venueOf(id));
    }

    // Temporary, local handler. CAPSTONE-4 replaces it with one @RestControllerAdvice for every error.
    @ExceptionHandler(EventNotFoundException.class)
    ProblemDetail notFound(EventNotFoundException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setProperty("code", ex.code());
        return pd;
    }
}
```

The seat map goes in the **`booking`** package as `SeatMapController`, mapped to `GET /api/v1/events/{id}/seats`. Availability is booking knowledge, and `booking` already depends on `event`. Putting it in `event` would create a cycle between the two packages. It returns `List<SeatResponse>`, where `SeatResponse(long id, int row, int number, boolean available)` is mapped from `engine.seatMap(id)`. Give it the same temporary 404 handler, or skip it there and accept a 500 for unknown events until next week.

### 5. MockMvc smoke test (12 min)

**MockMvc** drives your controllers through the real Spring MVC pipeline (message conversion, exception handling, JSON) without opening a socket. `@SpringBootTest` starts the whole context, so this also proves that the beans wire up.

```java
@SpringBootTest
@AutoConfigureMockMvc
@ActiveProfiles("test")
class EventApiSmokeTest {
    @Autowired MockMvc mvc;

    @Test
    void listsUpcomingEvents() throws Exception {
        mvc.perform(get("/api/v1/events"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.length()").value(3))
                .andExpect(jsonPath("$[0].name").value("Opening Night"))
                .andExpect(jsonPath("$[0].venueName").value("Test Hall"));
    }

    @Test
    void unknownEventIs404WithCode() throws Exception {
        mvc.perform(get("/api/v1/events/999"))
                .andExpect(status().isNotFound())
                .andExpect(content().contentType(MediaType.APPLICATION_PROBLEM_JSON))
                .andExpect(jsonPath("$.code").value("EVENT_NOT_FOUND"));
    }

    @Test
    void seatMapShowsAvailability() throws Exception {
        mvc.perform(get("/api/v1/events/1/seats"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.length()").value(10))
                .andExpect(jsonPath("$[0].available").value(true));
    }
}
```

`TicketHubPropertiesTest` is the same setup with `@Autowired TicketHubProperties props`, asserting `props.holdDuration()` is `Duration.ofMinutes(2)`. That proves the test profile, not the default, was applied.

## Hints

- **"No qualifying bean of type EventCatalog"** usually means the config class is outside `com.tickethub`, or you created a second `@SpringBootApplication` in a test package.
- **`startsAt` shows up as `1.7e9`**: you built your own `ObjectMapper` bean somewhere and lost Boot's defaults. Customise with `spring.jackson.*` properties or a `Jackson2ObjectMapperBuilderCustomizer` instead.
- **The record properties do not bind.** Check that `@ConfigurationPropertiesScan` is on the application class, and that the YAML key is `hold-duration` (kebab-case) while the record component is `holdDuration`.
- **`events` is empty in the test**: `upcoming` filters on the real clock, so seed dates in the past disappear. That is why the test seed uses 2030.
- Contexts are cached across test classes that share the same configuration. Avoid `@DirtiesContext` and `@MockitoBean` sprinkled in different combinations, or every class pays for a fresh startup.

## Talk about it in interviews

**"What is dependency injection and why does Spring use constructor injection?"**
- *What:* an object receives its collaborators instead of creating them, and the container decides which implementation each one gets.
- *How it works inside:* at startup Spring reads bean definitions (from scanning and `@Bean` methods), orders them by dependency, calls the constructors or factory methods with resolved arguments, and keeps singletons in its registry. Constructor injection makes the dependencies `final`, explicit, and impossible to forget.
- *Where used:* TicketHub's `BookingEngine` gets `EventCatalog`, `Clock` and the hold duration through a `@Bean` method. In unit tests the same class is built with `new` and a `MutableClock`, with no Spring involved.
- *What goes wrong:* field injection hides dependencies and makes the class untestable without reflection. Circular dependencies fail at startup (good). A singleton with unsafe mutable state is a concurrency bug, which is why the engine had to be thread-safe first.

**"`@Value` vs `@ConfigurationProperties`?"** `@Value` injects one string-resolved value at a time. `@ConfigurationProperties` binds a whole prefix into a typed object with relaxed names, conversions (`Duration`, `DataSize`, `Resource`) and validation at startup. TicketHub's hold duration is a `Duration`: a missing or malformed value stops startup instead of failing on the first booking.

**"How do you manage configuration across environments?"** Use profiles for the differences between environments, keep the defaults in `application.yml`, and put secrets in environment variables or a secret manager, never in profile files. A common mistake is `spring.profiles.active` committed in `application.yml`, which then silently overrides the deployment.

**"Why not return your domain objects from controllers?"** API records are the contract, and the domain can change behind them. It also stops accidental exposure of fields, and it matters most once JPA entities with lazy relations arrive.
