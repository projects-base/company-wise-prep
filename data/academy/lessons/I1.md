## Where we are

SYS-DES-1 gave you the two flavours of messaging: a **queue** deletes a message once it is processed, while a **stream** (a log) keeps it and lets each consumer group read at its own position. It also said that order holds only within a partition. This lesson opens Kafka up: how the log is stored, how producers and consumers really behave, and the exact settings behind "at least once" and "exactly once". These are the follow-ups interviewers ask once you say "I'd put Kafka here".

## The problem

The order service publishes `OrderPlaced`, `OrderPaid` and `OrderCancelled`. Three teams consume them: email, inventory and analytics. Then the questions arrive:

- A broker dies. Did we lose the `OrderPaid` event?
- The email service crashed halfway through a batch. Will customers get two emails, or none?
- Black Friday: the inventory consumer is ten minutes behind. Can we just add more instances?
- One event has a malformed payload and the consumer throws on it forever. Is everything behind it stuck?

Each answer depends on one specific Kafka mechanism. We will take them one at a time.

## Topic, partition, offset

A **topic** is a named stream, such as `orders`. It is split into **partitions**, and each partition is an **append-only log**: records are only ever added at the end. Each record gets an **offset**, its position number in that partition, starting at 0.

```text
topic "orders" (3 partitions)
  p0: [0][1][2][3][4][5]  ← new records appended here
  p1: [0][1][2]
  p2: [0][1][2][3]
```

Offsets are per partition, so "offset 2" means nothing without saying which partition. A record is a key, a value (bytes), a timestamp and optional headers. Kafka does not look inside the value: the producer and consumer agree on the format (JSON, Avro, Protobuf).

**The rule:** a partition is the unit of ordering, of storage and of parallelism. Almost every Kafka question comes back to partitions.

## How the log is stored, and how long

Each partition is a directory on a broker (a Kafka server). Inside it, the log is cut into **segment files**: `00000000000000000000.log`, plus `.index` and `.timeindex` files that map offsets and timestamps to byte positions. Only the newest, **active** segment receives writes.

Kafka is fast for a design reason, not magic: writes are sequential appends, reads are mostly sequential, the OS page cache does the caching, and data can be sent from disk to socket without copying through the JVM heap ("zero-copy"). Records are also batched and compressed.

Old data leaves by **retention**, applied to whole closed segments:

- **Time or size retention** (`cleanup.policy=delete`): delete segments older than `retention.ms` (the broker default is 7 days) or beyond `retention.bytes`. Reading a record does *not* delete it.
- **Log compaction** (`cleanup.policy=compact`): keep at least the latest record for each key and discard older ones. A record with a null value (a **tombstone**) deletes the key. Compacted topics act like a changelog of "current state per key", for example the latest price per product.

## Producers: the key decides the partition

The producer chooses a partition for each record:

- **With a key:** the default partitioner hashes the key (murmur2) modulo the partition count. The same key always lands in the same partition, so **all events for `order-7` stay in order**.
- **Without a key:** records are spread across partitions (in batches, by the "sticky" partitioner). No ordering promise.

Two consequences interviewers like:

1. **Adding partitions changes the mapping.** `hash % 3` and `hash % 6` differ, so new events for `order-7` may land in a new partition while old ones sit in the old one. Plan the count up front, and you can never reduce it.
2. **Hot keys make hot partitions.** If one tenant produces half the traffic, half the traffic lands on one partition, and one consumer.

## acks and the idempotent producer

**The problem:** the producer sends a record, the network blips, no reply comes. Retry, and you might write it twice. Don't retry, and you might lose it.

`acks` controls when the broker says "done":

| `acks` | Broker replies when | Risk |
|---|---|---|
| `0` | Never; fire and forget | Loss without any error |
| `1` | The partition leader has written it | Loss if the leader dies before followers copy it |
| `all` (`-1`) | All **in-sync replicas** have it | Safest; slightly higher latency |

The **idempotent producer** (`enable.idempotence=true`) solves the duplicate-on-retry case. The broker gives the producer an id, and the producer numbers each batch per partition. If a retried batch arrives with a sequence number the broker already has, it is dropped. It also keeps order with up to 5 in-flight requests. Since Kafka 3.0 the producer defaults are `acks=all` and idempotence on.

Note its limit: it prevents duplicates from *the producer's own retries within one session*. If your application crashes and re-sends the event after restart, that is a new send. Kafka cannot know it is a repeat.

## Replication, ISR and min.insync.replicas

Each partition has a **replication factor**, usually 3. One replica is the **leader** (all reads and writes go to it); the others are **followers** that copy from it.

The **ISR** (in-sync replicas) is the set of replicas that are caught up with the leader within `replica.lag.time.max.ms`. If the leader dies, a new leader is chosen from the ISR, so nothing acknowledged is lost.

```text
p0  leader: broker 1   followers: broker 2, broker 3   ISR = {1,2,3}
broker 3 falls behind  →  ISR = {1,2}   (acks=all now waits for 1 and 2 only)
```

That last line is the trap: if the ISR shrinks to just the leader, `acks=all` means "the leader has it", which is `acks=1`. **`min.insync.replicas=2`** closes the gap: writes with `acks=all` are refused (`NotEnoughReplicas`) unless at least 2 replicas are in sync.

**The rule:** replication factor 3, `min.insync.replicas=2`, `acks=all`. You survive one broker loss with no data loss and no write outage. Keep `unclean.leader.election.enable=false` (the default) so an out-of-sync replica never becomes leader and silently drops records.

Consumers only see records up to the **high watermark**: the highest offset copied to every ISR member. So a consumer never reads a record that could vanish in a failover.

## Consumer groups and rebalancing

A **consumer group** is a set of consumer instances sharing one `group.id`. Kafka assigns **each partition to exactly one consumer in the group**. Different groups are independent: email and inventory each get every event.

```text
topic orders: p0 p1 p2 p3 p4 p5
group "inventory" with 3 instances:  A ← p0,p1   B ← p2,p3   C ← p4,p5
add instance D:                      A ← p0,p1   B ← p2   C ← p4   D ← p3,p5 ... (rebalanced)
7 instances on 6 partitions:         one instance sits idle
```

So the answer to "can we just add consumers?" is: **only up to the number of partitions**.

A **rebalance** reassigns partitions. It happens when a consumer joins, leaves, stops heartbeating (`session.timeout.ms`), or takes too long between `poll()` calls (`max.poll.interval.ms`, default 5 minutes). That last one is a classic production bug: slow processing per batch causes the consumer to be kicked out, its partitions move, the work is redone, and it repeats.

Rebalances used to stop the whole group ("eager"). The **cooperative sticky** assignor moves only the partitions that need to move, **static membership** (`group.instance.id`) lets a restarting pod rejoin without a rebalance, and newer Kafka versions add a broker-driven consumer protocol (KIP-848) that makes rebalances incremental by design.

## Offset commits decide your delivery guarantee

A consumer **commits** its offset to the internal topic `__consumer_offsets`. The committed value is *the next offset to read*. After a crash or rebalance, the new owner of the partition starts there.

When you commit, relative to when you process, decides what a crash costs:

```text
at-most-once:   poll → commit → process      crash after commit = record skipped (lost)
at-least-once:  poll → process → commit      crash before commit = record processed again
```

- **Auto-commit** (`enable.auto.commit=true`, every 5 s by default) commits during later `poll()` calls. It is roughly at-least-once, but the boundary is hard to reason about. For important work, turn it off and commit after processing.
- **At-least-once** is the normal choice. It means duplicates *will* happen, so the consumer must be **idempotent**: record processed event ids, use upserts, or use a unique constraint.

**Exactly-once** in Kafka means something precise: a *read-process-write* pipeline from Kafka topics to Kafka topics.

1. The producer gets a `transactional.id`, calls `beginTransaction()`, writes its output records, and calls `sendOffsetsToTransaction(...)` so **the input offsets commit in the same transaction**, then `commitTransaction()`.
2. Downstream consumers set **`isolation.level=read_committed`** so they never see records from aborted transactions.

Kafka Streams turns this on with `processing.guarantee=exactly_once_v2`. It does **not** cover side effects outside Kafka. Sending an email or writing to Postgres is still at-least-once; make it idempotent, or store the offset in the same database transaction as the result.

## Consumer lag

**Lag** = the partition's latest offset (log end offset) minus the group's committed offset. It is the single most useful Kafka health metric.

```text
$ kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group inventory
TOPIC   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
orders  0          1200            1200            0
orders  1          900             5400            4500   ← one partition behind: hot key or stuck record?
```

Alert on lag that **keeps growing**, not on a fixed number. Lag on every partition means consumers are too slow (scale out, up to the partition count, or speed up processing). Lag on one partition means a hot key or a poison message.

## Poison messages and dead-letter topics

**The problem:** one record cannot be deserialized or always throws. An at-least-once consumer retries it forever, and because a partition is processed in order, **everything behind it stops**.

The fix: retry a bounded number of times (with backoff) for transient errors, then publish the record to a **dead-letter topic (DLT)** with the error in headers, commit, and move on. Someone inspects and replays the DLT later. In Spring Kafka:

```java
@Configuration
class KafkaErrorConfig {
    @Bean
    DefaultErrorHandler errorHandler(KafkaOperations<Object, Object> template) {
        var recoverer = new DeadLetterPublishingRecoverer(template);    // sends to "<topic>.DLT"
        var handler = new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 2)); // 2 retries, 1 s apart
        handler.addNotRetryableExceptions(IllegalArgumentException.class);          // bad data: no retry
        return handler;
    }
}
```

Boot wires a `CommonErrorHandler` bean into its listener container factory. For bad bytes, also configure `ErrorHandlingDeserializer` so a deserialization failure reaches this handler instead of crashing the poll loop. Never retry validation errors: they will fail the same way every time.

## Kafka versus RabbitMQ

| | Kafka | RabbitMQ |
|---|---|---|
| Model | Partitioned log; consumers track offsets | Broker routes messages to queues; deleted on ack |
| Replay | Yes, within retention | No (streams plugin aside) |
| Ordering | Per partition | Per queue, with one consumer |
| Routing | Topic + key only | Rich: direct, topic, fanout, headers exchanges |
| Scaling consumers | Up to partition count per group | Add competing consumers freely |
| Per-message features | Few | Per-message TTL, priorities, delayed retry |
| Best at | High-throughput event streams, many independent readers, event history | Task queues, complex routing, per-message work |

Pick Kafka when the events are a shared fact that many systems read (and may re-read). Pick RabbitMQ (or SQS) when messages are jobs to be done once by whoever is free.

## KRaft: no more ZooKeeper

Kafka used to store cluster metadata (brokers, topics, partition leaders) in a separate **ZooKeeper** cluster, which meant operating two distributed systems. **KRaft** moves that metadata into Kafka itself: a small quorum of **controller** nodes replicates a metadata log using the Raft consensus protocol. KRaft became production-ready in Kafka 3.3, and Kafka 4.0 removed ZooKeeper support entirely. Benefits: one system to run, faster controller failover, and support for far more partitions.

## Lab (~10 min)

Start a single-node KRaft broker and make a 3-partition topic:

```text
docker run -d --name kafka -p 9092:9092 apache/kafka:3.8.0
docker exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic orders --partitions 3
```

Add `org.apache.kafka:kafka-clients` to a Java 21 project. Producer:

```java
import org.apache.kafka.clients.producer.*;
import org.apache.kafka.common.serialization.StringSerializer;
import java.util.Properties;

public class OrderProducer {
    public static void main(String[] args) throws Exception {
        Properties p = new Properties();
        p.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        p.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
        p.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName());
        p.put(ProducerConfig.ACKS_CONFIG, "all");
        p.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
        try (var producer = new KafkaProducer<String, String>(p)) {
            for (int i = 0; i < 12; i++) {
                String key = "order-" + (i % 4);
                RecordMetadata md = producer.send(new ProducerRecord<>("orders", key, "event-" + i)).get();
                System.out.printf("%s -> partition %d, offset %d%n", key, md.partition(), md.offset());
            }
        }
    }
}
```

Consumer with manual, after-processing commits (at-least-once):

```java
import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.common.serialization.StringDeserializer;
import java.time.Duration;
import java.util.List;
import java.util.Properties;

public class InventoryConsumer {
    public static void main(String[] args) {
        Properties c = new Properties();
        c.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
        c.put(ConsumerConfig.GROUP_ID_CONFIG, "inventory");
        c.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
        c.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG, StringDeserializer.class.getName());
        c.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);
        c.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");
        try (var consumer = new KafkaConsumer<String, String>(c)) {
            consumer.subscribe(List.of("orders"));
            while (true) {
                ConsumerRecords<String, String> records = consumer.poll(Duration.ofSeconds(1));
                for (ConsumerRecord<String, String> r : records) {
                    System.out.printf("p%d@%d %s=%s%n", r.partition(), r.offset(), r.key(), r.value());
                }
                consumer.commitSync();   // commit only after the batch is processed
            }
        }
    }
}
```

**Observe:**

- Every `order-N` key always prints the same partition, and its events appear in order.
- Start two consumers: the console shows partitions split between them. Start four: one is idle.
- **Break it:** stop the consumers, run the producer again, then run `kafka-consumer-groups.sh --describe --group inventory` (as in the lag section). Lag shows the unread records. Now move `commitSync()` *before* the print loop, kill the consumer mid-batch with a debugger pause, and see records skipped: at-most-once.

## Gotchas

- **"Kafka is exactly-once, so my consumer needn't be idempotent."** Exactly-once covers Kafka-to-Kafka transactions only. DB writes and emails are at-least-once; dedupe by event id.
- **`acks=all` without `min.insync.replicas=2`.** If the ISR shrinks to the leader, you are back to `acks=1`. Set both, with replication factor 3.
- **Slow processing inside the poll loop.** Exceeding `max.poll.interval.ms` triggers a rebalance and reprocessing loops. Keep batches small (`max.poll.records`) or hand work off carefully.
- **More consumers than partitions.** The extras sit idle. Partition count caps parallelism per group, and changing it later remaps keys.
- **One poison record blocking a partition.** Bounded retries, then a DLT; never retry validation errors.
- **Relying on global order.** Order exists only within a partition. If you truly need total order, you need one partition, and you accept its throughput limit.

## In interviews

Typical prompts: "Explain Kafka's architecture", "How does Kafka guarantee ordering?", "At-least-once vs exactly-once?", "How do you avoid losing messages?", "Your consumer lag is growing; what do you do?", "Kafka or RabbitMQ?". Bank: [Kafka architecture](#/q/kafka-architecture), [Messaging systems (queues, pub/sub) in backend services](#/q/messaging-systems-fundamentals), [Design a distributed queue with multiple producers and consumers](#/q/design-distributed-message-queue), [Deduplicate a stream of device events within a time window](#/q/design-stream-deduplicator), [Idempotency in Payment Systems](#/q/idempotency-in-payment-systems).

A strong answer has four layers:

1. **What:** a distributed, replicated, partitioned commit log; consumers pull and track their own offsets.
2. **How it works inside:** key hash picks the partition; leader plus ISR replication; `acks=all` + `min.insync.replicas`; idempotent producer sequence numbers; one partition per consumer in a group; offsets in `__consumer_offsets`; transactions + `read_committed`.
3. **Where used:** event-driven microservices, change-data-capture, activity and metrics pipelines, event sourcing with compacted topics.
4. **What goes wrong:** rebalance storms from slow consumers, hot partitions, poison messages, duplicates on retry, key remapping after adding partitions.

**Follow-up: "How do you guarantee no loss end to end?"** Producer: `acks=all`, idempotence, handle the send callback's error. Broker: RF 3, `min.insync.replicas=2`, no unclean election. Consumer: commit after processing, idempotent handler. For "DB write + publish" in the producer service, the transactional outbox (coming in DIST-SYS-3).

**Follow-up: "Lag is growing on one partition only."** Look for a hot key or a stuck record. Check the DLT and error logs, then consider a better key (for example `tenantId:orderId`), not just more consumers.

## Explain it in 2 minutes

*"How does Kafka deliver a message from producer to consumer, and what can make it lost or duplicated?"*

- The producer hashes the key to a partition and sends to that partition's leader; `acks=all` waits for the in-sync replicas.
- The idempotent producer's sequence numbers stop retries from creating duplicates; `min.insync.replicas=2` stops the ISR shrinking to one.
- Records are appended to segment files and kept by retention, not deleted on read.
- In a consumer group each partition has one consumer; it polls, processes, then commits the next offset.
- Commit before processing gives at-most-once; after gives at-least-once with duplicates; Kafka transactions plus `read_committed` give exactly-once only inside Kafka.
- So consumers are idempotent, poison records go to a DLT, and lag is the health signal.

## Check yourself

1. A topic has 4 partitions and a group has 6 consumers. What happens, and how would you get more parallelism?
2. Why can `acks=all` still lose data, and which setting fixes it?
3. Your consumer commits offsets before processing. What delivery guarantee is that, and what is lost on a crash?
4. You add partitions to a topic keyed by `orderId`. What breaks?
5. What does `isolation.level=read_committed` do, and when do you need it?

### Answers

1. Four consumers each get one partition and two are idle. Increase the partition count (planning for the key remapping), or process records concurrently inside each consumer while preserving per-key order.
2. If the ISR has shrunk to the leader alone, `acks=all` only waits for the leader; if it then dies, the record is gone. Set `min.insync.replicas=2` with replication factor 3.
3. At-most-once. Records committed but not yet processed when the consumer crashed are never processed.
4. The key-to-partition mapping changes, so new events for an existing order can land in a different partition from its older events, and per-order ordering across the change is lost.
5. The consumer only reads records from committed transactions, skipping aborted ones and waiting for open ones. You need it downstream of transactional producers, as part of exactly-once pipelines.
