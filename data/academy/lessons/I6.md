## Where we are

DIST-SYS-5 packaged a Spring Boot service as an image and ran it on Kubernetes with probes and
rolling updates. That answers "how does it run". This lesson answers "how does a change get from your
laptop to production without breaking anything": Git deeply enough to reason about it, a CI pipeline
that earns trust, and the deployment strategies that let you release and undo safely.

## The problem

Thursday, 18:00. A two-week feature branch is merged; the merge took an afternoon of conflicts. The
build on `main` is red, so someone skips the tests "just this once". The jar is rebuilt on the prod
server, the deploy replaces every instance at once, and the release includes a migration that drops
a column. Errors spike. Rolling back the code does not help, because the old code needs the dropped
column. Each step was a choice; this lesson replaces each with a safer one.

## Git: snapshots, pointers and HEAD

Three facts explain almost every Git command:

- A **commit** is a full **snapshot** of the project (stored efficiently: unchanged files are shared),
  plus metadata and a pointer to its **parent** commit(s). Its id is a hash of all that, so a commit
  never changes; "editing" one creates a new commit with a new id.
- A **branch** is a movable pointer to one commit, nothing more. Committing moves the current branch
  forward.
- **HEAD** is a pointer to what you have checked out: normally a branch, sometimes a commit directly
  ("detached HEAD").

```text
A ─ B ─ C        ← main
         \
          D ─ E  ← feature   ← HEAD
```

Creating a branch writes one tiny file holding a commit id; that is why short-lived branches are cheap.

## Merge vs rebase

Both bring `main`'s new commits into `feature`; they record history differently.

- **Merge** creates a **merge commit** with two parents. History is true but branchy.
- **Rebase** replays your commits on top of the new `main`, creating *new* commits D' and E'.
  History is linear, but D and E are replaced.

```text
merge:   A ─ B ─ C ─ F ─ M      rebase:  A ─ B ─ C ─ F ─ D' ─ E'
                  \     /
                   D ─ E
```

**The golden rule:** never rebase commits that others already have (pushed to a shared branch).
Rebasing rewrites ids; teammates' copies still point at the old ones, and their next pull duplicates
or loses work. Rebase your own local work freely; merge (or squash) to share.

**Squash merge** turns a whole PR into one commit on `main`: clean history, one revert undoes the
feature. **Cherry-pick** copies one commit onto another branch (as a new commit), typically a hotfix
from `main` onto a release branch.

## Undo: revert vs reset

- `git revert <commit>` creates a *new* commit that undoes the change. Safe on shared branches,
  because history only grows. This is how you undo on `main`.
- `git reset` moves the branch pointer backwards. `--soft` keeps changes staged, `--mixed` (default)
  keeps them in the working tree, `--hard` throws them away. Only for local, unshared commits.
  Lost something to a reset? `git reflog` lists where HEAD has been, so it is usually recoverable.

## Conflicts and bisect

A **conflict** happens when both sides changed the same lines. Git writes both versions into the
file between `<<<<<<<`, `=======` and `>>>>>>>` markers; you edit to the correct result, `git add`
the file, and continue (`git merge --continue` or `git rebase --continue`). The correct result is a
*decision*, not a mechanical pick: often neither side is right alone. Run the tests before
continuing.

`git bisect` finds the commit that introduced a bug by binary search: you mark one good and one bad
commit, Git checks out the middle, you say good or bad, repeat. 1,000 commits take about 10 steps.
With `git bisect run <script>` (exit 0 = good, non-zero = bad) it is fully automatic, and a small
failing test makes the perfect script.

## Branching models

- **GitFlow**: long-lived `develop` and `main`, plus feature, release and hotfix branches. Suits
  software released in versions (mobile apps, on-prem products) but means long-lived branches,
  large merges and slow feedback.
- **Trunk-based development**: everyone integrates into `main` (the trunk) at least daily, through
  short-lived branches (hours to a couple of days) and PRs. Unfinished work hides behind feature
  flags rather than living on a branch.

Trunk-based pairs with **CI** (continuous integration: every change is built and tested
automatically as it merges) because integration is the point: small changes conflict rarely, break
less, and a red build points at one small change. Most teams deploying services continuously use
it.

## PR hygiene

A good pull request is small (a reviewer can hold it in their head: a few hundred lines at most),
does one thing, has a description that says *why* and how it was tested, and is green before review.
Reviewers look for correctness, failure handling, tests, naming and backward compatibility, not for
formatting, which a formatter and linter in CI should own. Protect `main`: required checks and at
least one approval before merge.

## A CI pipeline for a Spring Boot service

The stages, cheapest first so failures come fast:

```text
checkout → build + unit tests → integration tests (Testcontainers) → static analysis
        → dependency scan → build image → push image (tagged with the commit SHA)
```

In Maven, `verify` runs unit tests (Surefire, `*Test`) and then integration tests (Failsafe,
`*IT`, if configured), plus any analysis plugins bound to the build, such as Checkstyle, SpotBugs
or a formatter check. Testcontainers (SPRING-BOOT-8) needs Docker, which GitHub's Ubuntu runners
provide.

```yaml
# .github/workflows/ci.yml
name: ci

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
      - name: Build, unit and integration tests, static analysis
        run: ./mvnw -B -ntp verify
      - name: Keep test reports on failure
        if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: test-reports
          path: target/*-reports/

  dependency-review:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/dependency-review-action@v4
        with:
          fail-on-severity: high

  image:
    if: github.event_name == 'push'
    needs: build
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/acme/orders:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

Notes: `-B` is batch mode and `-ntp` hides download progress; `cache: maven` caches `~/.m2`; the
image job runs only after tests pass on `main`. Dependency review compares the PR's dependencies
against known vulnerabilities and needs GitHub's dependency graph (free for public repositories);
alternatives are OWASP Dependency-Check in the build or an image scanner such as Trivy after the
image is built. GHCR image names must be lowercase, which is why the name is written out rather
than taken from `github.repository`. Secrets come from the platform (`GITHUB_TOKEN`, repository
secrets), never from the YAML.

## The same pipeline in Jenkins

Many companies run **Jenkins** instead of GitHub Actions, so expect to read a `Jenkinsfile`. The ideas
are the same; the difference is that you run Jenkins yourself. A **controller** schedules jobs and
holds configuration, and **agents** are the machines that run the steps. The pipeline lives in a
`Jenkinsfile` in the repository, so it is reviewed and versioned like code.

```groovy
pipeline {
    agent { label 'docker' }
    options {
        timeout(time: 30, unit: 'MINUTES')
        disableConcurrentBuilds()
    }
    environment {
        IMAGE = "registry.example.com/shopkart/orders:${env.GIT_COMMIT}"
    }
    stages {
        stage('Build and test') {
            steps {
                sh './mvnw -B -ntp verify'
            }
            post {
                always {
                    junit 'target/surefire-reports/*.xml'
                }
            }
        }
        stage('Image') {
            when { branch 'main' }
            steps {
                withCredentials([usernamePassword(credentialsId: 'registry',
                        usernameVariable: 'REG_USER', passwordVariable: 'REG_PASS')]) {
                    sh '''
                        echo "$REG_PASS" | docker login registry.example.com -u "$REG_USER" --password-stdin
                        docker build -t "$IMAGE" .
                        docker push "$IMAGE"
                    '''
                }
            }
        }
    }
}
```

Notes: `when { branch 'main' }` needs a **multibranch pipeline**, which builds every branch and PR
that has a Jenkinsfile. Secrets come from Jenkins' credentials store through `withCredentials`. The
`sh` block uses single quotes on purpose, so the shell reads the secret from the environment; with
double quotes Groovy would paste it into the command string, where it can leak.

| | GitHub Actions | Jenkins |
|---|---|---|
| Who runs it | GitHub, or your own runners | You: the controller, agents, upgrades, plugins |
| Pipeline file | `.github/workflows/*.yml` | `Jenkinsfile` |
| Strength | Nothing to operate, close to the PR | Full control, runs inside a private network |
| Usual pain | Usage limits, less control | Plugin upgrades and looking after the controller |

Whichever tool it is, the interview answer is about the stages, not the syntax: fast feedback first,
one artifact built once, secrets outside the file.

## CD: one artifact, many environments

**Continuous delivery** means every green build *could* go to production; **continuous deployment**
means it does, automatically. Either way:

- **Build once, promote the same artifact.** The image tagged with the commit SHA that passed tests
  in staging is the exact image that goes to production. Rebuilding per environment means testing
  one thing and shipping another.
- **Config per environment, outside the artifact**: environment variables, ConfigMaps and Secrets
  (DIST-SYS-5), Spring profiles at most for defaults. The image contains no environment-specific
  URLs or passwords.
- **Environments**: typically dev, staging (production-like data shape and config), production,
  with an approval or automated checks gating each promotion.

## Deployment strategies

| Strategy | How | Downtime | Rollback | Cost / catch |
|---|---|---|---|---|
| **Recreate** | stop all old, start all new | yes | redeploy old | simplest; fine for batch jobs |
| **Rolling** | replace instances a few at a time | no | roll back the same way | old and new run together |
| **Blue-green** | full new stack (green) beside old (blue), switch traffic at once | no | switch back | double capacity during release; shared DB must suit both |
| **Canary** | send a small share of traffic to the new version, widen in steps | no | send the share back to zero | needs traffic splitting and good metrics |

**Rolling** is the Kubernetes default (DIST-SYS-5): `maxSurge` extra pods may be created,
`maxUnavailable` may be missing, and an old pod is removed only when a new one passes its
**readiness probe**. Honest readiness is what makes it safe.

**Blue-green** gives an instant, all-at-once switch (a load balancer or Service selector change)
and an equally instant switch back, as long as blue is kept running for a while.

**Canary** limits the **blast radius** (how many users a bad release can hurt): for example 5%, then
25%, then 100%, with **metrics-based promotion**: at each step compare the canary's error rate and
latency against the stable version, and stop or roll back automatically if it is worse. Tools like
Argo Rollouts or Flagger automate this on Kubernetes; a service mesh or ingress does the traffic
split. Without per-version metrics a canary is just a slow rollout.

## Feature flags: deploy is not release

A **feature flag** is a runtime switch around new behaviour:

```java
if (flags.isEnabled("new-pricing", customerId)) {
    return newPricing.quote(cart);
}
return legacyPricing.quote(cart);
```

**Deploy** (code on servers) and **release** (users see it) become separate decisions. You can merge
unfinished work to trunk switched off, enable it for internal users, then 1%, then everyone, and
turn it off in seconds without a deploy: a **kill switch**. The cost is complexity: every flag is a
branch in your code and in your test matrix. Give each flag an owner and remove it once fully
rolled out; stale flags become landmines. Flags can live in a library (Togglz, Unleash, OpenFeature
SDKs) or a hosted service; whatever you choose, decide what happens when the flag service is
unreachable (a safe default).

## Database migrations that allow rollback

Code rolls back in seconds; data does not. During a rolling or canary deploy, old and new code run
against the **same** database, and after a rollback the old code runs against the *migrated* one.
So every migration must work with both versions: **expand, then contract**.

Renaming `customer.phone` to `mobile`:

```text
release 1 (expand)    V7__add_mobile.sql: add nullable column mobile
                      code writes both phone and mobile, reads phone
backfill              copy phone → mobile in batches (not one huge locking UPDATE)
release 2             code reads mobile, still writes both
release 3 (contract)  code stops using phone; V9__drop_phone.sql drops it
```

At every step, the previous release still works, so rolling back one release is safe. Flyway
(`V<n>__name.sql`) or Liquibase (changesets) applies migrations in order and records them; treat
applied migrations as immutable, and never put a destructive change in the same release as the
code that stops needing the old shape.

## Rollback vs roll forward

**Rollback** is redeploying the previous artifact; it is the fastest fix when the change is
self-contained and the schema is compatible. **Roll forward** is shipping a new fix; it is needed
when rollback is impossible (a contract already happened, data already written in a new format) or
the fix is trivial and the pipeline is fast. Decide which applies *before* the release, and make
rollback the default by keeping releases small and migrations expand-only.

## Versions and tags

**Semantic versioning** (semver) is `MAJOR.MINOR.PATCH`: major for breaking changes, minor for
backward-compatible features, patch for fixes. It matters most for libraries and public APIs. A
service deployed many times a day often identifies builds by commit SHA and tags releases
(`git tag -a v1.4.2 -m "..."`, `git push origin v1.4.2`) so you can answer "what is running in
prod" and diff two releases. Never deploy a mutable tag like `latest`.

## Lab (~10 min)

**Part 1: conflict, rebase, bisect.** In an empty folder (Git Bash, macOS or Linux shell):

```bash
git init -b main git-lab && cd git-lab
git config user.name "Lab" && git config user.email lab@example.com
echo "price=100" > config.txt && git add config.txt && git commit -m "Add config"
git switch -c feature/discount
echo "price=90" > config.txt && git commit -am "Apply 10% discount"
git switch main
echo "price=120" > config.txt && git commit -am "Raise price"
git switch feature/discount
git rebase main
```

Expected: `CONFLICT (content): Merge conflict in config.txt` and `could not apply ... Apply 10%
discount`. `cat config.txt` shows:

```text
<<<<<<< HEAD
price=120
=======
price=90
>>>>>>> 1a2b3c4 (Apply 10% discount)
```

During a rebase, `HEAD` is `main`'s side and the bottom is your commit being replayed. Decide:
the discount applies to the new price.

```bash
echo "price=108" > config.txt && git add config.txt
GIT_EDITOR=true git rebase --continue      # keeps the commit message
git log --oneline --graph --all            # linear: Add config, Raise price, Apply 10% discount
git switch main && git merge --ff-only feature/discount
```

Now plant a bug among eight commits and let bisect find it:

```bash
for i in 1 2 3 4 5 6 7 8; do
  if [ $i = 6 ]; then echo "price=0" > config.txt; fi
  echo "note $i" > "note-$i.txt"; git add -A; git commit -qm "Change $i"
done
printf '#!/bin/sh\n! grep -q "price=0" config.txt\n' > ../check.sh   # exit 0 = good
git bisect start HEAD HEAD~8
git bisect run sh ../check.sh
git bisect reset
```

Expected: a few `Bisecting: N revisions left to test` lines, then `<sha> is the first bad commit`
showing `Change 6`. Three tests instead of eight; with 1,000 commits it would be about ten.

Finally, undo it the shared-branch way: `git revert --no-edit <that sha>` and check
`cat config.txt` is back to `price=108` with a new `Revert "Change 6"` commit on top (the revert also removes `note-6.txt`, because it undoes the whole commit).

**Part 2: the pipeline.** In a Spring Boot project with one `*IT` test using Testcontainers, add the
workflow above (change the image name), push a branch and open a PR. Confirm `build` and
`dependency-review` run on the PR and `image` runs only after merge. Then break a test and check the
PR cannot be merged once `build` is a required check.

## Gotchas

- **Rebasing a shared branch.** Rewritten ids break everyone else's copy. Rebase local work only;
  use `git push --force-with-lease`, never plain `--force`, on your own branch.
- **`git reset --hard` on `main`.** Use `git revert` for anything already pushed; `reflog` is the
  rescue for local accidents.
- **Rebuilding per environment.** You ship something you did not test. Build once, tag with the
  SHA, promote the same image.
- **Destructive migration in the same release as the code change.** Rollback then fails. Expand,
  migrate, contract, across separate releases.
- **Canary without per-version metrics.** You cannot tell whether the canary is worse. Label metrics
  by version and automate the comparison.
- **Flags that never die.** Each is a hidden branch and test case. Owner, expiry, cleanup ticket.

## In interviews

Asked as [CI/CD pipeline basics](#/q/ci-cd-pipeline-basics) and
[How do you ensure code quality?](#/q/ensuring-code-quality); it also surfaces inside
[A system failure you handled](#/q/system-failure-and-fault-tolerance-story) and
[A time you failed to do what you were supposed to](#/q/tell-me-about-a-failure), where "how did you
roll back and what did you change in the pipeline" is the expected follow-up.

- **"How do you deploy with zero downtime and roll back safely?"** *What:* rolling or canary, behind
  readiness, with flags. *Inside:* `maxSurge`/`maxUnavailable`, metrics-based promotion, immutable
  SHA-tagged image, expand/contract migrations. *Where:* every release. *What goes wrong:* a
  migration that breaks the old version, dishonest readiness, no per-version metrics.
- **"Merge or rebase?"** Rebase local work for a linear history; never rewrite shared history;
  squash-merge PRs so one revert undoes a feature.

**Follow-up: "Blue-green vs canary?"** Blue-green switches everything at once and back at once, at
double capacity; canary exposes a small slice first and needs traffic splitting and metrics. Both
need a schema that works for old and new.

## Explain it in 2 minutes

*"Walk me through how a change gets to production in your team."*

- Short-lived branch from trunk, small PR, required checks and review.
- CI: build, unit tests, Testcontainers integration tests, static analysis, dependency scan.
- One image tagged with the commit SHA, promoted unchanged through staging to production.
- Config and secrets per environment, injected at run time.
- Rolling or canary deploy gated by readiness and error-rate and latency metrics; risky features
  behind flags with a kill switch.
- Expand/contract migrations so rollback is always possible; revert, not reset, on `main`.

## Check yourself

1. What is a branch, physically, and why does that make trunk-based development cheap?
2. Why is rebasing a pushed, shared branch dangerous?
3. You must undo a bad commit already on `main`. Which command, and why not `reset`?
4. Why must a database migration be compatible with the previous code version?
5. What does a feature flag give you that a canary deploy does not?

### Answers

1. A pointer to one commit. Branches cost nothing to create or delete, so they can live for hours,
   and integrating often keeps conflicts small.
2. Rebase creates new commits with new ids; others' copies reference the old ones, so their history
   diverges and work can be duplicated or lost.
3. `git revert <sha>`: it adds an undo commit, so shared history only grows. `reset` rewrites the
   branch under everyone else.
4. During a rolling deploy both versions run against one database, and after a rollback the old
   version runs against the migrated schema.
5. Release decoupled from deploy: turning a feature on or off per user or percentage, instantly,
   with no new deploy, including a kill switch long after the rollout finished.
