## Where we are

From DB-SQL-1 you can write `SELECT`s and joins, and from JAVA-FUND-4 you know checked exceptions and
try-with-resources. This lesson connects the two: how a Java program actually sends SQL to a database
and gets rows back. That layer is **JDBC**, and every tool you will use later (JdbcTemplate, JPA,
Hibernate, Spring Data) is built on top of it.

## The problem

You have a table and a query that works in a SQL console. Now a Java method has to run it, with a
value that came from an HTTP request:

```java
List<Account> findByOwner(String owner) { ... }   // owner arrives from the user
```

To write that method you need answers to four questions:

1. How do I get a connection to the database, and how much does one cost?
2. How do I pass `owner` into the SQL *safely*?
3. How do I make two updates succeed or fail together?
4. What happens when 200 requests all want a connection at the same moment?

JDBC answers the first three. A connection pool answers the fourth.

## JDBC: one API, many drivers

**JDBC** (Java Database Connectivity) is a set of interfaces in `java.sql` and `javax.sql`:
`Connection`, `PreparedStatement`, `ResultSet`, `DataSource` and a few more. The JDK ships only the
interfaces. A **driver** is a jar from the database vendor (PgJDBC for Postgres, `mysql-connector-j`
for MySQL, H2 for the in-memory database used in the lab) that implements them and speaks that
database's wire protocol.

```text
your code ──► java.sql interfaces ──► driver (PgJDBC) ──TCP──► Postgres server
```

**The rule:** code against the interfaces only. Swapping Postgres for H2 in a test then means
changing a URL and a jar, not your code (SQL dialect differences aside).

## DriverManager versus DataSource

The oldest way to get a connection is a static call:

```java
Connection c = DriverManager.getConnection("jdbc:postgresql://localhost:5432/bets", "app", secret);
```

That opens a brand-new **physical connection** every time: a TCP handshake, often TLS, authentication,
and on Postgres a new server process. That is easily milliseconds per call, which is longer than many
queries take.

A **`DataSource`** is an interface for "something that hands out connections":

```java
DataSource ds = ...;                 // configured once, injected everywhere
try (Connection c = ds.getConnection()) { ... }
```

Your code looks the same, but *what* sits behind the interface is a deployment decision. It can open a
fresh connection each time, or, far more commonly, lend you one from a **pool**. In Spring Boot you
never call `DriverManager`; Boot builds a `DataSource` bean from `spring.datasource.*` properties and
injects it.

**The rule:** application code depends on `DataSource`, never on `DriverManager`. Use `DriverManager`
only in a throwaway script.

## Connection, PreparedStatement, ResultSet

Three objects, each of which holds a resource that must be closed:

```java
record Account(long id, String owner, long balance) {}

List<Account> findByOwner(DataSource ds, String owner) throws SQLException {
    String sql = "SELECT id, owner, balance FROM account WHERE owner = ?";
    try (Connection c = ds.getConnection();
         PreparedStatement ps = c.prepareStatement(sql)) {
        ps.setString(1, owner);                       // parameter indexes start at 1
        try (ResultSet rs = ps.executeQuery()) {
            List<Account> out = new ArrayList<>();
            while (rs.next()) {                       // cursor starts BEFORE the first row
                out.add(new Account(rs.getLong("id"), rs.getString("owner"), rs.getLong("balance")));
            }
            return out;
        }
    }
}
```

- A **`Connection`** is one session with the database. Transactions live on it.
- A **`PreparedStatement`** is SQL with `?` placeholders, sent once and then filled with values.
- A **`ResultSet`** is a cursor over the returned rows. `next()` moves to the next row and returns
  `false` when there are none.

try-with-resources closes them in reverse order (ResultSet, statement, connection), even when an
exception is thrown. Before Java 7 this took three nested `finally` blocks, and leaked connections were
one of the most common production bugs in Java.

Two small traps: `getLong` returns `0` for a SQL `NULL`, so call `rs.wasNull()` or use
`rs.getObject("col", Long.class)` when the column is nullable. And `executeQuery` is for `SELECT`;
`executeUpdate` is for `INSERT`/`UPDATE`/`DELETE` and returns the number of rows changed.

## SQL injection, and why PreparedStatement stops it

Here is the version people write before they know better:

```java
String sql = "SELECT id, owner, balance FROM account WHERE owner = '" + owner + "'";
ResultSet rs = conn.createStatement().executeQuery(sql);
```

Send `owner` = `x' OR '1'='1` and the database receives:

```sql
SELECT id, owner, balance FROM account WHERE owner = 'x' OR '1'='1'
```

Every account comes back. With a different payload an attacker can read other tables or, on drivers
that allow several statements in one call, modify data. This is **SQL injection**: user input changes
the *structure* of the query because it was pasted into the SQL text.

With `PreparedStatement`, the SQL text with `?` is fixed when you call `prepareStatement`. The value is
sent separately as data and is never parsed as SQL. `x' OR '1'='1` is just an odd owner name that
matches nobody. (Some drivers do substitute values client-side, but they escape them correctly; the
guarantee is the same.)

**The rule:** every value that comes from outside goes through a `?` placeholder. Two limits to know:

- Placeholders work only for **values**. You cannot write `ORDER BY ?` or `FROM ?` for a column or
  table name. For a user-chosen sort column, map the input to an allow-list
  (`Map.of("balance", "balance", "owner", "owner")`) and reject anything else.
- `LIKE ?` is safe from injection, but the user can still send `%` to match everything. Escape `%` and
  `_` if that matters.

## Autocommit and transactions

A **transaction** is a group of statements that either all take effect or none do. A new JDBC
connection is in **autocommit** mode: each statement is its own transaction and commits as soon as it
finishes. That is wrong for a money transfer:

```text
UPDATE account SET balance = balance - 50 WHERE id = 1;   -- committed
-- the app crashes here
UPDATE account SET balance = balance + 50 WHERE id = 2;   -- never runs; 50 has vanished
```

Turn autocommit off and decide the outcome yourself:

```java
void transfer(DataSource ds, long from, long to, long amount) throws SQLException {
    try (Connection c = ds.getConnection()) {
        c.setAutoCommit(false);                                     // transaction starts
        try (PreparedStatement debit = c.prepareStatement("UPDATE account SET balance = balance - ? WHERE id = ?");
             PreparedStatement credit = c.prepareStatement("UPDATE account SET balance = balance + ? WHERE id = ?")) {
            debit.setLong(1, amount);
            debit.setLong(2, from);
            debit.executeUpdate();
            credit.setLong(1, amount);
            credit.setLong(2, to);
            credit.executeUpdate();
            c.commit();                                             // both, or ...
        } catch (SQLException | RuntimeException e) {
            c.rollback();                                           // ... neither
            throw e;
        }
    }
}
```

**The rule:** a transaction belongs to one `Connection`. Both statements must run on the *same*
connection, between `setAutoCommit(false)` and `commit()`/`rollback()`. Catch `RuntimeException` too,
not only `SQLException`: a bug between the two updates must also roll back. And never swallow the
exception after rolling back; the caller needs to know the transfer failed.

This "same connection" rule is the entire secret of Spring's `@Transactional`, coming in
SPRING-BOOT-7. Spring's transaction manager takes a connection, turns autocommit off, binds the
connection to the current thread, and every JDBC or JPA call inside the method finds and reuses that
bound connection. What isolation level the transaction runs at, and what locks it takes, is
DB-SQL-7.

## Batch updates

Inserting 1,000 rows with 1,000 `executeUpdate()` calls means 1,000 network round trips. A **batch**
queues statements on the client and sends them together:

```java
try (PreparedStatement ps = c.prepareStatement("INSERT INTO bet(account_id, stake) VALUES (?, ?)")) {
    for (Bet b : bets) {
        ps.setLong(1, b.accountId());
        ps.setLong(2, b.stake());
        ps.addBatch();                 // queue, don't send
    }
    int[] counts = ps.executeBatch();  // one (or a few) round trips
}
```

Run large batches inside a transaction (autocommit off) so a failure halfway doesn't leave half the rows
committed, and flush every few hundred or thousand rows so the client doesn't hold everything in memory.
DB-SQL-8 shows driver flags that make batches even faster.

## Why connection pools exist

Physical connections are slow to open and expensive for the database to hold (on Postgres each one is
a server process with its own memory). A web app, meanwhile, needs a connection for a few milliseconds
per request, thousands of times a second. The fix is a **connection pool**: open a fixed number of
connections once, lend one to each request, and take it back afterwards.

```text
request threads          HikariCP pool (max 10)          database
  T1 ──borrow──►  [c1][c2][c3]...[c10]  ◄── 10 long-lived connections ──► Postgres
  T1 ◄─return───  close() does NOT disconnect; it returns c1 to the pool
  T11 waits in a queue up to connectionTimeout, then gets an exception
```

The `Connection` the pool gives you is a wrapper. Calling `close()` on it returns the real connection to
the pool. That is why try-with-resources matters even more with a pool: forget to close and the
connection is never returned. After ten such leaks the pool is empty and every request times out.

The analogy is a library lending books: borrowing is fast, but an unreturned book is gone for everyone.
It breaks in one place: a returned connection can carry state (autocommit off, a changed isolation
level, an open transaction). HikariCP resets the common settings and rolls back unfinished work on
return, but your code should leave the connection clean anyway.

## HikariCP: the settings that matter

**HikariCP** is Spring Boot's default pool. Configure it under `spring.datasource.hikari`:

```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/bets
    username: app
    password: ${DB_PASSWORD}
    hikari:
      maximum-pool-size: 10       # hard cap on connections (default 10)
      connection-timeout: 2000    # ms to wait for a free connection (default 30000)
      max-lifetime: 1500000       # ms before a connection is retired (default 30 min)
      idle-timeout: 600000        # ms an idle extra connection may live (only if minimum-idle < max)
      leak-detection-threshold: 20000   # log a stack trace if a connection is held > 20 s
```

- **`maximumPoolSize`**: the most connections the pool will ever open. Threads beyond this wait.
- **`minimumIdle`**: HikariCP recommends leaving it unset, which makes it equal to the maximum: a
  fixed-size pool with no ramp-up delay under a sudden spike.
- **`connectionTimeout`**: how long a thread waits for a free connection before
  `SQLTransientConnectionException`. The 30-second default means an exhausted pool shows up as
  30-second requests piling up. One or two seconds fails fast and lets you return a 503.
- **`maxLifetime`**: retire each connection after this long. Set it a little *shorter* than any idle
  cut-off in a firewall, load balancer or the database, so the pool closes connections before the
  network silently kills them.
- **`idleTimeout`**: only matters when `minimumIdle` is below the maximum; extra idle connections are
  closed after this.
- **`leakDetectionThreshold`**: off by default. Turn it on in lower environments to find code that
  forgets to close.

## Pool sizing intuition

The instinct is "more traffic, bigger pool". Usually wrong. Two facts:

1. **Little's law.** Connections busy on average = requests per second × seconds each request holds a
   connection. 500 requests/s × 10 ms = 5 connections busy.
2. **The database has a fixed number of CPU cores.** It cannot run 200 queries at once on 8 cores; they
   take turns, and each gets slower. HikariCP's sizing guide suggests starting near
   `(cores × 2) + effective disk spindles` connections and measuring from there.

And the pool is per application instance: 20 pods × 10 = 200 connections against one database's
`max_connections`. When the pool is exhausted, the fix is almost always to hold connections for less
time (shorter transactions, no HTTP calls inside them), not to add connections. DB-SQL-8 returns to this
with a full diagnosis walkthrough.

## JdbcTemplate and JdbcClient

Raw JDBC is verbose and throws checked `SQLException` everywhere. Spring wraps it:

```java
@Repository
class AccountRepository {
    private final JdbcClient jdbc;                     // auto-configured by Boot 3.2+

    AccountRepository(JdbcClient jdbc) { this.jdbc = jdbc; }

    Optional<Account> find(long id) {
        return jdbc.sql("SELECT id, owner, balance FROM account WHERE id = :id")
                   .param("id", id)
                   .query(Account.class)               // maps columns to the record's components
                   .optional();
    }

    int credit(long id, long amount) {
        return jdbc.sql("UPDATE account SET balance = balance + :amt WHERE id = :id")
                   .param("amt", amount).param("id", id)
                   .update();
    }
}
```

- **`JdbcTemplate`** (since Spring's early days) and the fluent **`JdbcClient`** (Spring Framework 6.1)
  do the boilerplate: borrow and close the connection, prepare the statement, iterate the `ResultSet`.
- They translate `SQLException` into Spring's unchecked **`DataAccessException`** hierarchy, for
  example `DuplicateKeyException`. That is the JAVA-FUND-4 idea in practice: a specific, unchecked
  exception the caller can choose to handle.
- They take part in Spring transactions automatically, by reusing the connection bound to the thread.

Underneath, it is still exactly the `Connection` / `PreparedStatement` / `ResultSet` code above. So is
JPA: Hibernate generates SQL and runs it through a `PreparedStatement` on a pooled connection.

## Lab (~10 min)

Plain Java 21, no Spring. Dependencies: `com.h2database:h2` and `com.zaxxer:HikariCP`.

```java
import com.zaxxer.hikari.HikariConfig;
import com.zaxxer.hikari.HikariDataSource;
import java.sql.*;
import javax.sql.DataSource;

public class JdbcLab {

    public static void main(String[] args) throws Exception {
        HikariConfig cfg = new HikariConfig();
        cfg.setJdbcUrl("jdbc:h2:mem:lab;DB_CLOSE_DELAY=-1");
        cfg.setUsername("sa");
        cfg.setPassword("");
        cfg.setMaximumPoolSize(2);
        cfg.setConnectionTimeout(1_000);
        try (HikariDataSource ds = new HikariDataSource(cfg)) {
            try (Connection c = ds.getConnection(); Statement s = c.createStatement()) {
                s.execute("CREATE TABLE account(id BIGINT PRIMARY KEY, owner VARCHAR(50), balance BIGINT)");
                s.execute("INSERT INTO account VALUES (1, 'akhil', 100), (2, 'ravi', 100)");
            }
            // 1. Injection: concatenation vs placeholder
            String evil = "x' OR '1'='1";
            try (Connection c = ds.getConnection(); Statement s = c.createStatement();
                 ResultSet rs = s.executeQuery("SELECT COUNT(*) FROM account WHERE owner = '" + evil + "'")) {
                rs.next();
                System.out.println("concatenated rows: " + rs.getInt(1));
            }
            try (Connection c = ds.getConnection();
                 PreparedStatement ps = c.prepareStatement("SELECT COUNT(*) FROM account WHERE owner = ?")) {
                ps.setString(1, evil);
                try (ResultSet rs = ps.executeQuery()) {
                    rs.next();
                    System.out.println("prepared rows: " + rs.getInt(1));
                }
            }
            // 2. Transaction: fail between debit and credit
            try {
                transfer(ds, 1, 2, 50, true);
            } catch (IllegalStateException e) {
                System.out.println("transfer failed: " + e.getMessage());
            }
            printBalances(ds);
            // 3. Pool exhaustion: hold both connections, ask for a third
            try (Connection a = ds.getConnection(); Connection b = ds.getConnection()) {
                long start = System.nanoTime();
                try (Connection third = ds.getConnection()) {
                    System.out.println("unexpected: got a third connection");
                } catch (SQLTransientConnectionException e) {
                    System.out.printf("pool exhausted after %d ms: %s%n",
                            (System.nanoTime() - start) / 1_000_000, e.getMessage());
                }
            }
        }
    }

    static void transfer(DataSource ds, long from, long to, long amount, boolean crash) throws SQLException {
        try (Connection c = ds.getConnection()) {
            c.setAutoCommit(false);
            try (PreparedStatement debit = c.prepareStatement("UPDATE account SET balance = balance - ? WHERE id = ?");
                 PreparedStatement credit = c.prepareStatement("UPDATE account SET balance = balance + ? WHERE id = ?")) {
                debit.setLong(1, amount);
                debit.setLong(2, from);
                debit.executeUpdate();
                if (crash) {
                    throw new IllegalStateException("simulated crash between debit and credit");
                }
                credit.setLong(1, amount);
                credit.setLong(2, to);
                credit.executeUpdate();
                c.commit();
            } catch (SQLException | RuntimeException e) {
                c.rollback();
                throw e;
            }
        }
    }

    static void printBalances(DataSource ds) throws SQLException {
        try (Connection c = ds.getConnection();
             PreparedStatement ps = c.prepareStatement("SELECT id, balance FROM account ORDER BY id");
             ResultSet rs = ps.executeQuery()) {
            while (rs.next()) {
                System.out.println("account " + rs.getLong("id") + " = " + rs.getLong("balance"));
            }
        }
    }
}
```

**Observe:**

- The concatenated query counts **2** rows; the prepared one counts **0**.
- After the failed transfer both balances are still 100: the rollback undid the debit.
- The third `getConnection()` waits about one second, then throws `SQLTransientConnectionException`.
- **Break it:** delete `c.setAutoCommit(false);` and the `c.rollback();` line. Run again: account 1
  now shows 50 and account 2 shows 100. Money vanished, exactly as in the autocommit diagram.
- **Bonus:** insert 10,000 rows into `account` twice, once with one `executeUpdate()` per row and once
  with `addBatch()` plus a single `executeBatch()`, both inside a transaction, and time each.

## Gotchas

- **Concatenating input into SQL.** Always use `?` placeholders; allow-list identifiers such as sort
  columns, which cannot be parameterised.
- **Not closing a pooled connection.** It is never returned, and a few leaks empty the pool. Use
  try-with-resources and enable `leakDetectionThreshold` outside production.
- **Two statements on two connections "in one transaction".** A transaction lives on one `Connection`.
  Calling `ds.getConnection()` twice gives you two independent transactions.
- **Rolling back only on `SQLException`.** A `RuntimeException` between statements also needs a
  rollback, and the exception must be rethrown, not swallowed.
- **Fixing pool exhaustion by raising `maximumPoolSize`.** Find what holds connections too long first;
  more connections usually make the database slower.
- **Default `connectionTimeout` of 30 s.** An exhausted pool then looks like a slow service. Lower it
  so the failure is fast and visible.

## In interviews

Typical prompts: "Walk me through what happens when Java runs a query", "How do you prevent SQL
injection?", "What is a connection pool and how would you size it?", "How do you do a transaction in
plain JDBC?", and code-review exercises with a leaking connection. Bank:
[Preventing SQL Injection](#/q/sql-injection-prevention),
[Connection Pooling and the DB Connection Process](#/q/jdbc-connection-pooling),
[Code review: Java/SQL connection snippet](#/q/review-jdbc-connection-code),
[What is JdbcTemplate and how do you use it?](#/q/spring-jdbctemplate).

A strong answer comes in four layers. For "Why use a connection pool?":

1. **What:** a fixed set of open connections that threads borrow and return, instead of opening one
   per request.
2. **How it works inside:** the pool hands out a proxy `Connection`; `close()` returns the real one;
   waiting threads queue up to `connectionTimeout`; connections are retired after `maxLifetime`.
3. **Where used:** every Spring Boot app through HikariCP; JdbcTemplate and Hibernate both borrow from
   it; a transaction holds one connection from begin to commit.
4. **What goes wrong:** leaks from unclosed connections, long transactions or remote calls inside a
   transaction exhausting the pool, too many connections across many pods overloading the database,
   and connections killed by a firewall when `maxLifetime` is too long.

**Follow-up: "Your service logs `Connection is not available, request timed out after 30000ms`."**
Say what holds connections: slow queries, long transactions, an HTTP call inside `@Transactional`, or a
leak. Check Hikari's active/pending metrics and leak detection, fix the holder, then lower
`connectionTimeout` so it fails fast. Raise the pool size last, and only after checking the database's
total connections.

**Follow-up: "Does an ORM make you immune to SQL injection?"** No. JPA parameters (`:name`) are safe, but
string-concatenated JPQL or native queries are just as injectable as raw JDBC.

## Explain it in 2 minutes

*"How does a Spring Boot app talk to Postgres, from `DataSource` to rows?"*

- JDBC is a set of interfaces; the vendor driver implements them over the wire protocol.
- Boot builds a HikariCP `DataSource`; code borrows a `Connection` and `close()` returns it to the pool.
- SQL goes through a `PreparedStatement`: fixed SQL with `?`, values sent separately, which prevents
  injection. Results come back through a `ResultSet` cursor.
- A transaction is autocommit off, statements on the same connection, then commit or rollback.
  `@Transactional` automates exactly that by binding the connection to the thread.
- Batching cuts round trips; pool size follows Little's law and database cores, not traffic alone.
- JdbcTemplate, JdbcClient and Hibernate all sit on top of this same layer.

## Check yourself

1. Why should application code depend on `DataSource` rather than `DriverManager`?
2. Why does `PreparedStatement` prevent SQL injection, and what can it *not* parameterise?
3. You call `ds.getConnection()` once for the debit and once for the credit, with autocommit off on
   both, and commit both. What guarantee have you lost?
4. What does `close()` do on a connection from HikariCP?
5. The pool is exhausted under load. Name two causes that are not "the pool is too small".

### Answers

1. `DataSource` is an injected abstraction that is usually backed by a pool; `DriverManager` opens a
   new, expensive physical connection on every call and hard-codes connection details.
2. The SQL structure is fixed when the statement is prepared and values travel as data, never parsed
   as SQL. It cannot parameterise identifiers such as table names, column names or `ORDER BY` targets;
   allow-list those.
3. Atomicity. They are two separate transactions; a crash between the two commits leaves one applied
   and not the other.
4. It returns the underlying physical connection to the pool (after resetting state and rolling back
   uncommitted work); it does not disconnect.
5. Connections held too long (slow queries, long transactions, remote calls inside a transaction) and
   leaks from code that never closes connections. Also: many instances multiplying the total.
