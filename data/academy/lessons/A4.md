## Where we are

From A2 you know every object lives on the shared heap, split into a young generation (eden + two
survivor spaces) and an old generation, and that running out gives `OutOfMemoryError: Java heap
space`. This lesson answers how the JVM frees heap memory by itself: how it decides what is
garbage, why the young/old split exists, and how the four main collectors differ.

## The problem

In C you call `free()` yourself. Forget, and memory leaks; free too early, and another part of the
program reads memory that now belongs to something else. Both bugs are common and hard to find.

Java removes `free()`. Instead, a **garbage collector (GC)** finds objects the program can no
longer use and reclaims their memory. That raises two hard questions, which the rest of this
lesson answers in order:

1. **Which** objects are garbage?
2. **How** do we reclaim them without freezing the application for long?

## Which objects are garbage: reachability

```java
void handle() {
    Order a = new Order();      // object #1
    Order b = new Order();      // object #2
    a.next = b;
    b = null;                   // #2 still reachable through a.next
    a = null;                   // now neither #1 nor #2 can be reached from anywhere
}
```

The rule the JVM uses is **reachability**: an object is alive if it can be reached by following
references starting from a **GC root**. Everything else is garbage, no matter what it points to.

**GC roots** are references the JVM knows are in use without looking at the heap:

- local variables and parameters in every thread's active stack frames,
- static fields of loaded classes,
- references held by native (JNI) code,
- live threads themselves, and objects used as locks by `synchronized` that is currently held.

```text
 ROOTS                       HEAP
 main() frame: cart ───────► Cart ──► Item ──► Price         reachable: kept
 static CACHE  ────────────► Map  ──► Entry
                                     Order ◄──► Payment      a cycle, but no root
                                                             reaches it: garbage
```

Notice the cycle. Java does **not** count references (as C++ `shared_ptr` does), so
two objects pointing at each other are still collected once nothing reachable points at them.

**Rule:** "alive" means "reachable from a root", not "has references to it". A leak in Java is an
object that is still reachable but that you will never use again.

## How a GC reclaims memory: mark, then sweep, compact or copy

Almost every collector starts by **marking**: walk the object graph from the roots and flag
every object reached. Then it reclaims the unmarked space in one of three ways:

| Technique | What it does | Good | Bad |
|---|---|---|---|
| **Sweep** | add dead objects' space to a free list | no moving | heap becomes fragmented |
| **Compact** | slide live objects together | no fragmentation | slow: touches everything, fixes every reference |
| **Copy** | copy live objects to an empty area, then treat the old area as empty | cost depends only on *live* objects; result is compact | needs spare space to copy into |

Keep the last row in mind: copying is cheap when **few** objects survive.

## Stop-the-world pauses

Moving an object while the application is reading it would be a disaster, so the simplest
collectors **stop the world**: every application thread is halted at a *safepoint* (a point in the
code where the JVM knows exactly where all references are), the GC works, and then the threads
resume. That halt is a **GC pause**.

Pauses are what users feel: a 300 ms pause turns a 20 ms request into a 320 ms one, and shows up
in your p99 latency. Much of GC history is about shrinking or eliminating pauses.

## The generational idea

Measure real programs and a pattern appears: **most objects die young**. Request DTOs, iterators,
temporary strings and lambdas live for microseconds. A few objects (caches, connection pools,
Spring beans) live for hours. This observation is called the **weak generational hypothesis**.

So split the heap and collect the young part often, with copying, which is cheap when almost
everything is dead:

```text
           new objects
               │
               ▼
 ┌───────────────────────────┬───────┬───────┐   ┌──────────────────────────┐
 │           EDEN            │  S0   │  S1   │   │           OLD            │
 └───────────────────────────┴───────┴───────┘   └──────────────────────────┘
  minor GC: copy live objects from eden + one     survivors that reach the
  survivor into the other survivor; age += 1      age threshold are PROMOTED
  eden is then empty again in one step            here; collected rarely
```

- A **minor (young) GC** runs when eden fills. Live objects are copied to the empty survivor
  space and their *age* goes up by one; eden and the other survivor are then simply empty.
- An object that survives enough minor GCs (the *tenuring threshold*, at most 15, because age is
  stored in 4 bits of the object header) is **promoted** to the old generation.
- The **old generation** fills slowly and is collected far less often, by a major or full
  collection.

One subtlety: an old object can point at a young one. To find those without scanning the whole
old generation on every minor GC, the JVM records which parts of the old generation were written
to (a *card table* / *remembered set*) and treats those as extra roots.

**Rule:** young collections are frequent, short and proportional to what *survives*. Trouble
starts when too much survives and gets promoted.

## Three goals you cannot all max out

Every collector trades between:

- **Throughput**: share of CPU time spent running your code rather than GC.
- **Latency**: how long the longest pauses are.
- **Footprint**: how much extra memory (and CPU) the GC needs.

Doing GC work *concurrently* (while the app runs) cuts pauses but costs CPU and memory for
bookkeeping. That is the trade-off behind the four collectors below.

## The collectors

**Serial** (`-XX:+UseSerialGC`): one GC thread, stop-the-world for both young and old.
Smallest overhead. Good for small heaps and containers with a single CPU. The JVM picks it
automatically when it sees fewer than 2 CPUs or less than about 1.8 GB of memory.

**Parallel** (`-XX:+UseParallelGC`): the same stop-the-world design, but using all cores. Best
raw throughput; pauses grow with heap size. Good for batch jobs where total run time matters and
nobody waits on a single request.

**G1, Garbage-First** (`-XX:+UseG1GC`, the default since Java 9 on most machines): the heap is cut
into many equal-sized **regions** (typically 1–32 MB each), each tagged eden, survivor, old or *humongous*.

- Young collections are still stop-the-world copies, but only of the young regions.
- The old generation is *marked concurrently* while the app runs. G1 then reclaims the old regions
  with the most garbage first (hence the name) during **mixed** collections, a few regions at a
  time, to stay within a pause-time goal (`-XX:MaxGCPauseMillis`, default 200 ms; a target, not a
  promise).
- Objects of half a region or more are **humongous** and go straight into dedicated old regions.
- If concurrent work cannot keep up, G1 falls back to a slow **full GC** of the whole heap.

Good default for typical services with heaps from a few hundred MB to tens of GB.

**ZGC** (`-XX:+UseZGC`, production-ready since Java 15): does marking *and* moving objects
concurrently, using *load barriers* (a small check the JIT adds whenever a reference is loaded
from the heap, which fixes up references to moved objects) and metadata bits stored in the
pointers themselves. Pauses do not grow with heap size and are typically well under a
millisecond. Costs: more CPU and memory headroom. Versions matter:

- Java 21: generational ZGC is available with `-XX:+UseZGC -XX:+ZGenerational`; plain `-XX:+UseZGC`
  is still the single-generation version.
- Java 23: generational became the default mode.
- Java 24 onward: the single-generation mode was removed.

Good for latency-sensitive services and large heaps. (**Shenandoah**, from Red Hat and included in
many OpenJDK builds, has similar goals. **Epsilon** is a no-op collector for testing that never
frees anything.)

## Choosing

```text
 Single CPU or tiny heap (CLI, small container) ........ Serial
 Batch / offline, maximise total throughput ............ Parallel
 General web service, no special requirement ........... G1 (the default: start here)
 Tight tail latency, or very large heap ................ ZGC (generational)
```

Start with the default, turn on GC logging, and change collector only when the logs show a
problem the change addresses. Most "GC problems" are allocation or retention problems in the code.

## Lab (~10 min)

`Churn.java` allocates lots of short-lived 1 KB arrays and keeps 1% of them alive for a while:

```java
import java.util.ArrayDeque;
import java.util.Deque;

public class Churn {
    public static void main(String[] args) {
        Deque<byte[]> keep = new ArrayDeque<>();      // a few long-lived objects
        long start = System.nanoTime();
        for (int i = 0; i < 2_000_000; i++) {
            byte[] temp = new byte[1024];             // dies almost immediately
            if (i % 100 == 0) {
                keep.addLast(temp);                   // 1% survive for a while
                if (keep.size() > 5_000) keep.removeFirst();
            }
        }
        System.out.printf("done in %d ms, kept %d%n",
                (System.nanoTime() - start) / 1_000_000, keep.size());
    }
}
```

Compile once (`javac Churn.java`), then run each collector with unified GC logging:

```text
java -XX:+UseSerialGC   -Xmx256m -Xlog:gc Churn
java -XX:+UseParallelGC -Xmx256m -Xlog:gc Churn
java -XX:+UseG1GC       -Xmx256m -Xlog:gc Churn
java -XX:+UseZGC -XX:+ZGenerational -Xmx256m -Xlog:gc* Churn
```

Read one line (from a real G1 run):

```text
[0.110s][info][gc] GC(1) Pause Young (Normal) (G1 Evacuation Pause) 39M->1M(246M) 1.356ms
   │                 │     │                                        │    │   │      └ pause length
   │                 │     │                                        │    │   └ committed heap
   │                 │     └ kind of collection and why             │    └ heap used after
   │                 └ GC sequence number                           └ heap used before
   └ time since JVM start
```

What to notice:

- Serial and Parallel log `Pause Young (Allocation Failure)`: eden filled up.
- "Before → after" drops sharply (for example 39M → 1M): almost everything was dead, exactly the
  generational hypothesis.
- With ZGC and `-Xlog:gc*`, find lines containing `Pause`: they are in the tens of
  *microseconds*, with the real work done concurrently.
- Add `-Xlog:gc+age=trace` to the G1 run to see the age table: bytes at age 1, 2, 3... as
  survivors are copied back and forth.

Numbers differ per machine; compare shapes, not values.

## Gotchas

- **Java does not leak through cycles**, but it does leak through *reachable* garbage: static
  maps, caches without eviction, listeners never removed. (A5 hunts these.)
- **`System.gc()` is a request**, often triggering a full, stop-the-world collection. Don't call
  it in production code; `-XX:+DisableExplicitGC` exists for libraries that do.
- **A one-CPU container silently gets Serial GC.** If you meant G1, request at least 2 CPUs or set
  the collector explicitly.
- **Bigger heap is not automatically better**: fewer collections, but with stop-the-world
  collectors each full GC takes longer.
- **Large arrays in G1 are humongous** and can cause premature old-gen growth or full GCs. Watch
  for `Humongous` in logs; a larger `-XX:G1HeapRegionSize` or smaller buffers help.
- **Tune from logs, not folklore.** Flags copied from old blog posts (CMS settings, PermGen flags)
  are often removed or harmful on Java 21. CMS itself was removed in Java 14.

## Explain it in 2 minutes

Prompt: "Explain Java garbage collection to a C++ developer."

- Liveness is reachability from GC roots (stack frames, statics, JNI, threads); cycles are fine.
- Collectors mark live objects, then sweep, compact or copy; copying costs only live objects.
- Weak generational hypothesis: most objects die young, so a young generation is collected often
  by copying; survivors age and get promoted to old.
- Stop-the-world pauses are the cost; concurrent collectors trade CPU and memory to shrink them.
- Serial (tiny), Parallel (throughput), G1 (default, region-based, pause target), ZGC
  (concurrent, sub-millisecond pauses; generational default from Java 23).

## Check yourself

1. Two objects reference only each other and nothing else references them. Are they collected?
2. Why is copying collection a good fit for the young generation?
3. What is promotion, and what limits the maximum tenuring age to 15?
4. Your service runs in a container with 1 CPU and 1 GB. Which collector will the JVM pick by
   default?
5. What does `Pause Young (Normal) (G1 Evacuation Pause) 147M->5M(247M) 1.863ms` tell you?

### Answers

1. Yes. They are unreachable from any GC root; tracing collectors ignore reference counts.
2. Its cost is proportional to the live objects, and almost everything in eden is dead.
3. Moving an object that survived enough minor GCs into the old generation. The age is stored in
   4 bits of the header, so 15 is the maximum.
4. Serial: with fewer than 2 CPUs (or under about 1.8 GB) the JVM does not consider the machine
   "server class".
5. A stop-the-world young collection in G1; heap use went from 147 MB to 5 MB, out of 247 MB
   committed, and the pause took about 1.9 ms. Most young objects were dead.
