## Where we are

In D1 you built a container that finds `@Component` classes, resolves constructor parameters by
type through reflection, caches singletons and catches cycles. This lesson puts real Spring in
its place. The core loop is the same as yours. What Spring adds is a separate *recipe* step,
more than one way to declare beans, more scopes, and a way to change the wiring per environment
without touching code.

## The problem

Your D1 container had three limits that matter in a real app:

1. **It only managed classes you wrote.** You cannot put `@Component` on a JDK class such as
   `Clock` or on a library's `DataSource`, so the container had no way to manage them.
2. **"Singleton or new each time" was the only choice.** Web apps also need "one per HTTP
   request" and "one per user session".
3. **Swapping implementations meant editing code.** You want a fake payment gateway on your
   laptop and the real one in production, with the same code.

Spring answers these with `@Bean` methods, scopes, and profiles plus the `Environment`.

## Bean definitions: the recipe comes first

Spring does not jump straight from a class to an object. It first reads a **bean definition**
for every bean: the recipe, which records the class or factory method, the scope, whether the
bean is lazy, any init and destroy methods, and so on. Only after all the recipes are loaded
does it create objects.

```text
 @Component classes ─┐
 @Bean methods ──────┼──► BeanDefinitionRegistry ──► create beans ──► singleton cache
 XML (legacy) ───────┘       (recipes only)          (instantiate,       (getBean)
                                                       inject, init)
```

Why bother with two steps? Because it means the recipes can be inspected and *changed* before
any object exists. Spring Boot relies on this heavily (D4), and so does any code that adds or
edits definitions at start-up (D9).

## Two ways to declare a bean

**Component scanning** is the D1 approach, done automatically. `@ComponentScan` walks a package
on the classpath and registers every class annotated with `@Component`, `@Service`,
`@Repository` or `@Controller`.

**`@Bean` methods** cover classes you cannot annotate. A method in a `@Configuration` class
returns the object, and Spring registers whatever it returns:

```java
@Configuration
class AppConfig {
    @Bean
    Clock clock() { return Clock.systemDefaultZone(); }
}
```

This repo's own `CompanyWisePrepApplication` does exactly this, so that tests can pin "today".
The parameters of a `@Bean` method are injected just like constructor parameters.

The rule: **use `@Component` for your own classes and `@Bean` for third-party objects, or when
building the object takes logic.**

## BeanFactory vs ApplicationContext

`BeanFactory` is the basic container interface: `getBean`, plus the creation and caching loop
from D1. It creates beans **lazily**, on the first `getBean`.

`ApplicationContext` extends `BeanFactory` and adds what an application needs:

| | BeanFactory | ApplicationContext |
|---|---|---|
| Creates singletons | on first request | all at start-up, in `refresh()` |
| Runs annotation processing (`@Autowired`, `@PostConstruct`) automatically | no, you register the processors yourself | yes |
| Environment, profiles, properties | not on its own | yes |
| Events, i18n messages, resource loading | no | yes |

Creating singletons at start-up is a deliberate choice: a missing bean or bad configuration
crashes the app at launch instead of at 3 a.m. on the first request. In practice you always use
an `ApplicationContext`. Spring Boot creates one for you, and `BeanFactory` is the engine inside
it.

## Constructor injection and choosing between candidates

As in D1, a class with a single constructor is autowired without needing `@Autowired`:

```java
@Service
class CheckoutService {
    private final PaymentGateway gateway;
    CheckoutService(PaymentGateway gateway) { this.gateway = gateway; }
}
```

When two beans match a type, Spring fails with `NoUniqueBeanDefinitionException`. There are
three ways to resolve it:

- **`@Primary`** on one bean makes it the default choice.
- **`@Qualifier("stripe")`** on the injection point names the bean you want.
- **Inject all of them** with `List<PaymentGateway>` or `Map<String, PaymentGateway>`, where the
  map key is the bean name. This is the usual way to write a strategy or plugin registry.

Field injection (`@Autowired` on a field) still works, but it hides dependencies and stops the
field being `final`. Prefer constructors.

## Scopes

A **scope** decides how long one bean instance lives and who shares it.

| Scope | One instance per… | Typical use |
|---|---|---|
| `singleton` (default) | container | services, repositories (stateless) |
| `prototype` | `getBean` call or injection | stateful helper objects |
| `request` | HTTP request (web apps only) | request-scoped context |
| `session` | HTTP session (web apps only) | user cart (rare today) |

**The trap from D1 is the same in Spring.** If you inject a prototype into a singleton, the
singleton gets exactly one instance, at the moment it is built. To get a fresh instance each
time, inject an **`ObjectProvider<T>`** and call `getObject()` when you need one. Scoped proxies
are the other fix: `request` and `session` beans are normally injected through one, because
there is no request in progress while the singleton is being built.

Singletons are shared across threads, so **a singleton must not hold per-request state in
fields.** That is a concurrency bug waiting to happen.

## Profiles: different beans per environment

A **profile** is a named switch such as `dev` or `prod`. A bean marked `@Profile("prod")` is
registered only when that profile is active.

```java
@Bean @Profile("!prod") PaymentGateway fakeGateway() { ... }   // anything except prod
@Bean @Profile("prod")  PaymentGateway realGateway() { ... }
```

You activate profiles with the property `spring.profiles.active=prod`, for example
`-Dspring.profiles.active=prod` or the environment variable `SPRING_PROFILES_ACTIVE=prod`. If no
profile is active, Spring uses the profile called `default`.

Use profiles to swap *which beans exist*. For values that differ between environments, use
properties, covered next.

## The Environment: one place to read settings

The **`Environment`** is the context's view of configuration. It has two parts: the active
profiles, and an ordered list of **property sources**, such as JVM system properties, OS
environment variables, and (in Boot) `application.yml`. When you look up a key, the first source
that has it wins.

```java
String url = env.getRequiredProperty("gateway.url");    // throws if missing
@Value("${app.currency:INR}") String currency           // injected; INR is the default
```

`${...}` is a **placeholder**, and everything after the `:` is its default value. Boot adds many
more property sources and a fixed order between them, which D4 covers. In this repo,
`DataImporter` takes `@Value("${prep.data-dir}") Path dataDir`, and Spring converts the string to
a `Path` for you.

## Lab (~10 min)

You need `org.springframework:spring-context` on the classpath (7.0.x if you follow Boot 4,
6.2.x for Boot 3). Spring Boot is not needed.

```java
import java.util.Arrays;
import java.util.UUID;

import org.springframework.beans.factory.ObjectProvider;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.*;
import org.springframework.core.env.Environment;
import org.springframework.stereotype.Component;

public class SpringCoreLab {
    public static void main(String[] args) {
        try (var ctx = new AnnotationConfigApplicationContext(AppConfig.class, CheckoutService.class)) {
            System.out.println("active profiles: " + Arrays.toString(ctx.getEnvironment().getActiveProfiles()));
            CheckoutService checkout = ctx.getBean(CheckoutService.class);
            checkout.pay(500);
            checkout.pay(700);
            System.out.println("same service? " + (checkout == ctx.getBean(CheckoutService.class)));
        }
    }
}

interface PaymentGateway { String charge(long paise); }

@Configuration
class AppConfig {
    @Bean @Profile("!prod")
    PaymentGateway fakeGateway() { return paise -> "FAKE charge " + paise; }

    @Bean @Profile("prod")
    PaymentGateway realGateway(Environment env) {
        String url = env.getRequiredProperty("gateway.url");
        return paise -> "POST " + url + " amount=" + paise;
    }

    @Bean @Scope("prototype")
    RequestId requestId() { return new RequestId(); }
}

class RequestId { final String value = UUID.randomUUID().toString().substring(0, 8); }

@Component
class CheckoutService {
    private final PaymentGateway gateway;
    private final RequestId fixedId;                  // injected once, kept for good
    private final ObjectProvider<RequestId> freshIds; // asks the container every time
    private final String currency;

    CheckoutService(PaymentGateway gateway, RequestId fixedId, ObjectProvider<RequestId> freshIds,
                    @Value("${app.currency:INR}") String currency) {
        this.gateway = gateway; this.fixedId = fixedId; this.freshIds = freshIds; this.currency = currency;
    }

    void pay(long paise) {
        System.out.printf("fixed=%s fresh=%s %s | %s%n",
                fixedId.value, freshIds.getObject().value, currency, gateway.charge(paise));
    }
}
```

What to try and observe:

1. Run it with no flags. You get the fake gateway and `INR`. `fixed` is the same on both lines,
   `fresh` differs, and `same service? true`.
2. Run it with `-Dspring.profiles.active=prod -Dgateway.url=https://pay.example -Dapp.currency=USD`.
   The real gateway is used, and the currency comes from a system property.
3. **Break it:** run with `-Dspring.profiles.active=prod` but without `gateway.url`. The context
   refuses to start and reports `Required key 'gateway.url' not found`. That is a start-up
   failure, which is exactly the point of eager creation.
4. **Break it:** remove `@Profile("!prod")` and run with `prod`. Two gateways now match, and
   you get `NoUniqueBeanDefinitionException`. Fix it with `@Primary`.

## Gotchas

- **A prototype injected into a singleton is created once.** Use `ObjectProvider<T>` or a
  scoped proxy when you need a fresh instance each time.
- **Singletons are shared by all threads.** Mutable fields in a `@Service` become a race
  condition. Keep services stateless.
- **Profiles choose beans, properties choose values.** Don't write five profile-specific beans
  that differ only by a URL. Use one bean that reads a property.
- **`@Profile("!prod")` matches every profile that isn't `prod`, including `default`.** That is
  convenient for local work, but make sure prod really does set its profile.
- **`@Value` without a default fails start-up when the key is missing.** That is usually what
  you want for required settings. Add `:default` only when a default is genuinely safe.

## In interviews

This is usually asked as "BeanFactory vs ApplicationContext?", "What bean scopes exist?", "What
happens when you inject a prototype into a singleton?" or "How do you configure different
environments?"

- [SOLID principles and dependency inversion](#/q/solid-principles): IoC containers are how
  dependency inversion is applied at scale.
- [Data Access Layer with Runtime-switchable Source](#/q/design-data-access-layer): one
  interface with several implementations, chosen by profile, property or `Map<String, Impl>`
  injection.
- [Design a Configuration Service](#/q/design-configuration-service): the `Environment` and
  property-source ordering are a local version of this.

Typical follow-ups:

- *"Are Spring singletons thread-safe?"* No. Spring only guarantees one instance. Thread
  safety depends on the bean being stateless or properly synchronised.
- *"Why constructor injection?"* Dependencies are immutable and explicit, tests need no
  container, and cycles fail fast.

## Explain it in 2 minutes

*"Walk me through how Spring's IoC container goes from your classes to ready objects."*

- It collects bean definitions (recipes) from component scanning and `@Bean` methods.
- `ApplicationContext.refresh()` creates every non-lazy singleton at start-up, resolving
  constructor dependencies by type.
- Ambiguity is resolved with `@Primary`, `@Qualifier`, or by injecting a collection.
- Scopes control instance lifetime: singleton, prototype, request and session. Beware the
  prototype-in-singleton trap.
- Profiles decide which beans exist, and the `Environment` resolves properties from ordered
  sources.
- `ApplicationContext` is a `BeanFactory` plus eager singletons, annotation processing, events
  and the environment.

## Check yourself

1. Why does Spring separate bean definitions from bean instances?
2. You need a `RestClient` built from a library builder. Do you use `@Component` or `@Bean`?
3. Two `PaymentGateway` beans exist and a service injects one. What happens, and what are three
   fixes?
4. What does `@Value("${app.currency:INR}")` do if the key is missing?

### Answers

1. So that the recipes can be inspected and changed (by Boot, conditions and post-processors)
   before any object is created.
2. `@Bean`, because you cannot annotate a library's class and building it takes code.
3. Start-up fails with `NoUniqueBeanDefinitionException`. You can fix it with `@Primary`,
   `@Qualifier`, or by injecting `List`/`Map<String, PaymentGateway>`.
4. It injects the default value, `INR`.
