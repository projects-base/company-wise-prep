## Where we are

F1 introduced the building blocks: read replicas, sharding, cache-aside and the cache stampede, in
one paragraph each. Q5–Q7 made one Postgres database as efficient as it can be: indexes,
transactions, round trips and pool sizing. This lesson goes back to F1's blocks with that depth,
applied to Postgres on AWS Aurora and the betting schema, and ends with the question interviewers
care about most: **which one would you reach for first, and why?**

## The problem

A Champions League final. Kick-off is at 20:00. From 19:30, logins climb steeply; at 19:55 bet
placement peaks; every goal brings another surge of bets and a flood of "My bets" refreshes. The
database that was comfortable on a Tuesday is now at 95% CPU, replicas are lagging, and the event
page cache expires at the worst possible moment.

You can't fix this by adding every technique at once. Each one costs complexity, and some (like
sharding) are very hard to undo. You climb a ladder, one rung at a time, and only as far as the
numbers force you:

```text
  6. Shard the write side by user_id        ← writes outgrow one primary
  5. CQRS: separate read models             ← reads need a different shape than writes
  4. Partition big tables by time           ← one table too big to maintain
  3. Cache hot, slightly-stale data (Redis)  ← the same reads, over and over
  2. Read replicas                           ← too many reads for one machine
  1. Bigger machine (vertical)               ← the cheapest step in engineering time
  0. Fix queries, indexes, pools (Q5–Q7)     ← always first
```

## Rung 1: scale vertically first

**Vertical scaling** means a bigger machine: more cores, more memory. It's unfashionable in
interviews and very effective in practice. It changes no code, keeps one consistent database and
needs no new failure modes. More memory alone can be dramatic, because once the hot data fits in
the buffer cache, `Buffers: read` turns into `hit` (Q5).

Its limits: there's a biggest instance; cost rises faster than capacity near the top; and on
Aurora, changing the instance class means a restart or a failover to a resized replica, so you plan
it rather than do it mid-match. Say this in an interview: "I'd first check we're on the right
instance size, because it's the cheapest fix in engineering time. Then I'd add replicas."

## Rung 2: read replicas and replication lag

A **read replica** is a copy of the database that serves reads only (F1). In betting, most reads
don't need to be up to the millisecond: event lists, results, statistics, last month's history.
Those go to replicas. Anything that decides money (balance checks, limit checks, bet placement) goes
to the **primary** (also called the writer).

**Replication lag** is the delay before a write on the primary is visible on a replica. It produces
the classic bug:

```text
19:58:01.000  POST /bets         → primary: bet 991 inserted, committed
19:58:01.040  GET /me/bets       → replica: lag 80 ms → bet 991 not there yet
              user: "where's my bet?!" ... taps Place again
```

The fix is a **read-your-writes** guarantee (F2): a user always sees their own writes. Ways to get
it, from simplest:

1. **Route a user's own data to the primary.** "My bets" and "my balance" read from the writer;
   only shared, non-personal data reads from replicas.
2. **Pin to the primary after a write.** After a user writes, send their reads to the primary for a
   few seconds (a flag in their session or in Redis).
3. **Let the client show what it just did.** The `POST /bets` response contains the new bet; the
   app inserts it into the list without waiting to re-read.

In Spring, the usual routing is an `AbstractRoutingDataSource` that picks the reader pool when the
transaction is `@Transactional(readOnly = true)`. Wrap it in a `LazyConnectionDataSourceProxy`.
Otherwise the connection is fetched *before* Spring has marked the transaction read-only, and every
query goes to the writer.

## Aurora specifics

**Amazon Aurora PostgreSQL** is AWS's Postgres-compatible database with a redesigned storage layer.
The well-established facts that change how you design:

- **Storage is separate from compute.** All instances in a cluster share one **cluster volume**,
  which keeps six copies of the data across three Availability Zones and grows automatically. A
  replica doesn't hold its own copy of the data. It reads the same volume.
- **Up to 15 Aurora Replicas** per cluster. Because they share storage, adding one doesn't copy the
  database, and lag is usually small. AWS documents it as typically well under 100 ms. Small is
  still not zero, so read-your-writes still matters.
- **Fast failover.** If the writer fails, Aurora promotes a replica (you control the preference
  with **promotion tiers**), usually in tens of seconds. In-flight transactions on the old writer
  are lost, and clients must reconnect. Your app must retry, and retries must be idempotent.
- **Endpoints.** The **cluster endpoint** always points at the current writer. The **reader
  endpoint** spreads *connections* across the replicas. It balances when a connection is opened
  (it's DNS-based), not per query, so a long-lived Hikari pool can stay stuck to one replica.
  There are also **custom endpoints** (a named group of instances, say for reporting) and
  **instance endpoints**.
- **Still one writer.** Replicas scale reads; every write still goes through one instance. For
  scaling writes, AWS also offers **Aurora PostgreSQL Limitless Database**, a managed sharding
  option, and for multi-region setups, **Aurora Global Database**.

**The rule:** on Aurora, rung 2 is cheap and fast to add. It does nothing for write load.

## Rung 3: caching with Redis

F1 covered cache-aside and delete-on-write. F6 covered hot keys and the delete-vs-set race. Here's
what's specific to betting.

**What to cache:** the catalogue (sports, events, markets, selections), which is read by every
visitor and changes rarely, and **current odds**, which change often but are read far more. **What
not to use the cache for:** decisions about money. Balances and limits come from the database
inside the bet transaction. A cached balance is fine for *display* only.

**Invalidation by events, not timers.** Odds don't change on a schedule, so a TTL is the wrong tool.
The odds service writes each new price to Redis as it publishes it (write-through), so the cache is
as fresh as the odds stream itself. A TTL stays only as a backstop, in case an update is missed.

**Stampede at kick-off.** A popular event's page key expires at 19:59:58, and thousands of requests
miss at once and hit the database. Three defences, best first:

1. **Don't let hot keys expire.** Big matches are scheduled, so warm their keys before kick-off and
   refresh them in the background.
2. **Single flight.** On a miss, only one caller rebuilds the key. Others wait briefly or get the
   stale value. With Redis, the lock is `SET lock:event:991 <token> NX PX 3000`: it succeeds for
   exactly one caller and expires on its own if that caller dies.
3. **Jittered TTLs**, so keys created together don't expire together.

**Hot keys:** at kick-off, one event's key is read by most users. Add a tiny in-process cache
(Caffeine, 1–2 s TTL) in each app instance in front of Redis, as in F6.

## Rung 4: partitioning a big table by time

Rungs 3 to 5 aren't strictly ordered: each fixes a different symptom. Partitioning fixes one table
being too big.

**Partitioning** splits one logical table into several physical tables (**partitions**) inside the
*same* database, by a key. `bets` grows forever, and almost every query on it asks about recent
bets. That makes it a natural fit for **range partitioning by time**:

```sql
CREATE TABLE bets (
  id                BIGINT        NOT NULL,      -- from a sequence or an ID generator
  user_id           BIGINT        NOT NULL,
  selection_id      BIGINT        NOT NULL,
  stake             NUMERIC(12,2) NOT NULL,
  odds_at_placement NUMERIC(8,2)  NOT NULL,
  placed_at         TIMESTAMPTZ   NOT NULL,
  status            TEXT          NOT NULL,
  settled_at        TIMESTAMPTZ,
  payout            NUMERIC(12,2),
  PRIMARY KEY (id, placed_at)
) PARTITION BY RANGE (placed_at);

CREATE TABLE bets_2026_10 PARTITION OF bets
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE bets_2026_11 PARTITION OF bets
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

CREATE INDEX bets_user_time ON bets (user_id, placed_at DESC);   -- created on every partition
```

What you get:

- **Partition pruning.** `WHERE placed_at >= '2026-10-01'` only touches October's and later
  partitions. `EXPLAIN` shows the skipped ones aren't scanned.
- **Small, hot indexes.** This month's partition and its indexes fit in memory.
- **Cheap retention.** Removing 2024's bets is `ALTER TABLE bets DETACH PARTITION bets_2024_10;`
  then archive and drop it. That's a metadata change instead of a `DELETE` of millions of rows,
  which would create millions of dead tuples for vacuum (Q6).

What it costs:

- **Every unique key must include the partition key**, which is why the primary key is
  `(id, placed_at)`. Global uniqueness of `id` alone has to come from the ID generator.
- **Queries without `placed_at`** ("all bets for selection 77") must check every partition. Keep
  the partition count sensible (monthly, not hourly), and keep a usable index on each partition.
- **Partitions must exist before the data arrives.** Create them ahead with a scheduled job or the
  `pg_partman` extension, and consider a `DEFAULT` partition as a safety net.

Partitioning doesn't add machines. It makes one big table behave like several small ones.

## Rung 5: CQRS and read models

**CQRS (command query responsibility segregation)** means using different models for writes and
reads. The write model is normalised and transactional: `bets`, `wallets`, the ledger, in Aurora.
**Read models** are separate, denormalised copies shaped for one screen or one question, built from
the stream of changes.

Betting has several read shapes that the write model serves badly:

```text
                    ┌─► "My bets" view: bet + event name + market + current status, per user
bets (Aurora) ──►   ├─► Liability per selection: "if Arsenal win, we pay out £2.3M", for traders
 outbox → Kafka     └─► Leaderboards, analytics, responsible-gambling activity summaries
```

The usual pipeline: the bet transaction also inserts a row into an **outbox** table (same
transaction, so it can't be lost). A relay (a poller, or change data capture such as Debezium)
publishes outbox rows to Kafka (S9). **Projectors**, consumers that build read models, update
their own stores, which might be Redis, another Postgres table, DynamoDB or OpenSearch.

Costs, which you must say out loud: read models are **eventually consistent** (show the user their
new bet from the API response, not the read model); you now run more stores; projectors must be
idempotent (S9: events can arrive twice); and you need a way to **rebuild** a read model by replaying
events.

**Reach for it when** read shapes differ a lot from the write shape, or read volume dwarfs writes so
much that replicas of the write model are wasteful. **Not** for a simple CRUD service.

## Rung 6: sharding by user_id

**Sharding** splits the data across several independent databases, each with its own writer (F1).
It's the only rung that scales *writes*, and the hardest to undo.

**Choosing the key.** For a betting platform, `user_id` is the natural shard key, because the most
important transaction (debit the wallet, insert the bet, write the ledger row) touches only one
user's data. With `user_id` as the key it's always a **single-shard transaction**, so you never need
a distributed transaction.

```text
logical shard = hash(user_id) % 4096
shard map:  logical 0–1023 → db-A    1024–2047 → db-B    2048–4095 → db-C
```

**Logical shards** (many more than you have databases) make resharding possible: to add db-D, you
move some *logical* shards to it and update the map, without rehashing every user. This is the same
idea as F1's consistent hashing with virtual nodes.

**Hotspots.** One very active user lands on one shard, but a single user can't place enough bets to
melt a shard. The real hotspot in betting is the **event**: a final where most users bet on the same
few selections. Sharding by user spreads those *writes* nicely. But anything **per event** becomes a
**cross-shard query**: "all open bets on selection 77" lives on every shard.

**Cross-shard work, handled deliberately:**

- **Settlement fans out:** each shard settles its own open bets for the event, in parallel, with a
  local index on `(selection_id) WHERE status = 'OPEN'`.
- **Per-event totals** (liability, bet counts) come from a CQRS read model fed by events, not from
  querying every shard.
- **IDs** must be unique across shards, so use a Snowflake-style or UUIDv7 generator rather than
  per-database sequences.

**Resharding** is the operation to plan for from day one: copy a logical shard to its new home,
stream changes until it catches up, briefly pause writes for that shard, flip the map, resume.

## When to reach for each

| Symptom | Reach for | Not yet |
|---|---|---|
| Slow queries, high CPU | Q5–Q7 fixes, then a bigger instance | anything below |
| Read CPU high, writes fine | Read replicas; route money reads to the writer | sharding |
| Same data read thousands of times a second | Redis, with event-driven invalidation | replicas alone |
| One table huge, deletes and vacuum painful | Time partitioning | sharding |
| Screens need joins across many tables at high volume | CQRS read models | bigger joins |
| Writes saturate the one writer, even after the above | Shard by `user_id` (or Limitless) | — |

## Lab (~10 min)

A design exercise, on paper. A betting platform on Aurora PostgreSQL has these measured numbers on
its biggest match day:

- Writer CPU 85% at peak; 70% of its load is `SELECT`s from the event page and "My bets".
- 4,000 bet placements a second at peak; each is one short transaction.
- `bets` holds 3 billion rows; nightly `DELETE` of bets older than two years runs for hours and
  bloats the table.
- Traders want live liability per selection, refreshed every few seconds.

For each line, pick a rung and write one sentence of "because". Then decide: do you need to shard?

Check here only after writing your answer:

```text
Reads on the writer → event page: Redis with pre-warming before kick-off;
                      "My bets": replicas for older pages, writer (or the client) for just-placed bets.
4,000 bets/s       → after the reads leave the writer, a single Aurora writer is very likely
                      enough for short transactions like these. Measure before sharding.
3 billion rows     → monthly range partitions on placed_at; retention = detach + drop.
Liability          → a CQRS read model fed from bet events (outbox → Kafka → projector),
                      not a GROUP BY over bets every few seconds.
Shard?             → not yet. Note user_id as the future shard key and keep transactions
                      single-user so the option stays open.
```

## Gotchas

- **Balance or limit checks on a replica.** Lag means the check sees stale money. Anything that
  decides money reads from the writer, inside the transaction.
- **Assuming the reader endpoint balances queries.** It balances *connections*, at DNS level. Pools
  can pile onto one replica. Monitor per-replica load, or use a driver that is aware of the cluster.
- **Partitioned tables without the partition key in queries.** They scan every partition. Design
  the hot queries to include `placed_at`, or accept the cost knowingly.
- **TTL-only caching of odds.** Prices change on events, not on timers. Write-through on change, and
  keep a TTL as a backstop only.
- **Sharding too early.** It makes cross-user queries, migrations, reporting and transactions all
  harder, permanently. Climb the cheaper rungs first, and say so.
- **CQRS read models used for decisions.** They lag. Use them for display and analytics; decide from
  the write model.

Typical follow-ups:

- *"Why user_id and not event_id as the shard key?"* The core transaction (wallet plus bet) is per
  user, so user sharding keeps it on one shard. Event sharding would put the final's entire write
  load on one shard and split every user's wallet transaction across shards.
- *"The primary fails mid-match. What happens?"* Aurora promotes a replica in tens of seconds;
  in-flight transactions roll back; clients get errors and retry with the same idempotency key, so no
  bet is placed twice; the app reconnects via the cluster endpoint.

## Explain it in 2 minutes

*"Your betting database is overloaded on match days. Walk me through how you'd scale it."*

- First, measure: fix queries, indexes and pools; consider a bigger instance.
- Move reads that can be slightly stale to replicas; keep money reads on the writer; handle
  read-your-writes.
- Cache the catalogue and odds in Redis, updated on change; pre-warm for scheduled big events.
- Partition `bets` by month for pruning, smaller indexes and cheap retention.
- Build read models (my bets, liability) from an outbox and Kafka: CQRS, eventually consistent.
- Only then shard writes by `user_id`, with logical shards, so the wallet transaction stays on one shard.

## Check yourself

1. Why should a balance check never run on a read replica?
2. What does the Aurora reader endpoint balance, and why does that matter with HikariCP?
3. Why must the primary key of a partitioned `bets` table include `placed_at`?
4. Name two defences against a cache stampede at kick-off, and why scheduled events make one of them
   easy.
5. Why is `user_id` a better shard key than `event_id` for bets, and what query gets harder?

### Answers

1. Replication lag: the replica may not yet show a debit, so the check could approve spending money
   that's already gone. Money decisions read from the writer, inside the transaction.
2. Connections, when they're opened (DNS). A pool opens its connections once and keeps them, so
   all of one app instance's reads can land on one replica.
3. Postgres enforces unique constraints per partition, so it requires the partition key in every
   unique key to guarantee uniqueness across the whole table.
4. Pre-warm and refresh hot keys in the background without expiry; single flight (one rebuilder via
   `SET ... NX PX`); jittered TTLs. Big matches are known in advance, so warming before kick-off is
   simple.
5. The wallet-plus-bet transaction is per user, so it stays on one shard, and event sharding would
   concentrate a final's writes on one shard. Per-event queries (all bets on a selection) become
   cross-shard, so settlement fans out and per-event totals come from read models.
