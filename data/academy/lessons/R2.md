## Where we are

LLD-DESIGN-2, LLD-DESIGN-3 and LLD-DESIGN-4 taught the core GoF patterns properly, with code and labs. This page is the
map around them: every GoF pattern in one place, plus the enterprise, distributed, concurrency and cloud patterns a
senior backend engineer is expected to name, each with what it buys you and what it costs.

## How to use this page

- **It is a reference, not a lesson.** Read it once end to end, then come back when a design question needs a name.
- **Each entry has the same shape:** intent in one line, *Use when*, *Benefit*, *Cost / misuse*, *In Java/Spring*,
  and *Depth* (the lesson that teaches it properly, if one exists). Where there is no depth lesson, the entry is
  enough for an interview.
- **A pattern is a name for a trade-off, not a goal.** Every entry lists a cost on purpose. In an interview, naming the
  cost is what separates "I memorised the book" from "I have used this".
- **Names matter most for communication.** "A Strategy picked by a Factory, behind a Proxy for transactions" tells
  another engineer a whole design in one sentence.

A few terms used throughout: **coupling** is how much one piece of code must know about another; **cohesion** is how
closely the things inside one unit belong together; **OCP** is the open/closed principle from LLD-DESIGN-1 (add
behaviour by adding code, not by editing working code).

## Creational (GoF)

Creational patterns decide *who* creates an object and *how*, so business code does not scatter `new` everywhere.

**Singleton** — guarantee one instance and give a global way to reach it.
- *Use when:* something must genuinely exist once per process, such as a connection pool or a metrics registry.
- *Benefit:* one shared resource; no accidental duplicates.
- *Cost / misuse:* hidden global state, hard to fake in tests; the naive lazy version races; "one" is per class
  loader, not per cluster. Misused as a convenient global variable.
- *In Java/Spring:* `Runtime.getRuntime()`; Spring beans are singleton-scoped by default (one per application
  context, injected, not reached through a static method), which is the modern way.
- *Depth:* LLD-DESIGN-2; the thread-safety detail is in JAVA-JVM-6.

**Factory Method** — let a subclass (or a method) decide which concrete class to create.
- *Use when:* the caller should depend only on an interface and the choice of class varies.
- *Benefit:* callers are closed to change (OCP); the "which class?" decision lives in one place.
- *Cost / misuse:* an extra class or hierarchy for a choice that never varies.
- *In Java/Spring:* `Collection.iterator()` (each collection creates its own iterator); static factories such as
  `List.of`, `Path.of`, `EnumSet.noneOf` (strictly "static factory methods", a looser cousin of the GoF form).
- *Depth:* LLD-DESIGN-2.

**Abstract Factory** — create *families* of related objects that must match each other.
- *Use when:* you swap a whole set of products together (a UI theme, a database vendor's matching classes).
- *Benefit:* products from one family are guaranteed compatible; swapping the family is one change.
- *Cost / misuse:* adding a new *kind* of product means changing every factory.
- *In Java/Spring:* `DocumentBuilderFactory`, `XPathFactory`; a JDBC `Connection` creating `Statement`s that match
  its driver.
- *Depth:* LLD-DESIGN-2 (table).

**Builder** — construct a complex object step by step, then validate and produce it in one go.
- *Use when:* about four or more parameters, several optional, and the result should be immutable and valid.
- *Benefit:* readable call sites, defaults, validation in one place (`build()`), no half-built objects.
- *Cost / misuse:* boilerplate for small objects where a `record` or constructor is clearer; a `build()` that does
  not validate only moves the bug.
- *In Java/Spring:* `HttpRequest.newBuilder()`, `StringBuilder` (the everyday, looser example),
  `UriComponentsBuilder`, `ResponseEntity.ok().header(...).body(...)`, `WebClient.builder()`, Lombok `@Builder`.
- *Depth:* LLD-DESIGN-2.

**Prototype** — create new objects by copying a configured instance.
- *Use when:* building from scratch is expensive or the configuration is complex, and copies differ slightly.
- *Benefit:* cheap creation of near-identical objects without knowing their concrete class.
- *Cost / misuse:* deep vs shallow copy bugs; `Object.clone()` is widely considered awkward. Prefer copy
  constructors or hand-written `withX` methods on records.
- *In Java/Spring:* `clone()`; Spring's `prototype` scope (a new bean per lookup) shares the name but is a
  different idea: it creates a fresh instance, it does not copy one.
- *Depth:* LLD-DESIGN-2 (table).

## Structural (GoF)

Structural patterns are about *wrapping and connecting* objects. Most of them look alike in code (one object holding
another); the difference is the intent.

**Adapter** — make an existing class fit an interface it was not written for.
- *Use when:* integrating a third-party or legacy API behind your own interface.
- *Benefit:* the rest of the code never sees the foreign API; you can replace the vendor in one class.
- *Cost / misuse:* adapters that leak the foreign model (returning vendor types) defeat the point.
- *In Java/Spring:* `InputStreamReader` (bytes to characters), `Arrays.asList` (array to `List`), Spring MVC's
  `HandlerAdapter` (lets `DispatcherServlet` call any kind of handler the same way).
- *Depth:* LLD-DESIGN-3. At service scale the same idea is the Anti-Corruption Layer, below.

**Bridge** — split an abstraction from its implementation so both can vary independently.
- *Use when:* you would otherwise get a class explosion (`N abstractions x M implementations`).
- *Benefit:* the two hierarchies grow separately; drivers can be added without touching callers.
- *Cost / misuse:* an extra layer of indirection that is overkill when only one side varies.
- *In Java/Spring:* JDBC (your code uses the `Connection`/`Statement` API, each driver implements it); the SLF4J API
  over different logging back ends.
- *Depth:* LLD-DESIGN-3 (table).

**Composite** — treat a group of objects the same way as a single object (a tree).
- *Use when:* the domain is naturally a tree: menus, org charts, file systems, nested pricing rules.
- *Benefit:* callers do not need `if (isGroup)` checks; recursion falls out naturally.
- *Cost / misuse:* the shared interface can become too general (leaf classes stuck with `add()` methods that throw).
- *In Java/Spring:* Swing `Container` is a `Component` that holds `Component`s; Spring's `CompositeCacheManager`.
- *Depth:* LLD-DESIGN-3 (table).

**Decorator** — add behaviour by wrapping an object that has the same interface.
- *Use when:* you want to stack optional behaviours (buffering, logging, caching, metrics) without subclassing every
  combination.
- *Benefit:* combine behaviours at runtime; each decorator has one job (SRP).
- *Cost / misuse:* deep wrapper stacks are hard to debug; order matters and is easy to get wrong.
- *In Java/Spring:* `new BufferedInputStream(new FileInputStream(f))`; `Collections.synchronizedList(list)`;
  `Collections.unmodifiableList(list)` (a read-only view; usually described as a decorator, and it also behaves like
  a protection proxy).
- *Depth:* LLD-DESIGN-3.

**Facade** — one simple entry point in front of a complicated subsystem.
- *Use when:* callers need a few common operations and should not learn ten classes to do them.
- *Benefit:* lower coupling to the subsystem; one place to change when it does.
- *Cost / misuse:* a facade that grows every method of the subsystem becomes a god object.
- *In Java/Spring:* SLF4J ("Simple Logging Facade for Java"); `JdbcTemplate` hides connections, statements and
  result sets.
- *Depth:* LLD-DESIGN-3 (table).

**Flyweight** — share many identical, immutable small objects to save memory.
- *Use when:* you have huge numbers of objects with mostly the same intrinsic state.
- *Benefit:* memory drops sharply; equality checks can become identity checks.
- *Cost / misuse:* only safe for immutable state; the shared/unshared split adds complexity.
- *In Java/Spring:* `Integer.valueOf` caches -128 to 127 (why `==` on boxed `Integer` "sometimes works"); string
  literals are interned.
- *Depth:* LLD-DESIGN-3 (table).

**Proxy** — a stand-in with the same interface that controls access to the real object.
- *Use when:* you need lazy loading, access control, remoting, or cross-cutting behaviour (transactions, security,
  caching) around calls.
- *Benefit:* the real object stays clean; the behaviour is added once for many methods.
- *Cost / misuse:* invisible behaviour; Spring's classic trap is **self-invocation** (a method calling another
  `@Transactional` method on `this` bypasses the proxy).
- *In Java/Spring:* `java.lang.reflect.Proxy`; Spring AOP (JDK dynamic proxies or CGLIB subclasses) behind
  `@Transactional`, `@Cacheable`, `@Async`; Hibernate lazy-loading proxies.
- *Depth:* LLD-DESIGN-3 and SPRING-BOOT-3.

## Behavioural (GoF)

Behavioural patterns are about *who does what and how objects talk*.

**Chain of Responsibility** — pass a request along a chain of handlers; each handles it, passes it on, or stops it.
- *Use when:* a request goes through an ordered, configurable series of checks or steps.
- *Benefit:* add, remove and reorder steps without touching the others.
- *Cost / misuse:* hard to see the whole flow; a handler that forgets to call the next one silently stops the chain.
- *In Java/Spring:* servlet `FilterChain`; Spring Security's `SecurityFilterChain`; Spring MVC
  `HandlerInterceptor`s in a `HandlerExecutionChain`.
- *Depth:* LLD-DESIGN-4.

**Command** — turn a request into an object so it can be queued, logged, retried or undone.
- *Use when:* you need undo/redo, job queues, audit logs or deferred execution.
- *Benefit:* decouples "what to do" from "when and where it runs".
- *Cost / misuse:* a class per action can be heavy; lambdas often suffice.
- *In Java/Spring:* `Runnable` and `Callable` handed to an `ExecutorService`; undo stacks in editors.
- *Depth:* LLD-DESIGN-4 (table).

**Interpreter** — represent a small language's grammar as classes and evaluate sentences in it.
- *Use when:* you have a small, stable rule language (filters, pricing rules, search queries).
- *Benefit:* each grammar rule is one small class; easy to extend with new rules.
- *Cost / misuse:* does not scale to large grammars; use a parser generator instead.
- *In Java/Spring:* `java.util.regex.Pattern`; Spring Expression Language (SpEL).
- *Depth:* LLD-DESIGN-4 (table).

**Iterator** — walk a collection without knowing how it is stored.
- *Use when:* always, for collections; you write your own for custom structures or paged results.
- *Benefit:* one way to traverse any structure; the structure can change without breaking callers.
- *Cost / misuse:* modifying a collection while iterating gives `ConcurrentModificationException` (fail-fast).
- *In Java/Spring:* `java.util.Iterator`, the enhanced `for` loop, `Spliterator` under streams.
- *Depth:* LLD-DESIGN-4 (table).

**Mediator** — objects talk through one coordinator instead of directly to each other.
- *Use when:* many components would otherwise form a many-to-many web of references.
- *Benefit:* components stay independent; interaction logic lives in one place.
- *Cost / misuse:* the mediator itself can become a god object.
- *In Java/Spring:* `DispatcherServlet` coordinating handler mappings, adapters and view resolvers.
- *Depth:* LLD-DESIGN-4 (table).

**Memento** — capture and restore an object's state without exposing its internals.
- *Use when:* undo, snapshots, checkpoints.
- *Benefit:* encapsulation is kept; the caretaker stores state it cannot read.
- *Cost / misuse:* memory grows with snapshot count; consider storing commands (diffs) instead.
- *In Java/Spring:* editor undo snapshots; game save states. Immutable records make cheap mementos.
- *Depth:* LLD-DESIGN-4 (table).

**Observer** — when one object changes, notify every object that subscribed.
- *Use when:* several parts of the code react to an event and the source should not know them.
- *Benefit:* loose coupling; add a reaction without editing the source (OCP).
- *Cost / misuse:* hard-to-trace flows; synchronous listeners that throw or are slow affect the publisher; memory
  leaks from listeners never removed.
- *In Java/Spring:* `ApplicationEventPublisher` with `@EventListener` and `@TransactionalEventListener`;
  `java.util.concurrent.Flow` for reactive streams. Across services it becomes Publish-Subscribe, below.
- *Depth:* LLD-DESIGN-4.

**State** — an object's behaviour changes with its internal state, with each state as its own class.
- *Use when:* a lifecycle with rules per state (order: created, paid, shipped, cancelled; vending machine).
- *Benefit:* no giant `switch(status)` repeated in every method; illegal transitions are impossible by construction.
- *Cost / misuse:* many small classes for a lifecycle with two states; an enum with a transition table is often enough.
- *In Java/Spring:* enum-based state machines; Spring Statemachine for heavier cases.
- *Depth:* LLD-DESIGN-4.

**Strategy** — swap an algorithm behind an interface.
- *Use when:* you have several interchangeable ways to do one thing (pricing, discount, routing, retry policy).
- *Benefit:* removes `if/else` chains; each algorithm is testable alone; new ones need no edits (OCP).
- *Cost / misuse:* an interface for a choice that has only ever had one implementation.
- *In Java/Spring:* `Comparator`; `RejectedExecutionHandler`; Spring Security's `PasswordEncoder`; injecting a
  `List<Strategy>` and indexing it by a key is the idiomatic Spring registry.
- *Depth:* LLD-DESIGN-4.

**Template Method** — a base method fixes the skeleton of an algorithm; subclasses fill in steps.
- *Use when:* several variants share the same steps in the same order and differ in a few of them.
- *Benefit:* the invariant part is written once and cannot be skipped (open the connection, always close it).
- *Cost / misuse:* inheritance couples subclass to base; prefer composition (pass the varying step as a lambda).
- *In Java/Spring:* `HttpServlet.service()` calling `doGet`/`doPost`; `AbstractList`. Spring's `JdbcTemplate`,
  `RestTemplate` and `TransactionTemplate` are the "template plus callback" variant: the fixed skeleton is in the
  template and the varying step is a callback you pass in, so no subclass is needed.
- *Depth:* LLD-DESIGN-4.

**Visitor** — add new operations to a fixed set of types without editing those types.
- *Use when:* the set of types is stable but operations keep growing (compilers, document exporters).
- *Benefit:* each operation lives in one class; types stay small.
- *Cost / misuse:* adding a new *type* means changing every visitor; double dispatch confuses readers.
- *In Java/Spring:* `Files.walkFileTree` with a `FileVisitor`; `javax.lang.model.element.ElementVisitor` in
  annotation processing.
- *Depth:* LLD-DESIGN-4 (table).

In Java 21, sealed interfaces plus pattern-matching `switch` often replace a Visitor. The compiler checks the `switch`
covers every permitted type, so adding a type is a compile error everywhere it must be handled:

```java
sealed interface Shape permits Circle, Square {}
record Circle(double r) implements Shape {}
record Square(double side) implements Shape {}

final class Areas {
    static double area(Shape s) {
        return switch (s) {                 // exhaustive: no default needed
            case Circle c -> Math.PI * c.r() * c.r();
            case Square q -> q.side() * q.side();
        };
    }
}
```

## Enterprise application patterns

Most of these were named in Martin Fowler's *Patterns of Enterprise Application Architecture*. They describe how a
typical Spring Boot service is already structured, which makes them easy to explain from your own code.

**Domain Model vs Transaction Script** — two ways to organise business logic.
- *Transaction Script:* one procedure per use case (`placeOrder()` does everything in a service method).
- *Domain Model:* behaviour lives on rich objects that protect their own rules (`order.addLine(...)` refuses to break
  an invariant).
- *Choose:* Transaction Script for simple CRUD-heavy logic; Domain Model when rules are many and interlock.
- *Cost:* a Domain Model needs more design up front; Transaction Scripts duplicate rules as the domain grows.
- *Depth:* LLD-DESIGN-7 (aggregates).

**Service Layer** — a layer that defines the application's use cases and owns the transaction boundary.
- *Benefit:* controllers stay thin; one place for `@Transactional`, authorisation and orchestration.
- *Cost / misuse:* it swallows all logic and the entities become empty data bags (see anemic domain model).
- *In Spring:* `@Service` classes with `@Transactional` methods.

**Repository** — a collection-like interface for loading and saving aggregates, hiding the storage.
- *Benefit:* domain code does not know SQL; easy to fake in tests; a natural port in hexagonal architecture.
- *Cost / misuse:* a repository per table (instead of per aggregate) leaks the schema into the domain; generic
  `findAll()` everywhere invites unbounded queries.
- *In Spring:* Spring Data `JpaRepository`, derived queries, `@Query`.
- *Depth:* SPRING-BOOT-7, LLD-DESIGN-7.

**Data Mapper vs Active Record** — who knows how to persist an object.
- *Active Record:* the object saves itself (`order.save()`); simple, but domain and persistence are welded together.
- *Data Mapper:* a separate layer maps objects to tables; the domain object knows nothing about the database.
- *Choose:* Active Record for simple CRUD apps; Data Mapper when the domain model and the schema diverge.
- *In Java:* JPA/Hibernate is a Data Mapper (the `EntityManager` does the work, even though annotations sit on the
  entity). Quarkus's Panache offers an Active Record style; Rails' ActiveRecord is the best-known example outside Java.

**Unit of Work** — track every object changed during a business transaction and write them all at the end.
- *Benefit:* one consistent flush; changes are batched; you do not call `save()` on every modified object.
- *Cost / misuse:* surprise writes at commit time (dirty checking updates an entity you only meant to read).
- *In Spring:* the JPA persistence context inside a `@Transactional` method; changes are flushed at commit.
- *Depth:* SPRING-BOOT-7, LIFECYCLE-6.

**Identity Map** — within one unit of work, load each row at most once and return the same object for it.
- *Benefit:* no two in-memory copies of one row disagree; repeated lookups hit memory.
- *Cost / misuse:* long-running persistence contexts grow and hold stale data.
- *In Spring:* the persistence context is the identity map (often called the first-level cache).
- *Depth:* LIFECYCLE-6.

**Lazy Load** — load related data only when it is first accessed.
- *Benefit:* avoids loading a whole object graph for a screen that needs one field.
- *Cost / misuse:* the N+1 query problem; `LazyInitializationException` when accessed after the session closes.
- *In Spring:* `FetchType.LAZY` and Hibernate proxies; fix N+1 with fetch joins or `@EntityGraph`.
- *Depth:* DB-SQL-8.

**DTO (Data Transfer Object)** — a plain object shaped for one boundary (an API, a message), separate from the entity.
- *Benefit:* the API contract does not change when the schema does; no accidental exposure of internal fields; no
  lazy-loading surprises during JSON serialisation.
- *Cost / misuse:* mapping code; one DTO reused for every endpoint becomes a second entity.
- *In Java:* records are ideal DTOs; MapStruct generates mappers.

**Specification** — a business rule as a combinable object (`isActive().and(placedAfter(date))`).
- *Benefit:* rules are named, reusable and testable; queries are composed instead of a method per combination.
- *Cost / misuse:* over-generic query builders that are harder to read than SQL.
- *In Spring:* Spring Data JPA's `Specification<T>` with `JpaSpecificationExecutor`:

```java
static Specification<Order> hasStatus(Status s) {
    return (root, query, cb) -> cb.equal(root.get("status"), s);
}
// orders.findAll(hasStatus(Status.PAID).and(placedAfter(cutoff)));
```

**Dependency Injection / Inversion of Control** — objects receive their collaborators instead of creating them;
a container wires the graph.
- *Benefit:* depend on interfaces (DIP); swap implementations for tests or environments; lifecycle managed for you.
- *Cost / misuse:* "magic" wiring that is hard to trace; field injection hides dependencies (prefer constructor
  injection); a constructor with ten dependencies is an SRP smell, not a DI problem.
- *In Spring:* the `ApplicationContext`; constructor injection; `@Configuration` + `@Bean`.
- *Depth:* SPRING-BOOT-1, SPRING-BOOT-2.

**MVC (Model-View-Controller)** — separate request handling (controller), data (model) and presentation (view).
- *Benefit:* each part changes independently; controllers are testable without a UI.
- *Cost / misuse:* fat controllers holding business logic.
- *In Spring:* `@Controller`/`@RestController`; for REST APIs the "view" is the JSON written by a message converter.
- *Depth:* BE-STORY-4, SPRING-BOOT-6.

**Front Controller** — one handler receives every request and dispatches it.
- *Benefit:* cross-cutting concerns (security, logging, error handling) happen in one place.
- *Cost / misuse:* a single place that everything depends on; keep it a dispatcher, not a logic holder.
- *In Spring:* `DispatcherServlet`.
- *Depth:* BE-STORY-4, LIFECYCLE-5.

## Distributed and integration patterns

These appear once a system spans processes and networks. Many come from the *Enterprise Integration Patterns* book
(Hohpe and Woolf) and from the microservices literature. DIST-SYS-3 and BE-STORY-10 teach the core ones in depth.

**API Gateway** — one entry point in front of many services: routing, auth, rate limits, TLS.
- *Benefit:* clients see one API; cross-cutting concerns are centralised.
- *Cost / misuse:* a single point of failure and a bottleneck; business logic creeping into it.
- *In Java/Spring:* Spring Cloud Gateway; managed gateways from cloud providers. *Depth:* WEB-API-5.

**Backend for Frontend (BFF)** — a separate thin backend per client type (web, mobile).
- *Benefit:* each client gets responses shaped for it; frontend teams move independently.
- *Cost / misuse:* duplicated logic across BFFs; it should aggregate and shape, not own business rules.
- *Depth:* WEB-API-5.

**Service Discovery** — services find each other's current addresses through a registry rather than fixed hosts.
- *Benefit:* instances can scale and move freely.
- *Cost / misuse:* another critical component; stale entries route to dead instances.
- *In Java/Spring:* Kubernetes Services and DNS; Eureka or Consul with Spring Cloud. *Depth:* WEB-API-5.

**Timeout** — bound how long you wait for any remote call.
- *Benefit:* a slow dependency cannot hold your threads forever; the first and cheapest resilience pattern.
- *Cost / misuse:* too long is useless, too short causes false failures; set from measured latency percentiles.
- *In Java/Spring:* `HttpClient` connect and request timeouts; Resilience4j `TimeLimiter`. *Depth:* DIST-SYS-3.

**Retry with backoff and jitter** — retry transient failures with growing, randomised delays.
- *Benefit:* rides out short blips without user-visible errors.
- *Cost / misuse:* retrying non-idempotent calls duplicates work; retrying validation errors is pointless; retries at
  every layer multiply load and can turn a slowdown into an outage. "Full jitter" sleeps a random time between zero
  and `min(cap, base * 2^attempt)`, which spreads clients apart instead of having them retry in sync.
- *In Java/Spring:* Resilience4j `Retry`, Spring Retry. *Depth:* DIST-SYS-3.

**Circuit Breaker** — after enough failures, stop calling a dependency for a while and fail fast.
- *Benefit:* protects your threads and gives the dependency room to recover; enables a fallback.
- *Cost / misuse:* thresholds need tuning; a breaker shared by unrelated endpoints trips for all of them.
- *In Java/Spring:* Resilience4j `CircuitBreaker` (closed, open, half-open). *Depth:* DIST-SYS-3.

**Bulkhead** — isolate resources (thread pools, connection pools) per dependency.
- *Benefit:* one slow dependency cannot exhaust the pool everyone shares.
- *Cost / misuse:* more pools to size; under-sized bulkheads reject healthy traffic.
- *In Java/Spring:* Resilience4j `Bulkhead`; separate `ExecutorService`s. *Depth:* DIST-SYS-3.

**Rate Limiter** — cap requests per client or per time window (token bucket, sliding window).
- *Benefit:* protects capacity and fairness; a defence against abuse.
- *Cost / misuse:* per-instance limits are not global; distributed limits need shared state (often Redis).
- *In Java/Spring:* Resilience4j `RateLimiter`; gateway filters. *Depth:* DIST-SYS-3, SYS-DES-4, LLD-DESIGN-8.

**Idempotent Receiver / idempotency key** — processing the same request or message twice has the same effect as once.
- *Benefit:* makes retries and at-least-once delivery safe; the foundation under almost every pattern below.
- *Cost / misuse:* needs a store of processed keys with a unique constraint and a retention period; checking and
  acting must be atomic, or two concurrent duplicates both pass the check.
- *In Java/Spring:* an `Idempotency-Key` header stored with the response; a processed-message table keyed by message
  id. *Depth:* DIST-SYS-3, WEB-API-3, CAPSTONE-10.

**Saga (orchestration vs choreography)** — a business transaction across services as a sequence of local
transactions, each with a compensating action.
- *Orchestration:* one coordinator tells each service what to do next. Easy to follow and monitor; the coordinator is
  extra code to run.
- *Choreography:* each service reacts to the previous one's events. No coordinator; the flow is hard to see and easy
  to tangle as steps grow.
- *Benefit:* consistency across services without distributed locks or two-phase commit.
- *Cost / misuse:* only eventual consistency; compensations must be idempotent and are not true rollbacks (an email
  already sent stays sent). *Depth:* DIST-SYS-3.

**Transactional Outbox** — write the business change and the event to publish in the *same* database transaction;
a separate relay publishes the events.
- *Benefit:* no lost or phantom events from the "write DB, then publish" dual-write problem.
- *Cost / misuse:* delivery is at-least-once, so consumers must be idempotent; the outbox table needs cleanup.
- *In Java/Spring:* a polling relay, or Debezium's outbox event router reading the table via CDC.
- *Depth:* DIST-SYS-3, CAPSTONE-10.

**Change Data Capture (CDC)** — stream row changes from the database's log (Postgres WAL, MySQL binlog) as events.
- *Benefit:* no application code changes; captures every change in commit order.
- *Cost / misuse:* events mirror tables, not business intent, so they couple consumers to your schema; publish
  curated events (or an outbox) for other teams. *In Java:* Debezium on Kafka Connect. *Depth:* DIST-SYS-9.

**CQRS (Command Query Responsibility Segregation)** — separate the write model from one or more read models.
- *Benefit:* each side is optimised for its job (normalised writes, denormalised fast reads); they scale separately.
- *Cost / misuse:* read models lag behind writes; two models to keep in sync; overkill for plain CRUD.
- *Depth:* DB-SQL-10.

**Event Sourcing** — store the sequence of events as the source of truth; current state is derived by replaying them.
- *Benefit:* a full audit history; rebuild or add read models at any time; "what did we know at time T?" queries.
- *Cost / misuse:* event schema evolution is hard (old events live forever); replays need snapshots; querying current
  state needs projections, so it usually comes with CQRS. Using it for a simple CRUD domain is a classic over-reach.

**Publish-Subscribe** — a publisher sends to a topic; every subscriber gets its own copy.
- *Benefit:* add consumers without touching the producer; the distributed Observer.
- *Cost / misuse:* nobody owns the end-to-end flow; event contracts become a public API that needs versioning.
- *In Java/Spring:* Kafka topics with different consumer groups; SNS-style fan-out. *Depth:* DIST-SYS-2, BE-STORY-11.

**Competing Consumers** — many consumers read from one queue; each message goes to only one of them.
- *Benefit:* horizontal scaling of work; a slow worker does not block the others.
- *Cost / misuse:* ordering is lost across consumers (in Kafka, order holds only within a partition, and parallelism
  is capped by the partition count).
- *In Java/Spring:* consumers in one Kafka consumer group; several workers on one SQS queue. *Depth:* DIST-SYS-2.

**Dead Letter Queue (DLQ)** — messages that keep failing go to a side queue instead of blocking or being dropped.
- *Benefit:* one poison message does not stall the stream; failures are kept for inspection and replay.
- *Cost / misuse:* a DLQ nobody monitors is a silent data-loss bin; alert on its depth and have a replay path.
- *In Java/Spring:* Spring Kafka's `DeadLetterPublishingRecoverer`; SQS redrive policies. *Depth:* DIST-SYS-2.

**Claim Check** — put a large payload in storage (for example S3) and send only a reference in the message.
- *Benefit:* keeps messages small and the broker fast; avoids broker message-size limits (roughly 1 MB by default in
  Kafka).
- *Cost / misuse:* two systems must both be available; payload lifecycle and access control need managing.

**Strangler Fig** — replace a legacy system gradually by routing one capability at a time to new code.
- *Benefit:* no big-bang rewrite; value delivered and risk reduced at every step.
- *Cost / misuse:* running two systems for a long time; the migration stalls at 80% if not driven to the end.
- *Depth:* BE-STORY-10.

**Anti-Corruption Layer (ACL)** — a translation layer so a legacy or external model does not leak into your domain.
- *Benefit:* your bounded context keeps its own language; the foreign system can change in one place.
- *Cost / misuse:* more mapping code; skipped "for now" and never added. *Depth:* BE-STORY-10, LLD-DESIGN-7.

**Sidecar** — a helper process deployed next to each service instance (in Kubernetes, a second container in the pod).
- *Benefit:* cross-cutting features (proxying, mTLS, log shipping) without changing application code, in any language.
- *Cost / misuse:* extra CPU, memory and latency per instance; another moving part to debug.
- *In practice:* Envoy as the proxy in a service mesh. *Depth:* BE-STORY-11.

**Leader Election** — exactly one instance among many is chosen to do a job (a scheduler, a partition owner).
- *Benefit:* avoids duplicate work without a single fixed master.
- *Cost / misuse:* split brain if two think they lead; use leases with expiry and fencing tokens.
- *In practice:* ZooKeeper, etcd, Kubernetes `Lease` objects; for a scheduled job, a DB-backed lock such as ShedLock is
  often enough. *Depth:* SYS-DES-3.

**Sharding** — split data across databases by a shard key so each holds a part.
- *Benefit:* write and storage capacity scale beyond one machine.
- *Cost / misuse:* cross-shard queries and transactions become hard; a bad key creates hot shards; resharding is
  painful. Do it after replicas, caching and partitioning. *Depth:* DB-SQL-10.

**Caching strategies** — where the cache sits relative to the database.
- *Cache-Aside:* the app reads the cache, on a miss loads from the DB and fills the cache; on write, updates the DB and
  evicts the key. Most common; simple; a short window of stale data is possible. Spring's `@Cacheable` works this way.
- *Read-Through:* the cache itself loads missing entries (Caffeine `LoadingCache`). Cleaner callers; the cache needs
  the loader.
- *Write-Through:* writes go to the cache and the DB synchronously. Reads are fresh; writes are slower.
- *Write-Behind (write-back):* writes go to the cache and reach the DB later. Fast writes; data loss if the cache dies
  before flushing.
- *Depth:* SYS-DES-1, DIST-SYS-1, DB-SQL-10.

**Materialized View** — precompute and store a query result (a database materialized view, or a read model fed by
events).
- *Benefit:* expensive joins and aggregates become cheap reads.
- *Cost / misuse:* staleness between refreshes; refresh cost on large data. In Postgres,
  `REFRESH MATERIALIZED VIEW CONCURRENTLY` avoids blocking readers but needs a unique index.

## Concurrency patterns

**Producer-Consumer** — producers put work on a bounded queue; consumers take it off.
- *Benefit:* decouples rates; the bound gives back-pressure instead of running out of memory.
- *Cost / misuse:* unbounded queues hide overload until the heap fills.
- *In Java:* `BlockingQueue` (`ArrayBlockingQueue`, `LinkedBlockingQueue`). *Depth:* JAVA-CONC-7.

**Thread Pool** — reuse a fixed set of worker threads for many tasks.
- *Benefit:* bounds concurrency and avoids thread-creation cost.
- *Cost / misuse:* wrong sizing; unbounded work queues; blocking calls starving a small pool. With virtual threads,
  pooling threads is no longer the point; limit concurrency with a semaphore instead.
- *In Java:* `ThreadPoolExecutor`, `Executors.newVirtualThreadPerTaskExecutor()`. *Depth:* JAVA-CONC-4, JAVA-CONC-6.

**Future / Promise** — a placeholder for a result that will exist later.
- *Benefit:* run independent calls in parallel and compose them.
- *Cost / misuse:* calling `get()` without a timeout; losing exceptions in long chains; running blocking work on the
  common pool. *In Java:* `Future`, `CompletableFuture`. *Depth:* JAVA-CONC-5.

**Read-Write Lock** — many readers at once, or one writer alone.
- *Benefit:* throughput for read-heavy data with slow reads.
- *Cost / misuse:* for short critical sections its bookkeeping often costs more than a plain lock saves; writer
  starvation is possible. *In Java:* `ReentrantReadWriteLock`, `StampedLock`. *Depth:* JAVA-CONC-2.

**Immutable Object** — state fixed at construction; to "change" it, create a new one.
- *Benefit:* safe to share between threads without locks; safe as map keys; easy to reason about.
- *Cost / misuse:* allocation churn for very hot, large objects; "immutable" classes that expose a mutable list.
- *In Java:* `String`, records (with defensive copies such as `List.copyOf`), `java.time` types. *Depth:* JAVA-JVM-6.

**Thread-Local** — each thread gets its own copy of a variable.
- *Benefit:* per-request context (user, tenant, correlation id) without passing it everywhere; non-thread-safe helpers
  without locking.
- *Cost / misuse:* leaks in pooled threads if not removed in a `finally`; context does not follow work to other
  threads; with millions of virtual threads, heavy thread-locals cost memory.
- *In Java/Spring:* `ThreadLocal`; Spring's `SecurityContextHolder` and `TransactionSynchronizationManager`; SLF4J
  MDC. *Depth:* JAVA-CONC-6.

**Double-Checked Locking** — check, lock, check again, so the lock is taken only during first initialisation.

```java
final class Config {
    private static volatile Config instance;   // volatile is what makes this correct

    private Config() { }

    static Config get() {
        Config local = instance;               // one volatile read on the fast path
        if (local == null) {
            synchronized (Config.class) {
                local = instance;
                if (local == null) {
                    instance = local = new Config();
                }
            }
        }
        return local;
    }
}
```

- *Why `volatile`:* `instance = new Config()` is several steps (allocate, run the constructor, publish the reference).
  Without `volatile`, the JVM may reorder them so another thread sees a non-null reference to an object whose
  constructor has not finished, and it skips the lock because the first check passed. The `volatile` write creates a
  happens-before edge with the next `volatile` read, so a thread that sees the reference also sees a fully built object.
- *Simpler alternative:* the lazy holder idiom or an `enum` singleton. *Depth:* JAVA-JVM-6, LLD-DESIGN-2.

## Choosing a pattern

| Problem you have | Pattern(s) to consider |
|---|---|
| A growing `if/else` or `switch` on a type or mode | Strategy (plus a Factory or a `Map` registry); State if it is a lifecycle |
| Object with many optional parameters | Builder (or a record if few fields) |
| Need to add logging, caching, transactions or security around calls | Decorator, Proxy (Spring AOP) |
| Third-party API you don't want to leak | Adapter; at service level, Anti-Corruption Layer |
| Ordered, configurable processing steps | Chain of Responsibility; Pipeline |
| Several parts must react when something happens | Observer in-process; Publish-Subscribe across services |
| Same steps, a few that vary | Template Method, or a template plus callback |
| Undo, queueing, auditing actions | Command, Memento |
| Tree-shaped data treated uniformly | Composite |
| Slow or failing downstream service | Timeout, Retry with jitter, Circuit Breaker, Bulkhead, Fallback |
| Event must be published if and only if the DB commit succeeds | Transactional Outbox (or CDC) |
| Duplicates from retries or at-least-once delivery | Idempotency key / Idempotent Receiver |
| Business transaction spanning services | Saga |
| Reads far outnumber writes, or need a different shape | Cache-Aside, Read replicas, CQRS, Materialized View |
| One database can't hold the writes | Sharding (after replicas, caching, partitioning) |
| Replacing a legacy system safely | Strangler Fig with an Anti-Corruption Layer |
| Large message payloads | Claim Check |
| A job must run on exactly one instance | Leader Election, or a distributed lock with a lease |
| Poison messages blocking a consumer | Retry topic plus Dead Letter Queue |

## Anti-patterns to name

An **anti-pattern** is a common solution that looks reasonable and reliably causes trouble. Naming one, and the fix,
is a strong interview signal.

- **God object** — one class that knows and does everything (`OrderManager` with 3,000 lines). Fix: split by
  responsibility (SRP); extract Strategies and collaborators. LLD-DESIGN-1 does this refactor.
- **Anemic domain model** — entities are only getters and setters, and all rules live in services. Fowler calls it an
  anti-pattern because invariants are not protected by the object that owns the data, so rules get duplicated and
  bypassed. *The nuance:* for a CRUD-heavy service with little logic, a Transaction Script over simple entities is
  honest and fine. It becomes a problem when there are real interlocking rules and nothing enforces them in one place.
- **Distributed monolith** — services that must be deployed together, share libraries with domain logic, or call each
  other synchronously in long chains. You pay the network and ops costs of microservices without independent
  deployment. Fix: align services to bounded contexts; prefer async events; or merge back into a modular monolith.
- **Shared database across services** — several services reading and writing the same tables. Any schema change
  breaks someone; no service owns its data. Fix: one owner per table; others use its API or its events.
- **Chatty services** — one user request triggers dozens of fine-grained calls between services. Latencies and failure
  probabilities add up. Fix: coarser APIs, aggregation (BFF), local read models fed by events, or rethinking the
  boundary.
- **Golden hammer** — using the familiar tool for everything (Kafka for a two-service app, microservices for a
  three-person team, a pattern for every class). Fix: start from the problem and name the trade-off you accept.

Typical follow-ups and what a strong answer contains:

- *"Isn't that over-engineering?"* Agree it can be: say what would have to change for the pattern to pay off (a
  second implementation, a second consumer), and that you would start without it if that is unlikely.
- *"Decorator and Proxy look identical in code. What's the difference?"* Intent: a Decorator adds behaviour the
  caller chooses to stack; a Proxy controls access to the real object (lazy loading, security, transactions), and the
  caller usually does not know it is there.

## Check yourself

1. Why is Spring's `JdbcTemplate` described as a "template plus callback" rather than a pure GoF Template Method?
2. What does `volatile` prevent in double-checked locking?
3. You must publish an `OrderPlaced` event exactly when the order row commits. Which pattern, and what must
   consumers still do?
4. When is an anemic domain model acceptable?
5. Orchestrated vs choreographed saga: give one advantage of each.

### Answers

1. The fixed skeleton (get connection, run, map, close, translate exceptions) lives in the template, but the varying
   step is passed in as a callback object (`RowMapper`, `PreparedStatementCreator`) instead of being supplied by a
   subclass. Composition replaces inheritance.
2. A reordering in which the reference is published before the constructor finishes, so another thread skips the lock
   and uses a partly built object. The `volatile` write and read create a happens-before edge.
3. Transactional Outbox (or CDC on an outbox table). Delivery is at-least-once, so consumers must be idempotent, for
   example by recording processed event ids under a unique constraint.
4. When the service is mostly CRUD with little business logic, so a Transaction Script is the honest design. It is a
   problem when interlocking rules exist and no object enforces them in one place.
5. Orchestration: the whole flow is visible in one place and easy to monitor and change. Choreography: no central
   coordinator to build or run, and services stay loosely coupled through events.
