## Where we are

From A4 you know that the GC keeps everything *reachable* from GC roots, that young collections
are cheap when most objects die, and how to read a `-Xlog:gc` line. This lesson turns that into a
debugging skill: given a service whose memory keeps climbing, prove whether it is a leak, find
what is holding the memory, and fix it, using the tools that ship with the JDK.

## The problem

A typical ticket: "Order service restarts every two days with `OutOfMemoryError`. Before it dies,
latency gets terrible." Three very different causes produce that same symptom:

1. **A leak**: objects stay reachable forever (a static map that only grows).
2. **The heap is too small** for the real working set (a legitimate cache, a big batch).
3. **Allocation pressure**: the app creates garbage so fast that the GC runs constantly, even
   though nothing leaks.

Each has a different fix (fix the code, raise `-Xmx`, reduce allocation), so the first job is
telling them apart.

## Reading the shape: sawtooth vs rising floor

Plot heap used over time. Each GC drops the line; the low point after each *full* or old-gen
collection is the **live set** (what is really reachable).

```text
 healthy                          leak                             too small
 used                             used                             used
  │ /|  /|  /|  /|                 │          /|/|/|                │/|/|/|/|/|/|/|/|  ← GC runs
  │/ | / | / | / |                 │     /|/|/  ← floor rises       │ constantly, floor
  │  |/  |/  |/  |/  ← flat floor  │/|/|/                           │ near the max
  └──────────────── time           └──────────────── time           └──────────────── time
```

**Rule:** a flat floor is healthy. A floor that keeps rising under steady load is a leak. A floor
that is flat but close to `-Xmx`, with GC running all the time, is an undersized heap or an
allocation problem.

You get this data from GC logs, `jstat` or your metrics system (Micrometer's
`jvm.memory.used` after GC). The tools below go from cheapest to most detailed.

## Tool 1: GC logs, always on

Turn them on in production from day one; the overhead is small and they are the only record of
what happened before a crash:

```text
-Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=5,filesize=20m
```

That writes detailed GC events to rotating files (5 × 20 MB). Look at the "after" number of each
collection over hours; that is your floor.

## Tool 2: jcmd, the Swiss army knife

`jcmd` attaches to a running JVM on the same machine (same user) and runs diagnostic commands.

```text
jcmd                                  # list running JVMs and their PIDs
jcmd <pid> help                       # what this JVM supports
jcmd <pid> VM.flags                   # effective flags (which GC? what Xmx?)
jcmd <pid> GC.heap_info               # current heap layout and usage
jcmd <pid> GC.class_histogram         # instance counts and bytes per class (live objects)
jcmd <pid> GC.heap_dump /tmp/app.hprof
jcmd <pid> Thread.print               # all thread stacks (also for deadlocks)
```

`GC.class_histogram` is the quickest leak clue. Taking two a few minutes apart and comparing
counts often names the culprit straight away:

```text
 num     #instances         #bytes  class name (module)
   1:         18266       78471040  [B (java.base@21.0.9)
   3:          8828         282496  java.util.HashMap$Node (java.base@21.0.9)
   4:         10383         249192  java.lang.String (java.base@21.0.9)
```

`[B` means `byte[]`. Byte arrays and strings are always near the top; what matters is a count
that only grows (here, `HashMap$Node` growing in step with `byte[]` points at a map).

Note: the histogram (by default) and heap dumps run a full GC first so they show only live
objects. That is a pause; on a big heap, do it on one instance, out of rotation if you can.

## Tool 3: jstat, watching GC live

`jstat -gcutil <pid> 1000` prints one line per second:

```text
  S0     S1     E      O      M     CCS    YGC     YGCT     FGC    FGCT     CGC    CGCT       GCT
     - 100.00  44.44  19.38  72.55  20.48      4     0.025     0     0.000     0     0.000     0.025
     - 100.00  39.68  36.76  72.55  20.48      5     0.033     0     0.000     0     0.000     0.033
```

| Column | Meaning |
|---|---|
| S0, S1, E, O | survivor 0/1, eden, old: % used |
| M, CCS | metaspace and compressed class space: % used |
| YGC / YGCT | young collections: count / total seconds |
| FGC / FGCT | full collections: count / total seconds |
| CGC / CGCT | concurrent cycles (G1, ZGC): count / total seconds |
| GCT | total GC time |

What to watch: **O** stepping up after every young GC and never coming down is a leak (or a
filling cache). **FGC** increasing means trouble. If **GCT** grows almost as fast as wall-clock
time, the app is mostly collecting garbage.

## Tool 4: heap dumps

A **heap dump** (`.hprof` file) is a snapshot of every object on the heap and the references
between them. Two ways to get one:

```text
jcmd <pid> GC.heap_dump /tmp/app.hprof                        # on demand
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps/      # automatically, at the moment of OOM
```

Always set the second pair in production; it captures the evidence exactly when it matters.
Remember: a dump is about the size of the used heap, takes a pause to write, and contains real
data (tokens, personal data), so treat it as sensitive.

## Reading a heap dump: retained size and the dominator tree

Open the dump in **Eclipse MAT** (free; VisualVM and IntelliJ can also open `.hprof` files). Two
definitions make it usable:

- **Shallow size**: memory of the object itself (header + fields). A `HashMap` object alone is
  tiny.
- **Retained size**: memory that would be freed if this object became unreachable, i.e. it plus
  everything only it keeps alive. The `HashMap` that holds a million entries retains hundreds of
  MB.

The **dominator tree** lists objects by retained size. A leak almost always shows as one object
near the top retaining a large share of the heap. Then use **Path to GC Roots** on it (excluding
weak references) to see *who* keeps it alive, for example
`Thread main → Leaky.CACHE (static) → HashMap → table → ...`. That chain is your bug report.
MAT's **Leak Suspects** report automates the first pass.

## The usual leak patterns

| Pattern | Example | Fix |
|---|---|---|
| Unbounded cache / static collection | `static Map<String, Result> CACHE` keyed by request id | size bound + eviction (Caffeine, or `LinkedHashMap` LRU), or TTL |
| Listeners and callbacks never removed | subscribe in constructor, never unsubscribe | unregister in `close()`; weak listeners where appropriate |
| `ThreadLocal` on pooled threads | per-request user stored in a `ThreadLocal`, never removed | `try { set } finally { remove() }` |
| Mutable or broken map keys | key's `hashCode` changes after insertion, or no `equals/hashCode` so "equal" keys pile up | immutable keys (records) with correct `equals/hashCode` |
| Unclosed resources | streams, JDBC connections, direct buffers | try-with-resources; pool limits and leak detection |
| Class-loader leaks | redeploys pile up classes; metaspace grows | stop threads, remove `ThreadLocal`s, deregister drivers on shutdown |

## Not every OOM is the heap

The message after `OutOfMemoryError:` tells you which area ran out:

| Message | Area | First step |
|---|---|---|
| `Java heap space` | heap | heap dump, dominator tree |
| `GC overhead limit exceeded` | heap (mainly Parallel GC: nearly all time spent in GC) | same as above |
| `Metaspace` | class metadata | class-loader leak; `jcmd <pid> VM.classloader_stats` |
| `Direct buffer memory` | NIO direct buffers | unreleased buffers, raise `-XX:MaxDirectMemorySize` |
| `unable to create native thread` | OS thread limit / native memory | thread leak; `Thread.print` |

And if the container is killed with **no Java error at all**, memory outside the heap pushed the
process over the container limit. Start the JVM with `-XX:NativeMemoryTracking=summary` and
compare `jcmd <pid> VM.native_memory summary` over time.

## Lab (~10 min)

`Leaky.java` simulates a request handler with a "cache" that never evicts:

```java
import java.util.HashMap;
import java.util.Map;

public class Leaky {
    static final Map<String, byte[]> CACHE = new HashMap<>();   // no eviction: the classic leak

    public static void main(String[] args) throws InterruptedException {
        System.out.println("PID " + ProcessHandle.current().pid());
        long request = 0;
        while (true) {
            String key = "req-" + request++;          // every key is unique, nothing is reused
            CACHE.put(key, new byte[10_000]);         // ~10 KB per request, never removed
            byte[] garbage = new byte[50_000];        // short-lived work: collected normally
            if (request % 100 == 0) Thread.sleep(200);
        }
    }
}
```

1. `javac Leaky.java` then
   `java -Xmx256m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=leak.hprof Leaky`.
   It dies after roughly a minute, leaving time to investigate.
2. In a second terminal: `jcmd` to find the PID, then `jstat -gcutil <pid> 2000`. Watch **O**
   climb after each young GC.
3. `jcmd <pid> GC.class_histogram` twice, 10 seconds apart. Which counts grow together?
4. Let it crash. Confirm `leak.hprof` exists. If you have Eclipse MAT, open it: the dominator tree
   puts `HashMap` at the top; Path to GC Roots leads to `Leaky.CACHE`.
5. Fix it with a bounded LRU and rerun: the old-gen floor goes flat.

```java
static final int MAX_ENTRIES = 1_000;
static final Map<String, byte[]> CACHE = new java.util.LinkedHashMap<>(16, 0.75f, true) {
    @Override
    protected boolean removeEldestEntry(Map.Entry<String, byte[]> eldest) {
        return size() > MAX_ENTRIES;                  // evict least-recently-used beyond the bound
    }
};
```

(If `jcmd`/`jstat` cannot attach on Windows, run the terminal as the same user as the JVM, and
make sure both use the same JDK.)

## Gotchas

- **Don't just raise `-Xmx` for a leak.** It only delays the crash, and makes each full GC and
  heap dump bigger.
- **Heap dumps pause the JVM and hold secrets.** Take them from one instance and store them like
  production data.
- **The histogram's top line is almost always `byte[]` or `String`.** That is normal; look for
  what *grows*, and use retained size to find the owner.
- **Measure the floor after GC, not the current usage.** A heap at 90% just before a young GC is
  normal.
- **`ThreadLocal` + thread pool = leak**, because pool threads never die. Always `remove()` in
  `finally`.
- **Container killed with no Java OOM** means native memory. Use Native Memory Tracking, not a
  heap dump.

## Explain it in 2 minutes

Prompt: "Walk me through debugging a suspected memory leak in production."

- Confirm the shape: post-GC heap floor rising under steady load (GC logs, `jstat`, metrics).
- Cheap clues first: `jcmd GC.class_histogram` twice; what grows?
- Heap dump (`jcmd GC.heap_dump` or `HeapDumpOnOutOfMemoryError`), handled as sensitive.
- MAT: dominator tree by retained size, path to GC roots names the holder.
- Typical causes: unbounded caches, listeners, `ThreadLocal` in pools, bad keys, class loaders.
- Fix the lifecycle, redeploy, confirm the floor is flat; non-heap OOMs need NMT instead.

## Check yourself

1. How do you tell a leak from an undersized heap using only GC logs?
2. What is the difference between shallow and retained size?
3. In `jstat -gcutil`, which column climbs in a classic leak, and which column signals trouble
   when it starts increasing?
4. Why is a `ThreadLocal` on a Tomcat worker thread a leak risk?
5. The pod is OOM-killed but there is no `OutOfMemoryError` in the logs. What tool next?

### Answers

1. Leak: the floor after each collection keeps rising under steady load. Undersized: the floor is
   flat but close to the maximum, with frequent GCs.
2. Shallow is the object alone; retained is everything that would be freed if it became
   unreachable.
3. **O** (old generation % used) climbs; **FGC** (full GC count) increasing signals trouble.
4. Pool threads live forever, so whatever the `ThreadLocal` holds stays reachable unless you call
   `remove()`.
5. Native Memory Tracking: `-XX:NativeMemoryTracking=summary` and `jcmd <pid> VM.native_memory
   summary`, because the growth is outside the heap.
