## Where we are

LLD-DESIGN-1 gave you dependency inversion, and LLD-DESIGN-5 gave you a routine for designing classes.
BE-STORY-10 split a system into services. This lesson answers the question between those two: how do
you decide where the boundaries go, and how do you keep business rules from dissolving into
controllers, entities and framework code as a service grows?

## The problem

ShopKart's `OrderService` is 3,000 lines. The rule "a placed order cannot change" exists in four
places, and one of them is wrong. `Order` is a bag of getters and setters, so anyone can call
`order.setStatus("PAID")`. Testing a discount needs a database and a running Spring context. The word
"customer" means a login to one team, a billing account to another and a delivery address to a third,
so every meeting ends in confusion.

Nothing here is a syntax problem. The model of the business has been lost inside the technology.
**Domain-Driven Design (DDD)** is about finding that model and giving it a home. **Hexagonal
architecture** is one way to keep that home free of frameworks.

## Ubiquitous language

Start with words. A **ubiquitous language** is one shared vocabulary used by developers and the
business, in conversation and in the code.

If the business says "an order is *placed*", the method is `order.place()`, not
`orderService.updateStatus(id, 2)`. When the code reads like the rules, a domain expert can spot a
mistake, and a new developer can learn the business from it.

## Bounded contexts

A **bounded context** is a boundary inside which each word has exactly one meaning. Trying to build
one `Customer` class for the whole company produces a 60-field class that serves nobody. So split the
meaning instead:

```text
 ┌─ Sales ──────────┐   ┌─ Billing ────────┐   ┌─ Shipping ───────┐
 │ Customer:        │   │ Customer:        │   │ Recipient:       │
 │  name, cart,     │   │  tax id, payment │   │  address, phone, │
 │  loyalty tier    │   │  terms, invoices │   │  delivery notes  │
 └──────────────────┘   └──────────────────┘   └──────────────────┘
        same real person, three separate models, linked by an id
```

This is the best tool you have for answering "where should the microservice boundary go?". A service
boundary usually follows a context boundary. Splitting one context across services gives you chatty
calls and shared tables, the distributed monolith from BE-STORY-10. A context does not have to be a
service, though. It can be a module inside a monolith.

When two contexts talk, an **anti-corruption layer** translates between them, so that a legacy
system's or vendor's model does not leak into yours. It is the Adapter pattern (LLD-DESIGN-3) at
system scale.

## Entities and value objects

Inside a context, the building blocks start with a simple question: does this thing have an identity?

An **entity** has an identity that lasts while its data changes. An order is the same order after its
address changes. Two entities are equal if their ids are equal.

A **value object** has no identity. It is defined entirely by its values, and it never changes: five
rupees is five rupees. In Java 21, a record is a natural fit:

```java
record Money(long paise) {
    Money {
        if (paise < 0) throw new IllegalArgumentException("Money cannot be negative");
    }
    Money plus(Money other) { return new Money(paise + other.paise); }
}
```

An invalid `Money` now cannot exist. That removes every "did someone check this?" from the rest of
the code. Replacing a raw `long`, `String` or `BigDecimal` with a small type like this is often the
cheapest improvement DDD offers.

## Aggregates: the consistency boundary

Some rules span several objects: "an order's total equals the sum of its lines". If any code can
change a line directly, nothing protects that rule.

An **aggregate** is a cluster of objects treated as one unit for changes. One entity is the
**aggregate root**, and everything outside may only go through it.

```text
 ┌─ Order aggregate ─────────────────────┐
 │  Order  (root)                        │     Customer and Product live
 │   ├── OrderLine                       │     in other aggregates, so
 │   ├── OrderLine                       │     Order keeps their ids,
 │   └── ShippingAddress (value object)  │     not object references
 └───────────────────────────────────────┘
```

Four rules give aggregates their value:

1. **Only the root is reachable from outside.** You call `order.addLine(...)`, never
   `order.getLines().add(...)`.
2. **The root protects the invariants.** An **invariant** is a rule that must always hold, and the
   aggregate is never left in a state that breaks one.
3. **One transaction changes one aggregate.** Its boundary is the unit of consistency, which keeps
   locks small (DB-SQL-7).
4. **Refer to other aggregates by id.** Holding a `Customer` object inside `Order` would drag in a
   second consistency boundary.

Keep aggregates small. A common mistake is a giant `Customer` holding every order ever placed: every
change locks it and loading it is slow. If a rule truly spans two aggregates, accept **eventual
consistency** between them, using domain events.

## Domain events

A **domain event** is a fact the business cares about, in the past tense: `OrderPlaced`,
`PaymentFailed`. The aggregate records it, and other parts of the system react, without the aggregate
knowing who they are.

```text
Order.place() ──records──► OrderPlaced ──► reserve stock
                                       ──► send confirmation
                                       ──► award loyalty points
```

Within one service, Spring can publish these: a root extending `AbstractAggregateRoot` calls
`registerEvent(...)`, and the events go out when the repository saves it. Across services, publish
through DIST-SYS-3's transactional outbox, because a plain publish after commit can be lost.

Keep two kinds apart: a *domain event* is internal and can change freely, while an *integration event*
on Kafka is a public contract and needs versioning.

Two more building blocks finish the set. A **repository** loads and saves one whole aggregate, so
there is one per aggregate root, not one per table. A **domain service** holds a rule that belongs to
no single entity, such as a pricing calculation across several aggregates.

## Hexagonal architecture: ports and adapters

Now to keep that model clean. In the usual layered design, the service layer depends on the
persistence layer, so business code ends up importing JPA and Kafka. **Hexagonal architecture**, also
called **ports and adapters**, was described by Alistair Cockburn. It turns the dependency around:

```text
   driving side                                            driven side
 ┌──────────────┐     ┌──────────────────────────┐     ┌────────────────┐
 │ REST adapter │───► │ port: PlaceOrder         │     │ JPA adapter    │
 │ Kafka adapter│───► │                          │     │ Stripe adapter │
 │ Test         │───► │  application + domain    │     │ In-memory fake │
 └──────────────┘     │                          │     └───────▲────────┘
                      │ port: OrderRepository ───┼─────────────┘
                      │ port: PaymentGateway  ───┼─────────────┘
                      └──────────────────────────┘
        all source-code dependencies point inward, toward the domain
```

- A **port** is an interface owned by the core.
- A **driving (inbound) port** is what the outside can ask the core to do, such as `PlaceOrder`.
- A **driven (outbound) port** is what the core needs from the outside, such as `OrderRepository`.
- An **adapter** connects a port to a real technology: a REST controller, a JPA repository, a Kafka
  listener.

This is the Dependency Inversion Principle applied to a whole application. The core defines
`PaymentGateway`, and the Stripe adapter implements it, so the core never mentions Stripe. **Onion**
and **Clean Architecture** differ in layer names, and share the same rule: dependencies point inward.

## A package layout in Spring Boot

```text
com.shopkart.orders
 ├── domain          Order, OrderLine, Money, OrderPlaced        no Spring, no JPA
 ├── application     PlaceOrderService; ports: OrderRepository, PaymentGateway
 └── adapter
      ├── in.web     OrderController, request and response DTOs
      ├── in.kafka   PaymentResultListener
      ├── out.db     JpaOrderRepository, OrderJpaEntity, mapper
      └── out.pay    StripePaymentGateway
```

A rule nobody enforces gets broken within months. **ArchUnit** can fail the build when `domain`
imports `jakarta.persistence`, and **Spring Modulith** verifies module boundaries in a modular monolith.

**One trade-off comes up in every real project: is the JPA entity also the domain object?** Separating
them keeps the domain pure, but costs a mapper for each aggregate. Annotating the domain class with
`@Entity` is less code, but JPA then shapes your model, for example by requiring a no-argument
constructor. Many teams accept the annotations and still keep setters out. Either is defensible if
you can say why.

## When not to use this

DDD and hexagonal architecture have a real cost: more types, more mapping, more indirection.

**Use them** where the business rules are complicated, change often and matter: pricing, claims,
bookings, payments.

**Skip them** for simple CRUD, such as an admin table of countries. A controller and a repository are
the right design there, and adding ports only hides the little logic there is. Even inside one
system, the core domain deserves this care and the supporting parts usually do not.

Say this in an interview. Knowing when *not* to apply a pattern is what marks senior judgement.

## Lab (~10 min)

A small hexagon in plain Java, with no framework, which is the point: the business rules run and are
tested with nothing else around them. Press Run, or save it as `OrderLab.java` and run
`java OrderLab.java`.

```java
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Optional;

public class OrderLab {
    // ---- domain: plain Java, knows nothing about the outside ----
    record Money(long paise) {
        Money {
            if (paise < 0) throw new IllegalArgumentException("Money cannot be negative");
        }
        Money plus(Money other) { return new Money(paise + other.paise); }
        Money times(int n) { return new Money(paise * n); }
    }

    record OrderLine(String sku, int quantity, Money unitPrice) {
        Money total() { return unitPrice.times(quantity); }
    }

    record OrderPlaced(String orderId, Money total) {}

    static final class Order {                       // the aggregate root
        private final String id;
        private final List<OrderLine> lines = new ArrayList<>();
        private final List<Object> events = new ArrayList<>();
        private boolean placed;

        Order(String id) { this.id = id; }

        void addLine(String sku, int quantity, Money unitPrice) {
            if (placed) throw new IllegalStateException("A placed order cannot change");
            if (quantity <= 0) throw new IllegalArgumentException("Quantity must be positive");
            lines.add(new OrderLine(sku, quantity, unitPrice));
        }

        void place() {
            if (lines.isEmpty()) throw new IllegalStateException("An empty order cannot be placed");
            placed = true;
            events.add(new OrderPlaced(id, total()));
        }

        Money total() {
            return lines.stream().map(OrderLine::total).reduce(new Money(0), Money::plus);
        }

        String id() { return id; }
        List<Object> pullEvents() {
            List<Object> out = List.copyOf(events);
            events.clear();
            return out;
        }
    }

    // ---- application: ports owned by the core, and one use case ----
    interface OrderRepository {
        void save(Order order);
        Optional<Order> find(String id);
    }

    interface PaymentGateway {
        boolean charge(String orderId, Money amount);
    }

    static final class PlaceOrder {                  // a driving port and its use case
        private final OrderRepository orders;
        private final PaymentGateway payments;

        PlaceOrder(OrderRepository orders, PaymentGateway payments) {
            this.orders = orders;
            this.payments = payments;
        }

        List<Object> handle(String orderId) {
            Order order = orders.find(orderId).orElseThrow();
            order.place();
            if (!payments.charge(order.id(), order.total())) throw new IllegalStateException("Payment declined");
            orders.save(order);
            return order.pullEvents();
        }
    }

    // ---- adapters: swap these without touching anything above ----
    static final class InMemoryOrders implements OrderRepository {
        private final Map<String, Order> store = new HashMap<>();
        public void save(Order order) { store.put(order.id(), order); }
        public Optional<Order> find(String id) { return Optional.ofNullable(store.get(id)); }
    }

    public static void main(String[] args) {
        InMemoryOrders orders = new InMemoryOrders();
        PaymentGateway alwaysPays = (id, amount) -> true;

        Order order = new Order("o-1");
        order.addLine("BOOK", 2, new Money(49_900));
        orders.save(order);

        System.out.println(new PlaceOrder(orders, alwaysPays).handle("o-1"));
        try {
            order.addLine("PEN", 1, new Money(1_000));
        } catch (IllegalStateException e) {
            System.out.println("Rule held: " + e.getMessage());
        }
    }
}
```

**What to observe:**

1. The rule "a placed order cannot change" lives in exactly one place, and no caller can get around
   it, because `lines` is never exposed.
2. Everything ran with no Spring, no database and no network. That is why tests of the core are fast.
3. **Swap an adapter:** replace `alwaysPays` with `(id, amount) -> false`, and nothing above the
   adapter section changes. Then look closely at what `handle` does. The order was marked placed
   *before* payment, and the exception left it that way in memory. Should payment come first? Should
   a declined order be its own state? These are the domain questions a good model makes visible.
4. **Break it:** add `List<OrderLine> lines() { return lines; }` to `Order` and call
   `order.lines().clear()` from `main` after placing. The invariant is gone. One getter undid it.

## Gotchas

- **Anaemic domain model.** Classes with only getters and setters, and all logic in services. It
  looks like DDD and gives none of the safety. Put behaviour on the aggregate.
- **Aggregates that are too big.** Every change locks and loads everything. Design small, and link by id.
- **Changing two aggregates in one transaction.** It couples them and raises contention. Use a domain
  event and accept eventual consistency, or ask whether they are really one aggregate.
- **A shared "common" model across contexts.** It rebuilds the 60-field `Customer`. Duplicate the few
  fields and translate at the edge.
- **Framework imports in the domain.** One `jakarta.persistence` import invites many more. Enforce
  the rule with ArchUnit.
- **Hexagonal for CRUD.** Interfaces with one implementation and mappers that copy fields add cost
  and no value.

## In interviews

Asked as "What is DDD?", "How do you decide microservice boundaries?", "What is an aggregate?",
"Explain hexagonal architecture" and "Entity vs value object?". Bank:
[Microservices patterns: API gateway, service discovery, circuit breaker, saga](#/q/microservices-design-patterns).

**Follow-up: "A rule spans Order and Inventory. What do you do?"** First ask how strict the rule is.
If they must always agree, they may belong in one aggregate. Usually they need not: place the order,
publish `OrderPlaced`, reserve stock, and compensate if reservation fails, which is a saga
(DIST-SYS-3). Mention the business trade-off: for a short time you may accept an order you cannot fill.

**Follow-up: "Isn't hexagonal over-engineering?"** For CRUD, yes. It pays off when the domain is
complex, or when you will swap or add adapters, or want fast tests of the rules. Apply it to the core
domain, and keep the simple parts simple.

## Explain it in 2 minutes

"How would you structure a service with complicated business rules?"

- Agree a shared language with the business and find the bounded contexts first.
- Model the rules in aggregates, which protect invariants and change in one transaction.
- Use value objects so invalid data cannot exist.
- Keep the domain free of frameworks; expose ports, and put JPA, REST and Kafka in adapters.
- Connect aggregates and contexts with domain events, through an outbox across services.
- Apply this to the core domain only; simple CRUD stays simple.

## Check yourself

1. What is a bounded context, and how does it help with microservice boundaries?
2. What is the difference between an entity and a value object? Give an example of each.
3. Why should one transaction change only one aggregate?
4. What is the difference between a driving port and a driven port?
5. What is an anaemic domain model, and why is it a problem?

### Answers

1. A boundary inside which each term has one meaning and one model. Service boundaries usually follow
   context boundaries, which keeps calls and shared data between services low.
2. An entity has a lasting identity even while its data changes, such as an order. A value object is
   defined only by its values and never changes, such as money.
3. The aggregate is the consistency boundary. Changing several in one transaction couples them, raises
   lock contention, and stops working once they live in separate services.
4. A driving port is what the outside asks the core to do (`PlaceOrder`). A driven port is what the
   core needs from outside (`OrderRepository`). The core owns both.
5. Objects with data and no behaviour, with the rules scattered across services. Nothing protects the
   invariants, so the same rule gets duplicated and drifts.
