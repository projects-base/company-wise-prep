## Where we are

- SPRING-BOOT-7 introduced the persistence context, flushing, N+1 queries and `@Transactional`'s rules.
- LIFECYCLE-5 showed that a request's transaction lives *inside* stage 7, the service call.

This lesson follows the two lifecycles that run there:

- **an entity's** (transient → managed → detached or removed);
- **a transaction's** (begin → flush → commit → close).

You'll be able to predict exactly when SQL runs.

## The problem

Here is the core of this repo's `ProgressService.apply`:

```java
@Transactional
public View apply(String slug, Action action, String notes) {
    Progress p = progress.findById(slug).orElseGet(() -> new Progress(slug));
    // ... setters ...
    return View.of(progress.save(p));
}
```

Simple questions about this method have surprising answers.

- When does the `UPDATE` run? (Not at `save`.)
- Is `save` needed for an existing row? (No.)
- Why does a *new* `Progress` cost an extra `SELECT`? (Its id is assigned by hand.)
- If the commit fails, which line throws? (None of these; it's the proxy, after the method returns.)

To answer them you need both lifecycles.

## The persistence context, in one sentence

The **persistence context** is a per-transaction map from (entity type, id) to the one Java object representing that row.

- Alongside each object it keeps a **snapshot** of the values as loaded.
- The `EntityManager` is your handle on it.

Everything below is about whether an object is *in that map* and *what happens when the map is synced with the database*.

## The entity lifecycle at a glance

```text
   new Progress("x")
         │
     TRANSIENT ──────persist()──────────► MANAGED ◄──── find() / query / merge() returns
   (unknown to JPA)                      (in the map,      a managed copy
                                          dirty-checked)
                                           │      │
                       detach() / clear() /│      │ remove()
                       tx ends (EM closed) │      ▼
                                           ▼    REMOVED ──flush──► DELETE
                                       DETACHED   (persist() undoes)
                                     (has an id, not tracked;
                                      changes are ignored)
```

## State 1: transient

**What it is:** a plain `new` object. JPA doesn't know about it, and changes cost nothing.

**Gotcha:** an object with an id you set yourself, like `new Progress("lru-cache")`, is *still transient*. Having an id is not the same as being known to JPA.

## persist(): transient → managed

**What it does:** puts the object into the map and schedules an `INSERT` **for the next flush**. It does not run SQL immediately.

**Gotcha:** with `@GeneratedValue(strategy = IDENTITY)`, Hibernate *must* insert at once to learn the id the database
generated.

- That also disables JDBC insert batching.
- Calling `persist` on a *detached* object throws, because Hibernate sees "detached entity passed to persist".

## State 2: managed, where dirty checking happens

**What it is:** the object is in the map.

- At flush, Hibernate compares every managed object with its snapshot and writes an `UPDATE` for each one that
  changed.
- This is **dirty checking**.

```java
Progress p = progress.findById("lru-cache").orElseThrow();  // managed
p.setStarred(true);                                         // no SQL yet
// method returns → commit → flush → UPDATE progress SET starred=true ...
```

**Gotcha:** for a managed object, `save()` is redundant.

- Many "I forgot to call save but it still saved!" surprises, and "I changed it only for display and it got saved!"
  bugs, come from here.
- Conversely, `@Transactional(readOnly = true)` makes Spring put the Hibernate session into a manual-flush, read-only
  mode.
- Changes made there are **silently not written**.

## flush(): sync the map to the database

**What it does:** runs the pending SQL (inserts, updates, deletes) **inside the current transaction**. It does *not* commit, so other transactions still can't see the changes, and a rollback still undoes them.

Flush happens:

1. before commit;
2. before a JPQL or native query whose result could be affected by pending changes (the default `FlushModeType.AUTO`);
3. when you call `flush()` (or `saveAndFlush`).

**Gotcha:** Hibernate *orders* the statements: inserts first, then updates, and **deletes last**.

- This repo's `DataImporter` hits exactly that.
- It deletes everything, then saves rows with the same ids.
- If both waited for the same flush, the inserts would run before the deletes and collide.
- That is why it uses `deleteAllInBatch()`, a bulk query that runs immediately, followed by `em.flush()`, before
  saving.

## clear() and detach(): managed → detached

**What they do:** `detach(e)` removes one object from the map. `clear()` removes all of them. **When the transaction ends, the context closes, and every object it held becomes detached.**

**Gotchas:**

- `clear()` *discards unflushed changes*. Flush first, as `DataImporter` does with `em.flush(); em.clear();`.
- A detached object's lazy associations throw `LazyInitializationException` when touched. With `open-in-view: false` (this repo), every entity is detached by the time the controller sees it.

## merge(): detached → a managed *copy*

**What it does:** finds the managed object with the same id, loading it with a `SELECT` if it isn't in the map.

- It **copies the detached object's state onto it** and returns *that* managed object.
- The argument stays detached.

```java
Progress managed = em.merge(detached);
detached.setNotes("x");   // ignored: not tracked
managed.setNotes("x");    // will be written at flush
```

**Gotcha:** this is the real reason the new-`Progress` path costs an extra query.

- Spring Data's `save()` calls `persist` if the entity *looks new*, and `merge` otherwise.
- "Looks new" means the id is `null` (or, with a `@Version` field, the version is `null`).
- `Progress` has an assigned `String` id, so `save` always merges.
- Merge issues a `SELECT` to check whether the row exists, then schedules the `INSERT`.
- Fixes: implement Spring Data's `Persistable<String>` with an `isNew()` flag, or add a `@Version Long version`.

## remove(): managed → removed

**What it does:** marks the object for deletion, and the `DELETE` runs at flush. Calling `persist` again before the flush cancels it.

**Gotcha:** `remove` on a *detached* object throws `IllegalArgumentException`.

- Load it first with `find`, or merge it.
- For many rows, a bulk `DELETE` query is far cheaper, but it **bypasses the persistence context**: managed objects in
  memory still look alive.
- That is why `@Modifying(clearAutomatically = true)` exists.

## The transaction lifecycle

A **transaction** is a group of database changes that commit together or roll back together. With Spring, `@Transactional` puts a proxy in front of the bean (SPRING-BOOT-3), and the proxy drives this sequence:

```text
caller ─► proxy (TransactionInterceptor)
  1. read @Transactional: propagation, isolation, readOnly, rollbackFor
  2. JpaTransactionManager.getTransaction(...)
       existing tx on this thread? → propagation decides: join (REQUIRED) / suspend+new (REQUIRES_NEW) / ...
       else: create EntityManager (= new persistence context)
             borrow a JDBC connection from the pool (HikariCP), setAutoCommit(false)
             bind EM + connection to the THREAD (TransactionSynchronizationManager)
  3. invoke your method
       repositories and @PersistenceContext EMs find the thread-bound EM → same map
  4a. returned normally (or threw a checked exception, by default):
       beforeCommit callbacks → FLUSH (dirty check → SQL) → beforeCompletion
       → JDBC COMMIT → afterCommit (@TransactionalEventListener AFTER_COMMIT)
       → afterCompletion → close EM (all entities DETACHED) → connection back to pool
  4b. threw RuntimeException / Error:
       ROLLBACK → afterCompletion(ROLLED_BACK) → close EM
```

**Gotchas at each step:**

- **(2)** The connection is held from begin to end. A slow HTTP call inside a `@Transactional` method holds a pooled connection the whole time, and enough of those exhaust the pool.
- **(2)** `REQUIRED` *joins* the outer transaction. If an inner method throws and marks it rollback-only, the outer method can catch the exception, but its commit then fails with `UnexpectedRollbackException`.
- **(4a)** Constraint violations usually surface **at flush, during commit**, so the exception comes from the proxy
  *after your method returned*.
  - A `try/catch` around `save()` inside the method never sees it.
  - Use `saveAndFlush` when you need the error at that line.
- **(4a)** A checked exception commits by default. Add `rollbackFor = Exception.class` if that's wrong for you.
- **(4a)** `afterCommit` work, such as sending an email, runs after the data is durable. That makes it the right hook for side effects.

## Hooking into entity events

Every state change above can trigger your code. JPA defines seven **callbacks**, each tied to a lifecycle moment:

| Callback | Fires | Typical use |
|---|---|---|
| `@PrePersist` | when `persist()` is called (also for new entities reached by cascade or `merge`) | default values, generate a UUID |
| `@PostPersist` | after the `INSERT` runs (at flush, or at `persist()` with `IDENTITY`) | read a generated id |
| `@PreUpdate` / `@PostUpdate` | around the `UPDATE` at flush, only for dirty entities | `updatedAt`, derived fields |
| `@PreRemove` / `@PostRemove` | at `remove()` / after the `DELETE` | guard rules, cleanup |
| `@PostLoad` | after `find` or a query builds the object | compute transient fields |

```java
@Entity
class Note {
    @Id String id;
    Instant updatedAt;

    @PrePersist @PreUpdate
    void touch() { updatedAt = Instant.now(); }      // no arguments, returns void
}
```

There are four ways to attach such code:

| Way | Example | Choose when | Pitfall |
|---|---|---|---|
| Callback method on the entity | `@PrePersist void touch()` | logic about this entity's own fields | grows into business logic inside the entity |
| `@EntityListeners` class | `@EntityListeners(AuditListener.class)` | one rule reused across entities | the same limits as callbacks (below) |
| Spring Data auditing | `@CreatedDate`, `@LastModifiedBy` + `@EnableJpaAuditing` | who and when created or last modified | records only the latest change, not history; needs `AuditingEntityListener` registered |
| Hibernate event listener | a `PostUpdateEventListener` registered in Hibernate's `EventListenerRegistry` | you need old **and** new values, or one hook for every entity | Hibernate-specific API; Hibernate Envers already builds full history on it |

**Predict:** a JPQL `UPDATE Note n SET n.updatedAt = :now` changes 10,000 rows. How many times does `@PreUpdate`
fire?

Zero. Bulk queries go straight to the database and bypass the persistence context (see remove() above), so no
entity callback or Hibernate entity event runs.

Two more rules from the Jakarta Persistence spec:

1. A callback should not call the `EntityManager`, run queries, or touch other entities, because it runs in the
   middle of a flush.
2. And an exception thrown from a callback marks the transaction for rollback.

**Watch out:** side effects such as emails or messages do not belong in callbacks at all.

- They fire at flush, before commit, so a rollback leaves the email sent.
- Use an `AFTER_COMMIT` `@TransactionalEventListener` (step 4a) for those.

## Lab (~10 min)

Watch both lifecycles print in order. This test uses the repo's real `Progress` entity and `TransactionTemplate` (a programmatic `@Transactional`), so each transaction boundary is visible.

```java
@SpringBootTest(properties = {
        "spring.datasource.url=jdbc:h2:mem:l7lab;DB_CLOSE_DELAY=-1",
        "spring.jpa.show-sql=true"})
class EntityLifecycleLabTest {

    @Autowired EntityManager em;            // a shared proxy: always the CURRENT tx's context
    @Autowired TransactionTemplate tx;

    static void phases() {
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override public void beforeCommit(boolean readOnly) { System.out.println("  -- beforeCommit (flush follows)"); }
            @Override public void afterCommit() { System.out.println("  -- afterCommit"); }
            @Override public void afterCompletion(int status) {
                System.out.println("  -- afterCompletion " + (status == STATUS_COMMITTED ? "COMMITTED" : "ROLLED_BACK"));
            }
        });
    }

    @Test
    void lifecycle() {
        Progress p = new Progress("lab-q1");                                   // TRANSIENT
        tx.executeWithoutResult(s -> {
            phases();
            System.out.println("A contains before persist: " + em.contains(p));
            em.persist(p);                                                     // MANAGED
            System.out.println("B contains after persist: " + em.contains(p) + " (no INSERT yet)");
            p.setStarred(true);                                                // dirty, no save()
            System.out.println("C about to return; watch SQL appear after beforeCommit");
        });
        System.out.println("D tx over: p is DETACHED");

        p.setNotes("edited while detached");
        Progress merged = tx.execute(s -> em.merge(p));
        System.out.println("E merge returned the same object? " + (merged == p));

        tx.executeWithoutResult(s -> {
            Progress managed = em.find(Progress.class, "lab-q1");
            em.remove(managed);                                                // REMOVED
            System.out.println("F removed; contains: " + em.contains(managed) + " (DELETE at commit)");
        });

        try {
            tx.executeWithoutResult(s -> { phases(); em.persist(new Progress("lab-q2")); throw new IllegalStateException("boom"); });
        } catch (IllegalStateException e) {
            System.out.println("G rolled back; row exists? " + (tx.execute(s -> em.find(Progress.class, "lab-q2")) != null));
        }
    }
}
```

**Observe:**

- A is `false` and B is `true`, with **no `insert` line yet**.
  - The SQL appears *after* "beforeCommit".
  - You may see an `insert` followed by an `update` for `starred`.
- At E, the answer is `false`: merge returns a different, managed instance, and you'll see a `select` before the `update`.
- F prints `contains: false`, and the `delete` appears at commit.
- G shows `ROLLED_BACK` and `row exists? false`.
- **Break it:** change the first block to call `em.flush()` right after `persist`, and the `insert` moves *before*
  "C".
  - Then add `s.setRollbackOnly();` as the last line of the first block.
  - It prints `ROLLED_BACK`, and the later `merge` now has to *insert* the row, because no row exists.

## Gotchas

- **Managed entities are saved without `save()`:** map to DTOs if you only adjust values for display.
- **An assigned id makes `save` call `merge`** (extra `SELECT`): implement `Persistable` or add `@Version`.
- **`clear()` drops unflushed changes:** flush first.
- **Flush-time exceptions surface at commit, outside your method:** use `saveAndFlush` to get the error in place.
- **Keep slow I/O out of transactions:** it holds a pooled connection throughout.
- **A caught inner exception can still poison the outer transaction** (`UnexpectedRollbackException`): use
  `REQUIRES_NEW` deliberately, or don't swallow it.

## Explain it in 2 minutes

*"What happens to an entity during a `@Transactional` service call?"*

- The proxy creates an `EntityManager`, borrows a connection, turns auto-commit off, binds both to the thread.
- `find`/queries return managed objects; `persist` makes transient ones managed; nothing written yet.
- Changes are dirty-checked against snapshots; flush emits SQL, inserts first, deletes last.
- Commit: flush, JDBC commit, `afterCommit` hooks, context closes, entities detached; `merge` returns a managed copy.
- Unchecked exceptions roll back; flush-time errors surface at commit, outside your method.

## Check yourself

1. An existing `Progress` is found and starred. When does the `UPDATE` run, and is `save` needed?
2. What's the difference between flush and commit?
3. A `try/catch` around `repository.save(e)` misses a unique-constraint violation. Why?

### Answers

1. At flush during commit, as the method returns through the proxy; `save` is unnecessary, dirty checking finds it.
2. Flush sends SQL inside the open transaction (rollbackable, invisible to others); commit makes it durable and visible.
3. The `INSERT` runs at flush during commit, after the method returned, so the proxy throws; use `saveAndFlush`.
