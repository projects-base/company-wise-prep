## Where we are

In S5 you built a mini Spring: an XML file describing beans, a container that creates and wires them (IoC/DI), and a proxy that adds transactions (AOP). You also saw the cost. Wiring lives in strings the compiler can't check, and a typo fails only at start-up. This lesson moves wiring **into Java itself** with annotations and Java configuration, and introduces **Maven**, which made builds and dependencies reproducible.

## The problem

A mid-2000s Spring app had three configuration problems at once:

1. **XML wiring sprawl.** Hundreds of `<bean>` entries. Renaming a class in the IDE silently broke the XML.
2. **Duplication.** The class already says what it needs (its constructor parameters), and the XML says it again.
3. **Unreproducible builds.** Libraries were JAR files copied into a `lib/` folder by hand. Which version of Hibernate is that, what does it need, and does a teammate have the same set? Nobody could say for sure. Ant build scripts, the common tool of the time, were custom per project.

## Annotations: metadata in the code

An **annotation** is a label attached to a class, method or field, such as `@Override`, that tools and frameworks can read at compile time or runtime. Java 5 (2004) added them to the language. You already wrote one in S5, your own `@Transactional`.

Spring 2.5 (2007) used annotations for wiring:

```java
@Repository                                   // "please create and manage one of these"
public class InMemoryOrderRepository implements OrderRepository { ... }

@Service
public class OrderService {
    private final OrderRepository repository;
    public OrderService(OrderRepository repository) {   // the constructor states the dependency
        this.repository = repository;
    }
}
```

- `@Component`, and its more specific forms `@Service`, `@Repository` and `@Controller`, mark a class as a bean. These are called **stereotype** annotations.
- **Component scanning** is the container searching a package for those annotations, so you no longer list beans by hand.
- **Autowiring** means the container fills constructor parameters (or fields) by **type**: "I need an `OrderRepository`; there is exactly one bean of that type, so use it." Since Spring 4.3, a class with a single constructor needs no `@Autowired` at all.

Rule: **the class declares what it is and what it needs, and the container connects them by type.**

## Java configuration: `@Configuration` and `@Bean`

Some objects can't be annotated because you don't own their source, such as a JDK `Clock` or a library's connection pool. Spring 3.0 (2009) let you describe them in a Java class:

```java
@Configuration
@ComponentScan("shopkart")                    // find @Component/@Service/@Repository classes here
public class AppConfig {

    @Bean                                     // for objects you can't annotate (JDK or library classes)
    public Clock clock() {
        return Clock.systemDefaultZone();
    }
}
```

A `@Bean` method is a factory, and its return value becomes a bean. This is plain Java, so the compiler checks types, the IDE can rename safely, and you can use `if` statements for conditional setup.

Rule: **annotate your own classes and use `@Bean` for everyone else's.**

## The trade-off: wiring becomes implicit

XML was verbose, but you could read the whole object graph in one file. With scanning and autowiring the graph is **spread across annotations** and resolved by the container at start-up. A new failure mode comes with it: **ambiguity**. If two beans match a type, the container refuses to guess:

```text
NoUniqueBeanDefinitionException: No qualifying bean of type 'shopkart.OrderRepository' available:
expected single matching bean but found 2: inMemoryOrderRepository,loggingOrderRepository
```

You resolve it explicitly with `@Primary` ("use this one by default") or `@Qualifier("name")` ("I want that specific one"). You'll trigger exactly this in the lab.

## Annotations reach the web layer

The same idea removed XML from web apps too:

- **Spring MVC's `@Controller` and `@RequestMapping`** (Spring 2.5) replaced the action mappings of S3. Any method on a POJO can handle a URL, and it is testable without a container.
- **Servlet 3.0 (Java EE 6, 2009)** allowed servlets to be declared with `@WebServlet` and registered from code. Spring 3.1 used this (`WebApplicationInitializer`) so that `web.xml` became optional.

```java
@Controller
public class OrderController {
    @RequestMapping("/orders")
    public String list(Model model) {
        model.addAttribute("orders", orderService.findAll());
        return "orders";                               // a view name, as in your S3 front controller
    }
}
```

## Maven: builds by convention

**Apache Maven** (1.0 in 2004 and the much more widely used 2.0 in 2005) replaced hand-written build scripts with **conventions** and a declarative project file, `pom.xml`:

- **A standard layout.** Code goes in `src/main/java` and tests in `src/test/java`. Every Maven project looks the same, so a newcomer knows where things are.
- **Coordinates.** Every library is identified by `groupId:artifactId:version`, for example `org.springframework:spring-context:7.0.6`.
- **A central repository.** Maven downloads libraries from **Maven Central** into a local cache (`~/.m2`) instead of you copying JARs around.
- **Transitive dependencies.** Declare `spring-context` and Maven also fetches what *it* needs (spring-core, spring-beans and so on).
- **A standard lifecycle.** `mvn test` and `mvn package` behave the same in every project: compile, test, package, in that order.

Gradle (2010s) offers the same model with a programmable build script. The ideas carry over.

Rule: **declare what you depend on and let the tool resolve, download and build it the same way everywhere.**

## The new pain: repeated setup

Annotations and Maven removed the XML and the `lib/` folder, but every new web project still needed the same pieces:

```text
- register DispatcherServlet (WebApplicationInitializer)
- @EnableWebMvc + JSON message converters (Jackson)
- a DataSource + connection pool + its settings
- a transaction manager + @EnableTransactionManagement
- logging configuration
- choose ~20 library versions that are compatible with each other
- build a WAR, install Tomcat separately, deploy into it
```

Every team copied that from its last project, which gives copy-paste drift, version clashes and an hour of setup before the first line of business code. **S7 automates exactly this list.**

## Lab (~10 min)

**Build:** port the S5 mini-Spring app to real Spring with annotations. In IntelliJ create a Maven project (IntelliJ bundles Maven, so no install is needed) with this `pom.xml`:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.example</groupId>
    <artifactId>shopkart-s6</artifactId>
    <version>0.1.0</version>

    <properties>
        <maven.compiler.release>21</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    </properties>

    <dependencies>
        <dependency>
            <groupId>org.springframework</groupId>
            <artifactId>spring-context</artifactId>
            <version>7.0.6</version>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.13.0</version>
                <configuration>
                    <parameters>true</parameters>  <!-- keep parameter names; Spring uses them -->
                </configuration>
            </plugin>
        </plugins>
    </build>
</project>
```

Put these in `src/main/java/shopkart/`: `OrderRepository` (an interface with `save(String)` and `List<String> findAll()`), the annotated `InMemoryOrderRepository` and `AppConfig` shown above, and:

```java
package shopkart;

import java.time.Clock;
import java.time.LocalTime;
import org.springframework.stereotype.Service;

@Service
public class OrderService {
    private final OrderRepository repository;
    private final Clock clock;

    // Constructor injection: with a single constructor, no @Autowired is needed.
    public OrderService(OrderRepository repository, Clock clock) {
        this.repository = repository;
        this.clock = clock;
    }

    public void placeOrder(String item) {
        repository.save(item + " @ " + LocalTime.now(clock).withNano(0));
    }

    public OrderRepository repository() { return repository; }
}
```

```java
package shopkart;

import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class Main {
    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(AppConfig.class)) {
            OrderService service = context.getBean(OrderService.class);
            service.placeOrder("book");
            service.placeOrder("pen");
            System.out.println("Saved: " + service.repository().findAll());
            System.out.println("Repository in use: " + service.repository().getClass().getSimpleName());
            for (String name : context.getBeanDefinitionNames()) {
                if (!name.startsWith("org.springframework")) System.out.println("bean: " + name);
            }
        }
    }
}
```

**Observe:** the beans listed are `appConfig`, `inMemoryOrderRepository`, `orderService` and `clock`. Bean names come from the class name with a lowercase first letter, or from the `@Bean` method name. There is no XML anywhere. In IntelliJ's Maven tool window (or `mvn dependency:tree`), note that one dependency brought in several others: spring-aop, spring-beans, spring-core, spring-expression and more.

**Break:** add a second repository:

```java
@Repository
public class LoggingOrderRepository implements OrderRepository {
    private final List<String> rows = new ArrayList<>();
    public void save(String order) { System.out.println("LOG save " + order); rows.add(order); }
    public List<String> findAll() { return rows; }
}
```

Run it. Start-up fails with `NoUniqueBeanDefinitionException ... expected single matching bean but found 2`. This is the start-up check that XML never gave you for free.

**Fix:** add `@Primary` to `LoggingOrderRepository` and run again. "LOG save" lines appear and `Repository in use: LoggingOrderRepository`. Alternatively, put `@Qualifier("inMemoryOrderRepository")` on the constructor parameter.

**Count:** list what you'd still need to add to make this a web app with a database (use the "new pain" list above). That list is S7's starting point.

## Gotchas

- **Component scan only sees its packages.** A bean in a package outside the scanned base package is silently not created, and you then get "no qualifying bean". Keep the configuration class at the root package.
- **Two beans of one type means start-up failure.** Use `@Primary` for a default and `@Qualifier` for a specific choice. Don't rely on parameter names happening to match bean names, because that is fragile.
- **`@Configuration` vs plain `@Component` with `@Bean` methods.** In a `@Configuration` class, calling one `@Bean` method from another returns the *same* singleton, because Spring proxies the class. In a plain `@Component` you get a new object on each call.
- **Transitive version conflicts.** Two libraries can pull in different versions of a third. Maven picks one ("nearest wins") and runtime errors such as `NoSuchMethodError` follow. Inspect with `mvn dependency:tree` and pin versions with `dependencyManagement` or a BOM.
- **Missing `-parameters`.** Some Spring features use constructor and method parameter names, and Spring 6.1+ needs the compiler's `-parameters` flag to see them. The pom above sets it, and Spring Boot's parent POM does too.

Typical follow-ups:

- *"Constructor vs setter vs field injection: which and why?"* Constructor for required dependencies (immutable, explicit, easy to test), setter for genuinely optional ones, and field injection avoided outside tests.
- *"Two beans implement the same interface. What happens and how do you choose?"* Start-up fails with `NoUniqueBeanDefinitionException`. Resolve with `@Primary`, `@Qualifier`, or by injecting `List<OrderRepository>` or `Map<String, OrderRepository>` to receive all of them.

## Explain it in 2 minutes

*"How did Spring configuration evolve from XML to annotations, and what did Maven add?"*

A good answer hits:

1. XML: an explicit graph in one place, but verbose, stringly-typed and duplicating what the classes already said.
2. Java 5 annotations led to **stereotypes plus component scanning plus autowiring by type** (Spring 2.5). The class declares itself and its needs.
3. **`@Configuration` and `@Bean`** (Spring 3.0): type-checked Java for third-party objects.
4. Trade-off: implicit wiring, so ambiguity is a start-up error resolved with `@Primary` or `@Qualifier`.
5. **Maven**: standard layout, coordinates, Central, transitive dependencies, a standard lifecycle, with version conflicts as the new risk.
6. Remaining pain: every project repeats the same infrastructure setup and still deploys a WAR to an external server.

1. What does `@ComponentScan("shopkart")` do?
2. When do you write a `@Bean` method instead of annotating a class?
3. What error did the second repository cause, and why?
4. What is a transitive dependency?
5. What setup still had to be repeated in every web project after annotations and Maven?

### Answers

1. It searches the `shopkart` package and its sub-packages for stereotype-annotated classes and registers each as a bean.
2. When you can't or shouldn't change the class's source, as with JDK or library types, or when creation needs logic.
3. `NoUniqueBeanDefinitionException`. `OrderService` needs one `OrderRepository` and two beans match by type, so Spring refuses to guess.
4. A library your dependency needs, which Maven downloads automatically even though you didn't declare it.
5. DispatcherServlet registration, MVC and JSON setup, a DataSource and pool, a transaction manager, logging, choosing compatible library versions, and building a WAR to deploy into a separately installed server.
