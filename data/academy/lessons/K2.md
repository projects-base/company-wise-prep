## Where we are

After CAPSTONE-1 your repo has the TicketHub domain in plain Java: the `Venue`, `Seat`, `Event` and `SeatHold` records, the `Booking` class with its `BookingStatus` state machine, and the `TicketHubException` hierarchy, all tested against a fixed `Clock`. Nothing *does* anything yet. Today you add the engine that holds and sells seats. It is still in memory, but it is already correct when many threads compete for the same seat.

## Goal

Build an `EventCatalog` (venues, events and seats loaded from a JSON file with Jackson) and a `BookingEngine` that can **hold** seats with an expiry, **confirm** a hold into a `Booking`, and **release** a hold. Collections and streams do the bookkeeping. The engine must be thread-safe: when 32 threads grab the same seat at the same instant, exactly one wins, and an overlapping multi-seat hold never claims only part of its seats. You prove both with a concurrent test using an `ExecutorService`. This engine is what CAPSTONE-3 wraps in Spring and CAPSTONE-5 replaces with PostgreSQL. Its behaviour (the tests) carries over.

## What you build

- [ ] `EventNotFoundException` (`event`, code `EVENT_NOT_FOUND`) and `HoldNotFoundException` (`booking`, code `HOLD_NOT_FOUND`)
- [ ] `event.EventCatalog`: immutable lookups (event by id, venue of an event, seats of an event, upcoming events)
- [ ] `event.SeedLoader`: reads `seed/dev-seed.json` into an `EventCatalog` with Jackson
- [ ] `booking.SeatAvailability(Seat seat, boolean available)` record
- [ ] `booking.BookingEngine`: `hold`, `confirm`, `release`, `seatMap`, all thread-safe
- [ ] Unit tests driven by the `MutableClock` from CAPSTONE-1, plus a concurrency test class

## Steps

### 1. Two more exceptions (3 min)

They have the same shape as CAPSTONE-1's: `EventNotFoundException(long eventId)` and `HoldNotFoundException(UUID holdId)`, both extending `TicketHubException`. CAPSTONE-4 maps all of the `*_NOT_FOUND` codes to 404.

### 2. The catalog: collections and streams (10 min)

The catalog is read-only after loading, so it uses plain immutable maps. Immutable data is thread-safe for free.

```java
package com.tickethub.event;

import java.time.Instant;
import java.util.*;
import java.util.function.Function;
import java.util.stream.Collectors;

public final class EventCatalog {
    private final Map<Long, Venue> venues;
    private final Map<Long, Event> events;
    private final Map<Long, List<Seat>> seatsByVenue;

    public EventCatalog(Collection<Venue> venues, Collection<Event> events) {
        // toUnmodifiableMap throws IllegalStateException on a duplicate id: fail loud on bad seed data
        this.venues = venues.stream().collect(Collectors.toUnmodifiableMap(Venue::id, Function.identity()));
        this.events = events.stream().collect(Collectors.toUnmodifiableMap(Event::id, Function.identity()));
        this.seatsByVenue = venues.stream().collect(Collectors.toUnmodifiableMap(Venue::id, Venue::seats));
        events.stream()
                .filter(e -> !this.venues.containsKey(e.venueId()))
                .findFirst()
                .ifPresent(e -> { throw new IllegalArgumentException("event " + e.id() + " has unknown venue"); });
    }

    public Event event(long eventId) {
        Event event = events.get(eventId);
        if (event == null) throw new EventNotFoundException(eventId);
        return event;
    }

    public Venue venueOf(long eventId) { return venues.get(event(eventId).venueId()); }

    public List<Seat> seatsOf(long eventId) { return seatsByVenue.get(event(eventId).venueId()); }

    public List<Event> upcoming(Instant now) {
        return events.values().stream()
                .filter(e -> e.startsAt().isAfter(now))
                .sorted(Comparator.comparing(Event::startsAt).thenComparing(Event::id))
                .toList();
    }
}
```

The `thenComparing(Event::id)` tie-breaker matters. Without it, two events that start at the same time come back in hash order, and pagination in CAPSTONE-4 would show an event twice or skip it.

```java
package com.tickethub.event;

import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.datatype.jsr310.JavaTimeModule;
import java.io.IOException;
import java.io.InputStream;
import java.util.List;

public final class SeedLoader {
    public record Seed(List<Venue> venues, List<Event> events) {}

    private final ObjectMapper mapper = new ObjectMapper().registerModule(new JavaTimeModule());

    public EventCatalog load(InputStream json) throws IOException {
        Seed seed = mapper.readValue(json, Seed.class);
        return new EventCatalog(seed.venues(), seed.events());
    }
}
```

Jackson 2.12+ creates records through their canonical constructor, so **your invariants run on seed data too**. A venue with `"rows": 0` fails at load time, not at the first booking. Unknown JSON fields fail by default (`FAIL_ON_UNKNOWN_PROPERTIES`). Keep it that way, because a typo such as `"seatPerRow"` should stop startup. `failsOnUnknownField` proves it.

### 4. The engine and the thread-safety decision (20 min)

**The problem.** Holding seats is a *check-then-act*: "are seats 1001 and 1002 free? then claim them". If two threads both check before either acts, both see the seats as free and both claim them. That is a double booking.

You have three options:

| Option | Correct? | Cost |
|---|---|---|
| `synchronized` on every engine method | Yes | Every event's bookings queue behind one lock, so a sell-out at one venue slows all the others. |
| `ConcurrentHashMap<seatId, Claim>` with one `compute` per seat | **No** for multi-seat holds | Seat 1001 is claimed, then 1002 turns out to be taken: you must roll 1001 back, and others saw it as taken in between. |
| `ConcurrentHashMap<eventId, Map<seatId, Claim>>` with one `compute` per **event** | Yes | Holds on one event take turns; different events run in parallel. |

The third option is the one to build. `ConcurrentHashMap.compute(key, fn)` runs `fn` **atomically for that key**: no other `compute` on the same key can interleave. If `fn` throws, the mapping is left unchanged and the exception reaches the caller. So "check all seats, then claim all of them, or throw" becomes one atomic step, with the lock scoped to one event. That is **lock striping**: the data is split into independently locked parts.

The inner map is **copy-on-write**. Each `compute` builds a new immutable `Map` and swaps it in. Readers such as `seatMap` call `get` without any lock. Because they only ever see a complete, immutable snapshot, they never see a half-updated `HashMap`. Copying is O(seats in the venue), which is fine at under 1,000 seats.

```java
package com.tickethub.booking;

import com.tickethub.event.EventCatalog;
import java.time.*;
import java.util.*;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentMap;

public final class BookingEngine {
    private record Claim(UUID holdId, Instant expiresAt, boolean sold) {
        boolean blocks(Instant now) { return sold || now.isBefore(expiresAt); }
    }

    private final EventCatalog catalog;
    private final Clock clock;
    private final Duration holdDuration;
    private final ConcurrentMap<Long, Map<Long, Claim>> claimsByEvent = new ConcurrentHashMap<>();
    private final ConcurrentMap<UUID, SeatHold> holds = new ConcurrentHashMap<>();
    private final ConcurrentMap<UUID, Booking> bookingsByHold = new ConcurrentHashMap<>();

    public BookingEngine(EventCatalog catalog, Clock clock, Duration holdDuration) {
        this.catalog = catalog;
        this.clock = clock;
        this.holdDuration = holdDuration;
    }

    public SeatHold hold(long eventId, String userId, List<Long> seatIds) {
        SeatHold hold = SeatHold.create(catalog.event(eventId).id(), userId, seatIds, clock, holdDuration);
        Set<Long> known = new HashSet<>(catalog.seatsOf(eventId).stream().map(s -> s.id()).toList());
        List<Long> unknown = hold.seatIds().stream().filter(id -> !known.contains(id)).toList();
        if (!unknown.isEmpty()) throw new SeatUnavailableException(eventId, unknown);

        claimsByEvent.compute(eventId, (id, current) -> {
            Map<Long, Claim> claims = current == null ? new HashMap<>() : new HashMap<>(current);
            Instant now = clock.instant();
            List<Long> taken = hold.seatIds().stream()
                    .filter(s -> claims.containsKey(s) && claims.get(s).blocks(now))
                    .toList();
            if (!taken.isEmpty()) throw new SeatUnavailableException(eventId, taken);   // nothing changes
            hold.seatIds().forEach(s -> claims.put(s, new Claim(hold.id(), hold.expiresAt(), false)));
            return Map.copyOf(claims);
        });
        holds.put(hold.id(), hold);
        return hold;
    }

    public List<SeatAvailability> seatMap(long eventId) {
        Map<Long, Claim> claims = claimsByEvent.getOrDefault(eventId, Map.of());
        Instant now = clock.instant();
        return catalog.seatsOf(eventId).stream()
                .map(seat -> new SeatAvailability(seat, !(claims.containsKey(seat.id()) && claims.get(seat.id()).blocks(now))))
                .toList();
    }
}
```

An expired hold needs no cleanup to free its seats: `blocks(now)` is false once `expiresAt` passes. This is **lazy expiry**. CAPSTONE-7 adds a scheduled sweeper so expired holds do not pile up in memory.

**Confirm and release.** One rule decides every race between them: `holds.remove(holdId)` is atomic, so **whoever removes the hold first wins**. Confirm removes it inside the event's `compute`, then marks the seats as sold. Release removes it first, then drops the unsold claims. Confirm also runs inside `bookingsByHold.computeIfAbsent`, so two concurrent confirms of the same hold produce exactly one booking, and a retry returns that same booking.

```java
    public Booking confirm(UUID holdId) {
        return bookingsByHold.computeIfAbsent(holdId, id -> {
            SeatHold hold = holds.get(id);
            if (hold == null) throw new HoldNotFoundException(id);
            claimsByEvent.compute(hold.eventId(), (eventId, current) -> {
                if (hold.isExpiredAt(clock.instant())) throw new HoldExpiredException(id);
                if (holds.remove(id) == null) throw new HoldNotFoundException(id);   // released meanwhile
                Map<Long, Claim> claims = new HashMap<>(current);
                hold.seatIds().forEach(s -> claims.put(s, new Claim(id, hold.expiresAt(), true)));
                return Map.copyOf(claims);
            });
            // The tier's base price; CAPSTONE-7 adds pricing rules on top.
            return Booking.confirmedFrom(hold, catalog.event(hold.eventId()).priceCategory().centsPerSeat(), clock);
        });
    }

    public void release(UUID holdId) {
        SeatHold hold = holds.remove(holdId);
        if (hold == null) throw new HoldNotFoundException(holdId);
        claimsByEvent.computeIfPresent(hold.eventId(), (eventId, current) -> {
            Map<Long, Claim> claims = new HashMap<>(current);
            claims.values().removeIf(c -> c.holdId().equals(holdId) && !c.sold());
            return Map.copyOf(claims);
        });
    }
```

Calling `compute` on `claimsByEvent` from inside `computeIfAbsent` on `bookingsByHold` is safe. They are different maps, and the locks are always taken in the same order (bookings, then claims), so there is no deadlock. The rule that `ConcurrentHashMap` does forbid is touching **the same map** from inside its own mapping function.

**Break it** (acceptance criterion): replace the `compute` in `hold` with `Map<Long, Claim> current = claimsByEvent.get(eventId); ... claimsByEvent.put(eventId, ...)`. Run the 32-thread test in the loop and watch winners become 2 or more. Then restore `compute`.

### 5. Tests, including the concurrent one (15 min)

Use the `MutableClock` from CAPSTONE-1 and the dev seed. Event 1 is in venue 1, so its seats are `1001` to `1200`.

```java
@Test
void expiredHoldFreesSeats() {
    engine.hold(1, "alice", List.of(1001L));
    clock.advance(Duration.ofMinutes(10));   // exactly expiresAt

    assertThat(engine.hold(1, "bob", List.of(1001L)).userId()).isEqualTo("bob");
}

@Test
void confirmCreatesBookingWithTotalInCents() {
    SeatHold hold = engine.hold(1, "alice", List.of(1001L, 1002L));
    Booking booking = engine.confirm(hold.id());

    assertThat(booking.totalCents()).isEqualTo(2 * PriceCategory.PREMIUM.centsPerSeat());   // event 1 is PREMIUM
    assertThat(engine.seatMap(1).stream().filter(SeatAvailability::available).count()).isEqualTo(198);
}
```

The concurrent test uses a **start gate**: a `CountDownLatch(1)` that every task waits on, so all the threads hit `hold` at once instead of one after another. `ExecutorService` is `AutoCloseable` since Java 19, and `close()` waits for the tasks to finish.

```java
@Test
void exactlyOneOf32ThreadsWinsTheSameSeat() throws Exception {
    int threads = 32;
    CountDownLatch startGate = new CountDownLatch(1);
    List<Future<Boolean>> results = new ArrayList<>();

    try (ExecutorService pool = Executors.newFixedThreadPool(threads)) {
        for (int i = 0; i < threads; i++) {
            String user = "user-" + i;
            results.add(pool.submit(() -> {
                startGate.await();
                try {
                    engine.hold(1, user, List.of(1001L));
                    return true;
                } catch (SeatUnavailableException e) {
                    return false;
                }
            }));
        }
        startGate.countDown();
    }

    long winners = 0;
    for (Future<Boolean> f : results) if (f.get(5, TimeUnit.SECONDS)) winners++;
    assertThat(winners).isEqualTo(1);
}
```

Write `overlappingHoldsNeverClaimPartially` the same way: half the threads try to hold `[1001, 1002]` and half `[1002, 1003]`. Afterwards, assert that exactly one hold succeeded, and that the seat only the losers asked for (1001 or 1003) is still available in `seatMap`.

## Hints

- **The lambda in `compute` must be quick and must not block** (no I/O, no sleeping). Other threads waiting on that key are stuck behind it.
- **`claims.get(s).blocks(now)` after a `containsKey` check is fine here**, because `claims` is your private copy. Doing the same on a shared map would be its own check-then-act race.
- **`Future.get()` with no timeout can hang a test forever** if you introduce a deadlock. Always pass a timeout.
- **If the concurrency test passes even with the broken `get`/`put`**, raise the thread count and add a `Thread.onSpinWait()` loop of a few hundred iterations between the get and the put to widen the window. Do this only in the broken version.
- `catalog.event(eventId).id()` in `hold` exists to throw `EventNotFoundException` early. Without it, an unknown event would surface as a `NullPointerException` deep in `seatsOf`.

## Talk about it in interviews

**"How do you prevent two users booking the same seat?"**
- *What:* the claim must be an atomic check-then-act, scoped as narrowly as correctness allows.
- *How it works inside:* in memory, `ConcurrentHashMap.compute` locks only that key's bin while the function runs. The function checks every requested seat and either claims them all or throws, and on a throw the map is unchanged. In a database (CAPSTONE-5) the same idea becomes a transaction plus optimistic locking on `event_seat`.
- *Where used:* TicketHub locks per event, so different events never contend. The 32-thread start-gate test proves exactly one winner.
- *What goes wrong:* a `get`-then-`put` race (you broke it on purpose and watched it fail). Per-seat locking makes multi-seat holds non-atomic. One global `synchronized` is correct but serialises unrelated traffic. And none of this works across two app instances, which is why the database or Redis must own the truth in production.

**"`synchronized` vs `ConcurrentHashMap` — when do you use which?"** `synchronized` gives you one monitor and simple reasoning. It is fine when the critical section is short and contention is low. `ConcurrentHashMap` gives you lock-free reads and per-bin locking for writes, and `compute`/`merge`/`computeIfAbsent` give you atomic read-modify-write on one key. Choose based on the **unit of atomicity** your invariant needs. Here that is "all seats of one hold, within one event".

**"How do you test concurrent code?"** Use a start gate (`CountDownLatch`) so the threads truly overlap, a fixed pool, timeouts on every `Future.get`, and an assertion on an invariant ("exactly one winner") rather than on timing. Run it in a loop, and prove the test can fail by breaking the code once. A concurrency test that has never failed proves nothing.

**"Why fail on unknown JSON fields?"** Fail fast: a misspelled field silently becomes a default value, and the bug shows up far from its cause. Records plus Jackson also run your constructor invariants on input data.
