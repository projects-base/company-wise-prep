## Where we are

From B2 you can protect shared state with `synchronized` or `ReentrantLock`, and you know that locks can deadlock. This lesson covers the lock-free tools: **atomic variables** built on a CPU instruction called compare-and-swap, the **concurrent collections** that the JDK builds on top of them, and a few small **coordinators** (latches, semaphores) that let threads wait for each other.

## The problem

Locks work, but they have costs. A thread that cannot get a lock is suspended, and waking it up again costs a trip through the operating system, typically microseconds. For a hot counter that is incremented millions of times, that cost dominates the work. Locks also bring the risk of deadlock.

For the common case of updating a single variable, the hardware offers something cheaper.

## Compare-and-swap (CAS)

**Compare-and-swap** is a single CPU instruction that says: "if this memory location still holds the value I expect, replace it with the new value; either way, tell me whether it worked." It is atomic in hardware, so no other thread can slip in between the compare and the swap.

Java exposes it as `compareAndSet`:

```java
AtomicInteger count = new AtomicInteger(0);

boolean ok = count.compareAndSet(5, 6);   // true only if count was 5; then it becomes 6
```

You can build a safe increment out of CAS with a **retry loop**:

```java
int increment(AtomicInteger c) {
    while (true) {
        int current = c.get();
        int next = current + 1;
        if (c.compareAndSet(current, next)) return next;  // nobody changed it: done
        // another thread won the race: loop, re-read, try again
    }
}
```

No thread ever waits for another. A thread that loses simply retries. Code like this, where some thread always makes progress, is called **lock-free**.

## Atomic classes

You rarely write the loop yourself. `java.util.concurrent.atomic` gives you ready-made classes:

- `AtomicInteger` and `AtomicLong`, with methods such as `incrementAndGet()`, `addAndGet(n)`, `updateAndGet(x -> x * 2)` and `accumulateAndGet(n, Math::max)`.
- `AtomicBoolean`, typically used for "run once" flags: `if (started.compareAndSet(false, true)) { ... }`.
- `AtomicReference<T>`, which does CAS on an object reference. You use it to swap a whole immutable object in one step.

Atomics also give visibility. A successful CAS behaves like a `volatile` write, and `get()` behaves like a `volatile` read.

Rule: **the function you pass to `updateAndGet` may run several times** if other threads keep winning the race, so it must have no side effects.

## The limits of atomics

**One variable only.** Two atomics are not atomic *together*:

```java
// BROKEN: another thread can change 'low' between these two lines
if (value.get() > low.get()) high.set(value.get());
```

When several variables must change together, either use a lock or put them into one immutable object and CAS an `AtomicReference` to it.

**The ABA problem.** CAS checks the *value*, not the *history*. Say a thread reads `A`. Meanwhile another thread changes it to `B` and then back to `A`. The first thread's CAS still succeeds. For counters this is harmless. For pointer-based structures such as a lock-free stack, it can corrupt the structure, because the node at the top may have been removed and reused in the meantime. `AtomicStampedReference` fixes this by pairing the value with a version number that is checked as well.

**Contention.** When many threads hammer one atomic, most of their CAS attempts fail and they retry, which wastes CPU.

## `LongAdder`: a counter built for contention

`LongAdder` spreads the count across several internal cells. When threads collide, they are steered to different cells, and `sum()` adds up all the cells.

```java
LongAdder hits = new LongAdder();
hits.increment();          // cheap, even with many threads
long total = hits.sum();   // not an atomic snapshot while writers are active
```

Use `LongAdder` for metrics and statistics counters that are written often and read rarely. Use `AtomicLong` when you need the exact current value or a CAS, for example to hand out unique ids.

## Concurrent collections: why not just synchronize a `HashMap`?

`Collections.synchronizedMap(new HashMap<>())` wraps every method in a single lock. That has three problems:

1. Every reader and writer queues on the same lock.
2. **Compound actions are still broken.** `if (!map.containsKey(k)) map.put(k, v)` is two calls, and another thread can run in between.
3. Iterating requires you to hold the lock manually, or you get a `ConcurrentModificationException`.

## `ConcurrentHashMap`

`ConcurrentHashMap` (CHM) is the default thread-safe map. Since Java 8:

- **Reads take no lock.** They are effectively `volatile` reads of the table.
- **Writes lock only one bin**, the slot that the key hashes to. An empty bin is filled with a CAS. Otherwise the thread synchronizes on that bin's first node. Writes to different bins proceed in parallel.
- **Compound actions are built in and atomic per key:** `putIfAbsent`, `computeIfAbsent`, `compute`, `merge`.

```java
ConcurrentHashMap<String, Integer> counts = new ConcurrentHashMap<>();
counts.merge(word, 1, Integer::sum);                          // atomic "increment or insert 1"
cache.computeIfAbsent(key, k -> expensiveLoad(k));            // loads at most once per key
```

There are some facts about CHM that interviewers like to check:

- **No `null` keys or values.** A `null` from `get` must mean "absent". Otherwise you could not tell "absent" from "mapped to null" without a second, racy call.
- **Iterators are weakly consistent.** They never throw `ConcurrentModificationException`. They may or may not reflect changes made while you iterate.
- **`size()` is an estimate** while writers are active.
- **Keep the function you pass to `compute` short.** It runs while the bin is locked. It must not update other keys of the same map: that can throw `IllegalStateException("Recursive update")` or deadlock.

Two other collections are worth knowing. `CopyOnWriteArrayList` copies the whole array on every write. That suits lists that are read constantly and written rarely, such as listener lists. `ConcurrentLinkedQueue` is a lock-free, unbounded queue.

## Blocking queues

A **blocking queue** is a queue where `put` waits while the queue is full and `take` waits while it is empty. It is the backbone of producer-consumer designs, which B7 builds by hand.

| Method | When full or empty |
|---|---|
| `put` / `take` | block until possible |
| `offer` / `poll` | return `false` / `null` immediately |
| `offer(e, t, unit)` / `poll(t, unit)` | wait up to a timeout |

The main implementations:

- `ArrayBlockingQueue(n)`: bounded, backed by an array, one lock.
- `LinkedBlockingQueue`: optionally bounded, with separate locks for putting and taking. **With no argument, its capacity is `Integer.MAX_VALUE`, which is effectively unbounded.** B4 shows why that is dangerous.
- `SynchronousQueue`: has no capacity at all. Each `put` waits for a matching `take`. It is a direct hand-off.
- `PriorityBlockingQueue` and `DelayQueue`: unbounded and ordered, by priority and by delay respectively.

## Coordinators

These classes let threads wait for each other without sharing any data:

- **`CountDownLatch(n)`.** Threads call `await()` until `countDown()` has been called `n` times. It is one-shot and cannot be reset. Typical uses are "start all workers at the same moment" and "wait for N services to come up".
- **`CyclicBarrier(n)`.** `n` threads wait for each other at a barrier, and then the barrier resets for the next round.
- **`Semaphore(permits)`.** `acquire()` takes a permit and waits if none are left; `release()` returns one. You use it to *limit concurrency*, for example "at most 10 calls to this API at once".

A semaphore is **not** a mutex. A mutex has an owner, and only the thread that locked it may unlock it. A semaphore has no owner: any thread may call `release()`, and a semaphore can admit N threads, not just one.

## Lab (~10 min)

Save this as `Atomics.java` and run it with `java Atomics.java`.

```java
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;

public class Atomics {
    static final int THREADS = 4, PER_THREAD = 2_000_000;
    static volatile int unsafeCount;
    static int lockedCount;

    public static void main(String[] args) throws Exception {
        // Part 1: one counter, four implementations
        time("volatile (broken)", () -> unsafeCount++);
        System.out.println("   = " + unsafeCount);

        Object lock = new Object();
        time("synchronized    ", () -> { synchronized (lock) { lockedCount++; } });
        System.out.println("   = " + lockedCount);

        AtomicInteger atomic = new AtomicInteger();
        time("AtomicInteger   ", atomic::incrementAndGet);
        System.out.println("   = " + atomic.get());

        LongAdder adder = new LongAdder();
        time("LongAdder       ", adder::increment);
        System.out.println("   = " + adder.sum() + "   (expected " + THREADS * PER_THREAD + ")");

        // Part 2: check-then-act on a ConcurrentHashMap
        List<String> words = List.of("a", "b", "c", "d");
        Map<String, Integer> broken = new ConcurrentHashMap<>(), fixed = new ConcurrentHashMap<>();
        runAll(() -> {
            for (int i = 0; i < 100_000; i++) {
                String w = words.get(i % 4);
                Integer c = broken.get(w);                 // check...
                broken.put(w, c == null ? 1 : c + 1);      // ...then act: RACE
                fixed.merge(w, 1, Integer::sum);           // atomic per key
            }
        });
        System.out.println("broken: " + new TreeMap<>(broken));
        System.out.println("fixed:  " + new TreeMap<>(fixed) + "  (expected 100000 each)");
    }

    static void time(String name, Runnable increment) throws InterruptedException {
        long t0 = System.nanoTime();
        runAll(() -> { for (int i = 0; i < PER_THREAD; i++) increment.run(); });
        System.out.printf("%s %5d ms", name, (System.nanoTime() - t0) / 1_000_000);
    }

    // Start THREADS threads at the same instant (a "starting gun") and wait for all of them.
    static void runAll(Runnable body) throws InterruptedException {
        CountDownLatch start = new CountDownLatch(1), done = new CountDownLatch(THREADS);
        for (int t = 0; t < THREADS; t++) {
            Thread.ofPlatform().start(() -> {
                try { start.await(); body.run(); }
                catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                finally { done.countDown(); }
            });
        }
        start.countDown();   // fire
        done.await();
    }
}
```

What you should observe:

1. The `volatile` count is well below 8,000,000. The other three are exactly 8,000,000.
2. Timings vary by machine, but `LongAdder` is usually the fastest under contention, and `synchronized` is often the slowest. Do not treat this as a benchmark: proper measurement needs JMH (A8). The point is that correctness differs, not the exact numbers.
3. `broken` shows counts below 100,000 for each word even though the map is a `ConcurrentHashMap`. **A thread-safe map does not make your two calls atomic.** `fixed` is exact.

**Break it further:** replace `merge` with `fixed.compute(w, (k, v) -> v == null ? 1 : v + 1)`. It is still exact, because `compute` is atomic per key too.

## Gotchas

- **Check-then-act on a concurrent collection.** `get` followed by `put`, or `containsKey` followed by `put`, races. Use `merge`, `compute`, `computeIfAbsent` or `putIfAbsent`.
- **Side effects inside `updateAndGet` or `compute`.** The atomic lambda may be retried, and the CHM lambda runs while a bin is locked. Keep them pure and short, and never touch other keys of the same map.
- **Combining two atomics.** They are not atomic together. Use a lock, or an `AtomicReference` to an immutable holder.
- **`new LinkedBlockingQueue<>()` is effectively unbounded.** Pass a capacity.
- **`LongAdder.sum()` during writes** is not a point-in-time snapshot. Do not use it to generate ids.
- **Calling a semaphore a mutex.** It has no owner, so any thread can release it, and it can have more than one permit.

## In interviews

Atomics come up directly: "Implement a thread-safe stack using only `AtomicReference`", in [Synchronized Stack Using Only AtomicReference](#/q/lock-free-stack-atomic-reference). This is a Treiber stack: CAS the `top` pointer and retry on failure. Mention ABA. Semaphores and mutexes appear in [Mutex vs semaphore and deadlock prevention](#/q/mutex-vs-semaphore-deadlock). Typical follow-ups:

- **"How does `ConcurrentHashMap` achieve concurrency?"** A strong answer: since Java 8 it is lock-free for reads, uses a CAS to fill an empty bin, and synchronizes on the bin's head node otherwise. Bins with too many collisions turn into trees. It is atomic per key through `compute` and `merge`, has no nulls, and has weakly consistent iterators. Note that the Java 7 version locked fixed "segments"; that is old knowledge, so date it if you mention it.
- **"`AtomicLong` or `LongAdder`?"** Use `LongAdder` for high-contention counters that are summed rarely. Use `AtomicLong` when you need the exact current value or CAS semantics.

## Explain it in 2 minutes

*"What is CAS, and how does `ConcurrentHashMap` use it?"*

- CAS is an atomic hardware instruction: if the value equals the expected value, replace it with the new one, and report success or failure.
- Lock-free code is a retry loop: read, compute, CAS, and retry on failure. No thread blocks.
- Its limits are that it covers one variable, it can suffer ABA (fixed with a stamped reference), and it burns CPU under heavy contention (which `LongAdder` addresses).
- CHM reads take no lock. Writes CAS an empty bin, or lock only the bin's head node.
- Use the atomic per-key operations (`merge`, `compute*`). A get-then-put still races.
