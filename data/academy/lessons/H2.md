## Where we are

You can write Java and solve problems on your own. An interview is a different task: you solve a
problem **while someone watches, in a fixed time, and is scored on how you work as much as on the
answer**. This lesson gives you a script for a 45–60 minute coding round that you can follow even
when nervous, and a plan for what to do when you get stuck.

## The problem

Microsoft candidates' reports from 2025–26 describe the same failures again and again: a brute-force
answer offered as the final one, a correct idea implemented too slowly, and code that was never run.
For SDE II, the bar described is roughly an optimal solution to a medium in about 25 minutes,
**compiling and running in the editor, with your own `main` and your own test cases**, plus a clear
answer to "how would you test this?"

So the goal isn't just "solve it". It's "solve it visibly, in order, and prove it works".

## The script

```text
 min   step              what you produce
 0-4   1. Clarify        restated problem, sizes, edge rules
 4-7   2. Examples       one normal + one edge example, worked by hand
 7-10  3. Brute force    one sentence + its complexity
10-17  4. Optimise       better idea + its complexity, agreed with the interviewer
17-35  5. Code           clean, runnable, narrated
35-45  6. Test           trace one example, run main with your tests, fix
45+    7. Wrap up        final complexity, trade-offs, what you'd add
```

The minutes are a guide for a 45-minute problem. Shrink them proportionally for a two-problem
round. Each step below explains why it exists.

## 1. Clarify

**Why:** half the "hard" bugs in interviews are a misread problem. Interviewers also often leave
details out on purpose to see whether you ask.

Ask about:

- **Input sizes and ranges.** These set your target complexity: n ≤ 10⁵ means O(n log n) or better.
- **Edge shapes:** empty input, one element, duplicates, negatives, already sorted.
- **Output rules:** any valid answer or a specific one? Indices or values? What if there's no answer?
- **Boundary semantics:** for intervals, does `[1,5]` overlap `[5,10]`?

*Say:* "Let me restate it: given a list of meetings as start and end times, return the minimum number
of rooms so that no two overlapping meetings share one. Can I assume n is up to around 10⁴ or 10⁵?
If one meeting ends at 5 and another starts at 5, can they share a room?"

## 2. Examples

**Why:** working one example by hand often reveals the algorithm, and it gives you a test case for
later.

Pick one normal case and one edge case. Write them in the editor as comments; they become your tests
in step 6.

```text
[[0,30],[5,10],[15,20]]  → 2   (0-30 overlaps both others; those two don't overlap each other)
[[1,5],[5,10]]           → 1   (touching endpoints share a room, as agreed)
```

## 3. State the brute force

**Why:** it proves you understand the problem, and it gives you a fallback. But don't stop there,
and don't code it unless asked.

*Say:* "The simplest idea is to check, for every meeting, how many meetings overlap it at its start
time, and take the maximum. That's O(n²). It works, but n up to 10⁵ means I want O(n log n)."

## 4. Optimise, and agree before coding

**Why:** coding the wrong algorithm for 15 minutes is the most expensive mistake in the round.

Find the work the brute force repeats, and pick a structure that remembers it. (C4 teaches this as a
playbook.)

*Say:* "If I process meetings in order of start time, I only need to know which rooms free up
soonest. A min-heap of end times gives me that. For each meeting, if the earliest-ending room is
free by its start, I reuse it. Otherwise I open a new room. The answer is the heap's size. That's
O(n log n) for the sort and the heap, and O(n) space. Shall I code that?"

The last question matters. It invites the interviewer to redirect you **before** you spend time.

## 5. Code: runnable from the start

**Why:** the code is judged for readability as well as correctness, and it has to run.

- Write the class, the method signature and `main` **first**, so you're never left without a
  runnable file.
- Use names that read like the explanation: `endTimes`, `rooms`, not `pq`, `x`.
- Pull fiddly parts into small helper methods.
- Narrate in short phrases: "sort by start", "free the room if it has ended".
- If something is out of scope, leave a short `// TODO: validate input` and say so, rather than
  silently skipping it.

```java
import java.util.*;

public class MeetingRooms {

    static int minRooms(int[][] meetings) {
        if (meetings.length == 0) return 0;
        int[][] byStart = meetings.clone();
        Arrays.sort(byStart, Comparator.comparingInt(m -> m[0]));
        PriorityQueue<Integer> endTimes = new PriorityQueue<>();
        for (int[] m : byStart) {
            if (!endTimes.isEmpty() && endTimes.peek() <= m[0]) {
                endTimes.poll();                 // that room is free: reuse it
            }
            endTimes.offer(m[1]);
        }
        return endTimes.size();
    }

    // --- tests ---
    static int failures = 0;

    static void check(String name, int expected, int actual) {
        if (expected != actual) {
            failures++;
            System.out.println("FAIL " + name + ": expected " + expected + ", got " + actual);
        } else {
            System.out.println("ok   " + name);
        }
    }

    public static void main(String[] args) {
        check("example",  2, minRooms(new int[][]{{0, 30}, {5, 10}, {15, 20}}));
        check("touching", 1, minRooms(new int[][]{{1, 5}, {5, 10}}));
        check("empty",    0, minRooms(new int[][]{}));
        check("single",   1, minRooms(new int[][]{{3, 4}}));
        check("all same", 3, minRooms(new int[][]{{1, 2}, {1, 2}, {1, 2}}));
        check("unsorted", 2, minRooms(new int[][]{{7, 10}, {2, 4}, {3, 8}}));
        System.out.println(failures == 0 ? "ALL PASS" : failures + " FAILED");
    }
}
```

The `check` helper takes ten seconds to type and makes every run self-explaining. It is also
the most direct way to show the "runnable code with your own tests" habit that Microsoft reports
describe.

## 6. Test like an engineer

**Why:** "how would you test it?" is part of the score, and running your own tests catches the bug
before the interviewer does.

First **trace one example by hand** through the code, saying the variable values out loud. This
catches off-by-one errors that tests might not hit. Then run. Choose tests from these categories,
and say the category as you add each one:

```text
normal          the given example
boundary        empty, one element, max size (say it; you can't type 10⁵ items)
duplicates      equal values / identical intervals
special values  negatives, zero, Integer.MAX_VALUE (overflow?)
order           sorted, reverse sorted, unsorted
the rule you clarified  e.g. touching endpoints
```

If a test fails, don't patch at random. Re-read the failing case, predict what the code should do
line by line, and find the first line where your prediction and the code disagree.

## 7. Wrap up

*Say:* "Final complexity: O(n log n) time, O(n) space. An alternative is a sweep line over two
sorted arrays of starts and ends: same complexity, no heap. In production I'd add input validation
for start > end."

One or two sentences, not a lecture.

## When you're stuck

Getting stuck is normal. The interviewer is watching **how you get unstuck**. Go through these out
loud, in order:

1. **Say so, calmly.** "I don't see the optimisation yet. Let me look at the example again." Silence
   is the worst signal.
2. **Solve your example by hand** and watch what *you* do. You often skip work your brute force
   repeats, and that's the algorithm.
3. **Simplify the problem.** Solve it for sorted input, for only two elements, for one dimension.
   Then add the complication back.
4. **Run the checklist of structures:** HashMap? Sorting? Two pointers? Heap? Prefix sums? Binary
   search on the answer? BFS/DFS? Ask "what would this give me?" for each.
5. **Ask a targeted question,** not "can I have a hint?" but "I'm thinking about ordering by end time
   instead of start time. Am I on the right track?"
6. **Fall back.** If about a third of the time is gone with no better idea, code the brute force
   cleanly, test it, and keep talking about how you'd improve it. Working code beats a half-built
   optimal idea.

When you get a hint, take it visibly: "That helps, so if I sort by start then..." Interviewers score
how you use hints. Ignoring one is worse than needing one.

## Lab (~10 min)

1. Copy `MeetingRooms` above, run it with `java MeetingRooms.java`, and confirm `ALL PASS`.
2. **Break it:** change `<=` to `<` in the `peek()` comparison. Run it and read which test fails.
   That single character is exactly what the clarifying question about touching endpoints was for.
3. Add two more tests of your own from categories not yet covered (for example meetings with
   negative timestamps, or one long meeting that contains all the others), predicting each answer
   before you run it.
4. Time yourself: from a blank file, write the class skeleton, `check` and `main` with three tests in
   under 4 minutes. Repeat until it's automatic, because you'll start every coding round this way.

## Gotchas

- **Trap: coding before agreeing on the approach.** End step 4 with "Shall I code that?".
- **Trap: no `main`, or no tests.** At Microsoft, runnable code with your own tests is part of the
  bar. Write `main` first.
- **Trap: long silences.** Narrate in short phrases. When thinking, say what you're thinking about.
- **Trap: testing only the happy path.** Name the categories (boundary, duplicates, special values,
  order) and pick one from each.
- **Trap: offering brute force as the final answer.** State it, then improve it. Only code it as an
  explicit fallback.
- **Trap: random patching when a test fails.** Trace the failing input line by line first.

## In interviews

Every DSA round uses this script. These Microsoft-reported problems are good for rehearsing all
seven steps, including the clarifying questions:

- [Meeting Rooms II](#/q/meeting-rooms-ii): the touching-endpoints question.
- [Number of Islands](#/q/number-of-islands): clarify whether diagonals count and whether you may
  modify the grid.
- [LRU Cache](#/q/lru-cache): clarify capacity 0 and what `get` returns on a miss. Expect
  thread-safety follow-ups.
- [Two Sum](#/q/two-sum): clarify duplicates, multiple answers, indices or values.
- [Spiral Matrix](#/q/spiral-matrix): non-square and single-row inputs as tests.
- [Add Two Large Numbers as Strings](#/q/add-strings): leading zeros, different lengths, final carry.

**Typical follow-up:** "How would you test this in production code?" A strong answer covers unit
tests by category (boundary, duplicates, special values), a randomised comparison against the
brute force, and a performance test at the maximum size.

## Explain it in 2 minutes

*"Walk me through how you approach a coding interview problem."*

A good answer covers:

1. Clarify sizes, edge cases and boundary rules, because sizes set the target complexity.
2. Work an example by hand, then state the brute force and its cost.
3. Optimise by removing repeated work, and agree on the approach before coding.
4. Write runnable code with `main` and a small `check` helper, narrating as you go.
5. Trace by hand, then run tests chosen by category, and finish with the complexity.
6. When stuck: say so, simplify, run the structures checklist, ask a targeted question, fall back to
   working brute force.

## Check yourself

1. Why ask about input size before anything else?
2. Why end the optimisation step with a question to the interviewer?
3. Name four categories of test case.
4. You're 20 minutes into a 45-minute round with no better idea. What do you do?
5. Why write `main` and `check` before the algorithm body?

### Answers

1. It sets the target complexity, which tells you which ideas are worth exploring.
2. To get agreement (or a redirect) before spending time coding the wrong approach.
3. Normal, boundary (empty/one/max), duplicates, special values (negative, zero, overflow), ordering,
   and any rule you clarified.
4. Say where you are, code the brute force cleanly and test it, and keep discussing the
   optimisation.
5. So the file always runs, and testing at the end is instant rather than a scramble.
