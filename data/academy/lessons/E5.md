## Where we are

You know SOLID (E1) and the everyday patterns: Factory, Builder and Singleton (E2); Adapter,
Decorator and Proxy (E3); Strategy, Observer, Template Method, Chain and State (E4). Knowing
patterns is not the same as passing an LLD round. This lesson gives you a **routine** for the
60 minutes, so you spend the time on design and working code and not on deciding what to do next.

## The problem

**LLD** (low-level design) means designing the classes, interfaces and methods of one component,
as opposed to HLD (high-level design), which is about services, databases and networks. In the
Microsoft loop it is a separate round of about 60–75 minutes. Reports describe it as classes,
interfaces, the common patterns, SOLID, extensibility and concurrency, sometimes in pseudocode
and often as **running Java with your own `main` and tests**.

The dossier lists the usual ways candidates fail: slow or buggy implementation, and, in one
recorded case, going straight to the Observer pattern for a notification system and being marked
down for not exploring requirements first. The interviewer is scoring your *process* as much as
your classes. A routine fixes both problems.

## The seven steps

```text
1 Requirements → 2 Entities → 3 Relationships → 4 Class diagram
      → 5 APIs → (code) → 6 Concurrency → 7 Extensibility
```

We'll walk through them on [Design a Vending Machine](#/q/design-vending-machine), which is
small enough to fit here. E6 applies the same steps to four bigger cases.

## Step 1: Requirements

A **functional requirement** is something the system must *do* ("dispense a product").
A **non-functional requirement** is a quality it must have ("safe if two requests arrive at
once", "easy to add card payments"). Write both down where the interviewer can see them, and
write what is **out of scope** too.

Vending machine, after asking:

```text
Functional
  F1  Show products by slot code (A1, A2...) with price and stock
  F2  Insert coins; select a slot; dispense if paid enough; return change
  F3  Cancel before dispensing -> refund inserted coins
  F4  Operator restocks slots and collects cash
Non-functional
  N1  Never dispense without payment; never lose money
  N2  New payment methods (card, UPI) later without rewriting the machine
Out of scope
  Networked fleet, card payments in this hour, a UI
```

**What to say:** "Before I design anything, let me confirm what's in scope. I'll write it down
so we agree." Then ask the 3–5 questions that change the design: Who are the actors? Is it one
machine or many? Single-threaded or concurrent? What should happen when we can't give change?
Don't ask 15 questions; ask the ones whose answers change your classes.

## Step 2: Entities

An **entity** here just means a class that represents a real concept with its own data and
identity. Underline the nouns in the requirements, then keep the ones that have behaviour or
state worth modelling.

Nouns: machine, product, slot, coin, payment, change, operator, inventory.
Kept: `VendingMachine`, `Product`, `Slot`, `Inventory`, `Coin` (an enum of values), and a
machine *state* (from the verbs "insert, select, cancel", which behave differently depending on
whether money has been inserted). `Operator` stays a role (a set of methods), not a class.

## Step 3: Relationships

For each pair, ask three questions:

- **Is-a or has-a?** Prefer has-a (composition). Use is-a only for real substitutability (LSP).
- **Who owns whom?** **Composition** means the part can't exist without the whole (a `Slot` lives
  inside an `Inventory`). **Aggregation** means the part is shared or outlives the whole (a
  `Product` can appear in many machines).
- **How many?** This is the **multiplicity**: one machine has many slots; one slot holds one
  product type and a count.

## Step 4: Class diagram

Draw it as text. A short legend keeps it readable:

```text
Legend:  ──▷ implements/extends    ◆── owns (composition)    ──▶ uses

             ┌─────────────────────────┐
             │     VendingMachine      │  holds current State; delegates to it
             │ insert(Coin)            │
             │ select(code): Product   │
             │ cancel(): List<Coin>    │
             └──┬─────────┬─────────┬──┘
                ◆         ◆         ──▶
                │         │           │
        ┌───────┴───┐ ┌───┴──────┐ ┌──┴───────────────┐
        │ Inventory │ │ CashBox  │ │ ChangeStrategy   │ «interface»
        │ slots: Map│ │ coins    │ │ makeChange(amt)  │
        └─────┬─────┘ └──────────┘ └──────────────────┘
              ◆                      GreedyChange ──▷ ChangeStrategy
        ┌─────┴─────┐
        │ Slot      │ code, Product, count
        └───────────┘

        IdleState, HasMoneyState, OutOfServiceState ──▷ «interface» MachineState
```

**What to say:** "The machine's behaviour depends on whether money is inserted, so I'll use the
State pattern: each state decides what `insert`, `select` and `cancel` do. Change-making is a
Strategy because the algorithm may change." This is the moment to name patterns: right after
the requirement that justifies them.

## Step 5: APIs

The **public methods** are the contract. Write the signatures before any bodies, including
return types and failure behaviour.

```java
public interface VendingMachine {
    void insert(Coin coin);                       // IllegalStateException when out of service
    Product select(String slotCode);              // throws if unknown slot, sold out or underpaid
    List<Coin> cancel();                          // returns the refund
    void restock(String slotCode, Product product, int count);  // operator role
}

interface MachineState {                          // each method returns the next state
    MachineState insert(SimpleVendingMachine m, Coin c);
    MachineState select(SimpleVendingMachine m, String code);
    MachineState cancel(SimpleVendingMachine m);
}
```

Decide early how errors are reported: exceptions for misuse (unknown slot), and return values
for expected outcomes (an `Optional` or a small result object for "sold out"). Say out loud
which you chose and why. Here `SimpleVendingMachine` is the class that implements
`VendingMachine` and holds the current state.

**Then code.** Build the *happy path* end to end first (insert → select → dispense → change)
with a `main` that runs it. Add error cases next, then tests. A running thin slice beats a
beautiful half-finished class tree.

## Step 6: Concurrency

**Thread-safety** means the object stays correct when several threads call it at the same time.
The failure to look for is a **race condition**: a result that depends on the timing of threads,
like the two singletons in E2's lab.

Go through each piece of **shared mutable state** (data that more than one thread can change)
and choose a tool:

| Situation | Tool |
|---|---|
| One counter or reference | `AtomicLong`, `AtomicReference.compareAndSet` |
| A map shared by threads | `ConcurrentHashMap`, `computeIfAbsent`, `merge` |
| Several fields that must change together | one lock (`synchronized` or `ReentrantLock`) around them |
| Per-key independence (per user, per slot) | a lock or atomic *per key*, not one global lock |
| Many readers, few writers, small list | `CopyOnWriteArrayList` (listeners) |

For the vending machine: a physical machine has one customer at a time, but as a service, the
balance and the slot count must change together, so one lock per machine is simplest and
correct. **What to say:** "The invariant is: the balance goes down and the stock goes down
together, or neither does. I'll guard both with one lock per machine. If it became a hotspot,
I'd split locks per slot, but I'd start simple."

## Step 7: Extensibility

Walk through two or three likely changes and show which classes change. A good design answers
"one new class, plus one line of wiring".

- *Card payments:* add a `PaymentMethod` strategy (`CoinPayment`, `CardPayment`). The states
  call the payment method, not `CashBox` directly.
- *A maintenance mode:* add `OutOfServiceState`. Nothing else changes.
- *Can't make exact change:* `ChangeStrategy` returns an empty result, and the machine refuses
  the sale and refunds. (Greedy change-making is optimal for most real coin systems but not for
  every set of coin values, which is one more reason to keep it behind an interface.)

## Time management for 60 minutes

```text
 0– 5  Requirements and scope, written down. Confirm with the interviewer.
 5–12  Entities, relationships, class diagram. Name the 1–2 patterns and why.
12–15  API signatures. Walk one use case through them in words.
15–45  Code the happy path, run it; then error cases; then 2–3 tests in main.
45–52  Concurrency: name the shared state, the invariant and the lock or atomic.
52–60  Extensibility and follow-ups; what you'd do with more time.
```

Rules that keep you on the clock:

- **Check in at each boundary**: "Does this model look right before I code it?" Interviewers
  often redirect here, and it's cheap at minute 12 and expensive at minute 40.
- **Stub the boring parts.** Real email sending, persistence and UIs are interfaces with an
  in-memory or printing implementation.
- **If you're behind at minute 30**, say so and cut scope: "I'll finish the core flow and
  describe the cancel path."
- **Leave the code runnable at every stage.** A `main` that prints something is your safety net.

The dossier also records an AI-assisted LLD variant (2026, a Windows team) that was judged on how
the candidate prompted the tool and verified its output. The same routine applies: you still own
the requirements, the diagram and the tests, and the tool only types faster.

## Lab (~10 min): a timed dry run

Set a 10-minute timer and do steps 1–5 (no code) for
[Design an Elevator System](#/q/design-elevator-system) on paper or in a text file.

1. Requirements: 4 functional, 2 non-functional, 2 out of scope. (Hint: how many elevators?
   requests from floors vs from inside the cab? what if an elevator is under maintenance?)
2. Entities and relationships.
3. A text class diagram with the legend above.
4. API signatures, for example `void requestPickup(int floor, Direction dir)` and
   `void requestFloor(int elevatorId, int floor)`.
5. Name where State goes (the elevator: idle, moving up, moving down, maintenance) and where
   Strategy goes (which elevator serves a pickup: nearest, least loaded).

What to check when the timer ends: could someone else write the code from your page? If the
diagram has a class with no methods, or a method with no class, fix that first.

## Gotchas

- **Naming patterns before requirements.** It reads as pattern-matching instead of design. Let
  the requirement come first and the pattern name second.
- **Diagram without code.** At Microsoft, reports expect runnable code. Keep the diagram to about
  7 minutes.
- **One giant `Manager` class.** If one class has every method, you've skipped steps 2 and 3.
  Split by reason to change (SRP).
- **"It's thread-safe because I used `ConcurrentHashMap`."** A concurrent map makes each single
  operation safe, not a check-then-act sequence across two calls. Use `computeIfAbsent`, `merge`
  or a lock.
- **No tests.** Two or three checks in `main` (happy path, one error, one edge) show that you
  test as you build.

Typical follow-ups and strong answers:

- *"Now make it thread-safe."* Name the shared state and the invariant first, then the tool, and
  explain why its scope (global vs per key) is right.
- *"Add X without changing existing code."* Point to the interface where X plugs in, write the
  new class, and show the one wiring line.

## Explain it in 2 minutes

Prompt: *"How do you approach a 60-minute LLD round?"*

- Clarify and write down functional and non-functional requirements and the scope (5 min).
- Entities from nouns, relationships (composition over inheritance), a text class diagram;
  name patterns only where a requirement justifies them.
- API signatures with clear error behaviour, then code the happy path end to end and keep it
  runnable.
- Concurrency: shared mutable state, the invariant, and the narrowest correct lock or atomic.
- Extensibility: show that a likely change is one new class.
- Check in with the interviewer at each step, and cut scope out loud if behind.

## Check yourself

1. What is the difference between a functional and a non-functional requirement? Give one of
   each for a parking lot.
2. When should you name a design pattern in an LLD round?
3. Composition or aggregation: an `Inventory` and its `Slot`s? A `Machine` and the `Product` type
   it sells?
4. Why is `if (!map.containsKey(k)) map.put(k, v)` unsafe even on a `ConcurrentHashMap`?
5. At minute 30 you're still on the class diagram. What do you do?

### Answers

1. Functional: what it does ("issue a ticket on entry"). Non-functional: a quality ("two cars
   must never get the same spot under concurrent entry").
2. Right after the requirement that justifies it, and with the reason ("behaviour depends on the
   machine's state, so State").
3. Slots: composition (they exist only inside that inventory). Product: aggregation (the same
   product type exists independently and in many machines).
4. Two threads can both see "absent" and both put; each call is atomic but the pair isn't. Use
   `putIfAbsent` or `computeIfAbsent`.
5. Say so, freeze the diagram, and code the happy path now; describe the remaining parts
   verbally at the end.
