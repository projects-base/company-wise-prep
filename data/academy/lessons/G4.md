## Where we are

From G2 you know **tool use**: you describe a function (name, description, input schema), the model asks to call it, your code runs it and returns a `tool_result`. Those tool definitions lived *inside your app*, written for one model API. This lesson is about **MCP**, a standard way to package tools and context once and plug them into any AI application.

## The problem

You build three tools over this app's question bank: `search_questions`, `get_question`, `list_companies`. Now you want them in three places:

1. your own Spring app (calling the Claude API),
2. Claude Code, while you study in the terminal,
3. some other AI desktop app or IDE assistant you try next month.

Without a standard, you write the integration three times, once per host and once per format of tool definition, auth and transport. With M AI apps and N data sources, everyone ends up writing M × N adapters.

```text
Without a standard:   M apps × N sources = M·N custom integrations
With a protocol:      M apps speak MCP + N sources speak MCP = M + N
```

This is the same problem that JDBC solved for databases, and the Language Server Protocol solved for editors and programming languages.

## MCP in one sentence

The **Model Context Protocol (MCP)** is an open protocol that defines how an AI application discovers and uses capabilities (tools, data and prompt templates) offered by separate programs called **MCP servers**.

Analogy: MCP is to AI apps what JDBC is to Java apps. Write a driver once, and any app can use the database. Where it breaks: JDBC is an in-process Java API, while MCP is a *wire protocol* between processes (often on different machines), and the "caller" deciding what to invoke is frequently the model rather than your code.

## The three roles: host, client, server

```text
┌──────────────────── HOST (e.g. Claude Code, your Spring app) ─────────────────┐
│   LLM  ◄──►  host logic                                                       │
│                 │                │                                            │
│           MCP CLIENT A     MCP CLIENT B      (one client per server connection)│
└─────────────────┼────────────────┼────────────────────────────────────────────┘
                  │ MCP            │ MCP
           ┌──────▼──────┐  ┌──────▼──────┐
           │ MCP SERVER  │  │ MCP SERVER  │
           │ question    │  │ GitHub      │
           │ bank        │  │             │
           └─────────────┘  └─────────────┘
```

- **Host:** the AI application the user interacts with. It owns the model and the conversation, and it decides what the model is allowed to do.
- **Client:** a component inside the host that holds a connection to *one* server.
- **Server:** a program that exposes capabilities, such as a wrapper around your bank, a database, GitHub or a file system.

The rule: **servers provide capabilities, and hosts decide how and whether to use them.** A server never talks to the model directly.

## The wire: JSON-RPC over a transport

MCP messages are **JSON-RPC 2.0**, a simple convention for requests (`method`, `params`, `id`) and responses (`result` or `error`, with the same `id`) encoded as JSON.

```json
{ "jsonrpc": "2.0", "id": 7, "method": "tools/call",
  "params": { "name": "get_question", "arguments": { "slug": "lru-cache" } } }
```

A **transport** carries those messages. The spec defines two standard ones:

- **stdio:** the host launches the server as a local child process and talks to it over standard input and output. Simple, local, no network.
- **Streamable HTTP:** the server runs as an HTTP service, which can stream messages back (using SSE, from G2). Use it for remote or shared servers; it needs real authentication.

A connection starts with an **`initialize`** handshake in which client and server agree on a protocol version and declare their **capabilities**, meaning which features each side supports. Then the client can list and use what the server offers.

## Server primitive 1: tools (the model decides)

A **tool** is a function the server exposes, defined exactly as in G2: name, description and input JSON Schema. The client discovers tools with `tools/list` and invokes one with `tools/call`.

```text
host: tools/list   → server: [ search_questions{query, company?}, get_question{slug} ]
host gives these definitions to the LLM (as G2 tool definitions)
LLM: tool_use get_question{slug:"lru-cache"}
host: tools/call get_question{slug:"lru-cache"} → server → result → back to the LLM
```

Tools are **model-controlled**: the model chooses when to call them. Hosts commonly ask the user for approval before running a tool, especially one that changes things.

## Server primitive 2: resources (the application decides)

A **resource** is read-only data the server exposes, identified by a URI, such as a file, a database row or a document. The client lists resources with `resources/list` and reads one with `resources/read`. Servers can also offer **resource templates**, parameterised URIs like `question://{slug}`.

```text
question://lru-cache        → the Markdown of that question
company://microsoft/dossier → the company dossier
```

Resources are **application-controlled**: the host (or the user, through the host's UI) decides which ones to pull into the context. Example: the user attaches "Microsoft dossier" to the conversation.

The rule: if it is *an action or a query with parameters the model should choose*, make it a tool. If it is *a document someone might attach as context*, make it a resource.

## Server primitive 3: prompts (the user decides)

A **prompt** is a reusable, parameterised message template the server offers. The client discovers prompts with `prompts/list` and fills one in with `prompts/get`. Hosts typically show them as slash commands or menu items.

```text
prompt "mock_interview" (args: company, roundType)
→ "You are a {company} interviewer running a {roundType} round. Ask one question at a time..."
```

Prompts are **user-controlled**: the user picks one explicitly.

```text
primitive   who decides to use it    example over the bank
─────────   ─────────────────────    ──────────────────────────────
tools       the model                search_questions, get_question
resources   the application/user     question://{slug}, company://{slug}/dossier
prompts     the user                 mock_interview, explain_like_lesson
```

The spec also defines features in the other direction, where a *server* asks the *client* for something (for example, **sampling**: the server asks the host's model to generate text). You don't need these to build a first server.

## Where MCP fits with what you already know

- **MCP doesn't replace tool use.** The host still turns MCP tools into ordinary tool definitions for its model (G2). MCP standardises how the host *gets* those tools and how it *runs* them.
- **Hosts are the gatekeepers.** Claude Code, IDE assistants and your own app all act as MCP hosts. The Claude API also offers an MCP connector (beta) that lets the API connect to a *remote* MCP server for you; the request needs both the server definition and a matching MCP toolset entry.
- **For Java,** there is an official MCP Java SDK, and Spring AI has MCP client and server support. This lesson stays at the protocol level, so check their docs for current class and method names rather than relying on memory.

## Lab (~10 min) — design exercise

Design an MCP server, `prepos-bank`, that exposes this app's question bank to any MCP host. Write your answers down before you read the sketch.

1. Which **tools** should exist? Give each a name, a one-line description written *for the model*, and an input schema.
2. Which **resources** and resource templates?
3. One **prompt**.
4. Which **transport** for (a) Claude Code on your laptop and (b) a shared deployment?
5. What must the server **not** allow?

A sketch to compare with (plain Java 21 types describing the contract, not SDK code):

```java
import java.util.List;
import java.util.Optional;

/** The contract an MCP server over the bank would expose. Protocol method in comments. */
public interface PrepBankMcpContract {

    // tools/list + tools/call ------------------------------------------------
    /** "Search interview questions by free text; optionally filter by company slug and type." */
    List<QuestionSummary> searchQuestions(String query, Optional<String> company,
                                          Optional<String> type, int limit);

    /** "Get one question's full Markdown, sightings and confidence by slug." */
    Optional<QuestionDetail> getQuestion(String slug);

    // resources/list + resources/read  (URI templates) ------------------------
    //   question://{slug}            -> question Markdown
    //   company://{slug}/dossier     -> company dossier Markdown
    String readResource(String uri);

    // prompts/list + prompts/get ----------------------------------------------
    //   mock_interview(company, roundType) -> messages to start a mock round
    List<String> mockInterviewPrompt(String company, String roundType);

    record QuestionSummary(String slug, String type, String title, List<String> companies) {}
    record QuestionDetail(String slug, String markdown, String confidence, List<String> sourceUrls) {}
}
```

Points a strong design includes:

- **Read-only to start.** No `add_sighting` tool yet. Any write tool would need user approval in the host *and* must keep the bank's rules: Claude-sourced material stays `confidence: claimed`, and it carries a source URL and a date.
- **Bounded outputs:** `limit` capped (say 20), with summaries in search results and full detail only in `getQuestion`. Tool results consume the host's context window.
- **Descriptions written for the model:** say *when* to use each tool, not just what it does.
- **Transport:** stdio for local Claude Code (no network exposure); Streamable HTTP with authentication for anything shared.
- **Untrusted content:** question text came from web research, so the host must treat tool results as data, not instructions (G6).

## Gotchas

- **Exposing everything as tools.** Large static documents fit better as resources the user or app attaches. Too many tools also make the model's choice harder.
- **Unbounded tool results.** A `search` that returns 500 full documents floods the host's context and its bill. Paginate, cap and summarise.
- **Remote servers without auth.** A Streamable HTTP server is a network API. Secure it like one: authentication, least-privilege scopes, rate limits.
- **Trusting a third-party server blindly.** Its tool descriptions and results flow into your model's context and can carry injected instructions. Only connect servers you trust, and keep a human approving side-effecting calls.
- **Inventing SDK method names from memory.** The protocol method names (`tools/list`, `tools/call`, `resources/read`, `prompts/get`) are stable. SDK APIs change, so check the docs.

## In interviews

MCP comes up as a "how would you connect an AI assistant to internal systems?" design question, and when you describe how you use AI tools day to day.

- [Design an Agentic Workflow](#/q/design-agentic-workflow): propose MCP servers as the integration layer between the agent and internal systems, with the host enforcing approvals.
- [How are AI tools helping you?](#/q/how-you-use-ai-tools): describing an MCP server you connected (or built) to a coding assistant is a concrete, credible answer.

Typical follow-ups:

- *"Why not just call REST APIs from the agent?"* You could. MCP gives a standard discovery mechanism (`list`) and invocation format that any host understands, so one server works across many AI apps. For a single app with two internal calls, plain tool use may be simpler.
- *"How do you secure it?"* Local stdio for local tools; authentication on HTTP servers; read-only by default; user approval for writes; treat all results as untrusted data; audit-log every `tools/call`.

## Explain it in 2 minutes

*"What is MCP and when would you use it?"*

1. Problem: M AI apps × N data sources means M·N custom integrations. MCP makes it M + N.
2. Roles: the host (the AI app) has one client per server, and servers expose capabilities.
3. JSON-RPC 2.0 over stdio (local) or Streamable HTTP (remote), starting with an `initialize` handshake that negotiates capabilities.
4. Tools (model-controlled), resources (application-controlled, by URI) and prompts (user-controlled templates).
5. The host still turns tools into ordinary tool-use definitions and gatekeeps execution.
6. Security: least privilege, approvals for writes, auth on remote servers, treat outputs as untrusted.

## Check yourself

1. What is the difference between an MCP host and an MCP client?
2. Who decides when a tool is used, versus a resource, versus a prompt?
3. Which transport would you choose for a server only your local IDE uses, and why?
4. Does MCP replace the tool-use mechanism from G2? Explain.
5. Why cap the size of tool results?

### Answers

1. The host is the AI application (it owns the model and the user experience). A client is the connection component inside the host, one per server.
2. Tools: the model. Resources: the application (often on the user's behalf). Prompts: the user, explicitly.
3. stdio. The host launches it as a local process, nothing is exposed on the network, and setup is simpler.
4. No. The host still presents MCP tools to the model as ordinary tool definitions and runs the calls. MCP standardises discovery and invocation between the host and external servers.
5. Results go into the model's context window. Huge results cost tokens, add latency and can bury the relevant facts.
