## Where we are

From D4 you know that Boot's auto-configuration created a `DispatcherServlet`, Jackson converters
and an embedded Tomcat because `spring-boot-starter-web` was on the classpath. This lesson
follows a single HTTP request through all of that, from the socket to your controller method and
back to JSON. Then you will know exactly where to plug in logging, auth, validation and error
handling.

## The problem

You write this, and it "just works":

```java
@GetMapping("/questions/{slug}")
public BankService.QuestionView question(@PathVariable String slug) { return bank.question(slug); }
```

Plenty of questions hide behind that one method, though. Who parsed the URL? Who turned the
returned record into JSON? Where does a `NotFoundException` become a 404? If you want to time
every request, or reject requests that have no API key, where does that code go? Without the
pipeline in your head, you end up guessing, and features land in the wrong layer.

## Servlets and filters: the layer below Spring

A **servlet** is a Java object the web server (Tomcat) calls to handle a request:
`service(request, response)`. Tomcat takes a thread from its pool for each request and calls the
servlet on that thread.

A **filter** is a servlet-level wrapper that runs *before and after* the servlet. Filters form a
chain, and each one decides whether to call `chain.doFilter(...)` to pass the request on:

```java
protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain) {
    // before: runs for every request, before Spring MVC sees it
    chain.doFilter(req, res);
    // after: the response has been produced
}
```

Filters know nothing about controllers. They see raw HTTP. Spring Security is built as a filter
chain (D7).

## DispatcherServlet: one front door

Spring MVC registers **one** servlet, the `DispatcherServlet`, mapped to `/`. It is a **front
controller**: every request comes through it, and it delegates each step to a pluggable
strategy bean:

```text
 Tomcat thread
   │
   ▼
 Filter chain ─────────────── (servlet level: raw HTTP, every request)
   │
   ▼
 DispatcherServlet.doDispatch
   1 HandlerMapping          which controller method?  (RequestMappingHandlerMapping)
   2 Interceptor.preHandle   (Spring level: knows the chosen method; may return false)
   3 HandlerAdapter          invoke it:
       ├─ ArgumentResolvers  @PathVariable, @RequestParam, @RequestBody (+ @Valid) …
       ├─ your controller method
       └─ ReturnValueHandler → HttpMessageConverter writes JSON
   4 Interceptor.postHandle  (skipped if the handler threw)
   ↳ on exception: HandlerExceptionResolvers → @ControllerAdvice / @ResponseStatus / defaults
   5 Interceptor.afterCompletion  (always)
   │
   ▼
 Filter chain (after part) → response bytes to the client
```

Each of the next sections covers one box.

## Handler mapping: which method?

At start-up, `RequestMappingHandlerMapping` scans every `@RestController` and builds a lookup
table from method, path pattern and conditions (such as `consumes`) to a `HandlerMethod`. A
request is matched against that table. If no entry matches, the result is a 404 before any of
your code runs.

That is why a typo in `@GetMapping` produces a 404, not an exception.

## Argument resolvers: filling in your parameters

Your method's parameters are not magic. For each one, the adapter asks a list of
**HandlerMethodArgumentResolver**s, "can you supply this?":

- `@PathVariable String slug` is taken from the matched URL pattern.
- `@RequestParam int page` comes from the query string, with type conversion.
- `@RequestBody ProgressRequest req` is read from the body by a **message converter**.
- `@Valid` on it triggers Jakarta Bean Validation. In this repo, `ProgressRequest` has
  `@NotNull action`, and a failure throws `MethodArgumentNotValidException`, which becomes a
  400.
- `HttpServletRequest`, `Principal` and `Locale` are supplied directly.

You can add your own resolver. For example, one that turns a header into a `CurrentUser`
parameter is registered through `WebMvcConfigurer.addArgumentResolvers`.

## Message converters: objects ⇄ bytes

An **HttpMessageConverter** reads a request body into an object and writes a return value into
the response body. Which converter is chosen depends on the `Content-Type` and `Accept`
headers. For JSON, Boot 4 and Spring 7 use Jackson 3 (`JacksonJsonHttpMessageConverter`), while
Boot 3 used `MappingJackson2HttpMessageConverter`.

`@RestController` is `@Controller` plus `@ResponseBody`. That `@ResponseBody` is what says "send
the return value through a converter" instead of "look up a view template".

## Errors: `@ControllerAdvice`

When a controller throws, the `DispatcherServlet` asks its **HandlerExceptionResolver**s to turn
the exception into a response, in this order:

1. **`@ExceptionHandler`** methods, either on the controller itself or in a
   **`@ControllerAdvice` / `@RestControllerAdvice`** class, which applies to all controllers.
2. **`@ResponseStatus`** on the exception class. This repo's `NotFoundException` uses
   `@ResponseStatus(HttpStatus.NOT_FOUND)`.
3. **Spring's defaults**, which map common exceptions to statuses (for example a validation
   failure to 400).

Return a **`ProblemDetail`** from a handler to get a standard `application/problem+json` body
(RFC 9457). Extending `ResponseEntityExceptionHandler` gives the same format for Spring's
built-in exceptions.

## Filters vs interceptors

| | Filter | HandlerInterceptor |
|---|---|---|
| Layer | servlet container (`jakarta.servlet`) | Spring MVC |
| Sees | every request, including static files and non-MVC paths | only requests mapped to a handler |
| Knows the controller method? | no | yes (`handler` argument) |
| Can wrap or replace the request/response? | yes (e.g. caching body wrappers) | no |
| Register via | a `@Component` filter or `FilterRegistrationBean` | `WebMvcConfigurer.addInterceptors` |
| Typical use | security, CORS, compression, request IDs, raw timing | per-endpoint auth checks, audit using method annotations |

The rule: **if the concern is about HTTP, use a filter; if it is about which controller method
runs, use an interceptor.** For business rules, use neither, and put them in the service.

## Lab (~10 min)

Add this file to this repo as `src/main/java/com/companywiseprep/web/PipelineLab.java`. It is a
lab only, so delete it afterwards.

```java
package com.companywiseprep.web;

import java.io.IOException;

import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.stereotype.Component;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.filter.OncePerRequestFilter;
import org.springframework.web.servlet.HandlerInterceptor;
import org.springframework.web.servlet.ModelAndView;
import org.springframework.web.servlet.config.annotation.InterceptorRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

@Component
class TimingFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        long t0 = System.nanoTime();
        System.out.println("[filter]      before " + req.getMethod() + " " + req.getRequestURI());
        try {
            chain.doFilter(req, res);
        } finally {
            System.out.printf("[filter]      after  status=%d in %d ms%n",
                    res.getStatus(), (System.nanoTime() - t0) / 1_000_000);
        }
    }
}

@Component
class TracingInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        System.out.println("[interceptor] preHandle -> " + handler);
        return true;                                   // false = stop; the controller never runs
    }
    @Override
    public void postHandle(HttpServletRequest req, HttpServletResponse res, Object handler, ModelAndView mv) {
        System.out.println("[interceptor] postHandle");
    }
    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res, Object handler, Exception ex) {
        System.out.println("[interceptor] afterCompletion, unhandled exception = " + ex);
    }
}

@Configuration
class InterceptorConfig implements WebMvcConfigurer {
    private final TracingInterceptor tracing;
    InterceptorConfig(TracingInterceptor tracing) { this.tracing = tracing; }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(tracing).addPathPatterns("/api/**");
    }
}

@RestControllerAdvice
class ApiErrors {
    @ExceptionHandler(NotFoundException.class)
    ProblemDetail notFound(NotFoundException e) {
        System.out.println("[advice]      handling " + e.getMessage());
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, e.getMessage());
    }
}
```

Start the app and run three requests (the port is 8090). In Windows PowerShell, type
`curl.exe`, because plain `curl` is an alias for `Invoke-WebRequest` there.

```text
curl http://127.0.0.1:8090/api/companies
curl http://127.0.0.1:8090/api/questions/nope
curl -X PUT -H "Content-Type: application/json" -d "{}" http://127.0.0.1:8090/api/questions/nope/progress
```

This is what was logged when the lab was run against this repo:

```text
[filter]      before GET /api/companies
[interceptor] preHandle -> com.companywiseprep.web.ApiController#companies()
[interceptor] postHandle
[interceptor] afterCompletion, unhandled exception = null
[filter]      after  status=200 in 927 ms
[filter]      before GET /api/questions/nope
[interceptor] preHandle -> com.companywiseprep.web.ApiController#question(String)
[advice]      handling No question nope
[interceptor] afterCompletion, unhandled exception = null
[filter]      after  status=404 in 11 ms
[filter]      before PUT /api/questions/nope/progress
[interceptor] preHandle -> com.companywiseprep.web.ApiController#updateProgress(String, ProgressRequest)
  WARN … DefaultHandlerExceptionResolver : Resolved [...MethodArgumentNotValidException: Validation failed for argument [1] ...]
[interceptor] afterCompletion, unhandled exception = null
[filter]      after  status=400 in 333 ms
```

The 404 body is now `{"detail":"No question nope","instance":"/api/questions/nope","status":404,"title":"Not Found"}`.

What to notice:

- The filter wraps everything, and the interceptor sees the exact controller method.
- On an exception, **`postHandle` is skipped**, and `afterCompletion` receives `null` because
  the advice already *handled* the exception.
- The 400 came from Spring's default resolver, because `@Valid` failed on `@NotNull action`
  before your method ran. Add an `@ExceptionHandler(MethodArgumentNotValidException.class)` to
  `ApiErrors` that returns a `ProblemDetail` listing the field errors.
- **Break it:** make `preHandle` return `false`. Requests then return 200 with an empty body,
  and the controller never runs.

## Gotchas

- **`postHandle` is useless for `@ResponseBody` responses.** The body has already been written
  by the converter. To change the response, use a filter or `ResponseBodyAdvice`.
- **Errors raised in a filter never reach `@ControllerAdvice`,** because that advice only
  covers exceptions thrown inside the `DispatcherServlet`. Handle them in the filter itself (or
  in Security's entry points).
- **A `@Component` filter is registered for every URL.** To limit its paths or set its order,
  use a `FilterRegistrationBean` or `@Order`.
- **Missing `Content-Type: application/json` gives a 415** (no converter for the body), not a
  validation error. Check the request headers first.
- **`@Valid` is required for validation to run.** Without it, the constraint annotations on the
  record are ignored.

## In interviews

This is asked as "What happens when a request hits a Spring Boot app?", "Filter vs
interceptor?" and "How do you handle exceptions globally?"

- [Debugging requests across microservices](#/q/debugging-across-microservices): a filter that
  adds a correlation ID to every request and log line is the standard answer.
- [Design a Rate Limiter](#/q/design-rate-limiter): in a Spring service, the limiter usually
  sits in a filter (per client/IP) or an interceptor (per endpoint).
- [Design an Idempotent API](#/q/design-idempotent-api): an `Idempotency-Key` header is often
  checked in a filter or interceptor before the controller runs.

Typical follow-ups:

- *"Where would you put authentication?"* In a filter, because it must run for every path,
  including non-MVC ones. That is why Spring Security is a filter chain.
- *"How does JSON get into your record?"* An argument resolver for `@RequestBody` picks a
  message converter by `Content-Type`, Jackson deserialises the body, then `@Valid` runs Bean
  Validation.

## Explain it in 2 minutes

*"Trace a `GET /api/questions/{slug}` through Spring MVC."*

- Tomcat gives the request a thread, and the filter chain runs (security, logging).
- `DispatcherServlet` asks a `HandlerMapping` for the controller method. If there is no match,
  the result is a 404.
- Interceptors' `preHandle` runs, then the adapter resolves the arguments (`@PathVariable`, or
  `@RequestBody` through a converter and `@Valid`).
- The method returns a record, and the Jackson message converter writes JSON.
- Exceptions go to exception resolvers: `@ControllerAdvice`, `@ResponseStatus`, then the
  defaults.
- `afterCompletion` runs, then the filters unwind on the way out.

## Check yourself

1. Why can a filter not tell which controller method will run?
2. What turns `@RequestBody ProgressRequest` from bytes into an object?
3. A controller throws `NotFoundException`. List the ways it can become a 404 in this repo.
4. You want to log the response status for *every* request, including 404s for unknown paths.
   Should you use a filter or an interceptor?

### Answers

1. Filters run before the `DispatcherServlet`, which is where handler mapping happens.
2. The `@RequestBody` argument resolver, using an `HttpMessageConverter` (Jackson).
3. `@ResponseStatus(NOT_FOUND)` on the exception class, or an `@ExceptionHandler` in a
   `@RestControllerAdvice` (which takes precedence).
4. A filter. Unknown paths never reach a handler, so interceptors never see them.
