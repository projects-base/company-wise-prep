## Where we are

In SPRING-BOOT-9 you turned an API into a **resource server**: it reads `Authorization: Bearer <JWT>`, checks the signature against the issuer's public keys, and maps `scope` to `SCOPE_*` authorities. One question was left open: *where does that token come from?* This lesson answers it. OAuth2 is the protocol for getting tokens, and OpenID Connect (OIDC) is the layer on top that makes "Log in with Google" work.

## The problem

Your prep app wants to add each interview to the user's Google Calendar. The 2005-era way: ask the user for their Google password, store it, and log in as them.

```text
user ──"my Google password"──► your app ──logs in as user──► Google Calendar
```

Everything about this is wrong:

- Your app can now do **anything** the user can: read mail, delete files. It only needed "write calendar events".
- The user cannot revoke your app without changing their password everywhere.
- If your database leaks, real Google passwords leak.
- Multi-factor login breaks, because your app is the one typing the password.

What we want is a **valet key**: a limited token, issued by Google, that says "this app may write calendar events for this user until it expires", and that the user can revoke without telling anyone their password. That is OAuth2.

## Three words people mix up

- **Authentication**: proving who someone is. "This is Akhil."
- **Authorization**: deciding what they may do. "Akhil may update progress."
- **Delegation**: a user letting an *application* act on their behalf, with limits. "The prep app may write to Akhil's calendar."

**OAuth2 is a delegation protocol.** It gives a client an **access token** to call an API. It deliberately does *not* tell the client who the user is. Using a bare access token as proof of login was a common source of real bugs, which is why OIDC was created (more below).

## The four roles

OAuth2 names four parties. Map each one onto the calendar example:

| Role | Who it is here | Job |
|---|---|---|
| **Resource owner** | Akhil, the user | Owns the data and grants consent |
| **Client** | Your prep app | Wants to call the API on the user's behalf |
| **Authorization server** | Google's login service (or Keycloak, Okta, Entra ID) | Logs the user in, asks for consent, issues tokens |
| **Resource server** | Google Calendar API (or your API from SPRING-BOOT-9) | Accepts tokens and serves data |

Clients come in two kinds. A **confidential client** runs on a server and can keep a `client_secret` hidden (your Spring Boot backend). A **public client** cannot keep a secret, because its code is on the user's device (a single-page app in the browser, a mobile app). Anything shipped to a device can be read by its owner.

## The authorization code flow, step by step

This is the flow you should be able to draw on a whiteboard.

```text
 Browser            Client (your app)           Authorization server        Resource server
   │ 1. click "Connect Google" │                          │                         │
   │──────────────────────────►│                          │                         │
   │ 2. 302 redirect to /authorize?response_type=code&client_id=..&redirect_uri=..   │
   │       &scope=calendar.events&state=xyz&code_challenge=..                       │
   │◄──────────────────────────│                          │                         │
   │ 3. user logs in at the AS, sees consent screen, clicks Allow                    │
   │────────────────────────────────────────────────────►│                         │
   │ 4. 302 back to redirect_uri?code=abc&state=xyz       │                         │
   │◄────────────────────────────────────────────────────│                         │
   │──────────────────────────►│ 5. POST /token  code=abc + client auth + code_verifier
   │                           │─────────────────────────►│                         │
   │                           │ 6. { access_token, refresh_token, id_token }       │
   │                           │◄─────────────────────────│                         │
   │                           │ 7. GET /events  Authorization: Bearer <access_token>
   │                           │───────────────────────────────────────────────────►│
```

Why is it two steps (a **code**, then a **token**)? The browser is a leaky channel: URLs end up in history, logs and `Referer` headers. So only a short-lived, single-use **authorization code** travels through the browser. The real tokens are fetched in step 5 over a direct back-channel call from the client to the authorization server, where a confidential client also proves who it is with its secret.

Two parameters protect the flow:

- **`redirect_uri`** must exactly match one registered for the client. Otherwise an attacker could ask for the code to be sent to their site.
- **`state`** is a random value the client stores before redirecting and checks when the user comes back. It stops an attacker from tricking a user's browser into finishing *the attacker's* login (a form of CSRF).

## PKCE: protecting the code itself

**The problem:** a public client has no secret, so in step 5 anyone holding the code could redeem it. On mobile, a malicious app can register the same custom URL scheme and intercept the redirect.

**PKCE** (Proof Key for Code Exchange, pronounced "pixy", RFC 7636) fixes this with a one-time secret made per login:

1. Before step 2, the client generates a random **`code_verifier`** and keeps it.
2. It sends **`code_challenge = BASE64URL(SHA-256(code_verifier))`** with `code_challenge_method=S256` in the authorize request.
3. The authorization server stores the challenge alongside the code.
4. In step 5, the client sends the original `code_verifier`. The server hashes it and compares.

An attacker who steals the code does not have the verifier, and cannot work it out from the challenge because SHA-256 is one-way. **The rule:** use authorization code + PKCE for every client, public or confidential. Current OAuth security guidance (RFC 9700, and the OAuth 2.1 draft) recommends exactly that.

## Three tokens, three jobs

| Token | Audience | Purpose | Typical lifetime |
|---|---|---|---|
| **Access token** | The resource server (API) | "The bearer may do *these scopes*." Sent on every API call | Short: minutes |
| **Refresh token** | The authorization server only | Get a new access token without asking the user again | Long: hours to weeks |
| **ID token** | The client | "This user logged in, here is who they are." OIDC only | Short |

- The access token may be a JWT (as in SPRING-BOOT-9) or an **opaque** random string that the API checks by calling the authorization server's **introspection** endpoint. The client should treat it as opaque either way.
- A refresh token is a powerful credential. Keep it server-side, and prefer **refresh token rotation**: each use returns a new refresh token and invalidates the old one, so a stolen, reused token is detected.
- **Never send an ID token to an API as a bearer token.** Its `aud` is your client id, not the API.

## OpenID Connect: login on top of OAuth2

OAuth2 answers "may this app call the API?" OIDC adds "who just logged in?" It is the same authorization code flow with a few additions:

- The client asks for the **`openid` scope** (plus `profile`, `email` if wanted).
- The token response includes an **ID token**: a signed JWT with claims such as `iss` (who issued it), `sub` (a stable user id at that issuer), `aud` (your client id), `exp`, `iat` and `nonce`.
- **`nonce`**: a random value the client sends in the authorize request and expects back inside the ID token, which stops an old ID token from being replayed.
- A **UserInfo endpoint** returns more profile claims for a valid access token.
- **Discovery**: every provider publishes `/.well-known/openid-configuration`, a JSON document listing its authorize, token, userinfo and `jwks_uri` endpoints. This is why one `issuer-uri` property was enough in SPRING-BOOT-9.

Identify users by **`iss` + `sub`**, never by email. Emails change and can be reused.

## Client credentials: service-to-service

**The problem:** the order service calls the inventory service at 3 a.m. from a scheduled job. No user is involved, so there is nobody to consent.

The **client credentials grant** is one call: the service authenticates as itself and gets an access token.

```text
order-service ──POST /token grant_type=client_credentials&scope=inventory:read
                 (client_id + client_secret, or a signed JWT assertion / mTLS)──► AS
             ◄── { access_token, expires_in }   (no refresh token: just ask again)
order-service ──Bearer <token>──► inventory-service (a resource server)
```

The token's `sub` is the client itself. Cache the token until shortly before `expires_in`, rather than fetching one per request.

## Grants that are deprecated, and why

- **Implicit grant** (`response_type=token`): the access token came back directly in the URL fragment. It was designed for browser apps before CORS existed. The token leaks through history and referrers, there is no way to bind it to the client, and there is no refresh token. Replaced by authorization code + PKCE.
- **Resource owner password grant**: the client collects the user's username and password and swaps them for a token. That is the exact problem OAuth2 exists to remove: the client sees the password, MFA and consent screens are bypassed, and users learn to type passwords into third-party apps.

Both are removed in the OAuth 2.1 draft. For devices with no browser (a TV), use the **device authorization grant** instead: the device shows a code and the user approves it on their phone.

## Scopes versus roles

- A **scope** limits what the *client* may do on the user's behalf. It is the user's consent. `calendar.events` means "this app may touch events", not "this user is an admin".
- A **role** describes what the *user* is allowed to do in your system. `ADMIN` is about the person.

The effective permission is the intersection: the client needs the scope **and** the user needs the right. A common design: the authorization server puts scopes in `scope` and roles in a custom claim (Keycloak uses `realm_access.roles`), and the resource server maps both, as you saw with `JwtAuthenticationConverter` in SPRING-BOOT-9.

## Validating tokens with JWKS, properly

A resource server validating a JWT access token must check:

1. **Signature**, using the key from the issuer's **JWKS** (JSON Web Key Set) at `jwks_uri`. The JWT header's **`kid`** says which key. Spring's `NimbusJwtDecoder` caches the set and refetches it when it meets an unknown `kid`, which is how **key rotation** works without downtime.
2. **Algorithm**: accept only the expected asymmetric algorithm (for example RS256). Never accept `alg: none`, and never let an HMAC check use the public key as a secret.
3. **`iss`** equals the expected issuer, and **`exp`** / `nbf` are within a small clock-skew window.
4. **`aud`** contains *this* API. Without it, a token minted for another API on the same issuer works on yours. In Boot 3.2+ set `spring.security.oauth2.resourceserver.jwt.audiences`.

## Spring Boot: two starters, two jobs

| | `spring-boot-starter-oauth2-client` | `spring-boot-starter-oauth2-resource-server` |
|---|---|---|
| Your app's role | **Client**: obtains tokens | **Resource server**: accepts tokens |
| DSL | `http.oauth2Login()` (user login), `oauth2Client()` | `http.oauth2ResourceServer(rs -> rs.jwt(...))` |
| Session | Usually yes: user logs in, tokens stay server-side | Stateless |
| Key types | `ClientRegistration`, `OAuth2AuthorizedClientManager`, `OidcUser` | `JwtDecoder`, `JwtAuthenticationToken` |

An app can be both: a backend that logs users in and also calls downstream APIs. A strong pattern for SPAs is the **BFF** (backend for frontend): the Spring backend is the confidential OAuth client, the browser holds only an `HttpOnly` session cookie, and tokens never reach JavaScript. Because that cookie authenticates the user, CSRF protection stays **on** (the opposite of the stateless API in SPRING-BOOT-9).

## Lab (~10 min)

**Part 1: PKCE by hand (pure Java 21, offline).** Save as `Pkce.java` and run `java Pkce.java`:

```java
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.SecureRandom;
import java.util.Base64;

public class Pkce {
    static String challenge(String verifier) throws Exception {
        byte[] hash = MessageDigest.getInstance("SHA-256").digest(verifier.getBytes(StandardCharsets.US_ASCII));
        return Base64.getUrlEncoder().withoutPadding().encodeToString(hash);
    }

    public static void main(String[] args) throws Exception {
        byte[] random = new byte[32];
        new SecureRandom().nextBytes(random);
        String verifier = Base64.getUrlEncoder().withoutPadding().encodeToString(random);
        System.out.println("code_verifier  = " + verifier);
        System.out.println("code_challenge = " + challenge(verifier));
        System.out.println("RFC 7636 check = " + challenge("dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"));
    }
}
```

**Observe:** the last line prints `E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM`, the test vector from RFC 7636 Appendix B. Change one character of the verifier and the challenge changes completely: that is why a stolen code is useless without it.

**Part 2: OIDC login with Spring.** Add `spring-boot-starter-oauth2-client` and a provider (a local Keycloak in Docker, or Google):

```yaml
spring:
  security:
    oauth2:
      client:
        registration:
          keycloak:
            client-id: prep-web
            client-secret: ${KEYCLOAK_CLIENT_SECRET}
            scope: openid,profile,email
        provider:
          keycloak:
            issuer-uri: http://localhost:8180/realms/prep
```

```java
@RestController
class MeController {
    @GetMapping("/me")
    Map<String, String> me(@AuthenticationPrincipal OidcUser user) {
        return Map.of("iss", user.getIssuer().toString(), "sub", user.getSubject());
    }
}
```

With the default chain plus `http.oauth2Login(Customizer.withDefaults())`, visit `/me`. Open the browser dev tools Network tab and **observe** the 302 to `/protocol/openid-connect/auth` with `state`, `nonce` and `scope=openid...`, then the return to `/login/oauth2/code/keycloak?code=...&state=...`. The token exchange never appears in the browser: it is a back-channel call.

Test it without a provider, using `spring-security-test`:

```java
@Test void me_returnsSubject() throws Exception {
    mvc.perform(get("/me").with(oidcLogin().idToken(t -> t.issuer("https://idp.test").subject("user-1"))))
       .andExpect(jsonPath("$.sub").value("user-1"));
}
```

**Break it:** register the client in Keycloak with a different redirect URI than `{baseUrl}/login/oauth2/code/keycloak` and watch the provider refuse with an `invalid redirect_uri` error before the login page even loads.

## Gotchas

- **Using OAuth2 alone for login.** An access token proves delegation, not identity, and may not even be meant for you. Use OIDC and validate the ID token (`iss`, `aud` = your client id, `exp`, `nonce`).
- **Skipping `aud` validation** on the resource server. Any token from the same issuer then works on your API. Configure audiences explicitly.
- **Tokens in `localStorage`.** Any XSS can read them. Prefer the BFF pattern with `HttpOnly` cookies, or keep tokens in memory with short lifetimes.
- **Keying users by email.** Use `iss` + `sub`; emails change, and some providers do not verify them.
- **PKCE only on mobile.** Use it for confidential clients too. In Spring Security 6, public clients get PKCE automatically; for a confidential client opt in with `OAuth2AuthorizationRequestCustomizers.withPkce()` (check your version's default).
- **Fetching a client-credentials token per request.** It hammers the authorization server and adds latency. `OAuth2AuthorizedClientManager` caches it until expiry.

## In interviews

Typical prompts: "Explain OAuth2", "Walk me through the authorization code flow", "What is PKCE and why?", "OAuth vs OIDC?", "How do two microservices authenticate to each other?", "Access token vs refresh token vs ID token?". Bank: [OAuth and JWT tokens](#/q/oauth-and-jwt).

A strong answer uses four layers:

1. **What:** OAuth2 is delegated authorization: a client gets a scoped, short-lived access token instead of the user's password. OIDC adds an ID token for authentication.
2. **How it works inside:** four roles; code through the front channel, tokens through the back channel; `state` against CSRF, PKCE against code interception, `redirect_uri` exact match; resource server validates signature via JWKS `kid`, then `iss`, `aud`, `exp`.
3. **Where used:** "Log in with Google" (OIDC + code + PKCE), SPA via BFF, microservices via client credentials, TVs via device code.
4. **What goes wrong:** implicit and password grants (why deprecated), missing `aud` checks, tokens in `localStorage`, ID token sent to APIs, long-lived access tokens that cannot be revoked.

**Follow-up: "How does service A call service B securely?"** Client credentials with a narrow scope such as `inventory:read`, the token cached until expiry, B validating `aud`. Mention mTLS or a service mesh as the transport layer, and that propagating the *user's* identity needs token exchange (RFC 8693), not reusing the user's token everywhere.

**Follow-up: "A refresh token was stolen. What limits the damage?"** Rotation with reuse detection (the authorization server revokes the whole token family when an old one is replayed), sender-constrained tokens (DPoP or mTLS) where supported, and short lifetimes.

## Explain it in 2 minutes

*"Explain what happens when a user clicks 'Log in with Google' on a Spring Boot app."*

- The app is an OAuth2 client; it redirects to Google's authorize endpoint with `client_id`, `redirect_uri`, `scope=openid email`, `state`, `nonce` and a PKCE `code_challenge`.
- The user logs in and consents at Google; Google redirects back with a one-time code and the same `state`.
- The app exchanges the code plus `code_verifier` (and its secret) on the back channel for an access token, refresh token and ID token.
- The app validates the ID token (signature via JWKS, `iss`, `aud`, `exp`, `nonce`) and creates a session keyed on `iss` + `sub`.
- If it calls Google APIs, it sends the access token as a bearer token and refreshes it when it expires.
- Implicit and password grants are deprecated because they leak tokens or passwords.

## Check yourself

1. Why does the authorization code flow use a code instead of returning the token directly?
2. What attack does PKCE prevent, and why can't the attacker compute the verifier?
3. Your API receives an ID token as a bearer token. What should happen, and why?
4. Which grant fits a nightly batch job calling another service, and what does it lack compared with the code flow?
5. What is the difference between `state` and `nonce`?

### Answers

1. The browser redirect is a leaky channel (history, logs, referrers). A short-lived single-use code goes through it, and the tokens are fetched on a direct back-channel call where the client can authenticate.
2. Authorization code interception: a malicious app or proxy captures the code and redeems it. Only the SHA-256 hash of the verifier was sent, and a hash cannot be reversed, so the stolen code cannot be exchanged.
3. Reject it with 401. Its `aud` is the client's id, not your API, so `aud` validation fails. ID tokens tell the client who logged in; they are not API credentials.
4. Client credentials. There is no user, so no consent, no ID token and normally no refresh token; the service just requests a new token when the old one expires.
5. `state` is checked by the client when the redirect comes back and protects the authorization response against CSRF. `nonce` is placed inside the ID token by the provider and protects against ID token replay.
