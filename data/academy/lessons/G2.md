## Where we are

From AI-ENG-1 you know that a model:

- reads tokens and predicts the next one in a loop;
- samples (so its output varies);
- sees only what is in its context window;
- hallucinates when asked to recall facts it doesn't have.

This lesson is about *using* a model from code: getting reliable output, letting it call your code, and keeping cost and latency under control.

## The problem

You want the app to read a job posting and pull out `{company, role, skills[]}`. The first attempt:

```text
prompt:  "Extract the company, role and skills from this posting as JSON: ..."
reply:   "Sure! Here's the JSON you asked for:
          ```json
          { "company": "Contoso", "role": "SDE II", "skills": "Java, Azure" }
          ```"
```

The reply has three problems:

- a chatty preamble;
- Markdown fences;
- `skills` comes back as a string instead of a list.

Your `ObjectMapper` throws. On the next run the shape is different again.

The posting is 3,000 tokens, and you run this for 500 postings a night.

Four things need fixing: **output shape, access to live data, latency for users, and cost**. Each section below fixes one of them.

All the examples use Claude through the official Java SDK (`com.anthropic:anthropic-java`) with model id `claude-opus-5-5`.

The concepts carry over to any provider. Only the syntax changes.

## The request: messages, system prompt, max tokens

A call to the **Messages API** sends a list of **messages** (alternating `user` and `assistant` turns), an optional **system prompt** (standing instructions that apply to the whole conversation, such as role, rules and format), and **`max_tokens`** (a hard cap on output length).

```java
AnthropicClient client = AnthropicOkHttpClient.fromEnv();   // reads ANTHROPIC_API_KEY

MessageCreateParams params = MessageCreateParams.builder()
    .model("claude-opus-5-5")
    .maxTokens(16000L)
    .system("You extract structured data from job postings. Never invent fields.")
    .addUserMessage("Posting:\n" + postingText)
    .build();

Message response = client.messages().create(params);
```

Two fields on the response matter every time:

- **`stop_reason`** says why generation stopped. **Check it before you trust the content.**
  - `end_turn` means it finished normally.
  - `max_tokens` means the output was cut off.
  - `tool_use` means it wants to call a tool.
  - `refusal` means a safety check declined the request.
- **`usage`** reports input and output token counts. Log it on every call, so that cost is measured rather than guessed.

## Prompting: be the clear spec you'd want to receive

**Prompting** is writing the instructions. Modern models follow instructions well, so a good prompt reads like a good ticket:

```text
Bad:   "Extract skills."
Good:  "Extract the technical skills the posting *requires* (not 'nice to have').
        Use the posting's own wording. If none are listed, return an empty list.
        The output feeds a study planner, so precision matters more than recall."
```

The rule: state

- the goal;
- the context ("who uses this output and why");
- the edge cases;
- what to do when information is missing.

Put large documents in the user message, wrapped in clear delimiters such as `<posting>…</posting>`, so the model can tell your data apart from your instructions. That separation matters again for security in AI-ENG-6.

## Prompting techniques

A clear spec is the base. These five techniques are the named tools on top of it.

You will usually combine two or three.

| Way | How | When to choose | Pitfall |
|---|---|---|---|
| Role / system prompt | Standing instructions in `system`: who the model is, rules, output format | Every production call | Putting per-request data in it, which breaks prompt caching (below) |
| Few-shot examples | 2–5 input → output pairs, each in `<example>` tags | The right answer is easier to *show* than describe: edge cases, tone, format | The model copies surface features; use varied examples, not five near-copies |
| Chain-of-thought vs extended thinking | CoT: ask for visible step-by-step reasoning before the answer. Extended thinking: the provider lets the model reason in separate `thinking` blocks first | Multi-step reasoning, planning, maths | On current Claude, thinking is built in; ask for visible CoT only when you want to read the steps |
| Prompt chaining | Split the task into calls; the output of one is the input of the next | Distinct sub-tasks, or you need to check an intermediate result | Every link adds latency, and errors flow downstream unless you validate between links |
| Templates with versions | Prompts live in files with placeholders; each call logs `prompt=extract-posting@v3` | As soon as more than one prompt is in production | Editing a prompt in place with no eval run: a silent regression |

**Thinking on the current API.** On `claude-opus-5-5`, thinking is adaptive and always on: the model decides how much to reason.

- **Off switch:** none. You can't turn it off.
- **The control** is **effort** (`low` to `max`, default `medium`).
- **Output:** the raw reasoning is never returned. You can ask for a readable summary (`display: "summarized"`).
- **Billing:** thinking tokens are billed either way.

So "think step by step" in the prompt is mostly redundant here. Raise effort instead, and measure.

**Predict:** you added three examples, all tech postings from large companies. A posting from a hospital comes in.

What can go wrong?

The model may force the hospital posting into the shape of your examples, for instance by listing "Java" because every example had it. Few-shot teaches by imitation, so vary the examples and include one with an empty answer.

A versioned template, kept in the repo next to its eval set:

```text
# prompts/extract-posting.v3.txt   (logged with every call as extract-posting@v3)
Extract only the skills the posting REQUIRES, in the posting's own words.
<example><posting>... Bonus points for Go ...</posting><skills>[]</skills></example>
<example><posting>... Must know SQL and Java ...</posting><skills>["SQL","Java"]</skills></example>
<posting>{{posting}}</posting>
```

The rule: spec first, examples for judgement calls, effort for reasoning depth, chains for separate jobs, and a version number on everything so that "the output got worse on Tuesday" can be traced to a change.

## Structured output: let the API enforce the shape

**Structured output** means giving the API a JSON Schema and having it *constrain* generation, so the response is guaranteed to parse into that shape. This replaces "please reply in JSON" and hoping.

In the Java SDK you can pass a class and get typed objects back. The SDK derives the schema from it:

```java
record JobPosting(String company, String role, List<String> skills) {}

StructuredMessageCreateParams<JobPosting> params = MessageCreateParams.builder()
    .model("claude-opus-5-5")
    .maxTokens(16000L)
    .outputConfig(JobPosting.class)
    .addUserMessage("<posting>\n" + postingText + "\n</posting>")
    .build();

client.messages().create(params).content().stream()
    .flatMap(cb -> cb.text().stream())
    .forEach(typed -> System.out.println(typed.text().skills()));
```

The general rule: **when code consumes the output, use structured output, not prompt instructions.**

- The schema guarantees the *shape*, not the *truth*.
- `skills` will be a list, but the items in it can still be wrong.
- You still need validation and evals (AI-ENG-6).

- On the wire, this is the `output_config.format` request field.
- Older code used a field called `output_format`, which is now deprecated.
- Current Claude models also reject "prefill", the old trick of starting the assistant's reply with `{` yourself.

## Four ways to get JSON back

You will meet all four in real codebases, often in this historical order. They differ in one thing: **who guarantees the shape**.

| Way | How | Shape reliability | Acceptable when | Pitfall |
|---|---|---|---|---|
| 1. Prompt only | "Reply only with JSON like `{...}`", then parse | Lowest: preambles, fences, wrong types | A prototype, or a human reads the result | Works in the demo, breaks on posting 312 of 500 |
| 2. Schema in prompt + parse + retry | Put a JSON Schema in the prompt, parse, validate, and on failure re-ask with the error | Good, but probabilistic; a retry costs another call | The provider or model has no native support, or you need portable code | Unbounded retries; no validation on a stream |
| 3. Tool call as schema | Define a tool whose `input_schema` is your shape and read the arguments as your JSON | High *if* the tool is called (`strict: true` keeps the arguments valid) | The output really is one action among several tools | Relying on forcing the tool (see below) |
| 4. Native structured output | `output_config.format` with a JSON Schema; the provider **constrains decoding** so only valid tokens can be generated | Highest for shape | The default whenever code consumes the output and the provider supports it | Shape is not truth; and only part of JSON Schema may be supported |

**Way 2 is what Spring AI's converter does.**

- `BeanOutputConverter` derives a JSON Schema from your class.
- `getFormat()` produces format instructions that go into the prompt.
- `convert()` parses the reply. Its docs call this "best effort".

Adding `validateSchema()` to an `entity(...)` call checks the reply against the schema and, on failure, sends the error back to the model and tries again (up to 3 attempts by default).

- **Watch out:** it doesn't work with streaming, because it needs the whole reply.
- **Way 4:** Spring AI can also switch to way 4 with `useProviderStructuredOutput()`. On a provider without support, that option is **silently ignored** and you are back on way 2.

**Way 3 has changed.** The classic trick was to force the tool with `tool_choice`.

- On `claude-opus-5-5`, a forced `tool_choice` (`any` or a named tool) is rejected with a 400.
- With `auto`, the model may answer in plain text instead.
- For "I just want JSON", use way 4.

**Predict:** way 4 guarantees valid JSON. Can you still get a reply that doesn't parse?

Yes. If generation stops at `max_tokens`, or the request ends in `refusal`, the JSON may be cut off or missing.

Constrained decoding controls *which* tokens can appear, not *whether generation finishes*. Check `stop_reason` first.

```text
reliability of shape:   1 prompt-only  <  2 schema + retry  <  3 strict tool (if called)  ≈  4 native
cost per good result:   rises with every retry in 1 and 2;  flat in 4
```

The rule: way 4 by default, way 2 as the portable fallback with a bounded retry count, way 3 only when the JSON really is a tool call, and way 1 never in a pipeline.

## Tool use: let the model ask your code for things

The model can't see your database or today's data. **Tool use** (also called **function calling**) lets you describe functions to the model.

1. The model replies with a request to call one.
2. Your code runs it.
3. You send back the result.

```text
you   → model : question + tool definitions [get_question_by_slug(slug)]
model → you   : stop_reason=tool_use, tool_use{name:"get_question_by_slug", input:{slug:"lru-cache"}}
you           : run your Java method → JSON result
you   → model : previous messages + tool_result{tool_use_id, content}
model → you   : stop_reason=end_turn, final answer that uses the result
```

Key facts:

- A tool definition is a **name**, a **description** (the model reads it to decide when to use the tool, so write it carefully), and an **input JSON Schema**.
- **The model never executes anything.** It only *asks*. Your code decides whether to run the call, so you control permissions, validation and side effects.
- One reply can contain several tool calls. Run them, then send **all** the results back together in one message.
- If a tool fails, return a `tool_result` marked as an error. Don't silently drop it.
- Setting `strict: true` on a tool makes the arguments always match its schema.

This loop of call → tool → call → tool is the seed of the agents in AI-ENG-5. The Java SDK also has a beta "tool runner" helper that runs the loop for you over annotated classes.

A current-API note: on `claude-opus-5-5`, forcing a specific tool through `tool_choice` (`any` or a named tool) is rejected.

- Use `auto` and say in the prompt which tool to use.
- If you only wanted JSON back, use structured output instead.

## Streaming: show tokens as they arrive

From AI-ENG-1 you know that output is generated one token at a time.

- Without **streaming**, the user stares at a spinner until the whole answer is done.
- With streaming, the API sends events as tokens are produced, over **Server-Sent Events (SSE)**, a one-way HTTP stream from server to client.

```java
try (StreamResponse<RawMessageStreamEvent> stream = client.messages().createStreaming(params)) {
    stream.stream()
        .flatMap(event -> event.contentBlockDelta().stream())
        .flatMap(delta -> delta.delta().text().stream())
        .forEach(text -> System.out.print(text.text()));
}
```

The rule: stream anything a human waits on, and anything with a large `max_tokens`, because a long non-streaming request can hit HTTP timeouts. Total generation time doesn't change; what improves is *time to first token*.

## Prompt caching: stop paying full price for the same prefix

Your system prompt and schema are the same on every call; only the posting changes.

**Prompt caching** lets the provider store the processed form of a stable **prefix** (the beginning of the request) and reuse it on later calls, so those tokens are cheaper and faster.

```text
call 1:  [system prompt + schema | posting A]   → writes the cache (costs slightly more)
call 2:  [system prompt + schema | posting B]   → reads the cache (costs much less)
          └──── identical prefix ───┘
```

```java
.systemOfTextBlockParams(List.of(
    TextBlockParam.builder()
        .text(longSystemPrompt)
        .cacheControl(CacheControlEphemeral.builder().build())   // mark the end of the cacheable prefix
        .build()))
```

The rules:

- It is a **prefix match**.
  - Any byte that changes inside the prefix (a timestamp, a reordered tool list) invalidates everything after it.
  - Put stable content first and variable content last.
- Cache entries expire. The default lifetime is about 5 minutes, refreshed on each hit, and a 1-hour option exists.
- Writing the cache costs a bit more than normal input; reading it costs a small fraction. It pays off from roughly the second request that reuses the prefix.
- Verify it is working: `usage.cache_read_input_tokens` should be above zero on repeat calls. If it stays at zero, something in your prefix keeps changing.
- Prompts shorter than a model-specific minimum aren't cached, and there is no error when that happens.

## Batch processing: half price when nobody is waiting

The nightly 500-posting job has no user waiting on it. The **Message Batches API** takes many requests at once, processes them asynchronously (usually within hours, with a 24-hour limit) and costs **50% less**.

```text
submit batch [ {custom_id:"posting-001", params}, ..., {custom_id:"posting-500", params} ]
poll until processing_status = "ended"
read results → each has custom_id + succeeded | errored | expired
```

Results come back in **any order**, so match them by `custom_id`, never by position. Batching and caching combine.

## Choosing a model: cost, latency, quality

Providers sell tiers: a large, most capable model; a mid-tier model; a small, fast, cheap one. Claude's current list prices per million tokens (input / output, at the time of writing; check the pricing page):

```text
Claude Opus 5.5    claude-opus-5-5     $4 / $20         default; strongest reasoning in the Opus line
Claude Sonnet 5.5  claude-sonnet-5-5   $2 / $10         strong and faster for everyday work
Claude Haiku 5.5   claude-haiku-5-5    $0.10 / $0.50    cheapest, fastest; simple high-volume tasks (prompts ≤100K tokens)
```

How to choose:

1. Start with the strongest model to find out whether the task is even solvable.
2. Build a small eval set (AI-ENG-6), then measure cheaper options *on your data*. That includes the same model at lower **effort**, a setting on current Claude models that trades depth of reasoning for tokens and speed.
3. Judge **cost per completed task**, not cost per call. A cheap call that needs retries or human fixes isn't cheap.
4. Apply the free wins first: caching, batching, and trimming the input.

## Lab (~10 min)

Turn the problem from the start of the lesson into a working extractor. You need `ANTHROPIC_API_KEY` set and the dependency `com.anthropic:anthropic-java` (the skill docs show version `2.34.0`; use the latest).

```java
import com.anthropic.client.AnthropicClient;
import com.anthropic.client.okhttp.AnthropicOkHttpClient;
import com.anthropic.models.messages.MessageCreateParams;
import com.anthropic.models.messages.StructuredMessageCreateParams;
import java.util.List;

public class ExtractLab {
    record JobPosting(String company, String role, List<String> requiredSkills) {}

    public static void main(String[] args) {
        AnthropicClient client = AnthropicOkHttpClient.fromEnv();
        String posting = """
            Contoso is hiring a Software Engineer II (Backend). You will build Java 21 /
            Spring Boot services on Azure. Must have: Java, SQL, distributed systems.
            Nice to have: Kubernetes, LLM integration experience.
            """;

        StructuredMessageCreateParams<JobPosting> params = MessageCreateParams.builder()
            .model("claude-opus-5-5")
            .maxTokens(4000L)
            .outputConfig(JobPosting.class)
            .addUserMessage("Extract only the REQUIRED skills, not nice-to-haves.\n<posting>\n"
                + posting + "\n</posting>")
            .build();

        client.messages().create(params).content().stream()
            .flatMap(cb -> cb.text().stream())
            .forEach(typed -> System.out.println(typed.text()));
    }
}
```

What to observe:

1. You get a `JobPosting` record back directly, with no JSON parsing and no fences.
2. `requiredSkills` should leave out Kubernetes. If it doesn't, tighten the prompt.
   - Notice that the *schema* held while the *content* was wrong: shape and truth are different problems.
3. Run it three times. The wording of the skills may vary slightly (AI-ENG-1: sampling).
4. Extension: make a plain `client.messages().create(...)` call without the schema and print `response.usage()` and `response.stopReason()`. That is your cost log line.

## Gotchas

- **"Reply in JSON" in the prompt:** breaks in production. Use the structured-output schema feature.
- **Ignoring `stop_reason`:** `max_tokens` means truncated, `refusal` means no answer. Branch on it first.
- **A changing value at the top of the prompt** (timestamp, request id) kills caching. Stable content first; check `cache_read_input_tokens`.
- **Matching batch results by position:** they arrive in any order. Key by `custom_id`.
- **Unchecked tool calls:** the model only requests. Validate arguments and enforce permissions in code.
- **Choosing a model by gut feel:** measure on an eval set; compare cost per completed task.

## Explain it in 2 minutes

*"Walk me through how you'd integrate an LLM into a backend feature reliably and cheaply."*

1. Clear system prompt (goal, context, edge cases), data kept separate from instructions.
2. Structured output for anything code consumes, then validate business rules.
3. Tools for live data: the model requests, your code executes and authorises.
4. Stream user-facing replies; check `stop_reason` every time.
5. Cache the stable prefix, batch offline work, log `usage`, pick the model by evals and cost per task.
