## Where we are

BE-STORY-7 introduced Maven: a `pom.xml`, coordinates, Maven Central and transitive dependencies. BE-STORY-8 used
it to build a Spring Boot fat jar with `mvn package`. This lesson opens the box: what actually happens when you type
`mvn clean install`, how dependency versions are chosen, and how a multi-module build is ordered. Interviewers ask
"explain the Maven lifecycle" to see whether you just run commands or understand your build.

## The problem

A teammate runs `mvn install -DskipTests` to "build faster", and the CI pipeline runs `mvn integration-test`. Both
look harmless. The first can publish an untested jar to everyone's local cache. The second can leave a test
database running, because the cleanup step never runs. And one day the service fails at start-up with
`NoSuchMethodError`, although it compiled. All three come from not knowing how the lifecycle and dependency
resolution work.

## Lifecycles and phases

A **phase** is a named step of a build, such as `compile` or `test`. A **lifecycle** is an ordered list of phases.
Maven has three built-in lifecycles:

```text
clean    pre-clean → clean → post-clean                       delete target/
default  validate → compile → test → package → verify → install → deploy   (main phases; there are more in between)
site     pre-site → site → post-site → site-deploy            project documentation
```

The main phases of the **default** lifecycle:

| Phase | What happens |
|---|---|
| `validate` | the project is correct and all information is available |
| `compile` | compile `src/main/java` into `target/classes` |
| `test` | run unit tests against the compiled code (nothing is packaged yet) |
| `package` | bundle the compiled code into its format: a jar, war, etc. |
| `verify` | run checks on the package, such as integration tests and quality gates |
| `install` | copy the package into your local repository, `~/.m2/repository` |
| `deploy` | upload the package to a remote repository (Nexus, Artifactory) for other teams |

The default lifecycle also has finer phases between these, for example `process-resources`, `test-compile`,
`prepare-package`, `pre-integration-test`, `integration-test` and `post-integration-test`.

**The key rule: running a phase runs every earlier phase of the same lifecycle first.** `mvn package` means
validate, compile, test, then package. `mvn clean install` runs the clean lifecycle up to `clean`, then the default
lifecycle up to `install`.

## Phases do nothing: plugin goals do the work

A **plugin** is a jar of build code, and a **goal** is one task inside it, written `plugin:goal`. A phase is just a
hook; Maven runs the goals **bound** to it. For a project with `<packaging>jar</packaging>`, the default bindings
include:

```text
process-resources  → resources:resources     copy src/main/resources
compile            → compiler:compile        javac
test-compile       → compiler:testCompile
test               → surefire:test           run unit tests
package            → jar:jar                 build the jar
install            → install:install
deploy             → deploy:deploy
```

The packaging type decides the bindings: a `war` project binds `war:war` to `package` instead. You add your own
by declaring a plugin `<execution>` with a `<phase>`. That is how Spring Boot works: its parent POM binds the
`spring-boot-maven-plugin`'s `repackage` goal to `package`, which turns the plain jar into the executable fat jar
you ran in BE-STORY-8.

You can also run a goal on its own, outside any lifecycle: `mvn dependency:tree` or `mvn spring-boot:run`. Then only
that goal runs (plus whatever it explicitly asks for), not the earlier phases.

Rule: **lifecycle = order, phase = hook, goal = work, packaging = default bindings.**

## Unit tests and integration tests

Two plugins run tests at different phases:

- **Surefire** runs in `test`. By default it picks classes named like `*Test`, `Test*`, `*Tests` and `*TestCase`.
  A failure stops the build.
- **Failsafe** runs `*IT` classes in `integration-test` and checks the results in `verify`. A failure in
  `integration-test` does not stop the build immediately, so `post-integration-test` still runs and can stop the
  server or container it started. Then `verify` fails the build.

So run `mvn verify`, never `mvn integration-test`: the latter stops before the cleanup and before the check that
fails the build.

Two skip flags people mix up:

| Flag | Compiles tests? | Runs tests? |
|---|---|---|
| `-DskipTests` | yes | no |
| `-Dmaven.test.skip=true` | no | no |

Both are fine on a laptop. Neither belongs in a pipeline that publishes artifacts.

## Dependency scopes

A **scope** says on which classpath a dependency belongs:

| Scope | Compile | Test | Runtime / packaged | Typical example |
|---|---|---|---|---|
| `compile` (default) | yes | yes | yes | spring-web |
| `provided` | yes | yes | no, the server or JDK supplies it | servlet API in a war, Lombok |
| `runtime` | no | yes | yes | the PostgreSQL JDBC driver |
| `test` | no | yes | no | JUnit, Mockito, Testcontainers |
| `import` | — | — | — | only inside `dependencyManagement`, to import a BOM |

The JDBC driver is `runtime` because your code talks to the `java.sql` interfaces (DB-SQL-5 territory later), never
to the driver's classes directly.

## How versions are chosen

Transitive dependencies mean two libraries can ask for different versions of a third. Maven keeps exactly one:

1. **Nearest wins.** The version declared closest to your project in the dependency tree is used.
2. **At equal depth, the first declaration wins** (the order in your `pom.xml`).

```text
your-app
├── lib-a 1.0
│   └── jackson-databind 2.15      depth 2
└── lib-b 3.0
    └── http-client 1.2
        └── jackson-databind 2.19  depth 3, loses
```

Maven picks 2.15. If `lib-b`'s code calls a method added in 2.19, it compiles (you compiled against your code, not
lib-b's) and fails at runtime with `NoSuchMethodError`. The fixes:

- `mvn dependency:tree` to see who brings what.
- `<dependencyManagement>` in your POM (or a parent) to pin one version for the whole build. It declares versions
  only; it adds no dependency by itself.
- A **BOM** (bill of materials), a POM that is just a curated `dependencyManagement`, imported with
  `<scope>import</scope>`. Spring Boot's dependency management is the BOM behind the versions you never write.
- `<exclusions>` to drop one transitive dependency.

## Multi-module builds

A larger service is often split into modules: `api`, `domain`, `persistence`, `app`. A parent POM with
`<packaging>pom</packaging>` lists them in `<modules>`:

```xml
<modules>
    <module>domain</module>
    <module>persistence</module>
    <module>app</module>
</modules>
```

The **reactor** (Maven's multi-module engine) reads every module's dependencies and builds them in dependency order,
not in the order listed. Useful flags: `-pl app -am` builds `app` and the modules it needs; `-T 4` builds
independent modules in parallel. Inheritance (`<parent>`) shares configuration; aggregation (`<modules>`) builds
together. A parent usually does both, but they are separate ideas.

Also worth knowing: `SNAPSHOT` versions (`1.4.0-SNAPSHOT`) mean "work in progress" and Maven re-checks them for
updates (`-U` forces it now), while release versions never change once published. `mvnw` (the Maven Wrapper)
downloads a fixed Maven version, so every machine and the CI server build with the same one.

## Lab (~10 min)

Use the Maven project from the BE-STORY-7 lab (or any Spring Boot project).

1. **See the bindings:** run `mvn help:describe -Dcmd=package`. It lists the phases of the lifecycle that contains
   `package` and the plugin goal bound to each one for this project.
2. **Phase order:** run `mvn clean compile` and look at `target/`: only `classes/`. Then run `mvn package` and watch
   the log lines `--- resources`, `--- compiler`, `--- surefire`, `--- jar`. That is the binding list, in order.
3. **The tree:** run `mvn dependency:tree` and find which dependency brought in `jackson-databind`.
4. **Break it:** add an old version directly, for example `jackson-databind` 2.12.0 (with no `<version>` overrides
   anywhere else), run `mvn dependency:tree` again and see that your direct declaration (depth 1) now wins over
   everything. Start the app: depending on what calls Jackson, you may get a `NoSuchMethodError` or
   `ClassNotFoundException`. Remove the line.

**Observe:** a phase name on the command line pulls in every earlier phase; a `plugin:goal` runs alone.

## Gotchas

- **`mvn integration-test` in CI.** It skips `post-integration-test` cleanup and the `verify` check, so failed
  integration tests may not fail the build. Run `mvn verify`.
- **`install` to share code between modules.** In a multi-module build, the reactor already passes module outputs
  along. Installing to `~/.m2` and building one module alone can pick up a stale jar from yesterday.
- **"It compiles, so the dependencies are fine."** Version conflicts show up at runtime as `NoSuchMethodError` or
  `NoClassDefFoundError`. Check `mvn dependency:tree` and pin with `dependencyManagement`.
- **`dependencyManagement` is not a dependency.** It only sets versions; you still declare the dependency.
- **Wrong scope.** A JDBC driver in `test` scope works in tests and fails in production; the servlet API in
  `compile` scope in a war clashes with the server's copy.
- **Depending on `SNAPSHOT`s in a release.** The build is not reproducible; a re-run can pull different code.

## In interviews

- [Explain the Maven build lifecycle](#/q/maven-build-lifecycle)

Typical follow-ups:

- *"What is the difference between `mvn install` and `mvn deploy`?"* `install` copies the artifact to your local
  `~/.m2` for other projects on this machine; `deploy` uploads it to a shared remote repository for other machines
  and teams.
- *"Two libraries need different versions of a jar. What does Maven do?"* Nearest wins, then first declaration;
  detect with `dependency:tree`, fix with `dependencyManagement`, a BOM or an exclusion.
- *"Maven vs Gradle?"* The same model (coordinates, repositories, lifecycle-like tasks); Gradle uses a programmable
  build script and incremental builds with a build cache, Maven a declarative XML file and fixed lifecycles.

## Explain it in 2 minutes

*"Explain the Maven lifecycle and what happens when you run `mvn clean install`."*

A good answer hits:

1. Three lifecycles: clean, default, site; a lifecycle is an ordered list of phases.
2. Main default phases: validate, compile, test, package, verify, install, deploy; running one runs all before it.
3. Phases are hooks; plugin goals bound to them do the work, and the packaging type sets the default bindings
   (Spring Boot binds `repackage` to `package`).
4. Surefire runs unit tests in `test`; Failsafe runs integration tests and fails the build in `verify`.
5. `install` puts the jar in `~/.m2`; `deploy` pushes it to a remote repository.
6. Scopes and "nearest wins" version resolution, with `dependencyManagement` or a BOM to control it.

## Check yourself

1. What runs when you type `mvn package`?
2. Why do phases not do anything on their own?
3. Why should a pipeline call `mvn verify` instead of `mvn integration-test`?
4. Which scope does a JDBC driver get, and why?
5. Your app compiles but fails at start-up with `NoSuchMethodError` in a library. What is the likely cause and the
   first command you run?

### Answers

1. The default lifecycle from `validate` up to `package`: resources, compile, test-compile, unit tests, then the jar.
2. A phase is only a step in the order; the work is done by plugin goals bound to it (by the packaging type or by
   your `<execution>` configuration).
3. `integration-test` stops before `post-integration-test` (cleanup) and `verify` (where Failsafe fails the build),
   so failures can pass silently and resources stay running.
4. `runtime`: the code compiles against `java.sql` interfaces and needs the driver only when it runs.
5. A dependency version conflict: Maven picked an older version of a shared library by "nearest wins". Run
   `mvn dependency:tree`, then pin the right version with `dependencyManagement`.
