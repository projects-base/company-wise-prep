## Where we are

You can write and run Java. You have probably used a chat assistant, but you have never had to reason about what is happening inside it. This lesson gives you a working mental model of a large language model: enough to predict when it will do well, when it will fail, and why. There is no maths here, only intuition. Every later lesson in this track builds on it.

## The problem

Suppose you ask a model: *"What is the default isolation level in PostgreSQL?"* It answers "Read Committed", which is correct. Then you ask: *"Which page of the Postgres 9.1 manual says that?"* It confidently names a page number, and that number is invented.

Same model, same confidence, one right answer and one made-up one. If you treat the model as a database or as a search engine, behaviour like this looks random. Once you know what the model actually does, it stops looking random. That is what this lesson is about.

## Tokens: what the model reads and writes

A **token** is a chunk of text, usually a piece of a word, that the model treats as one unit. The model never sees characters or words. It sees a sequence of token ids (integers).

```text
"Spring Boot autoconfiguration"
→ ["Spring", " Boot", " auto", "configuration"]     (illustrative split)
→ [ 9142,     8733,    3934,    15208 ]              (illustrative ids)
```

Common words are often one token. Rare words, identifiers and non-English text get split into several. As a rough rule of thumb, an English token is about three-quarters of a word, but this varies by model, because each model family has its own **tokenizer**, the component that does the splitting.

Why you care:

- **You pay per token**, and input and output are priced separately.
- **Limits are in tokens**, not characters.
- **Odd failures come from tokens.** "How many r's are in strawberry?" is hard for a model that sees two or three chunks rather than ten letters.

The rule: think in tokens, not characters. When cost or size matters, count the tokens with the provider's token-counting tool instead of guessing.

## Next-token prediction: the one thing it does

A language model does one thing. Given a sequence of tokens, it produces a **probability distribution** over what the next token could be: a score for every token in its vocabulary, with all the scores adding up to 1.

```text
Input:  "The default isolation level in PostgreSQL is Read"
Model:  " Committed" 0.91 | " Uncommitted" 0.04 | " committed" 0.03 | ...
```

Generating a reply is a loop:

```text
tokens = prompt
repeat:
    probs = model(tokens)          // one "forward pass"
    next  = pick(probs)            // sampling, covered below
    tokens.append(next)
until next == END or limit reached
```

Each output token costs one pass through the whole model. That is why output tokens cost more than input tokens and why long answers are slow: the input can be processed in parallel, but the output is produced one token at a time.

Where does the model get its probabilities from? **Training** is the process of showing the model an enormous amount of text and repeatedly adjusting its internal numbers (its **weights**) so that it predicts the next token of that text better. After further training on example conversations and human feedback, it becomes an assistant that follows instructions. The general rule is that everything the model "knows" is compressed into those weights as patterns, not stored as retrievable records. There is no table it looks facts up in.

## The context window: the model's only working memory

The **context window** is the maximum number of tokens the model can consider at once: your instructions, the conversation so far, any documents you paste in, and the reply it is writing.

```text
┌──────────────────────── context window ────────────────────────┐
│ system prompt │ earlier turns │ pasted document │ question │ reply… │
└────────────────────────────────────────────────────────────────┘
```

Analogy: the context window is like the RAM of a stateless request handler. Everything the handler needs must be in the request. Where it breaks: RAM is read uniformly, but a model can pay uneven attention across a very long context, so a fact buried in the middle of a huge input can get less weight than the same fact placed near the question.

Three consequences:

1. **The model has no memory between API calls.** A chat "remembers" because the app resends the whole conversation every time. Statelessness is your job to manage.
2. **Bigger context costs more.** You pay for every input token on every call.
3. **Context is how you give it facts it was not trained on**, such as your codebase, today's data or a private document. Lesson G3 (RAG) is built on this.

## Sampling: why the same prompt gives different answers

**Sampling** is how `pick(probs)` chooses the next token from the distribution. Always picking the most likely token (called **greedy** decoding) tends to be repetitive. So most systems pick randomly, weighted by the probabilities.

**Temperature** is the classic knob for this. Low temperature sharpens the distribution, so the top token almost always wins. High temperature flattens it, so unlikely tokens get picked more often.

```text
probs:          A 0.70   B 0.20   C 0.10
low temp   →    A 0.95   B 0.04   C 0.01   (predictable)
high temp  →    A 0.45   B 0.30   C 0.25   (varied)
```

General rule: generation is **non-deterministic by default**, so the same prompt can give different outputs. Design for that. Validate the output, don't compare it with exact string equality in tests, and don't assume a retry returns the same answer.

A current-API note: some newer models, including current Claude Opus models, no longer accept sampling parameters such as `temperature` at all, and the request is rejected if you send one. You steer them through the prompt and other controls instead (lesson G2). The concept still matters, because it explains the variability you will see.

## Why models hallucinate

A **hallucination** is fluent, confident output that is false. Go back to the opening example:

- "Read Committed" appears thousands of times in training text next to "Postgres default isolation", so it gets a very high probability.
- "Page 412 of the 9.1 manual" is a *plausible shape* of answer. The model has learned how citations look, but it has no stored record of page numbers. Next-token prediction still produces *something* that fits the shape.

The model is not lying and not looking anything up. It is producing a likely continuation. When the true answer was rare or absent in training, the likely continuation can be false while sounding exactly as confident.

Hallucination becomes likely when:

- the fact is rare, very recent (after the model's **training cutoff**, the date its training data ends), or private to you;
- the question asks for precise details: numbers, ids, URLs, quotes, API method names;
- the prompt assumes something false ("Why did Java 12 remove generics?"), and the model goes along with it.

The general rule, which shapes the whole track: **don't ask the model to recall facts that matter; give it the facts in the context and ask it to reason over them.** Then check the output. This is why RAG (G3), tools (G2) and evals (G6) exist.

## Lab (~10 min)

Build a toy "next-token sampler" in plain Java. No API key is needed. The goal is to *feel* temperature and non-determinism.

```java
import java.util.*;

public class ToySampler {
    // A fake model: a fixed distribution for the token after "The default isolation level is"
    static final Map<String, Double> LOGITS = new LinkedHashMap<>(Map.of(
        " Read Committed", 4.0,
        " Repeatable Read", 2.5,
        " Serializable", 1.5,
        " Snapshot", 0.5));

    static Map<String, Double> softmax(Map<String, Double> logits, double temperature) {
        Map<String, Double> out = new LinkedHashMap<>();
        double sum = 0;
        for (var e : logits.entrySet()) {
            double v = Math.exp(e.getValue() / temperature);
            out.put(e.getKey(), v);
            sum += v;
        }
        for (var k : out.keySet()) out.put(k, out.get(k) / sum);
        return out;
    }

    static String sample(Map<String, Double> probs, Random rnd) {
        double r = rnd.nextDouble(), acc = 0;
        String last = null;
        for (var e : probs.entrySet()) {
            acc += e.getValue();
            last = e.getKey();
            if (r < acc) return last;
        }
        return last;
    }

    public static void main(String[] args) {
        Random rnd = new Random();
        for (double t : new double[] {0.2, 1.0, 2.0}) {
            Map<String, Double> probs = softmax(LOGITS, t);
            Map<String, Integer> counts = new TreeMap<>();
            for (int i = 0; i < 1000; i++) counts.merge(sample(probs, rnd), 1, Integer::sum);
            System.out.printf("temp %.1f  probs=%s%n           counts=%s%n", t, probs, counts);
        }
    }
}
```

Here **logits** are the raw scores a model outputs before they are turned into probabilities, and **softmax** is the function that turns them into probabilities.

What you should observe:

- At temperature 0.2, "Read Committed" wins almost every time.
- At 2.0, wrong answers show up a meaningful fraction of the time.
- Run it twice: the counts differ between runs.

**Break it:** change the logits so that " Snapshot" is 3.9, almost tied with the correct answer. Even at low temperature the wrong answer now wins often. That is a small picture of hallucination: when the model's internal scores barely separate truth from a plausible alternative, confident-sounding wrong output follows.

## Gotchas

- **Treating the model as a database.** It stores patterns, not records. For facts that matter, put the source text in the context and ask the model to answer from it.
- **Estimating cost from characters or words.** Billing and limits are in tokens, and each model family tokenizes differently. Count with the provider's token counter.
- **Assuming the model remembers the last call.** Each API call is stateless. If it isn't in this request's context, the model doesn't know it.
- **Exact-match tests on model output.** Output is non-deterministic. Validate structure and key facts instead.
- **Trusting confidence.** Fluency says nothing about correctness. Be most sceptical about numbers, ids, URLs and API names.
- **Stuffing the context "just in case".** Every token costs money and latency on every call, and burying the key fact in noise can make answers worse.

## In interviews

This topic shows up as "how do you use AI tools?" and as follow-ups in AI-flavoured design rounds, where the interviewer checks whether you understand the model's limits.

- [How are AI tools helping you?](#/q/how-you-use-ai-tools): a strong answer names the limits (hallucinated APIs, stale knowledge) and how you verify output: tests, reading the docs, review.
- [Caching to reduce LLM cost; LLM observability](#/q/llm-cost-caching-and-observability) depends on understanding that cost is per token and that output tokens are the slow, expensive part.

Typical follow-ups:

- *"Why does the model make things up?"* A strong answer: it predicts likely continuations, it does not retrieve facts. Hallucination is worst for rare, recent, private or precise facts. The fixes are grounding (put sources in the context), tools, and validation.
- *"Why is a long answer slow?"* Output is generated one token at a time, one full model pass each. Input is processed in parallel.

## Explain it in 2 minutes

*"Explain to a backend colleague how an LLM produces an answer and why it sometimes invents things."*

A good answer hits:

1. Text becomes tokens, and cost and limits are measured in tokens.
2. The model predicts a probability distribution for the next token, then loops.
3. Sampling picks from that distribution, so output varies from run to run.
4. The context window is the only working memory, and calls are stateless.
5. Knowledge lives in the weights as patterns, so rare, recent or precise facts get "plausible" rather than true answers.
6. The fix is to ground the model with real sources in the context and to validate what it produces.

## Check yourself

1. Why do output tokens cost more and take longer than input tokens?
2. Your chatbot "forgets" what the user said three messages ago. What is the most likely cause?
3. You send the identical prompt twice and get two different answers. Is that a bug?
4. Which is more likely to be hallucinated: "What does HTTP 404 mean?" or "What is the exact method name for X in library Y version 3.2.1?" Why?
5. Name two things you can do to reduce hallucination without changing the model.

### Answers

1. Input tokens are processed in parallel in one pass. Each output token needs its own full pass through the model, one after another.
2. The app isn't resending the earlier turns, or it is trimming them to fit the context window. The model itself is stateless.
3. No. Sampling is random by design, so you should expect variation and validate the output rather than assert exact text.
4. The exact method name. It is a precise, rare detail, so a plausible-looking name can outscore the real one. HTTP 404 appears constantly in training text.
5. Put the authoritative source text in the context and ask the model to answer only from it; give it a tool to look the fact up; validate the output (schema checks, tests, citations you can verify).
