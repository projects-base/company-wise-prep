## Where we are

SPRING-BOOT-11 gave a service its instruments: Actuator, Micrometer metrics and a trace id. DIST-SYS-6
got that service into production. This lesson is about using those instruments once real traffic
arrives: what to record, where it goes, how Grafana shows it, when a human gets woken up, and how to
walk from an alert to the line of code at fault.

## The problem

Friday, 21:00. Support says "checkout feels slow". ShopKart runs six services. The dashboard shows
average latency of 60 ms, so everything looks fine. Someone opens the logs on one pod: plain text,
no request id, and 40,000 lines a minute. Nobody can say which requests are slow, for whom, or since
when. The fix takes four hours, and three of them are spent finding the problem.

**Monitoring** answers questions you thought of in advance ("is the error rate above 1%?").
**Observability** is being able to answer a question you did *not* think of, from the data the system
already emits, without shipping new code. You get it by recording the right three signals.

## Logs, metrics, traces: one job each

| Signal | What it is | Best at | Weak at |
|---|---|---|---|
| **Metric** | A number over time, already aggregated | "Is something wrong? Since when?" | Saying which request |
| **Trace** | The path of one request across services | "Where did the time go?" | Showing the overall trend |
| **Log** | One event, with detail | "Why did this one fail?" | Being cheap at high volume |

The order matters during an incident. A **metric** tells you something is wrong, a **trace** tells
you where, and a **log** tells you why. The trace id is what joins them: it is on the span and on
every log line, so one click takes you from a slow trace to the exact logs of that request.

## Structured logs

A plain log line is written for a human reading one file:

```text
2026-11-06 21:04:11 ERROR Payment failed for order 42
```

A **structured log** is the same event as fields, usually one JSON object per line, written for a
machine that searches millions of lines:

```json
{"ts":"2026-11-06T21:04:11Z","level":"ERROR","service":"payments","traceId":"4bf92f35","orderId":42,"msg":"Payment failed","reason":"gateway_timeout"}
```

Now `service=payments AND reason=gateway_timeout` is a query rather than a grep. Spring Boot 3.4 and
later can do this with one property, with no custom encoder:

```yaml
logging:
  structured:
    format:
      console: ecs        # also: logstash, gelf
```

Three rules keep logs useful:

- **Write to stdout.** In a container the platform collects stdout. The app should not manage log
  files or know where logs end up.
- **Use levels honestly.** `ERROR` means someone may need to act, `WARN` means unusual but handled,
  `INFO` marks business events, `DEBUG` stays off in production.
- **Never log secrets or personal data.** No passwords, tokens, card numbers or health records. Logs
  are copied widely, kept for a long time and read by many people.

## MDC: the trace id on every line

You do not want to pass a request id through every method. **MDC** (Mapped Diagnostic Context) is a
per-thread map in SLF4J. Put a value in once, and every log line on that thread carries it. With
tracing on, Boot fills in `traceId` and `spanId` for you. Your own fields work the same way:

```java
try (var ignored = MDC.putCloseable("orderId", orderId.toString())) {
    payments.charge(orderId);      // every log line in here carries orderId
}
```

The trap is in the words *per thread*. MDC is built on a `ThreadLocal`, so when work moves to another
thread (an `ExecutorService`, `@Async`, `CompletableFuture`), the context stays behind and those log
lines lose their trace id. Spring's fix is a `TaskDecorator` that copies the context across;
`ContextPropagatingTaskDecorator` does this using Micrometer's context propagation library. The lab
shows the failure and the fix.

## Metrics: types, labels and cardinality

SPRING-BOOT-11 introduced Micrometer. Three types cover nearly everything:

- **Counter:** only goes up, such as requests served. You look at its *rate*, not its value.
- **Gauge:** a current reading that moves both ways, such as queue depth or pool connections in use.
- **Timer / histogram:** a distribution of durations, placed into buckets.

Each metric has **labels** (Micrometer calls them tags), such as `uri` and `status`. Every distinct
combination of label values is a separate time series that has to be stored. The number of
combinations is the metric's **cardinality**.

```java
meter.counter("orders.placed", "channel", "mobile");    // a handful of values: fine
meter.counter("orders.placed", "userId", userId);       // one series per user: never
```

A label like `userId`, `orderId` or a raw URL can take down the metrics system itself. High-cardinality
detail belongs in logs and traces.

## Why the average lies

Suppose 98% of requests take 20 ms and 2% take 2 seconds. The average is about 60 ms, which looks
healthy, while 1 request in 50 is terrible. A page that makes ten such calls hits a slow one on
roughly 18% of loads (1 − 0.98¹⁰). That is what support was hearing about on Friday night.

So use **percentiles**. The p99 is the value that 99% of requests beat. Track p50 for the typical
user and p95 or p99 for the tail.

Percentiles have a trap of their own: **you cannot average them across instances**. The mean of three
pods' p99 values is not the service's p99. Export histogram buckets instead, which *can* be added
together, and compute the percentile afterwards:

```yaml
management:
  metrics:
    distribution:
      percentiles-histogram:
        http.server.requests: true
```

## Prometheus and Grafana

**Prometheus** is a time-series database that *pulls*: every few seconds it scrapes
`/actuator/prometheus` on each instance. **Grafana** stores nothing itself. It is the screen: it
queries data sources and draws panels. **Loki** stores logs, and **Tempo** or **Jaeger** stores
traces. An **OpenTelemetry Collector** often sits in the middle and receives, filters and forwards
this data, so services are not tied to one vendor.

```text
 service ──scrape /actuator/prometheus──► Prometheus ─┐
 service ──stdout──► log agent ─────────► Loki ───────┼──► Grafana ──► alert ──► on-call
 service ──OTLP────► OTel Collector ────► Tempo ──────┘
```

Grafana panels are queries in **PromQL**, Prometheus's query language. These two are worth knowing:

```text
# Share of requests that are failing, over the last 5 minutes
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
  / sum(rate(http_server_requests_seconds_count[5m]))

# p99 latency across all instances, built from the buckets
histogram_quantile(0.99, sum by (le) (rate(http_server_requests_seconds_bucket[5m])))
```

`rate(...[5m])` turns an ever-growing counter into per-second change. `sum by (le)` adds the buckets
from every pod, which is why histograms survive aggregation and percentiles do not.

## What to put on a dashboard

Two short lists stop a dashboard turning into 60 charts nobody reads.

**RED**, for anything that serves requests: **R**ate, **E**rrors, **D**uration.

**USE**, for anything that is a resource (CPU, a connection pool, a disk): **U**tilisation,
**S**aturation, **E**rrors. Saturation means work is waiting, like `hikaricp.connections.pending`
above zero or a growing Kafka consumer lag.

Build one screen per service: RED at the top, then its dependencies (database pool, downstream call
latency, consumer lag), then JVM health (heap after GC, GC pauses, threads). Mark deployments on the
timeline, because "what changed?" is the first question in almost every incident.

## SLOs and alerts that wake the right person

Three terms that are often mixed up:

- **SLI** (indicator): a measurement, such as the share of checkout requests under 500 ms.
- **SLO** (objective): your target for it, such as 99.9% over 30 days.
- **SLA** (agreement): a promise to a customer with a penalty. It is usually looser than the SLO.

The gap between 100% and the SLO is the **error budget**. At 99.9% over 30 days you may be out of
target for 43.2 minutes (43,200 minutes × 0.001). Budget left means ship; budget gone means slow down
and fix reliability. That turns "are we stable enough?" from an argument into a number.

Alert on **symptoms users feel**, not on causes. CPU at 90% with fast, successful requests needs no
one awake. Checkout errors burning the budget do. Each alert should need a human, say what is
affected, and link to a runbook. Teams that get paged for nothing soon stop reading pages.

## Tracing in practice

SPRING-BOOT-11 showed a trace as a tree of spans. Three things matter at scale:

- **Propagation.** HTTP calls carry the W3C `traceparent` header. Messages need it too: with
  `spring.kafka.template.observation-enabled=true` and `spring.kafka.listener.observation-enabled=true`
  the trace context travels in Kafka record headers, so a trace can cross DIST-SYS-2's topics.
- **Head sampling** decides at the start of a request whether to keep it, for example 5% at random.
  It is cheap, but it can drop the one rare failure you needed.
- **Tail sampling** decides after the request ends, so it can keep every error and every slow trace.
  It needs a collector that buffers spans, so it costs more to run.

Prometheus **exemplars** attach a sample trace id to a histogram bucket, so a spike on a Grafana
panel can link directly to a trace from that moment.

## From alert to root cause

Back to Friday, now with the instruments in place:

1. **Metric:** the alert fires on checkout's error budget. p99 is 2 s, while p50 is unchanged, so this
   is a tail problem and not a total failure.
2. **Scope it:** split by `uri`: only `POST /checkout`. Deploy markers show nothing recent.
3. **Trace:** a slow trace has a 1.9 s gap before a span in `payments`, and the SQL itself is fast.
4. **Saturation:** `hikaricp.connections.pending` in `payments` is climbing. Threads are queuing for
   a connection.
5. **Log:** filter by that trace id: a retry loop holds a connection during a gateway call.
6. **Mitigate first:** raise the pool or turn off the retry to stop the pain, then fix the code and
   write up what happened, without blame.

The order is the skill: scope, locate, explain, mitigate, then fix.

## Lab (~10 min)

One program, plain Java, two experiments: why the average lies, and how a thread hop loses the
trace id. Press Run, or save it as `ObservabilityLab.java` and run `java ObservabilityLab.java`.

```java
import java.util.Arrays;
import java.util.Random;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class ObservabilityLab {
    // What SLF4J's MDC does underneath: a value that belongs to one thread.
    static final ThreadLocal<String> TRACE_ID = new ThreadLocal<>();

    static void log(String level, String msg) {
        System.out.printf("{\"level\":\"%s\",\"thread\":\"%s\",\"traceId\":\"%s\",\"msg\":\"%s\"}%n",
                level, Thread.currentThread().getName(), TRACE_ID.get(), msg);
    }

    /** Copies the caller's trace id onto the worker thread, as a Spring TaskDecorator does. */
    static Runnable withContext(Runnable task) {
        String captured = TRACE_ID.get();
        return () -> {
            TRACE_ID.set(captured);
            try {
                task.run();
            } finally {
                TRACE_ID.remove();      // pooled threads are reused: never leave a value behind
            }
        };
    }

    static long percentile(long[] sorted, double p) {
        return sorted[(int) Math.ceil(p / 100 * sorted.length) - 1];
    }

    public static void main(String[] args) throws Exception {
        Random random = new Random(42);
        long[] millis = new long[1000];
        for (int i = 0; i < millis.length; i++) {
            millis[i] = random.nextInt(100) < 2 ? 2000 : 15 + random.nextInt(11);
        }
        Arrays.sort(millis);
        System.out.printf("avg=%.0f ms  p50=%d ms  p95=%d ms  p99=%d ms%n",
                Arrays.stream(millis).average().orElse(0), percentile(millis, 50),
                percentile(millis, 95), percentile(millis, 99));

        TRACE_ID.set("4bf92f35");
        log("INFO", "checkout started");
        try (ExecutorService pool = Executors.newSingleThreadExecutor()) {
            pool.submit(() -> log("INFO", "charging card, plain submit")).get();
            pool.submit(withContext(() -> log("INFO", "charging card, context copied"))).get();
        }
        TRACE_ID.remove();
    }
}
```

**What to observe:**

1. The average (48 ms) looks healthy, while p99 is 2,000 ms: about 100 times the p50. Change the `2`
   to `10` and watch the p95 jump while the p50 barely moves.
2. The plain `submit` logs `"traceId":"null"`: that line can no longer be found by trace id. The
   wrapped one keeps it.
3. **Break it:** delete `TRACE_ID.remove()` in `withContext`, then add a third plain `submit` after
   the wrapped one. The third line now shows a trace id it should not have. On a real pool, that is
   request A's id on request B's logs, which is worse than no id at all.

## Gotchas

- **Dashboards built on the average.** It hides the tail. Show p50 and p99 next to each other.
- **Averaging percentiles across pods.** The number means nothing. Add the histogram buckets, then
  compute the percentile.
- **A user or order id as a metric label.** It creates a series per value and can bring down
  Prometheus. Put it on the trace or log line.
- **Trace ids vanish after `@Async` or an executor.** The context is per thread. Use a `TaskDecorator`.
- **Paging on causes such as high CPU.** People stop trusting alerts. Page on what users feel.
- **Logging tokens or personal data "for debugging".** Logs last longer and travel further than the
  bug does. Log an id instead.

## In interviews

Asked as "How do you monitor a service in production?", "A user says the app is slow: walk me through
it", "Logs vs metrics vs traces?" and "What is an SLO?". Bank:
[Debugging requests across microservices](#/q/debugging-across-microservices),
[Design a Metrics Aggregator / Monitoring System](#/q/design-metrics-monitoring-system).

**Follow-up: "Why not just log everything?"** Cost and signal. Logs are the most expensive signal per
request and are slow to aggregate. Metrics are cheap and fixed-size, so they carry the trends. Traces
are sampled. Logs keep the detail for the events that matter.

**Follow-up: "How would you pick an alert threshold?"** Start from the SLO, not from a round number.
Alert when the error budget is burning fast enough to run out, rather than on a single spike, and
check that each page would have needed a human.

## Explain it in 2 minutes

"How would you find out why one endpoint became slow in production?"

- Metrics first: confirm it with p99 and the error rate, split by endpoint, and check deploy markers.
- Check whether it is the tail or everyone, because p50 against p99 changes the hypothesis.
- Open a slow trace and find the span, or the gap between spans, that holds the time.
- Check saturation of what that span depends on: connection pool, threads, consumer lag.
- Use the trace id to read the logs of that exact request.
- Mitigate first, then fix, then add the signal that would have caught it sooner.

1. Which of the three signals answers "where did the time go?", and how do you get from it to the logs?
2. Why is `userId` a bad metric label, and where does that detail belong?
3. Why can't you average p99 values across pods? What do you do instead?
4. An SLO is 99.9% over 30 days. What is the error budget in minutes?
5. Your logs lose the trace id inside an `@Async` method. Why, and what is the fix?

### Answers

1. Traces. Each log line carries the same trace id, so you filter logs by that id.
2. Every distinct value creates a new time series, so storage and query cost explode. Per-user detail
   belongs in logs and traces.
3. A percentile is not additive: the mean of p99s is not the p99 of all requests. Export histogram
   buckets, add them across pods, and compute the quantile from the sum.
4. 43.2 minutes (30 × 24 × 60 = 43,200 minutes, × 0.001).
5. MDC is thread-local and `@Async` runs on another thread. Use a `TaskDecorator`, such as
   `ContextPropagatingTaskDecorator`, to copy the context across.
