## Where we are

D5 introduced the pieces of Spring MVC: filters, the `DispatcherServlet`, handler mappings, interceptors, argument resolvers, message converters and `@ControllerAdvice`. This lesson lines them up as **one request's timeline**, from the TCP socket to the last byte. It names the class doing the work at each stage, and the trap waiting there. The example request is this repo's progress update:

```text
PUT /api/questions/lru-cache/progress
Content-Type: application/json

{"action":"DONE"}
```

## The problem

"The request returned 400 and my controller never ran." "My interceptor can't change the response." "My `@ControllerAdvice` doesn't catch the 401." Each of these puzzles has the same answer: *it happened at a different stage than you assumed*. If you know the order of the stages, these become easy to work out.

## The whole lifecycle at a glance

```text
 socket ─► Tomcat worker thread  (http-nio-8090-exec-N)                 (1)
            └─ servlet filter chain (in → )                              (2)
                └─ DispatcherServlet.doDispatch                          (3)
                     ├─ HandlerMapping → handler + interceptors          (4)
                     ├─ interceptors.preHandle (in order)                (5)
                     ├─ HandlerAdapter.handle:
                     │    ├─ argument resolvers (+ body read, @Valid)    (6)
                     │    ├─ YOUR CONTROLLER METHOD (+ service proxies)  (7)
                     │    └─ return value → message converter → bytes    (8)
                     ├─ interceptors.postHandle (reverse)
                     ├─ exception? → HandlerExceptionResolvers           (9)
                     └─ interceptors.afterCompletion (reverse, always)   (10)
            └─ filter chain (← out)
          Tomcat flushes, recycles objects, thread back to pool           (11)
```

## Stage 1: a Tomcat thread picks up the request

**What happens:** Tomcat's connector accepts the TCP connection. When bytes arrive, a **worker thread** from Tomcat's pool parses the HTTP request into `HttpServletRequest` and `HttpServletResponse` objects. **This one thread carries the request through every stage below.** That is why thread-locals such as the `SecurityContext` and logging MDC work at all.

**Gotcha:** the pool is bounded (`server.tomcat.threads.max`, default 200). If every thread is blocked on a slow downstream call, new requests queue and then time out, even while the CPU sits idle. Options: add timeouts to every outbound call, or use virtual threads (`spring.threads.virtual.enabled=true` on Java 21), which make blocking cheap.

## Stage 2: the servlet filter chain

**What happens:** the request passes through each registered `Filter` in order. In a typical Boot app those are `CharacterEncodingFilter`, `FormContentFilter`, `RequestContextFilter`, Spring Security's `springSecurityFilterChain` if it is present (D7), and Actuator's observation filter, which times the request. Each filter calls `chain.doFilter(...)` to pass the request on. The code *after* that call runs on the way back out.

**Gotchas:**

- Exceptions thrown here never reach `@ControllerAdvice`, because the `DispatcherServlet` hasn't been entered yet.
- Reading the body in a filter *consumes* the stream, so the controller then gets an empty body. Use `ContentCachingRequestWrapper` if you need to log it.
- Filters also run on **error dispatches** (forwards to `/error`). Extend `OncePerRequestFilter` to avoid running twice.

## Stage 3: DispatcherServlet

**What happens:** `FrameworkServlet.service` → `processRequest` (binds the locale and request attributes to the thread) → `DispatcherServlet.doService` → **`doDispatch`**. That last method is the heart of Spring MVC, and the best single breakpoint in it (D10).

**Gotcha:** the `DispatcherServlet` is mapped to `/`. Everything inside the app that isn't a static file goes through it, including your SPA's (single-page app's) routes.

## Stage 4: HandlerMapping, "who handles this?"

**What happens:** `doDispatch` asks each `HandlerMapping` in order. `RequestMappingHandlerMapping` holds a table built at startup from every `@RequestMapping`. It finds `ApiController.updateProgress` by matching path, method, consumes and produces, then wraps the method and the matching **interceptors** into a `HandlerExecutionChain`. Static-resource mappings come later, as a catch-all.

**Gotchas:**

- No controller matched? The resource handler finds no file either, and you get a 404. Since Spring 6.1 that 404 is raised as `NoResourceFoundException`.
- `/api/companies/` (trailing slash) no longer matches `/api/companies` by default since Spring 6.
- A path that matches but uses the wrong HTTP method gives **405**. A wrong `Content-Type` against `consumes` gives **415**.

## Stage 5: interceptors' `preHandle`

**What happens:** each `HandlerInterceptor.preHandle(request, response, handler)` runs in registration order. Unlike a filter, it knows **which controller method** was chosen (`handler` is a `HandlerMethod`). Returning `false` stops the request. You are then responsible for writing the response.

**Gotcha:** interceptors only see requests that reached the `DispatcherServlet` and matched a handler. For "every request, including static files and errors", use a filter.

## Stage 6: argument resolution and validation

**What happens:** `RequestMappingHandlerAdapter` builds the argument list. For each parameter, a `HandlerMethodArgumentResolver` that supports it produces the value:

```text
@PathVariable String slug         → PathVariableMethodArgumentResolver  → "lru-cache"
@Valid @RequestBody ProgressRequest → RequestResponseBodyMethodProcessor
        pick HttpMessageConverter by Content-Type (Jackson for JSON)
        read body → ProgressRequest(action=DONE, notes=null)
        @Valid → Bean Validation → @NotNull action ✓
```

**Gotchas:** every failure here is a 400 *before your method runs*.

- Malformed JSON, or an unknown enum value such as `"action":"FINISHED"`: `HttpMessageNotReadableException`.
- `{}`: action is null, so `@NotNull` fails and you get `MethodArgumentNotValidException`.
- `?page=abc` for an `int` parameter: `MethodArgumentTypeMismatchException`.

Putting a breakpoint in the controller won't help you debug any of these.

## Stage 7: your controller runs

**What happens:** the method is invoked by reflection. `progress.apply(...)` goes through `ProgressService`'s **transaction proxy**, so the transaction begins and commits *inside* this stage (L7).

**Gotcha:** this repo sets `spring.jpa.open-in-view: false`, so the persistence context closes when the service returns. Touching a lazy association after that, in the controller or during JSON writing in stage 8, throws `LazyInitializationException`. That is why the services return records (`ProgressService.View`), not entities. Boot's default is `open-in-view: true`, which hides the problem by holding a database connection for the whole request.

## Stage 8: return value to bytes

**What happens:** because this is a `@RestController`, `RequestResponseBodyMethodProcessor` handles the return value:

1. **Content negotiation** compares the `Accept` header with what the converters can produce, and picks `application/json`.
2. Any `ResponseBodyAdvice` beans get a chance to modify the body.
3. The Jackson converter serialises `View` and writes it to the response stream, then flushes it.

Once flushed, the response is **committed**: the status and headers have been sent.

**Gotchas:**

- `postHandle` runs *after* this stage, so for `@ResponseBody` methods it is **too late to change headers or status**. Use `ResponseBodyAdvice`, or a filter that wraps the response.
- A client that only accepts `text/xml` gets **406**.

## Stage 9: exceptions become responses

**What happens:** if any of stages 4–8 throws, `processHandlerException` asks the `HandlerExceptionResolver`s in order:

1. `ExceptionHandlerExceptionResolver`: your `@ExceptionHandler` methods, local or in `@ControllerAdvice`.
2. `ResponseStatusExceptionResolver`: `@ResponseStatus` on the exception class. This repo's `NotFoundException` becomes 404 this way.
3. `DefaultHandlerExceptionResolver`: Spring's own exceptions mapped to 400, 405, 415 and so on.

Resolvers 2 and 3 usually call `response.sendError(status)`. If nobody resolves the exception at all, it propagates to Tomcat. Either way, Tomcat then makes an **ERROR dispatch** to `/error`, where Boot's `BasicErrorController` renders the JSON error body. That second pass goes through the filter chain and the `DispatcherServlet` again.

**Gotcha:** a resolver that handles the exception *returns a response normally*, so callers further up see no exception.

## Stage 10: `afterCompletion`

**What happens:** `afterCompletion(request, response, handler, ex)` runs on every interceptor whose `preHandle` returned true, in **reverse** order. It runs even after errors. This is the place to clean up thread-locals and record timings.

**Gotcha:** `ex` is only non-null for exceptions that **no resolver handled**. A validation 400 or a `NotFoundException` 404 arrives here with `ex == null`.

## Stage 11: unwind and recycle

**What happens:** control returns up through the filters (their "after" code runs), Tomcat finishes writing, and the request and response objects are recycled. The worker thread goes back to the pool to serve someone else's request.

**Gotcha:** anything you put in a `ThreadLocal`, such as MDC keys or a custom context, **leaks into the next request on that thread** unless you clear it in a `finally` block.

## Lab (~10 min)

Log every stage you can hook into, then send three requests. Add these beans to the repo:

```java
@Component
class StageFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        System.out.printf("[%s] 2 filter IN  %s %s%n", Thread.currentThread().getName(), req.getMethod(), req.getRequestURI());
        try { chain.doFilter(req, res); }
        finally { System.out.printf("[%s] 11 filter OUT status=%d%n", Thread.currentThread().getName(), res.getStatus()); }
    }
}

@Component
class StageInterceptor implements HandlerInterceptor {
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        System.out.println("5 preHandle -> " + handler); return true;
    }
    public void postHandle(HttpServletRequest req, HttpServletResponse res, Object handler, ModelAndView mv) {
        System.out.println("8b postHandle committed=" + res.isCommitted());
    }
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res, Object handler, Exception ex) {
        System.out.println("10 afterCompletion ex=" + ex);
    }
}

@Configuration
class StageWebConfig implements WebMvcConfigurer {
    private final StageInterceptor interceptor;
    StageWebConfig(StageInterceptor interceptor) { this.interceptor = interceptor; }
    @Override public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(interceptor).addPathPatterns("/api/**");
    }
}

@RestControllerAdvice
class StageBodyAdvice implements ResponseBodyAdvice<Object> {
    public boolean supports(MethodParameter rt, Class<? extends HttpMessageConverter<?>> type) { return true; }
    public Object beforeBodyWrite(Object body, MethodParameter rt, MediaType mt,
            Class<? extends HttpMessageConverter<?>> type, ServerHttpRequest req, ServerHttpResponse res) {
        System.out.println("8a writing with " + type.getSimpleName()); return body;
    }
}
```

Also add `System.out.println("7 controller")` as the first line of `ApiController.updateProgress`. Then send:

```text
curl -X PUT localhost:8090/api/questions/lru-cache/progress -H "Content-Type: application/json" -d "{\"action\":\"DONE\"}"
curl -X PUT localhost:8090/api/questions/lru-cache/progress -H "Content-Type: application/json" -d "{}"
curl -X PUT localhost:8090/api/questions/nope/progress      -H "Content-Type: application/json" -d "{\"action\":\"DONE\"}"
```

**Observe:**

1. In the happy path, the order is 2 → 5 → 7 → 8a → 8b (with `committed=true`) → 10 → 11, all on the same `http-nio-8090-exec-N` thread.
2. With `{}`, there is no "7 controller" line: validation stopped the request in stage 6. You still get 10 with `ex=null` (a resolver handled it), and 11 shows status 400.
3. With the unknown slug, the controller runs, the service throws `NotFoundException`, and 11 shows status 404. The resolver called `response.sendError(404)`, so Tomcat then made an ERROR dispatch to `/error`, where `BasicErrorController` wrote the JSON body. Your filter does not log that dispatch, because `OncePerRequestFilter` skips error dispatches by default. Override `shouldNotFilterErrorDispatch()` to return `false` and you'll see a second "2 filter IN /error" line.
4. **Break it:** in `postHandle`, call `res.setHeader("X-Stage", "post")`, then check the response headers with `curl -i`. The header is missing, because the response was already committed.

## Gotchas

- **Filter exceptions bypass `@ControllerAdvice`.** Handle them in the filter, or with Security's entry point (D7).
- **Validation and binding failures are 400s before your controller runs.** Debug them in stage 6, not with a breakpoint in the controller.
- **`postHandle` can't change a `@ResponseBody` response.** Use `ResponseBodyAdvice` or a filter.
- **`afterCompletion`'s `ex` is null for resolved exceptions.** Read the status code instead.
- **`open-in-view` hides lazy-loading bugs** and holds a database connection for the whole request. Turn it off and return DTOs.
- **`ThreadLocal`s leak between requests** on pooled threads. Clear them in `finally` or in `afterCompletion`.

## In interviews

Typical prompts are "What happens when an HTTP request hits a Spring Boot app?", "Filter vs interceptor?", "Where does validation happen?", "How does `@ControllerAdvice` work?" and "Why is my app slow under load while the CPU is idle?" (thread pool exhaustion). Bank: [Debugging requests across microservices](#/q/debugging-across-microservices), [Design an Idempotent API](#/q/design-idempotent-api) (a filter versus interceptor placement decision), [TCP vs UDP](#/q/tcp-vs-udp) (what sits under stage 1).

**Follow-up: "Filter or interceptor for request logging with the controller name?"** Use an interceptor: it knows the `HandlerMethod`. For timing that must include security and errors, use a filter. Many teams use both.

## Explain it in 2 minutes

*"Trace a request through Spring MVC."*

- A Tomcat worker thread parses the request and carries it end to end, which is why thread-locals work and why they must be cleaned up.
- Servlet filters (encoding, security, observation) run before Spring MVC. Their exceptions bypass `@ControllerAdvice`.
- `DispatcherServlet.doDispatch`: the `HandlerMapping` finds the controller method plus its interceptors, and `preHandle` runs.
- Argument resolvers read the path and body through message converters, and `@Valid` runs. Failures are 400s before the controller.
- The controller and service proxies (transactions) run. The return value is negotiated, converted to JSON, written and committed.
- Exceptions go to resolvers (`@ExceptionHandler`, `@ResponseStatus`, defaults). `afterCompletion` runs in reverse, then the filters unwind and the thread returns to the pool.

## Check yourself

1. A request gets 400 and your controller breakpoint never hits. Name two stages that could have produced it.
2. Why can't `postHandle` add a header to a `@RestController` response?
3. Your `@ExceptionHandler` doesn't catch an exception thrown in a filter. Why?
4. What does `afterCompletion` receive as `ex` when `NotFoundException` maps to 404?
5. Why is it important that one thread handles the whole request, and what's the risk?

### Answers

1. Stage 6: message conversion (`HttpMessageNotReadableException`), `@Valid` (`MethodArgumentNotValidException`) or type conversion. Stage 2 is also possible, if a filter wrote the 400 itself.
2. The message converter in stage 8 already wrote and flushed the body, which committed the response, and that happens before `postHandle`.
3. Exception handlers are invoked by the `DispatcherServlet`, and filters run outside it, before it.
4. `null`. `ResponseStatusExceptionResolver` resolved it into a normal response.
5. Thread-locals (security context, MDC, transaction resources) rely on it. The risk is leaking that state into the next request on the reused thread, and exhausting the pool if threads block.
