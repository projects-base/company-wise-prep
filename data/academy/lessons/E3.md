## Where we are

From E1 you have small interfaces (ISP) and code that depends on them (DIP). From E2 you know
how objects get created. Structural patterns are about **wrapping and connecting** objects:
making a class fit an interface it wasn't written for, adding behaviour around it, or
controlling access to it. Small interfaces make all three cheap, which is why E1 came first.

## The problem

Your `OrderService` depends on an interface `Sender { void send(String to, String text); }`.
Three requests arrive:

1. Use a vendor SMS SDK whose method is `dispatch(SmsPayload p)`. You can't change their code.
2. Log and retry every send, for every channel, without editing each channel class.
3. Make `PaymentService` calls run inside a database transaction without writing
   `begin/commit/rollback` in every method.

All three are solved the same basic way: put an object *in front of* another object, with the
interface the caller expects. The three patterns differ in **why** the wrapper is there.

## Adapter: make an incompatible class fit

**Problem.** You have a class that does the right job with the wrong interface, and you can't
or shouldn't change it.

**Minimal example.**

```java
// Their SDK (can't change it)
record SmsPayload(String msisdn, String body) { }
class AcmeSmsClient { void dispatch(SmsPayload p) { System.out.println("ACME -> " + p); } }

// Our interface (from E1's ISP refactor)
interface Sender { void send(String to, String text); }

// The adapter: implements ours, delegates to theirs
final class AcmeSmsAdapter implements Sender {
    private final AcmeSmsClient client;
    AcmeSmsAdapter(AcmeSmsClient client) { this.client = client; }

    @Override public void send(String to, String text) {
        client.dispatch(new SmsPayload(to, text));     // translate the call
    }
}
```

`OrderService` never learns that ACME exists. Switching vendors means writing one new adapter.

**The rule:** an adapter **converts one interface into another**. It adds no new behaviour, it
only translates. In DDD this idea at system scale is called an *anti-corruption layer*: one
place where an outside model is translated into yours.

**Analogy:** a travel plug adapter. It doesn't change the electricity, only the shape of the
plug. (Where it breaks: a real adapter often also converts data types, units or error codes,
which a plug adapter never does.)

**Where the JDK and Spring use it:**

- `Arrays.asList(array)` makes an array usable as a `List`.
- `InputStreamReader` adapts a byte `InputStream` into a character `Reader`.
- Spring MVC's `HandlerAdapter`: `DispatcherServlet` can call very different kinds of handler
  (annotated `@Controller` methods, functional endpoints, older `Controller` classes) because a
  `HandlerAdapter` for each type gives them one common way to be invoked.

## Decorator: add behaviour by wrapping

**Problem.** You want to add logging, retries or metrics to *any* `Sender`. Subclassing doesn't
scale: `RetryingEmailSender`, `LoggingRetryingSmsSender`, ... is one class per combination.

**Minimal example.** A decorator implements the same interface *and* holds an instance of it.

```java
final class LoggingSender implements Sender {
    private final Sender inner;
    LoggingSender(Sender inner) { this.inner = inner; }

    @Override public void send(String to, String text) {
        System.out.println("sending to " + to);
        inner.send(to, text);
        System.out.println("sent");
    }
}

final class RetryingSender implements Sender {
    private final Sender inner;
    private final int maxAttempts;
    RetryingSender(Sender inner, int maxAttempts) { this.inner = inner; this.maxAttempts = maxAttempts; }

    @Override public void send(String to, String text) {
        for (int attempt = 1; ; attempt++) {
            try { inner.send(to, text); return; }
            catch (RuntimeException e) { if (attempt == maxAttempts) throw e; }
        }
    }
}

// Stack them in any order, on any Sender:
Sender sms = new LoggingSender(new RetryingSender(new AcmeSmsAdapter(new AcmeSmsClient()), 3));
```

**The rule:** a decorator has the **same interface** as the thing it wraps, adds behaviour
before or after delegating, and can be **stacked**. Each decorator does one thing (SRP), and
you add features by adding wrappers instead of editing classes (OCP).

**Where the JDK and Spring use it:**

- **`java.io` streams** are the textbook case:
  `new BufferedReader(new InputStreamReader(new FileInputStream("a.txt")))`. `FileInputStream`
  reads bytes, `InputStreamReader` turns them into characters (an adapter, strictly speaking),
  and `BufferedReader` adds buffering and `readLine()` (a decorator).
  `GZIPInputStream`, `BufferedInputStream` and `DataInputStream` all decorate an `InputStream`.
- `Collections.unmodifiableList(list)` and `Collections.synchronizedList(list)` wrap a list and
  change the behaviour of its methods.
- The Servlet API's `HttpServletRequestWrapper` lets a filter decorate the request, for example
  to cache the body so it can be read twice.

## Proxy: control access to an object

**Problem.** Some concerns are about *whether, when or how* a call reaches the real object:
check permissions, open a transaction, load the object lazily from the database, or call it over
the network. You don't want any of that code inside the business class.

**Minimal example: a hand-written caching proxy.**

```java
interface PriceService { double price(String sku); }

final class CachingPriceProxy implements PriceService {
    private final PriceService real;
    private final java.util.Map<String, Double> cache = new java.util.concurrent.ConcurrentHashMap<>();
    CachingPriceProxy(PriceService real) { this.real = real; }

    @Override public double price(String sku) {
        return cache.computeIfAbsent(sku, real::price);   // the real service may never be called
    }
}
```

Writing one proxy class per interface gets repetitive, so Java can generate them at runtime. A
**dynamic proxy** is a class the JVM creates while the program runs. It implements the
interfaces you list and sends every call to one handler method.

```java
import java.lang.reflect.*;

PriceService real = sku -> 42.0;
PriceService timed = (PriceService) Proxy.newProxyInstance(
        PriceService.class.getClassLoader(),
        new Class<?>[] { PriceService.class },
        (proxy, method, args) -> {
            long t0 = System.nanoTime();
            try { return method.invoke(real, args); }   // forward to the real object
            finally { System.out.println(method.getName() + " took " + (System.nanoTime() - t0) + " ns"); }
        });
timed.price("A1");                                      // prints the timing
```

**Decorator or Proxy?** The code shape is the same: same interface, wraps a target. The
difference is intent and who builds it. A **decorator** *adds features* and is usually stacked
by your own code. A **proxy** *controls access* to the target (lazy, remote, secured,
transactional) and is usually created by a framework so the caller doesn't know it's there.
In an interview, saying this distinction clearly matters more than the label.

**Where the JDK and Spring use it:**

- **Spring AOP.** For a bean with `@Transactional`, `@Cacheable`, `@Async` or a security
  annotation, Spring injects a *proxy* instead of your object. The proxy starts the transaction,
  calls your method, then commits or rolls back. If the bean implements an interface, Spring can
  use a JDK dynamic proxy like the one above. Otherwise (and by default in Spring Boot) it uses a
  generated subclass, built with the CGLIB library.
- **The self-invocation trap**, which follows directly from this: if a method in the bean calls
  another `@Transactional` method *of the same bean* with `this.other()`, the call never goes
  through the proxy, so no new transaction is applied. You will reproduce this in the lab.
- **Hibernate lazy loading:** `order.getCustomer()` can return a proxy that loads the row from
  the database on first access. Touching it after the session is closed gives the familiar
  `LazyInitializationException`.
- `java.lang.reflect.Proxy` itself, and RMI stubs for remote objects.

## The rest of the structural family

| Pattern | Problem it solves | Where you see it |
|---|---|---|
| Facade | One simple entry point to a complicated subsystem | SLF4J (literally "Simple Logging Facade for Java"); `JdbcTemplate` hides connection, statement and result-set handling |
| Composite | Treat a group of objects like one object (trees) | AWT/Swing `Container` holds `Component`s and is itself a `Component`; Spring's `CompositeCacheManager` |
| Bridge | Let an abstraction and its implementation vary independently | JDBC: your code uses the `Connection`/`Statement` API and each driver provides the implementation; SLF4J API with different logging back ends |
| Flyweight | Share many identical small objects to save memory | `Integer.valueOf` caches -128 to 127; `String` literals are interned |

## Lab (~10 min): break a proxy with self-invocation

Save as `ProxyLab.java` and run `java ProxyLab.java`.

```java
import java.lang.reflect.*;

public class ProxyLab {
    interface Account {
        void transfer();
        void audit();
    }

    static class RealAccount implements Account {
        public void transfer() {
            System.out.println("  transfer: moving money");
            audit();                                    // self-call: this.audit(), not proxy.audit()
        }
        public void audit() { System.out.println("  audit: writing audit row"); }
    }

    public static void main(String[] args) {
        Account real = new RealAccount();
        Account proxy = (Account) Proxy.newProxyInstance(
                Account.class.getClassLoader(),
                new Class<?>[] { Account.class },
                (p, method, a) -> {
                    System.out.println("[tx begin] " + method.getName());
                    try { return method.invoke(real, a); }
                    finally { System.out.println("[tx commit] " + method.getName()); }
                });

        System.out.println("Calling transfer through the proxy:");
        proxy.transfer();
        System.out.println("Calling audit through the proxy:");
        proxy.audit();
    }
}
```

What you should observe: `transfer` is wrapped in `[tx begin]` / `[tx commit]`, but the `audit`
call made *from inside* `transfer` is **not** wrapped. Only the direct `proxy.audit()` is. This
is exactly why a `@Transactional(propagation = REQUIRES_NEW)` method called from the same Spring
bean silently runs in the caller's transaction.

Then fix it in two ways and compare:

1. Move `audit()` to a separate class that is also proxied, and call it through that reference.
2. Write a `LoggingAccount` **decorator** (a plain class, no reflection) that wraps `RealAccount`
   and prints before and after each call. Notice that it has the same blind spot, because the
   wrapped object still calls `this`.

## Gotchas

- **Self-invocation skips proxies.** `@Transactional`, `@Cacheable` and `@Async` don't apply to
  calls from inside the same bean. Move the method to another bean.
- **Spring proxies only intercept calls that can be overridden.** With the subclass approach,
  `final` and `private` methods can't be intercepted, so annotations on them are silently ignored.
- **Decorator order matters.** `Logging(Retrying(x))` logs once per call, while
  `Retrying(Logging(x))` logs once per attempt. Choose deliberately.
- **An adapter should only translate.** Once it contains business rules, it is a hidden service
  that nobody tests.
- **`method.invoke` wraps exceptions.** In a dynamic proxy, the target's exception arrives as an
  `InvocationTargetException`. Unwrap it with `getCause()` and rethrow it, or callers see the
  wrong type.

## In interviews

- **Decorator** is the clean answer to "add retries, rate limiting or logging to every channel"
  in [Design a Notification System](#/q/design-notification-system), and to adding formatters
  and filters in [Design a Multi-module Logging Framework](#/q/design-logging-framework).
- **Adapter** shows up when the question says "we have three vendors with different APIs", for
  example the payment or SMS providers behind a notification system, or a switchable source in
  [Data Access Layer with Runtime-switchable Source](#/q/design-data-access-layer).
- **Proxy** comes up in Java and Spring discussions: "how does `@Transactional` work?" and "why
  didn't my transaction roll back?" are common in Java backend interviews, and a 7-year
  Spring résumé invites them in a project deep dive.

Typical follow-ups:

- *"Decorator vs Proxy?"* Same structure; a decorator adds behaviour and is stacked by you, a
  proxy controls access and is usually generated by a framework.
- *"How does Spring implement `@Transactional`?"* A proxy (JDK dynamic proxy or a CGLIB
  subclass) wraps the bean, opens the transaction, delegates, and commits or rolls back. Then add
  the self-invocation caveat without being asked.

## Explain it in 2 minutes

Prompt: *"Adapter, Decorator and Proxy all wrap an object. How are they different, and where
does Java use each?"*

- All three put an object in front of another; what differs is intent.
- Adapter changes the interface (vendor SDK → our `Sender`; `InputStreamReader`).
- Decorator keeps the interface and adds behaviour, stackable (`BufferedReader` around a
  reader; logging and retry around a channel).
- Proxy keeps the interface and controls access: lazy, remote, cached, transactional (Spring
  AOP, Hibernate lazy proxies).
- Spring proxies are JDK dynamic proxies or CGLIB subclasses; self-invocation bypasses them.

## Check yourself

1. You must use a vendor library whose method is `notifyUser(UserRef, Msg)`, but your code
   calls `Sender.send(to, text)`. Which pattern?
2. Why is a decorator better than subclasses for adding logging and retries to three channels?
3. A `@Transactional` method called from another method of the same bean doesn't start a
   transaction. Why?
4. Which pattern does `new BufferedReader(new FileReader("a.txt"))` show?
5. Give one Flyweight example from the JDK.

### Answers

1. Adapter: implement `Sender` and translate each call into `notifyUser`.
2. Subclassing needs one class per combination (3 channels × 2 features × orderings), while
   two decorators can wrap any channel in any order.
3. Spring's transaction logic lives in a proxy around the bean. An internal `this.method()` call
   goes straight to the target object and never passes through the proxy.
4. Decorator: `BufferedReader` adds buffering and `readLine()` to any `Reader`.
5. `Integer.valueOf(n)` returns a cached shared instance for -128 to 127.
