## Where we are

S10 closed the architecture pendulum: choose monolith, modular monolith or services to fit the team.
This lesson zooms back inside a single service to a pendulum of its own. In S2 you met **thread per
request**: the server gives each request its own thread. In S8's lab you watched ten threads all get
stuck waiting on a slow dependency. Here is how Java went from that, to reactive programming, and
back to thread per request with virtual threads.

## The problem

A typical ShopKart request spends almost all its time **waiting**:

```text
GET /orders/42
  parse request          0.1 ms   (CPU)
  query database        20   ms   (waiting)
  call Payments         50   ms   (waiting)
  render JSON            0.2 ms   (CPU)
```

Under 1% of the time is CPU work. Yet the thread is held for all 70 ms.

Java threads, until Java 21, were all **platform threads**: each one is an operating-system thread.
Each reserves its own stack memory (on common 64-bit platforms, roughly 1 MB of address space by
default) and costs the OS work to create and switch between. A server can run a few thousand of
them comfortably, not hundreds of thousands. So Tomcat uses a **thread pool** (a fixed set of
reusable threads; Tomcat's default maximum is 200).

With 200 threads and 70 ms per request, the ceiling is about 200 / 0.07 s ≈ 2,850 requests per
second, while the CPU sits mostly idle. If Payments slows to 5 s, the ceiling drops to 40. The
limit is not CPU or memory; it is the number of threads that are allowed to *wait*.

Dan Kegel's 1999 page *The C10K problem* (how to handle ten thousand concurrent connections on
one server) framed this question for a generation of servers.

## Invention 1: don't block, react

**Blocking** means a thread stops and waits until an operation (like a database read) finishes.
**Non-blocking I/O** means you start the operation and get notified when it's done; the thread is
free in the meantime. Java has had non-blocking network I/O (NIO) since Java 1.4 (2002).

The **event loop** model, popularised by Node.js (2009) and used in Java by Netty, runs a small
number of threads (often one per CPU core). Each thread never blocks: it starts I/O, registers a
callback, and moves to the next piece of work.

**Reactive programming** builds a programming style on top of that: you describe a *pipeline* of
steps over values that arrive later, and a library runs the steps when data is ready.

```java
// Spring WebFlux with Project Reactor (reading example)
Mono<OrderView> view(String id) {
    return orderRepo.findById(id)                                   // Mono<Order>
        .flatMap(order -> payments.status(order.paymentId())        // Mono<Status>
            .map(status -> new OrderView(order, status)))
        .timeout(Duration.ofSeconds(2));
}
```

A `Mono` is "zero or one value, later"; a `Flux` is "many values, later". Nothing runs until
someone subscribes. Key milestones: RxJava (from Netflix, early 2010s), the *Reactive Manifesto*
(2014 version), the Reactive Streams specification (2015, mirrored in Java 9 as
`java.util.concurrent.Flow`), Project Reactor, and Spring WebFlux in Spring Framework 5 (2017).

Reactive Streams also added **back-pressure**: a consumer tells the producer how many items it
can take, so a fast producer can't drown a slow consumer.

The rule: **a few threads can serve huge concurrency if nobody blocks.**

## The new pain: reactive code is hard to live with

Teams that adopted reactive got throughput, and paid for it:

- **Readability.** Simple `if`/`for`/`try` logic becomes chains of `flatMap`, `switchIfEmpty`,
  `onErrorResume`.
- **Stack traces.** An exception's stack shows the library's scheduler, not your call path.
- **Everything must be non-blocking.** One blocking JDBC call on an event-loop thread stalls every
  request that thread serves. Blocking drivers needed reactive replacements (R2DBC for SQL).
- **Thread-local context breaks.** Things stored per thread (security context, MDC log fields,
  transactions) don't follow a request that hops between threads.
- **It spreads.** A method returning `Mono` forces its callers to handle `Mono` too.

The trade-off was throughput versus debuggability and simplicity. Many teams decided it wasn't
worth it for ordinary CRUD services.

## Invention 2: virtual threads

What if threads were so cheap that blocking didn't matter? That's **Project Loom**, delivered as
**virtual threads** in Java 21 (JEP 444, released September 2023).

A **virtual thread** is a `java.lang.Thread` managed by the JVM, not the OS. Many virtual threads
run on a small pool of platform threads called **carrier threads**. When a virtual thread blocks
on I/O or `sleep`, the JVM **unmounts** it (saves its stack to the heap) and the carrier runs
another virtual thread. When the I/O completes, the virtual thread is mounted again, on any carrier.

```text
carriers (≈ CPU cores):   C1        C2
virtual threads:          v1 ─┐     v7
                          v2  │ waiting on DB (unmounted, stack on heap)
                          ... │
                          v9000┘
```

You keep writing plain blocking code:

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> {
        Order order = orderRepo.findById(id);          // blocks the virtual thread only
        Status status = payments.status(order.paymentId());
        return new OrderView(order, status);
    });
}
```

In Spring Boot 3.2 and later, `spring.threads.virtual.enabled=true` makes Tomcat run each request
on a virtual thread. Thread per request is back, without the 200-thread ceiling.

The rule: **virtual threads make waiting cheap; they don't make work faster.** CPU-bound code
gains nothing.

## The new-new pain: pinning and hidden limits

A virtual thread is **pinned** when it can't unmount while blocked, so it holds its carrier. In
Java 21 the main cause is blocking inside a `synchronized` block or method. With few carriers, a
handful of pinned threads can stall everything. Java 24 (JEP 491) removed pinning for
`synchronized`; on Java 21, prefer `ReentrantLock` around blocking calls. Native code can still pin.

Two more limits stay real:

- **Downstream capacity.** Ten thousand virtual threads can all ask for one of 20 database
  connections. The pool, or the database, becomes the bottleneck. Limit concurrency with a
  `Semaphore` or the connection pool, on purpose.
- **Don't pool virtual threads.** They are cheap to create; create one per task.

**Case: Netflix, *Java 21 Virtual Threads – Dude, Where's My Lock?* (Netflix Technology Blog,
2024).** Services that had moved to virtual threads started hanging. The investigation found
virtual threads pinned inside `synchronized` code, occupying all carrier threads, while the
virtual thread that could release a lock they needed had no carrier to run on. Read the original;
it's an excellent debugging story.

**Case: Discord, *Why Discord is switching from Go to Rust* (2020).** A different angle on the same
"runtime surprises" theme: a Go service showed periodic latency spikes that they traced to garbage
collection, and rewriting it in Rust (no garbage collector) removed them. The trade-off: managed
memory and productivity versus control over latency. In Java, low-pause collectors such as ZGC
are the usual first answer.

## Lab (~10 min)

**Build: one blocking endpoint, three ways.** Java 21, no dependencies. A sleep stands in for a
500 ms database call.

```java
import java.time.Duration;
import java.util.List;
import java.util.concurrent.*;
import java.util.stream.IntStream;

public class ThreeWays {
    static final int REQUESTS = 5_000;
    static final Duration IO = Duration.ofMillis(500);   // pretend database call

    // 1. Blocking code on a fixed pool of platform threads (classic Tomcat)
    static long platformPool() {
        try (ExecutorService pool = Executors.newFixedThreadPool(200)) {
            return time(() -> run(pool));
        }
    }

    // 2. Async style: nobody blocks; a callback runs when the "I/O" completes
    static long asyncCallbacks() {
        Executor io = CompletableFuture.delayedExecutor(IO.toMillis(), TimeUnit.MILLISECONDS);
        return time(() -> {
            List<CompletableFuture<String>> all = IntStream.range(0, REQUESTS)
                .mapToObj(i -> CompletableFuture.supplyAsync(() -> "row " + i, io)
                                                .thenApply(String::toUpperCase))
                .toList();
            CompletableFuture.allOf(all.toArray(CompletableFuture[]::new)).join();
        });
    }

    // 3. The same blocking code as (1), one virtual thread per request
    static long virtualThreads() {
        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            return time(() -> run(pool));
        }
    }

    static void run(ExecutorService pool) {
        List<Future<String>> results = IntStream.range(0, REQUESTS)
            .mapToObj(i -> pool.submit(() -> handle(i)))
            .toList();
        for (Future<String> f : results) {
            try { f.get(); } catch (Exception e) { throw new RuntimeException(e); }
        }
    }

    static String handle(int i) throws InterruptedException {
        Thread.sleep(IO);                 // blocking "query": reads top to bottom
        return ("row " + i).toUpperCase();
    }

    static long time(Runnable r) {
        long start = System.nanoTime();
        r.run();
        return (System.nanoTime() - start) / 1_000_000;
    }

    public static void main(String[] args) {
        System.out.println("platform pool (200): " + platformPool() + " ms");
        System.out.println("async callbacks:     " + asyncCallbacks() + " ms");
        System.out.println("virtual threads:     " + virtualThreads() + " ms");
    }
}
```

Run `java ThreeWays.java`. Expect the platform pool to take around 12–13 s (5,000 ÷ 200 batches of
0.5 s) and the other two well under a second. Then compare `handle` with the async chain: which
would you rather debug when step 3 of 6 throws?

**Break: pin the carriers (Java 21).**

```java
import java.util.concurrent.*;
import java.util.concurrent.locks.ReentrantLock;

public class Pinning {
    public static void main(String[] args) {
        boolean useSynchronized = args.length > 0 && args[0].equals("sync");
        long start = System.nanoTime();
        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 200; i++) {
                Object monitor = new Object();               // one lock per task: no contention
                ReentrantLock lock = new ReentrantLock();
                pool.submit(() -> {
                    if (useSynchronized) {
                        synchronized (monitor) {
                            Thread.sleep(100);                // blocks while holding a monitor
                        }
                    } else {
                        lock.lock();
                        try {
                            Thread.sleep(100);
                        } finally {
                            lock.unlock();
                        }
                    }
                    return null;
                });
            }
        }
        System.out.println((useSynchronized ? "synchronized: " : "ReentrantLock: ")
                + (System.nanoTime() - start) / 1_000_000 + " ms");
    }
}
```

Limit the scheduler to two carriers so the effect is obvious:

```text
java -Djdk.virtualThreadScheduler.parallelism=2 Pinning.java lock    → about 0.2 s
java -Djdk.virtualThreadScheduler.parallelism=2 Pinning.java sync    → about 10 s
java -Djdk.virtualThreadScheduler.parallelism=2 -Djdk.tracePinnedThreads=short Pinning.java sync
```

The last command prints where pinning happened (`reason:MONITOR`). Nobody contended for any lock;
the slowdown is purely carriers being held. On Java 24 or later, the `sync` run is fast too, and
the `jdk.tracePinnedThreads` flag no longer exists (use the JFR event `jdk.VirtualThreadPinned`).

## Gotchas

- **Blocking inside `synchronized` on Java 21.** It pins the carrier. Use `ReentrantLock`, or move
  to Java 24+; check your libraries too.
- **Expecting virtual threads to speed up CPU work.** They help when threads wait. For CPU-bound
  work, use a pool sized to the cores.
- **Forgetting downstream limits.** Unlimited virtual threads can flood a 20-connection pool or a
  partner API. Bound concurrency deliberately.
- **Pooling virtual threads.** Pooling defeats the point and hides per-task context. One per task.
- **Heavy `ThreadLocal` use.** With millions of threads, per-thread caches multiply memory. Pass
  values explicitly or use scoped values on Java versions where they are final.
- **Blocking on an event loop.** In WebFlux, one blocking call on a reactive thread stalls many
  requests. Keep reactive code fully non-blocking, or don't use reactive.

## Explain it in 2 minutes

**Prompt:** "Why did Java go from thread-per-request to reactive and back?"

1. Requests mostly wait on I/O; platform threads are costly OS threads, so pools cap concurrency.
2. Reactive: non-blocking I/O and event loops serve many requests with few threads, plus
   back-pressure.
3. Its cost: hard-to-read code, poor stack traces, lost thread context, everything must be async.
4. Virtual threads (Java 21): JVM-managed threads unmount on blocking, so plain blocking code scales.
5. Remaining traps: pinning (synchronized on 21), downstream limits, CPU-bound work.

## Check yourself

1. Why does a 200-thread pool limit throughput even when the CPU is idle?
2. What is back-pressure?
3. What happens to a virtual thread when it blocks on a socket read?
4. Name the main cause of pinning in Java 21 and two ways to avoid it.
5. Ten thousand virtual threads share a 20-connection pool. What do you expect to see?

### Answers

1. Each request holds a thread while waiting, so at most 200 requests can be in flight at once.
2. The consumer signals how much it can accept, so a fast producer can't overwhelm it.
3. The JVM unmounts it, keeping its stack on the heap, and the carrier runs other virtual threads
   until the read completes.
4. Blocking inside `synchronized`; use `ReentrantLock`, or run on Java 24 or later.
5. Most threads waiting for a connection: the pool is now the bottleneck, so throughput is bounded
   by the pool and the database, and you may see connection timeouts.
