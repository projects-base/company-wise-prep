## Where we are

From BE-STORY-1 you know that a client opens a TCP connection to a server's port, sends a plain-text HTTP request
(method, path, headers, optional body) and gets back a response with a status code, headers and a body. You also know
HTTP is stateless. This lesson fills in the vocabulary a backend engineer uses every day: what each method promises,
what each status code tells the caller, which headers drive caching and content types, and what HTTPS adds on top.

## The problem

Three real bugs, all caused by HTTP knowledge gaps:

- A mobile app times out on `POST /orders`, retries, and the customer is charged twice.
- An API returns `200 OK` with `{"error": "not found"}` in the body. The client's retry logic, its monitoring and the
  load balancer all think everything is fine.
- A product price changes, but some users see the old price for an hour because a cache was told it could keep the
  response.

None of these is a coding bug. Each is a broken **contract**: HTTP defines what methods, status codes and headers
mean, and clients, proxies, caches and browsers act on those meanings without asking you.

## Anatomy of a request and a response

```text
POST /api/orders?source=app HTTP/1.1          <- method, request target (path + query), version
Host: shop.example.com                         <- required in HTTP/1.1: which site on this IP
Content-Type: application/json                 <- what the body is
Accept: application/json                       <- what I can read back
Authorization: Bearer eyJhbGciOi...            <- who I am
Content-Length: 41                             <- body size in bytes
                                               <- blank line ends the headers
{"productId":"p1","quantity":2}                <- body
```

```text
HTTP/1.1 201 Created                           <- version, status code, reason phrase
Location: /api/orders/9812                     <- where the new resource lives
Content-Type: application/json
Content-Length: 58

{"id":"9812","status":"PENDING","total":998}
```

A URL such as `https://shop.example.com:443/api/orders?source=app` splits into **scheme** (`https`), **host**, **port**
(443 is the default for HTTPS, 80 for HTTP), **path** and **query string**. Header names are case-insensitive.

## Methods: safe and idempotent

Two properties decide how clients, proxies and frameworks are allowed to treat a request:

- **Safe**: the request does not change server state. A crawler or a prefetching browser may send it freely.
- **Idempotent**: sending the same request N times has the same effect on the server as sending it once. The
  *response* can differ (a second `DELETE` may return 404); the *state* ends up the same. Idempotent requests are the
  ones that are safe to retry automatically.

| Method | Purpose | Safe | Idempotent | Body |
|---|---|---|---|---|
| `GET` | read a resource | yes | yes | no |
| `HEAD` | `GET` without the body (check existence, size) | yes | yes | no |
| `OPTIONS` | what is allowed here (used by CORS preflight) | yes | yes | rarely |
| `PUT` | create or **replace** at a known URL | no | yes | yes |
| `DELETE` | remove | no | yes | rarely |
| `POST` | create under a collection, or run an action | no | **no** | yes |
| `PATCH` | partial update | no | not guaranteed | yes |

`PUT /users/42` with the full user twice leaves the same user. `POST /orders` twice creates two orders. That is the
first bug above: a retry of a non-idempotent request. The usual fix is an **idempotency key**: the client sends a
unique id in a header (commonly `Idempotency-Key`), and the server stores the result for that key and replays it on a
retry instead of creating a second order. Designing that properly is part of WEB-API-2.

`PATCH` is "not guaranteed" because it depends on the patch: `{"name":"Akhil"}` is idempotent, `{"op":"increment"}`
is not.

## Status codes: the five classes

The first digit is the contract; clients that do not know a specific code fall back to its class.

| Class | Meaning | Who should act |
|---|---|---|
| 1xx | informational, keep going | rarely seen by application code |
| 2xx | success | nobody |
| 3xx | go somewhere else, or use your cached copy | the client follows |
| 4xx | **the client** got something wrong | the client must change the request |
| 5xx | **the server** failed | the server's owners; the client may retry later |

The 4xx/5xx split matters for retries and alerting: retrying a 400 will fail forever, while a 503 may succeed in a
moment. That is why the second bug (errors as 200) is so damaging.

## The status codes that come up

| Code | Name | Use it when |
|---|---|---|
| 200 | OK | success with a body |
| 201 | Created | a `POST` (or `PUT`) created something; include `Location` |
| 204 | No Content | success, nothing to return (often `DELETE`, or `PUT` without a body) |
| 301 | Moved Permanently | URL changed for good; clients and search engines update |
| 302 | Found | temporary redirect |
| 304 | Not Modified | conditional `GET`: your cached copy is still valid (no body) |
| 400 | Bad Request | malformed request: unparseable JSON, missing required parameter |
| 401 | Unauthorized | not authenticated: no or invalid credentials ("who are you?") |
| 403 | Forbidden | authenticated, but not allowed ("I know you; no") |
| 404 | Not Found | no such resource (also used to hide existence from unauthorised callers) |
| 409 | Conflict | request conflicts with current state: duplicate username, version clash |
| 422 | Unprocessable Content | well-formed but fails business validation: quantity is -3 |
| 429 | Too Many Requests | rate limited; send `Retry-After` |
| 500 | Internal Server Error | an unhandled bug on the server |
| 502 | Bad Gateway | a proxy or gateway got an invalid response from the server behind it |
| 503 | Service Unavailable | overloaded or down for maintenance; temporary, may send `Retry-After` |
| 504 | Gateway Timeout | a proxy or gateway gave up waiting for the server behind it |

Distinctions interviewers like:

- **401 vs 403**: identity versus permission. The name "Unauthorized" is a historical misnomer for "unauthenticated".
- **400 vs 422**: cannot parse versus parsed but invalid. Many APIs use 400 for both; pick one rule and apply it
  everywhere.
- **502 vs 504**: you see these from a load balancer or gateway, not from your app. 502 means the upstream answered
  with garbage or closed the connection; 504 means it did not answer in time.
- **301/302 vs 307/308**: with 301 and 302, clients historically switched a `POST` to a `GET` when following the
  redirect. 307 (temporary) and 308 (permanent) require the client to keep the method and body.

## Headers that do real work

- **`Content-Type`** describes the body *being sent* (`application/json; charset=utf-8`). A server that cannot handle
  it returns **415 Unsupported Media Type**.
- **`Accept`** says what the client *wants back*. Choosing a representation from it is **content negotiation**; if the
  server cannot satisfy it, **406 Not Acceptable**.
- **`Authorization`** carries credentials, usually `Bearer <token>` or `Basic <base64(user:password)>`. Basic is only
  encoding, not encryption, so it is acceptable only over HTTPS.
- **`Location`** points to the new resource after 201, or to the target of a 3xx redirect.
- **`Content-Length`** gives the body size in bytes; for a body whose size is unknown up front, HTTP/1.1 uses
  `Transfer-Encoding: chunked` instead.
- **`Retry-After`** tells a client how long to wait after 429 or 503.

## Caching: Cache-Control and ETag

Caching lets a browser, CDN or proxy reuse a response instead of asking again. The server controls it with
**`Cache-Control`**:

| Directive | Meaning |
|---|---|
| `max-age=600` | fresh for 600 seconds; reuse without asking |
| `no-cache` | may store, but **must revalidate** with the server before each reuse |
| `no-store` | never store at all (use for sensitive data) |
| `private` | only the end user's browser may store it, not shared caches like CDNs |
| `public` | shared caches may store it too |

`no-cache` is the most misunderstood: it does not mean "do not cache". The third bug above was a `max-age=3600` on a
price that changes.

**Revalidation** uses an **ETag**, an opaque version identifier for a representation (often a hash of the body):

```text
1. GET /products/p1                      -> 200, ETag: "a1b2", body
2. GET /products/p1  If-None-Match: "a1b2" -> 304 Not Modified, no body   (unchanged)
3. (price changes)
4. GET /products/p1  If-None-Match: "a1b2" -> 200, ETag: "c3d4", new body
```

The 304 saves bandwidth and serialization, not the round trip. The same tag also enables **optimistic concurrency**
on writes: `PUT` with `If-Match: "a1b2"` succeeds only if the resource is still at that version; otherwise the server
returns **412 Precondition Failed**, and the client knows someone else changed it first. (`Last-Modified` with
`If-Modified-Since` is the older, timestamp-based version of the same idea.)

## Cookies: state on top of a stateless protocol

A **cookie** is a small name-value pair the server asks the browser to store and send back on later requests to the
same site:

```text
HTTP/1.1 200 OK
Set-Cookie: SESSION=7f3a9c; Path=/; Max-Age=1800; HttpOnly; Secure; SameSite=Lax

GET /cart HTTP/1.1
Cookie: SESSION=7f3a9c
```

The attributes are security controls:

- **`HttpOnly`**: JavaScript cannot read it, so an injected script cannot steal the session.
- **`Secure`**: sent only over HTTPS.
- **`SameSite=Lax` / `Strict`**: not sent on most cross-site requests, which blocks most cross-site request forgery.
  `None` requires `Secure`.
- **`Max-Age` / `Expires`**: without them, the cookie is deleted when the browser closes.

This is how "logged in" works on a stateless protocol; servlet sessions build on it in BE-STORY-3.

## Connections: keep-alive and HTTP versions

Opening a TCP connection costs a round trip, and HTTPS adds a TLS handshake on top. **Keep-alive** (persistent
connections, the default in HTTP/1.1) reuses one connection for many requests. HTTP clients and servers keep **pools**
of these connections.

| Version | Transport | What it changed |
|---|---|---|
| HTTP/1.1 | text over TCP | persistent connections; but in practice one request at a time per connection, so a slow response blocks the ones behind it (**head-of-line blocking**); browsers open several connections per host to compensate |
| HTTP/2 | binary frames over TCP | **multiplexing**: many concurrent requests (streams) on one connection; header compression (HPACK). A lost TCP packet still stalls every stream on that connection |
| HTTP/3 | over **QUIC**, on UDP | streams are independent at the transport level, so packet loss affects only its own stream; TLS 1.3 is built in and connection setup takes fewer round trips |

Methods, status codes and headers mean the same in all three. Your controller code does not change; the server,
proxy and client libraries handle the framing.

## HTTPS and TLS in plain terms

**HTTPS** is HTTP inside **TLS** (Transport Layer Security). TLS gives three guarantees:

1. **Confidentiality**: eavesdroppers on the network see encrypted bytes.
2. **Integrity**: tampered bytes are detected.
3. **Authentication**: you are talking to the real `shop.example.com`, not an impostor.

The handshake, simplified for TLS 1.3:

```text
client                                              server
  │ ClientHello: TLS versions, cipher suites,          │
  │   a key share (public half of a temporary key)     │
  │──────────────────────────────────────────────────►│
  │                ServerHello + its key share,        │
  │    certificate, signature proving it holds the     │
  │    certificate's private key, Finished             │
  │◄──────────────────────────────────────────────────│
  │ verify certificate; both sides now derive the same │
  │ symmetric session keys from the two key shares     │
  │ Finished, then encrypted HTTP request ────────────►│
```

Two ideas carry it. **Asymmetric** cryptography (public/private key pairs) is used only during the handshake, to agree
on keys and prove identity. **Symmetric** encryption (one shared key, much faster) protects the actual data. Because
the session keys come from temporary key shares (ephemeral Diffie-Hellman), recording traffic today and stealing the
server's private key later still does not decrypt it; this is **forward secrecy**. TLS 1.3 completes the handshake in
one round trip; TLS 1.2 needed two.

A **certificate** binds a public key to domain names, and is signed by a **certificate authority** (CA). The client
checks a **chain**: the server's certificate is signed by an intermediate CA, which is signed by a root CA that the
client already trusts (shipped with the OS, browser or JDK). It also checks that the hostname matches and the
certificate has not expired. In Java, the trusted roots live in the JDK's `cacerts` truststore; the famous
`PKIX path building failed` error means the JVM could not build that chain, typically for a corporate or self-signed
CA that is not in the truststore. The fix is to import that CA into a truststore, never to disable verification.

In production, TLS is often **terminated** at a load balancer, which then forwards plain HTTP (or re-encrypted
HTTPS) to your service. **Mutual TLS** (mTLS) adds a client certificate, so the server also authenticates the client;
it is common between internal services.

## CORS: the browser's rule, not the server's

Browsers enforce the **same-origin policy**: JavaScript loaded from one **origin** (scheme + host + port) may not read
responses from another origin. `https://app.example.com` calling `https://api.example.com` is cross-origin.

**CORS** (Cross-Origin Resource Sharing) is how the API opts in. The browser sends an `Origin` header; the server
answers with `Access-Control-Allow-Origin: https://app.example.com`, and only then does the browser let the script
read the response. For requests that are not "simple" (for example `PUT`/`DELETE`, a custom header such as
`Authorization`, or `Content-Type: application/json`), the browser first sends a **preflight**:

```text
OPTIONS /api/orders
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: authorization, content-type

204  Access-Control-Allow-Origin: https://app.example.com
     Access-Control-Allow-Methods: GET, POST, PUT
     Access-Control-Allow-Headers: authorization, content-type
     Access-Control-Max-Age: 600
```

Two facts interviewers check. CORS protects **users' browsers**, not your server: `curl` and server-to-server calls
ignore it entirely, so it is not access control. And `Access-Control-Allow-Origin: *` cannot be combined with
credentials (cookies); for those you must echo a specific allowed origin.

## Lab (~10 min)

A tiny server and client using only the JDK (`com.sun.net.httpserver` and `java.net.http`). Save as `HttpLab.java`,
run with `java HttpLab.java`.

```java
import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpServer;
import java.io.IOException;
import java.net.InetSocketAddress;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.time.Duration;

public class HttpLab {
    static volatile String product = "{\"id\":\"p1\",\"price\":499}";

    public static void main(String[] args) throws Exception {
        HttpServer server = HttpServer.create(new InetSocketAddress("127.0.0.1", 0), 0);
        server.createContext("/products/p1", HttpLab::handleProduct);
        server.createContext("/products", HttpLab::handleCreate);
        server.start();
        String base = "http://127.0.0.1:" + server.getAddress().getPort();
        HttpClient client = HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(2)).build();
        try {
            HttpResponse<String> first = send(client, HttpRequest.newBuilder(URI.create(base + "/products/p1")));
            String etag = first.headers().firstValue("ETag").orElseThrow();
            print("GET", first);
            print("GET If-None-Match", send(client, HttpRequest.newBuilder(URI.create(base + "/products/p1"))
                    .header("If-None-Match", etag)));
            product = "{\"id\":\"p1\",\"price\":449}";          // the resource changes
            print("GET If-None-Match", send(client, HttpRequest.newBuilder(URI.create(base + "/products/p1"))
                    .header("If-None-Match", etag)));
            print("POST json", send(client, HttpRequest.newBuilder(URI.create(base + "/products"))
                    .header("Content-Type", "application/json")
                    .POST(HttpRequest.BodyPublishers.ofString("{\"name\":\"lamp\"}"))));
            print("POST text", send(client, HttpRequest.newBuilder(URI.create(base + "/products"))
                    .header("Content-Type", "text/plain")
                    .POST(HttpRequest.BodyPublishers.ofString("lamp"))));
            print("GET missing", send(client, HttpRequest.newBuilder(URI.create(base + "/products/p1/nope"))));
        } finally {
            server.stop(0);
        }
    }

    static HttpResponse<String> send(HttpClient client, HttpRequest.Builder request) throws Exception {
        return client.send(request.timeout(Duration.ofSeconds(5)).build(), HttpResponse.BodyHandlers.ofString());
    }

    static void print(String label, HttpResponse<String> r) {
        System.out.printf("%-18s -> %d  ETag=%s  Location=%s  body=%s%n", label, r.statusCode(),
                r.headers().firstValue("ETag").orElse("-"), r.headers().firstValue("Location").orElse("-"), r.body());
    }

    static void handleProduct(HttpExchange ex) throws IOException {
        try (ex) {
            if (!ex.getRequestURI().getPath().equals("/products/p1")) {
                ex.sendResponseHeaders(404, -1);                           // -1 = no body
                return;
            }
            String body = product;
            String etag = "\"" + Integer.toHexString(body.hashCode()) + "\"";
            ex.getResponseHeaders().set("ETag", etag);
            ex.getResponseHeaders().set("Cache-Control", "no-cache");     // may store, must revalidate
            if (etag.equals(ex.getRequestHeaders().getFirst("If-None-Match"))) {
                ex.sendResponseHeaders(304, -1);
                return;
            }
            byte[] bytes = body.getBytes(StandardCharsets.UTF_8);
            ex.getResponseHeaders().set("Content-Type", "application/json");
            ex.sendResponseHeaders(200, bytes.length);
            ex.getResponseBody().write(bytes);
        }
    }

    static void handleCreate(HttpExchange ex) throws IOException {
        try (ex) {
            String type = ex.getRequestHeaders().getFirst("Content-Type");
            if (type == null || !type.startsWith("application/json")) {
                ex.sendResponseHeaders(415, -1);                           // Unsupported Media Type
                return;
            }
            ex.getResponseHeaders().set("Location", "/products/p2");
            ex.sendResponseHeaders(201, -1);
        }
    }
}
```

**Observe:** `200` with an ETag; `304` with an empty body for the conditional `GET`; `200` with a *new* ETag after the
price changes; `201` with a `Location`; `415` for the wrong `Content-Type`; `404` for an unknown path.

**Then, with real servers:** run `curl -v https://example.com -o NUL` (`-o /dev/null` on Linux/macOS). The `*` lines
show the TLS handshake, the negotiated TLS version and the certificate's subject, issuer and expiry; the `>` and `<`
lines are the request and response headers.

## Gotchas

- **Errors returned as 200.** Clients, retries, caches and monitoring all key on the status code. Return the right 4xx
  or 5xx with an error body.
- **Retrying non-idempotent requests.** A timed-out `POST` may have succeeded. Retry only idempotent methods
  automatically, or make `POST` safe to retry with an idempotency key.
- **`no-cache` read as "don't cache".** It means "revalidate first". Use `no-store` for responses that must never be
  stored, and `private` for per-user data that a CDN must not keep.
- **401 and 403 swapped.** 401 = not authenticated (send credentials), 403 = authenticated but forbidden (do not
  retry with the same identity).
- **Disabling TLS verification** to fix `PKIX path building failed` turns HTTPS into unauthenticated encryption,
  open to man-in-the-middle attacks. Add the missing CA to a truststore instead.
- **Treating CORS as security.** It only stops browsers from reading responses. Authenticate and authorise on the
  server regardless.

## In interviews

Asked as "Difference between PUT and POST?", "What does idempotent mean, and which methods are?", "401 vs 403?",
"502 vs 504?", "How does HTTP caching work?", "What happens in a TLS handshake?", "What is CORS and why does my
browser call fail when Postman works?", and the classic "What happens when you type a URL into the browser?". Bank:
[POST vs PUT in REST APIs](#/q/http-post-vs-put), [Web services (REST/SOAP) fundamentals](#/q/web-services-fundamentals),
[Design an Idempotent API](#/q/design-idempotent-api), [OAuth and JWT tokens](#/q/oauth-and-jwt) and
[TCP vs UDP](#/q/tcp-vs-udp) (often the lead-in to HTTP/3).

A strong answer shape, in four layers (example: "Explain HTTPS"):

1. **What:** HTTP over TLS, giving confidentiality, integrity and server authentication.
2. **How inside:** the handshake exchanges key shares and the server's certificate; the client verifies the chain to
   a trusted root and the hostname; both derive symmetric session keys; ephemeral keys give forward secrecy; TLS 1.3
   takes one round trip.
3. **Where used:** everywhere public; often terminated at the load balancer; mTLS between internal services.
4. **What goes wrong:** expired certificates (a classic outage), missing intermediate certificates, `PKIX` errors from
   an untrusted corporate CA, and the temptation to disable verification.

**Follow-up: "Is PUT always idempotent and POST never?"** By contract `PUT` must be idempotent and `POST` is not
required to be. Your implementation can break the `PUT` contract (for example a `PUT` that appends), and you can make
a `POST` idempotent with an idempotency key. The method states the promise; the server has to keep it.

## Explain it in 2 minutes

Prompt: *"What happens, at the HTTP level, when a browser loads `https://shop.example.com/products/p1`?"*

- DNS gives an IP; a TCP connection (or QUIC for HTTP/3) opens to port 443, often reused via keep-alive.
- TLS handshake: key shares, certificate chain verified against trusted roots and the hostname, session keys derived.
- `GET` request with `Host`, `Accept`, cookies, maybe `If-None-Match` from an earlier visit.
- The server answers `200` with `Content-Type`, `Cache-Control` and an `ETag`, or `304` if the cached copy is still
  valid; errors use 4xx (client's fault) or 5xx (server's fault).
- Cross-origin script calls go through CORS; cookies carry the session with `HttpOnly`, `Secure`, `SameSite`.
- Methods carry promises: `GET` safe, `PUT`/`DELETE` idempotent, `POST` neither, which decides what may be retried.

## Check yourself

1. A second `DELETE /orders/7` returns 404 after the first returned 204. Is `DELETE` still idempotent?
2. What is the difference between `Cache-Control: no-cache` and `no-store`?
3. Your service is healthy but users see 504 from the load balancer. What does that tell you?
4. Why can't a TLS client simply trust any certificate that contains the right domain name?
5. A React app on `localhost:5173` gets a CORS error calling your API on `localhost:8080`, but `curl` works. Why,
   and where is the fix?

### Answers

1. Yes. Idempotency is about server state: after one call or two, order 7 is gone. The response may differ.
2. `no-cache` allows storing but requires revalidation (for example with `If-None-Match`) before every reuse;
   `no-store` forbids storing the response at all.
3. The load balancer gave up waiting for your service: a slow endpoint, a timeout shorter than your processing time,
   or the service is stuck (threads or connections exhausted). 502 would instead suggest a bad or dropped response.
4. Anyone can create a certificate with any name. Trust comes from the CA signature chain ending in a root the client
   already trusts, plus the server proving it holds the matching private key.
5. Different ports make different origins, and the browser enforces the same-origin policy; `curl` does not. The fix
   is on the API: return the right `Access-Control-Allow-*` headers for that origin (and handle the `OPTIONS`
   preflight).
