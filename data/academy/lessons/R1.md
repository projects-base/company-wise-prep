## Where we are

This is not a lesson to study start to finish. It is a page to skim once, then come back to and search (Ctrl+F)
whenever a term in an interview question, a job description or another lesson stops you.

## How to use this page

- **First pass (about 30 minutes):** read the "Plain meaning" column only. Mark every term you could not explain out
  loud in one sentence.
- **Before an interview:** re-read the marked terms and the "Why it matters" column. That column is the part
  interviewers actually probe: not "what is X" but "when would you use X and what does it cost".
- **When a term is shallow for you:** follow the Lesson column. A display code such as SPRING-BOOT-7 means the 7th
  lesson of the SPRING-BOOT track; "—" means the Academy does not have a dedicated lesson for it yet.
- **Say it, don't just read it.** A term you can define but not give an example for is not yet yours.

Terms are grouped by area. Within each table, related terms sit next to each other so you can compare them.

## Java and the JVM

| Term | Plain meaning | Why it matters / example | Lesson |
|---|---|---|---|
| JVM (Java Virtual Machine) | The program that loads and runs compiled Java code on a real machine. | It is why the same `.class` files run on Linux, Windows and macOS. | JAVA-FUND-1 |
| JRE (Java Runtime Environment) | The JVM plus the standard class library, enough to run Java programs. | Since Java 11 there is no separate JRE download from Oracle; you ship a JDK or a trimmed runtime made with `jlink`. | JAVA-FUND-1 |
| JDK (Java Development Kit) | The JRE plus developer tools such as the compiler `javac`, `jar` and `jcmd`. | You need the JDK to build; a production image only needs a runtime. | JAVA-FUND-1 |
| Bytecode | The compact, platform-independent instruction set that `javac` writes into `.class` files. | The JVM interprets or compiles it; `javap -c` shows it when you want to see what your code really does. | JAVA-JVM-1 |
| Interpreter | The part of the JVM that executes bytecode one instruction at a time. | It starts instantly but runs slowly, which is why hot code is handed to the JIT. | JAVA-JVM-1 |
| JIT (just-in-time) compiler | The part of the JVM that compiles frequently run bytecode into native machine code while the program runs. | Explains JVM "warm-up": a service is slower in its first minutes than after the hot paths are compiled. | JAVA-JVM-1 |
| Escape analysis | A JIT optimisation that checks whether an object can be seen outside the method that created it. | If it cannot escape, the JIT may avoid allocating it on the heap at all, reducing GC work. | JAVA-JVM-1 |
| Classloader | The JVM component that finds a class's bytes, loads them and turns them into a usable class. | Behind `ClassNotFoundException`, `NoClassDefFoundError` and clashes between two versions of one library. | JAVA-JVM-4 |
| Parent delegation | The rule that a classloader first asks its parent to load a class before trying itself. | Stops your code from replacing core classes such as `java.lang.String`. | JAVA-JVM-4 |
| Heap | The memory area shared by all threads where objects live. | Sized with `-Xmx`; when it is full and GC cannot free space you get `OutOfMemoryError`. | JAVA-JVM-2 |
| Stack (thread stack) | Per-thread memory holding method frames: local variables and partial results. | Deep or endless recursion fills it and throws `StackOverflowError`. | JAVA-JVM-2 |
| Metaspace | Native (off-heap) memory where the JVM stores class metadata since Java 8. | Leaks here come from classloaders that are never freed, for example repeated redeploys in an app server. | JAVA-JVM-2 |
| String pool | A JVM-managed table that keeps one shared copy of each string literal. | Why `"a" == "a"` can be true while `new String("a") == "a"` is false; always compare strings with `equals`. | JAVA-JVM-2 |
| Garbage collection (GC) | The JVM automatically finding objects no longer reachable and reclaiming their memory. | You don't free memory by hand, but you still pay in CPU and pauses. | JAVA-JVM-5 |
| GC generations (young / old) | Splitting the heap so new objects are collected often and long-lived objects rarely. | Based on the observation that most objects die young, so young collections are cheap. | JAVA-JVM-5 |
| Stop-the-world pause | A moment when the GC halts all application threads to do part of its work. | Long pauses show up as p99 latency spikes; low-pause collectors such as ZGC aim to keep them very short. | JAVA-JVM-5 |
| Memory leak (in Java) | Objects that are no longer needed but are still referenced, so GC cannot reclaim them. | Classic causes: an ever-growing static map or cache, unremoved listeners, `ThreadLocal` in pooled threads. | JAVA-JVM-7 |
| Autoboxing | The automatic conversion between a primitive (`int`) and its wrapper object (`Integer`). | Hidden allocations in hot loops, and a `NullPointerException` when unboxing a null `Integer`. | DSA-CPLX-2 |
| Immutability | An object whose state cannot change after it is constructed. | Immutable objects are thread-safe without locks and safe to use as map keys. | JAVA-FUND-3 |
| equals / hashCode contract | Objects that are equal must return the same hash code. | Break it and a `HashMap` or `HashSet` "loses" your objects. | JAVA-FUND-3 |
| Record | A Java class form (`record Point(int x, int y)`) for immutable data carriers with generated constructor, accessors, `equals`, `hashCode` and `toString`. | Ideal for DTOs and value objects; final in Java since 16. | JAVA-JVM-3 |
| Sealed class / interface | A type that lists exactly which classes may extend or implement it. | Lets `switch` pattern matching know every case, so the compiler can check you covered them all. | JAVA-JVM-3 |
| Generics | Type parameters such as `List<Order>` that let the compiler check types for you. | Catches type mistakes at compile time instead of `ClassCastException` at runtime. | JAVA-FUND-5 |
| Type erasure | The compiler removing generic type arguments after checking them, so at runtime a `List<String>` is just a `List`. | Why you cannot write `new T()` or overload `m(List<String>)` with `m(List<Integer>)`. | JAVA-FUND-5 |
| Checked exception | An exception the compiler forces you to catch or declare, such as `IOException`. | Use for recoverable conditions the caller should handle; many modern APIs prefer unchecked. | JAVA-FUND-4 |
| Unchecked exception | A subclass of `RuntimeException` or `Error` that the compiler does not force you to handle. | Signals programming errors or failures callers usually cannot fix locally; note Spring rolls back on these by default. | JAVA-FUND-4 |
| try-with-resources | A `try (...)` form that closes anything `AutoCloseable` automatically, even on exceptions. | Prevents leaked connections, streams and files. | JAVA-FUND-4 |
| Lambda / functional interface | A lambda is a short inline function; a functional interface is an interface with exactly one abstract method that a lambda can implement. | `Comparator`, `Runnable`, `Function`: the building blocks of Streams. | JAVA-FUND-7 |
| Stream | A pipeline of operations (`filter`, `map`, `collect`) over a sequence of elements, evaluated lazily. | Readable data transformations; not always faster than a loop. | JAVA-FUND-7 |
| Platform thread | A Java thread backed one-to-one by an operating-system thread. | Costly to create and to keep blocked, which is why thread pools exist. | JAVA-CONC-1 |
| Virtual thread | A lightweight thread managed by the JVM (final in Java 21) that is mounted on an OS thread only while it runs. | Lets you write simple blocking code and still handle very many concurrent requests. | JAVA-CONC-6 |
| Race condition | A bug where the result depends on the unpredictable timing of threads. | Classic example: two threads doing `count++` and losing updates. | JAVA-CONC-1 |
| Happens-before | The Java Memory Model rule that guarantees one action's effects are visible to another. | Without a happens-before edge, another thread may never see your write. | JAVA-JVM-6 |
| volatile | A field modifier that makes every read see the latest write and prevents certain reorderings. | Fixes visibility (a stop flag), but does not make `count++` atomic. | JAVA-JVM-6 |
| synchronized | A keyword that lets only one thread at a time run a block for a given lock object, and also publishes its writes. | The simplest way to protect shared state; can become a bottleneck under contention. | JAVA-CONC-2 |
| Deadlock | Two or more threads each waiting forever for a lock the other holds. | Prevent it by always acquiring locks in the same order or using timeouts with `tryLock`. | JAVA-CONC-2 |
| CAS (compare-and-swap) | A CPU instruction that updates a value only if it still equals what you expected, in one atomic step. | Powers `AtomicInteger` and lock-free structures; retries in a loop on conflict. | JAVA-CONC-3 |

## Spring and Spring Boot

| Term | Plain meaning | Why it matters / example | Lesson |
|---|---|---|---|
| IoC (inversion of control) | Your objects stop creating their own dependencies; a framework creates and wires them. | Makes classes easy to test with fakes and to reconfigure. | SPRING-BOOT-1 |
| DI (dependency injection) | Handing an object its dependencies from outside, usually through the constructor. | Prefer constructor injection: required dependencies are explicit and fields can be `final`. | SPRING-BOOT-1 |
| Bean | An object created and managed by the Spring container. | Anything annotated `@Component`/`@Service` or returned from a `@Bean` method. | SPRING-BOOT-2 |
| ApplicationContext | Spring's container that creates beans, wires them and manages their lifecycle. | Startup failures like "no qualifying bean" come from here. | SPRING-BOOT-2 |
| Bean scope | How many instances of a bean Spring creates: singleton (one), prototype (new each time), request, session. | Default singleton means a bean is shared by all threads, so keep it stateless. | SPRING-BOOT-2 |
| Bean lifecycle | The steps from instantiation through dependency injection, init callbacks, use and destruction. | `@PostConstruct` runs after injection, not in the constructor. | LIFECYCLE-3 |
| Profile | A named set of beans and configuration activated per environment, such as `dev` or `prod`. | `spring.profiles.active=prod` switches data sources without code changes. | SPRING-BOOT-2 |
| Proxy | A generated wrapper object that intercepts calls to your bean to add behaviour. | How `@Transactional`, `@Async` and `@Cacheable` work. | SPRING-BOOT-3 |
| Self-invocation trap | A method calling another method on `this` bypasses the proxy, so annotations on the second method do nothing. | A very common "why didn't my transaction roll back?" bug. | SPRING-BOOT-3 |
| AOP (aspect-oriented programming) | Adding cross-cutting behaviour (logging, transactions, security) around methods without editing them. | Spring AOP is proxy-based, so it only intercepts calls that go through the proxy. | SPRING-BOOT-3 |
| Auto-configuration | Spring Boot creating beans for you based on what is on the classpath and your properties. | Add the PostgreSQL driver and a `DataSource` appears; your own bean wins and backs it off. | SPRING-BOOT-4 |
| Starter | A dependency that bundles a coherent set of libraries for one job, such as `spring-boot-starter-web`. | One line in the build instead of hand-picking compatible versions. | SPRING-BOOT-4 |
| DispatcherServlet | The front controller in Spring MVC that routes each HTTP request to the right controller method. | The centre of the request pipeline: handler mapping, argument binding, message conversion. | SPRING-BOOT-6 |
| @Transactional propagation | The rule for what happens when a transactional method calls another, such as `REQUIRED` (join) or `REQUIRES_NEW` (suspend and start a new one). | `REQUIRES_NEW` is how you commit an audit row even if the outer work rolls back. | SPRING-BOOT-7 |
| @Transactional isolation | The database isolation level requested for that transaction. | Defaults to the database's own level; raise it only for a specific anomaly you need to prevent. | SPRING-BOOT-7 |
| Persistence context | The first-level cache of entities that JPA tracks inside one transaction or session. | Changes to managed entities are flushed automatically ("dirty checking") without calling `save`. | SPRING-BOOT-7 |
| Lazy vs eager loading | Lazy loads related data only when first accessed; eager loads it with the parent immediately. | Lazy access outside a transaction throws `LazyInitializationException`. | SPRING-BOOT-7 |
| N+1 query problem | Loading a list with one query and then running one extra query per row for its related data. | 100 orders become 101 queries; fix with a fetch join, an entity graph or batch fetching. | DB-SQL-8 |
| Filter chain (Spring Security) | An ordered list of servlet filters each request passes through for authentication and authorisation. | Where JWT validation, CORS and CSRF handling happen before your controller runs. | SPRING-BOOT-9 |
| Actuator | A Spring Boot module that exposes health, metrics and info endpoints. | `/actuator/health` feeds Kubernetes probes; metrics feed Prometheus. | SPRING-BOOT-11 |
| Test slice | A Spring Boot test that loads only one layer, such as `@WebMvcTest` or `@DataJpaTest`. | Faster and more focused than `@SpringBootTest` loading everything. | SPRING-BOOT-8 |
| Testcontainers | A library that starts real dependencies (PostgreSQL, Kafka) in Docker for tests. | Tests run against the real database engine instead of an in-memory imitation. | SPRING-BOOT-8 |

## Web and APIs

| Term | Plain meaning | Why it matters / example | Lesson |
|---|---|---|---|
| Safe method | An HTTP method that is not meant to change server state, such as `GET` and `HEAD`. | Crawlers, caches and prefetchers may call it freely. | WEB-API-1 |
| Idempotent | Doing the operation twice has the same effect on the server as doing it once. | `PUT` and `DELETE` are idempotent, `POST` is not; idempotency makes retries safe. | WEB-API-3 |
| Idempotency key | A client-generated unique id sent with a request so the server can detect and ignore duplicates. | Stops a retried "pay" request from charging twice. | WEB-API-3 |
| Status code families | 1xx informational, 2xx success, 3xx redirect, 4xx client error, 5xx server error. | 4xx means "fix your request, don't retry blindly"; 429 and some 5xx (502/503/504) may be retried. | WEB-API-1 |
| REST | An architectural style where you expose resources at URLs and act on them with standard HTTP methods. | Most public and internal JSON APIs; nouns in URLs, verbs as HTTP methods. | WEB-API-3 |
| HATEOAS | A REST constraint where responses include links telling the client what it can do next. | Rarely fully used in practice; knowing it shows you know what "fully RESTful" means. | WEB-API-3 |
| Pagination: offset | Fetching pages with `LIMIT n OFFSET m`. | Simple, but slow on deep pages and can skip or repeat rows when data changes. | WEB-API-3 |
| Pagination: cursor (keyset) | Fetching the next page from a pointer to the last item seen, such as `WHERE id > :lastId`. | Stable and fast at any depth; you cannot jump to "page 57". | DB-SQL-8 |
| API versioning | Keeping old clients working while the API changes, via the URL (`/v2`), a header or a media type. | Breaking changes need a new version and a deprecation period. | WEB-API-3 |
| OpenAPI | A standard machine-readable format for describing an HTTP API's endpoints and schemas. | Generates docs, client SDKs and contract tests from one file. | — |
| Problem Details | A standard JSON error body (RFC 9457, earlier RFC 7807) with `type`, `title`, `status` and `detail`. | Consistent errors across services; Spring supports it via `ProblemDetail`. | WEB-API-3 |
| gRPC | A remote procedure call framework using HTTP/2 and Protocol Buffers for compact binary messages. | Popular for internal service-to-service calls with strict contracts and streaming. | WEB-API-6 |
| GraphQL | A query language where the client asks for exactly the fields it needs from a single endpoint. | Avoids over- and under-fetching for varied front ends; caching and N+1 resolvers are harder. | WEB-API-6 |
| WebSocket | A protocol that upgrades an HTTP connection into a long-lived two-way channel. | Chat, live scores, collaborative editing: the server can push without being asked. | WEB-API-2 |
| API gateway | A single entry point in front of services that handles routing, authentication and rate limiting. | Keeps cross-cutting concerns out of each service; can become a bottleneck if overloaded with logic. | WEB-API-5 |
| CORS | A browser mechanism where a server declares which other origins may call it from JavaScript. | A CORS error is the browser protecting users, not your server rejecting the call. | WEB-API-1 |
| CSRF | An attack that tricks a logged-in user's browser into sending an unwanted request to your site. | Matters for cookie-based sessions; stateless APIs using bearer tokens in headers are not exposed the same way. | WEB-API-4 |
| JWT (JSON Web Token) | A signed, compact token carrying claims such as user id and roles. | The server can verify it without a session lookup, but cannot easily revoke it before it expires. | SPRING-BOOT-9 |
| OAuth2 | A standard for granting an application limited access to a resource on a user's behalf, using access tokens. | It is about authorisation (what the app may do), not about who the user is. | SPRING-BOOT-10 |
| OIDC (OpenID Connect) | An identity layer on top of OAuth2 that adds an ID token describing who logged in. | "Sign in with Google" is OIDC. | SPRING-BOOT-10 |
| Rate limiting | Capping how many requests a client may make in a time window. | Protects capacity and fairness; returns `429 Too Many Requests`; token bucket is a common algorithm. | SYS-DES-4 |

## Databases

| Term | Plain meaning | Why it matters / example | Lesson |
|---|---|---|---|
| ACID | Atomicity, Consistency, Isolation, Durability: the guarantees of a database transaction. | A money transfer either fully happens or not at all, and survives a crash once committed. | DB-SQL-7 |
| Isolation levels | How much concurrent transactions can see each other's work: Read Uncommitted, Read Committed, Repeatable Read, Serializable. | Higher isolation prevents more anomalies but costs throughput or causes more retries. | DB-SQL-7 |
| Dirty / non-repeatable / phantom read | Reading uncommitted data / a row changing between two reads / new rows appearing in a repeated query. | The anomalies that each isolation level is defined to prevent. | DB-SQL-7 |
| MVCC (multi-version concurrency control) | Keeping several versions of a row so readers see a consistent snapshot without blocking writers. | Why reads and writes rarely block each other in PostgreSQL; old versions need cleanup (VACUUM). | DB-SQL-7 |
| Optimistic locking | Detecting conflicting updates at write time with a version column, and failing the loser. | JPA `@Version`; good when conflicts are rare. | DB-SQL-7 |
| Pessimistic locking | Locking rows when you read them so nobody else can change them until you finish. | `SELECT ... FOR UPDATE`; good when conflicts are frequent, risks waiting and deadlocks. | DB-SQL-7 |
| Deadlock (database) | Two transactions each waiting for a row lock the other holds; the database aborts one. | Your code should catch the error and retry the whole transaction. | DB-SQL-7 |
| Index | An extra data structure that lets the database find rows without scanning the whole table. | Speeds reads, slows writes and uses storage; index for your actual queries. | DB-SQL-6 |
| B-tree index | The default balanced-tree index that supports equality and range lookups in sorted order. | Handles `=`, `<`, `BETWEEN`, `ORDER BY` and prefix `LIKE 'abc%'`. | DB-SQL-6 |
| Composite index | One index over several columns in a fixed order. | An index on `(customer_id, created_at)` helps queries filtering on `customer_id` first, not on `created_at` alone. | DB-SQL-6 |
| Covering index | An index containing every column a query needs, so the table itself is never read. | Turns a lookup plus table fetch into an index-only scan. | DB-SQL-6 |
| Query plan (EXPLAIN) | The database's chosen strategy for running a query: which indexes, joins and order. | `EXPLAIN ANALYZE` shows a sequential scan where you expected an index. | DB-SQL-6 |
| Normalization | Organising tables so each fact is stored once, removing duplication. | Prevents update anomalies; costs more joins. | DB-SQL-3 |
| Denormalization | Deliberately duplicating data to make reads faster or simpler. | A stored `order_total` avoids summing lines on every read, but must be kept in sync. | DB-SQL-3 |
| Connection pool | A set of open database connections that requests borrow and return instead of opening new ones. | HikariCP in Spring Boot; too small causes waits, too large overloads the database. | DB-SQL-5 |
| Replication | Copying data from one database server to others. | Gives read scale and failover. | DB-SQL-10 |
| Synchronous vs asynchronous replication | Sync waits for the replica to confirm before commit; async commits first and copies later. | Sync is safer but slower; async is faster but can lose recent writes on failover and serve stale reads. | DB-SQL-10 |
| Read replica | A copy of the database that serves read queries. | Offloads reads from the primary; reads may lag behind writes ("replication lag"). | DB-SQL-10 |
| Partitioning | Splitting one large table into smaller pieces, usually inside one database server. | Monthly partitions make dropping old data instant and help queries that filter by date. | DB-SQL-10 |
| Sharding | Splitting data across several database servers, each holding a subset by a shard key. | Scales writes and storage; cross-shard queries and transactions become hard. | DB-SQL-10 |
| Consistent hashing | A way of mapping keys to nodes so adding or removing a node moves only a small share of keys. | Used by distributed caches and some databases to rebalance without reshuffling everything. | SYS-DES-1 |
| NoSQL types | Families of non-relational databases: key-value, document, wide-column and graph (search engines are often grouped alongside). | Pick by access pattern: Redis for key lookups, MongoDB for documents, Cassandra for huge write-heavy tables. | DB-SQL-11 |
| CAP theorem | When a network partition happens, a distributed system must choose between consistency and availability. | The choice only bites during a partition; it does not mean "pick two of three" all the time. | SYS-DES-3 |
| PACELC | Extends CAP: if Partitioned choose Availability or Consistency, Else choose Latency or Consistency. | Captures the everyday trade-off when there is no failure. | SYS-DES-3 |
| BASE | Basically Available, Soft state, Eventually consistent: the looser guarantee model of many NoSQL systems. | The contrast to ACID; you accept temporary inconsistency for availability and scale. | SYS-DES-3 |
| OLTP vs OLAP | OLTP serves many small transactional reads and writes; OLAP runs large analytical queries over lots of data. | Don't run heavy reports on the OLTP primary; feed a warehouse instead. | DIST-SYS-9 |

## Distributed systems

| Term | Plain meaning | Why it matters / example | Lesson |
|---|---|---|---|
| Latency | How long one operation takes. | Measured per request, usually in milliseconds. | SYS-DES-1 |
| Throughput | How many operations a system completes per unit of time. | Requests per second; you can raise throughput and still have bad latency. | SYS-DES-1 |
| Percentile (p50, p99) | The value below which that percentage of measurements fall; p99 means 99% of requests were faster. | Averages hide pain; the p99 is what your unluckiest users feel. | DIST-SYS-7 |
| SLI (service level indicator) | A measured number describing service health, such as the share of successful requests. | What you actually graph. | DIST-SYS-7 |
| SLO (service level objective) | An internal target for an SLI, such as 99.9% of requests succeed over 30 days. | Drives alerting and prioritisation. | DIST-SYS-7 |
| SLA (service level agreement) | A contract with customers that promises a level of service, often with penalties if missed. | Usually looser than the SLO so you have a safety margin. | DIST-SYS-7 |
| Error budget | The amount of failure an SLO allows, such as 0.1% of requests. | When it is spent, teams slow feature releases and focus on reliability. | DIST-SYS-7 |
| Vertical scaling | Making one machine bigger: more CPU, memory or faster disk. | Simple, but has a ceiling and keeps a single point of failure. | SYS-DES-1 |
| Horizontal scaling | Adding more machines and spreading the load across them. | Needs stateless services or partitioned data. | SYS-DES-1 |
| Stateless service | A service that keeps no client session data in its own memory between requests. | Any instance can serve any request, so you can add or kill instances freely. | SYS-DES-1 |
| Load balancer | A component that spreads incoming requests across several servers. | Also removes unhealthy servers from rotation using health checks. | SYS-DES-1 |
| L4 vs L7 load balancer | L4 routes by IP address and port (TCP/UDP); L7 understands HTTP and can route by path, header or cookie. | L7 enables `/api/*` to one service and `/static/*` to another, at more processing cost. | SYS-DES-1 |
| Cache | A fast store holding copies of data so you avoid slower recomputation or lookups. | Redis in front of a database; the hard part is keeping it fresh. | DIST-SYS-1 |
| Cache-aside | The application checks the cache, and on a miss reads the database and fills the cache. | The most common caching pattern; you invalidate on writes. | DIST-SYS-1 |
| Cache hit ratio | The share of reads served from the cache rather than the backing store. | A low ratio means the cache is costing memory without saving much. | DIST-SYS-1 |
| TTL (time to live) | How long a cached item or record is kept before it expires. | Bounds how stale data can get. | DIST-SYS-1 |
| Eviction policy | The rule for what to remove when a cache is full, such as LRU (least recently used) or LFU (least frequently used). | Redis `maxmemory-policy` decides what gets dropped under pressure. | DIST-SYS-1 |
| CDN (content delivery network) | A network of servers around the world that caches content close to users. | Images, scripts and video load from a nearby edge instead of your origin. | SYS-DES-1 |
| Message queue | A buffer where producers put messages and a consumer takes each message off once processed. | RabbitMQ, SQS; smooths spikes and decouples services. | SYS-DES-1 |
| Log (event log / stream) | An append-only, ordered record of events that consumers read at their own position and that is retained. | Kafka; many consumers can read the same events, and replay is possible. | DIST-SYS-2 |
| Partition (Kafka) | An ordered slice of a topic; ordering is guaranteed only within one partition. | Messages with the same key go to the same partition, so per-key order is kept. | DIST-SYS-2 |
| Consumer group | A set of consumers that share a topic's partitions, each partition read by one member. | Add consumers to scale, up to the number of partitions. | DIST-SYS-2 |
| Offset | A message's position in a partition; consumers commit offsets to record progress. | Commit after processing, or a crash loses messages; commit before and you may skip them. | DIST-SYS-2 |
| At-most-once delivery | Each message is delivered zero or one times; failures can lose it. | Acceptable for metrics or telemetry where loss is tolerable. | DIST-SYS-2 |
| At-least-once delivery | Each message is delivered one or more times; failures cause redelivery. | The common default; consumers must handle duplicates. | DIST-SYS-2 |
| Exactly-once processing | Each message's effect is applied once, even if it is delivered more than once. | Achieved with idempotent consumers or transactional processing inside one system, not by magic delivery. | DIST-SYS-2 |
| Idempotent consumer | A consumer that records processed message ids so a redelivered message has no extra effect. | The practical way to get exactly-once effects on top of at-least-once delivery. | DIST-SYS-3 |
| Dead-letter queue (DLQ) | A separate queue for messages that keep failing processing. | One poison message stops blocking the rest, and you can inspect and replay it. | DIST-SYS-2 |
| Backpressure | A slow consumer signalling or forcing a fast producer to slow down. | Bounded queues that block or reject are a simple form; without it, memory fills up. | JAVA-CONC-7 |
| Timeout | A limit on how long a caller waits for a response before giving up. | Every network call needs one, or one slow dependency ties up all your threads. | DIST-SYS-3 |
| Retry with exponential backoff and jitter | Retrying a failed call after growing delays with randomness added. | Jitter stops many clients from retrying in sync; only retry transient failures. | DIST-SYS-3 |
| Circuit breaker | A wrapper that stops calling a failing dependency for a while after too many errors, then tests it again. | Fails fast instead of piling up waiting threads; Resilience4j in Java. | DIST-SYS-3 |
| Bulkhead | Isolating resources (thread pools, connections) per dependency so one failure cannot exhaust everything. | A slow payment provider can't starve the threads serving product pages. | DIST-SYS-3 |
| Saga | A long business process split into local transactions, each with a compensating action if a later step fails. | Replaces distributed transactions across microservices: book, pay, and if payment fails, cancel the booking. | DIST-SYS-3 |
| Transactional outbox | Writing an event into an outbox table in the same database transaction as the business change, then publishing it separately. | Avoids the "saved to DB but failed to publish" gap (the dual-write problem). | DIST-SYS-3 |
| CDC (change data capture) | Streaming every committed change from a database's log to other systems. | Debezium reading PostgreSQL's log into Kafka; often used to publish the outbox. | DIST-SYS-3 |
| Eventual consistency | Replicas may disagree for a while, but converge to the same value if writes stop. | A "like" count may lag for a moment; fine for many features, not for account balances. | SYS-DES-3 |
| Strong consistency | Every read sees the most recent committed write. | Simpler to reason about, but needs coordination that costs latency and availability. | SYS-DES-3 |
| Quorum | A majority (or configured minimum) of replicas that must agree for a read or write to succeed. | With N replicas, choosing read and write quorums where R + W > N means reads overlap the latest write. | SYS-DES-3 |
| Leader election | Nodes choosing one of themselves to coordinate, and choosing again if it fails. | Only the leader runs the scheduled job or accepts writes. | SYS-DES-3 |
| Consensus (Raft, Paxos) | A protocol that lets a group of nodes agree on a value or log order despite some nodes failing. | Underpins etcd (Kubernetes' store) and Kafka's KRaft mode; needs a majority alive. | SYS-DES-3 |
| Split brain | Two parts of a cluster each believe they are in charge after a network split. | Both accept writes and data diverges; majority quorums and fencing tokens prevent it. | SYS-DES-3 |

## Security

| Term | Plain meaning | Why it matters / example | Lesson |
|---|---|---|---|
| Authentication | Proving who someone or something is. | Login, a validated JWT, a client certificate; failure is `401 Unauthorized`. | SPRING-BOOT-9 |
| Authorization | Deciding what an authenticated identity is allowed to do. | Role and ownership checks; failure is `403 Forbidden`. | SPRING-BOOT-9 |

## Check yourself

1. What is the difference between a safe method and an idempotent method? Give one example of each.
2. `volatile` fixes one concurrency problem but not another. Which is which?
3. Why does calling a `@Transactional` method from another method in the same class sometimes not start a transaction?
4. When would you choose cursor pagination over offset pagination?
5. What is the difference between partitioning and sharding?
6. Kafka gives you at-least-once delivery. How do you get exactly-once effects in your service?
7. What problem does the transactional outbox solve?
8. When is RAG a better choice than fine-tuning?

### Answers

1. A safe method does not change server state (`GET`). An idempotent method may change state, but repeating it has the
   same effect as doing it once (`PUT`, `DELETE`). Every safe method is idempotent; not every idempotent method is safe.
2. It fixes visibility (other threads see the latest write) and some reordering. It does not make compound actions such
   as `count++` atomic; use `AtomicInteger` or a lock for that.
3. Spring adds transactions through a proxy. A call on `this` goes straight to the object and never passes through the
   proxy, so the annotation is ignored.
4. For large or frequently changing data sets, infinite scroll and feeds: cursor pages stay fast at any depth and don't
   skip or repeat rows when items are inserted. Offset is fine for small tables where users jump to page numbers.
5. Partitioning usually splits a table into pieces inside one database server; sharding spreads data across several
   servers by a shard key, which scales writes but makes cross-shard queries and transactions hard.
6. Make the consumer idempotent: record each processed message id (or use a natural unique key) in the same
   transaction as the effect, and skip messages already recorded.
7. The dual-write problem: saving to the database and publishing an event are two separate operations, so one can
   succeed while the other fails. Writing the event to an outbox table in the same transaction and publishing it
   afterwards guarantees the event is eventually sent if, and only if, the change committed.
8. When the knowledge changes often, is private, or must be cited: RAG supplies current documents at request time
   without retraining. Fine-tuning suits teaching a style, format or narrow skill.
