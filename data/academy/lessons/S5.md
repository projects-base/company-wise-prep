## Where we are

In S4 you saw EJB 2 provide transactions and security by **intercepting calls through a container proxy**, and you saw the price: classes tied to the container, five artefacts per service, and nothing testable in `main`. You also rebuilt the good idea with a JDK `Proxy`. This lesson covers the counter-movement of 2002–2006: **Spring** (plain objects plus dependency injection plus AOP) and **Hibernate** (objects mapped to tables).

## The problem

Developers wanted three things together:

1. **Plain classes**: business logic that runs in `main` and in a unit test, with no framework interfaces.
2. **The enterprise services anyway**: declarative transactions and security, without hand-written `commit`/`rollback`.
3. **Less JDBC boilerplate**: turning `ResultSet` rows into objects by hand, in every query, was tedious and error-prone.

The answer came from outside the standards body.

## The story

In 2002 Rod Johnson published *Expert One-on-One J2EE Design and Development*, which criticised EJB-heavy designs and included the code of a lightweight framework. That code grew into the **Spring Framework**, and **Spring 1.0 shipped in March 2004**. At around the same time Gavin King started **Hibernate** (2001), an object-relational mapper. Both spread quickly, and as S4 described, **EJB 3.0 and JPA (2006)** adopted their ideas into the standard.

## POJO: the starting point

A **POJO** ("plain old Java object", a term coined by Martin Fowler and colleagues) is a class that doesn't extend or implement anything from a framework.

```java
public class OrderService {
    private OrderRepository orderRepository;
    public void setOrderRepository(OrderRepository repo) { this.orderRepository = repo; }
    public void placeOrder(String item) { orderRepository.save(item); }
}
```

You can create it with `new` and test it with a fake repository. Everything else Spring offers is built around keeping your code this plain.

## Inversion of control and dependency injection

Who creates `OrderRepository` and hands it to `OrderService`?

- **Without DI**, the class does it itself: `this.orderRepository = new JdbcOrderRepository();`. That hard-codes the choice, so a test can't substitute a fake.
- **With DI**, something outside the class creates both objects and *passes* the repository in, through a constructor or setter.

**Inversion of control (IoC)** means the framework, not your code, controls object creation and wiring. A **container** (Spring calls it the *application context*) reads a description of which objects exist and how they connect, creates them, and injects dependencies. The objects it manages are called **beans**. Martin Fowler's January 2004 article *Inversion of Control Containers and the Dependency Injection pattern* gave the technique the name **dependency injection**.

Early Spring used XML for the description:

```xml
<beans>
    <bean id="orderRepository" class="shopkart.JdbcOrderRepository"/>
    <bean id="orderService" class="shopkart.OrderService">
        <property name="orderRepository" ref="orderRepository"/>   <!-- calls setOrderRepository(...) -->
    </bean>
</beans>
```

Rule: **classes declare what they need, and the container decides what they get.** Swapping the real repository for a fake becomes a configuration change, not a code change.

## AOP: services wrapped around plain objects

**Aspect-oriented programming (AOP)** puts cross-cutting behaviour, such as transactions, security or logging, in one place and applies it to many methods. Spring implements it the way you did in S4: the container hands callers a **proxy** that wraps the real bean.

```text
caller ──► [ proxy ] ──► BEGIN tx ──► real OrderService.placeOrder() ──► COMMIT/ROLLBACK
```

You mark which methods need a transaction (originally in XML, later with `@Transactional`), and the proxy does the rest. The business code never sees a `Connection`.

The catch: **the proxy only intercepts calls that come through it.** If `placeTwo()` calls `this.placeOrder()`, that call goes directly to the real object, so the transaction logic never runs. This is the "self-invocation" trap, and you'll trigger it in the lab.

## Templates: removing JDBC boilerplate

Spring also shipped **`JdbcTemplate`**, which owns the open-connection, try, catch and close routine and turns `SQLException` into unchecked exceptions:

```java
List<String> items = jdbcTemplate.query(
        "SELECT item FROM orders WHERE user_id = ?",
        (rs, rowNum) -> rs.getString("item"),
        userId);
```

You supply the SQL and how to map one row. The template handles the rest.

## ORM: Hibernate

An **ORM (object-relational mapper)** maps classes to tables and objects to rows, so you work with `Order` objects and the ORM writes the SQL. Hibernate added:

- **Mapping**: `Order` maps to table `orders`, and `order.getItems()` maps to the join on `order_items`.
- **Lazy loading**: related objects are fetched only when you first touch them.
- **Dirty checking**: change a loaded object inside a transaction, and Hibernate issues the `UPDATE` at commit.

Lazy loading creates the best-known ORM performance bug, **N+1 queries**:

```text
List<Order> orders = session.createQuery("from Order").list();   -- 1 query: SELECT * FROM orders
for (Order o : orders) o.getItems().size();                       -- N queries, one per order:
                                                                  -- SELECT * FROM order_items WHERE order_id=?
```

Loading 100 orders costs 101 queries. The fix is to fetch what you need in one query (a **fetch join**: `select o from Order o join fetch o.items`). Track D6 covers this with a real database.

## The new pain: XML and WAR files

Spring made code plain and testable, but configuration moved into large XML files: hundreds of `<bean>` entries, typed as strings, with class names the compiler never checked. Wiring a web app also meant `web.xml` plus Spring's own XML, transaction-manager XML and Hibernate mapping files.

Deployment was still a **WAR** (web archive) dropped into an externally installed Tomcat or app server, which meant a server to install, version and configure separately from the app. S6 addresses the XML. S7 addresses the external server.

## Lab (~10 min)

**Build** a mini Spring with only the JDK: an XML container that does IoC and DI, plus an AOP proxy. Then **break** it with self-invocation. Put both files in one folder and run `java MiniSpring.java` from that folder.

`beans.xml`:

```xml
<beans>
    <bean id="orderRepository" class="MiniSpring$InMemoryOrderRepository"/>
    <bean id="orderService" class="MiniSpring$OrderServiceImpl">
        <property name="orderRepository" ref="orderRepository"/>
    </bean>
</beans>
```

`MiniSpring.java`:

```java
import java.io.File;
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import javax.xml.parsers.DocumentBuilderFactory;
import org.w3c.dom.Element;
import org.w3c.dom.NodeList;

public class MiniSpring {

    // ---------- Our own marker annotation (Spring has a real one) ----------
    @Retention(RetentionPolicy.RUNTIME) @Target(ElementType.METHOD)
    @interface Transactional {}

    // ---------- Plain old Java objects: no framework base classes ----------
    public interface OrderRepository { void save(String order); List<String> findAll(); }

    public static class InMemoryOrderRepository implements OrderRepository {
        private final List<String> rows = new ArrayList<>();
        public void save(String order) { rows.add(order); }
        public List<String> findAll() { return rows; }
    }

    public interface OrderService { void placeOrder(String item); void placeTwo(String a, String b); }

    public static class OrderServiceImpl implements OrderService {
        private OrderRepository orderRepository;
        public void setOrderRepository(OrderRepository repo) { this.orderRepository = repo; } // setter injection

        @Transactional
        public void placeOrder(String item) { orderRepository.save(item); }

        public void placeTwo(String a, String b) {   // NOT annotated; calls placeOrder on "this"
            placeOrder(a);
            placeOrder(b);
        }
    }

    // ---------- The container ----------
    private final Map<String, Object> beans = new LinkedHashMap<>();

    MiniSpring(String xmlFile) throws Exception {
        var doc = DocumentBuilderFactory.newInstance().newDocumentBuilder().parse(new File(xmlFile));
        NodeList defs = doc.getElementsByTagName("bean");
        // Pass 1: create every bean (IoC: the container calls 'new', not your code)
        for (int i = 0; i < defs.getLength(); i++) {
            Element def = (Element) defs.item(i);
            Object bean = Class.forName(def.getAttribute("class")).getDeclaredConstructor().newInstance();
            beans.put(def.getAttribute("id"), bean);
        }
        // Pass 2: wire dependencies (DI: call setX(ref) for each <property>)
        for (int i = 0; i < defs.getLength(); i++) {
            Element def = (Element) defs.item(i);
            Object bean = beans.get(def.getAttribute("id"));
            NodeList props = def.getElementsByTagName("property");
            for (int p = 0; p < props.getLength(); p++) {
                Element prop = (Element) props.item(p);
                Object dependency = beans.get(prop.getAttribute("ref"));
                String setter = "set" + Character.toUpperCase(prop.getAttribute("name").charAt(0))
                        + prop.getAttribute("name").substring(1);
                for (Method m : bean.getClass().getMethods()) {
                    if (m.getName().equals(setter) && m.getParameterCount() == 1) m.invoke(bean, dependency);
                }
            }
        }
        // Pass 3: AOP: wrap beans that have @Transactional methods in a proxy
        for (var entry : beans.entrySet()) {
            Object target = entry.getValue();
            boolean needsTx = false;
            for (Method m : target.getClass().getMethods()) needsTx |= m.isAnnotationPresent(Transactional.class);
            if (needsTx) entry.setValue(txProxy(target));
        }
    }

    private static Object txProxy(Object target) {
        return Proxy.newProxyInstance(target.getClass().getClassLoader(), target.getClass().getInterfaces(),
                (proxy, method, args) -> {
                    Method impl = target.getClass().getMethod(method.getName(), method.getParameterTypes());
                    boolean tx = impl.isAnnotationPresent(Transactional.class);
                    if (tx) System.out.println("  [tx] BEGIN " + method.getName());
                    try {
                        Object result = method.invoke(target, args);
                        if (tx) System.out.println("  [tx] COMMIT " + method.getName());
                        return result;
                    } catch (InvocationTargetException e) {
                        if (tx) System.out.println("  [tx] ROLLBACK " + method.getName());
                        throw e.getCause();
                    }
                });
    }

    @SuppressWarnings("unchecked")
    <T> T getBean(String id) { return (T) beans.get(id); }

    public static void main(String[] args) throws Exception {
        MiniSpring context = new MiniSpring("beans.xml");
        OrderService service = context.getBean("orderService");

        System.out.println("Call placeOrder through the proxy:");
        service.placeOrder("book");

        System.out.println("Call placeTwo, which calls placeOrder internally:");
        service.placeTwo("pen", "ink");

        OrderRepository repo = context.getBean("orderRepository");
        System.out.println("Saved: " + repo.findAll());
        System.out.println("Bean class handed out: " + service.getClass().getSimpleName());
    }
}
```

**What you should observe:**

```text
Call placeOrder through the proxy:
  [tx] BEGIN placeOrder
  [tx] COMMIT placeOrder
Call placeTwo, which calls placeOrder internally:
Saved: [book, pen, ink]
Bean class handed out: $Proxy3        (the number may differ)
```

- `placeOrder` called from outside gets a transaction.
- **`placeTwo` calls `placeOrder` twice and gets no transaction at all.** The inner calls go through `this`, the real object, not through the proxy. Real Spring behaves the same way.
- Change `beans.xml` to point at another repository class without touching `OrderServiceImpl`. That is DI paying off.

**Fix ideas to try:** annotate `placeTwo` itself, or move `placeOrder` into a separate bean so the call crosses a proxy. Then mistype a class name in `beans.xml`. It compiles fine and fails at start-up, which is the XML pain S6 removes.

## Gotchas

- **Self-invocation skips the proxy.** `this.method()` inside a bean bypasses `@Transactional`, `@Async`, `@Cacheable` and similar annotations. Put the annotated method on another bean, or annotate the outer method.
- **N+1 queries hide behind lazy loading.** Turn on SQL logging in development and count queries per request. Fix with fetch joins or batch fetching.
- **Lazy loading outside a transaction fails.** Touching an unloaded collection after the session is closed throws `LazyInitializationException`. Load what the view needs inside the transaction.
- **DI doesn't make a class testable by itself.** Hidden `new` calls and static lookups inside the class still block substitution. Inject everything the class depends on.
- **Field injection hides dependencies.** Prefer constructor injection: required dependencies are explicit, fields can be `final`, and tests just call the constructor.

- [Data Access Layer with Runtime-switchable Source](#/q/design-data-access-layer): program to an interface and inject the implementation.

Typical follow-ups:

- *"Why doesn't `@Transactional` work on a self-invocation?"* Spring applies it through a proxy around the bean. Only calls that enter through the proxy are intercepted, and `this.foo()` goes straight to the target. Fixes: restructure into another bean, inject the bean's own proxy (a workaround), or use AspectJ weaving.
- *"What is the N+1 problem and how do you detect and fix it?"* One query for the parents and N lazy queries for the children. Detect it with SQL logs or query counts in tests. Fix it with a fetch join, an entity graph or batch fetching.

## Explain it in 2 minutes

*"What did Spring and Hibernate change compared with EJB 2?"*

A good answer hits:

1. **POJOs**: business classes extend nothing and run in `main` and in tests.
2. **IoC/DI**: the container creates beans and injects dependencies, so implementations can be swapped through configuration.
3. **AOP via proxies**: transactions and security are wrapped around plain beans. The self-invocation trap follows from this.
4. **Templates** (`JdbcTemplate`) remove resource-handling boilerplate.
5. **Hibernate ORM**: object mapping, lazy loading, dirty checking, with the N+1 risk. It became the basis of JPA (2006).
6. New pain: **XML configuration sprawl** and **WAR deployment** to an external server.

## Check yourself

1. What is the difference between IoC and DI?
2. Why is constructor injection preferred over field injection?
3. In the lab, why didn't `placeTwo` produce `[tx]` lines?
4. A page lists 50 orders and their items and runs 51 queries. What is happening and what is the fix?

### Answers

1. IoC is the general principle that the framework controls object creation and flow. DI is the specific technique of passing dependencies into an object instead of the object creating or looking them up.
2. Dependencies are explicit and can be `final`, the object is never half-built, and tests can construct it directly without the container or reflection.
3. `placeTwo` was not annotated, and its inner `placeOrder` calls went through `this`, the real object, so the transaction proxy never saw them.
4. N+1: one query for orders, then one lazy query per order for its items. Fix it with a fetch join (or batch fetching) that loads the items in the same query.
