## Where we are

You have joins and anti-joins (Q1), `GROUP BY`, `HAVING`, `CASE` and CTEs (Q2), and window functions
with "rank in a CTE, filter outside" (Q3). Live SQL rounds reuse about nine problem shapes. This
lesson works through each one on the betting schema, the same way you should in the interview:
clarify, build in CTE steps, test the edge cases, then name the index.

## The problem

The interviewer says: "Give me each punter's two biggest bets." Ten seconds later: "What if two bets
tie?" Then: "This table has 500 million rows. Is it fast?"

A strong answer has four parts, and they are the same for every pattern below:

```text
1. Clarify    ties? NULLs? duplicates? what if there is no answer? what output columns?
2. Build      one CTE per step; run (or mentally run) each step on a tiny sample
3. Edge cases ties, NULLs, duplicates, empty groups, divide-by-zero
4. Speed      which index lets the database avoid reading/sorting the whole table
```

## One new idea first: an index, in one paragraph

An **index** is a separate structure, kept sorted on one or more columns, that points back to the
table's rows. With an index on `bets (user_id, stake DESC)`, the database can jump straight to Ben's
bets, already sorted biggest-first, and read only the first two. Without it, it reads all 500 million
rows and sorts them. Think of a phone book sorted by (surname, first name): it's fast for "Smiths,
by first name" and useless for "everyone called John". The analogy breaks down because a database
also has to keep every index up to date on each insert, so indexes slow writes down. **Column order
matters: equality columns first, then the sort or range column.** In PostgreSQL, a foreign key does
**not** get an index automatically, so join columns such as `bets.user_id` often need one. Q5 covers
how indexes work and how to prove one is used (`EXPLAIN`). Here you only pick the columns.

## Pattern 1: Nth highest

**Ask:** "What's the second-highest stake?" Clarify:

- Distinct values or rows? If two bets are 100.00, is the second-highest 100.00 or 50.00? Usually
  distinct, as in LeetCode 176/177.
- What if there's no Nth value? LeetCode expects `NULL`, not zero rows.

**Step 1: see the distinct values.**

```sql
SELECT DISTINCT stake FROM bets ORDER BY stake DESC LIMIT 4;
```

| stake |
|---|
| 100.00 |
| 50.00 |
| 40.00 |
| 30.00 |

**Step 2: skip N−1 of them, take one.** `OFFSET k` skips k rows.

```sql
SELECT DISTINCT stake
FROM bets
ORDER BY stake DESC
LIMIT 1 OFFSET 1;
```

| stake |
|---|
| 50.00 |

**Edge case: no Nth value.** The query above returns *zero rows* when N is too large. Wrap it as a
scalar subquery, which turns "no row" into `NULL`:

```sql
SELECT (SELECT DISTINCT stake FROM bets ORDER BY stake DESC LIMIT 1 OFFSET 19) AS twentieth_highest;
```

| twentieth_highest |
|---|
| NULL |

**The window version** returns the *bets* that hold the Nth distinct value, which is often the real
question. Use `DENSE_RANK`, because ties must share a rank and leave no gaps:

```sql
WITH ranked AS (
  SELECT id, user_id, stake,
         DENSE_RANK() OVER (ORDER BY stake DESC) AS stake_rank
  FROM bets
)
SELECT id, user_id, stake
FROM ranked
WHERE stake_rank = 2
ORDER BY id;
```

| id | user_id | stake |
|---|---|---|
| 7 | 2 | 50.00 |
| 8 | 2 | 50.00 |
| 12 | 3 | 50.00 |
| 13 | 3 | 50.00 |

With `RANK` there is no rank 2 at all here (two bets share rank 1, the next is 3). With
`ROW_NUMBER`, rank 2 is the *other* 100.00 bet. That is the classic wrong answer. For N = 2 only,
`SELECT MAX(stake) FROM bets WHERE stake < (SELECT MAX(stake) FROM bets)` also works and also returns
50.00.

**NULLs:** if the column is nullable, add `WHERE stake IS NOT NULL`. PostgreSQL sorts NULLs *first*
under `DESC`, so a NULL would become "the highest".

**Index:**

```sql
CREATE INDEX idx_bets_stake_desc ON bets (stake DESC);
```

The database walks the index from the top and stops after N distinct values, without a full sort.
(PostgreSQL can also scan a plain ascending index backwards.)

## Pattern 2: Top-N per group

**Ask:** "Each punter's two biggest bets." Clarify ties: exactly two rows per punter (`ROW_NUMBER`),
or every bet whose stake is among the top two values (`DENSE_RANK`)?

**Step 1: rank inside each group. Step 2: filter outside.**

```sql
WITH ranked AS (
  SELECT user_id, id, stake,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY stake DESC, id) AS rn
  FROM bets
)
SELECT user_id, id, stake, rn
FROM ranked
WHERE rn <= 2
ORDER BY user_id, rn;
```

| user_id | id | stake | rn |
|---|---|---|---|
| 1 | 5 | 30.00 | 1 |
| 1 | 4 | 25.00 | 2 |
| 2 | 7 | 50.00 | 1 |
| 2 | 8 | 50.00 | 2 |
| 3 | 14 | 100.00 | 1 |
| 3 | 12 | 50.00 | 2 |
| 4 | 16 | 10.00 | 1 |
| 4 | 17 | 10.00 | 2 |
| 5 | 19 | 100.00 | 1 |
| 5 | 20 | 15.00 | 2 |

**Edge case: ties.** Chloe has two 50.00 bets. `ROW_NUMBER` keeps one (bet 12, thanks to the `id`
tie-breaker) and drops bet 13. With `DENSE_RANK` you get the "top two stake values" reading:

```sql
WITH ranked AS (
  SELECT user_id, id, stake,
         DENSE_RANK() OVER (PARTITION BY user_id ORDER BY stake DESC) AS dr
  FROM bets
)
SELECT user_id, id, stake, dr
FROM ranked
WHERE dr <= 2
ORDER BY user_id, dr, id;
```

| user_id | id | stake | dr |
|---|---|---|---|
| 1 | 5 | 30.00 | 1 |
| 1 | 4 | 25.00 | 2 |
| 2 | 7 | 50.00 | 1 |
| 2 | 8 | 50.00 | 1 |
| 2 | 10 | 40.00 | 2 |
| 3 | 14 | 100.00 | 1 |
| 3 | 12 | 50.00 | 2 |
| 3 | 13 | 50.00 | 2 |
| 4 | 16 | 10.00 | 1 |
| 4 | 17 | 10.00 | 1 |
| 4 | 18 | 5.00 | 2 |
| 5 | 19 | 100.00 | 1 |
| 5 | 20 | 15.00 | 2 |

LeetCode 185 (Department Top Three Salaries) wants this `DENSE_RANK` reading.

**A group-of-groups variant:** "the biggest punter in each country". Aggregate first, then rank:

```sql
WITH turnover AS (
  SELECT u.country, u.name, SUM(b.stake) AS turnover
  FROM bets b JOIN users u ON u.id = b.user_id
  GROUP BY u.country, u.id, u.name
),
ranked AS (
  SELECT country, name, turnover,
         RANK() OVER (PARTITION BY country ORDER BY turnover DESC) AS rnk
  FROM turnover
)
SELECT country, name, turnover
FROM ranked
WHERE rnk = 1
ORDER BY country;
```

| country | name | turnover |
|---|---|---|
| AU | Ben | 185.00 |
| GB | Asha | 110.00 |
| IE | Chloe | 220.00 |

**Index:** partition columns first, then the order column.

```sql
CREATE INDEX idx_bets_user_stake ON bets (user_id, stake DESC);
```

For "top N for **one** user" this is ideal: jump to the user, read N entries, stop. For all users at
once, the planner may still scan everything. At large scale with few groups, PostgreSQL users write a
`LATERAL` join that does one small index lookup per group. Mention it, but you rarely need to write
it live.

## Pattern 3: Duplicates

**Ask:** "Find duplicate bets." Clarify **what makes two rows the same**. It's never the `id`. Here:
same user, selection, stake and `placed_at`, such as a double-click that placed the bet twice. Also
ask: list the groups, list every row, or delete the extras? Which copy survives?

**Find the duplicate groups:** `GROUP BY` the identifying columns, `HAVING COUNT(*) > 1`.

```sql
SELECT user_id, selection_id, stake, placed_at, COUNT(*) AS copies
FROM bets
GROUP BY user_id, selection_id, stake, placed_at
HAVING COUNT(*) > 1;
```

| user_id | selection_id | stake | placed_at | copies |
|---|---|---|---|---|
| 4 | 2 | 10.00 | 2026-08-20 19:30:00 | 2 |

**List every duplicate row**, and number the copies so you can choose which one to keep:

```sql
WITH counted AS (
  SELECT id, user_id, selection_id, stake, placed_at,
         COUNT(*)     OVER (PARTITION BY user_id, selection_id, stake, placed_at)          AS copies,
         ROW_NUMBER() OVER (PARTITION BY user_id, selection_id, stake, placed_at ORDER BY id) AS copy_no
  FROM bets
)
SELECT id, user_id, selection_id, stake, copy_no
FROM counted
WHERE copies > 1
ORDER BY id;
```

| id | user_id | selection_id | stake | copy_no |
|---|---|---|---|---|
| 16 | 4 | 2 | 10.00 | 1 |
| 17 | 4 | 2 | 10.00 | 2 |

**Delete the extras, keeping the lowest id** (LeetCode 196). Try it inside `BEGIN; … ROLLBACK;` so
your seed survives:

```sql
DELETE FROM bets
WHERE id IN (
  SELECT id FROM (
    SELECT id,
           ROW_NUMBER() OVER (PARTITION BY user_id, selection_id, stake, placed_at ORDER BY id) AS copy_no
    FROM bets
  ) d
  WHERE copy_no > 1
);
```

It deletes one row (bet 17).

**Edge cases.**

- **NULL in an identifying column:** `GROUP BY` and `PARTITION BY` put NULLs together in one group,
  so NULLs count as duplicates of each other. That differs from `=`, where `NULL = NULL` is not true.
- **Near-duplicates:** real double-clicks are often a second apart. Exact grouping misses them, and a
  self-join with a time window catches them:

```sql
SELECT b1.id AS first_id, b2.id AS dup_id, b1.user_id, b1.selection_id
FROM bets b1
JOIN bets b2
  ON  b2.user_id      = b1.user_id
  AND b2.selection_id = b1.selection_id
  AND b2.stake        = b1.stake
  AND b2.id           > b1.id
  AND b2.placed_at   >= b1.placed_at
  AND b2.placed_at   <= b1.placed_at + INTERVAL '5' SECOND;
```

| first_id | dup_id | user_id | selection_id |
|---|---|---|---|
| 16 | 17 | 4 | 2 |

**Index, and the real fix.** An index on the identifying columns makes the grouping and the self-join
cheap. The production answer, though, is to **prevent** duplicates with a unique constraint, usually
on an idempotency key that the client sends with each request. A unique index on the business
columns fails while duplicates exist:

```sql
CREATE UNIQUE INDEX uq_bets_same_bet ON bets (user_id, selection_id, stake, placed_at);
```

```text
ERROR: could not create unique index "uq_bets_same_bet"
  Detail: Key (user_id, selection_id, stake, placed_at)=(4, 2, 10.00, 2026-08-20 19:30:00) is duplicated.
```

So you clean up first, then add the constraint. Say that in the interview.

## Pattern 4: Consecutive rows ("gaps and islands")

**Ask:** "Each punter's longest losing streak." An **island** is a run of consecutive rows that share
a property. A **gap** is the break between runs. Clarify: consecutive in what order (`placed_at`, with
`id` breaking ties)? Do `OPEN` and `VOID` bets break a streak or get skipped? Here we look only at
WON/LOST bets.

**The trick:** number the rows twice, once over all of the user's bets and once within each status.
Inside a run of the same status, both numbers go up by 1 each step, so their **difference stays
constant**. That difference labels the island.

```sql
WITH settled AS (
  SELECT user_id, id, placed_at, status,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY placed_at, id)         AS rn_all,
         ROW_NUMBER() OVER (PARTITION BY user_id, status ORDER BY placed_at, id) AS rn_status
  FROM bets
  WHERE status IN ('WON', 'LOST')
)
SELECT user_id, id, status, rn_all, rn_status, rn_all - rn_status AS grp
FROM settled
WHERE user_id IN (1, 2)
ORDER BY user_id, rn_all;
```

| user_id | id | status | rn_all | rn_status | grp |
|---|---|---|---|---|---|
| 1 | 1 | WON | 1 | 1 | 0 |
| 1 | 2 | WON | 2 | 2 | 0 |
| 1 | 4 | LOST | 3 | 1 | 2 |
| 1 | 3 | LOST | 4 | 2 | 2 |
| 1 | 5 | WON | 5 | 3 | 2 |
| 2 | 7 | LOST | 1 | 1 | 0 |
| 2 | 8 | LOST | 2 | 2 | 0 |
| 2 | 9 | LOST | 3 | 3 | 0 |
| 2 | 10 | WON | 4 | 1 | 3 |

Asha's WON bet 5 also has `grp = 2`, the same as her LOST run. That's fine: an island is identified by
**(user, status, grp)**, never by `grp` alone.

**Step 2: group each island; step 3: keep the losing ones.**

```sql
WITH settled AS (
  SELECT user_id, id, placed_at, status,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY placed_at, id)         AS rn_all,
         ROW_NUMBER() OVER (PARTITION BY user_id, status ORDER BY placed_at, id) AS rn_status
  FROM bets
  WHERE status IN ('WON', 'LOST')
),
streaks AS (
  SELECT user_id, status, rn_all - rn_status AS grp,
         COUNT(*) AS streak_len, MIN(placed_at) AS streak_start, MAX(placed_at) AS streak_end
  FROM settled
  GROUP BY user_id, status, rn_all - rn_status
)
SELECT user_id, streak_len, streak_start, streak_end
FROM streaks
WHERE status = 'LOST'
ORDER BY streak_len DESC, user_id;
```

| user_id | streak_len | streak_start | streak_end |
|---|---|---|---|
| 2 | 3 | 2026-08-19 14:00:00 | 2026-09-04 11:00:00 |
| 1 | 2 | 2026-09-05 18:00:00 | 2026-09-10 09:00:00 |
| 4 | 2 | 2026-08-20 19:30:00 | 2026-08-20 19:30:00 |

**Step 4: the longest per punter**, keeping punters with no losing streak (0) through a LEFT JOIN:

```sql
WITH settled AS (
  SELECT user_id, placed_at, status,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY placed_at, id)         AS rn_all,
         ROW_NUMBER() OVER (PARTITION BY user_id, status ORDER BY placed_at, id) AS rn_status
  FROM bets
  WHERE status IN ('WON', 'LOST')
),
streaks AS (
  SELECT user_id, status, COUNT(*) AS streak_len
  FROM settled
  GROUP BY user_id, status, rn_all - rn_status
)
SELECT u.name, COALESCE(MAX(s.streak_len), 0) AS longest_losing_streak
FROM users u
LEFT JOIN streaks s ON s.user_id = u.id AND s.status = 'LOST'
WHERE EXISTS (SELECT 1 FROM bets b WHERE b.user_id = u.id)
GROUP BY u.id, u.name
ORDER BY longest_losing_streak DESC, u.name;
```

| name | longest_losing_streak |
|---|---|
| Ben | 3 |
| Asha | 2 |
| Dev | 2 |
| Chloe | 0 |
| Ella | 0 |

**Alternative: flag-and-sum.** Mark a row 1 when it *starts* a new island (its status differs from the
previous row's, found with `LAG`). A running `SUM` of those flags then numbers the islands. This
version generalises to any "new island when…" rule, such as "a gap of more than 30 minutes".

```sql
WITH settled AS (
  SELECT user_id, id, placed_at, status,
         CASE WHEN status = LAG(status) OVER (PARTITION BY user_id ORDER BY placed_at, id)
              THEN 0 ELSE 1 END AS new_island
  FROM bets
  WHERE status IN ('WON', 'LOST')
),
numbered AS (
  SELECT user_id, id, status, new_island,
         SUM(new_island) OVER (PARTITION BY user_id ORDER BY placed_at, id) AS island_id
  FROM settled
)
SELECT user_id, id, status, new_island, island_id
FROM numbered
WHERE user_id = 2
ORDER BY island_id, id;
```

| user_id | id | status | new_island | island_id |
|---|---|---|---|---|
| 2 | 7 | LOST | 1 | 1 |
| 2 | 8 | LOST | 0 | 1 |
| 2 | 9 | LOST | 0 | 1 |
| 2 | 10 | WON | 1 | 2 |

On the first row `LAG` is NULL, so the comparison is unknown, the CASE falls to `ELSE 1`, and the
first row correctly starts island 1.

**Consecutive days** (LeetCode 180, 601) is the same trick with dates. `day − row_number` is constant
across a run of consecutive days. `date - integer` works in PostgreSQL and H2. Use `DISTINCT` first,
so that two bets on one day don't break the numbering:

```sql
WITH active_days AS (
  SELECT DISTINCT user_id, CAST(placed_at AS DATE) AS bet_day
  FROM bets
),
numbered AS (
  SELECT user_id, bet_day,
         bet_day - CAST(ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY bet_day) AS INTEGER) AS grp
  FROM active_days
)
SELECT user_id, MIN(bet_day) AS first_day, MAX(bet_day) AS last_day, COUNT(*) AS days_in_row
FROM numbered
GROUP BY user_id, grp
HAVING COUNT(*) >= 2
ORDER BY user_id;
```

| user_id | first_day | last_day | days_in_row |
|---|---|---|---|
| 1 | 2026-08-18 | 2026-08-19 | 2 |
| 2 | 2026-08-19 | 2026-08-20 | 2 |

The `CAST(… AS INTEGER)` is needed because `ROW_NUMBER` returns a `bigint`, and PostgreSQL has no
`date - bigint` operator.

**Index:**

```sql
CREATE INDEX idx_bets_user_placed ON bets (user_id, placed_at);
```

Both window functions partition by user and order by time, so this index supplies rows in exactly
that order. In PostgreSQL you could add `INCLUDE (status)` so the index alone answers the query.

## Pattern 5: Running totals

**Ask:** "Cumulative turnover by day, and the first day it passed 300." Clarify: calendar days in
which time zone? (Here, the stored timestamp.) Should days with no bets appear? (See Pattern 6 for
filling gaps.)

**Step 1: aggregate to one row per day. Step 2: run a window sum over the days.** Summing per day
*first* also removes the `RANGE`-ties problem from Q3, because each day is now unique.

```sql
WITH daily AS (
  SELECT CAST(placed_at AS DATE) AS bet_day, SUM(stake) AS day_turnover
  FROM bets
  GROUP BY CAST(placed_at AS DATE)
)
SELECT bet_day, day_turnover,
       SUM(day_turnover) OVER (ORDER BY bet_day) AS cumulative_turnover
FROM daily
WHERE bet_day <= DATE '2026-09-07'
ORDER BY bet_day;
```

| bet_day | day_turnover | cumulative_turnover |
|---|---|---|
| 2026-08-18 | 20.00 | 20.00 |
| 2026-08-19 | 60.00 | 80.00 |
| 2026-08-20 | 120.00 | 200.00 |
| 2026-09-04 | 20.00 | 220.00 |
| 2026-09-05 | 25.00 | 245.00 |
| 2026-09-06 | 40.00 | 285.00 |
| 2026-09-07 | 55.00 | 340.00 |

**Careful:** the `WHERE` in the outer query runs *before* the window. Filtering the days in the outer
query is fine here, because we cut off only the end. If you filtered out *early* days, the running
total would restart from the first remaining day. To show a later range with the true cumulative
total, compute the running sum in a CTE and filter outside it.

**Step 3: the first crossing.** Running sum in a CTE, filter, take the earliest:

```sql
WITH daily AS (
  SELECT CAST(placed_at AS DATE) AS bet_day, SUM(stake) AS day_turnover
  FROM bets
  GROUP BY CAST(placed_at AS DATE)
),
running AS (
  SELECT bet_day, SUM(day_turnover) OVER (ORDER BY bet_day) AS cumulative_turnover
  FROM daily
)
SELECT bet_day, cumulative_turnover
FROM running
WHERE cumulative_turnover >= 300
ORDER BY bet_day
LIMIT 1;
```

| bet_day | cumulative_turnover |
|---|---|
| 2026-09-07 | 340.00 |

**A shortcut, PostgreSQL only.** A window over an aggregate, `SUM(SUM(stake)) OVER (…)`, does steps 1
and 2 in one SELECT:

```sql
SELECT CAST(placed_at AS DATE) AS bet_day,
       SUM(stake) AS day_turnover,
       SUM(SUM(stake)) OVER (ORDER BY CAST(placed_at AS DATE)) AS cumulative_turnover
FROM bets
GROUP BY CAST(placed_at AS DATE)
ORDER BY bet_day
LIMIT 3;
```

| bet_day | day_turnover | cumulative_turnover |
|---|---|---|
| 2026-08-18 | 20.00 | 20.00 |
| 2026-08-19 | 60.00 | 80.00 |
| 2026-08-20 | 120.00 | 200.00 |

H2 rejected this exact query ("Column PLACED_AT must be in the GROUP BY list"). The CTE form runs on
both.

The per-user running balance (Q3) is the same pattern with `PARTITION BY user_id`.

**Index:** `wallet_transactions (user_id, created_at)` for per-user balances. For the daily rollup,
an index on `bets (placed_at)` helps only when you restrict a date range. At scale, keep a
`daily_turnover` summary table that a job updates, rather than re-summing raw bets.

## Pattern 6: Month-over-month change

**Ask:** "Monthly turnover and the change from the previous month, in money and %." Clarify: calendar
months? What if a month has no bets (show 0, or skip)? What if last month was 0 (division by zero)?

**Step 1: bucket by month.** `DATE_TRUNC('month', ts)` rounds a timestamp down to the first instant of
its month. It works in PostgreSQL and H2.

```sql
SELECT DATE_TRUNC('month', placed_at) AS month_start, SUM(stake) AS turnover
FROM bets
GROUP BY DATE_TRUNC('month', placed_at)
ORDER BY month_start;
```

| month_start | turnover |
|---|---|
| 2026-08-01 00:00:00 | 200.00 |
| 2026-09-01 00:00:00 | 385.00 |
| 2026-10-01 00:00:00 | 70.00 |

**Step 2: `LAG` over the months.** `NULLIF(x, 0)` returns NULL when `x` is 0, so dividing by it gives
NULL instead of a division-by-zero error.

```sql
WITH monthly AS (
  SELECT DATE_TRUNC('month', placed_at) AS month_start, SUM(stake) AS turnover
  FROM bets
  GROUP BY DATE_TRUNC('month', placed_at)
)
SELECT month_start, turnover,
       LAG(turnover) OVER (ORDER BY month_start) AS prev_turnover,
       turnover - LAG(turnover) OVER (ORDER BY month_start) AS change,
       ROUND(100 * (turnover - LAG(turnover) OVER (ORDER BY month_start))
             / NULLIF(LAG(turnover) OVER (ORDER BY month_start), 0), 1) AS pct_change
FROM monthly
ORDER BY month_start;
```

| month_start | turnover | prev_turnover | change | pct_change |
|---|---|---|---|---|
| 2026-08-01 00:00:00 | 200.00 | NULL | NULL | NULL |
| 2026-09-01 00:00:00 | 385.00 | 200.00 | 185.00 | 92.5 |
| 2026-10-01 00:00:00 | 70.00 | 385.00 | -315.00 | -81.8 |

October is a partial month (the seed stops on 4 October). A good answer points out that comparing a
partial month with a full one is misleading.

**Edge case: missing months.** `LAG` compares with the previous *row*, not the previous *month*. If
July had no bets, there is no July row, and August would be compared with June. Fix it by building
the list of months and LEFT JOINing the totals. A `VALUES` list works on both engines:

```sql
WITH months (month_start) AS (
  VALUES (TIMESTAMP '2026-07-01 00:00:00'), (TIMESTAMP '2026-08-01 00:00:00'),
         (TIMESTAMP '2026-09-01 00:00:00'), (TIMESTAMP '2026-10-01 00:00:00')
),
monthly AS (
  SELECT DATE_TRUNC('month', placed_at) AS month_start, SUM(stake) AS turnover
  FROM bets
  GROUP BY DATE_TRUNC('month', placed_at)
)
SELECT m.month_start, COALESCE(t.turnover, 0) AS turnover,
       COALESCE(t.turnover, 0) - LAG(COALESCE(t.turnover, 0)) OVER (ORDER BY m.month_start) AS change
FROM months m
LEFT JOIN monthly t ON t.month_start = m.month_start
ORDER BY m.month_start;
```

| month_start | turnover | change |
|---|---|---|
| 2026-07-01 00:00:00 | 0 | NULL |
| 2026-08-01 00:00:00 | 200.00 | 200.00 |
| 2026-09-01 00:00:00 | 385.00 | 185.00 |
| 2026-10-01 00:00:00 | 70.00 | -315.00 |

In PostgreSQL you'd generate the months instead of listing them:

```sql
SELECT month_start
FROM generate_series(TIMESTAMP '2026-07-01 00:00:00', TIMESTAMP '2026-10-01 00:00:00',
                     INTERVAL '1 month') AS g(month_start);
```

| month_start |
|---|
| 2026-07-01 00:00:00 |
| 2026-08-01 00:00:00 |
| 2026-09-01 00:00:00 |
| 2026-10-01 00:00:00 |

`generate_series` is PostgreSQL-only. H2 rejected this call.

**Per punter:** add `user_id` to the `GROUP BY` and `PARTITION BY user_id` to each window. The
missing-month problem gets worse per punter, because most punters skip some months.

**Index:** filter months with a range such as `placed_at >= '2026-08-01' AND placed_at <
'2026-10-01'`, never with `EXTRACT(MONTH FROM placed_at) = 9`. A function wrapped around the column
stops a plain index on `bets (placed_at)` from being used. At scale this is a classic case for a
monthly rollup table.

## Pattern 7: Pivot with CASE

**Ask:** "One row per punter, one column per sport, with turnover in each cell." A **pivot** turns
values in rows into columns. Clarify: is the list of columns fixed? SQL needs to know its output
columns when the query is written, so a pivot over "whatever sports exist" needs dynamic SQL or a
pivot in the application.

**Step 1: the long form.** One row per (punter, sport):

```sql
SELECT b.user_id, sp.name AS sport, SUM(b.stake) AS turnover
FROM bets b
JOIN selections s ON s.id = b.selection_id
JOIN markets m    ON m.id = s.market_id
JOIN events e     ON e.id = m.event_id

```

**Step 2: one conditional SUM per column** (Q2's conditional aggregation):

```sql
WITH bet_sport AS (
  SELECT b.user_id, e.sport_id, b.stake
  FROM bets b
  JOIN selections s ON s.id = b.selection_id
  JOIN markets m    ON m.id = s.market_id
  JOIN events e     ON e.id = m.event_id
)
SELECT u.name,
       SUM(CASE WHEN bs.sport_id = 1 THEN bs.stake ELSE 0 END) AS football,
       SUM(CASE WHEN bs.sport_id = 2 THEN bs.stake ELSE 0 END) AS tennis,
       SUM(CASE WHEN bs.sport_id = 3 THEN bs.stake ELSE 0 END) AS racing,
       SUM(bs.stake)                                           AS total
FROM bet_sport bs
JOIN users u ON u.id = bs.user_id
GROUP BY u.id, u.name
ORDER BY u.id;
```

| name | football | tennis | racing | total |
|---|---|---|---|---|

**Edge cases.** `ELSE 0` gives 0 for "no bets". Leave out the `ELSE` and you get NULL, which some
reports prefer, since "no activity" isn't the same as "staked 0". Sanity-check that the columns add up
to `total`: here they do. If a fourth sport gets bets, it appears in `total` but in no column. Say so.
PostgreSQL (and H2) also accept the standard `FILTER` clause, `SUM(stake) FILTER (WHERE sport_id =
1)`, which reads more cleanly and returns NULL for no rows. The `CASE` form runs everywhere,
including MySQL. LeetCode 1179 (Reformat Department Table) is this pattern.

**Index:** a pivot reads every matching bet, so the indexes that matter are the ones for the join:
`bets (selection_id)`, `selections (market_id)` and `markets (event_id)`. PostgreSQL doesn't create
these foreign-key indexes for you.

## Pattern 8: Median

**Ask:** "Median stake." The **median** is the middle value once the values are sorted. With an even
count, it is the average of the two middle values. It resists outliers: one 10,000 bet barely moves
it, but it drags the mean up a lot. Clarify: an even count → average the middle two (the usual
reading)? Include open bets? What about NULLs?

**The built-in (PostgreSQL, also H2):**

```sql
SELECT PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY stake) AS median_stake
FROM bets;
```

| median_stake |
|---|
| 22.5 |

`PERCENTILE_CONT` interpolates between the two middle values. `PERCENTILE_DISC` returns an actual
value from the data instead. PostgreSQL returns a `double precision` here (shown as 22.5). H2
returned `22.500`. MySQL has neither function, which is why interviewers often ask for the manual
version.

**The manual version: number the rows, keep the middle one or two.** For n rows, the middle positions
are `(n + 1) / 2` and `(n + 2) / 2` in integer division. When n is odd these are the same position.
When n is even they are the two middle ones.

```sql
WITH ordered AS (
  SELECT stake,
         ROW_NUMBER() OVER (ORDER BY stake) AS rn,
         COUNT(*)     OVER ()               AS n
  FROM bets
)
SELECT ROUND(AVG(stake), 2) AS median_stake
FROM ordered
WHERE rn IN ((n + 1) / 2, (n + 2) / 2);
```

| median_stake |
|---|
| 22.50 |

There are 20 bets, so positions 10 and 11 hold 20.00 and 25.00, and their average is 22.50. The mean
is 32.75, pulled up by the two 100.00 bets. **Per group:** add `PARTITION BY user_id` to both windows
and `GROUP BY user_id` outside:

```sql
WITH ordered AS (
  SELECT user_id, stake,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY stake, id) AS rn,
         COUNT(*)     OVER (PARTITION BY user_id)                    AS n
  FROM bets
)
SELECT user_id, ROUND(AVG(stake), 2) AS median_stake
FROM ordered
WHERE rn IN ((n + 1) / 2, (n + 2) / 2)
GROUP BY user_id
ORDER BY user_id;
```

| user_id | median_stake |
|---|---|
| 1 | 17.50 |
| 2 | 40.00 |
| 3 | 50.00 |
| 4 | 10.00 |
| 5 | 57.50 |

**Edge cases.** Ties don't matter, because equal values are interchangeable. NULLs do. Filter them out
(`WHERE stake IS NOT NULL`) *before* numbering, or `n` counts rows that have no value.

**Index:** an index on `bets (stake)` gives sorted order for free. An exact median over a huge table
still has to read half of it. At scale, use approximate percentiles (sketches such as t-digest in
the metrics pipeline) or precomputed values.

## Pattern 9: Users who did X but not Y

**Ask:** "Punters who bet on Football but never on Tennis." Clarify: does a `VOID` tennis bet count as
"bet on Tennis"? Should punters with no bets at all appear? (No, they didn't do X.)

**The `EXISTS` / `NOT EXISTS` form**, the clearest and NULL-safe:

```sql
WITH bet_sport AS (
  SELECT b.user_id, e.sport_id, b.status
  FROM bets b
  JOIN selections s ON s.id = b.selection_id
  JOIN markets m    ON m.id = s.market_id
  JOIN events e     ON e.id = m.event_id
)
SELECT u.id, u.name
FROM users u
WHERE EXISTS     (SELECT 1 FROM bet_sport x WHERE x.user_id = u.id AND x.sport_id = 1)
  AND NOT EXISTS (SELECT 1 FROM bet_sport y WHERE y.user_id = u.id AND y.sport_id = 2)
ORDER BY u.id;
```

| id | name |
|---|---|
| 5 | Ella |

**The one-pass `GROUP BY … HAVING` form:** count X and Y per user with conditional aggregation, and
keep "X > 0 and Y = 0". This one shines when there are several conditions (did A and B, but not C):

```sql
WITH bet_sport AS (
  SELECT b.user_id, e.sport_id
  FROM bets b
  JOIN selections s ON s.id = b.selection_id
  JOIN markets m    ON m.id = s.market_id
  JOIN events e     ON e.id = m.event_id
)
SELECT user_id
FROM bet_sport
GROUP BY user_id
HAVING SUM(CASE WHEN sport_id = 1 THEN 1 ELSE 0 END) > 0
   AND SUM(CASE WHEN sport_id = 2 THEN 1 ELSE 0 END) = 0
ORDER BY user_id;
```

| user_id |
|---|
| 5 |

**The set form:** `EXCEPT` returns rows of the first query that are not in the second (and removes
duplicates):

```sql
WITH bet_sport AS (
  SELECT b.user_id, e.sport_id
  FROM bets b
  JOIN selections s ON s.id = b.selection_id
  JOIN markets m    ON m.id = s.market_id
  JOIN events e     ON e.id = m.event_id
)
SELECT user_id FROM bet_sport WHERE sport_id = 1
EXCEPT
SELECT user_id FROM bet_sport WHERE sport_id = 2
ORDER BY user_id;
```

| user_id |
|---|
| 5 |

**Edge case: the clarification changes the answer.** Dev's only tennis bet was voided. If voided bets
don't count, Dev qualifies too:

```sql
WITH bet_sport AS (
  SELECT b.user_id, e.sport_id, b.status
  FROM bets b
  JOIN selections s ON s.id = b.selection_id
  JOIN markets m    ON m.id = s.market_id
  JOIN events e     ON e.id = m.event_id
)
SELECT u.id, u.name
FROM users u
WHERE EXISTS     (SELECT 1 FROM bet_sport x WHERE x.user_id = u.id AND x.sport_id = 1)
  AND NOT EXISTS (SELECT 1 FROM bet_sport y WHERE y.user_id = u.id AND y.sport_id = 2
                                              AND y.status <> 'VOID')
ORDER BY u.id;
```

| id | name |
|---|---|
| 4 | Dev |
| 5 | Ella |

Avoid `user_id NOT IN (SELECT user_id …)` here (Q1, Trap 3). It's correct only while the subquery can
never return NULL.

**Index:** each `EXISTS` probe is "does this user have a bet on sport S?". `bets (user_id,
selection_id)` lets the database check one user's bets without touching the rest, and the foreign-key
indexes make the climb to `events.sport_id` cheap. In a real schema you'd often denormalise `sport_id`
onto `bets` for reporting. That is a Q8 trade-off.

## Gotchas

- **`ROW_NUMBER` vs `DENSE_RANK` is a question about ties. Ask it out loud.** For "Nth highest" the
  usual answer is `DENSE_RANK` (or `DISTINCT`). For "exactly N per group" it is `ROW_NUMBER` with a
  tie-breaker.
- **"No answer" should be NULL, not zero rows.** Wrap a `LIMIT/OFFSET` query in a scalar subquery.
- **`LAG` means the previous row, not the previous month.** Generate the full list of periods and
  LEFT JOIN, or the gaps silently compare the wrong months.
- **Filtering before a window changes the window.** `WHERE` runs first, so a running total or rank is
  computed only over the surviving rows. Rank in a CTE, filter outside.
- **NULLs sort first under `DESC` in PostgreSQL** and get grouped together by `GROUP BY`. Filter them
  or say `NULLS LAST` in Nth-highest, median and duplicate queries.
- **Functions on indexed columns block the index.** `EXTRACT(MONTH FROM placed_at) = 9` can't use an
  index on `placed_at`. A half-open range (`>= start AND < next_start`) can.

In the bank, [DB indexing, partitioning and sharding](#/q/db-indexing-partitioning-sharding) is where

**Typical follow-up:** "This runs on 500 million bets. Is it fast?" A strong answer names the index
(equality columns first, then the order column), says whether the query can stop early (top-N) or

**Another follow-up:** "What if two rows tie?" Answer by choosing between `ROW_NUMBER`, `RANK` and
`DENSE_RANK` out loud, and show the tie in the seed data.

## Explain it in 2 minutes

*"How do you approach an unfamiliar SQL question in an interview?"*

1. Clarify first: ties, NULLs, duplicates, empty results, and the exact output columns.
2. Name the pattern: Nth highest, top-N per group, duplicates, islands, running total, period-over-
   period, pivot, median, or X-not-Y.
3. Build in CTEs: aggregate to the right grain, then window, then filter outside. Check each step on a
   few rows.
4. Choose the ranking function deliberately, and add a tie-breaker for determinism.
5. Handle the edges: `NULLIF` for division, `COALESCE` for missing periods, `NOT EXISTS` over
   `NOT IN`.
6. Close with performance: the index (equality columns, then order), whether the query can stop
   early, and when to pre-aggregate.

## Check yourself

1. Why is `ROW_NUMBER() … WHERE rn = 2` the wrong answer to "second-highest distinct stake" on this
   seed?
2. In gaps and islands, why is `rn_all - rn_status` constant within a streak?
3. Monthly turnover has no row for July. What goes wrong with `LAG`, and how do you fix it?
4. For an even number of rows, which positions does `rn IN ((n + 1) / 2, (n + 2) / 2)` pick when
   n = 6?
5. Which index would you create for "each punter's three most recent bets", and why that column order?

### Answers

1. Two bets tie at 100.00, so `rn = 2` is the *other* 100.00 bet, not 50.00. Use `DISTINCT` with
   `OFFSET`, or `DENSE_RANK() = 2`.
2. Inside a run of one status, each step adds 1 to both numbers. Whenever the status changes,
   `rn_all` keeps counting but `rn_status` (for that status) doesn't, so the difference jumps to a new
   value.
3. August is compared with June (the previous *row*). Generate all months (a `VALUES` list or
   `generate_series`), LEFT JOIN the totals, and `COALESCE` the missing ones to 0.
4. Positions 3 and 4 (7/2 = 3 and 8/2 = 4 in integer division). Their average is the median.
5. `bets (user_id, placed_at DESC)`, or `(user_id, placed_at)`, which can be read backwards. Equality
   on `user_id` first narrows to one punter, then the rows are already in time order, so the database
   reads three entries and stops.

Lab solutions:

```sql
-- 1
SELECT (SELECT DISTINCT payout FROM bets WHERE payout IS NOT NULL
        ORDER BY payout DESC LIMIT 1 OFFSET 2) AS third_highest_payout;
```

```sql
-- 2
WITH ranked AS (
  SELECT user_id, id, placed_at,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY placed_at DESC, id DESC) AS rn
  FROM bets
)
SELECT user_id, id, placed_at FROM ranked WHERE rn = 1 ORDER BY user_id;
```

```sql
-- 3
WITH settled AS (
  SELECT user_id, status,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY placed_at, id)         AS rn_all,
         ROW_NUMBER() OVER (PARTITION BY user_id, status ORDER BY placed_at, id) AS rn_status
  FROM bets
  WHERE status IN ('WON', 'LOST')
),
streaks AS (
  SELECT user_id, COUNT(*) AS streak_len
  FROM settled
  WHERE status = 'WON'
  GROUP BY user_id, rn_all - rn_status
)
SELECT user_id, MAX(streak_len) AS longest_winning_streak
FROM streaks
GROUP BY user_id
ORDER BY longest_winning_streak DESC, user_id;
```

```sql
-- 4
WITH bet_sport AS (
  SELECT e.sport_id, b.status
  FROM bets b
  JOIN selections s ON s.id = b.selection_id
  JOIN markets m    ON m.id = s.market_id
  JOIN events e     ON e.id = m.event_id
)
SELECT sp.name AS sport,
       SUM(CASE WHEN bs.status = 'WON'  THEN 1 ELSE 0 END) AS won,
       SUM(CASE WHEN bs.status = 'LOST' THEN 1 ELSE 0 END) AS lost,
       SUM(CASE WHEN bs.status = 'OPEN' THEN 1 ELSE 0 END) AS open_bets,
       SUM(CASE WHEN bs.status = 'VOID' THEN 1 ELSE 0 END) AS void_bets
FROM sports sp
LEFT JOIN bet_sport bs ON bs.sport_id = sp.id
GROUP BY sp.id, sp.name
ORDER BY sp.id;
```

```sql
-- 5

FROM users u
WHERE EXISTS (SELECT 1 FROM bets b
              WHERE b.user_id = u.id
                AND b.placed_at >= TIMESTAMP '2026-08-01 00:00:00'
                AND b.placed_at <  TIMESTAMP '2026-09-01 00:00:00')

                  WHERE b.user_id = u.id
```
