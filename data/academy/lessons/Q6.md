## Where we are

Q5 made single queries fast: B-tree indexes, selectivity, and reading `EXPLAIN`. D6 showed
Spring's `@Transactional` and a table of isolation levels. This lesson is about what happens when
many transactions touch the same rows at the same moment, as they do when a goal goes in and
thousands of people bet at once. It covers what Postgres actually guarantees, how it does it
(MVCC), and how to write a bet placement that can't spend the same money twice.

## The problem

Akhil's wallet holds £10. He taps "Place bet £10" on his phone and on his laptop within the same
few milliseconds. Each request runs this code:

```text
balance = SELECT balance FROM wallets WHERE user_id = 42      -- both read 10.00
if balance >= stake:                                           -- both pass
    UPDATE wallets SET balance = 0.00 WHERE user_id = 42      -- both write 0.00
    INSERT INTO bets ...                                       -- two bets!
```

Two bets accepted, £10 paid. Every line is correct on its own. The bug is in the gap between
reading and writing. This lesson is about closing that gap.

(The shared schema keeps money movements in `wallet_transactions`. Summing that ledger on every
bet would be slow, so from here on we also keep a current balance per user in
`wallets(user_id, balance)`, updated in the same transaction as each ledger row. F8 develops this
into a full double-entry ledger.)

## ACID in one line each

A **transaction** is a group of statements that the database treats as one unit. ACID is what it
promises:

- **Atomicity:** all of the statements take effect, or none do. A crash halfway leaves nothing
  half-done.
- **Consistency:** constraints (`CHECK (balance >= 0)`, foreign keys, unique keys) hold before and
  after.
- **Isolation:** concurrent transactions don't see each other's half-finished work. *How* isolated
  is a setting, and it's the subject of most of this lesson.
- **Durability:** once `COMMIT` returns, the change survives a crash. Postgres writes it to the
  **write-ahead log (WAL)** and flushes that to disk before acknowledging.

## The five anomalies

An **anomaly** is a wrong result that can only happen because transactions overlap. Each one below
uses two transactions, T1 and T2, with time running downwards.

**Dirty read:** reading another transaction's uncommitted change.

```text
T1: UPDATE wallets SET balance = 500 ...          (not committed)
T2:                     SELECT balance → 500      ← T1 may still roll back
T1: ROLLBACK
```

**Non-repeatable read:** reading the same row twice in one transaction and getting different
values.

```text
T2: SELECT balance → 10
T1: UPDATE wallets SET balance = 0; COMMIT
T2: SELECT balance → 0                            ← same row, same transaction
```

**Phantom:** re-running a query and finding new rows that match it.

```text
T2: SELECT count(*) FROM bets WHERE user_id = 42 AND status = 'OPEN' → 3
T1: INSERT INTO bets (... user 42, 'OPEN' ...); COMMIT
T2: same SELECT → 4
```

**Lost update:** two read-modify-write cycles overlap, and one write silently overwrites the other.
That's the problem above.

**Write skew:** two transactions read the same data, each checks a rule, and each writes a
*different* row. Neither write conflicts with the other, but together they break the rule. A
betting example is a daily deposit limit of £500 with £400 already deposited today:

```text
T1: SELECT sum(amount) ... deposits today → 400;  400 + 100 ≤ 500 ✓
T2: SELECT sum(amount) ... deposits today → 400;  400 + 100 ≤ 500 ✓
T1: INSERT deposit 100; COMMIT
T2: INSERT deposit 100; COMMIT                    → 600 deposited, limit broken
```

## What each Postgres isolation level stops

D6's table gave the SQL standard's view. Postgres is stricter than the standard at two levels:

| Level in Postgres | Snapshot taken | Dirty | Non-repeatable | Phantom | Lost update | Write skew |
|---|---|---|---|---|---|---|
| Read uncommitted | (behaves exactly as read committed) | stopped | allowed | allowed | allowed* | allowed |
| **Read committed** (default) | at the start of each *statement* | stopped | allowed | allowed | allowed* | allowed |
| Repeatable read | at the first statement of the *transaction* | stopped | stopped | stopped | stopped (error) | allowed |
| Serializable | as repeatable read, plus conflict tracking | stopped | stopped | stopped | stopped (error) | stopped (error) |

What "stopped (error)" means: at repeatable read, if T2 tries to update a row that T1 changed and
committed after T2's snapshot, T2 fails with `could not serialize access due to concurrent update`
(SQLSTATE `40001`). At serializable, Postgres also tracks read/write dependencies and aborts one
transaction of any pair that could produce write skew. Either way, **your code must catch `40001`
and retry the whole transaction.**

\* The lost update at read committed only happens when the application computes the new value
itself (`SET balance = 0.00`). `UPDATE ... SET balance = balance - 10` is safe even at read
committed, as the next sections show.

**The rule:** keep the default, read committed, and close specific gaps with locks or atomic
statements. Use serializable for the few transactions where reasoning about every overlap is too
hard, and pay with retries.

## Row locks

Postgres takes a **row lock** whenever a transaction updates or deletes a row, and holds it until
`COMMIT` or `ROLLBACK`. A second transaction that tries to update the same row **waits**. Plain
`SELECT`s never wait for row locks; MVCC (below) lets them read the last committed version
instead.

There's one more read committed detail that makes atomic updates safe. When a waiting `UPDATE`
finally gets the lock, Postgres **re-checks its `WHERE` clause against the newly committed
version** of the row. So:

```sql
UPDATE wallets SET balance = balance - 10.00
WHERE user_id = 42 AND balance >= 10.00;
```

Device A updates and holds the lock. Device B waits. A commits with balance 0.00. B re-checks
`balance >= 10.00` against the new row, sees it is false, and updates **0 rows**. Your code reads
the update count: 1 means debited, 0 means insufficient funds. That's one statement, no race.

## SELECT … FOR UPDATE: lock first, then decide

Sometimes the check doesn't fit in one `WHERE` clause. It might need several rows, or Java logic.
`SELECT ... FOR UPDATE` reads the row **and** takes the row lock, so nobody else can change it
until you commit:

```sql
BEGIN;
SELECT balance FROM wallets WHERE user_id = 42 FOR UPDATE;   -- others now wait here
-- Java: check limits, odds, balance ...
UPDATE wallets SET balance = balance - 10.00 WHERE user_id = 42;
COMMIT;
```

This is **pessimistic locking**: assume a conflict is likely and block it up front. Variants worth
knowing: `FOR UPDATE NOWAIT` fails immediately instead of waiting, and `FOR UPDATE SKIP LOCKED`
skips locked rows, which is how you build a job queue in Postgres where several workers each claim
different rows.

Locking one "parent" row also fixes write skew. If every deposit first runs `SELECT ... FROM
wallets WHERE user_id = 42 FOR UPDATE`, two deposits for the same user can no longer overlap, so the
deposit-limit check sees the other's insert.

## Optimistic locking: a version column

**Optimistic locking** assumes conflicts are rare. Read without locking, and make the write
conditional on nothing having changed:

```sql
ALTER TABLE wallets ADD COLUMN version BIGINT NOT NULL DEFAULT 0;

-- read: balance = 10.00, version = 7
UPDATE wallets SET balance = 0.00, version = version + 1
WHERE user_id = 42 AND version = 7;          -- 0 rows → someone got there first: retry or reject
```

JPA's `@Version` (D6) generates exactly this. When to use which:

| | Pessimistic (`FOR UPDATE`) | Optimistic (version column) |
|---|---|---|
| Conflicts | frequent | rare |
| Time between read and write | milliseconds, inside one request | can be long (a user editing a form) |
| Cost on conflict | the other transaction waits | the loser retries all its work |
| Danger | lock waits, deadlocks | retry storms under heavy contention |

For a wallet, the single conditional `UPDATE` is simplest. For a trader editing a market's
settings in a back-office screen, optimistic wins.

## Deadlocks and lock ordering

A **deadlock** is two transactions each waiting for a lock the other holds. Neither can move.

Settlement pays a winner by moving money from the house account to the user. Meanwhile a refund
moves money the other way, locking in the opposite order:

```text
T1 (payout): UPDATE accounts ... id = HOUSE   ✓ lock HOUSE
T2 (refund): UPDATE accounts ... id = USER_42 ✓ lock USER_42
T1:          UPDATE accounts ... id = USER_42   waits for T2
T2:          UPDATE accounts ... id = HOUSE     waits for T1   → deadlock
```

Postgres runs its deadlock check once a transaction has waited on a lock for `deadlock_timeout`
(1 second by default). It aborts one transaction with SQLSTATE `40P01` and lets the other finish.

How to avoid them:

1. **Lock in a consistent order.** Always lock accounts in ascending id order, whatever the
   direction of the money. Then no cycle can form.
2. **Keep transactions short.** No HTTP calls, no waiting for a user, inside a transaction.
3. **Retry on `40P01`** (and `40001`), because ordering mistakes will still slip in somewhere.

## MVCC: how Postgres lets readers and writers not block each other

**MVCC (multi-version concurrency control)** means an `UPDATE` doesn't overwrite a row. It writes a
**new version** of the row and marks the old one as replaced. Each version (Postgres calls it a
**tuple**) carries two hidden fields:

- `xmin`: the id of the transaction that created this version,
- `xmax`: the id of the transaction that deleted or replaced it (empty if still current).

```text
UPDATE wallets SET balance = 0 WHERE user_id = 42;   -- by transaction 901

heap page:
  (user 42, balance 10.00)  xmin=850  xmax=901   ← old version, still on the page
  (user 42, balance  0.00)  xmin=901  xmax=—     ← new version
```

A **snapshot** records which transactions had committed when it was taken. A reader sees the
version whose `xmin` committed before its snapshot and whose `xmax` hadn't. A reporting query that
started before transaction 901 committed keeps seeing 10.00, consistently, without waiting for any
lock. Writers only block other writers of the same row. You can see these fields yourself with
`SELECT xmin, xmax, * FROM wallets;`.

**Analogy:** a wiki page history. Editors add new revisions, and readers who opened the page
earlier keep reading the revision they opened. Where it breaks: the wiki keeps history forever,
but Postgres must delete old versions or the table grows without limit. That's vacuum.

## Vacuum and bloat

Once no running transaction's snapshot can still see an old version, that version is **dead**.
**VACUUM** finds dead tuples and marks their space reusable. It also keeps the visibility map
(Q5's index-only scans) up to date and "freezes" old transaction ids: Postgres transaction ids are
32-bit and wrap around, so vacuum is mandatory, not optional. **Autovacuum** runs it automatically
in the background.

**Bloat** is space taken by dead tuples that haven't been reclaimed, so tables and indexes grow
larger than their live data and every scan reads more pages. Common causes:

- **A long-running transaction**, or a session stuck `idle in transaction` after a forgotten
  commit. Its old snapshot might still need old versions, so vacuum can't remove any version that
  died after that snapshot was taken, in any table of that database. Set
  `idle_in_transaction_session_timeout`.
- **Very hot rows**, such as a house account updated by every bet, create dead versions faster
  than autovacuum's default settings clean them.

Plain `VACUUM` rarely gives disk space back to the operating system; it makes the space reusable.
`VACUUM FULL` rewrites the table but locks it completely while doing so, so it's an
outage-window tool.

## Worked example: placing a bet without double-spend

Putting it together. One transaction, read committed, and the wallet row is the first thing
touched, so every bet for one user queues up on that one row lock:

```java
public boolean placeBet(Connection c, long userId, long selectionId,
                        BigDecimal stake, BigDecimal odds) throws SQLException {
    c.setAutoCommit(false);
    try {
        try (PreparedStatement debit = c.prepareStatement("""
                UPDATE wallets SET balance = balance - ?
                WHERE user_id = ? AND balance >= ?""")) {
            debit.setBigDecimal(1, stake);
            debit.setLong(2, userId);
            debit.setBigDecimal(3, stake);
            if (debit.executeUpdate() == 0) {          // not enough money: change nothing
                c.rollback();
                return false;
            }
        }
        try (PreparedStatement bet = c.prepareStatement("""
                INSERT INTO bets (user_id, selection_id, stake, odds_at_placement, placed_at, status)
                VALUES (?, ?, ?, ?, CURRENT_TIMESTAMP, 'OPEN')""")) {
            bet.setLong(1, userId);
            bet.setLong(2, selectionId);
            bet.setBigDecimal(3, stake);
            bet.setBigDecimal(4, odds);
            bet.executeUpdate();
        }
        try (PreparedStatement ledger = c.prepareStatement("""
                INSERT INTO wallet_transactions (user_id, amount, type, created_at)
                VALUES (?, ?, 'BET_STAKE', CURRENT_TIMESTAMP)""")) {
            ledger.setLong(1, userId);
            ledger.setBigDecimal(2, stake.negate());
            ledger.executeUpdate();
        }
        c.commit();
        return true;
    } catch (SQLException e) {
        c.rollback();
        throw e;
    }
}
```

Why it's safe:

- **Double-spend:** the conditional `UPDATE` re-checks the balance after waiting for the lock, so
  only one of two simultaneous £10 bets succeeds.
- **Atomicity:** if the bet insert fails, the debit rolls back too. No money disappears.
- **The last line of defence:** `CHECK (balance >= 0)` on `wallets` rejects any code path that gets
  this wrong.
- **Not covered here: retries.** If the client times out and resends, this code places a second
  bet. That needs an idempotency key with a unique constraint, which F8 adds.

## Lab (~10 min)

Race two "devices" against one £10 wallet, using H2 in Postgres mode. H2's locking is close enough
to show the effect, though it is not Postgres. Save as `DoubleSpendLab.java` and run
`java -cp <path-to>/h2-2.3.232.jar DoubleSpendLab.java`.

```java
import java.math.BigDecimal;
import java.sql.*;
import java.util.concurrent.*;

public class DoubleSpendLab {
    static final String URL = "jdbc:h2:mem:wallet;MODE=PostgreSQL;DB_CLOSE_DELAY=-1;LOCK_TIMEOUT=5000";
    static final BigDecimal STAKE = new BigDecimal("10.00");

    interface Strategy { boolean placeBet(Connection c, CyclicBarrier together) throws Exception; }

    public static void main(String[] args) throws Exception {
        try (Connection c = DriverManager.getConnection(URL); Statement s = c.createStatement()) {
            s.execute("""
                CREATE TABLE wallets (user_id BIGINT PRIMARY KEY,
                  balance NUMERIC(12,2) NOT NULL CHECK (balance >= 0))""");
            s.execute("""
                CREATE TABLE bets (id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
                  user_id BIGINT NOT NULL, stake NUMERIC(12,2) NOT NULL)""");
        }
        race("A. read, check in Java, write new balance", DoubleSpendLab::readCheckWrite);
        race("B. one conditional UPDATE", DoubleSpendLab::conditionalUpdate);
        race("C. SELECT ... FOR UPDATE first", DoubleSpendLab::selectForUpdate);
    }

    // Two devices place a 10.00 bet at the same moment on a wallet holding exactly 10.00.
    static void race(String label, Strategy strategy) throws Exception {
        try (Connection c = DriverManager.getConnection(URL); Statement s = c.createStatement()) {
            s.execute("DELETE FROM bets");
            s.execute("DELETE FROM wallets");
            s.execute("INSERT INTO wallets VALUES (42, 10.00)");
        }
        CyclicBarrier together = new CyclicBarrier(2);
        Callable<Boolean> device = () -> {
            try (Connection c = DriverManager.getConnection(URL)) {
                c.setAutoCommit(false);
                boolean accepted = strategy.placeBet(c, together);
                if (accepted) c.commit(); else c.rollback();
                return accepted;
            }
        };
        try (ExecutorService pool = Executors.newFixedThreadPool(2)) {
            Future<Boolean> a = pool.submit(device), b = pool.submit(device);
            boolean ra = a.get(), rb = b.get();
            try (Connection c = DriverManager.getConnection(URL); Statement s = c.createStatement();
                 ResultSet rs = s.executeQuery("""
                     SELECT (SELECT balance FROM wallets WHERE user_id = 42),
                            (SELECT count(*) FROM bets)""")) {
                rs.next();
                System.out.printf("%-42s accepted=%s,%s  balance=%s  bets=%d%n",
                        label, ra, rb, rs.getBigDecimal(1), rs.getInt(2));
            }
        }
    }

    static boolean readCheckWrite(Connection c, CyclicBarrier together) throws Exception {
        BigDecimal balance = readBalance(c, "SELECT balance FROM wallets WHERE user_id = 42");
        together.await();                                   // both devices have now read 10.00
        if (balance.compareTo(STAKE) < 0) return false;
        setBalance(c, balance.subtract(STAKE));
        insertBet(c);
        return true;
    }

    static boolean conditionalUpdate(Connection c, CyclicBarrier together) throws Exception {
        together.await();
        try (PreparedStatement ps = c.prepareStatement(
                "UPDATE wallets SET balance = balance - ? WHERE user_id = 42 AND balance >= ?")) {
            ps.setBigDecimal(1, STAKE);
            ps.setBigDecimal(2, STAKE);
            if (ps.executeUpdate() == 0) return false;      // 0 rows: not enough money
        }
        Thread.sleep(200);                                  // keep the row lock a while
        insertBet(c);
        return true;
    }

    static boolean selectForUpdate(Connection c, CyclicBarrier together) throws Exception {
        together.await();
        BigDecimal balance = readBalance(c, "SELECT balance FROM wallets WHERE user_id = 42 FOR UPDATE");
        Thread.sleep(200);                                  // the other device waits on the lock
        if (balance.compareTo(STAKE) < 0) return false;
        setBalance(c, balance.subtract(STAKE));
        insertBet(c);
        return true;
    }

    static BigDecimal readBalance(Connection c, String sql) throws SQLException {
        try (Statement s = c.createStatement(); ResultSet rs = s.executeQuery(sql)) {
            rs.next();
            return rs.getBigDecimal(1);
        }
    }

    static void setBalance(Connection c, BigDecimal newBalance) throws SQLException {
        try (PreparedStatement ps = c.prepareStatement("UPDATE wallets SET balance = ? WHERE user_id = 42")) {
            ps.setBigDecimal(1, newBalance);
            ps.executeUpdate();
        }
    }

    static void insertBet(Connection c) throws SQLException {
        try (PreparedStatement ps = c.prepareStatement("INSERT INTO bets (user_id, stake) VALUES (42, ?)")) {
            ps.setBigDecimal(1, STAKE);
            ps.executeUpdate();
        }
    }
}
```

What you should observe (checked over several runs):

```text
A. read, check in Java, write new balance  accepted=true,true  balance=0.00  bets=2
B. one conditional UPDATE                  accepted=true,false  balance=0.00  bets=1
C. SELECT ... FOR UPDATE first             accepted=false,true  balance=0.00  bets=1
```

A is the lost update: two bets for £10. Note that the `CHECK` constraint didn't save you, because
the balance never went negative. B and C accept exactly one bet; which device wins varies.

Break it further: in A, add
`c.setTransactionIsolation(Connection.TRANSACTION_REPEATABLE_READ);` after `setAutoCommit(false)`.
One device now fails with SQLSTATE `40001`. Postgres raises the same SQLSTATE with the message
"could not serialize access due to concurrent update"; H2's message wording differs. Then add a
version column and write strategy D, optimistic locking.

## Gotchas

- **Read-modify-write in Java at read committed.** Reading a value, computing in Java and writing an
  absolute value is a lost update waiting to happen. Use `SET x = x - ?` with a guard in `WHERE`,
  `FOR UPDATE`, or a version column.
- **Assuming repeatable read stops write skew.** It doesn't, in Postgres or anywhere else using
  snapshot isolation. Lock a common parent row, or use serializable.
- **Serializable without a retry loop.** Serializable and repeatable read *will* throw `40001` under
  load. Retry the whole transaction, with a limit and backoff.
- **Inconsistent lock order.** Two code paths that lock the same rows in different orders will
  eventually deadlock. Sort the ids before locking.
- **Long or idle transactions.** They hold locks, block vacuum and cause bloat. Never make a
  network call or wait for a user while a transaction is open.
- **Ignoring the update count.** `executeUpdate()` returning 0 is the database telling you the guard
  failed. Code that ignores it accepts the bet anyway.

Typical follow-ups:

- *"Why not just make everything serializable?"* It's correct, but conflicting transactions abort
  and must retry, which costs throughput on hot rows such as a popular market. Most systems use
  read committed plus targeted locks, and serializable for a few complex invariants.
- *"Your wallet row is a hotspot. Every bet locks it."* Per user it's fine: one user rarely places
  many bets per second. A single *house* account touched by every bet is the real hotspot; split it
  into several sub-accounts or update its balance asynchronously from the ledger (F8).

## Explain it in 2 minutes

*"How would you stop a user spending the same balance twice when two bets arrive at once?"*

- Name the anomaly: a lost update caused by read-check-write across two transactions.
- Postgres's default read committed doesn't prevent it when the application computes the new value.
- Fix it with one conditional `UPDATE ... SET balance = balance - ? WHERE ... AND balance >= ?` and
  check the row count; a waiting update re-checks the condition after the lock is released.
- Or lock first with `SELECT ... FOR UPDATE`, or use a version column for low-contention cases.
- Debit, bet row and ledger row go in one transaction; `CHECK (balance >= 0)` is the backstop.
- Retries need an idempotency key; deadlocks need consistent lock ordering and retry on `40P01`.

## Check yourself

1. Which anomaly lets a daily deposit limit be exceeded by two concurrent deposits, and which
   Postgres isolation level stops it on its own?
2. Why is `UPDATE wallets SET balance = balance - 10 WHERE user_id = 42 AND balance >= 10` safe at
   read committed?
3. When would you choose optimistic locking over `SELECT ... FOR UPDATE`?
4. In MVCC, what happens to the old version of a row after an `UPDATE`, and what eventually removes
   it?
5. A Postgres database is growing fast, though the number of live rows is stable. One session has
   been `idle in transaction` for six hours. Connect the two.

### Answers

1. Write skew (it involves a phantom: each transaction inserts a row the other's sum would have
   counted). Only serializable stops it automatically. Alternatively, lock the user's wallet row
   first.
2. The update takes a row lock. A concurrent update waits, then re-evaluates the `WHERE` clause
   against the newly committed row, so it sees the reduced balance and matches 0 rows.
3. When conflicts are rare or the read and the write are far apart in time, such as a form edited
   for minutes. Under heavy contention on short operations, pessimistic locking avoids retry storms.
4. It stays in the table, marked with the updating transaction's id in `xmax`. When no snapshot can
   see it any more, vacuum (usually autovacuum) marks its space reusable.
5. The idle transaction holds an old snapshot, so vacuum can't remove dead versions newer than it.
   Dead tuples pile up as bloat. Kill the session and set `idle_in_transaction_session_timeout`.
