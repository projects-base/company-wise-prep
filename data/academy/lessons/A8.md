## Where we are

From A1 you know the JIT compiles hot code after warm-up and can delete or reshape what it
compiles; from A4 and A5 you know how to read GC behaviour and find leaks. This lesson answers the
next question: **where does the time go?** It covers the two tools for that, profilers for real
systems and benchmarks for small pieces of code, and why a hand-written timing loop usually lies.

## The problem

"The order service burns 80% CPU and p99 latency doubled after the last release." The tempting
move is to guess: "probably JSON serialisation", rewrite it, and hope. Guesses are wrong
surprisingly often, and every wrong guess costs a release cycle.

Two different questions need two different tools:

| Question | Tool |
|---|---|
| In the real running system, which code uses the CPU, allocates memory, or waits? | a **profiler** (JFR, async-profiler) |
| Is version A of this method faster than version B? | a **microbenchmark** harness (JMH) |

## Sampling: how profilers see

A **sampling profiler** interrupts the program at regular intervals (say every 10–20 ms), records
the current stack trace of each running thread, and counts. A method that appears at the top of
30% of the samples is using about 30% of the CPU.

The alternative, *instrumenting* every method with timers, adds overhead to every call and
distorts the very timings it measures. Sampling has small, fixed overhead, which is why it is safe
in production.

## Safepoint bias: why some profilers lie

Older Java profilers asked the JVM for stack traces using the standard API, which can only take
them when threads reach a **safepoint** (A4: a point where the JVM knows where all references
are). The JIT puts safepoints at method returns and loop back-edges, not everywhere. So samples
pile up at those points, and a hot tight loop can be blamed on the method that *called* it. This
is **safepoint bias**.

Both tools below avoid it: JFR and async-profiler sample threads without waiting for safepoints.

**Rule:** if a profiler's answer makes no sense, ask whether it is safepoint-biased.

## JFR: the flight recorder built into the JVM

**Java Flight Recorder (JFR)** is part of the JDK (open-sourced in Java 11). It records *events*:
method samples, allocations, GC pauses, lock contention, file and socket I/O, exceptions, thread
states. Its default settings are designed for continuous production use, with overhead around
1%.

Start it at launch:

```text
java -XX:StartFlightRecording=duration=60s,filename=rec.jfr,settings=profile -jar app.jar
```

Or attach to a running JVM, without restarting it:

```text
jcmd <pid> JFR.start name=incident settings=profile
jcmd <pid> JFR.dump  name=incident filename=incident.jfr
jcmd <pid> JFR.stop  name=incident
```

(`settings=default` is the always-on profile; `settings=profile` samples more often and records
more, with somewhat higher overhead.)

Read the file with the `jfr` command-line tool that ships with the JDK, or in **JDK Mission
Control (JMC)**, a separate free GUI:

```text
jfr summary rec.jfr                          # which events, how many
jfr view hot-methods rec.jfr                 # top methods by samples (JDK 21+)
jfr view allocation-by-class rec.jfr
jfr print --events jdk.ExecutionSample rec.jfr
```

## async-profiler

**async-profiler** is an open-source profiler for HotSpot JVMs on Linux and macOS (on Windows, use
WSL or a container). It combines the JVM's internal stack-walking with the OS's performance
counters, so it sees Java frames *and* native, JVM and kernel frames (time spent in GC threads,
JIT compilers, `memcpy`, system calls). It has several modes:

```text
asprof -d 30 -e cpu   -f cpu.html   <pid>    # where the CPU goes
asprof -d 30 -e alloc -f alloc.html <pid>    # who allocates (feeds A5 investigations)
asprof -d 30 -e lock  -f lock.html  <pid>    # where threads wait on locks
asprof -d 30 -e wall  -f wall.html  <pid>    # wall clock: includes threads blocked on I/O
```

(Older releases call the launcher `profiler.sh`.) The `.html` output is an interactive flame
graph.

**CPU vs wall clock:** a CPU profile shows only threads that are running. If requests are slow
because they *wait* (database, downstream HTTP, locks), a CPU profile looks innocent; use wall
clock mode or JFR's I/O and lock events.

## Reading a flame graph

A **flame graph** draws every sampled stack at once:

```text
 width = share of samples (NOT time order; frames are sorted alphabetically)
 ┌──────────────────────────────────────────────────────────────────────────┐
 │                         ArrayList.indexOfRange                    │ Hash │  ← top: where the
 ├──────────────────────────────────────────────────────────────────┤ Map  │    CPU actually is
 │                         ArrayList.contains                        │ .put │
 ├──────────────────────────────────────────────────────────────────┼──────┤
 │                         OrderService.dedupe                       │ ...  │
 ├──────────────────────────────────────────────────────────────────┴──────┤
 │                         OrderController.handle                          │
 ├──────────────────────────────────────────────────────────────────────────┤
 │                         Thread.run                                      │  ← bottom: roots
 └──────────────────────────────────────────────────────────────────────────┘
```

- **y-axis** is stack depth: each box's caller is the box below it.
- **x-axis** is *not* time. Width is the fraction of samples containing that frame.
- Look for **wide boxes at the top** ("plateaus"): code that is itself running, not just calling
  others. Here, almost all CPU is a linear scan inside `contains`, a hint to use a `HashSet`.
- An allocation flame graph has the same shape but width = bytes allocated.

## Why naive benchmarks lie

Now the second question: "is A faster than B?" The obvious approach is timing a loop with
`System.nanoTime()`. On the JVM it is wrong in several ways:

1. **Warm-up** (A1): the first iterations run in the interpreter or C1. Measure too early and
   you time the wrong compiler.
2. **Dead-code elimination**: if a result is never used, C2 may delete the computation entirely.
   You then measure an empty loop.
3. **Constant folding**: if inputs are constants, the JIT can compute the answer at compile time.
4. **On-stack replacement**: one giant timed loop is compiled by OSR (A1), which can optimise
   differently from normal compilation.
5. **Profile pollution**: benchmarking A then B in the same JVM means B runs with call sites
   already shaped by A's types.
6. **Noise**: GC pauses, CPU frequency scaling, other processes.

Concrete proof (dead-code elimination), from the lab below on one machine:

```text
round 5: unused   0.00 ns/op   used   9.68 ns/op
```

"Zero nanoseconds per square root" is not a fast square root; it is no square root.

## JMH: the benchmark harness that handles this

**JMH** (Java Microbenchmark Harness) is the OpenJDK project's tool for microbenchmarks. It runs
warm-up iterations before measuring, forks fresh JVMs to avoid profile pollution, and gives you
ways to defeat dead-code elimination.

Create a project from the official Maven archetype:

```text
mvn archetype:generate -DarchetypeGroupId=org.openjdk.jmh \
    -DarchetypeArtifactId=jmh-java-benchmark-archetype \
    -DgroupId=lab -DartifactId=bench -Dversion=1.0
```

```java
package lab;

import java.util.*;
import java.util.concurrent.TimeUnit;
import org.openjdk.jmh.annotations.*;
import org.openjdk.jmh.infra.Blackhole;

@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.MICROSECONDS)
@Warmup(iterations = 5, time = 1)        // 5 × 1 s warm-up, results discarded
@Measurement(iterations = 5, time = 1)   // 5 × 1 s measured
@Fork(2)                                 // 2 fresh JVMs: no profile pollution
@State(Scope.Benchmark)
public class DedupeBench {
    @Param({"1000", "10000"})
    int size;
    int[] ids;

    @Setup
    public void setup() {                // not measured; inputs are not constants
        ids = new Random(42).ints(size, 0, size / 2).toArray();
    }

    @Benchmark
    public int withList() {              // returning the result keeps it "used"
        List<Integer> seen = new ArrayList<>();
        for (int id : ids) if (!seen.contains(id)) seen.add(id);
        return seen.size();
    }

    @Benchmark
    public void withSet(Blackhole bh) {  // or hand it to a Blackhole explicitly
        Set<Integer> seen = new HashSet<>();
        for (int id : ids) seen.add(id);
        bh.consume(seen.size());
    }
}
```

Build with `mvn clean verify`, run with `java -jar target/benchmarks.jar`. Read the `Score` *and*
the `Error` column: if two results' error ranges overlap, you have not shown a difference. Add
`-prof gc` to also report allocation per operation.

**Rule:** profile the real system to find *where*; use JMH to compare *alternatives* for that
spot; then confirm the improvement in the real system again.

## Lab (~10 min)

**Part 1: watch a naive benchmark lie.** Save as `NaiveBench.java` and run `java NaiveBench.java`:

```java
public class NaiveBench {
    static double x = 42.0;
    static double sink;                        // poor man's Blackhole

    static long timeUnused(int n) {
        long t = System.nanoTime();
        for (int i = 0; i < n; i++) {
            Math.sqrt(x + i);                  // result thrown away: the JIT may delete this
        }
        return System.nanoTime() - t;
    }

    static long timeUsed(int n) {
        long t = System.nanoTime();
        double acc = 0;
        for (int i = 0; i < n; i++) {
            acc += Math.sqrt(x + i);           // result is consumed
        }
        sink = acc;
        return System.nanoTime() - t;
    }

    public static void main(String[] args) {
        int n = 10_000_000;
        for (int round = 1; round <= 5; round++) {
            System.out.printf("round %d: unused %6.2f ns/op   used %6.2f ns/op%n",
                    round, timeUnused(n) / (double) n, timeUsed(n) / (double) n);
        }
        System.out.println(sink);
    }
}
```

Expect "unused" to fall towards 0.00 ns/op after the first round or two: dead-code elimination.

**Part 2: profile with JFR.** Save as `Hot.java`, then `javac Hot.java` and run
`java -XX:StartFlightRecording=filename=rec.jfr,settings=profile Hot` (about 20 seconds):

```java
import java.util.ArrayList;
import java.util.HashSet;
import java.util.List;
import java.util.Set;

public class Hot {
    static int dedupeWithList(int[] ids) {
        List<Integer> seen = new ArrayList<>();
        for (int id : ids) {
            if (!seen.contains(id)) seen.add(id);     // O(n) scan per element: the hot spot
        }
        return seen.size();
    }

    static int dedupeWithSet(int[] ids) {
        Set<Integer> seen = new HashSet<>();
        for (int id : ids) seen.add(id);              // O(1) average per element
        return seen.size();
    }

    public static void main(String[] args) {
        int[] ids = new java.util.Random(42).ints(20_000, 0, 10_000).toArray();
        long end = System.currentTimeMillis() + 20_000;   // run for about 20 s
        long total = 0;
        while (System.currentTimeMillis() < end) {
            total += dedupeWithList(ids);
            total += dedupeWithSet(ids);
        }
        System.out.println(total);
    }
}
```

Then `jfr view hot-methods rec.jfr`. On one machine, `ArrayList.indexOfRange` (the scan inside
`contains`) took about 97% of samples and `HashMap.putVal` about 1%. Same input, same result, very
different cost. On Linux/macOS, repeat with async-profiler (`asprof -d 15 -e cpu -f cpu.html
<pid>`) and open the flame graph.

## Gotchas

- **Never trust a `nanoTime` loop** for small code. Warm-up, dead-code elimination and constant
  folding make the numbers meaningless; use JMH.
- **Always use benchmark results.** Return them or pass them to a `Blackhole`.
- **A CPU profile can't see waiting.** Slow-but-idle services need wall-clock profiling or JFR
  lock/I/O events.
- **The flame graph x-axis is not time.** Don't read left-to-right as a timeline.
- **Microbenchmark wins may not survive production**, where caches, data sizes and concurrency
  differ. Confirm with a production profile or load test.
- **Profilers have overhead and access needs.** async-profiler may need kernel settings
  (`perf_event_paranoid`) in containers; JFR's `profile` settings cost more than `default`.

## Explain it in 2 minutes

Prompt: "How do you find and fix a performance problem in a JVM service?"

- Separate the questions: *where* (profile the real system) vs *which alternative is faster*
  (benchmark).
- Sampling profilers have low, fixed overhead; avoid safepoint-biased ones.
- JFR: built in, production-safe, rich events; start at launch or with `jcmd JFR.start`.
- async-profiler: CPU/alloc/lock/wall modes, sees native and kernel frames, flame graph output.
- Flame graphs: width = share of samples, look for wide top frames.
- JMH avoids warm-up, dead-code elimination, constant folding and profile pollution; always
  verify gains in production.

## Check yourself

1. What is safepoint bias, and which tools in this lesson avoid it?
2. On a flame graph, what does the width of a box mean? What does the x-axis order mean?
3. A naive benchmark reports 0.00 ns/op. What is the likely cause, and the JMH fix?
4. A service is slow but CPU is at 10%. Which kind of profile do you take?
5. Why does JMH fork new JVMs for each benchmark?

### Answers

1. Sampling only at safepoints, which misattributes time to safepoint locations. JFR and
   async-profiler avoid it.
2. Width is the share of samples containing that frame. The horizontal order is alphabetical, not
   time.
3. Dead-code elimination: the result was unused, so the JIT removed the work. Return the result
   or use `Blackhole.consume`.
4. Wall-clock (async-profiler `-e wall`) or JFR's I/O and lock events: the time is spent
   waiting, not computing.
5. To isolate each benchmark's JIT profile and heap state (no profile pollution between
   benchmarks).
