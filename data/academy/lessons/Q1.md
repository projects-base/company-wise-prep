## Where we are

You know Java, and you have used a database through Spring Data or JPA. You may never have written
SQL by hand. This lesson starts from zero: what a table is, how to read rows from it, and how to
combine tables with joins. Every later lesson in this track uses the betting schema you build here.

## The problem

In the SQL round the interviewer shares an editor with a few tables in it and says: "Show me every
punter who has never placed a bet." There is no IDE and no ORM. You get a blank editor and about five
minutes.

To answer, you need three things: to know how the tables connect, to pick the right kind of join,
and to know where `NULL` will trip you up. That is this lesson.

## Tables, rows and columns

A **relational database** stores data in **tables**. A table is a grid. Each **row** is one thing
(one user, one bet), and each **column** is one fact about it, with a fixed type.

```text
users
+----+-------+---------+---------------------+
| id | name  | country | created_at          |
+----+-------+---------+---------------------+
|  1 | Asha  | GB      | 2026-07-01 09:00:00 |
|  2 | Ben   | AU      | 2026-07-03 11:30:00 |
+----+-------+---------+---------------------+
```

The rule: **one table per kind of thing, one row per instance, one column per fact.** A bet does not
copy the user's name. It stores the user's `id` and looks the name up when needed. Storing each fact
once means it can't get out of sync.

**SQL** (Structured Query Language) is the language for asking questions of these tables. You say
*what* you want, and the database decides *how* to fetch it.

## Keys: how tables point at each other

A **primary key** is a column whose value is unique and never `NULL` in its table, so it names
exactly one row. Here, every table's primary key is `id`.

A **foreign key** is a column that holds another table's primary key. `bets.user_id` holds a
`users.id`. The database rejects a bet whose `user_id` doesn't exist in `users`.

```text
sports ──< events ──< markets ──< selections ──< bets >── users
                                                           │
                                       wallet_transactions >┘
   A ──< B  means "one A has many B"; B holds A's id as a foreign key
```

The betting words, briefly. An **event** is a fixture, such as "Arsenal v Chelsea". A **market** is
one question about that event, such as "Match Result". A **selection** is one possible answer,
such as "Arsenal", with decimal **odds** such as 2.10. A **bet** puts a **stake** (the money risked)
on one selection. If the bet wins, the **payout** is stake × odds. While the event hasn't finished,
the bet is `OPEN`, and its `settled_at` and `payout` are empty.

## SELECT, WHERE, ORDER BY, LIMIT

The smallest useful query: take rows from a table (`FROM`), keep some (`WHERE`), pick columns
(`SELECT`), sort them (`ORDER BY`) and cut the list (`LIMIT`).

```sql
SELECT id, user_id, stake, status
FROM bets
WHERE status = 'WON' AND stake >= 30
ORDER BY stake DESC, id;
```

| id | user_id | stake | status |
|---|---|---|---|
| 14 | 3 | 100.00 | WON |
| 19 | 5 | 100.00 | WON |
| 12 | 3 | 50.00 | WON |
| 13 | 3 | 50.00 | WON |
| 10 | 2 | 40.00 | WON |
| 5 | 1 | 30.00 | WON |

Strings use single quotes. `ORDER BY stake DESC, id` sorts by stake, highest first, and breaks ties
by `id`. **Without `ORDER BY`, row order is not guaranteed.** The database may return rows in any
order, and that order can change between runs.

```sql
SELECT id, name, odds FROM selections ORDER BY odds DESC LIMIT 3;
```

| id | name | odds |
|---|---|---|
| 11 | Riverbend | 9.00 |
| 10 | Kingsford | 6.00 |
| 7 | Spurs | 4.20 |

## INNER JOIN: rows that match on both sides

A bet row says `user_id = 2`. To show the name "Ben" you need the `users` table too. A **join**
combines rows from two tables wherever a condition holds. The plain `JOIN` (short for
`INNER JOIN`) keeps only the pairs that match.

```sql
SELECT b.id AS bet_id, u.name, b.stake, b.status
FROM bets b
JOIN users u ON u.id = b.user_id
WHERE b.status = 'OPEN'
ORDER BY b.id;
```

| bet_id | name | stake | status |
|---|---|---|---|
| 6 | Asha | 10.00 | OPEN |
| 11 | Ben | 25.00 | OPEN |
| 15 | Chloe | 20.00 | OPEN |
| 20 | Ella | 15.00 | OPEN |

`b` and `u` are **aliases**, short names for the tables. `ON` gives the matching rule. A useful
mental model is a nested loop: for each bet, find the users whose `id` equals the bet's `user_id`,
and output one combined row per match. The model breaks down on speed, because the database may use
a hash table or an index instead of looping. The result is the same.

## Joining a chain of tables

To learn which sport a bet was on, walk the foreign keys: bet → selection → market → event → sport.
Each `JOIN` adds one hop.

```sql
SELECT b.id AS bet_id, u.name AS punter, sp.name AS sport, e.name AS event,
       m.name AS market, s.name AS selection, b.stake
FROM bets b
JOIN users u       ON u.id = b.user_id
JOIN selections s  ON s.id = b.selection_id
JOIN markets m     ON m.id = s.market_id
JOIN events e      ON e.id = m.event_id
JOIN sports sp     ON sp.id = e.sport_id
WHERE u.name = 'Asha'
ORDER BY b.placed_at;
```

| bet_id | punter | sport | event | market | selection | stake |
|---|---|---|---|---|---|---|
| 1 | Asha | Football | Arsenal v Chelsea | Match Result | Arsenal | 20.00 |
| 2 | Asha | Football | Arsenal v Chelsea | Total Goals 2.5 | Over 2.5 | 10.00 |
| 4 | Asha | Tennis | Alcaraz v Sinner | Match Winner | Alcaraz | 25.00 |
| 3 | Asha | Football | Liverpool v Spurs | Match Result | Spurs | 15.00 |
| 5 | Asha | Football | Liverpool v Spurs | Match Result | Liverpool | 30.00 |
| 6 | Asha | Horse Racing | Melbourne Cup | Race Winner | Kingsford | 10.00 |

The general rule: **draw the path of foreign keys first, then write one `JOIN … ON child.fk =
parent.id` per arrow.** Most join bugs are a wrong or missing `ON` condition.

## LEFT JOIN: keep every row on the left

List every sport with its events. With an inner join, Cricket vanishes, because it has no events to
match. A **LEFT JOIN** keeps every row from the left table. Where nothing matches, the right-hand
columns are filled with `NULL`, a marker that means "no value".

```sql
SELECT sp.name AS sport, e.name AS event
FROM sports sp
LEFT JOIN events e ON e.sport_id = sp.id
ORDER BY sp.id, e.id;
```

| sport | event |
|---|---|
| Football | Arsenal v Chelsea |
| Football | Liverpool v Spurs |
| Football | Leeds v Everton |
| Tennis | Alcaraz v Sinner |
| Horse Racing | Melbourne Cup |
| Cricket | NULL |

Use a LEFT JOIN whenever the question says "every X, with its Y, if any".

## RIGHT and FULL JOIN

A **RIGHT JOIN** is the mirror image: it keeps every row of the right-hand table. `markets m RIGHT
JOIN events e` gives the same rows as `events e LEFT JOIN markets m`. Most people always write LEFT
JOIN and put the "keep everything" table first, because it reads more easily.

```sql
SELECT e.name AS event, m.name AS market
FROM markets m
RIGHT JOIN events e ON e.id = m.event_id
ORDER BY e.id, m.id;
```

| event | market |
|---|---|
| Arsenal v Chelsea | Match Result |
| Arsenal v Chelsea | Total Goals 2.5 |
| Liverpool v Spurs | Match Result |
| Alcaraz v Sinner | Match Winner |
| Melbourne Cup | Race Winner |
| Leeds v Everton | NULL |

A **FULL JOIN** (or `FULL OUTER JOIN`) keeps unmatched rows from both sides. It is rare in practice.
It is useful for reconciliation, such as "our ledger versus the payment provider's file: show what's
missing on either side". PostgreSQL supports it. **H2 2.3 does not.** In our run it failed with a
syntax error. The portable workaround is a LEFT JOIN plus the right-side rows that have no match,
glued together with `UNION ALL`, which stacks two results with the same columns:

```sql
SELECT u.name, w.type, w.amount
FROM users u
LEFT JOIN wallet_transactions w ON w.user_id = u.id AND w.type = 'WITHDRAWAL'
WHERE u.country = 'AU'
UNION ALL
SELECT NULL, w.type, w.amount
FROM wallet_transactions w
WHERE w.type = 'WITHDRAWAL'
  AND NOT EXISTS (SELECT 1 FROM users u WHERE u.id = w.user_id AND u.country = 'AU');
```

| name | type | amount |
|---|---|---|
| Ben | WITHDRAWAL | -150.00 |
| Ella | NULL | NULL |
| NULL | WITHDRAWAL | -50.00 |

That is "Australian users and their withdrawals, plus withdrawals by anyone else". (`NOT EXISTS` is
explained two sections down.)

## Self-join: a table joined to itself

"Which users share a country?" Both sides of the pair come from `users`. Give the same table two
aliases, and it behaves like two tables.

```sql
SELECT a.name AS user_a, b.name AS user_b, a.country
FROM users a
JOIN users b ON b.country = a.country AND a.id < b.id
ORDER BY a.id, b.id;
```

| user_a | user_b | country |
|---|---|---|
| Asha | Dev | GB |
| Asha | Gita | GB |
| Ben | Ella | AU |
| Dev | Gita | GB |

`a.id < b.id` does two jobs. It stops a user pairing with themself, and it stops each pair appearing
twice (Asha–Dev and Dev–Asha). Self-joins are also how you compare a row with "another row of the
same kind": two bets by the same user, or an employee and their manager (LeetCode 181).

## Anti-join: rows with no match

Back to the opening question: users who have never bet. You want the rows of `users` that have
**no** matching row in `bets`. This is called an **anti-join**. There are two standard ways to write
it.

**`NOT EXISTS`.** A **subquery** is a query inside another query. `EXISTS (subquery)` is true if the
subquery returns at least one row. Here the subquery refers to `u` from the outer query, so it is
checked once per user.

```sql
SELECT u.id, u.name
FROM users u
WHERE NOT EXISTS (SELECT 1 FROM bets b WHERE b.user_id = u.id)
ORDER BY u.id;
```

| id | name |
|---|---|
| 6 | Finn |
| 7 | Gita |

`SELECT 1` is a convention. `EXISTS` only checks whether a row exists, so what you select doesn't
matter.

**`LEFT JOIN … IS NULL`.** Left-join the bets. Users with no bets get a row whose bet columns are all
`NULL`, so keep just those rows.

```sql
SELECT u.id, u.name
FROM users u
LEFT JOIN bets b ON b.user_id = u.id
WHERE b.id IS NULL
ORDER BY u.id;
```

Same result: Finn and Gita. Test a column that can never be `NULL` in a real row, such as the
primary key. `EXISTS` without the `NOT` is a **semi-join**: "users who have at least one open bet",
with each user listed once, however many bets match. A plain join would repeat the user once per
matching bet.

Prefer `NOT EXISTS`. It says what you mean, it is safe with `NULL`s (see below), and PostgreSQL
plans both forms the same way.

## NULL: the three-valued trap

`NULL` means "unknown or missing". It is not zero and not an empty string. Any comparison with
`NULL` gives **unknown**, not true or false. `WHERE` keeps only rows where the condition is true, so
unknown rows silently disappear. This is called **three-valued logic**: true, false and unknown.

**Trap 1: `= NULL` never matches.**

```sql
SELECT name FROM users WHERE country = NULL;
```

| name |
|---|

Zero rows, and no error. Write `IS NULL` or `IS NOT NULL` instead:

```sql
SELECT name FROM users WHERE country IS NULL;
```

| name |
|---|
| Finn |

**Trap 2: `<>` drops the NULLs.** "Users not from GB" seems to mean everyone except the GB users:

```sql
SELECT name, country FROM users WHERE country <> 'GB' ORDER BY id;
```

| name | country |
|---|---|
| Ben | AU |
| Chloe | IE |
| Ella | AU |

Finn is missing, because `NULL <> 'GB'` is unknown. If you want him, add `OR country IS NULL`.

**Trap 3: `NOT IN` with a NULL in the list returns nothing.**

```sql
SELECT name FROM users WHERE country NOT IN ('GB', NULL);
```

| name |
|---|

`x NOT IN (a, b)` means `x <> a AND x <> b`. The `x <> NULL` part is unknown for every row, so no
row is ever true. The same happens when the list comes from a subquery that returns a `NULL`. This is
the main reason to prefer `NOT EXISTS` for anti-joins.

**Trap 4: arithmetic with NULL is NULL.** `payout - stake` for an open bet is `NULL`, not
`-stake`:

```sql
SELECT id, stake, payout, payout - stake AS profit
FROM bets WHERE user_id = 1 ORDER BY id;
```

| id | stake | payout | profit |
|---|---|---|---|
| 1 | 20.00 | 42.00 | 22.00 |
| 2 | 10.00 | 19.00 | 9.00 |
| 3 | 15.00 | 0.00 | -15.00 |
| 4 | 25.00 | 0.00 | -25.00 |
| 5 | 30.00 | 54.00 | 24.00 |
| 6 | 10.00 | NULL | NULL |

`COALESCE(a, b)` returns the first argument that isn't `NULL`. `COALESCE(country, '??')` shows
`??` for Finn.

**Trap 5: filtering a LEFT JOIN in `WHERE` turns it back into an inner join.** "Every user, with
their open bet if any":

```sql
SELECT u.name, b.id AS open_bet
FROM users u
LEFT JOIN bets b ON b.user_id = u.id
WHERE b.status = 'OPEN'
ORDER BY u.id;
```

| name | open_bet |
|---|---|
| Asha | 6 |
| Ben | 11 |
| Chloe | 15 |
| Ella | 20 |

Dev, Finn and Gita are gone. Their joined rows have `b.status = NULL`, and the `WHERE` drops them.
Move the condition into `ON`, so it limits which bets match but never removes users:

```sql
SELECT u.name, b.id AS open_bet
FROM users u
LEFT JOIN bets b ON b.user_id = u.id AND b.status = 'OPEN'
ORDER BY u.id;
```

| name | open_bet |
|---|---|
| Asha | 6 |
| Ben | 11 |
| Chloe | 15 |
| Dev | NULL |
| Ella | 20 |
| Finn | NULL |
| Gita | NULL |

**Trap 6: where NULLs sort.** PostgreSQL puts `NULL`s **last** in `ORDER BY country`. H2, even in
PostgreSQL mode, put Finn **first** in our run. If the position matters, say so with
`ORDER BY country NULLS LAST`. Both engines accept that.

## Gotchas

- **`= NULL` is never true.** Use `IS NULL`. The query runs without error and quietly returns
  nothing, which makes this easy to miss.
- **`NOT IN (subquery)` returns zero rows if the subquery yields a single NULL.** Default to
  `NOT EXISTS` for "X with no Y".
- **A `WHERE` condition on the right-hand table of a LEFT JOIN undoes the LEFT.** Put conditions about
  the optional table in `ON`.
- **No `ORDER BY` means no order.** A result that looks sorted in testing can come back in a
  different order under load or after a plan change. Always sort, and add a tie-breaker such as `id`.
- **FULL JOIN is not portable.** PostgreSQL has it and H2 2.3 does not. Emulate it with a LEFT JOIN,
  `UNION ALL`, and an anti-join for the right-side leftovers.
- **NULL sort position differs between engines.** Write `NULLS FIRST` or `NULLS LAST` when it matters.

## In interviews

SQL rounds open with joins. Typical prompts, with the classic LeetCode Database versions:

- "Every customer with their address, even if they have none." That is a LEFT JOIN (LeetCode 175,
  Combine Two Tables).
- "Customers who never ordered." An anti-join (LeetCode 183). Write `NOT EXISTS` and *say why* you
  didn't use `NOT IN`.
- "Employees earning more than their manager." A self-join (LeetCode 181).

The bank question [SQL injection prevention](#/q/sql-injection-prevention) is the other side of
writing SQL by hand. Never build these queries by gluing strings together in Java. Use bind
parameters.

**Typical follow-up:** "What happens to users with no bets in your query?" A strong answer names the
join type, says those users are dropped (INNER) or kept with NULLs (LEFT), and fixes it if needed.

**Another follow-up:** "`NOT IN` or `NOT EXISTS`?" Say that `NOT EXISTS` is correct even when NULLs
are present, `NOT IN` returns nothing if the subquery yields a NULL, and modern planners turn
`NOT EXISTS` into an efficient anti-join.

## Explain it in 2 minutes

*"Explain the different joins, and how you'd find rows in one table with no match in another."*

1. INNER JOIN keeps only matching pairs. A row with no partner disappears.
2. LEFT JOIN keeps every left row and fills the missing right side with NULLs. RIGHT JOIN is the
   mirror. FULL JOIN keeps unmatched rows from both sides.
3. A self-join gives one table two aliases, to compare rows of the same kind. Use `a.id < b.id` to
   avoid self-pairs and doubled pairs.
4. Anti-join: `NOT EXISTS` (preferred) or `LEFT JOIN … WHERE right.pk IS NULL`.
5. NULL is unknown. `= NULL` and `<> x` silently drop rows, and `NOT IN` with a NULL returns nothing.
6. Conditions on the optional side of a LEFT JOIN belong in `ON`, not `WHERE`.

## Check yourself

1. `bets` has 20 rows and `users` has 7. How many rows does `users LEFT JOIN bets ON …` return, and
   why?
2. Why does `WHERE country <> 'GB'` not return Finn?
3. Rewrite "sports with no events" as both an anti-join with `NOT EXISTS` and a `LEFT JOIN … IS NULL`.
4. In a `LEFT JOIN … WHERE b.id IS NULL` anti-join, why test the primary key rather than, say,
   `b.payout`?
5. What does `a.id < b.id` do in a self-join?

### Answers

1. 22. Each of the 20 bets matches exactly one user (20 rows). Finn and Gita have no bets, so each
   adds one row of NULL bet columns.
2. `NULL <> 'GB'` is unknown, not true, and `WHERE` keeps only true rows. Add `OR country IS NULL`.
3. `SELECT sp.name FROM sports sp WHERE NOT EXISTS (SELECT 1 FROM events e WHERE e.sport_id =
   sp.id);` and `SELECT sp.name FROM sports sp LEFT JOIN events e ON e.sport_id = sp.id WHERE e.id IS
   NULL;`. Both return Cricket.
4. `payout` is NULL on real rows too (open bets), so you'd wrongly keep users who have open bets. A
   primary key is NULL only when there was no match.
5. It stops a row pairing with itself and stops each pair appearing twice in mirrored order.

```sql
-- 1
SELECT s.name AS selection, m.name AS market, s.odds
FROM selections s
JOIN markets m ON m.id = s.market_id
JOIN events e  ON e.id = m.event_id
WHERE e.name = 'Arsenal v Chelsea'
ORDER BY s.odds;
```

```sql
-- 2
SELECT u.name AS punter, s.name AS selection, b.stake, b.status
FROM bets b
JOIN users u      ON u.id = b.user_id
JOIN selections s ON s.id = b.selection_id
JOIN markets m    ON m.id = s.market_id
JOIN events e     ON e.id = m.event_id
JOIN sports sp    ON sp.id = e.sport_id
WHERE sp.name = 'Tennis'
ORDER BY b.id;
```

```sql
-- 3
SELECT e.name
FROM events e
WHERE NOT EXISTS (
  SELECT 1
  FROM markets m
  JOIN selections s ON s.market_id = m.id
  JOIN bets b       ON b.selection_id = s.id
  WHERE m.event_id = e.id)
ORDER BY e.id;
```

```sql
-- 4
SELECT b1.user_id, b1.id AS bet_a, s1.name AS selection_a, b2.id AS bet_b, s2.name AS selection_b
FROM bets b1
JOIN selections s1 ON s1.id = b1.selection_id
JOIN bets b2       ON b2.user_id = b1.user_id AND b2.id > b1.id
JOIN selections s2 ON s2.id = b2.selection_id
WHERE s1.market_id = s2.market_id
  AND s1.id <> s2.id;
```

```sql
-- 5
SELECT name, country FROM users
WHERE country <> 'GB' OR country IS NULL
ORDER BY id;
```
