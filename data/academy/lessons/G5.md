## Where we are

From G2 you can make a model call, get structured output, and run the tool-use loop (the model asks, your code executes, the result goes back). This lesson is about **orchestration**: how to combine many calls into a system. There are three shapes, a single call, a fixed workflow and an agent, and choosing the right one is the most important design decision in an LLM feature.

## The problem

"Prepare me for Microsoft" is not one prompt. Someone has to find interview reports on the web, pull out questions, check them against the existing bank, and build a study plan. You could:

- (a) write one giant prompt and hope,
- (b) write code that runs fixed steps, some of them LLM calls, or
- (c) give the model tools and let it decide what to do next until it says it is done.

These differ a lot in cost, latency, debuggability and failure modes. Interviewers ask "design an agentic workflow" precisely to see whether you can tell the three apart and say *why* you picked one.

## Shape 1: the single call

One prompt, one response, optionally with structured output. Classification, extraction, summarisation and rewriting live here.

```text
input ──► [LLM] ──► output
```

- Cheapest, fastest, easiest to test.
- Fails when the task needs several distinct skills, information gathered along the way, or more context than you can sensibly send at once.

The rule: **start here.** Most "AI features" are a single well-designed call plus validation.

## Shape 2: the fixed workflow (a DAG of LLM steps)

A **workflow** is a pipeline whose steps and order are decided *by your code*. Some steps call an LLM, others are plain code. Drawn out, it is usually a **DAG** (directed acyclic graph): steps are nodes, arrows mean "this output feeds that step", and there are no cycles. It is the same idea as a build pipeline or an Airflow job.

This app's research pipeline (docs/ARCHITECTURE.md §3) is a real one:

```text
          ┌──────────────┐   ┌──────────────┐   ┌───────────────┐   ┌──────────┐   ┌──────────┐
company ─►│ 1 RESEARCH   │──►│ 2 EXTRACT    │──►│ 3 DEDUPE      │──►│ 4 REVIEW │──►│ 5 PLAN   │
          │ LLM + web    │   │ LLM + schema │   │ SQL trigram + │   │ human    │   │ code +   │
          │ search/fetch │   │ → drafts[]   │   │ LLM "same?"   │   │ queue    │   │ LLM text │
          └──────────────┘   └──────────────┘   └───────────────┘   └──────────┘   └──────────┘
             free text +        structured        per-draft,           drafts stay    scheduler is
             citations          questions         can fan out          `claimed`      deterministic
```

Notice the design choices:

- **Each LLM step does one job.** Research produces cited free text; extraction turns it into a schema. They are separate partly because the API rejects citations and schema-constrained output in the same request, and partly because two focused steps are easier to test than one big one.
- **Code does what code is good at.** Candidate matching uses a Postgres trigram index (`pg_trgm`), and the study scheduler is deterministic rules. The LLM only judges "is this the same question?" and writes the narrative.
- **A human checkpoint.** Nothing becomes `verified` without Akhil.
- **Fan-out and fan-in.** The dedupe step can run once per draft question *in parallel*, then join.

Common workflow patterns: **chaining** (A → B → C), **routing** (a cheap classifier picks which branch to run), **parallelisation** (fan out over items, or run several attempts and vote), and **evaluator–optimiser** (one step drafts, another critiques against a rubric, repeated a bounded number of times).

Why workflows win when the steps are known: predictable cost, testable steps, retry and resume per step, and clear logs of which step failed.

## Shape 3: the agent loop

An **agent** is a loop in which the *model* chooses the next action: which tool to call, with what arguments, and when to stop. Your code just executes and reports back.

```text
            ┌───────────────────────────────────────────┐
            ▼                                           │
 goal ──► [LLM decides] ──tool_use──► [your code runs tool] ──result──┘
              │
              └── end_turn ──► final answer
```

This is exactly the G2 tool loop, run until the model stops asking for tools.

Analogy: a workflow is a recipe card; an agent is a cook with a goal and a stocked kitchen. Where it breaks: a cook has common sense about when to stop and what not to touch. An agent only has what you put in its prompt, its tools and your limits.

Agents earn their cost when the path **can't be known in advance**: debugging an unfamiliar codebase, open-ended research where each finding decides the next search, multi-step tasks over a large, changing tool set.

## The trade-offs, side by side

```text
                    single call     workflow (DAG)          agent loop
who picks steps     —               your code               the model
cost                1 call          known, sum of steps     variable; can balloon
latency             lowest          predictable; parallel   unpredictable
reliability         high            high per step           compounding errors
debuggability       easy            per-step logs           trace a whole trajectory
flexibility         none            branches you wrote      handles the unforeseen
```

**Compounding errors** is the key reliability idea. If each step is right 95% of the time and a run takes 10 dependent steps, the run as a whole is right much less often than 95%. Agents take more steps, and each step's context contains the earlier steps' mistakes.

The rule: **use the simplest shape that solves the task.** Single call, then a workflow, then an agent. A good architecture often *mixes* them: a workflow whose one open-ended step is a small, bounded agent.

## Making agents safe to run

If you do build an agent, put the guardrails in code, not in hope:

- **Step limit and budget:** a maximum number of iterations and a token or dollar cap. Stop and report when either is hit.
- **Least-privilege tools:** read-only by default; writes need explicit approval (a human, or a policy check).
- **Validate every tool call:** schema-check the arguments and authorise the action in your code.
- **Log the trajectory:** every model turn, tool call, result and `usage`, so a bad run can be replayed and understood.
- **Clear stopping criteria** in the prompt ("stop when you have 3 sources that agree"), plus a check in code that the final output is valid.
- **Manage context:** long loops fill the context window. Trim or summarise old tool results.

Anthropic's own guidance points the same way: try single calls and workflows first, and use an agent only when the task is complex and hard to specify in advance, worth the extra cost, within the model's ability, and when errors can be caught and recovered from.

## Lab (~10 min)

Part A: run a DAG with a parallel fan-out on virtual threads. Part B: run an agent loop with a step limit. The "LLM steps" are stubs with `sleep`, so no API key is needed.

```java
import java.util.*;
import java.util.concurrent.*;

public class OrchestrationLab {

    // ---------- Part A: fixed workflow (DAG) ----------
    static String research(String company) { sleep(300); return "dossier:" + company; }
    static List<String> extract(String dossier) { sleep(200); return List.of("lru-cache", "design-rate-limiter", "new-question-x"); }
    static String dedupe(String draft) {
        sleep(150);
        return draft.startsWith("new-") ? draft + " -> NEW" : draft + " -> add sighting";
    }
    static String plan(List<String> decided) { return "plan over " + decided; }

    static void runWorkflow() {
        long start = System.currentTimeMillis();
        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            String dossier = research("microsoft");                          // step 1
            List<String> drafts = extract(dossier);                          // step 2
            List<CompletableFuture<String>> futures = drafts.stream()        // step 3: fan out
                .map(d -> CompletableFuture.supplyAsync(() -> dedupe(d), pool))
                .toList();
            List<String> decided = futures.stream().map(CompletableFuture::join).toList(); // fan in
            System.out.println(plan(decided));                               // step 5
        }
        System.out.println("workflow ms: " + (System.currentTimeMillis() - start));
    }

    // ---------- Part B: agent loop ----------
    sealed interface Action {}
    record CallTool(String tool, String arg) implements Action {}
    record Finish(String answer) implements Action {}

    /** Stand-in for the LLM: decides the next action from what it has observed so far. */
    static Action fakeModel(String goal, List<String> observations) {
        if (observations.isEmpty()) return new CallTool("search_questions", "caching microsoft");
        if (observations.size() == 1) return new CallTool("get_question", "lru-cache");
        return new Finish("Practise lru-cache first; it was asked at Microsoft.");
    }

    static String runTool(String tool, String arg) {
        return switch (tool) {
            case "search_questions" -> "[lru-cache, design-distributed-cache]";
            case "get_question" -> "LRU Cache: HashMap + doubly linked list ...";
            default -> "ERROR: unknown tool " + tool;
        };
    }

    static void runAgent(int maxSteps) {
        List<String> observations = new ArrayList<>();
        for (int step = 1; step <= maxSteps; step++) {
            Action action = fakeModel("what to study for caching", observations);
            switch (action) {
                case Finish f -> {
                    System.out.println("agent done in " + step + " steps: " + f.answer());
                    return;
                }
                case CallTool c -> {
                    String result = runTool(c.tool(), c.arg());
                    System.out.println("step " + step + ": " + c.tool() + "(" + c.arg() + ") -> " + result);
                    observations.add(result);
                }
            }
        }
        System.out.println("agent stopped: step limit " + maxSteps + " reached");
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }

    public static void main(String[] args) {
        runWorkflow();
        runAgent(5);
    }
}
```

What to observe:

- The workflow takes roughly 650–750 ms (300 + 200 + 150, plus some start-up overhead), not about 950 ms (300 + 200 + 3 × 150), because dedupe fans out in parallel.
- The agent's path is decided by `fakeModel`, not by your code. You only see it by logging each step.

**Break it:**

1. Change `fakeModel` so it never returns `Finish` (for example, it always searches again). Without `maxSteps` this would loop forever and burn tokens. With it, you get a clean "step limit reached".
2. Make `fakeModel` call a tool named `delete_question`. Your `runTool` refuses it. That is least privilege, enforced in code rather than in the prompt.

## Gotchas

- **Reaching for an agent first.** If you can draw the steps on a whiteboard, write a workflow. It is cheaper, faster and testable.
- **No step limit or budget.** A confused agent loops and burns money. Always cap iterations and tokens.
- **One giant prompt doing five jobs.** Split it into focused steps with structured outputs between them; each step becomes testable.
- **Letting the LLM do deterministic work.** Sorting, counting, scheduling and exact matching belong in code.
- **No trajectory logging.** Without per-step logs of tool calls and `usage`, you can't debug or cost an agent run.
- **Ignoring compounding errors.** Ten 95%-reliable steps make a much less reliable whole. Add validation and checkpoints between steps.

## In interviews

- [Design an Agentic Workflow](#/q/design-agentic-workflow): the core question. Open by asking about the task's shape, argue for the simplest shape that works, then show guardrails: step limits, budgets, approvals, validation, logging and evals.
- [Design a Task Scheduler (Cron/Airflow-like)](#/q/design-task-scheduler) and [Design a Distributed Job Scheduler](#/q/design-job-scheduler) cover the DAG execution side: dependencies, retries, idempotent steps, resume after failure.
- [How are AI tools helping you?](#/q/how-you-use-ai-tools): coding assistants are agents. Say how you bound them (review diffs, run tests).

Typical follow-ups:

- *"How do you make a step retry-safe?"* Make each step idempotent and keyed (by run id plus step id), store step outputs so a resumed run skips completed steps, and never repeat a side effect without a dedupe key.
- *"How do you know the agent is good?"* Use an eval set of tasks with checkable outcomes, measure success rate, cost and steps per task, and compare against a workflow baseline (G6).

## Explain it in 2 minutes

*"When would you use a single LLM call, a workflow, or an agent?"*

1. Single call for one well-defined transformation; validate the output.
2. A workflow (DAG) when the steps are known: code controls the order, cost is predictable, steps are testable, and branches can run in parallel.
3. An agent when the path depends on what is discovered along the way; the model picks the tools and when to stop.
4. Trade-offs: agents cost more, vary more, and errors compound.
5. Agent guardrails: step and budget limits, least-privilege tools, validation, approvals and trajectory logs.
6. Example: this app's research pipeline is a DAG with one human checkpoint and deterministic planning.

## Check yourself

2. Why are research and extraction separate steps in this app's pipeline?

4. Name three guardrails every agent loop should have.
5. Why do agents tend to be less reliable than workflows of a similar length?

### Answers

1. Steps are nodes and dependencies are edges, with no cycles. You can then run independent steps in parallel, retry or resume a single step, and know the run will finish.
2. The API rejects citations and schema-constrained output in the same request, and focused steps are easier to test and retry.
3. Justified: investigating an unfamiliar bug, where each finding decides the next step. Not justified: extracting fields from a posting, or a pipeline whose steps are known.
4. Any three of: a step limit, a token or dollar budget, least-privilege tools with approval for writes, argument validation, trajectory logging.
5. Errors compound across dependent steps, the model chooses the path (so it varies more), and mistakes stay in the context for later steps.
